# buildment docs — map

This folder is the full product + technical spec for **buildment**, split into small files so any
one work session (yours, or an LLM agent's) only has to load what's relevant to the task at hand,
instead of one giant document.

If you haven't already, read [`/AGENTS.md`](../AGENTS.md) first — it has the invariants that apply
regardless of which part of the doc set you're working from.

## How to use these docs

- **Starting a new build phase?** Go straight to `docs/phases/mN-*.mdx`. Each phase file names the
  topic docs it depends on — open only those, not the whole folder.
- **Shipping the demo?** Follow [`phases/demo-10-day.mdx`](phases/demo-10-day.mdx) — ten days,
  mandatory features first (progress, locking, ask-mentor). Do not start a database migration.
- **Making a product decision?** Check [`11-decisions-and-open-questions.mdx`](11-decisions-and-open-questions.mdx)
  first — it may already be resolved, or it may be explicitly listed as open with a recommendation.
- **Touching the schema?** [`08-data-model.mdx`](08-data-model.mdx) is the source of truth until
  `prisma/schema.prisma` exists, after which the schema file leads and this doc follows.
- **Adding or changing a block type?** [`03-blocks-registry.mdx`](03-blocks-registry.mdx) has the
  registry pattern and all six block specs — this is the single most-referenced doc in the set.

Roughly 8 focused weeks for one developer, one milestone at a time. M1, M2, and M5 carry the most
implementation risk; M0, M6, M7 are predictable.

## Keeping these docs honest

These files are meant to be edited as the project evolves, not treated as immutable history:

- When you resolve an open question, move it from "open" to the decision table in
  `11-decisions-and-open-questions.mdx` in the same change that implements it.
- When architecture changes (a library swap, a new constraint discovered mid-build), update
  `07-architecture.mdx` and/or `08-data-model.mdx` — don't let the docs and the code diverge.
- If a phase's scope changes, edit that phase file directly rather than leaving stale tasks in it.
