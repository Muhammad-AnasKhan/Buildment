# Mentor review queue

**Reads:** [`03-blocks-registry.mdx`](03-blocks-registry.mdx) (`OpenQuestion`, `CodeBlock` `submit` mode), [`04-progress-and-gating.mdx`](04-progress-and-gating.mdx)

The human-in-the-loop surface. If this is slow or annoying, mentors stop grading and the
platform's value collapses — so it gets first-class treatment, not a form buried in a table.

## Queue view

All pending items across the mentor's courses, filterable by course / mentee / block type / age.
Sorted oldest-first by default. Shows an aging indicator (**>48h waiting is highlighted**).

## Review view

One submission at a time, keyboard-driven.

- **Left:** the original question + the mentor's own rubric + reference answer.
- **Right:** the mentee's answer, rendered Markdown (or code with syntax highlighting + the run
  output they got).
- **Actions:** score (rubric-based or 1-5), written feedback (Markdown), and a verdict:
  **Approved** / **Needs revision**.
- `j` / `k` to move through the queue, `⌘+Enter` to submit and advance.
- Canned feedback snippets, saved per mentor, for repeated comments.

### AI-assisted draft

For pending `OpenQuestion` responses, the mentor may click **Draft with AI** to ask OpenRouter for
an evidence-based summary, feedback, suggested score, and suggested verdict. The draft pre-fills
the ordinary review form; it never submits a review, changes progress, or selects the final verdict
for the mentor. The mentor remains responsible for checking evidence, editing feedback, and choosing
**Approved** or **Needs revision**.

The UI discloses the data transfer before the mentor clicks: the learner answer, question, mentor-only
rubric/reference answer, and up to three recent feedback messages are sent to OpenRouter. Generation
is never automatic or run in the background. Buildment does not fetch learner-submitted URLs for the
model. The server sends only the text stored with the response and labels any URL as uninspected.

The browser sends only `responseId` to the server action. The server reloads the response, calls the
centralized course-mentor authorization guard, validates the block config and payload, and only then
constructs the provider request. Rubric and reference-answer text are not returned to the browser as
part of the AI payload; the browser receives only the generated draft.

## Needs-revision loop

**Needs revision** reopens the block for the mentee, notifies them in-app, and puts the
resubmission back at the **front** of the queue with the previous exchange threaded (so the mentor
sees their own prior feedback alongside the new attempt).

Note: a needs-revision verdict does **not** revert chapter completion — see the note in
[`04-progress-and-gating.mdx`](04-progress-and-gating.mdx). Completion tracks submission, review
tracks quality; these are intentionally decoupled so mentees are never blocked waiting on a mentor.

## Mentee evaluation workspace

The course mentee route (`/courses/[courseSlug]/mentees/[enrollmentId]`) is the mentor's unified
workspace for one learner. It places pending reviews and help requests before historical material,
then shows the full course map, latest attempt per checkpoint, the immutable response/review
timeline, and recent study activity. A mentor enters the existing single-submission review flow
from this workspace; it does not introduce a second grading or feedback system.

URL-based `OpenQuestion` responses are also projected into **Project evidence**. The server uses
the prompt and safe presentation fields (`submissionMode`, `urlLabel`, and `urlHint`) to label
repositories, demo videos, deployments, diagrams, and documents. The browser receives this
projection, never the full `Block.config`. Evidence URLs are stored as submitted links only:
Buildment does not connect to GitHub, clone repositories, fetch learner URLs, or embed arbitrary
video frames.

## Data model touch points

- `Response.status` drives what's in the queue: `PENDING_REVIEW` items are queued;
  `NEEDS_REVISION` items are reopened for the mentee; `REVIEWED` items are done.
- `Review` is `1:1` with `Response` (`Review.responseId @unique`). A resubmission creates a **new**
  `Response` (new `attempt`), not a new `Review` on the old response — the "previous exchange
  threaded" UI reads across the `Response` history for that `(blockId, userId)` pair.
- `Review.reviewerId` is independent of `Course.mentorId` — this is deliberate, so that adding
  co-teachers/TAs later (deferred, see [`10-deferred-v2.mdx`](10-deferred-v2.mdx)) is an
  access-control change only, not a schema change.

Full `Review` model: see [`08-data-model.mdx`](08-data-model.mdx).

## Mentor capacity

Aging highlights help prioritize a large queue, while AI-assisted drafting reduces the time spent
starting each written review. Bulk approval remains a separate future workflow because batching
human-evaluated work has a different risk profile from drafting one editable review at a time.
