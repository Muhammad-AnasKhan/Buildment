# Canvas spec: sysdesign-m2-estimator

- **Course and chapter:** system-design, 2.3 "Back-of-the-envelope estimation". Suggested home: the first beat, "From people to requests per second", in place of its Mermaid chain (new slug; replaces no canvas). It also carries the storage and bandwidth chains, so it can close the chapter's "driving number" beat as well.
- **Renderer:** custom beat canvas on `BeatFrame` and `useBeatClock`, with the new reusable primitive `primitives/estimate-chain.tsx` (`EstimateChain`, `StepSlider`). Custom because no kit renderer draws a worked estimate. The primitive takes cards, links, chips and inputs as data, so every case study's `[estimator]` step (roadmap 20.1, 21.1, 22.1 ...) can reuse it with its own chain.
- **Claim:** An estimate is a chain of small multiplications with a unit at every step; the number that drives the design is the one furthest past what one machine can do.
- **Inputs (tap a blue number in the picture, drag it sideways, or use arrows; the slider under the picture edits the one picked):** daily users (10 thousand to 1 billion, 1-2-5 steps), requests per user a day (1 to 200), peak factor (1 to 10), note size (10 KB to 10 MB). Fixed assumptions shown on the links: 1 in 10 users records a note, 10 plays per user, 3 copies, 5 years.
- **Model:** `models/envelope-estimate.ts`, unit tested. Requests a day = users x requests; average/s = day / 86,400; peak/s = average x peak. Stored a day = users x share x size; a year = day x 365 x copies. Sent a day = users x plays x size; bits/s = day / 86,400 x 8; peak = x peak factor. 1 KB = 1,000 bytes. Numbers shown to 3 significant figures.
- **Driving number:** each end result against a rule of thumb (one server about 1,000 requests/s, one disk about 20 TB, one link 10 Gbit/s); the highest ratio is circled and named in the verdict, for example "21.9 TB a year: more than one disk" or "Peak 174,000/s: one server will not do". Every verdict is at most 38 characters across all input steps (tested).
- **Default (the chapter's Sada):** 20 million requests a day, 231/s average, 694/s at peak; 20 GB a day, 21.9 TB a year with 3 copies, 110 TB after 5 years; 2 TB sent a day, 185 Mbit/s average, 556 Mbit/s at peak. Driving number: storage, as in the chapter.
- **Motion:** dots flow down each column at a rate that grows with the log of that column's ratio to its limit; the column's colour (green, amber, red) follows the same ratio. Reduced motion shows still dots.
- **What to notice:** users move every number in proportion; the peak factor moves only the rates, never the storage; a smaller note size can hand the driving number from storage to requests.
- **Accessibility:** each input in the picture is a `role="slider"` with arrows, Home and End and a value text; the SVG has a sentence label with the main results and the verdict; the slider below is the house shadcn slider for a 44 px target.
- **Sources:** inputs are the chapter's labelled assumptions; N = 3 copies follows the Dynamo paper [S45]; the rules of thumb are stated as such in the limits fold.
