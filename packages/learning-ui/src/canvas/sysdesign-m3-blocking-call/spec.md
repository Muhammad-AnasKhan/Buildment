# Canvas spec: sysdesign-m3-blocking-call

- **Course and chapter:** system-design, 3.6 ("Linux under your service"), beat 5 ("One blocking call stops everyone"). New slug.
- **Renderer:** custom beat canvas on `BeatFrame`, with the new `primitives/rail-slider.tsx` and `primitives/svg-chip.tsx`. `traffic-playground` has one lane and one server card, so it cannot show eight thread lanes; this canvas draws the same pieces (source card, request dots, a line of dots piling up, a curve inset with a dot that rides it, a rail) itself, in the same style.
- **Claim:** On an event loop, one blocking call stalls every request and lowers the server's ceiling. A thread pool contains the block but tops out far lower.
- **Model** (`models/blocking-call.ts`, all numbers illustrative): every request needs c = 1 ms of CPU and w = 50 ms of async wait; 100 requests arrive a second. A share s (none, 1%, 5%) also does B ms of CPU (0 to 200 ms, snaps 0, 20, 100, 200).
  - Event loop: ceiling = 1000 / (c + s B): 1,000 a second with no slow calls; about 333 at s = 1%, B = 200; about 91 at s = 5%, B = 200. Busy share = arrivals (c + s B) / 1000. While a slow call runs, every other request waits up to B ms (p99 rises by about B on every route).
  - Thread pool, T = 8: each request holds a thread for c + w + s B ms; ceiling = 8000 / (c + w + s B): about 157 a second, about 151 at s = 1%, B = 200. A slow call ties up 1 of the 8 threads.
  - Fold references: Little's law (S5); a context switch costs about 10 microseconds (S3).
- **Inputs:** a rail for B inside the picture; three share chips inside the picture (none, 1%, 5%; default 1%, B = 200); a toggle outside the picture between event loop and thread pool (two buttons, `aria-pressed`).
- **Picture:** a Requests card sends dots into a server panel. Event loop: one lane; during a slow call the lane fills red, the panel gets a red ring, and dots pile up in front of it (up to five, then three small dots); afterwards the line drains and short calls pass as green dots. Thread pool: eight thin lanes; during a slow call one lane fills red while the others keep carrying dots. At 5% and 200 ms the event loop is over 100% busy (1.1), so the calls come back to back and the line stays full. The inset plots the ceiling against B for the chosen mode, with a dot that rides the curve; the ceiling is read out at the top of the inset ("333 requests/s").
- **Numbers visible at once:** the arrival rate (Requests pill), the length of the slow call (rail caption and lane label), the ceiling (inset dot).
- **Verdicts (38 characters or fewer):** event loop: "Loop blocked {B} ms: all requests wait"; "Ceiling falls to {n} requests/s" when the arrivals exceed the loop's ceiling (5% at 200 ms: 91 a second); "No blocking: loop ceiling 1,000/s". Thread pool: "Pool: 1 of 8 threads stuck"; "Pool tops out near 157 requests/s" when nothing blocks. At 1% and 200 ms the 333 a second shows on the inset dot rather than in the banner.
- **Motion and reduced motion:** slow calls start on a fixed rhythm (every 4.6 s at 1%, 3.2 s at 5%, a longer call for a larger B); dots flow at 4 a second, standing for 100 requests. With reduced motion the dots stand still and the picture shows a frozen mid-call frame (lane partly red, line piled up), or the calm frame when nothing blocks. Pressing the rail pauses the loop.
- **Accessibility:** the B rail is a `role="slider"` (arrow keys step 10 ms) with value text that includes the verdict; chips and the toggle are buttons with `aria-pressed`; the SVG description gives the mode, the numbers, the ceiling and the verdict.
- **Sources:** S5 Little's law; S3 napkin math (context switch about 10 microseconds).
