# Canvas spec: sysdesign-m12-paxos-play

- **Course and chapter:** system-design, 12.7 ("Paxos and multi-leader setups"), beat 2 "Two proposers, three acceptors". New slug.
- **Renderer:** custom beat canvas on `BeatFrame`: `LaneCards` (`SvgNode` cards) for P1, P2 and A1 to A3, `LinkLine` for the active proposer's three links, `SvgChip` toggles for which acceptors hear the next message, `SvgPillButton` for Prepare, Accept and Reset, `VerdictBanner`, the beat clock for the travelling dots.
- **Claim:** Once a majority has accepted a value, any later proposer that gets promises from a majority is forced to propose that same value. Two values are never chosen.
- **Model** (`models/paxos-play.ts`): each acceptor keeps `promised` and the accepted proposal (number, value). `prepare(n)`: if n is above promised, promise and report the accepted proposal; otherwise refuse. `accept(n, v)`: if n is at least promised, accept; otherwise refuse. A proposer may send accept only with promises from 2 of 3; its value is the value of the highest numbered proposal reported in its promises, or its own (P1 wants A, P2 wants B). P1 uses numbers 1, 3, 5 and P2 uses 2, 4, 6. A value is chosen when 2 acceptors hold the same (number, value); the model remembers every value ever chosen, and a unit test searches all sequences of up to five messages to show there is never more than one.
- **Inputs:** tap P1 or P2 to make it the active proposer; tap A1, A2, A3 to choose who hears the next message (all three by default, reset after each send); "Prepare n", "Accept n, V" (disabled with a note until 2 promises), "Reset". The hint under the picture follows the scripted run step by step, then tells the learner to try the duel.
- **Scripted run:** P1 Prepare 1 to all; P1 Accept 1, A to A1 and A2 (A chosen, 2 of 3); P2 Prepare 2 to A2 and A3 (A2 reports (1, A), the value box locks to A with the note "A2 reported (1, A): P2 must propose A"); P2 Accept 2, A to A2 and A3 (all three hold A, "Still one value: A").
- **Duel:** P1 Prepare 1 and P2 Prepare 2 to all, P1 Accept 1, A is refused by all ("Refused: promised 2"); P1 Prepare 3, P2 Accept 2, B is refused ("Refused: promised 3"). After two refused actions the picture shows "Two proposers can keep outbidding".
- **Verdicts (38 characters or fewer):** "P2 must propose A, not B", "A is chosen: 2 of 3 accepted it", "Refused: promised 2", "No majority: P2 must wait", "Still one value: A", plus "Majority promised: now send Accept", "Only 1 of 3 accepted: not chosen", "P1 keeps A: it was accepted" and the opening line.
- **Motion:** a dot goes from the proposer to each chosen acceptor and a green or red dot comes back (0.9 s); state changes use CSS transitions, so a paused clock still shows the final state. Under reduced motion no dot travels and the last four steps are written as list lines under the picture.
- **Accessibility:** acceptor chips are toggle buttons ("A2, receives the message: on"); the proposer cards are buttons; a disabled Accept keeps `aria-disabled` and says why; a live region repeats the last step, each acceptor's state ("A2: promised 2, accepted 1 A") and the verdict.
- **Sources:** phases, majorities and the distinguished proposer [S67]. The rule that a promise reports the highest accepted proposal is from the same paper (section 2.2) and is flagged in the chapter as a source needed note.
