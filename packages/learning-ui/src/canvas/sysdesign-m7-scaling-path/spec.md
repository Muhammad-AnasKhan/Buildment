# Canvas spec: sysdesign-m7-scaling-path

- **Course and chapter:** system-design, 7.6 ("The database scaling path"), beat "Grow the traffic, add the right step".
- **Renderer:** custom beat canvas on `BeatFrame`, with `primitives/rail-slider.tsx` and `SliderRail` for the traffic rail, `SvgChip` for the steps and `SvgNode` for the cards. Model: `models/db-scaling.ts`. The traffic-playground primitive covers one source and one server only, so this picture is its own.
- **Claim:** Each database scaling step removes load from one part. A step that does not touch the part that is full leaves it full, so the order of steps follows the bottleneck.
- **Model (all made up, illustrative):** traffic R requests a second, 90% reads and 10% writes. One machine handles 4,000 units a second (8,000 when bigger, costing 2 instead of 1). A read costs 3 units without an index and 1 with one; a write costs 5. The cache answers 90% of the reads. With n replicas (n at least 1) all database reads go to the replicas, each taking an equal share; with n = 0 they go to the primary. With p partitions the writes (and the reads, when n = 0) are split equally over p primaries, so every partition shows the same percentage and the picture draws one stacked "Primary x p" card. Primary load = (writes x 5 + (n = 0 ? database reads x read cost : 0)) / p; replica load = database reads x read cost / n; utilisation = load / capacity. Cost per hour = (p + n) machines (x2 when bigger) + 1 for the cache + 1 for a search store.
- **Scenario chip "Add the search box":** a tenth of the reads (0.1 x r) are word searches, not cached, each costing 20 units on the database. With a search index they cost 0 on the database and go to a search store that handles 5,000 searches a second. The other reads are the remaining 0.9 x r.
- **Worked values (tested):** 3,000 a second with nothing: 9,600 units, 240%. With an index: 4,200, 105%. With index and cache: 1,770, 44%. 12,000 with index and cache: 7,080, 177%. Adding 2 replicas: primary 6,000, 150%, each replica 540, 14%. Adding 2 partitions instead: 3,540 each, 89%. Index, cache, 2 partitions and 2 replicas at 12,000: primary 3,000, 75%. At 25,000 with index and cache: 14,750, 369%; with 4 partitions 3,688 each, 92%.
- **Inputs:** traffic on a rail inside the picture with snaps 500, 1,000, 3,000, 6,000, 12,000, 25,000, 50,000 (default 3,000). Chips on the picture: Index, Cache (toggles), Replicas (tap cycles 0 to 3), Partitions (tap cycles 1, 2, 4, 8), Bigger machine, and with the scenario on, Search index. Under the picture: the scenario chip and Reset (Reset keeps the traffic).
- **Picture:** App, Cache, Primary, Replica and (scenario) Search store cards; the cache and replicas show as dashed empty slots when off; request dots flow along links at a rate that follows R (capped, one dot stands for many; dots into a full part are red); each database card has a pill with a number and a word (under 70% fine, up to 100% busy, over 100% full) and a red ring when full; the cost per hour is written beside the chips.
- **Verdicts (38 characters or fewer, by the worst part; N is the percentage):** "Every part has room"; "Primary N%: add an index" (reads outweigh writes on the primary, no index); "Primary N%: add a cache" (index on, no cache, reads still outweigh writes); "Writes N%: partition the data" (write units per partition at or above capacity, or any over-full primary that has replicas); "Reads N%: add a read replica"; "Searches overload: add a search index" (search units alone exceed a machine); fallbacks when a replica is full: "Replicas N%: add an index", "add a cache", "use bigger machines", "too many reads".
- **Accessibility:** the traffic rail is a `role="slider"`; chips are `role="button"` with `aria-pressed` and a label that says the state; the SVG description gives the traffic, each part's percentage, the steps on, the cost and the verdict.
- **Limits shown to the learner:** all numbers are made up to show the reasoning, not a benchmark; real databases differ, and real traffic is not 90% reads all day.
- **Sources:** the load model is a course example; replica lag [S38], [S39]; DynamoDB partitions [S40]; cache savings: Facebook leases [S24].
