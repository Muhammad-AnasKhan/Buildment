# Canvas spec: sysdesign-m9-rebalance-play

- **Course and chapter:** system-design, 9.5 ("Rebalancing and request routing"), beat 3, "Moving data while requests keep coming".
- **Renderer:** custom beat canvas on `BeatFrame`. Reuses `primitives/keyed-slider.tsx` (drag anywhere, arrow keys 1, Page keys 10), `SliderRail`, `DotGrid`, `VerdictBanner`; five compact node cards drawn here (five `SvgNode` cards do not fit 420 units). Uses `primitives/beat-choice.tsx` for the two switches.
- **Claim:** The scheme decides how much data must move (80% for hash mod N, about 20% for fixed partitions or a ring), and while the move runs, clients with an old map send requests to the wrong node in proportion to how much has already moved.
- **Inputs:** (1) "Hash mod N | Fixed partitions", default Hash mod N. (2) "Clients: old map | Clients: fresh map", default old map. (3) The progress of the move, 0 to 100% of the move time, by dragging across the picture; arrow keys 1%, Page keys 10%; default 0.
- **Model** (`model.ts`): data 1.8 TB, four nodes becoming five, 5,000 requests a second spread evenly over the keys, copy speed 100 MB a second. Changed share: 0.80 (mod) or 0.20 (fixed). `bytesToMove` is 1,440 or 360 GB; `moveSeconds` is 14,400 (4 h) or 3,600 (1 h). At progress p: `moved = p x bytesToMove`, `movedShare = moved / 1.8 TB`, wrong-node requests a second = `5,000 x movedShare` with the old map, else 0. Node volumes run from 450 GB each (four nodes) to 360 GB each (five nodes) in both schemes. Under mod, 75% of the moved data lands on a node that was already there (4/5 - 1/5 over 4/5).
- **Numbers to check:** p = 0.5, old map: mod has moved 720 GB with 2,000 wrong-node requests a second; fixed has moved 180 GB with 500. At p = 1 with the old map: 4,000 (mod) and 1,000 (fixed); with a fresh map both are 0.
- **Picture:** five node cards (node 5 dashed, new) with their volume in GB; a bus from the four old nodes to the new one; under mod a second bus (amber) for the waste between old nodes, labelled "waste: 75% of it moves between old nodes"; dots flow along both while the move is part way. Two bars: "Data moved" (GB so far of the total, against a dashed tick at the amount to move, on a scale of the whole 1.8 TB) and "Wrong-node requests" (against the 5,000 line, amber, red above 1,500). The rail's ends say "start" and the move time ("4 h").
- **Verdicts:** at p = 0: mod "1.44 TB to move: about 4 hours" (bad); fixed "360 GB to move: about 1 hour" (good). Old map and p above 0: "2,000 requests/s hit the wrong node" (warn, bad above 1,500). Fresh map and p above 0: "Map is fresh: no wrong-node requests" (good).
- **Reduced motion:** the picture shows the state at p; no flow dots.
- **Accessibility:** the picture is one `role="slider"` ("move 50% done, 720 GB moved, 2,000 wrong-node requests a second"); the toggles are real button pairs with `aria-pressed`.
- **Sources:** N over N+1 is arithmetic; Envoy ring hash [S16]; Dynamo [S45]. Suq's numbers and the copy speed are course assumptions.
