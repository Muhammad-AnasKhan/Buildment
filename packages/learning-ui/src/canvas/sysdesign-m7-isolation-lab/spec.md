# Canvas spec: sysdesign-m7-isolation-lab

- **Course and chapter:** system-design, 7.4 ("Transactions and isolation levels"), beat "Interleave two transactions, change the level".
- **Renderer:** custom beat canvas on `BeatFrame`, three lanes drawn in the canvas with `primitives/rail-slider.tsx` and `SliderRail` for the timeline, and a new reusable `primitives/beat-segmented.tsx` for the two choosers. The kit's `timeline` renderer was not used: it draws dots, spans and arrows only, and this picture needs dashed, hatched and red statement bars. The outcome table is data in `models/isolation.ts`.
- **Claim:** What can go wrong when two transactions overlap depends on the isolation level, and in PostgreSQL the stricter levels stop an anomaly by refusing one transaction with error 40001, which the app must retry.
- **Model:** a fixed script per story, an outcome per level from runs on PostgreSQL 18.6 (2026-10-24). No randomness.
- **Stories:** A "Lost update (app adds)": balance 100, T1 sets 150, T2 sets 130. B "Lost update (SQL adds)": `balance + 50` and `balance + 30`. C "Write skew (gates)": two gates open, each transaction closes one after seeing 2 open. D "Dirty read (seats)": left = 1, T1 sets 0 then rolls back, T2 reads.
- **Levels:** Read Committed (default), Repeatable Read, Serializable; for story D only, a fourth choice "Read Uncommitted (not PostgreSQL)" with the note "PostgreSQL treats this as Read Committed; this shows a database that allows dirty reads".
- **Outcomes (tested):** A: Read Committed, T2 waits then completes, final 130; Repeatable Read and Serializable, T2 refused with 40001 "could not serialize access due to concurrent update", final 150. B: Read Committed 180; the others 40001, retry gives 180. C: Read Committed and Repeatable Read, both commit, 0 gates open; Serializable, T2's COMMIT refused with 40001 "could not serialize access due to read/write dependencies among transactions", 1 gate open. D: the PostgreSQL levels, T2 reads 1; Read Uncommitted, T2 reads 0 and T1 rolls back.
- **Inputs:** a story chooser and a level chooser (segmented controls under the picture); inside the picture a timeline rail (drag, arrow keys) and Back and Next buttons. Default: story A at Read Committed, step 0. Changing the level keeps the step, so the new ending shows at once; changing the story starts at step 0, or at the last step if the learner was at the last step.
- **Picture:** lanes T1, Database and T2, time running down. Future statements are faint dashed ghosts (without their results). A read shows what it saw; an uncommitted write is dashed and turns solid at commit (struck through after a rollback); a statement that waits for a lock is hatched, the hatch drifting; a refused statement is red with "ERROR 40001"; the Database lane shows the value over time (dashed chips for uncommitted values); a message under the lanes gives the full error text and the final value. The current statement has a pulsing ring.
- **Verdicts (38 characters or fewer):** A at Read Committed "Lost update: 150 was erased"; A at the others and B at the others "Refused with 40001: retry"; B at Read Committed "No loss: 100 + 50 + 30 = 180"; C at Read Committed or Repeatable Read "Write skew: no gate stays open"; C at Serializable "Refused: one gate stays open"; D at PostgreSQL levels "No dirty read in PostgreSQL"; D at Read Uncommitted "Dirty read: saw a change that vanished". Before the last step the banner narrates the step.
- **Accessibility:** the timeline is a `role="slider"`; Back and Next are `role="button"`; the choosers are radio groups; the SVG description lists the statements run so far and the database value.
- **Limits shown to the learner:** outcomes are PostgreSQL 18.6 behaviour in a two-transaction script; other databases differ, and so do other timings.
- **Sources:** PostgreSQL transaction isolation docs (read 2026-10-24); Jepsen snapshot isolation [S46] (read 2026-10-24); the course runs behind the chapter's tables.
