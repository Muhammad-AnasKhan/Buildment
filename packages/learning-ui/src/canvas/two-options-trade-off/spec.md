# Canvas spec: Where should Qasir count clicks?

## Teaching claim
An AI's confident default is often right for a different project: the cache counter it suggests wins only when "fast under many clicks" matters most and everything else matters little, which describes heavy traffic; Yara's weights, set by her project's facts, pick counting in the database.

## Why a canvas
The chapter computes Yara's totals in prose. What prose cannot make felt is that the AI's suggestion is not simply wrong: there is a setting where it wins, and only one. Letting the learner hunt for it, and find that it matches a busy commercial service rather than Qasir, turns "do not trust the AI" into the better lesson, "the facts set the weights".

## Model
- Inputs: one weight per criterion.

  | Name | Unit | Min | Max | Step | Default |
  |---|---|---|---|---|---|
  | Simple to build | weight level | 1 | 3 | 1 | 3 |
  | Fast under many clicks | weight level | 1 | 3 | 1 | 1 |
  | No clicks lost if a part stops | weight level | 1 | 3 | 1 | 3 |
  | Easy to explain | weight level | 1 | 3 | 1 | 2 |

- Fixed data (Yara's illustrative judgement, 1 to 5), database / cache: simple 5 / 2; fast 2 / 5; no clicks lost 5 / 2; easy to explain 4 / 2.
- Outputs:

  | Name | Unit | Format |
  |---|---|---|
  | Total per option | points | whole number |
  | Leader or tie, and margin | points | text from the shared factor model |

- Formula: total(option) = sum of weight(criterion) x score(option, criterion).
- Checked totals (all 81 weight settings enumerated):
  - Default, Yara's weights (3, 1, 3, 2): database 40, cache 21.
  - Every weight at 2: database 32, cache 22.
  - Every weight at 1: database 16, cache 11.
  - Fast at 3, the rest at 1: database 20, cache 21. This is the only setting where the cache counter leads; there are no ties.
  - No clicks lost at 3, the rest at 1: database 26, cache 15.
- Assumptions: Qasir's traffic is a few hundred clicks a day on a busy link (the plan's example number); the cache in her lab keeps data only in memory, so a stop before the minute's save loses those clicks.
- Limitations: scores are judgement; real speed and loss risk depend on the setup and the traffic.

## Rendering
- Primary: the shared factor renderer (HTML weight controls, SVG bars).
- Why this renderer: the claim is a weighted comparison the learner changes.
- Static fallback: chapter 7.4 shows the score table and works Yara's totals (40 and 21) in prose under "Worked example: weighing the two options".

## Controls
Four weight controls with three levels each ("Matters a little", "Matters", "Matters a lot"). Each exists because each test is one of the angles in the chapter.

## Visualisation
Two bars, one per option, with the total as text; the leader named in words.

## Copy
- What this shows: `whatThisShows` in `data.ts`.
- Try this:
  1. Fast at "Matters a lot", the rest at "Matters a little": cache 21, database 20, the only one of the 81 settings. This answers the chapter's predict without restating it.
  2. "No clicks lost" first, the rest at "Matters a little": database 26, cache 15.
  3. Every weight at "Matters": database 32, cache 22.
- What changed: generated by `describeChange` in `renderers/factor/model.ts`.
- Limits of the model: `limits` in `data.ts`.

## Edge cases
No ties exist at any setting, so the leader is always named. The closest race is the single cache win, 21 to 20. Long criterion name "No clicks lost if a part stops" is 30 characters; the shared renderer wraps criterion names.

## Accessibility
Weight controls are native HTML controls with visible labels; totals are text, not only bar length; the leader is named in words.
