# Canvas spec: sysdesign-m1-block-map

- **Course and chapter:** system-design, 1.3 "The building blocks map", closing beat ("The whole map, one request at a time"). Replaces the beat's Mermaid map as the visual; the Mermaid diagram moves into the beat's fold.
- **Renderer:** custom, on the reusable `BlockMap` primitive (`primitives/block-map.tsx`, model `models/block-map.ts`). This folder holds only data. Reason for a primitive: tap-to-explore and break-to-see-failure on a fixed topology is an interaction several courses need (any architecture map), and a scene only plays.
- **Claim:** Each block has one job, a typical way to fail, and a managed service that does it. A request reaches a block along a path, so when one block fails, everything whose path runs through it, or that needs it, fails too.
- **Model:** every block lists its path from Students (for example Students, Gateway, Balancer, App servers, Cache) and, where it applies, blocks it needs off the path (the CDN and the gateway need DNS; workers need file storage). Breaking block X cuts off X and, repeated until nothing changes, every block whose path or needs include a cut-off block. Failed links are the links on each cut-off block's path from the first cut-off block onward, plus any link between two cut-off blocks. A request to the selected block stops at the edge of the first cut-off block on its path.
- **Blocks (11):** Students, DNS, CDN, Gateway, Balancer, App servers, Cache, Queue, Database, Files (object storage), Workers. Jobs, failure modes and AWS names (Route 53, CloudFront, API Gateway, Application Load Balancer, EC2, ElastiCache, SQS, RDS/Aurora/DynamoDB, S3, EC2 fed by SQS) are the chapter's "every block on one page" table.
- **Inputs:** tap a block (a real button over each card: Tab between blocks, Enter or Space selects). "Break it" toggles a failure on the selected block; one block is broken at a time, and it stays broken while the learner taps other blocks to see what still works.
- **What moves:** a request dot with a short trail travels the path to the selected block, and each card it passes lights briefly; the path's links turn accent. When something is broken the dot stops red at the edge of the first block that is down. The broken card turns red with a "down" pill, cut-off cards dim with "cut off", and a block that stays up but feels the failure shows an amber pill (a failure lists `strain` and `affects`): Cache down, the database says "every read" and the app servers "no cache"; Database down, the app servers say "no database"; Queue down, the app servers say "cannot queue"; Files down, "no files"; CDN down, the students say "no logo"; Workers down, the queue says "piling up". Under reduced motion the dot rests at its end point and the rest is the same.
- **Numbers on screen:** none; the words carry it.
- **What the learner should notice:** DNS is the quietest block and the widest failure; a cache failure does not stop Daftar but moves every read onto the database; the queue lets uploads keep working while workers are down.
- **Layout:** compact cards (120 by 50, same look as `SvgNode`) in three columns on a 420 by 318 viewBox; labels 12.5 units, pills 11.5. Tap areas reach 7 units past each card, about 50 px tall on a 375 px phone. The panel (what it does, when it fails, in AWS) sits under the picture inside the frame, in a polite live region.
- **Limits (fold):** one card stands for many machines, so one failure rarely takes a whole block down; the private network, request order and recovery time are left out. Daftar is fictional.
- **Sources:** the chapter's sources, especially the AWS us-east-1 DNS event summary [S135], ElastiCache lazy loading [S26], SQS visibility timeout [S84] and Elastic Load Balancing [S15].
