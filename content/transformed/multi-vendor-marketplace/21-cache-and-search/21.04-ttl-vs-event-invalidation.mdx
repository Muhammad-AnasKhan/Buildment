Production caches use **both**. TTL is a safety net; invalidation is correctness on writes.

Beginners often pick one and wonder why production still breaks. This sub-chapter gives you the **decision frame** before you implement in 21.9 and 21.11.

## TTL only

If your only tool is an expiry time, here is what you buy and what it costs — cheap and simple, but at the mercy of the clock.

| Pro | Con |
|---|---|
| Simple — set expiry, forget | Stale until expiry |
| No invalidation code paths | Wrong price visible for entire TTL window |
| Good for rarely changing data | Bad for vendor-edited catalogue |

**Example failure:** TTL = 15 minutes. Vendor fixes a typo price at 10:00. Customers see wrong price until 10:15.

## Event invalidation only

The flip side: freshness on every write, but every write path must remember to invalidate — miss one and the stale data never leaves.

| Pro | Con |
|---|---|
| Fresh immediately after writes | Miss one code path → stale **forever** |
| Correct for price changes | Orphan keys if key pattern wrong |
| Professional default for catalogues | More code to maintain |

**Example failure:** You invalidate on `PATCH` but forget `DELETE` — deleted products appear in cache until manual flush.

## Both (course mandate)

```
On GET:  try cache → on miss, query DB → set with TTL
On POST/PATCH/DELETE product:  delete cache keys for catalogue
```

| Layer | Role |
|---|---|
| **Event invalidation** | Correctness — user sees new price immediately |
| **TTL** | Safety net — orphaned keys expire; catches bugs in invalidation |

TTL catches bugs in invalidation — keys expire eventually. Invalidation catches user-visible errors — prices fix now.

## Key design

Document pattern in README:

```
catalogue:{hash(sortedQueryParams)}
```

Or single key `catalogue:all` if only unfiltered list cached — **prefer per-query** if filters exist from Ch 14.

Different `page`, `category`, and `search` params → different keys → invalidation must clear **all catalogue keys** (prefix delete), not one key.

## Invalidation call sites

`products.service.js` — after successful:

- `createProduct`
- `updateProduct`
- `deleteProduct`

Call `invalidateCatalogueCache()` — not scattered in routes. One function, one place to audit.

## In plain English

| Term | Simple meaning |
|---|---|
| **TTL** | "Throw this cached answer away after N seconds" — automatic |
| **Event invalidation** | "Throw cached answers away **when something specific happens**" — e.g. vendor saves product |
| **Prefix delete** | Delete all keys starting with `catalogue:` — clears every cached page/filter variant |

## Think of it like milk expiry dates

The two invalidation strategies map onto a shelf-life decision you already make in real life:

**TTL** = printed expiry date on the carton — good enough if nobody changes the recipe.

**Event invalidation** = pulling all cartons from the shelf the moment the recipe changes.

**Both** = pull immediately on recipe change *and* expiry date as backup for any cartons you missed.

## Common beginner questions

<FaqGroup>

<FaqItem question="What TTL should I pick?">

The course says 300–900 seconds (5–15 minutes) — pick one and document it. Think of TTL as a trade-off dial: shorter TTL means stale data disappears sooner but MongoDB sees more traffic; longer TTL means faster reads but a bigger stale window if invalidation ever misses. Because you'll also invalidate on writes, TTL is your safety net rather than your correctness mechanism, so the exact number matters less than having one and writing it in your README.

</FaqItem>

<FaqItem question="Can I use `FLUSHALL` to clear the cache when things go wrong?">

Don't — and especially not in this course. Your Redis instance also holds Chapter 22's BullMQ job queues, and `FLUSHALL` wipes every database, queue keys and all, plus all your cache keys. The right tool is a prefix delete: `SCAN` for keys matching `catalogue:*`, then `DEL` each one. That clears exactly the catalogue variants — different pages, categories, and search terms — and touches nothing you don't own. Remember the rule: avoid `KEYS` in production; `SCAN` is the safe way to find matching keys.

</FaqItem>

<FaqItem question="What happens if I only invalidate and skip TTL?">

You get perfect freshness but a nasty leak: every key you forget to invalidate stays in Redis forever. If you miss one write path — the classic example is `DELETE`, where a deleted product vanishes from MongoDB but lingers in cache — stale data survives until a human manually flushes it. TTL is the janitor: keys expire automatically even when your code forgets them. Freshness comes from invalidation; cleanup comes from TTL. That's why production caches use both, and why this course makes both mandatory.

</FaqItem>

<FaqItem question="What is a prefix delete, and why is it needed once filters exist?">

Different query parameters produce different cache keys — `?page=2`, `?category=Dairy`, `?search=milk` each cache separately — so one product change can affect several cached pages at once. You can't delete a key you don't know by name, so you delete by pattern: scan for keys starting with `catalogue:` and delete them all. That clears every page and filter variant in one operation. A single-key `DEL` only works in the toy case where you cache one unfiltered list; with filters from Chapter 14, prefix delete is the way.

</FaqItem>

<FaqItem question="Where should the invalidation code actually live?">

In `products.service.js`, as a single function like `invalidateCatalogueCache()`, called after `createProduct`, `updateProduct`, and `deleteProduct` succeed. Don't scatter `del` calls through the routes. One function, in the layer where the write happens, means you can audit every invalidation point by reading one file — and when the next cache-related bug appears, you know exactly where to look. That's the professional pattern: a single source of truth for a cross-cutting concern.

</FaqItem>

<FaqItem question="Should I implement TTL or invalidation first?">

The course order matters: build the cache with TTL in 21.9, then add invalidation in 21.11. Doing it in that order lets you *feel* the stale trap — you'll run the price test, watch the old price survive a PATCH because TTL hasn't expired, and then fix it with invalidation. You understand a bug far better after hitting it yourself than when someone simply warns you about it. The sequence isn't ceremony; it's the chapter teaching you why both mechanisms exist.

</FaqItem>

</FaqGroup>


## ✅ Do / ❌ Don't

**✅ Do:** Implement TTL in 21.9, invalidation in 21.11 — sequence matters for testing.

**✅ Do:** Use Redis `DEL` or `SCAN`+`DEL` for pattern — avoid `KEYS` in production docs note.

**❌ Don't:** Invalidate entire Redis DB — `FLUSHALL` nukes unrelated keys.

**❌ Don't:** Assume one cache key — filters and pagination multiply keys.
