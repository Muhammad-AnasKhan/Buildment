## In plain English

| Term | Simple meaning |
|---|---|
| **Redis** | A very fast in-memory database that sits beside MongoDB — like a sticky note the server checks before opening the filing cabinet |
| **Cache** | A saved copy of a recent answer — so the server does not repeat the same expensive work |
| **Cache hit** | The answer was already on the sticky note — instant return |
| **Cache miss** | Sticky note empty — server fetches from MongoDB, then saves a copy for next time |
| **TTL (time to live)** | How long a cached answer stays valid before it expires automatically — e.g. 5 minutes |
| **Cache invalidation** | Deliberately throwing away stale sticky notes when data changes — e.g. vendor updates a price |
| **Text index** | MongoDB's built-in search index — finds products by words in name and category without scanning every row |
| **Fallback** | When Redis is down, the app still works — just slower — by reading MongoDB directly |

## Think of it like a shop window display

The **catalogue** (`GET /products`) is your shop window — the most looked-at part of the store. Every customer who opens `/shop` asks the same question: *"What products are on page 1?"*

Without cache, your server walks to the warehouse (MongoDB) for **every single glance** — even when nothing changed since the last customer.

With cache, the first customer triggers a warehouse trip; the next hundred read from a **photograph of the window display** (Redis) until a vendor rearranges the shelf (product write) or the photograph expires (TTL).

**Important:** You cache the **shop window**, not the **checkout desk**. Cart, orders, and auth stay fresh every time — they are personal and change constantly.

## The hot path

```
Customer opens /shop
  → GET /products?page=1&category=Dairy
  → MongoDB query + populate store
  → repeat for every user, every page load
```

Catalogue is read-heavy. Chapter 21 adds a cache layer — not for cart or orders.

## Common beginner questions

<FaqGroup>

<FaqItem question="What is Redis? Do I need another database?">

Redis is a fast, in-memory key-value store that sits next to MongoDB like a sticky note beside a filing cabinet. The server checks the sticky note first (a cache hit — instant return), and only walks to the filing cabinet when the note is empty (a cache miss). In this course Redis holds cached catalogue JSON and, from Chapter 22, job queues for background work. MongoDB stays your **source of truth** for products, orders, and users — Redis is a helper that makes repeat reads faster, never a replacement.

</FaqItem>

<FaqItem question="Why not just make MongoDB faster instead of adding a cache?">

MongoDB isn't slow here — the problem is *repeating the same work*. If fifty people open `/shop?page=1` in a minute and the product list hasn't changed, that's fifty identical queries with populates. A cache turns fifty warehouse trips into one: the first request fetches from MongoDB and saves the answer, and the next forty-nine read the saved copy. You're not improving the database; you're stopping it from doing work it already did. That's why caching targets read-heavy data like the catalogue, never carts or orders.

</FaqItem>

<FaqItem question="What if a vendor changes a price and the cache still shows the old one?">

That's the **stale cache trap**, and Chapter 21.2 covers it in depth. The fix is invalidation: when a product is created, updated, or deleted, the server deletes the matching cache keys so the next request re-reads MongoDB. TTL (time to live) alone eventually fixes it, but "eventually" means customers can see a wrong price for minutes — unacceptable in a marketplace where vendors edit prices daily. Production caches combine both: invalidation for correctness, TTL as the safety net.

</FaqItem>

<FaqItem question="Will my app break if Redis isn't running?">

Not if you implement fallback, which this chapter requires in 21.14. Your cache layer should treat a Redis connection failure as a "skip caching" signal, not a crash: try Redis, and on failure go straight to MongoDB. The gate literally tests this — stop Redis, and the catalogue must still load, just slower. That fallback is the difference between a cache that speeds things up and a single point of failure that takes your shop down.

</FaqItem>

<FaqItem question="Is this the same Redis used in Chapter 22?">

Yes — one Redis server does both jobs. Catalogue cache keys use a `catalogue:*` prefix, while Chapter 22's BullMQ job queues use `bull:*` keys. Both share the same `REDIS_URL`; the prefixes keep them separate. That's also why you must never use `FLUSHALL` to clear cache — it would destroy unrelated queue data too. Prefixed keys let you delete exactly what you own and nothing else.

</FaqItem>

<FaqItem question="Do customers ever see the cache in the UI?">

No — caching is invisible server-side plumbing. Nothing about the shop page changes; the same products render from the same API. What customers might notice is that repeat visits feel snappier, and that the shop still works when Redis is down. That's the real goal of Chapter 21: not new features, but the difference between a demo that works for you and an app that stays fast when fifty people browse dairy at once.

</FaqItem>

</FaqGroup>
