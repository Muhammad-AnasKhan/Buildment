Pick **one deploy path** for this course. Document in README — not every option.

This decision affects how you set env vars, run the worker, and renew TLS. There is no universally "best" choice — only **best for your comfort level**.

## Options comparison

| Approach | Examples | Pros | Cons |
|---|---|---|---|
| PaaS API | Render, Railway, Fly.io | Fast TLS, env UI, git deploy | Cost, cold start on free tier |
| PaaS client | Vercel, Netlify | Easy static deploy, auto HTTPS | CORS must match production client URL |
| VPS | DigitalOcean, Hetzner, EC2 | Full control, strong viva story | You manage TLS, PM2, firewall |
| All-in-one VPS | Nginx + API + static + worker | One bill, one machine | More setup steps |

## Course recommendation

**Beginners:** API on Render/Railway + client on Vercel + **worker as second Render/Railway service** — fastest HTTPS, least Linux admin.

**Comfortable with Linux:** Single VPS + Caddy/Nginx + Let's Encrypt + PM2 for API and worker — best "I understand the full stack" viva story.

**Mandate:** HTTPS on both client and API. HTTP-only gate fails.

## Worker deployment per path

| Path | How worker runs |
|---|---|
| Render / Railway | Second service, same repo, start command `npm run worker` |
| VPS + PM2 | `pm2 start src/worker.js --name worker` + `pm2 save` |
| Fly.io | Second process in `fly.toml` or separate app |

**Never** assume checkout notifications work without verifying worker service in host dashboard.

## CORS production

Update `app.js` CORS `origin` to production client URL — not `localhost:5173` only.

Typical env key: `CLIENT_ORIGIN=https://app.yourdomain.com`

Browser login fails with cryptic CORS errors if this still points at local dev.

## MongoDB Atlas

Allow deploy host IP or use `0.0.0.0/0` with strong password for PaaS (IPs change). Document security tradeoff in learning log.

Worker and API **both** need `MONGODB_URI` if processor loads User/Order documents.

## In plain English

| Term | Simple meaning |
|---|---|
| **PaaS** | Platform runs the server for you — you push code, they handle machine |
| **VPS** | You rent a virtual Linux computer — you install Node, nginx, PM2 yourself |
| **Static host** | Serves pre-built HTML/JS/CSS files — no Node server for React in production |

## Think of it like housing

**PaaS** = furnished apartment — utilities included, less control, faster move-in.

**VPS** = empty flat — you bring furniture (nginx, PM2, certs), but you own the layout.

Both are valid homes for FreshMarket. Pick one and document it — do not half-deploy on three platforms.

## Common beginner questions

<FaqGroup>

<FaqItem question="Can I deploy client and API on the same Vercel project?">

Not the Express API and worker. Vercel is built for static sites and serverless functions, which don't fit a long-running Express server or a worker process that must stay alive to watch Redis. The typical split is Vercel for the built React client, and Render or Railway for the API plus a second worker service. You're not picking one host — you're picking where each of the three pieces lives.

</FaqItem>

<FaqItem question="Do I need a custom domain?">

No — the gate passes with platform HTTPS URLs like `*.onrender.com` and `*.vercel.app`. A custom domain is portfolio polish, not a requirement. What *is* required is HTTPS: an HTTP-only URL fails the gate, because secure cookies and professional demos both need the padlock. If you add a domain later, it's configuration on top of the same app, not a re-architecture.

</FaqItem>

<FaqItem question="What is a cold start?">

Free PaaS tiers put services to sleep after they've been idle for a while. The next request has to wake the machine and boot your app first, so the first hit can take 30–60 seconds instead of milliseconds. It's not a bug in your code. If your health check is slow after idle, retry it once before worrying — and mention it in your learning log so evaluators aren't surprised.

</FaqItem>

<FaqItem question="How do I decide between PaaS and VPS?">

Match the choice to your comfort level, not to what sounds impressive. PaaS (Render, Railway) is a furnished apartment: HTTPS and env vars are handled, you push code and move in fast. A VPS is an empty flat: you install Node, nginx or Caddy, PM2, and TLS yourself — more setup, but you understand every layer, which makes a stronger viva story. The course requires only that you pick one path, document it, and not half-deploy on three platforms.

</FaqItem>

<FaqItem question="Why does CORS need the production client URL?">

CORS is the browser's rule for which origins may call your API. If your API only allows `localhost:5173`, the deployed site at `https://app.yourdomain.com` gets blocked, and login fails with those confusing "blocked by CORS policy" errors. So you set the CORS `origin` in `app.js` — or `CLIENT_ORIGIN` in env — to the production client URL. It's one of the most common deploy bugs: the app works locally, then mysteriously breaks in production.

</FaqItem>

<FaqItem question="Why is the React app called \"static\" in production?">

Because after `npm run build`, your React app is just a folder of HTML, CSS, and JavaScript files in `client/dist/` — no Node server needed to serve them. A static host like Vercel stores those files and serves them fast; the React code runs in the browser. That's also why `VITE_API_URL` must be correct at build time: the bundle is frozen, and the static host serves exactly what you built.

</FaqItem>

</FaqGroup>


## ✅ Do / ❌ Don't

**✅ Do:** Match `VITE_API_URL` to deployed API including `https://`.

**✅ Do:** Deploy worker as explicit second service — not an afterthought.

**❌ Don't:** Deploy API without setting all env vars on host.

**❌ Don't:** Leave CORS on localhost only.
