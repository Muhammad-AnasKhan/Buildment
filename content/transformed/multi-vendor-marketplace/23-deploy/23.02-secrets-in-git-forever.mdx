Before deploy, re-run Chapter 4 discipline at production scale. **`git log -- .env` must be empty.** Production credentials pasted into README or learning log disqualify the gate.

Deploy amplifies every secret leak — a key in Git history can be scraped by bots within minutes of a public push. This sub-chapter is the **audit** before you touch a host env panel.

## Why this matters for first-time deployers

| Mistake | Real consequence |
|---|---|
| Commit `server/.env` "just once" | Key lives in Git history forever unless rotated |
| Paste `MONGODB_URI` in README | Anyone with repo access owns your database |
| Put `JWT_SECRET` in client `VITE_*` | Bundled into JavaScript — visible in browser DevTools |
| Screenshot host panel with values | Portfolio post leaks production creds |

**Environment variables on the host** are the production version of `.env` — same keys, different values, never committed.

## Production secret inventory

| Variable | Host | Never in |
|---|---|---|
| `MONGODB_URI` | API server env | Git, client bundle |
| `JWT_SECRET` / refresh pepper | API server env | Git |
| `CLOUDINARY_*` | API server env | Git |
| `REDIS_URL` | API server env **and worker** | Git |
| `VITE_API_URL` | **client build** env | Committed `.env` with prod URL ok in CI secret — not passwords |

## Pre-deploy verification

```bash
git log --all --full-history -- "**/.env"
git check-ignore -v server/.env client/.env
```

Rotate any secret ever committed — new Atlas password, new JWT secret, invalidate old tokens.

## `.env.example` completeness

Gate 23.8 requires **every** production variable documented with placeholder — teammates reproduce deploy without guessing.

`.env.example` is **committed**. `.env` is **not**. The example file is a map, not a vault.

## Host env panels

Render, Railway, Vercel, VPS `/etc/environment` or PM2 ecosystem — **same keys** as local, **different values**.

Screenshot host env panel for yourself — redact in portfolio.

## In plain English

| Term | Simple meaning |
|---|---|
| **Secret** | Password, API key, connection string — anything that grants access if leaked |
| **`.env.example`** | Template showing **which** variables exist — placeholders only |
| **Rotate** | Change a leaked secret to a new value — old one stops working |

## Common beginner questions

<FaqGroup>

<FaqItem question="I accidentally committed `.env` once. Am I fine if I delete it now?">

No — deleting the file does nothing, because Git history keeps every version forever. Anyone who cloned the repo at any point still has those values, and scraping bots may too. The fix is rotation: change every secret that was in the file (new Atlas password, new `JWT_SECRET`) so the old values stop working. Rewriting history with `git filter-repo` is possible, but only try it if your mentor advises — rotation is usually enough.

</FaqItem>

<FaqItem question="Can I commit production `VITE_API_URL`?">

The URL itself is usually fine to commit — it's already visible in your browser's Network tab whenever anyone uses the app. The danger is treating client env vars like a secret vault. Anything starting with `VITE_` gets bundled into your JavaScript, so a `VITE_MONGODB_URI` or an API password would be readable by anyone who opens DevTools. URLs are public; credentials are not.

</FaqItem>

<FaqItem question="Does the worker need the same secrets as the API?">

Yes, and this catches a lot of people. The worker is a separate process, so it needs its own env values on the host — especially `REDIS_URL`, because the API writes jobs to Redis and the worker reads them from the same place. And if a processor loads users or orders, it needs `MONGODB_URI` too. A missing env var on the worker looks like "checkout works but no notifications." Chapter 23.8 lists the full set for both.

</FaqItem>

<FaqItem question="Why is `.env.example` committed but `.env` never is?">

Because they serve opposite purposes. `.env.example` is a map: it lists which variables your app needs, with placeholders, so any teammate — or future you — can create a real `.env` from it. `.env` is the vault: it holds real credentials, so it must stay out of Git. The gate checks both: `git log -- "**/.env"` must be empty for secrets, and `.env.example` must be complete with no real values in it.

</FaqItem>

<FaqItem question="What does it mean to \"rotate\" a secret?">

Rotation means replacing a possibly-leaked secret with a brand-new one so the old value no longer grants access. If a `MONGODB_URI` ever hit Git, you'd create a new Atlas database user and update the host env panel; if `JWT_SECRET` leaked, you'd generate a new one — which also invalidates old tokens. It's like changing the locks after losing a key: the leaked copy becomes useless, and the damage stops.

</FaqItem>

</FaqGroup>


## ✅ Do / ❌ Don't

**✅ Do:** Use separate MongoDB user for production.

**✅ Do:** Restrict Atlas IP to deploy host or `0.0.0.0/0` with strong password — document tradeoff in learning log.

**❌ Don't:** Commit production `.env` "just once".

**❌ Don't:** Put `MONGODB_URI` in client `VITE_*`.

## Self-check

- [ ] Git history clean for `.env`
- [ ] Production secrets only on host (or gathered, not committed)
- [ ] `.env.example` files exist and have no real values
