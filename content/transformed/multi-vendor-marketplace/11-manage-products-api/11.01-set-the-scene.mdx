**Where the project is now:** Vendors have shops — API and UI from Chapters 9–10. A store document exists with `vendorId`. The Product model from Chapter 5 waits in `modules/products/` with grocery fields, but there is no **vendor product API** — no way to stock the shelves programmatically.

**Where this chapter goes:** Vendors **CRUD their own products** through protected routes — create, list mine, update, delete — with **store ownership** enforced and **cross-vendor PATCH → 403**.

This is a **build chapter**. Sub-chapters 11.7 onward add routes and service logic. The gate is curl-proof vendor product lifecycle plus isolation test.

## Bridge from last chapter

Chapters 9–10 gave vendors a **shop** — API and browser forms, with an onboarding gate blocking dashboard routes until a store exists. The Product model from Chapter 5 sits in MongoDB, but there is no way to **stock the shelves** yet. Chapter 11 adds vendor product CRUD on the server, reusing Chapter 8's ownership pattern: Vendor B must get **403** on Vendor A's kale. Same isolation discipline, new resource type.

| Term | Simple meaning |
|---|---|
| **Vendor inventory** | Products a seller manages — drafts, prices, stock |
| **Public catalogue** | Products shoppers browse — built in Chapter 14, not here |
| **`POST /products`** | Create a product linked to the vendor's store |
| **`GET /vendor/products`** | List only **my** products — not everyone's |
| **`storeId`** | Field tying each product to one store |
| **Ownership chain** | User → Store → Product — the path your guards follow |
| **`isPublished`** | Draft vs live flag — customers won't see drafts in Week 3 |

## Think of it like stocking a stall

The vendor signed the lease (Ch 10) and has an empty stall with a nameplate. Chapter 11 is **filling the shelves via the stockroom door** — API only, no shop window yet. Each crate (product) is tagged with which stall it belongs to. Another vendor cannot relabel your crates because the warehouse checks the ownership chain on every move.

## Common beginner questions

<FaqGroup>

<FaqItem question={"Why not let customers see products in this chapter?"}>

Because vendor inventory and the public catalogue are two different audiences with two different routes. The inventory routes here — `GET /vendor/products`, `POST /products` — are authenticated and scoped to the vendor's own store. The catalogue shoppers browse is an unauthenticated read built in Chapter 14. If you mixed them early, you'd have to solve filtering and privacy (drafts!) before the vendor API even exists. Same Product collection, two doors: the stockroom door for vendors now, the shop window for customers later.

</FaqItem>

<FaqItem question={"Can the client send `storeId` in the POST body?"}>

No — never trust the client to say which store a product belongs to. The server resolves the store from the authenticated JWT (`req.user.id` → the vendor's store) and links the product to that. If you accepted a `storeId` in the body, Vendor B could simply pass Vendor A's store id and stock a product on someone else's shelf — a textbook IDOR vector. This is the same principle as Chapter 9's `GET /stores/me`: the caller's identity, not a client-supplied id, decides ownership. Server-derived truth, always.

</FaqItem>

<FaqItem question={"What if a vendor has no store and tries to create a product?"}>

Reject the request — there's no shelf to stock. The route resolves the vendor's store from the JWT first; if none exists, it returns an error (404 "no store" or 403, depending on the choice you document in `docs/AUTHORIZATION.md`). This rule is why Chapter 10's onboarding gate matters: a real vendor is forced to open a shop before reaching product pages, so the UI rarely hits this case. But the server still enforces it, because curl doesn't care about your React gate.

</FaqItem>

<FaqItem question={"Is delete a hard delete?"}>

Yes, in this course. `DELETE /products/:id` removes the document from MongoDB for real. Hard delete is simple and matches an MVP, but note the tradeoff: if an order later references a deleted product, that link can break — which is why production systems often use a soft delete (a `deletedAt` flag or status) to keep history. The course picks hard delete to keep Chapter 11 focused on CRUD mechanics; write the tradeoff in your learning log so you remember it was a deliberate choice, not an accidental one.

</FaqItem>

<FaqItem question={"How does publish/unpublish work?"}>

Through a single boolean: `isPublished`. New products default to `false`, so they're drafts — saved and editable in the vendor's inventory but invisible to shoppers. Publishing is a `PATCH /products/:id` that sets `isPublished: true`; unpublishing flips it back. You'll build the toggle UI in Chapter 12; the API's job here is to let the owner change the flag safely, with the ownership check applied just like any other PATCH. The rule that matters later: Chapter 14's public catalogue must only ever show published products.

</FaqItem>

<FaqItem question={"Do I need the dashboard UI to test this chapter?"}>

No — curl is enough, same as Chapter 9. You'll register (or seed) two vendors with stores, log in for Bearer tokens, and prove the full lifecycle: create a product, list mine, update it, delete it, and confirm Vendor B gets 403 when PATCHing Vendor A's product. Testing through the API forces you to understand the contract — routes, JSON shapes, status codes — before the UI hides it behind forms. Chapter 12 then wires React to these exact shapes. If it works in curl, later UI bugs are UI bugs — a clean separation.

</FaqItem>

</FaqGroup>
