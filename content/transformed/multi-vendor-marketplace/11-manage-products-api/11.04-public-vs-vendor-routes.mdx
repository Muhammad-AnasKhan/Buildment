Route **naming and mount order** prevent accidental exposure of vendor inventory on public paths. This sub-chapter specs how Chapter 11 routes coexist with Chapter 14 stubs in `app.js`.

<BigWordAlert term="Route visibility" plainEnglish="Some endpoints are anonymous (browse); others require vendor auth and ownership checks." whyItMatters="FreshMarket public catalogue never exposes unpublished products or vendor-only fields." />

## Namespace strategy

The same `products` resource is spoken to by two very different audiences: a vendor managing their inventory, and a customer browsing the catalogue. Giving each audience its own namespace keeps their rules separate — you protect vendor routes with auth while leaving public routes open, without ever mixing the two stacks in one path.

| Namespace | Mount | Chapter |
|---|---|---|
| Vendor writes | `/api/products` POST, PATCH, DELETE | 11 |
| Vendor reads | `/api/vendor/products` GET | 11 |
| Public reads | `/api/products` GET | 14 |

**Collision note:** `POST /api/products` and future `GET /api/products` share path — different verbs — OK in REST.

Register routers so **vendor-specific paths** (`/vendor/products`) are not captured by `/:id` param routes incorrectly.

## Router organization options

Express gives you two ways to organize the same code, and the choice is about future maintenance more than today's feature. One router keeps everything in one file while it is small; split routers isolate the public surface from the vendor surface as the app grows.

| Option | Structure |
|---|---|
| A — single products router | All verbs in `products.routes.js` |
| B — split routers | `vendorProducts.routes.js` + `publicProducts.routes.js` in Ch 14 |

**Course default:** Option A for Ch 11 — add public GET handlers in same module Ch 14 with clear comments.

## Middleware stacks

Every vendor route runs the full security stack from Chapter 8 — the middleware does not care whether the resource is a store or a product, which is exactly why it is reusable. Notice that `GET /vendor/products` and the write routes carry the same auth layers; the only new check is ownership on routes that touch a specific product id.

| Route | Middleware |
|---|---|
| POST /products | requireAuth → requireRole('vendor') → validate → handler |
| GET /vendor/products | requireAuth → requireRole('vendor') → handler |
| PATCH /products/:id | requireAuth → requireRole('vendor') → assertProductOwner → handler |
| DELETE /products/:id | same as PATCH |

Customer calling vendor routes → **403**.

## Ownership check strategies

A product is owned *through* its store. There are two ways to check that chain, and the difference is where the `vendorId` lives — on the store document (the ERD's single source of truth) or copied onto the product. Duplicating it is faster but invites drift; the store chain keeps one source of truth.

| Strategy | How |
|---|---|
| **Store chain** | Load product → compare `product.storeId` → store.vendorId === userId |
| **Denormalized vendorId** | If product has vendorId field — compare directly |

Prefer **store chain** — matches ERD; one source of truth.

Helper name examples: `assertProductOwner`, `assertStoreOwnsProduct`.

## Body tampering vectors

A naive POST /products lets the client dictate *whose* store the product belongs to — the exact hole Chapter 8 taught you to close. The rules below are the authorization contract for the request body, and each one is enforced server-side, not by hiding fields in the UI.

| Field | Rule |
|---|---|
| `storeId` | Strip from POST/PATCH body — set on create from vendor's store |
| `vendorId` | Never on product — reject if sent |
| `price` | Vendor can set — validate positive number |

## Response shapes

The vendor and public views of a product differ deliberately: back office returns the full document, while the shop window (Chapter 14) will trim internal fields. Deciding this now means Chapter 14 adds a serializer instead of rewriting the route.

**Vendor list item:** full product document for own inventory.

**Public item (Ch 14):** may omit internal fields — not defined here.

## AUTHORIZATION.md rows

These four rows are the chapter's contract — the same shape as Chapter 8, now applied to products. Add them to `docs/AUTHORIZATION.md` before building, then the routes simply implement what the matrix already promised.

| Action | Role | Check |
|---|---|---|
| POST /products | vendor | auth + resolve store |
| GET /vendor/products | vendor | auth + store scope |
| PATCH /products/:id | vendor | auth + product ownership |
| DELETE /products/:id | vendor | auth + product ownership |

## Common beginner mistakes

1. **Mounting `/products/:id` before `/vendor/products`** — Express matches in order, so `vendor` gets parsed as a product id. Mount the more specific path first.
2. **Accepting `storeId` in the body** — a vendor can quietly create a product in another vendor's store. Derive `storeId` from the token.
3. **Adding the public `GET /products` in Chapter 11** — you do not have the draft/published filtering yet, and shipping it now means rebuilding it in Chapter 14.
4. **Skipping the ownership check "because POST already validates the vendor"** — the check that stops Vendor B editing Vendor A's product is `assertProductOwner`, not the role check.

## ✅ Do / ❌ Don't

**✅ Do:** Mount `/vendor/products` **before** `/products/:id` if on same router — avoid "vendor" parsed as id.

**✅ Do:** Document verb split in README.

**❌ Don't:** Add `GET /products` public list in Ch 11.

**❌ Don't:** Let vendor pass another store's id in POST body.
