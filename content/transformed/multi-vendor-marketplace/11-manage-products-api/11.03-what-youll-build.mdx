By Chapter 11 gate, vendors **CRUD products on their store** via API; cross-vendor mutation returns **403**; list is scoped to authenticated vendor's inventory only.

<BigWordAlert term="Products CRUD API" plainEnglish="Full create-read-update-delete routes for product documents scoped to the vendor's store." whyItMatters="Chapter 12's dashboard forms call these endpoints — API must exist before UI." />

Chapter 9 gave vendors a store; Chapter 10 let them open it in the browser. A store with nothing to sell is a store that earns nothing — so now the vendor needs to fill it: create, list, update, and remove products, scoped to their own store and nothing else. That last part is the real lesson: every endpoint here inherits the ownership checks you built in Chapter 8.

## API surface (Chapter 11)

Four endpoints, two audiences. All four require a vendor role; the difference between them is the ownership check on the ones that address a specific product id.

| Method | Path | Auth | Role | Purpose |
|---|---|---|---|---|
| POST | `/products` | yes | vendor | Create product on own store |
| GET | `/vendor/products` | yes | vendor | List own inventory |
| PATCH | `/products/:id` | yes | vendor | Update own product |
| DELETE | `/products/:id` | yes | vendor | Remove own product |

Prefix `/api` per your convention.

## POST /products — spec highlights

This is the route where the ownership pattern from Chapter 8 becomes a data-model decision. The client must never say whose store the product belongs to — the server resolves it from the token. Read each rule as "who decides this?" and the answer is always the server.

- Resolve vendor's store via `getStoreByVendorId` — no store → 404 or 403  
- Set `storeId` server-side — reject `storeId` in body from client  
- Validate grocery + price fields  
- Default `isPublished: false` if applicable  

## GET /vendor/products — spec highlights

The vendor list is scoped to the caller's own inventory — never to an id the client passes. That single scoping decision is what makes this route safe to build now and keeps it from leaking drafts to the public catalogue later.

- Query `{ storeId: vendorStoreId }`  
- Optional query params later: `?published=true` — not required for gate  
- Sort by `createdAt` desc — reasonable default  

## PATCH / DELETE — spec highlights

Both write routes run the same ownership check before touching the database. This is Chapter 8's `assertProductOwner` applied to a second resource — if you built the helper well in Chapter 8, this is just a new call site.

- `assertProductOwner(productId, vendorId)` or store-chain check  
- Vendor B on Vendor A product → **403**  
- Invalid id → 404

## Testing plan (11.13)

The order below is deliberate: prove the happy path with Vendor A first, then prove isolation by swapping in Vendor B on the *same* ids. A failing 403 here is a bug — a passing 403 is the whole chapter working.

1. Vendor A creates product → 201  
2. Vendor A lists → includes product  
3. Vendor A PATCH → 200  
4. Vendor B PATCH same id → 403  
5. Vendor A DELETE → success  
6. Vendor B DELETE → 403
