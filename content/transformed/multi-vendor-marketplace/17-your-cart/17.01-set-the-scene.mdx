## Bridge from last chapter

Chapter 16 gave you a **persisted cart API** — add, list, update quantity, remove — scoped to the logged-in user, with **`storeId` on every line** and stock checks on write. You proved it with curl: User A cannot touch User B's items; one cart can hold products from two stores.

What Chapter 16 did **not** give you: anything the customer **sees**. No cart page, no header badge, no working "Add to cart" on product detail.

What you carry into Chapter 17:

| From Chapter 16 | What the UI wires to |
|---|---|
| `GET /cart` with populated product + store | Cart page rows and store headings |
| `POST /cart` | Product detail "Add to cart" button |
| `PATCH /cart/:itemId` | Quantity steppers |
| `DELETE /cart/:itemId` | Remove line buttons |
| `storeId` grouping contract | Visual sections per vendor — same split checkout will use |

## In plain English

| Term | Simple meaning |
|---|---|
| **Cart page** | `/cart` — lists everything the customer intends to buy |
| **Grouped by store** | UI sections: all Green Valley items together, all Harbor Market items together |
| **Store subtotal** | Sum of line totals **within one vendor's section** |
| **Cart badge / icon** | Header number showing how many items are in the cart |
| **Refetch after mutation** | After PATCH or DELETE, call `GET /cart` again — do not trust stale React state |
| **Protected route** | `/cart` redirects to login if no customer token — same pattern as Chapter 7 |

## Think of it like reading your basket before checkout

Chapter 16 put items **in the basket** (database). Chapter 17 lets the customer **look inside the basket** — see which stall each item came from, change quantities, remove mistakes — before walking to checkout.

If the cart UI groups by store now, checkout (Chapter 20 UI) will not surprise the customer with "wait, this becomes two orders?" They already saw the split.

## Common beginner questions

<FaqGroup>

<FaqItem question="Why build the cart page after the API?">

Because the contract must exist before the screen that uses it. In Chapter 16 you proved `GET /cart`, `POST /cart`, `PATCH /cart/:itemId`, and `DELETE /cart/:itemId` with curl — including user isolation and multi-vendor adds. By the time Chapter 17 starts, the response shape is known, so the page is mostly wiring: fetch the cart, render rows, call the endpoints on clicks. Build the UI first and you'd be inventing endpoint names and shapes that might not match the server — rework you'd throw away.

</FaqItem>

<FaqItem question="Should I group cart items in the API or in React?">

In React, and only for display. The API returns a flat `items` array — each line with its `productId`, `storeId`, `quantity`, and populated product and store details. The cart page reads each line's `storeId` and builds visual sections: all Green Valley items under one heading, all Harbor Market items under another. Grouping in React keeps the API simple and reusable. Checkout in Chapter 18 will do its own *server-side* grouping by `storeId` when it creates one order per vendor — a different job for a different layer.

</FaqItem>

<FaqItem question="How do the quantity steppers actually change the cart?">

Each +/− button (or number input) calls the API: `PATCH /cart/:itemId` with the new `&#123; quantity &#125;`. The server updates that line and returns the fresh cart, then your UI **refetches `GET /cart`** and re-renders — the course calls this "refetch after mutation". Never let the displayed number drift from the database. If quantity reaches zero, or the user clicks remove, call `DELETE /cart/:itemId` to drop the line entirely. The stepper is just a button that speaks the API's language.

</FaqItem>

<FaqItem question="Are the totals on the cart page final prices?">

No — treat them as estimates. The cart page computes line totals and per-store subtotals from the *current* product prices returned by `GET /cart`'s populate. Real orders freeze prices: checkout in Chapter 18 takes a price snapshot onto each order line, so what you pay is locked at checkout, not when you're browsing. That's why the page uses "subtotal" language rather than presenting a final invoice — prices could shift between adding to cart and paying.

</FaqItem>

<FaqItem question="For the header badge, do I count lines or total quantity?">

Either — just pick one and stay consistent. "3" could mean three cart *lines* (rows) or three total *items* (the sum of quantities, where one line with 2 units plus one line with 1 unit equals 3). The badge is a quick glance indicator, so what matters is that it matches the cart from `GET /cart` and updates after every mutation. Document your choice in the README so the Week 3 demo doesn't leave anyone guessing whether the number is right.

</FaqItem>

<FaqItem question="Add to cart fails with 401 — what now?">

401 means "not authenticated" — the cart API is scoped to a logged-in user, so a missing or expired token is rejected. The fix is a login redirect: when the add-to-cart call returns 401, send the customer to the login page, and ideally remember the product so they can return to it after logging in. Minimum for the gate: login happens before the add works. It's also a good lesson in reading status codes — 401 asks "who are you?", while 403 would mean "what are you allowed to do?".

</FaqItem>

</FaqGroup>


## The gap between "cart in the database" and "cart in the customer's head"

Right now your marketplace can answer:

- What items does User X have in their cart? (API)
- Is stock sufficient to add? (API)

It cannot answer in the browser:

- How many items am I carrying?
- Which store is each line from?
- What is my subtotal per vendor before checkout?

Those are **presentation and interaction** problems — not persistence problems. Chapter 18 splits checkout by `storeId`; **Chapter 17 teaches the customer to see that split before they pay.**

## Why this chapter sits after Cart API

Chapter 16 enforced **contracts** — user scoping, `storeId` on every line, stock check on add. Building UI first would have produced a pretty page calling endpoints that don't exist, or worse, client-side-only carts that vanish on login.

Chapter 17 assumes:

- Cart API tested via curl or API client (Chapter 16 gate)
- Customer auth works (Chapter 7)
- Product detail page exists with add-to-cart stub (Chapter 15)

If Chapter 16 gate is incomplete, finish API scoping and multi-vendor add tests first.

## What "your cart" means in product terms

A grocery customer shops across **multiple local vendors** in one session. The cart page must:

| Concern | UI behaviour | API backing |
|---|---|---|
| Grouping | Sections per store name | `storeId` on each cart line |
| Line display | Name, unit, price, quantity | Populated product from `GET /cart` |
| Subtotal | Per-store and optional grand total | Client-side math from line prices |
| Quantity | Stepper or input → PATCH | `PATCH /cart/:itemId` |
| Remove | Button → DELETE | `DELETE /cart/:itemId` |
| Persistence | Reload keeps items | Server cart, not localStorage |

**Not client-side cart:** Browser memory alone breaks the Week 3 demo when the customer switches devices or clears cache.
