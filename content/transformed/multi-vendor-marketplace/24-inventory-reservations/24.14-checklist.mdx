# 24.14 — Checklist and learning log

Tick every box honestly before Chapter 25.

## Chapter 24 checklist

- [ ] `StockReservation` model with `active` / `confirmed` / `released`
- [ ] Product has a backfilled `reservedQty` counter with default `0`
- [ ] Unique index on `(checkoutId, productId)` and sweep index on `(expiresAt, status)`
- [ ] Checkout claims `reservedQty` with one guarded write; 409 when ATP is insufficient
- [ ] Multi-line claim and reservation inserts run in one transaction
- [ ] `payment_intent.succeeded` confirms and decrements `stockQty` plus `reservedQty` atomically
- [ ] Cancel / clear cart **releases** active holds for `checkoutId`
- [ ] Cancel and expiry release `reservedQty` without changing `stockQty`
- [ ] Worker reuses the domain release service and is safe to retry
- [ ] Product APIs expose `availableQty` (or equivalent computed field)
- [ ] Parallel checkout test documented (one success, one failure on last unit)
- [ ] TTL test documented (hold releases, stockQty unchanged)

## Learning log

1. **Two moments:** Why reserve at checkout start but decrement only on payment success?

2. **Worker safety:** How does conditional `status: 'active'` prevent double-release or confirm races?

3. **Concurrency:** Why can “aggregate active holds, then insert a reservation” still oversell even inside a transaction?

4. **Ops:** What do you log if payment succeeds but `$inc stockQty` fails?
