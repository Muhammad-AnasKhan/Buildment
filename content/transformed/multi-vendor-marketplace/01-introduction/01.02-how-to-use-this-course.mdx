# 1.2 — How to use this course

> **[Read]** · Chapter 01 — Introduction · *Chapters in order; checklist gate; learning log; how you're judged*

This is not a tutorial you copy-paste from start to finish. It's a **guided build**: each chapter teaches an idea in depth, compares the approaches a professional would weigh, and then walks you through implementing it on **your own project** — one folder, one file, one verification step at a time. You write the logic. The course tells you what it must do, what to avoid, and how to know it's working.

Read this section carefully. Everything else in the course assumes you understand how progress works here.

## If you're newer to full-stack — how to read this course

You do **not** need to already know MongoDB, JWT, Redis, or deployment. You **do** need patience to read the **Learn it** sections before the **Build it** steps.

**Read in this order within each chapter:**

1. **Set the scene** — where your repo stands; don't build yet
2. **Why it matters / What you'll build** — understand the goal
3. **Learn it** — concepts and trade-offs; use **In plain English** boxes
4. **Prime your thinking** — skim mandatory links
5. **Build it** — one sub-chapter at a time; verify before the next
6. **Gate** — checklist + learning log in the platform before the next chapter

**When you're stuck:**

| Symptom | What to do |
|---|---|
| "I don't understand the words" | Re-read **In plain English** in that sub-chapter |
| "Build step failed" | Read **Troubleshooting**; compare to "Where the project is now" |
| "Chapter feels like a jump" | Read **Bridge from last chapter** at the top |
| "I want to skip ahead" | Don't — later chapters assume earlier gates |

**Two folders, two jobs:** `server/` is your API. `client/` is the browser UI. They talk over HTTP.

## Step type labels

Every lesson shows a step type badge (Read, Learn, Build, Check, Gate) so you know what kind of step you are on:

| Label | What to do | Touch your repo? |
|---|---|---|
| **Read** | Orient — set the scene, why it matters | No |
| **Learn** | Understand concepts and trade-offs | No |
| **Build** | Hands-on — create files, wire routes, verify | **Yes** |
| **Check** | Quiz — MCQ and short-answer questions in the platform | No |
| **Gate** | Checklist + learning log — complete in the platform before the next chapter | Review only |

Read **[Read]** and **[Learn]** lessons fully before **[Build]** steps in the same chapter. On **[Gate]** lessons, use the checklist and answer fields at the bottom of the page — do not open the next chapter until you mark the current one complete.

Use the **sidebar** to move through lessons in order — work top to bottom within each module.

## The shape: course → chapters → lessons

One project: **your multi-vendor grocery marketplace.** One repository with `server/` and `client/`. One deployed URL at the end.

This course has **22 build chapters** (Chapters 2–23) plus this introduction and a closing chapter. Chapters are grouped into **four weeks** at full-time pace:

| Week | Name | Demo target |
|---|---|---|
| Week 1 | Foundations | Both apps run; MongoDB seeded; health check in browser |
| Week 2 | Vendor experience | Vendor opens shop, lists products with photos |
| Week 3 | Buyer experience | Customer browses, carts, pays with Stripe test card |
| Week 4 | Polish & ship | Cache, search, async jobs, live HTTPS URL |

Week labels are **checkpoints**, not folder names. If Week 2 ends and no vendor can add a product in the UI, Week 3 is not where you fix that.

Inside every chapter, you work through **lessons** in order — small, finishable steps following: open & motivate → learn it → build it → wrap → gate.

## How a chapter reads — the rhythm you'll repeat

**1. Set the scene.** Where the project stands and what this chapter adds.

**2. Learn it.** The concept, weak vs strong approaches — taught in prose first.

**3. Build it.** Exact folder and file, contract not implementation, verify steps.

**4. Gate.** Observable outcomes + learning log answers in the platform.

Concept chapters run shorter on *Build it* but still include applied work on your repo.

## The checklist is a gate — the most important rule

Every chapter ends in a **gate** — a Definition of Done checklist plus learning log questions **in this platform**.

**You do not move to the next chapter until every box is ticked and every learning log answer is written.**

- Each item must be something you can **see or demo**
- Skipping the gate means the next chapter builds on something that isn't there
- Phrase it as: **"All boxes ticked? Mark chapter complete. If not, that's today's work."**

## Learning log — in the platform

At the end of each chapter gate, you'll answer questions about decisions and trade-offs **here in the course platform**. Your answers are saved in your browser (PostgreSQL sync comes later).

This is evidence you cleared the gate with understanding — rehearsal for the final viva.

## How you're judged

You're evaluated on **understanding**, not just a running demo.

**During the course:** gates keep you honest chapter by chapter.

**At the end:** a **viva** — you walk through how your marketplace works and what would break it.

**AI tools:** You may use Cursor, Copilot, or similar. The viva checks that **you** can explain what you committed.

## Specs, not solutions

**You will get:** API contracts, folder trees, commands, config sketches, diagrams, measured symptoms.

**You will not get:** route handler bodies, middleware implementations, or copy-paste dashboard components.

## Mandatory reads, topics to read, and hints

**Mandatory reads** — blocking; read before the next build step.

**Topics to read** — recommended depth; not blocking.

**Hints** — nudges when stuck; never solution code.

## When you're stuck — in order

1. Read the error message — full stack trace
2. Read the official docs for the tool throwing the error
3. Explain expected vs actual out loud
4. Try a smaller test — one route, one query
5. Take a short break
6. Ask for help with: *"I expected X, I got Y, I tried Z"*
