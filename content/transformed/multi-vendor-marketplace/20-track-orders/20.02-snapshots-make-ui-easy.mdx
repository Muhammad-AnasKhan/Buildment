Order history UI would be fragile if every row required a live product fetch. **Snapshots mean the list endpoint is the only read** — no N+1 populate for price, no surprise when vendor deletes a product.

Chapter 18 embedded `nameAtPurchase`, `priceAtPurchase`, and `unitAtPurchase` on each order line for exactly this reason. Chapter 20 is where that design pays off in React.

## Why snapshots matter for beginners

Three tempting shortcuts exist, and all three corrupt the receipt. This is the "wrong way" table — read it to recognize the trap, then never build it.

| Approach | What goes wrong |
|---|---|
| Show `product.price` from live lookup | Vendor changes milk from ₹65 → ₹70 — last week's receipt shows ₹70 |
| Fetch `/products/:id` per line | 10-line order = 10 extra requests; product deleted → row breaks |
| Recompute total from catalogue | Order total changes when vendor edits — accounting nightmare |

**Snapshots freeze the truth at purchase time.** The order document is a **receipt**, not a live view of the catalogue.

## Render contract — order line row

Every row in every order UI reads the same embedded fields. There is no alternative source for these values.

| Display | Source field |
|---|---|
| Product name | `nameAtPurchase` |
| Unit price | `priceAtPurchase` + `unitAtPurchase` |
| Quantity | `quantity` |
| Line total | `lineTotal` or `priceAtPurchase * quantity` |

**Forbidden for price display:** `product.price` from populate.

## Order header row

The header layer adds context around those lines — store, total, date, status — none of which come from the product catalogue.

| Display | Source |
|---|---|
| Store name | populated `storeId.name` or `store.name` |
| Order total | `order.total` |
| Date | `createdAt` |
| Status | `order.status` |

## Deleted or unpublished product

`productId` link optional — "View product" may 404. Receipt line still renders from snapshots.

This is a feature, not a bug. Customers keep proof of what they bought even if the vendor delists the item.

## Customer vs vendor same data shape

Both UIs read same `orderItems` structure. Vendor view adds customer name from safe populate on `customerId`.

You build **one** `OrderLineRow` component — reuse on confirmation, customer history, and vendor inbox.

## In plain English

| Term | Simple meaning |
|---|---|
| **Snapshot** | A copy of product name, price, and unit **at the moment of purchase** — stored on the order, not fetched later |
| **Embedded line items** | Order lines live **inside** the order document — not separate Product documents |
| **Populate** | MongoDB join — fine for store **name** on the header; **not** for line prices |

## Think of it like a paper receipt

A paper receipt prints the price **that day**. If the shop raises prices next week, your old receipt does not change. `orderItems` with snapshot fields are that paper receipt — digital, but same rule.

## Common beginner questions

<FaqGroup>

<FaqItem question="Why not just store `productId` and look up the current price when rendering?">

Because prices change, and a receipt must not change after the sale. This is the price snapshot trap from Chapter 18.2: if milk is ₹65 on the day of purchase and the vendor raises it to ₹70 next week, a live lookup would show last week's order at the new price — and the total wouldn't match what was actually paid. That's why Chapter 18 embedded `nameAtPurchase`, `priceAtPurchase`, and `unitAtPurchase` on each order line. The order document is a receipt, not a live view of the catalogue.

</FaqItem>

<FaqItem question="Why is fetching one product per order line such a bad idea?">

Because a 10-line order turns into 10 extra requests — the "N+1 problem", where N is the number of lines. Every extra request adds latency and another chance to fail, and a busy history page multiplies that. Worse: if a product is deleted, that request 404s and the whole row breaks even though the customer genuinely bought the item. Snapshots avoid all of it — the list endpoint becomes the only read needed, returning everything the UI requires in a single response.

</FaqItem>

<FaqItem question="What if the vendor deletes a product I bought?">

Nothing breaks — and that's the whole point of snapshots. The receipt line renders from `nameAtPurchase` and `priceAtPurchase` stored on the order, so it survives even if the product is unpublished or deleted. The `productId` link behind a "View product" button might 404, but the line still displays correctly. That's a feature, not a bug: the customer keeps proof of what they bought even when the vendor delists the item — a protection a live price lookup could never give.

</FaqItem>

<FaqItem question="What if `nameAtPurchase` is missing on an old test order?">

That shouldn't happen for real orders — Chapter 18 writes the snapshot fields on every line — but orders created before that chapter won't have them. Fix it by re-seeding or re-checking out so your gate data has snapshots, and make your UI handle a missing field gracefully anyway, rendering something like "Unknown item" instead of crashing. Handling missing optional fields without breaking a row is good practice in every UI, not just this one.

</FaqItem>

<FaqItem question="Can I use `populate` to get the store name for the order header?">

Yes — that's the one join that's fine. Populating `storeId.name` (or `store.name`) is a single lookup per order rather than per line, and store names change rarely, so there's no stale-price problem. The rule to remember: populate for the order **header** is fine; fetching live product data for **line prices** is forbidden. Because both the customer history and the vendor inbox read the same embedded `orderItems` shape, you build one `OrderLineRow` component and reuse it everywhere.

</FaqItem>

</FaqGroup>


## ✅ Do / ❌ Don't

**✅ Do:** TypeScript/JSDoc optional fields matching API — `nameAtPurchase` required on lines.

**✅ Do:** Format unit in grocery style — `₹120/kg`.

**❌ Don't:** Fetch `/products/:id` per line for history page.

**❌ Don't:** Recompute order total from catalogue.
