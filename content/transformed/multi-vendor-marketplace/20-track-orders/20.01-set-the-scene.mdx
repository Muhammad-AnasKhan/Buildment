## In plain English

| Term | Simple meaning |
|---|---|
| **Checkout page** | Review cart + Stripe card form + Place order |
| **Payment Element** | Stripe's embeddable payment UI — safe card entry on your page |
| **Order confirmation** | "Thank you" after pay — may show **more than one order** if items came from different stores |
| **Order history** | Past orders the customer can return to |
| **Vendor order inbox** | Vendor's list of orders to pack — only **their** store's orders |
| **Order status** | Fulfilment progress — `pending` → `packed` → `dispatched` |
| **Snapshot fields** | Prices and names **frozen at purchase** on each line |

## Think of it like a real grocery run

You filled your basket at two stalls (multi-vendor cart). At checkout you review totals, tap your card on the machine (Payment Element), and the system prints **two receipts** — one per stall.

Chapter 20 builds those screens:

- Customer sees both receipts on confirmation and in order history.
- Each stall owner sees only **their** receipt.
- Status badges update when a stall marks "packed."

## Common beginner questions

<FaqGroup>

<FaqItem question={"Why build the UI after the payment API is done?"}>

Because you want the server contract proven before you build screens that talk to it. If the checkout screen misbehaves, you need to know whether the bug is in your React code or in the API — and if you built and curl-tested the API first in Chapter 19, you already know the answer. It's the same reason this course did login screens after the auth API in Chapters 6–7. Server first, browser second: the browser is the last step that turns a working API into something a human can actually use.

</FaqItem>

<FaqItem question={"Do I need any new payment routes for the checkout page?"}>

No — that's the point of this chapter. Chapter 19 already built the payment routes (gated `POST /checkout`, the Stripe Payment Intent flow, the webhook), so Chapter 20 only wires the browser to them. The new work is frontend: a checkout page that embeds Stripe's **Payment Element** so the customer can enter card details safely, then a call to the existing route. When you add UI on top of proven routes, every bug you meet is easier to isolate — if it fails in the browser but not in curl, the fault is on your page.

</FaqItem>

<FaqItem question={"Why does the confirmation screen sometimes show two orders?"}>

Because one payment can cover products from several stores, and each store fulfils its own part. If a customer buys milk from Vendor A and rice from Vendor B in the same cart, Stripe charges once, but the server splits the cart into two orders — one per store — from the Chapter 18 order engine. So the confirmation page shows two "receipts", and each store owner later sees only their own. A short line like "Each store fulfils separately" stops customers from thinking they were double-charged.

</FaqItem>

<FaqItem question={"Can I show the product's current price on order history instead of what was paid?"}>

No — that would break the receipt. If the vendor raises milk from ₹65 to ₹70 next week, last week's order would suddenly display ₹70, and the total wouldn't match what the customer actually paid. Chapter 18 froze the name, price, and unit on each order line at purchase time (`nameAtPurchase`, `priceAtPurchase`), and Chapter 20's order history must read those snapshot fields only. The receipt always says what it said on the day of the sale — like a paper receipt, which never changes when the shop reprices.

</FaqItem>

<FaqItem question={"What is an order status badge?"}>

A small label on an order card that shows where an order is in fulfilment: `pending` → `packed` → `dispatched`. The vendor moves the order forward — for example, marking it `packed` once they've boxed the groceries — and the customer sees the badge change on their history page after a refresh or poll. It's the visible heartbeat of the whole fulfilment flow: one side acts, the other sees the result. Building one reusable badge component keeps that status display consistent across customer and vendor screens.

</FaqItem>

</FaqGroup>
