<ArticleBreak title="Money enters the building" subtitle="Checkout is a state machine, not a form submit" readMinutes={8}>

Checkout is the most dangerous feature in FreshMarket. Cart totals, inventory, vendor splits, and payment authorization must agree within seconds.

Think in states: cart locked → orders created → payment initiated → payment confirmed → cart cleared. Each transition should be recoverable if the network drops.

Never assume the client saw the Stripe success page. Webhooks in module 19 confirm payment — checkout routes prepare orders; webhooks finalize them.

</ArticleBreak>

## In plain English

| Term | Simple meaning |
|---|---|
| **Checkout** | The server action that turns cart lines into **orders** |
| **Split orders** | One customer click → **multiple order documents** — one per vendor/store |
| **Price snapshot** | Copy of name, price, unit **at purchase time** — receipt never changes when vendor edits catalogue later |
| **Order line** | One purchased item embedded inside an order — with snapshot fields, not live product join |
| **Atomic stock decrement** | Reduce stock in one safe DB operation — two people cannot both buy the last item |
| **Fail-all checkout** | If any line fails stock check, **no orders created** and cart stays intact |
| **Immutability** | After order is created, historical prices on the order do not update |

## Think of it like one register, many stall receipts

The customer stands at **one checkout counter** with one basket (cart). The cashier (your server) looks inside, sorts items by stall (`storeId`), and prints **separate receipts** — Green Valley gets one, Harbor Market gets another. Each receipt lists exactly what that stall must pack, with prices **frozen at that moment**.

The customer walks away with one confirmation ("I ordered"). Each vendor sees **only their receipt** in their dashboard later.

## Common beginner questions

<FaqGroup>

<FaqItem question="Why is checkout harder than cart?">

Because a cart is just "maybe I'll buy this" — a wish list you can add to, remove from, and change without real-world consequences. An order is a **committed event**: money is owed, stock leaves the shelf, and the receipt is a legal record. If cart logic breaks, the worst that happens is a confusing UI. If order logic breaks, a vendor packs groceries nobody paid for, a customer's receipt shows the wrong price, and your accounting doesn't add up. That's why checkout gets its own careful server-side pipeline instead of being a button that saves the cart.

</FaqItem>

<FaqItem question="Why one order per store instead of a single combined order?">

Because each vendor needs to see only their own lines to pack and deliver. If you created one big order containing Green Valley's and Harbor Market's items together, each vendor's dashboard would be cluttered with another store's products. FreshMarket is a market hall, so fulfilment happens per stall: your server reads the cart, groups the lines by `storeId`, and writes a separate Order document for every store in the basket. The customer clicks one checkout button and gets one confirmation — but behind that, each vendor gets their own receipt.

</FaqItem>

<FaqItem question="Why snapshot the price — can't we just read the product?">

Because "the product" changes, but the order doesn't. If Green Valley raises basmati rice from ₹120/kg to ₹140/kg next month, and your order history page loads the *current* product price, every old order silently shows ₹140 — the receipt rewrites history. So at checkout you copy the name, price, and unit onto each order line as snapshot fields like `priceAtPurchase`, frozen forever. The order becomes self-contained: what you see on the receipt is exactly what was paid that day, no matter how the catalogue changes later.

</FaqItem>

<FaqItem question="Why reduce stock at checkout and not when I add to cart?">

Because adding to a cart is intent, not a purchase. If every add reserved stock, vendors would watch stock disappear for orders nobody ever places. Stock should leave the shelf only when the purchase is committed — successful checkout — and it must happen **atomically**, in one safe database operation, so two customers checking out the last bag of rice can't both succeed. One wins, the other gets a clear "not enough stock" error, and the whole checkout fails together rather than half-completing.

</FaqItem>

<FaqItem question="What happens if checkout fails halfway?">

Nothing gets created — that's the fail-all rule. Your server validates every line first: is the product published, is there enough stock? If any line fails, no orders are written and the cart stays intact, so the customer can fix the problem and try again. This prevents the worst case: three orders saved and stock reduced, then the fourth vendor's line fails — leaving a half-created order set, missing stock, and a confused customer. All-or-nothing keeps your orders and stock consistent every time.

</FaqItem>

<FaqItem question="Do I need Stripe or PayPal in this chapter?">

No — payment is Chapter 19's job. In Chapter 18, `POST /checkout` creates your split orders with `paymentStatus: 'pending'`, and you prove the whole pipeline works with curl and Compass. That's deliberate: you learn the hard commerce logic — snapshots, atomic stock, fail-all — without a payment gateway in the way. In Chapter 19 you add Stripe Payment Intents and gate checkout so no order is created until Stripe confirms the payment succeeded. Orders first, money second — each problem solved on its own.

</FaqItem>

</FaqGroup>


## Extra FAQ — checkout complexity for beginners

**Q: Walk me through checkout in plain steps.**  
1) Load customer's cart with products. 2) Reject if empty. 3) Validate every line (published, enough stock). 4) Group lines by `storeId`. 5) For each group, build an Order with **snapshot** lines. 6) Decrement stock for each product (conditional update). 7) Save all orders. 8) Delete cart items. 9) Return the created orders.

**Q: What's the difference between cart `storeId` and order `storeId`?**  
Cart line `storeId` = "which stall this item belongs to." Order `storeId` = "this **whole order** is fulfilled by this stall." One order document per store; many lines inside it share that order's `storeId`.

**Q: Embedded order lines vs separate OrderLine collection?**  
This course **embeds** snapshot lines inside the Order document — one read gives a full receipt. Separate collections do not remove the need to snapshot price.

**Q: MongoDB transactions — do I need them?**  
Ideal when your MongoDB deployment supports multi-document transactions (replica set). Local standalone may not — document your approach: transaction **or** careful ordering + compensating rollback in learning log.

**Q: What should `GET /orders/my` return for price display?**  
Only **embedded snapshot fields** on order lines — never live `product.price` from populate.

**Q: Vendor sees customer orders how?**  
`GET /vendor/orders` — orders where `storeId` matches **that vendor's store**, with ownership check from Chapter 8.

**Q: I'm overwhelmed — what sub-chapters matter most?**  
Read **18.2** (snapshot trap), **18.3** (blueprint), then build in order 18.8→18.16. Do not skip **18.16** snapshot test — it catches the most common bug.

## The hardest commerce problem in this course

Multi-vendor marketplaces fail demos in predictable ways:

| Failure | Symptom |
|---|---|
| Single combined order | Vendor B never sees their lines |
| Live product price on old orders | Receipt changes when vendor edits price |
| Partial stock decrement | Overselling under concurrency |
| Cart not cleared | Double checkout |

Chapter 18 addresses all four in the **orders module** — not in React.

## One checkout, many orders

```
Customer cart (3 lines, 2 stores)
        │
        POST /checkout
        │
        ├─► Order A (store 1) — embedded lines with snapshots
        └─► Order B (store 2) — embedded lines with snapshots
```

Customer experience: one button. Vendor experience: each sees **only their order**. Fulfilment is per store.
