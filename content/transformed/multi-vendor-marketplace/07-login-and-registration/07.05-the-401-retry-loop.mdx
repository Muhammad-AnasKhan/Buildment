When access token expires mid-session, user should not see login screen if refresh is valid. The API client implements **refresh once, retry once, else logout**.

<BigWordAlert term="401 retry loop" plainEnglish="When an API returns 401 Unauthorized, the client tries to refresh the token once, then retries the original request." whyItMatters="Shoppers should not be kicked to login mid-checkout just because an access token expired seconds ago." />

## Why this matters for absolute beginners

Without retry logic, users get kicked to login every 15 minutes while grocery shopping — unacceptable UX. With naive retry, infinite loops spam `/refresh`. The `_retried` flag is small but critical — distinguish expired access (refresh) from forbidden action (403, no refresh).

## Think of it like…

**Expired day pass at a museum.** Guard checks wristband (401) — not ejecting you immediately if membership desk (refresh) can print a new day pass once. Still forbidden rooms (403) are not fixed by a new wristband.

## Common beginner questions

<FaqGroup>

<FaqItem question={"Should a 401 from the login form trigger a refresh?"}>

No — and mixing these up wastes hours. A 401 from `POST /api/auth/login` almost always means a wrong password, not an expired token; refreshing can't fix bad credentials and just fires a pointless call. That's why the interceptor only wraps authenticated requests and must skip public routes like login, register, verify-otp, and health. The rule: refresh only when a request *should* have carried a valid access token but the token was stale. Wrong password and expired session are different problems — keep them separate.

</FaqItem>

<FaqItem question={"What if two requests 401 at the same time?"}>

Several requests can expire together — the boot refresh, a product list, and a cart call might all come back 401 in the same moment. If each one fires its own refresh, you get a burst of redundant calls. The clean fix is a mutex: the first 401 starts a single refresh promise, and every other request awaits that same promise before retrying. This is optional in this course — sequential refreshes still pass the gate — but if your Network tab shows duplicate refresh calls, note it in your learning log and consider adding the mutex.

</FaqItem>

<FaqItem question={"After a retry I get 403 — should I log out?"}>

No — 403 and 401 are different messages. 401 means "I don't know who you are," so a refresh is worth trying. 403 means "I know who you are, and you're not allowed to do this" — no token will fix it, and retrying would loop forever. The right move is to show a clear "you don't have permission" message and keep the session alive. In FreshMarket terms: a logged-in customer who clicks a vendor-only action gets 403. That's an authorization question, which arrives with Chapter 8 — not a login bug.

</FaqItem>

<FaqItem question={"Why retry only once — what is the `_retried` flag for?"}>

Without a "have I already tried?" marker, one stubborn 401 becomes an infinite loop: refresh, retry, 401 again, refresh, retry — hammering your API forever. The `_retried` flag is that marker. The retry passes with `_retried: true`, so if it still returns 401, the code knows refreshing didn't help and gives up: clear auth state, redirect to login. One retry is enough, because if the second attempt still fails, the problem isn't an expired token — it's something refreshing can never fix.

</FaqItem>

<FaqItem question={"What happens when the refresh token itself expires?"}>

Eventually every refresh token dies — that's its 7-day lifetime doing its job. When `POST /api/auth/refresh` itself returns 401, the session is genuinely over, so the code must not loop: clear the auth state, redirect to `/login` (optionally with a `session=expired` query for a friendly message), and let the user sign in again. This is the graceful end of the chain: access expired → refresh → refresh expired → logout. Anyone returning after a week away will land on exactly this path.

</FaqItem>

</FaqGroup>


## Algorithm

Here is the full flow the API client runs for every request. Read it as a decision tree, not a script to memorize — the two branches you must internalize are "expired access token" (refresh fixes it) and "authenticated but forbidden" (refresh does *not* fix it).

```
apiRequest(url, options):
  response = fetch with Bearer access

  if response.status !== 401:
    return response

  if options._retried:
    logout(); redirect login
    throw Unauthorized

  newAccess = await refreshAccessToken()  // cookie POST
  if !newAccess:
    logout(); redirect login
    throw Unauthorized

  setAccessToken(newAccess)
  return apiRequest(url, { ...options, _retried: true })
```

**Critical:** the `_retried` flag prevents an infinite loop. Without it, a request that still returns 401 *after* a successful refresh (say, the user genuinely lacks permission on that route) would trigger another refresh, another retry, forever. One retry is enough — if the second attempt still 401s, the problem is not an expired token.

## Concurrent 401s

Several requests can expire at the same moment — the app boot refresh, a product list, and a cart call may all come back 401 together. Without coordination, each one fires its own refresh, producing a burst of redundant calls. A mutex makes the first 401 start a single refresh promise and everyone else awaits it.

Optional mutex: first 401 starts refresh; others await same promise.

Stretch acceptable: sequential refresh calls — note in learning log if duplicate refresh seen.

## 401 vs 403 after retry

| Status after retry | Meaning | Action |
|---|---|---|
| 401 | Still unauthenticated | logout |
| 403 | Authenticated, forbidden | show message — **no** refresh loop (Ch 8) |

Only 401 triggers refresh — not 403.

## Public routes

Not every 401 means "your session expired." A wrong password on the login form also returns 401 — and refreshing would be pointless and harmful. The interceptor must know which endpoints are public so it never tries to refresh for them.

Login, register, verify, health — **no** Bearer header, **no** refresh on 401 from wrong password.

Interceptor applies to authenticated api client helper — not raw fetch on login form.

## Expired refresh

Eventually the refresh token itself expires or is revoked. When `/api/auth/refresh` returns 401, the session is truly over — do not loop. Clear the auth state and send the user to the login screen.

Refresh returns 401 → clear auth state → redirect `/login?session=expired` optional query.

## Testing

This is one of the few flows you genuinely cannot eyeball — it only triggers when a token expires mid-session. So you force an early expiry to observe it. Set the access expiry short, wait it out, then watch the network tab for the exact three-step dance below.

1. Login — set JWT_ACCESS_EXPIRY=30s on server temporarily  
2. Wait — click protected action  
3. Network tab: original 401 → refresh 200 → retry 200  
4. User stays on page — no login flash  

Document in learning log.

## Common beginner mistakes

1. **Refreshing on every 401, including 403 and wrong-password** — only *expired token* 401s should refresh; forbidden (403) is a different problem entirely.
2. **No `_retried` flag** — one lucky 401-then-still-401 turns into an infinite refresh loop that hammers your API.
3. **Retrying with the old access token** — the retry must use the *new* token or it 401s again instantly.
4. **Blocking the whole UI on refresh** — several requests expire together; make others wait on one refresh promise instead of each re-fetching.

## ✅ Do / ❌ Don't

**✅ Do:** Retry original request with new access only once.

**✅ Do:** Skip interceptor for /auth/login and /auth/register.

**❌ Don't:** Refresh on 403 — wrong semantics.

**❌ Don't:** Infinite retry loops.
