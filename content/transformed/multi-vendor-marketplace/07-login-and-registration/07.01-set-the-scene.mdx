**Where this chapter goes:** Login, Register, and Verify OTP **pages**, a **useAuth** hook or context storing access token in memory, API client attaching Bearer header, **401 refresh loop**, and **protected routes** redirecting unauthenticated users.

## Bridge from last chapter

Chapter 6 proved authentication **works on the server** — register, verify OTP, login, refresh, and `GET /api/auth/me` with Bearer token all pass curl tests. User documents in MongoDB have real bcrypt hashes. Yet your React app still only shows the health check; humans cannot register or sign in through the browser.

What carries forward: exact API request/response shapes from Chapter 6, CORS already enabled for Vite, and `client/src/pages/` + `api/client.js` from Chapter 2. What you add now is **session continuity in the browser** — forms, error messages, access token in memory (not localStorage), refresh token in httpOnly cookie, automatic retry when access expires, and protected routes that redirect strangers to login.

The hat you wear now is **frontend auth integrator**. You are not redesigning the API; you are making it usable by vendors and customers. Week 2's demo becomes "register in the browser, verify, login, land on the right page" — not just curl output in a terminal.

## Chapter 6 contract you inherit

Chapter 7 adds **zero new business logic** on the server. Every form, hook, and interceptor must call the endpoints you tested in Chapter 6 with the **same JSON shapes**. If Login.jsx sends `{ username }` but the API expects `{ email }`, the bug is client-side — but only because you broke a contract that already worked in curl.

| Chapter 6 endpoint (curl) | Chapter 7 consumer | What must match |
|---|---|---|
| `POST /api/auth/register` | Register.jsx | Body: `email`, `password`, `role`, `displayName`; handle 409 duplicate |
| `POST /api/auth/verify-otp` | VerifyOtp.jsx | Body: `email`, `otp`; then redirect to login |
| `POST /api/auth/login` | Login.jsx + useAuth | Response: `accessToken`, `refreshToken`, `user` — store per 7.4 |
| `POST /api/auth/refresh` | useAuth boot + interceptor | Cookie or body refresh → new `accessToken` |
| `GET /api/auth/me` | ProtectedRoute smoke test | Bearer header; 401 triggers refresh loop (7.5) |

**Phase shift:** Chapter 6 proved identity on the **server**. Chapter 7 proves the **browser** can hold and renew that identity safely — memory for access, httpOnly cookie for refresh, silent retry on 401.

## In plain English

| Term | Meaning |
|---|---|
| **Bearer token** | Access JWT sent in the `Authorization` header on API calls |
| **Auth context / hook** | Shared React state (`useAuth`) holding user and login methods |
| **httpOnly cookie** | Cookie JavaScript cannot read — used for refresh token |
| **Interceptor** | API client wrapper that attaches tokens and handles 401 retry |
| **Protected route** | Page that redirects to login if user is not authenticated |
| **Silent refresh** | On app load, call `/auth/refresh` to restore session without login form |
| **XSS** | Attack injecting script into your page — steels tokens if stored carelessly |
| **credentials: 'include'** | fetch option sending cookies on cross-origin requests |

## Common beginner questions

<FaqGroup>

<FaqItem question="Why not store the JWT in localStorage — it's easier?">

It is easier, and that's exactly the trap. Any script that runs on your page — a bad npm package, an unsanitized HTML string — can read `localStorage` in one line and steal your token, and the token stays there for later visitors too. That's why this course keeps the access token in **memory** and the refresh token in an **httpOnly cookie**: scripts can't read the cookie at all, and the in-memory token disappears when the tab closes. Less convenient on reload, much harder to steal — and it's the pattern real SPAs use.

</FaqItem>

<FaqItem question="Do I need new server endpoints?">

Usually no — Chapter 7 calls the same routes you tested in Chapter 6. The one small exception: if your login response returns the refresh token in the JSON body, you may add a `Set-Cookie` header so it moves into an httpOnly cookie, and enable `credentials: 'include'` on the client so that cookie actually gets sent. If you catch yourself inventing a brand-new endpoint, stop — you're probably breaking a contract that already worked in curl.

</FaqItem>

<FaqItem question="What happens on page reload if the access token is in memory?">

The token vanishes — memory doesn't survive a reload; only long-term browser storage does. So on boot the app calls `POST /api/auth/refresh` with the httpOnly cookie, the server mints a fresh access token, and the user stays logged in without ever seeing a form. That silent refresh is the heart of sub-chapters 7.4–7.5. If the refresh token is gone too, the app redirects to login. Either way, session continuity is the server's job, not the client remembering things.

</FaqItem>

<FaqItem question="Why separate chapters for API auth and UI auth?">

So you can debug each half on its own. Chapter 6 proved the server works with curl, where there's no browser, no React state, and no CORS to confuse you — a failure there is your server code. Chapter 7 layers the browser on top. The rule of thumb: if curl passes but the form fails, the bug is client-side; if curl fails too, it's server-side. Building both at once means debugging React and Express simultaneously — the hardest combination for a beginner.

</FaqItem>

<FaqItem question="Role-based UI (vendor vs customer) — this chapter?">

Not yet — this chapter only guards "are you logged in at all?" A `ProtectedRoute` wrapper redirects strangers to `/login`, and after login a vendor lands on a stub path while a customer lands on the shop stub. Deciding which screens a logged-in vendor may open — and stopping a customer from poking into vendor routes — is authorization, which needs server-side checks too. That's Chapter 8. For now, any authenticated user passes the door.

</FaqItem>

</FaqGroup>
