## Why this matters for absolute beginners

"Vague auth state" bugs dominate beginner SPAs — token in localStorage, refresh missing, reload logs everyone out, or refresh runs on login page causing loops. This page pins **exactly where each token lives** so implementation matches security intent from 7.2.

## Common beginner questions

<FaqGroup>

<FaqItem question="Why useRef instead of useState for the access token?">

Both work — the difference is re-renders. `useState` repaints every component that reads that state whenever the value changes, so a silent refresh (which rotates the token) could re-render the whole tree for no visible reason. `useRef` holds the value without triggering any re-render. The catch is that components don't automatically notice ref changes — but that's fine here, because your API client reads the token, not the UI. Either pattern passes the gate; pick one, use it consistently, and note the choice in your learning log.

</FaqItem>

<FaqItem question="Can React read the refresh cookie to debug?">

No — and that's by design. `httpOnly` makes the cookie invisible to JavaScript, so `document.cookie` won't show it and neither will `localStorage`. To check it, open the browser's Network tab, click the refresh request, and read the `Set-Cookie` response header — or look under DevTools → Application → Cookies. You'll see the cookie being set and sent without ever needing its value in code. If you can't find it there, the cookie wasn't set, which is a server-side question.

</FaqItem>

<FaqItem question="What is `credentials: 'include'`?">

Browsers don't send cookies on cross-origin requests by default — and your Vite dev server (port 5173) is a different origin from your Express API (port 3000). `credentials: 'include'` is the fetch option that says "yes, send cookies on this request," so the httpOnly refresh cookie actually reaches `/api/auth/refresh`. Forget it and the silent refresh always returns 401, because the cookie never left the browser — the classic "works in curl, fails in browser" bug. One line in the API client fixes it.

</FaqItem>

<FaqItem question="Why protect the refresh token more than the access token?">

Because the two tokens aren't equally valuable. The access token expires in ~15 minutes, so even if it's stolen, the damage window is short. The refresh token stays valid for days and can mint new access tokens the whole time — stealing it is like stealing the key to the cash machine instead of one day's cash. That asymmetry drives the whole split: the short-lived token gets the convenient but fragile home (memory), and the long-lived one gets the strongest protection the browser offers (an httpOnly cookie). Match each token's home to how much losing it would cost.

</FaqItem>

<FaqItem question="Why does page reload wipe the access token from memory?">

Memory isn't a storage location — it's temporary working space tied to the running page. On reload the browser tears down the old page and all its variables, then starts fresh, so anything kept only in JavaScript is gone. That's by design, not a bug: the access token never outlives the page session and can't be picked up later. The recovery plan is the boot sequence — the app calls `POST /api/auth/refresh` on mount and rebuilds the token from the cookie before rendering anything. That's exactly what `isLoading` exists to wait for.

</FaqItem>

</FaqGroup>


## Access token — memory only

The access token is a short-lived credential the API client attaches to every request. It lives in a JavaScript variable inside the AuthProvider — **not** in localStorage, sessionStorage, or a JS-readable cookie. The trade-off is deliberate: memory survives only while the tab is open, so a page reload requires a silent refresh (see 7.4's boot sequence). That small inconvenience buys you a much smaller theft window if a script ever runs on your page.

**Location:** `useRef` or closure variable inside AuthProvider — **not** React state if you want to avoid re-renders on token rotation; plain state is fine if simpler.

**Set when:**

- Login success  
- Refresh success  
- App boot refresh success  

**Clear when:**

- Logout  
- Refresh failure  
- 401 after retry  

**Never:** localStorage, sessionStorage, document.cookie (JS-readable).

## Refresh token — httpOnly cookie

The refresh token lives for days, so it needs the strongest protection the browser offers: a cookie JavaScript cannot read. The server writes it with `Set-Cookie`; the browser stores it; your React code never sees the value. When the API client calls `/api/auth/refresh` with `credentials: 'include'`, the browser attaches the cookie automatically — no token plumbing in your code at all.

**Set by:** Server `Set-Cookie` on login and refresh responses.

**Read by:** Browser automatically on `fetch(..., { credentials: 'include' })` to `/api/auth/refresh`.

**Client JS:** Does not read refresh value — opaque to React.

## Server cookie spec (coordinate with Ch 6)

| Attribute | Dev | Production |
|---|---|---|
| HttpOnly | true | true |
| Secure | false (localhost) | true |
| SameSite | Lax | Lax |
| Path | /api/auth | /api/auth |
| Max-Age | 7d | 7d |

Cookie name: `refreshToken` — document constant on both sides.

## Boot sequence

On every page load, the access token is gone from memory. The app must try to rebuild the session before rendering anything, otherwise a logged-in user flashes at the login screen for a moment — or gets bounced there entirely. This boot-time refresh is what makes the browser *feel* like the session survived the reload.

```
App mounts
  → AuthProvider calls refreshAccessToken()
  → POST /api/auth/refresh (cookie sent)
  → 200: set access in memory, set user from /me optional
  → 401: user stays logged out
  → set isLoading false
```

Prevents flash redirect on protected routes during boot.

## Logout sequence

Logging out is symmetric with logging in: the client drops what it holds in memory, and the server invalidates the refresh cookie so it cannot be replayed. Do both sides — clearing only the client leaves a usable refresh token behind.

```
Client: clear access memory
Client: POST /api/auth/logout (credentials include) — if implemented
Server: clear refresh cookie + refreshTokenHash
Redirect to /login
```

## Dual mode during migration

You may be wiring the client while Chapter 6 still returns the refresh token in the JSON body. That's an acceptable stepping stone — but be honest about it. Setting the cookie from the client's JavaScript is **less secure** (the browser sees the refresh value, even briefly) and should only be a temporary bridge. The gate requires the server-side httpOnly cookie for final submission.

- Ch 7 can set cookie from client — **less secure** — prefer server Set-Cookie  
- Gate requires httpOnly cookie pattern for final submission  

## Common beginner mistakes

Where token placement goes wrong, it usually fails in one of these ways:

1. **Access token in localStorage** — survives refresh, but any XSS script reads it in one line. This is the #1 MERN auth mistake and the reason this sub-chapter exists.
2. **Refresh token in a JS-readable cookie or localStorage** — the *most valuable* credential protected the *least*. The attacker now has the long-lived token, not the 15-minute one.
3. **No boot refresh** — memory is empty after reload, so users are logged out every time. The `isLoading` state exists precisely to wait for the boot refresh before rendering routes.
4. **Refresh loop on the login page** — the interceptor must skip public auth routes, otherwise a wrong password triggers a refresh attempt that also 401s, then a logout redirect — a confusing cascade.  

## ✅ Do / ❌ Don't

**✅ Do:** Use sameSite Lax for localhost dev.

**✅ Do:** Scope cookie Path to /api/auth minimum.

**❌ Don't:** Expose refresh to window object for debugging in committed code.
