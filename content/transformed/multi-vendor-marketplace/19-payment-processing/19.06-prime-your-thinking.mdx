Before scaffolding Stripe config and routes, read how Payment Intents and webhooks work in production. You will not paste Stripe's sample Express app wholesale — but you must understand **why** the flow is two-step (intent → confirm → verify) and **why** webhooks use raw bodies.

## Extra FAQ before the build cluster

**Q: I'm overwhelmed — where do I start?**  
Read 19.3 blueprint. Build in order: config (19.9) → intent route (19.10) → gated checkout (19.11) → webhook (19.12) → idempotency (19.13) → test (19.14). One sub-chapter per sitting.

**Q: Payment Intents vs Charges API?**  
Payment Intents are the **current** Stripe model — handles SCA, status lifecycle, client confirmation. Do not use legacy Charges API for new work.

**Q: Why raw body on webhook route?**  
Signature is computed over **exact bytes** Stripe sent. `express.json()` parses and re-serializes — signature verify fails. Mount `express.raw({ type: 'application/json' })` on webhook path only.

**Q: Confirm on client or server?**  
This course: **confirm with Stripe.js on client** (Ch 20 UI; you can test with Stripe CLI or API in 19.14). **Verify on server** before orders — always.

## Payment Intent lifecycle — what to remember

Typical happy path:

```
requires_payment_method → requires_confirmation → processing → succeeded
```

Your server creates the Intent (`requires_payment_method`). Client confirms card. You only run order creation when status is **`succeeded`** — retrieved via server SDK, not from client JSON alone.

Failed paths (`requires_payment_method`, `canceled`, `payment_failed`) must **not** create orders.

## Webhooks — what to remember

| Event | Your handler |
|---|---|
| `payment_intent.succeeded` | If orders missing for this PI, trigger checkout logic or mark audit log |
| `payment_intent.payment_failed` | Log; return 200 — do not create orders |

Stripe retries failed webhook delivery — handler must be **idempotent** (19.13).

Respond **200 quickly**. Long MongoDB transactions inside webhook without idempotency → duplicate orders on retry.

## Connection to Chapter 18 idempotency (18.6)

Chapter 18 documented double-click on bare checkout. Payment adds a **stronger** key: `paymentIntentId`. Same PI must not create two order sets — whether from double POST `/checkout` or webhook + checkout racing.
