**Why this step matters:** This is the **gate** between money and merchandise — if verification is wrong, you either give away groceries or charge without creating orders. Everything else in Chapter 19 supports this seam.

**Where the project is now:** `POST /payments/intent` creates intents; `POST /checkout` still runs Chapter 18 pipeline without payment — the fake-checkout trap.

**After this step:** `POST /checkout` requires `{ paymentIntentId }`, retrieves Payment Intent from Stripe, verifies `succeeded` and amount, then runs existing split/snapshot/stock/clear logic; each order gets `stripePaymentIntentId` and `paymentStatus: 'paid'`.

## Refactor checkout entry — contract

**Input body (required):**

```json
{
  "paymentIntentId": "pi_xxxxxxxx"
}
```

Missing `paymentIntentId` → **400** — "Payment required" or similar.

## verifyAndCheckout(userId, paymentIntentId) — contract

**Phase A — Payment verification (new):**

1. `getStripe().paymentIntents.retrieve(paymentIntentId)`.
2. If `status !== 'succeeded'` → **402** or **400** — payment not completed.
3. Recompute cart total with **same helper** as 19.10.
4. If `paymentIntent.amount !== computedTotal` → **400** — amount mismatch; log for fraud investigation.
5. Optional: assert `metadata.userId` matches auth user if you set it at intent creation.
6. **Idempotency:** if Order(s) already exist with this `stripePaymentIntentId` → return existing orders **200** — do not duplicate (detail in 19.13).

**Phase B — Chapter 18 pipeline (existing):**

7. Load cart; validate lines; group by `storeId`.
8. Build orders with snapshot fields.
9. Atomic stock decrement — fail-all unchanged.
10. Set on **each** order before insert: `stripePaymentIntentId`, `paymentStatus: 'paid'`.
11. Insert orders; clear cart.
12. Return `{ orders: [...] }` — 201 on first success.

**Do not rewrite** snapshot or stock logic — call existing functions from 18.10–18.13.

## Response contract

Same shape as Chapter 18 — array of split orders. Each order document includes payment fields:

```json
{
  "orders": [
    {
      "_id": "...",
      "storeId": "...",
      "total": 305,
      "stripePaymentIntentId": "pi_...",
      "paymentStatus": "paid",
      "orderItems": [ "... snapshots ..." ]
    }
  ]
}
```

## Status code guidance

| Case | Suggested status |
|---|---|
| PI not succeeded | 402 Payment Required or 400 |
| Amount mismatch | 400 |
| Cart validation fail | 400 |
| Stock fail | 400/409 — same as Ch 18 |
| Success first time | 201 |
| Idempotent replay same PI | 200 with same orders |

Pick one idempotent pattern — document in README.

## ✅ Do / ❌ Don't

**✅ Do:** Retrieve PI from Stripe on **every** checkout — no cached client status.

**✅ Do:** Attach same `stripePaymentIntentId` to **all** orders from one checkout.

**✅ Do:** Keep fail-all stock semantics from Chapter 18.

**❌ Don't:** Create orders when PI is `requires_payment_method` or `processing`.

**❌ Don't:** Skip cart re-validation because payment succeeded — prices/stock may change between intent and checkout.
