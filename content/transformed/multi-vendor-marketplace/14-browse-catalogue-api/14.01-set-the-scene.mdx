## In plain English

| Term | Simple meaning |
|---|---|
| **Public catalogue** | The shop window — products any visitor can browse without being a vendor |
| **Vendor-scoped route** | API that only returns **your** inventory when **you** are logged in as vendor |
| **N+1 query problem** | Loading a list, then running one extra database query **per row** — fast with 5 items, slow with 500 |
| **Populate** | Mongoose fetching related documents (e.g. store name) in a batched way instead of a loop |
| **Pagination** | Returning products in pages (e.g. 20 at a time) instead of the whole catalogue at once |
| **DTO** | The shape of JSON the API sends — public browse hides draft products and vendor secrets |

## Common beginner questions

<FaqGroup>

<FaqItem question="Do I delete the vendor routes or the vendor dashboard?">

No — delete nothing. `GET /vendor/products` stays exactly as it is: that's how a logged-in vendor sees their *own* inventory. Chapter 14 is purely additive: you write a new public route, `GET /products`, that sits beside the vendor routes and reads the same product collection. Vendors still manage their stalls from the back office; customers get the shop window. This "two routes, one collection" pattern is the heart of a marketplace and a classic interview talking point.

</FaqItem>

<FaqItem question="Why build the API before the shop UI (Chapter 15)?">

Same pairing as Chapters 6→7 and 11→12: backend contract first, React second. If you built the Chapter 15 grid before `GET /products` existed, you'd have to invent fake hardcoded products — then throw them away and rework the page once the real API arrived. With the API first, you prove it with curl: right shape, right filters, right pagination. Then the shop UI is mostly a matter of wiring fetch calls to fields you already know exist.

</FaqItem>

<FaqItem question="Can customers browse without logging in?">

Yes, for this chapter's gate. `GET /products` is a public read route — no JWT required — which is why it's called the public catalogue. Anyone with the URL can see published, in-stock products from every vendor. Login only becomes mandatory once a customer wants to act: adding to a cart (Chapters 16–17) and checking out (Chapter 18) both require a customer account. Browsing is window-shopping; acting is buying.

</FaqItem>

<FaqItem question="What's the difference between `/vendor/products` and `/products`?">

Think about who is asking. `GET /vendor/products` answers "show me *my* products" — it needs a vendor JWT and returns only the calling vendor's own inventory, drafts included. `GET /products` answers "show me *everyone's* published, in-stock products" — no token, and drafts and out-of-stock items are hidden. The gate also needs your seed to contain products from at least two stores, so the public route genuinely proves it's a multi-vendor marketplace rather than one shop's shelf.

</FaqItem>

<FaqItem question="What do `page`, `limit`, and `category` do in `GET /products?page=&limit=`?">

They're query parameters that shape the response without changing the route. `limit` sets how many products come back per request (say 20), `page` says which slice you want (page 2 skips the first 20), and `category` narrows results to one kind of product, like `"vegetables"`. The server builds a filtered, paginated query and returns one page plus enough information to know whether more pages exist. Fetching a page at a time keeps responses small and the shop fast — you never download the whole catalogue.

</FaqItem>

<FaqItem question="What is N+1 and why should I care before I have users?">

N+1 is a query pattern bug. Imagine listing 20 products and, for each one, running an extra query to fetch its store name — that's 1 query for the list plus 20 more, or 21 database trips, hence "N+1". With 5 products it's invisible; with 500 it's slow enough to feel broken. The fix, which Chapter 14 teaches, is Mongoose `populate`, which fetches the store names in one batched query. The skill you're building is *measuring* query count instead of assuming it's fine — so the shop never ships slow.

</FaqItem>

</FaqGroup>


## The gap between "vendor inventory" and "marketplace"

Right now your API can answer:

- What products does **this vendor** sell?
- Can Vendor A edit Vendor B's product?

It cannot answer:

- What can **any customer** browse without logging in (or with customer login)?
- How do we filter by category or store?
- How do we page through 200 tomatoes without loading all at once?

Those are **public read model** problems — different from vendor CRUD in Chapter 11.

## Why this chapter starts Week 3 on the backend

Chapter 15 builds the shop UI. UI without a stable API contract produces mock data and rework. **Backend first** — same pairing as 06→07, 11→12, 14→15.

Chapter 14 assumes:

- Product model has `isPublished`, `stockQty`, `category`, `storeId`, `imageUrl`
- Seed data includes products from **at least two stores**
- Vendor routes remain unchanged — public route is **additive**

## Public vs vendor routes — mental split

| Audience | Route pattern | Auth | Data scope |
|---|---|---|---|
| Vendor | `GET /vendor/products` | Required vendor JWT | Own store only |
| Customer/public | `GET /products` | Optional none for browse | All published, in-stock |
| Vendor write | `POST/PATCH/DELETE /products` | Vendor + ownership | Own only |

Never expose draft products or internal fields on public DTO.
