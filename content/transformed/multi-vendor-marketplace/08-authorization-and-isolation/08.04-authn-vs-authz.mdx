Two words, two responsibilities. Conflating them causes either open APIs or 401 loops where 403 is correct.

<BigWordAlert term="Authentication vs authorization" plainEnglish="Authentication proves who you are; authorization decides what you are allowed to do." whyItMatters="A logged-in vendor is authenticated — but only their own products should be editable. That check is authorization." />

The confusion is natural — both words start with "auth" and both show up as access errors. But they answer two completely different questions, and the client reacts differently to each. Get this split right and every later chapter (stores, products, orders) is just *applying the same two checks*. Get it wrong and you will send 401s everywhere, which tells the client "log in again" when the real message is "you are not allowed to do this."

## Authentication (authn)

Authentication answers **"who are you?"** It proves identity. Your Chapter 6–7 work already did this: the server verifies a JWT and learns the caller is Vendor A. Nothing in this chapter changes that — authorization *builds on top of* authentication. You cannot check permissions on an identity you have not verified first.

**Proves identity** — who is calling.

| Mechanism | FreshMarket |
|---|---|
| JWT access token | requireAuth |
| Result | req.user = &#123; id, role &#125; |
| Failure | **401 Unauthorized** |

*"I am Vendor A"*

## Authorization (authz)

Authorization answers **"what may you do?"** It proves permission — whether this verified identity may perform this action on this specific resource. There are two layers, and production systems use both. A customer might be authenticated (they are who they say they are) yet still be forbidden from touching a vendor's store — that is authorization, and it is where most marketplace bugs live.

**Proves permission** — may this identity perform this action on this resource.

| Layer | Check | Example |
|---|---|---|
| Function-level (RBAC) | role | requireRole('vendor') |
| Object-level (ownership) | resource owner | assertStoreOwner |
| Failure | **403 Forbidden** | identity valid, action denied |

*"Vendor A may edit Store A, not Store B"*

## 401 vs 403 — decision tree

The status code you return is not a style choice — the client's interceptor from Chapter 7 **behaves differently** based on it. A 401 tells the client "your session is bad, refresh and retry"; a 403 tells it "you are logged in, but this is not yours — do not retry." Sending the wrong one produces either infinite refresh loops or requests that are never retried when they should be.

```
Missing Bearer?
  → 401

Invalid/expired JWT?
  → 401

Valid JWT, customer hits vendor-only route?
  → 403

Valid JWT, vendor hits another vendor's store?
  → 403

Valid JWT, vendor hits own store, invalid body?
  → 400
```

Client refresh loop: **401 only** — not 403.

## Function-level vs object-level

Two kinds of authorization, two places in the request pipeline. Function-level checks happen *before* you load any data — "is the caller even the right kind of user for this endpoint?" Object-level checks happen *after* you load the resource — "does this specific record belong to this specific caller?" Most tutorials only teach the first; production leaks happen when teams stop at the second.

**Function-level:** "Only vendors may call POST /products" — role check once at route.

**Object-level:** "This product belongs to caller's store" — load resource, compare ids.

Both required for PATCH /products/:id — Chapter 11.

## Anonymous vs authenticated public reads

Not every route needs both checks — the matrix in `docs/AUTHORIZATION.md` records, per route, whether it is public, auth-only, role-gated, or ownership-gated. Deciding this *before* building keeps you from over-securing public pages or under-securing private data.

GET /products public catalogue — no authn (Ch 14).

GET /cart — authn required, authz scopes to userId (Ch 16).

Matrix documents each route.

## Common beginner mistakes

1. **Using 401 for everything** — the client interceptor treats 401 as "expired, refresh." A vendor hitting a customer-only route with 401 triggers a pointless refresh loop instead of a clean "not allowed" message.
2. **Only doing the role check** — `requireRole('vendor')` lets *any* vendor edit *any* store. The ownership check (object-level) is the half that actually prevents data leaks between vendors.
3. **Skipping server-side authorization because the UI hides buttons** — hiding a button is UX, not security. Anyone with curl can call the endpoint directly; the server must enforce the rule itself.
4. **Checking ownership before authentication** — you cannot compare `req.user.id` against anything if `req.user` does not exist yet. Auth runs first, always.

## ✅ Do / ❌ Don't

**✅ Do:** Return 403 for wrong role on authenticated request.

**✅ Do:** Document 401 vs 403 in AUTHORIZATION.md.

**❌ Don't:** Use 401 to mean "not allowed" — confuses client refresh.
