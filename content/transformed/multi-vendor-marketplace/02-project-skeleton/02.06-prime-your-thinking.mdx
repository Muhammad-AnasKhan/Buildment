## Why this matters for absolute beginners

Reading fifteen minutes before `git init` feels slow when you want to code. It prevents **false confidence** — copying a layer-based tutorial and discovering at Chapter 11 that "products module" does not exist in your repo. The mandatory reads connect this course's module mandate to how Express routing actually works, so sub-chapter 2.11 is not your first time seeing `app.get` and middleware.

## Common beginner questions

<FaqGroup>

<FaqItem question="Do I need to memorize the Express docs?">

No — you need to know where to look and what matters. Focus on basic routing (`app.get`), `express.json()`, and `Router()` — enough to mount `/health` and understand Chapter 6's POST bodies. Skip template engines and static files until you actually need them. Treat the docs like a dictionary, not a textbook to memorize: read the relevant sections now so sub-chapter 2.11 isn't your first encounter with `app.get`, and look things up whenever you're unsure. The skill is recognizing the tool when you see it, not reciting it from memory.

</FaqItem>

<FaqItem question="Can I skip the feature-vs-layer article if I trust the course?">

Read it anyway — not for the course's sake, but for yours. These mandatory reads exist to replace *false confidence* with real understanding. You chose module-based in 2.4 because the course mandated it; after reading, you can explain in your own words when layer-based works and why growing codebases move toward feature folders. Drop one paragraph in your learning log comparing the two, and the decision stops being "a checklist told me so" and becomes "I chose this with my eyes open." That's the difference between following along and learning.

</FaqItem>

<FaqItem question="Should I read Mongoose or JWT now?">

No — scattered reading derails focus, and the course order exists for a reason. Mongoose gets a full chapter in Chapter 5, JWT in Chapter 6, Redis in Chapter 21 — each when your repo is ready for it. Reading ahead feels productive, but you'll hold concepts in your head with nowhere to apply them, and they'll fade by the time you need them. Trust the order: skeleton now, database when there's a folder to connect it to, auth when there are users to protect. Right now, the only useful reads are the two this sub-chapter assigns.

</FaqItem>

<FaqItem question="What if I finish reading and still feel unsure?">

That's normal — reading about something is not the same as building it. Re-read 2.4 and 2.5, then complete the sanity-check sentences: business logic for products lives in `server/src/modules/products/`, React gets data via HTTP to the Express API (never a direct database call), and connection strings live in `server/.env`. If any of those three feels fuzzy, that's the exact signal to re-read before you scaffold. Wrong answers now are far cheaper than wrong folders after 2.11.

</FaqItem>

<FaqItem question="Why read about Express before I've written a single route?">

Because fifteen minutes of reading stops you from building on a guess. If 2.11 is your very first time seeing `app.get` and middleware, you'll copy syntax you don't understand and won't know where to look when it breaks. Reading first means the build steps feel like *applying* knowledge instead of *meeting* it for the first time — like assembling furniture with the manual open rather than discovering a random screw and hoping. It's also how professionals approach new tools: skim the docs, then build with the manual handy.

</FaqItem>

</FaqGroup>


## Mandatory read — before you scaffold the repo

Read **both** of the following (total time ~30–45 minutes):

### 1. Express application structure

**Topic to search:** *Express.js routing guide* — official Express documentation section on routing and middleware.

**Why now:** Chapter 2.11 mounts your first route. You should know what `app.get`, `app.use`, and `Router()` mean before you write them.

**After reading, you should be able to answer:**
- What does middleware do in the request pipeline?
- What's the difference between `app.listen` and defining routes on `app`?

### 2. Feature-based vs layered folder structure

**Topic to search:** *feature based vs layered folder structure node express*

**Why now:** You just chose module-based layout. This read shows you the alternative teams use and **when they switch**.

**After reading, you should be able to answer:**
- What problem does layer-based structure solve at small scale?
- Why do growing codebases often move toward feature folders?

## After reading — sanity check

Without opening notes, complete these sentences:

1. "In my repo, business logic for products will live in _____________."  
   → Expected: `server/src/modules/products/` (service + routes)

2. "The React app will get data by _____________."  
   → Expected: HTTP requests to the Express API (not direct DB)

3. "Database connection strings live in _____________."  
   → Expected: `server/.env`, not client

If any answer feels fuzzy, re-read 2.5 before 2.8.

<InterestingRead title="Colocate by feature vs organise by type" hook="Folders named `controllers/` age badly when products multiply." readMinutes={5}>

Many teams start with layer-first folders (all routes together, all models together). Feature-first layouts group everything for one capability — auth, cart, checkout — in one place. FreshMarket uses module folders on the server so each capability stays findable as the codebase grows.
