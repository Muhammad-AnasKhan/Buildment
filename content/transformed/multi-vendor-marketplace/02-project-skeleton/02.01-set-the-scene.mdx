<BigWordAlert term="Monorepo layout" plainEnglish="One Git repository that holds both the client app and the server app, usually in separate top-level folders." whyItMatters="FreshMarket keeps `client/` and `server/` side by side so you can run and deploy them together while keeping concerns separate." />

This chapter is where that changes.

<ArticleBreak title="Before you write feature code: how FreshMarket is wired" subtitle="A five-minute map of client, server, and the first request" readMinutes={6}>

FreshMarket runs as two applications: a Vite + React client and an Express + Node server. The client never talks to MongoDB directly — it calls HTTP routes on the server, and the server owns all data access.

Your skeleton chapter exists to prove that wiring works. When the home page shows a health check response, you have confirmed: the server listens on a port, the client knows that URL, CORS allows the browser request, and JSON travels both ways.

Every later chapter plugs into this same pattern. Auth adds protected routes. The catalogue adds public read routes. Checkout adds payment routes. The skeleton is boring on purpose — boring infrastructure is what lets exciting features ship safely.

</ArticleBreak>

## In plain English

| Term | Meaning |
|---|---|
| **Skeleton** | The empty but runnable shape of the app — folders, entry files, health check — before real features |
| **Monorepo** | One Git repository containing both `server/` and `client/` as separate apps |
| **Module folder** | A directory grouped by product area (auth, products, cart) — not by technical type (all controllers together) |
| **Health check** | A simple API route that answers "is the server up?" — your first proof the backend works |
| **Full-stack** | Browser UI (client) talking to Node API (server) over HTTP |
| **Scaffold** | Create folders and stub files so later chapters have named places to add code |
| **Gate / checklist** | Tickable outcomes at chapter end — you do not proceed until each box is checked |

If you skip the hall and start with a cheese counter in a field, every next delivery has nowhere to plug in.

## Common beginner questions

<FaqGroup>

<FaqItem question={"Why not start with MongoDB or login — the interesting parts?"}>

Because those features need *somewhere to live*. Without `server/src/modules/` and a running Express app, every later chapter would say "add this somewhere" and you'd paste into random files you don't understand. Think of it as building the market hall before the stalls open: you pour the foundation, run the wiring, and hang a "we're open" sign before any vendor stocks shelves. Get the skeleton right once, and every later feature — database, auth, products — slots into a folder you already know.

</FaqItem>

<FaqItem question={"Do I build inside the course folder (`multi-vendor-marketplace/`)?"}>

No. That folder is the textbook — the course content lives there. Your app is a **separate Git repository** you create in sub-chapter 2.8, somewhere like `~/projects/greenbasket/`. If you build inside the course folder, your app and the course materials get tangled, commits mix together, and instructions that say "create a file in your project root" become ambiguous. Keep the book on the shelf and your workspace separate — that's what real teams do too.

</FaqItem>

<FaqItem question={"I have never used Express or Vite. Is this chapter too early?"}>

Not too early — this chapter introduces them **one small step at a time**. You'll install packages, create entry files, and verify with curl and the browser, so each concept appears the moment you need it. Unfamiliar errors will happen, and that's fine; use the working rhythm from Chapter 1: read the message, search the docs, fix the smallest failing piece. By the end you won't be an Express expert — you'll just know enough to run a server and a client, which is precisely what's needed next.

</FaqItem>

<FaqItem question={"Why two terminals — can't one command run everything?"}>

Because the client and server are **two separate programs** during development, and two terminals make it obvious which half broke. You run `npm run dev` in `server/` to start the API on port 5000, and `npm run dev` in `client/` to start the React app on port 5173. When something fails, the terminal that shows the error tells you exactly where to look — "client works, API down" is a sentence you'll say often. Running both from one command is possible later, but it hides the architecture you're here to learn.

</FaqItem>

<FaqItem question={"What if I already have a MERN starter template?"}>

Unless it matches this course's **module-based** layout — `server/src/modules/…` — it will fight you. Every chapter names an exact path like `modules/products/products.routes.js`, and if your repo has no `modules/` folder, you'll translate every instruction for twenty chapters or diverge from the guide. Scaffolding fresh here takes an afternoon; un-teaching a random boilerplate takes weeks. If you love your template, adapt it to the target tree in 2.3 — otherwise, start clean and stay aligned.

</FaqItem>

<FaqItem question={"What does the health check actually prove?"}>

The health check — `GET /health` returning `&#123; "status": "ok" &#125;` — proves the wiring between Express and the browser works before you add anything complicated. When your React Home page fetches that endpoint and displays the result, you've confirmed the server boots and listens, the client renders, HTTP works across the two, and your folder conventions hold real files. It's the smallest possible proof that the full-stack loop is alive. Skip it and you'd debug connection problems later with database and auth code mixed in, which is much harder.

</FaqItem>

</FaqGroup>

## What "standing the project on disk" means

Professional teams don't start by writing a login handler. They start by answering boring questions:

- Where does the API code live?
- Where does the React code live?
- How do we start each app with one command?
- How do we know both halves are alive?

**Standing the project on disk** means: at the end of this chapter, you can open your repository in an editor, see a **folder tree you understand**, run **two commands in two terminals**, and **demo something real** — the React home page calling the API health check and showing the response.

No users. No products. No MongoDB. Still a **working full-stack skeleton** — and every future chapter attaches to it like scaffolding on a building.

## Why this chapter comes before MongoDB

Chapter 4 connects MongoDB. Chapter 5 builds schemas. You might wonder why not start with the database.

Because the **app must exist before the app needs a database**. The health check in this chapter proves:

- Express boots and listens
- React boots and renders
- HTTP works between browser and server
- Your folder conventions hold real files

When Chapter 4 adds `MONGODB_URI`, it slots into `server/src/shared/` — a place you already created and understand. If you started with Mongoose before you had `app.js`, every chapter would say "add this somewhere" and you'd paste into random files.

**Order matters:** skeleton → config & DB → data model → features.

## What this chapter is not

- **Not** the auth chapter — no JWT, no passwords
- **Not** the data model — no User or Product schemas yet
- **Not** a UI design chapter — one plain Home page is enough
- **Not** deployment — localhost only

It **is** the chapter where you make the **one structural decision** the rest of the course assumes: **module-based folders** in `server/src/modules/`. Change that later and every subsequent chapter's file paths stop matching.
