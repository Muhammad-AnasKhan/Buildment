## Copied, credited, and still not allowed

Adam is building a small online shop for his uncle's spice business. He found a public repository on GitHub with a neat search function, exactly what his shop needed. He copied the function, about 40 lines, into his project. Above it he wrote a comment with the author's username: "Search code by this author, thank you." He felt he had done the honest thing.

At his next mentor meeting, the mentor read the comment and asked one question: "What licence is that repository under?" Adam did not know. They opened it together. There was no licence file anywhere. The mentor explained that this changes everything. Without a licence, the author keeps all the rights to the code, and nobody may copy it into their own project, with or without thanks.

Adam removed the 40 lines. He kept what he had learned from reading them and wrote his own search, which took him two evenings. He also opened an issue on the repository, politely asking the author whether they would add a licence. This chapter is about avoiding Adam's mistake while still getting what he wanted: learning from code that other people have already written.

## Why read other people's code

<GlossaryTerm term="Open source" definition="Code shared under a licence that lets others read, use, change and share it, on the conditions the licence sets." /> projects are one of the best free teachers a fellow has. A real project shows things a tutorial leaves out: how the files are organised, what the tests check, how errors are handled, and which problems users reported in the issues. When Yara reached short codes in her plan, she did not only ask an AI to explain them. She went looking for a project that had already solved the problem, so she could see a solution that real people use and maintain.

Reading is always allowed. Copying depends on the licence. Keep those two apart and most of the risk disappears.

## Finding a project worth studying

At the time of writing (checked 2026-10-24), GitHub offers several ways to find projects. You can search by keyword. You can open topic pages, which group projects that their owners tagged with the same topic, such as link shorteners. Explore and Trending show projects that are active or popular. Many projects mark easy tasks for newcomers with labels such as "good first issue" and "help wanted". People also keep lists of good projects on a topic, often as a repository of their own. A good place to start is a project you already use.

Yara opened GitHub's topic page for link shorteners and read the first two pages of results. She chose two candidates. In this chapter the first is called shortlane, a made-up name for this example. It makes short codes in the way she wanted to learn. The second had far more stars, which are a way GitHub users bookmark a project, so it looked more popular.

## Signs of a healthy project

Popular is not the same as healthy. A guide that GitHub publishes on open source lists signs worth checking before you invest time in a project. It has a licence. It has recent commits. Several people contribute, not just one. The maintainers respond to issues and pull requests. Issues get closed. Pull requests get reviewed and merged. People are friendly in the discussions.

Yara checked shortlane against that list. It had an MIT licence. The last commit was three weeks old. Nine people had contributed. Most issues had an answer within a few days, and recent pull requests had been reviewed and merged. The popular project was different: its last commit was four years old, and it had no licence at all. She could still read it, but she would not reuse any of it, and she would not expect answers if she asked a question.

## Read it in order

A whole project is too much to read at once. This course suggests an order. It is the course's advice, not a tested method, but it keeps you moving from the big picture to the details.

First, read the README, the file that explains what the project does and how to run it. Second, run it. If your laptop is not strong enough, GitHub Codespaces gives you a computer in the browser; at the time of writing it has limited free hours each month, so check your usage page. Third, find the entry point, the file where the program starts. Fourth, follow one feature from start to end, inside one folder. Fifth, read that feature's tests, which show what the authors thought could go wrong. Last, ask an AI to explain one file, and check its explanation against the code.

Yara followed this order on shortlane. The README told her how to start it, and she ran it in Codespaces. Then she read only the folder that makes short codes. Its tests surprised her: one checked what happens when two links get the same code by chance. She had not thought of that.

Then she asked a chat assistant to explain the main file in that folder. The explanation was clear and mostly right, but it said the file "calls a function that checks the code is not already taken". Yara searched the file. There was no such function. The check happened somewhere else, in a rule in the database that refuses a code that already exists. An AI can explain a file to you. It can also invent a function that is not there. Check against the code.

## Licences in four cases

Licence law is large, and this course is not legal advice. For your own projects, four cases cover most of what you will meet. The table puts each one in a line.

| Licence | You may | You must |
|---|---|---|
| MIT | Reuse, change and share the code | Keep the copyright and licence notice |
| Apache 2.0 | Reuse, change and share; it includes a patent grant | Keep the notices and state your changes |
| GPL (version 3) | Reuse, change and share | If you distribute your work, share its full source under the GPL |
| No licence | Read it and learn from it | Not copy it; ask the author to add a licence |

The diagram below shows the same four cases as a decision you make before you copy anything. Read it from the top.

```mermaid
flowchart TD
  A["Code I want to reuse"] --> B{"Which licence?"}
  B -->|"none"| C["Read and learn only"]
  B -->|"MIT or Apache 2.0"| D["Reuse, keep the notices"]
  B -->|"GPL"| E["Reuse, share my source too"]
  D --> F["Credit in README and post"]
  E --> F
```

What to notice: only one branch ends without reuse, and it is the one people expect least, the public repository with no licence. The other branches all allow reuse, each with a condition. The takeaway is that the licence decides what you may copy, and credit comes after the licence, not instead of it.

One more rule sits under the table. Public is not the same as open source. GitHub's terms let other users view and fork a public repository, but that is not a licence to reuse the code elsewhere. Adam's search function was public. It was not open source.

## Credit, every time

Every licence in the table asks you to keep its notice. This course adds a habit on top: name the project you learned from in your README and in your write-up, even when you copied nothing. Credit costs one line, and it tells a reader you know where your ideas came from.

## Where it goes wrong

The first mistake is Adam's: treating public as permission. Look for the licence file before you copy a single line.

The second mistake is treating credit as permission. A thank-you comment is good manners. It does not replace a licence, and it does not replace keeping a licence's notice.

The third mistake is reading everything and understanding nothing. Reading one feature from start to end, with its tests, teaches more than skimming fifty files.

The fourth mistake is trusting the AI's tour of the code. Use it to find your way, then check every claim it makes against the file.
