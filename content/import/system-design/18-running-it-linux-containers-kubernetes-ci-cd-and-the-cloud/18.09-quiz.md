```quiz
type: mcq
question: "A container is limited to 0.5 CPU and 200 MB. During a burst, its p99 goes from 80 ms to 600 ms. There are no restarts, no errors, and memory stays at 90 MB. What is the most likely cause?"
options:
  - "The memory limit is killing and restarting the process"
  - "The Dockerfile has no HEALTHCHECK, so it is slow"
  - "Kubernetes is replacing the pods during a rollout"
  - "The CPU limit is making the busy process wait"
correct: 3
explanations:
  - "A memory kill ends the process with exit code 137 and shows as a restart. Here there are no restarts and memory is low."
  - "A health check reports status. It has no effect on how fast a request is answered."
  - "A rollout would show new pods and probably some errors. Nothing here points to one, and the slowness follows the burst."
  - "Right. A CPU limit is a time budget. In a burst the container uses it up and its threads wait for the next period, so requests slow down quietly."
```

```quiz
type: mcq
question: "Daftar runs on Kubernetes with a readiness probe. Each deploy still gives users a few errors per replaced pod. The service exits the moment it gets SIGTERM. What should the team add?"
options:
  - "A bigger CPU limit for every pod in the Deployment"
  - "A short wait and a drain before the service stops"
  - "A second Service in front of the first one"
  - "A liveness probe that calls the database"
correct: 1
explanations:
  - "A bigger limit does not change when the pod stops listening. The errors come from the shutdown, not from slowness."
  - "Right. The Service takes time to stop sending requests to a stopping pod. Waiting briefly, then finishing open requests, covers the gap between SIGTERM and the end of routing."
  - "Two Services do not change how one pod stops. The pod still quits while requests are on their way to it."
  - "A liveness probe restarts stuck containers. It does not help a pod that is stopping on purpose, and a database check can restart every pod."
```

```quiz
type: mcq
question: "A one-line change to server.js takes 4 minutes to build. The Dockerfile copies the whole folder, then runs npm ci. What change makes the build fast again?"
options:
  - "Copy package files, install, then copy the code"
  - "Run the build on a bigger machine with more memory"
  - "Remove the lock file so npm can pick packages freely"
  - "Switch the CMD from exec form to shell form"
correct: 0
explanations:
  - "Right. The install layer then depends only on the package files. A code change rebuilds just the last copy step and reuses the cached install."
  - "A bigger machine may speed the install up a little, but the install would still run on every change. The cause is the layer order."
  - "Without a lock file builds differ from each other, and npm ci refuses to run. It does not speed up the cache either."
  - "CMD runs when the container starts. It has no effect on how long the build takes."
```

```quiz
type: mcq
question: "A new checkout flow touches payments. The team wants real traffic to test it on 1% of users first, and wants to turn it off within a minute if the error rate rises. Which release plan fits best?"
options:
  - "A rolling update, then watch for complaints"
  - "A blue-green switch of all traffic at midnight"
  - "A canary or a flag, compared with stable"
  - "Stop the service, deploy, and start it again"
correct: 2
explanations:
  - "A rolling update grows the share of new pods step by step and has no way to hold at 1%. Undoing it is another slow update."
  - "A blue-green switch moves everyone at once. The rollback is fast, but the blast radius is 100% of users, not 1%."
  - "Right. A small share limits the users who can be hurt, comparing with the stable version shows the problem, and turning it off is a router or flag change."
  - "Stopping the service causes an outage and tests nothing on a small group first."
```

```quiz
type: mcq
question: "A small team wants to run PostgreSQL on its own virtual machine instead of a managed database, to save about $40 a month. Which cost are they most likely to miss?"
options:
  - "The domain name of the database server host"
  - "The network card inside the virtual machine"
  - "The size of any container image they choose"
  - "Their own backups, patching and failover"
correct: 3
explanations:
  - "A domain name is a small, one-time job. It is not what a managed service saves you from."
  - "The network card is part of the virtual machine and is not a cost the team has to think about."
  - "A database on a virtual machine need not use a container image. Image size is not the missing cost."
  - "Right. A managed database includes backups, patches and an automatic standby. Self-run, the team does all of it, and a missed backup or failed failover costs far more than $40."
```
