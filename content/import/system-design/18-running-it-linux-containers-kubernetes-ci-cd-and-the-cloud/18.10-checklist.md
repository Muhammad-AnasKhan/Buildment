## Your gate answer: a deploy and rollback plan

The scenario: Daftar adds a "share a note" feature. It needs a new route, `POST /notes/:id/share`, and a new column `share_token` on the `notes` table. Daftar runs as four pods on Kubernetes, behind a Service, with 20,000 students online on weekday evenings. The team has a pipeline like the one in challenge 17. The release is planned for a Tuesday at 4 pm, before the evening peak, so that there is time to watch it.

Why this question? Because it joins every chapter of the module into one decision. The pipeline gives the image, the probes and drain make a rolling update safe, the strategy decides who is reached first, and the column in the database is the part no strategy can undo. In a real review, nobody asks about these one at a time. They ask what happens at 4:10 pm if the error rate climbs.

A strong answer covers five things in about 120 words. First, the pipeline: which gates the change must pass, and what is built once. Second, the strategy: which of the four you use and why, with the share of users it reaches first. Third, the signal: what you watch, compared with what, and what number makes you stop. Fourth, the rollback: the exact action, and how long it takes. Fifth, the step that cannot be undone, which here is the new column, and how you make it safe. Think about how the old pods and the new pods can both live with the same table while the rollout runs.

Show numbers where you can. "A small share first" is weaker than "1 of 4 pods for 15 minutes, which is about 25% of requests, so I would rather use a flag at 5%". Use a result from your own challenge 17 run, for example how many requests failed with and without a readiness probe, or how long a rollback took.

Watch for three common gaps. The first is a plan with no stop number: "watch the dashboard" is not a decision rule. The second is a rollback that undoes the code but leaves the database change in a state the old code cannot read. The third is forgetting that a rolling update runs two versions at once, which is the reason the column should be added in a separate release before any code uses it.

How will the mentor read it? The plan is not graded on which strategy you pick. Several choices are defensible here: a flag with a rolling deploy, a small canary, or even a plain rolling update with strong probes for a team that is small and watches closely. What the mentor looks for is that your choice follows from your numbers, that you name the number at which you stop, and that your rollback is a specific action with a time attached. "I would roll back if it looks bad" fails all three. "I turn the flag off, which takes about ten seconds, if the flagged group's error rate passes 2% for three minutes" passes them.

The database change deserves a sentence of its own. The new column can be added in a release before the code that uses it, as chapter 18.6 described: old pods ignore a column they do not know about, and new pods can rely on it. That makes every later step reversible, and it is the part of this plan that no strategy can do for you. If you also have a view on what to do with a share token that has already been sent to someone, say so: some side effects cannot be taken back.

Keep the plan short. A release plan that nobody reads on the day is worth nothing, so write it as the five short answers above rather than an essay. Put the link to your challenge 17 folder in the link field. You may also record yourself explaining the plan at a whiteboard or on paper. The written answer is required; a recording is optional and should show only your work, not your surroundings. If the mentor asks a follow-up question, answer it by editing and resubmitting.
