Hana used to copy Daftar's code to the server by hand. One evening she forgot a step, and the site was half updated for an hour. A **pipeline** does the steps for her, the same way every time: it tests the code, builds the image and ships it.

## A commit starts a conveyor

<MermaidDiagram title="A pipeline for the Daftar API" chart={`flowchart LR
  C["Commit pushed"] --> L["Lint: 0.2 s"]
  L --> T["Service tests: 3 s"]
  T --> B["Build image: 38 s"]
  B --> S["Smoke test: 6 s"]
  S --> G{"Gates: size, scan, approval"}
  G -->|"all green"| R["Publish image to registry"]
  R --> D1["Deploy to staging"]
  D1 --> D2["Deploy to production"]
  L -.->|"red"| X["Stop, tell the author"]
  T -.->|"red"| X
  S -.->|"red"| X
`} legend="Each stage is a gate. A red stage stops the pipeline and the later stages do not run. The times are from the challenge 17 pipeline on a laptop." />

A pipeline is a chain of **stages**. A commit enters on the left. Each stage either passes it on or stops it with a red mark and a message to the author. Only a commit that passes every gate reaches production. The first half is **continuous integration** (CI): check every change. The second half is **continuous delivery** or **deployment** (CD): ship it.

<GoDeeper title="Go deeper: CI, delivery and deployment, and GitHub Actions words">

Three terms are often mixed up. <GlossaryTerm term="continuous integration" definition="Merging small changes into the shared code many times a day, and checking every merge automatically with a build and tests." /> means every change is built and tested automatically, soon after it is made. Continuous delivery goes further: every change that passes can be released, and a person presses the button. Continuous deployment removes the button: a change that passes every gate goes to production by itself. Which one a team uses depends on how much it trusts its gates, and how bad a wrong release is.

GitHub Actions, which you set up in chapter 1.5, uses four words. A **workflow** is a YAML file in `.github/workflows` that starts on an event, such as a push. A workflow has **jobs**. A job runs on a **runner**, a fresh machine, and is a list of **steps**. Jobs run at the same time unless one says `needs` another. A failed step fails its job, and a job that needs it is skipped [GitHub documentation, fetched 2026-10-24].

Here is the workflow from challenge 17, `.github/workflows/ship.yml`, cut down to its shape:

```yaml
name: ship
on:
  push:
    paths: ["challenges/challenge-17-ship-it/**", "toolkit/**"]
jobs:
  checks:                       # job 1: cheap checks, no Docker needed
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 24 }
      - run: node challenges/challenge-17-ship-it/part-1-containers/lint.js challenges/challenge-17-ship-it/app/Dockerfile
      - run: npm ci --prefix challenges/challenge-17-ship-it/app
      - run: node --test challenges/challenge-17-ship-it/app/server.test.js
  image:                        # job 2: runs only if job 1 passed
    needs: checks
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - run: docker build -t daftar-api:${{ github.sha }} challenges/challenge-17-ship-it/app
      - run: node challenges/challenge-17-ship-it/part-2-pipeline/smoke.js daftar-api:${{ github.sha }}
```

The `paths` filter means a commit that only changes another challenge does not run this pipeline. The image is tagged with the commit's ID, `github.sha`, so every image can be traced back to the code that made it.

## Play: step through, then break a stage

<InteractiveCanvas slug="sysdesign-m18-pipeline-step" />

Step a commit through the six stages and watch the clock count the seconds. Then tap a stage to break it. The stage turns red, every stage after it is skipped, and the clock shows how long you waited to find out. Break a late stage, then an early one, and compare.

<GoDeeper title="Go deeper: what the red mark should tell you">

A good pipeline answers three questions at once: what failed, where, and what to do. "Build failed" is a poor message. `lint: COPY . . copies your code before the install` is a good one, because the author knows the fix without opening a log.

Pipelines fail for three kinds of reasons. A real bug in the change, which is what the pipeline exists for. A broken environment, such as a registry that was down for a minute. And a flaky test, one that passes and fails on the same code. Flaky tests are the most costly. If the team learns that a red mark often means nothing, they start to ignore red marks, and then the gate no longer protects anything. Fix or delete a flaky test quickly; do not retry it until it goes green.

Treat a red pipeline on the main branch as an emergency. No new work lands on top of a broken main, because nobody then knows whether their own change is the cause.

The times in the picture are from the challenge 17 pipeline on a laptop with a cold cache: lint 0.2 s, service tests 2.8 s, build 38.0 s, smoke test 6.4 s, size check 1.0 s, 48.4 s in total. A real service is slower. What matters is the proportion, as the next beat shows.

</GoDeeper>

## Cheap checks go first

<InteractiveCanvas slug="sysdesign-m18-fail-fast" />

Both pipelines have the same stages and find the same Dockerfile mistake. One runs the cheap lint check first and is red after 0.2 seconds. The other builds the image first and is red after 25 seconds. Order stages from cheapest to dearest, so a failure never waits behind a long build.

<GoDeeper title="Go deeper: ordering stages, and the measured run">

Put the stages in order of cost, and put the ones most likely to fail early. Lint and unit tests take seconds. An image build takes much longer. Integration tests that start a database take longer still, and end-to-end tests longest. A change that fails the first check should never have paid for the last.

You can run both orders on your laptop in challenge 17. With the naive Dockerfile, which breaks several habits from chapter 18.3, we got:

| Order | Stages that ran | Time until red |
|---|---|---|
| Cheap first | Lint (red) | 0.2 s |
| Slow first | Build 12.2 s, smoke 8.2 s, tests 3.8 s, lint (red) | 24.6 s |

The same mistake, found more than 100 times sooner. On a shared runner in the cloud, the build also queues and costs money by the minute, so the saving is larger.

Two further ways to shorten a pipeline. Run independent stages at the same time (two jobs without `needs`). And reuse work: cache the downloaded packages and the Docker layers between runs, which is chapter 18.3's layer rule applied to the pipeline. A pipeline that takes an hour gets run less, and changes then pile up in bigger, riskier batches.

The principle of short feedback is old. Martin Fowler's description of continuous integration has the same advice: keep the build fast, so people run it often {/* source needed: Fowler, Continuous Integration, martinfowler.com/articles/continuousIntegration.html (not yet read for this dossier) */}.

</GoDeeper>

## Build once, promote the same image

<InteractiveCanvas slug="sysdesign-m18-build-once" />

CI builds the image one time and pushes it to a registry under a fingerprint, here `ab12cd`. Staging runs that image and the tests pass against it. Production pulls the very same image. What was tested is what ships. Settings that differ, like a database address, arrive from outside.

<GoDeeper title="Go deeper: artifacts, digests and what differs between environments">

The thing a pipeline produces and moves along is called an <GlossaryTerm term="artifact" definition="A built result that the pipeline stores and promotes from one environment to the next, such as a Docker image or a package. It is built once and never rebuilt." />. For Daftar the artifact is an image. A tag like `1.4.0` can be moved to point at another image. A <GlossaryTerm term="digest" definition="A fingerprint of an image's exact content, written sha256: followed by letters and numbers. Two images with the same digest are the same bytes." /> cannot. Deploying by digest, or by a tag that includes the commit ID as the pipeline above does, means you know exactly what is running.

If each environment rebuilt from source, three problems follow. The bytes can differ, as the prediction showed. A bug that appears only in production cannot be reproduced from the tested image. And a rollback means rebuilding an old version, which may no longer build, because a package it needs was removed.

The environments still differ in settings, such as the database address, the log level and secrets. These must come from outside the image: environment variables, a config object in Kubernetes, or a secrets service. In GitHub Actions, secrets are stored in the repository settings and shown to a job only when a step asks for them; they are hidden in logs. For a cloud, prefer short-lived credentials that the job gets for one run, not a long-lived key saved as a secret. Never write a secret into the image or the repository.

## A smoke test can undo a release

<InteractiveCanvas slug="sysdesign-m18-smoke-rollback" />

After deploying, the pipeline checks the new version before real users get it. It starts one v2 pod next to the running v1 pods and runs a **smoke test**: does it start, and do its main routes answer? Here it gets a 500, so the pipeline removes v2. Users stayed on v1 the whole time.

<GoDeeper title="Go deeper: what a smoke test does, and what it cannot do">

A <GlossaryTerm term="smoke test" definition="A very short test of a running system that checks only that it starts and answers its main requests. It is named after switching on new hardware and seeing whether smoke comes out." /> is cheap and broad. The one in challenge 17 starts the image, waits for `/ready`, then checks `/ready`, `/health` and `/` and prints each problem it finds. It takes about two seconds.

It catches the mistakes that cost the most users the most quickly: the image does not start, a setting is missing, a route is gone. It does not catch a slow memory leak, a bug that shows only with real data, or a change that is correct but unwanted. Those need metrics and a gradual release, which chapter 18.6 covers.

Automatic rollback needs two things. A check that is trustworthy (otherwise the pipeline cancels good releases), and a way back that is cheap. With Kubernetes the way back is `kubectl rollout undo`, or simply not promoting the new pods.

Add a **size gate** like the one in the challenge: fail the pipeline if the image is larger than a limit (300 MB there). A gate turns a habit into a rule that nobody can forget. The naive Dockerfile makes a 1,637 MB image and stops at that gate.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "The pipeline runs the cheap checks first and stops at the first red. It builds one image per commit and promotes that same image from staging to production. A smoke test checks the new version before users get it, and the pipeline rolls back if it fails."

The follow-up is usually: "Why not rebuild the image for each environment?" Because two builds can differ: a base image tag moves, or an install picks newer packages. Then the thing you tested is not the thing you shipped, and a production-only bug cannot be reproduced.

</GoDeeper>
