One container on one server is a single point of failure, as chapter 4.1 showed. Several copies on several machines fix that, but somebody must start them, replace the ones that die and roll out new versions. Kubernetes does that job. This chapter covers only what a system designer needs, not how to run a cluster.

## You declare it, the cluster keeps it true

<MermaidDiagram title="The objects you meet first" chart={`flowchart LR
  U["Users"] --> S["Service: stable address, finds pods by label"]
  S --> P1["Pod 1: container daftar-api"]
  S --> P2["Pod 2: container daftar-api"]
  S --> P3["Pod 3: container daftar-api"]
  D["Deployment: wants 3 pods, manages updates"] --> R["ReplicaSet: keeps the count"]
  R -.-> P1
  R -.-> P2
  R -.-> P3
  H["Autoscaler: changes the wanted count from CPU"] -.-> D
`} legend="You write what you want (a Deployment). The ReplicaSet keeps the right number of pods. The Service gives them one address. The autoscaler can change the number." />

A **pod** is the smallest thing Kubernetes runs: one or a few containers that share a network address. A **Deployment** says "keep 3 copies of this pod running, and update them safely". A **Service** gives those pods one stable address. You describe the result you want, and controllers work to make the real cluster match it, over and over.

<GoDeeper title="Go deeper: the control loop, and when Kubernetes is too much">

Kubernetes is a set of <GlossaryTerm term="control loop" definition="A program that compares the state you asked for with the real state, acts to close the gap, and repeats forever." /> programs. You store a wish in the cluster's database (3 replicas of this image). A controller reads the wish, counts the real pods, and starts or stops pods until the numbers match. If a machine dies, the count drops, and the controller starts pods on other machines. You never say "start a pod now". You say how many you want.

The machines that run pods are called nodes. The control plane, a set of programs on separate machines, holds the wishes and runs the controllers. A scheduler picks a node for each new pod, using the CPU and memory the pod asked for.

What you write is usually a YAML file. The Deployment in challenge 17 is about 50 lines. You apply it with `kubectl apply -f`, and `kubectl` talks to the cluster's API.

Kubernetes is not free. A cluster is more machines to run, more concepts to learn and more things that can go wrong. Alternatives that keep more of the work with a provider are worth a look: Amazon ECS runs containers without Kubernetes' extra concepts, and AWS Fargate removes the nodes entirely. A single server with Docker Compose is enough for a small service. Kubernetes pays off when many services, several teams or fast rollouts need a common way to run things.

The things this chapter skips are real topics: operators, network policies, service meshes and Helm charts are out of scope for this course.

## Kill a pod, a new one starts

<InteractiveCanvas slug="sysdesign-m18-pod-replaced" />

The Deployment wants three pods. Pod B crashes. The controller sees two of three and starts a new Pod B, which becomes ready. Nobody had to log in. In our test on a local cluster, a deleted pod was replaced within a second, and all three pods were ready again after about six seconds, most of it the service's own three-second warm-up.

<GoDeeper title="Go deeper: what a restart costs, and a crash loop">

There are two kinds of restart. If a container inside a pod exits, the kubelet (the agent on the node) restarts that container in the same pod. If the whole pod is deleted or its node dies, the ReplicaSet creates a new pod, possibly on another node.

A container that keeps crashing is restarted with an exponential back-off, so it cannot hammer the node. The status then shows `CrashLoopBackOff`, which means "waiting before the next try", not a separate failure. If it runs well for long enough, the delay resets.

The replacement is not instant for users. While a new pod starts, the other two carry the load. That is the N+1 rule from chapter 4.2: with three pods at 80% busy, losing one leaves two at 120%. Start with enough spare room that one lost pod leaves the rest under the knee.

Here is what the pods looked like in our run, a few seconds after a stuck pod was restarted by its liveness probe (the probes beat below explains why):

```text
NAME                          READY   STATUS    RESTARTS     AGE
daftar-api-66b7fcb95f-9sjtk   0/1     Running   1 (1s ago)   44s
daftar-api-66b7fcb95f-9xm4v   1/1     Running   0            33s
daftar-api-66b7fcb95f-mgqrr   1/1     Running   0            24s
```

`READY 0/1` means the restarted container has not passed its readiness probe yet, so it gets no traffic. `RESTARTS 1` shows the kubelet restarted it once.

</GoDeeper>

## A Service finds pods by label

<InteractiveCanvas slug="sysdesign-m18-service-labels" />

Pods come and go, and each new pod has a new address. The Service gives the group one fixed address and name. It sends each request to a pod that carries the right **label**, here `app=daftar-api`. Pod C carries a different label, so it gets nothing.

<GoDeeper title="Go deeper: selectors, DNS and the NodePort used in the challenge">

A label is a key and a value attached to an object, such as `app: daftar-api`. A Service has a selector with the same pair. The cluster keeps a list of the addresses of all ready pods that match, and the Service spreads requests over that list.

Inside the cluster, other pods reach the Service by name. A Service called `daftar-api` in the `default` namespace has the DNS name `daftar-api.default.svc.cluster.local`, and just `daftar-api` from the same namespace [S147]. This is service discovery, which module 12 introduced.

There are three common Service types. `ClusterIP` is reachable only inside the cluster. `NodePort` also opens one port, in the range 30000 to 32767 by default, on every node. `LoadBalancer` asks the cloud for a real load balancer in front. The challenge uses `NodePort` 30080 so that your laptop can reach the service, and `kind.yaml` maps laptop port 8080 to it.

```yaml
# The Service from challenge 17.
apiVersion: v1
kind: Service
metadata:
  name: daftar-api
spec:
  type: NodePort
  selector:
    app: daftar-api
  ports:
    - port: 80
      targetPort: 3000
      nodePort: 30080
```

In AWS, a `LoadBalancer` Service on EKS creates an AWS load balancer for you (chapter 4.4 named the two kinds, ALB and NLB).

## Not ready is not the same as stuck

<InteractiveCanvas slug="sysdesign-m18-probe-split" />

A **readiness** probe asks "should this pod get traffic now?" When it fails, the pod is taken out of the Service's list but left running. A **liveness** probe asks "is this pod stuck?" When it fails three times in a row, the kubelet restarts the container. Same HTTP check, two different actions.

<GoDeeper title="Go deeper: three probes, defaults and the failure we measured">

Kubernetes has three probes [S20]. A **startup** probe holds off the other two while a slow program starts. A **liveness** probe decides when to restart a container. A **readiness** probe decides whether the pod receives traffic. When a readiness probe fails, the EndpointSlice controller removes the pod's IP address from the lists of all matching Services.

The defaults are a check every 10 seconds, a timeout of 1 second, and 3 failures in a row before the probe counts as failed. They are set per probe; the challenge uses a readiness check every 2 seconds and a liveness check every 5 seconds.

This is the same idea as chapter 4.4's health checks, split in two. Keep the readiness check honest about this pod only: "have I finished warming up, and am I not shutting down?" Do not make a liveness check depend on the database. If the database is slow, restarting every app pod does not fix it and makes it worse.

We measured what a readiness probe buys. We rolled out a new version while 20 requests a second hit the Service, with two Deployment files. The careless one had no readiness probe and its service quit at once on SIGTERM. The careful one had both probes and a graceful drain.

| Deployment | Requests | Failed |
|---|---|---|
| Careless: no readiness probe, quits at once | 183 | 112 |
| Careful: probes, drain, no pod removed early | 392 | 0 |

The careless rollout finished faster, and that is the trap: it removed old pods before the new ones could serve. In the same run, a stuck pod (made to fail `/health`) was restarted by its liveness probe about 19 seconds later: three failures, five seconds apart, plus the time to restart.

## Play: kill, fail, scale

<InteractiveCanvas slug="sysdesign-m18-cluster-play" />

Tap a pod to kill it and watch the Deployment replace it. Tap the pill under a pod to fail its readiness check and watch the Service drop it. Switch the autoscaler on, drag the load up, and see how many pods it asks for. Keep the load steady and fail one pod: do the others stay under the knee?

<GoDeeper title="Go deeper: what to notice">

Three things to look for. First, killing a pod changes nothing for users if the pods that remain have room: that is N+1 again. Second, a pod that fails its readiness probe is alive but gets no requests, so the others carry its load, and the picture should show the same jump in load as if it had died. Third, the autoscaler does not act on one reading. It waits for its check, ignores small changes, and scales down slowly.

In the real cluster you can do the first two by hand. `kubectl delete pod NAME` kills a pod. To fail a readiness probe, make the endpoint answer 503, as the sample service does while it drains. `kubectl get pods --watch` shows the changes as they happen.

The model in the picture is simplified. It ignores start-up time, the time the Service takes to notice, and the cost of the control plane itself.

</GoDeeper>

## A rolling update swaps pods in small steps

<InteractiveCanvas slug="sysdesign-m18-rolling-surge" />

A rolling update starts one new pod, waits until it is ready, then stops one old pod, and repeats. With three pods, one extra allowed (`maxSurge: 1`) and none allowed to be missing (`maxUnavailable: 0`), there are always three ready pods. That is the careful setting used in the challenge.

<GoDeeper title="Go deeper: surge, unavailable and the order of events">

Two numbers control a rolling update. `maxSurge` is how many pods above the wanted count may exist during the update. `maxUnavailable` is how many may be missing. Both default to 25%, rounded: surge up, unavailable down [S35]. For four pods that is one extra and one missing.

The default allows one pod fewer than wanted. With the safe setting, `maxUnavailable: 0`, a new pod must be ready before an old one is removed, which needs room for one extra pod while it runs. Spare capacity again.

A rollout is only as safe as its probes. Without a readiness probe, "ready" means "started", and the update races ahead while new pods are still warming up. That is the 112 failed requests in the last table.

The old pod's shutdown also matters. The control plane removes a stopping pod from the Service and sends it SIGTERM at about the same time, and these are not guaranteed to reach every part of the system together. A short wait before the service stops listening, `SHUTDOWN_DELAY_MS` in the sample (3 seconds in the challenge manifest), covers that gap.

To go back, `kubectl rollout undo deployment/daftar-api` does another rolling update to the previous version. It is as slow as the update itself. Chapter 18.6 compares that with faster ways to undo a release.

## The autoscaler is chapter 4.6 inside the cluster

<InteractiveCanvas slug="sysdesign-m18-hpa-scale" />

The Horizontal Pod Autoscaler uses the rule you met in chapter 4.6: desired pods equal the current count times the measured value divided by the target, rounded up. Three pods at 90% CPU against a 60% target: 3 times 90 divided by 60 is 4.5, so 5 pods, each at 54%.

<GoDeeper title="Go deeper: requests, tolerance and the lag">

The autoscaler runs a loop every 15 seconds by default and applies the formula [S34]. Its CPU figure is a percentage of the pod's CPU **request**, not of the machine. A pod that asked for 100m (a tenth of a CPU) and uses 90m is at 90%. This is why requests matter: set them near real use, or the percentage means little.

It ignores small differences. If the ratio of measured to target is within 10% of 1.0, it does nothing. It scales up at once but scales down only after a stabilisation window, 300 seconds by default, so a short dip does not remove pods that are needed a minute later. Chapter 4.6 explained flapping, and this is the cure.

The delays from chapter 4.6 all apply. The autoscaler notices the spike after up to 15 seconds, and a new pod needs time to start and warm up, so the cluster is always a little late. If a new pod also needs a new node, add the time to get a machine. A readiness probe keeps the cold pod from taking traffic before it can serve.

A cluster needs a metrics source before the autoscaler can work. Many local setups, kind included, do not ship one, so we skip autoscaling in challenge 17 and use the picture instead.

Pick a ceiling. Twice as many pods send twice as many queries to the database, and that part may not scale (modules 8 and 9). In AWS, EKS clusters use this autoscaler, and the nodes underneath scale separately.

<GoDeeper title="In an interview">

Say: "I declare a Deployment with three replicas behind a Service. Readiness decides who gets traffic and liveness decides who gets restarted. A rolling update with maxUnavailable 0 and a readiness probe keeps capacity during a release. The autoscaler computes the new count as the current count times the measured CPU divided by the target, rounded up."

The follow-up is usually: "What happens if there is no readiness probe?" Pods count as ready as soon as the container starts, so they get traffic during warm-up and a rollout fails requests. In our measurement that was 112 failed requests out of 183, against none with the probe.

</GoDeeper>
