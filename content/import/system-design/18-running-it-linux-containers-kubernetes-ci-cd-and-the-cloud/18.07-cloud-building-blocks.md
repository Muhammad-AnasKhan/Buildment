Every design in this course used the same boxes: servers, a load balancer, a cache, a database, a queue. A cloud provider rents you each box by the hour. This chapter is a map from the boxes to cloud services, with Amazon Web Services (AWS) names as notes. It is not a tour of a catalogue.

## Four groups of blocks

`} legend="Compute runs your code. Data blocks keep state. The network is the walls and doors around everything. Each name is one example; other clouds have equivalents." />

Compute runs your code. Storage and databases keep state. A queue passes work between parts. The network decides who can reach what. When you read any cloud diagram, find these four groups first. The names change from provider to provider, but the groups stay.

<GoDeeper title="Go deeper: why cloud, and what you give up">

Renting has three benefits for a system designer. You pay for what you use, by the hour or the request, so a small service costs little. You can add capacity in minutes, which is what made the autoscaling of chapter 4.6 possible. And you do not run the hardware.

It has costs too. Prices are by the unit and the units add up: data leaving the cloud, requests, idle load balancers. A design that is cheap at 10 requests a second can be dear at 10,000. You depend on the provider, so moving later is work. And you share a machine with strangers, which is why the isolation of chapter 18.2 matters.

Most clouds group machines into **regions** (a place in the world) and **availability zones** (separate buildings inside a region, so one fire does not take all of them). Module 19 covers them in detail. For now: spread across zones, as chapter 4.2's N+1 rule says, and expect the network between zones to cost a little time and sometimes money.

This chapter gives AWS names as notes so a later AWS course can build on them. It is not a tour of AWS, and it does not teach certification topics. Prices appear only as made-up round numbers to compare shapes: always read the provider's current price page before you plan a budget.

</GoDeeper>

## Compute: how much do you manage?

<MermaidDiagram title="From virtual machine to function" chart={`flowchart LR
  VM["Virtual machine: EC2"] --> CO["Containers on your machines: ECS or EKS on EC2"]
  CO --> SC["Containers on provider machines: Fargate"]
  SC --> FN["Functions: Lambda"]
  VM -.-|"you manage the operating system and patches"| CO
  FN -.-|"you manage only the code"| SC
`} legend="Left to right: you manage less and the provider manages more. You also control less, and usually pay more per unit of work when the load is steady." />

Moving right, you manage less. On a **virtual machine** you patch the operating system. With **containers** you manage the image. **Fargate** runs containers without machines you can see. A **function** runs your code for one request and bills per run. The right choice depends on how steady your load is and how much control you need.

<GoDeeper title="Go deeper: the four options and when each fits">

**Virtual machine (EC2).** A server you rent by the hour. You choose the size and the operating system. This is the closest to what you ran in module 4. It suits steady load and software that needs a full machine. You patch it, and you handle scaling and failure yourself, perhaps with an Auto Scaling group.

**Containers on your machines (ECS or EKS on EC2).** You run the images from chapter 18.3. Amazon ECS is a container service from AWS; Amazon EKS runs Kubernetes (chapter 18.4). You still choose and pay for the machines under them. Amazon ECR holds the images.

**Containers without machines (Fargate).** You say how much CPU and memory a container needs, and the provider finds a place to run it. You do not see or patch the machine.

**Functions (Lambda).** AWS describes Lambda as a compute service that lets you run code without provisioning or managing servers {/* source needed: Lambda definition (docs.aws.amazon.com/lambda/latest/dg/welcome.html, fetched 2026-10-24) */}. Your code runs when an event arrives, for as long as it needs, and you pay for that time. It suits spiky or rare work, such as resizing an uploaded image. It does not suit a service that must hold a connection open for hours, and a function that has not run for a while starts slowly (a cold start).

The same trade-off appears everywhere: control and low price per unit for steady load on one side, no operations and flexible scaling on the other. For a steady, busy API, containers or virtual machines are often cheaper than functions. For a job that runs ten times a day, functions are almost free.

<GoDeeper title="Go deeper: the storage types and a sample of the map">

Storage comes in three shapes.

| Shape | Example | Think of it as | Best for |
|---|---|---|---|
| Object | Amazon S3 | A huge bucket of files, each reached by a name | Photos, exports, backups, static sites |
| Block | Amazon EBS | A disk you attach to one machine | A database's data files, a server's disk |
| File | Amazon EFS | A shared folder many machines mount | Files shared by several servers |

Amazon S3 stores data as objects within buckets; an object is a file plus its metadata, and a bucket is a container for objects. Amazon EBS provides volumes of several types that differ in performance and price, and attaches them to EC2 machines {/* source needed: S3, EBS and EFS definitions (AWS documentation pages fetched 2026-10-24); object storage is usually the cheapest per gigabyte and file storage the dearest, check current prices */}.

## The network around it: public and private

<MermaidDiagram title="A private network with a public door" chart={`flowchart TB
  NET["Internet"] --> IGW["Internet gateway"]
  subgraph VPC["VPC: your private network"]
    IGW --> ALB["Load balancer in public subnets, two zones"]
    subgraph PRIV["Private subnets"]
      ALB --> APP["App servers: no public address"]
      APP --> DB["Database: reachable only from the app"]
    end
    APP -.->|"outbound only, through a NAT gateway"| NET
  end
`} legend="Only the load balancer is reachable from the internet. App servers and the database sit in private subnets and accept traffic only from the layer in front of them." />

Put as little as possible where the internet can reach it. In a **VPC** (virtual private cloud) the load balancer sits in a public subnet. App servers and the database sit in private subnets with no public address. Security groups are rules that say which layer may talk to which. A request must pass the front door to get in.

<GoDeeper title="Go deeper: subnets, security groups and the hidden costs">

A VPC is your own isolated network inside the cloud, with address ranges you choose. You split it into **subnets**, usually one set per availability zone. A subnet is public if it has a route to the internet, and private if it does not. A **security group** is a firewall for a machine or a load balancer that lists what traffic may come in and go out. A common rule: the database accepts connections only from the app servers' security group, never from the internet.

Private servers sometimes need to reach out, for example to download a package or call a payment provider. A **NAT gateway** lets them make outbound connections without being reachable from outside. It is a service you pay for by the hour and by the gigabyte, and teams are often surprised by its bill {/* source needed: NAT gateway pricing model (AWS VPC pricing page, not read) */}.

This picture is the three-tier design from chapter 4's gate: web tier in front, app tier behind it, data tier behind that, with only the first tier public.

Two more costs live in the network. Data leaving the cloud to the internet is charged per gigabyte, which is why a CDN (module 5) can lower the bill as well as the latency. Data moving between zones may be charged too, which is a reason to keep chatty services together {/* source needed: data transfer charges, check the provider's price page */}.

</GoDeeper>

## Managed means the provider repairs it

<InteractiveCanvas slug="sysdesign-m18-managed-failover" />

The primary database fails. In a managed database the provider promotes the standby in another zone and the same name now points at it. The app reconnects. You did not wake up at 3 a.m. You also cannot log in to the machine, and you pay for the standby even when it is idle.

<GoDeeper title="Go deeper: what managed includes, and what it does not">

A **managed** service means the provider runs the machines for that block. For a database such as Amazon RDS, that usually includes backups, patching and a standby copy in another zone with automatic failover. The module on replication (module 8) showed what a failover costs in lost writes and wrong promotions; a managed service does that work for you, with settings you can read and tune. Aurora replicas, for example, are documented to lag by much less than 100 ms [S39].

What you give up: control and sometimes cost. You cannot install a custom extension that the provider does not allow. You pay a premium over running the same software on a virtual machine. Settings that matter, such as how long a failover may take and how much data may be lost, are still yours to choose. A failover is not instant, and requests in flight during it can fail, so your app must retry (module 6).

**Queues.** Amazon SQS is a managed queue. A standard queue delivers a message at least once, so duplicates can happen and the consumer must be safe to repeat [S83]. A message that is being processed is hidden for a visibility timeout, 30 seconds by default and at most 12 hours [S84]. A message that fails too many times can be moved to a dead-letter queue for a person to look at [S85]. Module 15 builds all of this.

**Rule of thumb.** Use the managed version of anything that is not your product. Run a database yourself only when you need something the managed one cannot give you, and know what you take on: backups, upgrades and failover.

</GoDeeper>

## Try the cloud APIs on your laptop

<MermaidDiagram title="The same code, two endpoints" chart={`flowchart LR
  APP["Your code: PUT to a bucket, send to a queue"] -->|"endpoint: https://s3.amazonaws.com"| AWS["Real AWS: needs an account and costs money"]
  APP -->|"endpoint: http://127.0.0.1:5000"| MOTO["moto in a container: needs nothing"]
`} legend="Cloud tools let you change the address they call. Point it at a local emulator and the same code runs on your laptop, with no account and no bill." />

You do not need an AWS account to learn how S3 and SQS behave. An **emulator** is a program that answers the same HTTP calls. **moto** is an open-source one (Apache-2.0 licence, about 104 MB as a container image [S127]). Start it, point your code at `http://127.0.0.1:5000`, and the calls work. Challenge 17 part 4 does exactly this, with no account and nothing to pay.

<GoDeeper title="Go deeper: moto, LocalStack, and what an emulator cannot tell you">

LocalStack was the usual choice for years. In March 2026 it changed: from release 2026.3.0 it ships a single image, and the latest releases need an account and an auth token, even in CI [S121, S122]. Its free Hobby plan prohibits commercial use [S123]. Older tags such as 4.14 still exist, but LocalStack itself warns that pinning one means drift and unpatched problems [S121]. This course uses moto by default because it needs no account.

An emulator is for learning the shape of an API and testing your code. It is not the real service. Differences to expect: limits, timing, permissions (real AWS checks who is allowed to do what, moto does not by default), and failure behaviour. Never trust an emulator for performance numbers or for security rules. Test against the real service before you rely on it for either.

The three habits from this chapter that matter most when you do meet the real thing: give every machine and database the smallest network access it needs, set a budget alert before you start, and delete what you create. Cloud bills come from things left running.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "I use the managed version of anything that is not my product: a managed database, object storage for files, a queue for background work. Steady services run in containers, rare jobs run as functions. The load balancer is the only public part. App servers and the database sit in private subnets."

The follow-up is usually: "Why not run Postgres yourself to save money?" Because you take on backups, patching and failover. The monthly saving is small next to one bad day, and a managed service documents the failover you would otherwise have to build.

</GoDeeper>
