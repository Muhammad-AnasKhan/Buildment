Every deploy of Daftar starts with a build. If a one-line change takes five minutes to build, or the image takes half an hour to download on a weak connection, people stop deploying often, and big risky releases follow. This chapter is about building images that are small, quick to rebuild and safe to run.

## An image is layers, a container adds one

<MermaidDiagram title="Image layers and a running container" chart={`flowchart TB
  subgraph IMG["Image daftar-api:1 (read-only layers)"]
    direction TB
    L1["Base: node:24-alpine"] --> L2["COPY package.json and lock file"]
    L2 --> L3["RUN npm ci: node_modules"]
    L3 --> L4["COPY server.js"]
  end
  L4 --> W["Container: thin writable layer on top, deleted with the container"]
`} legend="An image is a stack of read-only layers, one per Dockerfile step that changes files. A running container adds one thin writable layer on top." />

An **image** is a stack of read-only layers. Each Dockerfile step that changes files adds one layer. A **container** is an image that is running, with one thin writable layer on top. Many containers can share the same image layers on disk, so starting a second one costs almost nothing.

<GoDeeper title="Go deeper: layers, caching and the writable layer">

Each layer stores only the files that step changed. Docker names a layer by a fingerprint of its content. Two images that start with the same base share that base on disk and in the registry, and a machine that already has a layer does not download it again.

The writable layer on top is where a container writes any file that is not in a volume. It is deleted when the container is removed, which is why chapter 4.3's rule, keep servers stateless, is also a container rule. Writing there can also be slower than writing to a volume, because of how layers are merged.

The image stays the same as it runs: a container that creates files does not change its image. To make a new image you build one. That is the property that makes "the same image on every machine" true.

The Docker documentation describes the build cache with a simple rule that the next beat shows: each instruction is checked in order, and once one layer changes, every layer after it is built again.

## Change one file, see what rebuilds

<InteractiveCanvas slug="sysdesign-m18-layer-cache" />

Tap a file to change it, then switch the Dockerfile order. With the copy-everything order, any change rebuilds the slow install. With the package files first, a code change reuses the cached install and only the last step runs. Where a step sits decides how often it runs.

<GoDeeper title="Go deeper: a Dockerfile for a Node service, line by line">

This is the Dockerfile for the sample service in challenge 17. Slow-changing things come first, fast-changing things last.

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine
ENV NODE_ENV=production
WORKDIR /app

# 1. Dependencies change rarely, so they get their own layer.
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# 2. Your code changes on every commit, so it comes last.
COPY server.js ./

# 3. The version is baked into the image: build once, run the same image everywhere.
ARG APP_VERSION=dev
ENV APP_VERSION=$APP_VERSION

# 4. Do not run as root.
USER node
EXPOSE 3000
HEALTHCHECK --interval=10s --timeout=2s --start-period=5s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"

# Exec form: node itself is process 1 and receives SIGTERM.
CMD ["node", "server.js"]
```

`FROM node:24-alpine` picks the base. `npm ci` installs exactly what `package-lock.json` lists and fails if the lock file and `package.json` disagree, so every build gets the same packages. `--omit=dev` leaves out test tools. `USER node` runs the process as an ordinary user, so a bug in your code does not start with root rights inside the container. `CMD` is in exec form, for the reason chapter 18.2 gave.

Add a `.dockerignore` file next to the Dockerfile with `node_modules`, `.git` and test files. Without it, `COPY . .` would send your whole local `node_modules` folder, built for your operating system, into the build.

We measured the naive version against this one in challenge 17. The naive Dockerfile is `FROM node:24`, `COPY . .`, `RUN npm install`, `CMD node server.js`. Times depend on your network and machine; the pattern matters.

| | Naive | This Dockerfile |
|---|---|---|
| Image size on disk | 1,637 MB | 251 MB |
| First build, no cache | 7.4 s | 22.2 s |
| After editing server.js | 7.3 s, 1 of 4 steps reused | 5.6 s, 3 of 5 steps reused |
| After editing package.json | 8.7 s, 1 of 4 reused | 15.4 s, 1 of 5 reused |

The times are noisy, because the install depends on your network, and with only 13 packages the saved seconds are small. The steps-reused column is the reliable signal: the good Dockerfile skips the install after a code edit. A real service with hundreds of packages takes minutes to install, so the saving grows with the project.

## Small images pull fast

<InteractiveCanvas slug="sysdesign-m18-image-pull-weak-line" />

Size is time on a weak line. On a made-up 4 Mbit/s connection, the full Node image (about 410 MB packed) takes about 14 minutes to pull, and the alpine image (about 62 MB) about 2 minutes. Every new server, and every new Kubernetes node, pays this cost once.

<GoDeeper title="Go deeper: how to keep an image small">

The sizes are the packed (compressed) download sizes of the amd64 images on Docker Hub, measured on 24 October 2026: `node:24` is 409.9 MB, `node:24-slim` 81.0 MB and `node:24-alpine` 62.5 MB [S119]. On disk each is larger.

- **Pick a small base.** Alpine is the smallest. It uses a different C library (musl instead of glibc), so a few packages with native code need extra care. Slim is a Debian build with less in it, and is the safer choice when something fails on alpine.
- **Leave build tools out.** A <GlossaryTerm term="multi-stage build" definition="A Dockerfile with more than one FROM. An early stage builds the code with all its tools. The final stage copies only the result, so the compilers and sources never reach the shipped image." /> compiles in one stage and copies only the output into a clean final stage. Use it for TypeScript or any build step. The sample service has no build step, so one stage is enough.
- **Install only what runs.** `npm ci --omit=dev` skips test and build packages.
- **Do not copy what you do not need.** `.dockerignore` keeps `node_modules`, `.git` and local files out of the build.
- **Pin versions.** `node:24-alpine` moves when a new patch ships; a pinned digest does not. Pin when you need identical builds, and update on purpose.

Weak connections matter twice. The pull runs on every new machine, and a deploy that pulls 410 MB to ten servers moves 4 GB. The cost is real for registries too: some charge for data leaving them.

An image is also the unit you scan for known security problems and the unit you keep in a registry. In AWS the registry is Amazon ECR, which ECS and EKS pull from.

## A health check reports, it does not repair

<InteractiveCanvas slug="sysdesign-m18-docker-health" />

The `HEALTHCHECK` line makes Docker call `/health` every 10 seconds. When the service gets stuck, three checks in a row fail, and Docker marks the container **unhealthy**. Then nothing happens. Plain Docker does not restart it. Something else, such as Kubernetes, must act on the status.

<GoDeeper title="Go deeper: health in Docker and in Kubernetes">

A `HEALTHCHECK` runs a command inside the container on a schedule. The defaults in the Dockerfile reference are an interval of 30 seconds, a timeout of 30 seconds, a start period of 0 seconds and 3 retries. The status moves from `starting` to `healthy` and, after the retries fail in a row, to `unhealthy`.

In our test the sample service was stuck at time 0. The status was still `healthy` at 27 seconds, with a failing streak of 2, and became `unhealthy` at about 31 seconds. The restart count stayed at 0 for the whole minute. This is the same arithmetic as chapter 4.4: the time to notice is the interval times the failures needed.

Docker Swarm can act on the status. Kubernetes ignores the Dockerfile `HEALTHCHECK` and uses its own probes, which chapter 18.4 covers. What you carry over is the habit: keep `/health` local and cheap. It should check that the process works, not that the database is up, for the reason chapter 4.4 gave about deep checks.

A health check runs a program inside the container each time. The sample uses `node -e` and starts a new Node process every 10 seconds. A tiny tool such as `wget` or a built-in check in the service is lighter. Choose what your image already has.

## Data outlives the container

<InteractiveCanvas slug="sysdesign-m18-volume-survives" />

Container 1 saves a file in its own layer and is removed: the file is gone with it. Data that must stay goes to a **volume**, a folder stored outside the container, or to a database. Container 2 mounts the same volume and finds the notes. Containers are cattle, not pets: replace them freely.

<GoDeeper title="Go deeper: volumes, logs and configuration">

Three things should not live in the container's own layer.

**Data.** Use a volume (`docker run -v daftar-data:/data`) or, better for a service that runs in several copies, an external database (module 7). A volume still ties data to one machine. On a cluster, a pod that moves to another machine needs storage that moves with it, which is why most teams keep state in managed databases and object storage (chapter 18.7).

**Logs.** Write them to standard output, one JSON line per event, as the sample service does with the pino library. The runtime collects them and a log system reads them (module 17). A service that writes log files inside the container loses them when it is removed.

**Configuration.** Pass settings as environment variables at run time, not as files inside the image. The same image then runs in testing and in production with different values. Never put a secret in an image: anyone who can pull the image can read every layer.

This is the practical meaning of the stateless rule from chapter 4.3. A container you can delete at any time, and replace with an identical one, is a container you can scale, restart and roll back without fear.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "I order the Dockerfile from slow-changing to fast-changing: base image, package files, install, then my code. A code change then reuses the cached install. I use a small base, run as a non-root user, write logs to standard output, and keep data outside the container."

The follow-up is usually: "A one-line change takes four minutes to build. Why?" The code is copied before the install, so every change invalidates the install layer. Fix the order, and add a .dockerignore so local files do not enter the build.

</GoDeeper>
