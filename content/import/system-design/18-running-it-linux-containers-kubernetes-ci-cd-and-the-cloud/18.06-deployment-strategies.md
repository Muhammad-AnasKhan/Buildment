Every release is a bet that the new version is better than the old one. Sometimes the bet loses. A deployment strategy decides two things: how many users a bad release can reach, and how fast you can undo it. The first is the **blast radius**. The second is the **rollback time**. This chapter compares four strategies on those two numbers.

## Rolling: two versions run at once

<InteractiveCanvas slug="sysdesign-m18-mixed-versions" />

A rolling update (chapter 18.4) replaces pods a few at a time, so for a while v1 and v2 both serve users. Here v2 saves a note in a new format, and a v1 pod, still running, reads that note and cannot understand it. Both versions share one database, so both must live with the same data.

<GoDeeper title="Go deeper: expand, then contract">

Any strategy that runs old and new code together has this problem: the database is shared. The usual cure is to change the data in small steps that both versions accept. Martin Fowler's description of blue-green deployment gives the rule in one line: deploy schema changes separately from the code, so that both versions work [S109].

A safe way to rename a column is three releases. First **expand**: add the new column, keep the old one, and have the code write to both. Second, move the readers to the new column and backfill old rows. Third **contract**: stop writing the old column and remove it later, when no running version uses it. Each release works with the one before and the one after it, so you can stop or go back at any step.

Rolling is the default in Kubernetes, needs no extra capacity beyond `maxSurge`, and costs nothing extra to set up. Its weaknesses are that the blast radius grows as pods are replaced, and that the way back is another rolling update, as slow as the way forward.

Where each version can write also matters for caches (module 5): a v2 that stores a new shape in the cache can break a v1 that reads it. Think of the cache, the queue and the API as shared too.

</GoDeeper>

## Blue-green: switch the router, switch it back

<InteractiveCanvas slug="sysdesign-m18-blue-green" />

Blue runs v1 and serves users. Green runs v2 and is tested with no users on it. When ready, the router switches all traffic to green at once. If green shows errors, the router switches back to blue, which is still running. The rollback is the same one-step switch.

<GoDeeper title="Go deeper: what blue-green costs">

Blue-green keeps two full production environments, "blue" and "green", and a router that points at one of them [S109]. The strong point is the rollback: because the old environment is untouched, going back is just changing where the router points. There is no slow update to reverse.

The costs are real. You pay for two environments while both exist, which for a large service is a lot. The shared database must work with both versions, as the last beat showed. And the switch moves everyone at once, so the blast radius is 100% of users for as long as it takes you to notice. Users who have an open request at the moment of the switch can see an error.

The speed of the switch depends on what it is. Changing the target of a load balancer takes effect within moments for new requests. Changing a DNS record depends on the record's time to live (chapter 3.3): the Elastic Load Balancing records use 60 seconds, and clients that cache longer keep going to the old side [S15].

In Kubernetes you can do blue-green with two Deployments and a Service whose selector you change from `version: blue` to `version: green`. In AWS, a load balancer can send traffic to a chosen target group, and a deployment service such as CodeDeploy can run blue/green releases for ECS and Lambda. {/* source needed: AWS CodeDeploy blue/green support for ECS and Lambda, and ALB target group switching (AWS documentation) */}

</GoDeeper>

## Canary: a few users go first

<InteractiveCanvas slug="sysdesign-m18-canary-compare" />

A canary gets a small share of real traffic, here 5%, while the stable version serves the rest. Compare the two at the same time. The stable version has 0.2% errors and the canary has 9%. The router drops the canary to 0%. Five percent of users saw the bug. Ninety-five percent never did.

<GoDeeper title="Go deeper: comparing the canary with the control">

The Google SRE workbook defines a canary release as a partial and time-limited deployment of a change, followed by an evaluation of whether to go on [S110]. The key rule is to compare the canary with a **control** that runs at the same time, not with last week. Traffic changes with the hour, the day and the news; a difference between the canary and the stable version running side by side is a signal. A difference between now and last Tuesday is mostly noise.

A canary needs more machinery than the other strategies: a router that can split traffic by percentage, metrics that are tagged by version, and a rule that says what "worse" means. It also needs enough requests to tell a real difference from chance. A 5% canary on a service with 20 requests a minute sees one request a minute, and a rare error may take hours to show.

A canary can also be chosen by who, not only how many: staff first, then one country, then everyone. The SRE workbook recommends running one canary at a time, so that you know which change a signal belongs to [S110].

In Kubernetes, a simple canary is one pod of v2 next to nine of v1 behind the same Service, which gives about 10% of requests to v2. Finer control, such as exactly 5%, needs a router that supports weights, like a service mesh or the weighted target groups of an AWS Application Load Balancer. {/* source needed: ALB weighted target groups (AWS documentation) */}

</GoDeeper>

## Play: the share and the error rate

<InteractiveCanvas slug="sysdesign-m18-canary-blast" />

Drag the canary's share of traffic and the bug's error rate. The picture shows how many requests reach the bug before an alert fires, how many minutes that takes, and what the whole-service dashboard shows. A bigger share finds the bug sooner but puts more users on it at once. A rare bug hides for a long time, and the average hides it.

<GoDeeper title="Go deeper: the model behind the picture">

The model is simple. The service handles a fixed number of requests per minute. The canary receives a share of them. The bug makes a fraction of the canary's requests fail. An alert fires when the canary has produced a set number of failures, so that one unlucky request does not trigger it.

Three results follow, and the picture lets you see them. First, the failures the users suffer before the alert is about the alert threshold, whatever the share: a count-based alert fires after the same number of failures. Second, the time to the alert is the threshold divided by the failures per minute, so a bigger share or a worse bug fires sooner. Third, the dashboard of the whole service shows share times error rate, which for small numbers disappears into normal noise.

The practical lesson is to pair a canary with a check that looks at the canary alone, and to start with a share large enough to give a signal in minutes, not hours. The numbers in the picture are made up for the example (a service with a few thousand requests a minute).

The model leaves out: users who see the bug more than once, bugs that only appear after a delay, and the cost of the extra machinery.

</GoDeeper>

## Feature flags: release is not deploy

<InteractiveCanvas slug="sysdesign-m18-flag-flip" />

v2 is already deployed, with the new search switched off by a **flag**. You turn it on for 5% of users. A bug appears. You turn the flag off, and the feature disappears at once, with no new deploy. Deploying code and releasing a feature are two separate steps.

<GoDeeper title="Go deeper: flags, their costs, and the rollback table">

A <GlossaryTerm term="feature flag" definition="A setting the code reads at run time to decide whether to use a new code path. It lets you switch a feature on or off, or for some users only, without deploying again." /> (also called a feature toggle) lets you ship unfinished or risky code that does nothing until you switch it on. Martin Fowler describes several kinds, from short-lived release flags to long-lived ones that control behaviour per customer, and warns that each flag adds a path that must be tested and later removed {/* source needed: Fowler, Feature Toggles, martinfowler.com/articles/feature-toggles.html, fetched 2026-10-24, add to the dossier */}.

Flags work well with the other strategies. You can roll out a new version with a rolling update, with the feature off, and then turn the feature on gradually. The deploy risk (does it start?) and the feature risk (is it good?) are then separate. In AWS, AppConfig can serve flags, and many teams use a flag service or a simple config file.

Flags have costs: old flags left in the code are dead paths that confuse people, a flag that depends on another flag multiplies the cases to test, and a flag service that is down needs a safe default.

Here are the four strategies on the two numbers. The times are typical and illustrative: they depend on your router, your caches and your size.

| Strategy | Blast radius | Way back | Rollback time |
|---|---|---|---|
| Rolling | Grows as pods are replaced | Another rolling update | Minutes |
| Blue-green | All users at once | Switch the router back | Seconds to a minute |
| Canary | The canary's share (for example 5%) | Set the canary to 0% | Seconds |
| Feature flag | The users the flag is on for | Turn the flag off | Seconds |

</GoDeeper>

## Choose by blast radius and rollback time

<MermaidDiagram title="Which strategy to start with" chart={`flowchart TD
  Q1{"Can the change hide behind a flag?"} -->|yes| F["Feature flag: deploy dark, release by percentage"]
  Q1 -->|no| Q2{"Do you need real traffic to judge it?"}
  Q2 -->|yes| C["Canary: a small share first, compare with the stable version"]
  Q2 -->|no| Q3{"Can you pay for two environments and need an instant switch?"}
  Q3 -->|yes| B["Blue-green: switch the router, switch back to undo"]
  Q3 -->|no| R["Rolling update: the default, with probes and a rollback plan"]
`} legend="Start from the strategy with the smallest blast radius and the fastest way back that your system can support. Combine them: a rolling deploy with the feature behind a flag is common." />

Ask the two questions first: how many users can this reach, and how fast can I undo it? Pick the strategy that answers both well for your system. Strategies combine: deploy by rolling update, release by flag, and watch a canary's numbers. A small team with one service often does well with rolling updates, good probes and flags.

<GoDeeper title="Go deeper: what none of them can undo">

Some changes cannot be undone by any strategy. A database column that was dropped, an email already sent, a payment already taken, an event already published to other services. The strategies undo code, not side effects.

For those, the plan is to avoid the one-way step until you are sure. Expand before you contract. Send emails from a queue (module 15) so that a bad release can be stopped before the queue is read. Take payments through idempotent calls (module 6). Keep the old schema until the new code has run for a while.

In your gate answer for this module, you write a short deploy and rollback plan. It should say which strategy you use, how many users a bad release can reach, how long a rollback takes, and which step cannot be undone.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "I choose by blast radius and rollback time. Rolling is the default. A canary limits how many users a bad release can reach and I compare it with the stable version at the same time. Blue-green gives an instant rollback at the cost of two environments. A feature flag separates deploying from releasing. None of them undoes a database change, so I expand before I contract."

The follow-up is usually: "Your canary has 5% of traffic and a 20% error rate, but the dashboard looks fine. Why?" The bad share is averaged with the healthy 95%, so the whole-service rate rises by only about 1 point. You must look at the canary on its own.

</GoDeeper>
