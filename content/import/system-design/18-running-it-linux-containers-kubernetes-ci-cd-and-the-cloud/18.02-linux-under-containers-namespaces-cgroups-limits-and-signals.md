A container looks like a tiny computer, but it is not one. The mistake is costly: teams give a container a limit and are surprised when it is killed, or press stop and wait ten seconds. This chapter looks one level below Docker, at the Linux features it uses. It builds on chapter 3.6, where you met processes and file descriptors.

## A container is a process with blinders

<MermaidDiagram title="A virtual machine and a container" chart={`flowchart TB
  subgraph VM["Virtual machine: its own kernel each"]
    direction TB
    H1["Hardware"] --> HV["Hypervisor"]
    HV --> G1["Guest kernel + app A"]
    HV --> G2["Guest kernel + app B"]
  end
  subgraph CT["Containers: one shared kernel"]
    direction TB
    H2["Hardware"] --> K["Host Linux kernel"]
    K --> C1["Container A: app A in its own view"]
    K --> C2["Container B: app B in its own view"]
  end
`} legend="A virtual machine runs a whole guest operating system on top of a hypervisor. Containers are ordinary processes on the one host kernel, each given its own limited view." />

A virtual machine carries its own kernel. A container does not. It is a normal process on the host's Linux kernel, started with two limits: what it can **see**, and how much it can **use**. That is why a container starts in under a second and costs little memory. It also means a container is not a strong wall: all containers share one kernel.

<GoDeeper title="Go deeper: two Linux features, no magic">

Docker, Podman and Kubernetes all run containers with the same two kernel features. A <GlossaryTerm term="namespace" definition="A Linux feature that gives a group of processes their own private view of one kind of system resource, such as process numbers, network devices or mounted folders." /> controls what a process can see. A <GlossaryTerm term="cgroup" definition="A Linux control group: a way to put processes in a group whose use of resources such as memory and CPU can be limited and measured." /> (control group) controls how much it can use. The Linux manual says a namespace "wraps a global system resource in an abstraction" so that processes inside seem to have "their own isolated instance of the global resource", and that one use of namespaces is to implement containers. Control groups "allow processes to be organized into hierarchical groups whose usage of various types of resources can then be limited and monitored" [S117].

A container is therefore not a Linux object. There is no "container" system call. A runtime such as runc starts a process, puts it into a new set of namespaces, places it in a cgroup with limits, and gives it an image's files as its root folder. Everything you do to a container, you could do by hand with the `unshare` command and a few files in `/sys/fs/cgroup`.

Because containers share the kernel, a kernel bug can affect all of them, and a container built for Linux cannot run a Windows program. On Windows and macOS, Docker Desktop runs a small Linux virtual machine and starts your containers inside it. That is why `docker run` works the same on a laptop with any operating system. {/* source needed: Docker Desktop runs containers inside a Linux virtual machine on Windows and macOS (Docker Desktop documentation) */}

A virtual machine is the stronger wall, and it costs more: its own kernel, its own boot time and its own memory. When customers who do not trust each other share a machine, clouds often put containers inside lightweight virtual machines. The trade-off is isolation against cost.

## Namespaces decide what a process sees

<InteractiveCanvas slug="sysdesign-m18-isolation-layers" />

Tap a switch to turn an isolation on or off, and look at what the process can see. With process IDs isolated, it sees only itself. With the network isolated, it has its own ports. Turn one off, and the process sees the host's processes, ports or files. Then drag the memory and CPU limits.

<GoDeeper title="Go deeper: the namespace types, one by one">

The Linux manual lists eight kinds of namespace. The first five matter most for a service.

| Namespace | What it isolates | What a process sees when it is on |
|---|---|---|
| PID | Process numbers | Its own first process is number 1, and host processes are invisible |
| Network | Network devices, ports, routes | Its own network card and its own port 3000 |
| Mount | Mounted folders and files | The image's files as `/`, not the host's disk |
| UTS | Host name | Its own name, usually the container ID |
| IPC | Shared memory and message queues | Only its own |
| User, cgroup, time | User numbers, cgroup view, clocks | Less common in a first look |

Two services that both listen on port 3000 can run on one machine because each has its own network namespace. Docker then maps a port on the host to the port inside, which is what `-p 8080:3000` means.

You can see the PID namespace in one command. `docker run --rm alpine ps` lists only itself, as process 1:

```text
> docker run --rm alpine ps
PID   USER     TIME  COMMAND
    1 root      0:00 ps
```

Turning an isolation off is possible and sometimes useful. `docker run --network host` removes the network isolation, so the container uses the host's ports directly. `--pid host` lets it see every host process. Monitoring tools do this on purpose. A normal service should not.

## A memory limit kills

<InteractiveCanvas slug="sysdesign-m18-oom-kill" />

This service holds 20 MB more with each request. The container has a 100 MB limit. At 80 MB all is well. At the next request the process is over the line, the kernel's out-of-memory killer stops it, and the container exits with code 137. There is no slowdown first and no warning.

<GoDeeper title="Go deeper: why 137, and what to do about it">

Exit code 137 is 128 plus 9. Signal 9 is SIGKILL, the signal a program cannot catch or ignore. The kernel sends it when a cgroup runs out of memory and nothing can be freed. In the course challenge run, the sample service held 80 MB under a 100 MB limit and then the container showed `exited exit=137 oomKilled=true`. In Kubernetes the same event appears as `OOMKilled` in the pod's status.

A memory limit is a hard wall because memory cannot be shared out over time. A process that holds a page of memory holds it until it gives it back. When the wall is hit, there is nothing to wait for.

What to do about it:

- **Measure first.** Watch memory under real load before choosing a limit. A limit set just above the idle size will be hit at the first busy hour.
- **Leave room for the runtime.** A Node.js process uses memory beyond your data: its heap, buffers and the engine itself.
- **Treat exit 137 as a signal.** If a service restarts again and again with 137, it is almost always a leak or a limit that is too low, not bad luck.
- **Restart is not a fix.** A leak restarted every two hours is still a leak. Kubernetes will restart it forever, with growing delays.

The 100 MB limit and 20 MB steps come from the sample service in challenge 17, which has an `/alloc` route for exactly this test.

</GoDeeper>

## A CPU limit only slows

<InteractiveCanvas slug="sysdesign-m18-cpu-throttle" />

CPU is different. The same 200 ms of work takes 200 ms with a whole CPU and about 400 ms with half a CPU. The kernel lets the container run for a share of each short time slice, then pauses it until the next one. The request is slow, but nothing is killed.

<GoDeeper title="Go deeper: throttling, and why p99 feels it first">

A CPU limit of 0.5 does not give the container half the speed of one core. It gives the container a time budget: in each short period, it may use half of that period in CPU time. When the budget is spent, its threads wait until the next period.

In the challenge run, a request that needs 200 ms of CPU took about 213 ms with no limit and about 406 ms with `--cpus=0.5`: a slowdown of 1.9 times, as the budget predicts. The test counts CPU time, not clock time, so the work is the same in both runs.

Throttling is quiet. There is no error and no restart. A throttled service just looks slow, and the slowness shows up first in the tail: the p99 from chapter 2.4. A burst of requests that needs more CPU than the budget stretches every one of them. If a service has normal CPU graphs and a bad p99, check whether it is hitting its limit. Linux counts throttled periods in the cgroup's `cpu.stat` file.

Two settings in Kubernetes come from this. A **request** tells the scheduler how much CPU to reserve for the pod, and it is what the autoscaler compares usage against (chapter 18.4). A **limit** is the hard cap enforced by the cgroup. Many teams set a CPU request and no CPU limit, to avoid throttling, but always set a memory limit, because memory has no safe way to be shared.

## The signal nobody answers

<InteractiveCanvas slug="sysdesign-m18-sigterm-ignored" />

`docker stop` sends SIGTERM, which means "please finish and stop". This service has no handler, so nothing happens. Docker waits, then sends SIGKILL, which cannot be refused. In our test with `-t 10` the stop took 10.8 seconds and the exit code was 137. Requests in progress are cut off.

<GoDeeper title="Go deeper: process 1 and the missing default action">

Most programs stop when they get SIGTERM, because the kernel's default action for SIGTERM is to end the process. Process 1 of a PID namespace is special. The Linux manual says that only signals for which that process has set up a handler can be sent to it by other processes in its namespace, which protects the first process from being killed by accident. Inside a container, `node server.js` is process 1. Node has no SIGTERM handler unless you write one, so the signal is dropped.

Three ways to get a clean stop:

1. **Write a handler.** The sample service calls `process.on("SIGTERM", ...)`. It stops accepting new requests, waits for open ones, then exits with code 0. This is the best fix because it also lets you flush logs and close database connections.
2. **Run a tiny init process.** `docker run --init` puts a small program as process 1, which passes signals on. Without a handler, SIGTERM then ends Node at once. That is faster than a 10-second wait but still cuts requests in flight.
3. **Use the exec form of CMD.** `CMD ["node", "server.js"]` runs Node directly. The shell form, `CMD node server.js`, runs `sh -c node server.js`, so the shell is process 1 and may not pass the signal to Node at all.

How long Docker waits is set with `-t`. The default depends on the Docker version (we measured about 3 seconds on Docker 29.8.2), so set it explicitly when it matters. Kubernetes waits `terminationGracePeriodSeconds`, 30 seconds by default, between SIGTERM and SIGKILL.

We measured three variants with `docker stop -t 10` while a 2-second request was in flight:

| Variant | docker stop took | Exit | The request |
|---|---|---|---|
| No handler, node is process 1 | 10.8 s | 137 (killed) | Finished only because it was short |
| No handler, `--init` | 1.0 s | 143 (ended by SIGTERM) | Cut off |
| SIGTERM handler | 2.5 s | 0 (clean) | Finished |

## Drain, then exit

<InteractiveCanvas slug="sysdesign-m18-graceful-drain" />

With a handler, SIGTERM starts a **drain**. The service stops taking new work, finishes the request in flight, answers it, and exits with code 0. Nobody is cut off. A deploy that stops a hundred containers this way loses no requests.

<GoDeeper title="Go deeper: the shape of a graceful shutdown">

A graceful shutdown has four steps. First, mark the service as not ready, so the load balancer or Service stops sending new requests (chapter 4.4). Second, wait briefly, because the balancer needs a moment to notice. Third, stop the listener and let open requests finish. Fourth, close connections and exit. Set a time limit on the whole thing, so one stuck request cannot hold the process forever.

```js
// The core of the sample service (challenge 17). Partial code: error handling omitted.
process.on("SIGTERM", () => {
  draining = true;                       // /ready now answers 503
  setTimeout(() => {
    server.close(() => process.exit(0)); // exit when the last request ends
    server.closeIdleConnections();       // do not wait for idle keep-alive sockets
  }, SHUTDOWN_DELAY_MS);                 // give the balancer time to notice
  setTimeout(() => process.exit(1), FORCE_EXIT_MS).unref(); // never hang
});
```

While draining, the sample service also adds `Connection: close` to its answers. Without it, a client's kept-alive connection can sit idle, and `server.close()` waits until the connection times out. We hit this while building the challenge: the stop took seconds longer than the work needed.

The time limit must be shorter than the platform's grace period. If Kubernetes waits 30 seconds and your force-exit is 60, the platform's SIGKILL wins.

On Windows, Node cannot receive a real SIGTERM from another process, so tests for this behaviour run in Docker or in CI on Linux.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "A container is an ordinary Linux process. Namespaces limit what it can see and cgroups limit what it can use. A memory limit kills the process, while a CPU limit only throttles it. For shutdown, my service handles SIGTERM: it stops taking new work, finishes what is in flight, and exits before the grace period ends."

The follow-up is usually: "Why does your pod take 30 seconds to stop?" The answer: node is process 1 and has no SIGTERM handler, so the signal is ignored and Kubernetes sends SIGKILL at the end of the grace period, cutting any request in flight.

</GoDeeper>
