Kitabi's API is called by its own app and by three partner bookshops. Clients you do not control will call it for years, and some phones will run an old version of the app for months. Small choices made now, about names, pages, versions and errors, decide whether those clients break later.

## Name things, not actions

<MermaidDiagram title="Kitabi's resources" chart={`flowchart LR
  B["/books"] -->|"GET lists, POST adds"| B1["/books/42"]
  B1 -->|"GET reads, PATCH edits"| R["/books/42/reviews"]
  S["/sellers/7"] -->|"GET reads"| SB["/sellers/7/books"]
  O["/orders"] -->|"POST creates"| O1["/orders/512"]
  P["/payments"] -->|"POST with an idempotency key"| P1["/payments/pay_81"]
`} legend="Nouns name the things; the HTTP method is the verb. Nesting shows what belongs to what: reviews belong to a book." />

Name resources with nouns and let the HTTP method be the verb. `GET /books/42/reviews` reads reviews; `POST /orders` creates an order. Nest a path only where one thing belongs to another. Names like `/getBook` or `/doPayment` hide the verb in the name, so a client cannot tell what is safe to repeat.

<GoDeeper title="Go deeper: conventions that save clients from guessing">

The method tells every client, proxy and cache what a request does. A GET is safe to repeat and may be cached. A PUT or DELETE is idempotent: doing it twice leaves the same state. A POST creates or acts, and repeating it may do it twice, which is why 6.4 adds a key to `POST /payments`. When the verb hides in the path, as in `GET /deleteBook?id=42`, a crawler or a prefetching browser that "only reads" can delete data. {/* source needed: RFC 9110 sections on safe and idempotent methods */}

A few conventions keep an API easy to read:

- Plural nouns for collections (`/books`), an ID for one item (`/books/42`).
- Filters, sorting and search as query parameters: `/books?subject=chemistry&sort=-listed_at`.
- `201 Created` and the new resource's address when a POST creates something; `202 Accepted` and a status resource when the work finishes later, such as a refund the provider takes minutes to confirm. {/* source needed: RFC 9110 for 201, 202 and the Location header */}
- One naming style for fields everywhere, for example `listed_at`, never `listedAt` in one place and `listing_date` in another.

Do not leak your tables into your API. If `/books/42` returns every column of the books table, renaming a column breaks every partner. Decide what clients need, return that, and keep the freedom to change what is behind it.

</GoDeeper>

## Offset pages repeat when rows arrive

<InteractiveCanvas slug="sysdesign-m6-offset-repeat" />

Offset pagination says "skip 3 rows, then give me 3". Between Huda's two pages, a new book arrived at the top. Every row moved down one place, so skipping 3 now lands on book 7 again, and she sees it twice. A deleted row does the opposite: everything moves up, and one book is skipped without anyone noticing.

<GoDeeper title="Go deeper: why offsets break, and when they are fine">

An offset is a position in a list, and positions move whenever the list changes in front of them. Kitabi's list is newest first, so every new listing lands in front of everything Huda has seen. With one new book between page 1 and page 2, one book repeats. With 3 new books, all of page 1 comes back as page 2. A delete above the reader's position does the reverse and hides a book, which is worse, because nothing on the screen shows that anything is missing.

Offsets are also slow deep in a list. To answer "skip 30,000, give me 3", the database usually reads the 30,000 rows and throws them away. Page 1 is fast and page 10,000 is slow, so a partner that syncs the whole catalogue gets slower every night as the catalogue grows. {/* source needed: PostgreSQL documentation on the cost of a large OFFSET */}

Offsets are fine when the list does not change while people read it and stays short: an admin table of 200 sellers with page numbers, or search results a user looks at for a minute. They also give "jump to page 7", which cursors cannot. For a feed, a catalogue sync or any list that grows at the top, they repeat and skip rows.

</GoDeeper>

## A cursor remembers where you stopped

<InteractiveCanvas slug="sysdesign-m6-cursor-page" />

A cursor points at the last book you saw, not at a position. Page 1 ends at book 7, so page 2 asks for "books listed before book 7". A new book at the top changes nothing below it. Huda gets 6, 5 and 4: no repeats and no gaps. The list needs a sort order where no two rows tie.

<GoDeeper title="Go deeper: building cursor pagination">

The API returns a `next_cursor` with every page, and the client sends it back to get the next page. Inside, the cursor holds the sort key of the last row on the page. For a newest-first list sorted by `listed_at`, with the book's `id` to break ties, page 2 is a query like this:

```sql
SELECT id, title, price_cents, listed_at
FROM books
WHERE (listed_at, id) < ($1, $2)   -- the last row of page 1
ORDER BY listed_at DESC, id DESC
LIMIT 3;
```

With an index on `(listed_at, id)`, the database jumps straight to the right place, so page 10,000 is as fast as page 1. This style is also called keyset pagination. {/* source needed: PostgreSQL row comparison and keyset pagination with an index */}

Three details matter. First, the sort key must be unique, which is why `id` is added: two books listed in the same millisecond would otherwise tie, and one could be skipped. Second, make the cursor opaque, for example the two values encoded as base64, so clients pass it back without building their own and you can change it later. Third, the cursor still works if book 7 itself is deleted, because the query compares values; it does not look up book 7.

What you give up: there is no "jump to page 50", and a total count needs a separate, often slow, query. Most feeds and sync APIs do not need either.

</GoDeeper>

## Add new books while you page

<InteractiveCanvas slug="sysdesign-m6-paging-insert" />

Drag how many new books arrive between page 1 and page 2, then switch between offset and cursor. With offset, each new book pushes one book from page 1 onto page 2 again. Delete a book from page 1 instead, and offset skips a book Huda never saw. The cursor shows every book exactly once.

<GoDeeper title="Go deeper: the model behind the picture">

The playable uses a list of books sorted newest first, 3 per page. Page 1 is taken first. Then the list changes: some new books are added at the top, or a book on page 1 is deleted. Then page 2 is taken.

With an offset, page 2 is "rows 4 to 6 of the list as it is now". Each new book shifts every row down by one, so page 2 starts that many rows earlier in the old order: with k new books (k up to 3), the last k books of page 1 appear again. Each deleted book on page 1 shifts rows up by one, so the first book that should have been on page 2 is skipped.

With a cursor, page 2 is "the 3 rows that come after the last row of page 1 in sort order". Rows added above that point and rows removed above it do not change what comes after it, so nothing repeats and nothing is skipped.

The model leaves out two real cases. A row that changes its sort key, for example a book "bumped" to the top, can still appear twice with a cursor, because it really moved. And a list sorted by something other than time, such as price, needs the same unique tie-break.

</GoDeeper>

## Add freely; break only in a new version

<MermaidDiagram title="Can this change ship in the same version?" chart={`flowchart TD
  C["A change to the API"] --> Q{"Does it only add a field, an endpoint or an optional input?"}
  Q -->|"yes"| S["Ship it in the same version: old clients ignore what they do not know"]
  Q -->|"no: rename, remove, new meaning, new required input"| V["New version: /v2, or a new dated version"]
  V --> R["Run both, tell clients, retire v1 only when traffic has moved"]
`} legend="Additive changes are safe for clients that ignore unknown fields. Anything that changes what an existing client reads or must send is a breaking change." />

Old app versions stay on phones for months. Adding a field or an endpoint is safe, because old clients ignore what they do not know. Renaming, removing or changing what a field means breaks them. Put a breaking change in a new version, run both, and retire the old one only when its traffic is gone.

<GoDeeper title="Go deeper: versions, and keeping them few">

The safest change is one no client notices. Kitabi wants prices in whole cents to avoid rounding errors. Adding `price_cents` next to `price` is additive: old apps keep reading `price`, new apps read `price_cents`. Removing `price`, or reusing the name `price` for cents, breaks every old app at once, so it needs a new version.

There are two common ways to name versions. A version in the path, `/v1/books` and `/v2/books`, is easy to see in logs and to route at the gateway. A version in a header, or a dated version chosen per account, keeps one set of paths and lets the server translate each request to the version the client signed up for; Stripe is a well-known example of dated versions. {/* source needed: Stripe API versioning documentation */}

Rules that keep versions rare:

- Clients ignore fields they do not know. Write this into the API's documentation and into your own app.
- Never change the meaning or the unit of an existing field. Add a new field instead.
- New inputs are optional, with a default that matches the old behaviour.
- Measure who still calls v1, by partner and by app version, before you turn it off, and announce a date. {/* source needed: the Sunset and Deprecation HTTP headers */}

Every version you keep is code you must run, test and secure. Two live versions are normal. Five means changes were not designed to be additive.

</GoDeeper>

## Errors that tell the client what to do

<MermaidDiagram title="What should the client do with this error?" chart={`flowchart TD
  E{"Status code"} -->|"400, 422: bad request"| F["Fix the request; do not retry it as it is"]
  E -->|"401: not logged in"| L["Log in again, then retry"]
  E -->|"403, 404: not allowed, not found"| N["Stop; show the user why"]
  E -->|"409: conflict"| C["Read the current state, then decide"]
  E -->|"429: too many requests"| W["Wait for Retry-After, then retry"]
  E -->|"5xx or a timeout"| R["Retry with backoff, only if safe to repeat"]
`} legend="4xx codes say the request itself must change; 429 says slow down; 5xx and timeouts may pass, but only a safe or keyed request may be retried." />

An error should tell the client what to do next. A 4xx says "fix your request", so retrying it unchanged is pointless. A 429 says "slow down": wait, then retry. A 5xx or a timeout may pass on its own, but retry only a request that is safe to repeat. Every error body needs a stable code and a request id.

<GoDeeper title="Go deeper: a useful error body, and three common mistakes">

The status code tells the client's code which branch to take. The body tells the developer, and the support team, what happened. A body like this one serves both:

```json
{
  "error": {
    "code": "book_already_sold",
    "message": "Book 42 was sold at 14:02. Choose another copy.",
    "request_id": "req_7Hq2"
  }
}
```

`code` is stable, so client code can check it. `message` is for people and may change. `request_id` lets a partner quote one id and lets your team find that request in the logs (module 17). There is also a standard shape for error bodies, "problem details", which some teams adopt so every service returns errors the same way. {/* source needed: RFC 9457 problem details for HTTP APIs */}

429 Too Many Requests is the status for rate limiting, defined in RFC 6585 [S33]. A common mistake is to send 503 instead: nginx's rate limiter does that by default, unless you set `limit_req_status 429` [S31]. A client cannot tell that 503 from a server that is down. Send 429, and a `Retry-After` header saying how many seconds to wait. {/* source needed: Retry-After with 429 in RFC 6585 section 4 */}

The second mistake is `200 OK` with `{"error": ...}` in the body. Proxies, caches, dashboards and retry logic all read the status, so they all think it worked.

The third is retrying everything. A timeout or a 5xx may pass, so retrying makes sense, with exponential backoff and jitter so that thousands of clients do not retry in the same instant [S90]. But retry only requests that are safe to repeat: GET, PUT, DELETE, or a POST that carries an idempotency key. Brooker's rule is that APIs with side effects are not safe to retry without idempotency [S89]. That is the next chapter.

</GoDeeper>
