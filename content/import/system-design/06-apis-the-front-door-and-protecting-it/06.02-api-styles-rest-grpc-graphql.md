Kitabi's book page needs three things: the book, its seller and its reviews. A student in Singapore opens it, and Kitabi's servers are in EU West. The same data can be asked for in three styles, and each style makes a different thing cheap.

## REST: one address per thing

<InteractiveCanvas slug="sysdesign-m6-rest-round-trips" />

With REST, each thing has its own address. The app asks for book 42 first, and the reply names the seller. Then it asks for seller 7 and the reviews together. From Singapore to EU West, each round trip takes about 160 ms. Three requests cost two round trips: 320 ms of waiting before the page can draw.

<GoDeeper title="Go deeper: what REST gives you">

REST (representational state transfer) is a style, not a library. Each <GlossaryTerm term="resource" definition="A thing the API lets you name and act on, such as a book, a seller or an order. In REST each resource has its own address, for example /books/42." /> has an address (a URL), and the client acts on it with the standard HTTP methods. `GET /books/42` reads the book. `PUT /books/42` replaces it. `DELETE /books/42` removes it. `POST /orders` creates something new. {/* source needed: Fielding's 2000 dissertation as the origin of REST */}

The methods carry promises that matter later in this module. HTTP defines GET as safe: it must not change anything, so anyone may repeat it. PUT and DELETE are idempotent: doing them twice leaves the same state as doing them once. POST is neither, which is why Huda's payment in 6.1 charged twice. {/* source needed: RFC 9110 sections on safe and idempotent methods */}

REST's biggest gift is that it reuses the web. A `GET` with a `Cache-Control` header can be stored by the browser, by a CDN and by any shared cache on the way, with rules every one of them already understands [S22]. Every language has an HTTP client, every engineer can test it with a browser or `curl`, and every partner company can call it.

Its cost is the shape of the data. Each address returns a fixed shape. A screen that needs pieces of three resources makes three requests, and when one request needs an answer from another (the seller's id comes inside the book), they happen one after another. That is under-fetching: one reply does not have enough. The opposite also happens. The book resource may carry 40 fields when the list screen shows 3, which is over-fetching. On a fast network inside a data centre neither matters much. From a phone 160 ms away, every extra round trip is visible.

The 160 ms is the measured round trip between EU West and Singapore in the napkin-math table [S3]. The picture ignores the time the server spends working, which is small next to the trips here.

</GoDeeper>

## GraphQL: one query, exactly these fields

<InteractiveCanvas slug="sysdesign-m6-graphql-one-trip" />

With GraphQL, the app sends one query that lists the fields the page needs: title, price, seller name, star ratings. The server collects them from services next to it, where a round trip is about 0.25 ms. The phone pays one long trip instead of two, and gets only the fields it asked for.

<GoDeeper title="Go deeper: what GraphQL moves, and where it moves the cost">

GraphQL is a query language for APIs. The server publishes a schema: the types it knows (Book, Seller, Review) and how they connect. The client sends one query, usually as a POST to a single address such as `/graphql`, and names exactly the fields it wants, following the links between types. The reply has the same shape as the query. {/* source needed: the GraphQL specification for schema, queries and response shape */}

That fixes both REST problems for screens. A list screen asks for 3 fields, a detail screen for 30, and both use the same API. A screen that needs a book and its seller and its reviews gets them in one round trip, because the server follows the links inside the data centre. A round trip inside a region is about 0.25 ms, against 160 ms to Singapore [S3].

The cost moves to the server. Each field is filled by a small function called a resolver. A naive server that resolves the seller for each of 50 books makes 50 separate calls, which is known as the N+1 problem; servers batch those calls to avoid it. {/* source needed: N+1 and batching (for example DataLoader) */} A query can also ask for a lot: books, their sellers, every book of every seller, and their reviews. One request can cost as much as thousands, so a GraphQL server limits query depth or gives each query a cost, and rate limits by cost, not by count. {/* source needed: query depth and cost limiting practice */}

Caching gets harder. HTTP caches key on the URL, and most GraphQL queries are POSTs to one URL, so a CDN cannot cache them the way it caches `GET /books/42` [S22]. Teams cache inside the server or use persisted queries instead. {/* source needed: persisted queries and GraphQL caching guidance */}

GraphQL fits best when one team owns many client screens with different shapes, and the clients are far away. It fits worst for a simple public API that partners cache, or for two services exchanging the same small message millions of times.

</GoDeeper>

## gRPC: typed calls between services

<InteractiveCanvas slug="sysdesign-m6-grpc-call" />

Inside Kitabi, the orders service calls the payments service hundreds of times a second. With gRPC, both sides are generated from one contract file. Calls travel as small binary messages, and many calls share one HTTP/2 connection at once. A field of the wrong type fails when the code is built, not later in production.

<GoDeeper title="Go deeper: what gRPC is good at, and where it hurts">

gRPC is a framework for remote procedure calls: one program calls a function that runs in another program, as if it were local. You describe the service and its messages in a `.proto` file, for example `rpc Charge(ChargeRequest) returns (ChargeReply)`, and a tool generates the client and server code in each language. Messages are encoded with Protocol Buffers, a compact binary format, and sent over HTTP/2. {/* source needed: gRPC documentation for .proto services, Protocol Buffers encoding and HTTP/2 transport */}

HTTP/2 lets many requests share one TCP connection at the same time, as separate streams [S12]. A busy service keeps one connection open to each peer and sends calls on it without waiting for earlier ones. HTTP/2 also has a known weakness: a lost or reordered packet stalls every stream on that connection until it is recovered [S12]. HTTP/3 removes that stall by running over QUIC, which you met in module 3 [S12, S13].

gRPC also supports streaming in either direction and deadlines that travel with the call, so a service knows how long its caller will wait. Those matter for the timeouts and retries in module 16 [S89].

It hurts at the edges. Browsers cannot speak plain gRPC, so a web app needs a translating proxy (gRPC-Web) or a separate REST or GraphQL API. {/* source needed: gRPC-Web and browser support */} Binary messages cannot be read with `curl` or a browser tab, so debugging needs gRPC tools. And partner companies expect REST. That is why gRPC usually lives inside a system, between services one organisation controls.

</GoDeeper>

## Weigh what matters, see who wins

<InteractiveCanvas slug="sysdesign-m6-api-style-weigh" />

Tap how much each need matters for one API and watch the totals change. Start with a public API for partners: reach and caching matter most, and REST wins. Switch to your own mobile screens, where round trips matter most: GraphQL pulls ahead. Switch to two of your own services talking all day: gRPC wins. The scores are course judgments, not measurements.

<GoDeeper title="Go deeper: why each style scores the way it does">

**Reach (public partners and browsers).** REST is plain HTTP and JSON, which every client can call. GraphQL is also HTTP, but the client must learn the schema and the query language. gRPC needs generated code and does not run in a browser without a proxy.

**Few round trips for varied screens.** GraphQL lets one request follow links and return exactly the fields a screen needs. REST needs one request per resource, unless you add a special endpoint per screen. gRPC can return any shape you define, but each new shape is a new method in the contract.

**Small, fast calls between services.** gRPC's binary messages and long-lived HTTP/2 connections suit high-volume calls between services. JSON over HTTP works too and is often fast enough; measure before you switch.

**HTTP caching for free.** A REST `GET` can be cached by browsers and CDNs with standard headers [S22]. GraphQL's POST queries and gRPC's binary calls do not get that for free.

**Simple to run and debug.** REST is the easiest to read, log and test. GraphQL adds a schema, resolvers and query cost limits. gRPC adds code generation and binary traffic.

The playable model is a weighted sum: each style's score on each need, times how much that need matters, added up. Real decisions also weigh what your team already knows and runs. A team fluent in REST can cut round trips with one screen-shaped endpoint before adopting GraphQL. When the totals are close, choose the boring option your team can operate.

</GoDeeper>

## Most systems use more than one

<MermaidDiagram title="Pick the style by the caller" chart={`flowchart TD
  Q{"Who calls this API?"} -->|"partners, browsers, anyone"| R["REST: plain HTTP, cacheable GETs"]
  Q -->|"your own app screens, far away"| G["GraphQL, or one REST endpoint per screen"]
  Q -->|"your own services, inside the data centre"| C["gRPC: typed, binary, streaming"]
`} legend="One system often offers all three: REST at the public edge, a screen-shaped API for its own apps, and gRPC between its own services." />

The choice is per caller, not per company. Kitabi can offer REST to partners, GraphQL or one endpoint per screen to its own app, and gRPC between its own services. Each choice follows who is calling and how far away they are. Push updates to a live screen are a different need again: WebSockets or server-sent events, from module 3.

<GoDeeper title="Go deeper: the in-between options, and when to change">

A common middle path is a <GlossaryTerm term="backend for frontend (BFF)" definition="A small API built for one kind of client, such as the mobile app, that calls the internal services and returns exactly what that client's screens need." />: a thin API that the mobile team owns, which calls internal services (often over gRPC) and returns one screen-shaped reply in one round trip. It gives the main benefit of GraphQL for one client without a general query language. Chapter 6.6 places it next to the gateway. {/* source needed: the backend for frontend pattern (Sam Newman) */}

Real-time updates are a separate question from request and reply. If a screen must change when the server changes, such as a new message or a driver's location, the app needs a push channel: WebSocket, a two-way connection over TCP [S104], or server-sent events, where the server streams events to the browser and the browser reconnects on its own [S105]. You compared these in module 3.

When should Kitabi change style? If the app's screens multiply and every new screen needs a new REST endpoint, a GraphQL layer or a BFF starts to pay. If calls between two services become a large share of their latency or CPU, switching that one link to gRPC may pay; measure it first. If partners ask for an API, give them REST, even if everything inside speaks gRPC.

</GoDeeper>
