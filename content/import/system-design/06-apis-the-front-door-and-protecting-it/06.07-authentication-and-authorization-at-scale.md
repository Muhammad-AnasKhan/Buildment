Every request to Kitabi must answer two questions: who is this, and may they do this? With one server, a login cookie answers both. With many servers and many services, where the answer lives decides what is fast, and how quickly a ban takes effect.

## Who are you, and may you do this?

<MermaidDiagram title="Two questions, asked at different times" chart={`flowchart LR
  L["Login: password, or Sign in with Google"] --> A["Authentication: who are you? (once)"]
  A --> P["Proof: a session id or a signed token"]
  P -->|"sent with every request"| Z["Authorization: may Huda read order 512? (every time)"]
  Z -->|"yes"| OK["Serve it"]
  Z -->|"no"| NO["403, or 404 to hide it"]
`} legend="Authentication happens at login and ends with a proof. Authorization uses that proof, plus the data, on every request." />

Authentication asks who you are, once, at login. It ends with a proof the client sends on every request: a session id or a signed token. Authorization asks, on every request, whether this person may do this thing. A 401 means "we do not know who you are"; a 403 means "we know, and you may not".

<GoDeeper title="Go deeper: the two words, and where each check runs">

<GlossaryTerm term="Authentication" definition="Proving who you are, usually once at login, for example with a password or through Google. Short form: authn." /> turns a password, a passkey or a "Sign in with Google" into a proof the client can show later. <GlossaryTerm term="Authorization" definition="Deciding whether a known user may do a specific thing, such as read order 512. It runs on every request. Short form: authz." /> uses that proof, plus rules and data, to allow or refuse each request.

They fail differently, and the status codes say which. `401 Unauthorized` (a confusing name) means the request has no valid proof: log in again. `403 Forbidden` means the proof is fine and the answer is no. As 6.6 showed, some APIs answer 404 instead of 403 so that a user cannot learn which orders exist. {/* source needed: RFC 9110 definitions of 401 and 403 */}

Authorization has layers. A role says what kind of user you are: buyer, seller, support agent, admin. A permission says what a role may do: sellers may create listings. An ownership check says whether this object is yours: Huda may read her own orders and nobody else's. Roles and permissions can be checked from the proof alone, often at the gateway. Ownership needs the data, so it runs in the service that owns it.

The rest of this chapter is about the proof: where it lives, how a server checks it, and what happens when you need to take it away.

</GoDeeper>

## Sessions: the server looks you up

<InteractiveCanvas slug="sysdesign-m6-session-lookup" />

With a session, login creates a random id, such as a91, and the server stores who it belongs to. Every request sends the id in a cookie, and the API looks it up in a shared store such as Valkey, about half a millisecond away. Banning someone is instant: delete the session, and the next request is refused.

<GoDeeper title="Go deeper: what sessions cost at scale">

A session id is a long random string with no meaning of its own. All the meaning lives in the session store: user huda, role buyer, logged in at 09:12. Because Kitabi's API servers are stateless (module 4), the store must be shared, so any server can answer any request. Valkey is a common choice, and a key-value lookup in the same region costs about 500 microseconds [S3].

That lookup is the price of sessions, paid on every request. For one API it is usually small. For a request that passes through five services, each looking up the same session, it adds up, and the session store becomes a dependency of every request: if it is down, nobody is logged in. Teams protect it with replicas (module 8) and keep the lookup in one place, the gateway, which passes the user id on.

What sessions buy is control. The server can end a session at any moment: on logout, on a password change, when support bans a seller, or when a phone is reported stolen. The next request finds nothing and gets 401.

In a browser, the session id travels in a cookie. Mark the cookie so scripts cannot read it, so it is only sent over HTTPS, and so other sites cannot make the browser send it. {/* source needed: cookie attributes HttpOnly, Secure and SameSite */}

</GoDeeper>

## JWT: a signed note, checked alone

<InteractiveCanvas slug="sysdesign-m6-jwt-verify" />

A JSON Web Token (JWT) is a signed note: "this is huda, a buyer, until 12:15". The API checks the signature with the login server's public key and reads the note, with no lookup at all. That is why tokens spread so easily across many services. The catch is the expiry: the note stays valid until it runs out.

<GoDeeper title="Go deeper: inside a JWT, and the mistakes to avoid">

A JWT has three parts joined by dots: a header, a payload and a signature, each encoded in base64url. The payload holds claims, such as `sub` (who it is about), `exp` (when it expires), `iss` (who issued it) and `aud` (who it is for). {/* source needed: RFC 7519, JSON Web Token */}

The token is signed, not encrypted. Anyone who holds it can decode the payload and read it, so never put a secret in it. What the signature gives is integrity: if anyone changes `role: buyer` to `role: admin`, the signature no longer matches and the check fails.

Use an asymmetric signature for a system with many services. The login server signs with a private key that only it has; every service verifies with the matching public key. A service can then check tokens but cannot create them, so a compromised search service cannot mint admin tokens.

Three checks are easy to forget: verify the signature with an algorithm you chose, never the one the token's header asks for; check `exp`; and check `aud`, so a token issued for another API is not accepted by yours. {/* source needed: RFC 8725, JWT best current practices */}

Tokens are bigger than session ids and travel on every request, so keep the claims few. Put the user id and the role in the token, and look up anything that changes often.

</GoDeeper>

## Ban a seller: who notices, and when?

<InteractiveCanvas slug="sysdesign-m6-revoke-timeline" />

Ban a seller and watch each design notice. Drag the token lifetime. With sessions, the very next request is refused. With signed tokens alone, the seller keeps working until the token expires. Add a small list of banned tokens that services refresh every few seconds, and the gap shrinks to that refresh time, at the price of a lookup again.

<GoDeeper title="Go deeper: getting fast revocation back">

Pure signed tokens trade control for speed. Three common patterns buy some control back.

**Short access tokens, revocable refresh tokens.** The access token lives for a few minutes. When it expires, the app sends a longer-lived refresh token to the login server, which checks a database before issuing a new access token. A ban takes effect at the next refresh, so the worst-case gap equals the access token's lifetime. The login server pays one lookup every few minutes per user, not one per request. {/* source needed: OAuth 2.0 refresh tokens, RFC 6749 */}

**A denylist.** Each token carries a unique id. When support bans someone, their current token ids go on a small list in Valkey, and each service keeps a copy that it refreshes every few seconds. The gap is the refresh time, and the list stays small because entries can be dropped once the token would have expired anyway.

**Ask the issuer.** For a few dangerous actions, such as paying out a seller's balance, the service asks the login server whether the token is still good, every time. That is a lookup again, but only where it matters. {/* source needed: OAuth 2.0 token introspection, RFC 7662 */}

The playable's numbers are Kitabi's settings, made up for the example: a token lifetime you drag from 1 to 60 minutes, and a denylist refreshed every 10 seconds. Real systems choose them from the damage one more request could do.

</GoDeeper>

## OAuth and OIDC: who does what

<MermaidDiagram title="Sign in with Google, for the Kitabi app" chart={`sequenceDiagram
  participant H as Huda
  participant A as Kitabi app
  participant S as Sign-in server
  participant K as Kitabi API
  A->>S: send Huda to sign in, with a PKCE challenge
  H->>S: logs in, agrees to share name and email
  S->>A: a one-time code
  A->>S: the code plus the PKCE verifier
  S->>A: ID token (who she is) and access token (what the app may do)
  A->>K: request with the access token
  K->>A: data, if the token allows it
`} legend="Huda types her password only at the sign-in server. The app gets two tokens: one that says who she is, for the app, and one that says what it may do, for the API." />

"Sign in with Google" uses OAuth 2.0 and OpenID Connect. There are four roles: Huda, the app, the sign-in server and Kitabi's API. Huda logs in at the sign-in server, never inside the app. The app gets an ID token, which says who she is, and an access token, which says what it may do. The API trusts only the access token.

<GoDeeper title="Go deeper: delegation, identity, and the mobile-app flow">

OAuth 2.0 is about delegation: letting an app act on a user's behalf with limited permissions, called scopes, without ever seeing the user's password. The sign-in server, which OAuth calls the authorization server, issues an access token for an API, the resource server. {/* source needed: RFC 6749, The OAuth 2.0 Authorization Framework */}

OAuth alone does not say who the user is. OpenID Connect (OIDC) adds that: an ID token, a JWT that tells the app who logged in, when and through which provider. {/* source needed: OpenID Connect Core 1.0 */} The two tokens have different readers. The ID token is for the app. The access token is for the API. Sending the ID token to an API as if it were an access token is a common mistake, because its audience is the app.

A mobile app cannot keep a secret: anyone can unpack it and read what is inside. So it uses the authorization code flow with PKCE. The app makes a random verifier, sends only a hash of it when it starts sign-in, and later proves it has the original when it swaps the one-time code for tokens. An attacker who steals the code from the redirect cannot use it without the verifier. {/* source needed: RFC 7636, PKCE */}

You rarely build a sign-in server. Kitabi can use a hosted identity service and keep its own API simple: verify the access token's signature, issuer, audience and expiry, then check permissions. **In AWS**, Amazon Cognito is the managed service for user sign-in and tokens. {/* source needed: Amazon Cognito user pools documentation */}

</GoDeeper>

## Services prove who they are too

<InteractiveCanvas slug="sysdesign-m6-service-identity" />

Inside Kitabi, services call each other too. A request that reaches payments from inside the network is not safe just because it is inside. Each service proves who it is, with a certificate (mutual TLS) or a short-lived service token. Payments accepts the orders service, and refuses an unknown caller even on the private network.

<GoDeeper title="Go deeper: service identity and passing the user along">

In mutual TLS, both sides of a connection present a certificate, not only the server. Payments sees a certificate that says "orders service", checks that a certificate authority it trusts signed it, and then decides whether the orders service may call `Charge`. Certificates are issued automatically and expire after a short time, so a stolen one is soon useless. A service mesh can do this for every service without changing their code. {/* source needed: mutual TLS between services; service mesh documentation */}

The other common way is a short-lived service token: each service gets a signed token from an internal issuer and sends it with its calls, checked the same way as a user's JWT.

The principle behind both is to trust no request because of where it came from. A misconfigured route, a forgotten debug port or one compromised service would otherwise reach payments with full trust. {/* source needed: zero trust architecture, NIST SP 800-207 */}

A service call often acts for a user, too. Payments needs to know both that the orders service is calling and that it acts for Huda. Pass the user along in a form the next service can verify, such as Huda's own access token or a short internal token signed by the gateway, never a plain `user: huda` header that any caller could write.

</GoDeeper>
