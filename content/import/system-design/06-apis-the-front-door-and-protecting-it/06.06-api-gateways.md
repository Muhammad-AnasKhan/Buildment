Kitabi has grown from one API server into several services: books, search, orders and payments. Every one of them needs the same checks before doing any work. Where should those checks live, and which checks must stay with each service?

## Every service guarding its own door

<InteractiveCanvas slug="sysdesign-m6-no-gateway" />

Without a gateway, the phone calls each service directly. Each service must end the secure connection, check the login token and count requests. That is the same code written three times by three teams. The search team forgot the rate limit, so the scraper from 6.5 goes straight there. Every copy is another place to get security wrong.

<GoDeeper title="Go deeper: what direct calls cost as services multiply">

Direct calls work while there is one service. With four, the costs add up quickly.

Every service repeats the same edge work: ending TLS (the encryption on the connection), checking the token, counting requests, logging each request with an id, and answering errors in the same shape. Each team writes and tests its own copy, so the copies drift. One team checks token expiry and another forgets; one sends 429 and another sends 503. A security fix must ship in four places, and the one that is missed is the one an attacker finds.

The client also has to know every service's address. If the orders service moves or splits in two, every version of the app that is still on someone's phone must be updated, which takes months, as 6.3 showed.

Rate limits are the worst case. A limit counted inside each service limits each service, not the client. A scraper that spreads its requests across four services gets four times its limit, the same problem as one bucket per server that challenge 5 measures.

</GoDeeper>

## One door in front of many services

<InteractiveCanvas slug="sysdesign-m6-gateway-route" />

A gateway is one front door for many services. It ends the secure connection, checks the token, applies the rate limit, then routes by path: `/books` to the books service, `/payments` to payments. Each check is written and tested once. The price is one more hop, about 50 microseconds for a proxy, and one more part that must not fail.

<GoDeeper title="Go deeper: what a gateway usually does, and what it costs">

An <GlossaryTerm term="API gateway" definition="A server that sits in front of many services, receives every client request, applies shared checks such as login and rate limits, and forwards each request to the right service." /> is a reverse proxy with API jobs added. The common jobs are:

- **End TLS** and pass the request on inside the private network.
- **Authenticate**: check the token's signature and expiry (6.7), and pass the user id on in a header.
- **Coarse authorization**: "this token may call `/payments`", not "this user owns order 512".
- **Rate limit** per client, with one shared count (6.5 and challenge 5).
- **Route** by path, host or version: `/v1/books` and `/v2/books` can go to different deployments (6.3).
- **Tag and log** every request with a request id, so one id follows it through every service (module 17).
- **Aggregate** sometimes: call two services and merge the replies for one screen.

The extra hop is cheap in time. napkin-math puts a proxy hop through nginx, Envoy or HAProxy at about 50 microseconds [S3], small next to a 160 ms phone round trip. It is not cheap in availability. Every request now passes through the gateway, so in module 2's series maths its availability multiplies with everything behind it. A gateway is a stateless tier, so run several copies behind a load balancer, as in module 4, and keep shared state, like rate limit counts, in a store such as Valkey.

**In AWS.** Amazon API Gateway does routing, authentication hooks and throttling with a token bucket, answering 429 when a client goes over its rate or burst [S30]. AWS WAF has rate-based rules that count requests per IP or other key in front of it [S131]. nginx's `limit_req` gives the same kind of limit in a self-hosted gateway [S31].

</GoDeeper>

## Business rules stay with the data

<InteractiveCanvas slug="sysdesign-m6-ownership-check" />

The gateway knows who Huda is, but not who owns order 512. Only the orders service has that data. So the gateway passes her user id, and the orders service checks the owner and answers 404. Putting this rule in the gateway would mean copying order data into it, and every rule change would wait for the gateway team.

<GoDeeper title="Go deeper: object-level checks, and not trusting the inside">

There are two levels of authorization. The coarse level asks whether this kind of caller may use this kind of endpoint: a seller's token may call `POST /books`, a buyer's may not. The gateway can check that from the token alone. The fine level asks whether this user may act on this object: may Huda read order 512? That needs the order's owner, which lives in the orders database, so the check belongs in the orders service, next to the data.

Forgetting the fine check is one of the most common API security bugs: a logged-in user changes the number in the address, `/orders/513`, `/orders/514`, and reads other people's orders. {/* source needed: OWASP API Security Top 10, broken object level authorization */} The gateway cannot stop this, because every one of those requests carries a valid token.

Answer 404 rather than 403 when the user should not even learn that the order exists. A 403 tells a curious user "order 512 is real, just not yours".

A gateway that collects business rules turns into a bottleneck: every team's change needs the gateway team, and the gateway needs copies of data it does not own. Keep it thin. Also do not let services trust a request just because it came from inside the network. If a misconfigured route or a compromised service can reach payments directly, payments must still check who is calling. Chapter 6.7 covers how services prove their identity to each other.

</GoDeeper>

## Switch gateway jobs on and off

<InteractiveCanvas slug="sysdesign-m6-gateway-jobs" />

Turn the gateway's jobs on and off, then follow one request through. Turn off the token check, and anyone can reach payments. Turn off the limit, and the scraper floods search. Turn on order rules, and the gateway needs a copy of every order. Keep the checks every service shares; leave business rules in the services.

<GoDeeper title="Go deeper: a rule of thumb for each job">

A job belongs in the gateway when it is the same for every service and needs no business data. Ending TLS, checking a token's signature, counting requests per client, giving each request an id, and routing by path all pass that test.

A job belongs in the service when it needs the service's data or differs from service to service. Who owns an order, whether a book is still in stock, whether a refund is too old, what discount a seller gets: all of these live with the data that answers them.

Some jobs sit in between. Request validation, such as "the price must be a positive number", can be checked at the gateway against a schema to reject junk early, but the service must check again, because other callers, such as a batch job, may reach it without the gateway. Aggregation, calling three services to build one screen, can live in the gateway for one or two screens; when it grows, move it into a backend for each client, the next beat.

The playable shows the trade-off as a request's path. Each job you turn on is one more step the request passes, which costs microseconds. Each job you turn off removes a protection, and the picture shows who gets in. The job that does not belong, order rules, shows its cost differently: an arrow from the gateway to the orders data that should not exist.

</GoDeeper>

## One front door per kind of client

<MermaidDiagram title="Kitabi's front doors" chart={`flowchart LR
  M["Kitabi app"] --> MB["Mobile BFF: one reply per screen"]
  W["Kitabi website"] --> WB["Web BFF"]
  P["Partner bookshops"] --> PA["Public REST API: API keys, strict limits"]
  MB --> G["Shared gateway layer: TLS, tokens, rate limits, request ids"]
  WB --> G
  PA --> G
  G --> S["Services: books, search, orders, payments"]
`} legend="Each kind of client gets a thin front door shaped for it; all of them share the same checks and the same services." />

One door does not have to fit every caller. Kitabi's app gets a mobile backend that returns whole screens in one round trip. Partners get a public REST API with API keys and strict limits. Each is a thin layer owned by the team that serves that client. All of them share the same checks and the same services behind them.

<GoDeeper title="Go deeper: backends for frontends, and when to split gateways">

A backend for frontend (BFF) is a small API shaped for one kind of client. The mobile team owns the mobile BFF, so when a screen changes, the team changes its BFF without asking the partner team. It is the gateway's aggregation job, given to the team that needs it. {/* source needed: the backend for frontend pattern (Sam Newman) */} This is the "one endpoint per screen" option from 6.2, and an alternative to GraphQL for a client the same company owns.

The partner API is different on purpose. Partners need stable versions for years (6.3), API keys instead of user logins, stricter rate limits, and documentation. Mixing those rules into the mobile BFF would slow both teams.

Do not copy the shared checks into every BFF. Keep them in one shared layer, a gateway product or a shared library run in front of every BFF, so that a fix to token checking ships once. Split into more doors only when two kinds of clients really need different rules; three or four front doors are common, twenty is a warning sign.

</GoDeeper>
