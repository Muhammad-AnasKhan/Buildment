Back to Huda's double charge from 6.1. The app must retry, because networks and providers fail. The server must make the retry harmless. This chapter builds that in four steps, and each step closes a gap the last one left open.

## A timeout hides what happened

<InteractiveCanvas slug="sysdesign-m6-timeout-unknown" />

Huda's app sends Pay and waits. The provider charges her card, but the reply is slow, and the app stops waiting. All the app knows is "no answer in time". The request may never have arrived, may have failed, or may have worked with only the reply lost. A safe retry must be right in all three cases.

<GoDeeper title="Go deeper: why clients must time out, retry, and still be careful">

A client that waits forever holds a connection, a thread and a spinning wheel on a user's screen forever. So every call needs a timeout. Brooker suggests setting it from the downstream latency you accept as a false timeout, for example the p99.9, so that only about 1 call in 1,000 that would have succeeded is cut off [S89].

Once a call times out, the client must decide whether to retry. Retrying is how systems survive short failures, but it has two costs. The first is load. In Brooker's example, a call stack five layers deep where every layer tries three times sends 243 times the load to the database at the bottom [S89]; Google's SRE book gives a similar example of 64 attempts from three layers of four tries [S91]. So retry at one layer, with backoff and jitter [S90]. The second cost is the one Huda paid: a retried write can happen twice.

An operation is <GlossaryTerm term="idempotent" definition="Safe to repeat: doing it twice has the same effect as doing it once. Setting a price to 1850 is idempotent; adding 1 to a stock count is not." /> when doing it twice has the same effect as once. Some operations are idempotent by nature. "Set book 42's price to 1850" leaves the same price however many times it runs; "add 1 to the stock count" does not. DynamoDB's documentation makes the same point: a conditional write can be made idempotent, while an atomic counter update is not [S42]. "Charge $18" is not idempotent by nature. The next beat makes it so.

</GoDeeper>

## Same key, same answer

<InteractiveCanvas slug="sysdesign-m6-key-replay" />

Before the first try, the app makes one random key for this payment, k7, and sends it with every retry. The API saves the key with the result. When the retry arrives with k7, the API finds the saved reply and sends it again instead of charging. One tap, any number of tries, one charge.

<GoDeeper title="Go deeper: how Stripe's idempotency keys behave">

Stripe's API is a well-documented example [S80]. A client sends an `Idempotency-Key` header with a POST. The server saves the status code and body of the first request made with that key, and returns the same result for every later request with the key. That includes errors: if the first request ended in a 500, retries get the same 500. Keys can be up to 255 characters, and they may be removed after they are at least 24 hours old. If a key is reused with different parameters, the request fails, so a bug cannot quietly attach one key to two different payments.

The key belongs to the user's intent, not to the HTTP request. Make it once, when Huda taps Pay, and keep it until the app gets a final answer. A new key per retry protects nothing, because every retry then looks like a new payment. Store it on the phone too, so an app that crashes and restarts mid-payment retries with the same key.

Use a random identifier that cannot collide, such as a UUID. Version 7 UUIDs start with the time, which keeps database indexes tidy; RFC 9562 recommends v7 over older time-based versions [S66]. Scope keys to the account on the server, `idem:huda:k7`, so that two users can never collide and one user can never replay another's key.

</GoDeeper>

## Claim the key before you charge

<InteractiveCanvas slug="sysdesign-m6-key-race" />

Checking first and saving later leaves a gap: a retry that arrives during the charge finds nothing and charges again. Close the gap by claiming the key before charging, in one atomic step, such as `SET k7 NX` in Valkey. Only one request can claim it. A second copy gets 409, "still running", and asks again later.

<GoDeeper title="Go deeper: claiming, finishing, and crashing in between">

An atomic step is one that no other request can interleave with. Valkey's `SET key value NX PX 86400000` sets the key only if it does not exist, and it does so as one command, so two requests that send it at the same moment cannot both succeed. A database gives the same guarantee with a unique index: `INSERT ... ON CONFLICT DO NOTHING` inserts the key row for exactly one request. {/* source needed: Valkey SET NX and PX options; PostgreSQL INSERT ON CONFLICT */}

The key moves through two states. **Pending** means one request claimed it and is working. **Done** means the result is saved, and every later request with the key gets that result. A request that finds the key pending gets `409 Conflict` and retries after a short wait; one that finds it done gets the saved reply. In challenge 5 you build exactly this, with a fingerprint of the request body saved next to the key, so that a key reused for a different request gets `422`, following the same rule as Stripe [S80].

The hard case is a crash between the charge and the save. The key stays pending; the card was charged; the result was never saved. Three defences work together. Give the pending claim an expiry, so a key does not stay stuck forever. Pass the same key on to the provider when it accepts one, as Stripe does [S80], so the provider itself refuses a second charge for it. And before charging again after an expired claim, ask the provider whether a charge for this key exists. If the key and the order live in the same database, write both in one transaction, and the gap closes completely.

</GoDeeper>

## Retry with and without a key

<InteractiveCanvas slug="sysdesign-m6-retry-key" />

Drag how slow the provider is, and pick how the API treats keys. The app waits 250 ms, then retries, up to 4 tries. With no key, every slow try charges again. With "check, then save", a retry that lands during the charge charges again. With "claim first", every purchase is charged exactly once.

<GoDeeper title="Go deeper: the model, and what your challenge measured">

The playable follows one purchase. The app sends a try, waits 250 ms, and if no answer has come, waits 50 ms more and sends the next try with the same key, up to 4 tries. The provider takes the time you drag, from 100 to 600 ms, for every try that reaches it.

- **No key.** Every try is a new payment. If the provider answers within 250 ms, there is one try and one charge. If it is slower, all 4 tries time out, and all 4 are charged. The app then shows "payment failed" to a customer charged four times.
- **Check, then save.** The second try starts about 300 ms after the first. If the first charge has finished and been saved by then, the retry gets the saved reply. If not, it finds nothing and charges again. Later tries usually find a saved reply.
- **Claim first.** The first try claims the key. Every later try finds it pending (409, wait, ask again) or done (saved reply). One charge, whatever the provider's speed.

Challenge 5 runs this with real HTTP and Valkey: 60 purchases, provider times spread from 100 to 600 ms. In one run on a laptop, no key gave 180 charges for 60 purchases, check-then-save gave 93, and claim-first gave exactly 60. Your numbers will differ a little; the order will not.

</GoDeeper>

## Where the key lives, and for how long

<MermaidDiagram title="The life of one idempotency key" chart={`flowchart LR
  T["Huda taps Pay"] --> K["App makes key k7 once and stores it"]
  K -->|"every try sends k7"| A["Payments API: claim idem:huda:k7 for 24 h"]
  A -->|"same key k7"| C["Provider: refuses a second charge for k7"]
  C --> S["API saves the reply under k7"]
  S -->|"later tries"| R["Saved reply, no new charge"]
`} legend="One key per user intent, born on the phone, claimed atomically by the API, passed on to the provider, and kept long enough to cover every retry." />

The key is born on the phone when Huda taps Pay, and it lives until her app gets a final answer. The API keeps it for at least a day, scoped to her account. Passing the same key on to the provider means even a crash between charging and saving cannot charge her twice.

<GoDeeper title="Go deeper: retention, size, and idempotency beyond HTTP">

How long to keep keys? Long enough to cover every retry a client could make, including a phone that loses signal and retries the next morning. Stripe keeps them for at least 24 hours [S80]. Estimate the cost the way module 2 taught: if Kitabi handles 50,000 payments a day and each saved entry is about 1 KB with its reply, a day of keys is about 50 MB, which fits easily in Valkey with a 24-hour expiry on each key. (These are made-up Kitabi numbers; do the sum for your own system.)

Where to store them? Valkey is fast and expiry is built in, but its data and the database's order rows can disagree after a crash. A key row in the same database transaction as the order cannot disagree with it. Many teams keep keys in the main database for money and in Valkey for cheaper operations.

The same idea runs through the rest of the course. Queues deliver messages at least once by default, so consumers must handle duplicates: SQS standard queues say so directly [S83], and Kafka's exactly-once covers Kafka-to-Kafka processing, while other systems need idempotent consumers [S82]. The outbox pattern in module 14 may publish a message twice, so its consumers must be idempotent too [S79]. "Exactly once" in practice usually means "at least once, plus idempotency".

</GoDeeper>
