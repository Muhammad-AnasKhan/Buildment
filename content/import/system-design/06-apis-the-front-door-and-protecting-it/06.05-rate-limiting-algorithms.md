A script starts scraping Kitabi's search, many requests a second from one client. Search slows down for every student. A <GlossaryTerm term="rate limiter" definition="A check in front of an API that counts each client's requests and refuses the ones over an agreed limit, such as 5 a second, so one client cannot slow the API for everyone." /> decides, per client, how much is too much. Every limiter answers the same way; they differ in how they count.

## Too many requests: answer 429

<InteractiveCanvas slug="sysdesign-m6-limit-429" />

Kitabi lets each client search 5 times a second. The script sends 12 at once. The limiter serves 5 and answers the other 7 with 429 Too Many Requests and a Retry-After header. Huda's search a moment later is served, because the limit counts each client separately. The rest of this chapter is about how the limiter counts.

<GoDeeper title="Go deeper: why limit, whom to limit, and what to send back">

A rate limit protects three things. Capacity: one client cannot take the share that other clients need. Fairness: a partner on a free plan cannot crowd out paying ones. Cost and abuse: scraping, password guessing and runaway scripts are cut off early, before they reach the database.

The limit is counted per something, called the key. An API key or a user id is the most precise. An IP address works for clients that are not logged in, but it is blunt: a whole university or a mobile network can share one public address, so an IP limit can block hundreds of students for one script. Many APIs combine limits: per user, per IP for logins, and one global limit for the whole service.

The answer is `429 Too Many Requests`, defined in RFC 6585 [S33], with a `Retry-After` header saying when to try again. {/* source needed: Retry-After with 429 in RFC 6585 section 4 */} Do not answer 503: a client cannot tell "you are sending too much" from "the server is down". nginx's limiter sends 503 by default, so set `limit_req_status 429` [S31].

Real systems run more than one limiter. Stripe described four: a request rate limiter, a limit on concurrent requests, and two load shedders that drop lower-priority traffic when the whole fleet or its workers are overloaded [S32]. A rate limit protects you from one client; load shedding protects you from everyone at once.

</GoDeeper>

## Token bucket: drip in, spend out

<InteractiveCanvas slug="sysdesign-m6-token-bucket" />

A token bucket holds up to 5 tokens, and 1 more drips in every second. Each request spends one token. The script's 7 at once find 5 tokens: 5 pass and 2 are refused. Two seconds later, 2 tokens are back. The capacity sets the biggest burst, and the refill rate sets the speed over a long time.

<GoDeeper title="Go deeper: the formula, and who uses it">

A token bucket does not need a timer that adds tokens. It stores two numbers per client, the tokens left and the time it last looked, and on each request it catches up:

```js
// On each request, at time now (ms):
tokens = Math.min(capacity, tokens + (now - last) * ratePerSecond / 1000);
last = now;
if (tokens >= 1) { tokens -= 1; allow(); } else { refuse(); }
```

Two numbers give two promises. Over any stretch of t seconds, a client gets at most `capacity + rate x t` requests, which is the gray "most allowed" line you will draw in challenge 5. And a quiet client always has a full bucket, so a short burst of normal use, such as a screen that loads 5 things at once, is never refused.

AWS API Gateway throttles with a token bucket: its "rate" is the tokens added per second and its "burst" is the bucket's capacity, and clients over the limit get 429. Its documentation also says these limits are targets, not guaranteed ceilings, because the bucket is spread over many servers [S30]. Stripe runs its request limiter as a token bucket stored in Redis, so every API server shares one bucket per user [S32]; you build that in challenge 5. Brooker suggests the same structure on the client side, to cap how often a client retries [S89].

A request can also cost more than one token. A search that scans many books, or a GraphQL query with a high cost (6.2), can spend 5 tokens while a simple read spends 1.

</GoDeeper>

## Leaky bucket: a steady drip out

<InteractiveCanvas slug="sysdesign-m6-leaky-bucket" />

A leaky bucket is a queue that drains at a fixed rate, here 1 request a second, and holds at most 3. Of 7 requests at once, 1 goes through now, 3 wait their turn, and 3 are refused. The server behind it sees a smooth 1 a second. The price is waiting: the last request in the queue waits 3 seconds.

<GoDeeper title="Go deeper: nginx's leaky bucket, and when smoothing helps">

nginx's `limit_req` module describes its method as a leaky bucket. You set a rate, for example `rate=1r/s`. Requests above the rate are delayed in a queue of size `burst`, and requests beyond the queue are rejected. With `nodelay`, nginx serves the queued burst at once instead of spacing it out, while still counting it against the rate. Rejected requests get 503 unless you set `limit_req_status 429` [S31].

Token bucket and leaky bucket allow the same long-run rate. They differ in what the server behind them sees. A token bucket lets a burst straight through to the server, so the server must handle bursts. A leaky bucket spaces requests out, so the server sees a steady flow, which suits a fragile backend such as an old database or a partner API with a strict limit of its own. The cost moves to the client as delay, and delay holds a connection open on both sides.

When the queue is full, both refuse, and the refusal is the important part. A queue with no limit only turns a burst into a long wait, which Little's law from module 2 tells you: more in flight at the same rate means a longer time in the system.

</GoDeeper>

## Fixed windows let a double burst through

<InteractiveCanvas slug="sysdesign-m6-fixed-window-edge" />

A fixed window counts each client's requests per calendar minute and resets to 0 when the minute changes. The script sends 5 at 12:00:59: allowed. One second later a new window starts, and 5 more are allowed. That is 10 requests in 2 seconds, under a limit of 5 a minute. Fixed windows are cheap, though: one counter per client.

<GoDeeper title="Go deeper: fixed windows and sliding logs">

A fixed window is the simplest limiter to build on a shared store. In Valkey, one counter per client per minute does it: `INCR rl:script:12:01`, set it to expire after the minute, and refuse when the count passes the limit. One number per client, one command per request.

Its flaw is the boundary. The limit holds inside each window, but nothing connects two neighbouring windows. A client that fills the end of one window and the start of the next gets up to 2 times the limit within a short stretch, as in the picture. For a limit meant to protect a server, that burst is exactly what you wanted to stop. This follows from the design itself; no extra source is needed to see it.

A sliding log fixes the boundary exactly. It stores the time of every allowed request and, on each new request, drops times older than one window and counts the rest. "5 in any 60 seconds" is then true for every 60-second stretch. The price is memory: one stored time per request. With a limit of 1,000 a minute, each busy client needs up to 1,000 times in memory, and the counting work grows with it. In challenge 5 you run a sliding log next to the other limiters and see it hold the limit exactly.

</GoDeeper>

## Sliding counter: weigh the last window

<InteractiveCanvas slug="sysdesign-m6-sliding-counter" />

A sliding window counter keeps two numbers per client: last window's count and this window's. At 12:01:00 the last minute still counts in full, 5 x 100% + 0 = 5, so the burst is refused. At 12:01:30 only half of it counts: 5 x 50% = 2.5, so 2 more fit. Two numbers give a close estimate of a true sliding window.

<GoDeeper title="Go deeper: Cloudflare's numbers, and where the estimate slips">

Cloudflare described this counter in 2017. The estimated rate is the previous window's count, times the share of the previous window still inside the sliding window, plus the current window's count. For example, 40 requests last minute and 12 so far this minute, 15 seconds into it, give 40 x (45 / 60) + 12 = 42. Measured on 400 million requests from 270,000 sources, only 0.003% of requests were wrongly allowed or wrongly limited [S29].

The estimate assumes the previous window's requests were spread evenly across it. Usually that is close enough, as Cloudflare's number shows. It slips when traffic is bunched. In challenge 5, a deliberately bunched pattern (10 requests at the very end of one window, then a steady stream) let the counter allow 19 requests in one 1-second stretch under a limit of 10. It still stopped the boundary burst itself, where a fixed window allowed 20 in 0.1 seconds. Decide whether that worst case matters for your limit before you choose it.

The counter costs two numbers per client, the same order as a fixed window, and it can live in Valkey just as easily. That is why it is a common choice when there are millions of clients and the limit does not need to be exact.

</GoDeeper>

## Same burst, five limiters

<InteractiveCanvas slug="sysdesign-m6-limiter-burst" />

Send one burst pattern through all five limiters at once. Drag the second burst across the minute boundary. The fixed window lets all 10 through as soon as the boundary falls between them. The sliding log and the counter hold most of the second burst back, so the total stays near 5. The token bucket allows only what has dripped back; the leaky bucket makes requests wait instead.

<GoDeeper title="Go deeper: choosing a limiter">

| Limiter | Memory per client | A burst at the boundary | Behind it, the server sees |
|---|---|---|---|
| Token bucket | 2 numbers | Up to capacity, then the rate | Bursts up to capacity |
| Leaky bucket | A queue | Queued, then spaced out | A steady rate |
| Fixed window | 1 counter | Up to 2 times the limit | Bursts at each boundary |
| Sliding log | 1 time per request | Exactly the limit | Bursts up to the limit |
| Sliding window counter | 2 counters | About the limit | Bursts up to about the limit |

For most APIs a token bucket is the default choice: it allows the short bursts that normal clients make, it is cheap, and its two settings are easy to explain to a partner ("50 at once, 10 a second after that"). It is what API Gateway [S30] and Stripe [S32] use. A sliding window counter suits very many clients and a "per minute" limit that must not double at the boundary [S29]. A leaky bucket suits a fragile backend that needs a steady flow [S31]. A fixed window is fine for coarse limits where a double burst does no harm, such as 10,000 requests a day. Use a sliding log only when the limit is small and must be exact, such as 5 password attempts in 15 minutes.

Whatever you choose, the hard part at scale is where the count lives. One limiter per server lets a client get N times the limit across N servers. Chapter 6.6 puts the limiter in the gateway, and challenge 5 moves the count into Valkey with an atomic script.

</GoDeeper>
