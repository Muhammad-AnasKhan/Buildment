```quiz
type: mcq
question: "Kitabi's support tool calls POST /refunds. It times out after 5 seconds and retries on its own. One refund for order 88 was requested, and two refunds reached the customer. Which fix stops this?"
options:
  - "One key per refund, claimed before paying"
  - "Raise the support tool's timeout to 60 seconds"
  - "Retry only when the server answers 500"
  - "Check for a refund for order 88, then insert one"
correct: 0
explanations:
  - "Right. The tool sends the same key on every retry, and the server claims it in one atomic step before paying, so a retry gets the saved result."
  - "A longer timeout makes the problem rarer, not impossible. Some refund will always take longer than any timeout."
  - "The retry that caused the second refund followed a timeout, not a 500. The tool cannot see a status it never received."
  - "Check, then insert has a gap: a retry that arrives during the first refund finds nothing and pays again."
```

```quiz
type: mcq
question: "Kitabi runs 4 gateway copies behind a load balancer. Each copy keeps an in-memory token bucket of 100 requests a minute per API key. A partner's script spreads its requests evenly over the copies. About how many requests a minute can it get through?"
options:
  - "100: the limit is per API key"
  - "About 25: each copy gets a quarter"
  - "About 400: 4 buckets"
  - "About 200: the buckets share half"
correct: 2
explanations:
  - "The limit is per key in each copy, and the copies do not share their counts. Nothing joins the four buckets."
  - "Each copy sees a quarter of the traffic, but each still has a full bucket of 100, so none of them refuses early."
  - "Right. Each copy allows 100 a minute on its own, so the key gets about 4 times its limit. Keep the bucket in a shared store, changed atomically."
  - "In-memory buckets share nothing. Each copy counts only what it sees and allows its own full 100."
```

```quiz
type: mcq
question: "A partner app shows Kitabi's newest books in an endless scroll that loads 20 at a time with ?offset=20, ?offset=40 and so on. Users report seeing the same book twice, mostly at busy times. What causes it?"
options:
  - "The CDN served an old copy of one page"
  - "Offsets shift as new rows arrive"
  - "The partner's client retries every request"
  - "Two different books share one title"
correct: 1
explanations:
  - "A stale page could show old data, but repeats that grow with the number of new books point to positions moving."
  - "Right. Each new book at the top pushes every row down one place, so the next offset starts on a book already shown. A cursor fixes it."
  - "Retrying a GET returns the same page again; it does not move the next page back onto books already shown."
  - "The users see the same book, not two books with one name. The list's positions moved under them."
```

```quiz
type: mcq
question: "Kitabi's access tokens last 60 minutes and services check only their signature. Security wants a stolen token to stop working within 5 minutes, without a lookup on most requests. Which change fits?"
options:
  - "Check every token with the login server"
  - "Keep 60-minute tokens and add rate limits"
  - "Make tokens last forever, with a denylist"
  - "5-minute tokens, revocable refresh"
correct: 3
explanations:
  - "That meets the 5 minutes, but it puts a lookup on every request, which security asked to avoid."
  - "Rate limits slow a thief down but do not stop a stolen token. It still works for up to 60 minutes."
  - "Tokens that never expire depend completely on the denylist, which every service must check on every request."
  - "Right. A stolen access token dies within 5 minutes, and a ban stops the next refresh. Only the refresh, every few minutes, needs a lookup."
```

```quiz
type: mcq
question: "Kitabi must stop password guessing: at most 5 login attempts per account in any 15 minutes, counted exactly. There are 200,000 accounts, but few try to log in at the same time. Which limiter fits best?"
options:
  - "A fixed window of 15 minutes"
  - "A token bucket of 5, refilled hourly"
  - "A sliding log of attempt times"
  - "A leaky bucket draining 5 per window"
correct: 2
explanations:
  - "A fixed window allows 5 at the end of one window and 5 at the start of the next: 10 guesses in a few seconds."
  - "A bucket refilled over an hour does not match '5 in any 15 minutes', and it allows a full burst after any quiet hour."
  - "Right. The log keeps at most 5 times per active account and checks any 15-minute stretch exactly. With a limit this small, its memory cost is tiny."
  - "A leaky bucket queues extra attempts instead of refusing them, and it smooths the rate rather than counting exactly."
```
