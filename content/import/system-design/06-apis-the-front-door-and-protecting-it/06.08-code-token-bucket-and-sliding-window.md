In 6.5 you watched five limiters handle the same burst. Two of them are the ones most APIs actually run: the token bucket, which API Gateway and Stripe use, and the sliding window counter, which Cloudflare described. Both are a few lines of code, and both are easy to get subtly wrong in ways that only show up under real traffic. In this chapter you write them yourself, and tests with a fake clock check every awkward case in milliseconds.

By the end, you will have two tested JavaScript functions. `createTokenBucket({ capacity, refillPerSecond, now })` returns a limiter whose `take(cost)` says whether a request may pass, how many whole tokens are left, and how long to wait if it may not. `createSlidingWindowCounter({ limit, windowMs, now })` returns a limiter whose `allow()` says whether a request may pass and what the weighted count was. You will paste both into challenge 5, in the next chapter, and run them in front of a real server.

## Why the clock is passed in

Both limiters depend on time. The obvious way to read time is to call `Date.now()` inside the function. That makes the code hard to test: to check that a token comes back after one second, a test would have to wait a real second, and timers on a busy test machine are not exact, so the test would sometimes fail for no reason.

So both functions take a `now` argument, a function that returns the current time in milliseconds. In production you pass `() => performance.now()`. In a test you pass `() => t` and move `t` by hand: `t = 1000` means "one second has passed", instantly and exactly. This is called injecting the clock, and it is the same trick the shared simulation core of this course uses to make every run repeatable.

It also forces you to handle a clock that misbehaves. `Date.now()` follows the wall clock, and the wall clock can step backwards when NTP corrects it or a leap second is applied. On 1 January 2017 a leap second made one of Cloudflare's DNS servers measure a negative duration, and the panic that followed made some DNS queries fail [S133]. Your limiters must survive the same thing: if `now()` goes backwards, treat time as standing still. Never add negative tokens, and never move a window backwards. In production, prefer `performance.now()`, which only moves forward.

## The contract

**`createTokenBucket({ capacity, refillPerSecond, now })`.** The bucket starts full. It stores two numbers: the tokens it has and the time it last looked. On every `take(cost = 1)` it first catches up: it adds the elapsed milliseconds times `refillPerSecond / 1000`, and caps the total at `capacity`. Then, if there are at least `cost` tokens, it spends them and returns `{ allowed: true, remaining, retryAfterMs: 0 }`. If not, it spends nothing and returns `{ allowed: false, remaining, retryAfterMs }`, where `retryAfterMs` is how long until enough tokens will be back, rounded up. `remaining` is always the whole tokens left, rounded down, which is what an `X-RateLimit-Remaining` header would show.

Two inputs need care. A `cost` larger than `capacity` can never pass, however long the client waits, so it returns `retryAfterMs: Infinity` and spends nothing. A `capacity` or `refillPerSecond` that is zero, negative, infinite or not a number is a bug in the caller's settings, so creating the bucket throws a `RangeError`.

**`createSlidingWindowCounter({ limit, windowMs, now })`.** Windows start at multiples of `windowMs`: with 1,000 ms windows, they are 0 to 1,000, 1,000 to 2,000, and so on. The counter keeps three numbers: the start of the current window, the count of allowed requests in it, and the count in the previous window. On each `allow()` it works out which window `now()` is in. If time has moved into the next window, the current count becomes the previous one and the current count starts at 0. If time has jumped further, past a whole empty window, both counts start at 0. Then it computes the estimate: the previous count, times the share of the previous window still inside the sliding window, plus the current count. The request is allowed when the estimate plus 1 is at most `limit`. Only allowed requests are counted. `allow()` returns `{ allowed, estimate }`, with the estimate as it was before this request.

Counting only allowed requests is a design choice, and the tests check it. If refused requests counted too, a client that kept knocking after its limit would stay blocked for longer and longer. Some limiters do that on purpose, to punish abusers; this one does not.

## A worked example on a fake clock

Here are both limiters stepped by hand, on inputs that are not in the tests. First a bucket with `capacity: 3` and `refillPerSecond: 2`.

At t = 0, four requests arrive. The bucket is full with 3 tokens, so the first three pass, leaving 2, 1 and 0 whole tokens. The fourth is refused. It needs 1 token, the bucket has 0, and tokens come back at 2 a second, so `retryAfterMs` is 1 x 1000 / 2 = 500.

At t = 250, another request. Catching up adds 250 x 2 / 1000 = 0.5 tokens. Half a token is not enough, so it is refused, and it needs 0.5 more: 0.5 x 1000 / 2 = 250 ms. Note the subgoal here: the catch-up happened even though the request was refused, so the bucket now holds 0.5 and remembers t = 250.

At t = 1000, catching up adds 750 x 2 / 1000 = 1.5 tokens, so the bucket holds 2.0. The request passes and leaves 1 whole token.

Now a counter with `limit: 4` and `windowMs: 1000`. At t = 100, three requests: estimates 0, 1 and 2, all allowed. At t = 900, one more: estimate 3, allowed, so the window 0 to 1,000 has 4. Another at t = 900: estimate 4, and 4 + 1 is more than 4, so it is refused, and not counted.

At t = 1400 the window has moved on by exactly one, so the previous count is 4 and the current count is 0. The sliding window covers 400 to 1,400, and 600 ms of it lies in the previous window: a share of 0.6. The estimate is 4 x 0.6 + 0 = 2.4, and 2.4 + 1 is at most 4, so the request passes. A second request at 1,400 has an estimate of 2.4 + 1 = 3.4, and 3.4 + 1 is more than 4, so it is refused.

## Four ways this goes wrong

**A timer that adds tokens.** It is tempting to run `setInterval` to add a token every so often. With a million clients that is a million timers, timers drift, and a bucket in Valkey cannot run a timer at all. Store the time and catch up on each request instead, as the diagram shows.

**No cap.** Without `Math.min(capacity, ...)`, a client that was quiet for an hour comes back with 7,200 tokens at 2 a second and can send them all at once. One test leaves the bucket alone for a minute and checks that only `capacity` requests pass.

**Spending on refusal.** If a refused request still subtracts its cost, the tokens go negative, and a client that retries too eagerly digs itself deeper. The fix is to subtract only when allowing. One test sends four requests at an empty bucket and checks that a token still comes back after one second.

**Trusting a clock that steps back.** If `now()` drops from 10,000 to 4,000, a naive bucket computes a negative elapsed time and removes tokens, and a naive counter moves into an old window and forgets the requests it has seen. Only move time forward.

solution: |
  function createTokenBucket({ capacity, refillPerSecond, now }) {
    if (!(capacity > 0) || !Number.isFinite(capacity) || !(refillPerSecond > 0) || !Number.isFinite(refillPerSecond)) {
      throw new RangeError("capacity and refillPerSecond must be positive finite numbers");
    }
    let tokens = capacity;
    let last = now();
    return {
      take(cost = 1) {
        const t = now();
        if (t > last) {
          tokens = Math.min(capacity, tokens + ((t - last) * refillPerSecond) / 1000);
          last = t;
        }
        if (cost > capacity) return { allowed: false, remaining: Math.floor(tokens), retryAfterMs: Infinity };
        if (tokens >= cost) {
          tokens -= cost;
          return { allowed: true, remaining: Math.floor(tokens), retryAfterMs: 0 };
        }
        return { allowed: false, remaining: Math.floor(tokens), retryAfterMs: Math.ceil(((cost - tokens) * 1000) / refillPerSecond) };
      },
    };
  }

  function createSlidingWindowCounter({ limit, windowMs, now }) {
    if (!(limit > 0) || !Number.isFinite(limit) || !(windowMs > 0) || !Number.isFinite(windowMs)) {
      throw new RangeError("limit and windowMs must be positive finite numbers");
    }
    let last = now();
    let currentStart = Math.floor(last / windowMs) * windowMs;
    let current = 0;
    let previous = 0;
    return {
      allow() {
        const t = Math.max(now(), last);
        last = t;
        const start = Math.floor(t / windowMs) * windowMs;
        if (start !== currentStart) {
          previous = start === currentStart + windowMs ? current : 0;
          current = 0;
          currentStart = start;
        }
        const weight = (windowMs - (t - start)) / windowMs;
        const estimate = previous * weight + current;
        if (estimate + 1 <= limit) {
          current += 1;
          return { allowed: true, estimate };
        }
        return { allowed: false, estimate };
      },
    };
  }
