You can build a system and still fail to explain it. A defence is the test of the second skill. In five minutes you tell a mentor what the system must do, how you designed it, that it meets its targets, what happened when you broke it, and what would change at ten times the traffic. Then you answer three questions you did not choose. A mentor reviews your repository in under 45 minutes, and your recording is the first five of them.

By the end of this chapter, your repository has `part-3-defence/` with a README, a file of claims, a script that checks every claim against a fresh measurement, a test, a script for your talk, a `results.md` and a chart. You also have a recording and three probe answers. The recording is the one piece that is not in the repository: you submit its link.

**What you need.** Your core from 29.3, your experiment from 29.4, `toolkit/slo.js` from challenge 16 and `toolkit/bars.js` from challenge 8. A phone or laptop that can record voice, and a quiet place. Plan about an hour and a half: 30 minutes for the claims, 20 for the script and the probes, and 40 to practise and record.

## Claims you can defend

The most common failure in a defence is a number that is a little better than the evidence. "About 5 ms" when the run said 9. "Basically no errors" when 2,841 requests were lost. A mentor who catches one such number starts to doubt the rest. So before you write a script, you write down your numbers and let the repository refuse the ones that are not true.

Create `part-3-defence/claims.json`. It has two groups. `estimate` holds the numbers from section 2 of your `DESIGN.md`, written before you built anything. `claim` holds the numbers you will say aloud, after measuring. The two groups will usually differ, and the difference is a good thing to talk about. The five numbers are the p99, the availability, the cost per hour, the requests lost in your fault experiment and the seconds to recover. The values below are an example for one stand-in design, not yours:

```json
{
  "estimate": { "p99Ms": 5, "availability": 0.9995, "costPerHour": 0.35, "lostInFault": 100, "recoverSeconds": 5 },
  "claim": { "p99Ms": 1.3, "availability": 1, "costPerHour": 0.3, "lostInFault": 3, "recoverSeconds": 0 }
}
```

Now `part-3-defence/claims.js`. It reruns the measurement and the experiment for the scenario in `choice.js`, prints each claim beside the measured value, and says whether the claim matches. A claim matches when it is within an allowance of the measured value: the larger of a small fixed amount and 10% of the value, except for availability, where only the fixed amount counts, because 10% of 99.95% would make the claim meaningless. It also draws a bar chart of how much of each budget the system used, where 100 means exactly at the limit. The error budget bar uses your `burnRate` from chapter 17.7: the share of allowed failures that the run used.

```js
// Part 3: put every number you will say in your defence next to the number you
// measured, and refuse to let a claim be better than the evidence.
import { readFileSync, writeFileSync } from "node:fs";
import { pathToFileURL } from "node:url";
import { SCENARIO } from "../choice.js";
import { SCENARIOS } from "../scenarios.js";
import { measure } from "../part-1-core/measure.js";
import { runExperiment } from "../part-2-break-it/experiment.js";
import { burnRate } from "../../../toolkit/slo.js";
import { barChart } from "../../../toolkit/bars.js";

export const KEYS = ["p99Ms", "availability", "costPerHour", "lostInFault", "recoverSeconds"];
// How far a claim may be from the measurement and still be honest: the larger of
// this allowance and 10% of the measured value (10% does not apply to availability).
export const TOLERANCE = { p99Ms: 0.1, availability: 0.0005, costPerHour: 0.01, lostInFault: 5, recoverSeconds: 1 };

export function readClaims(url = new URL("./claims.json", import.meta.url)) {
  return JSON.parse(readFileSync(url, "utf8"));
}

// What the repository measures right now, for the scenario in choice.js.
export function measured() {
  const m = measure({ seeds: [1] });
  const e = runExperiment({ seed: 1 });
  const row = m.rows[0];
  return {
    targets: m.targets,
    values: { p99Ms: row.p99, availability: row.availability, costPerHour: row.cost, lostInFault: e.badRequests, recoverSeconds: e.recovery },
    wrong: row.wrong + e.wrong,
  };
}

export function honest(claim, value, key) {
  const relative = key === "availability" ? 0 : Math.abs(value) * 0.1;
  return Math.abs(claim - value) <= Math.max(TOLERANCE[key], relative);
}

// How much of each budget the system used. 100 means exactly at the limit.
export function budgetsUsed(values, targets) {
  return {
    "p99 time": (values.p99Ms / targets.p99Ms) * 100,
    "error budget": burnRate(values.availability, targets.availability) * 100,
    "cost": (values.costPerHour / targets.costPerHour) * 100,
  };
}

if (import.meta.url === pathToFileURL(process.argv[1]).href) {
  const { estimate, claim } = readClaims();
  const { targets, values, wrong } = measured();
  const rows = [
    ["p99 ms", "p99Ms", `<= ${targets.p99Ms}`, 2],
    ["availability", "availability", `>= ${targets.availability}`, 4],
    ["cost per hour", "costPerHour", `<= ${targets.costPerHour.toFixed(2)}`, 2],
    ["lost in fault", "lostInFault", "", 0],
    ["recover s", "recoverSeconds", "", 0],
  ];
  console.log("what            target       estimate  measured  claim    verdict");
  for (const [label, key, target, digits] of rows) {
    const ok = honest(claim[key], values[key], key);
    console.log(`${label.padEnd(15)} ${target.padEnd(12)} ${String(estimate[key]).padStart(8)}  ${values[key].toFixed(digits).padStart(8)}  ${String(claim[key]).padStart(6)}   ${ok ? "claim matches" : "CLAIM IS OFF"}`);
  }
  console.log(`wrong answers: ${wrong}`);
  const used = budgetsUsed(values, targets);
  writeFileSync(new URL("./chart.svg", import.meta.url), barChart({
    title: `${SCENARIOS[SCENARIO].title}: share of each budget used`,
    yLabel: "percent of the limit",
    unit: "%",
    bars: Object.entries(used).map(([label, value]) => ({ label, value })),
  }));
  console.log("wrote chart.svg");
}
```

And the test, which refuses a claim that is not true. It also refuses a measurement that misses a target, so the defence file cannot be green while the system is red.

```js
import test from "node:test";
import assert from "node:assert/strict";
import { KEYS, budgetsUsed, honest, measured, readClaims } from "./claims.js";

const { estimate, claim } = readClaims();
const { targets, values, wrong } = measured();

test("claims.json has an estimate and a claim for every number", () => {
  for (const key of KEYS) {
    assert.equal(typeof estimate[key], "number", `estimate.${key}`);
    assert.equal(typeof claim[key], "number", `claim.${key}`);
  }
});

test("the measurements meet the targets and break no promise", () => {
  assert.ok(values.p99Ms <= targets.p99Ms);
  assert.ok(values.availability >= targets.availability);
  assert.ok(values.costPerHour <= targets.costPerHour);
  assert.equal(wrong, 0);
});

test("every claim matches what the repository measures", () => {
  for (const key of KEYS) assert.ok(honest(claim[key], values[key], key), `${key}: claim ${claim[key]}, measured ${values[key]}`);
});

test("no budget is used up", () => {
  for (const [name, used] of Object.entries(budgetsUsed(values, targets))) assert.ok(used <= 100, `${name} used ${used.toFixed(0)}%`);
});

test("honest allows a small gap and refuses a big one", () => {
  assert.ok(honest(5.2, 5, "p99Ms"));
  assert.ok(!honest(3, 5, "p99Ms"));
  assert.ok(honest(0.9996, 0.9999, "availability"));
  assert.ok(!honest(0.99, 0.9999, "availability"));
});
```

## The script, in five parts

Write `part-3-defence/DEFENCE.md`: the words you will say, with the time you give to each part. Five minutes is short, so write what you will say and cut it until it fits. You will not read it aloud, but writing it forces the choice of what matters.

| Part | Time | What you say | What is on screen |
|---|---|---|---|
| 1. What and how big | 0:00 to 0:45 | The system in a sentence, the three targets, the promises, and the driving number with its working | The first lines of `DESIGN.md` |
| 2. The design | 0:45 to 1:45 | One picture, then three choices, each with a reason that has a number and an alternative you did not pick | Your design diagram |
| 3. Proof | 1:45 to 3:00 | The sandbox result and the three-seed table, the busiest box, and what the claims table says | `claims.js` output and the bar chart |
| 4. I broke it | 3:00 to 4:15 | The fault, the prediction, what happened on the chart, the gap and what you did about it | `chart.svg` of the experiment |
| 5. Ten times | 4:15 to 5:00 | The first thing that breaks at ten times the traffic, with a number, and the change | The sum on screen |

The most important part to prepare is part 5, because it is the one a mentor will test with a probe. Do the arithmetic before you record. Here is an example for the stand-in design of system A, with its own numbers. At the busiest moment it gets 8,400 requests a second. Ten times that is 84,000. A cached read costs the app 0.26 ms of work, so 84,000 times 0.26 ms is 21,840 ms of work every second, or about 22 workers busy at once. A medium box has 4 workers, and chapter 2.5 showed the knee: waiting grows fast as a box gets close to full. Choose to plan for 70% busy, as a rule of thumb. Then you need 22 divided by 0.7, about 31 workers, which is 8 medium boxes. At 0.10 an hour each that costs 0.80, twice the 0.40 budget. So at ten times the traffic, the budget breaks before the p99 does, and the change is to find a cheaper way to answer, not to buy more boxes. Your numbers will differ, and the shape of the answer is the same: a rate, a cost per request, a division, and a verdict.

## Three probes

After your five minutes, the mentor asks one to three follow-up questions. You prepare three in advance, one of each kind, so you are not surprised. Pick them from the bank below, or invent your own, and write each answer in three parts: **the number** (say the figure first), **the mechanism** (why it is that figure) and **the cost** (what the fix or the trade-off gives up). An answer without a number is an opinion. An answer without a cost is half a trade-off.

<GoDeeper title="Go deeper: the probe bank">

**Scale probes.** What breaks first if traffic grows 10 times, and at what traffic does it break? Which single box would you scale first, and what does it cost per hour? Where is the next bottleneck after that one? What would you stop doing at the peak to stay inside the budget? If the busiest key were twice as busy, what happens?

**Failure probes.** What happens to a user during your experiment, second by second? What if the fault lasted ten minutes instead of eight seconds? What if two things failed at once? How does the system notice that a box is sick, and how long does that take? What does a restarted box need before it can serve? What would you add to see this failure in production before a user tells you?

**Trade-off probes.** Why this choice and not its alternative, and at what number would you switch? What did you give up to meet the cost target? Which promise is most expensive to keep, and what would you do if the budget were cut in half? Which of your numbers are you least sure of? If you could add one box for free, where would it go?

A strong answer has the same shape every time. For "what breaks first at ten times?" it is: "At 84,000 requests a second the apps break first, because the work needs about 22 workers busy at once and I have 8. That is a cost problem before a latency one, since 8 boxes cost 0.80 an hour against a budget of 0.40. I would stop answering the viral link from the app box at all, and let a cache in front serve it." For "what if two things fail?" a strong answer says which promise still holds and which does not, and why. If you do not know, say so, say what you would measure to find out, and say how long it would take. That earns more than a guess.

</GoDeeper>

## Record it

Record once as a practice run, listen to it, and then record the real one. Time yourself: the first practice nearly always runs over. A few things help on a phone and on weak data.

You may record voice only, with your screen or your slides shown, or video, as you prefer. Audio alone is perfectly fine and much smaller. Show only your work: your screen, your chart and your repository, not your surroundings or other people. Do not read your script word for word, because the listener hears it at once. Say the number before the explanation. Keep the files small, and upload to any place where your mentor can open the link without signing in. Give the probe answers in the same recording, one after the other, after the five minutes, each in about a minute and a half, and say the question before each answer.

If you lose your connection or the power fails, nothing is lost: the script is in your repository, and a recording can be made again. If your English is a second language, speak slowly and use short sentences. A mentor listens for the numbers and the reasons, not for perfect grammar.

## Verify, including one failure on purpose

Make a claim false and watch it fail. In `claims.json`, change the p99 claim to half the measured value, run `npm test` and read the message. It names the key, the claim and the measured value. Put it back. Then time your recording against the clock on part 5: if you cannot finish the ten-times answer in 45 seconds, shorten part 3.

## The rubric for the defence

The recording feeds the communication row of the rubric, and the probes feed design choices. For communication, a 2 means five parts in five minutes, the driving number, one trade-off with a number, and probe answers with numbers. A 3 means no notes, a failure trade-off explained with a number, and a clear answer for ten times the traffic. A recording that reads the document aloud, or that runs far over time, is a 1.
