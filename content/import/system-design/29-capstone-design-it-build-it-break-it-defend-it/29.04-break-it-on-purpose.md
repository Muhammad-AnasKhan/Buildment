A design that passes on a good day has told you very little. Every system in this course was built to survive something: a box that dies, a network that splits, a dependency that slows. The design document you wrote in 29.2 has a table of failure modes, and until now every row of it was a hope. In this chapter you pick one row, write down what you expect to happen with numbers, break the system on purpose, and chart what really happens.

By the end, your repository has `part-2-break-it/` with a README, an experiment script, a test file, a `results.md`, and two charts. One experiment, done well, is better than three done quickly. The mentor does not look for a system that never fails. They look for a learner who predicted the failure, measured it, and can explain the difference.

**What you need.** Your core from 29.3, passing its tests. Nothing new to install. Plan about two and a half hours: thirty minutes to choose and predict, an hour to run and read, and the rest to write.

## Choose the fault that matters

The harness can inject three faults, each with a start and an end. A **kill** stops one box: work that was running is lost, new messages vanish, and when the box restarts it comes back with an empty memory. A **slow** fault makes one box a number of times slower, like a disk that is failing but not dead. A **cut** stops all messages between two nodes, like a broken link between two regions.

They are not equally interesting for every design, and the right choice is the fault that threatens your most important promise. Ask your design document: which failure would hurt most, and which row of the table am I least sure about?

| System | A natural fault | Why it matters |
|---|---|---|
| A. Hayat Links | Slow one app box, or kill the store, during the viral post | Tests whether the cache and the balancer hide a sick box at the busiest moment |
| B. Majlis | Kill the box that holds popular timelines | Tests whether timelines are rebuilt, and whether the 2 second promise survives |
| C. Souq | Cut the link between eu and na | Tests the choice between answering and being exactly right, with real numbers |

Fire the fault during the busy part of the run. In system A the viral post lasts from second 10 to second 20, so a fault from second 12 to second 20 hits the system when it is hardest to hide. A fault in a quiet moment proves little.

## Write your prediction first

Before you run anything, open `part-2-break-it/results.md` and write four lines. What fault, on which box or link, from when to when. What the user will see during the fault, with a number: what share of requests answered, and the p99. How many requests you expect to lose in total. And how many seconds after the fault ends the system is back to normal, which goes into the plan as `recoverWithinS`. Then commit and push the file with a message such as "Prediction for the failure experiment". The commit time shows that you predicted before you measured.

This step feels strange, and it is the most useful one. If your prediction is vague, "some errors for a while", you cannot be wrong, so you cannot learn. A prediction with numbers can be wrong, and the gap is what you explain at the end. You are allowed to be wrong. You are not allowed to change the prediction afterwards.

## Step 1: the experiment script

Create `part-2-break-it/experiment.js`. The `PLAN` at the top is the only part you edit. `eventsFor` turns the plan into two events for the harness. `runExperiment` runs your core twice with the same seed, once normally and once with the fault, so the only difference between the two runs is the fault. `recoverySeconds` finds the last second in which fewer than 99% of requests were answered, and counts from the end of the fault. `charts` draws two pictures.

```js
// Part 2: break your system on purpose, once, and chart what happens.
// Edit the plan below. Write your prediction in results.md BEFORE you run it.
import { writeFileSync } from "node:fs";
import { pathToFileURL } from "node:url";
import { SCENARIO } from "../choice.js";
import { SCENARIOS } from "../scenarios.js";
import { perSecond, runScenario, summarize } from "../harness.js";
import { seriesChart } from "../../../toolkit/series-chart.js";
import { createCore } from "../part-1-core/core.js";

export const PLAN = {
  fault: "kill", // "kill" a box, "slow" a box down, or "cut" the link between two nodes
  box: "app1", // for kill and slow: the id of one box in your core's boxes
  link: ["eu", "na"], // for cut: the two node ids that lose contact
  slowBy: 10, // for slow: how many times slower
  startMs: 12_000,
  endMs: 20_000,
  recoverWithinS: 3, // my prediction: normal again this many seconds after the fault ends
};

// Find one of your boxes by id, with a message that says what ids exist.
function boxOf(core, id) {
  const box = core.boxes[id];
  if (!box) throw new Error(`no box called "${id}"; your core has: ${Object.keys(core.boxes).join(", ")}`);
  return box;
}

// The events the harness runs at the start and the end of the fault.
export function eventsFor(plan) {
  if (plan.fault === "kill") {
    return [
      { atMs: plan.startMs, label: `kill ${plan.box}`, run: ({ core }) => boxOf(core, plan.box).kill() },
      { atMs: plan.endMs, label: `restart ${plan.box}`, run: ({ core }) => boxOf(core, plan.box).restart(0) },
    ];
  }
  if (plan.fault === "slow") {
    return [
      { atMs: plan.startMs, label: `slow ${plan.box} by ${plan.slowBy}`, run: ({ core }) => boxOf(core, plan.box).slow(plan.slowBy) },
      { atMs: plan.endMs, label: `${plan.box} back to normal`, run: ({ core }) => boxOf(core, plan.box).slow(1) },
    ];
  }
  if (plan.fault === "cut") {
    return [
      { atMs: plan.startMs, label: `cut ${plan.link.join(" and ")}`, run: ({ net }) => net.cut(...plan.link) },
      { atMs: plan.endMs, label: `heal ${plan.link.join(" and ")}`, run: ({ net }) => net.heal(...plan.link) },
    ];
  }
  throw new Error(`unknown fault "${plan.fault}"`);
}

// Seconds after the fault ends until every later second is back above 99% answered.
export function recoverySeconds(seconds, endMs) {
  const from = Math.ceil(endMs / 1000);
  let last = -1; // the last second that was still unhealthy
  seconds.forEach((s) => { if (s.ok + s.bad > 0 && s.ok / (s.ok + s.bad) < 0.99) last = s.second; });
  return Math.max(0, last + 1 - from);
}

export function runExperiment({ plan = PLAN, scenario = SCENARIO, seed = 1 } = {}) {
  const normal = runScenario({ createCore, scenario, seed });
  const broken = runScenario({ createCore, scenario, seed, events: eventsFor(plan) });
  const during = (run) => summarize(run, { fromMs: plan.startMs, toMs: plan.endMs });
  const seconds = perSecond(broken);
  return {
    plan, scenario, normal, broken, seconds, normalSeconds: perSecond(normal),
    duringNormal: during(normal), duringBroken: during(broken),
    recovery: recoverySeconds(seconds, plan.endMs),
    badRequests: seconds.reduce((sum, s) => sum + s.bad, 0) - perSecond(normal).reduce((sum, s) => sum + s.bad, 0),
    wrong: broken.violationCount,
  };
}

export function charts(result) {
  const { plan, seconds, normalSeconds, scenario } = result;
  const title = `${SCENARIOS[scenario].title}: ${plan.fault} ${plan.fault === "cut" ? plan.link.join("-") : plan.box} from ${plan.startMs / 1000} s to ${plan.endMs / 1000} s`;
  const line = (name, color, rows, key) => ({ name, color, points: rows.map((s) => ({ x: s.second, y: s[key] })) });
  return {
    requests: seriesChart({
      title, xLabel: "seconds", yLabel: "requests per second",
      series: [line("answered", "#2563eb", seconds, "ok"), line("not answered", "#dc2626", seconds, "bad"), line("normal run", "#9ca3af", normalSeconds, "ok")],
    }),
    p99: seriesChart({
      title, xLabel: "seconds", yLabel: "p99 ms (1000 = no answer)",
      series: [line("p99", "#2563eb", seconds, "p99"), line("normal run", "#9ca3af", normalSeconds, "p99")],
    }),
  };
}

if (import.meta.url === pathToFileURL(process.argv[1]).href) {
  const result = runExperiment();
  const { plan, duringNormal, duringBroken } = result;
  console.log(`fault: ${eventsFor(plan).map((e) => `${e.label} at ${e.atMs / 1000} s`).join(", ")}\n`);
  console.log("during the fault window          normal run   with the fault");
  console.log(`answered                         ${(duringNormal.availability * 100).toFixed(3).padStart(9)}%   ${(duringBroken.availability * 100).toFixed(3).padStart(9)}%`);
  console.log(`p99 ms                           ${duringNormal.p99.toFixed(2).padStart(10)}   ${duringBroken.p99.toFixed(2).padStart(13)}`);
  console.log(`\nrequests lost because of the fault: ${result.badRequests}`);
  console.log(`seconds to recover after the fault ended: ${result.recovery} (predicted ${plan.recoverWithinS})`);
  console.log(`wrong answers (the system broke a promise): ${result.wrong}`);
  for (const text of result.broken.violations.slice(0, 3)) console.log(`  ${text}`);
  const { requests, p99 } = charts(result);
  writeFileSync(new URL("./chart.svg", import.meta.url), requests);
  writeFileSync(new URL("./chart-p99.svg", import.meta.url), p99);
  console.log("wrote chart.svg and chart-p99.svg");
}
```

Three definitions decide how you read the numbers. **The fault window** is the time between `startMs` and `endMs`, and the table compares the normal run with the broken run inside that window only. **Requests lost** is the difference between the number of unanswered requests in the broken run and in the normal run over the whole run, so a fault that does not lose anything shows 0. A request counts as lost if it was in the box that died, even if it arrived a few milliseconds before the kill: that is why the number can be larger than what the window shows. **Wrong answers** are promises broken, which is different from requests lost. A system that says "sorry, try later" is unavailable. A system that says "yes" and then loses the data is wrong. The second is much worse.

## Step 2: the test

The test file says what you promised. It checks that the plan has a start and an end inside the run, that the same seed gives the same result, that the system keeps its promises during the fault, and that it recovers within the time you predicted. The fourth test is the one that reads your prediction from `PLAN.recoverWithinS`: change your prediction after the run and it still has to be true.

```js
import test from "node:test";
import assert from "node:assert/strict";
import { SCENARIO } from "../choice.js";
import { SCENARIOS } from "../scenarios.js";
import { PLAN, eventsFor, recoverySeconds, runExperiment } from "./experiment.js";

test("the plan starts a fault and ends it, inside the run", () => {
  const events = eventsFor(PLAN);
  assert.equal(events.length, 2);
  assert.ok(events[0].atMs < events[1].atMs);
  assert.ok(events[0].atMs >= SCENARIOS[SCENARIO].measureFromMs, "start the fault after the warm-up");
  assert.ok(events[1].atMs <= SCENARIOS[SCENARIO].durationMs - 2_000, "end the fault at least 2 s before the traffic stops, so recovery is on the chart");
});

test("the same seed gives the same result", () => {
  const a = runExperiment({ seed: 1 });
  const b = runExperiment({ seed: 1 });
  assert.deepEqual(a.seconds, b.seconds);
});

test("the system keeps its promises during the fault", () => {
  const result = runExperiment({ seed: 1 });
  assert.equal(result.wrong, 0, result.broken.violations.slice(0, 3).join("; "));
});

test("it recovers within the time I predicted", () => {
  const result = runExperiment({ seed: 1 });
  assert.ok(result.recovery <= PLAN.recoverWithinS, `recovered after ${result.recovery} s, predicted ${PLAN.recoverWithinS} s`);
});

test("recoverySeconds counts from the end of the fault", () => {
  const seconds = Array.from({ length: 10 }, (_, s) => ({ second: s, ok: s < 3 || s > 6 ? 100 : 50, bad: s < 3 || s > 6 ? 0 : 50 }));
  assert.equal(recoverySeconds(seconds, 5_000), 2); // unhealthy until second 6, fault ended at second 5
  assert.equal(recoverySeconds(seconds.map((s) => ({ ...s, ok: 100, bad: 0 })), 5_000), 0);
});
```

## Step 3: run it

From the top folder of the repository, set `PLAN` for your fault and run `node challenges/challenge-18-capstone/part-2-break-it/experiment.js`. This is the real output for a stand-in core for system A with two app boxes that each keep a small memory cache, and one store, killing `app1` from second 12 to second 20. It is not your design:

```text
fault: kill app1 at 12 s, restart app1 at 20 s

during the fault window          normal run   with the fault
answered                           100.000%     100.000%
p99 ms                                 1.29            0.47

requests lost because of the fault: 3
seconds to recover after the fault ended: 0 (predicted 3)
wrong answers (the system broke a promise): 0
wrote chart.svg and chart-p99.svg
```

The balancer skips the dead box, so almost nothing was lost: 3 requests that were running inside `app1` when it died. The p99 even fell, because with one box fewer the queue was shorter. A design that hides a dead box well is a good sign. But a dead box is the easy fault. On the same stand-in, here are the other two, each run by editing `PLAN` and nothing else:

| Fault on the stand-in (second 12 to second 20) | Answered in the window | p99 in the window | Lost in total | Wrong answers |
|---|---|---|---|---|
| Kill `app1` | 100.000% | 0.47 ms | 3 | 0 |
| Slow `app1` by 10 | 68.34% | 132.37 ms | 20,310 | 0 |
| Cut the link between `app1` and the store | 95.57% | 1000 ms | 2,841 | 0 |

The slow box is the surprise. It lost 20,310 requests, almost seven thousand times more than the dead box. A dead box is easy to notice, and the balancer stopped sending it work. A slow box still answers, so the balancer keeps sending it half of the traffic, and that half waits in a long line. This is why chapters 16.4 and 16.5 teach time limits, load shedding and bulkheads, and why chapter 4.4 teaches health checks that look at more than "is it alive". It is also a reason to keep tail latency in mind: hedged requests, which send a second copy of a slow request to another box, are one known answer to a slow machine [S8]. If your design relies on a health check, ask what it would do with a box that is ten times slower.

For system C, here is a cut between the two regions on two different stand-ins. The first answers carts in the shopper's own region, keeps one counter per region and merges them later. The second keeps everything in one region.

| Cut eu and na, second 12 to second 20 | Answered in the window | p99 in the window | Lost in total | Wrong answers |
|---|---|---|---|---|
| Counters per region, stock split in two | 100.00% | 0.75 ms | 0 | 0 |
| Everything in one region | 49.71% | 1000 ms | 1,725 | 0 |

The first design never stopped answering, and the harness read all the carts back from both regions after the link healed and found nothing lost. It paid for that: half the stock of each item sits in each region, so an item can be sold out in one region while the other still has units. The second design is simple and exactly right, and half of the shoppers could do nothing for eight seconds. Neither is wrong. They are two answers to the question in chapter 19.6, and you must say which one you chose and what it costs.

## Step 4: read the chart

The script writes `chart.svg`, with three lines: requests answered per second, requests not answered per second, and the answered line of the normal run in grey. It also writes `chart-p99.svg`, the p99 of each second, where 1000 means that some requests got no answer at all. Open the files in your browser and look at them for a minute before you write anything.

Read a failure chart in four places. First, **the start**: how many seconds after the fault does the "not answered" line rise? A detection delay shows up here as a ramp, not a step. Second, **the middle**: is the damage flat, or does it grow as queues fill? A growing line means something is accumulating, such as a waiting line or a backlog. Third, **the end**: how quickly does the line fall after the fault ends? A fast fall means the system recovers by itself. A slow fall means it has a backlog to clear, or something that does not restart on its own. Fourth, **the gap to the grey line**: after recovery, is the system really back to the normal run?

Write one sentence under the chart for each of the four places, in `results.md`, with seconds and numbers. A chart with no sentences is a picture. A chart with four numbered sentences is evidence.

## Step 5: explain the gap

Under your sentences, write a short section called "Prediction and result". Put your prediction from the start of the chapter beside the measured values, in a small table: answered, p99, requests lost, seconds to recover. Then write three things: which number was furthest from your prediction, why, and what you would change in the design because of it, or why you would accept it. "I would accept it, because losing 3 requests in 80,000 costs less than the extra box" is a good answer if the numbers are there. "It was a bit different" is not.

If your system lost a promise, `wrong answers` is above 0 and the test fails. That is the experiment doing its job. Find the first wrong answer in the list that the script prints, work out which mechanism should have prevented it, fix it in the core, and run again. Keep the first result in `results.md` as "before" and the second as "after". A mentor values this loop more than a clean first run.

## The rubric for the experiment

This work feeds two rows of the rubric. For correctness under failure, a 2 means zero wrong answers during the fault, and a 3 means you also broke a mechanism on purpose and showed the promise failing. For evidence, a 2 means a written prediction, a chart and a result, and a 3 means you also explain the gap and test a second fault or ten times the load.

## When it does not work

**"no box called app1; your core has: ...".** The names in `PLAN.box` must match the keys of the `boxes` object that your core returns. Print them with `Object.keys(core.boxes)` or read the error.

**The fault changes nothing at all.** Your core may already hide it, which is a result. Check first that the fault ran: the first line of the output lists the events and their times. If the box is idle at that moment, move the fault into the busiest stretch.

**"recovered after N s, predicted M s".** Your system takes longer to recover than you thought. Look at the end of the chart: a backlog that drains slowly, a cache that is empty after a restart, or a box that never restarts. Fix the system, or change your explanation, but not the prediction.

**The numbers differ between two runs.** Something uses `Math.random` or the real clock. Use `net.random()` and `net.now`.

**A wrong answer appears only in the fault run.** That is the interesting case. The check names the request. Remember that a box restarted with an empty memory forgets what it never wrote anywhere else.
