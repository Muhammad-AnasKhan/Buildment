Dardasha must reach people who are not looking at the app. A message for a phone that is off needs a push alert. A login needs an SMS code. A weekly summary needs an email. This is the third deep dive of the design loop. It builds the service that sends all three, and it leans on earlier chapters: queues (15.2 and 15.5), idempotency (6.4 and 14.5) and rate limits (6.5).

## One front door, one queue per channel

<MermaidDiagram title="The notification service" chart={`flowchart LR
  A["Chat, accounts, jobs"] -->|"event"| API["Notification API"]
  API --> CK["Checks: choices, dedupe, limits"]
  CK --> QP["Push queue"]
  CK --> QE["Email queue"]
  CK --> QS["SMS queue"]
  QP --> WP["Push workers"]
  QE --> WE["Email workers"]
  QS --> WS["SMS workers"]
  WP --> PP["Push provider"]
  WE --> PE["Email provider"]
  WS --> PS["SMS provider"]
  QS -.->|"too many failures"| D["Dead letters"]
  PP -.->|"receipt"| T[("Status store")]
`} legend="Every producer sends an event to one front door. Checks run once, then the job goes to the queue of one channel. Workers call the outside providers. A job that keeps failing is parked in dead letters. Receipts flow back to a status store." />

Chat, accounts and scheduled jobs all send an event to one front door. The service checks the person's choices, drops copies and enforces limits. Then it puts a job on the queue of one channel: push, email or SMS. A queue for each channel means a slow SMS provider cannot hold up push alerts.

<GoDeeper title="Go deeper: channels, providers and priorities">

A push alert goes through the phone maker's own push service, such as Apple's APNs or Google's FCM. {/* source needed: how APNs and FCM are used by a server, device tokens and invalid-token replies; the course names them as real systems and does not describe their limits. */} The app gets a device token from the phone and sends it to Dardasha, which stores it in the DEVICE table of chapter 22.2. Email goes through an email provider, and SMS through an SMS provider. Dardasha does not run these networks. It buys access, and each provider has a rate limit and its own failures.

The course plan for the peak is 2,000 notifications a second in total: 1,500 push, 400 email and 100 SMS. These are course numbers. They are small next to the message rate, and they are limited by the providers more than by Dardasha.

The queues are a bulkhead (chapter 16.5): trouble in one channel stays in that channel. The same idea works within a channel. A marketing email to 5 million people must not delay a login code. So login codes and security alerts get their own queue and their own workers, with high priority. Chat alerts are next, and marketing is last and is allowed to wait.

How does an event get to the front door without being lost? The chat service decides "the recipient is offline" after it saves the message. If the event is lost, the person misses one push, and the catch-up of chapter 22.4 still delivers the message on the next open. For a login code, a lost event is a person who cannot log in. The accounts service therefore writes the event in the same database transaction as the login attempt and publishes it with the outbox pattern (chapter 14.4) [S79].

An accepted request is not a delivered notification. The providers report later, through a callback, whether the alert reached the phone or the email bounced. The status store keeps "accepted", "delivered" and "failed" apart, like the ticks in chapter 22.4.

</GoDeeper>

## Read the person's choices first

<InteractiveCanvas slug="sysdesign-m22-prefs-filter" />

Sami wrote to Layla while her phone was off. The notifier reads Layla's saved choices: push only. So no email and no SMS go out. The event says what happened. The preferences say how to tell this person. Quiet hours and muted chats are checked here too.

<GoDeeper title="Go deeper: what a preference record holds, and what must not be skipped">

A record has a switch for each kind of notification (new message, order update, security code, marketing) and each channel (push, email, SMS), plus quiet hours with the person's time zone, and a list of muted chats. Choices are read for every event, so they sit in a fast store with a short cache of a few minutes. A slightly old choice is fine for a chat alert. An unsubscribe is not: it must apply at once, and the law in many places requires it. Every marketing email carries an unsubscribe link, and that link writes the preference right away.

Some kinds ignore the choices. A login code or a password reset is not marketing, and a person who turned off every alert still needs it. The record marks such kinds as required.

If the preference store is down, the service must pick a safe default. For marketing it sends nothing, because one unwanted email is worse than a late one. For security codes it uses the person's last known channel, because a blocked login is worse than a code the person did not choose. The default depends on the harm of each mistake.

A person with no valid push token has a fallback chain: push, then email, with a limit so one event never uses all three. The chain is a policy that the product team owns. The service only runs it.

</GoDeeper>

## The same event twice sends one push

<InteractiveCanvas slug="sysdesign-m22-dedupe-key" />

The chat service sends event e91 twice, because its first call looked slow. The notifier tries to add a key for e91. The first add works, and a push is sent. The second finds the key already there and drops the copy. Queues deliver at least once, so copies are normal.

<GoDeeper title="Go deeper: the key, the order of steps and how long to keep it">

The key is made of the person, the event id and the channel, and it is written with "add only if absent" and a time limit. It is the same idea as chapter 22.4 for messages, with the idempotency key of Stripe's API as the public example [S80]. A standard queue delivers a message at least once, so a duplicate is a normal event, not a bug [S83]. The producer's retry is a second source of copies.

The order of steps matters. If the notifier writes the key and then crashes before calling the provider, the notification is lost, because the retry sees the key and stops. If it calls the provider first and crashes before writing the key, the retry sends a second time. Dardasha picks the second risk and keeps it small. It writes the key as "pending" with a short limit of about a minute, calls the provider, and then sets it to "sent". A retry that sees "pending" waits. A retry that finds the pending key expired sends again. So the guarantee is at least once, and the duplicates are rare (chapter 14.5).

How long should the key live? As long as a copy can still arrive. A day is common [S80]. A key for each notification is small: 2,000 a second for 24 hours is about 170 million keys, and at 50 bytes each about 8.6 GB.

For SMS a duplicate also costs money, which is one more reason to keep the key.

</GoDeeper>

## A busy provider: wait longer each time

<InteractiveCanvas slug="sysdesign-m22-retry-backoff" />

The SMS provider answers 503, which means busy. The worker waits 1 second and tries again, then waits 2 seconds. The third try works. Each wait has a random part, so workers do not retry in step. The job stays on the queue until the worker is done, so a crash loses nothing.

<GoDeeper title="Go deeper: what to retry, how long to wait, and dead letters">

Retry only what can change. A timeout, a 429 (too many requests) and a 5xx error may work later. A reply that the phone number is invalid, or that a push token is no longer registered, never will. Retrying it wastes time and money. The worker marks the number or the token as bad, so the next event skips it, and moves on. {/* source needed: how push providers report an unregistered device token; the course states the rule in general terms. */}

The wait grows with each failure and has a random part. A common rule is to sleep a random time between 0 and the smaller of a cap and the base times 2 to the power of the try number. This is full jitter [S90]. Without the random part, all workers that failed together retry together. A limit on the number of tries, and a budget of retries across the whole service, stop retries from adding load to a provider that is already struggling [S89, S91].

When a job runs out of tries, it goes to a dead letter queue [S85]. Nothing is lost: the job is parked with its error, an alarm fires if the count rises, and a person can fix the cause and send the jobs again. A dead letter queue that nobody watches is a trash can, so the alarm is part of the design.

The queue itself keeps a job safe while a worker handles it. In SQS the job is hidden for a visibility timeout, 30 seconds by default, and reappears if the worker dies before it finishes [S84]. This is the ack-last rule of chapter 15.4.

Last, a provider that stays down is not worth calling. A circuit breaker (chapter 16.5) stops calls for a short time, and a second SMS provider can take over.

</GoDeeper>

## Drag the outage, drop the stale

<InteractiveCanvas slug="sysdesign-m22-outage-play" />

Drag the outage length and choose when to throw old codes away. A 5 minute outage leaves 30,000 codes waiting, and the queue needs 10 minutes to empty. Most of those codes have expired. Throw away codes older than 2 minutes and the queue clears in 4 minutes, with 18,000 codes dropped on purpose.

<GoDeeper title="Go deeper: the model, and a time limit for every notification">

The model is a first-in, first-out queue. Codes arrive at 100 a second. During the outage nothing is sent. After it, workers send 150 a second, which is the provider's limit and a course number. The queue shrinks at 150 minus 100, which is 50 a second, so the time to catch up is the outage length times 100 divided by 50, or twice the outage. The picture also drops any code that has waited longer than the limit you choose, and a dropped code costs no sending time.

| Outage | Waiting at the end | Back to normal (keep all) | Longest wait |
|---|---|---|---|
| 1 minute | 6,000 | 2 minutes | 1 minute |
| 2 minutes | 12,000 | 4 minutes | 2 minutes |
| 5 minutes | 30,000 | 10 minutes | 5 minutes |
| 10 minutes | 60,000 | 20 minutes | 10 minutes |

With a limit of 2 minutes, a 5 minute outage drops 18,000 codes and is back to normal in 4 minutes. A 10 minute outage drops 48,000 and is back in 4 minutes. With a limit of 5 minutes, a 10 minute outage drops 30,000 and is back in 10 minutes.

Every notification carries a time limit that fits its meaning. A login code is useless after a few minutes, and a person who did not get one asks for a new code. An alert that a driver has arrived is useless after two minutes. A weekly summary can wait hours. An old code delivered late is worse than none: the person types it, it fails, and they lose trust. Dropping stale work is also what lets a queue recover. Without a limit, the queue spends its recovery sending messages nobody wants, and new codes wait behind them.

This is the metastable pattern of chapter 16.4 in small form: a trigger ends but a backlog keeps the system hurt [S94]. Two more helps: separate queues by priority, so a login code never waits behind a campaign, and a second provider or a higher limit, which raises the 150 and shortens the catch-up.

The model leaves out the retry load that a recovering provider also sees, and the codes that people request a second time while they wait, which makes the arrival rate higher than 100.

</GoDeeper>

## Forty messages become one alert

<InteractiveCanvas slug="sysdesign-m22-collapse-limit" />

A busy group posts 40 messages in a minute while Sami's phone is off. The notifier counts them and sends one alert: "40 new messages in Family". Sami's phone buzzes once, and the limit for each person holds. The count is kept for each person and each chat, for a short time.

<GoDeeper title="Go deeper: limits for people, and when to wait before sending">

A limit protects the person, as a rate limiter protects a server. Dardasha uses a token bucket for each person and each kind (chapter 6.5), for example a burst of 3 alerts and then 1 more every 20 seconds. API Gateway and Stripe both use token buckets [S30, S32]. An event over the limit is not dropped. It is folded into the next alert.

The count is a small counter with a time limit, kept for each person and chat. The text is built when the worker sends, not when the job is queued. So after a backlog, the alert says "40 new" from the latest count and not "1 new" 40 times.

Another saver is to wait. The notifier holds the first alert for about 10 seconds and checks if the person has read the chat in that time, for instance on another device. If so, it sends nothing. The price is a 10 second delay on every alert, which is fine for chat and not for a login code.

If the counter store is down, the service must choose. Failing open sends every alert and risks a flood. Failing closed sends none and misses real messages. A middle way is to fall back to a plain limit in memory on each worker, which is rough and keeps the flood small.

Muting is the same machinery with a longer memory: "do not alert for this chat until 8 am".

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "One notification API receives events from chat, accounts and jobs. It checks the person's preferences, drops duplicates with a key of person, event and channel written add-only-if-absent, applies a per-person token bucket, and puts a job on a queue for that channel. Workers call the push, email or SMS provider. Timeouts, 429s and 5xx errors retry with exponential backoff and full jitter; invalid numbers and dead tokens do not retry. After a few tries a job goes to a dead letter queue with an alarm. Login codes have their own queue and a short time limit, so an outage does not make them arrive late and useless. I collapse a busy chat into one alert."

**Expect:** "What if the SMS provider is down for 5 minutes?" **Answer:** "The queue holds the jobs. I drop codes older than their time limit when the provider returns, so the backlog clears in minutes, and I fail over to a second provider if the outage is long."

</GoDeeper>
