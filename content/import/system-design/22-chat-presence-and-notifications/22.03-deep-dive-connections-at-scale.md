Dardasha holds 3 million lines open. This is the first deep dive of the design loop. It follows one line: how a gateway accepts it, how the rest of the system finds it, what a restart does to it, and how to tell when it has quietly died. Chapter 3.5 explained why the line is a WebSocket. This chapter deals with its cost: every line is state.

## Every line is written in a registry

<InteractiveCanvas slug="sysdesign-m22-register-session" />

Sami's phone opens a line to Gateway 2. The gateway checks the login, then writes "Sami is on Gateway 2" in the registry. Now any server can find Sami with one lookup. The entry has a time limit, so it cannot outlive the gateway. The registry is a map from user to gateway, kept in memory.

<GoDeeper title="Go deeper: how a phone reaches a gateway, and what the entry holds">

A phone finds a gateway through a name, such as `chat.dardasha.example`. The name points at a layer 4 balancer (chapter 4.4). An NLB picks a target once per connection with a flow hash and keeps the line on that target [S15]. Least connections is a good picker here, because lines last for hours and an even spread of requests is not the goal (chapter 4.5). The gateway ends the TLS session itself and checks a short-lived token that the login service gave the app.

Each line costs memory. If a connection takes about 10 KB (a course number), then 50,000 lines take about 500 MB, which is comfortable. If the gateway keeps big buffers for each line, the same server runs out of memory first. The 100,000 maximum in the plan comes from that kind of limit (chapter 3.6).

The registry key is per device, because a user may have a phone and a tablet. A lookup for a user returns every device, and the chat service sends to each. The value is the gateway id. The key has a time to live of about a minute, and the gateway renews it. This is the lease pattern of chapter 12.9: an entry that is not renewed disappears, so a crashed gateway cannot leave stale entries behind for long [S54].

The alternative to a registry is to compute the gateway from the user id with consistent hashing (chapter 9.3). Nothing needs to be looked up, and the chat service can work out where a user should be. The cost is that the balancer must send each phone to its assigned gateway, a restart leaves that gateway's users with no other place to go, and adding a gateway moves a share of the users. A registry gives freedom to put a line anywhere, at the price of running it.

</GoDeeper>

## Ask the registry, then deliver or keep it

<InteractiveCanvas slug="sysdesign-m22-route-lookup" />

To deliver a message, the chat service asks the registry which gateway holds Sami. A hit means: send it to that gateway. A miss means Sami is offline, so the service keeps the message and sends a push alert. The answer can be a little old, so the gateway must confirm that the phone really got it.

<GoDeeper title="Go deeper: cost, a stale answer, and a lost registry">

The lookup is cheap. A query to an in-memory store takes about 0.5 ms [S3]. Dardasha needs about 42,000 of them a second at peak, one for each delivery (chapter 22.2), and a group message can fetch all its members in one multi-key read.

The answer can be wrong in both directions. The registry may say Sami is on Gateway 2 when his phone left a moment ago. The send then goes to a gateway with no live line, or to a dead one (the last beat of this chapter). Or the registry may say nothing while the phone is connecting. In both cases the message is already saved, so nothing is lost. The phone catches up when it connects (chapter 22.4).

Now lose the registry. Say its machine restarts empty. Every lookup misses, so the chat service treats every user as offline, saves every message and asks the notifier for a push alert. That could be a flood of alerts for people who are looking at the app. Two defences help. First, each gateway re-registers all its lines when it sees the registry come back, 50,000 writes each, spread over a few seconds. Second, the notifier limits alerts per person (chapter 22.5, and a token bucket as in chapter 6.5). A registry kept in two or three copies, or sharded by user id, shrinks the problem.

An alternative with no registry is a publish and subscribe channel for each user. A gateway subscribes to `user:sami` when Sami connects, and the chat service publishes to that channel. The channel system keeps the map for you. It holds 3 million subscriptions and moves the same problem into another system.

</GoDeeper>

## Restart a few gateways, spread the return

<InteractiveCanvas slug="sysdesign-m22-connections-play" />

Tap how many gateways restart at once, and drag how long the phones spread their return. One gateway with a 5 second spread is fine. Six at once need about 15 seconds. Fifteen at once cannot be absorbed at any spread, and thirty fill every other gateway to its limit. Restart a few gateways at a time.

<GoDeeper title="Go deeper: the model, and what else causes a storm">

The model has three course numbers. A gateway holds 50,000 lines in the plan and 100,000 at most. A gateway accepts 500 new connections a second, because each one costs a TLS handshake, a login check and a registry write. The fleet is 60 gateways. When k gateways restart, the phones that must move are 50,000 times k. They go to the 60 minus k gateways that are still up.

The arrival rate is the phones that must move divided by the spread in seconds, and no spread means everyone within about 1 second. The fleet can accept (60 minus k) times 500 a second. If the arrival rate is higher, the extra attempts fail and come back, and the return takes at least the phones divided by that capacity. The second limit is lines. Each healthy gateway ends with 50,000 plus 50,000 times k divided by (60 minus k) lines. For k = 30 that is exactly 100,000, the maximum.

| Gateways restarted | Phones to move | Fleet accepts per second | Spread of 5 s | Spread of 15 s | Spread of 30 s |
|---|---|---|---|---|---|
| 1 | 50,000 | 29,500 | 10,000 a second: fine | 3,333: fine | 1,667: fine |
| 6 | 300,000 | 27,000 | 60,000: too many | 20,000: fine | 10,000: fine |
| 15 | 750,000 | 22,500 | 150,000: too many | 50,000: too many | 25,000: too many |
| 30 | 1,500,000 | 15,000 | too many | too many | 50,000: too many |

So a deploy restarts one to three gateways at a time and waits until the fleet has its lines back before it starts the next ones.

A storm can start without a deploy. A network blip in a region cuts every line at once. A bug in the app can make every phone reconnect on a fixed timer, and phones that wait the same time arrive at the same moment (chapter 15.5). The fix is on the phone: wait longer after each failure and add a random part, such as a random wait between zero and the cap, with full jitter [S90]. A retry cap of about a minute keeps phones coming back without hammering the gateways [S89, S91].

The model leaves out the work that phones do after they connect, such as catching up on messages, which adds load for a few seconds more. Real servers also have limits other than connections a second, such as CPU and bandwidth.

</GoDeeper>

## Drain before you stop

<InteractiveCanvas slug="sysdesign-m22-drain-gateway" />

Before a restart, Gateway 2 tells its phones to reconnect after a random wait. They come back one by one through the balancer, to gateways with room. The gateway stops only when it holds no lines. A planned restart then looks like a trickle, not a wall.

<GoDeeper title="Go deeper: the steps of a drain, and the stale registry entry">

A drain has four steps. First the gateway stops accepting new lines: it fails its readiness check, so the balancer stops sending phones to it (the readiness idea of chapter 4.4 and [S20]). Second, it sends each line a "reconnect later" message with a random wait, for example from 0 to 30 seconds. Third, it closes lines that are still open after a time limit. Fourth, it exits when the count is zero or the limit is reached. In Kubernetes this runs in the pre-stop step and the termination grace period [S20].

Phones that cannot hear the message still recover. An unplanned crash drops all 50,000 lines without a word. The phones find out through a failed ping or a failed write, and the jittered backoff above spreads them out. A drain only makes the common case gentle.

There is a trap in the registry. Sami reconnects to Gateway 5, which writes `sami = gw 5`. A moment later Gateway 2 finishes closing its old line and deletes `sami`. The delete removes the new entry. The fix is the compare-and-set of chapter 7.5: a gateway deletes a key only if the value is still its own id. The same idea guards the renewal.

The cost of draining is time. A deploy of 60 gateways, three at a time and 30 seconds each, takes about 10 minutes. That is a fair price for dropping nobody, and the deploys are rare.

</GoDeeper>

## A dead line can look open

<InteractiveCanvas slug="sysdesign-m22-half-open" />

Sami's phone loses signal in a lift. It cannot say goodbye, so the gateway still thinks the line is open and writes the message to it. Only a ping with no pong shows the line is dead. A write is not proof of delivery. Only a reply from the phone is.

<GoDeeper title="Go deeper: pings, acks and limits on every line">

A connection can break without either side being told. The phone is in a lift, its battery dies, or a router in between drops the state. The gateway's operating system learns this only when a send fails, which can take minutes. {/* source needed: RFC 9293 on half-open connections, and RFC 6455 on WebSocket ping and pong frames. */} So the gateway needs its own check. It sends a ping on every line every few seconds, and a line that misses a pong for a set time is closed. The WebSocket protocol has ping and pong messages for this. A short interval finds dead lines fast and costs traffic. A long one is cheap and leaves the registry wrong for longer. This is the same trade-off as the failure detectors of chapter 12.8, where a short timeout gives false alarms.

The message path must not rely on the write. Each message carries its number. The phone sends back an ack for it, and the gateway reports "delivered" to the chat service only when the ack arrives. If no ack comes in a few seconds, the chat service treats the message as not delivered, keeps it, and sends a push alert. The message is already saved, so this costs a delay and never a loss.

Every line also needs limits, or one bad phone can hurt a gateway. A send buffer of a fixed size, for example 64 KB, closes a line whose phone reads too slowly instead of letting the buffer grow in memory (the backpressure idea of [S88]). A token bucket per user caps messages, for example a burst of 20 and then 2 a second (chapter 6.5). A separate limit on new connections stops a loop of retries from becoming an attack on the login check.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Each phone holds one WebSocket to one of about 60 gateways, 50,000 lines each. On connect the gateway writes user to gateway in a registry with a short time to live, and renews it. To deliver, the chat service looks that up and sends to the gateway. I count a message delivered only when the phone acks it, not when the gateway writes it. A miss means offline, so I keep the message and send a push. For deploys I drain a few gateways at a time, and phones reconnect with exponential backoff and full jitter, so a restart is a trickle."

**Expect:** "What if the registry loses its data?" **Answer:** "Lookups miss, so messages are saved and pushed, and gateways re-register their lines. I limit pushes per person so a miss does not turn into a flood."

</GoDeeper>
