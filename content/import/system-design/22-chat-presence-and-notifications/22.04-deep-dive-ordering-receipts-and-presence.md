This is the second deep dive of the design loop, and it has three parts: order, receipts and presence. The first two decide whether Dardasha's promises hold: the same order for everyone, and no message lost or doubled. The third decides what the "online" dot costs. Clocks and ordering are chapters 10.1 to 10.3, and queues and retries are chapters 15.4 and 15.5.

## Two senders, two phones, two different orders

<InteractiveCanvas slug="sysdesign-m22-order-clash" />

Dana says "yes" and Omar says "no" a moment later. Dana's message reaches Layla fast and Sami slowly. Layla sees "yes, then no". Sami sees "no, then yes". If each phone sorts by arrival time, the chat is not the same chat for everyone. Chapter 10.2 showed that sorting by clocks fails too.

<GoDeeper title="Go deeper: why arrival order and clocks both fail">

The two copies of a message travel over different paths. One gateway may be busy, or one phone may be on a slow network. Arrival order depends on all of that, so two phones can disagree. This is the problem of chapter 10.1 with chat messages in place of log lines.

A timestamp from the sender's phone is no better. Phone clocks are wrong by seconds, and a person can set theirs on purpose (chapter 10.2). A timestamp from the server clock is better, but two chat servers still disagree by a few milliseconds, and messages that arrive within that gap get ordered by luck (chapters 10.5 and 10.6).

What a chat needs is one order that every member sees. It does not need the true order of events, and it does not need an order across different chats. It needs one agreed order inside each conversation.

</GoDeeper>

## One counter per conversation sets the order

<InteractiveCanvas slug="sysdesign-m22-sequence-play" />

The chat service gives each message the next number in its conversation, in the order it arrives. Tap Send for Dana and for Omar, then drag the delay to Sami. Sorted by arrival, the phones can disagree. Sorted by number, they always agree, and a message that arrives early waits for the one before it.

<GoDeeper title="Go deeper: who counts, and the hold rule">

Each conversation lives in one store partition, and that partition has one leader (chapter 8.2). The leader gives out the next number in the same write that saves the message, so a number exists only for a message that was saved. Two senders cannot get the same number, because there is one counter and one writer. It is the same idea as a Kafka partition, where events with the same key go to one partition and are read in the order they were written [S81], and as a sequence number in a Kinesis record [S132]. If the leader fails, a new one is elected and continues from the last saved number (chapter 12.6).

A Lamport clock (chapter 10.3) also gives numbers that respect cause and effect, but it needs no single writer and so it leaves gaps and ties [S58]. A chat can afford a single writer for each conversation, so it gets simple whole numbers with no gaps: 1, 2, 3.

The phone follows the hold rule. It shows message n only after it has shown n minus 1. If message 6 arrives and the phone has 1 to 4, it holds 6 back and asks the service for 5. If 5 does not arrive in a second or two, the phone asks for everything after 4. This costs a short delay and gives every phone the same order.

The cost is a single writer for each conversation. A very busy chat is limited by that writer. A group of 500 at 20 messages a second is far below the limit of one partition (chapter 22.2). Order across two different chats is not promised, and no user needs it.

</GoDeeper>

## A retry must not make a copy

<InteractiveCanvas slug="sysdesign-m22-retry-same-id" />

Layla's phone sends a message with an id it made up, 7f3, and never hears back. After 2 seconds it sends the same message again. The service has seen 7f3, so it answers with the old number and saves nothing new. The phone cannot tell a lost request from a lost reply. The id makes a retry safe.

<GoDeeper title="Go deeper: the dedupe key, and how long to remember it">

The phone creates a client id for each new message, for example a random value. It reuses the same id on every retry of that message. The service stores the message under a unique key made of the conversation, the sender and the client id. A second save with the same key fails, and the service returns the number that is already there. This is the idempotency key of chapter 6.4, with Stripe's API as the public example [S80]. It is also the claim-first rule of that chapter: the key and the message are written in one atomic step, never as a check followed by a save.

How long must the service remember? As long as a copy of the request can still arrive (chapter 14.5). The phone retries for about a minute and then shows "failed, tap to retry", which reuses the same id. Add the time a request can spend stuck in a queue or a network. Stripe keeps its keys for at least 24 hours [S80]. SQS FIFO queues remove duplicates only inside a 5 minute window [S86]. Dardasha picks 24 hours. Storing 400 million ids a day at about 40 bytes each is about 16 GB, which is small.

If the memory is too short, a late retry is saved twice and the chat shows the message twice. With the right memory, at-least-once sending plus a dedupe key gives an effect that happens once (chapter 14.5).

</GoDeeper>

## Sent, delivered and read are three facts

<InteractiveCanvas slug="sysdesign-m22-three-ticks" />

The service tells Layla "saved": one tick. Sami's phone tells the service "received": two ticks. When Sami opens the chat, his phone says "read": blue ticks. Each fact comes from a different step and travels as its own small message. A receipt may be late, but it must never claim more than is true.

<GoDeeper title="Go deeper: a receipt is a cursor">

If every message produced its own delivered and read receipt, the load would grow quickly. At 14,000 messages a second, that is up to 28,000 extra small messages a second going back to senders. A receipt can instead be a cursor: "my phone has up to 41" or "I have read up to 41". One small update covers every earlier message in that chat. A phone sends a read cursor when the chat opens and again if more messages arrive while it is open. This is the same cursor table as in the data model of chapter 22.2.

In a one-to-one chat there are two cursors to compare. In a group of 500 the service keeps one cursor per member, and "read by 17" is a count of cursors that are at or above the message number. Showing the full list is a read of up to 500 rows, so most apps show it only when asked.

Some people do not want to share read receipts. A setting can stop the service from forwarding that cursor. The phone still keeps its own cursor, which it needs to catch up (next beat). Receipts also travel over the same lines as messages, so they follow the same registry lookup and the same ack rule.

</GoDeeper>

## A returning phone asks from its last number

<InteractiveCanvas slug="sysdesign-m22-offline-sync" />

Sami's phone was off while messages 4, 5 and 6 arrived. Dardasha saved them and sent a push alert. When the phone is back, it says "I have up to 3" and gets 4, 5 and 6. There is no special queue for each phone. The numbers already say what is missing.

<GoDeeper title="Go deeper: cursors, gaps, long absences and new devices">

Each device keeps a cursor for each conversation: the last number it holds. On reconnect it sends its cursors and the service answers with the messages after them, a page of about 100 at a time. It works the same for a phone that was off for a minute or a month, and for a phone with a slow network. The push alert only wakes the phone up. It is not the delivery, and losing one costs nothing, because the next time the app opens it asks again. The idea of asking for what comes "after" the last id you saw is the same as in chapter 3.5 and the position token of chapter 8.4.

The same rule catches gaps while the phone is online. If the phone holds 5 and a live message arrives with number 7, it asks for 6. Live delivery is only a fast path. The numbers are what make it correct.

After a long absence, the phone first asks which of its chats changed, using the chat list index (chapter 9.6), then pages through each one. A phone off for 3 days may have 200 changed chats, and the app shows the newest first and loads the rest as the user scrolls. Dardasha keeps messages for a year, so a new device can load history on demand. A tablet that was never on before starts with cursor 0 and loads only the pages the user opens.

The failure to watch is a crowd. After a regional network outage, thousands of phones come back together and each asks for a catch-up. They use the same backoff as in chapter 22.3 and the same limits on the service.

</GoDeeper>

## Online is a key that expires unless renewed

<InteractiveCanvas slug="sysdesign-m22-presence-beat" />

Sami's app sends a ping every 30 seconds. Each ping renews a 60 second key in the presence store. When the phone goes silent, nothing renews the key and it runs out. Layla then sees Sami as offline. There is no "goodbye" message that could be lost. Two missed pings mean offline.

<GoDeeper title="Go deeper: why two missed pings, and what online means">

This is the lease with a heartbeat of chapter 12.9: a key with a time to live that each heartbeat renews. A crash, a dead battery and a lift all look the same, because the heartbeats just stop [S54]. The time limit is set to two intervals so that one lost ping does not flip a person to offline. It is the trade-off of chapter 12.2: a short limit finds a dead phone fast and gives false alarms, and a long one is steady and slow. SWIM and phi accrual detectors follow the same idea, by suspecting before they declare a node dead [S72, S73].

"Last seen" is the time of the last ping. When the key expires, the service saves that time, so friends see "last seen 12:03". A person with a phone and a tablet is online if any device is.

On a phone, "online" means the app is open and its line is up. Phones suspend apps in the background, so a closed app cannot ping. It receives push alerts instead. A typing indicator is a different thing: it is sent over the live lines only, expires in a few seconds, and is never saved.

Presence is best effort. The requirement in chapter 22.1 allows it to be a minute late. Nobody is hurt by a green dot that is 60 seconds old.

</GoDeeper>

## Drag the ping gap, watch the cost

<InteractiveCanvas slug="sysdesign-m22-presence-play" />

Drag the gap between pings. At 30 seconds, 3 million phones send 100,000 pings a second, 7 times the message rate. At 60 seconds the load halves, but a friend who left shows online for up to two minutes. Then flip where a ping ends. If it stops at the gateway, the store sees only status changes.

<GoDeeper title="Go deeper: end the ping at the gateway">

The model: pings a second are connected phones divided by the gap in seconds, and a phone shows offline when two pings are missed, so it can show online for up to two gaps after it left. For 3 million phones: 5 seconds gives 600,000 pings a second and offline after 10 seconds; 15 seconds gives 200,000 and 30 seconds; 30 seconds gives 100,000 and 60 seconds; 60 seconds gives 50,000 and 120 seconds; 120 seconds gives 25,000 and 240 seconds.

Where a ping lands matters more than its gap. If every ping renews a key in the presence store, the store takes 100,000 writes a second at a 30 second gap. That is about 2 nodes of a 50,000 operations a second plan, for a green dot. If the ping ends at the gateway, which already holds the line, the cost moves to cheap memory. The gateway keeps the time of the last ping for each line. When two pings are missing, it writes one "offline" change. The store sees status changes only: about 3,125 a second at peak (15 million devices changing state about 6 times a day, a peak of 3 times the average).

The gateway must now be trusted. Its own entry in the registry is a lease of about 15 seconds, renewed every 5 seconds. If the gateway dies, its entry expires and all its 50,000 users show as offline after 15 seconds. This is cheaper than 100,000 writes a second, and it moves the failure to one clear place.

Pings also keep a line from being closed by routers that drop quiet connections. {/* source needed: typical idle timeouts of mobile networks and NAT devices; the course states only that some networks drop quiet connections. */} So a gap of two minutes is not free either.

</GoDeeper>

## Tell only the people who are looking

<InteractiveCanvas slug="sysdesign-m22-presence-subscribe" />

When Sami goes online, who needs to know? Only the people who have Sami's chat open. Layla opens it and becomes a watcher. Dana, who only has Sami in her contacts, is told nothing. When Layla leaves, the watch ends. Telling every contact would multiply the work by 500.

<GoDeeper title="Go deeper: the count, and the rules for watching">

Take 3,125 status changes a second at peak. If each change were sent to 500 contacts, that is about 1.56 million updates a second. If only the one or two people who have that chat open are told, it is about 6,000 a second. The first number is more than 100 times the message rate and for nothing anyone is looking at.

A watch is a short record, stored with a time limit, that says "Layla is looking at Sami". When Layla opens a chat, her phone asks for Sami's current status once and registers as a watcher. Later changes go only to watchers. The chat list shows a status only for the rows on screen, and the phone watches those rows. Large groups show no presence at all.

A status can be private. A setting such as "only my contacts see my last seen" is checked when the watch is registered.

If the presence store is down, the app hides the green dot. A missing dot is better than a wrong one, and messages do not depend on presence at all. That is the sign of a good split: presence is nice to have, and chat works without it.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Order matters inside a conversation only. Each conversation lives in one partition, and its leader gives each message the next number in the same write that saves it. Phones show messages in number order, hold a message back if there is a gap and ask for the missing one. Each message carries a client id, and a unique key on conversation, sender and client id makes a retry safe, remembered for 24 hours. Receipts are cursors, so 'read up to 41' costs one update. A returning phone sends its last number and gets what it missed. Presence is a key with a time limit that pings renew. Two missed pings means offline. I end the pings at the gateway and send only status changes to the store, and I send changes only to people who have that chat open."

**Expect:** "Why not use timestamps?" **Answer:** "Clocks disagree by milliseconds, and phone clocks by seconds. Two messages inside that gap get ordered by luck. One counter per conversation has no such gap."

</GoDeeper>
