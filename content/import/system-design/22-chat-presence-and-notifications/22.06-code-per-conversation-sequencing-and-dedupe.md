In chapter 22.4 you gave Dardasha two rules. The service numbers each message inside its conversation and recognises a retry by the client id. The phone shows messages in number order and asks for any number it is missing. Those two rules are the whole of the chat's promise about order and copies. In this chapter you write them, one object for the service and one for the phone.

Both are short, and both are easy to get slightly wrong. A numbering function that uses one counter for the whole service passes every test with one chat and gives the wrong numbers with two. A dedupe check that uses only the client id passes until two people happen to pick the same id. An inbox that shows a message as soon as it arrives passes every test where the network behaves, and shows a different order from everyone else the day it does not.

## What the tests do to your code

The tests go for the places where these two rules fail. For the log they use two conversations at once, a retry after other messages were saved, two senders with the same client id, two ids that look alike when joined (`"a"` with `"bc"` and `"ab"` with `"c"`), a memory that is too small, and a caller who changes what `since` returned. For the inbox they send messages out of order, twice, and with holes of different sizes. The last test saves 200 messages from two senders with retries, shuffles and repeats what the phone receives, and checks that the inbox shows each message once, in order.

Nothing is `async`, and nothing reads a clock or a random number. Each test gives the same answer every time. The message of a failing test tells you which rule you broke.

## The contract

**`createConversationLog({ dedupeLimit = 1000 } = {})`** returns a log with three methods. `dedupeLimit` is how many client ids it remembers for each conversation. It must be a positive integer, or the function throws a `RangeError`.

`append(conversationId, senderId, clientId, body)` saves a message and returns `{ seq, duplicate }`. All four arguments must be non-empty strings, or it throws a `TypeError`. Numbers start at 1 in every conversation and go up by one, and each conversation counts on its own. If this sender already saved this client id in this conversation, and the log still remembers it, nothing is saved: the result is the original number and `duplicate: true`. Another sender with the same client id is a different message. When more than `dedupeLimit` ids are remembered in a conversation, the oldest saved one is forgotten, and a retry of a forgotten id is saved as a new message.

`since(conversationId, afterSeq = 0, limit = Infinity)` returns the messages with a number greater than `afterSeq`, in number order, at most `limit` of them, each as `{ seq, senderId, clientId, body }`. An unknown conversation gives an empty array. The result is a copy: changing it must not change the log. `afterSeq` must be a non-negative integer and `limit` a positive integer or `Infinity`, or it throws a `RangeError`.

`lastSeq(conversationId)` returns the number of the newest message, or 0 for a conversation with none.

**`createInbox({ startAfter = 0 } = {})`** is the phone's side. `startAfter` is the last number the phone already shows, a non-negative integer, or it throws a `RangeError`. `receive(message)` takes an object with a `seq` and returns the array of messages that can now be shown, in order. A `seq` that is not a positive integer throws a `RangeError`. A message at or below the last shown number is old, so the result is an empty array. The next number is shown at once, followed by any held messages that now follow without a gap. A later number is held, and the result is empty. A held number that arrives again is not held twice.

`lastSeq()` returns the last number shown. `missing()` returns `null` when nothing is held, and otherwise `{ from, to }`: the first range of numbers to ask for, from the one after the last shown up to the one before the lowest held.

## A worked example by hand

First the log, with Dana and Omar in a chat called `family` and `dedupeLimit` 2.

| Call | Sender and client id | Result | Why |
|---|---|---|---|
| 1 | Dana, d1 | `{ seq: 1, duplicate: false }` | First message in `family` |
| 2 | Omar, o1 | `{ seq: 2, duplicate: false }` | Next number |
| 3 | Dana, d1 | `{ seq: 1, duplicate: true }` | A retry. Nothing is saved |
| 4 | Dana, d2 | `{ seq: 3, duplicate: false }` | New id. The memory now holds 3 ids, so the oldest (d1) is forgotten |
| 5 | Dana, d1 | `{ seq: 4, duplicate: false }` | d1 was forgotten, so this is saved again |

Call 5 is the failure that the memory limit teaches. In the real service the memory is 24 hours, so a retry comes in time. With a limit of 2 it does not, and the chat would show the message twice.

Now the inbox with `startAfter` 3. Message 6 arrives: it is later than 4, so it is held, the result is `[]`, and `missing()` is `{ from: 4, to: 5 }`. Message 5 arrives: held as well, and `missing()` is `{ from: 4, to: 4 }`. Message 4 arrives: it is next, so it is shown, and 5 and 6 follow it in the same call. The result is messages 4, 5 and 6, `lastSeq()` is 6, and `missing()` is `null`. A second copy of 5 now returns `[]`, because 5 is at or below the last shown number.

## Five ways this goes wrong

**One counter for everything.** If the log keeps one counter, the second chat starts at the number where the first stopped. Keep the messages and the key memory per conversation.

**Joining the key without a separator.** If you build the key as `senderId + clientId`, then `"a"` with `"bc"` and `"ab"` with `"c"` give the same text, and one of two different messages is dropped as a duplicate. Keep the two parts apart, for example with `JSON.stringify([senderId, clientId])`.

**Saving before you check.** If `append` pushes the message and then looks for a duplicate, a retry is saved and the number goes up. Check first, and save only if the key is new.

**Handing out your own data.** If `since` returns the stored objects, a caller who edits one changes the log. Return new objects.

**Showing a message early.** An inbox that shows any message it receives passes tests with a calm network. Compare the number with the last shown number and hold anything that is not next.

When a test fails, read its message first. Each names the input, what it expected and what your code returned.

  function createConversationLog({ dedupeLimit = 1000 } = {}) {
    if (!Number.isInteger(dedupeLimit) || dedupeLimit < 1) {
      throw new RangeError("dedupeLimit must be a positive integer");
    }
    const chats = new Map(); // conversationId -> { messages, seen }
    const chatOf = (conversationId) => {
      let chat = chats.get(conversationId);
      if (!chat) {
        chat = { messages: [], seen: new Map() };
        chats.set(conversationId, chat);
      }
      return chat;
    };
    const need = (value, name) => {
      if (typeof value !== "string" || value === "") {
        throw new TypeError(name + " must be a non-empty string");
      }
    };
    return {
      append(conversationId, senderId, clientId, body) {
        need(conversationId, "conversationId");
        need(senderId, "senderId");
        need(clientId, "clientId");
        need(body, "body");
        const chat = chatOf(conversationId);
        const key = JSON.stringify([senderId, clientId]);
        if (chat.seen.has(key)) {
          return { seq: chat.seen.get(key), duplicate: true };
        }
        const seq = chat.messages.length + 1;
        chat.messages.push({ seq, senderId, clientId, body });
        chat.seen.set(key, seq);
        if (chat.seen.size > dedupeLimit) {
          chat.seen.delete(chat.seen.keys().next().value);
        }
        return { seq, duplicate: false };
      },
      since(conversationId, afterSeq = 0, limit = Infinity) {
        if (!Number.isInteger(afterSeq) || afterSeq < 0) {
          throw new RangeError("afterSeq must be a non-negative integer");
        }
        if (limit !== Infinity && (!Number.isInteger(limit) || limit < 1)) {
          throw new RangeError("limit must be a positive integer or Infinity");
        }
        const chat = chats.get(conversationId);
        if (!chat) return [];
        const end = limit === Infinity ? undefined : afterSeq + limit;
        return chat.messages.slice(afterSeq, end).map((m) => ({ ...m }));
      },
      lastSeq(conversationId) {
        const chat = chats.get(conversationId);
        return chat ? chat.messages.length : 0;
      },
    };
  }

  function createInbox({ startAfter = 0 } = {}) {
    if (!Number.isInteger(startAfter) || startAfter < 0) {
      throw new RangeError("startAfter must be a non-negative integer");
    }
    let shown = startAfter;
    const held = new Map(); // seq -> message
    return {
      receive(message) {
        const seq = message && message.seq;
        if (!Number.isInteger(seq) || seq < 1) {
          throw new RangeError("message.seq must be a positive integer");
        }
        if (seq <= shown) return [];
        if (seq > shown + 1) {
          if (!held.has(seq)) held.set(seq, message);
          return [];
        }
        const ready = [message];
        shown = seq;
        while (held.has(shown + 1)) {
          shown += 1;
          ready.push(held.get(shown));
          held.delete(shown);
        }
        return ready;
      },
      lastSeq() {
        return shown;
      },
      missing() {
        if (held.size === 0) return null;
        const lowest = Math.min(...held.keys());
        return { from: shown + 1, to: lowest - 1 };
      },
    };

## Check your understanding before you submit

Run one more case in your head. Make a log with `dedupeLimit` 1000 and save, in order: Dana `d1` in `family`, Dana `d1` in `work`, Omar `d1` in `family`. The first is `{ seq: 1, duplicate: false }`. The second is `{ seq: 1, duplicate: false }` too, because `work` is a different conversation, even though the sender and the id match. The third is `{ seq: 2, duplicate: false }`, because Omar is a different sender. Then retry Dana's first message: `{ seq: 1, duplicate: true }`. `lastSeq("family")` is 2 and `lastSeq("work")` is 1.

Now the inbox with `startAfter` 0. Send numbers 2, 2, 1. The first call holds 2 and returns `[]`. The second call sees 2 already held and returns `[]`. The third call shows 1 and then releases the held 2, so it returns messages 1 and 2, and `lastSeq()` is 2. If your code returned 2 twice, you stored it twice.

The log in this chapter lives in one process. Chapter 22.2 put each conversation in one store partition with three copies, and the leader of that partition does the same job: one counter, one writer, and a unique key for the retry. The memory of ids, held in 24 hours of keys, is a table with an index. The ideas are the same.

## How to say it in an interview

**Say:** "I number messages per conversation, not globally. Each conversation lives in one partition, and its leader assigns the next number in the same write that saves the message. The phone sends a client id with every message. A unique key on conversation, sender and client id makes a retry return the first number and save nothing. I keep those keys for 24 hours, longer than any retry. The phone shows message n only after n minus 1, holds a later one back and asks for the missing range. That gives every device the same order without clocks."

**Expect:** "What if the leader fails in the middle of an append?" **Answer:** "The number only exists once the write is committed. The new leader continues from the last committed number. The phone's append was never acknowledged, so it retries with the same client id, and the dedupe key makes sure it is saved once."

## What this unlocks

Numbers per key, a key to recognise a retry, and a reader that waits for the next number are patterns that you will see again. They are the offsets of a log, the sequence numbers of a stream, and the cursor of a sync. Chapter 22.9 asks you to use these ideas on scenarios you have not seen, and the notification service of chapter 22.5 uses the same dedupe key in front of a queue.
