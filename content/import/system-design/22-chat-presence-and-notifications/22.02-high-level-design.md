## Phones hold a line open to a gateway

<MermaidDiagram title="The blocks of Dardasha" chart={`flowchart LR

  G <-->|"messages and acks"| C["Chat service"]

  N -.->|"push, email, SMS"| X["Outside providers"]
`} legend="Phones talk only to gateways. The chat service owns the rules. The store keeps messages, the registry knows which gateway holds which phone, and the notifier reaches phones that are off. Dotted arrows are the slower path." />

Phones talk only to gateways, over one open line each. A gateway holds lines, checks logins and passes messages on. The chat service has the rules: it numbers and saves each message and finds the recipients. The store keeps every message. The registry knows which gateway holds which phone. Chapter 3.5 explains why the line is a WebSocket.

<GoDeeper title="Go deeper: why gateways are separate from the chat service">

A gateway has state: its open lines. The chat service has none. It keeps nothing between two requests, so it can run as many copies as needed behind any balancer, and a copy can be replaced at any time (chapter 4.3). Gateways cannot be treated that way, because stopping one drops 50,000 phones.

Keeping them apart gives three gains. They scale on different numbers: gateways by open lines, the chat service by messages a second. They deploy on different schedules, because a new chat rule should never drop a million lines. And a bug in the rules cannot take the connections down with it.

The price is one more hop. Inside one region a round trip costs about 250 microseconds [S3], so the hop is cheap. The other price is two kinds of server to run and watch.

The alternative is one process that does both jobs. It is simpler and it is right for a small app, say under 10,000 users on a single server. Switch when one deploy drops lines you cannot afford to drop, or when lines and CPU need different server sizes.

Everything that is not live uses plain HTTPS: login, creating a group, and fetching a page of old messages. Only the live path needs a WebSocket.

</GoDeeper>

## Sent means saved, not delivered

<InteractiveCanvas slug="sysdesign-m22-send-path" />

Layla's message goes through her gateway to the chat service. The service gives it the next number in this conversation and saves it. Only then does it answer "ok no. 41", and Layla sees one tick. The tick is a promise: the message will not be lost. It does not say that Sami has it.

<GoDeeper title="Go deeper: what the save costs, and what a crash does">

The server steps are cheap. By the napkin numbers, a round trip inside a region is about 250 microseconds and a disk write with fsync is about 300 microseconds [S3]. The path has four short round trips and one write, so the servers add roughly 1 to 2 ms. The 200 ms target is spent almost entirely on the internet between the phone and the region. This is why Dardasha can afford to save before it answers.

The store keeps three copies of every conversation and answers the write once a majority of them have it (chapters 8.2 and 12.3). A tick therefore also survives the loss of one machine.

Now crash the service at each point. If it dies before the save, no answer comes back, and the phone sends the message again. If it dies after the save but before the answer, the phone also sends it again, and chapter 22.4 shows how the second copy is recognised. In both cases the worst result is a short delay. The rule that makes this work is to answer last, never first.

The alternative is to answer first and save later. It cuts a few milliseconds from the sender's wait and breaks the promise whenever the service crashes at the wrong moment. For a chat app that is the wrong trade.

</GoDeeper>

## Step through the design at peak

<InteractiveCanvas slug="sysdesign-m22-design-stepper" />

Step through the build. One server holding 3 million lines is 60 times its plan. Gateways fix that. Then the store: 14,000 writes a second is 5.6 times one node's plan. Splitting by conversation brings each partition under its plan. The registry and the notifier come last.

<GoDeeper title="Go deeper: the numbers behind each step">

The picture uses these course numbers. A gateway holds at most 100,000 lines and is planned at half, 50,000. A chat server finishes at most 4,000 messages a second and is planned at half, 2,000. A store node finishes at most 5,000 writes a second and is planned at half, 2,500, the same as in chapter 20.2. A registry node is an in-memory store that finishes at most 100,000 operations a second and is planned at half, 50,000. Planning at half keeps the wait short (chapter 2.5).

| Step | What changes | Load |
|---|---|---|
| 1. One box | Lines, rules and storage on one server | 3,000,000 / 50,000 = 60 times its plan |
| 2. Gateways and chat servers | 60 gateways, and 14,000 / 2,000 = 7 chat servers | The store takes 13,889 writes a second, 5.6 times one node's plan |
| 3. Split the store | By a hash of the conversation id into k partitions | k = 4: 3,472 each, 1.4 times plan. k = 6: 2,315 each, 93%. k = 8: 1,736 each, 69% |
| 4. A registry | A lookup for every recipient and a write for every status change | 41,667 + 3,125 = 44,792 operations a second: 90% of one node, 45% on each of two |
| 5. A queue and a notifier | Take the 10% of deliveries that find a phone off | About 4,200 jobs a second into the queue |

The 10% is an assumption, and so is the 3,125 writes a second: 15 million devices, each changing state about 6 times a day (app opened or closed, network changed), a peak 3 times the average. Each partition keeps three copies on other machines, so 8 partitions are 24 nodes. Storage is 44 TB over 8 partitions, 5.5 TB each. That fits on a disk but leaves little room, and a copy takes a long time to rebuild at that size (chapter 9.5). A team might choose 16 partitions for that reason alone.

Failure, step by step. A gateway dying drops its 50,000 lines (chapter 22.3). A chat server dying costs nothing, because the other six take over. A store partition losing its leader pauses writes for that partition's conversations until a new leader is elected (chapter 12.5), and senders just see no tick for a moment. The registry is the next chapter's subject.

</GoDeeper>

## Messages are keyed by conversation and number

A message is found by its conversation and its number, so its row has no id of its own. The store is split by a hash of the conversation id (chapter 9.2), which keeps a whole chat in one partition. That makes numbering and reading in order cheap. Each device also keeps a cursor: the last number it has.

<GoDeeper title="Go deeper: choosing the store, and a hot chat">

Two choices fit. A key-value or wide-column store, such as DynamoDB, hashes the partition key for you and keeps rows with the same key sorted by a second key. The partition key would be the conversation id and the sort key the number [S40]. The alternative is PostgreSQL, sharded by hand. It gives you SQL and a familiar tool, but you run the shards, the routing and the moves yourself. A team of six is a reason to prefer the managed store.

The main question the store answers is "give me messages after number N in this conversation, at most 100". With the key above that is one range read inside one partition. It never touches the other partitions.

A very busy chat is a hot partition. In DynamoDB, one partition is designed for up to 1,000 writes a second [S40]. A group of 500 people sending 20 messages a second is far below that. This is one reason Dardasha caps a group at 500. A chat with 100,000 members would need another design (see the end of the next beat).

The member list lives in the same kind of store, keyed by conversation. "Which chats am I in?" is a different question, so it needs a second index keyed by user (chapter 9.6), which may be a little late. That is acceptable for a chat list.

</GoDeeper>

## A group is one write, many sends

<InteractiveCanvas slug="sysdesign-m22-group-fanout" />

A group message is saved once. The cost that grows is sending it. The chat service looks up each member's gateway and sends one batch to each gateway. So 499 sends become about 60 messages between servers. Members who are offline get the message later by catching up (chapter 22.4).

<GoDeeper title="Go deeper: fan-out, tail latency and very large groups">

Sending one message to many recipients is fan-out (chapter 15.7). Dardasha does fan-out on write: the work is done when the message is sent, so reading is cheap. A group of 500 means 499 deliveries, and the 3 recipients per message in the estimate is the average of all chats.

The sender must not wait for all deliveries. If each of 500 deliveries is slow 1% of the time, waiting for all of them makes 1 - 0.99^500, or 99.3%, of messages slow. The tail at scale paper gives the same effect for 100 servers, 63% [S8]. So the sender's tick comes after the save, and deliveries run on their own.

Batching by gateway cuts the number of internal messages. It needs one registry lookup per member, which can be a single multi-key read.

For a chat with 100,000 members, or a broadcast channel, writing a delivery for everyone is too much. The answer is the opposite choice, fan-out on read: members pull the new messages when they open the channel. Module 21 compares the two for a news feed, and the same trade-off applies here.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Phones keep a WebSocket to a gateway tier of about 60 servers, 50,000 lines each. Gateways are stateful and do nothing but hold lines. A stateless chat service numbers each message per conversation, saves it, and only then acknowledges the sender. The store is split by a hash of the conversation id, 8 partitions with 3 copies. A registry maps user to gateway. For a group I save once and send one batch per gateway. If the recipient is offline, a notifier sends a push and the phone catches up when it reconnects."

**Expect:** "Why not store the message after delivering it?" **Answer:** "Then a crash loses a message the sender thinks was sent. Saving first costs about a millisecond. I would answer last."

</GoDeeper>
