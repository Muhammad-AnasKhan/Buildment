Physical clocks are close but never exact. So give up on real time for a moment. Souq's three servers, A, B and C, can still count what they do and tell each other the count.

## A cause is a path of messages

<MermaidDiagram title="Events on three nodes" chart={`flowchart LR
  subgraph NA["Node A"]
    a1 --> a2
  end
  subgraph NB["Node B"]
    b1 --> b2
  end
  subgraph NC["Node C"]
    c1 --> c2
  end
  a2 -->|"message"| b1
  b2 -->|"message"| c2
`} legend="Arrows are either a node's own order or a message. If a path of arrows leads from one event to another, the first can have caused the second." />

An event is something one node does, such as saving a note or sending a reply. Event a happened before event b if a path of arrows leads from a to b. Here a1 happened before c2. But c1 has no path to or from a1, so those two are concurrent: neither could have caused the other.

<GoDeeper title="Go deeper: Lamport's three rules">

Leslie Lamport defined "happened before" in 1978 using no clock at all [S58]. Event a happened before event b, written a to b, in three cases. First, a and b are on the same node and a comes first. Second, a is the sending of a message and b is the receiving of that same message. Third, there is an event c such that a happened before c and c happened before b, so a chain of the first two cases counts.

If neither a happened before b nor b happened before a, the two events are concurrent. Concurrent does not mean "at the same moment". It means that no chain of messages links them, so nothing one event did could have reached the other. The word will return in every chapter that follows.

This is a different idea of order from the clock on the wall. It says nothing about how many milliseconds passed. It only records what could have influenced what.

</GoDeeper>

## One number per node, passed along

<InteractiveCanvas slug="sysdesign-m10-lamport-rule" />

Each node keeps one counter. Every event adds 1. A message carries the sender's counter as its stamp. The receiver sets its counter to the larger of its own and the stamp, then adds 1. B was at 5, so it goes to 6. C was at 0, so it jumps to 8. A receive always lands after its send.

<GoDeeper title="Go deeper: the rules and the promise">

Lamport wrote the two rules as IR1 and IR2 [S58]. IR1: a node adds to its counter between any two events. IR2: a message carries the sender's counter, and the receiver moves its own counter past both its old value and the stamp. In words that is all this chapter needs:

```js
// On every event, including a send:  counter = counter + 1
// On a receive:                      counter = Math.max(counter, stamp) + 1
```

These rules give the Clock Condition: if a happened before b, then the counter of a is smaller than the counter of b [S58]. The reason is short. Along any chain of arrows, each step either adds 1 on the same node or goes through a send and a receive, and a receive lands past its send. So every step makes the number bigger, and the end of a chain is bigger than its start.

The cost is small: one whole number on each message, and no extra messages. The counter only moves forward, so it needs no sync with anyone.

A worked example with a receiver that is already ahead of the sender:

| Step | Node | What happens | Counter |
|---|---|---|---|
| 1 | B | five events of its own | 5 |
| 2 | A | one event, then a send | 2, stamp 2 |
| 3 | B | receives stamp 2 | max(5, 2) + 1 = 6 |
| 4 | B | sends to C | 7, stamp 7 |
| 5 | C | receives stamp 7 | max(0, 7) + 1 = 8 |

Try one yourself: A is at 10 and receives stamp 4, then sends. What stamp does the message carry? The receive gives max(10, 4) + 1 = 11, and the send adds 1 more, so the stamp is 12.

</GoDeeper>

## Predict each counter before it appears

<InteractiveCanvas slug="sysdesign-m10-lamport-play" />

Tap a node to give it an event, or tap a node and then another to send a message between them. Before the new counter appears, tap your guess. The picture then shows the larger of the two numbers and the plus 1. Try a receiver far behind the sender, and one far ahead. Notice that no counter ever goes down.

<GoDeeper title="Go deeper: what to look for">

Three cases are worth trying. A receiver far behind the sender jumps forward by a lot, as C did in the last picture. A receiver far ahead of the sender goes up by exactly 1, because the stamp is smaller than its own counter. A receiver exactly level with the stamp also goes up by 1, since the stamp is not bigger. Together these cases are the whole rule.

Look at the numbers on nodes that never talk to each other. Their counters move at their own speed. A node that is busy reaches 50 while a quiet node is still at 3. The numbers on different nodes only line up where a message links them. That fact is the subject of the next beat.

</GoDeeper>

## A smaller number proves nothing

<InteractiveCanvas slug="sysdesign-m10-lamport-no-cause" />

A and C edit the same note and never exchange a message. A's counter is 5 and C's is 3. It looks as if C went first. It did not. The rule works in one direction only. A cause always has the smaller number, but a smaller number is not always a cause.

<GoDeeper title="Go deeper: what goes wrong in practice">

Lamport's paper states the limit directly: the Clock Condition holds one way, and the other way does not hold [S58]. A Lamport clock cannot tell "a came before b" from "a and b are concurrent". Both can give a smaller number to a.

This matters when two writes meet. A rule such as last write wins keeps the write with the bigger stamp and throws the other away. If the two writes were concurrent, the rule silently drops one of them, and nothing says that anything was lost. In a 2013 Jepsen test of Cassandra, which settles conflicts by last write wins on timestamps, about 28% of acknowledged writes were lost [S76]. Those were wall-clock timestamps, not Lamport stamps, but a Lamport stamp has the same blind spot: it picks a winner without knowing the writes were concurrent.

To know whether two events are concurrent you need more than one number. Chapter 10.4 gives each node a number for every node, and that is enough.

</GoDeeper>

## Sort by number, then node name

<InteractiveCanvas slug="sysdesign-m10-lamport-sort" />

Two events can still get the same number, like A4 and C4. Break the tie with the node name, and every server sorts the same events into the same list, whatever order they arrive in. Everyone agrees on this order. It is not the true order of concurrent events. It is just one order they all share.

<GoDeeper title="Go deeper: where an agreed order is used">

A shared order is what many systems need before they can do anything else. Lamport used it in his paper to build a way for nodes to take turns on a shared resource [S58]. A replicated log needs every copy to apply the same entries in the same order. Raft, a consensus algorithm you meet in module 12, uses a number called a term that only moves forward and that nodes copy from the messages they get, so it acts as a logical clock [S68].

The tie-break by node name looks arbitrary because it is. What matters is that every node uses the same rule. If A4 and C4 are concurrent, putting A4 first is as good as putting C4 first, as long as nobody disagrees.

Two limits remain. The stamps have no relation to real time, so you cannot ask for "everything from noon yesterday". And the order of concurrent events is invented. Chapter 10.4 fixes the second limit, and chapter 10.5 fixes the first.

</GoDeeper>

<GoDeeper title="Sources">

Lamport, "Time, Clocks, and the Ordering of Events in a Distributed System", Communications of the ACM, July 1978 [S58], for the happened-before relation, the rules IR1 and IR2, the Clock Condition, and the fact that the converse does not hold. Kingsbury, "Call Me Maybe: Cassandra" (2013) [S76], for the lost writes under last write wins. The Raft paper [S68], for terms as a logical clock. The Souq servers and the numbers in the pictures are course examples.

</GoDeeper>
