Lamport and vector clocks know nothing about real time. Souq's support team asks for "every order change between 2 and 3 pm", and a counter cannot answer that. Plain wall-clock stamps can answer it, but they break cause and effect. Can one stamp do both?

## Wall time alone stamps the effect first

<InteractiveCanvas slug="sysdesign-m10-wall-breaks-cause" />

Node A sends an update at its time 100. The trip takes 10 ms. Node B's clock is 40 ms behind, so it reads 70 when the update arrives and stamps the receive 70. The effect gets an earlier stamp than its cause. Wall-clock stamps keep cause and effect only if the clocks agree to better than the trip time.

<GoDeeper title="Go deeper: why the trip time is the yardstick">

A message trip inside one region takes about 0.25 ms in current measurements [S3]. Clocks that were synced a while ago can differ by several milliseconds, as chapter 10.2 showed. So the clock gap is usually many times bigger than the trip, and the reversal in the picture is not a rare accident. It happens whenever a message crosses between two nodes whose clocks differ by more than the trip.

This is the opening problem of the module again, in its simplest form: one message, two clocks, an effect stamped before its cause. Lamport clocks fix it by ignoring real time. A hybrid clock fixes it and keeps real time.

</GoDeeper>

## The hybrid clock keeps the later time

<InteractiveCanvas slug="sysdesign-m10-hlc-rule" />

A hybrid stamp has two parts: a time and a counter. B gets (100, 0) while its own clock reads 70. It keeps the larger time, 100, and adds 1 to the counter, so the receive is stamped (100, 1). Compare the time part first, then the counter. (100, 1) is after (100, 0), so the effect is after its cause.

<GoDeeper title="Go deeper: what the two parts mean">

Kulkarni and colleagues described the hybrid logical clock (HLC) in 2014 [S59]. Each node keeps a pair (l, c). The time part l is the biggest wall-clock time the node has seen, from its own clock or from any message. The counter c counts events that share that same l.

For a local event or a send, the node reads its clock. If the clock is past l, then l becomes the clock and c restarts at 0. If not, l stays and c goes up by 1. For a receive, l becomes the biggest of the node's own l, the message's l and the clock. The counter is then set so that the new pair is bigger than both the old pair and the message's pair.

The promise is the same as Lamport's: if event a happened before event b, then the stamp of a is smaller than the stamp of b [S59]. Stamps are compared as pairs, time first. The pair also fits in a 64-bit number, the size of an NTP timestamp, and the design tolerates the clock jumps that NTP sometimes makes [S59].

</GoDeeper>

## The receive rule in one picture

<MermaidDiagram title="The hybrid clock receive rule" chart={`flowchart TD
  M["Message arrives with (lm, cm). Node has (l, c) and a clock reading pt."] --> N["New time = the biggest of l, lm and pt"]
  N --> Q{"Where did the new time come from?"}
  Q -->|"the clock alone"| Z["counter = 0"]
  Q -->|"the node's own l"| A["counter = c + 1"]
  Q -->|"the message's lm"| B["counter = cm + 1"]
  Q -->|"own l and lm tie"| T["counter = max(c, cm) + 1"]
`} legend="If the clock is the biggest, the counter restarts. Otherwise it counts on from the biggest counter among the times that tie." />

On a receive, take the biggest of three times: the node's own l, the message's l, and the clock now. Then set the counter. If the clock alone is biggest, the counter restarts at 0. Otherwise it counts on from the biggest counter among the tied times, plus 1. Each case makes the new stamp bigger than every stamp the node has seen.

<GoDeeper title="Go deeper: all four cases, and who uses this">

Take the four cases one at a time. Only the clock is biggest: the node's time moved past everything it knew, so there is nothing to tie with and the counter restarts at 0. The node's own l is biggest, alone or tied with the clock: the node was already ahead of the message, so it counts one more event at the same l. Only the message's l is biggest: the node adopts the message's time and counts on from the message's counter. Both l values tie for biggest: the counter must beat both counters, so it takes the larger one and adds 1.

A local event or a send follows the same logic with no message: the clock is either past l, which restarts the counter, or not, which adds 1 to it.

Some databases use hybrid logical clocks to stamp their data, for example CockroachDB. Because the time part stays near wall time, a stamp can answer "what changed between 2 and 3 pm" and still put each effect after its cause.

## The counter climbs until the clock catches up

<InteractiveCanvas slug="sysdesign-m10-hlc-catch-up" />

After the receive, B is at (100, 1) but its clock reads 70. Its next events, at clock 80 and 92, get (100, 2) and (100, 3). The time part holds at 100 and the counter counts. At clock 105 the clock passes 100, so the stamp follows the clock and the counter restarts: (105, 0).

<GoDeeper title="Go deeper: how far ahead the stamp can run">

While a node's clock is behind, its time part is ahead of the clock. The paper shows that the time part never runs ahead of real time by more than the largest gap between any two clocks in the system, and that the counter stays small [S59]. Here the gap is 40 ms, so l can be at most about 40 ms ahead of B's clock. A counter of 3 is typical because the clock soon catches up.

{/* source needed: the bounds on l minus the clock and on the counter are theorems in S59 (Kulkarni et al. 2014); the dossier lists only the headline properties. Check the exact statements before publishing. */}

That bound only holds if every clock is within the stated gap. If one node's clock jumps a day ahead by mistake, every node that hears from it takes its time as the biggest, and their stamps follow it a day ahead. Systems that use hybrid clocks therefore set a limit and reject or flag a message whose time is too far ahead of the node's own clock. That limit is a design choice, not part of the basic rule.

</GoDeeper>

## Skew the clocks and watch the stamps

<InteractiveCanvas slug="sysdesign-m10-hlc-skewed" />

Three nodes each have their own clock. Drag a node's clock ahead or behind, then tap send between two nodes. Watch the stamp each receive gets. Put B's clock far behind A's and see how long the counter has to climb. Check that every receive is after its send.

<GoDeeper title="Go deeper: what a hybrid clock still cannot do">

A hybrid clock orders events that are linked by messages. If a receive follows a send, its stamp is bigger. Two events with no message between them get stamps that follow the clocks, and the clocks can be wrong by milliseconds. So (100, 0) on one node and (101, 0) on another say nothing about which event came first if no chain of messages joins them.

An application can add its own links. The client can carry the last stamp it received into its next request, much like the position token in chapter 8.4, and the server can raise its own stamp to match. That orders every action that one client does, even across servers. A person who switches from a laptop to a phone loses that link, and then only a bound on the clock error can help. That is the subject of chapter 10.6.

Sources: Kulkarni et al., "Logical Physical Clocks and Consistent Snapshots in Globally Distributed Databases" (2014) [S59], for the rules, the promise, the 64-bit fit and NTP tolerance. The latency table in the napkin-math reference [S3], for the round trip within a region. Souq and its numbers are a course example.

</GoDeeper>
