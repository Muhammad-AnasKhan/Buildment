Every order, message and photo in Souq needs an ID, and the IDs must never clash. Many servers make them at the same time. IDs also like to carry a timestamp, so every clock problem in this module comes back here. A wrong choice gives a bottleneck, a slow index, or IDs that repeat. This chapter compares four ways to make IDs, shows the bits inside two of them, and ends with a clock that goes backwards.

## One counter: simple, and one point of failure

<InteractiveCanvas slug="sysdesign-m10-id-counter" />

A database counter gives IDs 41, 42, 43: unique and in order. But every ID is a trip to one machine, and when that machine is down nobody can make an ID. Many servers, or many regions, all depend on that one counter.

<GoDeeper title="Go deeper: auto-increment and its repairs">

An auto-increment column or a database sequence is the right answer for a single database. It is compact, it sorts, and the database does the work. The trouble starts when many app servers each need an ID for every insert. Each ID costs a round trip to the one machine that holds the counter, and that machine is a single point of failure.

One repair is to hand each app server a block of numbers, say 1,000 at a time, and let it use the block without asking again. That cuts the trips, but IDs from different servers no longer arrive in order, and a crashed server wastes the rest of its block. Another trouble comes with sharding (module 9): if every shard keeps its own counter, two shards issue the same ID. A counter also leaks information. An ID of 1,204,331 tells a competitor how many orders you have had.

None of this makes counters wrong. It means the counter must be one of the things that scale-out removes.

</GoDeeper>

## Random IDs: no talking, no order

<InteractiveCanvas slug="sysdesign-m10-id-random" />

A version 4 UUID is 128 bits of which 122 are random. Each server makes IDs alone, and a clash is not a practical risk. But the IDs have no order. New rows land at random places in a sorted index, so every insert touches a different part of the index.

<GoDeeper title="Go deeper: why random keys hurt a B-tree">

UUID version 4 is defined in RFC 9562, the 2024 standard for UUIDs, and 122 of its 128 bits are random [S66]. With that many random bits, two servers making IDs without talking will, in practice, never meet the same one. That is its strength: nothing to coordinate, nothing to configure. Random IDs are also hard to guess, which is useful for a link that anyone could try to open.

The weakness shows up in the database. Most databases keep a primary key in a B-tree, a sorted structure stored in pages. With an increasing key, new rows go to the last page, which is warm in memory. With a random key, each new row goes to a random page, and on a large table most of those pages are not in memory. RFC 9562 gives this as a reason for time-ordered UUIDs: they have better index locality than random inserts [S66].

Size is the smaller cost: a UUID is 16 bytes, twice a 64-bit number, and it appears again in every index that points at the row.

</GoDeeper>

## Time first, then who, then a count

<MermaidDiagram title="Two layouts that put time first" chart={`flowchart LR

Both layouts put the time in the first bits, so IDs sort by time. A Snowflake ID also holds the machine and a count, so two machines never clash and no message passes between them. A UUIDv7 fills the rest with random bits, so it needs no machine number at all.

<GoDeeper title="Go deeper: the arithmetic of the bits">

Twitter's Snowflake gave each ID a 41-bit time in milliseconds counted from a chosen start, a 10-bit machine number and a 12-bit count [S65]. Add the unused first bit and the total is 64, which fits in a normal integer column. IDs from different machines are sorted within about a second of each other, not exactly [S65].

| Field | Bits | What it allows |
|---|---|---|
| Time | 41 | 2 to the power 41 ms, about 69.7 years |
| Machine | 10 | 1,024 machines |
| Count | 12 | 4,096 IDs per millisecond per machine |

If one machine needs more than 4,096 IDs inside a single millisecond, it waits for the next millisecond and starts the count again. Per machine that is 4,096 times 1,000, about 4.1 million IDs a second. For 1,024 machines it is about 4.2 billion a second. The start is a chosen date, not 1970: counted from 1970 the 41 bits would run out around 2039.

UUIDv7 puts 48 bits of Unix time in milliseconds first, which lasts about 8,900 years, then the version and variant bits, then random bits [S66]. RFC 9562 says that implementations should prefer UUIDv7 over the older time-based versions 1 and 6 where they can [S66]. UUIDv7 needs no machine number, so it needs no coordination between servers. The cost is size, 16 bytes against 8, and a clash is only very unlikely, not impossible.

The Snowflake repository was archived on 18 September 2021, but its layout is copied widely [S65].

</GoDeeper>

## Change the bits, then break the clock

<InteractiveCanvas slug="sysdesign-m10-snowflake-bits" />

Drag to move bits between the machine number and the count. The rest go to time. Watch the number of machines, IDs per millisecond and years of life change. Then step the clock back and see what each handling choice does: a duplicate, a wait, or an error.

<GoDeeper title="Go deeper: bits are a budget">

The 63 usable bits are a budget. Spend one more on the machine number and you double the machines, but you must take that bit from the count or from the time. Take it from the time and the layout lasts half as long: 40 bits of time last about 35 years. Take it from the count and each machine can make only 2,048 IDs per millisecond. The right split depends on how many machines you will have, how fast one makes IDs, and how long the system must run.

The machine number is the one place where a Snowflake-style generator needs coordination. If two servers get the same machine number, their IDs clash whenever both issue one in the same millisecond with the same count. The numbers are usually assigned when a server is deployed, from a config store or by the orchestrator. A mistake here causes duplicates that no clock can prevent.

</GoDeeper>

## A clock stepped back repeats an ID

<InteractiveCanvas slug="sysdesign-m10-id-rollback" />

Worker 7 made ID 996-7-0 when its clock read 996. Later the clock reads 1000, then is stepped back to 996. Trusting the clock, the worker makes 996-7-0 again, and the table refuses the duplicate. IDs stay unique only if the time inside them never goes back.

<GoDeeper title="Go deeper: three ways to survive a step back">

Remember the last time used, and compare. If the clock now is before that time, the generator has three choices.

| Choice | What it does | What it costs |
|---|---|---|
| Refuse | Throws an error until the clock passes the last time | The caller sees failures and must retry |
| Wait | Sleeps until the clock passes the last time | Delay for a short step; a long step is a long stall |
| Keep going | Uses the last time and keeps counting | IDs run ahead of the clock until it catches up |

A small step of a few milliseconds is best handled by waiting. A large step, a minute or more, should refuse and raise an alarm, because it usually means something is wrong with the host. Keeping going is the same trick as the hybrid logical clock in chapter 10.5: the time part holds still and the count carries on. It never fails a caller, but if the count runs out inside one held millisecond, the generator must borrow the next millisecond, so IDs run further ahead.

A restart is also a step back, in a way. A worker that crashes and comes back forgets its last time. It must read the last time from storage, or wait for a safe interval, before it issues IDs. Twitter's Snowflake relies on NTP and guards against clocks going backwards [S65]; the repository shows one way to do it. You build the three choices yourself in challenge 9.

Sources: the Snowflake repository (archived 2021-09-18) [S65], for the layout, the sorting within about a second, NTP and the guard. RFC 9562, May 2024 [S66], for UUID version 4, UUIDv7 and the index locality. The comparisons of counters, blocks and bit budgets are course reasoning, not from a source.

</GoDeeper>
