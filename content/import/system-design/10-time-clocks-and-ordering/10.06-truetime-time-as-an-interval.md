Server A stamps a write 12:00:00.000 and server B stamps another 12:00:00.001, but each clock may be up to 7 ms wrong. Which write really came first?

## Two writes, 1 ms apart

<InteractiveCanvas slug="sysdesign-two-clocks" />

Two servers, two clocks, two writes. Server A stamps its write .000 and server B stamps its write .001. Read as plain numbers, A came first by 1 ms. But in 10.2 you saw that every clock drifts, and NTP only pulls it back to roughly the right time. So A came first. Or did it?

<GoDeeper title="Go deeper: what the earlier clocks miss">

You already have three tools from this module. Lamport clocks (10.3) give an order that respects cause and effect. But they only see events linked by messages, and their numbers have nothing to do with real time. Vector clocks (10.4) tell "happened before" from "concurrent", but they also only see messages. Hybrid logical clocks (10.5) stay close to wall time and still respect cause and effect, again by passing timestamps along with messages.

All three fail when two events are linked outside the system. A person sees "done" on one server, then clicks something that goes to another server. No message passed between the servers. If the app carried a timestamp from the first reply into the second request, a hybrid clock could order them. If the person switched from a laptop to a phone, there is nothing to carry. The rest of this chapter is about that case.

</GoDeeper>

## Every clock is a little wrong

<InteractiveCanvas slug="sysdesign-clock-band" />

The line is the real time. The dot is what the clock shows, and the two drift apart. An honest clock does not hide this. It says "now is somewhere in this band". Half the width of the band is called epsilon. Drag sideways to change it: a smaller epsilon means a narrower band and less doubt.

<GoDeeper title="Go deeper: how Google keeps epsilon small">

Google's TrueTime is an interface with three calls (Spanner paper, section 3, Table 1). `TT.now()` returns an interval, `[earliest, latest]`, and guarantees that the true time of the call is inside it. `TT.after(t)` returns true if time `t` has definitely passed. `TT.before(t)` returns true if `t` has definitely not arrived yet. Epsilon is half the width of the interval.

TrueTime keeps epsilon small with hardware. Every data centre has a set of time master machines. Most have GPS receivers with their own antennas. The rest, which the paper calls Armageddon masters, have atomic clocks. GPS and atomic clocks fail in different ways, so using both protects against a fault in either.

Every machine also runs a daemon, a small background program, that polls several masters. It throws out any master whose time disagrees with the others, and syncs the local clock to the rest. Between polls it assumes the local clock drifts at a worst-case rate, so the uncertainty it reports grows until the next poll.

The paper gives the numbers. Epsilon rises steadily between polls and drops back at each one, a shape called a sawtooth. It moves from about 1 ms to about 7 ms over each poll interval, so it is about 4 ms most of the time. The daemon polls every 30 seconds and assumes a drift of 200 microseconds per second. Thirty seconds of that drift adds up to 6 ms, and about 1 ms more comes from the network delay to the masters. Epsilon can spike when time masters are down or machines are overloaded. When it does, Spanner gets slower, not wrong, as the last picture shows.

</GoDeeper>

## If the bands overlap, nobody knows the order

<InteractiveCanvas slug="sysdesign-band-overlap" />

Drag B's write along the line. While the two bands overlap, either write could really have come first, and the picture says "Order unknown". Only when the writes are more than 2 times epsilon apart do the bands separate. Then the order is certain. The opening example fails this test badly: the writes are 1 ms apart, with 7 ms of doubt on each.

<GoDeeper title="Go deeper: the opening example, worked out">

With 7 ms of doubt, A's write really happened somewhere between 11:59:59.993 and 12:00:00.007. B's write happened somewhere between 11:59:59.994 and 12:00:00.008. B's write could have come 13 ms before A's, or 15 ms after it. The 1 ms difference between the readings is smaller than the doubt in each, so it means nothing.

An overlap does not mean the order is wrong. It means the clocks cannot prove the order is right. Whether that matters depends on what the users saw.

If the two writes ran at the same time, and neither user saw the other's result, there is no real order anyone could observe. The writes are concurrent, in the sense of 10.4. The database may put them in either order. It must only pick one order and show the same one to every reader, and the timestamps already do that.

If A's write finished before B's started, and someone saw it finish, a real order exists, and users can notice when it is broken. The next picture shows that case.

</GoDeeper>

## The bug: Bob sees the photo

<InteractiveCanvas slug="sysdesign-truetime-bug" />

Alice removes Bob as a friend at true time 20 ms, sees "done", then posts a photo (a made-up example). Server A's fast clock stamps the unfriend s1 = 27.6. Server B's slow clock stamps the photo s2 = 22.4. The later write got the earlier timestamp. A reader who asks for the state at 25 ms sees the photo, and Bob is still her friend.

<GoDeeper title="Go deeper: why the timestamps must follow real order">

A snapshot read at time t returns every write stamped at or before t. Here s2 = 22.4 and s1 = 27.6, so a snapshot at 25 ms includes the photo but not the unfriend. That is a state that never really existed.

The promise Spanner makes against this is called <GlossaryTerm term="external consistency" definition="If transaction T1 finishes before transaction T2 starts, T1 gets a smaller commit timestamp than T2, even when nothing passes between the two servers. The Spanner paper says it equals linearizability, a strong guarantee you will meet in module 11." />. In plain words: if T1 commits before T2 starts, T1's commit timestamp is smaller than T2's (Spanner paper, section 1).

With these clocks, A is 3.6 ms fast and B is 3.6 ms slow, so they disagree by 7.2 ms. Without any fix, the order comes out right only if Alice waits more than 7.2 ms before posting. The database cannot ask users to wait, and it never knows how wrong its clocks are. It only knows epsilon. The fix has to work from epsilon alone.

</GoDeeper>

## The fix: wait out the doubt

<InteractiveCanvas slug="sysdesign-commit-wait" />

Server A picks the top of its band as the timestamp, s1 = 27.6. Then it waits until even the bottom of its band is past s1. Only then does Alice see "done". The wait is 2 times epsilon, 8 ms here. The photo now gets s2 = 30.4, later than the unfriend. Drag epsilon down and the wait shrinks: better clocks make every write faster.

<GoDeeper title="Go deeper: why commit wait works, and what it costs">

The guarantee follows from three short facts. First, A picks s1 as `TT.now().latest`, the top of its band (the paper's start rule, section 4.1.2). Second, A does not reply until `TT.after(s1)` is true, that is, until even the earliest possible true time is past s1 (the commit wait rule). So when Alice sees "done", true time is already later than s1. Third, Alice's next write starts after she sees "done", so it starts at a true time later than s1. Server B picks s2 as the top of its own band, which is never earlier than true time. So s2 is larger than s1. The two servers never talk. The order comes from A refusing to reply early, plus honest bands on both servers.

**The cost.** A waits for the bottom of its band to pass the top, and the band is 2 times epsilon wide. So the paper says the expected wait is at least 2 times the average epsilon (section 4.2.1). With epsilon near its typical 4 ms, that is at least 8 ms. The paper also measured the wait. In its single-replica benchmark, commit wait was about 5 ms (section 5.1), so epsilon in that test was lower than 4 ms. Spanner does other commit work during the wait, such as replicating the write with Paxos (a consensus protocol you meet in module 12). That hides part of the wait from the total latency. It does not make the wait itself shorter.

This is why better clocks make a faster database. Halve epsilon and you halve the wait on every write. A large epsilon is safe but slow: if a time master fails and epsilon grows, every commit waits longer, but no timestamp is ever wrong. For the opening example, with 7 ms of doubt, A would wait about 14 ms before replying.

**Commit wait in code.** `ttNow()` below is fake. It pretends `Date.now()` is the true time, adds a hidden clock error, and returns a band. Real code would get the band from a time service.

```js
// Fake TrueTime for learning. Date.now() plays the role of true time.
const EPSILON_MS = 4;
const HIDDEN_ERROR_MS = 3; // this clock is 3 ms fast, but callers never see this

function ttNow() {
  const reading = Date.now() + HIDDEN_ERROR_MS;
  return { earliest: reading - EPSILON_MS, latest: reading + EPSILON_MS };
}

const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function commitWithWait(saveWrite) {
  const s = ttNow().latest;          // 1. timestamp at the top of the band
  await saveWrite(s);                // 2. make the write durable at s
  while (ttNow().earliest <= s) {    // 3. commit wait: until TT.after(s)
    await sleep(1);
  }
  return s;                          // 4. only now tell the client "done"
}
```

Time it with a `saveWrite` that takes 0 ms. It returns after at least 8 ms, which is 2 times `EPSILON_MS`. Timers add a little more. On Windows, a 1 ms timer can take about 15 ms, so you may see 15 to 20 ms there. Make `saveWrite` take 5 ms and the total does not grow, because the save happened during the wait. `HIDDEN_ERROR_MS` never changes the wait: it depends only on epsilon, so the code is safe without knowing how wrong the clock is.

Two mistakes are easy here. Replying before the loop ends breaks the guarantee, and tests pass until two writes land close together. Using `Date.now()` directly as the timestamp, with no band, is the 12:00:00.000 trap from the start of the chapter.

**Without atomic clocks.** Hybrid logical clocks (10.5) order every write linked by a message, with no waiting. For the Alice case, the client must carry the last timestamp it received into its next request, like the position token in 8.4. A second device loses that link. Commit wait also works with a wider, honest bound from ordinary NTP, but each write waits longer. A third option is one node that hands out every timestamp. That removes clock doubt, but every write makes an extra trip to that node, and it becomes a bottleneck and a single point of failure.

**In AWS.** The Amazon Time Sync Service uses satellite-connected and atomic reference clocks in each Region, and EC2 instances can sync to it. AWS also publishes ClockBound, an open-source daemon and client library (MIT or Apache 2.0, your choice). It returns earliest and latest timestamps built from the local clock's error bound, the same shape as `TT.now()`. An AWS post from November 2023 gave typical error bounds under 100 microseconds over NTP. With the PTP hardware clock on supported instances, it was under 40 microseconds. If those held, commit wait would be well under 1 ms. Treat them as a dated example and measure your own bound.

</GoDeeper>
