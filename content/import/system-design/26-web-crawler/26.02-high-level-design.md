You have DalilBot's numbers: about 770 pages a second, 600 megabits a second in, 50 TB a month stored, and about 770 sites that must have work ready at once. This is the sketch step of the design loop. Draw the loop first, then add only the blocks the numbers ask for.

## The crawl loop, as blocks

<MermaidDiagram title="The crawl loop" chart={`flowchart LR
  S["Seed URLs"] --> F["URL frontier"]
  F -->|"1. next URL"| W["Fetchers + DNS and robots caches"]
  W -->|"2. GET page"| X["The open web"]
  X -->|"3. HTML"| W
  W -->|"4. HTML"| P["Parser"]
  P -->|"5. page text"| O[("Page storage")]
  P -->|"6. links"| U["URL filter + seen check"]
  U -->|"7. new URLs"| F
`} legend="Seeds start the loop. The frontier hands out URLs, fetchers download pages from the open web, and the parser saves the text and sends the links through a filter. Only new links return to the frontier. Fetchers are the only block that talks to the open web." />

Seed addresses start the loop. The <GlossaryTerm term="URL frontier" definition="The list of web addresses still to visit, together with the rules for which one comes next." /> hands out the next URL. A fetcher downloads the page and a parser reads it. Text goes to storage. Links pass a filter and a seen check, and only new ones return to the frontier.

<GoDeeper title="Go deeper: what each block does">

| Block | Job | Where it is taught |
|---|---|---|
| Frontier | Holds the URLs still to visit. Decides the next one, with a wait per site and a priority per URL | 26.3 |
| DNS and robots caches | Keep each host's IP address and each site's `robots.txt` rules, so most fetches skip two lookups | this chapter, 26.3 |
| Fetchers | Open a connection, download the page, stop at a time limit and a size limit, follow a few redirects, and record the status code | this chapter |
| Parser | Turns HTML into text and a list of links. Must survive broken HTML | this chapter |
| URL filter and seen check | Cleans each link, drops unwanted ones, and asks whether it was seen before | 26.4 |
| Content check | Fingerprints each page body to find copies at other addresses | 26.4 |
| Storage | Page bodies in object storage, plus a table of facts about each URL | this chapter |

Fetchers are stateless: all the state is in the frontier and the tables, so any fetcher can take any URL (chapter 4.3). They are also the only block that talks to the open web. Everything else sits inside Dalil's private network. A fetcher names itself in its `User-Agent` header and points to a page where site owners can read about the crawler and contact the team. That is a courtesy, and it is also how an owner decides whether to block you or to ask you to slow down.

Fetchers need limits, because the web is hostile by accident. The course uses 5 seconds to connect, 30 seconds for the whole download, and 5 MB for the body. A server that sends one byte a minute, or a file that never ends, must not hold a connection for ever. These are course choices, and each one is a number to tune.

</GoDeeper>

## Follow one page through

<InteractiveCanvas slug="sysdesign-m26-one-page" />

Watch one URL. The fetcher gets the page, and the parser finds 3 links. The URL check already knows 2 of them. Only the new link goes round again. Many links lead to pages the crawler already has, so this check does a lot of the stopping.

<GoDeeper title="Go deeper: relative links, redirects and status codes">

The parser must turn each link into a full address before the check sees it. A link such as `../pricing` is relative, so it is resolved against the page's own address (or against a `<base>` tag if the page has one). The URL object in JavaScript does this: `new URL("../pricing", "https://shop.example/a/b")` gives `https://shop.example/pricing`. Chapter 26.4 cleans the result further.

A fetch ends in a status code, and each one asks for a different follow-up.

- **200.** Save the page and read its links.
- **301 or 302.** The page moved. Put the new address through the filter and the seen check like any other link. Follow at most a few hops in a row, or a redirect loop will hold a fetcher for ever.
- **404 or 410.** The page is gone. Record it, and stop revisiting it soon.
- **429 or 503.** The site says "too many requests" or "unavailable". Make this host's wait longer, and honour a `Retry-After` header if it sends one. This is the signal that DalilBot is too fast, and the answer is to slow down (chapter 16.4).
- **Time-out or connection error.** Count it against the host. After several in a row, rest the host for a while instead of trying every second.

{/* source needed: RFC 9110 on the meaning of 301, 302, 404, 410, 429 (RFC 6585) and 503 and the Retry-After header; the course uses them as standard HTTP. */}

## Step through the design at peak

<InteractiveCanvas slug="sysdesign-m26-design-stepper" />

Step through the build for 772 pages a second. One fetcher that waits for each page manages 2. Many downloads in flight at once make a small fleet. A DNS cache trims it again. In step 4, choose how many frontier shards share the seen-URL check, and watch the memory each one needs.

<GoDeeper title="Go deeper: the numbers behind each step">

A fetch takes 0.5 s in the course's numbers: about 100 ms for a cold DNS lookup, then three round trips of about 80 ms each (connect, TLS, and the request, using the 80 ms from Europe to North America in [S3] and the one-round-trip TLS 1.3 handshake [S11]), and about 160 ms to download the body. With the DNS answer in a local cache the lookup falls to about 0.5 ms [S3], so a fetch takes about 0.4 s. A machine keeps 100 downloads in flight and is planned at half its limit, as chapter 2.5 advises.

| Step | What changes | Working | Result |
|---|---|---|---|
| 1. One fetcher | Waits for each page | 1 / 0.5 s | 2 pages/s, 386 times too slow |
| 2. Many in flight | 100 downloads per machine | 100 / 0.5 s = 200 max, 100 planned; 772 / 100 | 8 machines |
| 3. DNS cache | Fetch time falls to 0.4 s | 100 / 0.4 s = 250 max, 125 planned; 772 / 125 | 7 machines |
| 4. Frontier shards | Split the queues and the seen check by host | 38,600 checks/s and a 24 GB filter, divided by 4, 8 or 16 | 8 shards: 4,800 checks/s and 3 GB each |
| 5. Storage | Pages to object storage, facts to a table | 772 pages/s x 25 KB compressed | about 19 MB/s written, 50 TB a month |

The 24 GB filter is a Bloom filter for 20 billion URLs at 1% false positives, which chapter 26.4 builds. For now read it as "the seen set must live in memory, and one machine cannot hold all of it comfortably".

Step 3 also removes about 770 lookups a second from the outside DNS servers, which matters for a second reason: a crawler that asks the same question hundreds of times a second looks like abuse.

</GoDeeper>

## Look up each host once

<InteractiveCanvas slug="sysdesign-m26-dns-cache" />

Before it can connect, a fetcher needs the site's IP address. A cold lookup costs about 100 ms in our numbers, a fifth of the whole fetch. The crawler keeps answers in its own cache, so the next page on that host costs 0.5 ms. Chapter 3.3 explains the TTL that limits how long an answer may be kept.

<GoDeeper title="Go deeper: how a crawler should use a DNS cache">

Chapter 3.3 showed that every DNS answer has a TTL, the number of seconds a copy may be used [S9]. Chapter 3.7 had you build a cache that respects it. A crawler uses the same idea with one twist: it asks about the same host again and again, because the frontier sends many URLs of one site close together. A site fetched once a second keeps its answer warm for the whole 5 minutes, so 1 lookup serves about 300 fetches.

Two choices follow.

- **Honour the TTL, or set a floor.** A floor of a few minutes saves lookups when a site publishes a TTL of 5 seconds. The cost is that after a site moves, DalilBot may call the old address for a few minutes. The harm is small and short, and the fetch simply fails and is retried.
- **Cache failures briefly.** If a name does not exist, remember that for a short time. Otherwise DalilBot asks again for every URL of a dead site.

Two traps. First, different host names often share one IP address (shared hosting). If politeness counts only host names, 50 small sites on one server can receive 50 requests a second together. A careful crawler also limits requests per IP address. Second, DNS is a dependency, and its failures are wide: in October 2025 a race left DynamoDB's regional endpoint with an empty DNS record, and many services that depended on it failed for hours [S135]. Treat a DNS failure as a temporary fault for that host, and back off (chapter 16.4), so a DNS problem never turns into a retry storm.

</GoDeeper>

## One worker owns each host

<InteractiveCanvas slug="sysdesign-m26-host-shards" />

Hash the host name to pick a worker. All of one site's URLs queue on that worker, so it alone keeps the one-request-a-second rule. There is no shared lock and no talk between workers. Chapter 9.3 shows the ring that spreads hosts. Chapter 15.4 shows why one key keeps one order.

<GoDeeper title="Go deeper: scaling workers by adding hosts to them">

Partition the frontier by host, not by URL. If URLs were spread by a hash of the whole address, the pages of one site would land on every worker, and the workers would have to share a counter for each site to stay polite. A hash of the host removes that need: each worker sees every request to its hosts. In queue language, the host is the partition key (chapter 15.4).

The workers sit on a consistent hash ring (chapter 9.3). When a worker joins, it takes over only about 1 host in N from the others. When one fails, its hosts spread over the rest. Two cautions.

- **Hand over carefully.** For a moment the old and the new owner might both believe they own a host. Make the new owner wait one full delay after taking over, so a site never receives two requests together.
- **Skew.** A site with 50 million pages is slow to finish at one request a second, but it is not a burden for its worker: it uses one slot and one queue. What can skew a worker is the number of queued URLs it holds in memory, so spread by hash and watch the memory per worker.

Growth is simple, because hosts are independent. At 10 times the traffic, 20 billion pages a month, DalilBot needs about 7,700 pages a second and roughly 60 fetcher machines at the planned load. It needs 7,700 hosts ready at once, and the same ring gives it 10 times the shards. Nothing in the design must be redone, which is the sign of a good partition key.

</GoDeeper>

## What the crawler remembers

<MermaidDiagram title="The three records" chart={`erDiagram
  HOST {
    string name PK
    string robots_rules
    datetime robots_fetched_at
    int delay_ms
    datetime next_allowed_at
    int pages_left_in_budget
  }
  URL {
    string host PK
    string url_hash PK
    int priority
    datetime last_fetched_at
    datetime next_fetch_at
    string content_hash
  }
  PAGE {
    string content_hash PK
    string object_key
    int bytes
  }
  HOST ||--o{ URL : "owns"
  PAGE ||--o{ URL : "stored once for"
`} legend="HOST holds robots rules and when the next request is allowed. URL holds what is known about one address and when to visit it again, with the host as the partition key. PAGE is stored once per content fingerprint, so copies share a row." />

Three records are enough. HOST holds the robots rules and the time of the next allowed request. URL holds what is known about one address and when to visit it next. PAGE is stored once per content fingerprint, so copies share one row. The URL table is the truth, and the frontier can be rebuilt from it.

<GoDeeper title="Go deeper: keys, sizes and why the URL table is the truth">

The URL table is keyed by host first and then by a hash of the address. Hosting every URL of a site together makes "what is due on this host?" a local read. A key-value store that hashes the partition key spreads hosts over machines, and has per-partition limits [S40], so a giant site is split with a small suffix, as chapter 9.4 describes.

A URL record is small: an 8-byte hash, a host id, a priority, two times, a content hash and a counter, about 60 bytes in the course's estimate. At 20 billion URLs that is about 1.2 TB, which is a table on SSDs spread over machines, not memory. The seen check cannot read it for every link, which is why chapter 26.4 puts a small structure in memory in front of it.

The frontier is a view of the table: the URLs whose `next_fetch_at` has passed, grouped by host and priority. If a shard is lost, rebuild its queues from the table, and the crawl continues. This is why `next_allowed_at` is stored on the HOST record. A restarted shard that forgot it would send a request to every site at once.

PAGE is keyed by the content fingerprint. Two URLs with the same body point to the same stored page, which is how copies cost nothing extra.

</GoDeeper>

## A crashed fetcher loses nothing

<InteractiveCanvas slug="sysdesign-m26-worker-lease" />

The frontier lends each URL with a lease. A fetcher that crashes never reports back. When the lease ends, the URL goes to another fetcher. Fetching a page twice is harmless, so the crawl needs no exactly-once machinery. Chapter 15.5 covers retries and dead letters.

<GoDeeper title="Go deeper: leases, failures and an AWS note">

A lease is the same idea as the visibility timeout of a queue: a message is hidden while one consumer works on it, and it reappears if the consumer does not finish. SQS has a 30 second default [S84], and that is the lease length the course uses. A lease shorter than the slowest normal fetch hands out the same URL twice. A longer one leaves a crashed fetcher's URLs waiting. Set it a little above the 30 second total time limit.

What a crash costs. If a machine with 100 downloads in flight dies, those 100 pages wait up to a lease, then return. At 772 pages a second with 8 machines, that is about one machine's share for 30 seconds, and nothing is lost. A retry must still respect the host's wait, so the frontier counts a reissued URL like any other.

If a whole frontier shard dies, its queues are rebuilt from the URL table, as the last beat said. Some URLs may be queued twice. The seen check and the lease make that harmless: the worst result is one extra fetch.

**In AWS.** SQS standard queues deliver at least once and hide a received message for a visibility timeout [S83, S84], which is the lease. DynamoDB's partition key hashing and conditional writes fit the URL table, with the "add only if absent" step as a conditional write [S40, S42]. {/* source needed: AWS documentation for S3 as page storage, ElastiCache or MemoryDB for the in-memory seen set, and Route 53 Resolver caching; none is in the dossier. */}

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Seeds go into a URL frontier. Fetchers take URLs from it, use a DNS cache and a robots cache, download the page and pass it to a parser. The parser sends the text to storage and the links through a filter and a seen check. Only new links return to the frontier. I partition the frontier by a hash of the host, so one worker owns every request to a host and can keep the wait between requests with no shared lock. Fetchers are stateless and take URLs on a lease, so a crash only delays a page. At 770 pages a second, with 100 downloads in flight per machine, I need about 8 fetcher machines planned at half load."

**Expect:** "Why not partition by URL hash?" **Answer:** "Then one site's pages would spread across every worker, and they would need a shared counter per site to stay polite. Partitioning by host keeps that rule local."

</GoDeeper>
