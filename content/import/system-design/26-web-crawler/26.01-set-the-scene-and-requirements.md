Dalil is a search engine (a fictional service). It can only search pages it has already read. The reader is its web crawler, DalilBot: a program that visits web pages, saves them, and follows the links on them to find more. This module runs the design loop from chapter 1.4 on that crawler, from clarify to failure. This first chapter does the first two steps: say what DalilBot must do, then turn that into numbers.

## Every page leads to more pages

<InteractiveCanvas slug="sysdesign-m26-follow-links" />

DalilBot keeps a list of web addresses still to visit. It takes one, fetches the page, saves it and reads the links on it. The new links go back on the list. Start with a few known sites and the loop never runs dry, because every page points to others. The whole job is that loop, done two billion times a month.

<GoDeeper title="Go deeper: clarify first, the way chapter 1.4 does">

Before any numbers, ask what DalilBot must do and what it will not do. Dalil is made up, so all of this is a course choice.

**DalilBot does.** It starts from a list of seed addresses. It fetches pages over `http` and `https`, reads the links in them, and follows those links. It saves the page text and a few facts about each page. It reads each site's `robots.txt` rules and obeys them. It never sends a site more than one request a second unless the site allows it. It skips pages it already has, including near copies. It visits pages again so that its copy stays fresh.

**DalilBot does not, for now.** It does not run JavaScript to build a page, so pages that need it look empty. It does not fetch images or video, or pages behind a login. It does not build the search index or rank pages. That is the next system, and it reads what DalilBot saved. Each of these is a fair feature, and each would add work to every later step.

**Fast enough.** The target is 2 billion page fetches a month. Chapter 26.2 turns that into machines.

**Polite.** A crawler is a guest on other people's servers. A site that cannot cope will block it, and many sites ask crawlers to slow down.

**Fresh.** A news front page may change every few hours. An old article may not change for a year. DalilBot should look at the first often and the second rarely.

**Robust.** The web contains broken pages, slow servers, endless calendars and pages that lie. One bad site must not stop the crawl.

**Durable.** If a machine dies, the crawl continues. The list of addresses still to visit must not be lost.

## Drag the volume, find the load

<InteractiveCanvas slug="sysdesign-m26-estimate-play" />

Drag the pages per month, the page size and the wait between requests to one site. At 2 billion pages the crawler fetches about 770 pages a second and takes in about 620 megabits a second. Neither is huge. The ringed card is the surprise: at one request a second per site, about 770 different sites must have work ready at the same moment.

<GoDeeper title="Go deeper: the working, and what is an assumption">

Nobody gave DalilBot these numbers, so each one is written down as an assumption: 2 billion pages a month, 100 KB of HTML per page, 50 links per page, 0.5 seconds for one fetch from start to finish, one request a second to any one site, and a 4 to 1 saving when pages are compressed for storage. The method is the one from chapter 2.3: divide by seconds, and keep the unit next to every number.

| Quantity | Working | Result |
|---|---|---|
| Seconds in a month | 30 x 86,400 | 2,592,000 |
| Pages a second, average | 2,000,000,000 / 2,592,000 | about 772 |
| Data in a second | 772 x 100 KB | about 77 MB, or 620 Mbit/s |
| Fetches in flight | 772 x 0.5 s (Little's law, chapter 2.5) | about 386 |
| Sites busy at once | 772 x 1 s | about 772 |
| Links to check a second | 772 x 50 | about 38,600 |
| Raw data a month | 2,000,000,000 x 100 KB | 200 TB |
| Stored a month | 200 TB / 4 | about 50 TB, or 600 TB a year |

Now ask which number drives the design. Bandwidth of 620 Mbit/s is spread over many machines, so no single link carries it. About 386 fetches in flight is a few hundred open connections, which is easy for a modern server that waits on the network most of the time. Storage of 50 TB a month is large but plain: it only grows, and object storage is built for that. The number that shapes the design is the 772 sites. The crawler may send only one request a second to each site. To fetch 772 pages a second it needs work waiting for 772 different sites at the same moment. If it has only 20 sites in its list, it can fetch only 20 pages a second, however many machines it owns. Chapter 26.3 builds the structure that guards this rule.

Two more numbers will matter later. The 38,600 link checks a second must be answered from memory, because a disk read for each would be slow. And the list of every address ever seen may reach tens of billions, which is a memory question that chapter 26.4 answers.

These are averages and guesses. Say them out loud and invite correction. If real pages average 30 KB, bandwidth and storage drop by two thirds and the sites-at-once number does not change at all.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Before I draw, let me fix scope and numbers. I will crawl HTML over http and https, obey robots.txt, stay polite, skip duplicates and refresh by how fast a page changes. I will leave out JavaScript rendering, images and ranking. I will assume 2 billion pages a month. That is about 770 pages a second, about 620 megabits a second in, and about 50 TB a month after compression. The number that drives the design is politeness: at one request a second per site I need about 770 different sites ready at the same moment."

**Expect:** "Why is bandwidth not the problem?" **Answer:** "It is spread over many fetchers, so each carries a small share. The limit I cannot buy my way past is the per-site rate, so I will design the queue of addresses around hosts first."
