The web repeats itself. One article has many addresses, one page is mirrored on other sites, and a calendar makes new addresses for ever. Without checks DalilBot could spend many of its fetches on pages it already has. This second deep dive follows a link from the parser to storage and puts a cheap check at each step.

## Three spellings, one page

<InteractiveCanvas slug="sysdesign-m26-url-normalize" />

The same article can be written as `SHOP.example/a`, `shop.example/a#top` and `shop.example/a?sid=9`. To the seen check these are three strings. DalilBot first cleans each URL into one canonical form: lower-case host, no fragment, no session id, sorted query. Then three links become one entry.

<GoDeeper title="Go deeper: the rules, a runnable cleaner and the danger of cleaning too much">

The JavaScript `URL` object already lower-cases the scheme and host, drops a default port such as `:80`, and resolves `./` and `../` in the path. The cleaner adds the rules that are specific to crawling: drop the fragment (the part after `#` never reaches the server), drop known session and tracking parameters, sort the rest so their order cannot matter, and refuse anything that is not `http` or `https` or is longer than 2,048 characters.

```js
const DROP = new Set(["utm_source", "utm_medium", "utm_campaign", "sessionid", "phpsessid", "sid"]);

function normalizeUrl(input) {
  const u = new URL(input); // lower-cases scheme and host, drops default ports, resolves ./ and ../
  if (u.protocol !== "http:" && u.protocol !== "https:") throw new TypeError("not http or https");
  u.hash = ""; // a #fragment never reaches the server
  const keep = [...u.searchParams].filter(([k]) => !DROP.has(k.toLowerCase()));
  keep.sort(([a], [b]) => (a < b ? -1 : a > b ? 1 : 0));
  u.search = new URLSearchParams(keep).toString();
  if (u.href.length > 2048) throw new RangeError("URL longer than 2,048 characters");
  return u.href;
}
```

Run on three links:

```text
HTTP://Example.COM:80/a/./b/../c?b=2&a=1&utm_source=mail#top -> http://example.com/a/c?a=1&b=2
http://example.com/a/c?a=1&b=2&sessionid=XYZ -> http://example.com/a/c?a=1&b=2
http://example.com:80/a/c/?a=1&b=2 -> http://example.com/a/c/?a=1&b=2
```

The first two become the same string. The third keeps its trailing slash, on purpose. `/a/c` and `/a/c/` are different addresses to a server, and merging them could join two different pages.

That is the danger of cleaning. Drop a parameter that matters, such as `?id=7`, and two different pages become one, so a real page is never fetched. So the list of parameters to drop must be careful. A crawler can learn it per site: if removing a parameter never changes a page's fingerprint (see the next beats), it is safe to drop on that site. The same goes for `www.shop.example` and `shop.example`. They are usually the same site, but not always, so merge them only when the pages match.

## Drag the error, watch the memory

<InteractiveCanvas slug="sysdesign-m26-bloom-play" />

Drag the number of URLs and the error rate. At 20 billion URLs and 1% error the filter needs about 24 GB, against 160 GB for exact 8-byte fingerprints and 2 TB for the URLs themselves. Each 10 times lower error costs about 4.8 more bits per URL. Chapter 7.3 showed the small version, and chapter 23.4 covers Bloom filters in full.

<GoDeeper title="Go deeper: the formulas, a run and what the filter cannot do">

A Bloom filter has `m` bits and uses `k` hash functions. Adding a URL sets `k` bits. Asking about a URL checks the same `k` bits. If any is 0, the URL was never added. If all are 1, it may have been. There are no false negatives, and the false positive rate can be set [S113]. For `n` URLs and a wanted error `p`:

- bits needed `m = -n x ln(p) / (ln 2)^2`, so bits per URL = `-ln(p) / (ln 2)^2`
- best number of hash functions `k = (m / n) x ln 2` [S113]

| URLs (n) | Error (p) | Bits per URL | Hash functions | Memory |
|---|---|---|---|---|
| 1 billion | 1% | 9.6 | 7 | 1.2 GB |
| 20 billion | 10% | 4.8 | 3 | 12 GB |
| 20 billion | 1% | 9.6 | 7 | 24 GB |
| 20 billion | 0.1% | 14.4 | 10 | 36 GB |
| 20 billion | 0.01% | 19.2 | 13 | 48 GB |
| 100 billion | 1% | 9.6 | 7 | 120 GB |

Here is a small filter for URLs. It gets its `k` positions from one SHA-256 hash, using the double-hashing trick: position `i` is `h1 + i x h2`.

```js
import { createHash } from "node:crypto";

function createBloom(expected, falsePositive) {
  const m = Math.ceil((-expected * Math.log(falsePositive)) / Math.LN2 ** 2);
  const k = Math.max(1, Math.round((m / expected) * Math.LN2));
  const bits = new Uint8Array(Math.ceil(m / 8));
  function positions(url) {
    const d = createHash("sha256").update(url).digest();
    const h1 = d.readUInt32BE(0);
    const h2 = (d.readUInt32BE(4) | 1) >>> 0; // >>> 0 keeps it a positive number
    return Array.from({ length: k }, (_, i) => (h1 + i * h2) % m);
  }
  return {
    m, k,
    add(url) { for (const p of positions(url)) bits[p >> 3] |= 1 << (p & 7); },
    maybeHas(url) { return positions(url).every((p) => bits[p >> 3] & (1 << (p & 7))); },
  };
}
```

A run with 1 million URLs added, then 1 million other URLs asked about:

```text
target 10%: 4.79 bits per URL, 0.60 MB, k=3, false negatives 0, measured false positives 10.104%
target 1%: 9.59 bits per URL, 1.20 MB, k=7, false negatives 0, measured false positives 1.012%
target 0.1%: 14.38 bits per URL, 1.80 MB, k=10, false negatives 0, measured false positives 0.096%
```

The measured error matches the target, and no added URL was ever missed. One bug in the first version of this code is worth remembering: `| 1` turns the number into a signed 32-bit value, which can be negative, and a negative position silently writes nowhere. The result was thousands of false negatives. The fix is `>>> 0`.

What a Bloom filter cannot do. It cannot delete a URL, because clearing a bit may clear it for other URLs too. It cannot grow: if more URLs arrive than the `n` it was sized for, the error rises quickly. And it cannot say when a page was fetched. So the filter only answers "have we ever met this address?" The table of URL records from chapter 26.2 keeps the times and drives revisits.

Memory and the shards. The seen check is split with the frontier, by host (chapter 26.2). With 8 shards each keeps its own filter of about 3 GB and answers about 4,800 checks a second, all from memory.

The exact alternative is a set of 64-bit fingerprints: 160 GB for 20 billion. A 64-bit hash collides: the expected number of colliding pairs among 20 billion is about n(n-1)/2 / 2^64, which is 10.8. Ten or so wrongly skipped pages in 20 billion is almost nothing, so the exact set loses far fewer pages than the Bloom filter. It costs 6.7 times the memory. Which to choose depends on what 136 GB of memory costs against 1% of new URLs skipped, and the next beat looks at that loss.

</GoDeeper>

## A false yes skips a new page

<InteractiveCanvas slug="sysdesign-m26-bloom-false-yes" />

A Bloom filter says "surely not seen" or "maybe seen". The "no" is always right. The "maybe" is wrong about 1 time in 100 at 9.6 bits per URL, and then DalilBot skips a page it never saw. The same URL gets the same answer next time, so that page stays missed until the filter is rebuilt.

<GoDeeper title="Go deeper: what the loss costs and how to limit it">

The loss is real but bounded. If DalilBot meets 1 billion new URLs in a month, a 1% filter wrongly skips about 10 million of them. The skipped pages are not special, so across the whole web the loss is spread like random noise. It is also permanent for a given filter: a URL whose bits all happen to be set will always get "maybe".

Four ways to limit it.

- **Lower the error.** At 0.1% the memory is 36 GB, not 24, and the loss falls to about 1 million pages a month. Ten times less loss for 12 GB more.
- **Rebuild with new hash seeds.** Rebuild the filter from the URL table now and then with different seeds. A different 1% of URLs is hit each time, so no page is lost for good.
- **Let important URLs bypass it.** Seeds, sitemap entries and URLs with high priority can be checked in the exact URL table instead. They are few, so the disk read is affordable.
- **Confirm a "maybe" on the host's own table.** For a host the crawler cares about, a "maybe" triggers one exact lookup. The filter still saves the lookup for every "no".

The filter guards discovery only. A URL already in the table is revisited by its `next_fetch_at`, never by the filter, so a false positive never stops a known page from being refreshed.

Here is the trade-off, in the shape the module's gate asks for. The choice: a Bloom filter for the seen check. Why now: 20 billion URLs, with the seen set in memory on every shard. What it buys: 24 GB instead of 160 GB. What it costs: about 1% of new URLs skipped. When to switch: if memory is cheap or missed pages are costly, use an exact set of fingerprints or a lower error.

</GoDeeper>

## Same body, stored once

<InteractiveCanvas slug="sysdesign-m26-content-hash" />

Different addresses can serve the same page: mirrors, print views, a session id in every link. DalilBot hashes each body into a short fingerprint. If the fingerprint is already known, the page is a copy, so it keeps a link to the stored copy and stores nothing new. One changed character gives a different fingerprint.

<GoDeeper title="Go deeper: what to hash, how long the fingerprint is, and where it lives">

The URL check runs before the fetch. The content check runs after it, because only then is the body known. It catches what the URL check cannot: the same page under addresses that look different, such as a mirror on another site.

What to hash. A hash of the raw HTML fails on pages that put a timestamp, an ad or a one-time token in every response. Hash the main text after the parser has removed the scripts and the navigation, so those parts do not matter. The fingerprint then changes only when the real content changes. That is also what the revisit rule in chapter 26.3 needs: a changed fingerprint means the page changed.

How long. With 64 bits, 20 billion pages are expected to produce about 11 colliding pairs, as computed in the last beat. With 128 bits it is effectively none, at 16 bytes per page: 20 billion x 16 bytes = 320 GB. The fingerprint index is not split by host. Two copies of a page live on different hosts, so the index is split by the fingerprint's own hash across a key-value store.

When two copies are fetched at the same moment, both may find "not seen" and both are stored. That is harmless: a later pass drops one. The check is allowed to be a little late.

</GoDeeper>

## Almost the same page

<InteractiveCanvas slug="sysdesign-m26-simhash-near" />

Many copies are not identical: a new date, an ad, a related-links box. A simhash is a 64-bit fingerprint that changes only a few bits when the text changes a little. Count the bits where two fingerprints differ. In our test a near copy differed by 10 bits and an unrelated page by 32.

<GoDeeper title="Go deeper: how simhash works, a seeded run and choosing the threshold">

Break the text into every run of 3 words. Hash each run to 64 bits. For each of the 64 positions, add +1 if the hash has a 1 there and -1 if it has a 0, across all runs. The final bit is 1 where the sum is positive. Two texts that share most of their runs vote the same way at almost every position, so their fingerprints are close. Unrelated texts vote independently, so about half of their 64 bits differ.

```js
function hash64(piece) {
  let h = 0xcbf29ce484222325n; // FNV-1a, 64 bits
  for (const byte of Buffer.from(piece)) {
    h ^= BigInt(byte);
    h = (h * 0x100000001b3n) & 0xffffffffffffffffn;
  }
  return h;
}

function simhash(text) {
  const words = text.toLowerCase().match(/[a-z0-9]+/g) ?? [];
  const votes = new Array(64).fill(0);
  for (let i = 0; i + 3 <= words.length; i++) {
    const h = hash64(words.slice(i, i + 3).join(" "));
    for (let bit = 0; bit < 64; bit++) votes[bit] += (h >> BigInt(bit)) & 1n ? 1 : -1;
  }
  let print = 0n;
  for (let bit = 0; bit < 64; bit++) if (votes[bit] > 0) print |= 1n << BigInt(bit);
  return print;
}

function bitsApart(a, b) {
  let x = a ^ b, count = 0;
  while (x) { count += Number(x & 1n); x >>= 1n; }
  return count;
}
```

The test uses made-up 600-word texts from a seeded random generator, so every run prints the same numbers. A near copy changes 10 words and adds 8 words at the end, like a related-links box. Result:

```text
page A vs near copy B: 10 bits apart
page A vs other page C: 32 bits apart
200 near copies:       min 0, median 7, max 11
200 unrelated pages:   min 20, median 31, max 42
```

In this test a threshold of 16 bits separates the two groups with no mistake: every near copy is 11 bits or fewer apart, every unrelated pair 20 or more. That is a result for these made-up texts. Real pages are shorter or longer, and boilerplate such as menus is shared by unrelated pages, so a team chooses its threshold from labelled examples of real pairs. Published work on web-scale duplicate detection used 64-bit fingerprints and a small distance. {/* source needed: Charikar, "Similarity estimation techniques from rounding algorithms", STOC 2002, and Manku, Jain and Das Sarma, "Detecting near-duplicates for web crawling", WWW 2007; neither is in the dossier. */}

Finding every stored fingerprint within a few bits of a new one is the hard part at scale, because a plain lookup finds only exact matches. If two 64-bit fingerprints differ in at most 3 bits, then when you cut them into 4 blocks of 16 bits, at least one block is identical. So index the fingerprints by each block, look up the 4 blocks of the new fingerprint, and compare the few candidates bit by bit. That pigeonhole idea is the way near-duplicate lookups are made fast.

What to do with a near copy is a product choice. DalilBot can keep only the first and link the others, or keep all and mark them as a cluster so the search can show one result.

</GoDeeper>

## A calendar that never ends

<InteractiveCanvas slug="sysdesign-m26-trap-calendar" />

Some sites make new addresses without end: a calendar with a next-month link, a search page with endless filters, a session id in every link. Each address is new, so the seen check never stops them. A budget of pages per site does. DalilBot stops at 50 pages and moves on.

<GoDeeper title="Go deeper: the usual traps, defences and a run on a fake web">

Common traps, and none of them needs bad intent. A calendar with next and previous links. A site where every filter and sort order is a new address (`?color=red&size=m&sort=price`). A session id added to every link, so each visit sees new addresses. A path that repeats (`/a/b/a/b/a/b`) because of a broken relative link. Pages that are generated on demand for any number in the address (`/page/48213`).

Defences, from cheapest to most careful:

- **URL length.** Refuse addresses over 2,048 characters. Repeating paths grow fast.
- **Repeated segments.** Drop a URL where the same path segment appears three or more times.
- **Depth.** Count the links followed from a seed, and stop beyond a limit such as 15.
- **A budget for each host.** The course uses 50 pages for a new, unknown host and a larger budget for hosts that earn it: raise the budget while the pages are new and valuable, and stop when most of the last pages were duplicates.
- **Fingerprints.** If most new pages on a host turn out to be near copies of each other (previous beat), the host is probably a trap.

The course's fake web has four sites with no network at all: `news.example` (61 pages), `shop.example` (21), `wiki.example` (41) and `cal.example`, a calendar trap with a next-month link on every page. The crawler uses the polite frontier from chapter 26.5 with a 1 second delay. Three runs, with the simulated clock:

| Run | Fetches | Simulated time | Pages on cal.example | Smallest gap on any host |
|---|---|---|---|---|
| Three real sites, no trap | 123 | 60 s | none | 1,000 ms |
| With the trap, budget of 50 pages per host | 162 | 49 s | 50 | 1,000 ms |
| With the trap, no budget (stopped by hand at 2,000 fetches) | 2,000 | 1,876 s | 1,877 | 1,000 ms |

With the budget, the crawl finishes all four sites in 49 seconds. The budget also cut `news.example` from 61 pages to 50, which is the cost described below. Without it, the three real sites finish early and then the trap is the only host with work, so the crawler runs at 1 page a second for half an hour, and would never end. The trap also shows why the speed limit from chapter 26.3 hurts here: with one host left, DalilBot is no longer "770 sites at once" but 1. A good crawler notices that and stops.

A budget has a cost. A big, honest site, such as an encyclopaedia with millions of real pages, would be cut off at 50. That is why the budget must be earned and not fixed. It is a dial between missing pages and wasting fetches, and the setting depends on how the crawler measures a host's value.

</GoDeeper>

## The defences, in order

<MermaidDiagram title="The checks, in order" chart={`flowchart TD
  L["Link found by the parser"] --> N["Clean the URL: lower-case, no fragment, no session id"]
  N --> V{"http or https, under 2,048 characters, no repeating path?"}
  V -->|"no"| X1["Drop"]
  V -->|"yes"| R{"robots.txt allows it?"}
  R -->|"no"| X1
  R -->|"yes"| B{"Host still under its page budget?"}
  B -->|"no"| X1
  B -->|"yes"| S{"Bloom filter: seen?"}
  S -->|"maybe"| X1
  S -->|"no"| F["Add to the frontier"]
  F --> G["Fetch the page"]
  G --> C{"Content fingerprint known?"}
  C -->|"yes"| X2["Keep a link to the stored copy"]
  C -->|"no"| P["Store the page"]
`} legend="Cheap local checks run first. The seen check comes next. The content check runs after the fetch, because only then is the body known." />

Each defence is cheap and runs before the next. Local checks come first: spelling, length, rules and budget. The seen check comes next. The content fingerprint comes after the fetch, because only then is the body known. A link that is dropped early costs almost nothing, and a page that is fetched and then found to be a copy has already cost a request.

<GoDeeper title="Go deeper: why this order, and an AWS note">

Order the checks by cost and by how many links each one removes. Cleaning and the length test are a few microseconds. The `robots.txt` test is a lookup in a cached rule list. The budget is a counter. The Bloom filter is a few memory reads. The fingerprint needs the full download, which is the most expensive thing the crawler does, so it must be the last. Running it first would mean fetching a page just to find that it was a trap.

Two checks use state that other workers do not share. The budget, `robots.txt` and the Bloom filter are all per host, so they live on the worker that owns the host (chapter 26.2) and need no cross-worker call. The fingerprint index is the exception, since copies of a page live on different hosts, and it is a shared key-value store with a conditional write: "add this fingerprint if absent" [S42].

**In AWS.** A conditional write that succeeds only if the item does not exist yet is the DynamoDB form of "add if absent" [S42], and hashing the partition key spreads the fingerprints [S40]. {/* source needed: AWS documentation for a managed in-memory store with Bloom filter support; none is in the dossier, so the course does not name one. */}

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "I clean each URL first: lower-case host, no fragment, no session ids, sorted query. Then I check the host's budget and robots.txt, then a Bloom filter for URLs seen. At 20 billion URLs and 1% error that is about 24 GB, split over the shards, against 160 GB for an exact set. The cost is about 1% of new pages skipped, which I can cut with a lower error or a periodic rebuild. After the fetch I hash the page text for exact copies and use a simhash for near copies. For traps I put a page budget on each host and a depth limit."

**Expect:** "What if the Bloom filter says maybe seen for a new URL?" **Answer:** "I skip it and lose that page. For important URLs I check the exact URL table instead. I accept the loss on the long tail because it is small, random and bounded, and I can rebuild with new hash seeds."

</GoDeeper>
