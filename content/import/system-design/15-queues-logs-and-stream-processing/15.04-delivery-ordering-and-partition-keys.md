Chapter 14.5 explained why a broker sends a message twice. This chapter looks at the worker's side of the same problem: when to say "done", and what a retry does to the order of events.

## Ack first: a crash loses the job

<InteractiveCanvas slug="sysdesign-m15-ack-first" />

The worker gets "credit 18" and acknowledges at once. The queue deletes the job. The worker crashes before it pays. The queue has nothing to resend. The credit is lost for good. This is at most once: never repeated, but sometimes lost.

<GoDeeper title="Go deeper: at most once, in practice">

Kafka's documentation names three delivery semantics. At most once: messages may be lost but are never redelivered. At least once: messages are never lost but may be redelivered. Exactly once: each message is processed once and only once [S82].

On the consumer side, you choose between the first two with one decision: do you commit the offset (or ack) before the work, or after it? Before the work gives at most once. If the worker crashes after the ack and before the work, nobody will ever retry that message.

When is that the right choice? When a lost message costs less than a repeated one, or when the work cannot be repeated safely and cannot be made idempotent. A metrics sample, a "user is typing" signal, or a cache warm-up can be lost. A credit to a wallet usually cannot.

</GoDeeper>

## Ack last: a crash repeats the job

<InteractiveCanvas slug="sysdesign-m15-ack-last" />

Now the worker pays first and acks after. It pays 18 and crashes before the ack. The queue never saw the ack, so after a timeout it sends the job again. The wallet is paid twice: 36. This is at least once: never lost, sometimes repeated.

<GoDeeper title="Go deeper: why most systems choose at least once">

Kafka guarantees at least once by default [S82], and SQS standard queues deliver at least once [S83]. The reason is the one from chapter 14.5: a repeat can be made harmless, and a loss cannot be repaired. So the usual recipe is: ack after the work, and make the work safe to repeat with an idempotency key or a dedupe table in the same transaction as the effect.

Exactly once is not a delivery promise. It is the result of at least once plus an idempotent consumer. Kafka's exactly-once support covers reading, processing and writing inside Kafka, using idempotent producers and transactions. Once the effect leaves Kafka, for example into a database or an email service, the consumer must cooperate [S82]. In challenge 14, part 2, you run all three handlers (ack first, work then ack, and work then ack with a one-step claim) while workers crash, and count lost and doubled jobs.

</GoDeeper>

## A retry can swap two events

<InteractiveCanvas slug="sysdesign-m15-retry-reorder-play" />

Make the first send fail and watch the log. The retry lands after the second update, so the final state is wrong. Then switch on "one at a time": the producer waits for each ack before it sends the next, and the order holds, at the price of speed.

<GoDeeper title="Go deeper: three ways to keep order through a retry">

A retry reorders when two sends are in flight at once. The first fails and is sent again, while the second goes through. Nothing in a plain log stops this: the log writes what it receives, in the order it receives it.

There are three standard defences. First, send one at a time per key and wait for the ack. It is simple and correct, and it limits throughput to one round trip per event per key. Second, let the broker detect gaps. Kafka's idempotent producer gives each producer an ID and each message a sequence number, and the broker uses the sequence number to remove duplicates [S82]. Check the producer settings of your Kafka version for what it promises about order when several requests are in flight.

{/* source needed: what Kafka's idempotent producer guarantees about ordering with several in-flight requests, from the producer configuration documentation (not in the dossier). */}

Third, make order unimportant. If each event carries a version or sequence number for its order, the consumer can ignore any event that is older than the one it already applied. "Set status to refunded, version 7" arriving after "version 8" is simply skipped. This is the same idea as the per-entity sequence number in chapter 14.5, and it works with any broker.

The same trap exists on the consumer side. If a consumer fails on an event and puts it on a retry queue while it goes on to the next event for the same key, the retry arrives later and swaps the order. Chapter 15.5 returns to this, and the challenge counts the swaps.

</GoDeeper>

## The key picks the partition

<InteractiveCanvas slug="sysdesign-m15-key-routes" />

The shop sends events with a key, here the customer's name. Layla's events always go to partition 0 and Omar's to partition 1. Inside each partition, events keep the order they were written. The same key always goes to the same partition, so one customer's events stay in order.

<GoDeeper title="Go deeper: how the partition is chosen">

The producer picks a partition by hashing the key and taking the remainder after dividing by the number of partitions, the same idea as hash partitioning in chapter 9.2. Kafka states the guarantee in these words: events with the same key are written to the same partition, and a consumer of that partition reads the events in exactly the order they were written [S81]. Kinesis does the same with a partition key that selects a shard, and a sequence number on each record [S132]. SQS FIFO queues use a message group ID: messages in one group are processed in order, and different groups are processed in parallel [S84].

Ordering is a promise per key, so the key must be the thing whose events must be in order. For an order system, the order ID keeps one order's events in order. The customer ID keeps all of one customer's orders in order, which is stronger and also puts more events on one partition.

</GoDeeper>

## Choose a key: order against balance

<InteractiveCanvas slug="sysdesign-m15-partition-key-play" />

Pick a key and watch two things at once: whether related events stay in order, and how evenly the four partitions are loaded. A key that spreads well may split related events. A key that keeps related events together may overload one partition.

<GoDeeper title="Go deeper: the trade-offs of each key">

Take 1,000 events from an order system and 4 partitions. With the **order ID** as key, one order's events stay in order, and because there are many orders, the load is even. Events of different orders for the same customer are not ordered against each other, which is usually fine. With the **customer ID**, all of a customer's events are ordered, and a single very busy customer makes a hot partition, the problem from chapter 9.4. With the **country**, a small number of values means a few huge partitions and idle ones: it keeps no useful order and balances badly. With **no key**, the producer spreads events evenly, and nothing is ordered.

Ask two questions of any key. What must stay in order? Pick the smallest thing: usually one order, one conversation, one account. And how skewed is the key? Count the events per key value and look at the biggest. If one key could be 30% of the load, no partitioning scheme will spread it, and you need a different design: for example, split the hot key into sub-keys and accept that its order is only kept within each sub-key.

Changing the number of partitions later changes where keys land, so an order may continue on a new partition while its older events sit on an old one. Plan the partition count early (chapter 15.3).

</GoDeeper>

## Order holds per key, not across keys

<InteractiveCanvas slug="sysdesign-m15-order-per-key" />

A reader takes events from two partitions. It sees omar 1, layla 1, layla 2, omar 2. Each customer is in order, but there is no order between the customers. Order is a promise inside a partition, not across partitions.

<GoDeeper title="Go deeper: when you really need one global order">

A global order means one partition and one reader. That caps the throughput at what one consumer can do, and it makes the reader a single point of waiting. It is sometimes right, for example for a small ledger of rare, important events. Most designs do not need it, because most events only need to be ordered against related events.

If two events for different keys must be ordered, look for the real relationship. "Create the order, then pay it" are two events for the same order, and they should share the key. If the relationship spans keys, such as a transfer between two accounts, put the transfer in one event, or use an ordering id from a single writer, or handle it with a saga (chapter 14.3). Do not rely on arrival order across partitions: it changes between runs, as the picture shows.

</GoDeeper>
