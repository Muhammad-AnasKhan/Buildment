In chapter 15.6 you moved a watermark by hand and watched windows close, late events get counted, and very late events get set aside. The machine behind that picture is small. It needs a map from window start to a count, one number for the newest event time it has seen, and three rules. Each rule is easy to get slightly wrong, and a slightly wrong version passes every test that sends events in perfect order.

In this chapter you write that machine in plain JavaScript. By the end you have one tested function, `createAggregator`. In challenge 14 you will feed the same kind of events through a real stream, so it pays to get the logic right here, where a failing test costs a second.

## What the tests do to your code

Out-of-order events are the whole point, so the tests send them on purpose. They send an event that is a little late but still before the watermark. They send one that arrives after its window closed. They send one so late that it is past the allowed lateness. They send an old event after a new one and check that the watermark does not move back. Each test tells you in words which rule you broke.

The function is not `async`, has no timer and never reads the clock. Time here is event time, the number inside each event. That is what makes the tests exact: the same events always give the same answer.

## The contract

`createAggregator({ windowMs, maxDelayMs, allowedLatenessMs })` returns an object. `windowMs` is the size of each tumbling window in milliseconds and must be a finite number above 0, or the function throws a `RangeError`. `maxDelayMs` (default 0) is how far behind the newest event time the watermark runs. `allowedLatenessMs` (default 0) is how long after a window closes it still accepts late events. Both must be finite numbers of 0 or more, or a `RangeError` is thrown.

The object has four methods.

**`add(event)`** takes `{ time, value }`. `time` is the event time in milliseconds and must be a finite number, or `add` throws a `TypeError`. `value` is optional and counts as 0 when it is missing. The event belongs to the window that starts at `Math.floor(time / windowMs) * windowMs` and ends `windowMs` later. A window includes its start and excludes its end, so time 59,999 is in the window from 0 and time 60,000 is in the window from 60,000.

Before `add` changes anything, it reads the watermark as it was when the event arrived. The watermark is the newest event time seen so far minus `maxDelayMs`, or `null` if no event has been seen. Then `add` decides one of three outcomes and returns `{ status, windowStart }`. If the watermark is `null`, or is below the window's end, the status is `"counted"`. If the watermark is at or past the window's end, the window is closed. If it is still below the end plus `allowedLatenessMs`, the status is `"late"`: the event is added to the window anyway. If it is at or past the end plus `allowedLatenessMs`, the status is `"dropped"`, the event is not added, and the dropped counter goes up by one. After that, `add` updates the newest event time if this event is newer. An old event never moves it back.

**`watermark()`** returns the current watermark, or `null` before the first event.

**`droppedCount()`** returns how many events were dropped.

**`windows()`** returns an array with one entry per window that has at least one event, sorted by start. Each entry is `{ start, end, count, sum, closed }`. `sum` adds up the `value` of the events in the window. `closed` is true when the watermark is at or past the window's end, and false otherwise, including when there is no watermark yet.

## A worked example: orders per 10 seconds

Here is the machine applied by hand to a case that is not in the tests. Take `windowMs` 10,000, `maxDelayMs` 4,000 and `allowedLatenessMs` 6,000. Seven events arrive in this order, with these event times: 3,000, 12,000, 9,500, 15,000, 9,000, 25,000 and 8,000.

| Arrives | Time | Watermark before | Window | Outcome | Watermark after |
|---|---|---|---|---|---|
| 1 | 3,000 | none | 0 to 10,000 | counted | -1,000 |
| 2 | 12,000 | -1,000 | 10,000 to 20,000 | counted | 8,000 |
| 3 | 9,500 | 8,000 | 0 to 10,000 | counted, watermark 8,000 is below 10,000 | 8,000 |
| 4 | 15,000 | 8,000 | 10,000 to 20,000 | counted | 11,000 |
| 5 | 9,000 | 11,000 | 0 to 10,000 | late, 11,000 is at least 10,000 but below 16,000 | 11,000 |
| 6 | 25,000 | 11,000 | 20,000 to 30,000 | counted | 21,000 |
| 7 | 8,000 | 21,000 | 0 to 10,000 | dropped, 21,000 is at least 16,000 | 21,000 |

Event 3 arrived after event 2, so it came out of order, but the watermark had not reached the end of its window yet, so it counts normally. That is what `maxDelayMs` buys. Event 5 came after window 0 to 10,000 closed at event 4, but only 1,000 ms after the end, so it still gets in, and a reader of that window would have to accept a corrected number. Event 7 came 11,000 ms after the end, past the 6,000 of allowed lateness, so it is set aside. The final windows are 0 to 10,000 with count 3, 10,000 to 20,000 with count 2 and 20,000 to 30,000 with count 1. Windows 0 and 10,000 are closed, and window 20,000 is open because the watermark 21,000 has not reached 30,000.

## Five ways this goes wrong

**Mixing up closed and dropped.** A window is closed when the watermark reaches its end. An event for a closed window is not dropped yet: it is dropped only when the watermark has also passed the end plus the allowed lateness. The tests use watermarks that sit exactly on both lines.

**Letting the watermark move back.** An old event has a smaller time than the newest one seen. If you set the newest time to every event's time, the watermark falls, closed windows look open again and results change. Keep the maximum.

**Closing a window one millisecond early or late.** A window ends before its end time, so it is closed when the watermark is at or past the end, not above it. The tests use a watermark that equals the end exactly.

**Adding a dropped event anyway.** A dropped event must not change any window. If it does, a window that was already sent to a reader changes after the fact, and the counter that says how many you dropped no longer matches the data.

**Forgetting that the first event has no watermark.** Before any event, the watermark is `null`, and `null` compared with a number gives surprising answers in JavaScript. Treat `null` as "nothing is closed yet".

When a test fails, read its message first. Each one names the input, what it expected and what your code returned.

solution: |
  function createAggregator({ windowMs, maxDelayMs = 0, allowedLatenessMs = 0 } = {}) {
    if (typeof windowMs !== "number" || !Number.isFinite(windowMs) || windowMs <= 0) {
      throw new RangeError("windowMs must be a finite number above 0");
    }
    for (const [name, value] of [["maxDelayMs", maxDelayMs], ["allowedLatenessMs", allowedLatenessMs]]) {
      if (typeof value !== "number" || !Number.isFinite(value) || value < 0) {
        throw new RangeError(name + " must be a finite number of 0 or more");
      }
    }
    const windows = new Map(); // start -> { count, sum }
    let newest = null;
    let dropped = 0;
    const watermark = () => (newest === null ? null : newest - maxDelayMs);
    return {
      add(event) {
        if (!event || typeof event.time !== "number" || !Number.isFinite(event.time)) {
          throw new TypeError("event.time must be a finite number");
        }
        const value = typeof event.value === "number" ? event.value : 0;
        const start = Math.floor(event.time / windowMs) * windowMs;
        const end = start + windowMs;
        const mark = watermark(); // as it was when the event arrived
        let status = "counted";
        if (mark !== null && mark >= end + allowedLatenessMs) status = "dropped";
        else if (mark !== null && mark >= end) status = "late";
        if (status === "dropped") {
          dropped++;
        } else {
          const w = windows.get(start) ?? { count: 0, sum: 0 };
          w.count++;
          w.sum += value;
          windows.set(start, w);
        }
        if (newest === null || event.time > newest) newest = event.time;
        return { status, windowStart: start };
      },
      watermark,
      droppedCount: () => dropped,
      windows() {
        const mark = watermark();
        return [...windows.entries()]
          .sort((a, b) => a[0] - b[0])
          .map(([start, w]) => ({ start, end: start + windowMs, count: w.count, sum: w.sum, closed: mark !== null && mark >= start + windowMs }));
      },
    };
  }

## Check your understanding before you submit

Run one more case in your head with your code. Make an aggregator with `windowMs` 60,000, `maxDelayMs` 0 and `allowedLatenessMs` 0. Add an event at time 10,000, then one at 130,000, then one at 20,000. The first is counted. The second is counted and moves the watermark to 130,000, which closes windows 0 and 60,000 (the second one is empty and does not appear in `windows()`). The third is dropped, because 130,000 is past the end of window 0 and there is no allowed lateness. `droppedCount()` is 1 and window 0 still has a count of 1.

Now change only `allowedLatenessMs` to 120,000 and run it again. The third event is now `"late"`, because 130,000 is past 60,000 but not past 60,000 + 120,000. Window 0 shows a count of 2 and is closed. A reader who already saw window 0 with a count of 1 now has a stale number, which is the cost of allowing lateness.

## What this unlocks

In challenge 14 the events come from a stream instead of an array, but the three rules do not change. In module 16 you will see the same trade-off again in a different form: how long to wait for a slow answer before you act. Here the wait is `maxDelayMs`. A larger value loses fewer events and answers later. A smaller value answers sooner and loses more. There is no free setting, only one you can explain.
