Zaytoun Market sends a receipt email for every order. One order has a customer email address with a typo. The email service rejects it every time. This chapter is about what that one message does to everything behind it, and how to stop it.

## One bad message stops the line

<InteractiveCanvas slug="sysdesign-m15-poison-blocks" />

The consumer handles m1 fine. Message m2 has a bad address and fails. The consumer must keep order, so it retries m2 and does not start m3 or m4. A message that always fails is called a <GlossaryTerm term="poison message" definition="A message that fails every time it is processed, for example because its data is bad. Left alone, it is retried for ever and blocks the messages behind it." />.

<GoDeeper title="Go deeper: why the whole partition waits">

In a log, a consumer moves an offset forward. If it must keep order, it cannot move the offset past a message it has not finished. So when m2 fails, the choices are to retry m2, to stop, or to skip it. Retrying in place is the default in many consumers, and it turns one bad message into a stalled partition.

A queue is kinder. When a worker fails on a job, the job returns after the visibility timeout and other workers take the next jobs. The bad job keeps coming back, but it does not block the others [S84]. SQS FIFO queues are different: messages in one message group are processed in sequence, so a failing message holds back its group [S84]. The rule is the same in every system: ordering and skipping cannot both be free.

The stalled partition has a visible sign. The backlog grows, and the age of the oldest message grows with it, while the consumer looks busy. A consumer that is busy retrying one message is not making progress.

</GoDeeper>

## Wait in place, or park it

<InteractiveCanvas slug="sysdesign-m15-poison-play" />

Message 10 always fails. With the dead letter queue off, everything behind it waits for ever. Switch the queue on and pick a retry limit: after that many tries the message is parked and the line moves on. A bigger limit keeps the line stuck longer. Now make message 10 fail twice, then work, and set the limit to 2: a good message is parked too soon.

<GoDeeper title="Go deeper: what a dead letter queue is, and the numbers from the challenge">

A <GlossaryTerm term="dead letter queue" definition="A separate queue where a message is put after it has failed too many times. It keeps the message and the reason for a person or a repair job to look at, so the main line can move on." /> (DLQ) is a second queue for messages that could not be processed. In SQS you set a redrive policy with a `maxReceiveCount`: the number of times a consumer can receive a message before it moves to the dead letter queue [S85]. Streams such as Kafka or Valkey have no DLQ built in. You build one: count the deliveries or attempts, and after the limit write the message and the error to another stream, then ack the original.

{/* source needed: Valkey streams docs (https://valkey.io/topics/streams-intro/, read 2026-10-24): XPENDING shows a delivery count per entry, and once it reaches a threshold the page suggests moving the entry to another stream, which it calls the way streams implement the dead letter concept. */}

In challenge 14, part 3, 100 jobs run through one consumer: 5 always fail, 10 fail twice and then work, 85 are healthy. One run on a Windows laptop looked like this:

```text
mode                              ok  dead  stuck  healthy done  last healthy at s  out of order
retry in place, forever            9     0     91             8                0.4             0
retry in place, then dead letter  95     5      0            85                8.1             0
retry later, then dead letter     95     5      0            85                3.7            10
```

The first row is the blocked partition: 91 jobs never finish. The second row parks the 5 poison jobs after 5 tries, but each one makes the line wait through its whole backoff, so the last healthy job finishes at 8.1 seconds. The third row moves a failing job to a retry set and goes on, so the last healthy job finishes at 3.7 seconds. The price is in the last column: 10 jobs finished after a job with a higher number, which means out of order. That is the reorder from chapter 15.4. If order matters for these jobs, use the second row. If it does not, use the third.

</GoDeeper>

## Wait longer after each failure

<InteractiveCanvas slug="sysdesign-m15-backoff-waits" />

The mail service is down. The worker tries at second 0, waits 1 second, tries again, waits 2 seconds, then 4 seconds. Each wait is double the last. By the fourth try, at second 7, the service has had time to recover. Retrying at once, again and again, would only add load.

<GoDeeper title="Go deeper: the backoff formula">

Exponential backoff means each wait is a fixed multiple of the one before. A common form is `delay = min(cap, base x 2^(attempt - 1))`. With a base of 1 second and no cap, the waits are 1, 2, 4, 8 and 16 seconds. The cap stops the waits from growing without limit; a delay of an hour is rarely useful [S89, S90].

```js
// Partial: the delay before try number `attempt` (1, 2, 3 ...).
function backoffDelay(attempt, { baseMs = 100, capMs = 2000 } = {}) {
  return Math.min(capMs, baseMs * 2 ** (attempt - 1));
}
console.log([1, 2, 3, 4, 5, 6].map((n) => backoffDelay(n))); // [ 100, 200, 400, 800, 1600, 2000 ]
```

Pick the maximum number of tries so the total wait fits the job. Five tries with these numbers wait 100 + 200 + 400 + 800 = 1,500 ms in total. For an email, you may allow hours. For a payment shown on a screen, you may allow two seconds.

</GoDeeper>

## The same wait means the same moment

<InteractiveCanvas slug="sysdesign-m15-retry-herd" />

Three workers failed together because the database was down. Each waits exactly 2 seconds. When the 2 seconds are over, all three retry at the same instant. The database, still recovering, gets three requests at once and can fall over again. With hundreds of workers the crowd is hundreds.

<GoDeeper title="Go deeper: the retry crowd">

Backoff alone keeps clients in step. If 200 clients fail at the same moment and use the same schedule, they retry at the same moments for ever: at 0.5 seconds, 1.5, 3.5 and so on, in waves. Marc Brooker measured the effect and found that adding random waits (jitter) reduces the work and the clumping of retries [S90]. The Google SRE book also advises backoff, retry budgets and deadlines for retries [S91].

In challenge 14, part 3, a small program lets 200 clients fail together and retry 5 times, with waits that start at 500 ms. Without jitter the busiest 50 ms receives 200 retries, the whole crowd. With full jitter it receives 35:

```text
no jitter:   the busiest 50 ms gets 200 retries
full jitter: the busiest 50 ms gets 35 retries
```

</GoDeeper>

## A random wait spreads them out

<InteractiveCanvas slug="sysdesign-m15-retry-jitter" />

The same three workers now wait a random time. Their retries reach the database at 1.2, 2.0 and 2.9 seconds. It handles one at a time and stays up. The average wait is the same or shorter, and the crowd is gone.

<GoDeeper title="Go deeper: full jitter in one line">

With full jitter, the wait is a random time between 0 and the doubled ceiling: `wait = random() x min(cap, base x 2^(attempt - 1))`. Brooker compared full, equal and decorrelated jitter and found full jitter a good simple choice [S90]. Jitter has a price: a single client's wait is unpredictable, and it can be very short. That is fine for retries, where no one is waiting for a specific time.

Jitter belongs on every retry that many clients may do at once: a reconnect after an outage, a retry after a failed publish, a consumer that restarts after a deploy. A consumer that retries a message queue has one more reason: if the queue holds a delayed retry for each failure, the retry time is stored as a score, and jitter spreads the stored times.

</GoDeeper>

## Retry at one layer only

<MermaidDiagram title="Retries multiply across layers" chart={`flowchart LR
  A["Layer 1 tries 3 times"] --> B["Layer 2 tries 3 times"]
  B --> C["Layer 3 tries 3 times"]
  C --> D["Layer 4 tries 3 times"]
  D --> E["Layer 5 tries 3 times"]
  E --> F["Database: up to 3 x 3 x 3 x 3 x 3 = 243 attempts"]
`} legend="Each layer retries on its own. When the database is down, one request becomes 243 attempts at the bottom." />

If every layer retries three times, a five-layer call stack sends up to 243 attempts to the database for one request. In an example from Brooker, that is 243 times the load, on the one component that is already failing. Choose one layer to retry, usually the one nearest the user, and let the others fail fast.

<GoDeeper title="Go deeper: retry budgets, and queue consumers">

Brooker gives this example: with a stack five deep and three tries at each layer, the database can see 3 to the power of 5, which is 243 times the normal load [S89]. The Google SRE book has a similar example, three layers with four attempts each, which gives 64 attempts at the bottom [S91]. Bronson and colleagues describe how retry-driven work can keep a system down even after the original trigger is gone, a metastable failure [S94].

Defences: retry at one layer, put a budget on retries (for example, retries may be at most 10% of requests), use backoff with jitter, and use a deadline so work that nobody waits for is dropped. Chapter 16.4 returns to this for requests. For queue consumers the same rules apply, with one more: a limit on the number of tries per message, after which it goes to the dead letter queue.

</GoDeeper>

## Park the bad message and move on

<InteractiveCanvas slug="sysdesign-m15-dlq-parks" />

The consumer tries m2 three times and fails each time. It then moves m2, with the reason, to the dead letter queue and reads m3. The line moves on, and the bad message is saved instead of lost.

<GoDeeper title="Go deeper: a dead letter queue is not a bin">

A DLQ that nobody looks at is a bin with a label. Treat it as a work queue for people. Alarm on its depth, so the first parked message raises a notification. Store the reason and the number of attempts with each message. Decide in advance what a person does: fix the data and send the message again, fix the code and replay everything in the DLQ, or discard it on purpose and write down why.

SQS supports moving messages back with a redrive. Set the DLQ's retention longer than the source queue's, because the original enqueue time is kept for standard queues, and a message that is already old can expire soon after it arrives in the DLQ [S85]. SQS also warns against using a DLQ with a FIFO queue when you need to keep the exact order of operations, since the parked message breaks the sequence [S85]. Redrive puts messages back in the line, so a consumer must be idempotent (chapter 14.5). A DLQ is also the right answer to the question "what if the retry never works?" Without it, the only answers are "block" or "lose".

</GoDeeper>
