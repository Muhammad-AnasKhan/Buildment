Zaytoun Market wants a live board: how many orders were placed in each minute? Orders come from stall tablets, some on weak connections. A log holds the events. A stream processor reads them and counts. The hard part is deciding when a minute is finished.

## When it happened is not when it arrived

<InteractiveCanvas slug="sysdesign-m15-event-vs-arrival" />

A tablet records a sale at 0:50, loses its signal, and sends the sale at 2:10. The counter hears about it 80 seconds late. Counting by arrival puts the sale in the wrong minute. Counting by event time, the time on the device when the sale happened, puts it in the right one.

<GoDeeper title="Go deeper: event time and processing time">

Stream engines separate two clocks. <GlossaryTerm term="Event time" definition="The time at which an event happened on the device that made it, such as the time a sale was recorded on a tablet." /> is when the event happened. Processing time is the clock of the machine that handles the event. Counting by processing time is simple and always has an answer: when the minute ends on the machine, the count is done. But the result changes with network delays and with replays, because replaying yesterday's events today puts them all in today's minutes.

Counting by event time gives the same answer for the same events, however late or in whatever order they arrive. That is what you want for orders per minute. The price is the question this chapter answers: if events can arrive late, how do you know a minute is complete?

{/* source needed: Flink time concepts page (https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/time/, read 2026-10-24): processing time is the system time of the machine executing the operation, event time is the time each event occurred on its producing device. */}

Event time comes from the device clock, so it can be wrong, with all the problems of module 10. A tablet with a clock that is a day off puts its events in the wrong day. Some systems add a server receive time and compare the two, and drop or flag events whose device time is far from the receive time.

</GoDeeper>

## Three ways to cut time into windows

<InteractiveCanvas slug="sysdesign-m15-window-shapes-play" />

A window is a slice of time that you count. Tap a shape. Tumbling windows are fixed and never overlap: each event is in one. Sliding windows are fixed length but start more often, so they overlap and an event can be in several. Session windows follow activity: a gap of silence ends one.

<GoDeeper title="Go deeper: which window for which question">

The Flink documentation defines the shapes in these words: tumbling windows have a fixed size and do not overlap; sliding windows have a fixed length and start every "slide", so they overlap when the slide is smaller than the size; session windows group events by sessions of activity, and a session closes after a period with no events [S87].

Match the shape to the question. "Orders per minute" is a tumbling window of 1 minute. "Orders in the last 5 minutes, refreshed every minute" is a sliding window of 5 minutes with a slide of 1 minute: each order counts in 5 windows. "How long did each customer's visit last?" is a session window with a gap, say 30 minutes of silence, because visits have no fixed length. Flink also has a global window, which covers everything and needs a rule of your own for when to fire [S87].

Sliding windows cost more. With a 5 minute window and a 1 minute slide, each event is added to 5 windows, so the work and memory are 5 times as large as with a tumbling window of the same speed. Session windows are the hardest to compute, because two sessions can merge when a late event fills the gap between them.

</GoDeeper>

## The watermark says: time has passed

<InteractiveCanvas slug="sysdesign-m15-watermark-advances" />

Events arrive with times 30, 55 and 70. The counter keeps a watermark: its claim that time has reached a point. Here the watermark is the newest event time minus 10 seconds. When it reaches 60, the end of the first window, the window from 0 to 60 closes and its count is final.

<GoDeeper title="Go deeper: what a watermark promises">

<GlossaryTerm term="Watermark" definition="A number that a stream processor keeps. A watermark of t says that event time has reached t, so no more events with a time at or before t are expected. Windows that end before it can close." /> is described in the Flink documentation: a watermark of t declares that event time has reached t in the stream, and means there should be no more elements with a timestamp at or before t. {/* source needed: Flink time concepts page (read 2026-10-24): "A Watermark(t) declares that event time has reached time t in that stream", meaning there should be no more elements with a timestamp t' <= t. */}

A window fires once the watermark passes its end. It is a promise, not a fact: nothing stops an event with an older time from arriving afterwards. Such an event is late.

How do you produce a watermark? The simplest rule is bounded out-of-orderness: the watermark is the highest event time seen so far, minus a bound. The Flink example computes it exactly like that, as the current highest timestamp minus the out-of-orderness bound. With a 10 second bound, you promise that events are never more than 10 seconds out of order. The code exercise in chapter 15.8 uses this rule with a parameter `maxDelayMs`.

{/* source needed: Flink generating-watermarks page (https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/event-time/generating_watermarks/, read 2026-10-24): the periodic generator emits the current highest timestamp minus the out-of-orderness bound. */}

</GoDeeper>

## Drag the delay: fast or complete

<InteractiveCanvas slug="sysdesign-m15-watermark-delay-play" />

Drag the watermark delay. A short delay closes each window soon, so results come fast, but late events find the window already closed and are dropped. A long delay waits for stragglers and keeps more events, but every result comes later. There is no setting that is fast and complete.

<GoDeeper title="Go deeper: the trade-off, in numbers you can reason about">

The delay is the lever. Every window result is produced when the watermark passes its end, which is the delay after the newest event for that window arrives. So the delay is added to the age of every result: a 30 second delay means the live board is at least 30 seconds behind. In exchange, an event is counted if it arrives less than the delay after the newest event time seen.

To choose, measure the lateness of your events: for each event, the difference between its arrival time and its event time. Look at the distribution as you did for latency in chapter 2.4. If 99% of events are less than 20 seconds late and 1% are minutes late, a delay of 20 seconds counts 99% in the first result, and the rest need another rule (the next beat). A delay at p99.9 may be a minute, which makes the board feel slow for a gain of 0.9%.

The Flink documentation names the cost: event-time processing incurs some latency while waiting for out-of-order events, and delaying the watermarks too much is often not desirable, because it slows the evaluation of the windows.

{/* source needed: Flink time concepts page (read 2026-10-24): "event time processing incurs some latency while waiting for out-of-order events" and "delaying the watermarks by too much is often not desirable". */}

</GoDeeper>

## Late events: fix the count or set aside

<InteractiveCanvas slug="sysdesign-m15-late-rule" />

The window 0 to 60 is closed and shows 12. A late event arrives at watermark 75, within 30 seconds of the window's end, so the count is corrected to 13. A very late one arrives at watermark 95, past that limit, and goes to a side bin instead. The 30 seconds is called the allowed lateness.

<GoDeeper title="Go deeper: allowed lateness, late firings and side outputs">

Flink's default allowed lateness is 0: once the watermark passes the end of a window, later events for it are dropped. With a larger value, an event that arrives after the watermark passes the window's end, but before the end plus the allowed lateness, is still added to the window. This can make the window fire again, a late firing, with an updated result. The window and its state are removed once time passes the end plus the allowed lateness [S87]. You can also collect the dropped late events in a side output, a separate stream for audit, repair or a slower batch fix [S87].

Three things follow for your design. First, readers of a result must accept corrections: the number for 12:00 can change after it was shown. A dashboard can update in place, but a message sent to another system needs a way to say "replace the previous value". Second, allowed lateness costs memory, because the window must be kept until it is removed. Third, the side output is where you learn how many events you lose. Count it, and graph it. If it is more than you accept, raise the delay or the allowed lateness.

</GoDeeper>

## One silent input holds the watermark back

<InteractiveCanvas slug="sysdesign-m15-idle-partition" />

Two partitions feed the counter. Partition 0 sends events up to time 200. Partition 1 has been silent since 60. The counter's watermark is the smaller of the two, so it stays at 60. No window after 60 can close, however many events the busy partition sends.

<GoDeeper title="Go deeper: the minimum rule and idle inputs">

An operator with several inputs takes its event time from the slowest one: its current event time is the minimum of its input streams' event times. The minimum is the safe choice, because a watermark that was higher than one input's would promise something that input might break. The cost is the picture: a silent input stalls everything.

{/* source needed: Flink time concepts page (read 2026-10-24): "Such an operator's current event time is the minimum of its input streams' event times." Flink generating-watermarks page (read 2026-10-24): an idle input holds the watermark back, because it is the minimum over the parallel watermarks, unless the strategy marks it idle (withIdleness). */}

Silent inputs are common: a topic with 12 partitions and keys that rarely appear in some, or a stall that closes at night. Stream engines let you mark an input as idle after a timeout, so it stops holding back the watermark. The timeout is another trade-off. A short one frees the watermark fast, but if the input then sends old events, they are late. A long one keeps the board stuck. Whichever you choose, monitor the watermark itself: a watermark that stops while events keep arriving is a clear sign of an idle input.

</GoDeeper>
