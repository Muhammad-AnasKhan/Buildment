Zaytoun Market now has three things to do for every order: send a confirmation email, save a receipt, and count the sale. The order service could call all three. This chapter shows why it should not, and what it does instead.

## One event, many subscribers

<InteractiveCanvas slug="sysdesign-m15-fanout-one-event" />

The order service publishes one event, OrderPlaced, to a topic. The topic gives a copy to Email, Receipts and Stats. Each does its own job. The order service moved on the moment it published. This is publish and subscribe, and sending one event to many receivers is fan-out.

<GoDeeper title="Go deeper: topics, subscriptions and what each one gets">

A <GlossaryTerm term="topic" definition="A named channel that publishers send events to. Every subscriber to the topic gets its own copy of each event." /> is a channel with a name. Publishers write to it. Subscribers register with it, and each subscriber gets every event. The publisher does not know who the subscribers are, or how many. Adding a subscriber needs no change to the publisher.

Two designs do this in practice. In a log, such as Kafka, each subscriber is a consumer group with its own offsets, and every group reads every event (chapter 15.3). In a queue system, a topic copies each event into one queue per subscriber. On AWS, an SNS topic with an SQS queue subscribed for each application does exactly this: publish once to the topic, and SNS sends a message to each subscribed queue, where it stays until the application processes it.

{/* source needed: SNS to SQS fan-out page (https://docs.aws.amazon.com/sns/latest/dg/sns-sqs-as-subscriber.html, read 2026-10-24): when an SQS queue is subscribed to an SNS topic, a message published to the topic is sent as an SQS message to the subscribed queue, and messages persist in the queue for other applications to process later. */}

Compare this with the alternative, a direct call to each service. The order service would know about Email, Receipts and Stats, would wait for each one, and would fail or slow down if any one did. Fan-out through a topic turns "the order service knows three services" into "the order service knows one topic".

</GoDeeper>

## One slow subscriber, two designs

<InteractiveCanvas slug="sysdesign-m15-slow-subscriber-play" />

Drag Receipts' speed down. With the order service calling each subscriber in turn, every order now waits for the slow one, and the other two fall behind with it. With a queue for each subscriber, orders stay fast, and only Receipts' own queue grows. Switch between the designs and compare.

<GoDeeper title="Go deeper: the numbers in the picture">

The picture uses the numbers from the prediction: 20 events per second arrive, Email and Stats need about 33 ms per event (30 per second), and Receipts needs 167 ms (6 per second).

With direct calls in a row, one order takes about 33 + 33 + 167 = 233 ms of waiting, so one worker can place only about 4 orders per second. At 20 orders per second the order service needs about 5 workers just to wait, and when Receipts slows further, the whole order path slows with it. By Little's law: in flight = 20 per second x 0.233 s, about 5 requests, always held open.

With a queue for each subscriber, the order service writes one event and answers in a few milliseconds. Email and Stats read from their own queues and stay empty. Receipts' queue grows by 14 events per second. Its backlog is a problem for Receipts, which you can see on its own queue graph, and not a problem for orders or for the other subscribers. The fix is to add Receipts workers or make the job faster. Chapter 15.2 sized workers with Little's law, and the same sum applies to each subscriber on its own.

The price of the second design is that every subscriber's work is eventual. Receipts is minutes behind, and a customer who opens the receipt page at once may not find it. The page must say so, or read the receipt from a place that is filled in the request (chapter 15.2, the question about the user).

</GoDeeper>

## Each subscriber has its own line

<InteractiveCanvas slug="sysdesign-m15-fanout-isolated" />

Receipts fails on an event and retries. Email carries on with the next event. Each subscriber has its own queue, its own retries and its own dead letter queue, so when Receipts parks a bad event in its own dead queue, no other subscriber is touched.

<GoDeeper title="Go deeper: what is separate, and what must be shared">

Give each subscriber its own queue, its own retry settings and its own dead letter queue. A dead letter queue belongs to a source queue [S85], so a shared queue would mix the failures of different jobs, and one team's bad event would block another team's good ones. Each subscriber also gets its own alarms: backlog, age of the oldest event, dead-letter depth.

What must be shared is the event itself. All subscribers see the same fields, so the publisher owns a stable shape for it. Add fields freely, since old subscribers ignore them. Do not rename or remove a field without a plan, because you cannot know every subscriber. A version field helps; so does a short list of subscribers kept by the publisher's team, even if the code does not need it.

Delivery is at least once for every subscriber (chapters 15.4 and 14.5), so each one needs its own idempotent handling. The event carries a unique id, and each subscriber uses it to skip copies, in its own dedupe store. Do not share a dedupe table across subscribers: Email having handled event 42 says nothing about Receipts.

</GoDeeper>

## Say what happened, not what to do

<MermaidDiagram title="A command and an event" chart={`flowchart LR
  subgraph CMD["A command: the sender knows the receiver"]
    C1["Orders"] -->|"SendReceiptEmail to Layla"| C2["Email service"]
  end
  subgraph EVT["An event: the sender knows only what happened"]
    E1["Orders"] -->|"OrderPlaced: order 42, Layla, 3 items"| E2["Topic"]
    E2 --> E3["Email"]
    E2 --> E4["Receipts"]
    E2 --> E5["Stats"]
  end
`} legend="A command names the receiver and the action. An event names a fact. New subscribers can use a fact without any change to the sender." />

A command says what the receiver must do, and so the sender must know the receiver. An event says what happened: OrderPlaced, with the order id and its details. Any number of subscribers can decide what that means for them. Name events in the past tense, as facts that cannot be taken back.

<GoDeeper title="Go deeper: how much to put in an event">

There are two styles. A thin event carries little: the order id and a type. Subscribers call back to the order service for the rest. It keeps messages small and sensitive data out of the topic, but it brings back a dependency: every subscriber calls the order service, which makes it the weak point you tried to remove, and the data may have changed by the time they call. A fat event carries what subscribers need: the items, the totals, the customer id. Subscribers work alone, but the event is bigger, and you must think about personal data, since every subscriber and every copy in a log holds it for the retention period.

A good middle path is to put in the event the facts that were true at that moment and that most subscribers need, and leave out secrets and anything large. Include an event id that never repeats, a time for when it happened (event time, chapter 15.6) and a version of the shape. These three make idempotent handling, windows and safe change possible.

</GoDeeper>

## The whole path, from order to receipt

<MermaidDiagram title="Order events end to end" chart={`flowchart LR
  A["Order service"] -->|"one transaction"| B[("Orders table and outbox table")]
  B -->|"relay publishes, maybe twice"| T["Topic: OrderPlaced"]
  T --> Q1["Email queue"]
  T --> Q2["Receipts queue"]
  Q1 --> C1["Email consumer: skips copies"]
  Q2 --> C2["Receipts consumer: skips copies"]
  Q1 -.->|"after 5 failures"| D1["Email dead letter queue"]
  Q2 -.->|"after 5 failures"| D2["Receipts dead letter queue"]
`} legend="Each piece answers one failure: the outbox keeps the event if the publish fails, the queues isolate subscribers, retries and dead letter queues contain bad events, and idempotent consumers make copies harmless." />

This is the design for the gate of this module. The outbox from chapter 14.4 makes sure an event exists whenever an order does. The topic and one queue per subscriber fan it out and isolate slow subscribers. Retries with backoff and a dead letter queue stop a bad event from blocking a line. Idempotent consumers from chapter 14.5 make the repeats harmless.

<GoDeeper title="Go deeper: reading the design as a checklist, and the AWS names">

Walk the design as an interviewer would. What if the order service crashes after saving the order and before publishing? The outbox row is still there, and the relay publishes it later. What if the relay publishes twice? Consumers skip copies by event id. What if Receipts is down for an hour? Its queue holds the events, and it catches up. What if one event always fails? After a limit it goes to the dead letter queue, and an alarm tells a person. What if a new team needs the events? They add a queue to the topic, and the publisher does not change. What if the topic itself is down? Orders still save, and the outbox keeps its rows until the topic returns. Every answer is a sentence you can say aloud in an interview.

**In AWS.** An SNS topic with one SQS queue subscribed per application is the fan-out in the picture, and each SQS queue can have its own dead-letter queue [S85]. SQS standard queues deliver at least once [S83], and Kinesis Data Streams is the log with shards, partition keys and sequence numbers [S132]. The roadmap also names MSK (Kafka run for you) and EventBridge (routing events by rules between services); this chapter has not verified them against their documentation.
