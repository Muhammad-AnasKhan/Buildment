```quiz
type: mcq
question: "A fraud team wants to run a new rule over the last 3 days of order events and then keep watching live events. Orders now flow through a queue that deletes each message after the ack. What should change?"
options:
  - "Send the events to a log that keeps at least 3 days"
  - "Raise the visibility timeout to 3 days so jobs stay"
  - "Add more workers so the queue holds more old jobs"
  - "Turn on a dead letter queue to keep all old jobs"
correct: 0
explanations:
  - "Right. A log keeps events for its retention period, and a new consumer group can start from the oldest one. A queue has already deleted what was acknowledged."
  - "The visibility timeout only hides a message that a worker holds. Once the worker acks, the message is deleted, however long the timeout was."
  - "Workers take jobs out of the queue. More workers make it empty sooner and keep nothing for later readers."
  - "A dead letter queue holds messages that kept failing. It does not keep the ones that were processed and acknowledged."
```

```quiz
type: mcq
question: "A topic has 12 partitions. Each consumer handles 100 events per second and the load is spread evenly. With 5 consumers the group tops out near 400 per second. What does a sixth consumer give?"
options:
  - "About 480 per second, a fifth more"
  - "About 500 per second, 100 more"
  - "About 600 per second, two each"
  - "Still 400, since the sixth has no work"
correct: 2
explanations:
  - "That treats the group like a pool where every worker adds an equal share. A partition belongs to one consumer, so the busiest consumer sets the limit."
  - "That adds 100, one consumer's speed. The limit comes from the busiest consumer, so the change is bigger: the busiest drops from 3 partitions to 2."
  - "Right. 12 partitions over 6 consumers is 2 each. The limit is 12 x 100 / 2 = 600. With 5 consumers the busiest held 3, giving 12 x 100 / 3 = 400."
  - "The sixth consumer does get partitions. A rebalance moves some from the busy consumers to it, and no consumer idles, because 6 is below 12."
```

```quiz
type: mcq
question: "500 workers lose their database connection at the same moment. They retry after 1 second, 2 seconds, 4 seconds and so on, and the database falls over again each time it recovers. Which change helps most?"
options:
  - "Double the base wait to 2 seconds"
  - "Retry at every layer, so some get through"
  - "Retry at once, so the work finishes sooner"
  - "Add a random part to each wait (jitter)"
correct: 3
explanations:
  - "A longer wait still has the same shape. All 500 workers wait the same time and arrive together, only later."
  - "More retry layers multiply the attempts. A recovering database would receive even more requests than before."
  - "Retrying at once adds the most load at the worst moment. The database never gets time to recover."
  - "Right. A random wait spreads the 500 retries over time, so the database sees a trickle instead of a wave, and the average wait does not need to grow."
```

```quiz
type: mcq
question: "An order consumer must keep each customer's events in order. One message keeps failing. The team moves failing messages to a retry queue and carries on with the next event. What is the cost?"
options:
  - "That message is lost for good"
  - "Later events of that customer may run first"
  - "Every customer's events can now be reordered"
  - "The whole partition must be deleted to recover"
correct: 1
explanations:
  - "The message is not lost. It waits in the retry queue and goes back to the line when its time comes, or to a dead letter queue after the last try."
  - "Right. The retry returns after the events that were behind it, so for that customer the order can be swapped. Other customers are not affected."
  - "Only events with the same key as the failed message can be swapped. Different keys never had an order between them."
  - "Nothing needs to be deleted. The partition and the offsets stay as they are."
```

```quiz
type: mcq
question: "A dashboard counts orders per minute with a watermark delay of 10 seconds and no allowed lateness. For 12:00 it shows 98, and it never changes. The tablets in the stalls recorded 104. Which cause is most likely?"
options:
  - "The tablets' clocks are all exactly right"
  - "The windows overlap, so events count twice"
  - "Six events arrived late and were dropped"
  - "The log lost six events during the minute"
correct: 2
explanations:
  - "If the clocks were right, that would not explain a gap. A gap of 6 comes from events that did not make it into the window."
  - "Overlapping windows would make a count higher, not lower, because an event is counted in several windows."
  - "Right. Tablets with weak signals send events after the watermark has passed 12:01. With no allowed lateness, a closed window drops them. A longer delay or some lateness would keep them."
  - "A log keeps what it receives. The events missing from the count were most likely received late, not lost."
```
