Both a queue and a log hold messages between a sender and a receiver. They look alike from far away. They behave very differently when two readers want the same message, when a reader crashes, and when someone wants yesterday's messages.

## A queue gives each job to one worker

<InteractiveCanvas slug="sysdesign-m15-queue-handout" />

The queue holds jobs a, b and c. It gives a to worker 1 and b to worker 2. Each worker acknowledges (acks) its job when it is done, and the queue deletes it. A job goes to one worker and is then gone. This is how Amazon SQS works.

<GoDeeper title="Go deeper: how an SQS-style queue behaves">

When a consumer receives a message from an SQS queue, the message stays in the queue but becomes invisible to other consumers for the visibility timeout. The default is 30 seconds. If the consumer deletes the message in that time, it is gone. If it does not, for example because it crashed, the message becomes visible again and another consumer can take it [S84]. That is how a queue survives a crashed worker, and it is also why standard SQS queues deliver at least once: a slow worker can lose the message to a second worker while it is still working [S83].

A queue is good at independent jobs. Each job has its own life: it can be retried, delayed or moved to a dead letter queue by itself. Jobs do not need to be in order, and a failing job does not stop the next one, because other workers keep taking jobs. Adding workers makes the line shorter, with no planning.

What a queue cannot do is show the same message to a second reader. Once a worker acks, the message is deleted for everyone.

</GoDeeper>

## A log keeps everything, readers keep a place

<InteractiveCanvas slug="sysdesign-m15-log-offsets" />

A log is a list of events in order. Reading does not delete anything. Each reader remembers a number: the position of the next event it will read, called its offset. Email is at 4 and Stats is at 2. Each moves on alone, and the log still holds events 1 to 6.

<GoDeeper title="Go deeper: offsets, in a toy you can run">

In Kafka, the position of a consumer in each partition is a single integer: the offset of the next message to consume. That state can be saved from time to time, which is called committing an offset. Kafka does not delete messages when they are read. It keeps them for a retention period you set [S82].

The whole idea fits in a few lines of JavaScript. A queue is a list from which you remove items. A log is a list that you only add to, plus one number per reader.

```js
// A toy queue and a toy log. Partial: no crashes, no network.
const queue = ["a", "b", "c"];
console.log(queue.shift(), queue.shift(), queue); // a b [ 'c' ]: taken, gone

const log = ["e1", "e2", "e3", "e4", "e5", "e6"];
const offsets = { email: 4, stats: 2 }; // the next event each reader reads
function read(reader) {
  const event = log[offsets[reader]];
  if (event !== undefined) offsets[reader]++; // move the bookmark, delete nothing
  return event;
}
console.log(read("email"), read("stats"), offsets, log.length);
// e5 e3 { email: 5, stats: 3 } 6
```

Committing an offset is the log's version of an ack: "I have finished everything before this number." That is one number for a whole stretch of events, which is cheap. The price is that a log cannot ack, retry or delete one message by itself. If event 3 keeps failing, a reader that must keep order cannot go past it. Chapter 15.5 deals with that.

</GoDeeper>

## Add a consumer, watch the partitions move

<InteractiveCanvas slug="sysdesign-m15-rebalance-play" />

A topic is split into partitions. In a consumer group, each partition goes to exactly one consumer. Drag the number of consumers. Partitions move, in a rebalance, and the speed changes in steps. With more consumers than partitions, the extra ones sit idle.

<GoDeeper title="Go deeper: partitions, groups and rebalances">

A topic is divided into partitions so that many consumers can read in parallel. Kafka assigns each partition to exactly one consumer in each subscribing group at any time [S82]. That rule keeps the order inside a partition, because only one reader moves through it. It also sets a ceiling: a group can never use more consumers than the topic has partitions. Kinesis works the same way, with shards in place of partitions, and each record has a partition key and a sequence number [S132].

Try the numbers. With 6 partitions and a consumer that can do 100 events per second, the group's limit is 600 divided by the largest number of partitions any consumer holds. One consumer holds all 6: 100. Two hold 3 each: 200. Three hold 2 each: 300. Four hold 2, 2, 1, 1: still 300, because the busiest consumer limits the group. Five: still 300. Six: 600. Seven or eight: 600, with idle consumers. So more consumers help in steps, and the right counts are the divisors of the partition count: 1, 2, 3 and 6.

When a consumer joins or leaves, the group has to move partitions to match. This is a <GlossaryTerm term="rebalance" definition="The moving of partitions between the consumers of a group when a consumer joins, leaves or crashes. Reading from the moved partitions pauses until each new owner knows where to continue." />. During a rebalance, the moved partitions are not read, so a busy system sees a short pause. Kafka offers static membership to avoid a rebalance when a consumer restarts quickly: members keep their identity, so the group's membership does not change [S82]. The planning rule follows: choose the partition count for the peak parallelism you expect, with room to grow. Adding partitions later is possible, but it changes which partition a key maps to (chapter 9.5), which can break the order for existing keys.

</GoDeeper>

## Two groups read the same log

<InteractiveCanvas slug="sysdesign-m15-two-groups" />

Email is at event 8 and Stats is at event 3. Both read the same log, each at its own speed. A slow group does not slow the other, and the log keeps every event for both. With a queue you would need to send each message to two queues. With a log, a new reader just starts reading.

<GoDeeper title="Go deeper: one log, many applications">

Each consumer group keeps its own offsets, so groups do not interfere. A team can add a new application, such as a fraud check, as a new group, with no change to the sender and no copy of the data. This is what makes a log a good backbone: the sender writes once, and any number of readers use the events for their own purposes.

The cost is storage and planning. The log keeps events for its retention period, so disk use is the event rate times the event size times the retention. At 1,000 events per second of 500 bytes each, a day is 43 GB (1,000 x 500 x 86,400 bytes), which is a course example worth redoing with your own numbers. And one slow group costs the log nothing, as long as it reads before the retention ends: if it falls behind past the oldest event, it loses events it never read.

</GoDeeper>

## Rewind and read again

<InteractiveCanvas slug="sysdesign-m15-log-replay" />

The Stats reader had a bug and counted wrongly. The log still holds events 40 to 100, so the reader moves its offset back to 40 and reads them again. A consumer can deliberately rewind to an old offset and consume again. A queue that deleted each job after the ack cannot do this.

<GoDeeper title="Go deeper: what replay is used for">

Replay has three common uses. After a bug, fix the code and rewind to recompute. For a new application, start a new group from the oldest event and let it build its own state. After data loss in a downstream store, rebuild it from the log. All three need the same two things: events kept long enough, and a consumer that can safely see an event twice. The second is the idempotent consumer of chapter 14.5, and it matters more here than anywhere, because replay is a deliberate duplicate.

Replay also has a limit. If the consumer has side effects, such as sending an email, replaying sends them again. Separate the computing consumers, which are safe to replay, from the acting consumers, which need a record of what they already did. Keep the retention long enough for the longest repair you plan. A log with 7 days of retention cannot fix a bug found on day 8.

</GoDeeper>

## Choose by the question you ask

<MermaidDiagram title="Queue or log?" chart={`flowchart TD
  Q1{"Must a second system read the same events?"} -->|"Yes"| L["Log"]
  Q1 -->|"No"| Q2{"Will anyone need to read old events again?"}
  Q2 -->|"Yes"| L
  Q2 -->|"No"| Q3{"Are they independent jobs with their own retries and delays?"}
  Q3 -->|"Yes"| Q["Queue"]
  Q3 -->|"No"| Q4{"Do you need strict order per key at high volume?"}
  Q4 -->|"Yes"| L
  Q4 -->|"No"| Q
`} legend="A log answers questions about history and many readers. A queue answers 'who does this job'. When nothing points to a log, a queue is the simpler tool." />

Start from what you need. Many readers, replay or order per key point to a log. Independent jobs with their own retries and delays point to a queue. If neither side wins, take the simpler one, which is usually the queue.

<GoDeeper title="Go deeper: the two side by side">

| | Queue (SQS standard style) | Log (Kafka style) |
|---|---|---|
| After a read | The message is hidden, then deleted on ack | The message stays until retention ends |
| Readers | One worker gets each message | Each group gets every message |
| Order | Not guaranteed | Kept inside a partition |
| Replay | No | Yes, by moving the offset |
| Retry one message | Natural: it returns after the visibility timeout | Hard: the offset moves past all earlier events |
| Scaling readers | Add workers any time | Up to the number of partitions |

None of this makes one better. A queue is easier to run for background jobs. A log is better when events are a record worth keeping. Many systems use both: events flow in a log, and a consumer of the log puts the slow jobs in a queue for workers. On AWS, SQS is the queue and Kinesis Data Streams is the log with shards. Amazon MSK runs Kafka itself.
