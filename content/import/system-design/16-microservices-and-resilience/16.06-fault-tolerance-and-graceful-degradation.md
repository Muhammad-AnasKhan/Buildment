Parts will fail. A disk dies, a service slows, a zone loses power. A fault tolerant system keeps doing its job anyway. Often that means doing less than the full job: a customer can still order even when the picks row, the reviews or the delivery estimate are missing. Choosing what to give up, and what to show in its place, is design work, done before the outage.

## Core path and nice extras

<MermaidDiagram title="Tawseel's home screen by importance" chart={`flowchart LR
  subgraph MUST["Must work: no order without it"]
    A["Shop list"] --- B["Cart"] --- C["Payment"]
  end
  subgraph SHOULD["Should work: worse without it"]
    D["Delivery estimate"]
  end
  subgraph NICE["Nice to have: hide it if it fails"]
    E["Picks for you"] --- F["Reviews"]
  end
`} legend="Sort every feature by what happens to the customer's order when it is gone." />

Sort each feature by one question: can the customer still order without it? The shop list, cart and payment are the core path. The delivery estimate is better with a number, but a rough range will do. Picks and reviews are extras. Only the core path must always work. Everything else gets a fallback: a cheaper answer shown in its place.

<GoDeeper title="Go deeper: fault, failure and the words around them">

A **fault** is the cause: a crashed disk, a bug, a cut cable. A **failure** is when the service stops meeting its goal for the user. **Fault tolerance** means a fault does not turn into a failure: the system keeps working despite it. Two means are used. **Redundancy** has spare copies of the parts that can fail (servers, zones, data), so another can take over. **Graceful degradation** accepts that some features go away to protect the rest, and plans which.

Deciding the tiers is a product decision, not only an engineering one. Ask the people who run the business: if reviews disappear for an hour, what is lost? Often, little. If payments disappear, everything is lost. The tiers also decide the maths. The core path of three services, each at 99.9%, has availability about 99.7% (0.999 to the power 3, chapter 2.6). If all six features had to work, it would be about 99.4%. Making extras optional is the cheapest availability you can buy, and module 17 turns this into targets.

</GoDeeper>

## Break a service, choose a fallback

<InteractiveCanvas slug="sysdesign-m16-degrade-menu" />

Tap a service to break it. Tap a feature to choose what it does when its service is down: fail the page, hide, show a cached copy, show a default, or offer another way. Start with every feature set to fail the page and watch one broken extra stop the screen. Then choose fallbacks until the customer can still order with any one service down.

<GoDeeper title="Go deeper: the rules behind the picture">

The screen has six features, each depending on one service, and a fallback per feature. The default is "fail the page", which is what code does when no one wrote a fallback: the error travels up and the screen shows an error. Three rules decide the verdict.

First, the customer can order only if the shop list is shown (live or cached), the cart works, and payment works or has another way, such as cash on delivery. Second, the cart has no fallback: it is the customer's own data and a default would be wrong. Third, any feature left on "fail the page" breaks the whole screen when its service is down, extra or not.

Each fallback has a cost. A cached shop list can show a shop that has closed. A default delivery range of 30 to 45 minutes can be wrong. A hidden row means the customer may not see an offer. These are acceptable, because the other option is a blank screen. Money values, such as the final price and the amount charged, should never come from a cache or a default.

</GoDeeper>

## A fallback you chose ahead of time

<InteractiveCanvas slug="sysdesign-m16-fallback-cache" />

The Picks breaker is open, so Checkout does not call Picks. It asks a cache for the popular items, gets a list that is an hour old, and builds the page. The customer sees a row of popular items instead of a row made for them. It is a worse answer than the real one, and far better than an error.

<GoDeeper title="Go deeper: kinds of fallback">

- **Cached copy.** The last good answer, possibly old. Good for lists that change slowly. Mark how old it is, and never use it for money.
- **Default value.** A safe constant, such as a delivery range of 30 to 45 minutes. Cheap, and sometimes wrong.
- **Hide it.** Leave the feature out. The simplest fallback for extras.
- **Another way.** A different path to the same goal: pay on delivery when card payment is down, or call the shop.
- **Read-only mode.** Let the customer browse and keep the cart, but disable ordering until writes work again.
- **Do it later.** Save the request and finish it when the dependency is back. This is the message queue from 16.3.

A good fallback does not depend on the thing that failed. A fallback that calls a second service which shares the same database fails with it. And a fallback is code that rarely runs, so it is the code most likely to be broken on the day it matters. Test it (last beat).

</GoDeeper>

## Spare room makes redundancy real

<InteractiveCanvas slug="sysdesign-m16-no-headroom" />

A balancer sends 60 requests a second to each of two servers. Each is 60% busy and looks safe. Server B crashes, and all 120 go to A, which can do 100. A is overloaded at 120%, its answers slow down, and the failure spreads. Two servers survive the loss of one only if each runs at 50% or less.

<GoDeeper title="Go deeper: how much spare room, and which failure domain">

The rule is to have enough capacity left after losing the largest unit you plan to lose. With n equal servers and the loss of one, the survivors carry n divided by (n - 1) times the old load each. So the most each server can run at before the loss is (n - 1) / n of its capacity: 50% for two servers, 67% for three, 75% for four. More small servers cost less spare room than two big ones. This is the arithmetic behind the advice to run "N + 1".

Chapter 2.6 showed that two copies at 99.9% give 99.9999% in parallel. That holds only if they fail independently and the survivor can carry the load. Servers in one rack or one zone fail together, so spread copies across failure domains, such as separate zones (chapter 4.4). AWS lists multi-zone and multi-region designs among its disaster recovery strategies [S107].

Health checks matter here too. A check that tests an optional dependency can mark every server unhealthy at the same moment, and a balancer that then removes them all sends callers nowhere. Prefer local checks, and fail open when all checks fail [S19]. Callers that find servers by name (chapter 12.9) should keep their last good list if the registry itself is unreachable.

</GoDeeper>

## Test the fallbacks before an outage does

<MermaidDiagram title="A failure drill" chart={`flowchart LR
  A["List what each service depends on"] --> B["Write what the customer should see if it fails"]
  B --> C["Switch it off in a test"]
  C --> D{"Did the page behave as written?"}
  D -->|no| E["Fix the fallback"] --> C
  D -->|yes| F["Repeat for the next dependency"]
`} legend="One dependency at a time. A fallback that was never tested is a guess." />

For each dependency, write down what the customer should see if it fails. Then switch it off in a test and look. Most fallbacks fail the first time, because they call the dead service, wait too long, or were never run. Do the drill one dependency at a time, and repeat it after big changes. Challenge 15 does this for Picks.

<GoDeeper title="Go deeper: recovery is also a failure mode">

Getting back up can be harder than going down. On 2025-10-19 and 2025-10-20, an error in the automation behind the DynamoDB regional endpoint in AWS us-east-1 left the endpoint with no DNS addresses. EC2 launches and network load balancer health checks then failed for hours, as backlogs and health-check churn followed the first fault. The fixes included disabling that automation and adding limits on how fast health checks can remove capacity [S135]. The lesson fits this module: a dependency such as DNS is a dependency like any other, health checks can amplify a failure, and the work to recover (retries, backlogs, cold caches) can be larger than the work that was lost.

So plan the return too. When a dependency comes back, let traffic return gradually, as the breaker's single probe does. Warm caches before they take full load. Keep the retry budget (16.4) on, so a flood of retries does not meet a half-recovered service. And when a drill reveals a weak fallback, write the fix and run the drill again.

**In AWS.** Multi-AZ designs spread copies over zones; AWS Backup and Route 53 failover appear in AWS's disaster recovery strategies [S107].

</GoDeeper>

<GoDeeper title="In an interview">

Say: "I sort features by what the customer needs to complete the order. The core path must work, and everything else has a fallback: cached data, a default, or the feature hidden. For redundancy I keep spare capacity so the survivors can take the load of a lost server, and I spread copies over zones. I test the fallbacks by switching dependencies off one at a time."

An interviewer may ask: "How much spare capacity do you keep?" Say that with n servers you need the survivors to carry n divided by (n - 1) times their load, so for three servers keep each at or under about 67%.

</GoDeeper>
