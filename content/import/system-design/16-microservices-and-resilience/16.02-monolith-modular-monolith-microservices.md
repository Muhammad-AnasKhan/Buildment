Tawseel, the made-up delivery app from 16.1, began as one program. Now 14 engineers work on it, and two things hurt: releases wait for each other, and one team's bug can block everyone's deploy. Someone says, "Let's move to microservices." This chapter helps you answer: when is that right?

## Three shapes for one app

<MermaidDiagram title="Three ways to build Tawseel" chart={`flowchart TB
  subgraph M["Monolith: one deploy, one database"]
    M1["Orders code"] --- M2["Payments code"] --- M3["Catalog code"]
  end
  subgraph MM["Modular monolith: one deploy, strict walls"]
    N1["Orders module"] -->|"public interface only"| N2["Payments module"]
  end
  subgraph S["Microservices: many deploys, many databases"]
    S1["Orders service"] -->|"network call"| S2["Payments service"]
  end
`} legend="The same app in three shapes. The walls get harder to cross from top to bottom, and the cost of crossing them moves from a function call to a network call." />

A monolith is one program, deployed as one unit. A modular monolith is still one deploy, but its modules may only talk through small public interfaces, and each owns its own tables. Microservices are separate programs. Each is deployed and scaled alone, owns its own database, and talks to the others over the network.

<GoDeeper title="Go deeper: what each shape gives and costs">

**Monolith.** One codebase, one build, one deploy, one database. A change that touches orders and payments is one commit, and a transaction (module 7) can cover both. It is the easiest to run and debug. The cost shows up as the team grows: every change goes into the same release, a slow test suite slows everyone, and one bad commit can block all deploys. A part that needs ten times the machines still has to be scaled together with the rest.

**Modular monolith.** The same single deploy, but the code is divided into modules with clear public interfaces, and a module never reads another module's tables. The walls are enforced by tools, for example a check in the build that fails when `orders` imports a private file from `payments`. You keep one deploy and one transaction, and you gain the clear ownership that microservices promise.

**Microservices.** Each service has its own code, its own deploy pipeline and its own data. A team can release its service when it is ready, and scale it alone. The cost is that every call between services is now a network call, data is split (16.3), and there are many more things to run, watch and secure. Martin Fowler observed that the microservice stories he knew had started with a monolith that got too big, and that systems built as microservices from day one often ended up in serious trouble [S36].

A common failure is the **distributed monolith**: services that must be changed and deployed together, because they share a database or call each other in long chains. It has the costs of microservices and none of the benefits. {/* source needed: the term distributed monolith (a practitioner source such as Sam Newman, Building Microservices); not in the dossier. */}

</GoDeeper>

## A function call becomes a network call

<InteractiveCanvas slug="sysdesign-m16-call-can-fail" />

Inside one program, asking for a price is a function call. It always returns, or it throws at once. Between two services it is a network call. It may be answered, refused, slow or lost, and Checkout cannot tell which until it stops waiting. Splitting a program gives every call a new way to fail.

<GoDeeper title="Go deeper: what the network adds">

Chapter 2.2 gave the cost in time: a round trip inside one region takes about 250 microseconds [S3], and a read from main memory about 100 nanoseconds. That is roughly a thousand times more, and still small. The real change is not the delay. It is that a network call has outcomes that a function call does not.

- **No answer.** The other side crashed, the network dropped the message, or the answer is slow. The caller cannot tell these apart (chapter 12.2).
- **Half done.** The call may have worked even though the answer was lost. A retry could do the work twice (chapter 6.4).
- **Two versions at once.** During a deploy, Checkout version 5 may call Payments version 4, so interfaces must stay compatible.
- **Extra work per call.** Each call needs a connection, a serialised message, an authentication check and a log line.

Every one of these needs code that a function call did not. The rest of this module is that code: time limits, retries, breakers, pools and fallbacks.

</GoDeeper>

## Six services in a row: less available

<MermaidDiagram title="A page that needs six services, each 99.9% available" chart={`flowchart LR
  C["Checkout"] --> A["Catalog 99.9%"] --> B["Cart 99.9%"] --> D["Pricing 99.9%"] --> E["Stock 99.9%"] --> F["Payments 99.9%"]
  F --> G["Whole page: 0.999 to the power 6 = 99.4%"]
`} legend="When a page needs every service in the chain, availabilities multiply (chapter 2.6). Six services at 99.9% give about 99.4%." />

Each service on its own is available 99.9% of the time, about 43 minutes of trouble in a 30-day month. If a page needs all six, the chance that all six work is 0.999 to the power 6, about 99.4%. That is about 4.3 hours of trouble a month. More services in a chain means a page that fails more often.

<GoDeeper title="Go deeper: the sums, and fan-out">

Chapter 2.6 gave the series rule: if every part must work, multiply the availabilities. For six parts, 0.999 x 0.999 x 0.999 x 0.999 x 0.999 x 0.999 = 0.994015. The page fails 0.5985% of the time. A 30-day month has 43,200 minutes, so that is about 259 minutes, or 4.3 hours. One service alone fails 0.1%, which is 43.2 minutes. The numbers assume the failures are independent, which is often too kind: services that share a database or a network fail together.

Calls in parallel have another cost, from chapter 2.4. If a page calls 20 services at once and waits for all, and each is slow on 1 call in 100, then about 18 pages in 100 are slow, because 1 minus 0.99 to the power 20 is about 0.18. With 100 services it is 63 pages in 100 [S8]. Splitting a system into many services that a page must combine makes the tail worse.

The fix is not to avoid services. It is to cut the number of services a single page needs, and to make optional ones really optional, so that when one is slow the page still loads (16.6).

</GoDeeper>

## A modular monolith: walls without a network

<MermaidDiagram title="Walls inside one program" chart={`flowchart LR
  subgraph APP["One program, one deploy"]
    O["Orders module"] -->|"calls the public interface"| P["Payments module"]
    O -. "forbidden: reads payments tables" .-> T[("Payments tables")]
    P --> T
  end
`} legend="Orders may call Payments through its public interface. It may not read Payments' tables. A build check enforces the wall." />

A modular monolith draws the same boundaries as microservices, but keeps one deploy. Each module owns its tables and offers a small public interface. A build check fails if another module reaches past it. You get clear ownership and an easy path to split later, without a network between modules.

<GoDeeper title="Go deeper: how to make the walls real">

Walls that exist only in a diagram do not last. Three habits make them real.

- **One owner per table.** Only the owning module reads or writes its tables. Other modules call its interface. If Reports needs order data, it asks Orders.
- **A check in the build.** Use a lint rule or a dependency checker that fails when a module imports another module's private files. Without it, a deadline will break the wall within weeks.
- **Public interfaces shaped like network calls.** Pass plain data, not live objects, and keep the calls few and coarse. Then a module that later becomes a service needs a new transport, not a new design.

You still gain from one deploy: a transaction can cover two modules (module 7), a refactor is one commit, and a debugger sees the whole request. The cost is that the whole team deploys together and a part cannot scale alone. When that cost grows larger than the cost of a network, you split. {/* source needed: the modular monolith as a named architecture style; no primary source in the dossier. */}

</GoDeeper>

## Weigh team, releases and clarity

<InteractiveCanvas slug="sysdesign-m16-split-or-not" />

Drag the team size, the number of releases that waited for another team last month, and how clear the boundaries are. The recommendation changes. A big team with many collisions and proven boundaries has a reason to split the parts that hurt. A small team with unclear boundaries does not.

<GoDeeper title="Go deeper: the rule of thumb, and its limits">

The picture adds points. Team size gives 0 points up to 8 people, 1 for 15, 2 for 30 and 3 for 60 or more. Releases that waited for another team in a month give 0 for 0 or 1, 1 for 3, 2 for 6 and 3 for 10. Boundary clarity gives 0 for "new idea", 1 for "mostly clear" and 2 for "stable for a year". A total of 0 or 1 says to stay a monolith, 2 to 4 says a modular monolith, and 5 or more says to split the parts that hurt. If the boundaries are a new idea, the answer stops at a modular monolith, whatever the other points are.

This is a rule of thumb made for the course, not a law. It uses three factors that matter most often: how many people must coordinate, how often they block each other, and whether you know where the lines are. Other factors can override it: one part that needs ten times the machines, a part with a different security rule, or a part written in a different language by a different team.

Tawseel's numbers (14 people, 3 collisions a month, boundaries mostly clear) give 1 + 1 + 1 = 3 points: a modular monolith. That fits the story. The pain is release collisions, and walls plus a better release process may fix it without a network.

</GoDeeper>

## Split one part at a time

<MermaidDiagram title="Should this module become a service?" chart={`flowchart TD
  Q1{"Are its walls clear and stable?"} -->|no| A["Keep it in the monolith and fix the walls first"]
  Q1 -->|yes| Q2{"Does it need its own scaling, release pace, security or team?"}
  Q2 -->|no| B["Keep it in the modular monolith"]
  Q2 -->|yes| C["Extract it: move its tables, give it an interface, switch callers one by one"]
`} legend="Extract a module only when its walls are clear and something real needs it to stand alone." />

Do not split everything at once. Pick one module whose walls are clear and which needs something of its own: more machines, a faster release pace or a stricter security rule. Move its tables, give it a network interface, and switch its callers over one by one. Picks, for example, could scale alone.

<GoDeeper title="Go deeper: extracting a service safely">

Extraction is a small project, with the same shape every time. First, make the module's interface complete: no caller reads its tables. Second, put the interface behind a network call, but keep both the old in-process path and the new service path, and choose between them with a switch. Third, move the data: copy it to the service's own database, keep both in step for a while, then make the service the only writer. Fourth, move callers over one at a time, watching errors and latency. Last, delete the old code. At each step you can go back.

This is sometimes called the strangler pattern, because the new service slowly takes over the old one. {/* source needed: the strangler fig pattern (Fowler or Microsoft Azure Architecture Center); not in the dossier. */}

**Alternatives.** The boring alternative is to stay a modular monolith for years. Many teams that are told to move to microservices would be better served by a faster build and cleaner walls. Another is a few larger services, split by team rather than by tiny function: three or four services owned by three or four teams is a very different system from forty.

**When to switch.** Split when release collisions cost more than the network would, when one part needs to scale or fail apart from the rest, or when a team boundary would otherwise slow every change. Keep merging back in mind too: services that always change together should be one service.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "I would start with a modular monolith: one deploy, strict module boundaries, and each module owning its data. I would extract a service only when a module has stable walls and needs something of its own, such as separate scaling or release pace. Every service boundary adds network calls that can fail, so I would split the parts that hurt, not everything."

An interviewer may ask: "What would make you split Tawseel?" Name the evidence: release collisions that cost real time, one part that must scale alone, and boundaries that have stayed still for a long time.

</GoDeeper>
