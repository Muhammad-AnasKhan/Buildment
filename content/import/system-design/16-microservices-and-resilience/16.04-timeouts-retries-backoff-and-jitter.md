Tawseel's Checkout calls Picks on every home page, and Picks can be slow or fail. Whether that stays a small problem depends on four simple tools: a time limit on each call, careful retries, a random wait between retries, and a limit on how many retries are allowed at all.

## Give every call a time limit

<InteractiveCanvas slug="sysdesign-m16-timeout-fires" />

Checkout calls Picks and starts a 200 ms clock. Picks is slow today. When the clock runs out, Checkout gives up, shows the page without the picks row, and frees the worker. With no limit, the wait has no end. With a 200 ms limit, a stuck Picks holds at most 100 x 0.2 = 20 workers at 100 pages a second.

<GoDeeper title="Go deeper: what a time limit does, and does not do">

A time limit, also called a timeout, is the longest a caller will wait for an answer. When it passes, the caller stops waiting and treats the call as failed. It is the most basic protection, and the others in this module depend on it: a retry or a breaker has nothing to count if calls never end. Many HTTP clients wait for a very long time, or for ever, unless you set a limit, so check yours. In the challenge you set it with `AbortSignal.timeout(200)` on `fetch`.

A timeout does not mean the work stopped. Picks may still finish the job after Checkout has left. That is why a call that changes data must be safe to repeat (idempotent, chapter 6.4) before you retry it.

There are usually two limits. A connect limit says how long to wait to open a connection, and can be short. A total limit says how long to wait for the whole answer. Pass the time left down the chain, so a deeper service knows it has only 150 ms left and does not start work that nobody will wait for. The Google SRE book calls this deadline propagation [S91].

</GoDeeper>

## Drag the limit and see the price

<InteractiveCanvas slug="sysdesign-m16-timeout-line" />

Each bar is one call to Picks, and taller means slower. Drag the limit line. Bars above it are calls you cut off, though they would have worked. A short limit cuts many good calls. A long limit lets a hanging Picks hold many workers. At 100 pages a second with 50 workers, a limit above 500 ms lets a hang take every worker.

<GoDeeper title="Go deeper: choosing the number">

Brooker's rule is to set the timeout from the downstream latency percentile at which you accept a false timeout, a call cut off that would have worked. His example uses p99.9 [S89]. For Picks in the picture, the course numbers are p50 40 ms, p90 80 ms, p99 250 ms and p99.9 900 ms. A limit of 250 ms cuts about 1 call in 100, a limit of 900 ms cuts about 1 in 1,000.

The other side of the choice is the pool. When Picks hangs, every call waits the full limit, so the workers held are the rate times the limit. At 100 pages a second that is 25 workers for 250 ms, 50 for 500 ms and 90 for 900 ms. Tawseel has 50. So the p99.9 limit is too long for this pool, and the p99 limit fits. Pick the limit and the pool size together, and also keep the picks row optional, so that a cut-off call costs nothing but the row.

These numbers are made up for the course. For your own service, measure the percentiles of the dependency first (chapter 2.4), under both quiet and busy times.

</GoDeeper>

## Retries multiply down the stack

<MermaidDiagram title="Three tries at every layer" chart={`flowchart LR
  U["1 click"] -->|"x3"| A["Layer A"] -->|"x3"| B["Layer B"] -->|"x3"| C["Layer C"] -->|"x3"| D["Layer D"] -->|"x3"| DB[("Failing database: 243 tries")]
`} legend="Each layer tries up to 3 times, so the tries multiply: 3 to the power 5 is 243. Brooker's example [S89]." />

One retry at one layer is cheap. Retries at every layer multiply. With 3 tries at each of 5 layers, one click can cause 243 tries at the database, which is already failing. Google's SRE book has a smaller example: 3 layers with 4 attempts each give 64 attempts at the bottom [S91].

<GoDeeper title="Go deeper: why this happens, and the first rule">

Each layer sees only its own call. Layer B does not know that A has already retried, so it retries too. When the database is failing, all of those tries fail, and each failure triggers more tries. The load on the failing part rises by a factor that grows with every layer, exactly when it can least cope.

The first rule is to retry at one point in the stack, usually the layer closest to the user or the one that knows the call is safe to repeat, and to let all the others pass the error up [S89]. The second rule is a limit on the total (the budget, below). The third is that retries need a safe call: Brooker notes that APIs with side effects are not safe to retry unless they provide idempotency [S89].

</GoDeeper>

## Retries can keep a system down

<InteractiveCanvas slug="sysdesign-m16-retry-storm" />

A 5-second blip cuts the server to 30 requests a second, then it is healthy again. Drag the number of retries. With no retries the system is back 10 seconds after the blip. With retries at once, the load climbs to 160, 240 or 320 a second against a capacity of 100, and the system never recovers. Choose the budget to see it recover.

<GoDeeper title="Go deeper: a metastable failure, and why backoff alone does not fix it">

Chapter 1.1 said that retries can keep a system down after the first problem is over. This is the picture. Bronson and others call it a metastable failure: a trigger pushes a system into a bad state that persists even when the trigger is removed, held there by a sustaining effect such as work amplification from retries [S94].

In the model, the server does 100 requests a second, normal load is 80 a second, and clients give up after 1 second. During the blip a line builds up. Requests wait longer than 1 second, so the clients have gone by the time the server reaches them, but the server still spends its work on them (it answers late, and nobody listens). Each client that gave up retries, so the arrival rate becomes 80 times (retries + 1). With one retry that is 160 a second, which is above 100, so the line never empties and every answer is late. This is a model, made up to show the shape: real systems recover more easily, but the direction is the same.

Waiting before a retry, even with growing delays and random jitter, does not change the result in this model. Every request still tries retries + 1 times in the end, so the load is the same, only later. What helps is fewer attempts: a retry budget, a breaker that stops calls, or shedding load (16.5). It also helps to drop requests that are already too old before spending work on them.

</GoDeeper>

## A herd needs jitter

<InteractiveCanvas slug="sysdesign-m16-jitter-herd" />

1,000 clients fail together at second 0, and the server can serve 100 calls a second. With backoff but no jitter, they retry in lockstep and meet in waves. With full jitter, each client waits a random time, and the retries spread out. With 6 retries, backoff alone serves 600 of the 1,000. Jitter serves all 1,000, with fewer calls.

<GoDeeper title="Go deeper: full jitter in one line">

Exponential backoff means the wait before try number n doubles each time: 1 second, 2, 4, 8, up to a cap. It spreads out the retries of one client, but clients that failed at the same moment still retry at the same moments. Jitter adds randomness. With full jitter, the wait is a random number between 0 and the backoff ceiling: `random() * min(cap, base * 2 ** attempt)`. Brooker compared full, equal and decorrelated jitter in 2015. Equal jitter did worst of the three, and he concluded that jittered backoff should be considered a standard approach [S90].

```js
// Partial: the wait before retry number `attempt` (1, 2, 3, ...), in ms.
function fullJitterDelay(attempt, baseMs, capMs, random = Math.random) {
  return random() * Math.min(capMs, baseMs * 2 ** attempt);
}
```

In the picture, 1,000 clients and a capacity of 100 calls a second are course numbers. With 6 retries and a cap of 16 seconds, the model gives these totals: retrying at once makes 4,900 calls and serves 700 clients; backoff makes 4,500 calls and serves 600; full jitter makes 3,020 calls and serves all 1,000, 995 of them within 20 seconds. Jitter does not remove the load. It spreads it in time so that the server can use all its capacity.

</GoDeeper>

## Spend retries from a budget

<InteractiveCanvas slug="sysdesign-m16-retry-budget" />

A retry budget caps the extra load that retries can add. In the picture, a client has a budget of two retries. Each retry spends one. When the budget is empty, the next failure is not retried and the client fails fast. In the chapter's code, the budget refills by one unit for each request, and a retry costs ten units, so retries stay near 10% of requests.

<GoDeeper title="Go deeper: budgets in practice">

Brooker suggests limiting retries with a local token bucket: each client keeps a small bucket and a retry takes a token, so a failing dependency cannot make a client retry without limit [S89]. The SRE book describes two limits together: a cap on retries for each request, and a server-wide retry budget, for example that retries may be at most 10% of all requests [S91]. The 10% here is a design choice for the course, not a rule from either source.

With a budget of one retry per ten requests, 1,000 failing requests make at most 100 retries. The dependency sees 1,100 calls, not the 4,000 that three immediate retries would send. During an outage that is the difference between a dependency that is hit hard and one that can recover. When the failure is only a blip, the budget still has enough tokens to cover it, because a quiet period fills it again.

Also keep the budget per dependency, so one broken dependency cannot spend the tokens that others need. And log every refused retry: that line is the first sign that a dependency is in trouble.

## Retry only what is safe

<MermaidDiagram title="Should this failed call be retried?" chart={`flowchart TD
  F["A call failed"] --> S{"Safe to repeat? Reads, or writes with an idempotency key"}
  S -->|no| N["Do not retry: report the error"]
  S -->|yes| L{"Am I the one layer that retries?"}
  L -->|no| P["Pass the error up"]
  L -->|yes| B{"Budget left?"}
  B -->|no| N2["Fail fast"]
  B -->|yes| W["Wait a full-jitter delay, then try again"]
`} legend="Four questions before every retry. Any 'no' ends the retry." />

Before any retry, ask four questions. Is the call safe to repeat? Am I the one layer that retries? Is there budget left? Then wait a random time. A payment without an idempotency key fails the first question, because a repeat could charge twice (chapter 6.4).

<GoDeeper title="Go deeper: the whole rule, in a short loop">

Putting the tools together, a call to a dependency looks like this. It is a sketch, not the full code; you write the real pieces in 16.7.

```js
async function callWithRetries(send, { retries, budget, timeoutMs, baseMs, capMs }) {
  budget.recordRequest();
  for (let attempt = 0; ; attempt++) {
    try {
      return await send(AbortSignal.timeout(timeoutMs)); // 1. a time limit
    } catch (err) {
      if (attempt >= retries) throw err;                  // 2. a cap per request
      if (!budget.tryRetry()) throw err;                  // 3. a shared budget
      await sleep(fullJitterDelay(attempt + 1, baseMs, capMs)); // 4. a random wait
    }
  }
}
```

Which errors are worth a retry? A timeout, a connection error and a 503 are often temporary. A 400 or a 404 will fail the same way again. A 429 means the server asked you to slow down, so back off for longer, and honour a `Retry-After` header when one is sent. Retries also belong near the user's request, not deep in the stack, and the total time of all tries should fit inside the user's own time limit.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "Every remote call gets a timeout, chosen from the dependency's latency percentile and checked against my worker pool. I retry only safe, idempotent calls, at one layer, with exponential backoff and full jitter, and I cap retries with a budget, for example 10% of requests. Without the cap, retries can multiply the load on a failing dependency and keep it down after the trigger is gone."

An interviewer may ask: "Why jitter, if you already have backoff?" Backoff alone leaves clients that failed together retrying together. Jitter spreads them so the server can use its full capacity.

</GoDeeper>
