```quiz
type: mcq
question: "Two Tawseel services read and write the same database table. Every few weeks a change to one breaks the other, and they have to be deployed together. What is going on, and what is the fix?"
options:
  - "Healthy sharing; add a test that runs both services"
  - "A hidden link; give the table one owner and an interface"
  - "A cache problem; put a cache in front of the table"
  - "A scaling problem; add read replicas to the database"
correct: 1
explanations:
  - "A test can show the break sooner, but the coupling stays. The services still cannot change or deploy alone, which was the point of splitting them."
  - "Right. A shared table is a contract nobody wrote down. One service should own the data, and the other should use its interface or keep its own copy built from events."
  - "A cache reduces load. It does not remove the link that makes one service break when the other changes the table."
  - "Replicas help with read load. The breakage comes from the shared layout of the data, not from the load."
```

```quiz
type: mcq
question: "Three layers of services each make up to 4 attempts at the layer below, with no coordination. The database at the bottom is failing. How many attempts can reach it for one user request?"
options:
  - "12, three layers of 4"
  - "81, three multiplied 4 times"
  - "4, only the first layer retries"
  - "64, four multiplied 3 times"
correct: 3
explanations:
  - "That adds the layers. Each attempt at one layer causes up to 4 attempts at the next, so the numbers multiply."
  - "81 is 3 to the power 4, the numbers the wrong way round. There are 3 layers with 4 attempts each, so 4 to the power 3."
  - "Every layer retries in this setup, not only the first. Each layer multiplies the attempts below it."
  - "Right. 4 x 4 x 4 is 64 attempts at the database, the example in Google's SRE book. Retrying at one layer, with a budget, avoids it."
```

```quiz
type: mcq
question: "A breaker opens after 5 failures in a row and waits 10 seconds before half-opening. The probe call fails. When does the breaker send the next probe?"
options:
  - "10 seconds after the failed probe"
  - "Right away, on the next call that arrives"
  - "10 seconds after the first failure"
  - "Never, the breaker stays open for good"
correct: 0
explanations:
  - "Right. A failed probe opens the breaker again and the full wait starts again from that moment, so the dependency gets 10 seconds of rest."
  - "Sending the next call at once would turn every call into a probe and hammer a dependency that has just shown it is still unwell."
  - "The wait is measured from the moment the breaker last opened, which was the failed probe, not from the first failure."
  - "A breaker keeps probing. If it stayed open for ever, it would never notice that the dependency recovered."
```

```quiz
type: mcq
question: "A server can do 100 requests a second. 150 arrive each second, and clients give up after 1 second. Which choice keeps the most users served well?"
options:
  - "Queue every request and answer them in order"
  - "Make clients retry three times when they give up"
  - "Refuse the extra 50 at once with a busy answer"
  - "Raise the client wait from 1 second to 10 seconds"
correct: 2
explanations:
  - "The line grows by 50 a second and passes 100 after 2 seconds. After that every answer comes after the client has left, so nobody is served well."
  - "Retries add load to a server that is already over capacity. In the model they keep the system down for ever."
  - "Right. Refusing the excess early keeps the line short. The 100 requests the server can handle are answered on time, and the 50 get a quick busy answer."
  - "A longer wait lets the line grow longer, and it holds client resources for longer. It moves the failure later without removing it."
```

```quiz
type: mcq
question: "Tawseel's delivery estimate service is down. Which behaviour is the best fallback on the order screen?"
options:
  - "Show an error screen until the estimate returns"
  - "Show a default range, such as 30 to 45 minutes"
  - "Hide the order button so no one orders blind"
  - "Retry the estimate until it answers, then show"
correct: 1
explanations:
  - "An error screen stops orders because of a detail. The customer can still order without an exact time."
  - "Right. The estimate is useful but not essential. A default range, labelled as an estimate, lets the customer order, and it costs only some accuracy."
  - "Hiding ordering turns a missing detail into lost sales. The core path should stay open."
  - "Retrying holds the customer and a worker for as long as the outage lasts. A fallback answers at once."
```
