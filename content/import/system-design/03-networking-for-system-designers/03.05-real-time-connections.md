Omar sends Lina a chat message (a course example). HTTP was built for the app to ask and the server to answer, so how does the server tell Lina's phone that something new has happened? There are four common answers, and each one spends delay, requests or connections differently.

## Polling: ask again and again

<InteractiveCanvas slug="sysdesign-m3-polling" />

The app asks "anything new?" every 5 seconds. Most answers are "nothing". Omar writes at 6 seconds, and Lina sees it at the 10 second poll, 4 seconds late. Polling is simple and works everywhere, but it trades delay against wasted requests: poll faster and the delay shrinks, but the empty requests multiply.

<GoDeeper title="Go deeper: the arithmetic of polling">

With <GlossaryTerm term="polling" definition="The client asks the server for news on a fixed timer, whether or not anything has happened." />, two numbers follow from the interval alone.

**Delay.** A message appears at a random moment between two polls, so on average it waits half an interval before the next poll picks it up, and at worst a whole interval. With a 5 second interval: about 2.5 seconds on average, up to 5 seconds.

**Requests.** Every user sends one request per interval, news or not. 10,000 users polling every 5 seconds send 10,000 / 5 = 2,000 requests per second, even when nobody is typing. Halve the interval to halve the delay, and the requests double to 4,000 per second.

Each poll is a full HTTP request with headers, so the empty answers are not free either. In the run printed in chapter 3.8, polling once a second for 12 seconds made 12 requests and moved about 4,500 bytes to deliver 5 short messages, with a mean delay of about 640 ms.

Polling is still the right choice more often than it sounds. If updates are rare and a delay of a minute is fine, such as checking for a new app version, polling every minute is cheap and simple, and each poll is an ordinary request that needs nothing special from the network.

</GoDeeper>

## Long polling: the server holds the question

<InteractiveCanvas slug="sysdesign-m3-long-polling" />

The app asks once, and the server does not answer until it has news. When Omar writes at 6 seconds, the held request is answered at once, and the app immediately asks again. Delay drops to one trip across the network. The cost moves to the server: it holds one open request for every waiting user.

<GoDeeper title="Go deeper: how long polling behaves, and where it breaks">

<GlossaryTerm term="Long polling" definition="The client asks, and the server holds the request open until it has news or a time limit passes, then the client asks again at once." /> uses ordinary HTTP requests, so it works wherever polling works. RFC 6202 documents it, along with its known issues.

The server holds each request until a message arrives or a time limit passes, then answers, often with nothing, and the client asks again. So the number of requests is about the number of messages plus one for each time limit that runs out. In the challenge 2 run, five messages in 12 seconds took 6 requests: one per message and one still waiting when the run ended. Delay was about 2 ms on one machine, because the answer left the moment the message existed.

The costs are less visible. Every waiting user holds an open request, so 10,000 users means 10,000 open connections on the servers at all times. A burst of messages can cause a burst of new requests, because every client that just got an answer asks again at once. A message that arrives while the client is between two requests must be kept until the next one arrives, which is why the challenge server asks for messages "after" the last id the client saw. RFC 6202 lists more issues, such as each answer carrying full HTTP headers.

</GoDeeper>

## Server-sent events: one request, many messages

<InteractiveCanvas slug="sysdesign-m3-sse" />

The app opens one request, and the server never finishes its answer. Instead it writes each new message into it as an event. When the signal drops, the browser reconnects by itself and says which event it saw last, so the server resumes after it and nothing is lost. Messages flow only from server to app.

<GoDeeper title="Go deeper: EventSource, Last-Event-ID and the one-way limit">

<GlossaryTerm term="Server-sent events" definition="A way for a server to push a stream of text events down one long HTTP response; browsers read it with EventSource." /> (SSE) are defined in the HTML standard. A page creates an `EventSource` for a URL. The server answers with the content type `text/event-stream` and writes events as plain text: an optional `id:` line, a `data:` line, and a blank line to end each event.

The standard builds in the two hard parts. If the connection drops, the browser reconnects automatically. When it does, it sends a `Last-Event-ID` header with the id of the last event it received, so the server can send only what was missed. And a server that wants the client to stop for good answers with HTTP status 204, after which the browser does not reconnect.

The limit is direction. Events go from server to client only. When Lina sends a message, her app makes a normal request, such as a `POST`. For many products that is fine: a delivery map, a live score or a notification feed mostly flow one way.

Each listening user still holds one open response, so the server's open connection count equals its listening users, as with long polling. Unlike long polling, a burst of messages costs no new requests: in the challenge 2 run, SSE delivered all five messages with one request and about 700 bytes.

</GoDeeper>

## WebSocket: one connection, both directions

<InteractiveCanvas slug="sysdesign-m3-websocket" />

The app sends one HTTP request that asks to upgrade, and the server answers 101. From then on, the same connection is a two-way pipe. Lina's typing goes up, Omar's messages come down, at any moment, with no new request per message. A chat, a shared document or a multiplayer game fits this shape.

<GoDeeper title="Go deeper: the upgrade, frames and what the server pays">

A <GlossaryTerm term="WebSocket" definition="A two-way connection over TCP that starts as an HTTP request and then lets both sides send messages at any time." /> is defined in RFC 6455 as a two-way protocol over TCP, designed so that two-way apps do not need many HTTP connections or long polling. It starts as an ordinary HTTP request with an `Upgrade: websocket` header. The server proves it understood by answering `101 Switching Protocols` with a value computed from the client's key. After that, HTTP is over: both sides send small framed messages on the same TCP connection whenever they like.

You will write a tiny WebSocket server in challenge 2, part 3: about 15 lines to answer the upgrade and send one kind of frame. That is enough to see that a frame is a couple of bytes of header plus the message. In the challenge run, the WebSocket delivered five messages with one request and under 800 bytes in total, including the upgrade.

What the server pays is the open connection. Every connected user holds one connection, idle or not, and each connection is a file descriptor on the server. A server that gives each connection its own thread runs out of threads long before it runs out of users; an event loop, chapter 3.6, holds many idle connections on one thread. A long-lived connection also stays on the server it first reached, so moving users between servers, for a deploy or after a failure, means closing their connections and letting them reconnect. If every client reconnects at the same moment, that is a burst of handshakes; spreading the reconnects over random delays avoids it, the same idea as retry jitter in module 16.

</GoDeeper>

## Same chat, four ways, side by side

<InteractiveCanvas slug="sysdesign-m3-chat-four-ways" />

Drag the users rail, tap a poll interval, and tap a lane to look at one way. Watch three numbers: the delay before a message appears, the requests per second, and the open connections the servers must hold. Polling buys low connection counts with requests and delay. The other three buy low delay with open connections.

<GoDeeper title="Go deeper: the model behind the picture">

The picture's model, for N users who each get M messages a minute:

| Way | Delay before a message is seen | Requests per second | Open connections held |
|---|---|---|---|
| Polling every P seconds | about P / 2 on average, up to P | N / P | about none between polls |
| Long polling, held up to H seconds | one network trip | about N times (M / 60 + 1 / H) | about N |
| Server-sent events | one network trip | about none (reconnects only) | N |
| WebSocket | one network trip | about none (reconnects only) | N |

For example, 10,000 users who each get 2 messages a minute. Polling every 5 seconds: 2,000 requests per second, 2.5 seconds average delay. Long polling with a 30 second limit: about 10,000 times (2 / 60 + 1 / 30), about 670 requests per second, 10,000 open connections, and a delay of one trip, about 40 ms one way between western Europe and North America East (half of an 80 ms napkin-math round trip). SSE or WebSocket: almost no requests, the same 10,000 open connections and the same short delay.

The model leaves out the size of each message, the cost of headers, reconnects after network changes and how many connections one server can hold, which depends on its memory and on how it handles connections (chapter 3.6). The 2 messages a minute and the 30 second limit are illustrative.

</GoDeeper>

## Choose by direction, delay and scale

<MermaidDiagram title="Which real-time way?" chart={`flowchart TD
  A{"Does the server need to tell the app about news quickly?"} -->|"no, a minute is fine"| P["Polling with a long interval"]
  A -->|"yes"| B{"Does the app also send often, in both directions?"}
  B -->|"yes: chat, games, shared editing"| W["WebSocket"]
  B -->|"no: feeds, maps, scores"| C{"Can every network path keep a response open?"}
  C -->|"yes"| S["Server-sent events"]
  C -->|"no, or unsure"| L["Long polling as a fallback"]
`} legend="Each answer moves cost between delay, requests per second and open connections on the servers." />

Start with the direction and the delay the product needs. If a minute is fine, poll. If both sides talk often, use a WebSocket. If news flows mostly to the app, server-sent events are simpler and resume by themselves. Keep long polling as the fallback for networks that break long-lived connections.

<GoDeeper title="Go deeper: what changes at scale">

The choice does not end with the protocol. Three things follow from it, and module 4 picks them up.

**Open connections become the capacity limit.** With SSE or WebSockets, the number that sizes your servers is connected users, not requests per second. Each connection is a file descriptor on the server, so a design review should ask how many connections one server can hold and how many servers that means at peak.

**Connections are sticky.** A request can go to any server, but a WebSocket stays on the server it reached first. When you deploy or a server fails, its users reconnect, and they should not all reconnect at the same instant. Random delays before reconnecting, and a resume point such as `Last-Event-ID`, keep that orderly.

**The server must know who is connected where.** If Omar's message arrives at server 1 and Lina's WebSocket is on server 7, something must carry the message across. That is usually a shared queue or a publish and subscribe system, which module 15 teaches and module 22 uses for chat at scale.

</GoDeeper>
