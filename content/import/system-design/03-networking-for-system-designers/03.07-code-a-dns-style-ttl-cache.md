In chapter 3.3 a resolver kept each answer for its TTL, answered from memory while the answer was fresh, and passed on the time left. That small piece of logic decides how fast every DNS change in the world spreads, and the same pattern appears in every cache you will build in module 5. In this chapter you write it yourself, against a fake clock, so the tests can jump through minutes of time in a millisecond.

By the end you will have one tested function, `createResolverCache(lookup, now)`. It returns an object with one method, `resolve(name)`. The first call for a name asks `lookup`, which plays the name server. Later calls answer from the cache until the TTL runs out, then ask again.

## The contract

Fix the promises first, including the awkward cases. The tests check the awkward cases, because that is where real caches go wrong.

**The inputs.** `lookup(name)` returns an object such as `{ address: "203.0.113.7", ttl: 300 }`, where `ttl` is a whole number of seconds chosen by the name server. It may also throw, for example when the name does not exist or the name server is down. `now()` returns the current time in milliseconds. The cache must read time only from `now()`, never from `Date.now()`. That is what lets the tests use a fake clock, and it is a good habit: code that reads the real clock in a hundred places cannot be tested for what happens after an hour.

**A miss.** If the cache has no fresh answer for the name, call `lookup(name)` once, store the answer with the moment it expires, `now()` plus the TTL in milliseconds, and return `{ address, ttl, fromCache: false }` with the full TTL.

**A hit.** If the stored answer has not expired, return `{ address, ttl, fromCache: true }` without calling `lookup`. Here `ttl` is the time left, in whole seconds, rounded **down**. Rounding down is the safe direction. A downstream cache that receives your answer will keep it for the TTL you give it, so you must never promise more time than you have. With 240.5 seconds left, say 240. With 0.4 seconds left, say 0, which tells the receiver not to cache it at all.

**Expiry.** An answer stored at time t with TTL s is fresh while `now()` is less than t + s times 1,000. At exactly that moment it has expired, and the next `resolve` asks `lookup` again. This makes a TTL of 300 mean 300 seconds of use, not 301.

**Three things are never cached.** A TTL of 0, which RFC 1035 defines as "use this answer for this request only". A failed lookup: if `lookup` throws, `resolve` throws the same error and stores nothing, so the next call tries again. And a bad TTL: if `ttl` is negative, not a whole number, or not a number at all, throw a `RangeError` and store nothing. A name server that sends a TTL of 2.5 or -1 is broken, and a cache that quietly accepts it will produce strange expiry times that nobody can explain later.

## A worked example: one record over 70 seconds

Here is the contract applied by hand to a case the tests do not use: the record for `api.example.com` has a TTL of 60 seconds, and requests arrive at 0, 30, 59.6, 60 and 61 seconds on the fake clock.

<MermaidDiagram title="What resolve does for each call" chart={`flowchart TD
  A["resolve(name)"] --> B{"Stored answer, and now() before its expiry?"}
  B -->|"yes"| C["Hit: return address, time left rounded down, fromCache true"]
  B -->|"no"| D["Miss: call lookup(name)"]
  D --> E{"Did lookup throw, or is ttl not a whole number of 0 or more?"}
  E -->|"threw"| F["Throw the same error. Store nothing"]
  E -->|"bad ttl"| G["Throw RangeError. Store nothing"]
  E -->|"ttl is 0"| H["Return it with fromCache false. Store nothing"]
  E -->|"ttl is 1 or more"| I["Store with expiry now() + ttl x 1,000. Return with fromCache false"]
`} legend="Every call either answers from a fresh stored entry or goes to lookup; only a good answer with a TTL above 0 is stored." />

At 0 seconds the cache is empty: a miss. `lookup` returns the address with TTL 60, and the cache stores it with an expiry at 60,000 ms. The caller gets `ttl: 60, fromCache: false`.

At 30 seconds the entry is fresh, 30,000 is less than 60,000: a hit. The time left is 30,000 ms, so `ttl: 30, fromCache: true`. `lookup` is not called.

At 59.6 seconds it is still fresh, 59,600 is less than 60,000. The time left is 400 ms, which rounds down to `ttl: 0`. The caller gets the address, and any cache downstream will not keep it. Rounding up to 1 would have let a downstream copy live until 60.6 seconds, past the real expiry.

At 60 seconds the entry has expired, because 60,000 is not less than 60,000. That is a miss: `lookup` is called again, and if the owner changed the address at 45 seconds, this is the first moment this cache sees the new one. This is the spreading you dragged in chapter 3.3, seen from inside one resolver.

At 61 seconds the new entry, stored at 60 seconds, is fresh until 120 seconds: a hit with `ttl: 59`.

## Three ways this goes wrong

**Reading the real clock.** If any line uses `Date.now()`, the fake clock and the real one disagree, and either nothing ever expires or everything always does. The test that starts its fake clock at 0 catches this.

**Off by one at the boundary.** Comparing with `<=` instead of `<` keeps an answer one millisecond past its TTL. That sounds harmless, but it means a TTL of 0 seconds stored at time t is "fresh" at time t, so it gets cached after all. Write the rule once, as "fresh while now is less than expiry", and use it everywhere.

**Caching what should not be cached.** Storing the result before checking it caches a bad TTL. Wrapping `lookup` in `try` and storing a placeholder on failure caches the failure, so a name server that was down for one second looks down for five minutes. This exercise never caches a failure.

solution: |
  function createResolverCache(lookup, now) {
    const entries = new Map(); // name -> { address, expiresAt }

    function resolve(name) {
      const t = now();
      const hit = entries.get(name);
      if (hit && t < hit.expiresAt) {
        return { address: hit.address, ttl: Math.floor((hit.expiresAt - t) / 1000), fromCache: true };
      }
      entries.delete(name);
      const answer = lookup(name); // if this throws, nothing is stored
      if (!Number.isInteger(answer.ttl) || answer.ttl < 0) {
        throw new RangeError("ttl must be a whole number of seconds, 0 or more, got " + answer.ttl);
      }
      if (answer.ttl > 0) {
        entries.set(name, { address: answer.address, expiresAt: t + answer.ttl * 1000 });
      }
      return { address: answer.address, ttl: answer.ttl, fromCache: false };
    }

    return { resolve };
  }

## What this unlocks

This function is a TTL cache, and only its data is DNS-specific. In module 5 you put a cache in front of a database, and the same three decisions return: when an entry expires, what time left to pass on, and what must never be cached, such as an error or a value that is not safe to reuse. The fake clock returns too, whenever a test needs to cross minutes or hours of time.

The rounding rule also matters beyond DNS. Whenever a component hands a time limit to another component, a lease, a lock or a token, round in the direction that keeps the promise safe. Handing out a little less time than you have costs one extra lookup; handing out a little more can let two parts of a system disagree about what is true, which modules 10 and 12 come back to.
