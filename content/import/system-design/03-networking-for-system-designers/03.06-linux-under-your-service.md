Your Node.js service is one process on a Linux machine. When it slows down for everyone at once, the cause is often one level below your code: how the process waits, how it holds connections, and what happens when one piece of work refuses to let go of the thread.

## A process, its threads, its open files

<MermaidDiagram title="Inside one server process" chart={`flowchart TD
  P["Process 4120: node server.js, its own memory"] --> T1["Main thread: runs your JavaScript and the event loop"]
  P --> T2["A few helper threads: some file and DNS work"]
  P --> F["File descriptor table"]
  F --> F0["0, 1, 2: input, output, errors"]
  F --> F3["3: the listening socket on port 443"]
  F --> F4["4 and up: one per client connection, plus open files"]
`} legend="A process owns memory, threads and a table of numbered file descriptors. Every open connection takes one number in that table." />

A process is a running program with its own memory. Threads inside it run the code. Everything the process has open, a log file, the listening port, each client's connection, is a small number called a file descriptor. Ten thousand connected users means ten thousand file descriptors in this one table.

<GoDeeper title="Go deeper: processes, threads and file descriptors">

A <GlossaryTerm term="process" definition="A running program with its own memory, its own threads and its own table of open files, isolated from other processes by the operating system." /> is what the operating system runs when you type `node server.js`. It gets a number, its process ID, and memory that other processes cannot touch. If it crashes, other processes keep running.

A <GlossaryTerm term="thread" definition="One line of execution inside a process. Threads in the same process share its memory, and the operating system switches a CPU core between them." /> is a line of execution inside a process. All threads of a process share its memory. A CPU core runs one thread at a time; the operating system switches cores between threads many times a second. Each switch, a context switch, costs about 10 microseconds in the napkin-math estimates, about 30 times the cost of a simple system call (about 300 ns), so a design that keeps thousands of threads switching pays for it.

A <GlossaryTerm term="file descriptor" definition="A small number a process uses to refer to something it has open: a file, a pipe, a listening port or a network connection." /> is the number a process uses for something it has open. On Linux, files, pipes and network connections all get one. {/* source needed: Linux open(2), socket(2) and accept(2) man pages: sockets are file descriptors, numbers 0, 1 and 2 are standard input, output and error */} Every accepted connection is a new file descriptor, so a server holding 10,000 WebSockets holds 10,000 of them.

There is a limit per process on how many may be open at once. When a busy server hits it, new connections fail with an error such as `EMFILE` ("too many open files"), and the fix is to raise the limit or hold fewer connections. {/* source needed: per-process open file limit (RLIMIT_NOFILE, ulimit -n) and the EMFILE error */}

Containers add one more layer. Linux control groups, cgroups, let the system "organize processes into hierarchical groups whose usage of various types of resources can then be limited and monitored". That is how a container is limited to, say, two CPUs and 512 MB, and module 18 returns to it.

</GoDeeper>

## The port number picks the process

<InteractiveCanvas slug="sysdesign-m3-port-door" />

A connection arrives for port 443. The kernel finds the process listening on 443, the web app, and hands it a new socket, which is a new file descriptor. A connection for port 8080, where nothing listens, is refused at once. The port is how one machine runs many services at the same address.

<GoDeeper title="Go deeper: listening, accepting and a port already in use">

A <GlossaryTerm term="port" definition="A number from 0 to 65535 that, together with the machine's address, says which program a connection is for." /> is a number that, together with an address, names one service on a machine. {/* source needed: RFC 9293 (ports identify connection endpoints; a connection to a port with no listener is refused) */} A server process asks the operating system to listen on a port. From then on, every new TCP connection to that port is queued for that process, and the process accepts each one as a new socket with its own file descriptor. A TCP connection is identified by both addresses and both ports, which is why one listening port can hold thousands of client connections at once.

Two everyday errors follow from this. If you start a second copy of a server on a port that is already taken, it fails with `EADDRINUSE`, address already in use. If a client connects to a port where nothing listens, it gets `ECONNREFUSED`. When a deploy "cannot connect to the database", check first which port the database listens on and whether the process is running at all.

You have already used port 0 in challenge 1: listening on port 0 asks the operating system for any free port, and the server then reports which one it got. That is how the challenge scripts start several servers without clashing.

</GoDeeper>

## A thread per request: threads that only wait

<InteractiveCanvas slug="sysdesign-m3-thread-pool" />

One way to serve requests is to give each one its own thread from a pool. Here four requests take the four threads, and all four sit waiting for the database. Request 5 arrives and finds no free thread, so it waits, even though the CPU is doing nothing. The threads are busy only with waiting.

<GoDeeper title="Go deeper: when thread pools fit, and Little's law again">

In the thread-per-request model, a thread is held from the moment a request arrives until its response is sent, including all the time spent waiting for the database or another service. {/* source needed: thread-per-request server model, for example a servlet container's documentation */} The code is easy to read, because each request runs top to bottom as if nothing else existed.

The limit is Little's law from chapter 2.5. Threads in use equal requests per second times the time each request holds a thread. If each request needs 1 ms of CPU and waits 50 ms for the database, each holds a thread for about 51 ms. At 100 requests per second that is 100 times 0.051, about 5 threads busy on average, nearly all of them only waiting. At 1,000 requests per second it is about 51 threads. A pool of 8 threads can serve at most about 8 / 0.051, about 157 requests per second, however fast the CPU is.

More threads raise that ceiling, but each thread has a cost, and with many threads the operating system spends more time switching between them, at about 10 microseconds a switch. Thread pools fit when requests do a lot of CPU work, or when the number of requests in flight is modest. They fit badly when thousands of connections mostly wait, such as the WebSockets in chapter 3.5.

The numbers here (1 ms of CPU, 50 ms of waiting, 8 threads) are made up to show the shape, not measured.

</GoDeeper>

## An event loop: one thread, many waits

<InteractiveCanvas slug="sysdesign-m3-event-loop" />

An event loop works the other way. One thread starts each request's database query and moves on at once to the next request. When rows come back, it finishes that request. Five waits are in progress, and the thread is free. This is how Node.js runs your code.

<GoDeeper title="Go deeper: how Node.js waits without threads">

An <GlossaryTerm term="event loop" definition="One thread that starts work, moves on without waiting, and runs the next piece of code when a result is ready." /> is how Node.js waits. It runs your JavaScript on a single main thread. When your code calls something slow, such as a database query or a network request, it starts the operation and registers a callback or a promise, then returns. The operating system watches all the open sockets, and when one has data the event loop runs the code waiting for it. {/* source needed: Node.js documentation on the event loop and non-blocking I/O */}

Because waiting costs no thread, one process can hold many idle connections at once. That is why an event loop suits real-time servers with many WebSockets: thousands of connections that mostly wait do not need thousands of threads.

The rule that comes with it is strict. The single thread must never be kept busy for long. Waiting is free, but computing is not: while your code computes, the loop cannot start anything else. Each piece of work should be short, so the loop can come back quickly to everyone else. The next beat shows what happens when a piece of work breaks that rule.

</GoDeeper>

## One blocking call stops everyone

<InteractiveCanvas slug="sysdesign-m3-blocking-call" />

Drag the slow call's length and tap how often it runs. On the event loop, while one request computes, every other request freezes, and the whole server's throughput drops. Switch to the thread pool: the slow call stalls only one thread, but the pool tops out far lower. Each model has its own way to fail.

<GoDeeper title="Go deeper: finding and fixing blocking work">

The numbers behind the picture are illustrative. An event loop where each request needs 1 ms of CPU can serve at most about 1,000 requests a second, since the waits cost no thread. If 1 request in 100 also does 200 ms of CPU work, the average CPU per request becomes 1 + 0.01 times 200 = 3 ms, so the ceiling falls to about 333 requests a second. Worse, every 200 ms block makes every request that arrives during it wait, so the slowest requests, the p99 from chapter 2.4, jump by up to 200 ms for everyone, not only for the report.

Challenge 1 used exactly this on purpose. Its server's busy loop kept the thread for about 10 ms per request, which is why it behaved like a single-server queue with a capacity of about 100 requests a second.

Common causes of blocking in Node.js are functions whose names end in `Sync`, such as `fs.readFileSync` or `crypto.pbkdf2Sync`, parsing or building a very large JSON body, a long loop over a big array, and a regular expression that takes very long on some input. {/* source needed: Node.js guide "Don't block the event loop" */}

There are three fixes, in order of preference. Use the non-blocking version of the call, such as `fs.promises.readFile`. Break long work into small pieces, or limit the input size so no piece can run long. Or move heavy work off the main thread, to a worker thread or a separate worker service behind a queue, which module 15 builds.

To find blocking in a running service, watch event loop delay, the time between when a callback should have run and when it did. Node.js can measure it with `perf_hooks.monitorEventLoopDelay()`. If it jumps while CPU is high, something is computing on the loop. {/* source needed: Node.js perf_hooks.monitorEventLoopDelay documentation */}

</GoDeeper>
