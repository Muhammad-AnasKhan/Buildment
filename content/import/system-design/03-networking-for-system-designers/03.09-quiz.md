```quiz
type: mcq
question: "A shop's app servers in Singapore call a payment API in western Europe, about 160 ms away per round trip. Each checkout opens a new TCP connection with TLS 1.3 to the API and makes one request. The API's own work takes about 50 ms. Which change saves the most time per checkout?"
options:
  - "Ask the payment company for a faster API server"
  - "Compress the request and the response bodies"
  - "Keep a pool of open connections to the API"
  - "Move the app servers to larger machines"
correct: 2
explanations:
  - "The API's work is only about 50 ms. A new connection costs three round trips, about 480 ms, and a faster server shortens none of them."
  - "The bodies are small, so they fit in a few packets either way. The time goes on round trips, not on bytes."
  - "Right. A reused connection skips the TCP and TLS handshakes, so each checkout pays one round trip, about 160 ms, instead of three, about 480 ms."
  - "The app servers are waiting for the network, not computing. Larger machines do not shorten a round trip to Europe."
```

```quiz
type: mcq
question: "At 09:00 a team points api.example.com to a new server. The record's TTL is 300 seconds. A customer's resolver last fetched the record at 08:59. Which address does that customer get at 09:02?"
options:
  - "The old one, until about 09:04"
  - "The new one, as the change came first"
  - "The old one, until about 10:00"
  - "No address at all, until 09:05"
correct: 0
explanations:
  - "Right. The resolver's copy from 08:59 is good for 300 seconds, until 09:04. Until then it answers from its cache with the old address."
  - "The resolver does not know about the change. It keeps its cached copy until that copy's TTL runs out."
  - "The TTL is 300 seconds, five minutes, not an hour. The copy fetched at 08:59 expires at 09:04."
  - "A cached answer stays usable until it expires. Changing the record never leaves the resolver with no address."
```

```quiz
type: mcq
question: "A photo gallery page loads 40 thumbnails over HTTP/2. On trains, where the network often loses packets, users see all the thumbnails freeze together for a moment, several times per page. What explains it, and what helps?"
options:
  - "The server is overloaded, so add more servers"
  - "HTTP/2 caps the streams, so use more domains"
  - "The images are too large, so shrink each one"
  - "A lost packet stalls all streams; use HTTP/3"
correct: 3
explanations:
  - "An overloaded server would be slow everywhere, not only on trains, and would not freeze every thumbnail at the same moment."
  - "The thumbnails already share one connection as streams. The problem is what happens to all of them when a packet is lost."
  - "Smaller images send fewer packets, but any loss would still freeze every thumbnail together on HTTP/2."
  - "Right. HTTP/2 runs on one TCP connection, so one lost packet holds back every stream. On HTTP/3 a loss delays only its own thumbnail."
```

```quiz
type: mcq
question: "A shared whiteboard lets 8 students draw together. Every stroke a student draws must reach the other 7 within about 200 ms, and every student both draws and watches. Which way should strokes travel?"
options:
  - "Polling the server every 2 seconds"
  - "A WebSocket for each student"
  - "Server-sent events alone"
  - "Long polling with a 30 s hold"
correct: 1
explanations:
  - "A stroke could wait up to 2 seconds for the next poll, ten times the 200 ms target."
  - "Right. Strokes flow both ways, often and quickly, so one two-way connection per student fits. Each stroke needs no new request."
  - "SSE carries strokes to the students, but each student's own strokes would need a separate request every time."
  - "It delivers quickly, but every stroke received costs a new request, and students' own strokes need requests too."
```

```quiz
type: mcq
question: "A Node.js photo service resizes each upload in plain JavaScript inside the request handler, about 300 ms of CPU per photo. During upload peaks, requests to /health time out and the load balancer marks healthy servers as down. Why?"
options:
  - "The health check timeout is too strict for peaks"
  - "The database pool has too few connections for /health"
  - "Each resize blocks the thread that answers /health"
  - "The server has too many open file descriptors"
correct: 2
explanations:
  - "A longer timeout hides the symptom. /health is slow because nothing else can run while a resize holds the thread."
  - "A small pool makes requests wait for a connection while the CPU sits idle. Here the timeouts come while the CPU is busy resizing."
  - "Right. The event loop runs all JavaScript on one thread, so /health waits behind every 300 ms resize. Move resizing to worker threads or a separate worker."
  - "Too many open files makes new connections fail with an error, not makes existing requests slow while the CPU is busy."
```
