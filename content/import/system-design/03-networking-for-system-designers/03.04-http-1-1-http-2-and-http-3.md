A shop page needs three small files: a stylesheet, a script and a picture. How long they take depends less on the server than on how the HTTP version shares a connection between them, and on what happens when the network loses one packet.

## HTTP/1.1: one request at a time

<InteractiveCanvas slug="sysdesign-m3-http1-one-at-a-time" />

On one HTTP/1.1 connection, requests take turns. The browser asks for a.css and waits for it, then asks for b.js, then for c.png. Three files cost three round trips, 240 ms at 80 ms each, even though each file is tiny. Browsers work around this by opening several connections to the same server.

<GoDeeper title="Go deeper: why browsers opened many connections, and what that costs">

<GlossaryTerm term="HTTP" definition="Hypertext Transfer Protocol: the request and response rules that browsers, apps and servers use to ask for and send pages, files and API data." /> version 1.1 sends one request on a connection and then waits for the whole response before the next request on that connection. So a connection carries one request at a time.

The HTTP/3 standard, RFC 9114, describes the result: HTTP/1.1 clients open multiple TCP connections to the same server to get parallelism. Three files on three connections arrive together in one round trip. But each extra connection is a new TCP and TLS handshake, the two or three round trips you counted in chapter 3.2, plus a file descriptor on the server for every connection from every user (chapter 3.6).

A page with many small files therefore pays twice under HTTP/1.1: requests queue on each connection, and extra connections cost handshakes. HTTP/2 removes both costs.

</GoDeeper>

## HTTP/2: many streams, one connection

<InteractiveCanvas slug="sysdesign-m3-http2-streams" />

HTTP/2 sends all three requests at once on one connection, each as its own stream. The answers come back side by side, so all three arrive in one round trip: 80 ms instead of 240 ms. One connection means one set of handshakes.

<GoDeeper title="Go deeper: multiplexing, and the catch underneath">

A <GlossaryTerm term="stream" definition="One request and its response inside a shared connection. Streams are numbered, so their pieces can be mixed on the wire and sorted out at the other end." /> is one request and its response. Sending many streams over one connection, with their pieces mixed together, is called multiplexing. RFC 9114 sums up HTTP/2 this way: it multiplexes streams on one TCP connection. Each piece of data is labelled with its stream number, so the receiver can sort the pieces back into separate responses.

This removes both costs of HTTP/1.1. No request waits for another request's response, and the browser needs only one connection per server, so it pays the handshakes once. For a page with dozens of small files, that is a large saving.

The catch is the layer underneath. HTTP/2 streams are separate, but TCP below them is one ordered stream of bytes. TCP knows nothing about HTTP/2 streams; it only knows that byte 5,000 must be delivered before byte 5,001. The next beat shows what that means when a packet goes missing.

</GoDeeper>

## One lost packet stalls every stream

<InteractiveCanvas slug="sysdesign-m3-h2-stall" />

The network drops the packet for a. Packets b and c arrive, but TCP keeps them back, because it delivers bytes only in order and a is missing. Everything waits for a's resend, and all three files are usable only at 160 ms. One loss on one stream delayed every stream. This is called head-of-line blocking.

<GoDeeper title="Go deeper: head-of-line blocking at two layers">

<GlossaryTerm term="Head-of-line blocking" definition="When the item at the front of a line is stuck, everything behind it waits, even items that are ready." /> is the name for this: the front of the line is stuck, so everything behind it waits. RFC 9114 puts it plainly: with HTTP/2 over TCP, "a lost or reordered packet causes all active transactions to experience a stall". The streams are independent at the HTTP layer, but TCP turns them back into one line.

Head-of-line blocking appears at two layers, and the versions fix them in turn. HTTP/1.1 has it at the HTTP layer: a slow response blocks the requests queued behind it on the same connection. HTTP/2 removes that, but keeps it at the TCP layer: a lost packet blocks every stream. HTTP/3 removes the TCP one by moving to QUIC, next beat.

How much does this matter? On a network that rarely loses packets, the stall almost never happens. On a network that loses packets often, every loss stalls the whole page. A single connection also puts all eggs in one basket: under HTTP/1.1, a loss on one of six connections stalls one sixth of the requests, while under HTTP/2 it stalls all of them.

The picture draws the resend arriving one round trip later. In practice the sender first has to notice the loss, which can take longer, so the real stall can be longer than drawn.

</GoDeeper>

## HTTP/3: only the lost stream waits

<InteractiveCanvas slug="sysdesign-m3-h3-streams" />

HTTP/3 runs on QUIC instead of TCP. QUIC keeps each stream's bytes in order separately, so a lost packet blocks only its own stream. Here b and c are shown at 80 ms, as soon as they arrive. Only a waits for its resend. The same loss now costs one file, not the whole page.

<GoDeeper title="Go deeper: what HTTP/3 changes, and what it does not">

RFC 9114 describes HTTP/3 as HTTP mapped onto QUIC, which provides per-stream flow control and stream-level reliability. QUIC orders bytes within each stream, not across the whole connection. A missing packet holds back only the stream it belongs to; every other stream keeps flowing.

HTTP/3 also inherits QUIC's shorter handshake from chapter 3.2: one round trip for a new connection instead of two for TCP with TLS 1.3, and 0-RTT for repeat visits, only for requests that are safe to replay.

What it does not change: the request and response meaning is the same HTTP. Methods, status codes, headers and caching rules are the same, so your API design does not change with the version. And a lost packet still has to be resent; HTTP/3 only stops it from delaying everything else.

Which version should a design use? Most servers and load balancers can speak several versions and agree on one with each client, so this is rarely an either-or choice. {/* source needed: HTTP version negotiation (ALPN) and HTTP/3 discovery */} The difference shows most for users on lossy mobile networks and users far from the server, which is exactly where a lost packet or an extra round trip costs most.

</GoDeeper>

## Drop a packet, compare the versions

<InteractiveCanvas slug="sysdesign-m3-loss-toggle" />

Pick a version, then tap any packet to drop it (tap it again to undo). Watch which files are delayed. On HTTP/1.1, the dropped file and every file queued behind it on its connection wait. On HTTP/2, every file waits. On HTTP/3, only the file you dropped waits. With no drop, HTTP/2 and HTTP/3 look the same.

<GoDeeper title="Go deeper: the model behind the picture">

The picture uses three small files, a round trip of 80 ms (about western Europe to North America East in the napkin-math estimates) and one packet per file. A dropped packet is resent and arrives one round trip later.

Without a drop: HTTP/1.1 on one connection gives a at 80 ms, b at 160 ms and c at 240 ms. HTTP/2 and HTTP/3 give all three at 80 ms.

With a dropped: HTTP/1.1 gives a at 160 ms and pushes b and c back by one round trip too, to 240 ms and 320 ms, because they queue behind a on the same connection. HTTP/2 gives all three at 160 ms. HTTP/3 gives b and c at 80 ms and a at 160 ms.

Real pages have more files, more packets per file and loss detection that takes longer than one round trip. Use the picture to see the shape of each version's behaviour, not to predict a page's load time.

</GoDeeper>

## QUIC survives a change of network

<InteractiveCanvas slug="sysdesign-m3-quic-migration" />

A phone downloads over Wi-Fi, then walks out of range and switches to mobile data. Its address changes. A TCP connection is tied to the old address, so it breaks and must be opened and secured again. A QUIC connection is named by a connection ID, so the server recognises it on the new network and the download carries on.

<GoDeeper title="Go deeper: connection IDs and why they matter for phones">

A TCP connection is identified by four numbers: the two addresses and the two ports. When the phone's address changes, the old connection no longer matches anything, and the app must open a new one: new TCP handshake, new TLS handshake, and the request again. On a link 160 ms away that is half a second, every time the phone changes network.

QUIC, in RFC 9000, identifies each connection with a connection ID chosen by the endpoints. Packets from the phone's new address carry the same ID, so the server continues the same connection. This is called connection migration.

For users on phones that hop between Wi-Fi and mobile data, this is not a detail. It is the difference between a download that continues and one that restarts. When you design an app for such users, prefer connections that can survive a change of network, and make every long transfer resumable anyway, because sometimes even QUIC cannot continue.

</GoDeeper>
