## One tap, three round trips

<InteractiveCanvas slug="sysdesign-m3-open-a-link" />

First the phone asks a resolver for the shop's address. Then it opens a connection: SYN out, SYN-ACK back. Then it agrees on keys with TLS. Only then does `GET /` leave. Each step waits for an answer from Singapore, 160 ms away. The first byte arrives at 480 ms, and the server did almost no work.

<GoDeeper title="Go deeper: what each step is for">

Each step solves a different problem, and each costs time because it needs an answer before the next step can start.

**DNS: a name becomes an address.** Lina's phone knows the name of the shop, not where it lives. It asks a <GlossaryTerm term="resolver" definition="A server, usually run by your internet provider or a public service, that finds the address for a name and remembers the answer for a while." />, which answers from memory if someone asked recently, or asks other name servers if not. Here the resolver already had the answer, so this step was quick. In chapter 3.3 you will see the slow case, and why a change to a name can take hours to reach everyone.

**TCP: a connection both sides agree on.** The phone sends SYN ("I want to talk"), the server answers SYN-ACK ("I hear you, go ahead"), and the phone's ACK goes back with the request right behind it. That costs one <GlossaryTerm term="round trip" definition="The time for a message to go from one machine to another and for the answer to come back. Distance decides most of it." /> before any request can be sent.

**TLS: a secret only the two ends share.** HTTPS adds TLS on top of TCP. The two sides agree on keys so that nobody in between can read or change the page. With TLS 1.3, the current version, a full handshake costs one more round trip.

**HTTP: the request itself.** Now `GET /` can leave, and the answer comes back one round trip later.

So the time before the first byte is three round trips plus whatever DNS cost. Notice what is missing: the page's size and the server's speed. A faster server would barely help Lina. The distance, paid three times over, decides almost everything. The 160 ms is an estimate for a round trip from western Europe to Singapore, from the napkin-math project; real networks vary from day to day.

</GoDeeper>

## Where the half second goes

<MermaidDiagram title="Lina's tap, step by step" chart={`flowchart TD
  A["Tap on the link"] --> B["DNS: ask the resolver for the address. Cached here, so quick"]
  B --> C["TCP: SYN out, SYN-ACK back. 1 round trip, 160 ms"]
  C --> D["TLS 1.3: hello out, keys back. 1 round trip, 160 ms"]
  D --> E["HTTP: GET out, first byte back. 1 round trip, 160 ms"]
  E --> F["First byte at 480 ms. Distance paid 3 times"]
`} legend="Four steps run one after another; three of them each wait a full round trip to Singapore." />

Three of the four steps are round trips to Singapore, one after another. Cut the number of round trips, or shorten each one, and Lina waits less. This module shows how: reuse connections, use newer protocols, move servers or copies closer, and choose how real-time updates travel.

<GoDeeper title="Go deeper: what this module covers">

A system designer does not need to know every bit in a packet. You need to know what a request costs on the wire, so you can count it the way you counted latency in module 2.

Chapter 3.2 counts the round trips of each kind of connection: TCP, TCP with TLS 1.3, and QUIC, which does both handshakes in one. You will price them by distance and see why reusing a connection is one of the cheapest speed-ups there is. Chapter 3.3 opens up DNS: how a resolver finds an address, why answers are kept for a set time (the TTL), why changing a record is slow to reach everyone, and how one address can be served from many places at once. Chapter 3.4 compares HTTP/1.1, HTTP/2 and HTTP/3, and what happens to each when a single packet is lost. Chapter 3.5 asks how a chat or a delivery map gets news without the user pressing refresh: polling, long polling, server-sent events and WebSockets. Chapter 3.6 goes one level down, into the Linux process that runs your service: threads, file descriptors, ports, and why one slow call can freeze a Node.js server.

Then you practise. In 3.7 you write a small DNS-style cache with a TTL, with tests. In 3.8 you measure handshakes, connection reuse and four real-time methods on your own machine, in your challenges repository.

The numbers in this module come from public estimates and standards, and each chapter names its sources. Round trips between regions change with routes and load, so treat each number as a size, not a promise.

</GoDeeper>
