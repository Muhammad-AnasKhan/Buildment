A new HTTPS connection to a server 160 ms away costs half a second before the first byte, as Lina found in 3.1. This chapter counts where those round trips come from and which ones you can remove.

## TCP asks before it talks

<InteractiveCanvas slug="sysdesign-m3-tcp-handshake" />

Before any data moves, TCP runs a handshake. The client sends SYN, the server answers SYN-ACK, and the client's ACK leaves with the request right behind it. So one round trip, there and back, is spent before the request can go. At 80 ms per round trip, the first byte arrives at 160 ms.

<GoDeeper title="Go deeper: what TCP gives you, and UDP does not">

A <GlossaryTerm term="round trip" definition="The time for a message to reach the other machine and for its answer to come back. Often written RTT." /> is the unit of this chapter: count them, then multiply by the distance.

<GlossaryTerm term="TCP" definition="Transmission Control Protocol: a connection between two programs that delivers a stream of bytes reliably and in order, resending anything that is lost." /> turns an unreliable network into a reliable, ordered stream of bytes. The network itself may drop, delay or reorder packets. TCP numbers every byte, the receiver acknowledges what it got, and the sender resends what was not acknowledged. The receiving program always reads the bytes in the order they were sent (RFC 9293).

The three-way handshake sets that up. SYN carries the client's starting number, SYN-ACK carries the server's and confirms the client's, and ACK confirms the server's. Both sides now agree where counting starts, so both can spot a missing piece. The cost is one round trip before the client may send its request. The request can travel right behind the final ACK, which is why the picture shows "ACK, GET /" together.

<GlossaryTerm term="UDP" definition="User Datagram Protocol: sends each packet on its own, with no handshake, no resending and no ordering. Anything more is up to the program." /> is the other basic choice. It has no handshake and makes no promises: a packet arrives or it does not, in whatever order the network chooses. {/* source needed: RFC 768 (UDP: no connection setup, no delivery or ordering guarantee) */} That sounds worse, but it leaves the program free to build exactly the reliability it needs. QUIC, later in this chapter, is built that way on top of UDP.

Ordering has a hidden cost that chapter 3.4 makes visible. If one packet is lost, TCP holds back every byte behind it until the lost one is resent, even bytes that arrived safely. For one file that is fine. For many independent requests sharing one connection, it means one loss delays them all.

</GoDeeper>

## TLS adds a round trip on top

<InteractiveCanvas slug="sysdesign-m3-tls-handshake" />

HTTPS adds TLS on top of TCP. After TCP connects, the client says hello and the server answers with its keys and certificate. That is a second round trip, so the request leaves at 160 ms and the first byte comes back at 240 ms. The page is the same size. The wait grew because the secure setup needs one more conversation.

<GoDeeper title="Go deeper: what TLS 1.3 does in its one round trip">

<GlossaryTerm term="TLS" definition="Transport Layer Security: agrees on secret keys between client and server, proves the server is who it says it is with a certificate, and then encrypts everything sent." /> does three jobs. It agrees on keys that only the two ends know, it proves the server's identity with a certificate, and it encrypts and protects every byte after that.

In TLS 1.3, the client's first message (ClientHello) already carries its half of the key agreement. The server answers with its half, its certificate and a "Finished" message in one flight. When that flight reaches the client, both sides have the keys, so the full handshake costs one round trip (RFC 8446). The client's own "Finished" travels together with the request.

So a new HTTPS connection over TCP and TLS 1.3 costs about two round trips before the request leaves, and three before the first byte comes back. That is the number to remember.

TLS 1.2, the version before 1.3, needs more round trips for a full handshake. You will measure how many yourself in challenge 2, part 1, by forcing each version against the same server. {/* source needed: RFC 5246 (TLS 1.2 full handshake round trips) */} A server that still accepts TLS 1.2 lets an old client pay that extra cost without anyone noticing.

</GoDeeper>

## QUIC does both handshakes at once

<InteractiveCanvas slug="sysdesign-m3-quic-handshake" />

QUIC runs over UDP and carries the TLS 1.3 handshake inside its own first messages. Transport and keys are agreed in the same round trip. The connection is ready at 80 ms and the first byte arrives at 160 ms, one round trip earlier than TCP with TLS. HTTP/3, in chapter 3.4, runs on QUIC.

<GoDeeper title="Go deeper: QUIC, 0-RTT and the replay catch">

<GlossaryTerm term="QUIC" definition="A transport protocol that runs over UDP, builds in TLS 1.3, and carries many independent streams in one connection. HTTP/3 runs on it." /> is a newer transport protocol (RFC 9000). It runs over UDP and provides its own reliability, ordering inside each stream, and security. Its handshake is "a combined cryptographic and transport handshake": the first packet the client sends already carries the TLS 1.3 ClientHello. One round trip later both the connection and the keys are ready. That is where the saved round trip comes from: it is not a faster network, it is one fewer conversation.

QUIC and TLS 1.3 also offer **0-RTT**. When a client returns to a server it talked to before, it can reuse what it learned last time and send its request in its very first flight, with no round trip of setup at all. The first byte then comes back after one round trip.

The catch is in the TLS 1.3 standard: 0-RTT data has "no guarantees of non-replay between connections". An attacker who records that first flight can send it again, and the server may act on it twice. Reading a page twice is harmless. Placing an order twice is not. So 0-RTT is safe only for requests that are safe to repeat, which module 6 calls idempotent requests. Whoever turns 0-RTT on must decide which requests may use it, so that a payment endpoint never does.

UDP has a practical cost too. Some networks block or slow UDP traffic, so browsers and apps that speak HTTP/3 keep TCP as a fallback. {/* source needed: UDP blocked on some networks, and HTTP/3 clients falling back to TCP */}

</GoDeeper>

## Distance multiplies every round trip

<InteractiveCanvas slug="sysdesign-m3-handshake-cost" />

Tap a protocol, then drag the rail to move the server away: same region, across North America, across the Atlantic, to Singapore. The bar shows the time before the first byte. In the same region every choice is under a millisecond. At 160 ms per round trip, TCP with TLS costs 480 ms and QUIC 320 ms. The handshake count matters most when the server is far.

<GoDeeper title="Go deeper: the numbers behind the picture">

The time before the first byte on a new connection is the number of round trips times the time of one round trip. Count the round trips first, then multiply.

| Way to connect | Round trips before the first byte |
|---|---|
| TCP, plain HTTP | 2 (handshake, then the request) |
| TCP with TLS 1.3 | 3 (TCP, TLS, then the request) |
| QUIC (HTTP/3), first visit | 2 (combined handshake, then the request) |
| QUIC with 0-RTT, returning visit | 1 (the request rides in the first flight) |
| A reused connection, any of the above | 1 |

Now the distances, from the napkin-math project's estimates: about 0.25 ms for a round trip inside one cloud region, about 60 ms across North America from east to west, about 80 ms from western Europe to the east of North America, and about 160 ms from western Europe to Singapore.

Worked out for TCP with TLS 1.3 (3 round trips): 0.75 ms inside a region, 180 ms across North America, 240 ms across the Atlantic, 480 ms to Singapore. For QUIC (2 round trips): 0.5 ms, 120 ms, 160 ms and 320 ms.

Two design lessons follow. First, inside a data centre the handshakes are nearly free, so a service that calls its database in the same region barely notices them. Second, for users far from the server, the handshakes are most of the wait. You can attack that in three ways: fewer round trips (QUIC, 0-RTT for safe requests), fewer new connections (reuse, next beat), or a shorter round trip, by ending the connection on a machine close to the user. That last idea is the edge server and the CDN, which module 5 covers.

These numbers leave out DNS, the server's own work, the time to send a large page, and lost packets. They are a lower bound for a small request: real first bytes come later, never earlier.

</GoDeeper>

## Keep the connection, skip the setup

<InteractiveCanvas slug="sysdesign-m3-keep-alive" />

The handshakes are paid once per connection, not once per request. A second request on a connection that is already open and secure costs only its own round trip: 80 ms instead of 240 ms. Reusing connections is one of the cheapest speed-ups in system design, and you will measure it yourself in challenge 2.

<GoDeeper title="Go deeper: keep-alive, pools and their failure modes">

Keeping a connection open after a request, so the next request can use it, is called <GlossaryTerm term="keep-alive" definition="Leaving a connection open after a request so the next request can reuse it without new handshakes." />. A program that talks to the same server often keeps a small set of open connections, a connection pool, and hands one to each request.

This matters most between your own services. An app server that opens a new TLS connection to the payment service for every checkout pays three round trips each time. Inside one region that is under a millisecond, but across regions it is hundreds of milliseconds per request. With a pool, the cost is paid once and shared by thousands of requests.

In Node.js, an HTTP agent decides whether connections are reused. In challenge 2, part 2, you send ten requests with `new https.Agent({ keepAlive: false })` and ten with `keepAlive: true`, and compare the totals. In the run printed there, ten requests to a server about 120 ms away took about 3.7 seconds without reuse and about 1.4 seconds with it, and the second number opened one connection instead of ten.

Reuse has failure modes. A connection that sat idle may have been closed by the server or by something in between, and the next request on it fails and must be retried on a new connection. {/* source needed: idle keep-alive connections closed by the server, and the retry on a fresh connection (Node.js http.Agent documentation) */} A pool that is too small makes requests queue for a connection, which is Little's law from chapter 2.5 again: connections in use equal requests per second times the time each one holds a connection. A pool that is too large keeps thousands of idle connections open on the server, and each one holds a file descriptor, which chapter 3.6 explains.

</GoDeeper>
