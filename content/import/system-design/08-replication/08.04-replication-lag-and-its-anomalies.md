## Her comment vanished, then came back

<InteractiveCanvas slug="sysdesign-comment-flicker" />

Refresh 1 reaches replica 1 at 200 ms. Replica 1 got the comment at 150 ms, so Amna sees it. Refresh 2 reaches replica 2 at 350 ms, but replica 2 only gets the comment at 600 ms, so it is gone. Refresh 3 is back on replica 1: the comment returns. Two promises broke. Amna did not see her own write, and her page went back in time.

<GoDeeper title="Go deeper: the two broken promises">

Users expect a few simple things from a page they refresh. Terry and colleagues named these expectations in 1994 as <GlossaryTerm term="session guarantees" definition="Promises a replicated database makes to one client session, such as seeing its own writes and never seeing time go backwards. Named by Terry et al. in 1994." />. Two of them broke for Amna.

**Read-your-writes.** After you write something, your own later reads show it. Refresh 2 broke this. Other users may see a comment a little late, and that is usually fine. The writer seeing their own write vanish is not fine. It looks like data loss, so users post the comment again.

**Monotonic reads.** Once you have seen a value, your later reads never show an older state. Monotonic means "only moves forward". Amna saw the comment on refresh 1 and lost it on refresh 2. This can happen to any reader, not only the writer. A friend of Amna's could see her comment, refresh, and see it disappear.

Look closely at which read failed. Only refresh 2 went to the slow replica. Say Amna's first refresh had come at 450 ms or later. Then refresh 2 would arrive at 600 ms or later, after replica 2 caught up, and nothing would break. That is before the 600 ms lag. What matters is the read that hits the slow replica, and when it hits it. Now say she refreshed at once, at 0, 150 and 300 ms. Two reads would miss the comment, but nothing would go back in time, because she never saw it before losing it. Same lag, different symptom.

A third promise, consistent prefix, says readers see writes in the order they happened, so an answer never appears before its question. It needs two related writes, and this story has only one, so it is reproduced in 11.4.

</GoDeeper>

## Replicas run behind the leader

<InteractiveCanvas slug="sysdesign-replica-behind" />

The leader writes each change into its log, one box at a time. Each replica fills the same boxes in the same order, but later, by its lag. So a lag in time is also a lag in writes. Drag the picture to change replica 2's lag, and count how many writes it is missing. At zero lag, both replicas keep up with the leader.

<GoDeeper title="Go deeper: lag and log positions">

In 8.3 you chose asynchronous replication for the forum. The leader saves a write, tells the client "done", and then sends the change to each replica in the background. That keeps writes fast. Its price is that every replica is a little behind. The delay is called <GlossaryTerm term="replication lag" definition="The time between a write being saved on the leader and the same write being applied on a replica. With asynchronous replication it is never zero, and it grows when the replica or the network is busy." />.

How big is it? PostgreSQL's streaming replication is asynchronous by default. Its documentation describes the delay as typically under one second, if the replica can keep up with the load. Amazon Aurora replicas share storage with the writer, and AWS says their lag is usually much less than 100 milliseconds, growing under heavy writes. The 600 ms in this chapter is like a PostgreSQL replica under heavy writes. Lag is not a fixed number: the same replica can be fast one minute and slow the next.

Every box in the picture has a number that only grows. That number is a <GlossaryTerm term="log sequence number (LSN)" definition="The position of a change in the database's write log. It only grows. A replica that has applied position N has every change up to and including N." />. PostgreSQL calls a replica a standby. On the primary, `pg_current_wal_lsn()` returns the leader's current position. On a standby, `pg_last_wal_replay_lsn()` returns how far that replica has replayed.

Positions turn a timing question into a comparison. A router cannot measure lag in milliseconds exactly. It does not need to. To know whether a replica has Amna's comment, it only compares two numbers: the position of her write and the position the replica has applied.

</GoDeeper>

## Three fixes, three costs

<InteractiveCanvas slug="sysdesign-read-routing" />

Pick where Amna's reads go, and watch the same three refreshes again. With "Any replica", the comment flickers. "Leader for own reads" always shows it, but the leader now serves all 3 reads. "Replica at my position" also always shows it, and every read stays on a replica. Each fix moves the cost somewhere else: onto the leader, or into state the router must track.

<GoDeeper title="Go deeper: each fix and what it costs">

**Leader for own reads.** The router sends a user's reads to the leader for anything that user may have changed. Some apps do this only for a fixed time, such as one minute after the user's last write. It fixes both promises for the writer. The cost is leader load. If many users write often, most reads land on the leader, and the replicas sit idle. A fixed time window also hides a trap: if the lag ever grows past the window, the bug returns.

**Sticky replica.** This one is not in the picture. Each user always reads from the same replica, for example one picked by a hash of their user ID. A single replica never moves backwards, so monotonic reads hold. Read-your-writes does not. If Amna's sticky replica were replica 2, all three refreshes would miss the comment, because all three come before 600 ms. Busy users also make the load uneven. When a sticky replica fails, its users move to another one that may be further behind, and they can go back in time once.

**Replica at my position.** When the leader confirms a write, it also returns the write's log position. The client keeps it as a token, in a cookie or a header, and sends it with every read. The router picks a replica whose applied position is at least the token. If none has caught up, it falls back to the leader or waits a few milliseconds. The cost is state: the client carries the token, and the router must know every replica's position. A token also lives in one browser. On Amna's phone there is no token, so the bug can return on a second device.

| Fix | Read-your-writes | Monotonic reads | Main cost |
|---|---|---|---|
| Leader for own reads | Fixed | Fixed for the writer | Load on the leader |
| Sticky replica | Not fixed | Fixed | Uneven load; failover moves users |
| Replica at my position | Fixed | Fixed if reads raise the token | Client and router state |

A token that only records writes protects the writer. With one writer and one record, as in the picture, that is enough. To give monotonic reads to every reader, the router must also raise the token after each read. It sets the token to the position of the replica that served it. Then no later read can land on an older replica.

**Failure modes.** If every replica falls behind at once, the router sends every recent writer to the leader. A busy leader is often why the replicas fell behind. Cap the share of reads the leader will accept, and let the rest wait briefly. A replica restored from a backup can have its position move backwards, so remove it from rotation until it catches up. A cleared cookie or a new device looks like "no token". If read-your-writes matters across devices, store the user's last write position on the server, keyed by user ID.

**In AWS.** Aurora replicas read from the same shared storage as the writer, so their lag is usually much less than 100 ms. It is still not zero, so these anomalies can still happen. Amazon RDS also offers read replicas for engines such as PostgreSQL and MySQL. They are copied asynchronously, and AWS reports how far each one is behind in CloudWatch. Aurora's reader endpoint spreads new connections across replicas, so two page loads on separate connections can land on different replicas, like "Any replica". A pool that keeps one connection per user behaves more like a sticky replica.

## Carry your position, not a clock

<InteractiveCanvas slug="sysdesign-position-token" />

Amna's comment is position 1 in the leader's log, and her app carries that number with each read. The router knows replica 2 is still at 0 and replica 1 has reached 1. It skips replica 2 and reads from replica 1, so Amna sees her comment. No clock is involved. Comparing two numbers is enough to keep her own write on her screen.

<GoDeeper title="Go deeper: the routing decision in code">

The heart of the router is one comparison and one fallback. Here it is in Node-style JavaScript. It is deliberately partial. Three parts are left out: choosing among several fresh replicas, refreshing the replicas' positions, and raising the token after reads. You build them in code exercise 8.8.

```js
// The decision only: can this replica serve this client's read?
function nodeForRead(replica, session) {
  // The replica has the client's last write once it has applied that position.
  if (replica.appliedPosition >= session.lastWritePosition) {
    return replica.name;
  }
  // Not caught up yet. The leader has every write, so it is always safe.
  return "leader";
}
```

Walk through Amna's run. Her post returns position 1, so her `lastWritePosition` is 1. At 200 ms, replica 1 has applied position 1, so it serves the read. At 350 ms it is replica 2's turn, and replica 2 is still at 0. This function would send that read to the leader. The router in the pictures does one thing more: it tries replica 1 before the leader, and replica 1 has caught up. That is why "Replica at my position" kept all three reads on replicas.

The fallback is a choice, not a law. Sending the read to the leader keeps the page fast, but it loads the leader during a lag spike. Waiting a few milliseconds keeps load off the leader, but the page is slower.

To debug a router, log three numbers for every read: the client's token, the node chosen, and that node's applied position. A missed own write always shows up as a read where the chosen node's position is below the token. In challenge 7 you run the same decision against a real PostgreSQL replica.

</GoDeeper>
