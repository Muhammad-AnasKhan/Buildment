## The comment that came back

Amna runs an evening study group on a community forum app (a fictional product). She posts a comment: "Room 4 is booked for Thursday." She refreshes the page. The comment is there. She refreshes again, and it is gone. A third refresh, and it is back.

Nothing was deleted, and no server failed. The forum writes to one database, the leader, and reads from two copies of it, the replicas. Amna's three refreshes went to different copies, and one of them had not received her comment yet. You met this bug in 8.1. In this chapter you reproduce it on purpose, name the rules it breaks, and fix it three ways.

By the end you can read a replica story and name the promise it breaks. You can also pick the fix whose cost you can afford: more reads on the leader, uneven load, or extra state in the client.

## Where the lag comes from

In 8.3 you chose asynchronous replication for the forum. The leader saves a write, tells the client "done", and then sends the change to each follower in the background. That choice keeps writes fast. Its price is that every replica is a little behind the leader. The time between the leader saving a write and a replica applying it is called <GlossaryTerm term="replication lag" definition="The time between a write being saved on the leader and the same write being applied on a replica. With asynchronous replication it is never zero, and it grows when the replica or the network is busy." />.

How big is it? The PostgreSQL documentation says its streaming replication is asynchronous by default. It describes the delay as typically under one second, if the replica is powerful enough to keep up with the load. Amazon Aurora replicas share storage with the writer, and AWS says their lag is usually much less than 100 milliseconds, growing under heavy writes. So lag is not a fixed number. It changes with load, and the same replica can be fast one minute and slow the next.

The write and the reads take different roads. The write goes to the leader and is confirmed there. The reads go through a router to replicas that may not have the write yet. Every anomaly in this chapter comes from that split. Every fix is a rule for the router.

## Promises that lag can break

A user does not think about replicas. They expect a few simple things from a page they refresh. Terry and colleagues named these expectations in 1994 as <GlossaryTerm term="session guarantees" definition="Promises a replicated database makes to one client session, such as seeing its own writes and never seeing time go backwards. They were named by Terry et al. in 1994." />. This chapter covers two of them. Module 11 covers the rest.

**Read-your-writes.** After you write something, your own later reads show it. Amna's second refresh broke this: she wrote the comment, then read a copy without it. Other users may see the comment a little late, and that is usually fine. The writer seeing their own write vanish is not fine. It looks like data loss, and users post the comment again.

**Monotonic reads.** Once you have seen a value, your later reads never show an older state. Monotonic means "only moves forward". Amna broke this too. She saw the comment on refresh 1 and lost it on refresh 2, so her page went back in time. This can happen to any reader, not only the writer. A friend of Amna's could see her comment, refresh, and see it disappear.

There is a third promise, called consistent prefix: readers see writes in the order they happened, so an answer never appears before its question. It needs two related writes, and the canvas here has only one, so you will reproduce it in 11.4.

The next two reads go to replica 1, which has caught up by then.

**What changed.** In the default run you saw one missed own write and one trip back in time, both on refresh 2. Refreshes 1 and 3 landed on replica 1, which was already caught up. Now set **Any replica** and a first refresh of 0 ms. Two reads miss the comment, but nothing goes back in time. Amna never saw the comment before losing it. Same lag, different symptom: the symptom depends on the order of reads, not only on the size of the lag.

The second experiment holds a surprise. Nothing breaks from a first refresh of 450 ms, although the lag is 600 ms. Only refresh 2 goes to replica 2, and it arrives 150 ms after refresh 1, at 600 ms. That is exactly when replica 2 catches up. The reads that land on the fast replica never notice the slow one. What matters is the read that hits the slow replica, and when it hits it.

**Limits of the model.** Each replica's lag is fixed for the whole run, and there is only one writer and one record. Real lag moves from second to second and jumps under heavy writes. The **Any replica** router takes turns instead of choosing at random, so every run is the same. ## Why it happens: positions in a log

To fix the bug, the router needs a way to ask "has this replica got Amna's write?" The leader makes that question cheap. It writes every change to a log in order, and every entry has a number that only grows. A replica applies the log in the same order. So "how far behind is this replica?" becomes "which log number has it applied?"

That number is a <GlossaryTerm term="log sequence number (LSN)" definition="The position of a change in the database's write log. It only grows. A replica that has applied position N has every change up to and including N." />. PostgreSQL calls a replica a standby. On the primary, `pg_current_wal_lsn()` returns the leader's current position. On a standby, `pg_last_wal_replay_lsn()` returns how far that replica has replayed. In the canvas, Amna's comment is position 1. A replica "has" the comment once its applied position is 1 or more.

Positions turn a timing question into a comparison. The router does not need to know the lag in milliseconds, which it cannot measure exactly anyway. It only needs two numbers: the position of the client's last write, and the position each replica has applied.

## Three fixes and what each one costs

Each fix is a different routing rule. Each one removes some anomalies and moves the cost somewhere else.

**Read your own recent writes from the leader.** This is the canvas's **Leader for own reads**. The router sends a user's reads to the leader for anything that user may have changed. Some apps do this only for a fixed time, such as one minute after the user's last write. It is simple, and it fixes both read-your-writes and monotonic reads for the writer. The cost is leader load. In the canvas the leader took all 3 of Amna's reads. If many users write often, most reads land on the leader, and you added replicas for nothing. A fixed time window also hides a trap: if the lag ever grows past the window, the bug returns.

**Sticky replica.** Each user always reads from the same replica, for example the one picked by a hash of their user ID. A single replica never moves backwards, so monotonic reads hold. Read-your-writes does not. If Amna's sticky replica is replica 2, all three of her refreshes miss the comment, because all three come before 600 ms. Stickiness also spreads load unevenly when some users are much busier than others. When a sticky replica fails, its users move to another one that may be further behind. They can go back in time once.

**Position tokens.** This is the canvas's **Replica at my position**. When the leader confirms a write, it also returns the write's log position. The client keeps it as a token, in a cookie or a header, and sends it with every read. The router picks a replica whose applied position is at least the token. If none has caught up, it falls back to the leader, or waits a few milliseconds. This fixes read-your-writes and keeps reads on replicas whenever one is fresh enough. In the default canvas run, it sent 0 of 3 reads to the leader. The cost is state: the client must carry the token, and the router must know every replica's position. A token also lives in one browser. When Amna opens the forum on her phone, the phone has no token, so the bug can return on the second device.

| Fix | Read-your-writes | Monotonic reads | Main cost |
|---|---|---|---|
| Leader for own reads | Fixed | Fixed for the writer | Load on the leader |
| Sticky replica | Not fixed | Fixed | Uneven load; failover moves users |
| Position tokens | Fixed | Fixed if reads raise the token | Client and router state |

The table hides one detail worth saying in words. A token that only records writes protects the writer. In the canvas that is enough, because there is one writer and one record. To give monotonic reads to every reader, the router must also raise the token after each read. It sets the token to the position of the replica that served the read. Then no later read can land on an older replica.

## The routing decision in code

The heart of the position-token router is one comparison and one fallback. Here it is in Node-style JavaScript. It is deliberately partial. Three parts are left out: choosing among several fresh replicas, refreshing the replicas' positions, and raising the token after reads. You build them in code exercise 8.8.

```js
// The decision only: can this replica serve this client's read?
function nodeForRead(replica, session) {
  // The replica has the client's last write once it has applied that position.
  if (replica.appliedPosition >= session.lastWritePosition) {
    return replica.name;
  }
  // Not caught up yet. The leader has every write, so it is always safe.
  return "leader";
}
```

Walk through Amna's run with it. Her post returns position 1, so her session's `lastWritePosition` is 1. At 200 ms, replica 1 has applied position 1, so it serves the read. At 350 ms, it is replica 2's turn, and replica 2 is still at 0. This function would send that read to the leader. The canvas router does one thing more: it tries replica 1 before the leader, and replica 1 has caught up. That extra step is why the canvas sent 0 of 3 reads to the leader.

The fallback is a choice, not a law. Sending the read to the leader keeps the page fast, but it loads the leader during a lag spike. Waiting a few milliseconds for a replica keeps load off the leader, but it makes the page slower. In challenge 7 you run the same decision against a real PostgreSQL replica.

## Failure modes and how to debug them

**A lag spike sends everyone to the leader.** If every replica falls behind at once, the router falls back to the leader for every recent writer. The leader was already busy, which is often why the replicas fell behind. Cap the share of reads the leader will accept. Let the rest wait briefly for a replica instead.

**Stale replica positions.** The router only knows positions from its last health check. Old numbers are safe, because a position read 100 ms ago can only be lower than the real one. The router is cautious, not wrong. A replica restored from a backup is different: its position can move backwards. Remove it from rotation until it catches up.

**The token is lost.** A new device, a cleared cookie, or a mobile app that drops the header all look like "no token". The router then treats the read as safe for any replica. If read-your-writes matters across devices, store the user's last write position on the server, keyed by user ID.

To debug any of these, log three numbers for every read: the client's token, the node chosen, and that node's applied position. A missed own write always shows up as a read where the chosen node's position is below the token.

## In AWS

Aurora replicas read from the same shared storage as the writer, so their lag is usually much less than 100 milliseconds. It is still not zero, and it grows under heavy writes, so every anomaly in this chapter can still happen. Amazon RDS also offers read replicas for engines such as PostgreSQL and MySQL. Like the forum's replicas, they are copied asynchronously, and AWS reports how far each one is behind in CloudWatch. That lag figure is the first number to check when users report a vanishing write.
