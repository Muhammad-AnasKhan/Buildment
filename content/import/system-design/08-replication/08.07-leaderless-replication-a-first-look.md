Every design so far had a leader, a node with special power, and a procedure for when it dies. What if no node is special? Any node takes any write, and the client counts answers. This is a first look. Module 13 builds it in full.

## No leader: write to many nodes

<InteractiveCanvas slug="sysdesign-m8-write-many" />

There is no leader. The client sends the write to all five nodes that hold the key and counts the confirmations. Nodes 1, 2 and 3 answer quickly, and with three confirmations the write counts as done. Nodes 4 and 5 are slow and get the value a little later. No single node orders the writes, and none must stay alive.

<GoDeeper title="Go deeper: where leaderless designs come from">

Amazon's Dynamo paper of 2007 describes a leaderless store. Each key lives on N nodes. A write is sent to the nodes that hold the key and succeeds once W of them confirm. A read asks R nodes and takes the answer. The paper's common setting was N = 3, R = 2, W = 2 [S45]. Latency is set by the slowest of the W or R nodes you wait for [S45].

The great gain is that there is no failover. With a leader, losing the leader stops writes until the steps of chapter 8.5 finish. Here, losing one node changes nothing as long as enough others remain. The loss is that nothing orders the writes. Two clients can write the same key at once, and the store must keep both versions, or choose, or merge them, as in chapter 8.6. Dynamo used vector clocks for this, a small record of who saw what, which module 10 teaches [S45].

Teach with care: Dynamo (2007) is not the same system as Amazon DynamoDB (2022). The DynamoDB service replicates each partition with a leader and a group of three replicas, and writes are acknowledged when a quorum has stored the log record [S44]. Only the 2007 design is leaderless.

</GoDeeper>

## Write to three of five, read from two

<InteractiveCanvas slug="sysdesign-m8-quorum-nodes" />

Tap three nodes to write, tap Confirm write, then tap two nodes to read from. If the nodes you read include at least one that got the write, the read finds the newest value. Try reading from the two nodes that missed it. Then tap Reset, write to four nodes and read from two, and notice when a read can no longer miss.

<GoDeeper title="Go deeper: the overlap rule, and what it does not promise">

Call the number of nodes N, the number that must confirm a write W, and the number a read asks R. If R + W is more than N, every group of R nodes shares at least one node with every group of W nodes [S45]. That shared node holds the newest write, so the read sees it. With N = 5, W = 3 and R = 3 it always overlaps. A majority is (N + 1) / 2, which is 3 here, so choosing W and R as majorities always works [S52]. With W = 3 and R = 2 the sum is 5, not more than 5, so the read can miss, as the prediction showed.

| N | W | R | R + W > N? | What it means |
|---|---|---|---|---|
| 5 | 3 | 3 | yes (6) | Overlap guaranteed. Each side survives 2 failed nodes. |
| 5 | 3 | 2 | no (5) | A read can miss the newest write. |
| 5 | 4 | 2 | yes (6) | Overlap guaranteed. Writes survive only 1 failed node. |
| 5 | 5 | 1 | yes (6) | Reads are cheap. One failed node blocks every write. |

Overlap is necessary, not sufficient. A write that reached only 2 of 5 nodes before the client crashed was never confirmed, yet a later read may still see it, and a later one may not. Two writes at the same time can leave nodes with different values. And the rule breaks entirely when the group is not the usual one, as the fourth picture shows. Kleppmann's notes add that plain quorum reads need an extra step, read repair, before they are linearizable [S52].

</GoDeeper>

## A read can repair a stale copy

<InteractiveCanvas slug="sysdesign-m8-read-repair" />

Nodes can disagree. The client reads from three, sees two different versions, and keeps the newest, v2. It then writes v2 back to the node that was behind. A read does two jobs: it answers, and it repairs. Copies that nobody reads stay stale until a background process compares them.

<GoDeeper title="Go deeper: read repair, anti-entropy and versions">

Dynamo-style stores heal in two ways. Read repair happens on the read path, as in the picture, and fixes the nodes a client happened to contact. Anti-entropy is a background job: nodes compare their data, using Merkle trees, hash trees that let two nodes find the keys that differ without sending all the data, and copy what is missing [S45].

To keep "the newest" the client needs a way to tell newer from concurrent. A plain counter such as v1 and v2 works if one writer updates the key. With several writers, Dynamo attached a vector clock to each value. If neither version includes the other, they are concurrent and the store returns both [S45]. The paper reports that over 24 hours, 99.94% of requests saw exactly one version of the data [S45]. Concurrent versions are rare, and still they must be handled.

A leaderless system gives up a single order of writes to gain availability. It suits data where a stale read for a moment is fine, or where versions can be merged, such as shopping carts. It is a poor fit for a bank balance or a unique name.

</GoDeeper>

## When a node is down

<MermaidDiagram title="A stand-in holds the write" chart={`flowchart LR
  C["Client: write x = 7"] --> N1["Node 1: stores x"]
  C --> N2["Node 2: stores x"]
  C -.->|"node 3 is down"| N3["Node 3: unreachable"]
  C --> N6["Node 6, a stand-in: stores x with a note: for node 3"]
  N6 -.->|"node 3 is back: hand it over"| N3
`} legend="The stand-in keeps the write with a hint about its real owner, and hands it back when the owner returns." />

Node 3 is down. The client sends the write to a stand-in node instead, with a note: this belongs to node 3. Writes keep succeeding. When node 3 returns, the stand-in hands the write back. The price is that the group holding the data is not the usual one for a while, so a read may miss it.

<GoDeeper title="Go deeper: sloppy quorums and hinted handoff">

Dynamo calls this a sloppy quorum, with hinted handoff. Instead of failing a write when a usual node is unreachable, the store writes to the next healthy node and keeps a hint about where the data belongs. The hint is delivered when the owner is back [S45]. It keeps writes available through short failures, which is the point of the design.

But it breaks the overlap rule. The overlap argument assumed that the W nodes written and the R nodes read both come from the same N nodes. A stand-in is outside that set, so a read of the usual nodes can miss the write until the hint is delivered [S52]. A strict quorum refuses the write instead. Sloppy gives more availability and weaker guarantees. Choosing between them is the same trade-off you have seen all chapter: a write that always succeeds, or a read that always sees it.

Permanent failures need another repair, since a hint cannot be delivered to a node that never returns. That is the job of the anti-entropy process from the last picture [S45].

</GoDeeper>

## Three ways to copy, side by side

<MermaidDiagram title="Single-leader, multi-leader, leaderless" chart={`flowchart TD
  S["Single-leader: one node takes writes and orders them"] --> S2["Node dies: failover, lost writes, split brain"]
  M["Multi-leader: one leader per region"] --> M2["Same record in two regions: a conflict to settle"]
  L["Leaderless: any node takes a write, quorums decide"] --> L2["No failover, but stale reads and versions to merge"]
`} legend="Each design moves the difficulty somewhere else. None removes it." />

One leader orders every write, so there are no conflicts, and failover is the pain (chapters 8.2 to 8.5). Several leaders accept writes close to users, and conflicts are the pain (8.6). With no leader, any node accepts a write and quorums decide what counts, and stale reads and merging are the pain (here). Module 13 builds the third one in full.

<GoDeeper title="Go deeper: choosing, and where you meet each one">

| | Single-leader | Multi-leader | Leaderless |
|---|---|---|---|
| Who accepts writes | One node | One per region | Any node |
| What orders writes | The leader's log | Nothing across regions | Nothing, versions instead |
| When a node fails | Failover | Other regions carry on | Nothing to fail over |
| Main cost | Lost writes, split brain | Conflicts | Stale reads, merging |
| Where you see it | PostgreSQL, Aurora, each DynamoDB partition [S38, S39, S44] | DynamoDB global tables [S43] | The Dynamo design [S45] |

For most apps the first one is the right start. It is the easiest to reason about, because the log gives one order. Reach for the others when a measured need appears: users in several regions that cannot wait for one leader, or writes that must keep succeeding through failures.

**In AWS.** Amazon RDS and Aurora offer read replicas, and Aurora's replicas share one storage volume, up to 15 of them [S39]. DynamoDB global tables are the multi-leader option, with last writer wins by default and a strong mode that needs three Regions [S43].

Next, in 8.8 you write the router for the single-leader case, and in challenge 7 you run it against a real PostgreSQL pair.

</GoDeeper>

explanations:
