In chapter 8.4 the router was one comparison and one fallback: if the replica has applied the user's last write, read from it, otherwise ask the leader. That is enough for a picture. It is not enough for a real app, and the gaps are easy to see once you picture a bad afternoon. Every replica falls behind at once, and every recent writer is sent to the leader, which is already the busiest machine. A replica comes back from a backup and reports a position that is older than the one it reported yesterday. A reader sees a comment on one replica and then, on the next refresh, lands on a replica that has not got it yet.

In this chapter you write `createRouter`, a router that handles those three cases. When you finish, you have one JavaScript function that passes server tests, and you understand each rule well enough to explain why it exists. You use the same ideas against a real PostgreSQL replica in challenge 7, where positions are log sequence numbers instead of plain integers.

## The contract

Positions here are plain non-negative numbers that only grow, such as 1, 2, 3, as in chapter 8.4. A <GlossaryTerm term="session" definition="One user's run of requests, such as one browser or one phone. The router keeps one small object for it, with a token inside." /> is a plain object with one field: `{ token: 0 }`. The token is the highest position this user has seen so far, either from their own writes or from what they read.

`createRouter({ replicas, maxLeaderShare = 0.5, window = 10 })` takes the replica names, for example `["r1", "r2"]`, and returns an object with three methods.

**`report(name, position)`** tells the router how far a node has applied. `name` is a replica name or `"leader"`. The router never asks; the nodes report, as real replicas do every few milliseconds. A replica that has never reported is unknown and is never used. An unknown name throws an `Error`. A position that is negative, not a number or not finite throws a `RangeError`.

**`wrote(session, position)`** records a write. The leader returned `position` when it confirmed the write. The session's token becomes the larger of its old value and `position`, so a token never goes down. The router also learns that the leader is at least at `position`.

**`route(session)`** chooses where one read goes and returns `{ node }`. It follows four rules, in this order.

1. An **eligible** replica has reported, is not quarantined (rule 4), and has a position at or above `session.token`. Equal counts: a replica at exactly the token has the user's write. If any replica is eligible, use the one that has served the fewest reads so far, and break ties by the order of the `replicas` list. Then raise the token to that replica's position, so a later read cannot land on an older replica.
2. If no replica is eligible, the **leader** serves the read, but only if the leader is under its cap. The leader has every write, so after a leader read the token rises to the leader's reported position (0 if it never reported).
3. The **cap**: look at the last `window` routing decisions, including decisions that ended in a wait. The leader may have served at most `Math.floor(maxLeaderShare * window)` of them. If it is at the limit, return `{ node: "wait", retryAfterMs: 50 }` and do not touch the token. The app shows a spinner and asks again.
4. A replica whose reported position is **lower than the highest it ever reported** is quarantined. It was probably restored from an old backup. It stays out of rotation until it reports a position at or above its old highest. Its old reads were fine; the point is that its new, smaller position tells you nothing about what it holds.

## A worked example: Noor's notes app

Noor uses a notes app (a fictional one) with a leader and two replicas, `r1` and `r2`. The router was created with `maxLeaderShare: 0.2` and `window: 10`, so the leader may serve 2 of the last 10 decisions. Here is a short run, with every step shown.

Noor saves a note, and the leader answers `position 40`. The app calls `wrote(session, 40)`, so her token is 40. The replicas report `r1: 38` and `r2: 41`. Noor refreshes. `r1` is below her token, so it is not eligible. `r2` is at 41, so it is eligible and the router returns `r2`. The token rises to 41. That is the happy path.

Now a lag spike: both replicas report 41, but the leader has moved on and Noor saves another note at `position 52`. Her token is 52. Neither replica is eligible. The leader is under its cap, so the router returns `leader`, and the token stays at 52 (the leader reported 52). Her first refresh goes to the leader, 1 of the 2 allowed. Her second refresh also goes to the leader, 2 of 2. Her third refresh gets `wait`, because the cap is reached. Then `r1` reports 53. The next call finds an eligible replica, and Noor's read goes there. The cap held the leader steady, and the replica took over the moment it was safe.

Last, the backwards case. `r2` had reported 60 earlier in the day, and now reports 12. That is lower than its highest ever, so `r2` is quarantined. If the router believed 12, it would think `r2` is a fine replica for a user with token 5, and it would be wrong in a different way: `r2` may hold a mix of old and new data after a restore. It comes back only when it reports 60 or more.

## Three ways this goes wrong

**Raising the token only on writes.** This protects the writer and no one else. A reader who sees a note on `r1` and then lands on `r2`, which is behind, sees the note vanish. Raising the token after each read is one line, and it is what gives you monotonic reads.

**No cap on the leader.** During a lag spike every user with a recent write moves to the leader at once. The leader may be the reason the replicas are behind, so you add load to the machine that is already struggling. The cap does not remove the problem. It trades a few slower reads for a leader that survives. Your tests check the exact count.

**Trusting a position that went backwards.** A replica restored from a backup, or one that was reset, can report a smaller number than before. A router that only compares `position >= token` will use it. Quarantine by comparing each report with the highest value seen from that node.

One more choice is worth a sentence. The cap looks at the last `window` decisions, not at a rate per second. A window of decisions needs no clock, so the router is easy to test and behaves the same on a slow laptop and in production. A real system would also add a timer, so that old decisions expire when traffic is quiet. The decision window is the simplest honest version: it answers "how much of the recent work did the leader take?" without asking what time it is. It also means a quiet minute does not wash away the memory of a busy one, which is the right instinct when the replicas are still behind.

  - "Keep one small record per replica: { position, highest, reads }. A replica is quarantined when position < highest, and report sets highest to the larger value only when position is not lower."
  - "route: filter the replicas that have reported and are not quarantined and have position >= session.token. Sort by reads, then by index in the list; take the first. Raise the token with Math.max."

  - "The leader budget is Math.floor(maxLeaderShare * window). The leader may serve while the number of leader entries in the list is below the budget."
solution: |
  function createRouter({ replicas, maxLeaderShare = 0.5, window = 10 }) {
    const nodes = new Map(replicas.map((name) => [name, { position: null, highest: 0, reads: 0 }]));
    let leaderPosition = 0;
    const recent = [];
    const budget = Math.floor(maxLeaderShare * window + 1e-9);

    function checkPosition(position) {
      if (typeof position !== "number" || !Number.isFinite(position) || position < 0) {
        throw new RangeError("position must be a finite number of 0 or more, got " + position);
      }
    }

    function report(name, position) {
      checkPosition(position);
      if (name === "leader") {
        leaderPosition = Math.max(leaderPosition, position);
        return;
      }
      const node = nodes.get(name);
      if (!node) throw new Error("unknown node " + name);
      node.position = position;
      if (position >= node.highest) node.highest = position;
    }

    function wrote(session, position) {
      checkPosition(position);
      session.token = Math.max(session.token, position);
      leaderPosition = Math.max(leaderPosition, position);
    }

    function decide(kind) {
      recent.push(kind);
      while (recent.length > window) recent.shift();
    }

    function route(session) {
      const eligible = [];
      replicas.forEach((name, index) => {
        const node = nodes.get(name);
        if (node.position === null) return;
        if (node.position < node.highest) return; // quarantined
        if (node.position < session.token) return;
        eligible.push({ name, node, index });
      });
      if (eligible.length > 0) {
        eligible.sort((a, b) => a.node.reads - b.node.reads || a.index - b.index);
        const chosen = eligible[0];
        chosen.node.reads += 1;
        session.token = Math.max(session.token, chosen.node.position);
        decide("replica");
        return { node: chosen.name };
      }
      const leaderReads = recent.filter((kind) => kind === "leader").length;
      if (leaderReads < budget) {
        session.token = Math.max(session.token, leaderPosition);
        decide("leader");
        return { node: "leader" };
      }
      decide("wait");
      return { node: "wait", retryAfterMs: 50 };
    }

    return { report, wrote, route };
  }

## What this unlocks

In challenge 7 the same ideas run against a real PostgreSQL primary and replica. Positions become log sequence numbers such as `0/3000148`, which you compare as 64-bit numbers. The replica's position comes from `pg_last_wal_replay_lsn()` and the token from `pg_current_wal_lsn()`. You will see the cap and the wait as real milliseconds.

Chapter 11.5 generalises the token into the four session guarantees, and module 13 shows how leaderless stores give the same promises with version numbers instead of one log. The habit to keep: a router is a small state machine. Write down what it remembers, what each rule does with that memory, and what it does with a report that looks wrong.
