So far one node ordered every write. Suppose the forum has users in Europe and Singapore. With one leader, a Singapore user's write crosses the world: a round trip of about 160 ms between EU West and Singapore [S3]. A leader in each region removes that wait. This chapter shows what it breaks.

## Each region writes at home

<InteractiveCanvas slug="sysdesign-m8-two-leaders" />

A user in the EU writes to the EU leader, and a user in Singapore writes to the Singapore leader. Both writes finish in a couple of milliseconds, with no trip across the world. Then each leader sends its write to the other. Every region writes at home, and the leaders catch up in the background.

<GoDeeper title="Go deeper: what multi-leader buys and what it adds">

<GlossaryTerm term="multi-leader replication" definition="Several nodes, usually one per region, each accept writes and copy them to each other. Also called multi-primary or active-active." /> has two real benefits. Writes are fast for everyone, because each user writes to a nearby leader. And a region keeps accepting writes when the link to the others is cut, so a network problem between continents does not stop the whole service.

Amazon DynamoDB global tables work this way in their default mode. A write to a replica in one Region is copied to all the other replicas, and any Region accepts writes. Changes are copied asynchronously, typically within a second or less [S43].

The cost is that two leaders can accept writes to the same record at the same time, and neither knows about the other's write when it accepts its own. In a single-leader system that cannot happen, because the one leader sees the writes one after another. The next picture lets you cause it.

There are other costs. A rule such as "usernames must be unique" cannot be checked by one leader alone, because the other region may be registering the same name at that moment. Auto-numbered ids can collide. Topologies add questions too: if every leader sends to every other, the traffic grows quickly. If they pass writes along a ring, one broken link or node stops the chain. And a write that depends on an earlier one can arrive before it on a different leader. Plan for all of these before choosing multi-leader.

</GoDeeper>

## Two regions edit one document

<InteractiveCanvas slug="sysdesign-m8-two-regions-edit" />

Drag the Singapore edit along the timeline. Each region accepts its edit at once and sends it to the other, which takes about 80 ms. If the second edit starts before the first one arrives, the picture flags a conflict. Move the edits apart until it clears, and notice how far apart they must be.

<GoDeeper title="Go deeper: the conflict window">

The model is small. The EU edit happens at time 0. A copy travels one way in about 80 ms, half of the 160 ms round trip between EU West and Singapore [S3]. The Singapore edit conflicts with it if it starts before that copy arrives, which means within 80 ms either side. Further apart than that, the second user's leader had already received the first edit, so the second edit builds on it and there is nothing to settle.

Eighty milliseconds sounds small, but a shared document, a stock count or a seat map can be hit by many people in that time. And the window grows if the link is slow or cut. After an hour of partition, everything either side did in that hour conflicts with the other side.

Notice also what the conflict is not. Neither leader made a mistake. Each did exactly what it should. The conflict exists only when the copies meet, so it is found late, after both users have already seen "saved". That makes it different from a conflict in a single-leader database, where the second writer would see the first writer's change, or wait for it.

DynamoDB shows the two answers side by side. In its default mode, concurrent changes to the same item in different Regions are settled afterwards by a rule. In its strong mode, a write that touches an item being changed in another Region fails with a `ReplicatedWriteConflictException` and can be retried [S43]. One accepts the write and settles later; the other refuses it now.

</GoDeeper>

## Last writer wins, and one edit is lost

<InteractiveCanvas slug="sysdesign-m8-lww-loses" />

When the copies cross, each leader must pick one version. A common rule keeps the later timestamp. So Plan v3 wins, and Plan v2 is dropped without any message to its author. Both leaders now agree, so the system looks healthy. But one person's edit simply vanished.

<GoDeeper title="Go deeper: how last writer wins loses data">

<GlossaryTerm term="last writer wins" definition="A conflict rule: keep the write with the latest timestamp and discard the others. It makes every replica end with the same value, but it throws away concurrent writes." /> is DynamoDB's rule in its default global table mode: the modification with the latest internal timestamp wins, per item [S43]. Kleppmann's lecture notes say plainly that it implies data loss when several updates happen at the same time [S52]. In a 2013 test of Cassandra, which used last write wins, Kyle Kingsbury's Jepsen found that about 28% of acknowledged writes were lost in a lock-based test. That is a result for the 2013 versions, not for Cassandra today [S76].

Two things make it worse. First, "later" depends on clocks. Servers' clocks can drift by up to 50 parts per million, about 4 seconds a day, and NTP leaves milliseconds of error [S52]. The write that really came second can carry the smaller timestamp. Chapter 10.6 shows how Spanner avoids this with TrueTime, and what it costs.

Second, the rule works on a whole item. If the EU user changes the title and the Singapore user changes the description of the same document, they do not clash at all. Yet last writer wins on the whole item keeps one change and drops the other. Applying the rule per field helps. It does not make it safe.

The rule is fine when losing a concurrent write is acceptable: a "last seen" time, a cache entry, a temperature reading that will be replaced in a second. It is wrong for anything a person typed and expects to keep.

</GoDeeper>

## Four ways to settle a conflict

<MermaidDiagram title="Settling a conflict" chart={`flowchart TD
  A["Two regions changed the same record"] --> B["1. Avoid it: give each record one home region"]
  A --> C["2. Last writer wins: keep the later timestamp"]
  A --> D["3. Merge: a rule that gives one result in any order"]
  A --> E["4. Keep both and ask a person or the app"]
  B --> B2["Cost: far users pay the round trip"]
  C --> C2["Cost: one edit is lost"]
  D --> D2["Cost: needs a merge rule per data type"]
  E --> E2["Cost: someone has to decide"]
`} legend="Each answer pays a different price. None is free." />

There are four honest answers. Avoid the conflict by giving each record one home region. Keep the later write and drop the other. Merge the two edits with a rule that gives one result in any order. Or keep both and ask a person. Each one costs something: the first costs speed far from home, the second costs data.

<GoDeeper title="Go deeper: the four answers in more detail">

**Avoid.** Route all writes for one record to the same region, for example the home region of its owner. Then two leaders never write the same record, and multi-leader behaves like single-leader per record. The price is that a user far from the home region pays the long round trip, and if the home region fails, you need failover (chapter 8.5).

**Last writer wins.** Simple, always converges, loses data. See the last picture.

**Merge.** Use a data type that can combine concurrent changes. A CRDT, a conflict-free replicated data type, is built so that replicas reach the same result whatever order the changes arrive in. Examples from the research literature are the grow-only counter, the counter that can go up and down, and the observed-remove set [S74, S75]. Module 13 builds them.

**Keep both.** Store the two versions as siblings and let the application or the user merge them on the next read. Amazon's original Dynamo did this for shopping carts: merging two carts never loses an added item, but a deleted item can come back [S45]. That is a useful reminder that even a careful merge has a price.

How to choose: if a lost edit is unacceptable, avoid or merge. If speed matters more than any single edit, last writer wins can be right. Never choose it only because it is the default.

</GoDeeper>

## Where multi-leader fits

<MermaidDiagram title="Three places multi-leader earns its cost" chart={`flowchart LR
  R["Users in several regions"] --> M["Multi-leader"]
  O["Apps that must work offline"] --> M
  S["Shared documents edited together"] --> M
  M --> P["The price: conflicts to settle"]
`} legend="In each case something must accept a write without asking the others first." />

Multi-leader earns its complexity in three places: users in several regions, apps that must work offline, and shared documents edited by many people at once. For most apps one leader is simpler, and the 160 ms is paid only by the users far away. Choose it when waiting for the far leader is the bigger problem.

<GoDeeper title="Go deeper: each fit, and how to decide">

**Several regions.** Writes are local and fast, and a region survives a cut link. You need a conflict rule and a way to keep rules such as unique names. In AWS, DynamoDB global tables are this design [S43].

**Offline apps.** A phone with no signal accepts a note and syncs when it is back. In effect every device is a leader with its own local database, and the sync is the replication. The conflict window can be hours, so a conflict rule is a must, not an option.

**Shared documents.** When several people type into one document, no one can wait for a round trip per keystroke. Each editor applies its own change at once and merges the others later, which is why such editors use merge rules like the ones in module 13.

To decide, ask three questions. Do users really need to write locally, or is a fast read enough? Would a home region per record remove most conflicts? Can the business accept losing one edit, or must it merge? If the answers are "reads are enough", "yes" and "no", you do not need multi-leader.

Next, chapter 8.7 removes the leader altogether.

</GoDeeper>
