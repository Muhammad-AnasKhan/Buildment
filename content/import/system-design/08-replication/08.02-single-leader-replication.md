Back to the study forum from chapter 8.1. This chapter follows one write from the leader to its followers, then one read to a follower, and ends with a count of what the followers really buy. Keep one question in mind: what does each extra copy give us, and what does it cost?

## A write is saved once, then copied

<InteractiveCanvas slug="sysdesign-m8-write-path" />

Amna's post goes to the leader. The leader saves it as entry 7 and tells her OK. Only then do the copies travel, and they arrive at different times. Every write has one door, the leader, so the leader alone decides the order of changes.

<GoDeeper title="Go deeper: why one door for writes">

This design has many names: single-leader, primary and replica, leader and follower. The older name "master and slave" is still found in old tools. The rule is the same in all of them. One node, the <GlossaryTerm term="leader" definition="The one node that accepts writes. It decides the order of changes and sends each change to the followers." />, accepts every write. The other nodes, the <GlossaryTerm term="followers" definition="Nodes that copy the leader's changes. They answer reads, and one of them can be promoted to leader if the leader fails." />, only copy.

You see it in real systems. PostgreSQL has a primary that accepts writes. Its standby servers can answer read-only queries, which is called a hot standby, and they refuse writes [S38]. Amazon Aurora has one writer and up to 15 replicas that read the same shared storage [S39]. Inside DynamoDB, each partition has three replicas, and only the leader of that group serves writes and strongly consistent reads [S44].

The reason for one door is simple: two writers can disagree. If two nodes could both accept a change to the same row, someone would have to decide which one wins. With one leader there is no such decision, because the leader sees every write one after another. Chapter 8.6 shows what you pay when you remove this rule.

A write that reaches a follower by mistake is refused with an error that names the leader. It is not saved and sent on later. That would let the follower invent an order the leader never saw.

In the picture the leader says OK before the copies arrive. That is called asynchronous replication, and it is the default in PostgreSQL streaming replication [S38]. The next chapter asks what happens if the leader waits first.

</GoDeeper>

## Followers copy the log in order

<InteractiveCanvas slug="sysdesign-m8-log-order" />

The leader keeps a log: a list of every change, numbered 1, 2, 3. A follower receives the entries and applies them in the same order, because a later change may depend on an earlier one. So a follower is never a mix of old and new. It is the leader as it was a moment ago, and the gap to the leader is its lag.

<GoDeeper title="Go deeper: what is in the log, and how a new follower starts">

The log can hold different things. It can hold the SQL statements, the changed rows, or the low-level disk changes. PostgreSQL's streaming replication ships the write-ahead log, a record of every change to the database files that the leader writes before it changes the files themselves [S38]. A follower that applies the same records in the same order ends up with the same data.

Each entry has a position, a number that only grows. In PostgreSQL it is called a log sequence number (LSN), and it looks like `0/3000148`. A follower that has applied position N has every change up to N. Chapter 8.4 uses positions to route reads, and challenge 7 reads them from a real database.

A new follower cannot start from the log alone, because the log may be days long. It first copies a snapshot of the leader's data, then asks for the log from the position where that snapshot was taken, and catches up. This is why adding a follower to a big database takes hours, not seconds, and why the leader slows a little while it copies.

If the follower's network drops for a while, it simply asks for the missing entries when it returns. It does not lose its place. But the leader must keep those entries until every follower has taken them. A follower that stays away for too long forces the leader to keep a growing pile of log, so real systems set a limit and rebuild the follower when it is exceeded.

</GoDeeper>

## Reads can go to any copy

<InteractiveCanvas slug="sysdesign-m8-read-spread" />

Reads do not change data, so any copy can answer them. Two followers take the reads, and the leader keeps its time for writes. The catch is that a follower answers from what it has now, which may be a moment old. Chapter 8.4 is about that catch.

<GoDeeper title="Go deeper: which reads may go to a follower">

Most web apps read far more than they write. Showing a page is a read. Posting is a write. So read traffic is the first thing to move off the leader, and replicas are the usual first step on the scaling path you will see in module 7.

Not every read can tolerate old data. A question page, a list of courses or a profile picture can be a second old with nobody noticing. A page that shows the result of the user's own action cannot: it must show their new comment, their new name, their payment. Teams split reads into two kinds. Reads that may be a moment old go to any follower. Reads that must be fresh go to the leader, or to a follower that is known to be caught up.

Some tools make this choice for you, and some hide it. Aurora gives a reader endpoint that spreads new connections across replicas [S39], so two page loads on different connections can land on different copies. A plain connection pool sticks to one. If your app does not choose, the tool chooses, and neither choice protects the user's own writes.

</GoDeeper>

## Send writes, read anywhere, kill the leader

<InteractiveCanvas slug="sysdesign-m8-leader-followers" />

Tap Write to send a change to the leader, and watch the copies follow. Tap any node to read from it and see what it answers. Then tap Kill leader. Reads still work on the followers. Writes stop: nobody may accept them until a follower becomes the new leader (chapter 8.5).

<GoDeeper title="Go deeper: what you just saw, and what the picture leaves out">

Three things should have stood out. First, a read can return an older answer than the leader: tap Read on a follower right after a write and you may see the old value. Second, the followers keep answering reads after the leader dies, so the app still shows pages. Third, writes are unavailable. Replication gave the app a second life for reads, but it did not make writes survive a leader failure by itself.

To get writes back, someone must notice the leader is gone, choose a follower, make it the leader and tell every client where it is. That whole procedure is failover. The picture does not do it for you, on purpose, because it is the subject of chapter 8.5 and it is harder than it looks.

The picture also uses one write at a time and tiny delays. A real leader handles thousands of writes a second, and the copies stream continuously. What stays true at any size is the order: a follower applies the leader's entries in the leader's order.

</GoDeeper>

## Followers add reads, not writes

<MermaidDiagram title="Where the work goes, with two followers" chart={`flowchart LR
  A["App: 800 reads/s and 200 writes/s"] -->|"200 writes/s"| L["Leader: 200 writes/s, busy 20%"]
  L -->|"the same 200 writes/s"| F1["Follower 1: 200 writes + 400 reads, busy 60%"]
  L -->|"the same 200 writes/s"| F2["Follower 2: 200 writes + 400 reads, busy 60%"]
  A -->|"400 reads/s"| F1
  A -->|"400 reads/s"| F2
`} legend="Each machine can do 1,000 operations a second (a made-up number). Every write is applied on every machine. Reads are shared by the followers." />

Say each machine can do 1,000 operations a second (a made-up number). Every write must be applied on every machine, so each follower spends the same 200 a second as the leader. What is left, 800 a second, answers reads. More followers give more room for reads. They give no room for writes.

<GoDeeper title="Go deeper: the capacity formula and when replicas stop helping">

A simple model: every node can do C operations a second. Each write costs one unit on every node, because every node applies it. If the write rate is W, each node has C - W left for reads. With n nodes that answer reads, the cluster can serve n x (C - W) reads a second.

| Writes per second (W) | Reads per second with 3 nodes | With 1 node |
|---|---|---|
| 100 | 3 x 900 = 2,700 | 900 |
| 500 | 3 x 500 = 1,500 | 500 |
| 900 | 3 x 100 = 300 | 100 |

Look at the last row. At 900 writes a second, three nodes serve only 300 reads, and a fourth node adds 100. Replicas help a lot when the app is read-heavy and almost not at all when it is write-heavy. The maximum write rate of the whole group is still C, the limit of one machine, because the leader must take them all.

The model is a simplification. A write is usually more expensive than a read, and a follower may apply it more cheaply than the leader executed it. But the shape holds, and it gives a rule for interviews: replicas scale reads; to scale writes you must split the data across leaders, which is partitioning, the subject of module 9.

Replication also gives safety. A copy on another machine survives the loss of the first one, which is why teams add a replica even when reads are not a problem. A copy on the same disk array or in the same rack does not protect you from a failure of that rack, so place followers in different failure zones.

</GoDeeper>
