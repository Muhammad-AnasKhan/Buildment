Ticketline's database works on launch day. Then traffic grows, and one part after another hits its limit. Each limit has a first fix. The order matters: early fixes are cheap and easy to undo, and late fixes change your data model.

## The path, in order

<MermaidDiagram title="The database scaling path" chart={`flowchart LR
  A["1. Fix queries, add indexes"] --> B["2. Add a cache"]
  B --> C["3. Add read replicas"]
  C --> D["4. Partition the data"]
  D --> E["5. Add special stores"]
  A -.- a["Signal: one slow query, high CPU"]
  B -.- b["Signal: the same reads repeat"]
  C -.- c["Signal: reads outgrow one machine"]
  D -.- d["Signal: writes or data outgrow one machine"]
  E -.- e["Signal: a query shape the main store handles badly"]
`} legend="Each step has a signal that tells you it is time. Step 4 is the first that adds write capacity. Reaching for a later step before an earlier one is the most common mistake." />

Order the fixes by cost and by how hard they are to undo. Fix queries first. Cache repeated reads second. Add read replicas when reads outgrow one machine. Partition when writes or data outgrow one machine. Add a special store last. A bigger machine can buy time at any point.

<GoDeeper title="Go deeper: why this order">

Each step costs more than the one before it. An index takes a minute to create and can be dropped again. A cache is a new system to run, and it adds the stale-data problems of module 5. A read replica is another copy that runs behind the primary, which causes the anomalies of module 8. Partitioning changes how you query: joins and transactions that cross partitions get hard, and moving data between partitions is real work (module 9). A special store is one more system to keep in step with the main database.

The order also follows the signal. A database at high CPU because of one scan does not need a second server. It needs an index. Adding replicas to a database whose real problem is writes leaves the problem where it was, as the playable beat will show.

A bigger machine is the step that does not fit the list. Chapter 4.2 compared scaling up with scaling out. Scaling up is simple and has no data-model cost, but it has a ceiling and it keeps a single point of failure. Teams often scale up first, and take the later steps when the ceiling comes into view.

The list is also a warning against starting at the end. Teams that partition on day one pay for it in every query they write, long before they have the traffic to need it.

</GoDeeper>

## Step 1: an index fixes a slow query

<InteractiveCanvas slug="sysdesign-m7-path-index" />

The orders page takes 3.2 seconds and the database CPU sits at 92%. One query scans a big table. After one CREATE INDEX the page takes 40 ms and the CPU drops to 28%. No new server, no new system. All numbers here are made up for the story.

<GoDeeper title="Go deeper: find the slow query before you fix it">

Do not guess. Ask the database which query is slow and what it does. `EXPLAIN (ANALYZE, BUFFERS)` runs the query and prints the plan, the time, and the pages touched. You can read it from Node.js:

```js
async function showPlan(sql, params) {
  const plan = await pool.query(`EXPLAIN (ANALYZE, BUFFERS, COSTS OFF) ${sql}`, params);
  console.log(plan.rows.map((row) => row["QUERY PLAN"]).filter((line) => /Scan|Execution Time/.test(line)).join("\n"));
}

await showPlan("SELECT * FROM tickets_demo WHERE buyer_id = $1", [91]);
```

On a table of 300,000 made-up rows in PostgreSQL 18.6, it printed this before and after `CREATE INDEX tickets_demo_buyer ON tickets_demo (buyer_id)`:

```text
-- no index
  ->  Parallel Seq Scan on tickets_demo (actual time=0.830..18.375 rows=2.00 loops=2)
Execution Time: 37.816 ms
-- with index
Bitmap Heap Scan on tickets_demo (actual time=0.124..0.131 rows=4.00 loops=1)
  ->  Bitmap Index Scan on tickets_demo_buyer (actual time=0.104..0.104 rows=4.00 loops=1)
Execution Time: 0.261 ms
```

A line with Seq Scan on a big table, in a query that returns a few rows, is the sign. Chapter 7.3 explains why an index helps and what it costs on writes. Other query fixes belong here too: ask for only the columns you need, and do not run one query per row of a list (the "N plus 1" problem). Use cursor pagination instead of large offsets (chapter 6.3).

</GoDeeper>

## Step 2: a cache removes repeated reads

<InteractiveCanvas slug="sysdesign-m7-path-cache" />

The same event page is read thousands of times. With a cache that answers 9 reads in 10, the database sees only 1 read in 10. The 90% hit rate is an assumption. A cache does nothing for writes, and it can show data that is a little old.

<GoDeeper title="Go deeper: hit rate decides the saving">

The load on the database is the read rate times the miss rate. With 2,000 reads a second and a 90% hit rate, the database sees 200 a second. At 99%, it sees 20. So the last few points of hit rate matter a lot. A cache pays off only for data that is read far more often than it changes. Facebook's memcache paper reports that leases, which also limit stampedes, cut peak database queries from 17,000 a second to 1,300 on hot keys [S24].

This small cache-aside function, with a time limit, shows the effect. It reads 10 hot events 1,000 times:

```js
let databaseReads = 0;
const loadFromDatabase = (id) => {
  databaseReads++;
  return { id, name: `Event ${id}` };
};

const cache = new Map();
const TTL_MS = 30_000;

function getEvent(id, now = Date.now()) {
  const hit = cache.get(id);
  if (hit && hit.expiresAt > now) return hit.value; // answered from memory
  const value = loadFromDatabase(id); // miss: ask the database once
  cache.set(id, { value, expiresAt: now + TTL_MS });
  return value;
}

for (let i = 0; i < 1000; i++) getEvent(1 + (i % 10));
console.log(`1000 reads, ${databaseReads} database reads, hit rate ${((1 - databaseReads / 1000) * 100).toFixed(1)}%`);
```

It prints `1000 reads, 10 database reads, hit rate 99.0%`. Module 5 covers what this toy leaves out: invalidation when the data changes, stampedes when a hot key expires, and eviction when memory is full.

</GoDeeper>

## Step 3: replicas take reads, and run behind

<InteractiveCanvas slug="sysdesign-m7-path-replica" />

Writes go to the primary. A copy is sent to the replica, which serves reads. A read that arrives before the copy sees old data. Replicas multiply read capacity, but every replica is a little behind, so some reads must still go to the primary.

<GoDeeper title="Go deeper: routing, lag, and what replicas do not fix">

A read replica is a second database that copies every change from the primary. PostgreSQL's streaming replication is asynchronous by default, and the documentation says lag is typically under one second if the standby can keep up [S38]. Amazon Aurora replicas share one storage volume with the writer, so their lag is usually much less than 100 ms, and an Aurora cluster can have up to 15 replicas [S39]. Lag is never zero, and it grows when the primary is busy.

Routing is a decision in your app. In this sketch, writes and reads that must see the user's own write go to the primary, and other reads go to a replica:

```js
function poolFor({ writes, needsOwnWrite = false }) {
  if (writes || needsOwnWrite) return primary; // only the primary takes writes
  return replica; // a replica may be a little behind
}
```

```text
buy a ticket:        primary
browse events:       replica
my ticket, just now: primary
```

The third line is the read-your-writes problem from chapter 8.4: show a buyer their own ticket from a replica that has not received it yet, and they think the purchase failed. Module 8 gives the full fixes.

Replicas add read capacity only. Every write still goes to the one primary, and the primary also ships its changes to every replica. If writes are the bottleneck, more replicas do not help. That is the lesson of the next beat.

</GoDeeper>

## Step 4: partitions spread the writes

<InteractiveCanvas slug="sysdesign-m7-path-shard" />

Events are split over three databases by event id. A question about event 5 goes to one of them. A question about every event goes to all three. Partitioning is the first step that adds write capacity, because each partition takes a share of the writes. It costs you queries that cross partitions.

<GoDeeper title="Go deeper: choosing the key, and what you give up">

A partition key decides where a row lives. Ticketline's sales each touch one event, so event id is a natural key: a sale goes to one partition, and the check on seats left stays inside one machine. A question such as "top prices across all events" now needs every partition to answer, and the slowest one sets the time (chapter 9.6).

Three costs are worth knowing before you start. Joins and transactions across partitions are hard or impossible, so you design to keep related rows together. Moving data when you add a partition is real work. And one hot key can overload one partition. If a single famous event takes most of the traffic, partitioning by event id leaves that event on one machine. DynamoDB, for example, hashes the partition key to pick a partition. Each partition is designed for up to 3,000 read units and 1,000 write units a second, so a hot key hits that ceiling however many partitions exist [S40].

Module 9 covers hash and range partitioning, consistent hashing, hot keys and rebalancing. For now, know the rule: do not partition until a measurement says a single machine cannot take the writes or hold the data.

</GoDeeper>

## Grow the traffic, add the right step

<InteractiveCanvas slug="sysdesign-m7-scaling-path" />

Drag the traffic up and watch which part is full. When a part turns red, add the step that fixes it. A wrong step, such as read replicas for a write problem, leaves the red part red. Try to reach 12,000 requests a second with the fewest steps.

<GoDeeper title="Go deeper: the arithmetic behind the picture">

The picture uses a simple model with made-up numbers, so you can follow the reasoning on paper. One database machine handles 4,000 units of work a second. A read costs 1 unit when it uses an index and 3 units when it scans. A write costs 5 units. Traffic is 90% reads and 10% writes.

At 3,000 requests a second there are 2,700 reads and 300 writes.
- Start: 2,700 times 3, plus 300 times 5, is 9,600 units. That is 240% of the machine.
- Add an index: 2,700 plus 1,500 is 4,200. That is 105%.
- Add a cache with a 90% hit rate: 270 plus 1,500 is 1,770. That is 44%. Done.

At 12,000 requests a second there are 10,800 reads and 1,200 writes.
- With the index and cache: 1,080 plus 6,000 is 7,080. That is 177%. Writes are 6,000 of it.
- Add read replicas, so no reads reach the primary: 6,000 is 150%. Still over. Replicas helped little because writes are the load.
- Partition into 2: each partition takes 600 writes (3,000 units) and 540 reads, which is 3,540 units, or 89%. Now it fits.

The numbers are illustrative: they show the shape, not a benchmark of any real database. What carries over is the habit: compute the load in the same units for reads and writes, find the part that is over, and pick the step that removes load from that part.

</GoDeeper>

## Special stores come last

<MermaidDiagram title="Ticketline after the full path" chart={`flowchart LR
  App["App servers"] -->|"hot reads"| C["Cache"]
  App -->|"writes and own reads"| P["Primary, partitioned by event"]
  App -->|"browse reads"| R["Read replicas"]
  P -->|"copies"| R
  P -->|"change feed"| S["Search index"]
  P -->|"nightly export"| A["Analytics store"]
  App -->|"search box"| S
`} legend="Every box was added for a measured reason. The search index and analytics store are copies fed from the primary, so they can be rebuilt." />

Add a search index, an analytics store or a graph store only when a measured query shape needs one, and feed it from the main database. Every store is another system to run, secure and keep in step. The best database design is often the one with the fewest boxes that still meets the numbers.

<GoDeeper title="Go deeper: how to know it is time, and what it costs">

A special store is justified by a query the main store cannot do well enough: ranked word search, long chains of links, or heavy reports that slow down the sales path. Chapter 7.2 listed those shapes. The test is the same as for every step: a measurement shows a limit, and the step removes it.

The cost is keeping copies in step. A change feed from the primary is safer than the app writing to both places, because a crash between two writes leaves them different. Chapter 14.4 shows the outbox pattern for this. Plan for the copy to be a little behind, and for a way to rebuild it from the source.

**In AWS.** Aurora adds up to 15 read replicas on shared storage [S39]. DynamoDB partitions by hashing the partition key [S40], and its global secondary indexes are updated asynchronously [S41]. Amazon ElastiCache is the managed cache of module 5.

</GoDeeper>
