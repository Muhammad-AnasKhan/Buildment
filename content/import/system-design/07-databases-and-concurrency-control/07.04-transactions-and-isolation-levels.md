Ticketline refunds money, tops up wallets and sells seats. Each job changes more than one thing, and many jobs run at once. Two ideas keep this correct. A transaction groups changes together. An isolation level says how much two overlapping transactions can see of each other.

## A crash between two steps loses money

<InteractiveCanvas slug="sysdesign-m7-txn-crash" />

A refund takes 40 from the venue's wallet and adds 40 to Dina's. The app crashes after the first step. Nothing adds the 40 to Dina, and nothing puts it back. A transaction wraps both steps, so they both happen or neither does.

<GoDeeper title="Go deeper: begin, commit, roll back, in JavaScript">

A <GlossaryTerm term="transaction" definition="A group of database changes that the database treats as one unit. Either every change is saved (commit) or none is (rollback)." /> starts with `BEGIN` and ends with `COMMIT` or `ROLLBACK`. If the connection drops or the app throws before `COMMIT`, the database throws the changes away. This property is called atomicity: all or nothing.

Here is a small helper in Node.js with the `pg` package, and the refund from the picture. It runs with the refund crashing in the middle, with and without a transaction.

```js
async function withTransaction(pool, work, isolation = "READ COMMITTED") {
  const client = await pool.connect();
  try {
    await client.query(`BEGIN ISOLATION LEVEL ${isolation}`);
    const result = await work(client);
    await client.query("COMMIT");
    return result;
  } catch (error) {
    await client.query("ROLLBACK");
    throw error;
  } finally {
    client.release();
  }
}

async function refund(pool, amount, { crash = false, useTransaction = true } = {}) {
  const steps = async (db) => {
    await db.query("UPDATE wallets SET balance = balance - $1 WHERE name = 'venue'", [amount]);
    if (crash) throw new Error("app crashed between the two steps");
    await db.query("UPDATE wallets SET balance = balance + $1 WHERE name = 'dina'", [amount]);
  };
  if (useTransaction) await withTransaction(pool, steps);
  else await steps(pool); // two separate statements, no transaction
}
```

Starting from venue 500 and dina 0, the three runs print:

```text
no transaction, crash:             venue 460, dina 0
with transaction, crash:           venue 500, dina 0
with transaction, no crash:        venue 460, dina 40
```

Without a transaction, 40 vanished. With one, the crash rolled the first step back. Note the `finally`: a client that is never released leaks a connection, and a pool that runs out of connections stops the whole app.

Atomicity is one of four properties people list as ACID. Consistency means the database refuses changes that break its rules, such as a CHECK constraint. Isolation, the topic of this chapter, says how overlapping transactions affect each other. Durability means a committed change survives a crash.

</GoDeeper>

## Dirty read: a change that never happened

<InteractiveCanvas slug="sysdesign-m7-dirty-read" />

The buyer's app sets the count to 0 but has not committed yet. The counter page reads 0 and shows sold out. Then the payment fails and the change is rolled back. The page showed a sold-out state that never really existed. Reading another transaction's uncommitted change is called a dirty read.

<GoDeeper title="Go deeper: which databases allow it">

The SQL standard defines four isolation levels, from weakest to strongest: Read Uncommitted, Read Committed, Repeatable Read and Serializable. Read Uncommitted is the level that allows dirty reads.

PostgreSQL does not allow them at any level. Its documentation says Read Uncommitted mode behaves like Read Committed. In a test on PostgreSQL 18.6, a transaction at Read Uncommitted read 100 while another transaction held an uncommitted write of 50. Other databases do allow dirty reads at their lowest level, so check the documentation for yours.

At Read Committed, the default in PostgreSQL, each statement sees only data that was committed before the statement began. That alone stops the sold-out page above.

</GoDeeper>

## Lost update: two top-ups, one vanishes

<InteractiveCanvas slug="sysdesign-m7-lost-update" />

Amna adds 50 and Bilal adds 30 to the same wallet. Both read 100. Amna writes 150, then Bilal writes 130. The final balance is 130, not 180. Each read was fine when it ran. The second write replaced the first. This is the lost update from chapter 7.1, with money.

<GoDeeper title="Go deeper: what each level does with this story">

The trouble comes from where the new number is worked out. Each app read 100, added its amount in its own memory, and wrote a total. The database cannot know the total was based on an old read. Here is what PostgreSQL 18.6 did when two such transactions overlapped. The first wrote 150 and committed. The second wrote 130.

| Level | The second write | Final balance |
|---|---|---|
| Read Committed (default) | Succeeds, replaces 150 | 130 (update lost) |
| Repeatable Read | Fails with error 40001: could not serialize access due to concurrent update | 150 (you must retry) |
| Serializable | Fails with the same error | 150 (you must retry) |

So from Repeatable Read upward, PostgreSQL stops the lost update by refusing the late write. This matches Jepsen's description of snapshot isolation: if another transaction committed a write to an item after your snapshot began, you must abort, which prevents lost updates [S46]. The PostgreSQL documentation says that when you get this error you should abort the transaction and retry the whole thing from the beginning.

There is a second fix that works at the default level. Do not compute the total in your app. Write `UPDATE wallets SET balance = balance + 30`. Then the second statement waits for the first to commit, applies its change to the new row, and the balance ends at 180. The PostgreSQL documentation describes this: the second updater waits for the first, then applies its operation to the updated row and re-evaluates the WHERE clause. The same test gave 180. Chapter 7.5 builds on that.

</GoDeeper>

## Write skew: two safe checks, one broken rule

<InteractiveCanvas slug="sysdesign-m7-write-skew" />

The rule is that one gate must stay open. Staff A and staff B both count 2 open gates, and both decide it is safe to close one. They close different gates. Each change was fine alone. Together they break the rule. This anomaly is called write skew.

<GoDeeper title="Go deeper: why a lock or a version check on one row misses it">

In write skew, two transactions read the same facts, then write to different rows. No row is changed twice, so the lost update checks never fire. A version check on one gate row would not notice that the other gate row changed. The danger sits in the gap between what each one read (all gates) and what each one wrote (one gate).

Jepsen calls write skew the most notable anomaly that snapshot isolation allows [S46]. PostgreSQL implements its Repeatable Read level with snapshot isolation, which is why the result below matches. Here is the PostgreSQL 18.6 result when two transactions each counted the open gates, saw 2, and closed a different gate:

| Level | Commit of A | Commit of B | Gates open |
|---|---|---|---|
| Read Committed | ok | ok | 0 |
| Repeatable Read | ok | ok | 0 |
| Serializable | ok | Error 40001: could not serialize access due to read/write dependencies among transactions | 1 |

Only Serializable stopped it, by failing B. The PostgreSQL documentation shows the same effect with its own example: two transactions that each sum one class and insert into the other both commit at Repeatable Read, and one fails at Serializable. Before Serializable, you have other tools. You can lock every row the rule depends on with `SELECT ... FOR UPDATE`. You can keep the rule in one row, such as a counter of open gates, so the two writers touch the same row. Or you can let the database enforce the rule with a constraint when one can express it.

</GoDeeper>

## Interleave two transactions, change the level

<InteractiveCanvas slug="sysdesign-m7-isolation-lab" />

Pick a story and an isolation level, then step the two transactions forward one statement at a time. The picture shows what each one sees, and says which anomaly appears. Try each story at each level, and find the weakest level where the story ends well.

<GoDeeper title="Go deeper: the four levels and PostgreSQL's table">

The SQL standard defines levels by the anomalies they allow. Two more names appear in it. A non-repeatable read happens when you read a row twice in one transaction and get different values, because another transaction committed a change in between. A phantom read happens when you run the same query twice and the second run returns new rows that another transaction inserted.

PostgreSQL's documentation gives this table for PostgreSQL itself:

| Level | Dirty read | Non-repeatable read | Phantom read | Serialization anomaly |
|---|---|---|---|---|
| Read Uncommitted | Not possible | Possible | Possible | Possible |
| Read Committed | Not possible | Possible | Possible | Possible |
| Repeatable Read | Not possible | Not possible | Not possible | Possible |
| Serializable | Not possible | Not possible | Not possible | Not possible |

A serialization anomaly is any result that could not happen if the transactions had run one at a time in some order. Write skew is one. Notice that lost update is not a column here: in PostgreSQL it appears as an error at Repeatable Read and above, as the earlier table showed. Other databases differ in the details, so never assume one database's levels behave like another's.

</GoDeeper>

## What each level stops

<MermaidDiagram title="The isolation ladder in PostgreSQL" chart={`flowchart LR
  RU["Read Uncommitted: behaves like Read Committed"] --> RC["Read Committed (default): no dirty reads"]
  RC --> RR["Repeatable Read: also no lost update, by an error you retry"]
  RR --> SER["Serializable: also no write skew, by an error you retry"]
`} legend="Each step up stops one more anomaly and costs more retries or waiting. Lost update appears as error 40001 from Repeatable Read upward." />

Read it as a ladder. In PostgreSQL, Read Committed stops dirty reads. Repeatable Read also stops lost updates, by raising an error. Serializable also stops write skew. Each step up stops more, but your app must retry the transactions the database refuses.

<GoDeeper title="Go deeper: which level to use, and the retry loop">

The usual choice is to stay at the default, Read Committed, and fix the few places that need more. Use a relative update (`balance = balance + 30`), a row lock, or a version check where a lost update would hurt. Raise the level to Serializable for a transaction where a rule spans several rows, or for a whole app if you would rather have the database find the clashes. The price is retries: the PostgreSQL documentation says an application that uses Serializable should retry a transaction that fails with SQLSTATE 40001, and should have a generalized way of handling serialization failures.

A retry wrapper is small. This one retries on serialization failure (40001) and deadlock (40P01), with a limit, and uses the `withTransaction` helper from the first beat. In the demo, two requests try to close the north and south gates at once under Serializable. A pause between the count and the update makes them overlap.

```js
async function withRetry(pool, work, attempts = 5) {
  for (let attempt = 1; ; attempt++) {
    try {
      return { result: await withTransaction(pool, work, "SERIALIZABLE"), attempts: attempt };
    } catch (error) {
      const retryable = error.code === "40001" || error.code === "40P01"; // serialization failure, deadlock
      if (!retryable || attempt === attempts) throw error;
    }
  }
}
```

The run printed:

```text
north -> {"result":"closed","attempts":1}
south -> {"result":"refused: the last gate must stay open","attempts":2}
gates open: south
```

South failed once with 40001, tried again, counted 1 open gate, and refused. The rule held, and the app got a clear answer. Two things to keep in mind. The whole transaction must be repeatable, so do not send an email inside it. And the number of attempts must be limited, or a busy row can keep a request retrying for a long time.

</GoDeeper>
