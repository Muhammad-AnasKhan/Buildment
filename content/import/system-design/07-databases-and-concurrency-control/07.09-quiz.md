```quiz
type: mcq
question: "A campus library app (a made-up example) must show a student's loans with book titles and due dates. A return must update the loan and the book's availability together. Which store family fits this core data best?"
options:
  - "Key-value, with one record per student id"
  - "Time-series, with one row per loan event"
  - "Relational, with a transaction on return"
  - "Graph, with one node for each book title"
correct: 2
explanations:
  - "Keyed by student, loans are easy to fetch. But the titles live elsewhere and a return changes two records, with no all-or-nothing step across them."
  - "Loans are not a stream of events that you read by time range. The return also needs two records to change together."
  - "Right. Loans, students and books are linked tables, so a join gives the page in one query, and a transaction makes the loan and the availability change together."
  - "A graph store is built to follow chains of links. Nothing here needs that, and it gives no easier way to change two records together."
```

```quiz
type: mcq
question: "A table of 50 million rows has a B-tree index on email. WHERE email = 'x@example.com' is fast. WHERE email LIKE '%@gmail.com' is slow. What is the most likely reason?"
options:
  - "The pattern starts with a wildcard, so the index is not used"
  - "The index pages are full, so every lookup has to split a page"
  - "A LIKE query skips every index, whatever pattern it uses"
  - "A B-tree can only index columns that hold numbers"
correct: 0
explanations:
  - "Right. A B-tree is sorted from the start of the value. With a fixed start, such as 'x%', it can jump to the right place. With a wildcard first, there is no place to jump to, so the database scans."
  - "Splits happen when you insert into a full page, not when you read. A read never splits a page."
  - "A pattern with fixed text at the start, such as 'x@%', can use a B-tree. It is the leading wildcard that stops it."
  - "A B-tree works on any data that can be sorted, including text. Email is indexed in the first query."
```

```quiz
type: mcq
question: "At PostgreSQL's default isolation level, two requests overlap on the same wallet row. Which code path can lose one of the two updates?"
options:
  - "One UPDATE that sets balance = balance + 30 in the database"
  - "One UPDATE guarded by WHERE balance >= 30 in the database"
  - "SELECT FOR UPDATE, then an UPDATE, in one transaction"
  - "SELECT the balance, add 30 in the app, UPDATE to the total"
correct: 3
explanations:
  - "The database adds to the latest committed balance. The second request waits for the first, then adds its own amount, so nothing is lost."
  - "The check and the change are in one statement. The second request waits, re-checks the guard on the new balance, and applies its change."
  - "The lock makes the second request wait before it reads, so it reads the first request's committed result."
  - "Right. Both requests can read the same balance. Each computes a total in the app and writes it, so the second write erases the first."
```

```quiz
type: mcq
question: "Ticketline's seat check needs a 150 ms call to a fraud service between the read and the write. 40 buyers compete for one hot event. The team compares a row lock held during the call with a version check and retries. Which statement is true?"
options:
  - "The lock repeats the fraud call for every collision"
  - "The lock caps the event at about 7 sales a second"
  - "The version check caps the event at about 7 sales a second"
  - "Both give the same sales per second, whatever the load"
correct: 1
explanations:
  - "Waiting does not repeat any work. It is the version check that repeats the call, once for each refused write."
  - "Right. The lock is held for the whole 150 ms, so sales go one after another. One divided by 0.15 seconds is about 7 a second, however many servers there are."
  - "With a version check, the fraud calls of different buyers run at the same time. Only the short write is exclusive, so the cap is not 7 a second. The cost is repeated calls."
  - "They behave differently under load. One queues and the other retries, and their throughput and wasted work do not match."
```

```quiz
type: mcq
question: "A Ticketline database sits at 95% CPU. EXPLAIN shows its slowest query already uses an index. About 85% of reads ask for the same 300 event pages, and writes are 5% of the load. What should the team add next?"
options:
  - "Partition the data by event id"
  - "A search index for the event titles"
  - "A cache in front of the event pages"
  - "A second primary to take half the writes"
correct: 2
explanations:
  - "Partitioning is for writes or data that outgrow one machine. Here writes are only 5%, and the load is repeated reads."
  - "A search index serves word queries. These reads are repeated fetches of known pages, not searches."
  - "Right. The same 300 pages are read again and again, so a cache answers most of them from memory and takes that load off the database. The query is already indexed, so the next cheap step is the cache."
  - "Writes are 5% of the load. A second primary adds a hard consistency problem for a small share of the work."
```
