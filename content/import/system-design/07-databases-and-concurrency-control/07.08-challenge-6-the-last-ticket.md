## How the experiment works

A burst of buyers hits one row of a table in a real PostgreSQL database. Each part changes only the way a buyer sells a seat. Everything else stays the same, so the differences you see come from the fix and nothing else.

Four design choices make the numbers honest.

**One hot row, on purpose.** All buyers fight over a single `events` row, like the last ticket in chapter 7.1. Real systems spread load over many rows, but a launch day for one popular show looks exactly like this.

**A pause between the read and the write.** Each strategy calls `think(thinkMs)` between reading the seat count and writing it. It stands for the work a real app does there: a payment check, a fraud rule, a call to another service. Without a pause, the gap is a fraction of a millisecond and the bug hides. With a pause of 5 ms, it shows up every time. One warning for Windows: a timer for 5 ms can take about 15 ms, so your pauses may be longer than the number you typed.

**Two kinds of run.** A burst sends 60 buyers who each try once, at random moments in one second. It shows whether a strategy is correct. A loop sends a fixed number of buyers who keep buying until the event is sold out. It shows how fast the strategy is.

**Two numbers for the damage.** `oversold` is tickets sold beyond the seats that exist. `lostUpdates` is sales that the counter never subtracted, which is the update that was lost. A correct strategy scores 0 on both.

```js
  return new pg.Pool({ ...config, max });
}

// Postgres needs a few seconds to start. Try SELECT 1 until it answers.
export async function waitForDb(pool, seconds = 30) {
  const until = Date.now() + seconds * 1000;
  while (true) {
    try {
      await pool.query("SELECT 1");
      return;
    } catch (error) {
      if (Date.now() > until) {
        throw new Error(`Postgres did not answer on port ${config.port}. Did you run: docker compose up -d? (${error.message})`);
      }
      await new Promise((resolve) => setTimeout(resolve, 500));
    }
  }
}
```

```js
export function barChart({ title, yLabel, bars, color = "#2563eb" }) {
```

Now the shared runner, `challenges/challenge-6-last-ticket/run.js`. `resetEvent` creates the two tables and puts one event in them. `report` reads the database after a run to count the damage. `runBurst` and `runBuyers` are the two kinds of run:

```js
// Shared runner: reset one event, send buyers at it, and report what happened.
import { percentile } from "../../toolkit/stats.js";

export async function resetEvent(pool, seats) {
  await pool.query("CREATE TABLE IF NOT EXISTS events (id int PRIMARY KEY, seats_left int NOT NULL, version int NOT NULL DEFAULT 0)");
  await pool.query("CREATE TABLE IF NOT EXISTS sales (id bigserial PRIMARY KEY, event_id int NOT NULL, buyer text NOT NULL)");
  await pool.query("TRUNCATE sales");
  await pool.query(
    "INSERT INTO events (id, seats_left, version) VALUES (1, $1, 0) ON CONFLICT (id) DO UPDATE SET seats_left = $1, version = 0",
    [seats]
  );
}

// What the database holds after a run, and how far it is from the truth.
async function report(pool, seats, extra) {
  const { rows: [{ count }] } = await pool.query("SELECT count(*)::int AS count FROM sales");
  const { rows: [{ seats_left: seatsLeft }] } = await pool.query("SELECT seats_left FROM events WHERE id = 1");
  return {
    seats,
    sold: count,
    seatsLeft,
    // More tickets sold than seats: the real damage.
    oversold: Math.max(0, count - seats),
    // Sales that the counter never subtracted: the update that was lost.
    lostUpdates: count - (seats - seatsLeft),
    ...extra,
  };
}

// A sale opens: `buyers` people each try exactly once, at random moments in `spreadMs`.
export async function runBurst({ pool, strategy, seats, buyers, spreadMs = 1000, thinkMs = 5 }) {
  await resetEvent(pool, seats);
  const start = performance.now();
  const results = await Promise.all(
    Array.from({ length: buyers }, async (_, n) => {
      await new Promise((resolve) => setTimeout(resolve, Math.random() * spreadMs));
      return strategy(pool, { eventId: 1, buyer: `b${n}`, thinkMs });
    })
  );
  return report(pool, seats, {
    buyers,
    seconds: (performance.now() - start) / 1000,
    retries: results.reduce((sum, r) => sum + (r.retries ?? 0), 0),
    gaveUp: results.filter((r) => r.gaveUp).length,
  });
}

// `workers` buyers run at the same time. Each one keeps buying until it sees "sold out".
export async function runBuyers({ pool, strategy, seats, workers, thinkMs = 5 }) {
  await resetEvent(pool, seats);
  const latencies = [];
  let retries = 0;
  let gaveUp = 0;
  const start = performance.now();
  await Promise.all(
    Array.from({ length: workers }, async (_, w) => {
      for (let n = 0; ; n++) {
        const t0 = performance.now();
        const result = await strategy(pool, { eventId: 1, buyer: `w${w}-${n}`, thinkMs });
        retries += result.retries ?? 0;
        if (result.gaveUp) gaveUp++;
        if (result.sold) latencies.push(performance.now() - t0);
        if (result.soldOut) break;
      }
    })
  );
  const seconds = (performance.now() - start) / 1000;
  const summary = await report(pool, seats, { seconds, retries, gaveUp, p50: percentile(latencies, 50), p99: percentile(latencies, 99) });
  return { ...summary, perSecond: summary.sold / seconds };
}
```

## Part 1: reproduce the lost update

**The README first.** Create `part-1-lost-update/README.md`. A README here is a short lesson for someone who has never seen the topic, and you are that person's teacher. Write four things in your own words. First, the idea from zero, with an everyday picture: for example, two cashiers who each look at the same paper note that says "1 ticket left", and each sells it. Second, a step table that points at the code, like the one below. Third, where each number in the results comes from. Fourth, the real results and the chart, which you add last.

| Step | What happens | Where in the code |
|---|---|---|
| 1 | The buyer reads the count | `SELECT seats_left` in `buyUnsafe` |
| 2 | The buyer sees it is above 0 | `if (left <= 0)` |
| 3 | The app pauses, like a payment check | `await think(thinkMs)` |
| 4 | The buyer writes the count it computed | `UPDATE ... SET seats_left = $1` with `left - 1` |
| 5 | The ticket is recorded | `INSERT INTO sales` |

Steps 1 and 4 are separate statements, and nothing stops another buyer from running steps 1 to 4 in between. That gap is the bug.

**The strategy.** Create `challenges/challenge-6-last-ticket/strategies.js` with the header and the first buyer. This buyer reads, thinks, then writes back a number it computed from a read that may already be stale:

```js
// Five ways to sell one seat. Each takes the pool and { eventId, buyer, thinkMs }
// and returns { sold, soldOut, retries, gaveUp }.
//
// "thinkMs" stands for the work an app does between reading the seat count and
// writing it back: a payment check, a fraud rule, a call to another service.
// It is what opens the gap that the race lives in.

export const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
// A think time of 0 means no pause at all (setTimeout(0) would still wait about a millisecond).
const think = (ms) => (ms > 0 ? sleep(ms) : Promise.resolve());
// 1. The bug: read, think, write back a number you computed from a stale read.
export async function buyUnsafe(pool, { eventId, buyer, thinkMs }) {
  const { rows } = await pool.query("SELECT seats_left FROM events WHERE id = $1", [eventId]);
  const left = rows[0].seats_left;
  if (left <= 0) return { sold: false, soldOut: true };
  await think(thinkMs);
  await pool.query("UPDATE events SET seats_left = $1 WHERE id = $2", [left - 1, eventId]);
  await pool.query("INSERT INTO sales (event_id, buyer) VALUES ($1, $2)", [eventId, buyer]);
  return { sold: true };
}
```

## Part 2: fix it with a row lock

**The strategy.** Add `buyWithLock` to `strategies.js`. It opens a transaction and reads with `FOR UPDATE`. Any other buyer who asks for the same row waits until this transaction ends. The sale happens inside the lock:

```js
// 2. Fix one: lock the row until we are done. Everyone else waits in line.
export async function buyWithLock(pool, { eventId, buyer, thinkMs }) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query("SELECT seats_left FROM events WHERE id = $1 FOR UPDATE", [eventId]);
    if (rows[0].seats_left <= 0) {
      await client.query("ROLLBACK");
      return { sold: false, soldOut: true };
    }
    await think(thinkMs);
    await client.query("UPDATE events SET seats_left = seats_left - 1 WHERE id = $1", [eventId]);
    await client.query("INSERT INTO sales (event_id, buyer) VALUES ($1, $2)", [eventId, buyer]);
    await client.query("COMMIT");
    return { sold: true };
  } catch (error) {
    await client.query("ROLLBACK").catch(() => {});
    throw error;
  } finally {
    client.release();
  }
}
```

**The test.** Create `part-2-row-lock/row-lock.test.js`. The second test shows the lock itself. A second connection asks for the lock with `NOWAIT`, which means "do not wait", and PostgreSQL answers with error `55P03`, lock not available. It also shows that a plain read is not blocked by the lock:

```js
import { test, before, after } from "node:test";
import assert from "node:assert/strict";
import { makePool, waitForDb } from "../../../toolkit/pg.js";
import { resetEvent, runBurst } from "../run.js";
import { buyWithLock } from "../strategies.js";

let pool;
before(async () => {
  pool = makePool();
  await waitForDb(pool);
});
after(() => pool.end());

test("with a row lock, forty buyers for ten seats sell exactly ten", async () => {
  const r = await runBurst({ pool, strategy: buyWithLock, seats: 10, buyers: 40, spreadMs: 300 });
  assert.equal(r.sold, 10);
  assert.equal(r.seatsLeft, 0);
  assert.equal(r.oversold, 0);
  assert.equal(r.lostUpdates, 0);
});

test("a held row lock makes a second locker fail fast with NOWAIT", async () => {
  await resetEvent(pool, 5);
  const holder = await pool.connect();
  const second = await pool.connect();
  try {
    await holder.query("BEGIN");
    await holder.query("SELECT seats_left FROM events WHERE id = 1 FOR UPDATE");
    await second.query("BEGIN");
    // 55P03 is lock_not_available: the row is locked, and NOWAIT refuses to wait.
    await assert.rejects(
      second.query("SELECT seats_left FROM events WHERE id = 1 FOR UPDATE NOWAIT"),
      (error) => error.code === "55P03"
    );
    // A plain read is not blocked by the lock.
    const read = await pool.query("SELECT seats_left FROM events WHERE id = 1");
```

## Part 3: fix it with compare-and-set

**The strategy.** Add two constants above the buyers in `strategies.js`, then `buyWithCas`. The constants limit the attempts and add a random wait between them. The buyer reads the count and the version, thinks, and writes only if the version is still the one it read. If no row changed, it waits and starts over:

```js
const MAX_ATTEMPTS = 50;
// Full jitter: wait a random time up to a cap that doubles each attempt.
const backoff = (attempt) => sleep(Math.random() * Math.min(40, 2 ** attempt));
```

```js
// 3. Fix two: compare-and-set. Write only if the version is still the one we read.
export async function buyWithCas(pool, { eventId, buyer, thinkMs }) {
  for (let attempt = 0; attempt < MAX_ATTEMPTS; attempt++) {
    const { rows } = await pool.query("SELECT seats_left, version FROM events WHERE id = $1", [eventId]);
    const { seats_left: left, version } = rows[0];
    if (left <= 0) return { sold: false, soldOut: true, retries: attempt };
    await think(thinkMs);
    const client = await pool.connect();
    try {
      await client.query("BEGIN");
      const update = await client.query(
        "UPDATE events SET seats_left = $1, version = version + 1 WHERE id = $2 AND version = $3",
        [left - 1, eventId, version]
      );
      if (update.rowCount === 1) {
        await client.query("INSERT INTO sales (event_id, buyer) VALUES ($1, $2)", [eventId, buyer]);
        await client.query("COMMIT");
        return { sold: true, retries: attempt };
      }
      await client.query("ROLLBACK"); // someone else got there first
    } catch (error) {
      await client.query("ROLLBACK").catch(() => {});
      throw error;
    } finally {
      client.release();
    }
    await backoff(attempt);
  }
  return { sold: false, gaveUp: true, retries: MAX_ATTEMPTS };
}
```

Notice that the pause for thinking sits outside the transaction, before `BEGIN`. Nothing is locked while the buyer thinks, so many buyers can think at once. The transaction covers only the write and the sales record.

## Part 4: SERIALIZABLE with retries, and the final comparison

**Two more strategies.** Add `buySerializable` and `buyAtomic` to `strategies.js`. The first runs the same read, think and write as the unsafe buyer, but inside a `SERIALIZABLE` transaction. PostgreSQL detects the clash and refuses one buyer with error `40001`, and the code retries on that error. The second is the one-statement fix from chapter 7.5: the check and the write are in a single `UPDATE`, so there is no gap and no pause inside it.

```js
// 4. Fix three: let Postgres detect the conflict (SERIALIZABLE) and retry on error 40001.
export async function buySerializable(pool, { eventId, buyer, thinkMs }) {
  for (let attempt = 0; attempt < MAX_ATTEMPTS; attempt++) {
    const client = await pool.connect();
    try {
      await client.query("BEGIN ISOLATION LEVEL SERIALIZABLE");
      const { rows } = await client.query("SELECT seats_left FROM events WHERE id = $1", [eventId]);
      if (rows[0].seats_left <= 0) {
        await client.query("ROLLBACK");
        return { sold: false, soldOut: true, retries: attempt };
      }
      await think(thinkMs);
      await client.query("UPDATE events SET seats_left = seats_left - 1 WHERE id = $1", [eventId]);
      await client.query("INSERT INTO sales (event_id, buyer) VALUES ($1, $2)", [eventId, buyer]);
      await client.query("COMMIT");
      return { sold: true, retries: attempt };
    } catch (error) {
      await client.query("ROLLBACK").catch(() => {});
      // 40001 = serialization_failure, 40P01 = deadlock_detected: both mean "try again".
      if (error.code !== "40001" && error.code !== "40P01") throw error;
    } finally {
      client.release();
    }
    await backoff(attempt);
  }
  return { sold: false, gaveUp: true, retries: MAX_ATTEMPTS };
}

// 5. The one-statement fix: check and write in the same UPDATE. No gap, no think time.
export async function buyAtomic(pool, { eventId, buyer }) {
  const update = await pool.query(
    "UPDATE events SET seats_left = seats_left - 1 WHERE id = $1 AND seats_left > 0",
    [eventId]
  );
  if (update.rowCount === 0) return { sold: false, soldOut: true };
  await pool.query("INSERT INTO sales (event_id, buyer) VALUES ($1, $2)", [eventId, buyer]);
  return { sold: true };
}
```

## When something goes wrong

**`ECONNREFUSED 127.0.0.1:5476` or "Postgres did not answer".** The database is not running. Start Docker Desktop, then run `docker compose up -d` in the challenge folder and wait for `healthy`. If another program already uses port 5476, change the port in both places, as above.

**`password authentication failed for user "postgres"`.** You may have another Postgres on the same port, or a stale container from an older run. Run `docker compose down`, then `docker compose up -d`.

**`sorry, too many clients already`.** Postgres allows about 100 connections by default, and each buyer in a lock or SERIALIZABLE run holds one. The pool is capped at 60, and `--test-concurrency=1` keeps test files from adding more. If you raised the number of buyers, lower it again.

**`npm test` never finishes.** A test file forgot `after(() => pool.end())`, so the pool keeps the process alive. Press Ctrl+C and add the hook.

**The unsafe test fails because nothing was oversold.** The buyers never overlapped. Raise `thinkMs` or lower `spreadMs` in the test. A test of a race must make the race likely, and this one proves nothing if it passes without one.

**The numbers jump between runs.** They will. Docker on a laptop shares the machine with everything else, and timers on Windows round up. Close other programs, plug in the charger, and compare shapes, not single numbers. Run a part three times and write down the range.
