The last-ticket bug from chapter 7.1 has three standard fixes. A lock makes writers queue. A version check refuses a stale write. A single statement removes the gap altogether. Each one costs something different, and the cost is what you choose between.

## A row lock makes the second buyer wait

<InteractiveCanvas slug="sysdesign-m7-fix-lock" />

Dina locks the ticket row while she reads and writes it. Omar asks for the same lock and waits. When Dina commits, Omar reads 0 and sees sold out. Nobody oversells. The price is the waiting: the lock stays on for as long as Dina's transaction runs.

<GoDeeper title="Go deeper: FOR UPDATE, waiting, and deadlocks">

In PostgreSQL the lock is one clause: `SELECT seats_left FROM events WHERE id = 1 FOR UPDATE`. The rows returned are locked until the transaction ends. Other transactions that try to update, delete or lock the same rows wait. The documentation notes that these row locks do not affect plain reads: they block only writers and lockers of the same row.

A transaction using it looks like this, with the `withTransaction` helper from chapter 7.4. The `think` step stands for the work between reading and writing, such as a payment check.

```js
await withTransaction(pool, async (db) => {
  const { rows } = await db.query("SELECT seats_left FROM events WHERE id = 1 FOR UPDATE");
  if (rows[0].seats_left <= 0) return "sold out";
  await think(); // payment check, fraud rule... the lock is held all this time
  await db.query("UPDATE events SET seats_left = seats_left - 1 WHERE id = 1");
  return "sold";
});
```

Two options change the waiting. `NOWAIT` makes the statement fail at once if the row is locked, instead of waiting. `SKIP LOCKED` skips locked rows. That suits a queue where each worker wants any free job. The documentation warns that it gives an inconsistent view of the data, so it is not for general use.

Locks bring a new risk, the deadlock. Transaction 1 holds row A and wants row B. Transaction 2 holds row B and wants row A. Neither can move. PostgreSQL detects this and aborts one of the two, and the documentation's advice is to lock rows in a consistent order, and to retry a transaction that was aborted. With a single row, as in Ticketline's last ticket, a deadlock cannot happen. With a cart of several events it can.

The real cost is the hold time. If the lock is held for 200 ms while a payment check runs, that one event can sell at most 5 tickets a second (1 divided by 0.2), however many servers you add. Challenge 6 measures this: in one run with 30 buyers, sales per second fell from 65 with no pause to 12 with a 60 ms pause inside the lock.

</GoDeeper>

## A version check refuses the stale write

<InteractiveCanvas slug="sysdesign-m7-fix-cas" />

Both buyers read 1 ticket at version 7. Dina writes first and moves the row to version 8. Omar's write says only if the version is 7, so it changes nothing, and the database reports 0 rows changed. Nobody waited. Omar reads again and sees sold out.

<GoDeeper title="Go deeper: compare-and-set in SQL and in other stores">

<GlossaryTerm term="Compare-and-set" definition="An update that carries what you expect the current value (or version) to be. It applies only if that is still true, and otherwise changes nothing and tells you so." /> is written CAS(x, old, new): set x to new only if x still equals old [S52]. In SQL you add the expected version to the WHERE clause and then look at how many rows changed:

```js
const result = await pool.query(
  "UPDATE events SET seats_left = $1, version = version + 1 WHERE id = 1 AND version = $2",
  [seatsLeft - 1, version]
);
if (result.rowCount === 0) {
  // Someone else changed the row after we read it. Read again and decide again.
}
```

Nothing is locked while the app thinks, so many buyers can think at once. Only the instant of the UPDATE is exclusive. The cost moves to the loser, who must do the work again. A version counter is safer than comparing the value itself. If you compare `seats_left = 1`, a row that went 1, then 0, then back to 1 (a refund) fools you. A version only goes up.

The same idea exists across stores. DynamoDB supports conditional writes: a write that succeeds only if attributes meet a condition, and otherwise returns an error. The DynamoDB documentation shows how it stops Bob from overwriting Alice's change. It also notes that a conditional write is idempotent when the check is on the attribute being changed. A retry after a network error is then safe. An unconditional atomic counter is not [S42]. etcd offers transactions that are an atomic If/Then/Else with comparisons on the revision of a key [S53].

In a distributed system, a compare-and-set that behaves as if it happened at one instant needs the nodes to agree on an order. Kleppmann's notes show that it needs total order broadcast, which is equivalent to consensus [S52]. On a single PostgreSQL primary, the one machine gives you that order for free. Module 12 shows what it costs when you have many machines.

</GoDeeper>

## Retries must be bounded

<MermaidDiagram title="The compare-and-set loop" chart={`flowchart TD
  A["Read the row and its version"] --> B{"Enough seats?"}
  B -->|"no"| X["Answer: sold out"]
  B -->|"yes"| C["Write only if the version is unchanged"]
  C -->|"1 row changed"| D["Done: ticket sold"]
  C -->|"0 rows changed"| E{"Tries left?"}
  E -->|"yes"| F["Wait a short random time"]
  F --> A
  E -->|"no"| G["Answer: busy, try again later"]
`} legend="A refused write is not an error to show the buyer. It means: read again and decide again. The loop needs a wait with some randomness, and a limit on the number of tries." />

A refused write means read again and decide again. Wait a short, random time first, so rivals do not collide again in step. Stop after a few tries. Without a limit, a busy row keeps many requests retrying, and the database does mostly wasted work.

<GoDeeper title="Go deeper: why the wait is random, and what the limit costs">

If ten losers all retry at the same instant, ten new reads happen at the same instant, and one wins again while nine lose. A random wait spreads them out. Marc Brooker's guide to retries in Amazon's Builders' Library recommends backoff with jitter for the same reason. It also warns that retries multiply load. In his example, a five-deep call stack with three tries per layer sends 243 times the load to the database (3 to the power 5) [S89]. Here the loop is one layer deep, but the lesson holds: unlimited retries on a hot row make things worse, not better.

Challenge 6 measures this on real PostgreSQL. In one run with a 5 ms pause between the read and the write, a buyer needed 0.8 failed attempts per sale on average with 2 buyers competing. It needed 5.8 with 10 buyers and 17.2 with 40. With 40 buyers, 10 purchases hit the limit of 50 attempts and gave up. Throughput also fell, from 43 sales a second at 20 buyers to 22 at 40.

When the limit is reached, the right answer is an honest one: busy, try again. Do not show payment failed, and do not charge. If the buyer clicks again, the request must be safe to repeat, which is what idempotency keys (chapter 6.4) are for. The loop retries only the read-and-write, not the whole checkout.

</GoDeeper>

## Two writers, one row

<InteractiveCanvas slug="sysdesign-m7-two-writers" />

Two writers hit one row. Choose nothing, a lock or a version check, and set how long each writer thinks before it writes. The picture counts lost updates, retries and the finish time. With a lock or a version check nothing is lost. But one waits and the other repeats work.

<GoDeeper title="Go deeper: what the counters show">

With nothing, both writers read the same value, so one update is lost. A longer think time makes the gap wider, so the loss is more certain. With a lock, no update is lost and there are no retries, but the second writer waits for the whole transaction of the first, think time included. With a version check, no update is lost, but the second writer wastes its think time and does it again after the retry.

So the lock pays in waiting and the version check pays in repeated work. When a think step is short, the two are close. When it is long and writers rarely meet, the version check wins because nobody waits. When writers meet all the time, the version check wastes a lot of work and the lock wins because it never repeats a step. The model in the picture has two writers only. With many writers, retries grow, as the previous beat measured.

</GoDeeper>

## MVCC: readers never wait for writers

<InteractiveCanvas slug="sysdesign-m7-mvcc-versions" />

The writer adds version 2 of the row but has not committed. A reader asks and is handed version 1 at once. After the commit, new reads get version 2. This is multiversion concurrency control, MVCC. Writing never blocks reading, and reading never blocks writing.

<GoDeeper title="Go deeper: snapshots, vacuuming, and what MVCC does not fix">

PostgreSQL's documentation states the promise: in MVCC the locks acquired for reading data do not conflict with locks acquired for writing, so reading never blocks writing and writing never blocks reading. Each statement sees a snapshot of the data, as it was at some earlier moment. At Read Committed, a query sees a snapshot as of the instant the query begins. At Repeatable Read, the snapshot is taken once, at the first statement of the transaction, so every query in it sees the same data.

An update does not overwrite the old version. It adds a new one. PostgreSQL keeps the old version while some transaction might still need it. When none can, a cleanup job called VACUUM removes it and marks the space for reuse. If a transaction stays open for hours, the old versions it might need pile up and the table grows. A long idle transaction is a real production problem for this reason.

MVCC does not remove the lost update. Two writers that change the same row still conflict: the second waits for the first, or fails with the serialization error you saw in chapter 7.4. It also does not stop write skew below Serializable. What MVCC removes is the long queue of readers behind a writer. That is why a busy PostgreSQL database can serve thousands of reads while one slow update runs.

</GoDeeper>

## Lock, version, or one statement?

<MermaidDiagram title="Choosing a fix for a lost update" chart={`flowchart TD
  Q1{"Can the check and the write be one statement?"} -->|"yes"| S["One statement: UPDATE ... WHERE seats_left > 0"]
  Q1 -->|"no"| Q2{"Do writers collide often on the same row?"}
  Q2 -->|"often, and the work in the middle is short"| L["Row lock: writers queue"]
  Q2 -->|"rarely, or the work in the middle is slow"| V["Version check: retry the loser"]
  Q2 -->|"no shared transaction, as with DynamoDB"| C["Conditional write on one item"]
`} legend="Start at the top. The one-statement fix has no gap to protect, so it comes first. Then choose by how often writers collide and how long the work between read and write takes." />

If the check and the write fit in one statement, do that. Otherwise choose by how often writers collide. Collide often and briefly: a lock. Collide rarely, or the work in the middle is slow: a version check. No shared transaction, as in DynamoDB: a conditional write on one item.

<GoDeeper title="Go deeper: the measured cost of each, and what goes wrong in production">

Challenge 6 runs all four correct ways on one event with 150 seats and a 5 ms pause between read and write, with 3 buyers and with 30 buyers competing. One run on a laptop with PostgreSQL 18.6 in Docker gave:

```text
buyers  strategy          sales/s  oversold  retries  p99 ms
     3  row lock               23         0        0     298
     3  compare-and-set        33         0      223     920
     3  serializable           32         0      232     870
     3  one statement          91         0        0      88
    30  row lock               34         0        0     991
    30  compare-and-set        22         0     2368    4213
    30  serializable           27         0     2851    2506
    30  one statement         110         0        0     653
```

Your numbers will differ, and a laptop with Docker is noisy, so read the shape. All four are correct: nothing was oversold. The three that keep a gap open between read and write end up at similar speed, bound by that one row and the pause inside the critical section. The one-statement fix is several times faster because it has no pause inside the critical section at all. The best way to make a lock cheaper is to hold it for less time.

Four failure modes to watch for. A lock held across a slow call, such as a payment API, which turns a 3 ms update into a 300 ms queue. A deadlock between two rows locked in different order. A retry storm on a hot row, where most of the work is repeated work. And one hot row for the whole system: if every buyer sells the same event, no fix removes the single-row limit. Splitting the count into several rows is the usual answer, covered with sharded counters in module 27.

To debug, log three things per request: how long it waited for a lock, how many attempts it made, and how long the transaction was open. A rise in any of them shows contention before users complain.

**In AWS.** DynamoDB conditional writes are the version check as a service [S42]. Amazon RDS and Aurora PostgreSQL offer the same row locks and isolation levels as PostgreSQL.

</GoDeeper>
