Ticketline keeps tickets, orders, gate scans and event search (a fictional app). Each is read and written in a different way. That way, not the brand of the database, should pick the store.

## Start from how you read, not the brand

<MermaidDiagram title="Pick a store by the question you ask" chart={`flowchart TD
  Q["How will the data be read?"] --> A{"Join different kinds of data and change them together?"}
  A -->|"yes"| R["Relational"]
  A -->|"no"| B{"Fetch one record by its key?"}
  B -->|"yes"| K["Key-value or document"]
  B -->|"no"| C{"Huge stream of writes, read by time or key range?"}
  C -->|"yes"| W["Wide-column or time-series"]
  C -->|"no"| D{"Follow links, or search by words?"}
  D -->|"links"| G["Graph"]
  D -->|"words"| S["Search"]
`} legend="Read the questions top to bottom. The first yes names the store family to try first. Real choices have more questions, but these five cover most cases." />

Ask one question first: how will this data be read? Joins and all-or-nothing changes point to a relational store. One record by key points to key-value or document. A flood of time-ordered writes points to wide-column or time-series. Links across many hops point to a graph. Words and ranking point to search.

<GoDeeper title="Go deeper: the seven families in one table">

A <GlossaryTerm term="database" definition="A program that stores data on disk and lets many programs read and change it safely at the same time." /> is chosen for what it does well and what it makes hard. The table lists the seven families this chapter covers. The examples are real products, named only so you can look them up.

| Family | Good at | Hard or weak | Examples |
|---|---|---|---|
| Relational | Joins, constraints, transactions across rows, questions you did not plan | Spreading writes over many machines | PostgreSQL |
| Key-value | One record by key at very large scale | Any question that is not "give me this key" | DynamoDB |
| Document | Reading a whole record, with nested parts, as one unit; a changing shape | Relations between documents; multi-document changes | MongoDB |
| Wide-column | Huge write streams, rows sorted by key | Ad hoc queries and joins | Bigtable, Cassandra |
| Time-series | Append by time, read by time range, drop old data | General-purpose queries | TimescaleDB |
| Graph | Following relationships many hops deep | Bulk analysis of unconnected rows | Neo4j |
| Search | Finding and ranking documents by their words | Being the only copy of the data | Search engines built on Lucene |

Two warnings about the table. First, the families overlap. TimescaleDB is built on PostgreSQL, and PostgreSQL itself has many index types. Second, a family says what a store is built for, not what it can never do. You can store time-series data in a relational table, and many teams do, up to a size. The question is what happens when the data grows ten times.

A useful habit is to write the access patterns down before you pick: the five most common reads and the three most common writes, each with a rate. Then ask, for each candidate store, how many records it must touch to answer each read. That count, not the brand, is the cost.

</GoDeeper>

## Relational: facts in tables, answers by join

<InteractiveCanvas slug="sysdesign-m7-store-join" />

The My tickets page needs a ticket, its event and its venue. A relational store keeps them in three linked tables and joins them in one query. It can also change several rows as one all-or-nothing step, called a transaction. Money, seats and orders usually need exactly that.

<GoDeeper title="Go deeper: what a relational store buys, and costs">

Three things make a relational database the usual first choice. First, <GlossaryTerm term="join" definition="A query step that combines rows from two tables by matching a column, for example a ticket's event id with an event's id." /> lets you ask questions nobody planned for. Second, constraints such as unique keys, foreign keys and CHECK rules let the database itself refuse bad data. Third, transactions let several changes succeed or fail together (chapter 7.4).

The My tickets page above is one query:

```sql
SELECT t.id, e.name, e.starts_at, v.hall
FROM tickets t
JOIN events e ON e.id = t.event_id
JOIN venues v ON v.id = e.venue_id
WHERE t.buyer_id = 91;
```

The cost is scale on the write side. One relational database is one machine for writes, until you split the data (chapter 7.6 and module 9). Joins are cheap while the tables sit together, and expensive once they sit on different machines. The CHECK rule is also worth knowing now: a column such as `seats_left int CHECK (seats_left >= 0)` makes PostgreSQL refuse to go below zero. It does not fix the race in chapter 7.1, but it turns a silent oversell into a loud error.

Many teams start here. If you choose another family later, do it for a measured reason.

</GoDeeper>

## Key-value and document: fetch by key

<InteractiveCanvas slug="sysdesign-m7-store-keyed" />

Fetching order 8841 by its key is one cheap read. A document store returns the whole order, seats and all, in that one read. Asking for every order of event 7 is another matter. The store has no index (a sorted lookup list) for it, so it looks at every key. Fast by key, slow by anything else.

<GoDeeper title="Go deeper: designing for the questions you know">

A key-value store is a giant lookup table. DynamoDB hashes the partition key to choose where a record lives, so a read by key goes straight to one place. Each DynamoDB partition is designed for up to 3,000 read units and 1,000 write units a second [S40]. Across all its tables, DynamoDB served a peak of 89.2 million requests a second on Amazon Prime Day 2021 [S44].

A document store keeps a record as one nested document. MongoDB's data modelling guide states the rule: data that is accessed together should be stored together. For Ticketline, an order document can hold the buyer, the seats and the payment. One read gets the whole order. A document store can usually also index a field inside the document, so a question like "orders of event 7" can be made fast if you add that index.

With DynamoDB you handle the other question by adding a secondary index on the event number. DynamoDB updates global secondary indexes asynchronously, so they are eventually consistent [S41]. A read through that index can be a moment behind the table.

The cost of this family is that you design for the questions you know. Change the question later and you may have to rebuild the data. Relations between records are your job: the store will not check that an order's event exists. For changes that must succeed together, you get less than a relational store gives. A conditional write on one item is cheap and safe (chapter 7.5), but a change across many items is harder.

</GoDeeper>

## Wide-column and time-series: writes in a flood

<InteractiveCanvas slug="sysdesign-m7-store-stream" />

Gate scanners write about 18 rows a second, always at the newest end, and the ops screen reads the last 5 minutes. A store that keeps rows sorted by time appends cheaply and reads one range. Wide-column stores such as Bigtable and Cassandra, and time-series stores, are built for this shape.

<GoDeeper title="Go deeper: sorted by key, spread by key">

Eighteen scans a second sounds small. It is about 1.6 million rows a day and about 570 million a year (18 times 86,400 seconds, times 365). Rows are never changed once written. That is an append-heavy, range-read workload.

Bigtable describes its data as a sparse, distributed, persistent multi-dimensional sorted map, indexed by a row key, a column key and a timestamp. It keeps rows in lexicographic order by row key, and any read or write under a single row key is atomic. Because rows are sorted, "all rows between two keys" is a cheap range read.

Cassandra asks you to model around your queries. Its data modelling guide says modelling is query-driven. The partition key decides which node holds a row. Data is copied so that each query reads one table, and joins are not supported. TimescaleDB takes a different route. It keeps PostgreSQL, but splits a table into chunks that each hold one time range, so a query for the last hour touches only the newest chunks.

The main danger is the key. If the key is only the time, every new write lands on the newest partition, and that partition becomes hot while the rest sit idle. The usual fix is to put something else first, such as the gate number, so writes spread out. Module 9 covers hot partitions.

</GoDeeper>

## Graph and search: questions joins answer badly

<InteractiveCanvas slug="sysdesign-m7-store-special" />

Friends of friends who bought a ticket follows links across several hops, which a graph store does without joins. A search for jazz night ranks documents by their words, which a search index does. Both answer fast because their data is laid out for exactly that question.

<GoDeeper title="Go deeper: when the question is the shape of the data">

In SQL, each extra hop in "friends of friends" is another join of the friends table with itself. Three hops is three self-joins, and the work grows with the number of friends at each step. A graph database such as Neo4j stores relationships natively next to the data. Its documentation says it does not use joins, so following a link is a direct step, not a table search. Use a graph store when the relationships are the question: recommendations, fraud rings, route finding.

A search index is built from words. Lucene, a search library, keeps an inverted index: for each term, the list of documents that contain it [S100]. A query for "jazz night" reads two short lists and combines them. Ranking, typo tolerance and stemming sit on top. A LIKE query on a plain table cannot do that well: a pattern that starts with a wildcard cannot use a normal B-tree index, so it scans.

Both engines have the same weakness. They are usually not the only copy of the data. A search index can be a few seconds behind, and it is rebuilt from the main database when it is wrong. Treat them as derived copies, as the last beat shows.

</GoDeeper>

## Sort eight workloads to a store

<InteractiveCanvas slug="sysdesign-m7-store-sorter" />

Eight Ticketline workloads arrive one at a time. Tap the store family that fits, or drag the card onto it. A wrong tap shakes and says why. Look for the clue words in each card: join, by key, all day, hops, words.

<GoDeeper title="Go deeper: the clue words">

Each workload carries clues in its wording. Learn to spot them, because interviewers hide the same clues in their questions.

"Must succeed together", "never below zero", "join" and "report across" point to relational. "By id", "per user", "session" and "profile" point to key-value or document. "Every second", "append", "last hour" and "never updated" point to wide-column or time-series. "Friends of friends", "path between" and "who is connected" point to graph. "Typo", "rank", "contains the word" and "relevance" point to search.

When two families both seem to fit, ask which question is hard. If the hard question is "keep this consistent", pick the store with transactions. If the hard question is "serve this at huge scale by key", pick the key-value family. The sorter has cards where the first guess is wrong on purpose.

</GoDeeper>

## One source of truth, many copies

<MermaidDiagram title="Ticketline's stores" chart={`flowchart LR
  App["Ticketline app"] -->|"writes"| P["Relational database: source of truth"]
  P -->|"change feed"| S["Search index"]
  P -->|"change feed"| C["Cache"]
  P -->|"nightly export"| A["Analytics store"]
  App -->|"search box"| S
  App -->|"hot reads"| C
`} legend="Orders live in one relational database. A change feed keeps a search index and a cache in step. If a copy is wrong, you rebuild it from the source." />

Real systems rarely use one store. Ticketline keeps orders in a relational database and sends copies to a search index and a cache. If a copy is wrong, rebuild it from the source. Each extra store is one more thing to run, secure and keep in step, so add one only when a measured access pattern needs it.

<GoDeeper title="Go deeper: the cost of many stores">

Using several stores for different jobs is sometimes called polyglot persistence. It works when exactly one store is the source of truth for each fact, and every other store is a copy that can be rebuilt. It goes wrong when two stores both accept writes for the same fact. Then you have a distributed consistency problem, and the stores will disagree.

The hard part is keeping the copies in step. The simple way is a dual write: the app writes to the database, then writes to the search index. If the app crashes between the two, the copies differ forever. Chapter 14.4 shows the fix, the outbox pattern, and change data capture, which reads the database's own log.

Every store you add also adds a way to fail, a thing to back up, a thing to secure and a skill the team needs. A two-person team that runs five kinds of database spends its week on operations. Start with the one relational database. Add the cache when reads need it (chapter 7.6), the search index when search needs it, and so on.

**In AWS.** Amazon RDS and Aurora run relational engines such as PostgreSQL; Aurora replicas share one storage volume [S39]. DynamoDB is the key-value and document service [S40].

</GoDeeper>

```quiz
  - "Key-value, with one key per event id"
  - "Relational, with one transaction"
  - "Wide-column, with rows sorted by time"
  - "Graph, with one node for each ticket"

explanations:
  - "A key-value store can protect one item, but this change spans a count, an order and a payment. It would give you no all-or-nothing step across the three."
  - "Right. A relational database changes several rows as one transaction, and a CHECK rule can stop the count at 0. The three steps then succeed or fail together."
  - "Wide-column stores are tuned for huge write streams read by key range. They do not give you a transaction over three kinds of rows."
  - "A graph store is built to follow links. Nothing in this sale is a long chain of links, and it adds no all-or-nothing guarantee."
```
