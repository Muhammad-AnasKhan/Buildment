Ticketline's tickets table has 2,000,000 rows (made-up data). Finding one buyer's tickets must not mean reading all of them. An index fixes that. But how an index stores data decides whether writes or reads are cheap.

## No index means reading every page

<InteractiveCanvas slug="sysdesign-m7-index-scan" />

Buyer 91 has 18 tickets among 2,000,000 rows. With no index, the database reads every table page: 12,739 of them. With an index on the buyer id, it reads 21. An index is a second copy of one column, kept in sorted order, with a pointer to each row. You pay for it on every write.

<GoDeeper title="Go deeper: reading the numbers, and what an index costs">

These numbers come from one run on PostgreSQL 18.6 in Docker, with 2,000,000 made-up rows and 100,000 buyers. A <GlossaryTerm term="page" definition="The fixed-size block a database reads and writes on disk. In PostgreSQL a page is usually 8 kB." /> of the table held about 157 rows, so the table took 12,739 pages. The plan for `WHERE buyer_id = 91` with no index was a parallel sequential scan: it read all 12,739 pages, and took 65 ms with a warm cache. After `CREATE INDEX` on `buyer_id`, the plan read 3 index pages and 18 table pages, and took 0.22 ms.

Why 18 table pages for 18 tickets? The rows of one buyer are scattered, so each sits on its own page. The index finds the 18 places fast, but the table still has to be visited. If a query matches a large share of the table, a scan can be cheaper than an index, because a scan reads pages in order. The database planner makes that choice. `EXPLAIN (ANALYZE, BUFFERS)` shows the plan it chose and the pages it touched, so use it before you add an index.

An index is not free. The index above took 1,947 pages, about 15 MB, and it must be kept in step. Every insert, update or delete that touches an indexed column must change the index too. So an extra index speeds up some reads and slows down every write. A table with ten indexes writes ten places for each new row.

For time, use the napkin-math numbers [S3]: a random SSD read of 8 KiB takes about 100 microseconds, and reading 1 MB in order from SSD about 100 microseconds. Twenty-one random pages is about 2 ms from a cold disk, and often less because the top of the tree stays in memory. A full scan of 12,739 pages is about 100 MB. These are rough numbers, good for the shape of the difference, not for a benchmark.

</GoDeeper>

## A B-tree: three hops to any key

<MermaidDiagram title="A B-tree on 2,000,000 buyer ids" chart={`flowchart TD
  R["Root page: 7 entries"] --> M1["Middle page: about 280 entries"]
  R --> M2["Middle page"]
  R --> M3["5 more middle pages"]
  M1 --> L1["Leaf page: about 1,000 sorted keys"]
  M1 --> L2["Leaf page: next 1,000 keys"]
  L1 -.->|"link to next leaf"| L2
  L1 --> T["Pointers to table rows"]
`} legend="One lookup follows one path: root, middle page, leaf page. Leaves are linked in key order, so a range is one lookup plus a walk along the leaves. Counts come from a PostgreSQL 18.6 run." />

A B-tree keeps keys sorted in pages. The root points to middle pages, those point to leaf pages, and leaves point to rows. A lookup follows one path down. Leaves are linked in order, so a range such as buyers 91 to 95 is one lookup and a short walk along the leaves.

<GoDeeper title="Go deeper: why the tree stays so shallow">

PostgreSQL describes its default index as a multi-way balanced tree of internal pages and leaf pages, where each leaf page holds entries that point to table rows. Each page holds many keys, so the tree is wide and short. In the run above, a leaf page held about 1,000 keys. The root had 7 entries, and each of its 7 children pointed to about 280 leaf pages. That is 7 times 280 times 1,000, about 2,000,000 keys in three levels.

A fourth level would multiply the capacity by about 280 again, to over 500 million keys. That is why a B-tree lookup stays nearly flat as a table grows: ten times more rows rarely adds a level.

Sorted keys also give you range scans and ordering for free. By default, `CREATE INDEX` makes a B-tree in PostgreSQL, and it can serve `<`, `<=`, `=`, `>=`, `>`, `BETWEEN`, `IN`, and `ORDER BY`. PostgreSQL's hash index stores a 32-bit hash and answers only `=`. A pattern such as `LIKE 'jazz%'` can use a B-tree, because it starts with fixed text. A pattern such as `LIKE '%jazz'` cannot, and must scan.

</GoDeeper>

## A B-tree changes pages in place

<InteractiveCanvas slug="sysdesign-m7-btree-split" />

Key 47 belongs in a leaf page that is full, so the page splits. Half the keys move to a new page and the parent gets a new pointer. One insert wrote three pages. Most inserts find room, but writes land all over the file, and each one changes a whole page.

<GoDeeper title="Go deeper: page splits and the cost of random keys">

A B-tree writes in place. To add a key, it finds the right leaf page, changes that page in memory, and writes the page back later. Before that, it appends the change to a log, so a crash does not lose it (PostgreSQL calls it the write-ahead log). A change of a few bytes still rewrites a whole 8 kB page.

When the page is full, it splits, as in the picture. A split leaves both halves partly empty. If keys arrive in order, only the right-most leaf is ever full, so pages fill up tight. If keys arrive in random order, every leaf takes inserts and splits all the time.

You can measure this. A run on PostgreSQL 18.6 loaded 500,000 random UUIDs (version 4) as a primary key, and then 500,000 time-ordered UUIDs (version 7). Both keys are 16 bytes. The random-key index took 19 MB, with leaf pages 72% full. The time-ordered index took 15 MB, with leaf pages 90% full. RFC 9562 says time-ordered UUIDs benefit from greater database-index locality [S66], and the numbers agree: new keys land together on the right edge.

A practical rule follows. If you use UUIDs as primary keys in a B-tree store, prefer time-ordered ones (UUIDv7). Module 10 covers ID generation in depth.

</GoDeeper>

## An LSM tree only appends

<InteractiveCanvas slug="sysdesign-m7-lsm-write" />

A write goes to a log and to a small table in memory. When that table is full, it is written out as one sorted file that is never edited. Nothing is rewritten in place, so every write is an append. The cost is paid later, when old files are merged.

<GoDeeper title="Go deeper: the write path, and a toy LSM in JavaScript">

An LSM tree (log-structured merge tree) is what RocksDB uses. Per the RocksDB overview, a write goes into an in-memory buffer called the memtable, and can also be appended to a write-ahead log. When the memtable is full it becomes immutable and a background thread writes it as a sorted file. Duplicate and overwritten keys are dropped at that point. In the background, compaction merges files into larger ones and drops deleted or overwritten keys [S37].

A read looks in the memtable first, then in the files from newest to oldest, and stops at the first hit. That is why an overwrite is safe: the newest copy is found first, and the older copy is cleaned up later by compaction.

This toy shows the shape in 30 lines. It leaves out the log, levels and any real file format.

```js
// A toy LSM store. Real engines add a write-ahead log, levels and Bloom filters.
class ToyLsm {
  constructor(limit = 4) {
    this.limit = limit;
    this.memtable = new Map(); // newest writes, in memory
    this.files = []; // flushed sorted files, newest first
    this.filesChecked = 0;
  }
  put(key, value) {
    this.memtable.set(key, value);
    if (this.memtable.size >= this.limit) this.flush();
  }
  flush() {
    const sorted = [...this.memtable].sort(([a], [b]) => (a < b ? -1 : 1));
    this.files.unshift(new Map(sorted)); // a file is never changed after this
    this.memtable = new Map();
  }
  get(key) {
    if (this.memtable.has(key)) return this.memtable.get(key);
    for (const file of this.files) {
      this.filesChecked++;
      if (file.has(key)) return file.get(key);
    }
    return undefined;
  }
  compact() {
    const merged = new Map();
    for (const file of [...this.files].reverse()) for (const [k, v] of file) merged.set(k, v); // newer wins
    this.files = [merged];
  }
}

const db = new ToyLsm(4);
for (let i = 1; i <= 12; i++) db.put(`seat-${String(i).padStart(2, "0")}`, "free");
db.put("seat-03", "sold"); // overwrite: the old value stays in an older file
db.put("seat-07", "sold");
console.log("files:", db.files.length, "| memtable keys:", db.memtable.size);

db.filesChecked = 0;
db.get("seat-01"); // oldest key: checked every file
console.log("get seat-01 checked", db.filesChecked, "files");

db.compact();
db.filesChecked = 0;
db.get("seat-01");
console.log("after compaction: files:", db.files.length, "| get seat-01 checked", db.filesChecked, "file");
console.log("seat-03 is", db.get("seat-03"));
```

Running it prints:

```text
files: 3 | memtable keys: 2
get seat-01 checked 3 files
after compaction: files: 1 | get seat-01 checked 1 file
seat-03 is sold
```

Three files means the oldest key costs three checks. Compaction merged them into one, so the same read costs one check, and the old value of seat-03 is gone for good. That merge is the work the LSM tree postponed. It rewrites data that was already written, which is why LSM trees have write amplification: the number of bytes written to disk for each byte the app wrote.

</GoDeeper>

## Step through writes, flushes and merges

<InteractiveCanvas slug="sysdesign-m7-lsm-stepper" />

Press Next to put keys in, flush the memory table, and merge files. After each step, read the two counters: how many files a read must check, and how many bytes were written for each byte you wrote. More files make reads slower. Merging makes reads faster and writes costlier.

<GoDeeper title="Go deeper: read, write and space amplification">

Three numbers describe the cost of a storage engine. <GlossaryTerm term="Write amplification" definition="The bytes a storage engine writes to disk for each byte the application wrote. Log writes, flushes and compaction all add to it." /> counts the extra writing. Read amplification counts the extra reading: the files or pages a read must open. Space amplification counts the extra disk used by old versions that are not yet cleaned up.

You cannot lower all three at once. RocksDB's overview describes the trade-off in its two main compaction styles. Leveled compaction merges one file with only the files it overlaps in the next level, which keeps space use low. Universal compaction merges many files at once, which typically gives lower write amplification but higher space and read amplification [S37].

The stepper uses toy rules, so the numbers are easy to follow. The memory table holds 4 keys, and the script merges the files once 3 exist. Each key is counted once when logged, once when flushed, and once for each merge that rewrites it. Real engines tune these with levels, file sizes and background threads. What carries over is the direction: flushing more often makes more files and slower reads, and merging more often makes fewer files and more rewriting.

</GoDeeper>

## A Bloom filter lets a read skip files

<InteractiveCanvas slug="sysdesign-m7-bloom-skip" />

Each file has a Bloom filter, a small row of bits. If the filter says no, the key is surely not in that file, so the read skips it. If it says maybe, the read opens the file. Here a read opens one file instead of three.

<GoDeeper title="Go deeper: how a Bloom filter works, in JavaScript">

A <GlossaryTerm term="Bloom filter" definition="A small row of bits that can say 'surely not here' or 'maybe here'. It never says 'not here' about a key that was added, but it sometimes says 'maybe here' about a key that was not." /> starts with all bits at 0. To add a key, run it through k hash functions and set those k bits to 1. To test a key, check the same k bits. If any bit is 0, the key was never added: a sure no. If all are 1, the key may have been added, or other keys may have set those bits: a maybe. A Bloom filter has no false negatives, only false positives [S113].

This toy filter is about 20 lines. The `hash` function uses FNV-1a with a seed, so it gives k different hashes.

```js
// A toy Bloom filter: a row of bits and a few hash functions.
function hash(text, seed) {
  let h = 2166136261 ^ seed; // FNV-1a, with a seed so we get several hashes
  for (let i = 0; i < text.length; i++) h = Math.imul(h ^ text.charCodeAt(i), 16777619);
  return h >>> 0;
}

class ToyBloom {
  constructor(bitCount, hashCount) {
    this.bits = new Uint8Array(bitCount);
    this.hashCount = hashCount;
  }
  add(key) {
    for (let s = 0; s < this.hashCount; s++) this.bits[hash(key, s) % this.bits.length] = 1;
  }
  mightHave(key) {
    for (let s = 0; s < this.hashCount; s++) if (!this.bits[hash(key, s) % this.bits.length]) return false;
    return true; // "maybe": every bit was set, by this key or by others
  }
}
```

The test added 10,000 keys, then checked those same keys and 100,000 keys that were never added. The result:

```text
5 bits/key, 3 hashes: stored keys missed 0, false positives 9.18% (formula 9.18%)
10 bits/key, 7 hashes: stored keys missed 0, false positives 0.73% (formula 0.82%)
15 bits/key, 10 hashes: stored keys missed 0, false positives 0.06% (formula 0.07%)
```

No stored key was ever missed. The false positive rate falls fast as you spend more bits. Let m be the bit count, n the key count and k the number of hashes. The false positive rate is about (1 minus e to the power of minus k times n divided by m), all to the power k. The best k is about (m divided by n) times ln 2 [S113]. RocksDB's documentation suggests about 10 bits per key, which gives about a 1% false positive rate. It also says whole-key filters help only point lookups, not range scans.

The memory cost is easy to work out. At 10 bits per key, a billion keys need 10 billion bits, which is 1.25 GB. That is why the filters are kept in memory while the data sits on disk: a 1% chance of one wasted disk read is much cheaper than reading every file.

</GoDeeper>

## Drag the bits per key

<InteractiveCanvas slug="sysdesign-m7-bloom-bits" />

Drag to change the bits per key. At 5 bits, about 9 lookups in 100 wrongly say maybe and open a file for nothing. At 10 bits it is under 1 in 100. Each extra bit costs a little memory and saves disk reads. The curve falls fast at first, then flattens.

<GoDeeper title="Go deeper: B-tree or LSM tree?">

Neither wins everywhere. The choice follows the workload.

| | B-tree (for example PostgreSQL) | LSM tree (for example RocksDB) |
|---|---|---|
| Write | Changes a page in place; may split pages | Appends to memory and a log; merges later |
| Read | One path down, a few pages | Memory table, then several files; Bloom filters help |
| Range scan | Walk the linked leaves | Merge across files |
| Cost paid | On every write, a page change | In the background, compaction |
| Fits | Mixed reads and writes, many different queries | Heavy write streams, such as logs and gate scans |

Two cautions. First, an LSM store pays a hidden bill: compaction uses disk and CPU in bursts, and a slow compaction can stall writes. RocksDB advises keeping threads reserved for flushing to avoid write stalls [S37]. Second, do not guess. Measure your own mix of reads and writes. In module 15 you meet the same idea again in logs and streams.

**In AWS.** Amazon RDS for PostgreSQL and Aurora PostgreSQL use PostgreSQL's B-tree indexes. DynamoDB hides its storage engine, so you choose keys and secondary indexes, not index types [S40, S41].

</GoDeeper>
