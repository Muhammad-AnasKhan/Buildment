Ticketline sells seats for small venues (a fictional app). Saturday's show has one ticket left. Dina and Omar both tap Buy in the same second.

## Both read 1, both write 0

<InteractiveCanvas slug="sysdesign-m7-last-ticket" />

Both phones ask how many tickets are left, and both hear 1. Each then sets the count to 0 and is told the ticket is theirs. Look at the last line of the picture. What do you notice? Nothing crashed, and no error was shown.

<GoDeeper title="Go deeper: what exactly went wrong">

Nothing crashed and no error was shown. The database did nothing wrong: it saved two writes, one after the other. Each request, taken alone, was correct. Read 1, check, write 0 is exactly what a single buyer should do. The mistake is in how the two requests overlap. The second write used a number that the first write had already made false.

This kind of bug has a name: a <GlossaryTerm term="lost update" definition="Two transactions read the same value, then each writes a new value worked out from what it read. The later write replaces the earlier one, so the earlier change is lost." />. Dina's change to the count is lost, because Omar's write erased it. Here the visible damage is one seat sold twice.

It is easy to miss in testing. One buyer at a time always works. The bug needs two requests close together, with a gap between each one's read and write. That gap can be a few milliseconds long, for example while the app checks a payment. On a quiet day it almost never happens. During a sale it happens all the time.

A sold-twice seat costs real things: a refund, an apology, and a buyer who does not come back. The rest of this module shows how to close the gap, and what each way of closing it costs.

</GoDeeper>

## More buyers, more oversold seats

<InteractiveCanvas slug="ticketline-seat-hold-race" />

Now six buyers want the last four seats. Move the sliders and compare the two bars. The separate read-then-write bar can accept more buyers than there are seats. The atomic bar never does. The more buyers there are at once, the worse the first bar gets, so the opening minute of a sale is the worst moment.

<GoDeeper title="Go deeper: what this module covers">

This is a system design problem, not only a coding slip. A single server with a single database user will never show it. A busy system with many app servers, all talking to one database, shows it daily.

The chapters ahead follow the problem from the data to the fix. Chapter 7.2 asks which kind of database fits which kind of data. Chapter 7.3 explains indexes, the structures that make a read cheap, and why some stores write fast and read slower. Chapter 7.4 names the anomalies that overlapping transactions can cause, and the isolation levels that stop them. Chapter 7.5 fixes the lost update three ways: a lock, a version check, and retries. Chapter 7.6 puts the steps for growing a database in order.

Then you practise. In chapter 7.7 you write a compare-and-set update with a retry loop in JavaScript. In challenge 6 (chapter 7.8) you reproduce this exact bug in a real PostgreSQL database in your own repository, fix it three ways, and measure what each fix costs.

The canvas above is a worst-case picture. It assumes every unguarded request reads the same count. Real timing is messier, and the exact number of oversold seats varies from run to run. The direction does not: more overlap, more oversell.

</GoDeeper>
