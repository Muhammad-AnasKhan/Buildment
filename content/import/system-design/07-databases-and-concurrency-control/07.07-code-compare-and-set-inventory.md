In chapter 7.5 you saw the version check as one line of SQL: `WHERE version = 7`. In a real database, the work splits in two. The database does the compare-and-set itself, in one step that nobody can interrupt. Your app does everything around it: the read, the decision, and the retry. Both halves matter, and a bug in either one sells a seat twice.

In this chapter you write both halves in plain JavaScript, against a tiny in-memory store. By the end you have two tested pieces. `createStore(initial)` returns a store where every key carries a version, with a `get` and a `compareAndSet`. `reserveSeats(store, key, qty, options)` sells seats with a bounded retry loop. In challenge 6 you will write the same loop against PostgreSQL, so it pays to get the shape right here, where a failing test costs seconds.

## How the tests make a race happen

A race needs two things to run at once, and the grader runs your code in one plain, synchronous step. So the tests do not rely on luck. They create the race on purpose. The tests wrap your store's `get`. Right after your code reads, a rival buyer takes a seat using your store's own `compareAndSet`. When control returns to your code, the version it holds is out of date, exactly as if another request had slipped in between your read and your write.

This is a useful trick outside this exercise, too. To test a race, do not hope for bad timing. Put a hook at the exact point between the read and the write, and let the test change the data there. The test then fails every time your code is wrong, not one time in a hundred.

For the same reason, your functions are not `async`. A real database call is asynchronous, but the logic is the same, and the plain version keeps the tests exact. Do not add `async`, `await` or a timer.

## The contract for each function

Fix what each function promises before writing it, including the awkward inputs. The tests check the awkward inputs first, because that is where sold-twice bugs live.

**`createStore(initial)`** takes an object of keys and numbers, for example `{ "show-1": 3 }`, and returns an object with two methods. Every key in `initial` starts at version 1. A key that does not exist has version 0.

**`store.get(key)`** returns `{ value, version }`. For a missing key it returns `{ value: undefined, version: 0 }`. It must return a new object each time. If it handed out the object it keeps inside, a caller could change the stored data by writing to the result, with no version change and no check. That is a quiet kind of bug, and one test looks for it.

**`store.compareAndSet(key, expectedVersion, newValue)`** returns `true` or `false`. If the key's current version equals `expectedVersion`, it stores `newValue`, raises the version by 1, and returns `true`. Otherwise it changes nothing and returns `false`. A missing key counts as version 0, so a call with expected version 0 creates the key, once. A second call with version 0 is refused, because the key now has version 1.

**`reserveSeats(store, key, qty, options)`** sells `qty` seats of the event under `key`. It runs a loop of at most `options.maxAttempts` rounds, default 5. In each round it reads, decides, and tries the compare-and-set.

- If the key does not exist, it returns `{ ok: false, reason: "unknown-event", attempts }`.
- If fewer than `qty` seats are left, it returns `{ ok: false, reason: "sold-out", attempts }` and writes nothing. A sold-out answer never calls `compareAndSet`.
- If the compare-and-set succeeds, it returns `{ ok: true, left, attempts }`, where `left` is the seats remaining after this sale.
- If the compare-and-set is refused and another round is allowed, it calls `options.onConflict(attempt)`, where `attempt` is the number of the round that just failed, and reads again.
- If all rounds are refused, it returns `{ ok: false, reason: "too-many-conflicts", attempts }`.

A `qty` that is not a whole number of 1 or more throws a `RangeError`, and so does a `maxAttempts` below 1. This follows the rule from chapter 2.7. An empty or missing answer is a normal case and gets a plain result. A wrong argument is a bug in the caller and gets a loud error.

## A worked example: two spots in a workshop

Here is the loop applied by hand to a case that is not in the tests. A free workshop has 2 spots. Amna and Bilal both press Join at the same moment. The store holds `{ value: 2, version: 1 }`.

Take the steps one at a time. The first subgoal is the read. Both people see 2 spots at version 1. The second subgoal is the decision: 2 is at least 1, so both go ahead. The third is the write, and this is where the version earns its place. Amna's write says "set the value to 1, if the version is still 1", and it is. The store accepts it and moves to version 2. Bilal's identical write also says "if the version is still 1". It is not, so the store refuses it and changes nothing.

Bilal's refusal does not mean "no spots". It means "the data moved". So he reads again and gets 1 spot at version 2. He decides again: 1 is at least 1. His second write says "set the value to 0, if the version is still 2", and it is. Bilal's result is `{ ok: true, left: 0, attempts: 2 }`. If a third person had joined, their read would show 0, and they would get `sold-out` on their first attempt, with nothing written.

Notice what the version bought. Without it, Bilal's first write would have said "set the value to 1" and been accepted, and the store would end with 1 spot left after 2 people joined. With the version, the store can tell that Bilal's decision was based on data that is no longer true.

## Five ways this goes wrong

**Reusing the first read.** The most common bug is to read once before the loop and retry the write with the same numbers. The version in your hand is stale, so every retry is refused, until the attempts run out. The tests catch this with a rival who buys once: the retry must read again and succeed on attempt 2. The read belongs inside the loop.

**Writing without a version check.** If `compareAndSet` ignores `expectedVersion` and always writes, nothing is protected. Every test passes until two writers overlap, and then the second silently erases the first. This is the lost update from chapter 7.1. One test calls `compareAndSet` with a stale version and expects `false` and an unchanged store.

**Keeping the loop open too long, or closing it too soon.** Two small mistakes live in the loop bounds. An off-by-one in the `for` loop gives you one attempt too few, so `attempts` is wrong. And calling `onConflict` after the final failed attempt tells the caller to wait for a retry that never comes. The tests count the attempts and the `onConflict` calls exactly.

**Writing when sold out.** If fewer seats remain than you want, answer `sold-out` and stop. Do not call `compareAndSet`, not even to write the same number back. A write that changes nothing still moves the version, and it can make a real buyer's compare-and-set fail for no reason. The test counts the calls to `compareAndSet`.

**Returning the stored object.** If `get` returns the object the store keeps, then a caller who changes `result.value` changes the store. In a real database the result is always a copy, because it comes from another process. Your fake store should behave the same way, and a test changes the returned object and then reads the key again.

One more habit helps. When a test fails, read its message first. Each one names the input, the expected answer and what your code returned, and several name the usual mistake behind that result.

solution: |
  function createStore(initial = {}) {
    const data = new Map();
    for (const [key, value] of Object.entries(initial)) data.set(key, { value, version: 1 });
    return {
      get(key) {
        const entry = data.get(key);
        return entry ? { value: entry.value, version: entry.version } : { value: undefined, version: 0 };
      },
      compareAndSet(key, expectedVersion, newValue) {
        const entry = data.get(key);
        const current = entry ? entry.version : 0;
        if (current !== expectedVersion) return false;
        data.set(key, { value: newValue, version: current + 1 });
        return true;
      },
    };
  }

  function reserveSeats(store, key, qty, options = {}) {
    const { maxAttempts = 5, onConflict = () => {} } = options;
    if (!Number.isInteger(qty) || qty < 1) {
      throw new RangeError("qty must be a whole number of 1 or more, got " + qty);
    }
    if (!Number.isInteger(maxAttempts) || maxAttempts < 1) {
      throw new RangeError("maxAttempts must be a whole number of 1 or more, got " + maxAttempts);
    }
    for (let attempt = 1; attempt <= maxAttempts; attempt++) {
      const { value, version } = store.get(key); // read again on every attempt
      if (value === undefined) return { ok: false, reason: "unknown-event", attempts: attempt };
      if (value < qty) return { ok: false, reason: "sold-out", attempts: attempt };
      if (store.compareAndSet(key, version, value - qty)) {
        return { ok: true, left: value - qty, attempts: attempt };
      }
      if (attempt < maxAttempts) onConflict(attempt);
    }
    return { ok: false, reason: "too-many-conflicts", attempts: maxAttempts };
  }

## What this unlocks

In challenge 6, the next chapter, you run this same loop against a real PostgreSQL database. The `compareAndSet` becomes `UPDATE events SET seats_left = $1, version = version + 1 WHERE id = 1 AND version = $2`, and "refused" becomes `rowCount === 0`. The retry loop keeps its shape, with a real pause between attempts. You will also measure what the retries cost as more buyers compete, which a single-threaded test cannot show.

The design habit to keep is the order of the steps: read, decide, write if unchanged, and on a refusal read again. Every compare-and-set system, from a SQL version column to a DynamoDB conditional write to an etcd transaction, asks the same of its caller.
