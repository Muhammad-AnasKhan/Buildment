In chapter 27.5 you met a video with 5,000 views a second and a row that can take 1,000 writes a second. You split the count into shards, and you let a merger fold the shards into one total every few seconds. The idea fits in a few lines. The details are where counters break. A counter that loses a view only when two things happen at the same moment passes every simple test and fails in production, on exactly the videos that matter most.

In this chapter you write two things in plain JavaScript. The first is a small function that says how many shards a video needs. The second is a sharded counter with three jobs: add a view to a shard, read the exact count, and merge the shards into a total. The store underneath is a fake with two methods, so every test runs in a fraction of a second and gives the same answer every time.

## What the tests do to your code

The tests are built around the places where this design fails. For the size function they use the edges of the rounding: a rate that is exactly on a boundary, one view over it, a rate of zero, and a pair of numbers where decimal arithmetic in JavaScript gives an answer a hair too large. For the counter they count increments by shard, they pick shards in turn to prove the load is spread, they give it a shard number that does not exist, and they check that reading never changes anything.

Two tests deserve a warning. In one, a view lands on a shard in the middle of a merge, and the test checks that it survives. In the other, the test watches the count after every single write the merge makes, and checks that the count never goes below the true number. The second test encodes a design choice, explained below.

## The contract

**`shardsNeeded({ writesPerSecond, limitPerShard = 1000, planFraction = 0.5 })`** returns the smallest whole number of shards, at least 1, such that `writesPerSecond / shards` is no more than `limitPerShard * planFraction`. It throws a `RangeError` if `writesPerSecond` is not a finite number of 0 or more, if `limitPerShard` is not a positive finite number, or if `planFraction` is not above 0 and at most 1.

**`createShardedCounter({ shards, store, pick })`** returns an object. `shards` is a positive whole number. `store` is the fake database: `store.get(key)` returns the number held under a key, or 0 if there is none, and `store.add(key, delta)` adds a number, which may be negative, to that key in one step. `pick(id, shards)` chooses the shard for one increment and returns a whole number from 0 to `shards - 1`. If you pass no `pick`, choose a shard at random.

The shard of video `v81` number 2 is stored under the key `v81#s2`, and the merged total under `v81#total`.

- `increment(id, n = 1)` adds `n` to the chosen shard and returns the shard number. It throws a `RangeError` if `n` is not a positive safe integer, or if `pick` returns anything that is not a whole number in range, and in that case it writes nothing.
- `read(id)` returns the total plus all the shards: the exact number of views so far. It changes nothing.
- `shardValues(id)` returns an array with the value of each shard, in order.
- `merge(id)` moves every shard into the total and returns how many views it moved. For each shard it reads the value once. If the value is 0 it does nothing for that shard. Otherwise it adds the value to the total first, and then takes the same amount out of the shard.

The constructor throws a `RangeError` for a bad `shards`, and a `TypeError` if `store` does not have `get` and `add` as functions.

## A worked example by hand

Take 3 shards and a `pick` that returns 0, 1, 2, 0, 0 in turn. Five increments arrive for `v81`, adding 1, 1, 1, 2 and 1.

| Step | Shard 0 | Shard 1 | Shard 2 | Total | `read` |
|---|---|---|---|---|---|
| After the five increments | 1 + 2 + 1 = 4 | 1 | 1 | 0 | 6 |
| After `merge` of shard 0 | 0 | 1 | 1 | 4 | 6 |
| After `merge` of shard 1 | 0 | 0 | 1 | 5 | 6 |
| After `merge` of shard 2 | 0 | 0 | 0 | 6 | 6 |

The read stays at 6 the whole time. In the middle of one shard's merge it is briefly 10, because the total has already received the 4 and the shard has not yet given them up. That is the choice the second test checks: a count that is briefly too high can be found and fixed later, and a count that is too low has lost views that nobody can find.

Now the race. Merge starts on shard 0 and reads 4. Before it writes anything, 5 more views land on shard 0, so the shard holds 9. If your code asks the store for the shard's value again to decide what to subtract, it sees 9, subtracts 9, and the 5 new views vanish. If it keeps the 4 it read and subtracts exactly 4, the shard keeps 5 and the next merge counts them. The size function has its own small example: 8,000 views a second with a limit of 1,000 and a plan of one half needs 8,000 / 500 = 16 shards, and 8,001 needs 17.

## Five ways this goes wrong

**Reading the shard twice.** One read to see the value and another to subtract it looks harmless, and it loses every view that lands in between. Read once, keep the number.

**Taking out before putting in.** If the merge subtracts from the shard first and then adds to the total, a crash in the middle loses the views for good. Add to the total first.

**Rounding that goes the wrong way.** In JavaScript, 1470 / (700 * 0.7) is 3.0000000000000004, and `Math.ceil` turns that into 4 shards. Round the ratio to nine decimal places before you take the ceiling.

**Trusting `pick`.** A `pick` that returns 4 for a counter with 4 shards writes to a row that no merge ever visits. The views are in the store and they are never counted. Check the number before you write.

**Writing zeros.** A merge that adds 0 to the total and 0 to the shard for every empty shard does extra database writes on every pass, for every video. The tests count the writes, so skip the shards that are empty.

When a test fails, read its message first. Each one names the input, what it expected and what your code returned.

solution: |
  function shardsNeeded({ writesPerSecond, limitPerShard = 1000, planFraction = 0.5 } = {}) {
    if (typeof writesPerSecond !== "number" || !Number.isFinite(writesPerSecond) || writesPerSecond < 0) {
      throw new RangeError("writesPerSecond must be a finite number of 0 or more");
    }
    if (typeof limitPerShard !== "number" || !Number.isFinite(limitPerShard) || limitPerShard <= 0) {
      throw new RangeError("limitPerShard must be a positive finite number");
    }
    if (typeof planFraction !== "number" || !(planFraction > 0 && planFraction <= 1)) {
      throw new RangeError("planFraction must be above 0 and at most 1");
    }
    const ratio = Number((writesPerSecond / (limitPerShard * planFraction)).toFixed(9));
    return Math.max(1, Math.ceil(ratio));
  }

  function createShardedCounter({ shards, store, pick } = {}) {
    if (!Number.isInteger(shards) || shards < 1) {
      throw new RangeError("shards must be a positive whole number");
    }
    if (!store || typeof store.get !== "function" || typeof store.add !== "function") {
      throw new TypeError("store needs get(key) and add(key, delta)");
    }
    const choose = typeof pick === "function" ? pick : (id, k) => Math.floor(Math.random() * k);
    const shardKey = (id, i) => id + "#s" + i;
    const totalKey = (id) => id + "#total";

    return {
      increment(id, n = 1) {
        if (!Number.isSafeInteger(n) || n < 1) throw new RangeError("n must be a positive safe integer");
        const index = choose(id, shards);
        if (!Number.isInteger(index) || index < 0 || index >= shards) {
          throw new RangeError("pick must return a whole number from 0 to shards - 1");
        }
        store.add(shardKey(id, index), n);
        return index;
      },
      read(id) {
        let sum = store.get(totalKey(id));
        for (let i = 0; i < shards; i++) sum += store.get(shardKey(id, i));
        return sum;
      },
      shardValues(id) {
        const values = [];
        for (let i = 0; i < shards; i++) values.push(store.get(shardKey(id, i)));
        return values;
      },
      merge(id) {
        let moved = 0;
        for (let i = 0; i < shards; i++) {
          const key = shardKey(id, i);
          const value = store.get(key); // read once, use twice
          if (value === 0) continue;
          store.add(totalKey(id), value); // total first: a crash now leaves the count too high, not too low
          store.add(key, -value); // take out exactly what was read
          moved += value;
        }
        return moved;
      },
    };
  }

## Check your understanding before you submit

Run one more case in your head. Make a counter with 2 shards and a `pick` that always returns 1. Call `increment("a", 4)`, then `merge("a")`, then `increment("a", 3)`, then `read("a")` without a second merge. The total is 4, shard 1 holds 3, and the read is 7. A merge now returns 3 and leaves the total at 7. Shard 0 was never used, so the merge made no writes for it. The second merge made exactly two writes.

Now check the arithmetic of the size function against Lamha. A video at 5,000 views a second needs 10 shards, planned at half the limit. At 30,000 views a second it needs 60. That is the whole platform's peak of 35,000 views a second going to one video, which would never happen, so 60 shards is a ceiling and not a plan. A real counter gives most videos one shard and adds more only when a video's rate passes a threshold. The exercise uses a fixed number so the idea stays visible.

## How to say it in an interview

**Say:** "One counter row is a hot spot, because a row takes one write at a time. I split it into N shard rows and add to a random one, with N equal to the write rate divided by half the limit of a row. A read sums the shards, so for the page I run a merger every few seconds that moves each shard into a total row. The merge reads a shard once and subtracts exactly that amount, so a view that lands during the merge is not lost. It writes the total first, so a crash leaves the count slightly high, not low."

**Expect:** "Why not just set the shard to zero after you read it?" **Answer:** "Because a view can land between the read and the write. Setting it to zero erases that view. Subtracting what I read keeps it for the next merge."

## What this unlocks

The pattern of splitting one hot key into several and summing them is not only for views. It works for likes, stock counts, rate limit counters and any other number that many writers add to. The wider idea, that addition does not care about order, is why these counters need no lock between writers, and it comes back in the CRDT counters of chapter 13.7. Chapter 27.8 asks you to use these ideas on scenarios you have not seen.
