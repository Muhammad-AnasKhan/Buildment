Lina's lesson goes viral. For an hour, about 5,000 people a second press play on it. Each play must add 1 to the view count on its watch page. This is the third deep dive of the design loop. It is a small number in bytes, and it is where many designs break.

## One popular video is one hot row

<InteractiveCanvas slug="sysdesign-m27-hot-row" />

Three app servers each add 1 to the same row: the views of video `v81`. The database lets one write change the row at a time, so the others wait in line. A bigger fleet does not help, because every server needs the same row. One row can only go so fast.

<GoDeeper title="Go deeper: how fast one row can go">

A row is a single place that many writers want. A database protects it with a lock or a version check (chapter 7.5), so writers take turns. The turn is short, but turns do not overlap, so the row has a top speed no matter how many servers push on it.

For a managed key-value store the top speed is written down. DynamoDB allows 1,000 write units a second per partition, and one item lives in one partition [S40]. At 5,000 views a second, one row would be asked for five times what it can take, and the extra writes would be throttled or would wait.

The platform total is not the problem. At the peak, all of Lamha has 35,000 view events a second, spread over millions of videos, and most videos get a few a day. The trouble is the top of the skew from chapter 27.4: the few videos that are watched the most are also the rows that are written the most.

An update such as "views = views + 1" is also not safe to repeat. If the writer times out and retries, the add may happen twice. Atomic counters in DynamoDB are not idempotent [S42]. For a view count that is a small error. For money it would not be, which is why a second, exact count exists (beat 5).

</GoDeeper>

## Split one count into many rows

<InteractiveCanvas slug="sysdesign-m27-shards-split" />

Instead of one row, keep several: shard 1, 2 and 3. Each view adds 1 to a shard chosen at random, so three writers now write to three rows and each row sees a third of the load. To read the count, the page adds the shards up. This is a sharded counter.

<GoDeeper title="Go deeper: why adding is safe">

The trick works because addition does not care about order. Add 1 to shard 2, then 1 to shard 1, or the other way round, and the sum is the same. That is also why a sharded counter needs no coordination between writers, which is the idea behind the G-Counter in chapter 13.7: each replica adds to its own slot, and the value is the sum [S74].

The cost moves to the read. A read of the true count touches every shard, so 64 shards means 64 reads. Reads of the count are far more frequent than writes, so the design must not do that on every page view. Beat 4 shows how.

Choosing the shard is simple. Pick one at random for each increment (the simplest), or use a hash of the viewer's id. Random choice spreads the load evenly in the long run. In any one second the busiest shard is a little above the average, so the plan leaves room.

The same idea is used in other places where one key is too popular: a like count, a stock counter, a rate limit counter (chapter 6.5), a hot cache key (chapter 5.6).

</GoDeeper>

## Drag the views, count the shards

<InteractiveCanvas slug="sysdesign-m27-shards-play" />

Drag the views a second for one video, then the number of shards. The busiest shard is the hot spot. Keep it under half of the 1,000 writes a second that a row can take. More shards fix the writes and make every full read add up more rows. That is the price, and the picture shows both.

<GoDeeper title="Go deeper: choosing the number of shards">

The fewest shards is the writes per second divided by the planned rate per shard, rounded up: shards = ceil(writes / 500). At 5,000 views a second that is 10, and at 30,000 it is 60. In practice you pick a round number a little above, such as 16 or 64, so a surprise does not need a re-split.

More is not free. Each extra shard is another row, another place to read when merging, and another chance for one slow shard to hold up the merge. A fixed number for every video is wasteful, since most videos need one. A common answer is to start every video with one row and give it more shards only after its rate passes a threshold, say 200 writes a second. The count then sums rows over the shards that exist. The code exercise in chapter 27.6 uses a fixed number to keep the idea clear.

The model is deliberately simple: views arrive evenly, shards are picked evenly, and a row's limit is 1,000 writes a second [S40]. Real traffic has bursts, and a good plan leaves room for them.

</GoDeeper>

## Merge the shards every few seconds

<InteractiveCanvas slug="sysdesign-m27-merge-total" />

Adding every shard on each page view would be slow. So a merger runs every 5 seconds. It reads each shard, adds them up, writes the sum into one total row, and takes what it read out of the shards. The watch page reads only the total. The count may be 5 seconds late, and no view is lost.

<GoDeeper title="Go deeper: the merge, the race and the buffer">

The merge has one dangerous detail. While the merger reads a shard and finds 412, five more views may land on that shard. If the merger then sets the shard to zero, those five views are lost. The safe way is to subtract exactly what was read: the shard goes from 417 to 5. Nothing is lost, and the next merge picks up the 5. This is the exercise in chapter 27.6.

A second saving comes before the database. An ingest worker can count views in memory and write once a second for each video, not once per view. With 50 workers, a video then gets at most 50 writes a second whatever its views, and the shards only need to handle that. The price is that a crash loses up to one second of counts on that worker. For a video at 5,000 views a second spread over 50 workers, that is up to 100 views, about 0.002% of a day's count for a video with 5 million views. This is bounded error: the loss has a known limit.

Lamha's promise was a count up to a minute late and within 1%. The buffer adds about 1 second and the merge up to 5 more, so the count is at most about 6 seconds old, or 11 with the 5 second page cache, far inside the budget. The error from a crash is far below 1% for any video that matters.

Events arrive through a queue, which delivers at least once [S83]. A retry can add a view twice. For the fast count that is a small, acceptable error.

</GoDeeper>

## Keep a fast count and an exact count

<MermaidDiagram title="Two counts for two questions" chart={`flowchart LR
  P["Player"] -.->|"view event"| Q["Queue"]
  Q --> W["Ingest worker: count in memory, flush every 1 s"]
  W --> S[("Shard rows")]
  S --> M["Merger every 5 s"]
  M --> T[("Total row: shown on the page")]
  Q --> L[("Event log")]
  L --> J["Daily job: count each event once"]
  J --> X[("Exact counts: used to pay creators")]
`} legend="The top path feeds the number on the page: fast, a few seconds late, within 1%. The bottom path keeps every event, removes repeats, and gives the exact count used for money." />

The page needs a number that is fast and close. Paying a creator needs a number that is exact. They are two questions, so Lamha keeps two counts. The top path is the shards. The bottom path keeps every event in a log, and a daily job counts each event once. If the two disagree by a little, the exact one wins.

<GoDeeper title="Go deeper: exactness, uniques and trends">

The exact path needs an event id on every view. The job drops repeats by id, which is the idempotent consumer of chapter 14.5, and it can also drop views from bots and from the same viewer opening the video again and again. These rules are business choices (what counts as a view?), and they belong in the exact path so that the fast count stays simple.

Two other questions look like counting and are better answered with small, approximate structures from chapter 23.4. "How many different people watched?" is a count of distinct items, and a HyperLogLog gives it in small memory: Redis uses up to 12 KB per counter with a standard error of 0.81% [S115], about 2% accuracy at 1.5 KB for more than a billion items in the original paper [S114]. "Which videos are trending now?" needs the heaviest hitters, and a count-min sketch finds them in fixed memory, with the caution that small counts below its error threshold should be ignored [S116].

The rule for choosing: use an exact count where money or a promise depends on it, and use a bounded error elsewhere, with the bound written down and shown to the people who rely on it.

</GoDeeper>

## The watch page reads one small record

<MermaidDiagram title="Reading the watch page" chart={`flowchart LR
  A["API"] --> C[("Metadata cache: 60 s")]
  C -.->|"miss"| D[("Metadata database")]
  A --> T[("Total row: cached 5 s")]
  D --> R["Page: title, status, qualities"]
  T --> R
`} legend="The title and qualities change rarely and are cached for 60 seconds. The view total changes constantly and is cached for 5 seconds. Both come from small rows, read by the video id." />

The watch page needs one small record and one number. The title and the list of qualities change rarely, so they are cached for a minute. The view total changes all the time, so it is cached for only 5 seconds. At a 95% hit rate, the 35,000 reads a second at peak leave about 1,700 reads a second for the database.

<GoDeeper title="Go deeper: the metadata store, step by step">

This is the cache-aside read path of chapter 20.4, with two different lifetimes. A short lifetime for the count is allowed because the count is allowed to be late. A longer one for the title saves reads, and an edit is handled by deleting the cached entry when the title changes, not by updating it [S24].

For a hot video, many requests may miss at the moment its cache entry expires. `stale-while-revalidate` lets the cache answer with the old value while one request fetches the new one [S23]. That is the stampede control of chapter 5.6.

The table is keyed by video id and split by a hash of the id (chapter 9.2). A read touches one partition. A question like "all videos by this creator" needs an index by creator (chapter 9.6), which is updated a moment late [S41]. The status field, uploading, processing, playable or ready, comes from the upload state machine in chapter 27.3. Replicas of the database take read load, and a replica that lags a little is acceptable for a title (chapter 8.4). For the uploader looking at the status of the video they just sent, read from the leader, so they do not see an old status (read your writes, chapter 8.4).

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "A single counter row is a hot spot, so I shard the count into N rows and add 1 to a random one, with N set from the rate: writes per second divided by half the limit of one row. Reads must not add N rows each time, so an ingest worker buffers counts in memory and flushes every second, and a merger adds the shards into one total row every few seconds. The page reads the total, a few seconds late and within 1%. For money I keep a second path: every view event goes to a log, and a daily job counts each event once. Unique viewers use a HyperLogLog."

**Expect:** "What do you lose in a crash?" **Answer:** "At most one flush interval of counts on that worker, which is a known and tiny share of the total. The merge subtracts exactly what it read, so concurrent views are never lost."

</GoDeeper>
