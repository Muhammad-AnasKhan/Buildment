You have Lamha's numbers: about 12.5 Tbit/s of video at peak, 17 uploads a second at peak, 135 PB stored a year, and 35,000 view events a second at peak. This is the sketch step of the design loop. Draw the two paths first, then add only the blocks the numbers ask for.

## A new video travels to a queue

<MermaidDiagram title="The upload path" chart={`flowchart LR
  U["Uploader app"] -->|"1. start upload"| A["API"]
  A -->|"2. signed address"| U
  U -->|"3. chunks, sent direct"| R[("Raw storage")]
  R -->|"4. upload complete"| Q["Job queue"]
  Q --> T["Transcode workers"]
  T -->|"5. versions + playlists"| P[("Video storage")]
  T -->|"6. mark ready"| M[("Metadata database")]
`} legend="The API only starts and finishes the upload. The file goes straight to raw storage in chunks. A queue hands the work to workers, which save the playable versions and then mark the video ready." />

Lina uploads a lesson. Her app asks the API to start an upload and gets a signed address back. It sends the file in chunks straight to raw storage. When the last chunk lands, an event puts a job on a queue. Workers make several versions of the video, save them, and mark the video ready.

<GoDeeper title="Go deeper: the contract and the checks">

The upload API is a few small requests. The names are the course's own.

```text
POST /videos               body: { title, sizeBytes, contentType }
                           -> 201 Created  { videoId, uploadId, chunkSizeBytes, chunkUrls }
                           -> 400 Bad Request   if the size is over 10 GB or the type is not video
                           -> 429 Too Many Requests   if the user is over the limit
PUT  <chunk url>           one chunk of the file -> 200 OK with a checksum
POST /videos/ID/complete   body: the list of chunk checksums -> 202 Accepted
GET  /videos/ID            -> 200 { status: "uploading" | "processing" | "ready" | "failed", ... }
```

The create call is limited per user with a token bucket (chapter 6.5). It carries an idempotency key (chapter 6.4), so a phone that retries after a timeout does not start two uploads. The `202 Accepted` on complete means "I took the job", not "it is playable". The status moves to `ready` only after the workers have saved at least one playable version.

The queue is the buffer from chapter 15.2. Uploads arrive in bursts, and transcoding is slow, so a queue lets the workers run at their own pace. A job that fails goes back in line, and a job that keeps failing goes to a dead letter queue (chapter 15.5). Chapter 27.3 opens this box.

</GoDeeper>

## Play starts with a page, then pieces

<MermaidDiagram title="The play path" chart={`flowchart LR
  V["Player"] -->|"1. GET /watch/ID"| A["API"]
  A --> C[("Metadata cache")]
  C -.->|"miss"| M[("Metadata database")]
  A -->|"2. page + playlist link"| V
  V -->|"3. playlist, then pieces"| D["CDN edge"]
  D -.->|"miss"| S["Origin shield"]
  S -.->|"miss"| P[("Video storage")]
  V -.->|"4. one event per view"| E["View events"]
`} legend="Solid arrows are the plays that happen every time. Dotted arrows are misses or side paths. The player gets the page from the API and the video from the CDN. The view event goes off to be counted." />

The player asks the API for the watch page. The API reads the title and view count from a cache, with the database behind it. The page names a playlist, a file that lists the pieces of the video. The player gets the playlist and the pieces from a CDN edge. Only an edge that lacks a piece goes back to storage.

<GoDeeper title="Go deeper: two different problems on one page">

The watch page and the video are different loads. The page is a small read, about 1 KB of metadata, at 11,600 a second on average and about 35,000 at peak. That is the cache-aside problem from chapter 20.4: a cache in front of a table, keyed by video id. One cache hit costs about 0.5 ms [S3].

The video is the opposite: a few requests for very large files, and 12.5 Tbit/s in total. No cache in front of a database helps with that. A CDN does, because an edge near the viewer keeps copies of the pieces (chapter 5.7). The two loads scale separately: the API fleet by requests, the CDN by bytes.

The "origin shield" is a middle cache layer. Without it, each of the CDN's many edge locations would fetch a missing piece from storage on its own. With it, they ask the shield, and the shield asks storage once (chapter 5.7).

The dotted arrow from the player is the view event. It is sent after the video starts, not before, so counting can never slow the start. Chapter 27.5 follows it.

</GoDeeper>

## The bytes skip the API servers

<InteractiveCanvas slug="sysdesign-m27-bytes-bypass" />

Lina's phone asks the API for permission and gets a signed address. That address works for one upload and then expires (chapter 5.7). The 300 MB goes straight to storage, and the API sees only two small requests. The API fleet stays small because it never carries video.

<GoDeeper title="Go deeper: what the API would carry otherwise">

Suppose the file went through the API. At the peak of 17.4 uploads a second, each of 300 MB, the API fleet would carry 17.4 x 300 MB = 5.2 GB/s, about 42 Gbit/s, in the middle of the path and for no reason. It would also hold thousands of slow connections open, since a phone on weak data may need many minutes to send 300 MB. Each open connection ties up a server.

With a signed address, the API does a small, fast job: check the user, check the size, make the address. The storage service carries the bytes, and it is built for that.

What you give up is a look at the bytes as they arrive. The API cannot check them in the request. So the checks move later: the signed address limits the size and type, and the first job in the pipeline opens the file and checks that it really is a video (chapter 27.3). A file that fails is marked `failed`, and the user is told.

The alternative is a resumable upload server that sits in the path and speaks a protocol such as tus. It is simpler for a team that cannot expose storage addresses to clients, but it carries the bytes and must be scaled for them. {/* source needed: the tus resumable upload protocol (tus.io) and the S3 multipart upload limits; the course uses the ideas, not the exact limits. */}

</GoDeeper>

## Step through the design at peak

<InteractiveCanvas slug="sysdesign-m27-design-stepper" />

Step through the build and watch the card with the biggest number. One box sends all 12.5 Tbit/s: 250 times its plan. Storage and app servers alone do not cut the bytes. The CDN does: at a 95% hit rate, storage sends 0.63 Tbit/s. Processing and counting then get paths of their own.

<GoDeeper title="Go deeper: the numbers behind each step">

The picture uses these course numbers. A sending machine can push 100 Gbit/s and is planned at half of that, 50 Gbit/s (chapter 2.5). Lamha's origin budget is 1 Tbit/s: the most that its own storage should send at peak. It is a course number.

| Step | What changes | The card to watch |
|---|---|---|
| 1. One box | App and video files on one server | 12,500 / 50 = 250 times its plan |
| 2. Storage and apps | Files in object storage, stateless API servers for pages | Storage sends 12.5 Tbit/s, 12.5 times the budget |
| 3. A CDN | 95 of 100 plays answered at the edge | Storage sends 0.63 Tbit/s, under the budget |
| 4. A queue and workers | Upload leaves the request, transcoding runs behind a queue | About 15,600 busy machines at peak (chapter 27.1) |
| 5. Sharded counters | View events counted in many rows (chapter 27.5) | A viral video's writes spread over 16 rows, 313 a second each |

In step 3, tap the hit rate to see 70%. Storage then sends 3.75 Tbit/s, nearly four times the budget. One number in the whole design, the hit rate, moves the bill more than any other. Chapter 27.4 asks whether 95% is believable for a long catalogue.

Each part also needs a copy. Object storage keeps its own copies for durability. The metadata database has replicas (chapter 8.2). The CDN edge is a cache, so a lost edge only costs a refill.

</GoDeeper>

## Four tables hold what Lamha knows

<MermaidDiagram title="The data model" chart={`erDiagram
  VIDEO {
    string video_id PK
    string owner_id
    string title
    string status
    int duration_s
    datetime created_at
  }
  UPLOAD {
    string upload_id PK
    string video_id
    int chunk_count
    int chunks_done
    string state
  }
  RENDITION {
    string video_id
    string quality
    int bitrate_kbps
    string playlist_key
  }
  VIEW_SHARD {
    string video_id
    int shard
    int views
  }
  VIDEO ||--o{ UPLOAD : "is sent by"
  VIDEO ||--o{ RENDITION : "has"
  VIDEO ||--o{ VIEW_SHARD : "is counted in"
`} legend="VIDEO is the row the watch page reads. UPLOAD tracks a chunked upload. RENDITION lists the versions that exist. VIEW_SHARD holds the view count in pieces, so one popular video is not one hot row." />

Lamha keeps few facts, and each has one owner. VIDEO is the row the watch page reads. UPLOAD tracks a chunked upload. RENDITION lists the versions that exist. VIEW_SHARD holds the count in pieces (chapter 27.5). Five years of this is under 1 TB, so metadata is the small part of Lamha.

<GoDeeper title="Go deeper: choosing the store">

A row in VIDEO is about 1 KB in the estimate: ids, a title and description, a status, a duration, and a few times. With 912 million videos in five years, that is about 0.9 TB, which fits on one disk but not on one machine that must also serve 35,000 reads a second at peak.

Two stores fit. A key-value or wide-column store hashes the key for you and spreads load. Its limits matter: DynamoDB allows 3,000 read units and 1,000 write units a second per partition [S40], which is the reason a hot video row needs a cache in front and a counter in shards. The alternative is PostgreSQL with sharding by video id (chapter 9.2), which gives SQL and joins and costs more to run.

"Show me my videos" asks a different question from "show me this video", so it needs a secondary index by owner (chapter 9.6). A global secondary index in DynamoDB is updated asynchronously [S41], so a new video may show in the owner's list a moment late. That is acceptable.

The segment files themselves are not in any table. The RENDITION row holds only the key of the playlist, and the playlist names the segments. That keeps the table small, since a 5 minute video has hundreds of segment files.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Two paths. For upload, the client gets a signed address from a small API and sends chunks straight to object storage, so the API never carries video. An upload-complete event goes on a queue, and workers make several versions and then mark the video ready. For play, the API serves a cached watch page, and the player gets a playlist and short pieces from a CDN. With a 95% hit rate, my origin sends under 1 Tbit/s at peak instead of 12.5. View events go to a counter built from shards, off the play path."

**Expect:** "Why not stream the upload through your servers?" **Answer:** "It would put 40 Gbit/s of file bytes through the API at peak and tie up connections on slow phones. A signed address moves the bytes to storage and keeps the API small. I check the file later in the pipeline."

</GoDeeper>
