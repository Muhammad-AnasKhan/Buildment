  - "Ask the server which chunks it holds, then send the rest"
  - "Start again from chunk 1, so that no chunk can be missing"
  - "Continue at chunk 41, because 40 chunks were sent before"
  - "Send the whole file again in one request to the server"
correct: 0
explanations:
  - "Right. The server's record is the truth. It may hold 39 or 40 chunks, and only it knows. The app sends exactly the missing ones and nothing twice."
  - "This is safe but wasteful. It resends 320 MB over a weak connection, which is the cost that chunking and resuming were meant to avoid."
  - "The app has lost its memory, so it cannot know that 40 were sent. Chunk 40 may also have been cut off when the battery died."
  - "One request for 600 MB is the case that fails most often on a weak connection, and it throws away every chunk already saved."

  - "In about 5.6 hours"

  - "That is 20,000 / 10 seconds, as if nothing new arrived. But 8 new videos arrive every second and use most of the capacity."

  - "This doubles the right answer. It would need the line to shrink by only 1 video a second."
  - "The workers finish 10 a second and only 8 arrive, so the line does shrink, by 2 a second. It is slow, but it ends."

```quiz
type: mcq
question: "Lamha stores one 1080p version of a video at 6 Mbit/s. Viewers on 3 Mbit/s mobile connections see it stall all the time. What fixes the cause?"
options:
  - "Add a bigger CDN cache near those viewers"
  - "Cut the video into shorter pieces, one quality"
  - "Let the API choose a quality for each viewer"
  - "Add lower bitrate versions to the playlist"
correct: 3
explanations:
  - "A closer cache lowers the delay, but a 3 Mbit/s connection still cannot carry 6 Mbit/s. The video needs fewer bits a second."
  - "Shorter pieces start sooner, but each second of video still needs 6 Mbit. Every piece is too big for the link."
  - "The API does not see the viewer's link or buffer, and it is not in the path of the pieces. The player is the one that measures the connection."
  - "Right. With 2 or 3 lower versions in the playlist, the player measures its speed and steps down to one the link can carry, so it stops stalling."
```

```quiz
type: mcq
question: "Creators are paid for each view. A developer suggests using the view count on the watch page, which comes from shards merged every 5 seconds. What is the problem?"
options:
  - "Merging every 5 seconds drops a few views each time"
  - "A sum of shards is always lower than the true count"
  - "A crash or a retry can lose or repeat a few views"
  - "The page cache adds the same view to the count twice"
correct: 2
explanations:
  - "A correct merge loses nothing: it subtracts exactly what it read. The 5 seconds only makes the count late, not wrong."
  - "The sum of all shards plus the total is the exact count of what was received. It is not systematically low."
  - "Right. A crash can lose the second of counts held in memory, and a queue that delivers twice can count a view twice. That is fine for a page, not for pay."
  - "A cache only repeats the number it was given. It does not add views, and its only effect is that the number can be a few seconds old."
```
