In chapters 17.3 and 17.4 you saw a small chain of three ideas. First, count good and valid requests to get an SLI. Second, compare the SLI with the SLO to get a burn rate: how many times faster than allowed the error budget is being spent. Third, ask the same question over a long window and a short window, and page a person only if both say "too fast". Each step is one or two lines of arithmetic. The care is in the edges: what counts as a valid request, what a window with no traffic means, and when a page should stop.

In this chapter you write the chain as four plain JavaScript functions, against a list of log entries in memory. By the end you have `computeSli(requests, options)`, `burnRate(sli, slo)`, `errorBudgetLeft(sli, slo)` and `shouldPage(requests, now, slo, rules, options)`. In challenge 16 you will paste the same functions into your `toolkit/` folder and point them at a day of fake traffic with three incidents, so a wrong edge here costs you a lot more there.

## What the tests do to your code

An alert function that only runs on a calm, normal day looks perfect. The tests therefore feed yours the awkward days. They send a mix of good requests, server errors and client mistakes. They send a slow success, a fast failure and an empty hour. They build a three-minute blip, a twenty-minute outage that has just been fixed, and a slow leak that never gets bad enough to trip the fast rule. For each one the test says in words what a good alert should do, and the failure message tells you what yours did instead.

Your functions are not `async`, and they take their time from the `now` you pass in. They never call `Date.now()`. A function that reads the clock itself cannot be tested on a day that happened last week, and a test that waits an hour is not a test.

## The contract for each function

Fix what each function promises before you write it.

**A log entry** is `{ ts, status, ms }`: `ts` is the time in milliseconds, `status` the HTTP status code, and `ms` how long the request took.

**`computeSli(requests, options)`** returns `{ valid, good, sli }`. A request is *valid* unless its status is 400 to 499. Those are the caller's mistakes, such as a wrong password or a page that does not exist, and they say nothing about whether we did our job, so they are left out of both counts. A valid request is *good* if its status is below 500 and, when `options.latencyMs` is given, it took no more than `latencyMs` milliseconds. So a 503 is bad however fast it came back, and a 200 that took too long is bad too. `sli` is `good / valid`, or `null` when there are no valid requests, because "no traffic" is not "100%". `requests` that is not an array throws a `TypeError`. A `latencyMs` that is not a number above 0 throws a `RangeError`. If `latencyMs` is missing, speed is ignored.

**`burnRate(sli, slo)`** is `(1 - sli) / (1 - slo)`. An `sli` equal to the `slo` burns at exactly 1: the budget lasts the whole window. A `null` `sli` returns 0. An `slo` that is not a number above 0 and below 1 throws a `RangeError`, and so does an `sli` that is neither `null` nor a number from 0 to 1.

**`errorBudgetLeft(sli, slo)`** is the share of the budget still unspent when the SLI was measured over the whole SLO window: `1 - burnRate(sli, slo)`. It can go below 0. A value of `-1` means the team spent the budget twice over.

**`shouldPage(requests, now, slo, rules, options)`** takes the same `requests` and `options`, a time `now`, and a list of rules. A rule is `{ longMs, shortMs, burn }`. For each rule, look at the requests with `ts` after `now - windowMs` and up to and including `now`, once for the long window and once for the short one. Compute the burn rate of each. The rule *fires* when both burn rates are at least `burn`. The function returns `{ page, fired, burns }`: `page` is true when any rule fired, `fired` lists the numbers of the rules that fired, and `burns` has one `{ long, short }` pair of burn rates per rule. A rule with `longMs`, `shortMs` or `burn` not above 0, or with `shortMs` above `longMs`, throws a `RangeError`. A `rules` that is not an array throws a `TypeError`.

## A worked example: a photo upload service

Here is the chain applied by hand to a case that is not in the tests. A photo upload service has an SLO of 99.9%. It uses two rules: the fast rule, 1 hour and 5 minutes at burn 14.4, and a slow one we leave out here. In the last hour it served 2,000 valid requests, and 36 of them failed. In the last 5 minutes it served 200 valid requests, and 10 failed.

Take the steps one at a time. The first subgoal is the long window. The SLI is 1,964 good out of 2,000, which is 0.982. The burn rate is (1 - 0.982) / (1 - 0.999) = 0.018 / 0.001 = 18. The second subgoal is the short window. The SLI is 190 out of 200, which is 0.95, and the burn rate is 0.05 / 0.001 = 50. Both are at least 14.4, so the rule fires and a person is paged.

Now change one thing: the problem was fixed 6 minutes ago, so the last 5 minutes were clean. The long window still burns at 18, but the short window burns at 0. The rule does not fire. That is the whole point of the short window: the page stops soon after the fix, instead of ringing for another hour while the long window slowly forgets.

## Five ways this goes wrong

**Counting client mistakes as failures.** If you treat every status of 400 or more as bad, a bot that sends 500 requests with a wrong password makes your service look broken. The tests mix 404s into good traffic and check that the SLI does not move.

**Treating no traffic as perfect or as broken.** An empty window has no valid requests. An SLI of 1 would hide a service that is down because nobody can reach it. An SLI of 0 would page for every quiet night. The contract says `null` for the SLI and 0 for the burn, and the test for the empty window checks that you do not divide by zero.

**Paging on the long window alone.** The service was fixed, the last five minutes are clean, but the hour still looks bad. If your code ignores the short window, the page keeps ringing. One test builds exactly this day.

**Paging on the short window alone.** A three-minute blip with 8% errors burns very fast over five minutes. But over an hour it burns about four times too fast, which is not worth waking anyone for. One test builds this day too, and a function that only looks at the short window fails it.

**Getting a window edge wrong.** The window runs from just after `now - windowMs` up to and including `now`. A log entry exactly at the old edge belongs to the last window, not this one, and an entry after `now` has not happened yet. A test puts a failed request on each edge. Also compare burn rates with "at least", not "more than", so a burn of exactly the threshold fires.

When a test fails, read its message first. Each one names the input, the expected answer and what your code returned.

solution: |
  function computeSli(requests, options = {}) {
    if (!Array.isArray(requests)) throw new TypeError("requests must be an array");
    const { latencyMs = Infinity } = options;
    if (typeof latencyMs !== "number" || !(latencyMs > 0)) {
      throw new RangeError("latencyMs must be a number above 0, got " + latencyMs);
    }
    let valid = 0;
    let good = 0;
    for (const r of requests) {
      if (r.status >= 400 && r.status <= 499) continue;
      valid++;
      if (r.status < 500 && r.ms <= latencyMs) good++;
    }
    return { valid, good, sli: valid === 0 ? null : good / valid };
  }

  function checkSlo(slo) {
    if (typeof slo !== "number" || !(slo > 0 && slo < 1)) {
      throw new RangeError("slo must be a fraction above 0 and below 1, got " + slo);
    }
  }

  function burnRate(sli, slo) {
    checkSlo(slo);
    if (sli === null) return 0;
    if (typeof sli !== "number" || !(sli >= 0 && sli <= 1)) {
      throw new RangeError("sli must be null or a fraction from 0 to 1, got " + sli);
    }
    return (1 - sli) / (1 - slo);
  }

  function errorBudgetLeft(sli, slo) {
    return 1 - burnRate(sli, slo);
  }

  function shouldPage(requests, now, slo, rules, options = {}) {
    checkSlo(slo);
    if (!Array.isArray(rules)) throw new TypeError("rules must be an array");
    for (const rule of rules) {
      const ok = rule && rule.longMs > 0 && rule.shortMs > 0 && rule.burn > 0 && rule.shortMs <= rule.longMs;
      if (!ok) throw new RangeError("each rule needs longMs, shortMs and burn above 0, and shortMs not above longMs");
    }
    const burnOver = (windowMs) => {
      const inWindow = requests.filter((r) => r.ts > now - windowMs && r.ts <= now);
      return burnRate(computeSli(inWindow, options).sli, slo);
    };
    const burns = rules.map((rule) => ({ long: burnOver(rule.longMs), short: burnOver(rule.shortMs) }));
    const fired = [];
    rules.forEach((rule, i) => {
      if (burns[i].long >= rule.burn && burns[i].short >= rule.burn) fired.push(i);
    });
    return { page: fired.length > 0, fired, burns };
  }

## Check your understanding before you submit

Run the photo upload example in your head with your code, then with real numbers. Build 2,000 entries for the last hour with 36 failures, and put 10 of those failures in the last 5 minutes of 200 requests. With one rule `{ longMs: 3600000, shortMs: 300000, burn: 14.4 }` and an SLO of 0.999, `shouldPage` should return `page: true` and `burns[0]` near `{ long: 18, short: 50 }`. Move the 10 failures to the middle of the hour. The long burn stays at 18, the short burn drops to 0, and the page goes away.

Then try one question the tests do not ask. Your service gets 1 request a minute at night. One failed request in the last 5 minutes makes the short window burn at 200 times the allowed rate. What stops that from paging you? The long window does: one failure in an hour of 60 requests is a burn of about 17, so it also passes the 14.4 line. Your function will page for a single failed request. That is the honest limit of any ratio-based alert on a low-traffic service, and chapter 17.4 mentions the usual answers: a minimum number of requests before an alert may fire, or measuring with a synthetic probe that sends steady traffic.
