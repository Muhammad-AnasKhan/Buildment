A customer says an order was slow. You have three kinds of evidence, and each one answers a different question. Pick the wrong one and you lose the evening.

## Three signals, three questions

<MermaidDiagram title="Which signal answers which question" chart={`flowchart TD
  Q1["Is something wrong, and how big is it?"] --> M["Metrics: numbers over time"]
  Q2["Where did this one request spend its time?"] --> T["Traces: one request across services"]
  Q3["What exactly happened inside that step?"] --> L["Logs: one record per event"]
  M -->|"points at a service and a time"| T
  T -->|"points at a span and a trace id"| L
`} legend="Start from the question. The usual path runs from a metric alarm to a trace to the log lines of the slow step." />

Start with the question, not the tool. Metrics say that something is wrong and how big it is. Traces say where one request spent its time. Logs say what happened inside one place. The usual path is: a metric alarm, then a trace, then the log lines of the slow step.

<GoDeeper title="Go deeper: the three signals side by side">

OpenTelemetry, the open standard for collecting this data, names traces, metrics and logs as its main signals, and adds baggage (small facts carried along with a request) and profiles [S98]. The three are not rivals. They are three views of the same running system, and a good team links them with shared labels and ids.

| Signal | Shape | Best at | Weak at | Cost |
|---|---|---|---|---|
| Metrics | A number saved on a schedule | Trends, alarms, dashboards, "how many" | Saying which request was slow | Low and steady, however much traffic comes |
| Traces | One tree of timed steps per request | Where the time went, which service | Seeing inside a step, and rare requests that were not kept | Several records per request, so usually sampled |
| Logs | One text or JSON record per event | The exact detail: inputs, errors, decisions | Following one request across servers without an id | Storage for every line, and search is slow on a big pile |

The Google SRE book makes a related split between black-box monitoring, which tests what a user can see, and white-box monitoring, which uses what the system reveals about itself such as logs and metrics. Black-box catches problems that are happening now; white-box helps explain them and can show trouble that retries are hiding [S97].

The three-signal path is a habit, not a law. Sometimes a log line is the first clue, such as a crash message. Sometimes a trace of one bad request is the only evidence a customer complaint gives you. What matters is that you can move from one signal to the next without starting again.

</GoDeeper>

## A log line is one event

<InteractiveCanvas slug="sysdesign-m17-log-lines" />

A log line records one thing that happened, with a time. Write it as JSON and put the same request id on every line. Then a search for r-4471 finds the api line, the menu line and the payments line, even though they sit on three servers. Without that id you are guessing which lines belong together.

<GoDeeper title="Go deeper: write logs that can be searched">

Plain text such as `order ok` is easy to write and hard to search. A structured log is one JSON object per line. The fields have names, so a tool can filter on `status` or `traceId` without guessing. This is the line the api writes in challenge 16:

```json
{"ts":"2026-10-24T05:46:26.105Z","service":"api","level":"info","msg":"request done","traceId":"d08c8c89d1a567e341eba89d318aa037","status":200,"ms":603}
```

Five habits keep logs useful. Give every line a time, a service name and a level (info for normal events, error for failures). Put the request id or trace id on every line that belongs to a request. Write one line per event, not a story. Do not put secrets in a log: passwords, card numbers and personal details end up in log storage that many people can read. And keep the volume sane, because every line costs money to store and time to search.

A log line cannot show a trend easily. Counting the error lines over an hour is possible but slow, and that is why the next beat exists. A log also tells you nothing about a request that never reached the server, such as a failed DNS lookup on the phone.

**What it costs.** Logs grow with traffic. At 1,000 requests a second and one 300-byte line per request, a service writes about 26 GB a day. This is simple arithmetic (1,000 times 300 bytes times 86,400 seconds), and it is why teams drop debug lines in production and keep error lines longer.

</GoDeeper>

## A metric is a number over time

<InteractiveCanvas slug="sysdesign-m17-metric-scrape" />

A metric is a small number saved on a schedule. The api keeps one running count. Every 15 seconds the metrics store reads it and saves the point with its time. Three points make a line. Metrics are cheap and show trends, but no single point can say which request was slow.

<GoDeeper title="Go deeper: counters, gauges and histograms">

There are three common kinds of metric. A <GlossaryTerm term="counter" definition="A number that only goes up while the program runs, such as the total requests served. You get a rate by subtracting two readings and dividing by the time between them." /> counts events. A gauge goes up and down, such as the number of open connections. A <GlossaryTerm term="histogram" definition="A set of counters, one per range of values (for example up to 25 ms, up to 100 ms, up to 500 ms), that shows how many observations fell in each range. Histograms from two servers can be added together." /> records how long things took, in buckets.

A rate is the difference between two readings of a counter divided by the time between them. From the picture: (1,500 minus 1,200) divided by 15 seconds is 20 requests a second, and (1,830 minus 1,500) divided by 15 is 22. The counter never needs to be reset, and a missed pull only makes the next gap longer.

Metrics usually carry labels, such as the service name or the status code. Each different combination of labels is a separate series, and every series costs memory and storage. If you add a label with millions of values, such as the user id, the number of series explodes. This is called high cardinality, and it is the usual way to break a metrics system. Put the user id in a log or a trace, not a metric label.

Many tools use the plain-text format that the Prometheus project made popular. One line holds a name, labels and a value, and histogram buckets are cumulative: each bucket counts everything up to its limit. {/* source needed: Prometheus exposition format and cumulative histogram buckets (prometheus.io docs) */} Challenge 16 prints this format from your own services:

```text
http_requests_total{service="api",code="200"} 281
http_request_duration_ms_bucket{service="api",le="100"} 262
http_request_duration_ms_bucket{service="api",le="500"} 292
http_request_duration_ms_bucket{service="api",le="+Inf"} 300
```

</GoDeeper>

## Tap the span that holds the time

<InteractiveCanvas slug="sysdesign-m17-trace-request" />

A trace follows one request through every service. Each step is a span with a name, a start and an end, and a span inside another is its child. Switch between the fast order and the slow one, then tap the span where the time went. In the slow order, almost all of the 780 ms is one call.

<GoDeeper title="Go deeper: reading a trace waterfall">

A <GlossaryTerm term="trace" definition="The full record of one request as it passes through a system, made of spans that share one trace id." /> is a tree of spans. Each <GlossaryTerm term="span" definition="One timed step of a request: a name, a start time, an end time and the id of its parent span. A span without a parent is the root." /> has a name, a start, an end and the id of its parent. The root span has no parent and covers the whole request. Spans can come from different services and different machines. {/* source needed: OpenTelemetry traces concept page (trace, span, parent span id) */}

A <GlossaryTerm term="waterfall" definition="The usual picture of a trace: one row per span, indented under its parent, with a bar placed on a time axis." /> draws the tree on a time axis. To read it, look for the row with the most time of its own. That is the span's duration minus the time covered by its children, called self time. In the slow order of the picture:

| Span | Duration | Self time |
|---|---|---|
| api GET /order | 780 ms | 7 ms |
| api call menu | 18 ms | 4 ms |
| menu GET /menu | 14 ms | 2 ms |
| menu SELECT items | 12 ms | 12 ms |
| api call payments | 755 ms | 5 ms |
| payments GET /payments | 750 ms | 8 ms |
| payments provider.charge | 742 ms | 742 ms |

The self times add up to the 780 ms of the whole order, and the one call to the card provider holds 742 of them, 95%. In the fast order the same call takes 66 ms of 95. The service that looks slow from outside (the api) is not the one to fix; the trace shows where to look. The spans and times are course numbers, shaped like the output of challenge 16.

One trace is also evidence a person can show to a card provider. "Your call took 742 ms at 19:42, trace d08c8c89" is harder to argue with than "it felt slow".

</GoDeeper>

## Pass the id on every call

<InteractiveCanvas slug="sysdesign-m17-propagate-id" />

A trace only holds together if each service passes the trace id on. The api puts it in a header called traceparent. Menu reads it and joins the trace. Payments never gets the header, so it starts a trace of its own and the order is cut in two. One forgotten header breaks the whole picture.

<GoDeeper title="Go deeper: the traceparent header">

The W3C Trace Context standard defines the header. It has four fields joined by dashes [S99]:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

The first field is the version, `00`. The second is the trace id, 32 hex characters (16 bytes), the same for the whole request. The third is the parent id, 16 hex characters, the id of the span that makes this call. The last is a flags byte, and its lowest bit says whether the caller chose to record the trace. An id of all zeros is not valid. A service that receives a good header makes its own span the child of the parent id and passes the same trace id on. A service that receives no header, or a bad one, starts a new trace.

In practice you rarely write this by hand. Libraries such as the OpenTelemetry SDKs add the header to outgoing calls and read it on incoming ones. The risk is the places they do not reach: a call made with a raw socket, a job put on a queue (the header has to travel inside the message), or a worker that starts a fresh context. Each one makes a gap that looks like a separate, smaller trace.

In challenge 16 you will see this on purpose. With the header, 269 orders make 269 traces. With the api told to forget the header, the same 269 orders make 807 traces, three per order, and no trace shows the whole story.

</GoDeeper>

## You cannot keep everything

<MermaidDiagram title="What each signal costs per request" chart={`flowchart LR
  R["1,000 requests a second"] --> M["Metrics: a few numbers per pull. Keep all"]
  R --> L["Logs: one line per request. Keep most, drop debug"]
  R --> T["Traces: several spans per request. Keep a sample"]
`} legend="The cost of metrics does not grow with traffic. The cost of logs and traces does." />

Each signal has a price. A metric costs a few numbers every pull, however many requests there are. A log line costs storage for every request. A trace costs several spans per request, so teams keep only a share, and try to keep the slow and the failed ones.

<GoDeeper title="Go deeper: sampling, tools and AWS">

<GlossaryTerm term="Sampling" definition="Keeping only some of the traces, for example 1 in 100, to save storage and money." /> comes in two kinds. With head sampling, the first service decides at the start of a request whether to record it, and the choice travels in the sampled flag of the traceparent header. It is simple and cheap, but it cannot know yet whether the request will be slow. With tail sampling, the spans are collected first and the choice is made when the trace is complete, so all the slow and failed traces can be kept. It needs more memory, because a collector must hold every span until the trace ends. {/* source needed: head and tail sampling in OpenTelemetry documentation */}

**Tools.** OpenTelemetry is the open standard for producing and moving all three signals. Prometheus stores and queries metrics. Jaeger stores and shows traces; its image is about 55 MB and the Prometheus image about 114 MB (compressed, checked 23 October 2026 [S119]). Grafana draws dashboards, but its image is about 483 MB, so this course draws its charts as SVG files instead.

**In AWS.** Amazon CloudWatch collects metrics and logs. For traces, the AWS X-Ray SDKs and daemon entered maintenance mode on 25 February 2026, which means security fixes only, and AWS is moving X-Ray users to OpenTelemetry [S129]. So a new design should produce its traces with OpenTelemetry and send them to CloudWatch or another backend. {/* source needed: CloudWatch metrics and logs documentation */}

**The honest limit.** A sampled trace system cannot answer "show me every request from this customer". A log system can, if the customer id is in the lines. The two cost models are different on purpose.

</GoDeeper>

<GoDeeper title="In an interview">

How to say it: "I use three signals. Metrics tell me that something is wrong and how big it is, cheaply. Traces show where one request spent its time across services. Logs show the detail inside one step. I join them with a request or trace id, so I can go from an alarm to a trace to the right log line."

The follow-up you will get: "Your tracing bill is too high. What do you do?" A good answer samples, and says how: keep all the failed and slow traces and a small share of the rest, and keep metrics for everything, because metrics do not grow with traffic.

</GoDeeper>
