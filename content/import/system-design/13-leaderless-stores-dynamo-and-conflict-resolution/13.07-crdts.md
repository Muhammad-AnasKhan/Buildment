Last write wins loses data. Siblings need merge code in every client. A third way is a data type that merges itself. Such types are called CRDTs, short for conflict-free replicated data types. This chapter shows three: a counter, a counter that goes down, and a set.

## Merging a counter by max loses likes

<InteractiveCanvas slug="sysdesign-m13-counter-naive" />

Two replicas both show 5 likes. Each gets one like, so each shows 6. They swap numbers and keep the bigger one. The count is 6, but 7 likes happened. A plain number cannot merge, because it does not remember who counted what. Adding the two numbers does not work either.

<GoDeeper title="Go deeper: why a plain number cannot merge, and what a CRDT is">

Try the two obvious merges on a plain count. Keep the larger number: two likes become one, as in the picture. Add the two numbers: 6 plus 6 is 12, and every repeat of the same merge adds more. A merge must give the right answer when the same state arrives twice, late, or in a different order, because networks do all three.

A <GlossaryTerm term="CRDT" definition="A conflict-free replicated data type: a data type with a merge rule built in, so that replicas which have received the same updates are in the same state, whatever the order the updates arrived in." /> fixes this by changing the data, not the network. The state remembers enough history to merge safely. Shapiro and colleagues call the guarantee strong eventual consistency: replicas that have seen the same updates hold the same state, with no further talk between them [S75]. This chapter uses the state-based kind: a replica sends its whole state, and the receiver merges it in.

</GoDeeper>

## Each replica counts in its own slot

<InteractiveCanvas slug="sysdesign-m13-gcounter" />

Give each replica its own slot. A counts 2 in slot A. B counts 3 in slot B. To merge, take the larger value of each slot. Both end with A:2 B:3, a total of 5. An old copy of A's slot arrives later and changes nothing.

<GoDeeper title="Go deeper: the G-Counter">

The grow-only counter, or G-Counter, keeps one count per replica [S74]. A replica adds only to its own slot. The value is the sum of all slots. The merge takes the larger value of each slot. Because each slot has exactly one writer, a larger value is always a newer one, so "take the larger" is the same as "take the newest".

It meets the three laws of the later beat. Taking the larger of two numbers does not depend on the order, does not depend on how you group three of them, and gives the same number when you repeat it. That is why the old copy in the picture does no harm.

The price is size: one slot for every replica that ever counted. And it only counts up. Counting down needs one more idea.

</GoDeeper>

## Two G-Counters make a counter that goes down

<InteractiveCanvas slug="sysdesign-m13-pncounter" />

To count down, keep two G-Counters: one for ups and one for downs. Each merges by max on its own. The value is the ups minus the downs. A holds 3 ups. B holds 1 down. Both show 3 - 1 = 2. A single counter could not go down, because the merge keeps the larger number.

<GoDeeper title="Go deeper: the PN-Counter">

The PN-Counter has two vectors: P for increments and N for decrements [S74]. Increment adds to your own slot in P. Decrement adds to your own slot in N. The value is the sum of P minus the sum of N. Merge is the slot-wise maximum on each vector.

A decrement is stored as growth in N, never as a smaller number. That keeps both halves growing, so the max-merge stays safe. The value itself can go below zero, which matters in the last beat. Use it for things like a stock estimate or likes that can be taken back.

</GoDeeper>

## A remove kills only the adds it saw

<InteractiveCanvas slug="sysdesign-m13-orset" />

Both replicas hold milk, added once with tag A:1. A removes it: tag A:1 is marked removed. At the same time B adds milk again with a new tag, B:1. After the merge, B:1 is alive and A:1 is removed, so milk stays. The add survives, and the older add is gone.

<GoDeeper title="Go deeper: the OR-Set, and the sets it improves on">

The observed-remove set, or OR-Set, gives each add a unique tag, such as the replica name and a counter [S74]. A remove marks every tag of the element that the replica currently sees. An element is in the set when it has at least one tag that is not marked removed. Merge keeps every tag from either side and every removed mark from either side.

Two simpler sets exist in the same paper [S74]. A G-Set can only add. A 2P-Set can add and remove, but a removed name stays removed forever, so a re-add is lost. The OR-Set fixes that, and its rule is called add wins: an add the remover never saw beats the remove.

You write all three types in chapter 13.8, and in challenge 12 you use the OR-Set as the shopping cart.

</GoDeeper>

## Merge in any order, three set types

<InteractiveCanvas slug="sysdesign-m13-crdt-play" />

Three replicas hold different changes: A removes milk and rice, B adds rice again, C adds eggs. Tap to merge any replica into any other, in any order. Switch between the plain set, remove-by-name and the OR-Set. All three agree, in every order. Only the OR-Set agrees on the right cart: eggs and rice.

<GoDeeper title="Go deeper: agreeing is not the same as being right">

All three set types are CRDTs: they converge. The plain set merges by union, so it can never remove, and the milk that A removed comes back. Remove-by-name keeps a list of removed names that always wins, so B's new rice is hidden. Both end in the same cart on every replica, in every order, and both are wrong. The OR-Set ends in the same cart in every order, and the cart is right: milk is gone, rice stays, eggs are added.

The lesson is the one from chapter 11.6: converging only means the copies match. Which cart they converge to is decided by the merge rule. Pick the type whose rule matches what users mean.

</GoDeeper>

## Three laws let the order not matter

<MermaidDiagram title="Why any order gives one answer" chart={`flowchart LR
  L1["Commutative: A with B equals B with A"] --> R["Any order, grouping and repeat: the same final state"]
  L2["Associative: (A with B) with C equals A with (B with C)"] --> R
  L3["Idempotent: A with A equals A"] --> R
  R --> S["Replicas that received the same updates hold the same state"]
`} legend="A merge with all three laws can be reordered, delayed or repeated by the network without changing the result." />

Why does order not matter? Three laws. Merging in either order gives the same result: commutative. Grouping does not matter: associative. Merging the same state twice changes nothing: idempotent. The network can delay, repeat or reorder merges, and the replicas still end up equal.

<GoDeeper title="Go deeper: the laws as tests">

Each law can be written as a test and checked on random replicas. Build three replicas from random operations, then check that a merged with b equals b merged with a, that merging a and b first, then c, equals merging b and c first, then a, and that a merged with itself equals a. That is exactly what the property tests of chapter 13.8 do, with a fixed seed so a failure can be repeated.

State-based types like these three need the laws. A second family, operation-based CRDTs, sends each operation instead of the state, and needs the network to deliver each operation exactly once and in a causal order [S74]. The state-based kind is easier to get right, and costs more to send.

</GoDeeper>

## What a CRDT cannot promise

<InteractiveCanvas slug="sysdesign-m13-crdt-limit" />

A CRDT makes copies agree. It cannot enforce a rule that needs a global view. Two branches each see a balance of 100 and each allow an 80 withdrawal. After the merge the balance is -60. A rule such as never below zero needs agreement before the write: a leader, or consensus.

<GoDeeper title="Go deeper: what CRDTs cost">

**They cannot hold invariants.** A unique username, a stock count that must stay above zero, a seat sold once: each needs one place to say no before the write. A CRDT has no such place by design. For those, use a leader or a conditional write (chapter 13.4), or consensus (module 12).

**Their state grows.** The OR-Set keeps a tag for every add and a mark for every remove. In challenge 12 you add and remove one item 1,000 times and are left with 1,001 tags and 1,000 removed marks for a cart of one item. Cleaning them up safely needs every replica to have seen the remove, which is a coordination problem. A counter keeps a slot for every replica that ever counted.

**They fit some data, not all.** Counters and sets fit. A bank account does not. The benefit is real: no merge code in the app, no lost adds, and no coordination on the write path.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "A CRDT is a data type designed so that replicas can merge in any order, any number of times, and still agree. A G-Counter keeps one slot per replica and merges by max. A PN-Counter uses two of them. An OR-Set tags every add so a remove only kills the adds it saw. They need no coordination, but they cannot enforce a rule like a balance above zero, and their metadata grows."

A follow-up an interviewer may ask: "When would you not use a CRDT?" A good answer: when the data has an invariant, such as a unique name or a balance that must stay above zero. That needs a leader or consensus to say no before the write.

</GoDeeper>
