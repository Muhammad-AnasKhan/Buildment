Nodes fail, and a cart must keep accepting adds. This chapter follows one write through three kinds of trouble, then shows the repairs that bring every copy back. Read repair, the third repair, you met in chapter 8.7, so it appears here only in the folds.

## A strict quorum can refuse a write

<InteractiveCanvas slug="sysdesign-m13-strict-fails" />

The cart's key lives on A, B and C and needs two confirmations. B and C are down. Only A answers, so the write is refused, even though nodes D and E are healthy. A strict quorum counts only the key's own three nodes. Two failures inside that group stop all writes to the key.

<GoDeeper title="Go deeper: how many failures a strict quorum survives">

With N = 3 and W = 2, a strict quorum accepts writes while at most one of the key's three nodes is down. Raise W to 3 and it accepts none. The general rule: writes survive N - W down nodes, and reads survive N - R [S52]. Chapter 12.3 has the full table.

That is the safe choice when a read must never miss a confirmed write. For a cart, it is too strict. The nodes D and E are healthy and could hold the add. A strict quorum will not use them, because a read of the usual nodes would then miss it.

</GoDeeper>

## A stand-in takes the write with a note

<InteractiveCanvas slug="sysdesign-m13-hinted-handoff" />

Dynamo's answer is a sloppy quorum. When C is down, the write goes to the next healthy node on the ring, D, with a note: this belongs to C. The client is told OK after two confirmations. When C returns, D hands the write over and drops the note. This is hinted handoff.

<GoDeeper title="Go deeper: sloppy quorum and hinted handoff, and what they cost">

A <GlossaryTerm term="sloppy quorum" definition="A quorum that counts the first N healthy nodes on the ring, not only the key's own N nodes. A write can succeed on nodes that are not the usual holders of the key." /> keeps writes available through a failure [S45]. The stand-in stores the write apart from its own data, with the name of the owner. It checks its hints from time to time, and when the owner answers, it sends the write over and deletes the hint [S45].

{/* source needed: hinted replicas are kept in a separate local database that is scanned periodically (Dynamo paper, section 4.6); the dossier states the technique but not these details. */}

The price is in chapter 12.3's last warning: the overlap rule assumes the W nodes written and the R nodes read come from the same N nodes. A stand-in is outside that group. Until the hint is delivered, a read of the usual nodes can miss a write that was confirmed [S45, S52]. Sloppy gives more availability and weaker guarantees. A strict quorum gives the opposite.

</GoDeeper>

## Take nodes down, write, bring them back

<InteractiveCanvas slug="sysdesign-m13-cluster-heal" />

Tap nodes to take them down or up, then tap Write and Read. Under Strict, writes need the usual three. Under Sloppy, they go to stand-ins. Take the three usual nodes down, write, bring them back and read at once: the read returns the old value. Tap Wait, read again, and it is fixed.

<GoDeeper title="Go deeper: a script to try, and what to notice">

Try this order with Sloppy and Hints on. First take down the key's three usual nodes. Tap Write. The write lands on the two stand-ins and is confirmed. Bring all three nodes back. Tap Read at once: all three hold the old value, so the read is stale. Wait for the hints to move across, and tap Read again: the new value.

Now turn Hints off and repeat. The stand-ins keep the write, but they never hand it over, so the usual nodes stay stale. Switch to Strict and try the first step again: the write is refused. These three runs are the whole trade-off. Strict never loses sight of a confirmed write and sometimes refuses it. Sloppy never refuses and sometimes hides it for a while. Without hints, it can hide it for good.

In challenge 12, part 2, you build this on the simulated network and measure how long the hidden window lasts.

</GoDeeper>

## A stand-in that fails loses the hint

<InteractiveCanvas slug="sysdesign-m13-hint-lost" />

A hint only helps if the stand-in lives until the owner returns. Here D crashes and loses its note. C comes back with the old value, and nothing says it is behind. Reads that reach C show old data. Something else must find the gap.

<GoDeeper title="Go deeper: why hints are not enough">

Hints cover short failures. A node that is down for a long time, a disk that is replaced, or a stand-in that fails first all leave a copy behind with no hint to fix it. The Dynamo paper pairs hinted handoff, for temporary failures, with a background process called anti-entropy, for the rest [S45].

Read repair (chapter 8.7) helps too: a read that finds an older copy writes the newer one back. But it only repairs keys that someone reads, so a key nobody asks for can stay behind for good. Only a process that looks at every key can promise to find all gaps, and it must do so without sending all the data. That is the job of the next picture.

</GoDeeper>

## Merkle trees find the differing keys

<MermaidDiagram title="Two trees, one differing key" chart={`flowchart TD
  subgraph NA["Node A's tree"]
    RA["root 91f3 (differs)"] --> LA["left 5c2a (same)"]
    RA --> RRA["right e7d1 (differs)"]
    LA --> A1["k1 hash 11"]
    LA --> A2["k2 hash 22"]
    RRA --> A3["k3 hash 33 (same)"]
    RRA --> A4["k4 hash 44 (differs)"]
  end
  subgraph NC["Node C's tree"]
    RC["root 4b0e"] --> LC["left 5c2a"]
    RC --> RRC["right 0a9d"]
    LC --> C1["k1 hash 11"]
    LC --> C2["k2 hash 22"]
    RRC --> C3["k3 hash 33"]
    RRC --> C4["k4 hash 99"]
  end
`} legend="Each parent holds a hash of its children. Hashes are shortened for the picture. The nodes follow only the branches that differ." />

Anti-entropy compares two nodes without sending all the data. Each node builds a tree of hashes over its keys. If the roots match, the nodes agree. If they differ, compare the children and follow only the branches that differ. Here five comparisons find the one key, k4, that C holds differently.

<GoDeeper title="Go deeper: why a tree beats comparing every key">

A <GlossaryTerm term="Merkle tree" definition="A tree in which every leaf is the hash of one piece of data and every parent is the hash of its children. If two trees have the same root, all their data is the same. If the roots differ, comparing the children shows which half differs." /> lets two nodes find their differences by exchanging a few hashes [S45]. With 1,048,576 keys (2 to the power 20) a tree is 20 levels deep. One differing key means about two hash comparisons per level, around 40 in all, instead of a million key comparisons. The nodes then copy only the key that differs.

Dynamo keeps a separate tree for each key range that a node holds, so two nodes compare only the ranges they share [S45]. The cost is upkeep: a tree must be updated when a key changes, and rebuilt when the ranges move after a node joins or leaves [S45].

{/* source needed: one Merkle tree per key range, and the cost of rebuilding trees when membership changes (Dynamo paper, section 4.7); the dossier lists Merkle-tree anti-entropy without these details. */}

Anti-entropy is slow on purpose. It runs in the background and may take minutes. Hints and read repair are the fast paths. Merkle trees are the net under them that catches every gap.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "When a node in a key's list is down, a sloppy quorum writes to the next healthy node on the ring with a hint for the owner, and hands it over when the owner returns. That keeps writes available, but a read of the usual nodes can miss the write for a while, so R + W more than N is no longer a guarantee. Read repair fixes keys that get read, and background anti-entropy with Merkle trees finds the rest."

A follow-up an interviewer may ask: "What if the stand-in dies before it hands over the hint?" A good answer: the owner stays behind, with no hint to fix it. Read repair fixes it if the key is read. Anti-entropy fixes it for sure, by comparing trees and copying only the keys that differ.

</GoDeeper>

<GoDeeper title="Sources">

DeCandia et al., "Dynamo" (SOSP 2007) [S45], for sloppy quorum, hinted handoff for temporary failures, and anti-entropy with Merkle trees for permanent failures. Kleppmann's Cambridge notes [S52], for quorum survival rules and why sloppy quorums break the overlap. The 1,048,576-key count and the 40-comparison figure are course arithmetic, not from the paper.

</GoDeeper>
