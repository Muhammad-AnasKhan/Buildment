A store that always says yes will sometimes hold two versions of one cart. In chapter 10.4 you learned that vector clocks tell you when two versions are concurrent. This chapter is about what to do next, and how a merge can still go wrong. A wrong merge loses data without any error, so it is worth learning well.

## Without the context, siblings multiply

<InteractiveCanvas slug="sysdesign-m13-sibling-context" />

The store returns two versions with a context. The app merges them by union and saves, but forgets the context. The store cannot see that the new cart builds on both, so it keeps it as a third version. The app reads again, merges, and saves with the context. Now one version remains. The context is a token: pass it back unchanged.

<GoDeeper title="Go deeper: what the context does, and what a sibling is">

A <GlossaryTerm term="sibling" definition="One of several versions of the same key that the store keeps because none of them covers the others. The next read returns all the siblings so the application can merge them." /> is a version that no other version covers. The store finds siblings by comparing vector clocks, as in chapter 10.4 [S45].

When the coordinator takes a write, it builds the new clock by merging the clocks in the context and adding 1 to its own slot (chapter 13.2). The new version then covers every version the app had seen. Without the context, the new clock covers nothing, so it is concurrent with the siblings, and the store keeps all of them [S45].

The context must come back unchanged. The app should treat it as an opaque token: it does not read it or edit it. If the app drops it, siblings pile up. If the app invents one, it can hide a write.

The vector also grows. It gets a slot for each node that coordinates a write for the key. Real stores cap its size by dropping the oldest entries, which can make two ordered versions look concurrent [S45].

## A removed item can come back

<InteractiveCanvas slug="sysdesign-m13-cart-resurrect" />

Hana removes milk at node A. At the same time Dina adds tea at node B. The nodes merge their carts by union: eggs, milk and tea. Hana's removal is undone. In Dynamo's own cart, deleted items could come back. A union never loses an add, but it cannot tell an item that was removed from an item the other side never saw removed.

<GoDeeper title="Go deeper: the shopping cart of the Dynamo paper">

The Dynamo paper used exactly this rule for its shopping cart. Two divergent carts are merged by union, so no added item is ever lost. The paper says the price is that deleted items can resurface [S45]. For a cart, Amazon judged that a rare reappearing item is better than a lost add.

The reason is built into a plain set of names. Hana's cart without milk and Dina's cart with milk are two different sets, and nothing in either says which one is newer or why milk is missing. Union takes everything. To merge correctly, the data must carry a record of removals. A simple way is a tombstone, a mark saying "this name was removed". But a tombstone by name brings a new problem, which the playable below shows.

</GoDeeper>

## Try four merge rules on one conflict

<InteractiveCanvas slug="sysdesign-m13-cart-merge" />

Pick a merge rule and see the cart it makes. Start with Hana removing milk while Dina adds tea. Then switch to Dina adding milk back. Last write wins, union and remove-by-name each fail one of the two cases. Only tagged adds, the OR-Set of chapter 13.7, get both right. Try each rule on both cases before you read on.

<GoDeeper title="Go deeper: the four rules and the two cases">

The cart starts as eggs and milk. In case 1, Hana removes milk and Dina adds tea. The cart they both mean is eggs and tea. In case 2, Hana removes milk and Dina adds milk again. The cart they mean is eggs and milk, because Dina's add happened without seeing Hana's removal.

| Rule | Case 1: remove milk, add tea | Case 2: remove milk, add milk |
|---|---|---|
| Last write wins | Milk is back, or the tea is lost, by the stamps | Right or wrong by the stamps |
| Union | Milk is back | Eggs and milk (right) |
| Remove by name | Eggs and tea (right) | The re-add is lost |
| Tagged adds (OR-Set) | Eggs and tea (right) | Eggs and milk (right) |

Each simple rule has a blind spot. Union cannot remove. Remove by name cannot add again. Tagged adds work because each add has a unique tag, and a removal only kills the tags it has seen. A later add has a new tag that no removal knew about. The cost is that the cart must keep tags and removal marks, so its state grows (chapter 13.8 and challenge 12 measure this).

</GoDeeper>

## Three places can do the merge

<MermaidDiagram title="Who settles the conflict" chart={`flowchart TD
  C["Two concurrent versions reach the store"] --> A["The app merges: the store returns siblings, the app writes back with the context"]
  C --> T["The data type merges: a rule built into the type, such as a CRDT"]
  C --> S["The store picks one: last write wins"]
  A --> A2["Cost: every client needs correct merge code"]
  T --> T2["Cost: only some data fits a type, and the metadata grows"]
  S --> S2["Cost: one write is lost"]
`} legend="The merge has to live somewhere. Each place costs something different." />

Three places can do the merge. The app can, as in Dynamo: the store returns siblings and the app writes back one merged cart. The data type can, as in a CRDT: the rule lives in the type. Or the store picks one version, which loses a write. The app's merge code is the cost of the first choice. Ask who can be trusted to get it right.

<GoDeeper title="Go deeper: choosing where to merge">

An app-level merge is the most flexible. The app knows what a cart is, and can use business rules: keep the higher quantity, or ask the user. The cost is that every client, in every language, must implement the same merge correctly, and a bug in one of them can hide a write. Dynamo's paper puts the decision on the application on purpose [S45].

A merge inside the data type moves that code into one tested place. The next chapter shows how a counter and a set can be built so that any order of merges gives the same result [S74]. It only works for data that fits such a type.

Last write wins needs no code at all, and is right only when a lost write is acceptable (chapter 13.5).

For a new design, the usual order of preference is: avoid concurrent writes if you can (give each record one writer), use a CRDT type if the data fits one, merge in the app if it does not, and use last write wins only for data you can afford to lose.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "When a Dynamo-style store sees two concurrent versions, it keeps both as siblings, found by comparing vector clocks. The next read returns both with a context. The app merges them and writes back with the context, so the merged version replaces them. For a cart, union never loses an add but can bring a deleted item back, so I would record removals with unique tags, or use a CRDT set."

A follow-up an interviewer may ask: "What happens if the client forgets the context?" A good answer: the new version is concurrent with the siblings, so the store keeps it as one more sibling. The count grows with every write until a request carries the context.

</GoDeeper>
