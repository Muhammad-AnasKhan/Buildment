You met last write wins in chapters 8.6 and 11.6: keep the version with the later timestamp, drop the other. Those chapters showed it dropping a concurrent write. This chapter asks a sharper question. Which write is the later one? Clocks decide, and clocks disagree. Try the question yourself before you look at the picture.

## A slow clock hides the later write

<InteractiveCanvas slug="sysdesign-m13-lww-skew-story" />

Hana saves tea through node A, whose clock is 10 ms fast. Dina sees OK, then saves rice 5 ms later through node B, whose clock is 10 ms slow. A stamps 30. B stamps 15. The rule keeps the larger stamp, so the rice, which really came later, is dropped. Dina was told OK. No error is raised, and nobody learns the rice is gone.

<GoDeeper title="Go deeper: the arithmetic, and why nobody is told">

A stamp is the real time plus the error of the clock that reads it. Hana's write happens at real time 20 on a clock that is 10 ms fast, so A stamps 30. Dina's write happens at real time 25 on a clock that is 10 ms slow, so B stamps 15. The later write loses whenever the gap between the writes is smaller than the gap between the two clock errors, here 20 ms.

How big are real clock errors? A quartz clock can drift by up to 50 parts per million, about 4 seconds a day, and NTP leaves a few milliseconds of error [S52]. Chapter 10.2 has the numbers. So gaps of a few milliseconds between writes on different servers are easily smaller than the clock gap.

The loss is silent. Both clients were told OK. The store sees two versions, keeps one, and has no reason to raise an error. A famous test shows the scale.

<RealWorldEvent title="Jepsen counts the lost writes in Cassandra" when="24 September 2013" summary="Kyle Kingsbury tested Cassandra, which settled conflicts by last write wins, using it as a lock. About 28% of the writes that Cassandra had acknowledged were lost. When two writes carried equal timestamps, the store picked one by comparing the values." lesson="An OK from the store does not prove the write survived. Count the acknowledged writes after the cluster settles. This result is for the 2013 versions, not for Cassandra today." />

The numbers come from the test write-up [S76].

</GoDeeper>

## Drag the skew and count wrong winners

<InteractiveCanvas slug="sysdesign-m13-lww-skew" />

Drag the clock skew and the gap between the two writes. When the gap is bigger than the skew, the later write wins, as it should. When it is smaller, the later write loses. Switch to Concurrent: now one of the two is lost whatever the clocks say. The counter shows wrong winners out of 20 pairs. At a skew of 20 ms, 19 of 20 pairs go wrong.

<GoDeeper title="Go deeper: the model behind the counter">

Write 1 happens on node A at real time 20, and A's clock is s ms ahead of B's. Write 2 happens on node B g ms later. Stamp 1 is 20 plus half the skew, and stamp 2 is 20 plus g minus half the skew. Write 2 has the larger stamp exactly when g is bigger than s. If g equals s, the stamps tie and the store's tie rule decides.

The counter uses 20 pairs, with gaps of 1, 2, 3 up to 20 ms. For each skew, this many pairs have the later write lose:

| Skew s | Wrong winners (g less than s) | Ties (g equals s) |
|---|---|---|
| 0 ms | 0 | 0 |
| 5 ms | 4 | 1 |
| 10 ms | 9 | 1 |
| 20 ms | 19 | 1 |
| 30 ms | 20 | 0 |

In Concurrent mode neither client saw the other's write, so there is no right winner. Last write wins keeps one and drops one in all 20 pairs. Better clocks cannot change that: it is a property of the rule. Better clocks only fix the first case, where one write really followed the other.

</GoDeeper>

## Different fields, one edit still lost

<InteractiveCanvas slug="sysdesign-m13-lww-whole-item" />

Last write wins also works on whole items. Hana changes the quantity of tea. Dina adds a gift note to the same item. The two changes do not clash, but the rule keeps the whole item with the later stamp, so one change vanishes. Applying the rule per field would keep both edits here.

<GoDeeper title="Go deeper: item or field, and what clocks can and cannot fix">

DynamoDB global tables settle conflicts by last writer wins per item, using an internal timestamp [S43]. An edit to one attribute can be lost because another attribute of the same item changed in another Region at about the same time. A rule applied per field would keep both edits here. It would still drop one of two edits to the same field.

Better clocks help one part of the problem. A hybrid logical clock (chapter 10.5) puts every write after the writes it has seen, so the sequential case in the first picture comes out right when the client carries the stamp along. TrueTime with commit wait (chapter 10.6) does it with an error bound, at a cost on every write. Neither makes two truly concurrent writes into one. Only a different rule can do that: keep both, merge by type, or order them with a leader.

</GoDeeper>

## When last write wins is still fine

<MermaidDiagram title="Is losing one write acceptable?" chart={`flowchart TD
  Q["Two writes to one record may meet. Can one be lost?"]
  Q -->|"Yes, the next write replaces it anyway"| Y["Last write wins is fine: a last-seen time, a cache entry, a sensor reading"]
  Q -->|"No, a person typed it"| N["Keep both versions (13.6) or merge by type (13.7)"]
  Q -->|"No, and the order must hold"| L["Put a leader and a condition in front (13.4, module 12)"]
`} legend="The rule is cheap and always converges. The question is only whether the data can afford a silent loss." />

Last write wins is fine when losing one write does not matter: a last-seen time, a cache entry, a sensor reading that the next one replaces. It is wrong for anything a person typed and expects to keep. Then keep both versions (13.6), merge by type (13.7), or put a leader and a condition in front (13.4). First ask what one lost write would cost.

<GoDeeper title="Go deeper: how to find out if your store is losing writes">

Do not trust a store that says OK. Test it the way Jepsen did: many clients write unique values to the same keys while nodes fail and clocks are skewed. After the system settles, read everything back and count how many acknowledged values are missing [S76]. In challenge 12 you run this count on the simulated network: with last write wins, 200 of 200 concurrent carts lose an add.

When you must use last write wins, shrink the damage. Apply it per field, not per item. Keep clocks tight and monitor their error. Give each record one writer where you can. And write down, in the design, which data is allowed to lose a write and which is not. That sentence is more useful than any setting.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "Last write wins keeps the version with the highest timestamp. It always converges, but it silently drops concurrent writes, and with clock skew it can even drop the later of two writes. I use it where the next write replaces the last one anyway, such as a last-seen time, and not for carts, counters or anything a person typed."

A follow-up an interviewer may ask: "Can better clocks fix it?" A good answer: they fix the skew error. A hybrid clock orders writes that are linked by a message, and TrueTime waits out the uncertainty. They cannot fix concurrency: two writes that never saw each other still leave one winner and one loss. For that I need siblings or a merge type.

</GoDeeper>

```quiz
explanations:
  - "Siblings need a vector clock or a similar check. Last write wins compares two stamps and keeps one, so no sibling is made."
  - "Real time says the second write is later, but the stamps decide. B's stamp is smaller by about 5 ms (8 ms of skew minus the 3 ms gap)."
  - "A store never drops both. It always keeps one version, and here the stamp from A is the larger one."
  - "Right. A's stamp is the real time plus 8 ms, B's is 3 ms later in real time. A's stamp is about 5 ms larger, so the later write is lost silently."
```
