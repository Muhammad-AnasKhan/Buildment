In chapter 13.7 you watched replicas apply changes in different orders and still agree. The trick was never in the network. It was in the data type: a merge rule that gives the same answer however the pieces arrive. In this chapter you write three of those types yourself, so you know exactly what each merge does at its edges.

By the end you will have three tested JavaScript classes. `GCounter` is a counter that only goes up, such as the likes on a product. `PNCounter` can go up and down, such as the stock a warehouse believes it has. `ORSet` is a set that supports both add and remove, such as the items in a Souq shopping cart (a made-up shop). Each one has an `id` for the replica that owns it, a `merge` method, and a `state` method that returns plain data. In challenge 12 you will paste all three into `toolkit/crdt.js` and use the set as a cart.

## Why merge returns a new object

There are two ways to build a CRDT. An operation-based type sends each change to every replica and needs the network to deliver each change exactly once. A state-based type sends its whole state now and then, and the receiver merges it in. You write the state-based kind. It is simpler to get right, because a state that arrives twice, late or out of order is harmless: merging is safe to repeat.

For that to hold, `merge` must be a pure function of its two inputs. It builds and returns a new object, and it never changes either input. A merge that edits `this` in place looks correct in a small test and breaks as soon as two replicas share one object by accident. The tests pass objects in, call `merge`, and check that both inputs are unchanged.

The second rule is that `merge` keeps the replica identity of `this`. If replica A merges the state of replica B, the result is still A's copy, and A keeps adding changes under its own `id`. That detail matters for the set, where every add needs a tag that no other replica can ever produce.

## The contract

Fix the rules first. The tests check these exact rules.

**GCounter.** `new GCounter(id)` starts with no counts. The state is one count per replica, stored in `counts`, an object such as `{ A: 3, B: 2 }`. A missing slot counts as 0. `increment(n = 1)` adds `n` to the slot of this replica only, and returns the new `value()`. If `n` is not a whole number of at least 1, throw a `RangeError`. `value()` is the sum of all slots. `merge(other)` returns a new `GCounter` with the larger value of every slot that appears in either counter. `state()` returns a copy of the slots as a plain object.

**PNCounter.** A counter that can go down cannot just subtract, because `merge` takes the larger value and a smaller value would lose. So it keeps two grow-only counters, one for increments and one for decrements. `increment(n)` and `decrement(n)` follow the same rules as the grow-only counter, including the `RangeError`. `value()` is the sum of increments minus the sum of decrements, and may be negative. `merge(other)` merges each half. `state()` returns `{ p, n }`, the slots of the increment half and of the decrement half.

**ORSet.** `add(element)` gives the add a new tag, made of the replica `id`, a colon and a counter that goes up by 1 on every add on this replica: `A:1`, `A:2`, and so on. It returns the tag. Elements are strings. `remove(element)` marks every tag that this replica can see for that element as removed, and returns how many tags it removed. Removing an element this replica has never seen does nothing and returns 0. `has(element)` is true when at least one tag of the element is not removed. `values()` returns the elements that are present, in alphabetical order. `merge(other)` returns a new set that holds every tag from either side and every removed mark from either side. `state()` returns `{ adds, removed }`: `adds` maps each element ever added to the list of its tags, and `removed` lists the removed tags. The order inside the lists does not matter, because the tests sort them.

Notice that none of the three stores its answer. The counter stores who counted what, and the set stores which tags exist and which are removed. The answer is worked out when you ask. That is why two replicas that hold the same history always give the same answer.

## A worked example: a concurrent add and remove

Here is the set applied by hand to a case that is not in the tests. Replica A adds `rice`, which gets the tag `A:1`. Replica B merges that state, so B now holds `rice` with the tag `A:1` too. Now two things happen at the same time, with no message between them. A removes `rice`: it marks the tag `A:1` as removed. B adds `rice` again: this is a new add, with the tag `B:1`.

Each replica now holds a different state. A holds the tag `A:1`, marked removed. B holds `A:1` (not removed) and `B:1`. Merge them in either order. The result holds both tags, and a removed mark on `A:1`. The tag `B:1` has no removed mark, because A never saw it when it removed. So `rice` is still present. Both replicas will say so.

The subgoal is to ask, for each tag, whether anyone removed that exact tag. A remove only reaches the adds it has seen. That rule is called add wins: an add that nobody had seen when the remove happened survives the remove. If you wrote the set so that `remove("rice")` deleted the name, B's new add would be lost, and the answer would depend on the order of the merge.

## Three ways this goes wrong

**Merging by adding.** It is tempting to write `merge` for the counter as the sum of the two slots. Try it with a replica that merges its own old copy: `{ A: 3 }` merged with `{ A: 1 }` gives 4, and the value grows every time two replicas swap state. The merge must take the larger value of each slot. A test merges a counter with a stale copy of itself and expects the value not to move.

**Changing an input.** If `merge` starts from `this.counts` and edits it, the caller's counter changes, and so does every copy that shares that object. Always build a fresh object. The same goes for the sets of tags inside `ORSet`: copy them, do not reuse them.

**Reusing a tag.** If the counter that makes tags is not kept, or restarts at 0 after a merge, two different adds on one replica get the same tag, and a later remove kills both. Keep the counter on the set, add 1 for every add, and let `merge` carry it over. Also remember that `remove` has to leave the tag in `adds` and put a removed mark beside it. Deleting the tag from `adds` looks the same on one replica, but a merge with a replica that still holds the tag would bring the element back.

## Write the three types

Write plain class declarations and do not add `export`. The tests create everything by name. The last three tests are property tests: they build random replicas from a fixed seed, merge them in random ways, and check three laws on every triple. A merge is **commutative** when `a` merged with `b` equals `b` merged with `a`. It is **associative** when merging `a` and `b` first, then `c`, equals merging `b` and `c` first, then `a`. It is **idempotent** when merging a state with itself changes nothing. These three laws are exactly what lets replicas swap states in any order, any number of times.

  class GCounter {
    constructor(id) {
      this.id = id;
      this.counts = {};
    }

    increment(n = 1) {
      if (!Number.isInteger(n) || n < 1) throw new RangeError("increment needs a whole number of at least 1, got " + n);
      this.counts[this.id] = (this.counts[this.id] ?? 0) + n;
      return this.value();
    }

    value() {
      return Object.values(this.counts).reduce((sum, x) => sum + x, 0);
    }

    merge(other) {
      const out = new GCounter(this.id);
      for (const id of new Set([...Object.keys(this.counts), ...Object.keys(other.counts)])) {
        out.counts[id] = Math.max(this.counts[id] ?? 0, other.counts[id] ?? 0);
      }
      return out;
    }

    state() {
      return { ...this.counts };
    }
  }

    constructor(id) {
      this.id = id;
      this.up = new GCounter(id);
      this.down = new GCounter(id);

      this.up.increment(n);
      return this.value();
    }

    decrement(n = 1) {
      this.down.increment(n);

  class ORSet {
    constructor(id) {
      this.id = id;
      this.counter = 0;
      this.adds = new Map();
      this.removed = new Set();
    }

    add(element) {
      this.counter += 1;
      const tag = this.id + ":" + this.counter;
      if (!this.adds.has(element)) this.adds.set(element, new Set());
      this.adds.get(element).add(tag);
      return tag;
    }

    remove(element) {
      let count = 0;
      for (const tag of this.adds.get(element) ?? []) {
        if (!this.removed.has(tag)) {
          this.removed.add(tag);
          count += 1;
        }
      }
      return count;
    }

    has(element) {
      for (const tag of this.adds.get(element) ?? []) {
        if (!this.removed.has(tag)) return true;
      }
      return false;
    }

    values() {
      return [...this.adds.keys()].filter((element) => this.has(element)).sort();
    }

    merge(other) {
      const out = new ORSet(this.id);
      out.counter = this.counter;
      for (const source of [this, other]) {
        for (const [element, tags] of source.adds) {
          if (!out.adds.has(element)) out.adds.set(element, new Set());
          for (const tag of tags) out.adds.get(element).add(tag);
        }
        for (const tag of source.removed) out.removed.add(tag);
      }
      return out;
    }

    state() {
      const adds = {};
      for (const [element, tags] of this.adds) adds[element] = [...tags];
      return { adds, removed: [...this.removed] };
