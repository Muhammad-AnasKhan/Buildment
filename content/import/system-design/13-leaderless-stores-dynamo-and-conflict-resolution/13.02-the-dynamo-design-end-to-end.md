Souq's cart store must always accept an add. This chapter lays out the whole design, from Amazon's Dynamo paper, step by step. It builds on the hash ring of chapter 9.3 and the quorum rule of chapter 12.3, and does not repeat them.

## A key lives on the next three nodes

<MermaidDiagram title="One key, one preference list" chart={`flowchart LR
  subgraph ring["The ring, clockwise"]
    A["Node A"] --> B["Node B"] --> C["Node C"] --> D["Node D"] --> E["Node E"] --> A
  end
  K["Key cart:42 hashes to a point just before B"] --> B
  B --> P["Preference list for N = 3: B, C, D. B coordinates."]
`} legend="The key walks clockwise from its own point. The first node coordinates, and the first N nodes hold the copies." />

Hash the key to a spot on the ring. Walk clockwise. The first node is the coordinator, and the first N nodes hold the copies. Here N = 3, so the cart lives on B, C and D. That list is the key's preference list. Every node can work it out alone, with no master to ask.

<GoDeeper title="Go deeper: no master, and how nodes know the ring">

The Dynamo paper describes a store with no central node. Every node can be asked for any key, and it can work out the key's preference list from the ring [S45]. The paper calls the node that handles a request its <GlossaryTerm term="coordinator" definition="The node that receives a read or write for a key and carries it out: it contacts the other nodes that hold the key and waits for enough answers." />. Usually it is the first node of the preference list.

For that to work, every node must know the ring. Dynamo uses gossip: nodes tell each other about members joining and leaving, so each keeps its own copy of the ring [S45]. Failure detection is local too. A node that does not answer is skipped for a while and tried again later [S45]. Chapter 12.8 explains how gossip spreads news and how SWIM suspects a silent node before it blames it. This chapter only needs the result: no master, and every node can find a key's nodes.

{/* source needed: Dynamo's failure detection is a local notion, a node skips a peer that does not answer (Dynamo paper, section 4.8); the dossier lists gossip failure detection without this detail. */}

N is a setting of the store. Amazon's paper reports (N, R, W) = (3, 2, 2) as the common choice [S45].

</GoDeeper>

## Drag the key, skip repeated machines

<InteractiveCanvas slug="sysdesign-m13-ring-write" />

Drag the key around the ring and tap Write. Three copies appear, each on a different machine. Now turn off Skip repeats and drag the key to 10. Two points of machine A come first, so only two machines hold the key. Skipping keeps every copy on a different machine.

<GoDeeper title="Go deeper: the preference list, step by step">

In chapter 9.3 you gave each node many points on the ring, called virtual nodes, to even out the load. They create a new problem for copies. Walking to the next three points can give you the same machine twice, because one machine owns several neighbouring points. The Dynamo paper says the preference list is built so that it holds only distinct physical nodes [S45].

{/* source needed: the Dynamo paper section on the preference list (distinct physical nodes, and spreading copies across data centres); the dossier states virtual nodes and the technique list but not this detail. */}

The rule is short. Start at the key's point. Walk clockwise, point by point. Keep a machine the first time you meet it and skip its other points. Stop when you hold N machines. The nodes after those, in ring order, are the stand-ins that chapter 13.3 uses when a usual node is down.

Why distinct machines? Copies exist to survive a failure. Two copies on one machine fail together. Real stores go further and spread the copies over racks or zones, so a power cut in one rack cannot take all of them. The course picture uses only machines, to keep it small.

</GoDeeper>

## A write waits for W copies, not all

<InteractiveCanvas slug="sysdesign-m13-write-path" />

The client sends the write to the coordinator, node A. A saves it and sends it on to B and C. B answers first, which is the second copy. With W = 2 that is enough, so A tells the client OK. C is slower and gets the value a moment later. The wait is the second-fastest copy.

<GoDeeper title="Go deeper: what the coordinator does, and what it cannot undo">

The coordinator gives the write a new version, with a vector clock from chapter 10.4: it adds 1 to its own slot, on top of the clock the client sent as context. Then it sends the version to the other N - 1 nodes and counts the answers. Its own save counts as one [S45]. When W have answered, it replies to the client.

{/* source needed: the coordinator writes locally and waits for W - 1 replies from the other nodes (Dynamo paper, section 4.5); the dossier does not list this detail. */}

The speed of a write is set by the W-th fastest node, not the slowest. That is why Dynamo lets you choose W below N: one slow or broken node does not slow the cart. The paper measures its service levels at the 99.9th percentile, not the average, because the cart must feel fast for almost everyone [S45].

There is no undo. If the coordinator saves the write and copies it to one other node, then fails before W answer, the client gets an error. But the write is on two nodes. A later read may find it, or may not. Kleppmann's notes call this the gray zone of a quorum write that did not finish [S52]. So a client that times out must treat the write as maybe done, and make a retry safe: the same cart saved twice is the same cart.

</GoDeeper>

## A read asks R nodes and returns versions

<MermaidDiagram title="A read returns the versions and a context" chart={`sequenceDiagram
  participant Cl as Client
  participant B as Node B (coordinator)
  participant C as Node C
  participant D as Node D
  Cl->>B: get cart:42
  B->>C: read
  B->>D: read
  C-->>B: cart version 7 with its clock
  Note over B: B's own copy and C's answer make R = 2, so B stops waiting
  B-->>Cl: cart version 7 and its context
  D-->>B: cart version 6, too late to count
`} legend="The coordinator asks all N nodes and answers after R replies. The context is the clock information the client must send back with its next write." />

A read goes to the coordinator, which asks the same N nodes and stops waiting after R answers. It returns the newest version it saw, or every version if some are concurrent, together with a context. The context is the vector clocks of what the client saw. The client sends it back with its next write.

<GoDeeper title="Go deeper: why the context travels with the client">

The store does not remember who read what. It is leaderless and stateless between requests, so the only way to tell it "my write builds on what I read" is to hand the clock back. That is the context. Chapter 13.6 shows what goes wrong when a client forgets it.

If the R answers disagree, the coordinator compares the clocks. A version that another version covers is dropped. Versions that neither covers are kept side by side, as siblings. The paper's own measurement of the shopping cart over 24 hours found that 99.94% of requests saw exactly one version [S45]. Siblings are rare, and still every client must be ready for them.

The coordinator can also repair what it sees. When one of the nodes it asked returned an older version, it can send the newer one back, as you saw in chapter 8.7. A quorum read by itself is not linearizable (module 11); the read repair that the ABD algorithm adds is what closes that gap [S52].

</GoDeeper>

## N, R and W are dials, not facts

<MermaidDiagram title="Three settings, three behaviours" chart={`flowchart TD
  D["Dials: N copies, W to write, R to read"] --> C["N 3, W 2, R 2: the common setting. A read overlaps the last write, and one node can be slow."]
  D --> F["W 1: always writable and fastest to write. A read can miss the newest write for a moment."]
  D --> R["R 1 and W 3: fast reads. One node down blocks every write."]
`} legend="Each setting moves risk to a different place. None removes it." />

Pick the dials for the job. The common setting is N = 3, W = 2, R = 2. Souq's cart wants writes that never fail, so it may lower W to 1 and accept that a read can miss the newest add for a moment. A store that reads far more than it writes can lower R instead. Each choice moves a risk. None removes one.

<GoDeeper title="Go deeper: the dials in a table">

For N = 3, each row below shows what a setting buys and what it costs. "Overlap" means R + W is more than N, so every read asks at least one node that has the latest finished write (chapter 12.3).

| W | R | Overlap | Writes survive | Reads survive | Main cost |
|---|---|---|---|---|---|
| 2 | 2 | yes | 1 node down | 1 node down | Two answers to wait for each time |
| 1 | 3 | yes | 2 nodes down | none down | Every read waits for all three |
| 3 | 1 | yes | none down | 2 nodes down | One slow or down node blocks every write |
| 1 | 1 | no | 2 nodes down | 2 nodes down | A read can miss the newest write |

The last row is what an always-writable cart can pick. Overlap is not the whole story, though. It is a promise about writes that finished. Even with overlap, two clients can write the same cart at once, and that case is the subject of the rest of the module. In challenge 12, part 1, you run these settings on a simulated network and count how many reads miss the write.

A sloppy quorum, covered in 13.3, goes further: it lets a write succeed on nodes outside the key's list, which breaks the overlap on purpose [S45].

</GoDeeper>

<GoDeeper title="In an interview">

Say: "Dynamo is leaderless. Each key lives on N nodes, found by walking a consistent-hash ring, and any of them can coordinate. A write returns after W acknowledgements and a read after R answers, and a read returns a context that the client sends back with its next write. I pick N = 3 and tune W and R for the job: W = 1 if the write must never fail, R + W more than N if reads must see the latest finished write."

A follow-up an interviewer may ask: "What happens if the coordinator dies after two of three copies are written?" A good answer: the client times out and cannot tell if the write happened. The two copies may be read later, so the client retries, and the write must be safe to repeat. Nothing is rolled back.

</GoDeeper>
