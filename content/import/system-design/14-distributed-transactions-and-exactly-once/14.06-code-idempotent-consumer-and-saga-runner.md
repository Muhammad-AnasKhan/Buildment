In chapters 14.3 to 14.5 you saw two small machines. The first is a consumer that can be handed the same message twice and still change the world once. The second is a saga runner that does a list of steps, and when one step fails, undoes the steps that already finished. Both are short. Both are easy to get slightly wrong, and a slightly wrong version passes every test that does not crash anything in the middle.

In this chapter you write both in plain JavaScript, against in-memory objects. By the end you have three tested pieces. `createDedupeStore(ttlMs, now)` remembers message ids for a limited time. `handleOnce(store, message, handler)` runs `handler` once per id. `runSaga(steps, ctx, options)` runs the steps and the compensations. In challenge 13 you will build the same shapes on PostgreSQL, so it pays to get the logic right here, where a failing test costs seconds.

## What the tests do to your code

A duplicate message and a failed step are both things that happen "in the middle", and a test that only calls your function once cannot see them. So the tests do the awkward things on purpose. They hand your consumer the same message id twice. They make a handler throw halfway. They move a fake clock past the expiry time. They make a compensation fail twice and then work. Each test tells you in words which rule you broke.

Your functions are not `async`. A real consumer talks to a database and a real saga calls other services, and both are asynchronous. The logic is the same, and the plain version keeps the tests exact. Do not add `async`, `await` or a timer. The tests also pass a clock in, so the expiry test never waits.

## The contract for each function

Fix what each function promises before you write it, including the awkward inputs.

**`createDedupeStore(ttlMs, now)`** returns an object with two methods. `now` is a function that returns the current time in milliseconds, and it defaults to `() => Date.now()`. A `ttlMs` that is not a number above 0 throws a `RangeError`. The method `put(id, result)` saves the result and the time it was saved. The method `get(id)` returns `{ found: true, result }` when the id was saved less than `ttlMs` milliseconds ago, and `{ found: false }` otherwise. An id saved exactly `ttlMs` ago is forgotten. A forgotten id is also deleted from the store, so the store does not grow for ever.

**`handleOnce(store, message, handler)`** takes a message with a string `id`. A message without a non-empty string `id` is a bug in the caller, so it throws a `TypeError`. If the store already knows the id, it does not call the handler, and it returns `{ status: "duplicate", result }` with the saved result. Otherwise it calls `handler(message)`, saves the handler's result under the id, and returns `{ status: "processed", result }`. If the handler throws, nothing is saved and the error goes up to the caller. That rule matters: a failed message must be able to come back and try again.

**`runSaga(steps, ctx, options)`** takes a list of steps. Each step is an object `{ name, action, compensate }`. `action(ctx)` does the work and throws if it fails. `compensate(ctx)` is optional and undoes the action. The runner calls the actions in order, passing the same `ctx` object to every one. If an action throws, the runner stops. It then calls the `compensate` of every earlier step that finished and has one, newest first. The step that failed is not compensated, because it did not finish.

A compensation can fail too. The runner tries each compensation up to `options.maxCompensationTries` times, default 3, then gives up on that one and moves on to the next. It never stops compensating because one compensation is stuck. The result always has the same shape: `{ status, completed, failedStep, error, compensated, stuck }`. `status` is `"completed"` when every action worked, `"compensated"` when a step failed and every compensation worked, and `"stuck"` when at least one compensation ran out of tries. `completed` lists the names of the steps whose action worked, in order. `failedStep` and `error` (the error's message) are `null` when nothing failed. `compensated` and `stuck` list step names in the order they were handled.

A list of steps that is not an array, a step without a string `name` or an `action` function, or a `maxCompensationTries` that is not a whole number of 1 or more is a bug in the caller. The runner throws a `TypeError` for the first two and a `RangeError` for the last.

## A worked example: a workshop booking

Here is the saga runner applied by hand to a case that is not in the tests. A community centre books a workshop in three steps: hold a room, charge a fee, send the confirmation. Hold and charge have compensations, and the confirmation does not, because a sent message cannot be unsent. That is why it comes last.

Take the steps one at a time. The first subgoal is the loop over the actions, in order. The hold works, so `completed` is `["hold room"]`. The charge throws, so the loop stops and `failedStep` is `"charge fee"`. The second subgoal is the walk backwards. Only the hold finished, so the runner calls its `compensate`, and `compensated` is `["hold room"]`. The status is `"compensated"`. The confirmation was never started, so nothing is sent.

Now change one thing: the room release also fails, three times in a row. With the default of 3 tries, the runner gives up on it, and the result is `status: "stuck"` with `stuck: ["hold room"]`. A person must now release that room by hand. The runner reports the problem honestly instead of hiding it, and in challenge 13 that report becomes a row that an operator can see.

## Five ways this goes wrong

**Saving the id before the handler runs.** If you call `put` first and the handler then throws, the message is marked done but nothing happened. The redelivered message is skipped, and the work is lost for good. Save the id only after the handler has returned. The tests check this by letting a handler throw once and delivering the same id again.

**Checking the id but never saving it.** A `handleOnce` that reads the store and calls the handler, but forgets to `put`, passes the first-message tests. Only the duplicate test shows it, because the handler runs twice.

**Compensating in the wrong order.** The compensations must run newest first. Releasing stock before refunding the card can leave a window where stock is free and a refund has not happened yet. More simply, a later step often depends on an earlier one, so you undo in the reverse order that you did. The tests record the order and compare it.

**Compensating the step that failed.** The failed step threw, so it did not finish. Refunding a charge that never happened is a bug of its own, and some compensations throw when there is nothing to undo. The runner calls compensations only for steps in `completed`.

**Stopping at the first stuck compensation.** If the refund is stuck, the stock still has to be released. A runner that gives up on everything leaves half of the mess behind. The tests make one compensation fail for ever and check that the others still ran.

One more habit helps. When a test fails, read its message first. Each one names the input, the expected answer and what your code returned, and several name the usual mistake.

  function createDedupeStore(ttlMs, now = () => Date.now()) {
    if (typeof ttlMs !== "number" || !Number.isFinite(ttlMs) || ttlMs <= 0) {
      throw new RangeError("ttlMs must be a number above 0, got " + ttlMs);
    }
    const seen = new Map();
    return {
      get(id) {
        const entry = seen.get(id);
        if (!entry) return { found: false };
        if (now() - entry.savedAt >= ttlMs) {
          seen.delete(id);
          return { found: false };
        }
        return { found: true, result: entry.result };
      },
      put(id, result) {
        seen.set(id, { result, savedAt: now() });
      },
    };
  }

  function handleOnce(store, message, handler) {
    if (!message || typeof message.id !== "string" || message.id === "") {
      throw new TypeError("message.id must be a non-empty string");
    }
    const known = store.get(message.id);
    if (known.found) return { status: "duplicate", result: known.result };
    const result = handler(message);
    store.put(message.id, result);
    return { status: "processed", result };
  }

  function runSaga(steps, ctx = {}, options = {}) {
    const { maxCompensationTries = 3 } = options;
    if (!Array.isArray(steps) || steps.some((s) => !s || typeof s.name !== "string" || typeof s.action !== "function")) {
      throw new TypeError("steps must be an array of { name, action, compensate? }");
    }
    if (!Number.isInteger(maxCompensationTries) || maxCompensationTries < 1) {
      throw new RangeError("maxCompensationTries must be a whole number of 1 or more");
    }
    const finished = [];
    for (const step of steps) {
      try {
        step.action(ctx);
        finished.push(step);
      } catch (error) {
        const compensated = [];
        const stuck = [];
        for (let i = finished.length - 1; i >= 0; i--) {
          const done = finished[i];
          if (typeof done.compensate !== "function") continue;
          let worked = false;
          for (let attempt = 1; attempt <= maxCompensationTries && !worked; attempt++) {
            try {
              done.compensate(ctx);
              worked = true;
            } catch (ignored) {
              // try again, up to the limit
            }
          }
          (worked ? compensated : stuck).push(done.name);
        }
        return {
          status: stuck.length > 0 ? "stuck" : "compensated",
          completed: finished.map((s) => s.name),
          failedStep: step.name,
          error: error && error.message ? error.message : String(error),
          compensated,
          stuck,
        };
      }
    }
    return { status: "completed", completed: finished.map((s) => s.name), failedStep: null, error: null, compensated: [], stuck: [] };
  }

## What this unlocks

In challenge 13, the next chapter, the dedupe store becomes a table. The id goes into `processed_messages` in the same database transaction as the effect, so there is no gap between "did it" and "wrote it down". The saga runner keeps its shape too, but its state moves into a table of saga rows, so a crash in the middle can be picked up again. The design habit to keep is the order of the steps: do the work, then record that it is done, and make both safe to repeat.
