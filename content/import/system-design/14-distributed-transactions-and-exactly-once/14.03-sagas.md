Layla's order touches Stock, Payments and Courier: three services, three databases. A saga does it as a chain of small local transactions. When a step fails, the saga runs new steps that undo the finished ones.

## Three small commits, one after another

<InteractiveCanvas slug="sysdesign-m14-saga-steps" />

Stock reserves one bag and commits. Then Payments charges 18 and commits. Then Courier books a van and commits. Each step is a normal transaction in one database. No lock is held across all three, so no service waits for another to finish.

<GoDeeper title="Go deeper: where sagas come from">

The idea is older than microservices. Garcia-Molina and Salem described it in 1987 for long-lived transactions in one database: a long job split into a sequence of shorter transactions, so that locks are not held for hours [S78]. Their rule is simple. Either all the transactions in the sequence complete, or compensating transactions are run to amend a partial execution.

Today the word means the same thing across services. Richardson describes a saga as a reliably coordinated sequence of local transactions, and notes that the pattern gives up the isolation of ACID: other users can see the middle (see beat 5). {/* source needed: Richardson, microservices.io saga pattern page (https://microservices.io/patterns/data/saga.html, read 2026-10-24) is not yet in the dossier. */}

A saga trades one big all-or-nothing commit for many small commits and a plan for failure. It is a good fit when the steps live in different services and each can be undone by a business action. It is a poor fit when you need other users never to see the middle of the work.

</GoDeeper>

## Fail a step and watch the undo

<InteractiveCanvas slug="sysdesign-m14-saga-fail" />

Tap the step that fails. The saga stops, then runs the undo steps of the finished ones, newest first. Fail step 1 and nothing needs undoing. Fail step 3 and two undo steps run. Step 4, the receipt email, has no undo, so it sits last, and if it fails the saga retries it.

<GoDeeper title="Go deeper: compensating transactions, one by one">

A <GlossaryTerm term="compensating transaction" definition="A new step that cancels the effect of an earlier committed step, such as a refund for a charge. It does not erase the first step; it adds a second one that cancels it." /> is not a database rollback. The charge happened. Layla's bank may show a charge of 18 and then a refund of 18. The compensation is a second action that brings the business state back, and both actions stay on record.

Each step in the playable has a matching undo: reserve stock has release, charge card has refund, book courier has cancel booking. Four rules make compensations work.

First, run them newest first. Cancel the courier before you refund the card, because later steps often depend on earlier ones. Second, make every action and every compensation safe to run twice, with an idempotency key like the one in 6.4. A crash can happen after a step commits but before the saga records it, and then the step runs again. Third, never give up on a compensation. If the refund fails because the payment provider is down, retry it until it works, and alert a person if it takes too long. Fourth, put steps that cannot be undone last. An email cannot be unsent. If it comes first and the payment later fails, Layla has a receipt for an order that never happened.

The last step is sometimes called the point of no return. Once it commits, the saga is done and will not undo anything. Steps before it must be undoable; the step itself must be retried until it works.

</GoDeeper>

## Orchestration: one conductor

<InteractiveCanvas slug="sysdesign-m14-saga-orchestra" />

An orchestrator is a service that holds the plan. It tells Stock to reserve, waits for done, tells Payments to charge, waits, and so on. If a step fails, it knows what to undo. The whole flow is in one place, which makes it easy to read, test and change.

<GoDeeper title="Go deeper: the cost of one conductor">

The orchestrator must remember where it is. If it crashes after Payments says done and before it calls Courier, a new copy has to find out which step comes next. So the saga's state is stored: a row per order that says which step is next and whether the saga is running, compensating, completed or compensated. You build exactly this table in challenge 13.

The orchestrator also becomes a place that many teams depend on. It must be available, and it knows about every service in the flow. That coupling is the price of seeing the whole plan in one file. Managed workflow services, for example AWS Step Functions, offer this role as a service. {/* source needed: AWS Step Functions saga guidance page not yet verified (dossier lists it as UNVERIFIED). */}

</GoDeeper>

## Choreography: no conductor

<InteractiveCanvas slug="sysdesign-m14-saga-chorus" />

In choreography, services talk through an event bus. Stock publishes "reserved". Payments hears it, charges, and publishes "charged". Courier hears that and books. Each service knows only which event it reacts to and which event it publishes. No service holds the whole plan.

<GoDeeper title="Go deeper: when each style is the better fit">

Choreography needs no central component, so there is no orchestrator to keep alive, and services stay loosely coupled. Its cost is visibility. To answer "what happens when a card is declined?" you must read the code of every service, because the flow exists only as a chain of reactions. Adding a step means changing a service that listens to another. Cycles are easy to create by accident: A reacts to B, which reacts to A.

A rough rule: choreography suits a short flow of two or three services with simple failure paths. Orchestration suits a longer flow, a flow with many failure branches, or one where a person must be able to see in a single place how far an order got.

Both styles hit the same two traps. Events travel over a broker that delivers at least once (14.4 and 14.5), so every step must handle a repeated message. And a crash between "my transaction committed" and "I published my event" loses the next step. The outbox pattern of 14.4 closes that gap.

</GoDeeper>

## Others can see the half-done order

<InteractiveCanvas slug="sysdesign-m14-saga-not-isolated" />

Layla's saga holds the last bag. Omar asks to buy and is told sold out. Then her card is declined and the saga releases the bag. For a moment, Omar saw a state that was later undone. A saga has no isolation: each step is visible as soon as it commits.

<GoDeeper title="Go deeper: living without isolation">

Chapter 7.4 listed what isolation levels prevent: dirty reads, lost updates, write skew. A saga gives up even the first of these. Another request can read the stock count after step 1 and before step 3, a state that may never become final. Richardson calls this the lack of isolation and notes that teams use countermeasures to cope. {/* source needed: countermeasures wording from the microservices.io saga page; see the note in beat 1. */}

Practical countermeasures are simple. Mark the order as pending, and show held stock as "reserved for someone, may return". Do not give Omar a hard "sold out"; give him "none available now, check again". Take the risky step first. If the card is likely to be declined, charge before you reserve, so you hold stock for a shorter time. Re-read before you act: a step can check that the data is still what it expected.

If your business cannot accept any of these, a saga is the wrong tool for that part of the flow. Keep that part inside one database, with an ordinary transaction.

</GoDeeper>

## What every compensation must satisfy

<MermaidDiagram title="Designing one saga step" chart={`flowchart TD
  S["A step in the saga"] --> Q{"Can it be undone by a business action?"}
  Q -->|"yes"| C["Write a compensation. Make both the action and the compensation safe to run twice"]
  Q -->|"no"| L["Put it last, and retry it until it works"]
  C --> R["If the compensation fails, retry it, and alert a person if it stays stuck"]
`} legend="Each step needs a decision: undoable, or last." />

For each step, ask one question: can a business action undo it? If yes, write the undo, and make both safe to run twice. If no, move the step to the end and retry it. A compensation that fails is retried, not dropped. If it stays stuck, a person must be told.

<GoDeeper title="Go deeper: the saga runner you will write">

In chapter 14.6 you write `runSaga(steps, ctx, options)`. It runs each action in order. When one throws, it calls the compensations of the finished steps, newest first, and tries each up to a set number of times. A compensation that never works lands in a `stuck` list, and the runner still runs the others. A stuck item is a real operations event: a charge that could not be refunded needs a person.

In challenge 13 the same rules run on PostgreSQL. The saga's progress is a row. Each action is a transaction that is safe to run twice. A worker that crashes is restarted, and it carries on from the row. You then check, with SQL, that no order ended half done.

</GoDeeper>

```quiz
  - "Refund the card, then release the stock"
  - "Release the stock only"
  - "Cancel the courier, refund, then release"
  - "None: the failed step undoes itself"
correct: 1
explanations:
  - "There is no charge to refund. Step 2 failed, so the card was never charged. Only finished steps are undone."
  - "Right. Only step 1 finished. The saga runs its undo, release stock, and stops. The failed step and the later steps never ran."
  - "The courier was never booked, because step 3 had not started. Undoing a step that did not run can even throw an error."
  - "The failed step did not commit, so it has nothing to undo, but step 1 did commit. Someone must release the stock."
```
