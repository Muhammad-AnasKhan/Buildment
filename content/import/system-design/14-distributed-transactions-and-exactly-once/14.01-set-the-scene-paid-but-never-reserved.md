Zaytoun Market is a made-up online grocery. Layla pays for her basket. Checkout calls two other services, one after the other: Payments, then Stock. Look at the picture and ask yourself one everyday question: what would you check first, and why?

## She paid, but nothing was reserved

<InteractiveCanvas slug="sysdesign-m14-paid-not-reserved" />

Checkout asks Payments to charge Layla 18, and Payments does. Then checkout crashes. It never tells Stock to hold her items. Her card is charged and no bag is held for her. No line of code is wrong. Two services were changed with two separate calls, and the crash fell in the gap between them.

<GoDeeper title="Go deeper: why no order of the two calls is safe">

Try the calls the other way round. Reserve the stock first, then charge. Now a crash in the gap leaves the stock held and no money taken. That is a smaller harm, but it is still a half-done order: the bag is locked away for a customer who never paid, and nobody is told.

Retrying does not fix it by itself. If checkout restarts and runs the whole order again, it may charge Layla a second time. In chapter 6.4 you made a retry safe with an idempotency key, which stops the second charge. That fixes one half of the problem. It does not tell checkout which steps already ran.

In chapter 7.4 a transaction fixed the same shape inside one database: `BEGIN`, two changes, `COMMIT`, and a crash in the middle rolls both back. That tool needs one database. Here Stock and Payments are two services with two databases, so no single `BEGIN` and `COMMIT` covers both. The rest of this module is about what to do instead.

Zaytoun Market, Layla and the 18 are made up for this course. The price is a course number.

</GoDeeper>

## Four tools, one problem each

<MermaidDiagram title="The path through module 14" chart={`flowchart LR

  T --> S["14.3 Sagas: undo finished steps"]
  S --> O["14.4 Outbox: never lose an event"]
  O --> I["14.5 Idempotent consumers: copies are harmless"]

Two-phase commit makes two databases agree, but it can block. A saga lets each step commit and runs undo steps if a later one fails. The outbox stops an event from being lost between a database and a message broker. An idempotent consumer makes a repeated message harmless.

<GoDeeper title="Go deeper: what you already have, and what this module adds">

You already hold three tools. An idempotency key (6.4) makes a repeated request safe. A transaction (7.4) makes several changes inside one database all-or-nothing. Compare-and-set (7.5) refuses a write based on stale data. All three work at one place: one API, or one database.

This module is about the gaps between places. 14.2 shows the classic answer, two-phase commit, and where it fails. 14.3 shows the answer most microservice teams use, the saga. 14.4 and 14.5 deal with messages: how to publish one without losing it, and how to receive one that might arrive twice. The common claim "exactly once" turns out to be at least once plus a consumer that can cope with copies.

Then you write code. In 14.6 you build a dedupe store and a saga runner with graded tests. In challenge 13 you run an order saga on PostgreSQL, crash it on purpose, and check that no order is left half done.

</GoDeeper>
