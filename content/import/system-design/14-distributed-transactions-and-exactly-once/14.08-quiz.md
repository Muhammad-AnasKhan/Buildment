```quiz
type: mcq
question: "A checkout uses two-phase commit across an Orders DB and a Payments DB. The coordinator process is killed after both databases voted yes. Other customers try to buy the same item. What do they see?"
options:
  - "Orders fail at once, because the item counts as sold"
  - "Orders run on a spare copy and are merged later"
  - "Orders hang, because the prepared rows stay locked"
  - "Orders succeed, because prepared rows are unlocked"
correct: 2
explanations:
  - "No one has decided yet. The item is neither sold nor free, and nothing answers 'sold' at once; the rows are simply held."
  - "Two-phase commit has no spare copy to merge into. The databases keep the rows locked until the decision arrives."
  - "Right. A prepared database promised to wait for the decision and holds its locks. Other orders for the same rows queue until the coordinator returns."
  - "Prepared rows keep their locks. That is what stops anyone from seeing a half-done order, and also what makes the others wait."
```

```quiz
type: mcq
question: "A saga has four steps: reserve stock (undo: release), charge card (undo: refund), book courier (undo: cancel) and send an SMS (no undo). The courier booking fails. Which undo steps run, in which order?"
options:
  - "Refund the card, then release the stock"
  - "Release the stock, then refund the card"
  - "Cancel the courier, refund, then release"
  - "Refund, release, then unsend the SMS"
correct: 0
explanations:
  - "Right. Steps 1 and 2 finished, so their undo steps run newest first: refund, then release. The failed step and the SMS never ran."
  - "The order is reversed. Undo steps run newest first, because a later step may depend on an earlier one."
  - "The courier booking failed, so there is nothing to cancel. Only finished steps are undone."
  - "The SMS is step 4 and never ran, since step 3 failed first. An SMS also cannot be unsent."
```

```quiz
type: mcq
question: "Which of these designs can still lose an order event if the app crashes at the worst moment?"
options:
  - "Save the order and the outbox row in one transaction"
  - "Save an outbox row; a relay publishes and marks it sent"
  - "A change data capture connector reads the database log"
  - "Save the order, then publish the event in the code"
correct: 3
explanations:
  - "Both rows commit together or not at all. A crash cannot leave an order without its event row."
  - "The row is already saved, so a crash only delays the publish or repeats it. The event is not lost."
  - "The log records every committed change, so the connector finds the row after a restart. Nothing is skipped."
  - "Right. Two separate writes have a gap between them. A crash in the gap leaves a saved order and an event that is never sent."
```

```quiz
type: mcq
question: "A wallet service gets 'credit 18, id m-9' twice. Which consumer ends with exactly one credit even if it crashes at any moment?"
options:
  - "Look up m-9 in a cache, add 18, then store m-9"
  - "One transaction: insert m-9 as a key, add 18 if new"
  - "Add 18, then ask the broker to delete the message"
  - "Add 18 unless the same message came in the last minute"
correct: 1
explanations:
  - "A crash after the add and before the cache write leaves the id unsaved. The copy then looks new and credits again."
  - "Right. The id and the credit commit together or not at all. A copy finds the key and adds nothing, and a crash rolls both back."
  - "The delete can fail or be lost, just like the ack. The message may come back and add 18 again."
  - "A time guess is not an id check. A copy that arrives after a minute is credited again, and two real credits in a minute are dropped."
```

```quiz
type: mcq
question: "A vendor says its pipeline is exactly-once from Kafka to your PostgreSQL table. What is the best reply?"
options:
  - "Great: no dedupe is needed anywhere in the pipeline"
  - "Exactly-once cannot exist, so ignore the claim"
  - "Ask where it ends; make the table write idempotent"
  - "Turn off retries so no message can repeat"
correct: 2
explanations:
  - "Kafka's exactly-once covers work inside Kafka. The write into PostgreSQL is outside it, and a retry there can still repeat."
  - "Exactly one effect can be built. It takes at-least-once delivery plus an idempotent write, so the claim is worth checking, not ignoring."
  - "Right. Find the edge of the guarantee, and give the last step an id check or a natural idempotent write, so a repeat changes nothing."
  - "Without retries, a failure loses the message. That trades a repeat for a loss, which is usually worse."
```
