## How the experiment works

An order is saved in PostgreSQL. Something else has to hear about it, or has to be changed because of it: a message broker, a stock count, a payment. Each part of this challenge makes that second thing fail in a different way, and each fix closes one gap. The shared code stays small, so the differences you see come from the fix and from nothing else.

Four design choices keep the numbers honest.

**A crash is an exception.** You cannot really kill a process halfway through a function inside a test. So `toolkit/faults.js` gives you a `Crash` error and a way to throw it at a named point, such as `after-order-saved`. Code that catches a `Crash` must act as if nothing after that point ran, exactly like a process that died there. What survives is only what the database had committed. This is the same idea as the rival buyer in 7.7: do not hope for bad timing, put a hook at the exact point.

**The broker is a tiny object with at-least-once delivery.** `toolkit/broker.js` holds a queue. A message that is received but never acknowledged goes back on the queue later, like an SQS message when its visibility timeout runs out. You publish, receive and ack; nothing is persisted, because the point is the delivery rule, not the storage.

**The random numbers are seeded.** The chance of a crash comes from the seeded generator of challenge 1, so a run repeats exactly. Each strategy in a table sees the same crash luck, so the rows are fair to compare.

**There are two kinds of check.** Parts 1 and 2 count: how many events were lost, how many were repeated, how many bags were reserved beyond the orders. Part 3 audits: after hundreds of orders and dozens of crashes, SQL queries ask the database whether any order is half done. A correct system scores zero on every audit line.

One warning about speed. The outputs in this chapter come from a Windows laptop with Docker Desktop, where one database round trip took about 11 ms. Part 3 makes thousands of them, so it ran for a few minutes. Your machine may be faster or slower. Start the scripts, then read on while they run.

## Step 1: the toolkit and the tables

Add this function to the end of `toolkit/pg.js`. It runs your code between `BEGIN` and `COMMIT`, and undoes everything if the code throws. You wrote the same helper in chapter 7.4:

```js
// Run work(db) inside BEGIN ... COMMIT. Any error rolls everything back.
export async function withTransaction(pool, work) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const result = await work(client);
    await client.query("COMMIT");
    return result;
  } catch (error) {
    await client.query("ROLLBACK");
    throw error;
  } finally {
    client.release();
  }
}
```

Next, `toolkit/faults.js`. A `faultPlan` throws a `Crash` at a named point with the chance you give it. `crashOnce` throws exactly once, for tests. `noFaults` never throws.

```js
// toolkit/faults.js: make a program "crash" at a named point, on purpose.
// A Crash is an error that stands for "the process died right here".
// Code that catches a Crash must act as if nothing after that point ran.
export class Crash extends Error {
  constructor(point) {
    super(`crashed at ${point}`);
    this.name = "Crash";
    this.point = point;
  }
}

// Crash at a point with a chance, using a seeded random function so a run repeats.
// chances: { "after-order-saved": 0.1, ... }. counts says how often each point fired.
export function faultPlan(random, chances = {}) {
  const counts = {};
  return {
    counts,
    maybeCrash(point) {
      if (random() < (chances[point] ?? 0)) {
        counts[point] = (counts[point] ?? 0) + 1;
        throw new Crash(point);
      }
    },
  };
}

// For tests: crash exactly once, the first time the code reaches this point.
export function crashOnce(point) {
  let fired = false;
  return {
    counts: {},
    maybeCrash(here) {
      if (here === point && !fired) {
        fired = true;
        throw new Crash(here);
      }
    },
  };
}

// Never crash.
export const noFaults = { counts: {}, maybeCrash() {} };
```

Then `toolkit/broker.js`. Read `redeliverUnacked`: it is the only place where a message comes back, and it is the whole reason for this module.

```js
// toolkit/broker.js: a tiny in-memory message broker with at-least-once delivery.
// A message that is received but never acknowledged comes back later, the way
// a message returns to an SQS queue when its visibility timeout runs out.
export class Broker {
  constructor() {
    this.queue = [];
    this.inFlight = new Map(); // receipt -> message
    this.nextReceipt = 1;
    this.published = []; // every publish call, in order, for counting
  }

  publish(message) {
    const copy = structuredClone(message);
    this.published.push(copy);
    this.queue.push(copy);
  }

  // Hand out the next message with a receipt. The consumer must ack it.
  receive() {
    const message = this.queue.shift();
    if (!message) return null;
    const receipt = this.nextReceipt++;
    this.inFlight.set(receipt, message);
    return { receipt, message };
  }

  ack(receipt) {
    this.inFlight.delete(receipt);
  }

  // Put every unacknowledged message back on the queue: the timeout ran out.
  redeliverUnacked() {
    for (const message of this.inFlight.values()) this.queue.push(message);
    const count = this.inFlight.size;
    this.inFlight.clear();
    return count;
  }

  get pending() {
    return this.queue.length + this.inFlight.size;
  }
}
```

```js
// The tables of challenge 13. resetSchema throws everything away and starts clean,

export async function resetSchema(pool, { stock = 1000 } = {}) {
```

## Step 2: part 1, the outbox

You will save 500 orders in two ways. The first writes the order and then publishes the event, like the dual write of 14.4. The second writes the order and an outbox row in one transaction, and lets a relay publish the row later. In both runs the app crashes after saving an order with a 10% chance. In the second run the relay also crashes, with a 2% chance after each row it publishes. Create `challenges/challenge-13-order-saga/orders.js`:

```js
// Part 1: three ways to save an order and tell the rest of the system about it.
import { withTransaction } from "../../toolkit/pg.js";

const INSERT_ORDER = "INSERT INTO orders (id, customer, total) VALUES ($1, $2, $3)";
const eventFor = (order) => ({ eventId: `order-placed-${order.id}`, type: "OrderPlaced", orderId: order.id, total: order.total });

// The wrong way: two writes to two systems, and nothing joins them.
export async function placeOrderDualWrite(pool, broker, order, faults) {
  await pool.query(INSERT_ORDER, [order.id, order.customer, order.total]);
  faults.maybeCrash("after-order-saved"); // the app dies here: the order exists, the event never will
  broker.publish(eventFor(order));
}

// The outbox way: the order and its event are one commit. Nothing is published here.
export async function placeOrderOutbox(pool, order, faults) {
  await withTransaction(pool, async (db) => {
    await db.query(INSERT_ORDER, [order.id, order.customer, order.total]);
    faults.maybeCrash("between-order-and-outbox"); // a crash here rolls back the order too
    const event = eventFor(order);
    await db.query("INSERT INTO outbox (event_id, payload) VALUES ($1, $2)", [event.eventId, JSON.stringify(event)]);
  });
  faults.maybeCrash("after-order-saved"); // the same crash is now harmless: the event is saved
}

// The relay: publish the rows nobody has sent yet, then mark them sent.
// If it dies after publishing but before the commit, the marks are rolled back
// and the next run publishes those rows again: at least once, not exactly once.
export async function relayBatch(pool, broker, faults, limit = 20) {
  return withTransaction(pool, async (db) => {
    const { rows } = await db.query(
      "SELECT id, payload FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED",
      [limit]
    );
    for (const row of rows) {
      broker.publish(row.payload);
      faults.maybeCrash("relay-after-publish");
      await db.query("UPDATE outbox SET sent_at = now() WHERE id = $1", [row.id]);
    }
    return rows.length;
  });
}

// Count what reached the broker. Missing: orders with no event. Duplicates: extra copies.
export function countEvents(broker, orders) {
  const seen = new Map();
  for (const m of broker.published) seen.set(m.orderId, (seen.get(m.orderId) ?? 0) + 1);
  const missing = orders.filter((o) => !seen.has(o.id)).length;
  const duplicates = [...seen.values()].reduce((sum, n) => sum + (n - 1), 0);
  return { published: broker.published.length, missing, duplicates };
}
```

Read `relayBatch` slowly. It locks a batch of unsent rows with `FOR UPDATE SKIP LOCKED`, publishes each row, and marks it sent, all in one transaction. If a `Crash` is thrown after some rows were published, the transaction rolls back, the marks vanish, and the next run publishes those rows again. The code does not hide this. It is the at-least-once rule of 14.4 in twelve lines.

Now the script, `part-1-outbox/outbox.js`. It runs both approaches on the same 500 orders and counts, with `countEvents`, how many orders have no event (missing) and how many extra copies were published (duplicates):

```js
// Part 1: save 500 orders while the app and the relay crash now and then.
// Compare a dual write with an outbox, and count missing and duplicate events.
import { writeFileSync } from "node:fs";
import { makePool, waitForDb } from "../../../toolkit/pg.js";
import { seededRandom } from "../../../toolkit/stats.js";
import { Broker } from "../../../toolkit/broker.js";
import { Crash, faultPlan } from "../../../toolkit/faults.js";
import { barChart } from "../../../toolkit/chart.js";
import { resetSchema } from "../schema.js";
import { countEvents, placeOrderDualWrite, placeOrderOutbox, relayBatch } from "../orders.js";

const ORDERS = 500;
const APP_CRASH = 0.1; // chance the app dies right after it saves an order
const RELAY_CRASH = 0.02; // chance the relay dies right after it publishes one row

const pool = makePool(10);
await waitForDb(pool);
const orders = Array.from({ length: ORDERS }, (_, i) => ({ id: `o-${i + 1}`, customer: `c-${i % 40}`, total: 18 }));
const results = [];

// Run 1: the dual write.
{
  await resetSchema(pool);
  const broker = new Broker();
  const faults = faultPlan(seededRandom(11), { "after-order-saved": APP_CRASH });
  for (const order of orders) {
    try {
      await placeOrderDualWrite(pool, broker, order, faults);
    } catch (error) {
      if (!(error instanceof Crash)) throw error;
    }
  }
  results.push({ name: "dual write", appCrashes: faults.counts["after-order-saved"] ?? 0, relayCrashes: 0, ...countEvents(broker, orders) });
}

// Run 2: the outbox, with a relay that also crashes.
{
  await resetSchema(pool);
  const broker = new Broker();
  const faults = faultPlan(seededRandom(11), { "after-order-saved": APP_CRASH, "relay-after-publish": RELAY_CRASH });
  for (const order of orders) {
    try {
      await placeOrderOutbox(pool, order, faults);
    } catch (error) {
      if (!(error instanceof Crash)) throw error;
    }
  }
  // The relay runs until the outbox is empty. A crash only costs it a retry.
  while (true) {
    try {
      if ((await relayBatch(pool, broker, faults)) === 0) break;
    } catch (error) {
      if (!(error instanceof Crash)) throw error;
    }
  }
  const { rows: [{ unsent }] } = await pool.query("SELECT count(*)::int AS unsent FROM outbox WHERE sent_at IS NULL");
  console.log(`outbox rows still unsent after the relay finished: ${unsent}`);
  results.push({ name: "outbox + relay", appCrashes: faults.counts["after-order-saved"] ?? 0, relayCrashes: faults.counts["relay-after-publish"] ?? 0, ...countEvents(broker, orders) });
}
await pool.end();

console.log(`\n${ORDERS} orders; the app crashes after saving with chance ${APP_CRASH}, the relay with chance ${RELAY_CRASH} per row\n`);
console.log("approach         app crashes  relay crashes  published  missing  duplicates");
for (const r of results) {
  console.log(
    `${r.name.padEnd(16)} ${String(r.appCrashes).padStart(11)}  ${String(r.relayCrashes).padStart(13)}  ` +
    `${String(r.published).padStart(9)}  ${String(r.missing).padStart(7)}  ${String(r.duplicates).padStart(10)}`
  );
}

writeFileSync(new URL("./chart.svg", import.meta.url), barChart({
  title: "Wrong events out of 500 orders",
  yLabel: "events",
  bars: [
    { label: "dual: missing", value: results[0].missing, color: "#dc2626" },
    { label: "outbox: missing", value: results[1].missing, color: "#dc2626" },
    { label: "dual: duplicates", value: results[0].duplicates, color: "#d97706" },
    { label: "outbox: duplicates", value: results[1].duplicates, color: "#d97706" },
  ],
}));
console.log("\nwrote chart.svg");
```

And its tests, `part-1-outbox/outbox.test.js`. Each test crashes at exactly one point, using `crashOnce`, so it fails every time the code is wrong and not one time in a hundred:

```js
import test, { after, beforeEach } from "node:test";
import assert from "node:assert/strict";
import { makePool, waitForDb } from "../../../toolkit/pg.js";
import { Broker } from "../../../toolkit/broker.js";
import { Crash, crashOnce, noFaults } from "../../../toolkit/faults.js";
import { resetSchema } from "../schema.js";
import { placeOrderDualWrite, placeOrderOutbox, relayBatch } from "../orders.js";

const pool = makePool(5);
const order = { id: "o-1", customer: "layla", total: 18 };
const count = async (sql) => (await pool.query(sql)).rows[0].n;

beforeEach(async () => {
  await waitForDb(pool);
  await resetSchema(pool);
});
after(() => pool.end());

test("dual write: a crash between the two writes loses the event for good", async () => {
  const broker = new Broker();
  await assert.rejects(placeOrderDualWrite(pool, broker, order, crashOnce("after-order-saved")), Crash);
  assert.equal(await count("SELECT count(*)::int AS n FROM orders"), 1, "the order was saved");
  assert.equal(broker.published.length, 0, "but no event was ever published");
});

test("outbox: the same crash loses nothing, because the event is saved with the order", async () => {
  const broker = new Broker();
  await assert.rejects(placeOrderOutbox(pool, order, crashOnce("after-order-saved")), Crash);
  assert.equal(await count("SELECT count(*)::int AS n FROM outbox WHERE sent_at IS NULL"), 1);
  await relayBatch(pool, broker, noFaults);
  assert.deepEqual(broker.published.map((m) => m.orderId), ["o-1"]);
});

test("outbox: an order and its outbox row are saved together or not at all", async () => {
  await assert.rejects(placeOrderOutbox(pool, order, crashOnce("between-order-and-outbox")), Crash);
  assert.equal(await count("SELECT count(*)::int AS n FROM orders"), 0, "the order was rolled back");
  assert.equal(await count("SELECT count(*)::int AS n FROM outbox"), 0, "and so was the outbox row");
});

test("relay: a crash after publishing means the event is published again later", async () => {
  const broker = new Broker();
  await placeOrderOutbox(pool, order, noFaults);
  await assert.rejects(relayBatch(pool, broker, crashOnce("relay-after-publish")), Crash);
  assert.equal(await count("SELECT count(*)::int AS n FROM outbox WHERE sent_at IS NULL"), 1, "the row was not marked sent");
  await relayBatch(pool, broker, noFaults);
  assert.equal(broker.published.length, 2, "the same event went out twice");
  assert.equal(broker.published[0].eventId, broker.published[1].eventId, "with the same event id, so a consumer can spot the copy");
  assert.equal(await count("SELECT count(*)::int AS n FROM outbox WHERE sent_at IS NULL"), 0);
});
```

## Step 3: part 2, the idempotent consumer

The repeats from part 1 have to be handled by whoever reads the events. This part gives a consumer 300 "reserve one bag of rice" messages and crashes it in two places: before the ack (a 20% chance, so the message comes back) and between the work and the record of the id (a 5% chance, only for the strategies that have such a gap). It then compares how many bags were reserved with the 300 that should have been. Create `challenges/challenge-13-order-saga/consumer.js`:

```js
// Part 2: three ways to handle an "OrderPlaced" message that reserves one bag of rice.
// The effect is a counter: stock.reserved goes up by the quantity. A counter is not
// idempotent, so a copy of the message that is handled twice reserves two bags.
import { withTransaction } from "../../toolkit/pg.js";
import { Crash } from "../../toolkit/faults.js";

const RESERVE = "UPDATE stock SET reserved = reserved + $1 WHERE sku = 'rice-5kg'";

// 1. No protection at all.
export async function handleNaive(pool, message) {
  await pool.query(RESERVE, [message.qty]);
  return "processed";
}

// 2. Look in the table, do the work, write the id down. Three separate statements.
// A crash between the work and the write leaves the work done and the id unrecorded.
export async function handleCheckThenRecord(pool, message, faults) {
  const seen = await pool.query("SELECT 1 FROM processed_messages WHERE message_id = $1", [message.eventId]);
  if (seen.rowCount > 0) return "duplicate";
  await pool.query(RESERVE, [message.qty]);
  faults.maybeCrash("between-work-and-record");
  await pool.query("INSERT INTO processed_messages (message_id) VALUES ($1)", [message.eventId]);
  return "processed";
}

// 3. Claim the id and do the work in one transaction. Both happen or neither does.
export async function handleOneTransaction(pool, message, faults) {
  return withTransaction(pool, async (db) => {
    const claimed = await db.query(
      "INSERT INTO processed_messages (message_id) VALUES ($1) ON CONFLICT DO NOTHING",
      [message.eventId]
    );
    if (claimed.rowCount === 0) return "duplicate"; // someone already handled this id
    await db.query(RESERVE, [message.qty]);
    faults.maybeCrash("between-work-and-record"); // rolls back the claim as well
    return "processed";
  });
}

// Deliver everything on the broker. A crash anywhere in the handler, or before the
// ack, leaves the message unacknowledged; the broker hands it out again next round.
export async function deliverAll(pool, broker, handler, faults) {
  let deliveries = 0;
  while (broker.pending > 0) {
    let got;
    while ((got = broker.receive())) {
      deliveries++;
      try {
        await handler(pool, got.message, faults);
        faults.maybeCrash("before-ack"); // the work is done, the ack is lost
        broker.ack(got.receipt);
      } catch (error) {
        if (!(error instanceof Crash)) throw error;
      }
    }
    broker.redeliverUnacked();
  }
  return deliveries;
}
```

Notice what makes the effect dangerous: `reserved = reserved + 1` is a counter. Adding 1 twice adds 2. That is the "atomic counter is not idempotent" case from 6.4. `handleCheckThenRecord` looks in the table, does the work, then writes the id, as three separate statements. `handleOneTransaction` claims the id and does the work in one transaction, so a crash in between undoes both.

## Step 4: part 3, the order saga

Now the whole order. Each order is a saga of three steps: reserve stock, charge the card, book a courier. The first two have a compensation: release the stock, refund the card. The saga's progress is a row in the `sagas` table. A worker that crashes is restarted, finds every saga that is not finished, and carries on from its row. Create `challenges/challenge-13-order-saga/saga.js`:

```js
// Part 3: an order saga that survives crashes.
// Three steps: reserve stock, charge the card, book a courier. Each step is one
// local transaction that is safe to run twice. The saga's progress lives in the
// `sagas` table, so a restarted worker can carry on from where the old one died.
import { withTransaction } from "../../toolkit/pg.js";
import { Crash } from "../../toolkit/faults.js";

// A business failure: the step ran and the answer was "no". Retrying will not help.
export class BusinessFailure extends Error {}

// Whether the card is declined or no courier is free is decided by the order id,
// so a step that runs twice after a crash gets the same answer both times.
// Tests can force an outcome with an id prefix: "good-", "decline-" or "nocourier-".
function bucket(text) {
  let h = 2166136261;
  for (const ch of text) {
    h ^= ch.charCodeAt(0);
    h = Math.imul(h, 16777619);
  }
  return (h >>> 0) % 100;
}
const cardDeclined = (id) => id.startsWith("decline-") || (!id.startsWith("good-") && bucket(`${id}:card`) < 10); // about 10%
const noCourier = (id) => id.startsWith("nocourier-") || (!id.startsWith("good-") && bucket(`${id}:courier`) < 15); // about 15%

const PRICE = 18;

export const STEPS = [
  {
    name: "reserve stock",
    async action(db, orderId) {
      // The primary key makes a repeat a no-op: the second insert changes no row.
      const claim = await db.query("INSERT INTO reservations (order_id, sku, qty) VALUES ($1, 'rice-5kg', 1) ON CONFLICT DO NOTHING", [orderId]);
      if (claim.rowCount === 0) return;
      const taken = await db.query("UPDATE stock SET reserved = reserved + 1 WHERE sku = 'rice-5kg' AND on_hand - reserved >= 1");
      if (taken.rowCount === 0) throw new BusinessFailure("out of stock"); // rolls the claim back too
    },
    async compensate(db, orderId) {
      const gone = await db.query("DELETE FROM reservations WHERE order_id = $1 RETURNING qty", [orderId]);
      if (gone.rowCount > 0) await db.query("UPDATE stock SET reserved = reserved - $1 WHERE sku = 'rice-5kg'", [gone.rows[0].qty]);
    },
  },
  {
    name: "charge card",
    async action(db, orderId) {
      if (cardDeclined(orderId)) throw new BusinessFailure("card declined");
      // The order id is the idempotency key: one payment row per order, ever.
      await db.query("INSERT INTO payments (order_id, amount, status) VALUES ($1, $2, 'charged') ON CONFLICT DO NOTHING", [orderId, PRICE]);
    },
    async compensate(db, orderId) {
      await db.query("UPDATE payments SET status = 'refunded' WHERE order_id = $1 AND status = 'charged'", [orderId]);
    },
  },
  {
    // The last step needs no compensation: nothing comes after it that could fail.
    name: "book courier",
    async action(db, orderId) {
      if (noCourier(orderId)) throw new BusinessFailure("no courier free");
      await db.query("INSERT INTO bookings (order_id) VALUES ($1) ON CONFLICT DO NOTHING", [orderId]);
    },
  },
];

export async function startSaga(pool, orderId) {
  await pool.query("INSERT INTO sagas (order_id, state) VALUES ($1, 'running') ON CONFLICT DO NOTHING", [orderId]);
}

// Drive one saga to the end. Every pass reads the saga row, does one thing, and
// writes the row. If a Crash is thrown, the row says exactly where to resume.
// With compensate: false a failed saga just stops, to show what that costs.
export async function advance(pool, orderId, faults, { compensate = true } = {}) {
  while (true) {
    const { rows: [saga] } = await pool.query("SELECT * FROM sagas WHERE order_id = $1", [orderId]);
    if (["completed", "compensated", "failed"].includes(saga.state)) return saga.state;

    if (saga.state === "running") {
      if (saga.next_step === STEPS.length) {
        await pool.query("UPDATE sagas SET state = 'completed' WHERE order_id = $1", [orderId]);
        continue;
      }
      const step = STEPS[saga.next_step];
      try {
        await withTransaction(pool, (db) => step.action(db, orderId));
      } catch (error) {
        if (!(error instanceof BusinessFailure)) throw error;
        const next = compensate ? "compensating" : "failed";
        await pool.query(
          "UPDATE sagas SET state = $2, failed_step = $3, error = $4, comp_index = $5 WHERE order_id = $1",
          [orderId, next, step.name, error.message, saga.next_step - 1]
        );
        continue;
      }
      faults.maybeCrash("after-action"); // the step is saved, the saga row does not know yet
      await pool.query("UPDATE sagas SET next_step = $2 WHERE order_id = $1", [orderId, saga.next_step + 1]);
      continue;
    }

    // state is "compensating": undo the finished steps, newest first.
    if (saga.comp_index < 0) {
      await pool.query("UPDATE sagas SET state = 'compensated' WHERE order_id = $1", [orderId]);
      continue;
    }
    const step = STEPS[saga.comp_index];
    if (step.compensate) await withTransaction(pool, (db) => step.compensate(db, orderId));
    faults.maybeCrash("after-compensation");
    await pool.query("UPDATE sagas SET comp_index = $2 WHERE order_id = $1", [orderId, saga.comp_index - 1]);
  }
}

// A restarted worker: find every saga that is not finished and carry it on.
export async function recover(pool, faults, options) {
  let rounds = 0;
  while (true) {
    const { rows } = await pool.query("SELECT order_id FROM sagas WHERE state IN ('running', 'compensating') ORDER BY order_id");
    if (rows.length === 0) return rounds;
    rounds++;
    for (const { order_id: orderId } of rows) {
      try {
        await advance(pool, orderId, faults, options);
      } catch (error) {
        if (!(error instanceof Crash)) throw error;
      }
    }
  }
}

// Place a batch of orders, one saga each, then recover until all are finished.
export async function runOrders(pool, orderIds, faults, options) {
  for (const orderId of orderIds) {
    await startSaga(pool, orderId);
    try {
      await advance(pool, orderId, faults, options);
    } catch (error) {
      if (!(error instanceof Crash)) throw error;
    }
  }
  return recover(pool, faults, options);
}

// Check the promises a saga makes. Every number here should be 0.
export async function audit(pool) {
  const one = async (sql) => (await pool.query(sql)).rows[0].n;
  return {
    unfinished: await one("SELECT count(*)::int AS n FROM sagas WHERE state IN ('running', 'compensating')"),
    completedMissingParts: await one(`
      SELECT count(*)::int AS n FROM sagas s WHERE s.state = 'completed' AND NOT (
        EXISTS (SELECT 1 FROM reservations r WHERE r.order_id = s.order_id)
        AND EXISTS (SELECT 1 FROM payments p WHERE p.order_id = s.order_id AND p.status = 'charged')
        AND EXISTS (SELECT 1 FROM bookings b WHERE b.order_id = s.order_id))`),
    undoneButHolding: await one(`
      SELECT count(*)::int AS n FROM sagas s WHERE s.state IN ('compensated', 'failed') AND (
        EXISTS (SELECT 1 FROM reservations r WHERE r.order_id = s.order_id)
        OR EXISTS (SELECT 1 FROM payments p WHERE p.order_id = s.order_id AND p.status = 'charged')
        OR EXISTS (SELECT 1 FROM bookings b WHERE b.order_id = s.order_id))`),
    stockCounterDrift: await one(`
      SELECT abs(reserved - (SELECT count(*) FROM reservations))::int AS n FROM stock WHERE sku = 'rice-5kg'`),
  };
}
```

Take it in three pieces. First, the steps. Each action runs in one transaction and is safe to run twice: `ON CONFLICT DO NOTHING` on a primary key means a second run changes no row. The order id is the idempotency key, as in 6.4. A step that says no throws a `BusinessFailure` ("card declined"), which is different from a `Crash`: a crash means the process died and the saga must resume; a business failure means the step ran and the answer was no, so the saga must undo.

Second, `advance`. Every pass through its loop reads the saga row, does one thing, and writes the row. A crash can fall between the action and the row update, shown in the code as `after-action`. Then the row still says "step 1 next", and a restarted worker runs step 1 again. That is fine, because step 1 is idempotent. It is the reason every action must be.

Third, `audit`. It asks the database four questions and each answer must be 0: how many sagas are not finished, how many completed orders lack a reservation, a charged payment or a booking, how many undone or failed orders still hold stock, money or a courier, and whether the stock counter agrees with the number of reservation rows.

The script, `part-3-order-saga/order-saga.js`, runs 150 orders three ways. Run A has no crashes. Run B crashes the worker with a 5% chance at every step boundary. Run C switches the compensations off, to show what that costs. The stock is 110 bags for 150 orders, so some orders find none.

```js

  console.log(`  audit: ${JSON.stringify(result.audit)}`);
  return result;
```

Run C is the reason compensations exist. With them switched off, the failed orders keep what they took: the audit shows 27 orders that still hold stock or a charge, and 83 orders completed instead of 110. The 27 stuck bags were never given to anyone else. Money was taken for orders that never shipped, and stock was lost for ever. Nothing crashed in run C. The saga simply stopped at the first failure.

## When something goes wrong

**"Postgres did not answer on port 5476."** The container is not running or not healthy yet. Run `docker compose ps` in the challenge folder. If another Postgres, such as the one from challenge 6, holds the port, stop it with `docker compose down` in its folder.

**`relation "orders" does not exist`.** A script or a test ran before `resetSchema`. Every script and every test file calls it first. If you ran two test files at the same time, one dropped the tables under the other; use `npm test`, which runs one file at a time.

**A test fails with `Missing expected rejection (Crash)`.** The code did not reach the crash point, so nothing crashed. In the saga crash test, a good order reaches `after-action` three times and an order that fails at the courier reaches it twice. Asking for a crash on a point that the code never reaches gives this message.

**`duplicate key value violates unique constraint`.** An action ran a second time and was not idempotent. In part 3 this is the sign that you removed a `ON CONFLICT DO NOTHING`. See the experiment below.

**Part 3 seems stuck.** It is slow, not stuck. Each order makes about twenty database calls. Check progress in another terminal with `docker compose exec postgres psql -U postgres -c "SELECT state, count(*) FROM sagas GROUP BY state"` and watch the counts grow.

**Your numbers differ from the ones above.** Part 1 and part 2 use seeded random numbers, but a small change in the order of your calls changes which call gets which random number. That is normal. Check the shape: missing is 0 for the outbox, extra is 0 for the one-transaction consumer, and every audit line is 0 in runs A and B.

## Break it on purpose

A test you have never seen fail is a test you cannot trust. Do three experiments, and undo each one before the next.

First, in `saga.js`, remove `ON CONFLICT DO NOTHING` from the `INSERT INTO payments` line. Run the part 3 tests. The crash test fails with `duplicate key value violates unique constraint "payments_pkey"`: after a crash the charge step ran a second time, and the database refused a second payment row for the same order. Without the unique key, the same replay would have charged the card twice and nothing would have failed. That quiet version is the dangerous one, which is why the key matters.

Second, in `advance`, change `if (step.compensate) await withTransaction(...)` to `if (false) await withTransaction(...)`. Four of the part 3 tests fail, because refunds and releases no longer happen. Undo it.

Third, in `placeOrderOutbox` in `orders.js`, change the first `db.query(INSERT_ORDER, ...)` to `pool.query(INSERT_ORDER, ...)`. The order is now saved outside the transaction. The test "an order and its outbox row are saved together or not at all" fails with the message "the order was rolled back", because the order stays behind when the crash undoes only the outbox insert. You have just rebuilt the dual write inside the outbox.
