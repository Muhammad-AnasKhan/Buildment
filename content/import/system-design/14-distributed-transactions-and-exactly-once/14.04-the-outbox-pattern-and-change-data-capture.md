Layla's order is saved in the Orders database. Other services must hear about it through a broker, a service that passes messages along. That is two writes again: one to the database, one to the broker. A crash between them is the problem of this chapter. The fix is smaller than you might expect, and it ends with a promise you can check: an event is never lost, but it may arrive twice.

## Save, crash, and no event

<InteractiveCanvas slug="sysdesign-m14-dual-write" />

The app saves order o-7, then crashes before it publishes the event. The database has the order. The broker has nothing, and nothing will ever send it later. Stock never hears that the order exists. A write to a database and a write to a broker are two separate systems, so one commit cannot cover both.

<GoDeeper title="Go deeper: the other order of the two writes fails too">

You might try to publish first and save second. Then a crash in the gap leaves the opposite problem: an event about an order that was never saved. Stock reserves items for an order that does not exist, and the saga from 14.3 has no order to attach its compensation to.

You might also wrap both calls in a try block and retry. A retry runs inside the same process, so it does not help when the process itself dies. And retrying the publish alone can publish the event twice. Richardson names this problem and its fix, the transactional outbox [S79]. The fix does not try to make the two systems commit together. It makes the broker write a separate job that can be repeated.

The same shape appears with a cache, a search index or an email service: any time one handler writes to a database and then to something else.

</GoDeeper>

## Crash between the two writes

<InteractiveCanvas slug="sysdesign-m14-outbox-crash" />

Pick how the order is saved, and where the app or the relay crashes. Count the events that reach the broker for one order. Save then publish loses it. Publish then save sends a ghost. The outbox always delivers it at least once: never zero, and sometimes twice.

<GoDeeper title="Go deeper: reading the result table">

For one order, the playable shows how many events reach the broker and whether the order exists.

| Approach | No crash | Crash between the two steps | Crash after publishing, before marking sent |
|---|---|---|---|
| Save, then publish | 1 event, order saved | 0 events, order saved | not applicable |
| Publish, then save | 1 event, order saved | 1 event, no order (a ghost) | not applicable |
| Outbox and relay | 1 event, order saved | 1 event, order saved (later) | 2 events, order saved |

The outbox row never goes missing: it was saved in the same transaction as the order. Its weak spot is the last column. The relay publishes first and marks the row sent second, so it has the same gap, just in a place where the damage is a repeat and not a loss. A repeat can be handled by the consumer (14.5). A lost event cannot be handled by anyone.

</GoDeeper>

## One commit, then publish later

<InteractiveCanvas slug="sysdesign-m14-outbox-relay" />

The app saves the order and an outbox row in one transaction. The relay, a small background worker, asks for rows nobody has sent, publishes each one to the broker, and marks it sent. If the app crashes after the commit, nothing is lost. The event row is already safe in the database.

<GoDeeper title="Go deeper: the outbox table and the relay in SQL">

The outbox is an ordinary table in the same database as the order. A minimal version has an event id that never repeats, the payload, and a `sent_at` column that is empty until the relay has published the row.

```sql
CREATE TABLE outbox (
  id bigserial PRIMARY KEY,
  event_id text NOT NULL UNIQUE,
  payload jsonb NOT NULL,
  sent_at timestamptz
);
```

The app writes both rows in one transaction: `BEGIN`, insert the order, insert the outbox row, `COMMIT`. The relay runs a loop. It reads a batch with `SELECT ... WHERE sent_at IS NULL ORDER BY id LIMIT 20 FOR UPDATE SKIP LOCKED`, publishes each row, sets `sent_at`, and commits. `FOR UPDATE` locks the rows so two relays do not publish the same row at once (7.5). `SKIP LOCKED` lets a second relay take other rows instead of waiting. The ordering by id keeps events in the order they were written.

Two jobs remain. Old rows with a `sent_at` must be deleted or archived, or the table grows for ever. And the relay needs a delay between polls when the table is empty. The poll interval is the delay your events add: with a 1 second poll, an event waits up to 1 second plus the time to publish.

In challenge 13, part 1, you build this and crash it on purpose.

</GoDeeper>

## The relay can publish twice

<InteractiveCanvas slug="sysdesign-m14-outbox-twice" />

The relay publishes e-7 and crashes before it marks the row sent. After the restart, e-7 still looks unsent, so it publishes again. The consumer receives e-7 twice. The outbox turned a lost event into a repeated one. Delivery is at least once, so every consumer must cope with copies.

<GoDeeper title="Go deeper: why not mark sent first?">

If the relay marked the row sent first and published second, a crash in the gap would lose the event again. That is the failure you came here to remove. Repeating is the safer error, because a repeat can be made harmless and a loss cannot be repaired.

So the relay is deliberately at least once. Each event carries a unique `event_id`, saved in the outbox row. The consumer records the ids it has seen and skips repeats. That is the job of 14.5. Debezium's outbox router passes the row's id along in a message header, and its documentation says you can use it, for example, to remove duplicate messages. {/* source needed: Debezium outbox event router page (https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html, read 2026-10-24) is not yet in the dossier. */}

In challenge 13 the numbers are plain. In one run of 500 orders, the relay crashed 11 times and published 103 events a second time. Each crash repeats every row of its batch that was already published, so the batch size sets how many repeats one crash makes.

</GoDeeper>

## Read the database log instead of polling

<MermaidDiagram title="Two ways to get outbox rows to the broker" chart={`flowchart LR
  subgraph Poll["Polling relay"]
    D1["Orders DB: outbox table"] -->|"SELECT unsent rows every second"| R1["Relay"] --> B1["Broker"]
  end
  subgraph CDC["Change data capture"]
    D2["Orders DB: write-ahead log"] -->|"reads each committed change"| R2["CDC connector"] --> B2["Broker"]
  end
`} legend="Polling asks the table. Change data capture reads the log the database already writes, so it sees every committed row at once." />

A polling relay asks the table again and again. Change data capture, or CDC, reads the log of changes the database already keeps. It sees each committed row as soon as it is written and does not run a query every second. Debezium is a well-known open-source tool that does this for PostgreSQL.

<GoDeeper title="Go deeper: polling versus CDC">

Every database already writes a log of its changes before it applies them, so that it can recover after a crash. PostgreSQL calls this the write-ahead log, or WAL. CDC tools read that log. Debezium's PostgreSQL connector uses PostgreSQL's logical decoding and a replication slot. It remembers the log position of each event and, after a restart, continues from where it left off. {/* source needed: Debezium PostgreSQL connector page (https://debezium.io/documentation/reference/stable/connectors/postgresql.html, read 2026-10-24): logical decoding, replication slot, resumes from the last recorded position. Dossier has no Debezium entry. */}

| | Polling relay | CDC connector |
|---|---|---|
| Delay | Up to one poll interval | Close to the commit |
| Load | A query every interval | None on the tables; reads the log |
| Setup | A table and a loop | Log access, a slot, a connector to run |
| Failure | Repeats after a crash | Resumes from the last saved position; may also repeat |
| Good fit | Small teams, low volume | High volume, low delay |

CDC is not magic. The connector can repeat events after a restart, because it saves its position only every so often. So the consumer still needs the event id (14.5). If the connector stops for a long time, the database keeps the log it has not read yet, and the disk can fill. Watch the lag.

Other stores offer the same idea. DynamoDB Streams keeps a time-ordered record of item changes for up to 24 hours, and its documentation says each stream record appears exactly once in the stream and in the order of the changes to each item. {/* source needed: DynamoDB Streams page (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Streams.html, read 2026-10-24), not in the dossier. */} That is a promise about the stream. A consumer that reads it and calls another service can still run twice, so it must still be idempotent.

</GoDeeper>
