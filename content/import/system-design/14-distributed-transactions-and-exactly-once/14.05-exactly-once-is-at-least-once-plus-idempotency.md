The wallet service at Zaytoun Market receives the message "add 18 to Layla's wallet" from a broker. Brokers promise to deliver the message. They do not promise to deliver it only once. This chapter follows one message through a crash. It adds a dedupe table, shows where that table still fails, and closes the gap. It ends on what "exactly once" can honestly mean.

## The ack is lost, the message returns

<InteractiveCanvas slug="sysdesign-m14-ack-lost" />

The consumer adds 18 to the wallet, then crashes before it tells the broker. The broker cannot tell "never arrived" from "arrived, but the ack was lost". After a timeout it sends the message again. The wallet is credited twice: 36, not 18.

<GoDeeper title="Go deeper: three delivery promises, and what systems really offer">

A delivery promise comes in three kinds. At most once means the broker sends a message one time and never retries, so a failure loses it. At least once means the broker keeps sending until it gets an ack, so a failure can repeat it. Exactly once means one delivery and one effect. The Kafka documentation lists the same three, and warns that many systems claim exactly-once delivery, but you should read the fine print [S82].

The common default is at least once. Amazon SQS standard queues deliver at least once and tell you to design consumers that are not harmed by processing the same message more than once [S83]. While a consumer holds a message, SQS hides it from others for the visibility timeout, 30 seconds by default [S84]. If no delete arrives in that time, the message comes back. A slow consumer, not only a crashed one, can cause a repeat: the work finishes at second 35 and the message was already re-sent at second 30.

Why can the broker not do better? From where it stands, a missing ack is the same event whether the consumer never got the message or did the work and lost the ack. Retrying risks a repeat. Not retrying risks a loss. Most systems pick the repeat, because a repeat can be made harmless and a loss cannot be repaired.

</GoDeeper>

## Count the copies, with and without a table

<InteractiveCanvas slug="sysdesign-m14-dedupe-flow" />

Pick a consumer, then drag how often the ack is lost. With nothing, every copy counts. With a dedupe table in a separate step, a crash between the work and the record still lets copies through: drag the crash-in-the-gap rail. With the id and the work in one transaction, the count stays at exactly 100.

<GoDeeper title="Go deeper: the three consumers, and a real run">

The playable compares three consumers handling the same stream of 100 messages, each of which reserves one bag of rice. The challenge run below uses 300 messages, so its numbers are three times as large.

The first does nothing special. The second looks in a table, does the work, then writes the id, as three separate statements. The third saves the id and does the work in one database transaction. In challenge 13, part 2, you run all three while the consumer crashes. In one run, with a 20% chance of losing the ack and a 5% chance of crashing between the work and the record:

```text
strategy              deliveries  expected  reserved  extra
no protection                368       300       368     68
check, work, record          409       300       324     24
one transaction              409       300       300      0
```

The second row is the lesson. The table stopped the repeats where the crash came after the id was written. It still let 24 through, the ones where the crash came between the work and the write. The third consumer saw even more deliveries (409), because a crash inside the transaction undoes everything and the message comes back. It still reserved exactly 300.

</GoDeeper>

## Write the id with the work

<InteractiveCanvas slug="sysdesign-m14-dedupe-txn" />

The consumer saves the message id and does the work in one transaction. When the copy arrives, the id is already there and the work is skipped. A crash before the commit undoes both, so the retry starts clean. There is no moment where the work exists and the id does not.

<GoDeeper title="Go deeper: the claim step in SQL and in JavaScript">

The trick is to claim the id first, inside the transaction, with a unique key. `INSERT ... ON CONFLICT DO NOTHING` inserts the id for one caller only, and reports how many rows it inserted. Zero rows means someone already handled it.

```js
// Partial: error handling and the real work are left out.
async function handleOnce(pool, message, work) {
  return withTransaction(pool, async (db) => {
    const claimed = await db.query(
      "INSERT INTO processed_messages (message_id) VALUES ($1) ON CONFLICT DO NOTHING",
      [message.eventId]
    );
    if (claimed.rowCount === 0) return "duplicate"; // already handled
    await work(db, message);                        // same transaction as the claim
    return "processed";
  });
}
```

This is the same claim-first idea as 6.4: claim the key before you act, so two copies cannot both pass the check. It works because the id and the effect live in one database, so one transaction covers both. If the effect is a call to another service, such as a payment provider, you cannot put it in your transaction. Then pass the message id to that service as its idempotency key, and let it refuse the second charge [S80].

Some effects are idempotent by nature. "Set the price to 1850" can run any number of times. "Add 18 to the wallet" cannot. If you can redesign the effect, redesign it: store each credit as a row keyed by message id, and compute the balance from the rows. A repeated insert then changes nothing.

</GoDeeper>

## Exactly once is a promise about effects

<MermaidDiagram title="What you can build from an unreliable network" chart={`flowchart LR
  A["At most once: send, never retry"] -->|"a failure can lose the message"| X["Lost work"]
  B["At least once: retry until acked"] -->|"a failure can repeat the message"| Y["Repeated work"]
  B --> C["Add an idempotent consumer"]
  C --> Z["Exactly one effect"]
`} legend="No network gives exactly one delivery. At least once plus a consumer that skips copies gives exactly one effect." />

No network can promise one delivery. What you can build is one effect: deliver at least once, and let the consumer skip copies. Kafka's exactly-once covers reading, processing and writing inside Kafka. For any other system, the consumer must cooperate.

<GoDeeper title="Go deeper: what Kafka and SQS FIFO really promise">

Kafka's documentation says its exactly-once processing covers a read-process-write cycle inside Kafka, using idempotent producers and transactions. For exactly-once into another system, it says this generally requires cooperation with that system [S82]. If your consumer reads from Kafka and then writes to PostgreSQL, the PostgreSQL write is outside Kafka's promise, and you need an idempotent write there.

SQS FIFO queues do remove duplicates for retries, but only within a deduplication interval of 5 minutes [S86]. After that, a repeat with the same deduplication id is treated as new. It is a helpful extra layer, not a replacement for an idempotent consumer.

So when someone says "our pipeline is exactly once", ask two questions. Where does the guarantee start and end? And what happens to a message that arrives after the guarantee's window? The honest answer is almost always "at least once, plus idempotency at the last step".

</GoDeeper>

## Remember ids as long as copies can arrive

<InteractiveCanvas slug="sysdesign-m14-dedupe-forgot" />

The dedupe table keeps each id for 24 hours. A copy arrives 30 hours after the first delivery. The id is gone, so the copy looks new and the work is done twice. The time you remember an id must be longer than the longest delay before a copy can arrive.

<GoDeeper title="Go deeper: choosing how long, and keeping the table small">

How long can a copy be delayed? Add up the longest things that can hold a message: the broker's retention, the longest retry schedule of the sender, and the longest time a consumer can stay down. Then add a safety margin. Stripe keeps idempotency keys for at least 24 hours and may remove them after that [S80]. SQS FIFO uses 5 minutes [S86]. Those are choices for their own retry patterns, not rules for yours.

The cost is easy to estimate with the method of module 2. Say Zaytoun handles 50,000 messages a day and each saved id takes about 100 bytes: one day of ids is about 5 MB. Keeping them for a week is 35 MB. These are course numbers; do the sum for your own system. A `processed_at` column and a daily job that deletes old rows keep the table small.

There is a cheaper way when messages for one entity arrive in order. Store only the highest sequence number you have handled for each wallet, and ignore any message whose number is not higher. The memory grows with the number of wallets, not the number of messages, and it never forgets. The price is that the sender must number its messages per entity, and the broker must keep them in order.

</GoDeeper>
