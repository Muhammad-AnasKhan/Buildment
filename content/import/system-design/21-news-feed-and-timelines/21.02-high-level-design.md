You have Hikaya's numbers: about 17,400 feed opens and 350 posts a second at peak, which is 50 reads for each post. This is the sketch step of the design loop. Start with what Hikaya has to store, draw the two paths, then test one tempting shortcut against the numbers.

## Three lists: posts, follows, timelines

<MermaidDiagram title="What Hikaya stores" chart={`erDiagram
  ACCOUNT ||--o{ POST : writes
  ACCOUNT ||--o{ FOLLOW : "is part of"
  ACCOUNT ||--o{ TIMELINE_ENTRY : owns
  POST ||--o{ TIMELINE_ENTRY : "listed in"
  ACCOUNT {
    bigint account_id PK
    string name
  }
  POST {
    bigint post_id PK
    bigint author_id
    string body
    datetime created_at
  }
  FOLLOW {
    bigint follower_id
    bigint followee_id
    datetime since
  }
  TIMELINE_ENTRY {
    bigint owner_id
    bigint post_id
  }
`} legend="A POST is stored once. A FOLLOW links two accounts. A TIMELINE_ENTRY says that one post is in one reader's list." />

Hikaya stores three things. Posts are found by post id. Follows are kept in both directions, so Hikaya can answer "who does Salma follow?" and "who follows Karim?". A timeline is a reader's list of post ids, newest first. It holds ids only, 8 bytes each, so it stays small. The feed is built by looking up the posts in a timeline.

<GoDeeper title="Go deeper: the stores and their keys">

Each store is looked up by one key, which is what makes them easy to spread over many machines (chapter 9.2).

| Store | Looked up by | Kept in order | Size |
|---|---|---|---|
| Posts | `post_id`, hashed across partitions | A second index by `author_id` then `post_id`, for profile pages | About 3.7 TB a year |
| Follows | Two copies: by `follower_id` ("who do I follow?") and by `followee_id` ("who follows me?") | Not needed | 15 billion edges x 16 bytes = 240 GB per copy, 480 GB in all |
| Timelines | `owner_id` | Newest first, at most 800 ids | 50 million active readers x 800 x 8 bytes = 320 GB |

Post ids are 64-bit numbers that start with the time, like a Snowflake id (chapter 10.7), so sorting ids newest first is almost the same as sorting by time. Snowflake ids from different machines are sorted to within about a second, not exactly [S65].

Which database? Every question above is "give me the rows for this one key", so a key-value or wide-column store fits all three. DynamoDB, for example, hashes the partition key for you [S40]. The alternative is PostgreSQL split by hand (chapter 7.2). It gives you SQL, but you run the shards and the moves yourself. A team of six is a reason to prefer a managed store.

The second index on posts, by author, answers "show me Dina's posts" for a profile page. In DynamoDB a global secondary index is updated asynchronously [S41], so a new post may be missing from a profile for a moment. That is acceptable. The author's own view is fixed in the next beat.

</GoDeeper>

## Publishing: save first, spread later

<MermaidDiagram title="The write path" chart={`flowchart LR
  C["Client"] -->|"POST /posts + key"| G["Gateway: rate limit"]
  G --> P["Post service"]
  P -->|"1. save"| PS[("Post store")]
  P -->|"2. event"| Q["Queue"]
  P -->|"201 Created"| C
  Q --> W["Fan-out workers"]
  W -->|"3. who follows?"| FS[("Follow store")]
  W -->|"4. add the id"| TL[("Timeline store")]
`} legend="The author gets her answer after step 2. Steps 3 and 4 run later, in the background." />

The post is saved, an event goes on a queue, and the author gets `201 Created` right away. Fan-out workers then look up the followers and add the post id to each follower's timeline. Spreading takes longer than saving, and that is allowed: followers see the post a few seconds later.

<GoDeeper title="Go deeper: retries, repeats and the author's own timeline">

The whole write API is one request.

```text
POST /posts   headers: Idempotency-Key    body: { "text": "...", "photo": "<upload id, optional>" }
              -> 201 Created   { "id": "6803941727115264", "created_at": "..." }
              -> 400 Bad Request   if the text is empty or over 280 characters
              -> 429 Too Many Requests   if the author is over the posting limit
```

A phone on a weak connection will time out and retry. Without care, each retry makes a second post. An idempotency key (chapter 6.4) fixes that: the client sends a random key, and Hikaya returns the first answer for a key it has already seen.

The event must exist whenever the post exists. Saving the post and writing the event in one transaction, then letting a relay publish it, is the outbox pattern from chapter 14.4. The queue itself is the one from chapter 15.7, and it delivers at least once (chapter 15.4). So a worker will sometimes see the same event twice. That is safe if adding a post to a timeline is idempotent. Keying each timeline entry by `(owner_id, post_id)` makes a second add change nothing.

The author is a special reader. The post service also adds the new id to the author's own timeline before it replies, so she never sees her own post vanish. This is the read-your-writes rule from chapter 8.4, applied to a feed.

How the workers spread a post, and why that gets hard for very popular accounts, is chapter 21.3.

</GoDeeper>

## Opening the feed: ids first, posts second

<MermaidDiagram title="The read path" chart={`flowchart LR
  B["Phone"] -->|"GET /feed"| F["Feed service"]
  F -->|"1. my post ids"| TL[("Timeline cache + store")]
  F -->|"2. fetch these posts, one batch"| PC[("Post cache + store")]
  F -->|"3. a page of 20"| B
`} legend="Two cheap steps: read one list of ids, then fetch those posts in one batch." />

The feed service reads the reader's list of post ids, then fetches those posts in one batch and returns a page of 20. That is one list read and one batch read, not 150 lookups. Names, counts and photos come from other caches and from the CDN (chapter 5.7).

<GoDeeper title="Go deeper: batches, caches and deleted posts">

A batch read ("multi-get") asks one cache or store node group for many keys in one round trip. Twenty posts in one batch costs far less than twenty separate calls. The post cache is a cache-aside cache (chapter 5.3): look in the cache, on a miss read the store and put the post in the cache.

Posts almost never change, which makes them easy to cache. A very popular post is the exception, because millions of readers want the same key. That is a hot key. Facebook's memcache paper handled it with leases, which cut peak database queries from 17,000 to 1,300 a second in one test [S24]. Chapter 5.6 explains the idea.

A timeline can hold the id of a post that was deleted later. Fixing every timeline at delete time would be a huge fan-out in reverse. Hikaya does it lazily: the batch read finds a deleted marker for that id and skips it. To still fill a page of 20, the service asks for about 25 ids and keeps the first 20 that exist.

Photos are not part of the post row. The row holds a photo id, and the app fetches the image from a CDN near the reader. That keeps the post store small and the feed path light.

</GoDeeper>

## One query per feed open is too much

<InteractiveCanvas slug="sysdesign-m21-one-query-feed" />

One feed open becomes 150 lookups, so 17,400 opens become 2.6 million lookups a second. One database node does a few thousand. Something has to give. The cheap fix is to do the work when a post is published, not when the feed is opened, and keep the result as a timeline. There are only 350 posts a second to handle.

<GoDeeper title="Go deeper: how big the shortcut would be">

Plan a database node at about half busy, 2,500 operations a second (chapter 2.5). Then 2,600,000 / 2,500 is about 1,040 nodes, just to read feeds. A cache with a 90% hit rate would still pass 260,000 lookups a second to the database, which is about 100 nodes. And every feed open would wait for the slowest of its 150 lookups, so the tail latency from chapter 2.4 gets worse.

The shortcut is not wrong everywhere. For a small app with 100 daily users and 20 follows each, it is the right answer, and the first design in chapter 1.4 made the same choice for PasteBox. The numbers decide. Here they say no.

The alternative is to move the work to the write side. That costs a timeline store (320 GB) and a fan-out fleet, and it makes a feed open one list read. Whether to do it for every account is the question of chapter 21.3.

</GoDeeper>

## Tap an action, see what it touches

<InteractiveCanvas slug="sysdesign-m21-action-map" />

Tap Open feed, Publish, Open profile and Follow. Each lights the blocks it uses and shows how often per second at the busiest time. Opening the feed touches few blocks, but 17,400 times a second. Publishing touches the most blocks, but only 350 times a second, and a queue can absorb its bursts. So keep the feed path simple and put the heavy work on the write path.

<GoDeeper title="Go deeper: the load on each action">

These are peak rates from the chapter 21.1 numbers, with two more course assumptions: 5 profile views and 0.1 new follows per daily user per day.

| Action | Working | Peak rate | Blocks it touches |
|---|---|---|---|
| Open feed | 50,000,000 x 10 / 86,400 x 3 | about 17,400 a second | Gateway, feed service, timeline, post cache |
| Open profile | 50,000,000 x 5 / 86,400 x 3 | about 8,700 a second | Gateway, post service, post store (author index) |
| Publish | 50,000,000 x 0.2 / 86,400 x 3 | about 350 a second | Gateway, post service, post store, queue, fan-out workers, follow store, timeline |
| Follow | 50,000,000 x 0.1 / 86,400 x 3 | about 175 a second | Gateway, follow store (two writes, one per copy) |

The Publish row hides a large number. Each post is written into the timeline of every follower. If every account had 150 followers that would be about 52,000 timeline writes a second. Real follower counts are far from equal, and chapter 21.3 shows what that does.

Notice what the map does not show: the ranker, the page cache and the star-account lists. They arrive in chapters 21.3 and 21.4, and each one fits on the map as one more block on the read path.

</GoDeeper>

## The newest slice of timelines stays in memory

<InteractiveCanvas slug="sysdesign-m21-timeline-cache" />

A timeline holds ids only, so the newest 200 ids of 50 million active readers take about 80 GB. That fits in memory. A reader seen today is a hit, answered in about half a millisecond. A reader who has been away is a miss: Hikaya loads the full list of 800 from the store and puts the head back in memory.

<GoDeeper title="Go deeper: sizing, eviction and the reader with no timeline">

The sums: 50,000,000 readers x 200 ids x 8 bytes = 80 GB for the heads in memory. The full lists are 50,000,000 x 800 x 8 bytes = 320 GB in the store. Three copies of the store make about 1 TB. A cache query takes about 0.5 ms [S3]. The few milliseconds for a read from the store are a course assumption.

Timelines are written by the fan-out workers, not expired by a timer. An LRU rule (chapter 5.4) drops the heads of readers who have not come back, so the memory goes to active readers. Hikaya keeps no timeline at all for an account that has been inactive for 30 days (an assumption). The fan-out workers skip such accounts, which saves work.

A returning reader with no timeline gets one built by the slow way: the feed service reads the latest posts of the accounts the reader follows (about 150 lookups), merges them by time, and stores the result. That is expensive, so it must be rare and limited. If the whole timeline cache restarts empty, millions of readers miss at once, which is the stampede of chapter 5.6. Chapter 21.4 returns to this as the failure step.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Three stores: posts by id, follows kept in both directions, and a timeline of post ids for each active reader. On publish, I save the post, return 201, and put an event on a queue. Fan-out workers look up the followers and add the id to each timeline. On read, the feed service takes the timeline ids, fetches those posts in one batch and returns a page. Building a feed from the posts table on every open would be about 2.6 million lookups a second, so I do the work at publish time. Timelines hold ids only, so the heads of 50 million readers fit in about 80 GB of memory."

**Expect:** "What if the queue loses an event?" **Answer:** "I use an outbox so the event exists whenever the post does, and workers are idempotent so a repeat is harmless. A repair job can rebuild a timeline from the follow store and the posts."

</GoDeeper>
