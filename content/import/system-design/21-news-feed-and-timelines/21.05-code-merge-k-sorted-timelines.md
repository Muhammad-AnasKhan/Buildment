In chapter 21.3 you chose the hybrid for Hikaya. Most accounts are pushed into the reader's timeline. Accounts with 100,000 or more followers are pulled, so their recent posts sit in cached lists of their own. When Salma opens her feed, the feed service must combine her timeline with the lists of the stars she follows. Every one of those lists is already sorted newest first. Chapter 21.4 asked for the newest 500 of the merge, and chapter 6.3 asked for a cursor so that the next page never repeats or skips a post.

That is a small problem with sharp edges. Merging k sorted lists is a classic exercise, and a heap is the classic tool. Paging adds the part that goes wrong in real feeds: a cursor that names a place in the order, posts that appear in two lists, and lists that are far longer than one page. In this chapter you write the heap, then the paged merge, in plain JavaScript.

## What the tests do to your code

The tests are built around the places where feeds break. For the heap they check order for a smallest-first and a largest-first comparator, an empty heap, and pushes mixed with pops. For the merge they use ties in time, copies of one post in two lists, a cursor whose own post was deleted, newer posts arriving at the top between two pages, a last page that is exactly full, empty lists and bad input.

Two tests are about cost. One counts how many entries your code reads from three lists of 100,000 entries each. A solution that copies, slices or sorts whole lists reads all 300,000 and fails. The same test starts from a cursor deep inside the lists, and a solution that scans from the top to find its place reads tens of thousands. Another test freezes nothing, but it compares the lists before and after, so removing entries from an input list fails.

Nothing is asynchronous, and nothing reads a clock or a random number. Each test gives the same answer every time, and the message of a failing test names the input and what it expected.

## The contract

A post in a list is an object `{ id, ts }`. The `ts` is the time it was published, and a larger `ts` is newer. When two posts have the same `ts`, the larger `id` is newer. This gives every post one exact place in the order. The function `isNewer(a, b)` is given to you in the starter code and says whether `a` comes before `b` in a newest-first list.

**`createHeap(before)`** returns an object with four methods. `push(item)` adds an item. `pop()` removes and returns the item that `before` puts first, or `undefined` when the heap is empty. `peek()` returns that item without removing it, or `undefined`. `size()` returns how many items are inside. The function `before(a, b)` returns true when `a` must come out before `b`. It throws a `TypeError` if `before` is not a function.

**`mergeTimelines(lists, { limit = 20, cursor = null })`** takes an array of lists, each sorted newest first. It returns `{ items, nextCursor }`. The `items` are at most `limit` posts, newest first, each post once. If a `cursor` is given, only posts strictly older than the cursor are returned. A cursor is `{ ts, id }`, the place of the last post of the previous page.

The `nextCursor` is `{ ts, id }` of the last post in `items` when at least one more post would follow, and `null` when this page holds the last post. The same post can be in two lists, for example when an account crosses the follower line and its posts are both pushed and pulled. It must appear once. A copy of the last post is not "more".

The function throws a `TypeError` if `lists` or one of its lists is not an array, or if `cursor` is something other than `null` or an object with numeric `ts` and `id`. It throws a `RangeError` if `limit` is not a positive integer. It never changes the lists it is given.

## A worked example by hand

Take three lists, written as id at time. List a is 10@90, 8@70, 3@20. List b is 9@80, 5@40. List c is 7@60. Ask for a page of 3 with no cursor. The heap starts with the three heads: 10@90, 9@80 and 7@60.

| Step | Popped | Pushed from the same list | Taken so far |
|---|---|---|---|
| 1 | 10@90 (list a) | 8@70 | 10 |
| 2 | 9@80 (list b) | 5@40 | 10, 9 |
| 3 | 8@70 (list a) | 3@20 | 10, 9, 8 |

The page is full. The heap still holds 7@60, 5@40 and 3@20, none of them a copy of post 8, so there is more. The cursor is `{ ts: 70, id: 8 }`. Now ask for the next page with that cursor. Each list is searched for its first post strictly older than the cursor. In list a that is 3@20, because 8@70 is the cursor itself. In list b it is 5@40, and in list c it is 7@60. The heap starts with those three heads and the page is 7, 5, 3. After taking 3, the heap is empty, so the cursor is `null`.

Now change the world between the two requests. Post 8 is deleted, and two newer posts arrive at the top of the lists. The cursor still names the place `{ ts: 70, id: 8 }` in the order, whether post 8 exists or not. The binary search lands at the same places, and page 2 is still 7, 5, 3. That is the whole reason to use a value and not a position. An offset of 3 would now start one post early.

## Five ways this goes wrong

**Sorting everything.** Joining the lists and sorting them gives the right answer on small input. Its cost is the size of all lists, every time, for a page of 20. A star's list holds thousands of posts, and a feed opens 17,000 times a second. The heap reads about one post per post returned, plus one per list.

**Reading the cursor from the wrong side.** "Older than the cursor" and "at or older than the cursor" differ by one post: the cursor's own. Choose the second and every page starts with the last post of the page before. Choose a rule that compares time only and a post that shares the cursor's time is skipped or repeated.

**Forgetting ties.** Two posts in the same millisecond are not rare in a busy feed. If your comparison looks at `ts` only, the heap puts them in an arbitrary order, and the cursor cannot say which of them was last. Always compare `ts` first and `id` second.

**Getting the last page wrong.** A cursor on the last page makes the client ask for one more page and get nothing. A missing cursor on a page that is not last loses posts. The case that catches most solutions is a page that is exactly full with only a copy of its last post left behind it.

**Changing the input.** Calling `shift` or `splice` on a list to remember where you are changes the caller's data, and the next request sees a shorter list. Keep a position number for each list instead.

When a test fails, read its message first. It names the input and what it expected, and the heap tests are small enough to trace by hand.

  // Merging timelines for Hikaya: a heap, and a paged merge of sorted lists.

  // Given. Entries are { id, ts }. A larger ts is newer; the same ts is broken by the larger id.
  function isNewer(a, b) {
    return a.ts > b.ts || (a.ts === b.ts && a.id > b.id);
  }

  // before(a, b) is true when a must come out of the heap before b.
  function createHeap(before) {
    if (typeof before !== "function") throw new TypeError("before must be a function");
    const items = [];
    const swap = (i, j) => {
      const t = items[i];
      items[i] = items[j];
      items[j] = t;
    };
    return {
      push(item) {
        items.push(item);
        let i = items.length - 1;
        while (i > 0) {
          const parent = (i - 1) >> 1;
          if (!before(items[i], items[parent])) break;
          swap(i, parent);
          i = parent;
        }
      },
      pop() {
        if (items.length === 0) return undefined;
        const top = items[0];
        const last = items.pop();
        if (items.length > 0) {
          items[0] = last;
          let i = 0;
          for (;;) {
            const left = 2 * i + 1;
            const right = left + 1;
            let best = i;
            if (left < items.length && before(items[left], items[best])) best = left;
            if (right < items.length && before(items[right], items[best])) best = right;
            if (best === i) break;
            swap(i, best);
            i = best;
          }
        }
        return top;
      },
      peek() {
        return items[0];
      },
      size() {
        return items.length;
      },
    };
  }

  function mergeTimelines(lists, { limit = 20, cursor = null } = {}) {
    if (!Array.isArray(lists)) throw new TypeError("lists must be an array");
    if (!Number.isInteger(limit) || limit < 1) throw new RangeError("limit must be a positive integer");
    if (cursor !== null && cursor !== undefined) {
      if (typeof cursor !== "object" || !Number.isFinite(cursor.ts) || !Number.isFinite(cursor.id)) {
        throw new TypeError("cursor must be { ts, id } or null");
      }
    }

    // The first position in a list whose entry is strictly older than the cursor.
    const startOf = (list) => {
      if (!cursor) return 0;
      let lo = 0;
      let hi = list.length;
      while (lo < hi) {
        const mid = (lo + hi) >> 1;
        if (isNewer(cursor, list[mid])) hi = mid;
        else lo = mid + 1;
      }
      return lo;
    };

    const heap = createHeap((a, b) => isNewer(a.entry, b.entry));
    lists.forEach((list, k) => {
      if (!Array.isArray(list)) throw new TypeError("each list must be an array");
      const pos = startOf(list);
      if (pos < list.length) heap.push({ entry: list[pos], k, pos });
    });
    const advance = (node) => {
      const next = node.pos + 1;
      if (next < lists[node.k].length) heap.push({ entry: lists[node.k][next], k: node.k, pos: next });
    };

    const items = [];
    while (items.length < limit && heap.size() > 0) {
      const node = heap.pop();
      advance(node);
      const last = items[items.length - 1];
      if (last && last.id === node.entry.id) continue; // the same post from another list
      items.push(node.entry);
    }

    // Is anything left after this page? Copies of the last post do not count.
    let more = false;
    const lastItem = items[items.length - 1];
    while (heap.size() > 0) {
      const top = heap.peek();
      if (lastItem && top.entry.id === lastItem.id) {
        advance(heap.pop());
        continue;
      }
      more = true;
      break;
    }
    return { items, nextCursor: more && lastItem ? { ts: lastItem.ts, id: lastItem.id } : null };
  }

Run one more case in your head. Take two identical lists, `[2@2, 1@1]` and `[2@2, 1@1]`, and ask for a page of 2. The heap starts with two copies of post 2. You take the first, pop the second and drop it as a copy, and take post 1 next. The page is 2, 1. The heap still holds one copy of post 1. It is a copy of the last post taken, so it does not count as "more", and the cursor must be `null`.

Then try the cursor `{ ts: 2, id: 2 }` on the same lists. The binary search must land on post 1 in each list, not on post 2. If your search treats "equal" as "older", you will return post 2 again.

## How to say it in an interview

**Say:** "Each source list is sorted newest first, so I merge them with a heap that holds only the head of each list. I pop the newest, then push the next post from the same list. A page of 20 costs about 20 heap operations plus one read per list, not the length of the lists. The cursor is the time and id of the last post, so it names a place in the order. Each list is searched with a binary search to start after the cursor, which stays correct when posts are added or deleted. I drop copies of the same post by id, and I return no cursor when nothing is left."

**Expect:** "Why not keep a position number per list in the cursor?" **Answer:** "Positions move when posts arrive or are deleted, and the cursor would have to hold one number per list. A time and id pair works for any set of lists, so the client holds one small value."

## What this unlocks

The cursor idea, naming a place in the order and not a count, is not only for feeds. Any list that grows at the top and is read in pages needs it, from order histories to audit logs. The heap merge also appears in storage engines, where sorted files are merged during compaction (chapter 7.3), and in the log merge that opens chapter 10.1. Chapter 21.7 asks you to use these ideas on scenarios you have not seen.
