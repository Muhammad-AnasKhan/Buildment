```quiz
type: mcq
question: "A news site runs in North America East. Readers in EU West say article pages are slow. The team adds Valkey next to the database and reaches a 95% hit rate, but pages barely get faster for those readers. What is the most likely reason?"
options:
  - "Valkey needs a hit rate above 99% before it helps"
  - "Most of the wait is the 80 ms ocean crossing"
  - "Valkey reads are slower than the database's reads"
  - "News articles change too often to be cached at all"
correct: 1
explanations:
  - "No hit rate fixes this. Every request still crosses the ocean before it reaches Valkey."
  - "Right. A round trip from EU West to North America East is about 80 ms. Only a copy near the readers, such as a CDN edge, removes it."
  - "Inside one data centre a Valkey read and a simple query cost about the same. Neither is the slow part here."
  - "Articles change rarely once published, and a CDN lifetime of a minute or two would serve most reads."
```

```quiz
type: mcq
question: "A forum caches each thread's reply count with cache-aside and deletes the key after every new reply. A few times a week, a count stays wrong for the full 10-minute TTL right after a reply. Every delete succeeded. Which change closes this gap?"
options:
  - "Write the new count into the cache, not a delete"
  - "Switch the eviction policy to allkeys-lfu"
  - "Use leases, so a set after the delete is refused"
  - "Shorten the TTL from 10 minutes to 5 minutes"
correct: 2
explanations:
  - "Writing the value has the same race the other way round: two writers can arrive out of order and leave the older count."
  - "Eviction only decides what leaves when memory is full. The wrong count was put back by a slow reader."
  - "Right. This is a stale set. A lease from the miss is cancelled by the delete, so the slow reader's late set is refused."
  - "This halves how long the wrong count lives, but the slow reader can still put it back after every reply."
```

```quiz
type: mcq
question: "A sports app's live score page is one key, read 10,000 times a second through 50 app servers. Rebuilding it takes 20 ms. Each server coalesces misses in its own memory. About how many rebuild queries reach the database when the key expires?"
options:
  - "About 1, since the requests share one query"
  - "About 200, one for every miss in the 20 ms"
  - "About 10,000, one for every read that second"
  - "About 50, one from each app server"
correct: 3
explanations:
  - "Requests share a query only inside one server. The 50 servers do not know about each other's queries."
  - "200 is the herd with no fix at all: 10,000 a second times 0.02 s. Coalescing joins each server's misses."
  - "Only reads in the 20 ms gap miss. 10,000 is a whole second of reads, nearly all of them hits."
  - "Right. Each server sends its first miss to the database and its other misses wait on it. A shared lock or lease would bring it to 1."
```

```quiz
type: mcq
question: "A course site serves lesson videos named by a hash of their content, such as lesson-7.3fa9c1.mp4, from HTML pages that link to them. Lessons are sometimes edited. Which caching plan fits best?"
options:
  - "Videos: very long max-age. HTML: short max-age."
  - "Videos: no-store. HTML: a very long max-age."
  - "Both: no-cache, so every edge always revalidates."
  - "Both: a max-age of one year, and purge on change."
correct: 0
explanations:
  - "Right. A hashed name never changes its content, so it can live for a long time. The HTML must change when a lesson does, so it gets a short life."
  - "no-store sends every video view to the origin, the most expensive files there are, while the page that changes is kept longest."
  - "Revalidating a file whose name already proves its content wastes a trip to the origin on every view."
  - "A purge does not reach browsers, which would keep the old HTML for a year and never link to the edited video."
```

```quiz
type: mcq
question: "A bank's app shows each customer's balance. To cut database writes, a team proposes write-back caching for deposits: the cache confirms each deposit and writes it to the database a few seconds later. What is the strongest objection?"
options:
  - "Write-back caches cannot store exact decimals"
  - "A crash can lose deposits already confirmed"
  - "Every read after a write would miss the cache"
  - "It would need a CDN in front of the cache"
correct: 1
explanations:
  - "A cache stores whatever bytes it is given, including exact amounts in cents. The problem is when the database gets them."
  - "Right. Between the confirmation and the flush, the deposit lives only in the cache. A crash in that window loses money the customer was told is safe."
  - "Write-back keeps the new value in the cache, so reads after a write hit. Losing writes is the risk, not misses."
  - "A CDN keeps copies near users. It has nothing to do with when the cache writes to the database."
```
