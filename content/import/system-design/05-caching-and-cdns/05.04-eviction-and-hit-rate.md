Matjar sells 10,000 products, but its cache has room for about 1,000 product pages. The cache must decide which copies to keep. That choice, and the way shoppers spread their reads, decide the hit rate.

## A full cache must drop something

<InteractiveCanvas slug="sysdesign-m5-lru-evict" />

The cache has room for three items: A, B and C, written from the oldest use to the newest. The app reads A, so A becomes the newest. Then the app stores D, and something must go. LRU, least recently used, drops the item whose last use is oldest. That is B, even though A was stored before it.

<GoDeeper title="Go deeper: eviction, and how LRU is built">

Removing an item to make room is called <GlossaryTerm term="eviction" definition="When a cache is full and must store something new, it removes an existing item. The rule that picks which item goes is the eviction policy, for example LRU or LFU." />. A cache has a fixed amount of memory, and in a busy system it is full almost all the time, so eviction runs on nearly every new store.

<GlossaryTerm term="LRU" definition="Least recently used: when the cache is full, remove the item whose last read or write is the oldest. It bets that what was used recently will be used again soon." /> bets that recent use predicts the next use. A simple exact LRU keeps the items in order of last use. Every read moves the item to the newest end, and eviction takes from the oldest end. In JavaScript, a `Map` keeps keys in the order they were inserted, so deleting a key and setting it again moves it to the end. That is the trick you will use in chapter 5.8.

Exact LRU costs memory and work on every read. Redis does not keep a full order. It samples a few keys and evicts the oldest of the sample. The result is close to LRU for much less cost, and Redis uses the same sampling for LFU. Valkey, which you run in challenge 4, offers the same policy names. {/* source needed: Valkey's own eviction documentation, to confirm it samples the same way */}

</GoDeeper>

## One scan can flush LRU

<InteractiveCanvas slug="sysdesign-m5-scan-flush" />

Shoppers read product A all day. At night a report job reads thousands of rows once each. Under LRU each new row is the "most recent" item, so the rows push A out. In the morning the first shopper read of A misses. LFU, least frequently used, counts uses instead, and would keep A over rows read once.

<GoDeeper title="Go deeper: LFU, and when each policy loses">

<GlossaryTerm term="LFU" definition="Least frequently used: when the cache is full, remove the item that has been used the fewest times. It bets that popular items stay popular." /> keeps a use count per item and evicts the item with the smallest count. A scan of one-time reads cannot push out a key with a high count, which is exactly the failure in the picture.

LFU has the opposite weakness. A product that was hugely popular last week and is cold now still has a high count, and it can sit in the cache while today's new product misses. A pure count remembers too much, so a useful LFU cache needs some way to let old counts fade. {/* source needed: how Redis or Valkey LFU lets its counters decay over time */}

Which one to choose depends on the traffic. If popular items change quickly, like news or a daily sale, LRU follows them faster. If the cache sees large one-time scans mixed with a steady set of hot items, LFU protects the hot items. Redis offers both as `allkeys-lru` and `allkeys-lfu`, each approximated by sampling. When unsure, measure the hit rate with each on real traffic, which takes one setting change.

A third choice avoids the scan problem from the other side: keep the scan out of the cache. The report job can read the database directly, or a replica, and never touch the cache that serves shoppers.

</GoDeeper>

## Skew lets a small cache win

<InteractiveCanvas slug="sysdesign-m5-working-set" />

Two shops, each with 10,000 products and the same cache of 1,000 pages. In the even shop every product is read equally, so a read hits 10% of the time. In the skewed shop a few products get most reads. The same cache holds those top sellers and catches 76.5% of reads. The traffic, not only the size, sets the hit rate.

<GoDeeper title="Go deeper: working sets and the Zipf curve">

The <GlossaryTerm term="working set" definition="The items a system actually reads over a period, such as one hour. If the working set fits in the cache, almost every read after warm-up is a hit." /> is what matters, not the whole catalogue. If shoppers in one hour read only 800 different products, a cache of 1,000 pages holds all of them, and after the first read of each, almost every read hits.

When the working set is bigger than the cache, the shape of the traffic decides. A common model for skewed popularity is the Zipf curve: the product ranked k is read in proportion to 1/k to the power s. With s = 1, product 2 is read half as often as product 1, product 3 a third as often, and so on. {/* source needed: a measurement showing that web or shop request popularity is Zipf-like */}

The arithmetic for the picture, done for this course: the share of reads that go to the top k of N products is H(k) / H(N), where H(n) = 1 + 1/2 + 1/3 + ... + 1/n. H(1,000) is about 7.485 and H(10,000) about 9.788, so the top 1,000 get 76.5% of reads. The top 100, just 1% of the catalogue, already get 53.0%.

That is why a small cache can help a lot. Each step up in size helps less: going from 100 to 1,000 pages adds 23.5 points, but going from 1,000 to 2,000 adds only about 7 more (83.6%). Past some size, more memory buys almost nothing, and that is the point to stop.

Even traffic is the bad case. If a job sends reads evenly over all 10,000 products, a cache of 1,000 can only catch 10%, and each miss also costs the trip to the cache first. Before adding a cache, ask whether your reads are skewed.

</GoDeeper>

## Drag the size, watch the hits

<InteractiveCanvas slug="sysdesign-m5-hit-rate-curve" />

Drag the cache size along the curve, from 0.1% of the catalogue to all of it. The axis is logarithmic: equal steps right multiply the size. Then drag the skew. With strong skew a small cache catches most reads and each doubling adds fewer points. With even traffic the hit rate is just the share cached. Find where doubling adds under 5 points (try skew 1.2).

<GoDeeper title="Go deeper: what the curve does not show">

The curve assumes the cache holds exactly the most popular items. A real cache learns which items are popular from the reads it sees, and LRU or LFU only approximate that. Expect a real hit rate a little under the curve, and lower still right after a restart, when the cache is empty.

Popularity also moves. A sale changes the top sellers in minutes. The curve is a snapshot; LRU follows a moving set better than LFU, as the previous beat showed.

The hit rate is not the goal by itself. It is a means to two numbers from chapter 5.2: the time shoppers wait and the load on the database. A 76.5% hit rate means the database gets 23.5% of the reads. If that is still too many for it, the fix may be a bigger cache, more skew-friendly keys (caching a whole category page instead of each product), or a bigger database.

Measure the real curve with your own traffic. Challenge 4 has you measure hit rate against lifetime, which is the other half of the story: a copy that expires early is a miss even when there is room for it.

</GoDeeper>

## Pick an eviction policy

<MermaidDiagram title="Which eviction policy for this cache?" chart={`flowchart TD
  Q1{"Is the cache the only copy of the data?"}
  Q1 -->|"yes, e.g. a job queue"| N["noeviction: refuse writes when full"]
  Q1 -->|"no, only copies"| Q2{"Do some keys have a TTL, and others must stay?"}
  Q2 -->|"yes"| VT["volatile-ttl: evict keys closest to expiry"]
  Q2 -->|"no"| Q3{"Big one-time scans mixed with hot keys?"}
  Q3 -->|"yes"| LFU["allkeys-lfu"]
  Q3 -->|"no"| LRU["allkeys-lru"]
`} legend="Four of the Redis and Valkey eviction policies. Copies can be evicted; the only copy of anything must never be." />

First ask whether the cache holds the only copy of anything. If it does, it must never evict: refuse new writes when full. If it holds only copies, pick by key and traffic. Keys with a lifetime can be evicted closest-to-expiry first. Otherwise choose LRU, or LFU when large scans mix with hot keys.

<GoDeeper title="Go deeper: TTL and eviction are different jobs">

A <GlossaryTerm term="TTL" definition="Time to live: how long a stored copy may be used before it must be removed or checked again. After the TTL, the copy has expired." /> and eviction both remove items, for different reasons. Eviction removes by space: the cache is full and something must go, however fresh it is. A TTL removes by age: the copy may be wrong by now, however much room there is. A cache uses both, and they answer different questions. Eviction asks "what is least worth keeping?"; TTL asks "how long may this be stale?".

So set the TTL from the data, not from the memory. A price that changes a few times a day and is deleted on write can have a long TTL as a safety net. A stock hint shown on a busy product page might get a few seconds. Then size the memory from the working set, and let the eviction policy handle the rest.

The Redis and Valkey policies in the picture are four of several. `noeviction` returns an error on writes when memory is full, which is right when the data cannot be rebuilt from anywhere else. `volatile-ttl` only evicts keys that have a TTL, choosing the ones closest to expiry, so keys without one are kept. `allkeys-lru` and `allkeys-lfu` evict from all keys by recency or by use count. A cache that holds only copies, with every key given a TTL, usually runs `allkeys-lru` or `allkeys-lfu`.

</GoDeeper>
