Lina opens Matjar's sale page on her phone in Singapore, and Matjar's servers are in EU West. Her request can be answered by a copy at several stops on the way. This chapter finds those stops and adds up what each one saves.

## Five places a copy can live

<MermaidDiagram title="One request, five places a copy can live" chart={`flowchart TD
  P["Lina's phone: browser cache"] -->|"miss"| E["CDN edge in Singapore"]
  E -->|"miss: about 160 ms round trip"| L["Load balancer in EU West"]
  L --> A["App server: its own memory"]
  A -->|"miss"| V["Valkey: shared cache"]
  V -->|"miss"| D["Database: pages in memory"]
  D -->|"miss"| S["Disk (SSD)"]
`} legend="Each box with a copy can answer the request and end the trip there. The load balancer usually keeps no copy." />

Follow Lina's request down the picture. Five stops can keep a copy: her browser, a CDN edge in Singapore, the app server's own memory, a shared cache such as Valkey, and the database's memory in front of its disk. A hit at any stop ends the trip there. A miss passes the request on to the next stop.

<GoDeeper title="Go deeper: what each layer holds, and who controls it">

**Browser cache.** The browser keeps responses on the phone, following the `Cache-Control` header the server sent (chapter 5.7). A hit costs no network trip at all. But the server cannot reach into the phone to delete a copy, so whatever lifetime it sends, it has to live with. Each copy serves one person only.

**CDN edge.** A <GlossaryTerm term="CDN" definition="Content delivery network: many cache servers, called edges, spread around the world, which keep copies of responses close to users and fetch from your server, the origin, on a miss." /> keeps copies on servers near the user. One edge copy serves everyone near that edge, so a hit there saves the long trip to the origin for thousands of people. It holds only responses that are the same for everyone, such as a product page without the shopper's name in it.

**App server memory.** The app can keep a small map of recent results in its own process. Reading it costs about what a memory read costs, around 100 ns, with no network trip. Every app server keeps its own copy, so ten servers can hold ten slightly different versions, and a restart empties it.

**Shared cache.** Valkey (open source, BSD licence), Redis and Memcached are separate servers that every app server talks to over the network. One copy serves all app servers, and it survives an app restart. Each read is a network trip inside the data centre.

**Database memory.** The database keeps recently read data pages in its own memory. A query whose pages are already there avoids the disk. You do not manage this cache directly, but it is why the same query is faster the second time.

The load balancer usually keeps no copy. It only forwards requests, and it adds about 50 microseconds per hop in the dossier's rough numbers.

</GoDeeper>

## A hit returns early

<InteractiveCanvas slug="sysdesign-m5-edge-hit" />

Lina's request reaches the CDN edge in Singapore. Miss: the edge fetches the page from the origin in EU West, a round trip of about 160 ms, and keeps a copy for 60 seconds. The next shopper in Singapore gets that copy straight from the edge. Their request never makes the long trip.

<GoDeeper title="Go deeper: why distance decides where the copy should be">

The 160 ms comes from the dossier's latency table: a round trip from EU West to Singapore is about 160 ms. No amount of faster code on the origin removes it, because it is the time light and routers take to cross the distance. Only a copy closer to the shopper removes it.

The trip from Lina's phone to the edge is paid in both cases, so the picture leaves it out. {/* source needed: a typical round trip from a phone on a mobile network to a CDN edge in the same city */} What the edge saves is everything after it.

A real page is not one request. It is the HTML, then stylesheets, scripts and images, and a new connection needs its own round trips before the first byte (module 3). If each of those must cross to EU West, the 160 ms is paid several times. That is why CDNs matter most for users far from the origin, and least for users in the same region.

The edge can only keep what is the same for everyone. A product page that greets Lina by name, or shows her basket, cannot be shared. Teams split such pages: a shared part the edge keeps, and a small personal part fetched from the origin.

</GoDeeper>

## Next door, a cache saves little

<InteractiveCanvas slug="sysdesign-m5-next-door" />

Inside one data centre, a Valkey read and a simple query both take about 0.5 ms, because most of that time is the trip, not the work. The cache wins when one read replaces slower work. Matjar's product page needs 5 queries in a row, 2.5 ms. One cache read of the finished page takes 0.5 ms, and the database does nothing.

<GoDeeper title="Go deeper: cache work, not rows">

napkin-math puts a Redis, Memcached or MySQL query at about 500 microseconds, and a round trip inside a region at about 250 microseconds. Half or more of a simple query is the network. Putting a network cache in front of a fast indexed lookup adds a second network trip on every miss and saves almost nothing on a hit.

So cache the result of work, not a copy of a single row. Good things to cache are a page built from several queries, the result of a join or a sort, a list of recommendations that took real computing, or a response from a slow outside service. The more work one cache read replaces, the more it saves.

A cache always saves database load, even when it saves no time. Every hit is a query the database does not run. In chapter 5.1 the cache was not there for speed: it kept 5,000 reads a second away from a database that could answer 800. Ask both questions about every cache: how much time does a hit save, and how much load does it take away?

A copy in the app's own memory is different. It skips the network, so a hit costs about 100 ns instead of 0.5 ms. The price is that each server holds its own copy, which you cannot delete from outside the server. Keep such copies small and short-lived, often a few seconds.

napkin-math's author warns its numbers can be 2 to 3 times off. Use them to compare layers, then measure your own system, as you will in challenge 4.

</GoDeeper>

## Add up the path

<InteractiveCanvas slug="sysdesign-m5-cache-path" />

Drag the hit rate on each layer and watch two numbers: the time added after the edge for an average shopper, and the queries a second that reach the database. Raise the edge first, then Valkey. Notice which layer cuts the wait most, and which one protects the database most. They are not the same layer.

<GoDeeper title="Go deeper: the formula behind the picture">

Each layer is reached only by the requests that missed every layer above it. So the average time is the sum, over the layers, of the chance of reaching that layer times what it costs. The <GlossaryTerm term="hit rate" definition="The share of requests a cache answers from its copy, for example 0.9 when 9 of every 10 reads are hits. The miss rate is 1 minus the hit rate." /> of each layer sets those chances.

With an edge hit rate h_e and a Valkey hit rate h_v, and the costs from this chapter (160 ms to reach the origin, 0.5 ms for a Valkey read, 2.5 ms for the 5 queries), the time added after the edge is:

T = (1 - h_e) x (160 + 0.5 + (1 - h_v) x 2.5) ms

The database load for 1,000 page views a second is 1,000 x (1 - h_e) x (1 - h_v) x 5 queries a second.

Work it once. With h_e = 0.8 and h_v = 0.9: T = 0.2 x (160.5 + 0.25) = about 32 ms, and the database runs 1,000 x 0.2 x 0.1 x 5 = 100 queries a second. Raise the edge to 0.9 and T halves to about 16 ms, while the database load also halves to 50. Lower Valkey to 0.5 instead and T barely moves (about 32.4 ms), but the database load jumps to 500 queries a second.

That is the lesson of the picture. The layer nearest the user decides the wait, because it removes the expensive trip. The layer nearest the database decides the load, because it removes the queries. A design needs both numbers.

Look at the miss path too. With Valkey at a 0% hit rate, a request pays 0.5 ms for the Valkey miss and then the full 2.5 ms anyway. A cache with a poor hit rate is slower than no cache, which is one reason chapter 5.4 is about hit rates.

</GoDeeper>

## Every copy can go stale

<MermaidDiagram title="The price changes: who finds out, and when?" chart={`flowchart TD
  D["Database: the price is now 899"]
  D -.->|"app deletes it: about 0.5 ms"| V["Valkey copy"]
  D -.->|"own timer, on each server"| M["App memory copies"]
  D -.->|"lifetime, or a purge"| E["CDN edge copies"]
  D -.->|"lifetime only"| B["Browser copies"]
`} legend="Dashed lines are the ways each copy learns about the change. Only the shared cache can be told at once; the others wait for a timer." />

The price changes in the database. Valkey's copy can be deleted at once. The app servers' copies wait for their own timers. The edge copies wait for their lifetime or a purge, and the copies inside browsers wait for their lifetime with no way to reach them. Every layer that saves time is also one more place to show the old price.

<GoDeeper title="Go deeper: lifetimes by layer">

Each layer needs its own answer to "how long may this copy be wrong?". The further a copy is from the database, the harder it is to reach and the longer it may stay wrong.

A common way to decide: things that never change get very long lifetimes at every layer. A stylesheet whose file name includes its version, such as `app.v2.css`, can live in browsers and edges for a long time, because a new version gets a new name (chapter 5.7). Things that change, like a price, get short lifetimes at the outer layers, and a delete on write at the shared cache (chapter 5.5).

Personal data never goes into a shared layer. A response with Lina's basket must be marked so that a CDN does not keep it and serve it to the next shopper. The `private` directive in `Cache-Control` says exactly that (chapter 5.7).

You met the same idea in module 3 with DNS: a record's TTL says how long a resolver may keep it, and a change spreads only as old copies expire. Every cache in this module follows the same rule.

</GoDeeper>
