Matjar's cache now holds product pages. Two questions decide how it behaves: who puts copies into the cache, and what happens to the copy when a price changes. Each answer is a named pattern, and each pattern fails in its own way when a cache node crashes.

## Cache-aside: the app does the work

<InteractiveCanvas slug="sysdesign-m5-aside-read" />

The app asks the cache for product p42. Miss. The app reads the database, then stores a copy with a 60-second lifetime. That is three trips. The next read finds the copy: one trip. The cache never talks to the database. The app does both jobs, and only data that someone actually reads ends up in the cache.

<GoDeeper title="Go deeper: cache-aside and read-through">

This pattern is called <GlossaryTerm term="cache-aside" definition="The app checks the cache first; on a miss it reads the database itself and stores a copy in the cache. The cache sits beside the data path and never talks to the database. AWS calls it lazy loading; Facebook calls it look-aside." />, lazy loading or look-aside. Facebook's memcache is a "demand-filled look-aside cache": copies appear only when someone asks for them. AWS's ElastiCache guide calls it lazy loading and lists its costs: a miss takes three trips instead of one, and the copies can go stale. Its strength follows from the picture. Only data someone reads is cached, so memory is not spent on the rest. And because the cache only holds copies, a cache node that dies costs speed and database load, not data.

A small cache-aside read in JavaScript, with `cache` and `db` standing for your Valkey client and database code:

```js
// Cache-aside read. The copy lives 60 s, then the next read reloads it.
async function getProduct(id) {
  const key = `product:${id}`;
  const cached = await cache.get(key);          // trip 1
  if (cached !== null) return JSON.parse(cached);
  const row = await db.loadProduct(id);         // trip 2
  await cache.set(key, JSON.stringify(row), { ttlSeconds: 60 }); // trip 3
  return row;
}
```

**Read-through** moves the same logic into a cache library or layer. The app asks only the cache; on a miss the cache layer loads from the database itself, using a loader function the app gave it. The trips are the same. What changes is where the code lives: one place, shared by every caller, instead of in every function that reads. {/* source needed: a primary definition of read-through caching */}

Cache-aside is the default in most systems because it is simple and it survives a cache failure. Choose something else when its slow first read or its stale copies hurt more than its simplicity helps.

</GoDeeper>

## Write: change the database, drop the copy

<InteractiveCanvas slug="sysdesign-m5-delete-on-write" />

The admin sets p42 to 899. The app updates the database first, then deletes the cached copy. It does not write 899 into the cache. The next shopper's read misses, loads 899 from the database and stores it. The copy is fresh again, and only the database decided what the price is.

<GoDeeper title="Go deeper: why delete, and why the database first">

Facebook's memcache paper gives the reason to delete instead of update: deletes are idempotent. Deleting a key twice has the same effect as deleting it once, so a retried or repeated delete is harmless. Two updates of the same key can arrive in the wrong order and leave the older value in the cache, with nothing to correct it until the lifetime ends.

The database goes first because it is the source of truth. If the app deleted the copy first and then updated the database, a read in between could miss, load the old price from the database and store it again. The delete would be wasted.

Even in the right order, a gap remains. A read that started before the write can store its old value after the delete. Chapter 5.5 shows that race and the fixes for it. Writing the new value into the cache, instead of deleting, does not help: it is the reordering problem above.

This write path, update the database and leave the cache alone or drop the copy, is sometimes called write-around: writes go around the cache. Data written but never read stays out of the cache. {/* source needed: a primary definition of write-around caching */}

</GoDeeper>

## Write-through fills the cache on write

<InteractiveCanvas slug="sysdesign-m5-write-through" />

With write-through, every write goes into the cache and on to the database before the app hears "ok". Reads after a write find a fresh copy, with no miss. But every written item takes space, read or not. Here the app writes p77, and nobody ever reads it. Each write also pays for two stores instead of one.

<GoDeeper title="Go deeper: what write-through buys and costs">

AWS's ElastiCache guide describes write-through as updating the cache whenever data is written to the database. Its benefit: the cached copy stays fresh, because every write updates it. Its cost: the cache fills with data that is written but never read, which the guide calls churn. The guide also says a lifetime (TTL) bounds how stale a copy can get, which is why write-through is usually given one too: unread data then leaves on its own. A second cost follows from the picture: each write now goes to two places before the app hears "ok".

Write-through also has a gap after a crash. When a cache node restarts empty, every key it held is missing, and write-through only refills a key when it is written again. Reads of keys that are rarely written would miss forever. So write-through is usually paired with cache-aside reads: misses still load from the database.

"Never stale" also has a fine print. If the cache write succeeds and the database write fails, or the other way round, the two disagree. A system that needs them to agree must handle that partial failure, for example by deleting the cache key when the database write fails.

Write-through suits data that is read soon after it is written: a user's own profile right after they edit it, a game score shown right after it changes. It wastes memory on data written often and read rarely, such as logs.

</GoDeeper>

## Write-back is fast, until a crash

<InteractiveCanvas slug="sysdesign-m5-write-back-crash" />

With write-back, the cache confirms the order at once and plans to write it to the database a second later. That makes writes fast and lets the cache combine many writes into one. Then the cache node crashes before the flush. The database still says stock 5, and the order the shopper was told about is gone.

<GoDeeper title="Go deeper: when write-back is worth the risk">

Write-back (also called write-behind) turns the cache into a temporary owner of the data. The cache confirms the write, keeps it in memory, and writes it to the database later, often in batches. If 1,000 page views each add one to a view counter, write-back can turn 1,000 database writes into one write of "+1,000".

The risk is the window between the confirmation and the flush. A crash, a restart or an eviction in that window loses every confirmed write it held. Some caches can log writes to disk or copy them to a replica, which shrinks the risk, but the database is no longer the only place that knows the truth. Recovery has to replay the cache's log, in order, before anyone trusts the database again.

So the rule is about what a lost write costs. A view counter that loses a few seconds of counts is fine. An order, a payment or a stock count is not: the shopper was told "placed", and the shop now sells a phone it does not have. For those, the database must have the write before anyone is told "done".

The dossier found no primary source that defines write-back for application caches, so this chapter teaches it as a trade-off rather than quoting a definition. The same idea appears inside CPUs and disks, which also hold writes in fast memory and flush them later.

</GoDeeper>

## Pick a pattern, then crash it

<InteractiveCanvas slug="sysdesign-m5-pattern-stepper" />

Pick a pattern, then step through a read, a price change, a crash of the cache node, and one more read. Watch three things at each step: whether the cache copy is fresh, whether the database has the write, and how many reads reach the database after the crash. Only one pattern loses a write.

<GoDeeper title="Go deeper: the five patterns side by side">

| Pattern | Who fills the cache | A write goes to | After a cache crash |
|---|---|---|---|
| Cache-aside | The app, on a miss | The database, then delete the copy | Misses until copies return; nothing lost |
| Read-through | The cache layer, on a miss | The database (with a write rule of your choice) | Same as cache-aside |
| Write-through | Every write | The cache and the database, before "ok" | Cold cache; reads miss; nothing lost |
| Write-back | Every write | The cache now, the database later | Writes not yet flushed are lost |
| Write-around | Reads only | The database only | Same as cache-aside |

Read the table by its last column first. A cache crash is not rare: nodes restart for upgrades, run out of memory and get replaced. Every pattern except write-back treats the cache as a copy, so a crash costs only speed and database load. That load is real, as chapter 5.1 showed: a cold cache sends every read to the database at once, so plan the warm-up after a crash, not only the steady state.

The read side and the write side are separate choices. Most systems read with cache-aside and write by deleting the copy. Write-through is added for data that is read right after it is written. Write-back is kept for data where losing a few seconds of writes is acceptable.

</GoDeeper>

## Choose a pattern per kind of data

<MermaidDiagram title="Which write pattern fits this data?" chart={`flowchart TD
  Q1{"Can you lose the last few seconds of writes?"}
  Q1 -->|"yes, e.g. view counts"| WB["Write-back: fast, batched writes"]
  Q1 -->|"no"| Q2{"Is it read right after it is written?"}
  Q2 -->|"yes, e.g. own profile"| WT["Write-through, plus a TTL"]
  Q2 -->|"no, e.g. prices, pages"| CA["Cache-aside reads, delete on write"]
`} legend="One question about loss, one about reads after writes. Most data in a shop lands on cache-aside with delete on write." />

Ask two questions about each kind of data. Can you afford to lose the last few seconds of writes? Only then is write-back an option. Is the data read right after it is written? Then write-through saves a miss. Everything else, which is most of a shop, uses cache-aside reads and deletes the copy on write.

<GoDeeper title="Go deeper: Matjar's choices">

For Matjar, the decision tree gives three answers. Product pages and prices: cache-aside, delete on write, and a lifetime as a safety net in case a delete is lost. A shopper's own account page, which they see right after editing it: write-through, so the edit shows at once, with a lifetime so unread copies leave. The "viewed 3,000 times today" counter on each product: write-back in the cache, flushed to the database every few seconds, because losing a few seconds of counts in a crash hurts nobody.

Stock counts and orders are not on the list. Matjar keeps them in the database and reads them from the database at checkout. A cached stock count can be shown on the product page as a hint, but the decision to sell the last phone is made against the source of truth. Chapter 7 covers how the database makes that decision safely when two shoppers try at once.

**In AWS.** Amazon ElastiCache runs a managed cache. Its caching strategies guide describes lazy loading (cache-aside) and write-through, and the TTL that bounds staleness for both.

</GoDeeper>
