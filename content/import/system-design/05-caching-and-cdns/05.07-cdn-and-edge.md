Matjar's shoppers are spread across many countries, and its servers are in EU West. A CDN puts copies of its pages and files in edge servers near those shoppers. This chapter is about the rules those edges follow, and the load they leave for the origin.

## The header tells the edge how long

<InteractiveCanvas slug="sysdesign-m5-cache-control" />

The origin answers the first request with `Cache-Control: max-age=60`. The edge keeps the page and treats it as fresh for 60 seconds. A second shopper 12 seconds later gets the edge's copy, and the origin is not asked. After 60 seconds the copy is stale, and the edge must fetch or check again.

<GoDeeper title="Go deeper: the directives that matter">

HTTP caching is defined in RFC 9111. The origin controls every cache on the path, browsers and CDNs alike, through the `Cache-Control` header on its responses. The directives you will use most:

- `max-age=60`: the response is fresh for 60 seconds after it was made. The `Age` header tells how old a cached copy already is.
- `s-maxage=300`: the same, but only for shared caches such as a CDN, and it wins over `max-age` there. With `max-age=60, s-maxage=300`, browsers keep the page for 60 seconds and the CDN for 300.
- `private`: only the user's own browser may store it, never a shared cache. Use it for anything personal, such as a basket or an account page.
- `no-cache`: a cache may store it but must check with the origin before each use (next beat).
- `no-store`: no cache may store it at all.
- `must-revalidate`: once stale, the copy must not be used without checking with the origin first.

The split between `max-age` and `s-maxage` is useful because you can reach the CDN later and the browsers never. A purge (beat 5) can remove a CDN copy, but a copy inside a shopper's browser lives out its `max-age`. So give browsers the shorter lifetime and the CDN the longer one.

Set the header on every response on purpose, including `private` or `no-store` where they are needed, so that every cache on the path follows your rule instead of its own defaults.

</GoDeeper>

## no-cache means ask first

<InteractiveCanvas slug="sysdesign-m5-revalidate" />

Despite its name, `no-cache` does not forbid storing. The edge keeps the page, but must ask the origin before each use. It sends the copy's ETag, a short tag for this version of the page. The origin answers 304 Not Modified, with no body, and the edge serves its stored copy. To forbid storing, the header is `no-store`.

<GoDeeper title="Go deeper: revalidation with ETag and Last-Modified">

A stale or `no-cache` copy can be checked instead of fetched again. This is called revalidation. When the origin first sends the page, it adds a validator: an `ETag`, which is a short string that changes whenever the content changes, or a `Last-Modified` time. To revalidate, the cache sends a conditional request: `If-None-Match` with the ETag, or `If-Modified-Since` with the time. If nothing changed, the origin answers `304 Not Modified` with no body, and the cache uses its copy. If something changed, the origin sends the new page with status 200.

What revalidation saves is bandwidth and origin work, not the trip. The edge still waits a full round trip to the origin, about 160 ms from Singapore to EU West. For a large file that is mostly unchanged, a 304 instead of the whole body is a large saving. For a small page, the trip is most of the cost, and a `max-age` that lets the edge answer by itself saves far more.

A common mistake is to send `no-cache` on pages that must never be stored, such as a bank statement, thinking it forbids caching. It does not: the copy is stored and only checked before use. For those pages, use `no-store`, or `private` if the user's own browser may keep it.

</GoDeeper>

## Twenty edges, twenty misses: add a shield

<InteractiveCanvas slug="sysdesign-m5-origin-shield" />

Each edge keeps its own copy, so when the page expires, each edge misses once and asks the origin: 20 edges, 20 fetches per lifetime. An origin shield is a middle cache that every edge asks on a miss. Edge 1 misses, and the shield fetches the page once. Edge 20 misses later and gets the shield's copy. The origin builds the page once.

<GoDeeper title="Go deeper: what a shield costs">

A shield is one more cache layer, with the same arithmetic as chapter 5.2. It removes repeated misses from many edges, and it adds a hop for every miss that reaches it. {/* source needed: a CDN's documentation of origin shield, for example Amazon CloudFront Origin Shield */}

It pays off when the origin is expensive or far away, and when many edges read the same objects. A page built from heavy queries, or a video file that costs money to send from a storage bucket, gains a lot: 20 fetches become one. It pays off less for objects that only one edge ever reads, because the shield's copy is never reused and the extra hop is wasted.

A shield also changes staleness. An edge that fetches from the shield gets the shield's copy, which may already be up to one lifetime old. So with a lifetime of 60 seconds at both layers, a shopper can see a page up to about 120 seconds old. If that matters, give the edges a shorter lifetime, or pass the `Age` header along so the edge counts the time the copy already spent in the shield.

A shield is also a single place many misses meet. If the shield is slow or down, every edge miss is slow or fails, so ask how your CDN handles a shield failure before you depend on one.

</GoDeeper>

## Predict the origin's load

<InteractiveCanvas slug="sysdesign-m5-cdn-origin-load" />

Drag the lifetime from one second to an hour, and drag the traffic each edge gets. Watch three numbers move: the edge hit rate, the origin's requests a minute, and how old a page a shopper can see. Then switch the shield on. A longer lifetime cuts origin load and raises staleness. The shield cuts load without adding much staleness.

<GoDeeper title="Go deeper: the formula behind the picture">

Take one page at one edge. A miss fetches a copy, which then lives for the lifetime T. Every request in that time is a hit. If the edge gets r requests a second for the page, one copy serves about r x T hits after the miss that fetched it. So out of every 1 + r x T requests, one is a miss:

miss rate = 1 / (1 + r x T)

The origin gets one fetch per copy, so each edge sends it about r / (1 + r x T) requests a second. For many requests per lifetime that is close to 1 / T: one fetch per edge per lifetime, whatever the traffic.

Work it for Matjar. 20 edges each get 5 requests a second for the sale page, and T = 60 s. Each edge's miss rate is 1 / 301, about 0.33%, so its hit rate is about 99.7%. The origin gets 20 x 5 / 301 = about 0.33 requests a second, about 20 a minute. With T = 10 s, the miss rate is 1 / 51, about 2%, and the origin gets about 118 a minute.

With a shield, the 20 edges' misses all go to the shield, which sees about 0.33 requests a second and keeps its own copy for T. Its miss rate is 1 / (1 + 0.33 x 60), about 1 in 21, so the origin gets about one request a minute. The worst-case age of a page a shopper sees is about T without a shield and about 2 x T with one, as the previous fold explained.

The model assumes requests arrive at random and the edge never evicts the page early. A real edge evicts rarely read objects to make room, which lowers the hit rate for the long tail of a catalogue.

</GoDeeper>

## Purge every edge, or change the name

<InteractiveCanvas slug="sysdesign-m5-versioned-file" />

Matjar ships a new stylesheet. It could tell every edge to delete `app.css`, which is called a purge or an invalidation. Instead it ships the file as `app.v2.css`, and pages link to the new name. Every edge misses once on the new name and fetches it. The old file is never asked for again, and no edge can serve it by mistake.

<GoDeeper title="Go deeper: when to purge, and when to rename">

Amazon CloudFront's documentation offers both choices: invalidate files, or use versioned file names. It also notes the cost of the first: the first 1,000 invalidation paths a month are free, and more are charged. Other CDNs have their own limits and prices.

A purge has two weaknesses. It does not reach browsers, which keep their copy for its `max-age`. And it is not instant: the request has to reach every edge, and requests in the meantime can still get the old copy. {/* source needed: how long a CDN purge takes to reach all edges */}

A versioned name has neither weakness, because nothing old is ever reused under the new name. You can put a short hash of the file's content into its name, such as `app.4f2c9a.css`, so the name changes exactly when the content does. Such a file can be given a very long lifetime at every layer, because its content can never change under that name.

The page that links to the file, the HTML, cannot be renamed: shoppers type `matjar.example/p/42`. So the usual split is: versioned files with very long lifetimes, and HTML with a short lifetime, plus a purge when a page must change at once. A price change during a sale is that case. The page needs either a short CDN lifetime or a purge, and chapter 5.5's lessons about stale windows apply to the edge just as they did to Valkey.

</GoDeeper>

## A signed URL is a ticket

<InteractiveCanvas slug="sysdesign-m5-signed-url" />

Some files are private, such as a manual a buyer paid for. The app gives the buyer a link that carries an expiry time and a signature, valid for 5 minutes. The edge checks the signature and the time itself and serves the file. The same link at 6 minutes is refused. The app was never asked.

<GoDeeper title="Go deeper: how a signed URL works, and its limits">

The app and the CDN share a key, set up ahead of time. To give a buyer access, the app builds a link with the file path, an expiry time and sometimes other limits, then signs them with the key. The signature is a short code that only someone with the key could make. The edge recomputes it from the link: if it matches and the time has not passed, the edge serves the file, from its cache if it has it. Changing the path or the expiry breaks the signature. {/* source needed: a CDN's signed URL documentation, for example Amazon CloudFront signed URLs, including the status code for an expired link */}

The point is that the edge can make the decision alone, at the speed of a cache hit. Without signing, every download would have to ask the app whether this buyer may have this file, which brings back the trip the CDN was meant to save.

The limits follow from the design. Anyone who holds a valid link can use it until it expires, so links are kept short-lived and are not posted in public places. A signed URL proves the link was issued, not who is using it. And because the file itself is cached once and shared by every valid link, signing controls access without losing the benefit of the cache.

</GoDeeper>
