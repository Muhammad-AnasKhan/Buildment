## The copy expires at peak

<InteractiveCanvas slug="sysdesign-m5-sale-expiry" />

Each shopper's request first asks the cache for the page, and the cache answers. Then the cached copy reaches the end of its life and expires. For a moment there is no copy, so every request misses and asks the database. The database was sized for the few misses a cache lets through, not for 5,000 queries a second.

<GoDeeper title="Go deeper: why one expiry is enough">

The team had done the sums for a normal day. The page is built from one heavy query that joins the product, its price, its stock and its reviews. On a calm database that query takes about 50 ms, and the database can run about 800 of them a second. With the cache in front, the database saw one query a minute for this page, because the copy lived for 60 seconds. Nobody worried.

The cache did more than make the page fast. It hid the real load. 5,000 reads a second were landing on a system that could answer 800, and the cache absorbed the difference. When the copy expired, that difference arrived at the database all at once.

Little's law from chapter 2.5 tells you how many requests pile up. The first request after the expiry misses and starts the 50 ms query. Until that query finishes and the copy is stored again, every request also misses. At 5,000 a second, 50 ms holds 5,000 times 0.05, which is 250 requests. So 250 copies of the same query land on the database in the first 50 ms. This has a name: a <GlossaryTerm term="cache stampede" definition="Many requests miss the same expired cache entry at the same moment, and all of them ask the database for the same data. Also called a thundering herd or dog-piling." />, also called a thundering herd.

Matjar is a course story. Its numbers are made up and rounded so the arithmetic is easy. The pattern is real: Facebook's engineers described thundering herds on hot keys in their 2013 paper on scaling memcache, and the fix they built is in chapter 5.6.

</GoDeeper>

## Down, and staying down

<MermaidDiagram title="Why the database does not recover by itself" chart={`flowchart TD
  A["The copy expires"] --> B["Every request misses"]
  B --> C["The database gets the full traffic"]
  C --> D["Each query takes longer"]
  D --> E["The copy takes longer to come back"]
  E --> B
  D --> F["Pages time out"]
  F --> G["Shoppers press refresh"]
  G --> B
`} legend="Two loops feed the misses: slower queries keep the cache empty for longer, and timeouts bring back the same shoppers as new requests." />

Once the database is overloaded, every query slows down, including the one that would refill the cache. The longer the cache stays empty, the more requests miss. Pages time out, shoppers press refresh, and each refresh is one more miss. The sale stays down long after the moment of expiry.

<GoDeeper title="Go deeper: what this module covers">

A cache is a copy of data kept somewhere faster or closer than the original. That definition hides three hard questions, and this module takes them one at a time.

**Where should the copy live?** Chapter 5.2 follows a request from the shopper's phone to the database and counts every place a copy can live: the browser, a CDN edge near the shopper, the app's own memory, a shared cache such as Valkey, and the database's own memory. Each hit stops the trip early.

**How does the copy get there and leave?** Chapter 5.3 compares the patterns that fill and update a cache, including what each one loses when a cache node crashes. Chapter 5.4 covers what a full cache throws away, and why a small cache can still answer most reads.

**When is the copy wrong?** Chapter 5.5 measures the stale window, the time a copy shows old data, for three ways of invalidating it, and shows a race that puts old data back. Chapter 5.6 returns to Matjar's sale: request coalescing, random lifetimes and serving a slightly old copy, each of which stops the stampede you just watched. Chapter 5.7 moves the cache to the edge of the internet with CDNs.

Then you build. In 5.8 you write an LRU cache with expiry in JavaScript, with tests. In 5.9 you put Valkey in front of a slow database in your own repository, measure the hit rate as the lifetime changes, and reproduce this exact stampede before you fix it.

A note on the numbers in this module. Latency numbers come from the course's research dossier, which takes them from rough, dated tables. Story numbers, like Matjar's 5,000 requests a second, are made up and labelled as such.
