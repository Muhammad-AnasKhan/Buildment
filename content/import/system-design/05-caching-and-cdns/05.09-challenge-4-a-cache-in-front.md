In this module you watched caches in pictures: a hit that ends the trip early, a copy that goes stale, a herd of misses on one hot key. Now you will run a real cache and count those things yourself. You will put Valkey, an open-source cache server, in front of a database that is slow on purpose, send it the same traffic with and without the cache, and measure what changes.

By the end of this chapter, your `system-design-challenges` repository has `challenges/challenge-4-cache-in-front/` with three parts. Part 1 measures cache-aside against no cache. Part 2 measures how the TTL trades hit rate against stale reads, and what delete-on-write does to that trade. Part 3 reproduces the stampede from chapter 5.1 on one hot key and fixes it twice. Each part has a `README.md` that teaches the idea from zero, a script, a `node:test` test, a `results.md` with your own numbers and a `chart.svg`. Two small files join `toolkit/`: a Valkey client and a traffic pacer, both plain Node.js with no packages. The only download is the Valkey image, `valkey/valkey:9-alpine`, about 19 MB compressed.

## How the experiment works

Every part runs one Node.js script on your laptop. The script plays the shoppers, the app servers and the database, and only the cache runs separately, in a Docker container. That keeps the setup small and lets the script count everything that happens.

Three design choices make the numbers mean something, and each one fixes an easy mistake.

**The database is pretend, and slow on purpose.** A real database would need its own container, data and tuning, and its speed would change with your laptop. The pretend one keeps rows in memory, makes every query wait a fixed time, and lets only 4 queries run at once while the rest wait in line, like requests waiting for a connection pool. That gives it a known capacity: 4 connections at 20 ms each is about 200 queries a second. It also counts every query and the longest line it ever had, which is exactly what you want to know about a cache: how much work it kept away from the database.

**The traffic is open loop and skewed.** As in challenge 1, reads start at random moments at a steady average rate, whether or not earlier reads have finished. A slow database therefore piles up work instead of quietly slowing the test down. And as in chapter 5.4, a few products get most of the reads: product k is read in proportion to 1 / k, a Zipf curve. A cache with even traffic would show you very little.

**The tests do not need Docker.** GitHub Actions runs `npm test` on a fresh machine with no Valkey. So `cache.js` offers two caches with the same methods: one that talks to Valkey, and a fake in a `Map` with a clock you control. The scripts use Valkey; the tests use the fake. The logic under test, in `shop.js`, cannot tell the difference.

## Step 1: two toolkit files

First, `toolkit/valkey.js`. Valkey speaks a simple text protocol called RESP. A command goes out as an array of strings, each with its length in front, and replies come back in the order the commands were sent. So the client keeps a queue of waiting promises, and each reply settles the oldest one. Read the comments on each reply type: `+` is a short status such as `OK`, `$` is a string with its length (or `-1` for "no such key"), `:` is a number, `*` is an array, and `-` is an error. Later challenges reuse this client, which is why it lives in `toolkit/`.

```js
// toolkit/valkey.js: a tiny Valkey client with no packages. It speaks RESP,
// the text protocol Valkey and Redis use: a command goes out as a list of
// strings, and replies come back in the same order the commands were sent.
import net from "node:net";

export const VALKEY_PORT = Number(process.env.VALKEY_PORT ?? 6379);

export function connect({ host = "127.0.0.1", port = VALKEY_PORT } = {}) {
  const socket = net.createConnection({ host, port });
  socket.setNoDelay(true);
  const waiting = []; // one { resolve, reject } per command, oldest first
  let buffer = Buffer.alloc(0);

  socket.on("data", (chunk) => {
    buffer = Buffer.concat([buffer, chunk]);
    while (waiting.length > 0) {
      const reply = parseReply(buffer, 0);
      if (!reply) break; // the rest of this reply has not arrived yet
      buffer = buffer.subarray(reply.end);
      const { resolve, reject } = waiting.shift();
      if (reply.value instanceof Error) reject(reply.value);
      else resolve(reply.value);
    }
  });
  socket.on("error", (err) => {
    for (const w of waiting.splice(0)) w.reject(err);
  });
  const ready = new Promise((resolve, reject) => {
    socket.once("connect", resolve);
    socket.once("error", reject);
  });

  return {
    ready,
    // send("SET", "k", "v") resolves to the reply: "OK", a number, a string, null or an array.
    send(...args) {
      const parts = args.map(String);
      let out = `*${parts.length}\r\n`;
      for (const p of parts) out += `$${Buffer.byteLength(p)}\r\n${p}\r\n`;
      return new Promise((resolve, reject) => {
        waiting.push({ resolve, reject });
        socket.write(out);
      });
    },
    close: () => socket.end(),
  };
}

// Read one reply starting at `start`. Returns null if it is not all here yet.
export function parseReply(buf, start) {
  const lineEnd = buf.indexOf("\r\n", start);
  if (lineEnd === -1) return null;
  const type = String.fromCharCode(buf[start]);
  const line = buf.toString("utf8", start + 1, lineEnd);
  const next = lineEnd + 2;
  if (type === "+") return { value: line, end: next }; // simple string, like OK
  if (type === "-") return { value: new Error(line), end: next }; // error
  if (type === ":") return { value: Number(line), end: next }; // integer
  if (type === "$") { // bulk string, or null when the length is -1
    const length = Number(line);
    if (length === -1) return { value: null, end: next };
    if (buf.length < next + length + 2) return null;
    return { value: buf.toString("utf8", next, next + length), end: next + length + 2 };
  }
  if (type === "*") { // array of replies
    const count = Number(line);
    if (count === -1) return { value: null, end: next };
    const items = [];
    let pos = next;
    for (let i = 0; i < count; i++) {
      const item = parseReply(buf, pos);
      if (!item) return null;
      items.push(item.value);
      pos = item.end;
    }
    return { value: items, end: pos };
  }
  throw new Error(`unexpected reply type "${type}"`);
}
```

Next, `toolkit/pace.js`. It is the open-loop part of challenge 1's load generator, pulled out so it can start any task, not only an HTTP request. It hands each task the time since the start, in seconds, which part 1 uses to group reads by second.

```js
// toolkit/pace.js: start an async task at a steady average rate, at random
// moments, without waiting for earlier tasks to finish (an open loop, as in
// challenge 1). Resolves to the list of the tasks' results, in start order.
import { exponential, seededRandom } from "./stats.js";

// Timers on Windows tick about every 15 ms, so check the clock in a loop
// that still lets other work run.
async function waitUntil(t) {
  while (performance.now() < t) await new Promise((resolve) => setImmediate(resolve));
}

export async function paced({ rate, seconds, seed = 7 }, task) {
  const random = seededRandom(seed);
  const start = performance.now();
  const stop = start + seconds * 1000;
  const pending = [];
  let planned = start;
  while (true) {
    planned += exponential(random, 1000 / rate);
    if (planned > stop) break;
    await waitUntil(planned);
    pending.push(task((performance.now() - start) / 1000)); // seconds since start
  }
  return Promise.all(pending);
}
```

## Step 2: start Valkey

Create `challenges/challenge-4-cache-in-front/compose.yaml`. Two lines matter beyond the image. Valkey's default eviction policy is `noeviction`, which you met in chapter 5.4: when memory is full, it refuses writes. That is right for data with no other copy and wrong for a cache, so the `command` line caps memory at 64 MB and picks `allkeys-lru`. The port line publishes Valkey only on `127.0.0.1`, so nothing outside your laptop can reach it. If port 6379 is busy, set `VALKEY_PORT` to another port before starting it and before running the scripts.

## Step 3: the shop and its pretend database

Four small files in the challenge folder hold the code all three parts share. Create `slowdb.js`, the pretend database. Notice how a finished query hands its connection straight to the next query in line. If it freed the connection first, a brand new query could jump the line.

```js
// A pretend database for the challenge. The rows live in memory, but every
// query takes queryMs, and at most `connections` queries run at once; the
// rest wait in line, like requests waiting for a connection pool. It counts
// every query, so you can see how many reads got past the cache.
export function createSlowDb({ products = 1000, queryMs = 20, connections = 4 } = {}) {
  const rows = new Map();
  for (let id = 1; id <= products; id++) rows.set(id, { id, price: 1000 + id, version: 1 });

  const stats = { queries: 0, waitingNow: 0, peakWaiting: 0 };
  let running = 0;
  const line = []; // queries waiting for a free connection
  const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

  async function query(work) {
    stats.queries++;
    if (running < connections) {
      running++; // a free connection: take it
    } else {
      stats.waitingNow++;
      stats.peakWaiting = Math.max(stats.peakWaiting, stats.waitingNow);
      await new Promise((resolve) => line.push(resolve)); // wait to be handed one
      stats.waitingNow--;
    }
    try {
      await sleep(queryMs);
      return work();
    } finally {
      const next = line.shift();
      if (next) next(); // hand this connection straight to the next in line
      else running--;
    }
  }

  return {
    stats,
    loadProduct: (id) => query(() => ({ ...rows.get(id) })),
    updatePrice: (id, price) =>
      query(() => {
        const row = rows.get(id);
        row.price = price;
        row.version++;
        return { ...row };
      }),
    // A free peek for measuring only: is a copy with this version stale now?
    currentVersion: (id) => rows.get(id).version,
  };
}
```

Then `cache.js`, the two caches. `setIfAbsent` uses `SET` with `NX`, which stores the value only if the key does not exist yet. Part 3 builds its lock from it.

```js
// Two caches with the same four methods. valkeyCache talks to a real Valkey
// server; memoryCache is a fake in a Map, with a clock you can control, so
// the tests run anywhere, including in GitHub Actions without Docker.

export function valkeyCache(client) {
  return {
    get: (key) => client.send("GET", key), // the value, or null on a miss
    set: (key, value, ttlMs) => client.send("SET", key, value, "PX", Math.round(ttlMs)),
    // SET ... NX only stores the value if the key does not exist yet.
    setIfAbsent: async (key, value, ttlMs) =>
      (await client.send("SET", key, value, "PX", Math.round(ttlMs), "NX")) === "OK",
    del: (key) => client.send("DEL", key),
  };
}

export function memoryCache(now = () => Date.now()) {
  const items = new Map(); // key -> { value, expiresAt }
  const live = (key) => {
    const item = items.get(key);
    if (item && now() >= item.expiresAt) items.delete(key);
    return items.get(key);
  };
  return {
    get: async (key) => live(key)?.value ?? null,
    set: async (key, value, ttlMs) => {
      items.set(key, { value, expiresAt: now() + ttlMs });
      return "OK";
    },
    setIfAbsent: async (key, value, ttlMs) => {
      if (live(key)) return false;
      items.set(key, { value, expiresAt: now() + ttlMs });
      return true;
    },
    del: async (key) => (items.delete(key) ? 1 : 0),
  };
}
```

Then `shop.js`, the heart of the challenge. `getProduct` is cache-aside from chapter 5.3: look in the cache, and on a miss load the database and store a copy. `updatePrice` writes the database first and then deletes the copy, unless part 2 turns that off. The two stampede fixes from chapter 5.6 are at the top: coalescing on one app server, and a lock in the shared cache for the whole fleet.

```js
// Matjar's product reads and price changes, with a cache in front of the
// slow database. One shop object stands for one app server.
//   ttlMs          how long a cached copy lives
//   deleteOnWrite  after a price change, delete the cached copy (part 2 turns it off)
//   stampede       what a miss does: "none", "coalesce" or "lock" (part 3)
const productKey = (id) => `product:${id}`;
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

export function createShop({ cache, db, ttlMs = 60_000, deleteOnWrite = true, stampede = "none" }) {
  const inFlight = new Map(); // "coalesce": one load per key on this server

  async function loadAndStore(id) {
    const row = await db.loadProduct(id);
    await cache.set(productKey(id), JSON.stringify(row), ttlMs);
    return row;
  }

  // Part 3, fix 1: requests on this server that miss the same key share one load.
  function loadCoalesced(id) {
    if (!inFlight.has(id)) {
      inFlight.set(id, loadAndStore(id).finally(() => inFlight.delete(id)));
    }
    return inFlight.get(id);
  }

  // Part 3, fix 2: a lock key in the shared cache lets one server in the
  // whole fleet load; the others wait for the copy to appear.
  async function loadWithLock(id) {
    const lockKey = `lock:${productKey(id)}`;
    const giveUpAt = Date.now() + 2000;
    while (Date.now() < giveUpAt) {
      if (await cache.setIfAbsent(lockKey, "1", 2000)) {
        try {
          // Look once more: the last lock holder may have stored it just now.
          const stored = await cache.get(productKey(id));
          if (stored !== null) return JSON.parse(stored);
          return await loadAndStore(id);
        } finally {
          await cache.del(lockKey);
        }
      }
      await sleep(10);
      const cached = await cache.get(productKey(id));
      if (cached !== null) return JSON.parse(cached);
    }
    return loadAndStore(id); // the lock holder seems stuck: load it ourselves
  }

  async function getProduct(id) {
    const cached = await cache.get(productKey(id));
    if (cached !== null) return { row: JSON.parse(cached), hit: true };
    const load = stampede === "coalesce" ? loadCoalesced : stampede === "lock" ? loadWithLock : loadAndStore;
    return { row: await load(id), hit: false };
  }

  async function updatePrice(id, price) {
    const row = await db.updatePrice(id, price); // the database first: it is the truth
    if (deleteOnWrite) await cache.del(productKey(id)); // then drop the old copy
    return row;
  }

  return { getProduct, updatePrice };
}
```

Last, `zipf.js`. It adds up 1 / k for every product once, then picks a product by drawing a random point along that total. Popular products cover more of the total, so they are picked more often.

```js
// Pick product IDs from 1 to n so a few are read far more than the rest:
// product k is read in proportion to 1 / k^s (a Zipf curve, chapter 5.4).
export function zipfPicker(random, n, s = 1) {
  const cumulative = [];
  let total = 0;
  for (let k = 1; k <= n; k++) {
    total += 1 / k ** s;
    cumulative.push(total);
  }
  return function pick() {
    const target = random() * total;
    let lo = 0;
    let hi = n - 1;
    while (lo < hi) { // binary search for the first cumulative >= target
      const mid = (lo + hi) >> 1;
      if (cumulative[mid] < target) lo = mid + 1;
      else hi = mid;
    }
    return lo + 1;
  };
}
```

## Step 4: part 1, cache-aside

Part 1 sends 400 reads a second for 5 seconds, over 1,000 products, twice: once straight to the database and once through the cache. The database manages about 200 queries a second, so without the cache it gets twice what it can serve. Then it changes the top seller's price and reads it again, to check the write path. Create `part-1-cache-aside/aside.js`:

```js
// Part 1: the same traffic with and without Valkey in front of the slow
// database (cache-aside), then one price change through the write path.
import { writeFileSync } from "node:fs";
import { connect } from "../../../toolkit/valkey.js";
import { paced } from "../../../toolkit/pace.js";
import { seededRandom, summarize } from "../../../toolkit/stats.js";
import { lineChart } from "../../../toolkit/chart.js";
import { createSlowDb } from "../slowdb.js";
import { valkeyCache } from "../cache.js";
import { createShop } from "../shop.js";
import { zipfPicker } from "../zipf.js";

const RATE = 400; // reads per second
const SECONDS = 5;
const PRODUCTS = 1000;

const client = connect();
await client.ready;
await client.send("FLUSHDB"); // start with an empty cache

async function run(useCache) {
  // 4 connections x 20 ms per query: at most about 200 queries a second.
  const db = createSlowDb({ products: PRODUCTS, queryMs: 20, connections: 4 });
  const shop = createShop({ cache: valkeyCache(client), db, ttlMs: 60_000 });
  const pick = zipfPicker(seededRandom(42), PRODUCTS); // the same reads in both runs
  const reads = await paced({ rate: RATE, seconds: SECONDS }, async (at) => {
    const id = pick();
    const t0 = performance.now();
    const hit = useCache ? (await shop.getProduct(id)).hit : (await db.loadProduct(id), false);
    return { at, ms: performance.now() - t0, hit };
  });
  return { reads, db, shop };
}

console.log(`${RATE} reads a second for ${SECONDS} s over ${PRODUCTS} products; the database manages about 200 queries a second\n`);
console.log("mode         reads  hit rate  db queries  peak line  p50 ms  p99 ms");
const results = {};
for (const mode of ["no cache", "cache-aside"]) {
  const { reads, db, shop } = await run(mode === "cache-aside");
  const s = summarize(reads.map((r) => r.ms));
  const hits = reads.filter((r) => r.hit).length;
  results[mode] = { reads, shop };
  console.log(
    `${mode.padEnd(11)}  ${String(reads.length).padStart(5)}  ${((hits / reads.length) * 100).toFixed(1).padStart(7)}%` +
    `  ${String(db.stats.queries).padStart(10)}  ${String(db.stats.peakWaiting).padStart(9)}` +
    `  ${s.p50.toFixed(1).padStart(6)}  ${s.p99.toFixed(1).padStart(6)}`
  );
}

// How the cache warms up: hit rate in each second of the cache-aside run.
console.log("\nsecond  reads  hit rate");
const points = [];
for (let sec = 0; sec < SECONDS; sec++) {
  const inSec = results["cache-aside"].reads.filter((r) => r.at >= sec && r.at < sec + 1);
  const rate = (inSec.filter((r) => r.hit).length / inSec.length) * 100;
  points.push({ x: sec + 1, hit: rate });
  console.log(`${String(sec + 1).padStart(6)}  ${String(inSec.length).padStart(5)}  ${rate.toFixed(1).padStart(7)}%`);
}

// The write path: change the top seller's price, then read it again.
const shop = results["cache-aside"].shop;
const before = await shop.getProduct(1);
await shop.updatePrice(1, 899);
const after = await shop.getProduct(1);
console.log(`\nproduct 1 before the change: ${before.row.price} (${before.hit ? "hit" : "miss"})`);
console.log(`product 1 after the change:  ${after.row.price} (${after.hit ? "hit" : "miss"}, loaded fresh)`);
client.close();

writeFileSync(new URL("./chart.svg", import.meta.url), lineChart({
  title: "Cache-aside warming up: hit rate each second",
  xLabel: "second of the run",
  yLabel: "hit rate %",
  points,
  series: [{ key: "hit", color: "#2563eb" }],
}));
console.log("\nwrote chart.svg");
```

Its test, `part-1-cache-aside/aside.test.js`, checks the Valkey reply parser on exact bytes, then checks cache-aside with the fake cache: one query for a miss, none for a hit, a fresh read after a price change, and a reload exactly when the TTL runs out.

```js
import test from "node:test";
import assert from "node:assert/strict";
import { parseReply } from "../../../toolkit/valkey.js";
import { createSlowDb } from "../slowdb.js";
import { memoryCache } from "../cache.js";
import { createShop } from "../shop.js";

test("Valkey replies parse", () => {
  const read = (text) => parseReply(Buffer.from(text), 0);
  assert.equal(read("+OK\r\n").value, "OK");
  assert.equal(read(":42\r\n").value, 42);
  assert.equal(read("$5\r\nhello\r\n").value, "hello");
  assert.equal(read("$-1\r\n").value, null); // GET of a missing key
  assert.deepEqual(read("*2\r\n$1\r\na\r\n:7\r\n").value, ["a", 7]);
  assert.ok(read("-ERR wrong\r\n").value instanceof Error);
  assert.equal(read("$5\r\nhel"), null); // not all here yet
});

test("a miss loads the database once, then reads hit", async () => {
  const db = createSlowDb({ products: 10, queryMs: 1 });
  const shop = createShop({ cache: memoryCache(), db, ttlMs: 60_000 });
  const first = await shop.getProduct(3);
  const second = await shop.getProduct(3);
  assert.equal(first.hit, false);
  assert.equal(second.hit, true);
  assert.equal(second.row.price, 1003);
  assert.equal(db.stats.queries, 1);
});

test("a price change deletes the copy, so the next read is fresh", async () => {
  const db = createSlowDb({ products: 10, queryMs: 1 });
  const shop = createShop({ cache: memoryCache(), db, ttlMs: 60_000 });
  await shop.getProduct(1);
  await shop.updatePrice(1, 899);
  const after = await shop.getProduct(1);
  assert.equal(after.hit, false);
  assert.equal(after.row.price, 899);
});

test("a copy expires after its TTL", async () => {
  let t = 0;
  const db = createSlowDb({ products: 10, queryMs: 1 });
  const shop = createShop({ cache: memoryCache(() => t), db, ttlMs: 60_000 });
  await shop.getProduct(5);
  t = 59_999;
  assert.equal((await shop.getProduct(5)).hit, true);
  t = 60_000;
  assert.equal((await shop.getProduct(5)).hit, false);
  assert.equal(db.stats.queries, 2);
});
```

## Step 5: part 2, TTL and hit rate

Part 2 is the trade-off from chapter 5.5, measured. It sends 500 reads a second over 200 products, while 10 price changes a second land mostly on popular products. It repeats this for six TTLs with delete-on-write turned off, so the TTL is the only thing that refreshes a copy. Then it runs the longest TTL once more with delete-on-write on. A read counts as stale when the copy it returned has an older version than the database has at that moment. Create `part-2-ttl-and-hit-rate/ttl.js`:

```js
// Part 2: the same reads and price changes with different TTLs. Longer
// copies mean more hits, and more stale reads, unless writes delete the copy.
import { writeFileSync } from "node:fs";
import { connect } from "../../../toolkit/valkey.js";
import { paced } from "../../../toolkit/pace.js";
import { seededRandom } from "../../../toolkit/stats.js";
import { lineChart } from "../../../toolkit/chart.js";
import { createSlowDb } from "../slowdb.js";
import { valkeyCache } from "../cache.js";
import { createShop } from "../shop.js";
import { zipfPicker } from "../zipf.js";

const PRODUCTS = 200;
const READS_PER_SECOND = 500;
const WRITES_PER_SECOND = 10; // price changes, mostly on popular products
const SECONDS = Number(process.env.RUN_SECONDS ?? 8);
const RUNS = [
  ...[500, 1000, 2000, 3000, 4000, 5000].map((ttlMs) => ({ ttlMs, deleteOnWrite: false })),
  { ttlMs: 5000, deleteOnWrite: true },
];

const client = connect();
await client.ready;

console.log(`${READS_PER_SECOND} reads and ${WRITES_PER_SECOND} price changes a second for ${SECONDS} s, ${PRODUCTS} products\n`);
console.log("ttl ms  delete on write  hit rate  stale reads  db queries/s");
const points = [];
for (const { ttlMs, deleteOnWrite } of RUNS) {
  await client.send("FLUSHDB");
  const db = createSlowDb({ products: PRODUCTS, queryMs: 5, connections: 8 });
  const shop = createShop({ cache: valkeyCache(client), db, ttlMs, deleteOnWrite });
  const pickRead = zipfPicker(seededRandom(42), PRODUCTS);
  const pickWrite = zipfPicker(seededRandom(99), PRODUCTS);
  const [reads, writes] = await Promise.all([
    paced({ rate: READS_PER_SECOND, seconds: SECONDS, seed: 7 }, async () => {
      const id = pickRead();
      const { row, hit } = await shop.getProduct(id);
      return { hit, stale: row.version < db.currentVersion(id) }; // older than the database now
    }),
    paced({ rate: WRITES_PER_SECOND, seconds: SECONDS, seed: 11 }, async () => {
      await shop.updatePrice(pickWrite(), 500 + Math.floor(Math.random() * 1000));
    }),
  ]);
  const hit = (reads.filter((r) => r.hit).length / reads.length) * 100;
  const stale = (reads.filter((r) => r.stale).length / reads.length) * 100;
  const readQueries = (db.stats.queries - writes.length) / SECONDS; // leave out the price updates
  if (!deleteOnWrite) points.push({ x: ttlMs, hit, stale });
  console.log(
    `${String(ttlMs).padStart(6)}  ${(deleteOnWrite ? "yes" : "no").padStart(15)}  ${hit.toFixed(1).padStart(7)}%` +
    `  ${stale.toFixed(2).padStart(10)}%  ${readQueries.toFixed(0).padStart(12)}`
  );
}
client.close();

writeFileSync(new URL("./chart.svg", import.meta.url), lineChart({
  title: "Longer TTL: more hits, more stale reads (no delete on write)",
  xLabel: "TTL in ms",
  yLabel: "% of reads",
  points,
  series: [{ key: "hit", color: "#2563eb" }, { key: "stale", color: "#dc2626" }],
}));
console.log("\nwrote chart.svg");
```

Its test, `part-2-ttl-and-hit-rate/ttl.test.js`, pins the trade with the fake clock. With a TTL alone, a read 999 ms after a change still shows the old price, and a read at 1,000 ms shows the new one. With delete-on-write, the next read is fresh. And for one read every 100 ms, a 250 ms TTL gives 66 hits in 100 reads while a 1,000 ms TTL gives 90.

```js
import test from "node:test";
import assert from "node:assert/strict";
import { createSlowDb } from "../slowdb.js";
import { memoryCache } from "../cache.js";
import { createShop } from "../shop.js";

test("with a TTL only, a read after a change is stale until the copy expires", async () => {
  let t = 0;
  const db = createSlowDb({ products: 5, queryMs: 1 });
  const shop = createShop({ cache: memoryCache(() => t), db, ttlMs: 1000, deleteOnWrite: false });
  await shop.getProduct(1); // the copy says 1001
  await shop.updatePrice(1, 500);
  t = 999;
  const old = await shop.getProduct(1);
  assert.equal(old.row.price, 1001);
  assert.ok(old.row.version < db.currentVersion(1), "the copy should be older than the database");
  t = 1000;
  const fresh = await shop.getProduct(1);
  assert.equal(fresh.row.price, 500);
});

test("delete on write closes the stale window", async () => {
  let t = 0;
  const db = createSlowDb({ products: 5, queryMs: 1 });
  const shop = createShop({ cache: memoryCache(() => t), db, ttlMs: 1000, deleteOnWrite: true });
  await shop.getProduct(1);
  await shop.updatePrice(1, 500);
  t = 10;
  const read = await shop.getProduct(1);
  assert.equal(read.row.price, 500);
  assert.equal(read.row.version, db.currentVersion(1));
});

test("a longer TTL turns more of the same reads into hits", async () => {
  async function hitsWith(ttlMs) {
    let t = 0;
    const db = createSlowDb({ products: 1, queryMs: 0 });
    const shop = createShop({ cache: memoryCache(() => t), db, ttlMs });
    let hits = 0;
    for (t = 0; t < 10_000; t += 100) if ((await shop.getProduct(1)).hit) hits++; // a read every 100 ms
    return hits;
  }
  assert.equal(await hitsWith(250), 66); // each copy serves 2 reads after its miss
  assert.equal(await hitsWith(1000), 90); // each copy serves 9
});
```

## Step 6: part 3, the stampede

Part 3 is chapter 5.1's sale in miniature. One hot product is read 2,000 times a second through 4 app servers, which take turns like a load balancer. Its copy lives 1 second, so it expires again and again during the 5-second run. The page query takes 50 ms and the database manages about 80 of them a second. The script runs three times: with no fix, with coalescing on each app server, and with the shared lock. Create `part-3-stampede/stampede.js`:

```js
// Part 3: one hot product, read 2,000 times a second through 4 app servers.
// Its copy lives 1 s, so it expires again and again. Count the database
// queries each time, with no fix, with coalescing, and with a shared lock.
import { writeFileSync } from "node:fs";
import { connect } from "../../../toolkit/valkey.js";
import { paced } from "../../../toolkit/pace.js";
import { summarize } from "../../../toolkit/stats.js";
import { lineChart } from "../../../toolkit/chart.js";
import { createSlowDb } from "../slowdb.js";
import { valkeyCache } from "../cache.js";
import { createShop } from "../shop.js";

const SERVERS = 4;
const RATE = 2000; // reads a second of the hot product
const SECONDS = 5;
const TTL_MS = 1000;
const BUCKET = 0.5; // seconds per point on the chart

// Each app server has its own connection to Valkey.
const clients = Array.from({ length: SERVERS }, () => connect());
await Promise.all(clients.map((c) => c.ready));

console.log(`${RATE} reads a second of one product through ${SERVERS} app servers, TTL ${TTL_MS} ms, ${SECONDS} s`);
console.log("the page query takes 50 ms, and the database manages about 80 of them a second\n");
console.log("fix        db queries  peak line  hit rate  p50 ms  p99 ms   max ms");
const points = Array.from({ length: SECONDS / BUCKET }, (_, i) => ({ x: (i + 1) * BUCKET }));
for (const stampede of ["none", "coalesce", "lock"]) {
  await clients[0].send("FLUSHDB");
  const db = createSlowDb({ products: 1, queryMs: 50, connections: 4 });
  // Note when every query starts, to draw queries per half second.
  const started = [];
  const load = db.loadProduct;
  const t0 = performance.now();
  db.loadProduct = (id) => {
    started.push((performance.now() - t0) / 1000);
    return load(id);
  };
  const shops = clients.map((client) => createShop({ cache: valkeyCache(client), db, ttlMs: TTL_MS, stampede }));
  let n = 0;
  const reads = await paced({ rate: RATE, seconds: SECONDS }, async () => {
    const shop = shops[n++ % SERVERS]; // the load balancer takes turns
    const begin = performance.now();
    const { hit } = await shop.getProduct(1);
    return { ms: performance.now() - begin, hit };
  });
  const s = summarize(reads.map((r) => r.ms));
  const hitRate = (reads.filter((r) => r.hit).length / reads.length) * 100;
  for (const p of points) p[stampede] = started.filter((at) => at >= p.x - BUCKET && at < p.x).length;
  console.log(
    `${stampede.padEnd(9)}  ${String(db.stats.queries).padStart(10)}  ${String(db.stats.peakWaiting).padStart(9)}` +
    `  ${hitRate.toFixed(1).padStart(7)}%  ${s.p50.toFixed(1).padStart(6)}  ${s.p99.toFixed(1).padStart(6)}  ${s.max.toFixed(1).padStart(7)}`
  );
}
clients.forEach((c) => c.close());

console.log("\nqueries started in each half second");
console.log("   at s" + ["none", "coalesce", "lock"].map((m) => m.padStart(10)).join(""));
for (const p of points) console.log(p.x.toFixed(1).padStart(7) + [p.none, p.coalesce, p.lock].map((q) => String(q).padStart(10)).join(""));

writeFileSync(new URL("./chart.svg", import.meta.url), lineChart({
  title: "Database queries for one hot key, per half second",
  xLabel: "seconds",
  yLabel: "queries",
  points,
  series: [
    { key: "none", color: "#dc2626" },
    { key: "coalesce", color: "#d97706" },
    { key: "lock", color: "#2563eb" },
  ],
}));
console.log("\nwrote chart.svg");
```

Start with the hit rate column, because it hides the problem. With no fix, 96.9% of reads hit, which sounds healthy. ## When something goes wrong

**`connect ECONNREFUSED 127.0.0.1:6379`.** Valkey is not running, or it runs on another port. Run `docker compose ps` in the challenge folder. If you changed `VALKEY_PORT` for Docker, set the same variable in the terminal where you run the scripts.

**The script never ends.** A command waits for a reply that never comes, usually because the container stopped mid-run. Press Ctrl+C, check `docker compose ps`, and run again.

**`OOM command not allowed when used memory > 'maxmemory'`.** Valkey is full and its policy is `noeviction`, the default. You started a container without the `command` line from `compose.yaml`. Run `docker compose up -d` again from the challenge folder; Docker recreates the container with the right settings.

**The hit rate in part 1 stays near 0%.** Check that `getProduct` stores the copy after a miss and that the key is the same string for the get and the set. `product:1` and `product: 1` are different keys.

**Part 3 shows 2 queries for some expiries with the lock.** The first version of this lock, written for this course, did exactly that. A server can miss the cache just before the lock holder stores the page, and win the lock just after the holder releases it. It then loads the page again. The fix is the "look once more" line in `loadWithLock`: after winning the lock, read the cache before loading. If you removed it, put it back.

**A lock that outlives its 2-second lifetime.** If a lock holder stalls for longer than 2 seconds, its lock expires, another server takes a new one, and the first server's `del` can then delete the second server's lock. That is fine for this challenge but not for anything that must run exactly once. Module 12 teaches the fix, fencing tokens.

**Break it on purpose.** In `shop.js`, comment out the `cache.del` line in `updatePrice` and run `npm test`. Two tests fail: "a price change deletes the copy, so the next read is fresh" and "delete on write closes the stale window". Undo it. Then make `loadCoalesced` skip the map and just `return loadAndStore(id);`, and watch the coalescing test fail with `expected: 2` and `actual: 20`. Undo that too.
