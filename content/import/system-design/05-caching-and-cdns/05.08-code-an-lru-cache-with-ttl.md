In chapters 5.4 to 5.6 you watched a cache drop the least recently used item, saw copies expire after their TTL, and met the short in-memory copy an app server keeps to protect a hot key. All three ideas meet in one small piece of code: a cache that lives inside your process, holds at most a fixed number of items, and forgets each item after its lifetime. Many apps have one, and most libraries that provide one are a few hundred lines. In this chapter you write the core of it yourself, so you know exactly what it does at its edges.

By the end you will have a tested JavaScript class, `LruTtlCache`. It holds at most `capacity` items. `get(key)` returns a live value, or `undefined` for a miss. `set(key, value, ttlMs)` stores a value that lives for `ttlMs` milliseconds. When a new key would not fit, the cache first drops expired items, then the least recently used live one. It counts hits, misses and evictions, so you can read its hit rate. And it never calls `Date.now()` itself: it asks a clock function you pass in, which is what makes it testable.

## Why the clock is passed in

A cache with a TTL depends on time, and time is awkward in tests. If your code calls `Date.now()`, a test that checks "the item is gone after 60 seconds" must really wait 60 seconds, or it cannot check expiry at all. Tests that wait are slow, and tests that depend on the real clock are flaky: a busy test machine can make a "1 ms later" check land 15 ms later.

The fix is to inject the clock. The constructor takes a function `now` that returns the current time in milliseconds. In production you pass `() => Date.now()`. In a test you pass a fake clock: a variable you move by hand.

```js
let t = 0;                       // the fake time, in ms
const cache = new LruTtlCache(2, () => t);
cache.set("a", 1, 1000);         // lives until t = 1000
t = 999;  cache.get("a");        // 1: still alive
t = 1000; cache.get("a");        // undefined: expired exactly now
```

The tests on the server work this way, so a learner's code that calls `Date.now()` inside the class will fail them: the fake clock moves, but the real one barely does. You may have met the same idea in module 3, where a DNS resolver cache also takes a fake clock.

## The contract

Fix the rules before writing code, including the awkward cases. The tests check these exact rules.

**Construction.** `new LruTtlCache(capacity, now)`. The capacity must be a whole number of at least 1; anything else throws a `RangeError`. A cache with room for zero items, or for 2.5 items, is a bug in the caller, and failing loudly at once is better than a cache that silently stores nothing. If `now` is not given, use `() => Date.now()`.

**Expiry.** An item stored at time `s` with `ttlMs` lives while the clock is before `s + ttlMs`. At exactly `s + ttlMs` it is expired. `ttlMs` must be a number above 0 that is finite; zero, negative numbers, `NaN` and `Infinity` throw a `RangeError`. Expired items are removed when you meet them, which is called lazy expiry. You do not need a timer that wakes up and removes them.

**get(key).** If the key is stored and alive, return its value, count a hit, and make it the most recently used item. If the key is missing, or stored but expired, count a miss and return `undefined`. An expired item found this way is removed.

**set(key, value, ttlMs).** If the key is already stored, replace its value and lifetime, and make it the most recently used. That never evicts anything, because the key already had a place. If the key is new and the cache is full, first remove every expired item. If it is still full, evict the least recently used live item and count one eviction. Then store the new item as the most recently used. Values are never `undefined`.

**delete(key)** removes the key and returns `true` if it was stored, `false` otherwise. **size()** returns the number of live items: stored and not expired at the current time. **stats()** returns `{ hits, misses, evictions }`. Items removed because they expired are not evictions: eviction means "removed for space while still alive".

## A worked example: two exchange rates

Here is the contract applied by hand to a case that is not in the tests: a cache with room for 2 items that holds currency exchange rates for 10 minutes (600,000 ms). The times below are in seconds, to keep them short.

<MermaidDiagram title="Map order, oldest use first, as the cache runs" chart={`flowchart TD
  A["t = 0 s: set USD, lives to 600 s. Order: USD"] --> B["t = 10 s: set EUR, lives to 610 s. Order: USD, EUR"]
  B --> C["t = 20 s: get USD, hit. Move to the end. Order: EUR, USD"]
  C --> D["t = 30 s: set GBP. Full, nothing expired. Evict the first: EUR. Order: USD, GBP"]
  D --> E["t = 700 s: get USD. Expired at 600 s: remove, miss. Order: GBP"]
`} legend="A JavaScript Map keeps keys in insertion order. Deleting a key and setting it again moves it to the end, so the first key is always the least recently used." />

The subgoal at each step is to keep the items in order of last use, oldest first. A JavaScript `Map` does most of the work. It remembers the order in which keys were inserted, and `map.keys().next().value` gives the first, oldest key. To mark a key as just used, delete it and set it again: it moves to the end.

Step by step: at 0 s, USD goes in. At 10 s, EUR goes in after it. At 20 s, a read of USD is a hit, so USD is deleted and set again, and the order becomes EUR, USD. At 30 s, GBP arrives and the cache is full. First look for expired items: USD lives until 600 s and EUR until 610 s, so neither has expired. Evict the first key in the map, EUR, and count one eviction. The order is now USD, GBP. At 700 s, a read of USD finds an item that expired at 600 s. Remove it, count a miss, and return `undefined`. The stats are 1 hit, 1 miss, 1 eviction.

Notice what the read at 20 s did. Without it, USD would have been the oldest at 30 s, and USD would have been evicted instead of EUR. Recency on read is the whole difference between LRU and "first in, first out".

## Three ways this goes wrong

**Forgetting recency on a read.** If `get` returns the value without moving the key to the end, the cache evicts in the order items were stored, not used. It still passes simple tests, and it loses hot keys in production, exactly the problem LRU exists to avoid. One test reads an old key and then forces an eviction to catch this.

**Evicting a live item while an expired one takes space.** If the cache is full of items and one of them has expired, the right move is to drop the expired one, which is useless anyway, and keep every live one. Code that always evicts the first key in the map can throw away a fresh, popular item while a dead one stays. One test stores an item with a short TTL first, lets it expire, and checks that it, not the live item behind it, makes room.

**Off by one at the moment of expiry.** "Lives for 1,000 ms" must mean one exact rule. This chapter's rule is: alive while `now < storedAt + ttlMs`. Writing `<=` keeps the item for one extra millisecond. That sounds harmless, but a test at the exact boundary fails, and in a real system two parts of the code that disagree about the boundary will disagree about whether a copy is fresh. Decide once, write it down, and test the boundary on both sides.

solution: |
  class LruTtlCache {
    constructor(capacity, now = () => Date.now()) {
      if (!Number.isInteger(capacity) || capacity < 1) {
        throw new RangeError("capacity must be a whole number of at least 1, got " + capacity);
      }
      this.capacity = capacity;
      this.now = now;
      this.items = new Map(); // key -> { value, expiresAt }, oldest use first
      this.counts = { hits: 0, misses: 0, evictions: 0 };
    }

    get(key) {
      const item = this.items.get(key);
      if (item === undefined || this.now() >= item.expiresAt) {
        if (item !== undefined) this.items.delete(key);
        this.counts.misses++;
        return undefined;
      }
      this.items.delete(key);
      this.items.set(key, item);
      this.counts.hits++;
      return item.value;
    }

    set(key, value, ttlMs) {
      if (typeof ttlMs !== "number" || !Number.isFinite(ttlMs) || ttlMs <= 0) {
        throw new RangeError("ttlMs must be a finite number above 0, got " + ttlMs);
      }
      const now = this.now();
      if (this.items.has(key)) {
        this.items.delete(key);
      } else if (this.items.size >= this.capacity) {
        for (const [k, item] of this.items) {
          if (now >= item.expiresAt) this.items.delete(k);
        }
        if (this.items.size >= this.capacity) {
          this.items.delete(this.items.keys().next().value);
          this.counts.evictions++;
        }
      }
      this.items.set(key, { value, expiresAt: now + ttlMs });
    }

    delete(key) {
      return this.items.delete(key);
    }

    size() {
      const now = this.now();
      let live = 0;
      for (const item of this.items.values()) if (now < item.expiresAt) live++;
      return live;
    }

    stats() {
      return { ...this.counts };
    }
  }

## What this unlocks

The cache you wrote is the in-process layer from chapter 5.2 and the short local copy that shielded a hot node in chapter 5.6. Real apps use a library for it, with the same core and more features: a size limit in bytes instead of items, a callback when an item is evicted, and a "stale but usable" window for the stale-while-revalidate idea. You now know what such a library does on every call, and which edge cases to look for in its documentation.

The habit carries over to everything with a clock. In challenge 4 you measure a real Valkey cache, where you cannot inject the clock, so you control time the other way round: you choose short TTLs and run the experiment for long enough to see many expiries. Later modules meet clocks again in leases, timeouts and retries, and the same rule holds there: decide what happens at the exact boundary, and make time something your tests can control.
