Matjar's admin drops the sale phone's price from 999 to 899. For how long can a shopper still see 999? That time is the <GlossaryTerm term="stale window" definition="The time during which a cache can return an old value after the source of truth has changed. Invalidation is about making this window short and bounded." />, and each way of invalidating a cache gives a different one.

## TTL alone: stale until expiry

<InteractiveCanvas slug="sysdesign-m5-ttl-stale" />

The price changes at 0 s. The cache got its copy of 999 just before, with a 60-second TTL. Nothing tells the cache that the database changed, so at 20 s a shopper still sees 999. Only when the copy expires at 60 s does the next read load 899. With a TTL alone, the stale window can be the whole TTL.

<GoDeeper title="Go deeper: when a TTL alone is the right choice">

A TTL alone is the simplest kind of invalidation: no code runs on a write. Each copy is trusted for a fixed time and then reloaded. AWS's ElastiCache guide describes the TTL as the way to bound how stale lazy-loaded data can get.

The worst case is the one in the picture: the copy was stored just before the write, so it stays wrong for the full TTL. If writes come at random times, the average stale window is shorter, about half the TTL, but users notice the worst case, not the average.

So pick the TTL from what a wrong answer costs. A product description that is 60 seconds old harms nobody, and a TTL alone is fine. A price that is 60 seconds old means a shopper sees 999 and pays 899 at checkout, or the other way round, which the shop must handle. A stock count that is 60 seconds old during a sale sells phones that are gone.

A TTL also has a cost on the other side. A short TTL means more misses, so a lower hit rate and more database load, even when nothing changed. Challenge 4 has you measure exactly this trade: hit rate against stale reads as the TTL changes.

</GoDeeper>

## Delete on write shrinks the window

<InteractiveCanvas slug="sysdesign-m5-delete-window" />

Now the app deletes the copy right after the commit. The copy is wrong only between the commit and the end of the delete: one cache command, about 0.5 ms. The next read misses and loads 899. The stale window drops from up to 60 seconds to under a millisecond, as long as the delete arrives.

<GoDeeper title="Go deeper: when the delete does not arrive">

Delete-on-write is what Facebook's memcache does: update the database, then delete the key. It works only if the delete happens. Three things can stop it.

**The app crashes between the commit and the delete.** The database has 899 and the cache keeps 999 until the TTL ends. This is why a delete-on-write cache still sets a TTL: it is the safety net that bounds the damage when a delete is lost.

**The delete fails.** The cache node is slow or briefly unreachable, and the delete times out. Retrying is safe, because deletes are idempotent, which is the reason Facebook gives for deleting instead of updating. Retry a few times, then log it; the TTL catches the rest.

**Another copy is not deleted.** The app deletes the Valkey key, but app servers also keep a few seconds of copies in memory, and the CDN keeps the page for its own lifetime. Each layer from chapter 5.2 needs its own answer.

There is also a fourth case, which the delete does arrive for and still loses. The next beat shows it.

</GoDeeper>

## The race: a slow reader wins

<InteractiveCanvas slug="sysdesign-m5-stale-set-race" />

The reader misses and reads 999 at 10 ms, then is slow. The writer commits 899 at 20 ms and deletes the key at 25 ms. At 40 ms the reader stores the 999 it read earlier into the empty cache. The delete came and went, and the old price is back until the TTL ends. Facebook calls this a stale set.

<GoDeeper title="Go deeper: why the race happens at scale">

The race needs a reader that is slow between its database read and its cache set, while a write and a delete pass in between. Many things make a reader slow for a few milliseconds: a garbage collection pause in the app (when the runtime stops the program to free memory), a busy CPU, a slow network packet, a retry.

For one read the chance is small. But a hot key at Matjar is read thousands of times a second and its price changes during the sale. Every write opens a gap a few milliseconds wide, and with thousands of reads going on, some reader is almost always inside a gap. Facebook's paper lists stale sets as one of the two problems it built leases to solve.

Notice what does not fix it. Deleting twice does not help, because the stale set comes after both deletes. Writing 899 into the cache instead of deleting has the same race the other way round: two writers can arrive in the wrong order. Making the TTL shorter limits how long the old price lives but does not stop it.

What does fix it is a rule in the cache: refuse a set that is based on a read older than the last delete. The next two beats show two ways to get that rule.

</GoDeeper>

## Move the slow reader, find the race

<InteractiveCanvas slug="sysdesign-m5-stale-race" />

Drag the reader's late set along the timeline and watch what the cache holds at the end. If the set lands before the delete, the delete removes it and the window is a few milliseconds. If it lands after the delete, the old price stays until the TTL. Then switch leases on and drag again.

<GoDeeper title="Go deeper: the three outcomes on the timeline">

The timeline has fixed points: the reader reads at 10 ms, the writer commits at 20 ms and deletes at 25 ms. Only the reader's set moves.

**Set before 20 ms.** The cache holds 999, which is still correct, because the price has not changed yet. At 20 ms it becomes stale, and at 25 ms the delete removes it. Stale window: 5 ms.

**Set between 20 and 25 ms.** The cache holds 999 from the set until the delete removes it at 25 ms. Stale window: the few milliseconds to the delete.

**Set after 25 ms.** The delete has already happened, so nothing removes the set. The cache holds 999 until its TTL ends. Stale window: up to the whole TTL, 60 seconds here.

So the danger is entirely in the order of two events: the delete and the stale set. With leases on, the cache refuses any set whose lease was cancelled by a delete, so the third case also ends with an empty cache, and the next read loads 899.

The same reasoning tells you what to measure. If your monitoring compares cached values with the database now and then, a stale value that lives for a whole TTL right after a write is the sign of this race.

</GoDeeper>

## A lease turns the late write away

<MermaidDiagram title="Facebook-style leases stop a stale set" chart={`sequenceDiagram
  participant R as Reader app
  participant C as Cache
  participant D as Database
  participant W as Writer app
  R->>C: get p42
  C-->>R: miss, lease token 7
  R->>D: read p42
  D-->>R: 999
  W->>D: update p42 to 899
  W->>C: delete p42
  Note over C: the delete cancels token 7
  R->>C: set p42 = 999 with token 7
  C-->>R: refused, token 7 is no longer valid
`} legend="A miss hands out a lease token. A delete cancels it. A set must show a valid token, so a set based on a read from before the delete is refused." />

On a miss, the cache hands the reader a lease token. The writer's delete cancels that token. When the slow reader finally tries to store 999, it shows token 7, which is no longer valid, so the cache refuses the set. The cache stays empty, and the next reader loads 899 from the database.

<GoDeeper title="Go deeper: one tool for two problems">

Facebook's memcache paper introduced leases to solve two problems at once: stale sets, shown here, and thundering herds, which chapter 5.6 covers. A lease is a small token the cache gives to a client that missed. It is the client's right to fill that key. A delete invalidates every lease for that key, so a set that relies on data from before the delete carries a dead token and is refused.

For thundering herds, the same token limits who may fill a key. The cache hands out a lease for a key at most once every 10 seconds. Other clients that miss in that time are told to wait a moment and try again, by which time the copy is usually there. In one of Facebook's tests, this cut peak database queries from 17,000 a second to 1,300.

You can build a similar rule with ordinary cache commands. The reader stores a version number with its value, and the set uses a compare-and-set that only writes if the version in the cache is not newer. Chapter 7 teaches compare-and-set in depth. The simplest alternative, if your cache has no leases, is the one in the next beat: give each version its own key.

</GoDeeper>

## Versioned keys never go stale

<InteractiveCanvas slug="sysdesign-m5-versioned-keys" />

Here every write raises the product's version, from v7 to v8, and the cache key includes it. A reader asks for the current version first, then reads `p42:v8`. The old copy under `p42:v7` is never read again, so there is nothing to delete, and a late set of v7 cannot hurt anyone. It expires on its own.

<GoDeeper title="Go deeper: what versioned keys cost">

Versioned keys turn invalidation into naming. A copy under a version's key is never wrong for that version, so it never needs deleting. The stale set from the race writes an old version's key, which no reader asks for.

The cost is the version lookup. Every read must learn the current version before it knows which key to read. That lookup must itself be cheap and fresh: a small version number in the database row the page already loads, a tiny version key in the cache that is updated on write, or a version the client already holds. If the version lookup is itself cached and stale, the old key comes back.

The second cost is memory. Old versions stay until they expire or are evicted, so give them a TTL. Under memory pressure, LRU removes them first, since nobody reads them.

CDNs use the same idea for files, which chapter 5.7 shows: a new stylesheet ships as `app.v2.css`, and no edge ever needs to be told to drop `app.v1.css`. For data, versioned keys work best for things that are read far more than they change, such as a product page or a category list. The idea is the same as for files; the dossier has no separate source for its use with data caches.

</GoDeeper>
