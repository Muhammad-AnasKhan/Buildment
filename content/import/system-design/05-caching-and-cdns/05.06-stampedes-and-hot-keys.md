## A hot key expires: everyone misses

<InteractiveCanvas slug="sysdesign-m5-herd" />

The copy expires. The first request misses and starts the page query, which takes 50 ms. Until it returns, every new request also misses and sends the same query. At 5,000 requests a second, 50 ms brings 250 of them. The database gets 250 copies of one query for one key, and the cache gets nothing until the first one finishes.

<GoDeeper title="Go deeper: counting the herd with Little's law">

A <GlossaryTerm term="hot key" definition="One cache key that gets a large share of all reads, such as the page of a product on sale. Its expiry, or the node that holds it, can become the bottleneck of the whole system." /> is the case where a stampede hurts. A key read once a minute that expires causes one miss. A key read 5,000 times a second causes a crowd.

The size of the crowd is Little's law from chapter 2.5: requests in the system equal the arrival rate times the time each one stays. Here the "system" is the gap between the expiry and the moment the copy is stored again. The rate is 5,000 a second and the gap is the 50 ms rebuild, so 5,000 x 0.05 = 250 duplicate queries.

The real number is usually worse. 250 heavy queries at once slow the database, so the rebuild takes longer than 50 ms, so the gap grows, so more requests miss. If the rebuild slows to 200 ms, the herd is 1,000 queries. That is the loop from chapter 5.1.

The 2015 paper on cache stampedes by Vattani, Chierichetti and Lowenstein defines the problem the same way: when a hot item expires, many requests try to regenerate it at the same time. Every fix in this chapter attacks one part of the formula: fewer requests allowed to rebuild, a rebuild nobody waits for, or expiries that do not line up.

</GoDeeper>

## Coalescing: one query, many waiters

<InteractiveCanvas slug="sysdesign-m5-coalesce" />

With coalescing, the first miss for a key starts the query, and every other request for that key waits for the same answer. On one app server, the database sees one query instead of 250. Matjar has 20 app servers, and each coalesces on its own, so the database sees 20. A lock shared through the cache brings it down to one.

<GoDeeper title="Go deeper: single-flight in code, and a fleet-wide lease">

Coalescing on one server is a few lines of JavaScript. Keep a map of queries in flight, keyed by cache key. A request that finds a promise already in the map waits on it instead of starting a new query. This pattern is often called single-flight.

```js
// Coalesce misses on one server: one load per key at a time.
const inFlight = new Map();

async function loadOnce(key, load) {
  if (inFlight.has(key)) return inFlight.get(key); // join the query in flight
  const p = load().finally(() => inFlight.delete(key));
  inFlight.set(key, p);
  return p;
}
```

Every server has its own map, so the fleet sends one query per server. To go from 20 to 1, the servers must agree on who rebuilds. Facebook's memcache does it with leases: on a miss, the cache hands out a lease token for a key at most once every 10 seconds. A client without the token waits a short time and asks the cache again, by which time the copy is usually back.

A simpler version uses a lock key in the shared cache. The first server to set `lock:p42` with "set only if it does not exist" and a short lifetime rebuilds the page; the others wait a few milliseconds and read the cache again. The lock's lifetime matters: if the rebuilding server dies, the lock must expire so another can try. Challenge 4 has you build this lock with Valkey and count the queries.

</GoDeeper>

<RealWorldEvent title="Facebook's leases tame thundering herds" when="NSDI 2013 paper" summary="Facebook's memcache fleet saw hot keys under heavy read and write load hammer the database whenever a key was missing. They added leases: the cache hands out the right to fill a key at most once every 10 seconds, and other clients wait and retry." lesson="In one of their tests, peak database queries fell from 17,000 a second to 1,300. Limiting who may rebuild a key is worth more than a faster database." />

## Serve stale, refresh once

<InteractiveCanvas slug="sysdesign-m5-swr" />

Coalescing still makes 250 shoppers wait 50 ms. Stale-while-revalidate removes the wait. The copy is a little past its fresh time but still usable, so shoppers get it at once, and one background request refreshes it. When the new page arrives, it replaces the old one. Nobody waited for the database, and only one query ran.

<GoDeeper title="Go deeper: two lifetimes instead of one">

`stale-while-revalidate` comes from RFC 5861, an HTTP standard. It gives a response two lifetimes. During the fresh lifetime, the copy is used as it is. During a second, stale lifetime, the copy may still be served at once, but the cache starts a refresh in the background. After both run out, the copy is no longer used. A sibling directive, `stale-if-error`, lets a cache keep serving a stale copy when the origin returns errors, which turns an outage into old data instead of an error page.

The same idea works inside an app cache. Store each value with a "fresh until" time that is earlier than its real expiry. A read after "fresh until" returns the value and starts one refresh, coalesced as in the previous beat so that only one refresh runs.

The 2015 stampede paper goes one step further with probabilistic early expiration, which it calls XFetch. Each request that reads a copy close to its expiry decides at random whether to refresh it early, with a chance that grows as expiry gets closer. One request usually refreshes the copy just before it expires, and nobody ever sees a miss. The paper proves this choice of chance is optimal under its model.

The cost of every "serve stale" idea is in the name. A shopper may see a page that is a few seconds old. That is fine for a description or a review count, and wrong for anything the shopper will act on, such as the last item in stock.

</GoDeeper>

## Same TTL, same second

<InteractiveCanvas slug="sysdesign-m5-expiry-lineup" />

After a restart, Matjar's app caches 1,000 product pages in the same second, each with a 60-second TTL. Sixty seconds later, all 1,000 expire together, and the database gets 1,000 misses at once. Give each copy a random TTL between 54 and 66 seconds instead, and the same misses arrive over 12 seconds: about 83 a second.

<GoDeeper title="Go deeper: why randomness helps, and how much to add">

This is a stampede of many keys instead of one. No single key is hot, but copies that were stored together expire together. It happens after a restart, after a deploy that empties the cache, after a bulk import, or after a cache node is replaced.

The fix is the same idea as retry jitter in module 16: when many clients would act at the same moment, add randomness so they spread out. Marc Brooker's AWS article compares ways to add jitter to retries; the reasoning carries over. Here, instead of `ttl = 60`, use `ttl = 60 * (0.9 + 0.2 * Math.random())`, which gives a lifetime from 54 to 66 seconds. The dossier found no primary source that names this practice for TTLs, so treat it as reasoning, not as a citation.

How much jitter to add is a trade-off. More spread means a smoother load, but a less predictable lifetime. This chapter uses 10% each way. What matters is that the spread is wide compared to how long the database needs to answer the burst: 1,000 misses spread over 12 seconds is about 83 a second, well under the 800 a second Matjar's database can manage.

Jitter does nothing for one hot key. A single key expires once, whatever its TTL. One hot key needs coalescing, a lease or stale-while-revalidate. Jitter is for many keys that would otherwise expire in step.

</GoDeeper>

## Toggle the fixes, watch the database

<InteractiveCanvas slug="sysdesign-m5-stampede-toggles" />

Matjar's hot key expires every minute in this picture. Switch each fix on and off and watch the queries that reach the database at each expiry, and how long shoppers wait. Try coalescing alone, then the shared lease, then stale-while-revalidate. Then switch to 1,000 keys stored together and try random TTLs.

<GoDeeper title="Go deeper: which fix for which stampede">

Each fix attacks a different part of the problem, and they combine.

| Fix | What it cuts | Queries per expiry (20 servers) | Shoppers wait for the rebuild? |
|---|---|---|---|
| None | Nothing | about 250, more as the database slows | Yes |
| Coalescing per server | Duplicate queries on one server | about 20 | Yes |
| Shared lease or lock | Duplicate queries across servers | 1 | Yes, or retry briefly |
| Stale-while-revalidate | The wait | 1 with a lease | No |
| Random TTLs | Many keys expiring together | spreads the misses | Not a fix for one key |

A production cache for a sale page usually uses three of them: a shared lease so one server rebuilds, stale-while-revalidate so nobody waits, and random TTLs for the many ordinary keys. The numbers in the picture are Matjar's story numbers: 5,000 reads a second, a 50 ms rebuild, 20 app servers, and a database that manages about 800 page queries a second.

</GoDeeper>

## A hot key can melt one node

<InteractiveCanvas slug="sysdesign-m5-hot-node" />

A cache cluster spreads keys over its nodes, but every read of one key goes to the one node that holds it. The sale page's key sends 5,000 reads a second to node 1 while node 2 is idle. Keeping a 1-second copy in each app server's own memory takes almost all of those reads off node 1.

<GoDeeper title="Go deeper: hashing spreads keys, not reads">

Cache clusters decide which node holds a key by hashing the key, often with consistent hashing, which was first designed for exactly this kind of distributed cache. It spreads keys evenly over nodes. It cannot split one key: every read of `page:phone-x` hashes to the same node. A common myth is that consistent hashing removes hot spots. It balances key ranges, not a single hot key, and hot partitions remained a top problem in DynamoDB's own history (module 9).

Two fixes are common. **A short local copy.** Each app server keeps the hot page in its own memory for about a second. Twenty app servers then send about 20 reads a second to node 1 instead of 5,000. The price is up to a second of staleness on each server, and copies that cannot be deleted from outside. **Several copies in the cluster.** Store the hot page under several keys, such as `page:phone-x:1` to `page:phone-x:4`, which hash to different nodes, and have each read pick one at random. Each node now takes a quarter of the reads. The price is that a write must update or delete all the copies.

You need to know which keys are hot to use either fix. Watch the busiest keys per node, and treat a sale or a launch as a hot key you can see coming.

</GoDeeper>
