A server that is 90% busy sounds efficient: only 10% wasted. This chapter shows why requests on that server wait five times longer than on one that is 50% busy, and gives you one formula to reason about any queue.

## More in than out: the queue grows

<InteractiveCanvas slug="sysdesign-m2-queue-grows" />

Two requests arrive every second. The server finishes one per second. Every second, one more request joins the line, and the line never stops growing. When arrivals beat service for good, no amount of waiting fixes it: requests time out, memory fills, and the server falls over. Capacity must be above the arrival rate.

<GoDeeper title="Go deeper: arrival rate, service rate and utilisation">

Three numbers describe a simple queue. The <GlossaryTerm term="arrival rate" definition="How many requests arrive per second, written with the Greek letter lambda. For example 90 requests per second." /> is written lambda. The service rate is how many requests one server can finish per second when it never stops, written mu (the Greek letter). A server that needs 10 ms per request has mu = 100 per second.

<GlossaryTerm term="Utilisation" definition="The share of time a server is busy, written rho: arrival rate divided by service rate. 90 arrivals per second on a server that can do 100 per second is 90% utilisation." /> is lambda divided by mu, written rho. It is the share of time the server is busy. In this picture, lambda is 2 per second and mu is 1 per second, so rho would be 2, or 200%. Any rho at or above 100% means the queue grows without limit.

Real systems do not grow forever. Something gives way first: a queue limit drops new requests, clients time out and retry (which adds even more arrivals, module 16), or the process runs out of memory. Each failure looks different on a dashboard, but the cause is the same arithmetic: more in than out.

</GoDeeper>

## Half idle, and still a line

<InteractiveCanvas slug="sysdesign-m2-bursts-wait" />

Now the server is fast enough on average: it is busy only half the time. But three requests arrive at once, then nothing for a while. The first is served at once, the second waits one second, the third waits two. Requests do not arrive evenly, so a queue forms long before the server is full.

<GoDeeper title="Go deeper: why randomness creates waiting">

If requests arrived perfectly evenly, one every 20 ms on a server that needs 10 ms each, no request would ever wait. Each would find the server idle. Real arrivals are not even. Users act independently, so sometimes three arrive within a millisecond and sometimes none arrive for 100 ms. Service times vary too: one request reads from cache, the next misses and goes to disk.

The bursts are what make requests wait. During a burst, requests pile up; during a gap, the server sits idle, and that idle time cannot be saved and used later. The busier the server is on average, the less idle time it has to clear each burst before the next one comes, so queues from one burst run into the next.

The standard model for this is the M/M/1 queue: random arrivals (the first M), random service times (the second M) and one server (the 1). It is simple enough to give exact formulas, which the next beat uses. Marc Brooker notes that real systems do not match its assumptions exactly. Use it to understand the shape of the curve, then measure your own system, as you will in challenge 1.

</GoDeeper>

## The knee: waiting explodes near full

<InteractiveCanvas slug="sysdesign-m2-knee-play" />

Drag requests a second toward the server's limit of 100. At 50 a second, 1 request is inside and each spends 20 ms. At 90, the line holds 9 and the wait is 100 ms. At 99, it is a full second. Halve the spare room and the wait doubles. Watch Little's law hold at every point: inside equals rate times time.

<GoDeeper title="Go deeper: the formula, and why p99 warns you first">

For the M/M/1 queue, the average time a request spends in the system (waiting plus service) is W = 1 / (mu - lambda). The average number of requests in the system is L = rho / (1 - rho). Both come from the MIT queueing notes in the sources.

With mu = 100 per second (10 ms per request):

- lambda = 50: W = 1 / 50 s = 20 ms, and L = 0.5 / 0.5 = 1.
- lambda = 90: W = 1 / 10 s = 100 ms, and L = 0.9 / 0.1 = 9.
- lambda = 99: W = 1 / 1 s = 1,000 ms, and L = 0.99 / 0.01 = 99.

The term mu - lambda is the spare capacity. The wait depends on it, not on how busy the server is. Going from 50% to 90% busy cuts spare capacity from 50 to 10 per second, five times less, so the wait grows five times. Going from 90% to 99% cuts it ten times more. That is why the last few percent of utilisation are so expensive, and why "we run at 90%, it is efficient" is a trap.

These are averages. The slow tail grows faster still: in an M/M/1 queue, the time in system is spread out so that its p99 is several times its mean. Brooker points out that high-percentile latency is a leading indicator of overload: p99 starts to climb before the average looks bad. Watch p99 to see the knee coming.

Where should you run? There is no single number; it depends on how bursty your traffic is and how much latency you can accept. Measure your own curve, as you will in challenge 1, and choose a target utilisation that keeps p99 within your goal with room for a peak.

</GoDeeper>

## Little's law: L = λW

<InteractiveCanvas slug="sysdesign-m2-littles-law" />

Requests arrive at 200 per second, and each one stays 50 ms. So, on average, 200 times 0.05 gives 10 requests inside the server at any moment. That is Little's law: the number inside (L) equals the arrival rate (lambda) times the time each one stays (W). It works for any stable queue.

<GoDeeper title="Go deeper: why Little's law is so useful">

<GlossaryTerm term="Little's law" definition="L = lambda W: the average number of items in a system equals the average arrival rate times the average time each item spends in the system. It holds for any stable system, whatever the arrival pattern or order of service." /> says L = lambda W. John Little proved it, and in a 2011 paper marking its 50th anniversary he stresses how little it assumes: it holds over a finite window even if the system is never empty, needs no assumptions about how arrivals or service times are distributed, and does not care in what order requests are served.

Units keep it honest. Lambda in requests per second times W in seconds gives L in requests. 200 per second times 0.05 seconds is 10 requests. If you mix milliseconds and seconds, you are off by 1,000.

You can solve it for any one of the three numbers:

- **How many in flight?** L = lambda W. 200 per second, 50 ms each: 10 in flight.
- **How long do they stay?** W = L / lambda. If a dashboard shows 30 requests in flight at 600 per second, each stays about 50 ms, without timing a single request.
- **How much traffic can we take?** lambda = L / W. If a server can hold at most 100 requests in flight and each takes 0.2 s, it can take at most 500 per second.

It also checks the M/M/1 numbers: at 90 per second and 100 ms each, L = 90 times 0.1 = 9 requests in the system, the same as rho / (1 - rho) = 9. In challenge 1 you will measure L, lambda and W on your own server and see the law hold.

</GoDeeper>

## Size a pool with Little's law

<MermaidDiagram title="How many database connections does the API need?" chart={`flowchart TD
  A["300 requests per second"] -->|"× 0.02 s holding a connection"| B["L = 6 connections busy on average"]
  B --> C{"Pool size?"}
  C -->|"5 connections"| D["Fewer than 6: the queue grows without end"]
  C -->|"10 connections"| E["60% busy: room for bursts and peaks"]
`} legend="Little's law gives the average number in use. A pool smaller than that can never keep up; a pool near it sits at the knee." />

An API handles 300 requests a second, and each holds a database connection for 20 ms. Little's law says 6 connections are busy on average. A pool of 5 can never keep up: the first beat again. A pool of 10 runs at 60% busy and leaves room for bursts.

<GoDeeper title="Go deeper: pools, workers and threads">

Any limited resource that requests hold for a while is a small queue: database connections, worker threads, open files, seats in a waiting room. Little's law gives the average number in use, L = lambda W, and the knee tells you not to provision exactly that.

The working: 300 requests per second times 0.02 seconds is 6. So on average 6 connections are in use. With a pool of 5, utilisation would be 6 / 5 = 120%, above 100%, so the wait for a connection grows without end, exactly like the first picture in this chapter. With a pool of 6, utilisation is 100% and the wait still grows without limit, because bursts never get cleared. With 10, utilisation is 60%, below the knee.

Bigger is not always better. A database also has a limit on how many connections it can serve well; ten API servers each with a pool of 10 open 100 connections. The database's own work per query then becomes the queue. Little's law works on that queue too: if the database can run 50 queries at once and each takes 20 ms, it can do at most 50 / 0.02 = 2,500 queries a second.

The law also explains a common failure. If the database slows down so each query takes 100 ms instead of 20, the same 300 requests per second now need 300 times 0.1 = 30 connections. A pool of 10 is suddenly far too small, requests queue for a connection, and the API looks broken even though it did nothing wrong. Slowness downstream turns into more requests in flight upstream.

</GoDeeper>
