A nanosecond (ns) is a billionth of a second, and a microsecond (µs) is a thousand of them. Numbers that small are hard to feel. So in this chapter, every nanosecond lasts one human second.

## A cache hit takes one human second

<InteractiveCanvas slug="sysdesign-m2-cache-vs-memory" />

The CPU needs two values. Value a is in its L1 cache, a tiny memory inside the CPU, and arrives in 1 human second. Value b is in main memory and takes 100 human seconds. Same machine, same kind of read, 100 times the wait. Keeping hot data close is the first idea behind every cache in this course.

<GoDeeper title="Go deeper: why memory is far away">

A CPU core runs a few billion simple steps a second. Colin Scott's latency model puts its clock at about 3 GHz, which is 3 steps every nanosecond, and an L1 cache hit at about 3 steps, or 1 ns. Main memory sits on separate chips across the board, and one reference to it costs about 100 ns in the same model. In the model, that number has stayed flat since about 2000, and the clock speed has stayed flat since about 2005.

The model is a model. Scott's page starts from timing numbers that Peter Norvig published around 2002 and grows or holds them by year with simple formulas. It is useful for feel, not as a benchmark of your laptop. Norvig's own table lists 0.5 ns for an L1 hit and 100 ns for memory, so the shape is the same: memory is about 100 to 200 times slower than L1.

Real CPUs fight this gap. They fetch memory ahead when they can guess what comes next, keep several reads in flight at once, and run other work while they wait. That is why reading an array from start to end is fast, and jumping around memory at random is slow. You will see the same idea at every level of a system: a sequential read is cheap, a random read is expensive.

</GoDeeper>

## One SSD read takes a human day

<InteractiveCanvas slug="sysdesign-m2-ssd-read" />

Your code asks the operating system's kernel for 8 KiB from an SSD. The request itself, a system call, costs 5 human minutes. The SSD read costs about 28 human hours. One read from a fast SSD is a full day of waiting, compared with a second for the cache. Reading from disk is a decision, not a detail.

<GoDeeper title="Go deeper: system calls, context switches and the page cache">

A <GlossaryTerm term="system call" definition="A request from your program to the operating system's kernel, for example to read a file or send on the network. It costs more than a normal function call because the CPU switches into the kernel and back." /> costs about 300 ns in the napkin-math table, which was partly re-measured in March 2026. A random 8 KiB read from an SSD costs about 100 µs. In human time that is 300 seconds (5 minutes) against 100,000 seconds (about 28 hours).

Two more rows from the same table help when you read profiles later. A context switch, when the operating system stops one thread and runs another, costs about 10 µs, which is about 2.8 human hours. Writing 8 KiB to an SSD and waiting until it is safely stored (fsync) costs about 300 µs, about 3.5 human days. That is why databases group many small writes into one flush.

Sequential reads are a different story. Reading 1 MB in a row from an SSD takes about 100 µs in the current table (about 8 GiB a second), about the same as one random 8 KiB read. Reading 1 MB in a row from memory takes about 50 µs. The old tables that many courses still copy say 1 ms for 1 MB from an SSD, ten times slower than today. Tables age, so always note the year.

Many reads never reach the SSD at all. The kernel keeps recently read file data in memory, called the page cache. A "disk read" that hits the page cache costs memory time, not SSD time. When you measure, check which one you really measured.

</GoDeeper>

## Next door: a cache query takes days

<InteractiveCanvas slug="sysdesign-m2-region-round-trip" />

Now the app server asks Redis, a cache on another machine in the same data centre region. The network round trip alone is about 3 human days. The whole query takes about 6. Asking a cache next door is still thousands of times slower than reading your own memory, so a page that makes 50 such calls one by one adds up fast.

<GoDeeper title="Go deeper: what a round trip is">

A <GlossaryTerm term="round trip" definition="A message going to another machine and the answer coming back. Its time (round-trip time, RTT) is the least any request to that machine can take, even when the work there is free." /> is the time for a message to reach another machine and for the answer to come back. Inside one cloud region, napkin-math puts a round trip at about 250 µs, and a simple Redis, Memcached or MySQL query at about 500 µs. A hop through a proxy such as nginx, Envoy or HAProxy adds about 50 µs.

In human time, 250 µs is 250,000 seconds, about 2.9 days, and 500 µs is about 5.8 days. Compare that with 100 seconds for a memory read. A cache server is fast compared with a database on disk, but it is far slower than memory in your own process. That is why some systems keep a small cache inside the app as well as a shared one.

Older tables give 500 µs for a round trip inside a data centre. Colin Scott's model keeps it as a constant 500 µs, and the System Design Primer copies the same value. The current napkin-math number is lower. Both are fine for estimates; pick one, say which, and keep going.

</GoDeeper>

## Across the world: years

<InteractiveCanvas slug="sysdesign-m2-across-the-world" />

A server in Western Europe asks for data in Singapore. The round trip is about 160 ms, which is 5 human years. Europe to the east coast of North America is about 2.5 years. Faster servers do not shrink this, because the time is spent travelling the distance. Only moving the data closer to the user does.

<GoDeeper title="Go deeper: distance is the cost you cannot optimise">

The napkin-math table gives these round trips between cloud regions: North America east to west about 60 ms, EU West to North America East about 80 ms, EU West to Singapore about 160 ms. The classic tables give 150 ms for California to the Netherlands and back, and Colin Scott's model keeps that number constant across the years, because better chips do not make the Earth smaller. {/* source needed: a citable reference that propagation delay over fibre dominates inter-region round-trip time */}

This changes designs. A user in Gaza whose request is served from a region in Western Europe pays tens of milliseconds per round trip before any work starts. A page that needs three round trips (a connection, a secure handshake, then the request itself, which module 3 counts in detail) pays that three times. Content delivery networks (module 5) and multi-region designs (module 19) exist mainly to cut this distance.

One more row is worth knowing: a GET of 128 KiB from blob storage such as S3 or Google Cloud Storage, over one connection, measured about 80 ms in March 2026. That is the same order as crossing the Atlantic, even inside one region, because the storage service does real work for each request. Object storage is cheap and huge, not fast.

</GoDeeper>

## The ladder on one page

<InteractiveCanvas slug="sysdesign-m2-latency-ladder" />

Watch the trip to Singapore while the counter fills: 1.6 million memory reads fit inside one round trip. Now tap SSD read, then Region trip: only 2.5 times apart. Tap any two rungs and read the band names under the ruler, not the units. Seconds and minutes stay inside one machine, days mean the network, years mean another continent.

<GoDeeper title="Go deeper: how to use the ladder in an argument">

The ladder is for comparing options, not for predicting exact times. The napkin-math author warns that some values are 2 to 3 times off and are rounded to keep the arithmetic easy. That is good enough to decide between designs whose costs differ by 10 times or more, which is most of the decisions in this course.

A useful habit: count the steps on the slowest rungs and ignore the rest. A request that makes 1,000 memory reads (100 µs in total) and one round trip across a region (250 µs) spends most of its time on the round trip. Making the memory reads twice as fast saves 50 µs; removing the round trip saves 250 µs.

To turn a real time into human time, multiply by one billion and read the answer in seconds. 250 µs is 0.000250 seconds; times one billion is 250,000 seconds. There are 86,400 seconds in a day, so that is about 2.9 days. There are about 31.5 million seconds in a year, so 160 ms (160 million human seconds) is about 5.1 years.

</GoDeeper>

## Twenty trips across the sea

<InteractiveCanvas slug="sysdesign-m2-chatty-page" />

The page asks 20 questions, one after another, and each waits for its own trip across the Atlantic. In one region the 20 queries take about 10 ms. Across the sea they take about 1.6 seconds. The code did not change. The fix is to move the server next to the database, or to ask everything in one query.

<GoDeeper title="Go deeper: chatty calls and how to fix them">

A page or service that makes many small calls in sequence is called chatty. Each call is cheap on its own, but each pays a full round trip, so the total grows with the number of calls times the distance. The arithmetic: 20 queries times 0.5 ms is 10 ms in one region; 20 times 80 ms is 1,600 ms across the Atlantic. Nothing about the queries changed, only where they travel.

There are three standard fixes, and each has a cost.

**Batch.** Ask for everything in one call: one SQL query with a join or an `IN` list, one Redis `MGET` for many keys. One round trip instead of twenty. The cost is code that is less simple to read and to cache.

**Run calls in parallel.** If the 20 queries do not depend on each other, send them at the same time and wait for all. The page then pays about one round trip, not twenty. The cost is the tail-latency problem in chapter 2.4: the page now waits for the slowest of 20 calls.

**Move the code to the data.** Put the app server in the same region as its database, and serve distant users from there, or keep a copy of the data near them. The cost is more regions to run and data that may be a little out of date (module 8).

The same arithmetic catches a common bug called the N + 1 query: code loads a list of 50 posts with one query, then loads each post's author with its own query. In one region that is 51 times 0.5 ms, about 25 ms, and nobody notices. Move the database one continent away and it becomes about 4 seconds.

</GoDeeper>
