## How the measurement works

The idea is simple, and the details matter. A load generator sends requests to a server at a chosen rate, for example 80 per second. For every request it notes the moment the request was meant to be sent and the moment the answer came back. The difference is that request's latency. After a few seconds it sorts the latencies and reads p50, p95 and p99 with the `percentile` function you wrote in chapter 2.7. Then it raises the rate and does it again.

Three design choices make the numbers honest, and each one fixes a mistake that is easy to make.

**The server is one worker.** The server's "work" is a loop that keeps the CPU busy for about 10 ms. While that loop runs, Node.js cannot do anything else, so a second request has to wait for the first to finish. That makes the server behave like the single-server queue in chapter 2.5, with a capacity of about 100 requests per second. Most real Node.js handlers wait on a database instead of spinning, but the queueing is the same once any single resource is busy.

**The work and the arrivals are random.** If every request took exactly 10 ms and arrived exactly on schedule, nothing would ever wait until the server was 100% busy, and you would see no knee at all. Real users arrive independently, and real work varies. So the server picks each request's work time at random around 10 ms, and the load generator picks random gaps between requests around the target rate. Both use the exponential shape: many short values and a few long ones. That is the M/M/1 model from chapter 2.5, so you can compare your numbers with its formulas.

**The load generator does not wait for answers.** It sends the next request on schedule even if earlier answers have not come back, which is called an open loop. Real users behave like that: a slow server does not stop new students from opening the app. A load generator that waits for each answer before sending the next one quietly slows down when the server slows down, and then hides the very queue you want to see. Such a tester leaves the slow moments out of its own results, because it stopped sending during them.

Two practical details. The server runs in its own process, so its busy loop cannot block the load generator. And the load generator checks the clock in a tight loop instead of using timers, because on Windows a timer for "1 ms from now" often fires about 15 ms later, which would wreck a 10 ms measurement. That loop keeps one CPU core busy while a test runs; this is expected.

## Step 1: the toolkit

First, `toolkit/stats.js`. Paste your `percentile` function from chapter 2.7 where the comment says, and put `export` in front of it. If you have not finished 2.7 yet, do that first: this file depends on it, and the part 1 test checks it again.

```js
// toolkit/stats.js: small statistics helpers. No packages needed.

// Paste your percentile function from chapter 2.7 here, with export in front:
// export function percentile(values, p) { ... }

// The numbers a results table needs, from a list of latencies in ms.
export function summarize(latencies) {
  const mean = latencies.reduce((sum, x) => sum + x, 0) / latencies.length;
  return {
    count: latencies.length,
    mean,
    p50: percentile(latencies, 50),
    p95: percentile(latencies, 95),
    p99: percentile(latencies, 99),
    max: percentile(latencies, 100),
  };
}

// Seeded random numbers (the mulberry32 method): the same seed gives the
// same numbers, so two runs send the same pattern of requests.
export function seededRandom(seed) {
  let a = seed >>> 0;
  return function random() {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// A random duration with the given mean, shaped like independent events:
// many short ones and a few long ones (an exponential distribution).
export function exponential(random, mean) {
  return -mean * Math.log(1 - random());
}
```

Next, `toolkit/load.js`, the load generator. Read the comments: they are the three design choices from above. The part that adds up "requests in flight times time" is for part 3.

```js
// toolkit/load.js: start a server in its own process, and send it requests
// at a target rate (an open-loop load generator).
import http from "node:http";
import { fork } from "node:child_process";
import { fileURLToPath } from "node:url";
import { exponential, seededRandom } from "./stats.js";

// Start a server script as a child process. The script must send { port }
// to its parent once it is listening. Its own process means its busy work
// cannot slow down the load generator.
export function spawnServer(scriptUrl, env = {}) {
  const child = fork(fileURLToPath(scriptUrl), { env: { ...process.env, ...env } });
  return new Promise((resolve, reject) => {
    child.once("error", reject);
    child.once("message", ({ port }) => {
      resolve({ url: `http://127.0.0.1:${port}/`, stop: () => child.kill() });
    });
  });
}

const agent = new http.Agent({ keepAlive: true, maxSockets: Infinity });

function get(url) {
  return new Promise((resolve, reject) => {
    http.get(url, { agent }, (res) => {
      res.resume();
      res.on("end", resolve);
    }).on("error", reject);
  });
}

// Wait until a moment in time. Timers on Windows tick about every 15 ms,
// too coarse here, so check the clock in a loop that still lets answers in.
async function waitUntil(t) {
  while (performance.now() < t) await new Promise((resolve) => setImmediate(resolve));
}

// Send requests at `rate` per second for `seconds`, at random moments, like
// independent users. Each request calls the server `fanout` times in
// parallel and finishes when all calls are back.
export async function runLoad({ url, rate, seconds, fanout = 1, seed = 7 }) {
  const random = seededRandom(seed);
  const latencies = [];
  const pending = [];
  // For Little's law: add up "requests in flight x time" as time passes.
  let inFlight = 0;
  let area = 0;
  let lastChange = performance.now();
  const change = (delta) => {
    const now = performance.now();
    area += inFlight * (now - lastChange);
    lastChange = now;
    inFlight += delta;
  };

  const start = performance.now();
  const stop = start + seconds * 1000;
  let planned = start;
  while (true) {
    planned += exponential(random, 1000 / rate);
    if (planned > stop) break;
    await waitUntil(planned);
    const sentAt = performance.now(); // within a fraction of a ms of `planned`
    change(+1);
    const calls = Array.from({ length: fanout }, () => get(url));
    pending.push(Promise.all(calls).then(() => {
      change(-1);
      latencies.push(performance.now() - sentAt);
    }));
  }
  await Promise.all(pending);
  change(0);
  const elapsed = performance.now() - start;
  return {
    latencies,
    throughput: latencies.length / (elapsed / 1000), // lambda: finished per second
    inFlightAvg: area / elapsed, // L: average requests in flight
  };
}
```

Last, `toolkit/chart.js`. It writes SVG, a text format for pictures that GitHub shows directly in a README.

```js
// toolkit/chart.js: draw a small line chart as SVG text, one line per series.
// points: [{ x: 20, p50: 8.4, p99: 58.4 }, ...]; series: [{ key: "p50", color: "#2563eb" }]
export function lineChart({ title, xLabel, yLabel, points, series }) {
  const W = 560, H = 340, L = 60, R = 24, T = 44, B = 50;
  const xs = points.map((p) => p.x);
  const xMin = Math.min(...xs), xMax = Math.max(...xs);
  const yMax = Math.max(...points.flatMap((p) => series.map((s) => p[s.key])));
  const X = (x) => L + ((x - xMin) / (xMax - xMin || 1)) * (W - L - R);
  const Y = (y) => H - B - (y / (yMax || 1)) * (H - T - B);
  const lines = series.map((s) => {
    const d = points.map((p, i) => `${i ? "L" : "M"}${X(p.x).toFixed(1)},${Y(p[s.key]).toFixed(1)}`).join(" ");
    const last = points.at(-1);
    return `<path d="${d}" fill="none" stroke="${s.color}" stroke-width="2.5"/>\n` +
      `<text x="${X(last.x) - 4}" y="${Y(last[s.key]) - 8}" text-anchor="end" fill="${s.color}">${s.key}</text>`;
  });
  const ticks = xs.map((x) => `<text x="${X(x)}" y="${H - B + 18}" text-anchor="middle">${x}</text>`);
  return `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 ${W} ${H}" font-family="sans-serif" font-size="13">
<rect width="${W}" height="${H}" fill="white"/>
<text x="${L}" y="26" font-size="15" font-weight="bold">${title}</text>
<line x1="${L}" y1="${H - B}" x2="${W - R}" y2="${H - B}" stroke="#999"/>
<line x1="${L}" y1="${T}" x2="${L}" y2="${H - B}" stroke="#999"/>
<text x="${L - 8}" y="${T + 4}" text-anchor="end">${Math.round(yMax)}</text>
<text x="${L - 8}" y="${H - B}" text-anchor="end">0</text>
<text x="${(L + W - R) / 2}" y="${H - 10}" text-anchor="middle">${xLabel}</text>
<text x="16" y="${(T + H - B) / 2}" transform="rotate(-90 16 ${(T + H - B) / 2})" text-anchor="middle">${yLabel}</text>
${ticks.join("\n")}
${lines.join("\n")}
</svg>
`;
}
```

## Step 2: the server

The server reads its settings from environment variables, so each part can start it differently. `SERVICE_MS` is the average work per request. `DIST` chooses random work around that average (`exp`) or exactly that much every time (`fixed`). `SLOW_CHANCE` and `SLOW_MS` make a share of requests wait for something slow, for part 2. Create `challenges/challenge-1-measure-a-server/server.js`:

```js
// A tiny HTTP server with a simulated service time.
// The work below blocks the event loop, so this server is one worker:
// a request that arrives while another is being served waits its turn.
import http from "node:http";
import { exponential, seededRandom } from "../../toolkit/stats.js";

const SERVICE_MS = Number(process.env.SERVICE_MS ?? 10); // average work per request
const DIST = process.env.DIST ?? "exp"; // "exp": random around the average; "fixed": always the same
const SLOW_CHANCE = Number(process.env.SLOW_CHANCE ?? 0); // share of requests that also wait
const SLOW_MS = Number(process.env.SLOW_MS ?? 0); // how long those slow requests wait

const random = seededRandom(1);
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

function busyWork(ms) {
  const end = performance.now() + ms;
  while (performance.now() < end) {
    // spin: this loop is the "work"
  }
}

const server = http.createServer(async (req, res) => {
  // A few requests wait for something slow, like a cold disk. They wait
  // without blocking, so other requests keep being served meanwhile.
  if (random() < SLOW_CHANCE) await sleep(SLOW_MS);
  busyWork(DIST === "exp" ? exponential(random, SERVICE_MS) : SERVICE_MS);
  res.end("ok\n");
});

// Port 0 asks the operating system for any free port.
server.listen(0, "127.0.0.1", () => {
  const { port } = server.address();
  if (process.send) process.send({ port }); // started by toolkit/load.js
  else console.log(`listening on http://127.0.0.1:${port}/ (service ${SERVICE_MS} ms, ${DIST})`);
});
```

You can try it on its own: `node challenges/challenge-1-measure-a-server/server.js` prints the address, and opening it in a browser shows "ok". Press Ctrl+C to stop it.

## Step 3: part 1, the knee

Create `part-1-the-knee/knee.js`. It starts the server, runs eight steps from 20 to 95 requests per second for 10 seconds each, prints one row per step and writes `chart.svg`. The last column is the M/M/1 prediction for the mean, 1 / (mu - lambda), from chapter 2.5.

```js
// Part 1: raise the request rate step by step and watch p50 and p99.
import { writeFileSync } from "node:fs";
import { runLoad, spawnServer } from "../../../toolkit/load.js";
import { summarize } from "../../../toolkit/stats.js";
import { lineChart } from "../../../toolkit/chart.js";

const SERVICE_MS = 10; // average work per request, so capacity is about 100 per second
const SECONDS = Number(process.env.STEP_SECONDS ?? 10); // how long each step runs
const RATES = [20, 40, 60, 70, 80, 85, 90, 95]; // requests per second

const server = await spawnServer(new URL("../server.js", import.meta.url), { SERVICE_MS: String(SERVICE_MS) });
const capacity = 1000 / SERVICE_MS;
console.log(`service time ${SERVICE_MS} ms, so capacity is about ${capacity} requests per second\n`);
console.log("rate/s  busy  p50 ms  p95 ms  p99 ms  mean ms  M/M/1 mean");

const points = [];
for (const rate of RATES) {
  const { latencies } = await runLoad({ url: server.url, rate, seconds: SECONDS });
  const s = summarize(latencies);
  const busy = Math.round((rate / capacity) * 100);
  const mm1 = 1000 / (capacity - rate); // chapter 2.5: W = 1 / (mu - lambda), in ms
  points.push({ x: rate, p50: s.p50, p99: s.p99 });
  console.log(
    `${String(rate).padStart(6)}  ${String(busy).padStart(3)}%  ${s.p50.toFixed(1).padStart(6)}  ` +
    `${s.p95.toFixed(1).padStart(6)}  ${s.p99.toFixed(1).padStart(6)}  ${s.mean.toFixed(1).padStart(7)}  ` +
    `${mm1.toFixed(1).padStart(10)}`
  );
}
server.stop();

writeFileSync(new URL("./chart.svg", import.meta.url), lineChart({
  title: `Latency as load grows (service time ${SERVICE_MS} ms)`,
  xLabel: "requests per second",
  yLabel: "milliseconds",
  points,
  series: [{ key: "p50", color: "#2563eb" }, { key: "p99", color: "#dc2626" }],
}));
console.log("\nwrote chart.svg");
```

Then its test, `part-1-the-knee/knee.test.js`. It checks your `percentile` once more, checks `summarize`, and runs a quiet server for two seconds with fixed 10 ms work, so every answer must take at least 10 ms.

```js
import test from "node:test";
import assert from "node:assert/strict";
import { percentile, summarize } from "../../../toolkit/stats.js";
import { runLoad, spawnServer } from "../../../toolkit/load.js";

test("percentile uses the nearest rank", () => {
  const ms = [40, 100, 30, 20, 50];
  assert.equal(percentile(ms, 50), 40);
  assert.equal(percentile(ms, 0), 20);
  assert.equal(percentile(ms, 100), 100);
  assert.ok(Number.isNaN(percentile([], 50)));
  assert.throws(() => percentile(ms, 101), RangeError);
});

test("summarize reports the mean and the percentiles", () => {
  const s = summarize([10, 20, 30, 40]);
  assert.deepEqual(s, { count: 4, mean: 25, p50: 20, p95: 40, p99: 40, max: 40 });
});

test("a quiet server answers in about one service time", async () => {
  const server = await spawnServer(new URL("../server.js", import.meta.url), { SERVICE_MS: "10", DIST: "fixed" });
  try {
    const { latencies } = await runLoad({ url: server.url, rate: 10, seconds: 2 });
    assert.ok(latencies.length >= 10, `only ${latencies.length} answers`);
    const p50 = percentile(latencies, 50);
    assert.ok(p50 >= 10, `p50 was ${p50.toFixed(1)} ms, less than the 10 ms of work`);
    assert.ok(p50 < 100, `p50 was ${p50.toFixed(1)} ms, far more than 10 ms of work`);
  } finally {
    server.stop();
  }
});
```

## Step 4: part 2, percentiles lie

This part makes 2 calls in 100 wait 200 ms, like a cold disk, while all other calls are almost free. Then each "page" calls the server 1, 2, 5, 10 and 20 times in parallel, as in the fan-out pictures of chapter 2.4. The last column compares the share of slow pages you measured with the formula 1 - (1 - 0.02) to the power n. Create `part-2-percentiles-lie/tail.js`:

```js
// Part 2: 2 calls in 100 are slow. Compare the mean with the percentiles,
// then make each page call the server several times and watch the tail grow.
import { writeFileSync } from "node:fs";
import { runLoad, spawnServer } from "../../../toolkit/load.js";
import { summarize } from "../../../toolkit/stats.js";
import { lineChart } from "../../../toolkit/chart.js";

const SLOW_CHANCE = 0.02; // 2 calls in 100 wait for something slow
const SLOW_MS = 200;
const FANOUTS = [1, 2, 5, 10, 20]; // calls per page

const server = await spawnServer(new URL("../server.js", import.meta.url), {
  SERVICE_MS: "0", SLOW_CHANCE: String(SLOW_CHANCE), SLOW_MS: String(SLOW_MS),
});
console.log(`each call is slow (${SLOW_MS} ms) with chance ${SLOW_CHANCE}; other calls are almost free\n`);
console.log("calls/page  mean ms  p50 ms  p95 ms  p99 ms  slow pages (predicted)");

const points = [];
for (const fanout of FANOUTS) {
  const { latencies } = await runLoad({ url: server.url, rate: 40, seconds: 10, fanout });
  const s = summarize(latencies);
  const slowShare = latencies.filter((ms) => ms >= SLOW_MS).length / latencies.length;
  const predicted = 1 - (1 - SLOW_CHANCE) ** fanout; // chapter 2.4
  points.push({ x: fanout, p50: s.p50, p95: s.p95 });
  const f = (n) => n.toFixed(1).padStart(6);
  console.log(
    `${String(fanout).padStart(10)}  ${f(s.mean).padStart(7)}  ${f(s.p50)}  ${f(s.p95)}  ${f(s.p99)}  ` +
    `${(slowShare * 100).toFixed(0).padStart(6)}% (${(predicted * 100).toFixed(0)}%)`
  );
}
server.stop();

writeFileSync(new URL("./chart.svg", import.meta.url), lineChart({
  title: "Fan-out: more calls per page, slower pages",
  xLabel: "calls per page",
  yLabel: "milliseconds",
  points,
  series: [{ key: "p50", color: "#2563eb" }, { key: "p95", color: "#dc2626" }],
}));
console.log("\nwrote chart.svg");
```

Its test, `part-2-percentiles-lie/tail.test.js`, needs no server. It pins down the two surprises from chapter 2.4 with exact numbers: a mean that no request took, and a slow 1% that p99 can miss.

```js
import test from "node:test";
import assert from "node:assert/strict";
import { summarize } from "../../../toolkit/stats.js";

test("the mean is a time no request took", () => {
  const ms = [...Array(98).fill(1), 200, 200]; // 2 slow calls in 100
  const s = summarize(ms);
  assert.equal(s.p50, 1);
  assert.equal(s.p99, 200);
  assert.equal(s.mean, 4.98);
  assert.ok(!ms.includes(s.mean));
});

test("one slow call in 100 can hide below p99", () => {
  const ms = [...Array(99).fill(1), 200];
  assert.equal(summarize(ms).p99, 1); // the 99th of 100 sorted values is still fast
  assert.equal(summarize(ms).max, 200);
});

test("fan-out makes slow pages common", () => {
  const slowPage = (calls, chance) => 1 - (1 - chance) ** calls;
  assert.ok(Math.abs(slowPage(1, 0.01) - 0.01) < 1e-9);
  assert.ok(Math.abs(slowPage(100, 0.01) - 0.634) < 0.001);
  assert.ok(Math.abs(slowPage(20, 0.02) - 0.332) < 0.001);
```

## Step 5: part 3, Little's law

The load generator already adds up, at every moment, how many requests are in flight. Divided by the time, that is L, the average number in flight. Part 3 measures L, lambda (finished requests per second) and W (mean latency) at four rates, so you can check L = lambda W, and compares L with the M/M/1 formula rho / (1 - rho). Create `part-3-littles-law/little.js`:

```js
// Part 3: check Little's law, L = lambda x W, on your own measurements,
// and compare L with the M/M/1 prediction from chapter 2.5.
import { writeFileSync } from "node:fs";
import { runLoad, spawnServer } from "../../../toolkit/load.js";
import { summarize } from "../../../toolkit/stats.js";
import { lineChart } from "../../../toolkit/chart.js";

const SERVICE_MS = 10;
const RATES = [50, 70, 80, 90];
const server = await spawnServer(new URL("../server.js", import.meta.url), { SERVICE_MS: String(SERVICE_MS) });

console.log("rate/s  lambda/s  W ms   L measured  lambda x W  M/M/1 L");
const points = [];
for (const rate of RATES) {
  const { latencies, throughput, inFlightAvg } = await runLoad({ url: server.url, rate, seconds: 15 });
  const W = summarize(latencies).mean / 1000; // seconds
  const rho = (throughput * SERVICE_MS) / 1000; // how busy the server was
  const mm1 = rho / (1 - rho); // chapter 2.5: L = rho / (1 - rho)
  points.push({ x: rate, measured: inFlightAvg, mm1 });
  console.log(
    `${String(rate).padStart(6)}  ${throughput.toFixed(1).padStart(8)}  ${(W * 1000).toFixed(1).padStart(5)}  ` +
    `${inFlightAvg.toFixed(2).padStart(10)}  ${(throughput * W).toFixed(2).padStart(10)}  ${mm1.toFixed(2).padStart(7)}`
  );
}
server.stop();

writeFileSync(new URL("./chart.svg", import.meta.url), lineChart({
  title: "Requests in flight (L): measured and M/M/1",
  xLabel: "requests per second",
  yLabel: "requests in flight",
  points,
  series: [{ key: "measured", color: "#2563eb" }, { key: "mm1", color: "#9ca3af" }],
}));
console.log("\nwrote chart.svg");
```

And `part-3-littles-law/little.test.js`:

```js
import test from "node:test";
import assert from "node:assert/strict";
import { runLoad, spawnServer } from "../../../toolkit/load.js";
import { summarize } from "../../../toolkit/stats.js";

test("L equals lambda times W on a real run", async () => {
  const server = await spawnServer(new URL("../server.js", import.meta.url), { SERVICE_MS: "5" });
  try {
    const { latencies, throughput, inFlightAvg } = await runLoad({ url: server.url, rate: 50, seconds: 3 });
    const W = summarize(latencies).mean / 1000;
    const predicted = throughput * W;
    const gap = Math.abs(inFlightAvg - predicted) / predicted;
    assert.ok(gap < 0.05, `L ${inFlightAvg.toFixed(2)} and lambda x W ${predicted.toFixed(2)} differ by ${(gap * 100).toFixed(1)}%`);
  } finally {
    server.stop();
  }
});
```

Run `node challenges/challenge-1-measure-a-server/part-3-littles-law/little.js` (about 60 seconds):

```text

    50      47.1   20.7        0.98        0.98     0.89
    70      66.7   32.3        2.15        2.15     2.00
    80      77.3   50.2        3.87        3.87     3.40
    90      87.2  111.3        9.71        9.71     6.83
```

The "L measured" and "lambda x W" columns match to two decimals in every row. That is Little's law at work, and it is not a coincidence of this server: it is accounting. Every request in flight adds its time to the total, so the average number in flight must equal the rate times the average time. If those two columns ever disagree by more than a few percent, your measurement has a bug, which is how engineers use the law in practice. The M/M/1 column is a different matter: it is a model, and it is close at 50% busy, then off by more near the knee, where 15 seconds is still a short run. Notice also that lambda is a little below the target rate: random gaps and the time to drain the last requests both lower it.

Make `part-3-littles-law/results.md` with your four rows, one sentence on whether L matched lambda x W, and one on where M/M/1 was close or far. End with `![Requests in flight](chart.svg)`.

## When something goes wrong

**`SyntaxError: The requested module './stats.js' does not provide an export named 'percentile'`.** You pasted `percentile` without `export` in front, or not at all. Fix `toolkit/stats.js` and run again.

**`Cannot find module` with a path that ends in `server.js` or `toolkit`.** A file is in the wrong folder or has a typing mistake in its name. Compare your folders with the tree at the top. The scripts find each other through their own location, so it does not matter which folder you run them from, but the files must be where the imports expect them.

**Every number is huge, even at 20 per second.** Something else is using the CPU, or the laptop is saving power. The server and the load generator each keep one core busy, so a machine with two cores and a browser open has no room left. Close programs, plug in, and run again. If p50 at 20 per second is still above 30 ms, write that in your results; it is a real finding about your machine.

**p99 is lower at 95 than at 90.** At the knee, results swing between runs. Run part 1 again with `STEP_SECONDS=30`. A single short run near capacity is weak evidence; say so in your results instead of hiding it.

**`ECONNRESET` or `socket hang up`.** The server process stopped, usually because you edited `server.js` and introduced an error. Run `node challenges/challenge-1-measure-a-server/server.js` on its own to see the error.

**Break it on purpose.** As in challenge 0, see a test fail before you trust it. In `server.js`, change `busyWork(...)` to `busyWork(0)` and run `npm test`: the quiet-server test fails because answers now come back faster than 10 ms of work. Undo the change. Then in `toolkit/stats.js`, remove the comparison function from `sort`, and watch the percentile test fail. Undo that too.
