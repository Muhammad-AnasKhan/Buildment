Every dashboard you will read in this course shows a p99, and every design review ends with an availability number. Both come from a few lines of code. When those lines are wrong, the dashboard still shows a number, and it looks just as confident. In this chapter you write the three functions yourself, so you know exactly what the numbers mean and where they break.

By the end, you will have three tested JavaScript functions. `percentile(values, p)` returns the p-th percentile of a list of measurements using the nearest-rank method from chapter 2.4. `seriesAvailability(parts)` returns the availability of a chain where every part must work. `parallelAvailability(copies)` returns the availability of redundant copies where any one is enough. You will use the same percentile function in challenge 1, in the next chapter, on your own measurements.

## The contract for each function

Before writing code, fix what each function promises, including the awkward inputs. Tests check the awkward inputs first, because that is where real bugs live.

**`percentile(values, p)`** takes an array of numbers, such as latencies in milliseconds, and a percentile `p` from 0 to 100. It uses the nearest-rank method: sort the values from smallest to largest, compute the rank as p times n divided by 100, round the rank up to a whole number, and return the value at that rank, counting from 1. For `p = 0`, return the smallest value (rank 1). For `p = 100`, return the largest. The answer is always one of the values you measured; the method never invents a value between two measurements.

It must also handle two bad inputs, and they get different treatment on purpose. An empty array returns `NaN` (not a number). An empty list is a normal situation: a service that got no requests at 4 am has no p99, and a monitoring job should not crash because of that. A `p` below 0, above 100, or not a number at all throws a `RangeError`. That situation is not normal. It means the calling code has a bug, such as passing `0.99` where it meant `99`, and failing loudly is better than returning a quiet wrong answer.

Finally, `percentile` must not change the caller's array. Sorting in JavaScript sorts in place, so sorting the caller's array would silently reorder their data, perhaps a list they still need in arrival order. Copy first, then sort the copy.

**`seriesAvailability(parts)`** takes an array of availabilities as fractions between 0 and 1, such as `[0.9999, 0.999, 0.999]`, and returns their product. An empty chain returns 1: a request that passes through no parts cannot fail because of them. This is also the natural starting value for a product, in the same way that a sum starts at 0.

**`parallelAvailability(copies)`** takes the same kind of array and returns 1 minus the product of the down chances, 1 minus each availability. An empty list returns 0: with no copies at all, nothing can serve the request. One perfect copy (availability 1) makes the result 1, whatever the others are.

Both availability functions throw a `RangeError` for any value below 0 or above 1. The most common mistake in practice is passing percentages, `99.9` instead of `0.999`. With `99.9`, the series product would be enormous and the parallel result would be negative. Neither is an availability, and both would flow into a report without anyone noticing.

## A worked example: p90 of eight build times

Here is the percentile method applied by hand to data that is not in the tests: eight build times in seconds, in the order they finished: 41, 38, 120, 45, 39, 44, 40, 43.

First, the subgoal: get the values in order without touching the original. Copy with `[...values]` and sort the copy with a comparison function, `(a, b) => a - b`, which gives 38, 39, 40, 41, 43, 44, 45, 120.

Second, find the rank. With n = 8 and p = 90, p times n divided by 100 is 7.2. Ranks are whole numbers, and nearest rank always rounds up, so the rank is 8. Rounding up guarantees that at least 90% of the values are at or below the answer: 8 of 8 here. Rounding down to rank 7 would give 45, and only 7 of 8 values (87.5%) are at or below 45, which is less than 90%.

Third, read the value. Ranks count from 1 but JavaScript arrays count from 0, so rank 8 is index 7: 120 seconds. That one slow build is the p90 for such a small sample. With eight values, every percentile above 87.5 is the slowest build, which is the sample-size warning from chapter 2.4 in action.

Check p = 50 the same way: 50 times 8 divided by 100 is 4, a whole number already, so rank 4 is index 3: 41 seconds. And p = 0 gives a rank of 0, which you raise to rank 1, the smallest value, 38.

## Three ways this goes wrong

**Sorting numbers as text.** Called without a comparison function, JavaScript's `sort` converts values to strings and sorts them like words in a dictionary. `[100, 9, 20, 3].sort()` gives `[100, 20, 3, 9]`, because the string "100" comes before "20". Your function would then return a wrong percentile, with no error. Always pass `(a, b) => a - b`. One of the tests uses exactly these four numbers.

**Off by one.** Mixing up ranks (from 1) and indexes (from 0) shifts every answer by one place. The symptom is that p = 100 returns `undefined`, because index n is past the end of the array, or that p = 0 crashes. Test both ends.

**A floating-point slip.** Computers store most decimals as close approximations, not exactly. In JavaScript, `(99.9 / 100) * 1000` is `1000.0000000000001`, not 999, and rounding up then gives rank 1000 instead of 999: the wrong value for p99.9 of 1,000 measurements. Multiply first and divide last, `Math.ceil((p * n) / 100)`, which gives exactly 999 here. A test checks p99.9 of 1,000 values. The same care applies to the availability results: compare them with a small tolerance rather than with `===`, as the tests do.

solution: |
  function percentile(values, p) {
    if (typeof p !== "number" || !(p >= 0 && p <= 100)) {
      throw new RangeError("p must be a number from 0 to 100, got " + p);
    }
    if (values.length === 0) return NaN;
    const sorted = [...values].sort((a, b) => a - b);
    const rank = Math.max(1, Math.ceil((p * sorted.length) / 100));
    return sorted[rank - 1];
  }

  function checkAvailability(a) {
    if (typeof a !== "number" || !(a >= 0 && a <= 1)) {
      throw new RangeError("availability must be a fraction from 0 to 1, got " + a);
    }
  }

  function seriesAvailability(parts) {
    let up = 1;
    for (const a of parts) {
      checkAvailability(a);
      up *= a;
    }
    return up;
  }

  function parallelAvailability(copies) {
    let allDown = 1;
    for (const a of copies) {
      checkAvailability(a);
      allDown *= 1 - a;
    }
    return 1 - allDown;
  }
