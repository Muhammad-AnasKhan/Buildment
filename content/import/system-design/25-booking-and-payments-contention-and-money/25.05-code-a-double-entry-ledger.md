In chapter 25.3 you learned the rules of Tazkara's ledger. Entries only grow. Every transaction has debits and credits that add up to the same total. A repeated event posts once. A refund adds lines and never edits. The rules are short, and each one is easy to break by accident. A ledger that passes every test with one tidy transaction can still lose a cent on the day two copies of one webhook arrive together.

In this chapter you write the core of that ledger in plain JavaScript. It is one object with five methods, and no database. The same code could sit in front of a table, and the same rules would apply. What you practise is the order of the checks, because in a ledger the order is the correctness: look first, then store, and never the other way round.

## What the tests do to your code

The tests are built around the places where a ledger breaks. They post one real sale and check three balances. They refuse transactions that do not add up, and also transactions that add up but have a bad line, such as a fraction, a zero, text instead of a number, or a line with both sides. They check that a refused request leaves no trace: no entry and no changed balance. They post the same id twice, then again after other transactions, then with different lines.

They also attack your copies. A test changes the lines array after `post()` and changes what `entries()` returned, and then checks that the ledger did not move. One test passes numbers so large that adding them loses digits. The last test sends 500 mixed requests, valid, repeated, unbalanced and reversed, and checks after every request that the books still balance.

Nothing is `async`, and nothing reads a clock or a random number except one seeded generator in the last test. Each test gives the same answer every time, and the message of a failing test names the rule you broke.

## The contract

**`post({ id, lines })`** adds one transaction. Each line is `{ account, debit }` or `{ account, credit }`, where the amount is a positive safe integer of cents and the account is a non-empty string. A transaction needs at least two lines, and the sum of its debits must equal the sum of its credits. A bad line, a wrong total, or a sum too big to add exactly throws a `RangeError`. A missing or empty `id`, or one that is not a string, throws a `TypeError`. When the transaction is accepted, `post` returns `{ status: "posted" }`.

If the `id` was already posted with the same lines in the same order, `post` returns `{ status: "duplicate" }` and changes nothing. If the `id` was posted with different lines, it throws an `Error` whose `name` is `"ConflictError"`. The lines are checked before the id is looked up, so a bad request is always a `RangeError`, whatever the id.

**`balanceOf(account)`** returns the debits minus the credits for one account, and 0 for an account nobody has used. **`trialBalance()`** returns `{ debits, credits, balanced }` for the whole ledger. **`entries()`** returns copies of all transactions in posting order.

**`reverse(id, reversalId)`** posts a new transaction under `reversalId` with every debit and credit swapped, and remembers that it reverses `id`. The new transaction also carries `reverses: id` in `entries()`. An unknown `id` throws a `RangeError`. Repeating the same call returns `{ status: "duplicate" }`. Reversing the same `id` under a different `reversalId`, or using a `reversalId` that belongs to another transaction, throws a `ConflictError`.

## A worked example by hand

Here is the code applied to a case that is not in the tests: a workshop seat that costs 60.00, so 6000 cents, split 5400 to the organizer and 600 to Tazkara. The output below comes from a real run of a finished version of the function.

```text
post evt-1 (workshop seat, 60.00)  {"status":"posted"}
post evt-1 again, same lines       {"status":"duplicate"}
post evt-1, split 5500 and 500     ConflictError: id evt-1 was already used with different lines
post evt-2, credits 5900 only      RangeError: not balanced: debits 6000, credits 5900
trialBalance                       {"debits":6000,"credits":6000,"balanced":true}
balanceOf provider-clearing        6000
reverse evt-1 as refund-1          {"status":"posted"}
reverse evt-1 as refund-2          ConflictError: transaction evt-1 was already reversed by refund-1
balanceOf provider-clearing        0
entries().length                   2
```

Walk down it slowly. The first post is new, so it is stored. The second is the same id with the same three lines, so it is a duplicate and nothing is added. The third reuses `evt-1` with a different split. Its totals do balance (5500 + 500 is 6000), so it passes the line checks and then meets the stored `evt-1`, and the lines differ. That is a `ConflictError`. The fourth is a new id, but its credits are 5900, so it fails the balance check before the id is even looked up, and the ledger is unchanged. The trial balance still reads 6000 and 6000.

The reversal puts three new lines in the ledger, so there are two entries and the balance of `provider-clearing` returns to 0. The history still shows the sale, then the refund. A second refund under another id is refused, because the sale has already been reversed. This is the rule from chapter 25.3: undo by adding, and only once.

## Five ways this goes wrong

**Storing before checking.** If `post()` pushes the transaction and then validates, a refused request leaves a half-stored entry behind. Do all the checking first, and push last. The tests ask for the entries and balances after every refusal.

**Trusting the caller's objects.** If you store the array you were given, the caller can change the amount a minute later and the ledger changes with it. Build new line objects when you store, and build new ones again in `entries()`. Two tests change the data after the call.

**Checking the id before the lines.** A repeated id with a broken body should still be a `RangeError`. If you look up the id first, a bad duplicate may be reported as a duplicate. Validate the lines, then look at the id.

**Letting a sum run past the safe limit.** Above `Number.MAX_SAFE_INTEGER`, JavaScript numbers look fine and quietly lose their last digits, so two sides can appear equal when they are not. Check `Number.isSafeInteger` on the running totals inside the loop, not at the end.

**Letting a second reversal through.** A refund posted twice under two ids takes the money out twice. Remember which transactions have been reversed, and refuse another reversal under a new id. The same call repeated is a duplicate, and a different id is a conflict.

When a test fails, read its message first. Each one names the input and what it expected.

solution: |
  function createLedger() {
    const transactions = [];
    const byId = new Map();
    const reversedBy = new Map();

    const isAmount = (v) => Number.isSafeInteger(v) && v > 0;

    function checkLines(lines) {
      if (!Array.isArray(lines) || lines.length < 2) {
        throw new RangeError("a transaction needs at least two lines");
      }
      let debits = 0;
      let credits = 0;
      for (const line of lines) {
        if (!line || typeof line.account !== "string" || line.account === "") {
          throw new RangeError("every line needs an account name");
        }
        const hasDebit = line.debit !== undefined;
        const hasCredit = line.credit !== undefined;
        if (hasDebit === hasCredit) {
          throw new RangeError("a line has either a debit or a credit");
        }
        if (hasDebit) {
          if (!isAmount(line.debit)) throw new RangeError("debit must be a positive whole number");
          debits += line.debit;
        } else {
          if (!isAmount(line.credit)) throw new RangeError("credit must be a positive whole number");
          credits += line.credit;
        }
        if (!Number.isSafeInteger(debits) || !Number.isSafeInteger(credits)) {
          throw new RangeError("the total is too large to add exactly");
        }
      }
      if (debits !== credits) {
        throw new RangeError("not balanced: debits " + debits + ", credits " + credits);
      }
    }

    const copyLines = (lines) =>
      lines.map((l) => (l.debit !== undefined ? { account: l.account, debit: l.debit } : { account: l.account, credit: l.credit }));
    const sameLines = (a, b) =>
      a.length === b.length && a.every((l, i) => l.account === b[i].account && l.debit === b[i].debit && l.credit === b[i].credit);

    function conflict(message) {
      const err = new Error(message);
      err.name = "ConflictError";
      return err;
    }

    function post({ id, lines } = {}) {
      if (typeof id !== "string" || id === "") throw new TypeError("id must be a non-empty string");
      checkLines(lines);
      const known = byId.get(id);
      if (known) {
        if (sameLines(known.lines, lines)) return { status: "duplicate" };
        throw conflict("id " + id + " was already used with different lines");
      }
      const tx = { id, lines: copyLines(lines) };
      transactions.push(tx);
      byId.set(id, tx);
      return { status: "posted" };
    }

    function balanceOf(account) {
      let balance = 0;
      for (const tx of transactions) {
        for (const l of tx.lines) {
          if (l.account === account) balance += (l.debit ?? 0) - (l.credit ?? 0);
        }
      }
      return balance;
    }

    function trialBalance() {
      let debits = 0;
      let credits = 0;
      for (const tx of transactions) {
        for (const l of tx.lines) {
          debits += l.debit ?? 0;
          credits += l.credit ?? 0;
        }
      }
      return { debits, credits, balanced: debits === credits };
    }

    function reverse(id, reversalId) {
      const original = byId.get(id);
      if (!original) throw new RangeError("unknown transaction " + id);
      const earlier = reversedBy.get(id);
      if (earlier !== undefined && earlier !== reversalId) {
        throw conflict("transaction " + id + " was already reversed by " + earlier);
      }
      const existing = byId.get(reversalId);
      if (existing && existing.reverses !== id) {
        throw conflict("id " + reversalId + " is already used by another transaction");
      }
      const lines = original.lines.map((l) =>
        l.debit !== undefined ? { account: l.account, credit: l.debit } : { account: l.account, debit: l.credit });
      const result = post({ id: reversalId, lines });
      if (result.status === "posted") {
        byId.get(reversalId).reverses = id;
        reversedBy.set(id, reversalId);
      }
      return result;
    }

    function entries() {
      return transactions.map((tx) => ({ ...tx, lines: copyLines(tx.lines) }));
    }

    return { post, balanceOf, trialBalance, reverse, entries };
  }

The balance of `b` is 200 - 500 = -300, and the balance of `c` is -200. The three balances add up to 0, as they always must, and `trialBalance()` reads 700 for debits and 700 for credits.

Now reverse `t1` under `r1`. The balance of `a` goes to 0 and the balance of `b` goes to -300 + 500 = 200. The entry list holds three transactions: `t1`, `t2` and `r1`. Post `t1` again with the same lines: it is a duplicate, and no balance moves. Reverse `t1` under `r2`: that is a `ConflictError`, because `r1` already reversed it. If you can predict all of these before you run the tests, your design is right.

## How to say it in an interview

**Say:** "The ledger is an append-only list of transactions. Each one has two or more lines in whole cents, and the debits must equal the credits, or I refuse it before storing anything. A balance is the sum of an account's lines. Every transaction has a source id: the same id with the same lines is a no-op, and the same id with different lines is an error. A refund is a new transaction that swaps the sides. In a database I would add a unique key on the id, in the same transaction as the lines, and a nightly check that all debits equal all credits."

**Expect:** "Why integers, and what if you need a fraction of a cent?" **Answer:** "Floating point cannot add decimals exactly, so I store the smallest unit as an integer. For a fraction of a cent, such as a price per message, I pick a smaller unit, or I round at one named step and give the leftover to a named account."
