Tazkara does not run card processing. A payment provider does that, and Tazkara talks to it in two ways: Tazkara asks through API calls, and the provider tells through webhooks, which are calls from the provider to a URL on Tazkara's server. This is the third deep dive of the design loop, and it also does the last two steps: the trade-offs and the failures. You will reuse idempotency keys (6.4), sagas (14.3) and idempotent consumers (14.5).

## Hold, authorize, confirm, capture

<MermaidDiagram title="One purchase, in order" chart={`sequenceDiagram
  participant D as Dina
  participant B as Booking
  participant P as Payment service
  participant X as Provider
  D->>B: hold seat 7
  B-->>D: hold h1, 10 minutes
  D->>P: pay for h1
  P->>X: authorize 80, key h1-auth
  X-->>P: authorized
  P->>B: confirm seat 7 for h1
  B-->>P: sold
  P->>X: capture 80, key h1-cap
  X-->>P: captured
  P-->>D: ticket
`} legend="Authorize holds the money on the card without taking it. The seat is confirmed next. Capture takes the money only after the seat is safe. Each provider call carries a key built from the hold id." />

Dina holds a seat, then pays. Tazkara first authorizes the card: the money is held, not taken. Next it confirms the seat. Only then does it capture, which takes the money. If the seat cannot be confirmed, Tazkara voids the authorization and nothing was ever charged.

<GoDeeper title="Go deeper: the order is a trade-off, and the keys come from the hold">

The order of the steps is the design. Here is the trade-off in the usual shape.

- **The choice.** Authorize first, confirm the seat, then capture.
- **Why now.** At 20 fans per seat, some buyers will type their card and still lose the seat, for example after a late payment (chapter 25.2).
- **What it buys.** A buyer who loses the seat is never charged. There is no refund to send and no confusing line on a bank statement.
- **What it costs.** Two provider calls for every sale instead of one: about 330 calls a second at the peak of 167 payments a second. It also adds a state to track, because an authorization can expire before capture. {/* source needed: how long a card authorization stays valid; it depends on the card network and the bank, so the course gives no number. */}
- **The alternative.** Charge at once and refund if the seat fails. It is one call and simple. But money moves and then moves back, the buyer sees a charge, and a refund may arrive days later. {/* source needed: whether fees are returned on a refund; this differs by provider. */}
- **When to switch.** If a payment method cannot separate authorization from capture, you must charge at once and build the refund path (beat 6 and chapter 25.3).

Every call to the provider carries an idempotency key, built from the hold id: `h1-auth` for authorize and `h1-cap` for capture. If the call times out, Tazkara sends the same call again with the same key and gets the saved answer, never a second charge. This is chapter 6.4. Stripe's documentation says the first result is saved and replayed for the same key, a changed request with the same key is an error, and keys may be removed once they are at least 24 hours old [S80].

That last point matters. A provider key is not a permanent record. Tazkara keeps its own table, one row per payment attempt, with its own state (created, authorized, confirmed, captured, voided), so it never depends on a provider key staying alive.

</GoDeeper>

## Save the webhook, reply, work later

<InteractiveCanvas slug="sysdesign-m25-webhook-inbox" />

The provider tells Tazkara the result with a webhook. The endpoint checks who sent it, saves the raw event in an inbox, and answers 200 at once. A worker takes the event later and does the real work. If the reply is slow, the provider sends the event again.

<GoDeeper title="Go deeper: what the endpoint must and must not do">

The endpoint is a public URL, so anyone can call it. It must check that the call really came from the provider. Providers sign each webhook with a secret that only they and Tazkara know, and the endpoint checks that signature before it trusts the body. {/* source needed: the provider's signature scheme; each provider documents its own, so the course names none. */} A request with a bad signature gets an error and is never saved as an event.

Then it saves the raw event, with the provider's event id under a unique key, and replies success. It does nothing else. No ledger writes, no emails, no calls to other services. Work that takes time makes the reply slow, and a slow reply makes the provider retry, which creates the duplicates you will meet in the next beat.

The worker reads the inbox and does the work: update the payment's state, post to the ledger, issue the ticket. If it crashes, the event is still in the inbox and another run picks it up. This is the inbox side of the pattern in chapter 14.5, and its twin is the outbox in chapter 14.4 [S79]. A webhook gives at-least-once delivery, like most queues [S82, S83], so the worker must be safe to repeat.

A good habit is to treat the webhook as a nudge and not as the data. The event says "payment pay_7 changed". The worker then asks the provider for the current state of pay_7 and uses that answer. A forged or old body can then do no harm, because Tazkara never believes it.

</GoDeeper>

## Duplicate, late, out of order

<InteractiveCanvas slug="sysdesign-m25-webhook-order" />

Events can arrive twice, late, or in the wrong order. Choose the order they arrive in. A rule that takes the last event shows the wrong status. A payment that only moves forward, and ignores any event that would move it back, always ends in the right place.

<GoDeeper title="Go deeper: a payment as a state machine">

A payment has a short life with a clear direction. It is created, authorized, captured and sometimes refunded. It can also fail or be voided. Give each state a rank:

| State | Rank | Can move to |
|---|---|---|
| created | 0 | authorized, failed |
| authorized | 1 | captured, voided |
| captured | 2 | refunded |
| voided | 2 | none |
| refunded | 3 | none |

The rule is small: apply an event only if its state ranks higher than the current state, and in every case save the event. A "captured" event that arrives while the payment is still "created" is accepted, because a captured payment must have been authorized first. When "authorized" arrives afterwards, it ranks lower than the current "captured" and is ignored. The final status is captured in both orders.

A duplicate is handled before the rule. The event id is stored under a unique key (chapter 25.3, beat 5), so a second copy changes nothing.

Why not use the event's timestamp to sort? Clocks differ between the provider's machines, and two events can carry the same second. Arrival order is not event order, and timestamps are too coarse to be a rule. State rank does not depend on either, which is why it is the safer choice. {/* source needed: whether providers promise webhook order; the course assumes they do not and teaches the safe rule. */}

The strongest version of the rule is the nudge from the previous beat. On any event, fetch the payment from the provider and store its current state. Arrival order then stops mattering at all. The price is one extra API call for each event.

</GoDeeper>

## The webhook that never comes

<InteractiveCanvas slug="sysdesign-m25-missing-webhook" />

Sometimes no webhook arrives. Tazkara's endpoint may have been down, or the event may have been lost. A checker wakes every 5 minutes, finds payments that have been pending too long, asks the provider for their status, and applies the answer. Silence is not failure.

<GoDeeper title="Go deeper: the checker, and why you still need webhooks">

The checker is a loop over a query: payments in `authorized` or `created` state for more than 5 minutes. For each one it fetches the current state from the provider and applies it with the same rule as before (rank, save, idempotent). It is safe to run twice, and safe to run while a late webhook arrives, because both paths apply the same rule.

Why keep webhooks at all if the checker works? Polling every payment all the time is slow and wasteful. With 20,000 payments in two minutes, a webhook tells you within seconds, and the checker only sweeps the rest. Webhooks are the fast path. The checker is the safety net.

Providers retry a failed webhook for a while and then give up. {/* source needed: how long and how often a given provider retries webhooks; this is provider-specific, so the course gives no number. */} So an endpoint that was down for a long time can miss events for good. The checker and the reconciliation in the next beat catch those.

The same pattern appears with queues. A message a worker did not finish becomes visible again after a timeout [S84], and a dead-letter queue collects the ones that keep failing [S85]. A payment stuck in pending is that same stuck message.

</GoDeeper>

## Reconciliation: compare the books

<InteractiveCanvas slug="sysdesign-m25-reconcile" />

Each night a job takes the provider's own record of the day and compares it with Tazkara's ledger, payment by payment. Most match. Some gaps can be fixed by asking the provider. A few need a person. Nothing is left as "probably fine".

<GoDeeper title="Go deeper: the three outcomes, and what to compare">

Reconciliation is the test that does not trust Tazkara's own code. Everything so far (conditional updates, idempotency, state rank) can still have a bug. Reconciliation compares Tazkara against an outside record that was written by someone else.

The match key is the provider's payment id. Compare more than presence. Compare the amount, the currency and the status too. A payment that exists on both sides but with 80 on one and 70 on the other is a different bug from a payment that is missing.

There are three outcomes for each difference.

1. **In the provider's record, not in the ledger.** Usually a lost webhook. Fetch the payment, check it, and post it with the normal path. The ledger entry carries its source id, so a late webhook cannot double it.
2. **In the ledger, not in the provider's record.** This is the dangerous one: Tazkara believes it took money that the provider never took. It may have issued a ticket for nothing. A person must look at it, and the ticket may need to be cancelled.
3. **In both, but different.** A partial refund, a dispute, a fee, or a bug. Compare the amounts and the events, and find the reason.

A reconciliation run ends with a number for each outcome, and the goal is that every difference has a cause, a fix or an owner. Tazkara also compares totals, not only rows: the sum of captured payments minus the provider's fees should equal what the provider pays out to Tazkara's bank. {/* source needed: the format and timing of a real provider's settlement reports; they differ by provider. */}

Run it every day. A gap found the next morning is a small problem. A gap found at the end of the quarter is an investigation.

</GoDeeper>

## The seat is gone: void, do not refund

<InteractiveCanvas slug="sysdesign-m25-void-not-refund" />

The card was authorized, then the seat confirm failed. Tazkara voids the authorization. The hold on the card is released, and the bank app shows no charge. If Tazkara had captured first, it would need a refund, a second ledger transaction and days of confusion.

<GoDeeper title="Go deeper: the failure table, and going round the loop again">

The last step of the design loop asks what breaks and what users see. Each row below uses an idea from this module or from an earlier one.

| Block | If it fails | What users see | Plan |
|---|---|---|---|
| Waiting room | No new fans admitted | Fans stay in line | A static page and a counter, easy to replicate. Fail closed: do not admit everyone |
| Seat store | No holds | "Try again", never a double sale | A standby copy (chapter 8); confirm still checks the hold id |
| Payment service, crash after authorize | Card held, seat not confirmed | The hold expires | A recovery job voids attempts that are authorized and past their hold (a saga, chapter 14.3) |
| Provider slow or down | Authorize times out | "Payment is taking longer" | Retry once with the same key; a circuit breaker (chapter 16.5); extend the hold once |
| Webhook endpoint down | Events are missed | Ticket arrives late | Provider retries, the checker polls, reconciliation catches the rest |
| Ledger write fails | Money taken, entries missing | Ticket arrives late | The worker retries from the inbox; the nightly trial balance and reconciliation alarm |

The payment-service row is a saga. Hold the seat, authorize, confirm, capture: each step is a local commit, and each has an undo (release the hold, void the authorization). A recovery job reads the attempts table and drives each stuck attempt to a clean end, forward or backward. That table is the reason Tazkara never relies on memory in one process.

Now go round the loop again, as chapter 1.4 says. The failure table raises a clarify question: how long may a buyer wait for a ticket after paying? If the answer is "under 10 seconds", the checker's 5 minutes is too slow for the first look, and the nudge from beat 2 becomes important. Late answers in a late step change early requirements. That is why it is a loop.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "I would authorize the card first, confirm the seat with a conditional update on the hold id, and capture only after that. If the seat fails I void, so the buyer is never charged. Every provider call has an idempotency key built from the hold id. Webhooks go to an endpoint that verifies the signature, saves the raw event under a unique id and replies 200. A worker applies it with a payment state machine that only moves forward. A checker polls payments stuck in pending, and a nightly job reconciles the ledger with the provider's record. A recovery job voids authorizations whose hold has expired."

**Expect:** "What if the provider sends events out of order?" **Answer:** "Arrival order is not event order. The state rank ignores any event that would move the payment backwards, and the safest version fetches the current state from the provider on every event."

</GoDeeper>
