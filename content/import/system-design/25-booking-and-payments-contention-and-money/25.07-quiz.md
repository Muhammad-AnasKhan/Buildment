```quiz
type: mcq
question: "Tazkara runs a 150 ms fraud check inside a row lock before it writes the hold. 30 fans want the same seat at the same moment. About how long does the last fan wait to hear that the seat is taken?"
options:
  - "About 150 ms"
  - "About 45 seconds"
  - "About 4.5 seconds"
  - "No wait; locks never queue"
correct: 2
explanations:
  - "That is the wait for one fan. The lock passes one holder at a time, so the last of 30 fans waits behind 29 others."
  - "That multiplies by 1.5 instead of 0.15. 30 x 150 ms is 4,500 ms, which is 4.5 seconds."
  - "Right. Each fan holds the lock for 150 ms, so the 30th waits about 30 x 0.15 = 4.5 seconds, just to be told no."
  - "A lock is exactly a queue. Others wait until the holder commits. A single conditional update avoids the queue because it holds nothing."
```

```quiz
type: mcq
question: "Mina's hold on seat 12 expired at 10:10. Hadi held the seat at 10:11. Mina's payment is authorized at 10:12. Which check stops Tazkara from selling the seat twice?"
options:
  - "Confirm the seat only if the hold id is still hers"
  - "Check that her phone's clock shows a time before 10:10"
  - "Capture the money first, and check the seat afterwards"
  - "Lock every seat for the whole length of the sale"
correct: 0
explanations:
  - "Right. The confirm is a conditional update on the hold id. Hadi's hold replaced Mina's, so her confirm changes 0 rows, and her authorization is voided."
  - "A phone clock can be wrong or changed by the user. The store must decide from its own data and its own clock."
  - "Taking the money first means a refund when the check fails. It is the wrong order, and it does not stop the second sale."
  - "A lock for the whole sale would stop all buying for everyone else. The problem needs a check at the moment of the sale, not a longer lock."
```

```quiz
type: mcq
question: "The nightly check finds debits of 4,812,400 and credits of 4,812,350 across the whole ledger. Which of these can leave the books off by 50?"
options:
  - "A webhook posted twice with the same id"
  - "A refund reversed twice under two ids"
  - "Prices rounded when shown to users"
  - "A sale stored with one line missing"
correct: 3
explanations:
  - "A repeated post of a balanced transaction adds equal debits and credits, so the two sides stay equal. It makes the money wrong, but not unbalanced."
  - "Each reversal is itself balanced, so the totals stay equal. This is a real bug that the balance check cannot see."
  - "Display rounding happens when a person looks at a price. It does not change the stored entries."
  - "Right. A transaction without one of its lines adds more to one side than the other, so the totals differ by the size of the missing line."
```

```quiz
type: mcq
question: "A payment is already captured. Then a late 'authorized' event for it arrives with a new event id. What should the worker do?"
options:
  - "Move it back to authorized, since it is the newest event"
  - "Save the event, and keep the status captured"
  - "Delete the payment and rebuild it from the events"
  - "Ask the provider, then ignore its answer anyway"
correct: 1
explanations:
  - "Arrival order is not event order. A payment that has been captured must not move back, or the books will think the money was never taken."
  - "Right. The event is new, so it is saved, but its state ranks lower than captured, so it changes nothing. A payment only moves forward."
  - "Rebuilding from events that arrive in any order brings the same problem back, and it throws away the saved history."
  - "Asking the provider is a good habit, but ignoring the answer makes the call pointless. The answer should set the state."
```
