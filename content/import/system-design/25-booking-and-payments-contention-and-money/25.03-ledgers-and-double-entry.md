Seats were a race to win one row. Money is a different problem. Nobody has to win it, but everybody has to be able to prove every number. This is the second deep dive of the design loop on Tazkara, and it serves the rule from chapter 25.1: money is never lost. A ledger is the tool that makes that rule checkable.

## A balance column has no history

<InteractiveCanvas slug="sysdesign-m25-balance-no-trail" />

A refund of 30 runs twice because of a retry. The balance goes from 100 to 70 to 40. Support asks why, and the database can only answer "40". Nothing shows which step took the extra 30. A number that is updated in place cannot explain itself.

<GoDeeper title="Go deeper: why an audit log next to the balance is not enough">

The usual first fix is an audit table: every time the code changes the balance, it also writes a log row. That is two writes. If the app crashes between them, the log and the balance disagree, and you have the dual-write problem from chapter 14.4 inside your own database. Wrapping both in one transaction (chapter 7.4) helps, but the balance is still the truth and the log is a copy. When they differ, which one do you believe?

A ledger turns this around. The entries are the truth, and the balance is only a sum of them. Nothing can disagree, because there is only one list.

The retry in the picture is also a lesson. A refund job that runs twice should not change the money twice. That is the idempotency problem from chapter 6.4, and beat 5 shows how the ledger solves it. A "subtract 30" update is not idempotent by nature, just like the atomic counter in the DynamoDB documentation [S42].

</GoDeeper>

## Entries only grow, and add to zero

<MermaidDiagram title="A ledger in three tables" chart={`erDiagram
  ACCOUNT {
    string name PK
    string kind
  }
  TRANSACTION {
    string id PK
    string source_id UK
    datetime created_at
    string reverses
  }
  ENTRY {
    string transaction_id FK
    string account FK
    string side
    int amount_cents
  }
  TRANSACTION ||--|{ ENTRY : "has 2 or more"
  ACCOUNT ||--o{ ENTRY : "receives"
`} legend="A transaction is one business event. It has two or more entries. Each entry is a debit or a credit on one account. The debits and credits of a transaction add up to the same total." />

A ledger is a list of entries that only grows. One business event is one transaction, made of two or more entries. Each entry is a debit or a credit, which are just the two sides of a move. In every transaction the debits and the credits add up to the same total. A balance is not stored. It is the sum of the entries on one account.

<GoDeeper title="Go deeper: why two sides, and Tazkara's accounts">

Every move of money has a "from" and a "to". Writing both sides, always, is called double-entry bookkeeping. It gives you one cheap test: add all debits and all credits in the whole ledger. They must be equal. If they are not, some transaction lost a side, and you know the books are wrong before any customer does. That check is called a trial balance.

The course uses one convention, and it is not the only one: a balance is debits minus credits, so an account the provider holds for us shows as positive and an account we owe shows as negative. {/* source needed: a primary reference for double-entry bookkeeping and the usual debit and credit sides by account type; the course states its own convention and does not claim it is the only one. */}

Tazkara needs three accounts for ticket sales:

| Account | What it means | Sign in our convention |
|---|---|---|
| provider-clearing | Card money the provider holds for us, not yet paid out | Positive |
| organizer-payable | Money we owe the organizer (90%) | Negative |
| fee-revenue | Tazkara's own 10% | Negative |

A ticket costing 100 (a course number) is one transaction of three entries: debit provider-clearing 100, credit organizer-payable 90, credit fee-revenue 10. Debits are 100 and credits are 90 + 10 = 100. Two later events add more transactions: a payout to the organizer, and a refund. The provider and the organizer are outside Tazkara, so each account is Tazkara's record of a promise, not a bank balance.

A balance is a sum, and summing a long list on every request is slow. There are two usual answers. Keep a balance row per account that is updated in the same transaction as the entries, and compare it with the real sum every night. Or take a snapshot (the balance up to entry number N) and add only the entries after it. At Tazkara's 167 payments a second, an index on the account and a nightly check is enough.

</GoDeeper>

## Post a sale, then break the books

<InteractiveCanvas slug="sysdesign-m25-post-entries" />

Post a ticket sale of 100: take it from the card, owe 90 to the organizer, keep 10 as the fee. Tap an entry out and watch the check. With a side missing, the books are off by exactly the missing amount. The fix is one more entry, never an edit.

<GoDeeper title="Go deeper: what a missing side looks like in real life">

A missing side is the most common ledger bug. It comes from code that posts the money line and crashes before the fee line, or from a new feature that forgets a fee. Every case where the check fails is worth an alarm, because it means the ledger lost its one promise.

Two habits stop it. First, post all the entries of a transaction in one database transaction (chapter 7.4), so a crash leaves none of them or all of them. Second, make the ledger refuse an unbalanced transaction before it stores anything. You write that check in chapter 25.5.

The nightly trial balance is the safety net, not the first defence. It finds a gap after the fact. Refusing at the door finds it at the moment the bug runs.

Some teams add a "suspense" account that takes any leftover amount so a transaction always balances. It is tempting and it hides the bug, because the books look fine while the suspense account fills with unexplained money. Use it only as a clearly named, watched holding place, never as an automatic repair.

</GoDeeper>

## A refund adds lines, never edits

<InteractiveCanvas slug="sysdesign-m25-reversal" />

The refund job adds three new entries that swap every debit and credit of the sale. The ledger grows from 3 entries to 6. The balances return to zero. The auditor can still see the sale and the refund. Nothing was edited or deleted.

<GoDeeper title="Go deeper: why history must not change">

Other systems have already read the sale. A report for last month, an email sent to the organizer, a payout file: all of them used the old entries. If you edit the sale afterwards, those reports no longer match the ledger, and nobody can say why. A reversal keeps every old report true. It records that something changed today, not that it never happened.

A mistake is fixed the same way. Reverse the wrong transaction, then post the right one. Both stay visible, and the history shows the correction and its date.

A strong habit is to give the app's database role only permission to insert and read ledger tables, with no update or delete. Then a bug or a tired developer cannot rewrite history, because the database refuses.

A partial refund is a second, smaller transaction with its own entries, not an edit of the first. The ledger can hold many reversals for one sale, as long as together they never reverse more than the sale. In chapter 25.5 your `reverse` function refuses a second full reversal of the same transaction.

</GoDeeper>

## The same event twice posts once

<InteractiveCanvas slug="sysdesign-m25-same-event-twice" />

The provider sends "paid pay_91", gets no reply in time, and sends it again. Both copies reach the worker. The ledger holds one posting. The second is recognised by its id and changes nothing.

<GoDeeper title="Go deeper: the id, and where it must live">

This is idempotency (chapter 6.4) applied at the ledger. Every transaction carries a source id, such as the provider's payment id or event id. The ledger enforces that this id exists at most once, with a unique key.

```sql
CREATE TABLE ledger_tx (
  id          bigserial PRIMARY KEY,
  source_id   text NOT NULL UNIQUE,   -- the provider's event or payment id
  reverses    bigint REFERENCES ledger_tx(id),
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

The unique key and the entries must be in the same database and the same transaction. If the id lives in a cache and the entries in a table, a crash between them leaves one without the other, which is the gap from chapter 14.5. With one transaction, either the id and all the entries are stored, or none of them are.

When the same id arrives again with the same content, the ledger returns "already posted" and does nothing. When the same id arrives with different content, that is a bug somewhere, and the ledger must refuse loudly. Stripe's idempotency keys follow the same rule: a repeated key returns the saved result, and the same key with different parameters is an error [S80].

In PostgreSQL, `INSERT ... ON CONFLICT DO NOTHING` reports 0 rows when the id exists. {/* source needed: PostgreSQL documentation for INSERT ... ON CONFLICT; the course relies on the behaviour described. */} Check the row count to tell "posted" from "already posted".

How long must the id be kept? As long as a copy can arrive (chapter 14.5). For money, that means forever. A ledger id is not a cache entry.

</GoDeeper>

## Count whole cents, not decimals

<InteractiveCanvas slug="sysdesign-m25-cents-not-floats" />

Add 0.1 and 0.2 in most programming languages and you get 0.30000000000000004. Add 10 and 20 cents and you get exactly 30. So money is stored as whole numbers of the smallest unit, and every sum stays exact.

<GoDeeper title="Go deeper: integers, rounding and the last cent">

Decimal fractions like 0.1 cannot be stored exactly in binary floating point, so tiny errors appear and grow. Run in Node.js on 2026-10-24: adding 0.10 a million times gives 100000.00000133288, while adding 10 cents a million times gives exactly 10000000. Whole numbers are exact up to `Number.MAX_SAFE_INTEGER`, which is 9,007,199,254,740,991. In cents that is about 90 trillion, far beyond Tazkara.

Not every currency has two decimal places. Some have none and some have three, so store the smallest unit and the currency together. {/* source needed: ISO 4217 minor units per currency; the course claims only that the number of decimal places differs by currency. */}

Splitting money is where a cent gets lost. Take a 10% fee on 3335 cents. The fee is 333.5, which rounds to 334, and the organizer's share is 3001.5, which rounds to 3002. Both rounded up, so 334 + 3002 = 3336, one cent more than the customer paid. The ledger is now off by a cent on every such sale. The safe rule is to round one share and give the other whatever is left:

```js
function splitSale(totalCents, feePercent) {
  const fee = Math.round((totalCents * feePercent) / 100);
  return { fee, organizer: totalCents - fee };
}
// splitSale(10001, 10) -> { fee: 1000, organizer: 9001 }, and 1000 + 9001 = 10001
// splitSale(3335, 10)  -> { fee: 334, organizer: 3001 }, and 334 + 3001 = 3335
```

The two shares always add up to the total, so the transaction always balances. Which share absorbs the leftover cent is a business rule, and you should write it down.

Display is a separate step. Convert cents to a decimal string only when you show a price to a person. Never do arithmetic on the displayed value.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "I would not keep a balance as the truth. I would keep an append-only ledger. Each business event is one transaction with two or more entries, and debits equal credits. A balance is the sum of the entries. Amounts are integers in cents. A refund is a new transaction that reverses the old one, so history never changes. Each transaction has a unique source id, in the same database transaction as the entries, so a repeated webhook posts once. A nightly trial balance checks that all debits equal all credits."

**Expect:** "How do you read a balance quickly?" **Answer:** "Keep a balance row per account, updated in the same transaction as the entries, and verify it against the sum every night. For huge ledgers, add snapshots."

</GoDeeper>
