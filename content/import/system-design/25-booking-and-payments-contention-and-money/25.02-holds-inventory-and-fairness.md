## Three paths: wait, hold, pay

<MermaidDiagram title="Tazkara, first sketch" chart={`flowchart LR
  F["Fans"] --> W["Waiting room"]

Three paths. The waiting room lets fans in at a steady rate. The booking service holds seats in the seat table. The payment service talks to the card provider, confirms the seat and writes the ledger. This chapter covers the first two. Chapters 25.3 and 25.4 cover the money.

<GoDeeper title="Go deeper: the contract and the table">

The booking API is small.

```text
POST /holds        body: { "eventId": 1, "seatId": "B12" }
                   -> 201 Created   { "holdId": "...", "expiresAt": "..." }
                   -> 409 Conflict  the seat is held or sold
                   -> 429 Too Many Requests   not admitted yet, or too fast
POST /holds/{id}/pay   header: Idempotency-Key   -> 200 with a ticket, or 402, or 409 (hold gone)
```

One table holds the truth about seats. Each seat is one row, so a rush on one seat is a rush on one row.

```sql
CREATE TABLE seats (
  event_id         int         NOT NULL,
  seat_id          text        NOT NULL,
  status           text        NOT NULL DEFAULT 'free',   -- free, held or sold
  hold_id          uuid,                                  -- who holds it now
  hold_expires_at  timestamptz,                           -- when the hold ends
  sold_to          text,
  PRIMARY KEY (event_id, seat_id)
);
```

The seat map that fans see is a read of this table, or of a copy of it that may be a few seconds old (we promised that in chapter 25.1). A stale map is fine because the hold request is the real check. A wrong "free" on the map only costs the fan a 409.

The waiting room and the booking service are separate on purpose. The waiting room is a cheap static page and a counter that scales on its own. The booking service and the seat table are the part that must not be flooded.

</GoDeeper>

## Check then write oversells

<InteractiveCanvas slug="ticketline-seat-hold-race" />

Raise the buyers above the seats. The unguarded path lets every buyer through in the worst case. The atomic path accepts only as many as there are seats. For numbered seats the rule is the same, one seat at a time: one row, one winner.

<GoDeeper title="Go deeper: why the gap exists, and what it costs">

A check followed by a write has a gap between its two steps. Any number of other requests can run inside that gap. On one laptop with one buyer, the gap never shows. Under 80,000 requests a second it shows within a second.

The fixes are the three from chapter 7.5: a row lock, a version check, or a single statement. The rest of this chapter chooses between them for Tazkara. The canvas treats the seats as a counter (4 left), which is how a general admission area works. With numbered seats there are 20,000 separate rows and each row is its own small race.

The race is not rare. At 20 fans per seat, every popular seat has a rush on it. A bug that needs two requests at the same instant on the same row is a bug that happens thousands of times in the first ten seconds.

</GoDeeper>

## A hold is a seat with a clock

<MermaidDiagram title="The life of one seat" chart={`stateDiagram-v2
  [*] --> Free
  Free --> Held: hold (sets hold id and expiry)
  Held --> Sold: confirm, hold still current
  Held --> Free: expires or buyer leaves
  Sold --> [*]
`} legend="A seat is free, held or sold. A hold has an expiry. Only a hold that is still current can become sold." />

A seat is free, held or sold. A hold carries an expiry time. If the buyer does not finish, the seat falls back to free by itself. Only a hold that is still current can become sold, and sold is final.

<GoDeeper title="Go deeper: three ways to make a hold expire">

Expiry is part of the data, not an afterthought. There are three ways to do it, and they work well together.

**Check the time in every write.** The hold statement accepts a seat if it is free, or if it is held and `hold_expires_at` is already in the past. Then an expired hold is as good as free the moment its time passes, and no background job has to run first. This is the rule that keeps the system correct.

**Sweep.** A job runs every few seconds and sets expired holds back to free. It does not decide anything. It keeps the seat map tidy so fans see a seat come back. If the job stops for an hour, nothing breaks, because the statement above already ignores dead holds. This is the same habit as PasteBox in chapter 1.4: reads never trust the cleanup job.

**A key with a time to live in a cache.** Some teams keep holds only in a cache and let the key expire. It is fast, but now the truth is in two places: the cache says held, the database says free. Every crash and every eviction can make them disagree. For Tazkara the database is the truth, and a cache may only help the seat map.

Which clock? Use the database's own `now()`, not the app server's. Server clocks drift (chapter 10.2), and a fan whose request lands on a fast server would get a shorter hold than the next fan. One clock, the database's, keeps every hold the same length.

The same idea appears in queues. An SQS message that a worker has taken is hidden for a visibility timeout (30 seconds by default), and if the worker does not finish, the message becomes visible again [S84]. A hold is a visibility timeout for a seat.

How long should a hold be? Longer holds are kinder to slow typers and to phones on weak data. They also keep seats away from other fans. With 20,000 seats and about 30% of buyers who never pay (a course assumption), a 10-minute hold means that for 10 minutes some seats look sold and are not. Ten minutes is a course choice. Say the number and say what you give up.

</GoDeeper>

## A lock keeps buyers safe, and in line

<InteractiveCanvas slug="sysdesign-m25-hold-lock-queue" />

Lock the row, check the card, then sell. Nobody oversells. But Omar waits while Dina's card check runs. With a 200 ms check inside the lock, the 20th fan behind one seat waits about 4 seconds, just to hear no.

<GoDeeper title="Go deeper: pessimistic locking and why a drop hurts it">

Chapter 7.5 showed `SELECT ... FOR UPDATE`. It is called pessimistic because it assumes a collision will happen and makes everyone wait their turn. It is the right tool when collisions are common and the work inside the lock cannot be redone.

The cost is the hold time. If a lock is held for 200 ms, one row passes 5 lock holders a second (1 divided by 0.2). Twenty fans queued on one popular seat need 20 x 0.2 = 4 seconds for the last one to be told no. While they wait, each one holds a database connection. A pool of 100 connections is used up by five popular seats with 20 waiting fans each. After that, even fans who want free seats cannot get a connection. A slow row has slowed the whole system.

Locks can also deadlock when a request takes two seats in different orders. Chapter 7.5 gave the habit: always lock rows in the same order, such as by seat id.

The fix is to keep the lock short. Do the card check outside the transaction, never inside. Then the lock covers one fast statement, and the waiting nearly vanishes. That leads to the next beat: if the lock covers only one statement, you do not need a lock at all.

</GoDeeper>

## One statement, no waiting

<InteractiveCanvas slug="sysdesign-m25-hold-atomic" />

Put the check inside the write: hold the seat only if it is free, or its hold has run out. The store applies the two requests one after the other. One row changes, one buyer wins, and the other hears "taken" at once and tries another seat.

<GoDeeper title="Go deeper: the statement, and optimistic versus pessimistic">

The whole hold is one statement. The `WHERE` clause is the check, and it is inside the write, so there is no gap.

```sql
UPDATE seats
SET status = 'held', hold_id = $1, hold_expires_at = now() + interval '10 minutes'
WHERE event_id = $2 AND seat_id = $3
  AND (status = 'free' OR (status = 'held' AND hold_expires_at <= now()));
```

If the driver reports 1 row changed, return 201 with the hold. If it reports 0 rows, return 409 "taken". This is compare-and-set from chapter 7.5, with the seat's status as the thing compared. DynamoDB has the same idea as a conditional write [S42].

This is called optimistic: assume there will be no collision, write, and handle the loser. The trade-off in the usual shape:

- **The choice.** One conditional update, no lock held across other work.
- **Why now.** Collisions on a popular seat are certain, but the statement takes about a millisecond, and a refusal is a complete answer.
- **What it buys.** No waiting line, no connection held, and a refusal in one round trip.
- **What it costs.** The loser must pick another seat. A client that retries the same seat in a loop creates a retry storm: retries multiply load, and unbounded retries can hold a system down [S89, S94]. So retries must be bounded, as in chapter 7.5, and the client should move to a different seat.
- **The alternative.** A row lock (previous beat), which suits rare, long, many-step edits.
- **When to switch.** If the work between check and write cannot be redone, such as a multi-step approval, use a lock and keep it short.

A cart of four seats together is one transaction: update all four rows with `seat_id IN (...)`, and commit only if 4 rows changed. Otherwise roll back, and no seat stays held. Two carts that want overlapping seats can deadlock if they touch rows in different orders, so sort the seat ids first.

General admission is a different shape: one counter for "tickets left" is one hot row. Every sale updates it, one after another. If each update takes 2 ms the row passes about 500 a second, and no extra server helps. Split the counter into sections or shards, so many rows share the load, as in chapter 9. A DynamoDB partition, for comparison, is designed for up to 1,000 write units a second [S40].

</GoDeeper>

## A late payment must not take the seat

<InteractiveCanvas slug="sysdesign-m25-late-payment" />

Dina's hold ran out while she typed. Omar now holds the seat. Her payment still comes in. Before the seat is sold, the confirm step asks one question: is this hold still the current one on the seat? If not, it is refused, the card authorization is voided and Dina is told.

<GoDeeper title="Go deeper: confirm is a conditional update too">

The confirm step is one more conditional statement. It sells the seat only if the seat is still held by this exact hold.

```sql
UPDATE seats
SET status = 'sold', sold_to = $2
WHERE event_id = $3 AND seat_id = $4 AND hold_id = $1 AND status = 'held';
```

The hold id works like a fencing token (chapter 12). A fencing token is a number that grows with each new lock holder, and storage rejects the older ones [S70]. Here the hold id is new for each hold, and the seat row remembers only the current one. A paused or slow buyer with an old hold id is refused, the same way a paused client with an old lease is refused.

Without this check, the failure is quiet and bad. Dina pays, the code marks the seat sold to Dina, and Omar's hold is overwritten. Two people think they own seat 7. Neither the database nor the card shows an error. The clue comes at the gate, or in a support ticket.

Confirm should be safe to repeat. If the same hold id has already sold the seat, a second confirm returns the same ticket. That matters in chapter 25.4, where duplicate messages are normal.

There is a design choice. When a buyer starts paying, you can extend the hold by two more minutes (a course number), so a payment that is in progress is less likely to be late. That keeps a seat away from other fans for a little longer. Tazkara chooses to extend once, because a late payment after a successful authorization is more painful than a slightly longer hold.

</GoDeeper>

## Let fans in at a steady rate

<InteractiveCanvas slug="sysdesign-m25-waiting-room" />

Drag the admit rate. Too fast and the seat store carries many times its plan. Too slow and the show takes an hour to sell out. A good rule: keep about as many fans inside as there are seats. With 2 minutes inside, that is 20,000 divided by 120, about 167 fans a second.

<GoDeeper title="Go deeper: Little's law, and fairness">

The number inside at once is the arrival rate times the time each one stays (Little's law, L = lambda W, chapter 2.5 [S5]). If fans stay 120 seconds and you admit 167 a second, about 167 x 120 = 20,040 are inside. That is one shopper per seat. Admit more and most shoppers will never get a seat. Admit fewer and seats stay free while the line outside is long.

The picture uses these course numbers: each admitted fan makes 4 requests, the seat store is planned for 5,000 requests a second, and half of the admitted fans end up buying. Admitting 167 a second gives 668 requests a second, 13% of plan, and a sell-out in about 4 minutes. Admitting 20,000 a second (no waiting room) gives 80,000 requests a second, 16 times the plan.

The waiting room is cheap by design. It is a static page plus a counter, and it hands out a signed admission token with an expiry. The booking service accepts only requests that carry a valid token. Fans stay in line on a page that costs almost nothing to serve.

Fairness is a product rule, and engineers must make it explicit. There are three common rules.

- **First come, first served.** It is simple to explain. It rewards fast connections and bots, and it punishes a phone on weak data.
- **A random draw among everyone who arrives in the first few minutes.** A fan with a slow connection gets the same chance as a fast one. It needs a fixed window, such as 5 minutes, and it is harder to explain.
- **Pre-registration with a lottery.** It also fights bots, but it needs accounts and a longer plan.

Tazkara picks the random draw in a 5-minute window, and a limit of 4 seats for each fan. Per-fan limits and rate limits use the token bucket from chapter 6.5 [S30, S32]. None of these rules is perfect. A good answer names the rule, the person it hurts and the reason.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "I would make a hold one conditional update: set the seat to held with a hold id and an expiry, only if it is free or its old hold has expired. One row changed means 201, none means 409. No lock is held, so there is no queue, and the database clock sets the expiry. Confirm is another conditional update that checks the hold id, so a late payment cannot take a seat that was re-held. In front of it I would put a waiting room that admits about as many fans as there are seats, using Little's law."

**Expect:** "Why not a distributed lock in a cache?" **Answer:** "The seat table is already the source of truth, and a conditional update on it is atomic. A cache lock adds a second place that can disagree and needs fencing to be safe. I would only add it if the work could not live in one database."

</GoDeeper>
