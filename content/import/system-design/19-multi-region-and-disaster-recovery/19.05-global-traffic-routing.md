## Dark until the cache expires

<InteractiveCanvas slug="sysdesign-m19-dns-timeline" />

Three failed checks, 30 seconds apart, take 90 seconds to change the DNS answer. A phone that cached the old answer just before then keeps using it for up to 60 seconds more. Add them: 150 seconds. The check time and the cache time are two separate waits, and users feel both.

<GoDeeper title="Go deeper: what makes up the wait">

The wait has two parts, and each has a knob. The first is detection. Amazon Route 53 health checkers in many places send a request to the endpoint, every 10 seconds or every 30 seconds as you choose. The endpoint must fail a number of checks in a row, the failure threshold, before it counts as down. Route 53 combines the checkers' views: if more than 18% of them say healthy, the endpoint counts as healthy, which stops one checker's bad network from failing a good endpoint. The detection time is the interval times the threshold: 30 s x 3 = 90 s, or 10 s x 3 = 30 s. A faster check finds a real fault sooner and also reacts sooner to a false alarm.

The second part is the cache, the TTL from chapter 3.3. A record cached just before the answer changed lives for the whole TTL. So the worst case is detection plus TTL, and it can never be shorter than the TTL. Setting the TTL lower costs more DNS lookups. A lower TTL set on the day of the disaster does nothing for caches that already hold the old answer, as 3.3 showed, so set it ahead.

Two things make it worse than the sum. Apps that hold a long-lived connection, such as the WebSockets in chapter 3.5, stay on the old address until the connection closes. And some resolvers and clients may keep answers longer than the TTL, so keep the failed region's addresses answering with an error page, not silence, as long as you can.

## Route users, then fail a region

<InteractiveCanvas slug="sysdesign-m19-route-users" />

Pick a routing policy, then tap a region to fail it. Latency routing sends each user to the nearest healthy region. Location routing sends them by country. Failover keeps everyone on A until it fails. Anycast has no DNS cache to wait for. Watch where each group of users lands and how long they are dark.

<GoDeeper title="Go deeper: the four policies, side by side">

All four policies answer the same question: which healthy region gets this user? They differ in what they prefer and in how the user learns the answer changed.

| Policy | It prefers | When Region A fails | Dark time |
|---|---|---|---|
| Latency | the region with the lowest round trip | A's nearest users move to B | detection + TTL |
| Location (by country) | the region assigned to the user's country | A's countries move to the fallback | detection + TTL |
| Failover | the primary, then the secondary | everyone is already on A, all move to B | detection + TTL |
| Anycast | the nearest announcement of one address | routes change, the address stays | detection only |

The three DNS policies share one wait: the DNS answer changes and then every cache must expire. With a TTL of 60 seconds and 90 seconds of detection that is 150 seconds. With a TTL of 300 seconds it is 390 seconds. Anycast, such as AWS Global Accelerator, gives the service static addresses announced from the AWS edge. There is no changed answer to cache, so users move when the health check does. The AWS guide says Global Accelerator also avoids the caching issues of DNS [S107]. The detection number for anycast in the picture, 90 seconds, is a course assumption equal to the DNS case, so the gap you see is the TTL alone.

Choosing between them. Latency routing is the default for an active-active app. Failover routing is the natural fit for active-passive. Location routing is for rules about where a country's users may be served, which is chapter 19.6. Anycast fits when you want the quickest move and can pay for the service. The AWS guide also lists weighted routing and traffic dials that change the percentage sent to each region, which are useful for sending 5% of users to a new region first. Changing a weight is a control plane action, so for a real disaster it prefers switches that are data plane actions, such as the Route 53 Application Recovery Controller routing controls [S107].

## Health first, then the policy picks

<MermaidDiagram title="What a routing policy decides" chart={`flowchart TD
  U["A user's request arrives"] --> H{"Is the region healthy?"}
  H -->|"no"| X["Never pick it"]
  H -->|"yes"| P{"Which policy?"}
  P -->|"latency"| L["Pick the lowest round trip"]
  P -->|"location"| G["Pick by the user's country, even if slower"]
  P -->|"failover"| F["Pick the primary, the secondary only if the primary fails"]
`} legend="Every policy checks health first, then applies its own preference." />

Every policy checks health first. Then it picks. Latency chooses the fastest region. Location chooses by the user's country. Failover chooses the primary until it fails. Use location routing when a rule says where a country's users must be served, even if another region is faster. Chapter 19.6 returns to that rule.

<GoDeeper title="Go deeper: who the router thinks the user is">

DNS routing decides from the address of the resolver that asks, not the phone behind it. Chapter 3.3 noted that a user on a far-away public resolver can be sent to the wrong region. For latency routing that costs speed. For location routing it can cost compliance, if a rule says a country's users must stay in a region, because the router may misjudge where the user is. Use location routing as a first line of defence and enforce the real rule in the data layer, where the user's account says which region owns their data.

## The survivor must carry everyone

<InteractiveCanvas slug="sysdesign-m19-survivor-overload" />

Each region serves 50 requests a second and can handle 60. When A fails, its users move to B, which now gets 100 and can serve 60. Both groups see errors. Failover moves traffic, not capacity. Both regions must be sized for the full load, or the survivor must shed the extra and stay up for the users it can serve.

<GoDeeper title="Go deeper: sizing, shedding and the retry trap">

The sizing rule is the same one as for zones in 19.2, with a bigger price. With two regions, each must handle 100% of the traffic alone, so the pair costs about twice one region. With more regions the factor falls: three regions, each sized to carry half of the total, cost 1.5 times, as three zones did.

If you cannot afford idle capacity, you can shed load. The survivor serves as many users as it can, and answers the rest with a quick refusal, rather than slowing down for everyone. The Google SRE book describes load shedding and a server-wide retry budget for this reason [S91].

The trap is the retry. Failed requests are retried. Module 16 showed how retries multiply load, 243 times in a five-layer example [S89], and how an overloaded system can stay down after the original cause is gone [S94]. Moving a whole region's users onto a survivor at once is a good way to start that. Move users in steps if you can, use weighted routing for it, and keep retries capped.

Scaling up after the failure is another dependency on the control plane, as the AWS guide warns. Some teams scale the standby to a size that handles the first wave of traffic, then rely on automatic scaling. Others keep the full size ready. The guide notes this as a trade between cost and resilience [S107]. Whichever you choose, test it: the guide's active-active test list includes whether the other regions can handle all the traffic [S107].

</GoDeeper>

## A health check can fail a healthy region

<MermaidDiagram title="One slow dependency fails every region" chart={`flowchart LR
  C["Health checker"] -->|"deep check: calls the payment provider"| A["Region A: app healthy, provider slow"]
  C -->|"deep check: calls the payment provider"| B["Region B: app healthy, provider slow"]
  A --> X["Both marked unhealthy"]
  B --> X
  X --> Y["No region left to route to"]
  C -->|"shallow check: is this region's own app answering?"| Z["Both stay healthy: users see a slow payment step only"]
`} legend="A deep check that depends on something both regions share fails both regions together." />

A health check that calls a shared dependency, such as a payment provider, fails in every region when the provider is slow. Then no region looks healthy and routing has nowhere to go. Prefer checks of the region's own parts, and raise the dependency's failure as a separate alarm. When all regions look unhealthy, a router should fail open and keep sending traffic.

<GoDeeper title="Go deeper: the same shape, three times">

Chapter 4.4 gave the rule: dependency checks can fail a whole fleet at once, so prefer local checks and fail open [S19]. The multi-region version is the same mistake one level up. A check that is "deeper" feels safer, because it proves more. But every extra thing it proves is something that, when it fails, takes the region out of rotation. If both regions depend on it, both go.

The Meta outage of 4 October 2021 had the same shape. Meta's DNS servers were built to withdraw their anycast routes when they could not reach the data centres. When a maintenance command cut the backbone, every server could not reach the data centres, so every server withdrew its routes together, and the internet could no longer find Meta's DNS [S136]. A rule that is right for one server became a disaster when all servers applied it at once.

Three habits help. Check what the region itself controls, and watch shared dependencies with a separate alarm that pages a person. Add a floor: never let automation remove the last healthy region, or more than a set share of capacity, which echoes AWS's own fix after the October 2025 event, where health checks removed capacity too fast [S135]. And keep a way in that does not depend on the system you are fixing, such as a second way to reach the routing switches.

</GoDeeper>
