In chapters 12.5 and 12.6 you followed a Raft cluster by eye. The safety of the whole algorithm rests on a few small rules, and a small mistake in one of them does not crash anything. It lets two leaders win the same term, or lets a committed entry be lost, and the cluster looks fine until the day it does not. In this chapter you write those rules as plain functions, so you know exactly what each one promises.

By the end you will have five tested JavaScript functions. `majority` and `toleratedFailures` do the quorum maths. `isUpToDate` compares two logs. `handleRequestVote` is a server's answer to a vote request. `commitIndexFor` is the leader's rule for what counts as committed. You will reuse all five in challenge 11, where they run inside a Raft node on a simulated network.

## Why these are pure functions

A Raft node is full of timers and messages, and those are hard to test. The rules are not. Each rule takes some state and a request, and returns an answer. If you write them as functions that read their inputs and return a new result, a test can feed them any situation and check the answer. No network, no clock, no randomness.

There is one more reason. The most dangerous bugs in this area are rules that change something they should not. If `handleRequestVote` edits the state object you passed in, the caller cannot tell whether the node's term changed, and a rejected vote can quietly change a vote that was already given. So the contract below says: never change an input, return a new state.

## The contract

Fix the rules first. The tests check these exact rules.

**majority(n)** returns the smallest number of servers that is more than half of `n`. For 3 it is 2, for 4 it is 3, for 5 it is 3. **toleratedFailures(n)** returns how many servers can be down while a majority is still up: `n` minus the majority. For 4 servers it is 1, the same as for 3.

**isUpToDate(candidate, mine)** compares two logs by their last entry. Each argument is `{ lastLogIndex, lastLogTerm }`. The log with the larger last term is more up to date. If the last terms are equal, the longer log, the one with the larger last index, is more up to date. Equal logs count as up to date. It returns true when the candidate is at least as up to date as mine.

**handleRequestVote(state, request)** answers a vote request. The state is `{ currentTerm, votedFor, log }`, where `log` is a list of entries such as `{ term: 2 }` and the first entry has index 1. The request is `{ term, candidateId, lastLogIndex, lastLogTerm }`. It returns `{ state, reply }`, where `reply` is `{ term, voteGranted }`. The rules, in order:

1. If `request.term` is smaller than `currentTerm`, reject. The reply carries the server's own term, and the state does not change.
2. If `request.term` is larger than `currentTerm`, the server adopts the new term and forgets its old vote, because it has not voted in the new term yet. This happens even if it then refuses the vote.
3. Grant the vote only if the server has not voted in this term, or already voted for this same candidate, and the candidate's log is at least as up to date as the server's own. When it grants, it remembers the candidate in `votedFor`.
4. The reply always carries the term the server holds after step 2.

**commitIndexFor({ matchIndex, log, currentTerm, commitIndex })** is the leader's commit rule. `matchIndex` has one number for every server, the leader included: the highest index known to be stored there. It returns the highest index `N` above `commitIndex` such that a majority of servers have stored `N` and the entry at `N` belongs to `currentTerm`. If there is none, it returns `commitIndex`. It never goes down.

Notice that `majority` sits under three of the others. If it were wrong by one, every other rule would still look sensible and be wrong. That is why the tests check it for both odd and even sizes.

## A worked example: one vote, by hand

A server is in term 2, has voted for S1 in that term, and holds the log `[{ term: 1 }, { term: 2 }]`. Three requests arrive, one after another, and each starts from the state the one before it left.

First, S3 asks for a vote in term 2, with `lastLogIndex` 2 and `lastLogTerm` 2. The term is not old. But the server already voted for S1 in term 2, and S3 is not S1. Reject, and the reply is `{ term: 2, voteGranted: false }`.

Second, S4 asks in term 3 with `lastLogIndex` 1 and `lastLogTerm` 1. The term is larger, so the server adopts term 3 and forgets its vote. Now the log check: the server's last term is 2, and S4's is 1, so S4 is behind. Reject. But the state has still changed: the term is now 3 and `votedFor` is `null`. The reply is `{ term: 3, voteGranted: false }`.

Third, S5 asks in term 3 with `lastLogIndex` 2 and `lastLogTerm` 2. The term matches, nobody has this term's vote, and the logs are equal. Grant. The state becomes term 3, `votedFor` S5.

The sub-goal in each case is to settle the term first, then ask the two questions about the vote and the log. Writing the code in that order keeps it short.

## Four ways this goes wrong

**Not resetting the vote on a new term.** If the server keeps `votedFor` from term 2 when term 3 begins, it refuses every candidate in term 3 except the old one. A cluster can then fail to elect anyone. The test "a newer term forgets the old vote" catches it.

**Comparing log length first.** A long log full of old entries is not more up to date than a short log with a newer last term. The rule looks at the last entry's term first and the length second. A candidate with a stale long log, if it wins, can erase committed entries.

**Changing the input.** If you write `state.currentTerm = request.term`, the object the caller holds has changed. A test freezes the input and calls your function; any write throws.

**Counting an old entry as committed.** An entry from an earlier term that sits on a majority of servers is not safe by that fact alone, because a later leader that never had it could still be elected and erase it. The commit rule counts copies only for entries of the current term. Older entries commit indirectly, when a later entry commits. A test builds exactly this situation.

solution: |
  function majority(n) {
    return Math.floor(n / 2) + 1;
  }

  function toleratedFailures(n) {
    return n - majority(n);
  }

  function isUpToDate(candidate, mine) {
    if (candidate.lastLogTerm !== mine.lastLogTerm) return candidate.lastLogTerm > mine.lastLogTerm;
    return candidate.lastLogIndex >= mine.lastLogIndex;
  }

  function handleRequestVote(state, request) {
    if (request.term < state.currentTerm) {
      return { state, reply: { term: state.currentTerm, voteGranted: false } };
    }
    let { currentTerm, votedFor } = state;
    if (request.term > currentTerm) {
      currentTerm = request.term;
      votedFor = null;
    }
    const mine = {
      lastLogIndex: state.log.length,
      lastLogTerm: state.log.length > 0 ? state.log[state.log.length - 1].term : 0,
    };
    const free = votedFor === null || votedFor === request.candidateId;
    const voteGranted = free && isUpToDate(request, mine);
    if (voteGranted) votedFor = request.candidateId;
    return { state: { ...state, currentTerm, votedFor }, reply: { term: currentTerm, voteGranted } };
  }

  function commitIndexFor({ matchIndex, log, currentTerm, commitIndex }) {
    let best = commitIndex;
    for (let n = commitIndex + 1; n <= log.length; n++) {
      const copies = matchIndex.filter((m) => m >= n).length;
      if (copies >= majority(matchIndex.length) && log[n - 1].term === currentTerm) best = n;
    }
    return best;
  }

## Check your understanding before you submit

Replay the three requests of the worked example against your function, one after the other, passing the state from each reply into the next call. You should see `{ term: 2, voteGranted: false }`, then `{ term: 3, voteGranted: false }` with `votedFor` null, then a grant to S5 in term 3. For the commit rule, take a log whose terms are `[1, 2, 3]` and a leader in term 3. With `matchIndex` `[3, 2, 2, 1, 1]` nothing above the old commit index should commit. With `[3, 3, 3, 1, 1]`, the answer is 3.

If a test fails, read its message first. Each one names the case, the expected result and what your code returned. The most common mistakes are keeping the old vote into a new term, comparing log length before the last term, and writing to the state you were given.
