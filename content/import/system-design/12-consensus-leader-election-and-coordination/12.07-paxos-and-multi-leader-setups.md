Raft is the newer way to agree. Paxos is the older one, and it sits inside many large systems. You do not need to build Paxos. You need to read about it without fear, and to say how it differs from Raft. This chapter walks the simplest version, which chooses one value.

## Prepare, promise, accept, accepted

<MermaidDiagram title="Single-decree Paxos with one proposer" chart={`sequenceDiagram
  participant P as Proposer
  participant A1 as Acceptor 1
  participant A2 as Acceptor 2
  participant A3 as Acceptor 3
  P->>A1: prepare(1)
  P->>A2: prepare(1)
  A1-->>P: promise(1), nothing accepted yet
  A2-->>P: promise(1), nothing accepted yet
  Note over P: 2 of 3 promised: a majority
  P->>A1: accept(1, A)
  P->>A2: accept(1, A)
  A1-->>P: accepted(1, A)
  A2-->>P: accepted(1, A)
  Note over P,A2: A is chosen: a majority accepted it
`} legend="Phase 1 is prepare and promise. Phase 2 is accept and accepted. Numbers grow with each attempt." />

A proposer wants to get one value chosen, say A. In phase 1 it sends a numbered prepare to the acceptors. A majority promise to ignore any lower number. In phase 2 it asks them to accept A. Once a majority has accepted, A is chosen, and it can never change.

<GoDeeper title="Go deeper: the rules each side follows">

There are three roles: proposers suggest values, acceptors vote on them, and learners find out the result. A server often plays all three. Every proposal has a unique number, and a later attempt uses a bigger number.

In phase 1, the proposer sends prepare(n) to the acceptors. An acceptor that has not promised a higher number answers with a promise: it will not accept any proposal numbered below n, and it reports the proposal with the highest number it has already accepted, if there is one. In phase 2, once the proposer holds promises from a majority, it sends accept(n, v). An acceptor accepts unless it has promised a higher number since. A value is chosen when a majority of acceptors accept the same proposal [S67].

Lamport wrote that Paxos, "when presented in plain English, is very simple" [S67]. The simple part is this single decision. The hard parts come after: using it again and again for a log, replacing failed servers, and recovering after a crash. Raft's authors ran a study that suggests students learn Raft more easily than Paxos [S68].

</GoDeeper>

## Two proposers, three acceptors

<InteractiveCanvas slug="sysdesign-m12-paxos-play" />

Two proposers want different values: P1 wants A, P2 wants B. Step through the messages and choose which acceptors each message reaches. Let P1 reach two acceptors with its accept, then start P2 with a higher number. Watch P2 discover A in the promises and change its mind. Then try to make both values chosen. You cannot.

<GoDeeper title="Go deeper: the safety rule in numbers">

Take three acceptors. P1 prepares with number 1 and gets promises from A1, A2 and A3. P1 sends accept(1, A) and A1 and A2 accept. Now A is chosen: 2 of 3 accepted it.

P2 prepares with number 2. Any majority it hears from includes at least one of A1 and A2, because two majorities of three always share an acceptor, as in 12.3. That acceptor says in its promise that it accepted (1, A). So P2 must send accept(2, A). It cannot send B. The value stays A.

Now suppose A3 is the only acceptor that P2 reaches first, with A1 and A2 silent. P2 cannot form a majority, so it cannot send anything. It tries again or waits. There is no state in which two different values are chosen, which is the safety Paxos promises. What is not promised is that every attempt finishes, which the next beat shows.

</GoDeeper>

## Two proposers can outbid each other

<InteractiveCanvas slug="sysdesign-m12-paxos-duel" />

P1 prepares with 1, then P2 prepares with 2 before P1 can finish. P1's accept is refused, so it prepares with 3. Now P2's accept is refused. Each proposer keeps raising the number and spoiling the other's round. Nothing is chosen, though nothing unsafe happened. This stuck state is called a livelock.

<GoDeeper title="Go deeper: why real systems pick one proposer">

Paxos is safe in every case but not always fast. Two proposers can keep outbidding each other forever. Lamport notes that progress needs a single distinguished proposer, a leader that the others leave alone. Because of the FLP result in 12.2, choosing that proposer needs randomness or real time [S67].

In practice, a proposer that fails waits a random time before trying again, like a Raft follower. Or the group elects one leader, and only the leader proposes. That leader is the key to the next beat.

</GoDeeper>

## Multi-Paxos is Raft's cousin

<MermaidDiagram title="Same shape, different details" chart={`flowchart LR
  subgraph MP["Multi-Paxos"]
    M1["Phase 1 once: win leadership with a higher number"] --> M2["Phase 2 for each log slot: accept"]
  end
  subgraph RF["Raft"]
    R1["Election once: win a term by majority vote"] --> R2["AppendEntries for each log entry"]
  end
`} legend="Both elect a leader once, and then need one round trip to a majority for each new entry." />

A real system chooses many values in a row: a log. Multi-Paxos does phase 1 once to win leadership, then runs only phase 2 for each new slot. Raft does an election once, then sends AppendEntries for each new entry. The shape is the same. The details differ.

<GoDeeper title="Go deeper: what is different">

| | Multi-Paxos | Raft |
|---|---|---|
| Leader | Any server that wins phase 1 with a higher number | Elected by vote in a numbered term |
| Log slots | Slots may fill in any order; gaps are filled later | Entries are added in order, with no gaps |
| Who may lead | Any server, which then learns the values it missed | Only a server whose log has every committed entry |
| Description | A family of variants | One full description, including how to change the members |

The main practical difference is the log. In Raft the leader's log is the source of truth, and followers are made to match it. In Multi-Paxos a new leader may need to fill gaps and re-propose values it did not know about. Raft restricts who can become leader to avoid that work, and in exchange has fewer cases to think about.

Both pay one round trip to a majority for each entry in the normal case. Both stop making progress without a majority.

## One leader per group, many groups

<MermaidDiagram title="Where each design is used" chart={`flowchart TD
  subgraph ONE["One leader per group, chosen by consensus"]
    SP["Spanner: a Paxos group for each piece of data, leader lease of 10 s"]
    DY["DynamoDB: 3 replicas per partition, Multi-Paxos, leader lease"]
  end
  subgraph MANY["Many writers, conflicts resolved later"]
    GT["DynamoDB global tables: every Region accepts writes, last writer wins"]
  end
`} legend="Consensus gives one order inside a group. Multi-leader replication gives many writers and merges the results." />

Be careful with the words. A consensus group has one leader at a time. Multi-leader replication, from 8.6, lets several servers accept writes and merges conflicts afterwards. They solve different problems, and big systems use both: Paxos inside a group of replicas, multi-leader between regions.

<GoDeeper title="Go deeper: real systems and a common mix-up">

Each DynamoDB partition has three replicas in a replication group that uses Multi-Paxos with a leader that holds a lease. A write is acknowledged once a quorum has stored the log record [S44]. Spanner's Paxos groups have leaders with a 10 second lease [S60]. In both, the leader gives the order, and a lease keeps the leader unique for a time.

DynamoDB global tables work another way. In the default mode every Region accepts writes, and concurrent writes to the same item are resolved by last writer wins on a timestamp [S43]. That is multi-leader replication, with the data loss risk you saw in module 10. Another mode offers strong consistency across Regions [S43].

Do not say "DynamoDB uses sloppy quorums and vector clocks". That describes Dynamo, the 2007 paper, not the service. Dynamo was leaderless and used sloppy quorums, hinted handoff and vector clocks [S45]. The service built later uses a leader per partition [S44]. Module 13 covers the paper's design.

The same agreement tool also fixes a weak point in transactions. Two-phase commit blocks if its coordinator fails. Gray and Lamport's Paxos Commit uses 2F + 1 coordinators and keeps going with F + 1 of them [S77].

</GoDeeper>

<GoDeeper title="In an interview">

Say: "Paxos picks one value. A proposer sends prepare with a number, a majority promises, then it sends accept with a value. If any acceptor already accepted a value, the proposer must use that value, which keeps a chosen value chosen. Multi-Paxos elects a stable leader so each log entry takes one round trip. Raft is the same idea with a stricter, simpler leader and log."

An interviewer may ask: "Why do real systems run Multi-Paxos or Raft instead of plain Paxos?" Because they need a log of many decisions, and a stable leader avoids the duel and the extra round trip for each entry.

</GoDeeper>
