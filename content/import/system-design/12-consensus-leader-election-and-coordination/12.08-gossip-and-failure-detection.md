A cluster of 1,000 servers cannot have every server ping every other one. That is about a million pings a round. Large clusters need a cheaper way to know who is alive and to spread news. They use gossip: each server talks to a few random others, and news travels like a rumor.

## A rumor doubles each round

<InteractiveCanvas slug="sysdesign-m12-gossip-rumor" />

N1 knows something new. In round 1, it tells N4. In round 2, N1 and N4 each tell one more: N2 and N6. In round 3, three nodes tell three more. Seven nodes know after three rounds. Each round roughly doubles the number of nodes that know. This is the best case, where no one tells a node that already knows.

<GoDeeper title="Go deeper: why random picks need a few extra rounds">

In the picture the nodes pick perfectly. Real nodes pick at random, so some tell a node that already knows. The spread starts as doubling and slows at the end, when almost everyone knows and a random pick rarely finds the last few.

A simulation shows the size of the effect. With 7 nodes and fanout 1 (each informed node tells one random node per round), the news reached everyone in 5.0 rounds on average over 300 runs, not 3. The best case is log base 2 of 7, about 2.8, rounded up to 3. The extra rounds come from repeated picks.

The cost of one round stays small. Each node sends only a few messages, whatever the size of the cluster. The count of rounds grows slowly with the cluster. This is why the Dynamo paper uses gossip for membership and failure detection [S45], and why SWIM's updates travel on the messages the nodes already send, which the paper calls infection style [S72].

</GoDeeper>

## Drag the size and the fanout

<InteractiveCanvas slug="sysdesign-m12-gossip-spread" />

Drag the cluster size from 7 to 10,000 nodes and watch the rounds needed. Then raise the fanout from 1 to 3. A hundred times more nodes, from 100 to 10,000, needs only about 12 more rounds. A bigger fanout cuts the rounds, at the cost of more messages. Tap "Suspect a healthy node" to see a false rumor travel at the same speed.

<GoDeeper title="Go deeper: the numbers behind the slider">

The table shows the average number of rounds for the news to reach every node, from a simulation of random picks (300 runs for each row up to 1,000 nodes, 40 runs for 10,000).

| Nodes | Fanout 1 | Fanout 2 | Fanout 3 |
|---|---|---|---|
| 7 | 5.0 | 3.2 | 2.5 |
| 16 | 7.4 | 4.6 | 3.6 |
| 100 | 12.3 | 7.4 | 5.7 |
| 1,000 | 18.1 | 10.7 | 8.2 |
| 10,000 | 23.9 | 14.0 | 10.7 |

The cluster is 10 times larger from one row to the next, but the rounds grow by only about 6 for fanout 1. That is the shape of a logarithm. The first part, doubling up to half the cluster, takes about log base 2 of N rounds. The last part, finding the final few nodes, adds a smaller amount. These are course figures from a simulation, and a real network adds delays and lost messages.

Each round, each informed node sends fanout messages. So the load per node is fixed by the fanout and does not depend on the cluster size, while a design where everyone pings everyone grows with the square of the cluster size. The price of gossip is that nobody has the full picture at once. Different nodes know the news at different rounds, so gossip gives eventual agreement, not instant agreement.

## Ask a friend before blaming

<InteractiveCanvas slug="sysdesign-m12-swim-indirect" />

A pings B and gets no ack in time. A does not blame B yet. It asks two other nodes, C and D, to ping B for it. B answers C, and C tells A that B is alive. A's own link to B was the problem, not B. A one-hop check removed a false alarm.

<GoDeeper title="Go deeper: how SWIM works">

SWIM was published at the DSN conference in 2002. It splits the job in two. A failure detector finds out which nodes may have failed. A dissemination part spreads the news about joins, leaves and failures. A simple design has every node send heartbeats to every other node, and its load grows with the square of the cluster size.

In SWIM every node, once per protocol period, picks one other node at random and pings it. If an ack comes back in time, all is well. If not, the node picks k other nodes at random and asks each to ping the target and report. If any report an ack, the target is alive. If none do, the node marks the target as suspected. Each node sends and receives a fixed number of messages per period, so the load on a node and the time to detect a failure do not grow with the size of the group [S72].

Asking others matters because the network does not fail evenly. One link between two nodes can be bad while both nodes are fine. With the indirect check, a false alarm needs many separate paths to fail together, which is much less likely.

</GoDeeper>

## Suspect first, declare dead later

<InteractiveCanvas slug="sysdesign-m12-swim-suspect" />

When the indirect check also fails, A does not call B dead. It marks B as suspected and gossips this. B hears the news, replies with a larger incarnation number, "alive #2", and gossips that. A and C clear the suspicion. A slow node got time to speak up, and no restart was needed.

<GoDeeper title="Go deeper: the suspicion step and what it costs">

SWIM adds a suspicion stage between alive and failed. A suspected node stays in the group for a suspicion time. If the node itself, or anyone, shows it alive in that time, the suspicion is cleared. If not, the node is declared failed and removed [S72].

To tell fresh news from stale news, a node has an incarnation number that only it can raise. "B is alive, incarnation 2" beats "B is suspected, incarnation 1". A node that sees itself suspected raises its own number and gossips the correction.

This is the same trade as in 12.2, with a better knob. A longer suspicion time means fewer false deaths but a slower reaction to real ones. Because the suspicion step gives a slow node a chance to reply, the cluster can use a short detection time without every pause causing a removal.

Gossip systems do not guarantee that all nodes agree on who is alive at the same moment. If you need a decision that must be right, such as "who is the single leader of this shard", you still need a majority vote. Gossip is for health and membership, consensus is for decisions.

</GoDeeper>

## A suspicion level, not yes or no

<MermaidDiagram title="Phi accrual failure detection" chart={`flowchart LR
  H["Record the gaps between past heartbeats"] --> F["Fit a distribution of normal gaps"]
  F --> P["phi = how surprising the current silence is"]
  P --> T{"phi above the threshold?"}
  T -->|yes| S["Suspect the node"]
  T -->|no| OK["Keep waiting"]
`} legend="The threshold is set once. The detector adapts to each node's own rhythm." />

A fixed timeout treats a node with steady beats and a node with jumpy beats the same. The phi accrual detector learns each node's rhythm and reports a number, phi, that grows as the silence becomes more surprising. You choose a threshold. A low threshold detects fast but raises false alarms. A high one is slow but calm.

<GoDeeper title="Go deeper: the formula and the settings">

The detector computes phi as minus the base-10 logarithm of 1 minus F, where F is a distribution fitted to the gaps between past heartbeats, so 1 minus F is the chance that a healthy node would be this late. A phi of 1 means about a 10 percent chance that the node is fine, 2 about 1 percent, and 8 about one in a hundred million.

The Pekko documentation gives a default threshold of 8 and suggests 12 on EC2, because delays on shared cloud networks vary more and a higher threshold avoids false alarms there [S73]. The documentation also notes the trade: lowering the threshold detects crashes faster, and raises the number of false positives [S73].

Compare with the slider in 12.2. A fixed timeout needs you to guess the right value for each network. Phi accrual measures the network for you, and you only pick how sure you want to be.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "At large scale I would not have every node ping every node. I would use gossip for membership and a SWIM-style detector: each node pings one random peer per period, asks k others to check on a silent one, and marks it as suspected before it declares it dead. The load per node stays constant and news spreads in about log N rounds."

An interviewer may ask: "Can gossip elect a leader?" Not safely by itself, because nodes may disagree for a while. Use gossip for health and membership, and a consensus group for decisions that must be exactly right.

</GoDeeper>
