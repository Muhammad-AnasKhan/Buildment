"Eventually consistent" sounds like a promise of speed. It is not. It is a promise about the end, not about the journey. It promises one thing about where copies end up, and says nothing about how long that takes or what a reader sees on the way. So the first question to ask of any system called eventually consistent is not how fast it is, but what else it promises.

## No new writes: copies end up the same

<InteractiveCanvas slug="sysdesign-m11-eventually" />

A write lands on copy A. The copies sync with each other in the background: A with B, then B with C. When the writes stop, all three hold the same value. That is the whole promise. It does not say when, and it does not say what a reader sees before then.

<GoDeeper title="Go deeper: the promise, and how long real systems take">

**Eventual consistency** says: if no new writes arrive, all copies of an item eventually hold the same value. The related idea of strong eventual consistency says that any two copies which have received the same set of updates are already in the same state, whatever order they got them in [S75]. Eventual consistency needs a rule to settle conflicts. Strong eventual consistency builds that rule into the data type, as CRDTs do (chapter 13.7).

{/* source needed: the textbook definition of eventual consistency (Vogels, "Eventually Consistent", 2009) is not in the dossier; the wording here follows the convergence idea in Shapiro et al. [S75]. */}

The promise says nothing about time. Real systems show how wide the range is:

| Copy | Typical delay behind the writer | Source |
|---|---|---|
| etcd watch event | about 10 ms in a healthy cluster, unbounded otherwise | [S54] |
| Aurora replica | usually much less than 100 ms, longer under heavy writes | [S39] |
| PostgreSQL asynchronous replica | typically under 1 second if it keeps up | [S38] |
| DynamoDB global secondary index | asynchronous, no figure given | [S41] |
| Replica in another region | no general figure found | none |

Terry's list of guarantees makes the same point from the other side. Eventual consistency is the weakest on his list, and the others, such as read-your-writes, monotonic reads and bounded staleness, are separate promises that a system may or may not add [S50, S51]. Bounded staleness is the one that does put a time limit on it.

</GoDeeper>

## The sync interval sets the clock

<InteractiveCanvas slug="sysdesign-m11-sync-rate" />

Each round, every copy swaps updates with one random copy. Drag the sync interval and the number of copies. With 5 copies it takes about 2.4 rounds on average, so the time is about 2.4 times the interval. More copies add only a little: 32 copies take about 5 rounds.

<GoDeeper title="Go deeper: the model, and what else decides the time">

The model is the simplest background repair: each round, every copy picks one other copy at random, and the two swap updates, so both end with the newest value either had. We ran 20,000 random runs for each number of copies (a course experiment, not a measurement of any product).

| Copies | Average rounds | Rounds needed in 95 of 100 runs |
|---|---|---|
| 3 | 1.5 | 2 |
| 5 | 2.4 | 3 |
| 8 | 3.1 | 4 |
| 16 | 4.2 | 5 |
| 32 | 5.1 | 6 |

The time to agree is rounds times the sync interval. At 5 copies and a 2-second interval, that is about 4.7 seconds, and at a 30-second interval about 71 seconds. The number of copies matters much less than the interval: doubling the copies adds roughly one round, as gossip does (chapter 12.8).

Four things decide the real time. The sync interval, as above. The number of copies, a little. The failures: a copy that is down, or cut off by the network, cannot take part, and the time is at least the time until it returns. And the write rate: the promise only applies "if writes stop". A busy item may never have a moment when all copies agree, though each copy keeps getting closer.

</GoDeeper>

## A copy that is down sets the clock

<InteractiveCanvas slug="sysdesign-m11-no-deadline" />

Copies A and B agree after 2 seconds. Copy C is down until second 48. Only then do all three agree. Eventual consistency has no deadline: the time is set by the slowest copy and by failures, not by the sync interval alone.

<GoDeeper title="Go deeper: why a number would be a lie">

Imagine a vendor writes "copies agree within 5 seconds". That is a promise with a time bound, and it is a different, stronger one. Terry's list calls it bounded staleness: reads are at most a given time behind [S51]. It is real, and it costs: to keep it, a system must stop or slow down when a copy falls too far behind. Eventual consistency makes no such promise, so it needs no such stop.

Kleppmann makes a related point about networks: partitions are not optional, so any design must say what it does while some copies cannot talk [S55]. A copy that cannot talk to the others cannot converge. The time to agree then includes the outage, and nobody can set a limit on an outage.

For a user, the sensible reading is: do not expect "a few milliseconds". Read the system's guarantee, test it with a copy switched off, and add the promises users notice, such as read-your-writes from chapter 11.5.

</GoDeeper>

## Three ways a stale copy catches up

<MermaidDiagram title="How copies converge" chart={`flowchart LR
  W["A write lands on one copy"] --> S["1. The replication stream sends it on, a little later"]
  W --> R["2. Read repair: a read that finds an older copy writes the newer value back"]
  W --> A["3. Anti-entropy: copies compare what they hold in the background and fix differences"]
  S --> C["All copies hold the same value"]
  R --> C
  A --> C
`} legend="Each way covers a gap the others leave. The stream can lose a message. Read repair only fixes what readers touch. Anti-entropy checks everything, slowly." />

A stale copy catches up in three ways. The stream sends each change on, but a message can be lost. Read repair fixes the copies a read happens to touch. Anti-entropy, a background job, compares copies and fixes the rest. Each covers a gap the others leave.

<GoDeeper title="Go deeper: read repair, anti-entropy and what they cost">

**The stream.** The leader or the writing node sends each change to the other copies. This is the normal path and is fast, but it can fail if a copy is down or a message is dropped.

**Read repair.** A read asks several copies and compares what they say. If one is older, the reader writes the newer value back to it. You saw this in chapter 8.7. It costs nothing extra on the write path, but it only repairs data that someone reads. A value that is never read can stay stale forever on one copy.

**Anti-entropy.** A background process compares two copies and copies across the differences. Comparing every item would be slow, so Dynamo compares Merkle trees, which are trees of hashes, to find which ranges differ and copy only those [S45]. The cost is background traffic and a delay: it runs every few seconds or minutes, which is the sync interval in the picture above.

Chapter 13.3 covers hinted handoff, read repair and Merkle trees together. For now, the point is that "eventually" is made by work that someone built. If that work stops, nothing converges.

</GoDeeper>

## Agreeing is not the same as being right

<InteractiveCanvas slug="sysdesign-m11-cart-lost" />

Two copies each got a different item added to the same cart. A rule keeps the cart with the later timestamp. Both copies end up the same, and one item is gone. Eventually the same is not the same as correct. The merge rule decides what survives.

<GoDeeper title="Go deeper: merge rules, and what each can lose">

Convergence only needs the copies to end up equal. A rule that keeps one side and drops the other converges, and it loses data. "Last writer wins" is that rule. Jepsen's 2013 test of Cassandra, which resolves conflicts that way, lost about 28% of acknowledged writes in one lock-based test [S76]. If the timestamps come from clocks that differ by milliseconds, "later" may also be wrong (chapters 10.2 and 10.6).

Dynamo's shopping cart took a different rule: merge the two carts, so no added item is ever lost. The price is that a deleted item can come back, because the merge cannot tell a delete from an item the other copy never saw [S45]. CRDTs go further: data types are designed so that any order of updates merges to the same, correct result [S74, S75].

So when you read "eventually consistent", ask two questions. How long can the wait be? And when two writes meet, what happens to them? The first is about time and the second is about data loss. Module 13 builds the answers.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "Eventual consistency means that if writes stop, all copies end up with the same value. It gives no time limit and says nothing about what a reader sees before that. The time depends on how often copies sync, how many there are, and on failures. I add session guarantees for what users notice, and I check the merge rule so a concurrent write is not lost."

A follow-up an interviewer may ask: "Can an eventually consistent store lose data?" A good answer: yes, if its conflict rule drops one of two concurrent writes, as last-writer-wins does. A merge rule or a CRDT keeps both. Name the cost of the second: more complex data and sometimes surprising merges.

</GoDeeper>
