In 11.1 Mariam's balance went back in time. To say exactly what went wrong, and what a system promises, we need a way to write a run down so that two people can argue about it. That way is a history. A history says nothing about copies, leaders or networks. It lists only what the clients did and what they saw, so anyone can check a promise against it.

## A history is a list of bars

<InteractiveCanvas slug="sysdesign-m11-build-history" />

Each operation is a bar. It starts when a client sends the request and ends when the client gets the answer. A write says what it stored. A read says what it got back. Tap a lane to add a bar. Bars that overlap are concurrent: neither clearly came first.

<GoDeeper title="Go deeper: what a history records, and who records it">

A history is a list of operations. Each one has a client (who asked), a kind (read or write), a key (what it touched), a value (what the write stored or the read returned), a start and an end. That is all. It says nothing about copies, leaders or networks. That is the point: a promise should be something a user could check without looking inside the system.

The record is kept from the client's side, because the client is the only one who sees both ends. The start is the moment it sent the request. The end is the moment it got the answer. The system may take its time in between, and it may reorder work, but it cannot change what the client saw.

If a client never gets an answer, the operation has a start and no end. The write may or may not have happened. A checker has to allow both, and chapter 11.8 draws such an operation with an end of infinity.

Test tools record histories like this while they break a system on purpose, and then check the record against a model. The Jepsen tests on Cassandra in 2013 are an example of the idea: clients recorded which writes were acknowledged, and the test counted how many later vanished [S76].

## One write: start, end, and an instant inside

<InteractiveCanvas slug="sysdesign-m11-one-operation" />

Ada's write starts at 10 and ends at 40. Somewhere between those two times the store applies it, and Ada cannot see when. That instant is the effect of the write. Every promise in this module is a promise about where those instants may fall.

<GoDeeper title="Go deeper: why the instant is a model, not a measurement">

No machine records "the instant a write took effect". A real system does many steps: it receives the request, writes to a log, copies to other machines, and answers. Any of these could be called the moment the write counts. The model does not pick one. It only says that for the history to make sense, there must be some instant between start and end that behaves as if the whole write happened at once.

Herlihy and Wing used exactly this idea in 1990 when they defined linearizability [S47]. The word "linearization point" in chapter 11.3 means this instant.

Two things follow. First, a longer bar is looser: the instant could be anywhere in a wide range, so more orders fit. A slow request makes a history easier to explain, not harder. Second, a short bar is strict. If a write is acknowledged within 1 ms and another client reads 2 ms later, the room for argument is tiny.

</GoDeeper>

## Overlap means either answer is fine

<InteractiveCanvas slug="sysdesign-m11-overlap-or-not" />

Drag Ben's read along the timeline. If it ends before the write starts, only 0 is possible. If it starts after the write ends, only 1 is possible. In between, the bars overlap, their order is not fixed, and both answers are fine.

<GoDeeper title="Go deeper: ordered pairs, overlapping pairs, and the exact rule">

Take two operations, a and b. If a's end is before b's start, a finished before b began, and every legal order must put a first. We say a is before b in real time. If neither is before the other, the bars overlap and the order is open. In this course two bars that only touch at one instant count as overlapping, so the rule is strict: a is before b only when a.end < b.start.

The set of values a single read may return follows from this. The read may return the value of any write that overlaps it. It may also return the value of the latest write that finished before it started, or the starting value if none finished. A write that finished before the read, but was followed by another write that also finished before the read, is out: the later write hides it.

This is a necessary check for one read, not a full test of a history. Two reads can each be allowed alone and still be impossible together. Chapter 11.3 shows that case, which is where the interesting failures live.

The system does not need to know real time to behave well, but the person checking does. A tester records start and end with one trusted clock, as the judge does in challenge 9. In chapter 10.6 you saw that two servers cannot compare their own clocks exactly. The history is recorded by the client, not by the servers, so the bars are comparable even when the servers' clocks are not.

</GoDeeper>

## Pretend it ran one at a time

<InteractiveCanvas slug="sysdesign-m11-one-at-a-time" />

A legal order has one rule: each read returns the last write before it in that order. Ada writes 5, so Ben's next read must be 5. Ada writes 7, so the next read must be 7. A promise such as "linearizable" says that a legal order exists that also fits the bars.

<GoDeeper title="Go deeper: the one-machine illusion">

Imagine the database were one machine, handling one request at a time, with no copies. Every history it produced would be legal in this sense. Each read would show the last write before it, because there would be no other answer.

A replicated database cannot always keep that illusion cheaply. It has several copies, each handling requests at its own pace. A consistency model says how much of the one-machine illusion the system keeps. The strictest models keep all of it. Weaker models give up parts, such as the link to real time, or the single order that every client agrees on.

To check a history against a model, you try to find a legal order that the model accepts. If you find one, that order is a witness: proof that the history is allowed. If you search every possible order and find none, the history breaks the promise. In chapter 11.8 you write that search for a single register. A register is the simplest object: one value, read and written.

Keep in mind that the one-at-a-time order is imaginary. The system never builds it. We build it afterwards, on paper, to judge what the clients saw.

</GoDeeper>

## Strong promises allow fewer histories

<MermaidDiagram title="The ladder of consistency models" chart={`flowchart TB
  SS["Strict serializable"] --> LIN["Linearizable (11.3)"]
  LIN --> SEQ["Sequential (11.4)"]
  SEQ --> CAU["Causal (11.4)"]
  CAU --> WFR["Writes follow reads (11.5)"]
  CAU --> PRAM["PRAM"]
  PRAM --> RYW["Read your writes (11.5)"]
  PRAM --> MR["Monotonic reads (11.5)"]
  PRAM --> MW["Monotonic writes (11.5)"]
  EV["Eventual (11.6): where copies end up"] -.-> CAU
`} legend="An arrow means 'implies': a system with the model at the tail also has the model at the head. The dotted line marks a different kind of promise: eventual consistency says where copies end up, not what a reader sees on the way." />

Each arrow reads "implies". A linearizable system is also sequential, and a sequential one is also causal. Going down the ladder allows more histories and needs less coordination between copies. Going up costs waiting or refusing to answer. Chapter 11.7 puts numbers on that price.

<GoDeeper title="Go deeper: the rungs, and which can stay available">

The map below follows the Jepsen consistency model map [S46]. **Strict serializable** is the strongest: transactions behave as if they ran one at a time, in real-time order. **Linearizable** is the same promise for single operations. Be careful: linearizability is not serializability. Serializability is about transactions in some order, with no link to real time. Linearizability is about single operations, in real-time order [S46, S52].

**Sequential** drops real time but keeps one order that every client agrees on, and that respects each client's own order of operations [S48]. **Causal** keeps only the order between operations that could have caused each other, and lets unrelated operations appear in different orders to different readers [S49]. **PRAM** is the three promises about one client's own order taken together: read your writes, monotonic reads and monotonic writes [S46]. These are the session guarantees from chapter 8.4, and the fourth one, writes follow reads, sits just under causal [S50].

The map also says which models can survive a network cut. Models at or above sequential cannot be totally available: some requests must be refused. Models at or above read-your-writes can be at most "sticky available", which means a client must keep talking to the same server. Weaker models can be totally available [S46, S49]. The CAP chapter, 11.7, builds on this.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "A consistency model is a rule about which histories a system may produce. A history is every operation with its start, end and result. Stronger models allow fewer histories, so they cost more coordination." Then give one example: after a write finishes, a linearizable store must show it to every later read, and an eventually consistent store need not.

A follow-up an interviewer may ask: "Is eventual consistency a model on the same ladder?" A good answer: it is a different kind of promise. It only says that copies agree once writes stop, with no time limit. On its own it forbids almost nothing, so people add session guarantees on top.

</GoDeeper>
