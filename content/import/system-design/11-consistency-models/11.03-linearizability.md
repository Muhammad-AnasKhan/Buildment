In 11.2 a legal order needed one instant inside each bar. Linearizable is the promise that such instants always exist, for every history the system can produce. It is the strictest promise for a single operation, and it is the one people usually mean by "strong consistency".

```predict

correctOptionId: no
```

## Find one point inside every bar

<InteractiveCanvas slug="sysdesign-m11-is-it-linearizable" />

Each dot is the instant an operation takes effect, and it must sit inside its bar. When a legal order exists, the picture places the dots for you, left to right. If every read matches the last write before it, the history is linearizable. Tap Ben's, Dan's or Cam's read to change what it returned. Find a change that makes the history impossible, and read what the picture says.

<GoDeeper title="Go deeper: the definition, and what the checker is doing">

A history is **linearizable** if two things hold. First, there is one order of all operations in which every read returns the value of the last write before it. Second, that order respects real time: if one operation finished before another started, it comes first [S47]. Equivalent words: every operation seems to take effect at a single instant between its start and its end, and all clients agree on the order of those instants.

In the picture, Ada's write runs from 10 to 60. Ben (20 to 30) and Dan (40 to 50) both overlap it. Cam's read starts at 70, after the write ended. The rules leave three good combinations: Ben 0 and Dan 0 with Cam 1, Ben 0 and Dan 1 with Cam 1, and Ben 1 and Dan 1 with Cam 1. Cam must read 1 in every case, because the write finished first. Ben 1 with Dan 0 is the broken case from the prediction: time goes backwards.

A checker finds an order by search. It picks an operation that no unplaced operation must come before, checks that a read matches the current value, places it, and repeats. If it gets stuck, it backs up and tries another. When it places everything, the order it built is a witness. You write this in chapter 11.8.

This is the guarantee Spanner calls external consistency. In chapter 10.6 you saw commit wait buy it with about 2 times epsilon of waiting. For transactions it is strict serializability, a rung that includes linearizability [S46, S60].

</GoDeeper>

## A stale copy breaks the promise

<InteractiveCanvas slug="sysdesign-m11-stale-replica-read" />

Ada's write is confirmed. Ben starts a read afterwards, but his read lands on a replica that has not received the copy yet. He gets 0. The write had finished before the read began, so no legal order can put the read first. This is the stale read from chapter 8.4, now with a name.

<GoDeeper title="Go deeper: which reads are safe">

Any read that can be answered by a copy that is behind may break linearizability. That includes a replica behind a leader, a cache, and the "any replica" routing from 8.4. The lag may be small: the PostgreSQL documentation says typically under one second [S38], and Aurora replicas usually lag by much less than 100 ms [S39]. A small lag is still a window in which a finished write is invisible.

There are three ways to read linearizably. Send the read to the leader, which has every write (but see the failover warning in chapter 8.5). Read through the same agreement process that orders the writes, which is what etcd does: its reads are linearizable by default [S54]. Or ask a majority of copies and write the newest value back before answering, which is the ABD algorithm in the Kleppmann notes [S52].

Each costs something. A leader read adds load to the leader and a hop for faraway users. An agreement read waits for other machines. A majority read adds a round trip. DynamoDB makes the choice visible: it offers both strongly consistent and eventually consistent reads [S44]. The strong kind costs more, and that gap is the subject of chapter 11.7.

</GoDeeper>

## A unique name needs one order

<InteractiveCanvas slug="sysdesign-m11-username-twice" />

Two sign-ups ask for the name noor at once. Each lands on a different copy, and each copy checks only itself. Both say yes, and the copies learn about the clash later. A rule like "this name is unique" needs every claim to see the latest state. That is what linearizability gives.

<GoDeeper title="Go deeper: locks, leases and seat holds have the same shape">

Claiming a name is the same move as taking a lock or holding a seat. In each case a client says: change this from free to mine, but only if it is still free. If two copies can both answer yes, the rule is broken. A distributed lock built on a store that is not linearizable can have two holders. A seat hold can sell the same seat twice.

Linearizability is what turns "check, then act" into one step. The check and the change happen at one instant, so no other claim can slip in between.

Even a linearizable lock is not enough alone. A client may take a lock, pause for longer than the lease, and then write after the lease has passed to someone else. A fencing token that the storage checks stops that; you build it in module 12 and the idea is in chapter 8.5 [S70].

The names and the numbers in the picture are a course example. Chapter 7.5 showed the single-database version of this fix, with a row lock and a version check.

</GoDeeper>

## Compare-and-set: the first claim wins

<MermaidDiagram title="Two claims, one order" chart={`flowchart LR
  A["Client 1: set name noor to user 1, only if free"] --> L["One leader or one agreement group puts all claims in one order"]
  B["Client 2: set name noor to user 2, only if free"] --> L
  L --> R1["First in the order: the name was free, ok"]
  L --> R2["Second in the order: the name is taken, refused"]
`} legend="Both claims reach the same place. That place picks an order. The first sees 'free'. The second sees 'taken'." />

Compare-and-set from chapter 7.5 says: change x only if it still equals what I last saw. If every claim passes through one order, the first sees "free" and wins, and the second sees "taken" and is refused. That single order is what linearizability gives you. It is why a leader, or a consensus group, sits in the middle.

<GoDeeper title="Go deeper: where the one order comes from">

A compare-and-set written as CAS(x, old, new) sets x to new only if x still equals old. The Kleppmann notes show that making it work across machines needs a total order of all operations, which in turn needs total order broadcast, the problem consensus solves [S52]. Module 12 covers consensus. For now, the practical rule is: use a store that offers this as a primitive, and do not build it from plain replicas.

etcd gives it as a transaction: an atomic If/Then/Else with comparisons on a key's revision, so a client can say "if this key's mod_revision is still 7, then write" [S53]. DynamoDB gives it as a conditional write: the write goes through only if a condition on the item holds, which stops the lost update [S42]. A conditional write is safe to retry when its condition checks the attribute it changes. An atomic counter increment is not, because retrying it adds twice [S42].

Chapter 7.7 had you code a compare-and-set for inventory on one machine. Here the lesson is the cost: every claim must reach the machine that holds the single order. Faraway users wait for that trip.

</GoDeeper>

## Overlapping quorums are still not enough

<InteractiveCanvas slug="sysdesign-m11-quorum-not-enough" />

Three copies, write to 2, read from 2: the two groups always overlap, so a read should see the newest write. But here a write is still in progress. Reader A hears the new value from node 1. Reader B starts after A is done, asks two other nodes, and gets the old value. New, then old. Overlap is necessary, not sufficient.

<GoDeeper title="Go deeper: why R + W over N is not the same as linearizable">

With N copies, a write that must reach W of them and a read that must ask R of them will overlap in at least one copy when R + W is more than N. That is the rule behind 8.7, and Dynamo commonly runs (N, R, W) as (3, 2, 2) [S45]. The overlap guarantees that a read sees a finished write. It does not guarantee anything about a write that is still in progress.

In the picture the write has reached only node 1 so far. A's quorum includes node 1, so A sees it. B's quorum is nodes 2 and 3, so B does not. B started after A finished, but returns the older value. The history has A reading 1, then B reading 0, with the write overlapping both. That is the "new then old" pattern from the first picture, and it has no legal order.

The Kleppmann notes give the fix: when a read finds a newer value on some copies, it first writes that value back to a majority, and only then returns it (the ABD algorithm). After that, any later read must meet a copy that has the new value [S52]. The cost is one more round trip on reads. A sloppy quorum, which accepts writes on other nodes when the usual ones are down, breaks even the overlap [S45].

</GoDeeper>

## Linearizable is not serializable

<MermaidDiagram title="Two similar words, two different promises" chart={`flowchart TB
  S["Serializable: transactions behave as if one at a time, in any order, with no link to real time"]
  L["Linearizable: single operations take effect in real-time order"]
  S --> SS["Strict serializable: both promises together"]
  L --> SS
`} legend="Serializability is about transactions. Linearizability is about single operations and real time. Having both is strict serializable." />

People mix up two similar words. Serializability is about transactions: they behave as if they ran one at a time, in any order, even one that ignores real time. Linearizability is about single operations and insists on real-time order. Having both is called strict serializable. Spanner offers that for its transactions.

<GoDeeper title="Go deeper: which promise protects what">

A bank transfer has two writes. Serializability protects the pair: no reader sees one half. It does not say that a transfer finished at noon is visible to a reader at 12:01. A linearizable single register protects that, but it knows nothing about pairs. A system that needs both, like a payment ledger, wants strict serializable [S46, S52].

Spanner's external consistency is this top rung: if one transaction commits before another starts, its commit timestamp is smaller, even when the two never exchange a message [S60]. Chapter 10.6 showed the price: a wait of at least 2 times epsilon on every commit. At the typical epsilon of about 4 ms, that is about 8 ms.

Most features do not need the top rung. A like count, a profile photo or a feed can be stale for a moment without harm. The last chapters of this module ask you to say which features need which rung, and to defend the choice with a cost.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "Linearizable means the system behaves as if there were one copy. Each operation seems to take effect at one instant between its start and its end, so once a write finishes, every later read sees it. I use it for unique usernames, locks and seat holds, and pay for it in latency or availability."

A follow-up an interviewer may ask: "If I read and write with R + W greater than N, is that linearizable?" A good answer: not by itself. The quorums overlap, but a write in progress can be seen by one read and missed by a later one. Fix it with read repair before returning (ABD), or send the operation through a leader.

</GoDeeper>
