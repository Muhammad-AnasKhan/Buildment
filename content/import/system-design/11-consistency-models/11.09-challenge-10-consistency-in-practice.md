In chapter 11.5 you saw four session guarantees as pictures and as a short piece of code. Now you will measure them. You will run a small forum on replicas that lag, count how often a user sees something strange, and then give each user a session token and count again. The first count is the "before". The second is the "after". The gap between them is what a consistency promise is worth, and the leader's extra work is what it costs.

By the end of this chapter, your `system-design-challenges` repository has `challenges/challenge-10-consistency/` with two parts. Each part has its own `README.md` that teaches the idea from zero, a script you can run, a `node:test` test that passes, a `results.md` with your own numbers, and a `chart.svg` drawn from them. Three new helper files go in `toolkit/`: a shard (a leader with replicas that copy its log), a counter for anomalies, and the session client. Everything is plain Node.js 24 with no packages to install, and no Docker is needed. The whole challenge runs in under a second per script.

**What you need.** The repository from chapter 1.5, with `toolkit/stats.js` and `toolkit/chart.js` from challenges 1 and 2 (`seededRandom`, `lineChart` and `barChart`), and `toolkit/simnet.js` from challenge 9. Plan for an hour and a half.

## How the experiment works

In challenge 7 you ran a real PostgreSQL primary and a replica in Docker, made the replica lag, and fixed the bug with log positions. This challenge keeps the same arrangement but runs it inside the simulated network of challenge 9. A leader keeps a log, and each entry gets the next position: 1, 2, 3. A replica copies the log in order, a fixed number of milliseconds later, so a replica at position 5 holds exactly the first five entries. The simulation lets you run thousands of reads in a fraction of a second, with the same result every time you run it.

Three design choices keep the numbers honest.

**The forum has two shards.** The forum (a made-up study forum) keeps questions in one shard and replies in another. Reply number 7 answers question number 7. Each shard has its own leader and its own replicas, so a reply can reach its copy before the question reaches its copy. A forum with one log could not show the third anomaly, because one log copies entries in order.

**The workload has its own random numbers.** The stories use a separate seeded generator from the one that picks replicas. If both shared one, a client that makes different choices would also change the stories, and the comparison would be unfair. With separate generators, every client sees exactly the same 400 stories.

**The judge reads the trace, not the client.** Every read and write is written to a list: who, which shard, and the position the read showed. The counter in `anomalies.js` looks only at that list. A client cannot make itself look good by counting its own mistakes.

## Step 1: the toolkit

First, `toolkit/shards.js`. A shard has a log and replicas. `write` adds an entry and schedules each replica to apply it later. Notice the line with `Math.max`: a replica never applies an entry before the one in front of it, which keeps every replica a prefix of the log.

```js
// toolkit/shards.js: a shard is one log with a leader and replicas, on simnet.
// Every write is appended to the leader's log and gets the next position
// (1, 2, 3 ...). Each replica copies the log in order, `lag` ms later, so a
// replica that has applied position 5 holds exactly the first 5 entries.
// This is the same arrangement as the PostgreSQL pair in challenge 7, but
// inside the simulation, so thousands of reads run in a fraction of a second.

export function createShard(net, { name, lagsMs }) {
  const log = []; // the leader's log: { position, value, deps }
  const replicas = lagsMs.map((lag, i) => ({ name: `${name}-r${i + 1}`, lag, applied: 0, lastAt: 0 }));

  return {
    name,
    replicas,

    // Append to the leader's log and start copying to each replica.
    // `deps` are the positions in other shards that the writer had seen.
    write(value, deps = {}) {
      const position = log.length + 1;
      log.push({ position, value, deps });
      for (const replica of replicas) {
        // A replica applies entries in order, never earlier than the one before.
        const at = Math.max(net.now + replica.lag, replica.lastAt);
        replica.lastAt = at;
        net.at(at, () => {
          replica.applied = position;
        });
      }
      return position;
    },

    // What a read returns from the leader: every entry so far.
    readLeader() {
      const saw = log.length;
      return { node: `${name}-leader`, saw, deps: saw > 0 ? log[saw - 1].deps : {} };
    },

    // What a read returns from a replica: the entries it has applied.
    readReplica(replica) {
      const saw = replica.applied;
      return { node: replica.name, saw, deps: saw > 0 ? log[saw - 1].deps : {} };
    },
  };
}
```

Next, `toolkit/anomalies.js`, the judge. It walks the trace once and keeps a few maps. Read the comments at the top: they say what each count means. `ownMissed` is chapter 8.4's read-your-writes failure. `wentBack` is its monotonic-reads failure. `prefixBroken` is the reply before its question from chapter 11.4.

```js
// toolkit/anomalies.js: count what a user would notice in a recorded trace.
//
// A trace is a list of events in time order:
//   { type: "write", session, shard, position }       a write that was confirmed
//   { type: "read",  session, shard, saw }            a read that saw the shard's log up to `saw`
//
// "Saw position 5" means the read showed entries 1 to 5 and no more.
//
// Three anomalies are counted, each once per read that shows it:
//   ownMissed    the read is older than a write this session already made (read-your-writes)
//   wentBack     the read is older than an earlier read by the same session (monotonic reads)
//   prefixBroken the session read a reply and then a question list that lacks that
//                reply's question (consistent prefix). In this forum, reply number p
//                answers question number p, so `dependsOn` says: replies need questions.

export function countAnomalies(trace, dependsOn = { replies: "questions" }) {
  const wrote = new Map(); // "session|shard" -> highest confirmed write
  const best = new Map(); // "session|shard" -> highest position seen by a read
  const needs = new Map(); // "session|shard" -> position that earlier reads implied must exist
  const counts = { reads: 0, ownMissed: 0, wentBack: 0, prefixBroken: 0 };

  for (const e of trace) {
    const key = `${e.session}|${e.shard}`;
    if (e.type === "write") {
      wrote.set(key, Math.max(wrote.get(key) ?? 0, e.position));
      continue;
    }
    counts.reads++;
    if (e.saw < (wrote.get(key) ?? 0)) counts.ownMissed++;
    if (e.saw < (best.get(key) ?? 0)) counts.wentBack++;
    if (e.saw < (needs.get(key) ?? 0)) counts.prefixBroken++;
    best.set(key, Math.max(best.get(key) ?? 0, e.saw));
    // Seeing reply number `saw` means question number `saw` must exist too.
    const target = dependsOn[e.shard];
    if (target) {
      const t = `${e.session}|${target}`;
      needs.set(t, Math.max(needs.get(t) ?? 0, e.saw));
    }
  }
  return counts;
}
```

## Step 2: the forum

`forum.js` plays 400 stories, one every 50 ms of virtual time. In each story an asker posts a question and reads the question list twice, a replier reads the question from the leader and posts a reply, and Hana reads the replies and then, 1 ms later, the questions. The questions shard is the busy one: its two replicas lag by `lagMs` and twice that. The replies shard is quiet: its replicas lag by a fifth and a half of `lagMs`. All of those are course numbers, chosen so the effects are easy to see. The function takes a `makeClient` argument, which is the only thing parts 1 and 2 change.

```js
// The forum workload shared by parts 1 and 2 (a fictional study forum).
// Two shards: "questions" and "replies". Reply number p answers question number p.
// Every 50 ms of virtual time one story plays out, with three people:
//   asker   posts a question, then reads the question list twice
//   replier reads the question from the leader (so the reply really follows it)
//           and posts the reply
//   hana    reads the replies, one millisecond later reads the questions
// The only thing that changes between runs is the client that decides where
// each read goes, and how far behind the replicas are.
import { createNet } from "../../toolkit/simnet.js";
import { createShard } from "../../toolkit/shards.js";
import { seededRandom } from "../../toolkit/stats.js";

export function runForum({ seed = 1, lagMs = 100, stories = 400, makeClient }) {
  const net = createNet({ seed });
  // Questions are busy, so their replicas run behind by lagMs and twice that.
  // Replies are quiet, so their replicas keep up faster. (Course numbers.)
  const shards = {
    questions: createShard(net, { name: "questions", lagsMs: [lagMs, lagMs * 2] }),
    replies: createShard(net, { name: "replies", lagsMs: [lagMs * 0.2, lagMs * 0.5] }),
  };
  const trace = [];
  const client = makeClient({ net, shards, trace });
  // The workload has its own random numbers, so every client sees the same stories.
  const random = seededRandom(seed + 1000);

  for (let i = 0; i < stories; i++) {
    const t0 = 100 + i * 50;
    net.at(t0, () => client.write("asker", "questions", `question ${i + 1}`));
    net.at(t0 + 5, () => client.read("replier", "questions", { leader: true }));
    net.at(t0 + 8, () => client.write("replier", "replies", `reply ${i + 1}`));
    net.at(t0 + 10, () => client.read("asker", "questions"));
    net.at(t0 + 25, () => client.read("asker", "questions"));
    const hanaAt = t0 + 14 + Math.floor(random() * 30); // between 14 and 43 ms after the question
    net.at(hanaAt, () => client.read("hana", "replies"));
    net.at(hanaAt + 1, () => client.read("hana", "questions"));
  }
  net.run(100 + stories * 50 + 2000);
  return { trace, client };
}
```

## Step 3: part 1, the anomalies before

Part 1 uses a plain client: every write goes to the leader, and every read goes to a random replica. It remembers nothing between requests. Create `part-1-anomalies/plain-client.js`:

```js
// A plain client: every write goes to the leader, every read goes to a random
// replica. It remembers nothing between requests. This is the "before".
export function makePlainClient({ net, shards, trace }) {
  return {
    write(session, shardName, value) {
      const position = shards[shardName].write(value);
      trace.push({ type: "write", session, shard: shardName, position, t: net.now });
      return position;
    },
    read(session, shardName, { leader = false } = {}) {
      const shard = shards[shardName];
      const result = leader
        ? shard.readLeader()
        : shard.readReplica(shard.replicas[Math.floor(net.random() * shard.replicas.length)]);
      trace.push({ type: "read", session, shard: shardName, saw: result.saw, node: result.node, t: net.now });
      return result;
    },
  };
}
```

## Step 4: part 2, the session client

Part 2 gives every user a token and counts again. Create `toolkit/session.js`. It is chapter 11.5's token as a client. `makeSessionClient` takes the three promises as switches and returns a function that the forum calls. The `need` function picks the position a replica must have reached. If no replica has, the leader answers, and the client counts that read as a fallback.

```js
// toolkit/session.js: a client that remembers positions between requests.
//
// Each session (one user on one device) carries a small token with three
// maps from shard name to a log position:
//   wrote      the highest position of this session's own confirmed writes
//   seen       the highest position any read of this session has shown
//   inherited  positions that the entries it read said they depended on
//
// A read goes to a random replica whose applied position is at least what the
// switched-on guarantees need. If no replica is far enough ahead, the leader
// answers, because the leader has every write.
//
//   ryw  (read-your-writes)      need at least `wrote`
//   mr   (monotonic reads)       need at least `seen`
//   wfr  (writes-follow-reads)   a write carries what its session has seen, and
//                                a read inherits what the entry it shows depended on

export function makeSessionClient({ ryw = false, mr = false, wfr = false } = {}) {
  return function make({ net, shards, trace }) {
    const sessions = new Map();
    const stats = { reads: 0, leaderReads: 0 };

    function session(id) {
      if (!sessions.has(id)) sessions.set(id, { wrote: {}, seen: {}, inherited: {} });
      return sessions.get(id);
    }
    const raise = (map, key, value) => {
      map[key] = Math.max(map[key] ?? 0, value);
    };

    // How far along a replica must be for this session's next read of a shard.
    function need(s, shardName) {
      return Math.max(
        ryw ? s.wrote[shardName] ?? 0 : 0,
        mr ? s.seen[shardName] ?? 0 : 0,
        wfr ? s.inherited[shardName] ?? 0 : 0
      );
    }

    return {
      stats,

      write(id, shardName, value) {
        const s = session(id);
        // A write remembers what its writer had seen and written, if wfr is on.
        const deps = {};
        if (wfr) {
          for (const [name, p] of Object.entries(s.seen)) raise(deps, name, p);
          for (const [name, p] of Object.entries(s.wrote)) raise(deps, name, p);
        }
        const position = shards[shardName].write(value, deps);
        raise(s.wrote, shardName, position);
        trace.push({ type: "write", session: id, shard: shardName, position, t: net.now });
        return position;
      },

      read(id, shardName, { leader = false } = {}) {
        const s = session(id);
        const shard = shards[shardName];
        const wanted = need(s, shardName);
        const ready = shard.replicas.filter((r) => r.applied >= wanted);
        let result;
        if (leader) {
          result = shard.readLeader(); // the caller asked for the leader on purpose
        } else if (ready.length > 0) {
          result = shard.readReplica(ready[Math.floor(net.random() * ready.length)]);
          stats.reads++;
        } else {
          result = shard.readLeader(); // nobody is far enough ahead: the leader has everything
          stats.reads++;
          stats.leaderReads++;
        }
        raise(s.seen, shardName, result.saw);
        if (wfr) for (const [name, p] of Object.entries(result.deps)) raise(s.inherited, name, p);
        trace.push({ type: "read", session: id, shard: shardName, saw: result.saw, node: result.node, t: net.now });
        return result;
      },
    };
  };
}
```

Next, `part-2-session-tokens/tokens.js`. It runs the forum at a lag of 100 ms with six settings of the switches, and then runs all three promises at six lags to show the cost.

```js
// Part 2: run the same forum with session tokens switched on one guarantee at
// a time, count the anomalies, and see what the guarantees cost: the share of
// reads the leader has to take.
import { writeFileSync } from "node:fs";
import { runForum } from "../forum.js";
import { makeSessionClient } from "../../../toolkit/session.js";
import { countAnomalies } from "../../../toolkit/anomalies.js";
import { barChart, lineChart } from "../../../toolkit/chart.js";

const STORIES = 400;
const LAG_MS = 100;
const SETUPS = [
  { label: "none", options: {} },
  { label: "ryw", options: { ryw: true } },
  { label: "mr", options: { mr: true } },
  { label: "ryw+mr", options: { ryw: true, mr: true } },
  { label: "wfr", options: { wfr: true } },
  { label: "all three", options: { ryw: true, mr: true, wfr: true } },
];

function run(lagMs, options) {
  const { trace, client } = runForum({ seed: 1, lagMs, stories: STORIES, makeClient: makeSessionClient(options) });
  const c = countAnomalies(trace);
  return { ...c, leaderShare: (client.stats.leaderReads / client.stats.reads) * 100 };
}

console.log(`Table 1: replica lag ${LAG_MS} ms, ${STORIES} stories\n`);
console.log("guarantees  own missed  went back  reply first  leader share");
const groups = [];
for (const setup of SETUPS) {
  const c = run(LAG_MS, setup.options);
  groups.push({ label: setup.label, anomalies: c.ownMissed + c.wentBack + c.prefixBroken });
  console.log(
    `${setup.label.padEnd(10)}  ${String(c.ownMissed).padStart(10)}  ${String(c.wentBack).padStart(9)}  ` +
    `${String(c.prefixBroken).padStart(11)}  ${c.leaderShare.toFixed(1).padStart(11)}%`
  );
}

console.log("\nTable 2: all three guarantees on, as the lag grows\n");
console.log("lag ms  anomalies  leader share");
const points = [];
for (const lagMs of [0, 20, 50, 100, 200, 400]) {
  const c = run(lagMs, { ryw: true, mr: true, wfr: true });
  points.push({ x: lagMs, leaderShare: c.leaderShare });
  console.log(
    `${String(lagMs).padStart(6)}  ${String(c.ownMissed + c.wentBack + c.prefixBroken).padStart(9)}  ${c.leaderShare.toFixed(1).padStart(11)}%`
```

Its test, `part-2-session-tokens/tokens.test.js`, has two groups. The first four tests use a fake shard whose positions you set by hand, so you can check each decision exactly: a replica behind the token is skipped, the leader answers when every replica is behind, a read never goes to a replica behind what the session saw, and a read the caller sends to the leader on purpose is not counted as a fallback. The other three run the forum: with all three promises no anomaly shows at lags 20, 100 and 400; each promise fixes its own anomaly and not the others; and with no lag the promises cost nothing.

```js
import test from "node:test";
import assert from "node:assert/strict";
import { makeSessionClient } from "../../../toolkit/session.js";
import { countAnomalies } from "../../../toolkit/anomalies.js";
import { runForum } from "../forum.js";

// A tiny fake world: replicas whose positions we set by hand, and a leader at 10.
// The next write gets position `next`, then next + 1, and so on.
function fakeWorld(positions, next = 1) {
  const shard = {
    name: "questions",
    replicas: positions.map((applied, i) => ({ name: `r${i + 1}`, applied })),
    write() { return next++; },
    readLeader() { return { node: "leader", saw: 10, deps: {} }; },
    readReplica(r) { return { node: r.name, saw: r.applied, deps: {} }; },
  };
  return { shard, shards: { questions: shard }, net: { now: 0, random: () => 0 }, trace: [] };
}

test("read-your-writes skips a replica behind the session's own write", () => {
  const w = fakeWorld([3, 8], 5); // Amna's write gets position 5
  const client = makeSessionClient({ ryw: true })(w);
  client.write("amna", "questions", "hello");
  assert.equal(client.read("amna", "questions").node, "r2"); // r1 is at 3, below her 5
});

test("read-your-writes falls back to the leader when every replica is behind", () => {
  const w = fakeWorld([3, 8], 9); // her write gets position 9: both replicas are behind
  const client = makeSessionClient({ ryw: true })(w);
  client.write("amna", "questions", "hello");
  assert.equal(client.read("amna", "questions").node, "leader");
});

test("monotonic reads never go to a replica behind what the session saw", () => {
  const w = fakeWorld([2, 9]);
  w.shard.replicas[0].applied = 2;
  const client = makeSessionClient({ mr: true })(w);
  const first = client.read("omar", "questions"); // random() is 0, so replica r1 (position 2)
  assert.equal(first.node, "r1");
  w.shard.replicas[1].applied = 9;
  const second = client.read("omar", "questions"); // r1 and r2 are both >= 2, r1 is chosen again
  assert.equal(second.saw >= first.saw, true);
  w.shard.replicas[0].applied = 1; // r1 "goes back" to 1 (a restored backup)
  const third = client.read("omar", "questions"); // r1 is below 2 now, so r2 must be used
  assert.equal(third.node, "r2");
});

test("a leader read on purpose is not counted as a fallback", () => {
  const w = fakeWorld([0, 0]);
  const client = makeSessionClient({ ryw: true })(w);
  client.read("replier", "questions", { leader: true });
  assert.deepEqual(client.stats, { reads: 0, leaderReads: 0 });
  client.write("amna", "questions", "x");
  client.read("amna", "questions"); // replicas are at 0, her token is 1: leader fallback
  assert.deepEqual(client.stats, { reads: 1, leaderReads: 1 });
});

test("with all three guarantees on, no anomaly shows at any lag", () => {
  for (const lagMs of [20, 100, 400]) {
    const { trace } = runForum({ seed: 1, lagMs, stories: 100, makeClient: makeSessionClient({ ryw: true, mr: true, wfr: true }) });
    const c = countAnomalies(trace);
    assert.equal(c.ownMissed + c.wentBack + c.prefixBroken, 0, `lag ${lagMs}: ${JSON.stringify(c)}`);
  }
});

test("each guarantee fixes its own anomaly and not the others", () => {
  const counts = (options) => countAnomalies(runForum({ seed: 1, lagMs: 100, stories: 100, makeClient: makeSessionClient(options) }).trace);
  assert.equal(counts({ ryw: true }).ownMissed, 0);
  assert.ok(counts({ ryw: true }).prefixBroken > 0);
  assert.equal(counts({ mr: true }).wentBack, 0);
  assert.ok(counts({ mr: true }).ownMissed > 0);
  assert.equal(counts({ wfr: true }).prefixBroken, 0);
  assert.ok(counts({ wfr: true }).ownMissed > 0);
});

test("with no lag the guarantees cost nothing", () => {
  const { client } = runForum({ seed: 1, lagMs: 0, stories: 50, makeClient: makeSessionClient({ ryw: true, mr: true, wfr: true }) });
  assert.equal(client.stats.leaderReads, 0);
});
```

Table 1 is the whole lesson of chapter 11.5 in numbers. Read it row by row. Read-your-writes alone removes the 800 own-write misses and leaves 103 backwards reads, which are Hana's, not the asker's. Monotonic reads alone removes every backwards read and leaves the 800 misses. Writes-follow-reads alone removes the 399 replies without questions, and happens to lower the backwards reads as a side effect, which is not a promise it makes. Only all three give zero everywhere.

The last column is the cost. The leader took none of the reads for monotonic reads, because a replica that was ahead was always available. It took half of them for read-your-writes, because the asker reads 10 ms after posting, before any replica can have the write. All three together put 74.9% of the 1,600 reads that were free to choose a replica onto the leader. Table 2 shows that the cost saturates once the lag passes the time between a write and the next read: at 50 ms it is already 64.9%, and from 100 ms it stays near 75%. This is the price of being sure, and it is why chapter 8.8 added a cap on leader reads.

Notice what the experiment leaves out. Monotonic writes never fail here, because each shard has one leader and a client waits for each write to be confirmed, which is why the code has only three switches. The cost is measured in leader reads, not milliseconds: a real leader, farther away or busier, would add latency to each of them.

## When something goes wrong

**`Cannot find module` with a path that ends in `simnet.js`, `stats.js` or `chart.js`.** A file is in the wrong folder, or you skipped an earlier challenge. `simnet.js` comes from challenge 9, `seededRandom` in `stats.js` from challenge 1, and `barChart` in `chart.js` from challenge 2. Compare your folders with the tree above.

**`barChart is not a function` or `lineChart is not a function`.** The chart helpers are not exported. Both must be in `toolkit/chart.js` with `export` in front.

**Part 1 prints all zeros.** The lags are not reaching the replicas. Check that `forum.js` passes `lagsMs` to `createShard`, and that `shards.js` uses `replica.lag` in the line with `Math.max`.

**The numbers change every time you run a part.** Something is using `Math.random()` or `Date.now()` instead of `net.random` and the seeded `random` in `forum.js`. Search your files for both words.

**Part 2 shows anomalies with all three switches on.** Check which column is not zero. A non-zero third column (reply first) usually means the write does not copy `seen` into its `deps`, or the read does not merge `deps` into `inherited`. A non-zero second column (went back) usually means `seen` is raised before the read, not after.

**Part 2 puts every read on the leader.** The replicas never apply anything. Check that `net.run` is called at the end of `runForum`, and that the replica callback in `shards.js` sets `replica.applied`.

**Break it on purpose.** See a test fail before you trust it. In `toolkit/session.js`, replace the line `ryw ? s.wrote[shardName] ?? 0 : 0,` with `0,` and run `npm test`: five tests fail, among them "read-your-writes skips a replica behind the session's own write" (expected `r2`, got `r1`) and "with all three guarantees on, no anomaly shows at any lag" (expected 0, got 151). Undo it. Then in `toolkit/anomalies.js`, change `e.saw < (best.get(key) ?? 0)` to `e.saw < 0`, and watch "a read older than an earlier read is counted, for any reader" fail, and the part 1 bug test with it. Undo that too.
