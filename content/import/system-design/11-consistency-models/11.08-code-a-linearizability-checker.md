In chapter 11.3 you decided by eye whether a history was linearizable. You put a dot inside each bar and checked that every read matched the last write. For three or four bars that works. For ten it does not, and a person makes mistakes. A machine has to do it. This is the same kind of tool that testing teams use after a failure test: record what the clients saw, then ask whether any legal order explains it.

In this chapter you write that checker. When you finish you have one JavaScript function, `findLinearization`, that passes server tests. It handles overlapping bars, a stale read, a read that goes from new to old, a write that never got an answer, and ten overlapping writes without freezing. It is for small histories of one register. Real checkers add more pruning and many keys, but the idea you write here is the core of them.

## The contract

A <GlossaryTerm term="register" definition="The simplest shared object: one value that can be written and read. A write replaces the value. A read returns the current one." /> holds one value. A history is an array of operations on it. Each operation is a plain object: `id` (a unique string), `client` (who asked), `kind` (`"read"` or `"write"`), `value` (what the write stored or the read returned), `start` and `end` (numbers, with `start` no later than `end`).

`findLinearization(history, initial = 0)` takes the history and the value the register holds before any write. It returns an array of ids in a legal order, or `null` if no legal order exists. An order is legal when two rules hold.

**The real-time rule.** If one operation's `end` is less than another's `start`, the first must come earlier in the order. Operations that overlap, or that only touch at one instant (`end` equals `start`), have no fixed order.

**The register rule.** Walk along the order with a current value that starts at `initial`. A write sets the current value to its `value`. A read must have a `value` equal to the current value.

If several legal orders exist, return any one. The tests check that the order is valid, not which one you found. The empty history returns `[]`. An operation that never got an answer is written with `end: Infinity`: nothing has to come after it, so it fits anywhere after its start.

Check the input before you search. A `history` that is not an array throws a `TypeError`. A `kind` that is not `"read"` or `"write"` throws a `TypeError`. An operation whose `end` is less than its `start`, or is not a number, throws a `RangeError`. A repeated `id` throws an `Error`. The function must not change the history it is given.

## How the search works

The checker builds the order one operation at a time. At each step it looks at the operations not yet placed and asks which one can go next. An operation can go next if no other unplaced operation ended before it started, because that other operation would have to come first. A read can go next only if its value equals the current value of the register. A write can always go next, and it changes the current value.

If the checker places everything, the order it built is the answer. If it reaches a point where nothing can go next, it backs up one step, undoes the last placement, and tries a different operation. This is called backtracking. If it backs all the way out, no legal order exists.

## A worked example: Ada, Ben and Dan

Ada writes 1 from time 10 to 60. Ben reads from 20 to 30 and gets 1. Dan reads from 40 to 50 and gets 0. This is the "new then old" history from 11.3. Here is the search, with the sub-goal at each step.

Start with the register at 0 and nothing placed. Which operations can go first? Ada can: nothing ended before time 10. Ben can: nothing ended before time 20. Dan cannot: Ben ended at 30, before Dan started at 40, so Ben must come first.

Try Ada first. A write is always allowed. The register becomes 1. Now Ben can go: he reads 1 and the register is 1. Place Ben. Dan can now go as far as the real-time rule is concerned, but he reads 0 and the register is 1. He cannot be placed. Nothing else is left, so this branch fails. Back up and undo Ben, then undo Ada.

Try Ben first instead. He reads 1 but the register is 0. He cannot be placed, so there is nothing else to try. The checker has tried every start, so it returns `null`. The history is not linearizable, and the reason is visible in the trace: after Ben saw 1, Dan was stuck.

Now change Dan to read 1. Ada first, then Ben (1 matches), then Dan (1 matches). The order is Ada, Ben, Dan, and the function returns `["a", "b", "d"]` if those are the ids.

## Three ways this goes wrong

**Checking pairs instead of the whole order.** Every pair of operations in the history above looks fine alone. Ada and Ben can be ordered. Ada and Dan can be ordered. The contradiction only shows up when the whole order has to hold together. A checker that compares pairs says "yes" to a history that has no legal order.

**Forgetting to undo.** When you back up, three things must go back: the flag that says an operation is placed, its place in the order you are building, and the register's value. The easiest way to handle the value is to pass it as an argument to the function that does the search, so each step has its own copy. The flag and the order need an explicit undo.

**Not remembering failed states.** With n writes that all overlap, there are as many orders as ways to line them up: n times (n minus 1) times (n minus 2), and so on down to 1. For ten writes that is 3,628,800. But there are only 2 to the power 10, which is 1,024, different sets of placed operations. A state is just which operations are placed plus the register's value, and two different orders that reach the same state have the same future. If you remember the states that failed, you try each state once. We measured a version without this memory: nine overlapping writes took about 2.5 seconds and ten took about 28 seconds. With the memory, ten took a fraction of a second. A key such as `JSON.stringify([placedFlags, value])` is enough.

A smaller slip is to write `end <= start` for the real-time rule. That makes two operations that only touch count as ordered, and the test for touching operations catches it.

solution: |
  function findLinearization(history, initial = 0) {
    if (!Array.isArray(history)) throw new TypeError("history must be an array");
    const ids = new Set();
    for (const op of history) {
      if (op === null || typeof op !== "object") throw new TypeError("every operation must be an object");
      if (op.kind !== "read" && op.kind !== "write") throw new TypeError("kind must be 'read' or 'write', got " + String(op.kind));
      if (!(op.start <= op.end)) throw new RangeError("operation " + op.id + " ends before it starts");
      if (ids.has(op.id)) throw new Error("duplicate operation id " + op.id);
      ids.add(op.id);
    }

    const n = history.length;
    const done = new Array(n).fill(false);
    const order = [];
    const failed = new Set(); // states already tried that lead nowhere: placed set plus register value

    function search(value, placedCount) {
      if (placedCount === n) return true;
      const state = JSON.stringify([done.map((d) => (d ? 1 : 0)).join(""), value]);
      if (failed.has(state)) return false;
      for (let i = 0; i < n; i++) {
        if (done[i]) continue;
        const op = history[i];
        // op can go next only if no unplaced operation finished before it started
        let blocked = false;
        for (let j = 0; j < n; j++) {
          if (!done[j] && j !== i && history[j].end < op.start) { blocked = true; break; }
        }
        if (blocked) continue;
        // a read must return the current value of the register
        if (op.kind === "read" && op.value !== value) continue;
        done[i] = true;
        order.push(op.id);
        if (search(op.kind === "write" ? op.value : value, placedCount + 1)) return true;
        order.pop();
        done[i] = false;
      }
      failed.add(state);
      return false;
    }

    return search(initial, 0) ? order : null;
  }

## What this unlocks

A linearizability checker is a way to turn a vague complaint ("the database sometimes returns old data") into a yes or no on a recorded run. In challenge 10 (11.9) you count three kinds of anomaly on lagging replicas, with detectors written for that workload. This checker is the general tool underneath. In module 12 you meet consensus, which is how a real system gets one order for all clients, so that checkers like this one have a chance of saying yes.

The habit to keep: when someone says a system "is consistent", ask for a history that would show it is not, and then run the history through a checker.
