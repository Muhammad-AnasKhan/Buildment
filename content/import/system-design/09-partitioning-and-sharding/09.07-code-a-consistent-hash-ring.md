In chapter 9.3 you watched keys find their node on a ring, and saw that a new node takes keys from its neighbours only. Suq's cache cluster, its shard router and Envoy's ring hash all rest on the same few lines of code. In this chapter you write those lines yourself, so you know exactly what a ring does at its edges.

By the end you will have a tested JavaScript class, `HashRing`. It keeps many points per node, called virtual nodes. `addNode(name)` and `removeNode(name)` change the ring. `getNode(key)` returns the node that owns a key. `nodes()` lists the nodes. It also takes the hash function as an option, and that is what makes it testable.

## Why the hash function is passed in

A ring is only as good as its hash, and a good hash is the opposite of testable: its answers look random. If a test says "key k150 goes to node b", you would have to run the real hash and copy its output into the test, which proves nothing. The fix is the same as the fake clock in chapter 5.8: the constructor takes the hash as an option. In production you use the default. In a test you pass a fake hash, a small table where you choose every position yourself.

```js
const hash = (s) => ({ "a#0": 100, "b#0": 200, k150: 150 })[s];
const ring = new HashRing({ vnodes: 1, hash });
ring.addNode("a");
ring.addNode("b");
ring.getNode("k150"); // "b": the first point at or after 150 is b at 200
```

The server runs exact tests like this one first. Then it switches to the real hash, with thousands of keys, to check that the spread is even and that adding or removing a node moves few keys.

## The contract

Fix the rules before writing code. The tests check these exact rules.

**Construction.** `new HashRing({ vnodes = 100, hash = hash32 } = {})`. The `vnodes` option must be a whole number of at least 1, otherwise throw a `RangeError`. `hash32` is given to you in the starter code. It turns a string into a whole number from 0 to 4,294,967,295. Do not change it: the spread tests were measured with it.

**Points.** A node called `name` owns `vnodes` points. Point number `i`, counting from 0, sits at position `hash(name + "#" + i)`. So the node `a` with 3 virtual nodes has points at `hash("a#0")`, `hash("a#1")` and `hash("a#2")`.

**Owner.** `getNode(key)` hashes the key to a position `p`. The owner is the node of the first point whose position is `p` or higher. If there is no such point, the ring wraps round and the owner is the node of the very first point. A key whose position equals a point's position belongs to that point. If two points have exactly the same position, the one whose node name is smaller (compared with `<` on strings) comes first. That tie rule means the answer does not depend on the order in which nodes were added.

**Changes.** `addNode(name)` returns `true` if it added the node, or `false` if the node was already on the ring, in which case it must not hash anything or add points again. `removeNode(name)` returns `true` if it removed a node and `false` if there was none. `nodes()` returns a new array of the node names in alphabetical order.

**Empty ring.** `getNode` on a ring with no nodes throws an `Error`. A ring that quietly returns `undefined` hides a setup mistake until a request fails far away.

## A worked example: three nodes, one point each

Here is the contract applied by hand to a case that is not in the tests. Three nodes with one point each, at positions 100, 200 and 300.

Key `k50` hashes to 50. The first point at or after 50 is `a` at 100, so `a` owns it. Key `k100` hashes to 100, exactly on `a`'s point, so `a` owns it too: the rule says "at or after". Key `k101` is one past `a`, so `b` owns it. Key `k301` is past the last point, so it wraps to `a`.

Now remove `b`. The points are `a` at 100 and `c` at 300. Key `k150` used to belong to `b` and now belongs to `c`. Keys `k50` and `k301` do not change owner. That is the whole idea of chapter 9.3 in four sentences, and your code should make it true for 20,000 keys at once.

## Three ways this goes wrong

**Sorting numbers as text.** In JavaScript, `[100, 20, 3].sort()` gives `[100, 20, 3]`, because the default sort compares values as strings. A ring sorted that way looks right for small test numbers and is wrong for real hashes. Always pass a comparison function: `(a, b) => a.position - b.position`.

**Forgetting to wrap.** Binary search returns "past the end" when the key is higher than every point. If your code returns `undefined` or throws there, one key in a few hundred fails, always the ones near the top of the range. One test uses a key higher than every point to catch this.

**Using "after" when you mean "at or after".** If the search looks for a point strictly greater than the key, a key sitting exactly on a point goes to the next node. It happens rarely with a real hash and always in a test with chosen positions. Decide once that the rule is "at or after", and test the boundary on both sides.

solution: |
  function hash32(text) {
    let h = 0x811c9dc5;
    for (let i = 0; i < text.length; i++) {
      h ^= text.charCodeAt(i);
      h = Math.imul(h, 0x01000193);
    }
    h ^= h >>> 16;
    h = Math.imul(h, 0x85ebca6b);
    h ^= h >>> 13;
    h = Math.imul(h, 0xc2b2ae35);
    h ^= h >>> 16;
    return h >>> 0;
  }

  class HashRing {
    constructor({ vnodes = 100, hash = hash32 } = {}) {
      if (!Number.isInteger(vnodes) || vnodes < 1) {
        throw new RangeError("vnodes must be a whole number of at least 1, got " + vnodes);
      }
      this.vnodes = vnodes;
      this.hash = hash;
      this.names = new Set();
      this.points = [];
    }

    addNode(name) {
      if (this.names.has(name)) return false;
      this.names.add(name);
      for (let i = 0; i < this.vnodes; i++) {
        this.points.push({ position: this.hash(name + "#" + i), node: name });
      }
      this.points.sort(
        (a, b) => a.position - b.position || (a.node < b.node ? -1 : a.node > b.node ? 1 : 0)
      );
      return true;
    }

    removeNode(name) {
      if (!this.names.delete(name)) return false;
      this.points = this.points.filter((p) => p.node !== name);
      return true;
    }

    getNode(key) {
      if (this.points.length === 0) throw new Error("the ring is empty");
      const h = this.hash(key);
      let lo = 0;
      let hi = this.points.length;
      while (lo < hi) {
        const mid = (lo + hi) >> 1;
        if (this.points[mid].position < h) lo = mid + 1;
        else hi = mid;
      }
      return this.points[lo === this.points.length ? 0 : lo].node;
    }

    nodes() {
      return [...this.names].sort();
    }
  }

## What this unlocks

The ring you wrote is the one inside many caches and routers. In challenge 8, next, you use it to spread 100,000 keys over shards, measure how many keys move when you add a node, and compare it with hash mod N. You will see the 80% from chapter 9.2 and the 20% from chapter 9.3 on your own machine.

A word on speed. Your `addNode` sorts all the points every time, which is fine for tens of nodes and a few thousand points, and is the simplest code that is right. A production ring inserts the new points into the sorted list instead of sorting again, and some keep a cache of recent lookups. Your `getNode` is the part that must be fast, because it runs on every request, and binary search keeps it to a handful of comparisons even with a million points. If you ever see a ring slow down, measure `getNode` and `addNode` separately before changing anything.

Two features are left out on purpose. Real rings let a bigger machine have more virtual nodes than a smaller one. And real systems store each key on the next few nodes round the ring, not only one, so the data has copies. Both are small changes to this class: the first changes how many points `addNode` creates, and the second changes `getNode` to walk past the first owner and collect more names, skipping repeats of the same machine.
