Suq has decided to split its orders table over four shards (chapter 9.1). Now it needs a rule that says which shard holds each order. There are two classic rules, and each one is good at something the other is bad at.

## Range: the newest date takes every write

<InteractiveCanvas slug="sysdesign-m9-range-hot-tail" />

Suq's first rule is one shard per quarter of the year. This is range partitioning: each shard holds a range of keys. Every new order has today's date, so shard 4 takes all 3,000 writes a second while shards 1 to 3 sit idle. The rule is easy to read, and it overloads one shard.

<GoDeeper title="Go deeper: why ranges suit reads and hurt writes">

In <GlossaryTerm term="range partitioning" definition="Splitting keys into sorted ranges, such as January to March, and giving each range to one shard. Keys that are next to each other in order stay on the same shard." /> the keys are sorted, and each shard owns a stretch of the sort order. Its great strength is that neighbours stay together. "All orders from 1 to 7 March" sits on one shard, or on two if the week crosses a border. A scan reads one place, in order.

Its weakness is any key that grows over time. Dates, timestamps, auto-increment ids and time-ordered ids such as UUIDv7 all put the newest keys at the end of the range. UUIDv7 is liked because time-ordered ids give a database index good locality [S66]. In a range-partitioned table that same locality means that every new write goes next to the previous one, on the same shard.

Suq's numbers show how bad it is. The writes are 3,000 a second in total. Shard 4 takes all of them, three times its limit of about 1,000 a second (DynamoDB's design limit for one partition [S40], used as a round number). The other three shards use none of their capacity. Adding more shards does not help, because only the newest range is ever written.

Real systems that use ranges often split a hot range in two when it grows, and that helps for a while. It does not remove the pattern: the new writes still hit the newest range.

</GoDeeper>

## Hash: neighbours land on different shards

<InteractiveCanvas slug="sysdesign-m9-hash-spread" />

Now Suq hashes the order id. A hash function turns any key into a number that looks random but is always the same for the same key. The number picks the shard. Neighbouring orders, 9041 and 9042, land on different shards, and each shard takes about 750 writes a second.

<GoDeeper title="Go deeper: what a good partition hash does">

<GlossaryTerm term="hash partitioning" definition="Running the key through a hash function and using the result to choose the shard. Keys are spread by their hash, not by their order, so neighbouring keys end up on different shards." /> trades order for balance. DynamoDB hashes the partition key to pick a partition [S40], and Kafka sends records with the same key to the same partition [S81].

A partition hash must have three properties. It gives the same answer every time and on every machine, so any app server can find any key. It spreads keys evenly, even when the keys look alike, such as `order:9041` and `order:9042`. And it is fast. It does not need to be secret. A cryptographic hash such as SHA-256 works but is slower than needed.

Two mistakes are common. The first is a weak hash, such as adding up the character codes of the key: similar keys give similar numbers and the spread is lumpy. The second is a hash that changes between runs or between languages. Some languages randomise their built-in hash on purpose, so two servers would disagree on where a key lives. Use one fixed function everywhere.

In a test with the hash you will write in chapter 9.7, 100,000 keys named `order:0` to `order:99999` spread over four shards as 25.0%, 24.9%, 25.2% and 25.0%. That is about as even as a random choice can be.

</GoDeeper>

## Range or hash? Slide a week across

<InteractiveCanvas slug="sysdesign-m9-range-vs-hash" />

Tap Range or Hash, then drag the blue week along the year. Under range, the week touches one shard (two where it crosses a border), but today's writes pile onto one shard. Under hash, writes are even, but the same week touches all four shards, because its orders are scattered.

<GoDeeper title="Go deeper: the trade in one table">

| | Range | Hash |
|---|---|---|
| Writes for time-ordered keys | One shard takes all of them | Spread evenly |
| One order by its id | One shard | One shard |
| A week of orders | One or two shards | Every shard |
| Sorted scan | Cheap, in order | Not possible without asking every shard and merging |
| Main risk | A hot range | Range queries become scatter-gather (chapter 9.6) |

A lookup by exact key costs the same in both: one shard. The difference is everything that is not an exact key. If Suq's most common question were "what did this buyer order last week", a hash on order id would send that question to all four shards. With 20 shards, that is 20 requests for one page.

Notice also what neither rule can fix. Both choose a shard from the key alone. If one key gets a huge share of the traffic, its shard is overloaded under either rule. That is the hot partition problem of chapter 9.4.

</GoDeeper>

## Pick the rule by the question you ask

<MermaidDiagram title="Which partitioning rule?" chart={`flowchart TD
  Q["What do most queries ask for?"] --> A["One item, by its key"]
  Q --> B["A run of neighbouring keys, in order"]
  Q --> C["Both"]
  A --> H["Hash the key"]
  B --> R["Range partition the key"]
  C --> K["Compound key: hash the first part, sort by the second"]
`} legend="Start from the question the app asks most. A compound key hashes one part, such as the seller, and keeps the other part, such as the order date, sorted inside that shard." />

Look at the question the app asks most. One item by its key: hash. A run of neighbours in order: range. Both: use a compound key. Hash a first part, such as the seller, to choose the shard, and keep a second part, such as the order date, sorted inside that shard. Then "Noor's orders this week" is one shard and one ordered read.

<GoDeeper title="Go deeper: compound keys, and what they cost">

DynamoDB works this way: a partition key that is hashed, and an optional sort key that orders items sharing that partition key. {/* source needed: DynamoDB keeps items with the same partition key together, in sort key order (HowItWorks.Partitions or data-modelling docs page, not yet in the dossier). */} Many other stores offer the same shape under other names.

The compound key keeps the best of both for one kind of question: everything about one seller, in date order, on one shard. Its cost is that all of one seller's data now lives on one shard. A seller with a flash sale is a hot key. Chapter 9.4 shows what that does and how to split the key again.

Choose the first part of the key by asking two things. Does it have many different values, so that hashing spreads them? A field with three values, such as order status, gives three busy shards at most. And is the load per value roughly even? Buyer id passes both tests for Suq's buyer pages. Seller id passes the first and fails the second, because a few sellers are much bigger than the rest.


</GoDeeper>

## Adding a shard moves most keys

<InteractiveCanvas slug="sysdesign-m9-mod-n-reshuffle" />

Suq now has 5 shards, so the rule becomes hash mod 5 instead of hash mod 4. Key 17 was on shard 1 and is now on shard 2. Key 20 stayed on shard 0. In a test with 100,000 keys, 80% changed shard. Every moved key is data to copy, and reads sent to the old shard miss.

<GoDeeper title="Go deeper: why N over N+1 of the keys move, and what it costs">

A key stays only when `hash mod 4` equals `hash mod 5`. Look at hash values from 0 to 19, which is one full cycle of both rules. Only 0, 1, 2 and 3 give the same answer under both, so 4 of every 20 keys stay and 16 of 20 move. In general, going from N to N+1 shards keeps 1 key in N+1 and moves N in N+1. From 10 shards to 11, 91% move. The test with 100,000 keys gave 80.2% for 4 to 5 and 91.0% for 10 to 11.

For Suq, 80% of 1.8 TB is 1.44 TB to copy. At a copy speed of 100 MB a second, that is 14,400 seconds, 4 hours, with the shards busy serving customers at the same time. Until it is done, reads for moved keys go to a shard that does not have them yet.

The same trap catches caches. If a cache cluster picks a node with `hash mod 10` and one node dies, switching to `mod 9` keeps only 10% of the keys on the right node. The other 90% miss, and the database behind the cache takes the load, which is the stampede from chapter 5.6.

The lesson is not "never use mod". For a number of shards that never changes, mod is simple and perfect. The lesson is that mod ties every key to N. A rule that lets N change while moving few keys is what the next chapter builds: consistent hashing.


</GoDeeper>

<GoDeeper title="In an interview">

Say: "I would hash the key to spread load evenly, and use a range only when I need ordered scans. For time series I would not range by time alone, because the newest range takes every write. I would use a compound key, with a hashed first part. Hash mod N reshuffles about N over N+1 of the keys when N changes, so I would use consistent hashing or many small fixed partitions instead."

The follow-up is usually: "What happens when you add a shard, and how many keys move?" With mod N, about 80% when going from 4 to 5. With consistent hashing, about 1 in N+1, and they all move to the new shard.

</GoDeeper>
