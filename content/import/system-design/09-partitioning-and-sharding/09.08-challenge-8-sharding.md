## How the experiment works

A key-value store splits its keys over nodes, and a router decides which node owns each key. In parts 1 and 2, each node is a `Map` in one Node.js process, and the router is the thing under test. That is honest for these two parts: how many keys land on a node, and how many keys change owner when a node joins, depend only on the router and the keys. They do not depend on whether the node is a machine or a `Map`. Part 3 is about load and waiting, which a `Map` cannot show, so it starts four real shard servers as separate processes, and measures real latencies against them.

Three design choices keep the numbers honest, and each one fixes a mistake that is easy to make.

**The keys are fixed.** Every run uses the same keys, `order:0` to `order:99999`, and the same seeded random numbers. If two schemes used different keys, you would not know whether a difference came from the scheme or from the luck of the keys. The hash function is yours from chapter 9.7, so the same name always lands on the same shard.

**The load is open loop, as in challenge 1.** The load generator sends the next request on schedule even if earlier answers have not come back. A generator that waits for each answer slows down when a shard slows down, and so it hides the very queue you want to see.

**Each shard is one worker, as in challenge 1.** The shard server's work is a loop that keeps the CPU busy for 4 ms, so a second request must wait for the first. One shard can then serve roughly 200 to 230 requests a second on a typical laptop. That is the shard limit in this challenge, and your machine will give a different number.

Next, `toolkit/store.js`. It has three routers and the store. A router answers one question, `route(key)`: which node owns this key? The store keeps one `Map` per node and counts the writes each node takes. Its `addNode` does what a real rebalance does: it adds the node, then moves every key whose owner changed, and returns how many moved.

```js
// toolkit/store.js: a key-value store split over named nodes, and three
// routers that decide which node owns a key. A node here is a Map in memory;
// the placement logic is the same as when each node is a machine.
import { hash32, HashRing } from "./hash.js";

// Router 1: hash mod N. Simple, and it reshuffles most keys when N changes.
export function modRouter(names) {
  let list = [...names];
  return {
    label: "hash mod N",
    route: (key) => list[hash32(key) % list.length],
    add: (name) => { list = [...list, name]; },
    remove: (name) => { list = list.filter((n) => n !== name); },
  };
}

// Router 2: your hash ring from chapter 9.7, with `vnodes` points per node.
export function ringRouter(names, vnodes = 100) {
  const ring = new HashRing({ vnodes });
  for (const name of names) ring.addNode(name);
  return {
    label: `ring, ${vnodes} point${vnodes === 1 ? "" : "s"}`,
    route: (key) => ring.getNode(key),
    add: (name) => ring.addNode(name),
    remove: (name) => ring.removeNode(name),
  };
}

// Router 3: range by month. Keys start with a date, like "2026-10-24/00099999".
// `boundaries` are the first months of shards 2, 3, ...: ["2026-04", "2026-07", "2026-10"].
export function monthRangeRouter(names, boundaries) {
  return {
    label: "range by date",
    route: (key) => {
      const month = key.slice(0, 7);
      let i = 0;
      while (i < boundaries.length && month >= boundaries[i]) i++;
      return names[i];
    },
    add: () => { throw new Error("a range router needs new boundaries, not just a new name"); },
    remove: () => { throw new Error("a range router needs new boundaries, not just a removed name"); },
  };
}

export class ShardedStore {
  constructor(router, names) {
    this.router = router;
    this.nodes = new Map(names.map((name) => [name, { data: new Map(), writes: 0, reads: 0 }]));
  }

  put(key, value) {
    const node = this.nodes.get(this.router.route(key));
    node.data.set(key, value);
    node.writes++;
  }

  get(key) {
    const node = this.nodes.get(this.router.route(key));
    node.reads++;
    return node.data.get(key);
  }

  // Add a node, then move every key whose owner changed. Returns how many moved.
  addNode(name) {
    this.nodes.set(name, { data: new Map(), writes: 0, reads: 0 });
    this.router.add(name);
    let moved = 0;
    for (const [from, node] of this.nodes) {
      for (const [key, value] of [...node.data]) {
        const to = this.router.route(key);
        if (to !== from) {
          node.data.delete(key);
          this.nodes.get(to).data.set(key, value);
          moved++;
        }
      }
    }
    return moved;
  }

  // Remove a node and hand its keys to their new owners. Returns how many moved.
  removeNode(name) {
    const leaving = this.nodes.get(name);
    this.nodes.delete(name);
    this.router.remove(name);
    for (const [key, value] of leaving.data) this.nodes.get(this.router.route(key)).data.set(key, value);
    return leaving.data.size;
  }

  keyCounts() {
    return Object.fromEntries([...this.nodes].map(([name, node]) => [name, node.data.size]));
  }

  writeCounts() {
    return Object.fromEntries([...this.nodes].map(([name, node]) => [name, node.writes]));
  }
}

// The busiest value divided by the average: 1 is perfectly even.
export function busiestOverAverage(counts) {
  const values = Object.values(counts);
  return Math.max(...values) / (values.reduce((a, b) => a + b, 0) / values.length);
}
```

Read `modRouter` and `monthRangeRouter` closely. They are the two simple rules from chapter 9.2. The range router needs keys that start with a date, such as `2026-10-24/00099999`, and it cannot take a new node without new boundaries, which is why its `add` throws. `busiestOverAverage` at the bottom is the one number you will use to judge evenness: the busiest node's count divided by the average. A value of 1 is perfect.

```js
// toolkit/bars.js: draw a small bar chart as SVG text, one bar per label.
// bars: [{ label: "hash mod N", value: 1.04 }, ...]
export function barChart({ title, yLabel, bars, unit = "" }) {
  const W = 560, H = 340, L = 60, R = 24, T = 44, B = 60;
  const yMax = Math.max(...bars.map((b) => b.value)) * 1.15 || 1;
  const slot = (W - L - R) / bars.length;
  const barW = Math.min(90, slot * 0.6);
  const Y = (v) => H - B - (v / yMax) * (H - T - B);
  const rects = bars.map((b, i) => {
    const x = L + slot * i + (slot - barW) / 2;
    const y = Y(b.value);
    return `<rect x="${x.toFixed(1)}" y="${y.toFixed(1)}" width="${barW.toFixed(1)}" height="${(H - B - y).toFixed(1)}" fill="#2563eb"/>\n` +
      `<text x="${(x + barW / 2).toFixed(1)}" y="${(y - 6).toFixed(1)}" text-anchor="middle" font-weight="bold">${b.value.toFixed(2)}${unit}</text>\n` +
      `<text x="${(x + barW / 2).toFixed(1)}" y="${H - B + 20}" text-anchor="middle">${b.label}</text>`;
  });
  return `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 ${W} ${H}" font-family="sans-serif" font-size="13">
<rect width="${W}" height="${H}" fill="white"/>
<text x="${L}" y="26" font-size="15" font-weight="bold">${title}</text>
<line x1="${L}" y1="${H - B}" x2="${W - R}" y2="${H - B}" stroke="#999"/>
<line x1="${L}" y1="${T}" x2="${L}" y2="${H - B}" stroke="#999"/>
<text x="${L - 8}" y="${T + 4}" text-anchor="end">${yMax.toFixed(1)}</text>
<text x="${L - 8}" y="${H - B}" text-anchor="end">0</text>
<text x="16" y="${(T + H - B) / 2}" transform="rotate(-90 16 ${(T + H - B) / 2})" text-anchor="middle">${yLabel}</text>
${rects.join("\n")}
</svg>
`;
}
```

## Step 2: part 1, the spread

Part 1 loads 90,000 older orders spread from 1 January to 23 October, then 10,000 new orders that all carry today's date, 24 October. It does this four ways: range by month, hash mod 4, a ring with one point per shard, and a ring with 100 points per shard. For each, it prints the share of all keys on each shard, and the share of today's writes on each shard. Today's writes are the Suq problem from chapter 9.2: all new traffic has the same date. Create `part-1-spread/spread.js`:

```js
// Part 1: spread 100,000 orders over 4 shards four ways, and watch today's writes.
import { writeFileSync } from "node:fs";
import { ShardedStore, busiestOverAverage, modRouter, monthRangeRouter, ringRouter } from "../../../toolkit/store.js";
import { barChart } from "../../../toolkit/bars.js";

const NODES = ["shard-1", "shard-2", "shard-3", "shard-4"];
const DAY_MS = 24 * 60 * 60 * 1000;
const FIRST_DAY = Date.UTC(2026, 0, 1);
const TODAY = "2026-10-24";
const OLD_ORDERS = 90_000; // spread over 1 January to 23 October
const NEW_ORDERS = 10_000; // all placed today

// A key starts with the order's date, then its number: "2026-10-24/00099999".
const dateOfDay = (day) => new Date(FIRST_DAY + day * DAY_MS).toISOString().slice(0, 10);
const oldKey = (i) => `${dateOfDay(Math.floor((i / OLD_ORDERS) * 296))}/${String(i).padStart(8, "0")}`;
const newKey = (i) => `${TODAY}/${String(OLD_ORDERS + i).padStart(8, "0")}`;

const schemes = [
  () => monthRangeRouter(NODES, ["2026-04", "2026-07", "2026-10"]),
  () => modRouter(NODES),
  () => ringRouter(NODES, 1),
  () => ringRouter(NODES, 100),
];

const pct = (counts, name) => `${((counts[name] / Object.values(counts).reduce((a, b) => a + b, 0)) * 100).toFixed(1).padStart(5)}%`;

console.log("scheme             all keys per shard (%)           today's writes per shard (%)     busiest / average");
const bars = [];
for (const make of schemes) {
  const router = make();
  const store = new ShardedStore(router, NODES);
  for (let i = 0; i < OLD_ORDERS; i++) store.put(oldKey(i), i);
  const writesBefore = store.writeCounts();
  for (let i = 0; i < NEW_ORDERS; i++) store.put(newKey(i), i);
  const today = Object.fromEntries(NODES.map((n) => [n, store.writeCounts()[n] - writesBefore[n]]));
  const keys = store.keyCounts();
  const ratio = busiestOverAverage(today);
  bars.push({ label: router.label, value: ratio });
  console.log(
    `${router.label.padEnd(16)}   ${NODES.map((n) => pct(keys, n)).join(" ")}     ${NODES.map((n) => pct(today, n)).join(" ")}     ${ratio.toFixed(2)}`
  );
}

writeFileSync(new URL("./chart.svg", import.meta.url), barChart({
  title: "Today's writes: busiest shard divided by the average",
  yLabel: "busiest shard / average (1 is even)",
  bars,
}));
console.log("\nwrote chart.svg");
```

const NODES = ["shard-1", "shard-2", "shard-3", "shard-4"];

test("a range router sends each month to its shard", () => {

## Step 3: part 2, keys moved

Part 2 asks the question from chapters 9.2 and 9.3 with real keys. Load 100,000 keys on four shards, add `shard-5`, and count how many keys moved. It does this for hash mod N, and then for a ring with 1, 2, 5, 10, 20, 50, 100 and 200 points per shard. It also counts a second number that matters: how many keys moved from one old shard to another old shard, which is data copied for no gain. Create `part-2-keys-moved/moved.js`:

```js
// Part 2: add a fifth shard to four and count how many of 100,000 keys move.
import { writeFileSync } from "node:fs";
import { ShardedStore, modRouter, ringRouter } from "../../../toolkit/store.js";
import { lineChart } from "../../../toolkit/chart.js";

const OLD = ["shard-1", "shard-2", "shard-3", "shard-4"];
const KEYS = 100_000;
const IDEAL = 100 / (OLD.length + 1); // a fair share for the new shard: 20%

// Load 100,000 keys, add shard-5, and report how many moved and where they went.
function addShard(router) {
  const store = new ShardedStore(router, OLD);
  for (let i = 0; i < KEYS; i++) store.put(`order:${i}`, i);
  const before = new Map();
  for (const [name, node] of store.nodes) for (const key of node.data.keys()) before.set(key, name);
  const moved = store.addNode("shard-5");
  let betweenOld = 0;
  for (const [name, node] of store.nodes) {
    for (const key of node.data.keys()) if (before.get(key) !== name && name !== "shard-5") betweenOld++;
  }
  return { moved: (moved / KEYS) * 100, betweenOld };
}

const mod = addShard(modRouter(OLD));
console.log(`hash mod N: ${mod.moved.toFixed(1)}% moved, ${mod.betweenOld} between old shards (ideal ${IDEAL}%)\n`);
console.log("points per shard   moved   between old shards");

const points = [];
for (const vnodes of [1, 2, 5, 10, 20, 50, 100, 200]) {
  const ring = addShard(ringRouter(OLD, vnodes));
  points.push({ x: vnodes, ring: ring.moved, mod: mod.moved, ideal: IDEAL });
  console.log(`${String(vnodes).padStart(16)}   ${ring.moved.toFixed(1).padStart(5)}%   ${String(ring.betweenOld).padStart(10)}`);
}

writeFileSync(new URL("./chart.svg", import.meta.url), lineChart({
  title: "Keys moved when a 5th shard joins (percent of 100,000)",
  xLabel: "points per shard on the ring",
  yLabel: "% of keys moved",
  points,
  series: [{ key: "mod", color: "#dc2626" }, { key: "ring", color: "#2563eb" }, { key: "ideal", color: "#9ca3af" }],
}));
console.log("\nwrote chart.svg");

And its test, `part-2-keys-moved/moved.test.js`. Notice the third test. It checks the exact property that makes consistent hashing worth using: when a node is added, a key may move only to the new node.

```js
import test from "node:test";
import assert from "node:assert/strict";
import { ShardedStore, modRouter, ringRouter } from "../../../toolkit/store.js";

const OLD = ["shard-1", "shard-2", "shard-3", "shard-4"];

function loaded(router, keys = 20_000) {
  const store = new ShardedStore(router, OLD);
  for (let i = 0; i < keys; i++) store.put(`order:${i}`, i);
  return store;
}

test("after adding a shard every key can still be read", () => {
  for (const router of [modRouter(OLD), ringRouter(OLD, 100)]) {
    const store = loaded(router, 5000);
    store.addNode("shard-5");
    for (let i = 0; i < 5000; i++) assert.equal(store.get(`order:${i}`), i, `${router.label} lost order:${i}`);
  }
});

test("hash mod N moves about 80% of the keys when a fifth shard joins", () => {
  const store = loaded(modRouter(OLD));
  const moved = store.addNode("shard-5") / 20_000;
  assert.ok(moved > 0.75 && moved < 0.85, `moved ${(moved * 100).toFixed(1)}%`);
});

test("a ring with 100 points moves about 20%, and only to the new shard", () => {
  const store = loaded(ringRouter(OLD, 100));
  const before = new Map();

Its `/top` page lists the three most requested keys, which is how you find a hot key in real life too:

```js
// One shard as a tiny HTTP server: a Map of keys, and about SERVICE_MS of work per request.
// The work blocks the event loop, so a shard is one worker: requests wait their turn,
// exactly like the server in challenge 1.
//   GET /?key=K            read a key
//   GET /?key=K&set=V      write a key
//   GET /top               the 3 most requested keys so far (this is how you find a hot key)
import http from "node:http";
import { URL } from "node:url";

const SERVICE_MS = Number(process.env.SERVICE_MS ?? 2);
const data = new Map();
const hits = new Map(); // key -> number of requests
let requests = 0;

function busyWork(ms) {
  const end = performance.now() + ms;
  while (performance.now() < end) {
    // spin: this loop is the "work"
  }
}

const server = http.createServer((req, res) => {
  const url = new URL(req.url, "http://shard");
  if (url.pathname === "/top") {
    const top = [...hits].sort((a, b) => b[1] - a[1]).slice(0, 3).map(([key, count]) => ({ key, count }));
    res.end(JSON.stringify({ requests, top }));
    return;
  }
  const key = url.searchParams.get("key");
  busyWork(SERVICE_MS);
  requests++;
  hits.set(key, (hits.get(key) ?? 0) + 1);
  if (url.searchParams.has("set")) data.set(key, url.searchParams.get("set"));
  res.end(JSON.stringify({ key, value: data.get(key) ?? null }));
});

server.listen(0, "127.0.0.1", () => {
  const { port } = server.address();
  if (process.send) process.send({ port }); // started by toolkit/load.js
  else console.log(`shard listening on http://127.0.0.1:${port}/ (${SERVICE_MS} ms of work per request)`);
});
```

The load generator, `toolkit/sharded-load.js`, is the open-loop generator of challenge 1 with one change: the caller says which shard each request goes to, and the latencies are kept per shard. A shard so overloaded that it refuses connections counts as a failure and does not crash the run:

```js
// toolkit/sharded-load.js: send requests at a target rate to several shards,
// choosing the shard for each request, and keep the latencies of each shard.
// Same open-loop idea as toolkit/load.js: the next request is sent on schedule
// even if earlier answers have not come back.
import http from "node:http";
import { exponential, seededRandom } from "./stats.js";

const agent = new http.Agent({ keepAlive: true, maxSockets: Infinity });

function get(url) {
  return new Promise((resolve, reject) => {
    http.get(url, { agent }, (res) => {
      res.resume();
      res.on("end", resolve);
    }).on("error", reject);
  });
}

async function waitUntil(t) {
  while (performance.now() < t) await new Promise((resolve) => setImmediate(resolve));
}

// next(random) returns { shard: "shard-1", url: "http://127.0.0.1:1234/?key=..." }.
// Returns { byShard: { "shard-1": [latency ms, ...] }, all: [...], failed: { "shard-1": 3 } }.
// A shard so overloaded that it refuses connections counts as a failure, not a crash.
export async function runShardedLoad({ next, rate, seconds, seed = 7 }) {
  const random = seededRandom(seed);
  const byShard = {};
  const failed = {};
  const all = [];
  const pending = [];
  const stop = performance.now() + seconds * 1000;
  let planned = performance.now();
  while (true) {
    planned += exponential(random, 1000 / rate);
    if (planned > stop) break;
    await waitUntil(planned);
    const sentAt = performance.now();
    const { shard, url } = next(random);
    pending.push(
      get(url).then(
        () => {
          const latency = performance.now() - sentAt;
          (byShard[shard] ??= []).push(latency);
          all.push(latency);
        },
        () => {
          failed[shard] = (failed[shard] ?? 0) + 1;
        }
      )
    );
  }
  await Promise.all(pending);
  return { byShard, all, failed };
}
```

Then the salting helpers, `part-3-hot-key/salt.js`. `saltedKey` is what a writer uses. `allSubKeys` is what a reader needs: every sub-key a writer might have used.

```js
// Salting: one hot key becomes `ways` sub-keys, chosen at random on every write.
// With ways = 1 the key is left alone.
export function saltedKey(key, ways, random = Math.random) {
  if (!Number.isInteger(ways) || ways < 1) throw new RangeError("ways must be a whole number of at least 1");
  if (ways === 1) return key;
  return `${key}#${Math.floor(random() * ways)}`;
}

// All the sub-keys a reader must ask for to see the whole key.
export function allSubKeys(key, ways) {
  if (!Number.isInteger(ways) || ways < 1) throw new RangeError("ways must be a whole number of at least 1");
  if (ways === 1) return [key];
  return Array.from({ length: ways }, (_, i) => `${key}#${i}`);
}
```

The script is `part-3-hot-key/hot.js`. It runs the same traffic four times: no salt, then 4, 8 and 16 sub-keys. Routing uses the ring from your toolkit with 100 points per shard. After the first run it asks the slowest shard for its `/top` keys.

```js

// 400 requests a second, and compare no salt with 4, 8 and 16 sub-keys.
import { writeFileSync } from "node:fs";
import { spawnServer } from "../../../toolkit/load.js";
import { runShardedLoad } from "../../../toolkit/sharded-load.js";
import { percentile } from "../../../toolkit/stats.js";
import { HashRing } from "../../../toolkit/hash.js";
import { barChart } from "../../../toolkit/bars.js";
import { saltedKey } from "./salt.js";

const NAMES = ["shard-1", "shard-2", "shard-3", "shard-4"];
const SERVICE_MS = 4; // work per request, so one shard handles roughly 200 to 230 a second
const RATE = Number(process.env.RATE ?? 400); // requests a second, all shards together
const HOT_SHARE = 0.5; // share of requests that go to the hot seller
const SECONDS = Number(process.env.RUN_SECONDS ?? 8);
const HOT_KEY = "seller:noor-crafts";

const servers = await Promise.all(
  NAMES.map(() => spawnServer(new URL("../shard-server.js", import.meta.url), { SERVICE_MS: String(SERVICE_MS) }))
);
const urlOf = Object.fromEntries(NAMES.map((name, i) => [name, servers[i].url]));
const ring = new HashRing({ vnodes: 100 });
for (const name of NAMES) ring.addNode(name);

console.log(`${RATE} requests a second for ${SECONDS} s; ${HOT_SHARE * 100}% go to ${HOT_KEY}; each shard does ${SERVICE_MS} ms of work per request\n`);
const bars = [];

// Ask a shard which keys it was asked for most. This is how you find a hot key.
async function showTopKeys(name) {
  const { requests, top } = await (await fetch(`${urlOf[name]}top`)).json();
  console.log(`  busiest keys on ${name} (${requests} requests so far):`);
  for (const { key, count } of top) console.log(`    ${key.padEnd(24)} ${String(count).padStart(5)}  (${Math.round((count / requests) * 100)}%)`);
}
for (const ways of [1, 4, 8, 16]) {
  const { byShard, all, failed } = await runShardedLoad({
    rate: RATE,
    seconds: SECONDS,
    next: (random) => {
      const key = random() < HOT_SHARE ? saltedKey(HOT_KEY, ways, random) : `seller:${Math.floor(random() * 100000)}`;
      const shard = ring.getNode(key);
      return { shard, url: `${urlOf[shard]}?key=${encodeURIComponent(key)}` };
    },
  });
  console.log(`salt ${ways} way${ways === 1 ? "" : "s"}:  overall p99 ${percentile(all, 99).toFixed(0)} ms`);
  console.log("  shard     req/s   p50 ms   p99 ms");
  let worst = 0;
  let slowest = NAMES[0];
  for (const name of NAMES) {
    const ms = byShard[name] ?? [];
    const p99 = percentile(ms, 99);
    if (p99 > worst) { worst = p99; slowest = name; }
    const refused = failed[name] ? `   (${failed[name]} refused)` : "";
    console.log(`  ${name}  ${(ms.length / SECONDS).toFixed(0).padStart(6)}  ${percentile(ms, 50).toFixed(0).padStart(7)}  ${p99.toFixed(0).padStart(8)}${refused}`);
  }
  if (ways === 1) await showTopKeys(slowest);
  console.log();
  bars.push({ label: ways === 1 ? "no salt" : `salt ${ways} ways`, value: worst });
}
for (const server of servers) server.stop();

writeFileSync(new URL("./chart.svg", import.meta.url), barChart({
  title: "p99 of the slowest shard, in milliseconds",
  yLabel: "milliseconds",
  bars,
}));
console.log("wrote chart.svg");

**Find the hot key.** In the first run, shard-2 took 263 requests a second while the others took 44 to 53, and its p50 was almost a second. The `/top` page names the cause: `seller:noor-crafts` was 78% of the requests that shard had seen. The other keys had 2 requests each. That is a hot key, and the evidence is a ranked list, not a guess. In a real system you would keep a count of the busiest keys per shard for exactly this reason.

Why did one shard queue and the others not? The hot shard was offered 263 requests a second and can serve roughly 230. Chapter 2.5 told you what a server does when arrivals exceed what it can finish: the queue grows for as long as the overload lasts. After 8 seconds the p99 was 1,789 ms. **Fix it.** With the key salted 4 ways, the busiest shard took 162 requests a second, the p99 of every shard stayed under 60 ms, and nobody queued. With 8 and 16 ways the busiest shard took 156 and 145. It never became equal at about 100 requests a second each, because the sub-keys land by hash and the hash does not spread them perfectly. That is the same luck you met in the playable of chapter 9.4: one shard always gets more than its share of sub-keys. The p99 numbers at 4, 8 and 16 ways are all in the tens of milliseconds and reorder from run to run, so do not read a trend into them. The step from no salt to any salt is the finding.

Salting has a price that this experiment does not show, and your README must name it: reading Noor's total now takes as many reads as there are sub-keys. `allSubKeys` gives the list a reader must ask for. With 16 sub-keys, each read of her total is 16 requests, so a salted key should be one you read rarely and write often.
