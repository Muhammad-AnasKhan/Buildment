Suq's orders are split by order id. That makes "show order 9041" fast: one shard. But buyers do not remember order ids. They open "My orders" and ask for everything they bought. This chapter is about every question that is not about the partition key.

## Search by buyer asks every shard

<InteractiveCanvas slug="sysdesign-m9-scatter-gather" />

Orders are placed by order id, so Sara's orders are spread over all four shards. A search for her sends the question to every shard and waits for all the answers. This is scatter-gather: scatter the request, gather the replies. Three shards answer in 5 ms. One takes 200 ms, and the search takes 200 ms too.

<GoDeeper title="Go deeper: the cost of asking everyone">

The partition key is the only column the system can use to go straight to one shard. Any other column, such as the buyer, the status or the price, gives no hint about where the matching rows are. The only safe answer is to ask all shards and merge the results.

That has three costs. The work: the question runs on every shard, even those with no matching rows, so adding shards does not make the search cheaper. The count: 20 shards means 20 requests for one page. And the wait: the search is as slow as its slowest shard, the tail effect you met in chapter 2.4 with the fan-out of a web page. The next beats put a number on it.

Ordering and limits add trouble. "The 10 most recent orders of Sara" needs the top 10 from every shard, merged, and then cut to 10. Each shard must return 10 even if only one of them has any, so the work is shards times 10 rows.

</GoDeeper>

## Local index or global index?

<MermaidDiagram title="Two kinds of secondary index" chart={`flowchart LR
  subgraph L["Local index: each shard indexes its own rows"]
    S1["Search: buyer = Sara"] --> A1["Shard 1 and its index"]
    S1 --> A2["Shard 2 and its index"]
    S1 --> A3["Shard 3 and its index"]
  end
  subgraph G["Global index: the index is its own partitioned table"]
    S2["Search: buyer = Sara"] --> IX["Index shard for Sara"]
    IX -.-> D["Pointers to the order rows"]
  end
`} legend="A local index makes the search ask every shard. A global index is split by the indexed value, so the search asks one index shard." />

A local index lives on each shard and covers only that shard's rows. A write touches one shard, but a search must ask every shard. A global index covers all rows and is itself split by the indexed value, here the buyer. A search asks one index shard. The price moves to the write.

<GoDeeper title="Go deeper: reads, writes and the trade between them">

<GlossaryTerm term="local secondary index" definition="An index kept on each shard for that shard's own rows. Updating it is part of the same write, but a search by the indexed value has to ask every shard." /> and <GlossaryTerm term="global secondary index" definition="An index over all rows, split into partitions by the indexed value. A search by that value asks one index partition, but each write must also update the index, on a different shard." /> trade in opposite directions.

| | Local index | Global index |
|---|---|---|
| Search by the indexed value | Asks every shard | Asks one index shard |
| Write cost | One shard, one transaction | Two or more shards: the row and the index entry |
| Is the index always current? | Yes, same write | Usually not: updated a moment later |
| Good for | Searches that already name the partition key, and rare reports | Frequent searches by another column |

A local index is cheap to keep exact, because the row and its index entry are on the same machine and change together. A global index makes reads cheap and writes dearer: every write to an indexed column also writes to the index shard for the new value, and a change of value writes twice, to remove the old entry and add the new one.

Each global index is one more copy of part of the data to store and to update. Two indexes on buyer and on status mean every order is written three times, once for the row and once for each index entry. That is the real cost of "just add an index".

</GoDeeper>

## A global index can miss a new write

<InteractiveCanvas slug="sysdesign-m9-global-index-lag" />

The order is saved on its own shard first. The index lives on other shards, and it is updated a moment later. A search made right after the write goes to the index, finds nothing, and Sara's new order is missing. A moment later the index catches up. A global index is usually eventually consistent.

<GoDeeper title="Go deeper: why the index lags, and how apps live with it">

To keep the row and the index entry exactly in step, both writes would have to succeed or fail together, on two different shards. That needs a distributed transaction (module 14 covers how), which makes every write slower and makes the write fail when either shard is down. Most systems choose a faster write and a lagging index instead. DynamoDB's global secondary indexes are updated asynchronously and are eventually consistent [S41]. The lag is the same kind of lag you saw with replicas in chapter 8.4, and the same tricks apply.

The most common workaround is simple: do not read your own write from the index. When Sara places an order, the write already returned the order. The app can show it from that response and merge it into the list from the index. A second workaround is to send the buyer's reads for a minute after a write to the data shard itself, with a scatter-gather, when freshness matters more than cost.

Decide per query how stale is acceptable. "My orders" a few seconds behind is usually fine. A stock check before payment is not, and it should read the row, not the index.

</GoDeeper>

## Drag the shard count: the tail grows

<InteractiveCanvas slug="sysdesign-m9-scatter-play" />

Drag the shard count from 1 up to 100 with the local index. Every search asks every shard, so the share of slow searches climbs: 18% at 20 shards, 63% at 100. Now tap Global index. The search asks one index shard and stays near 1%. The cost shows up elsewhere: each write now costs two writes.

<GoDeeper title="Go deeper: the formula, and what else cuts the tail">

If each shard is slow with chance p, the chance that a search over n shards is slow is 1 - (1 - p)^n. With p = 1%, that gives 1% at 1 shard, 9.6% at 10, 18% at 20, 39% at 50 and 63% at 100. Dean and Barroso give the same example for 100 servers in "The Tail at Scale" [S8]. The numbers are why a rare slowness on one machine becomes the usual experience of the whole search.

Three things shrink the problem. First, avoid the fan-out: use a global index, or choose the key so the common query is on the key. Second, limit how many shards a query must ask, for example by asking only the shards for a given date range. Third, hedged requests, which Dean and Barroso describe: send a second copy of a slow request to another replica of the same shard and use whichever answer comes first [S8].

The global index does not remove the cost, it moves it. A write to an indexed column is now two writes, so the write rate to the data doubles in the worst case. And as the previous beat showed, the index can lag.

The 1% slow chance and the 200 ms slow time are made-up story numbers, as in challenge 1, where you measured the same fan-out on your own machine.

</GoDeeper>

## Which query path should Suq use?

<MermaidDiagram title="Choosing how to answer a query that is not on the key" chart={`flowchart TD
  Q["A query not on the partition key"] --> F["How often does it run, and how fresh must it be?"]
  F --> R["Rare, or an admin report"]
  F --> O["Often, and a little stale is fine"]
  F --> H["Often, and it must be fresh"]
  F --> T["Free text or heavy analysis"]
  R --> R1["Scatter-gather over all shards"]
  O --> O1["Global secondary index"]
  H --> H1["Change the key so the query is on the key"]
  T --> T1["Copy the data to a search or analytics store"]
`} legend="The query decides the design. Each branch pays in a different place: reads, writes, or a second system to run." />

Ask how often the query runs and how fresh the answer must be. Rare: ask every shard. Often, and a little stale is fine: a global index. Often and fresh: change the key so the query is on the key. Free text or heavy analysis: copy the data to a search or analytics store.

<GoDeeper title="Go deeper: applying it to Suq">

Take Suq's three queries. "Show order 9041" is on the key, so it is one shard with no index. "My orders", by buyer, runs all day and tolerates a few seconds of lag, so a global index on buyer fits. "All orders this month for the finance report" runs once a day, so scatter-gather at night is fine, or the finance team reads a copy in an analytics store.

Changing the key is the strongest fix and the hardest. If "My orders" mattered more than "show order 9041", Suq could use buyer id as the first part of the key, with the order id second. Then "My orders" is one shard, in order. The price is that all of one buyer's orders sit on one shard, which is fine for buyers but would be a hot key for a seller, and "show order 9041" now needs the buyer id as well. One table cannot be keyed two ways; a second copy keyed the other way is the global index again.

**In AWS.** Treat a DynamoDB global secondary index as a second table that the system fills in for you, a moment behind the first [S41]. Plan for the lag the same way as for replicas.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "A query on anything other than the partition key has to ask every shard and merge the answers, so its latency is the slowest shard's, and it gets worse with more shards. A local index keeps writes cheap but still fans out. A global index makes reads cheap, but writes touch a second shard and the index lags."

The follow-up is usually: "How do you make 'My orders' fast and correct?" Answer: use a global index on buyer, show the buyer's own new order from the write response so the lag is invisible, and read the data shard directly where freshness matters.

</GoDeeper>
