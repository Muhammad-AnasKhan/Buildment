```quiz
type: mcq
question: "A chat app stores messages. Its most common query is 'the latest 50 messages of one conversation'. Which partition key and rule fit best?"
options:
  - "Range partition on the time each message was sent"
  - "Hash partition on each message's own unique id"
  - "Hash the conversation id; sort by time within it"
  - "Hash partition on the sender id of each message"
correct: 2
explanations:
  - "Every new message carries the current time, so the newest range takes all the writes. It also does not group a conversation's messages together."
  - "This spreads writes well, but one conversation's messages end up on every shard. Loading the latest 50 would ask them all."
  - "Right. Hashing the conversation id spreads conversations over the shards, and sorting by time inside it makes 'latest 50' one shard and one ordered read."
  - "A sender's messages are grouped, but a conversation's messages are not. The common query would still ask many shards."
```

```quiz
type: mcq
question: "A cache cluster of 8 nodes with 100 virtual nodes each holds 1.8 TB. A ninth node joins. About how much data moves, and how does that compare with hash mod N?"
options:
  - "About 200 GB; hash mod N would move about 1.6 TB"
  - "About 1.6 TB; hash mod N would move about 200 GB"
  - "About 200 GB; hash mod N would move the same"
  - "About 900 GB; hash mod N would move about 900 GB"
correct: 0
explanations:
  - "Right. The new node takes about 1 in 9 of the data, 1.8 TB / 9 = 200 GB. Hash mod N moves 8 in 9 of the keys, about 1.6 TB."
  - "This swaps the two. The ring is the one that moves little, and hash mod N is the one that reshuffles most of the data."
  - "Hash mod N does not keep keys where they were. It moves N over N+1 of them, which is far more than 200 GB."
  - "Half the data would move only if the new node had to take half. A new node takes its fair share, 1 in 9."
```

```quiz
type: mcq
question: "A table has 40 shards. One shard has a p99 of 2 s while the other 39 sit at 40 ms. Its /top page shows one key at 70% of its requests, and the traffic is mostly writes. What is the best first fix?"
options:
  - "Add 40 more shards so every key gets more room"
  - "Switch the table from hash to range partitioning"
  - "Add read replicas of the slow shard to share work"
  - "Salt the key into sub-keys so its writes spread"
correct: 3
explanations:
  - "More shards cool down the other keys, but the hot key is still one key on one shard. Its load barely changes."
  - "A range rule also sends one key to one shard. It can even group the hot key with its neighbours and make things worse."
  - "Replicas copy every write, so they do not lift a write limit. They help with reads, and this traffic is mostly writes."
  - "Right. Splitting the key into sub-keys lets its writes land on different shards. The price is that reads of the whole key must ask every sub-key."
```

```quiz
type: mcq
question: "During a rebalance, a team switches the partition map to the new node first, and then starts copying the data. What goes wrong?"
options:
  - "Nothing: the old node keeps answering from its copy"
  - "Moved keys are asked of a node that lacks the data yet"
  - "The hash function now gives different answers for keys"
  - "The new node refuses every write until the copy ends"
correct: 1
explanations:
  - "Once the map points to the new node, requests no longer go to the old node. And an old copy would miss new writes anyway."
  - "Right. Until a key's data has arrived, the new node says 'not found'. Copy first, catch up, and only then switch the map entry."
  - "The hash function is unchanged. Only the map from partitions to nodes changed, which is why the data must be there first."
  - "The new node would accept the writes. That is a different problem: it would then hold new data without the old data."
```

```quiz
type: mcq
question: "Orders are sharded by order id. A support tool searches orders by customer email about 20 times a day, and a few seconds of lag is fine. What is simplest and good enough?"
options:
  - "A global index on email, kept in the same transaction"
  - "Re-key the whole table so that email comes first"
  - "Ask every shard and merge the answers each time"
  - "A second table keyed by email, written with each order"
correct: 2
explanations:
  - "A transaction across the order shard and the index shard makes every order write slower, to speed up a query that runs 20 times a day."
  - "That would make every order lookup by id ask all shards. It trades the main query for a rare one."
  - "Right. 20 searches a day is a trivial load, even if each asks every shard. A rare query does not justify a second copy of the data."
  - "This is a global index built by hand. It doubles the writes and can lag, a cost that a query this rare does not repay."
```
