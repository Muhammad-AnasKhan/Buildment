Suq adds a fifth node. Chapter 9.3 showed how few keys must move. Now comes the harder part: moving them while 700 writes a second keep arriving, and making sure every request still finds the right node while the map changes.

## Fixed partitions: a new node takes whole pieces

<InteractiveCanvas slug="sysdesign-m9-fixed-partitions" />

Cut the data into many more partitions than nodes, say 64, and never change that number. The rule from key to partition stays fixed. A fifth node joins and takes whole partitions from the others: 13 of 64 move, about 20% of the data. Only the table that says which node holds which partition changes.

<GoDeeper title="Go deeper: choosing the number of partitions">

With fixed partitions, a key's partition never changes. What changes is the map from partitions to nodes. Moving a partition means copying it to the new node, then changing one entry in the map. The key to partition rule is untouched.

For Suq, 13 of 64 partitions of 1.8 TB is about 370 GB. At a copy speed of 100 MB a second, that is about 3,700 seconds, a little over an hour. The copy speed is an assumed figure, and real systems throttle it on purpose, so that the move does not starve live traffic.

The partition count is a decision made early that is hard to undo. You can never have more nodes than partitions, because a partition lives on one node. Too few partitions and the pieces are huge, so a move is slow and the load is lumpy. Too many and the bookkeeping grows: every partition has its own files, its own replicas and its own place in the map. A rule of thumb, which is advice and not a sourced figure, is to start with at least ten times as many partitions as the nodes you expect to need.

A hash ring with virtual nodes (chapter 9.3) is close to the same idea. The points are the many small partitions, and the ring computes which node owns each one. The difference is that fixed partitions keep the ownership as an explicit table, which is easy to inspect and to move by hand. {/* source needed: which real systems use a fixed number of partitions (for example Kafka topics have a partition count; the dossier records only that the same key goes to the same partition [S81]). */}

</GoDeeper>

## Dynamic split: a full partition becomes two

<InteractiveCanvas slug="sysdesign-m9-dynamic-split" />

The other way is to start small and let partitions grow. When one reaches a size limit, here 10 GB, it splits at its middle key into two halves of 5 GB, and one half moves to a node with room. A big table ends up with many partitions. A small table stays small, with no wasted pieces.

<GoDeeper title="Go deeper: splitting and its limits">

A split cuts a partition into two. For a range partition, it picks the middle key and gives everything below it to one half. For a hash partition, it halves the hash range that the partition owns. Either way, only the data of that one partition is copied, and the rest of the table does not move.

The trigger can be size, as in the picture, or load: a partition that takes too many writes can be split even if it is small. That helps with a hot range, like the newest dates in chapter 9.2, because the hot part gets smaller and can move to its own node.

Dynamic splits have a blind spot. If a single key is hot, splitting does nothing: one key cannot be cut in half. Chapter 9.4 is about that case, and the answer there is to split the key, not the partition.

The limit of 10 GB is made up for the picture. Real systems choose their own limits and their own triggers. {/* source needed: a real system's automatic split rule (not in the dossier). */}

</GoDeeper>

## Moving data while requests keep coming

<InteractiveCanvas slug="sysdesign-m9-rebalance-play" />

Tap a scheme, then drag the move forward in time. Hash mod N must copy 80% of the data, 1.44 TB. Fixed partitions copy 20%. Now tap the map switch: while clients still hold the old map, requests for data that has moved go to the wrong node. Watch how the wrong-node count follows the amount already moved.

<GoDeeper title="Go deeper: the numbers and the safe order of steps">

The picture uses Suq's story numbers: 1.8 TB of data, 5,000 requests a second spread evenly over the keys, and a copy speed of 100 MB a second. Going from four nodes to five:

| Scheme | Data to move | Time at 100 MB/s | Wrong-node requests half way, old map |
|---|---|---|---|
| Hash mod N | 80%, 1.44 TB | 14,400 s, 4 hours | 40% of 5,000, 2,000 a second |
| Fixed partitions or ring | about 20%, 360 GB | 3,600 s, 1 hour | 10% of 5,000, 500 a second |

The wrong-node figure is requests per second times the share of keys already moved, with every client on the old map. Half way through, a mod N move has relocated 40% of all the keys and a partition move has relocated 10%.

A safe move for one partition has four steps. Copy it to the new node while the old node keeps serving it. Copy the writes that arrived during the copy. Pause writes to that partition for a moment, then switch its entry in the map. Delete it from the old node. The pause is short because the new node is almost caught up before the switch.

The unsafe move is to switch the map first and copy afterwards. The new node answers "not found" for every key that has not arrived yet. This is the mistake behind most "rebalancing caused an outage" stories. A per-partition map makes the safe order easy, because each partition switches when its own copy is done. With hash mod N there is no such unit: the rule itself changes for every key at once.

</GoDeeper>

## Who knows where a key lives?

<MermaidDiagram title="Three places to keep the partition map" chart={`flowchart LR
  subgraph A["1. The client holds the map"]
    C1["Client with map"] --> N1["Right node"]
  end
  subgraph B["2. A proxy holds the map"]
    C2["Client"] --> P["Router tier"] --> N2["Right node"]
  end
  subgraph C["3. Any node can forward"]
    C3["Client"] --> N3["Any node"] --> N4["Right node"]
  end
`} legend="The same map, kept in three places. The fewer places that hold a copy, the easier it is to keep fresh. The fewer hops, the faster each request." />

There are three ways to find the right node. The client holds the map and goes straight there. A proxy holds the map, and the client knows only the proxy. Or the client asks any node, and that node forwards the request. Each design keeps the map, and the cost of keeping it fresh, in a different place.

<GoDeeper title="Go deeper: the three designs side by side">

| | Client holds the map | Proxy holds the map | Any node forwards |
|---|---|---|---|
| Hops for a request | 1 | 2 | 1 or 2 |
| Who must be updated on a move | Every client | The proxies | The nodes |
| Main risk | Stale maps in many clients | The proxy is a bottleneck and a new failure point | Extra load on nodes, and every node must know the map |
| Typical use | Smart client libraries | A router tier or a service proxy | Systems where the nodes gossip the map to each other |

A proxy that picks the node by consistent hash is a router tier. Envoy's ring hash load balancing does this [S16]. Putting the map in a proxy means a move changes one place instead of thousands of clients. The cost is one more hop and one more thing to run and scale.

Letting any node forward needs every node to hold the map. Dynamo did this with gossip: nodes tell each other about members and changes [S45]. {/* source needed: a small coordination service such as etcd or ZooKeeper is where many systems keep the authoritative partition map (the dossier lists a coordinator as a building block [S68] but not this use). */}

Whichever design you choose, the map needs a version number. A node that receives a request can compare the client's version with its own, and tell the client when it is behind. That is the next beat.

## A stale map costs one extra hop

<InteractiveCanvas slug="sysdesign-m9-stale-map" />

The client has map version 7, so it asks node 1 for a key that moved to node 5. Node 1 replies with the new owner. The client updates its map to version 8 and asks node 5. The stale request cost one extra hop and nothing else. After that, the client's requests go straight to the right node.

<GoDeeper title="Go deeper: redirects, forwards and the cost of a stale client">

An old owner can answer a stale request in two ways. It can redirect: reply "this key moved, ask node 5", and let the client retry. Or it can forward: pass the request to node 5 itself and return the answer. Redirects keep the old node simple and teach the client the new map. Forwards hide the move from the client but make the old node do extra work for a while.

What it must never do is serve the key from its old copy after the switch. That copy no longer receives writes. A read returns old data, and a write sent to it is lost when the old copy is deleted.

A stale map is cheap for one client. It is expensive when many clients are stale at once. After a large move, thousands of clients each pay one extra hop, and the old nodes get a burst of redirect traffic. Version numbers help, because each redirect carries the new version, so a client is stale at most once per move. A proxy tier avoids the burst, since only a few proxies are stale.

For Suq, a move that relocates 20% of the keys, with every client on the old map, means 20% of requests pay one extra hop until the client has learned the new map. That is a small cost next to a mod N move that relocates 80%.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "I would split the data into many fixed partitions, far more than nodes, and keep an explicit map from partition to node. Adding a node moves whole partitions, so only about 1 over N+1 of the data is copied. A move copies a partition while the old node keeps serving, then switches its map entry. The map has a version, so a stale client is redirected once."

The follow-up is usually: "Where do you keep the map?" Give the three options (client, proxy, any node) and say you would pick a proxy or a smart client with versioned maps, depending on whether you control the clients.

</GoDeeper>
