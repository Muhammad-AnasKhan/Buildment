Suq is an online marketplace where sellers list items and buyers order them (a made-up company). Every order is a row in one `orders` table, in one database, on one machine. That worked for two years. Then the numbers moved.

Today the database takes 700 writes a second, and its 2 TB disk is 1.8 TB full. Watch the picture below. What do you notice about the two numbers, the disk and the writes? Which one do you think will cause trouble first?

## One machine, two ceilings

<InteractiveCanvas slug="sysdesign-m9-one-table" />

Orders flow into one database. Watch the strip: the disk is 1.8 TB full out of 2 TB, and 40 GB of new orders arrive every day. In 5 days no new order can be saved. A second ceiling is on its way too: this database can take only about 1,000 writes a second.

<GoDeeper title="Go deeper: why a bigger machine only buys time">

The first answer is always "buy a bigger machine". It works, for a while. This is vertical scaling, which you met in chapter 4.2. A bigger disk gives Suq months, not years. Machines also have a largest size, and each step up costs more than the one before. One machine is also one place to fail: if it goes down, every order goes with it.

The second answer is "add replicas", the copies from module 8. Replicas help with reads, because many machines can answer them. They do nothing for the two limits in the picture. Each replica holds a full copy of the table, so the disk problem is repeated on every machine. Each replica also applies every write that the leader takes, so the write limit does not move.

Back to the question above. The disk has (2,000 - 1,800) / 40 = 5 days left. If writes grow 10% a month, they reach 1,000 a second only when 700 x 1.1^n = 1,000, which is after about 3.7 months. So space runs out first, and the write limit follows.

So Suq has two ceilings that copies cannot lift. One is space: the table does not fit on one disk. The other is the write rate: one machine cannot apply 3,000 writes a second, let alone more. Both need the same change. The data must be split, so that each machine holds only part of it and takes only part of the writes.

The numbers are Suq's story numbers and are rounded to make the arithmetic easy. The limit of about 1,000 writes a second per machine is borrowed from DynamoDB's design limit for one partition [S40], as a round number to work with. Real databases differ a lot, and the right limit for yours comes from measuring it, as you did in challenge 1.

</GoDeeper>

## Cut the table into slices

The fix is to cut the table into slices and put each slice on its own machine. A slice is called a shard. A rule on the key, such as the order id, says which shard holds each order. With four shards, each holds about 450 GB and takes about 175 writes a second. The rest of this module is about choosing that rule.

<GoDeeper title="Go deeper: partition, shard, and what you give up">

<GlossaryTerm term="partition" definition="One slice of a table's data. Partitioning means splitting the data so that each slice holds only some of the keys." /> and <GlossaryTerm term="shard" definition="A partition kept on its own machine or database. People often use the two words for the same thing, and so does this module." /> mean nearly the same thing. A partition is a slice of the data. A shard is a slice with a machine of its own. DynamoDB and Kafka say partition [S40, S81]; many SQL setups say shard.

Splitting is not free. Four problems come with it, and the rest of the module takes them in turn. First, the rule decides how evenly the load spreads, and a bad rule leaves one shard doing all the work (chapters 9.2 and 9.4). Second, a rule such as "hash mod N" breaks when you add a machine, because most keys change shard (9.2 and 9.3). Third, moving data while the system runs, and finding the right shard for each request, need care (9.5). Fourth, any question that is not about the key must ask every shard (9.6), and a transaction across two shards is much harder than one inside a shard.

That last point is why you should not shard early. A single database, with replicas for reads, goes a long way. Shard when you can name the ceiling you are hitting, as Suq did: space first, then writes.

</GoDeeper>
