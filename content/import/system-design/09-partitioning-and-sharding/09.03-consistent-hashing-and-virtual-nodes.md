Chapter 9.2 ended with a trap: with hash mod N, adding one shard to four moves 80% of the keys. Suq needs a rule where a new node takes only its fair share, about a fifth, and leaves the rest alone. That rule is consistent hashing.

## A key goes to the next node

<InteractiveCanvas slug="sysdesign-m9-ring-lookup" />

Hash the nodes as well as the keys, and put both on a ring of numbers. After the highest number comes 0 again. A key belongs to the first node at or after its position. Here k1 goes to B, k2 goes to C, and k3 wraps round past 100 to A.

<GoDeeper title="Go deeper: the ring in a few lines">

The ring is the range of the hash function. A 32 bit hash gives numbers from 0 to 4,294,967,295, and the highest number sits next to 0, which is why it is a ring and not a line. Each node is hashed once, from its name, and keeps that spot. Each key is hashed too. To find the owner, look for the first node position that is the same as or higher than the key's position. If there is none, wrap round to the lowest one.

In code, the node positions sit in a sorted array. Finding the owner is a binary search for the first position at or above the key's hash, which takes a few steps even with thousands of points. You write this in chapter 9.7.

Consistent hashing was introduced by Karger and colleagues in 1997 for distributed caches, to relieve hot spots on web servers [S18]. Amazon's Dynamo used it to partition data [S45]. Envoy, a proxy, offers it as "ring hash" load balancing, in the style called Ketama [S16].

The ring does not store anything. It is only a rule that every client can compute from the same list of nodes. Two clients with the same list always agree on where a key lives, with no talking between them.

</GoDeeper>

## A new node takes keys from one neighbour

<InteractiveCanvas slug="sysdesign-m9-ring-add-node" />

Node D joins at position 60. Only the keys between B and D change owner, and they all come from C. In a test, adding a fifth node to four moved 19.4% of 100,000 keys, and none moved between old nodes. Hash mod N moved 80% in the same test.

<GoDeeper title="Go deeper: what the saving is worth to Suq">

When D joins, it takes over the stretch of the ring between the node before it and itself. Before, those keys belonged to the node after D. Nothing else changes: keys on every other stretch still find the same first node clockwise. So a new node takes at most one stretch, and that is about 1 key in N+1 on average.

For Suq's 1.8 TB across four nodes, a fifth node should take about a fifth of the data: 360 GB. At a copy speed of 100 MB a second, that is 3,600 seconds, one hour. With hash mod N, 80% of the data moves, 1.44 TB, which is about 4 hours. The two numbers are the test from chapter 9.2 and this one, applied to Suq's story size.

Removing a node works the same way in reverse. Its keys go to the next node on the ring, and no other key moves. In the test, removing one of five nodes moved only that node's keys, and none moved between the others.

The saving has a limit that the next beats show. Moving 1 key in N+1 on average does not say how evenly the keys sit, and it does not say which node pays for a failure.

</GoDeeper>

## One point per node gives lopsided slices

<InteractiveCanvas slug="sysdesign-m9-ring-uneven" />

Each node got one random point. The slices are 40%, 10% and 50% of the ring, so C holds five times as many keys as B. With only a few random points, one slice is often huge. Ten nodes with one point each left the busiest node with 2.6 times its fair share in the test.

<GoDeeper title="Go deeper: why random points are lumpy">

Think of throwing three darts at a clock face. The darts cut it into three arcs, and arcs of equal length are rare. For n random points, the longest arc is on average (1/n)(1 + 1/2 + ... + 1/n) of the ring. For three points that is 61%. The chance that one arc is over half the ring is 3 x (1/2)^2, which is 75%. This is a standard result that the simulation here agrees with, and it is course arithmetic, not a figure from a paper.

The test from chapter 9.2 shows the same thing in a real ring. With 10 nodes and one point each, the busiest node held 2.6 times the average and the quietest held 0.03 times. Four nodes with one point each gave the busiest 1.68 times the average.

An uneven ring is bad for two reasons. The busy node needs a bigger machine than the average, or it becomes the first hot spot. And a quiet node wastes money. Adding more nodes does not fix it, because every new node is one more random point.

</GoDeeper>

## Virtual nodes: many small points per node

<InteractiveCanvas slug="sysdesign-m9-ring-play" />

Give each node many points, called virtual nodes, spread round the ring. Drag the dial from 1 point up to 200. The busiest node's load falls toward the average. Then tap Add node or Remove node and read how many keys moved. Try 1 point, then 100, and compare.

<GoDeeper title="Go deeper: measured spread and what extra points cost">

<GlossaryTerm term="virtual node" definition="One of many points a single machine owns on the hash ring. Each machine is hashed many times, for example from the names node-a#0, node-a#1 and so on, so its keys come from many small slices instead of one big one." /> is the fix in Dynamo, where each physical node owns several points on the ring [S45]. With many small slices per node, the random lumps average out. This is what the dial in the picture shows.

These numbers come from the course simulation: 100,000 keys named `order:0` to `order:99999`, nodes named node-a to node-d, adding node-e as the fifth, with the hash from chapter 9.7.

| Points per node | Busiest node, times the average | Keys moved when adding the 5th node |
|---|---|---|
| 1 | 1.68 | 1.4% |
| 10 | 1.26 | 21.1% |
| 100 | 1.14 | 19.4% |
| 200 | 1.09 | 19.1% |

The ideal move is 20%. With one point, the number is noisy: here the new node landed in a tiny slice, which looks like a win but leaves it nearly empty, and the spread is poor. At 100 points both are close to ideal. More points keep helping, with smaller gains each time. The cost is memory and lookup size: 10 nodes with 200 points each is 2,000 ring entries, which is still tiny, but a ring with millions of points is slower to rebuild when a node joins.

A bigger machine can be given more points than a smaller one, so that it holds a bigger share. {/* source needed: Dynamo assigns a number of virtual nodes per physical node based on its capacity (Dynamo paper, SOSP 2007, partitioning section; the dossier records only that each node owns several points [S45]). */}

</GoDeeper>

## When a node fails, who takes its keys?

<InteractiveCanvas slug="sysdesign-m9-ring-node-fails" />

Node D fails. With one point, its whole slice falls on one neighbour, which jumps from 25% to 50% and may fall over next. With 100 points each, D's many small slices go to A, B and C, and each rises to about 33%. Virtual nodes share a failure, not only the normal load.

<GoDeeper title="Go deeper: planning for the node you lose">

The failed node's keys go to whoever owns the next point on the ring. With one point each, that is always the same neighbour, so one machine suddenly takes twice its work. If it was already busy, it fails too, its keys fall on the next node, and the failure spreads round the ring one node at a time. That is a cascade.

With many points, D's slices sit next to many different nodes, so the load is shared by all survivors. {/* source needed: the Dynamo paper says that when a node becomes unavailable its load is dispersed evenly over the remaining nodes (section on partitioning strategies; not in the dossier). */} With four nodes, each of the three survivors takes a third of D's keys.

You can turn that into a rule for how busy to run. If N nodes share the load evenly and one fails, each survivor must carry N/(N-1) times its old load. For four nodes that is 4/3, an increase of a third. So four nodes should run at no more than 75% of capacity, or the loss of one pushes the rest over the edge. With ten nodes the limit is 90%. More nodes means less spare room is needed, which is one more reason small machines in large numbers often win.

**In AWS.** DynamoDB hashes the partition key to choose a partition, and you do not manage a ring yourself [S40]. If you route with Envoy, its ring hash option is this chapter's idea [S16].

Do not leave this chapter believing that consistent hashing removes hot spots. It spreads keys evenly, but one very popular key is still one point and one node. DynamoDB's 2022 paper names hot partitions among its most common early problems [S44]. Chapter 9.4 is about them.

</GoDeeper>

<GoDeeper title="In an interview">

Say: "Consistent hashing puts nodes and keys on a ring, and a key goes to the next node clockwise. Adding or removing a node moves only about 1 key in N+1, so rebalancing is cheap. Virtual nodes give each machine many points, so the load is even and a failed node's load is shared by all the others."

The follow-up is usually: "Does consistent hashing fix hot keys?" The answer is no. A hot key is one point on the ring, so one node takes all of it. It balances the keys, not the traffic of one key.

</GoDeeper>
