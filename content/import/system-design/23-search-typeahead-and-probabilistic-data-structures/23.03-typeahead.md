In chapter 23.1 you found that Dalil gets about 35,000 suggestion calls a second at the peak, each with a budget of 100 ms. This chapter is the deep dive for suggestions. It also takes the trade-off step and the failure step of the design loop, because the choices here are sharp.

## A suggestion must beat the next key

<InteractiveCanvas slug="sysdesign-m23-budget" />

A shopper types fast, so a suggestion that arrives late is useless. The budget is 100 ms from the key press to the screen. If the server is 60 ms away, the road alone takes most of it. The lookup itself must take almost no time, and the server must be near the shopper.

<GoDeeper title="Go deeper: where the 100 ms goes">

The budget has to pay for every step: the phone sends the prefix, the network carries it, a server finds the answer, the network carries it back, and the phone draws it. The numbers below come from napkin-math [S3] and are rounded, so treat them as shapes.

| Step | Time | Source |
|---|---|---|
| Round trip inside one region | 0.25 ms | S3 |
| One Redis, Memcached or MySQL query | 0.5 ms | S3 |
| Round trip, North America East to West | 60 ms | S3 |
| Round trip, EU West to North America East | 80 ms | S3 |
| Read of a 128 KiB blob from object storage | 80 ms | S3 |
| One dependent memory read | 100 ns | S1 |

Read the table as a list of things you may and may not put on the path. A trip to a far region (60 to 80 ms) uses most of the budget by itself. A blob read (80 ms) can never be on the path. A cache or database query (0.5 ms) is fine. A walk through a trie of 20 letters is 20 dependent memory reads, about 2 microseconds. So the lookup is not the problem. The distance is.

The scatter-gather search of chapter 23.2 is out for the same reason: it asks 8 shards, and the slowest one sets the time. The answer is to run the suggestion service near shoppers, in several regions or at the edge, with the whole structure in memory. A budget like this is measured as a p99 (chapter 2.4), because a shopper notices the slow ones.

</GoDeeper>

## A trie stores queries by their first letters

<MermaidDiagram title="Part of a trie of popular queries" chart={`flowchart TD
  R(("start")) --> S["s"]
  R --> W["w"]
  S --> SH["sh"]
  SH --> SHO["sho"]
  SH --> SHI["shi"]
  SHO --> SHOE["shoe"]
  SHO --> SHOR["shor"]
  SH --> SHE["she"]
  SHOE --> SHOES["shoes (9,200)"]
  SHOR --> SHORTS["shorts (4,100)"]
  SHI --> SHIRT["shirt (7,000)"]
  W --> WA["wa"] --> WATCH["watch (5,200)"]
`} legend="Each step down is one letter. A node is a prefix. Every query below a node starts with that prefix. The numbers are how often each query was searched." />

Each letter is one step down. Typing "sho" walks s, h, o and stops on a node. Every query below that node starts with "sho". Finding the node takes one step for each letter, so a ten-letter prefix takes ten steps, however many queries exist.

<GoDeeper title="Go deeper: why a trie, and what it does not solve">

A <GlossaryTerm term="trie" definition="A tree where each step down is one letter, so every path from the top spells a prefix. All words with the same start share the same first nodes." /> is a tree built from prefixes. Words that start the same share the same nodes, which saves memory. Finding a prefix costs one step per letter, and the cost does not grow with the number of queries.

The trie is not the only way to find a prefix. A sorted list of all queries with a binary search finds the first match in about 24 steps for 10 million queries, because 2 to the power 24 is about 16 million. A B-tree index in a database can do the same for a `LIKE 'sho%'` query, as the PostgreSQL notes in chapter 7.3 say. Many search engines also have a built-in suggester. {/* source needed: the suggester feature and its data structure in the documentation of the search engine you choose. */}

All of these find where the prefix starts. None of them tells you which of the thousands of queries below that point are the best three. That is the real problem, and the next beat solves it. The trie is the shape. The trick is what is stored on its nodes.

</GoDeeper>

## Keep the best three at every node

<InteractiveCanvas slug="sysdesign-m23-trie-walk" />

Tap letters to type. The picture walks down the trie and shows the three answers stored on the node you reach. Nothing below the node is read. Type s, h, o, then e, and watch the list change. Then type a letter that no query starts with, and see the empty answer.

<GoDeeper title="Go deeper: a trie with the best three on every node, in JavaScript">

While building, each query is offered to every node on its path. A node keeps only the best few by count. At lookup time the server walks the prefix and returns what is stored. The builder does the sorting, once, ahead of time.

```js
function buildTrie(queries, k = 3) {
  const root = { next: new Map(), top: [] };
  for (const [text, count] of queries) {
    let node = root;
    for (const ch of text) {
      if (!node.next.has(ch)) node.next.set(ch, { next: new Map(), top: [] });
      node = node.next.get(ch);
      node.top.push([text, count]);                 // this query is a candidate at every prefix node
      node.top.sort((a, b) => b[1] - a[1]);
      if (node.top.length > k) node.top.pop();      // keep only the best k per node
    }
  }
  return root;
}

function suggest(root, prefix) {
  let node = root;
  for (const ch of prefix) {
    node = node.next.get(ch);
    if (!node) return [];                           // nothing starts with this prefix
  }
  return node.top.map(([text]) => text);            // no walk below this node: the answer is stored
}

function countNodes(node) { let n = 1; for (const c of node.next.values()) n += countNodes(c); return n; }

const queries = [
  ["shoes", 9200], ["shorts", 4100], ["shoes red", 3100], ["shower curtain", 1800],
  ["shoulder bag", 1500], ["shoelaces", 900], ["shirt", 7000], ["sheets", 2600], ["watch", 5200],
];
const trie = buildTrie(queries, 3);
for (const p of ["s", "sh", "sho", "shoe", "shir", "wa", "x"]) console.log(p.padEnd(5), JSON.stringify(suggest(trie, p)));
console.log("nodes", countNodes(trie), "total characters", queries.reduce((n, [t]) => n + t.length, 0));
```

Run on nine made-up queries with counts (shoes 9200, shirt 7000, watch 5200, shorts 4100, shoes red 3100, sheets 2600, shower curtain 1800, shoulder bag 1500, shoelaces 900):

```text
s     ["shoes","shirt","shorts"]
sh    ["shoes","shirt","shorts"]
sho   ["shoes","shorts","shoes red"]
shoe  ["shoes","shoes red","shoelaces"]
shir  ["shirt"]
wa    ["watch"]
x     []
nodes 50 total characters 71
```

Notice that "sh" and "s" give the same three, and "sho" drops shirt, because shirt does not start with sho. The 71 characters in the nine queries needed only 50 nodes, counting the top node, because queries share their first letters.

**What it costs.** Memory. Suppose Dalil keeps the 10 million most popular queries, 20 characters each. In the worst case every character is its own node, which is 200 million nodes. Say a node holds 20 bytes of structure plus the numbers of its best 10 queries at 4 bytes each, which is 40 bytes. That is 60 bytes a node, so the worst case is about 200 million x 60 bytes = 12 GB. The picture keeps three answers so it fits on a phone; Dalil shows up to ten. Real tries share prefixes and use less, but 12 GB is a safe ceiling, and it fits in the memory of one server. All numbers here are course assumptions.

**How many servers.** One lookup takes microseconds, so the limit is the network and the web layer, not the trie. If a server handles 10,000 calls a second at most and is planned at half, 5,000, then 35,000 / 5,000 = 7 servers, and a few more to survive a zone failure. Every server holds the whole trie. A copy per server is simpler than splitting the trie, and splitting would send every call to the shard for its prefix, which creates a hot shard for the letter s.

**The alternative.** Search the main index for each prefix, with no trie. It reuses what you have and costs 280,000 shard calls a second at peak, with the budget problem of the first beat.

</GoDeeper>

## Rebuild the trie from search counts

<MermaidDiagram title="How the trie stays fresh" chart={`flowchart LR
  A["Searches"] --> B["Log queue"]
  B --> C["Counter: count per query"]
  C -->|"every 10 minutes"| D["Builder"]
  D --> E[("New trie snapshot")]
  E -->|"swap in"| F["Suggest servers"]
`} legend="Searches are logged and counted. A builder makes a new trie from the counts every ten minutes. The suggest servers swap it in. No search touches the live trie." />

Suggestions follow what shoppers searched a few minutes ago. A builder counts queries, builds a fresh trie with the best three on each node, and the servers swap it in. Reads never wait for a write, because the live trie is never changed.

<GoDeeper title="Go deeper: the trade-off between a rebuild and a live update">

**The choice.** Rebuild the trie from counts every 10 minutes and swap it in, instead of updating the live trie on every search.

**Why now.** Dalil gets about 2,300 searches a second. If each one updated the best three on every node of its path, that is about 20 node updates for each search, so about 46,000 node updates a second, while 35,000 reads a second are reading the same nodes. Those updates need locks, or careful copying, on the hottest nodes.

**What it buys.** A snapshot is read-only, so reads need no locks. The builder can be slow, check its work, drop rude or private queries, and be tested before it goes live. A bad build is not swapped in, and the old snapshot keeps serving. Rolling back is swapping back.

**What it costs.** Delay. A query that suddenly becomes popular, after a news event or a sale, takes up to 10 minutes plus build time to appear. For a shop that is acceptable. For a news site it might not be.

**The alternative.** Update counts live and keep a small separate list of trending queries that the server merges into the answer. That gives freshness in seconds for the few queries that matter, and keeps the big trie as a snapshot. Many teams end up here after the first version. **When to switch.** When product owners can show that stale suggestions lose sales.

**Counting without storing everything.** The counter needs the count of every query in a window. Storing an exact counter for every query that was ever typed is large, because most queries are typed once. Chapter 23.4 shows the count-min sketch, which counts approximately in a small, fixed memory. It is a natural fit for the box marked "Counter".

**Rules the builder applies.** Keep only queries searched at least a minimum number of times, for example by 100 different shoppers (a course rule), so one person's private search is never shown to others. Remove blocked words. Lowercase and trim the query the same way as the search analyzer (chapter 23.2).

</GoDeeper>

## Short prefixes are answered by a cache

<InteractiveCanvas slug="sysdesign-m23-prefix-cache" />

There are only 26 one-letter and 676 two-letter prefixes, and every shopper types them first. A small cache keeps all 702 answers, so those calls never reach the trie. A longer prefix is a miss and goes on to the suggest servers.

<GoDeeper title="Go deeper: the cache, the swap and the client">

This is the same cache-aside idea as chapter 5.3, with a very small, very hot set of keys. The set is tiny, so the hit rate for those prefixes is close to 100%, and the rest pass through. The caches of chapter 5.2 are placed the same way: a copy in the app, a shared cache, and an edge cache near the shopper. A CDN or edge cache can hold answers with `Cache-Control: max-age=60` [S22], so many shoppers share one answer for a minute.

The danger is staleness after a swap. If the cache holds answers from the old trie for 60 seconds while the new snapshot is live, shoppers see slightly old suggestions for a minute. That is acceptable here. If it is not, put the snapshot version in the cache key, as in the versioned keys of chapter 5.5, so a new snapshot misses the old entries.

The letter s is a hot key (chapter 5.6): thousands of shoppers a second ask for it. Each suggest server can keep the answers for the 702 shortest prefixes in its own process, which costs almost nothing.

The phone helps too. When a shopper types "sho" after "sh", the app already has the top three for "sh". It can show the ones that still match while the next call is on its way, and drop any answer that arrives for a prefix that is no longer in the box.

</GoDeeper>

## A slow suggestion is dropped

<InteractiveCanvas slug="sysdesign-m23-suggest-timeout" />

Suggestions are a convenience. If the suggest service is slow, the phone waits 100 ms, drops the call and shows no ideas. The shopper keeps typing, and the search itself works. The failure is quiet, so someone must be told about it.

<GoDeeper title="Go deeper: the failure step of the loop, block by block">

The failure step asks what a user sees when each block fails.

**Suggest servers are slow or down.** The app times out at 100 ms and shows nothing. After a few failures in a row it stops asking for 30 seconds, a circuit breaker as in chapter 16. This protects the servers while they recover, and stops every key press from waiting 100 ms. Retries must be limited, because a retry on every key press would multiply the load [S89, S91].

**The cache fails.** The suggest servers answer every call themselves. At 7 servers planned at half load, they have room for it. If the cache restarts empty, the load on the servers rises for a moment and falls again as it warms up. This is the cold cache of chapter 20.4.

**The builder fails.** Nothing breaks at once. The servers keep the last good snapshot, and suggestions get older. The risk is that nobody notices. The fix is to alert on the age of the snapshot, for example more than 30 minutes old, not on errors.

**A bad snapshot is built.** For example, it is empty, or it contains a blocked word. The servers check a new snapshot (size within a range of the last one, a few known prefixes return known answers) before the swap, and keep the old one if the check fails.

**A late answer arrives.** The shopper typed "shoes" while the answer for "sho" was still on its way. The answer carries its prefix, and the app drops it unless the prefix still matches the box.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Suggestions get their own path, because a call per key press is about 35,000 a second at peak and has a 100 ms budget that includes the network. I keep the 10 million most popular queries in a trie in memory. Each node stores its best three queries, built ahead of time, so a lookup is one step per letter and reads nothing below the node. A builder makes a new snapshot every 10 minutes from query counts and the servers swap it in. A small cache holds the 702 shortest prefixes. If suggestions fail, the app drops them after 100 ms and search still works."

**Expect:** "How do trending queries show up faster?" **Answer:** "A rebuild every 10 minutes has that delay. I would add a small live list of trending queries counted in a sketch, and merge it into the answer. The big trie stays a snapshot."
