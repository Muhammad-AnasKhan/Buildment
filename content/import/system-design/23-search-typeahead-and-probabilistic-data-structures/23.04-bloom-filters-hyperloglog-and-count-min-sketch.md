Dalil has three counting jobs that are too big to do exactly: check whether a word exists at all, count how often each query is typed, and count how many different shoppers searched today. This chapter gives each one a structure that is a little wrong and very small. It is the trade-off step of the design loop.

## A sure no skips every shard

<InteractiveCanvas slug="sysdesign-m23-typo-filter" />

Chapter 7.3 showed a Bloom filter letting a read skip files. Here the same filter holds every word in the catalogue. A typo like shoez gets a sure no, and no shard is asked. A real word gets a maybe, and the search runs as before. The filter answers no only when it is certain.

<GoDeeper title="Go deeper: where this filter sits, and whether it is worth it">

The filter lives in the coordinator, in front of the 8 shards of chapter 23.2. When all of a query's words must match (AND), one word that is not in the catalogue means no product can match. The coordinator checks each word in the filter. If any word gets a sure no, it returns an empty result at once. If every word gets a maybe, it does the normal search. A wrong maybe costs one search that finds nothing. It never gives a wrong result, because the shards still decide.

Chapter 7.3 explained how a Bloom filter works and how to read its false positive rate, so this chapter does not repeat it. What is new here is the size question and the other two structures.

**The choice.** Add a Bloom filter of all known words in front of the shards. **What it buys.** An empty answer without any shard call. Suppose one search in 20 uses a word that does not exist (a typo; an illustrative number). At the peak of 7,000 searches a second that is 350 searches, and each would have cost 8 shard calls. That saves 2,800 shard calls a second, about 5% of the 56,000 total. **What it costs.** About 125 MB of memory in each coordinator for 100 million words at 10 bits each, a nightly rebuild (a filter cannot forget a word), and one more thing to run. **The alternative.** Do nothing. Shards check their word lists in memory in microseconds, so an empty search is cheap on the shard, and only the network trip is wasted. **When to switch.** Measure the share of searches with no result. If it is low, skip the filter. It is a small win for Dalil. It becomes a big one where the "no" saves a disk read or an expensive remote call, which is the case in chapter 7.3.

</GoDeeper>

## Drag the bits and the hashes

<InteractiveCanvas slug="sysdesign-m23-bloom-size" />

Drag the bits per word, then the number of hashes. Too few hashes and a typo slips through. Too many and the row fills with ones. There is a best hash count for each size. At 10 bits per word and 7 hashes, about 1 wrong maybe in 120. For 100 million words that is 125 MB.

<GoDeeper title="Go deeper: sizing a filter from the error you can accept">

Let n be the number of words, m the number of bits and k the number of hashes. The chance of a wrong maybe is about (1 minus e to the power of minus k times n divided by m), all to the power k. The best k is about (m divided by n) times ln 2. Turn that around to size a filter for an error rate p: m = n x ln(1/p) / (ln 2)^2 bits, with k = (m / n) x ln 2 [S113]. In code:

```js
function bloomSize(n, p) {
  const bits = Math.ceil((-n * Math.log(p)) / Math.LN2 ** 2);
  const hashes = Math.max(1, Math.round((bits / n) * Math.LN2));
  return { bits, hashes };
}

console.log(bloomSize(1e8, 0.01));   // Dalil's 100 million words, 1% wrong maybes
console.log(bloomSize(1e6, 0.01));
console.log(bloomSize(1000, 0.001));
```

```text
{ bits: 958505838, hashes: 7 }
{ bits: 9585059, hashes: 7 }
{ bits: 14378, hashes: 10 }
```

The first line is about 9.6 bits per word and 7 hashes: 958,505,838 bits is about 120 MB. A rule worth remembering: about 10 bits per word gives about 1%, and every extra 5 bits cuts the error by about a factor of ten.

The picture's hash count matters, and here is the proof. This sweep used 10,000 words in a filter of 100,000 bits (10 bits per word) and tested 200,000 words that were never added. It was measured with the filter you write in chapter 23.5.

| Hashes | Wrong maybes, measured | By the formula | Bits set |
|---|---|---|---|
| 1 | 9.51% | 9.52% | 9.5% |
| 2 | 3.26% | 3.29% | 18.2% |
| 4 | 1.19% | 1.18% | 32.9% |
| 7 | 0.86% | 0.82% | 50.4% |
| 10 | 1.04% | 1.02% | 63.3% |
| 14 | 1.97% | 1.90% | 75.4% |
| 20 | 5.59% | 5.46% | 86.5% |

The error falls to a low point at 7 and then rises again. At the best hash count, about half of the bits are set. Past it, the row is too full. The measured numbers match the formula to within a fraction of a percent.

**What a Bloom filter cannot do.** It cannot remove a word, because a bit may belong to several words. It cannot list its members. It cannot say a word is present, only that it may be. It does not grow: a filter sized for 100 million words that receives 300 million has most of its bits set, and its wrong maybes climb. So size it for the words you expect, and rebuild it when you pass that. Two filters of the same size and hash count can be merged by OR-ing their bits.

**A near miss.** A Bloom filter for "has this shopper already seen this product?" is a fair use, because a wrong maybe only hides one product. The same filter for "has this payment already been taken?" is wrong, because a wrong maybe would refuse a real payment. Use it where a wrong maybe is cheap, or where a second check makes the final decision.

</GoDeeper>

## A count-min sketch counts with a small grid

<InteractiveCanvas slug="sysdesign-m23-sketch-count" />

To find the popular queries, Dalil must count how often each is typed. A count-min sketch is a small grid. Each search adds one to one cell in every row. To ask for a count, read the query's cell in every row and take the smallest. Other queries share cells, so cells only run high. The smallest is closest.

<GoDeeper title="Go deeper: the sketch in JavaScript, and how wrong it is">

A sketch has d rows of w cells. Each row has its own hash function. To add a query, hash it once per row and add to that cell. To estimate, read the same cells and take the minimum. A cell can only go up, and a query always adds to its own cells, so every cell is at least the true count. The minimum is therefore never below the truth, and it is above only when every one of its cells is shared with other queries. {/* source needed: the count-min sketch paper by Cormode and Muthukrishnan (2005) was not read for the dossier; the one-sided error here follows from the structure, as the dossier notes. */}

```js
class CountMin {
  constructor(width, depth) {
    this.width = width; this.depth = depth; this.total = 0;
    this.rows = Array.from({ length: depth }, () => new Uint32Array(width));
  }
  add(key, count = 1) {                                      // one cell in every row goes up
    for (let r = 0; r < this.depth; r++) this.rows[r][hash(key, r) % this.width] += count;
    this.total += count;
  }
  estimate(key) {                                            // the smallest of the key's cells
    let best = Infinity;
    for (let r = 0; r < this.depth; r++) best = Math.min(best, this.rows[r][hash(key, r) % this.width]);
    return best;
  }
}
```

Here `hash(key, r)` is a hash function that takes a seed, the same one you meet in chapter 23.5. We fed one million searches over 50,000 different queries, where query 0 is the most popular and query i is about 1/(i+1) as popular, into a sketch of 2,000 cells by 5 rows, which is 40,000 bytes (the stream is a few lines of seeded random numbers, left out here, and a map of exact counts sits beside the sketch to check it):

```text
distinct queries: 47421  sketch bytes: 40000
query          true  estimate  over
query-0        87659     87797   138
query-9         9004      9099    95
query-99         841       971   130
query-999         90       241   151
query-9999         8       155   147
query-40000        4        79    75
estimates below the true count: 0 of 47421
```

Look at the last column. Every estimate is above the truth by 75 to 151, and none is below. The error is about the same for popular and rare queries. That is the key point. For query 0, an error of 138 on 87,659 is 0.2%. For query 40000, an error of 75 on a true count of 4 is a count 20 times too high. A sketch is good at the top and poor at the bottom. For finding popular queries, that is what we want. Redis says the same: ignore small counts that are below the error threshold [S116].

The error depends on the width. We counted the same stream with four widths and five rows, and measured the average over-count of the queries typed five times or fewer:

| Width | Bytes | Average over-count of rare queries |
|---|---|---|
| 500 | 10,000 | 742.6 |
| 2,000 | 40,000 | 126.1 |
| 8,000 | 160,000 | 16.2 |
| 32,000 | 640,000 | 0.8 |

Wider sketches are more exact, and the cost is memory. The usual rule: the error is at most about (e / w) times the total number of events, with a chance of failing that falls as the rows grow. {/* source needed: the sizing rule w = e / epsilon and d = ln(1 / delta) from Cormode and Muthukrishnan; the dossier cites only the Redis page [S116]. */} For Dalil, with 8.3 million searches an hour on average and an error target of 0.01% of them, w = 27,183 and 5 rows, which is about 540 KB. Compare that with an exact counter for tens of millions of different queries.

**What it cannot do.** A sketch answers "how many times was X typed?" It does not list the popular queries. A real counter keeps a small list of the top candidates beside the sketch, and uses the sketch to decide who stays on it. Two sketches of the same size merge by adding their cells, so each machine can count its own share.

</GoDeeper>

## HyperLogLog counts different shoppers

<InteractiveCanvas slug="sysdesign-m23-hll-registers" />

How many different shoppers searched today? Fifty million IDs stored exactly take 400 MB. HyperLogLog hashes every ID into a few thousand small registers. Drag the registers up. At 16,384 registers, 12 KB, the answer is within about 1% of 50 million.

<GoDeeper title="Go deeper: how it counts without remembering anyone">

The idea is a coin game. Hash each shopper ID into random bits. If you flip a fair coin and see 10 heads in a row, you probably flipped many times. In the same way, if some ID's hash starts with 20 zero bits, you have probably seen about a million different IDs. One lucky ID would fool you, so HyperLogLog splits the IDs into many groups. The first bits of the hash pick a register. The register keeps the longest run of zeros seen in its group. The estimate averages all registers, in a way that damps out lucky ones. The standard error is about 1.04 divided by the square root of the number of registers m [S114].

The same ID always lands in the same register with the same run, so counting the same shopper twice changes nothing. That is why it counts different items. Redis uses at most 12 KB with a standard error of 0.81% [S115]: 16,384 registers of 6 bits is 12,288 bytes, and 1.04 / 128 = 0.8125%. The paper reports about 2% with 1.5 KB for counts above a billion [S114].

```js
class HyperLogLog {
  constructor(p) { this.p = p; this.m = 1 << p; this.registers = new Uint8Array(this.m); }
  add(item) {
    const h = hash32(item);
    const index = h >>> (32 - this.p);                       // the first p bits pick a register
    const rest = (h << this.p) >>> 0;                        // the remaining bits
    const rank = rest === 0 ? 32 - this.p + 1 : Math.clz32(rest) + 1; // position of the first 1 bit
    if (rank > this.registers[index]) this.registers[index] = rank;   // each register keeps its maximum
  }
  count() {
    const m = this.m;
    const alpha = m === 16 ? 0.673 : m === 32 ? 0.697 : m === 64 ? 0.709 : 0.7213 / (1 + 1.079 / m);
    let sum = 0, zeros = 0;
    for (const r of this.registers) { sum += 2 ** -r; if (r === 0) zeros++; }
    const raw = (alpha * m * m) / sum;                       // harmonic mean of the registers
    return raw <= 2.5 * m && zeros > 0 ? m * Math.log(m / zeros) : raw; // small counts: linear counting
  }
  merge(other) { for (let i = 0; i < this.m; i++) this.registers[i] = Math.max(this.registers[i], other.registers[i]); }
}

const N = 300_000;
for (const p of [6, 10, 12, 14]) {
  let total = 0;
  for (let trial = 0; trial < 8; trial++) {              // 8 different streams of shoppers
    const hll = new HyperLogLog(p);
    for (let i = 0; i < N; i++) hll.add("shopper-" + trial + "-" + i);
    total += Math.abs(hll.count() - N) / N;
  }
  const m = 1 << p;
  console.log(`${String(m).padStart(6)} registers, ${String(m * 6 / 8).padStart(6)} bytes: average error ${(total / 8 * 100).toFixed(2)}%  (formula 1.04 / sqrt(m) = ${(104 / Math.sqrt(m)).toFixed(2)}%)`);
}

const monday = new HyperLogLog(14), tuesday = new HyperLogLog(14);
for (let i = 0; i < 600000; i++) monday.add("u" + i);
for (let i = 300000; i < 900000; i++) tuesday.add("u" + i);   // 300,000 shoppers came on both days
monday.merge(tuesday);                                         // union: keep the larger register
console.log("two days together:", Math.round(monday.count()), "(true 900000)");
const few = new HyperLogLog(14);
for (let i = 0; i < 10; i++) few.add("x" + i);
console.log("10 shoppers:", Math.round(few.count()));
```

Here `hash32` is a 32-bit hash that mixes its bits well. We added 300,000 different shopper IDs, eight times with a different set of IDs each time, and recorded the average error for four register counts:

```text
    64 registers,     48 bytes: average error 7.42%  (formula 1.04 / sqrt(m) = 13.00%)
  1024 registers,    768 bytes: average error 3.19%  (formula 1.04 / sqrt(m) = 3.25%)
  4096 registers,   3072 bytes: average error 1.35%  (formula 1.04 / sqrt(m) = 1.63%)
 16384 registers,  12288 bytes: average error 0.81%  (formula 1.04 / sqrt(m) = 0.81%)
two days together: 910296 (true 900000)
10 shoppers: 10
```

The formula is the typical error, and a single run can be above or below it. The constants in the code are standard for large counts, and at tiny sizes such as 64 registers the real error is rough. Each step of 4 times more registers halves the error.

The line "two days together" is the useful trick. Monday's and Tuesday's registers merge by taking the larger value in each register, and the merged sketch counts the union. 300,000 shoppers came on both days, and they are counted once: 910,296 against a true 900,000. You cannot get this from two plain counters. A small set, such as 10 shoppers, is counted exactly by a built-in correction.

**What it cannot do.** It cannot list who the shoppers were. It cannot tell you whether one shopper is in the set. It cannot subtract. The error is relative, so 0.8% of 50 million is about 400,000, which is fine for a dashboard and wrong for billing.

</GoDeeper>

## Which structure answers which question

<MermaidDiagram title="Choosing a structure" chart={`flowchart TD
  Q{"What do you need to know?"}
  Q -->|"Is X in the set?"| B["Bloom filter: sure no, or maybe"]
  Q -->|"How many times did X happen?"| C["Count-min sketch: too high, never too low"]
  Q -->|"How many different items?"| H["HyperLogLog: within about 1%"]
  Q -->|"The exact answer, or money"| E["Keep exact data"]
`} legend="Each structure answers one question with a small, known kind of error. If a wrong answer costs money, keep the exact data." />

Each structure answers one question, with a known kind of error. A Bloom filter says no for sure or maybe. A sketch never counts too low. HyperLogLog is within about a percent. All three can be merged, so each machine can build its own and a coordinator combines them. When a wrong answer costs money, keep exact data.

<GoDeeper title="Go deeper: the trade-off, and where else they are used">

**The choice.** Use an approximate structure when memory is the limit and a small, bounded error is acceptable. **Why now.** At Dalil's size the exact versions are large: 400 MB of IDs for one day of distinct shoppers, and counters for tens of millions of queries, and the numbers multiply when you want them per hour, per category and per region. **What it buys.** Fixed memory, in kilobytes or a few hundred megabytes, however many items arrive, plus fast updates and the ability to merge across machines. **What it costs.** An error you must understand, explain and test. A wrong maybe, a count that is too high, a distinct count that is off by 1%. Nobody can look up a single record in them. **The alternative.** Exact structures: a hash set, a hash map, a database table. They are simple and exact, and they grow with the data. **When to switch.** When the memory is affordable, or when a wrong answer costs more than the memory saves: payments, stock, permissions, legal counts.

Merging is what makes these fit distributed systems. The two filters with the same size merge with OR. Two sketches merge by adding cells. Two HyperLogLogs merge by taking the larger register. A search shard can build its own structure and the coordinator can combine them without moving the raw data.

You will see them in real tools. RocksDB uses Bloom filters to skip files (chapter 7.3). Redis has built-in Bloom filter, count-min sketch and HyperLogLog types [S115, S116]. Check the documentation of your version before relying on one.

The sketch and filter feed the Dalil design like this. The sketch, in the counter box of chapter 23.3, finds popular queries for the trie. The filter guards the shards. HyperLogLog counts distinct shoppers and queries on the dashboard.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "When memory is the constraint and a small error is fine, I use a probabilistic structure. A Bloom filter answers 'is it in the set?' with no false negatives. Size it with m = n ln(1/p) / (ln 2) squared bits and k = (m/n) ln 2 hashes: about 10 bits per item for 1%. A count-min sketch counts frequencies in fixed memory and only overcounts, so it finds heavy hitters well and rare items badly. HyperLogLog counts distinct items in about 12 KB with under 1% error, and merges by taking the max of registers. I would not use any of them where a wrong answer costs money."

**Expect:** "Can you delete from a Bloom filter?" **Answer:** "Not a plain one, because bits are shared. You rebuild it, or use a variant such as a counting Bloom filter that stores small counters instead of bits, at several times the memory."

</GoDeeper>
