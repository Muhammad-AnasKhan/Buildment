Dalil has 200 million products, and a shopper types "red waterproof shoes". This chapter is the sketch and the first deep dive of the design loop: how a search system finds the matching products, puts the best first, spreads over many machines, and stays fresh.

## Reading every product takes seconds

<InteractiveCanvas slug="sysdesign-m23-scan-vs-index" />

Scanning all 200 GB of product text takes about 10 seconds for one query, even at memory speed. Dalil must answer in a fraction of a second, thousands of times a second. The fix is the index at the back of a book: for each word, a list of the places it appears. Dalil's index keeps, for each word, a list of products.

<GoDeeper title="Go deeper: why a scan cannot be made fast enough">

The arithmetic uses the numbers from chapter 23.1 and the memory speed from napkin-math: reading 1 MB in order from memory takes about 50 microseconds [S3]. The text is 200 GB, which is 200,000 MB, so one full scan takes 200,000 x 50 microseconds = 10 seconds on one thread. From a fast SSD, at about 100 microseconds for each MB, it takes 20 seconds. The source says some of its numbers are 2 to 3 times off, so read these as shapes, not benchmarks.

You can split a scan over many threads or machines, but that only divides the time. The total work for each query stays at 200 GB. At the peak of 7,000 searches a second, a scan design would read 7,000 x 200 GB = 1.4 PB of text every second. No cluster of a sensible size does that.

An index changes the question. Instead of asking every product "do you contain red?", it asks one list "which products contain red?". The work for a query is the length of the lists it reads, not the size of the catalogue. Lucene, the library under many search engines, stores exactly this: a term dictionary of every word, and for each word a list of the documents that contain it [S100]. Lucene calls the word list the term dictionary and each document list a posting list.

</GoDeeper>

## Build an index from three documents

<InteractiveCanvas slug="sysdesign-m23-tiny-index" />

Step through three products: split each into words, then flip the table so each word points to its products. Tap the words red, waterproof and shoe and watch their lists. The flipped table is an <GlossaryTerm term="inverted index" definition="A table that maps each word to the list of documents that contain it. It is 'inverted' because a normal table maps each document to its words." />.

<GoDeeper title="Go deeper: the whole tiny index in JavaScript">

This is about 15 lines. It splits text into terms, then records, for each term, which products contain it and how many times. The next beats add the search and the ranking.

```js
function tokenize(text) {
  return text
    .toLowerCase()                          // one case: "Shoes" and "shoes" match
    .split(/[^a-z0-9]+/)                    // split on anything that is not a letter or digit
    .filter(Boolean)                        // drop empty pieces
    .map((w) => (w.length > 3 && w.endsWith("s") ? w.slice(0, -1) : w)); // crude plural stripping
}

function buildIndex(docs) {
  const postings = new Map();               // term -> Map(product id -> times it appears)
  for (const [id, text] of Object.entries(docs)) {
    for (const term of tokenize(text)) {
      if (!postings.has(term)) postings.set(term, new Map());
      const list = postings.get(term);
      list.set(Number(id), (list.get(Number(id)) ?? 0) + 1);
    }
  }
  return { postings, docCount: Object.keys(docs).length };
}

const docs = { 1: "Red running shoes", 2: "Blue running shorts", 3: "Red waterproof hiking shoes" };
const index = buildIndex(docs);
for (const [term, list] of [...index.postings].sort()) console.log(term.padEnd(11), JSON.stringify([...list.keys()]));
```

Output, run on Node.js 22:

```text
blue        [2]
hiking      [3]
red         [1,3]
running     [1,2]
shoe        [1,3]
short       [2]
waterproof  [3]
```

Read the table by word. Red is in products 1 and 3. Waterproof is only in product 3. The lists are kept sorted by product number, which makes them cheap to combine. Real engines store them compressed, as the gaps between numbers, and keep the word table in a structure that fits in memory.

How big is Dalil's index? Each of the 200 million products has about 100 different words, so there are 20 billion entries. At 4 bytes for one entry (the product number and a count, compressed), that is 80 GB. Both numbers are course assumptions, and real sizes vary with the language and the compression. The takeaway is that the index is smaller than the text, but still too big and too busy for one machine.

</GoDeeper>

## Tokenizing decides what matches

<MermaidDiagram title="From text to terms" chart={`flowchart LR
  T["Running Shoes!"] --> L["1. Lower case"]
  L --> S["2. Split on spaces and punctuation"]
  S --> P["3. Strip plurals"]
  P --> R["running, shoe"]
  Q["Query: shoes"] -.->|"same steps"| L
`} legend="The product text and the shopper's query go through the same steps. Both end as the terms the index stores." />

Before a word enters the index, it is cleaned: one case, no punctuation, plurals removed. So "Shoes!" finds "shoe". The rule that bites is simple: the query must use exactly the same steps as the index, or words that look equal will not match.

<GoDeeper title="Go deeper: what each step buys and costs">

The pipeline above is a tokenizer. A real one is called an analyzer, and each step is a choice with a price.

Lower casing is almost free and almost always right. Splitting on punctuation turns "hiking-shoes" into two terms, which helps a shopper who types "hiking shoes" and hurts one who wants the exact brand "Hi-King". Plural stripping, a simple form of stemming, helps recall: a shopper who types "shoes" finds products that say "shoe". It also causes mistakes. Run on "this", the one-line rule above returns "thi". Real stemmers are smarter, and they still make mistakes.

```js
console.log(tokenize("Running Shoes!"));
console.log(tokenize("  Red, WATERPROOF hiking-shoes (size 42) "));
console.log(tokenize("this"), tokenize("bus"));
```

```text
[ 'running', 'shoe' ]
[ 'red', 'waterproof', 'hiking', 'shoe', 'size', '42' ]
[ 'thi' ] [ 'bus' ]
```

Two more choices. A stop word list drops very common words such as "the" so the index is smaller, but it makes a phrase like "to be or not to be" hard to find. Synonyms map "sneakers" to "shoe" so a shopper finds products the seller named differently. Synonyms are usually applied on the query, because a change to the list then needs no re-index.

The near miss is the one that hurts in production. Suppose the index lowercases but the query path does not. A shopper types "Shoes" and finds nothing, and every test with lower case input passes. This happens often after a team changes the index rules and forgets that a re-index is needed. The fix is to make one analyzer definition and use it on both sides, and to re-index when the definition changes.

Other languages need other rules. A tokenizer for English splits on spaces. Some writing systems have no spaces between words, and Arabic has letter forms that a good analyzer folds together. Dalil is English only (chapter 23.1) because each language adds its own analyzer and tests.

</GoDeeper>

## Two words, two lists, one intersection

<InteractiveCanvas slug="sysdesign-m23-intersect" />

A shopper wants products that contain all three words. The index reads the shortest list first. Waterproof names one product. Only that product is then checked against the lists for red and shoe. The work depends on the rarest word, not on the commonest.

<GoDeeper title="Go deeper: merging lists, and skipping ahead">

Combining two sorted lists of product numbers is a short loop with two pointers. Look at the front of each list. If they match, keep that number. Otherwise move forward in the list that is behind. This costs about the sum of the two lengths.

When one list is tiny and the other is huge, that is wasteful. Suppose "shoe" is in 1,000,000 products and a rare word is in 1,000 (illustrative numbers). The better plan looks up each of the 1,000 numbers in the long list by halving the range each time (a binary search). Real engines store skip pointers so they can jump through a long list in the same spirit. Both plans are in this code, with a step counter:

```js
function mergeIntersect(a, b) {                 // walk both lists together
  const out = [];
  let i = 0, j = 0, steps = 0;
  while (i < a.length && j < b.length) {
    steps++;
    if (a[i] === b[j]) { out.push(a[i]); i++; j++; }
    else if (a[i] < b[j]) i++;
    else j++;
  }
  return { out, steps };
}

function skipIntersect(short, long) {           // look each short id up in the long list
  const out = [];
  let steps = 0;
  for (const id of short) {
    let lo = 0, hi = long.length - 1;           // binary search: halve the range each step
    while (lo <= hi) {
      steps++;
      const mid = (lo + hi) >> 1;
      if (long[mid] === id) { out.push(id); break; }
      if (long[mid] < id) lo = mid + 1; else hi = mid - 1;
    }
  }
  return { out, steps };
}

const common = Array.from({ length: 1_000_000 }, (_, k) => k * 3);   // a word in 1,000,000 products
const rare = Array.from({ length: 1_000 }, (_, k) => k * 3000);      // a word in 1,000 products
console.log("merge steps:", mergeIntersect(rare, common).steps);
console.log("skip steps: ", skipIntersect(rare, common).steps);
```

Run on a rare list of 1,000 numbers against a common list of 1,000,000 numbers:

```text
merge steps: 999001
skip steps:  18986
```

The skip plan does about 50 times less work. The lesson is the same as in the picture: order the words by list length, shortest first, and let the short list drive.

An "all of these words" query (AND) is the cheapest kind, because the shortest list limits the work. An "any of these words" query (OR) must read every list in full and score every product that matches any word. Shoppers usually expect AND, with ranking to sort out the rest.

## Rare words count more

<InteractiveCanvas slug="sysdesign-m23-rare-words" />

Many products match "red shoes". Which goes first? A word in few products tells you more than a word in most products. Red is in 2 of 3 products and adds 0.4. Waterproof is in 1 of 3 and adds 1.1. Product 3 has the rare word, so it wins.

<GoDeeper title="Go deeper: the weight is called idf, and the score is tf-idf">

The weight in the picture is called the inverse document frequency, idf. For a word that is in df of N products, idf = ln(N / df). With N = 3, red has ln(3/2) = 0.405, shoe has 0.405, and waterproof has ln(3/1) = 1.099. The score of a product is the sum, over the query words it contains, of the number of times the word appears in it (the term frequency, tf) times the idf. This is called tf-idf.

```js
function rank(index, query) {
  const scores = new Map();
  for (const term of tokenize(query)) {
    const list = index.postings.get(term);
    if (!list) continue;
    const idf = Math.log(index.docCount / list.size);   // rare terms weigh more
    for (const [id, tf] of list) scores.set(id, (scores.get(id) ?? 0) + tf * idf);
  }
  return [...scores].sort((a, b) => b[1] - a[1]);
}

const show = (q) => rank(index, q).map(([id, s]) => id + ":" + s.toFixed(3)).join("  ");
console.log(show("red waterproof shoes"));
console.log(show("red shoes"));
```

Run on the three products, with the `tokenize` and `buildIndex` code from the earlier fold. Each item is a product number, a colon and its score, best first:

```text
3:1.910  1:0.811
1:0.811  3:0.811
```

For "red waterproof shoes", product 3 scores 0.405 + 1.099 + 0.405 = 1.910 and product 1 scores 0.811. For "red shoes" the two products tie at 0.811, so tf-idf alone cannot order them. Ties are normal, and they are where other signals decide.

Real engines use a refinement of this idea. The usual one is called BM25. It stops a word that repeats 50 times from scoring 50 times as much, and it takes the length of the text into account, so a match in a short title counts for more than a match in a long description. {/* source needed: BM25 definition and its use as the default similarity in Lucene-based engines, from the Lucene or Elasticsearch documentation. */}

A marketplace adds signals that are not about words at all: sales in the last week, ratings, stock, price, and how well the product title matches the query exactly. A common design scores cheaply across all matches, then re-ranks only the top few hundred with a slower, better model. {/* source needed: a first-party description of two-stage ranking. */} Ranking quality is a field of its own. The point for system design is where the work happens: scoring runs inside each shard, on the products that shard holds.

</GoDeeper>

## Shards hold slices; copies share the load

<MermaidDiagram title="Dalil search at a glance" chart={`flowchart LR
  subgraph W["Write path"]
    P[("Product database")] -->|"changes"| I["Indexer"]
    I --> S1["Shard 1"]
    I --> S8["Shard 8"]
  end
  subgraph R["Read path"]
    C["Shopper"] -->|"red waterproof shoes"| G["Coordinator"]
    G -->|"1. ask one copy of each shard"| S1
    G -->|"1."| S8
    S1 -->|"2. best 10"| G
    S8 -->|"2. best 10"| G
    G -->|"3. merge, best 10"| C
  end
`} legend="Changes flow from the product database through an indexer into the shards. A search is sent to one copy of every shard, and the coordinator merges the best ten from each." />

The 80 GB index is cut into 8 shards of about 10 GB, by product number. A search goes to one copy of every shard. Each shard returns its best ten, and the coordinator keeps the best ten of all. This is scatter-gather, as in chapter 9.6.

<GoDeeper title="Go deeper: shards, copies, the slow shard and deep pages">

This is the sketch step of the loop, and it uses chapter 9.6 directly. A search index is a local index: each shard indexes the products it holds, so any query must visit every shard. The other choice, a global index split by word, would send a query to only the shards that hold its words, but a write would then touch many shards, and a multi-word query would ship long lists between machines. Search engines pick the local index because queries are far more common than writes and because it keeps ranking inside one shard.

Shards and copies do two different jobs. Shards cut the size: 80 GB in 8 shards is 10 GB each, which fits in memory on a node. Copies cut the load. At the peak, 7,000 searches a second each reach every shard. If one copy of a shard is planned at 1,000 shard queries a second (a course number, half of an assumed maximum of 2,000), each shard needs 7 copies, so 8 x 7 = 56 nodes. Adding load means adding copies, as the first quiz at the end of this chapter shows. Adding data means adding shards, and that is a hard change, because the products must be re-spread by chapter 9.5.

Scatter-gather has a cost in the tail. A search finishes when the slowest shard answers. Suppose each shard is slow, in its own p99, in 1 of 100 queries. With 8 shards, the chance that at least one is slow is 1 - 0.99^8 = 7.7%, so about 1 search in 13 is as slow as a shard's worst 1%. With 100 shards it would be 63% [S8]. This is why a search engine does not use hundreds of tiny shards when a few bigger ones will do. Sending the request to a second copy if the first is slow (a hedged request) trims the tail [S8].

Deep pages are the other trap. To show page 1, each shard sends its best 10. To show page 100, which starts at result 991, each shard must send its best 1,000, and the coordinator merges 8,000 candidates to keep 10. Page depth multiplies the work, so most search products limit how deep a shopper can go.

Merging is correct because of one fact. A product that belongs in the best ten of all must also be in the best ten of its own shard. So no shard has to send more than ten, as long as the scores mean the same thing on every shard. Idf depends on counts, and each shard counts only its own products, so scores can differ slightly between shards. With millions of products in each shard the difference is small.

</GoDeeper>

## A saved product shows up later

<InteractiveCanvas slug="sysdesign-m23-refresh-lag" />

The new product waits in a buffer. The shopper searches and sees nothing. After the next refresh, the same search finds it. The product database is up to date at once. The search index is up to date a moment later. Dalil allows 30 seconds.

<GoDeeper title="Go deeper: segments, refresh and what the seller sees">

A search index is built from small immutable files called segments. A new product is added to an in-memory buffer. At each refresh, the buffer is turned into a new small segment that searches can read, and only then can a search find the product. Segments are never edited. An edit is a delete mark on the old version plus a new copy in a new segment, and a background job merges small segments into big ones, much like compaction in the LSM tree of chapter 7.3. {/* source needed: the default refresh interval and the near-real-time model in the Elasticsearch or Lucene documentation. */}

The refresh interval is a dial. A short interval, such as one second, makes products appear fast but creates many tiny segments and more merging work. A long one saves work and makes shoppers wait. Dalil allows 30 seconds, so a refresh every few seconds meets it with room. During a burst of 174 changes a second, the buffer simply grows between refreshes.

Two things can go wrong. First, each copy of a shard refreshes on its own timer, so two shoppers can briefly see different results, like the replication lag of chapter 8.4. Second, a seller who saves and then searches for the product expects to see it. The fix is the one from chapter 8.4: show the seller their product from the database response, not from the index, for the first minute.

The index is rebuilt from the product database. If a shard is lost, a new copy is built from another copy, or from the database. Because the database is the source of truth, a stale or lost index is a slow recovery, not lost data.

</GoDeeper>
