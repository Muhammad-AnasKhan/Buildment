```quiz
type: mcq
question: "After a release, a shopper who types 'Shoes' gets no results, but 'shoes' works. The index lowercases all text. The release removed lower casing from the query path. What is the right fix?"
options:
  - "Add two more copies of every shard"
  - "Re-index all products with capital letters"
  - "Run queries through the index analyzer"
  - "Make the refresh interval much shorter"
correct: 2
explanations:
  - "Copies add capacity, not matches. Every copy holds the same lower case terms, so 'Shoes' still finds nothing on all of them."
  - "That moves the problem to lower case queries and costs a full re-index. The two sides still use different rules."
  - "Right. The query and the index must apply the same steps, so one analyzer definition serves both. Then 'Shoes' becomes 'shoe' on both sides."
  - "Refresh decides how soon new products appear. The products are already in the index, and the terms do not match."
```

```quiz
type: mcq
question: "A shop has 4 products. 'Cotton' is in 1 of them and 'shirt' is in 2. A shopper searches 'cotton shirt'. Product A has both words and product B has only 'shirt'. Weights are ln(4 / products with the word), one occurrence each. How does A's score compare with B's?"
options:
  - "About 3 times as much"
  - "About 2 times as much"
  - "The same score"
  - "About 1.5 times as much"
correct: 0
explanations:
  - "Right. Cotton weighs ln 4 = 1.39 and shirt weighs ln 2 = 0.69. A scores 1.39 + 0.69 = 2.08 and B scores 0.69, which is 3 times as much."
  - "That counts words, 2 against 1. It ignores that the rare word, cotton, weighs twice as much as the common one, shirt."
  - "Both contain shirt, but only A contains cotton. The rare word adds 1.39 to A's score, so the scores differ."
  - "That would be the case if cotton and shirt weighed the same. Cotton is in fewer products, so it weighs more."
```

```quiz
type: mcq
question: "A search is sent to 16 shards, and a search finishes when the last shard answers. Each shard is slower than its own p99 on 1 query in 100, independently. About what share of searches wait for at least one slow shard?"
options:
  - "About 1%"
  - "About 50%"
  - "About 63%"
  - "About 15%"
correct: 3
explanations:
  - "One percent is the chance for a single shard. With 16 shards there are 16 chances for one to be slow."
  - "Half would need about 69 shards. At 16 shards the chance is still far below that."
  - "That is the figure for 100 shards (1 - 0.99^100). With 16 shards it is much lower."
  - "Right. The chance that all 16 are fast is 0.99^16 = 0.85, so the chance that at least one is slow is about 15%."
```

```quiz
type: mcq
question: "Dalil rebuilds its suggestion trie every 10 minutes. A news event makes a new query very popular, and the product owner wants it suggested within a minute. Which change fits best?"
options:
  - "Rebuild the whole trie every second"
  - "Merge a small live list of trending queries"
  - "Give every suggest server a second trie copy"
  - "Cache every prefix for a full hour"
correct: 1
explanations:
  - "A rebuild reads every count and builds millions of nodes. Doing that every second would swamp the builder, to fix a few queries."
  - "Right. A small live list, counted in a sketch, is cheap and fresh. The big snapshot stays read-only and is merged with the list at lookup."
  - "A second copy adds capacity. It holds the same old data, so the new query is still missing."
  - "A longer cache makes suggestions older, not fresher. The new query would appear even later."
```

```quiz
type: mcq
question: "A payments team wants to avoid charging an order twice. They keep a Bloom filter of paid order IDs and skip the charge when it says 'maybe'. What is wrong with this plan?"
options:
  - "A Bloom filter cannot hold order ID strings"
  - "A Bloom filter says no for IDs that were added"
  - "A wrong maybe would skip a charge that is due"
  - "A Bloom filter needs a database to answer"
correct: 2
explanations:
  - "A Bloom filter can hold any string, because it only hashes it. The type of the key is not the problem."
  - "That never happens. An added ID always finds all its bits set. The error goes the other way."
  - "Right. A maybe can be wrong, so some real orders would be marked as paid and never charged. Money needs an exact check, such as a unique key."
  - "A Bloom filter answers from its own bits and needs no database. That is why it is cheap."
```
