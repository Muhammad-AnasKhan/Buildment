```quiz
type: mcq
question: "A clinic booking app (fictional) has this line in its requirements: 'Patient data must stay on servers inside the country.' What kind of requirement is it, and why does it matter for the design?"
options:
  - "A functional requirement: it is something users do"
  - "A non-functional requirement about speed and load"
  - "A preference the team may drop if it is costly"
  - "A constraint: it rules out some hosting choices"
correct: 3
explanations:
  - "No patient performs this action. It limits where the system may run, which makes it a constraint."
  - "It says nothing about how fast or how much. It fixes where data may live, whatever the speed."
  - "A rule about where data may live usually comes from law or policy. The team cannot drop it to save money."
  - "Right. It is a fixed limit on the solution. Any provider or region outside the country is ruled out before the design starts."
```

```quiz
type: mcq
question: "A ticket site (fictional) sells the 5,000 seats of one concert hall once a year. Sales open at 10:00, and about 100,000 fans try to buy in the first minute. The rest of the year, traffic is tiny. Which number should drive the design?"
options:
  - "The 5,000 seats in the hall"
  - "About 1,700 tries a second at opening"
  - "The average request rate over the year"
  - "The 100,000 fans with accounts"
correct: 1
explanations:
  - "The seat count matters for correctness (never sell one seat twice), but it is not what loads the servers at 10:00."
  - "Right. 100,000 tries in 60 seconds is about 1,700 a second, all at once. The system must survive that minute, so it drives the design."
  - "The yearly average is close to zero and hides the one minute that matters. Size for the peak you must survive."
  - "Accounts do not load a server; requests in the same second do. The fans matter because they all arrive in one minute."
```

```quiz
type: mcq
question: "Daftar's app servers each save uploaded PDFs on their own local disk. There are two app servers behind a load balancer that takes turns. What goes wrong?"
options:
  - "Another server answers and the PDF is not there"
  - "The load balancer stops accepting any uploads"
  - "The CDN serves an old copy of every PDF"
  - "The database soon runs out of room for note titles"
correct: 0
explanations:
  - "Right. The servers are not stateless. A student who uploads to App 1 may be sent to App 2 next time, and App 2 has no copy. Files belong in object storage that every server can reach."
  - "The load balancer does not look at where files are kept. It keeps sending requests; some of them just reach the wrong disk."
  - "The CDN only holds copies of what it fetched. The problem is that half the app servers cannot find the original file."
  - "The database stores titles and file names, which are small. The PDFs on local disks are the problem, not the database."
```

```quiz
type: mcq
question: "A team estimates its new internal tool at about 3 requests a second and 5 GB of data. One engineer wants to start with a cache, a queue and a database split across three servers 'so it scales'. What does the design loop suggest?"
options:
  - "Build all of it now, since adding parts later is hard"
  - "Add the cache only, since caches are always worth it"
  - "Start with one database; write down when to add parts"
  - "Skip the estimate and ask users how fast it should feel"
correct: 2
explanations:
  - "Every part has a cost: money, time to run it, and new ways to fail. At 3 requests a second they buy nothing yet."
  - "A cache helps when reads are heavy. At 3 requests a second the database is nearly idle, and the cache only adds stale copies."
  - "Right. The estimate says the system is small. Keep the design simple, and write down the number at which each extra part would be worth adding."
  - "Asking users is part of clarifying, but the estimate is what shows the system is small. Skipping it is how teams overbuild."
```

```quiz
type: mcq
question: "PasteBox runs two app servers behind a load balancer, and one PostgreSQL database. The database server's disk fails. What do users see, and what is the first fix on the next time round the loop?"
options:
  - "Nothing, because the second app server takes over"
  - "Only new pastes fail; reads still come from the app"
  - "Some reads fail; add a third app server for safety"
  - "Every request fails; add backups and a standby"
correct: 3
explanations:
  - "The second app server covers a crashed app server, not a lost database. Both app servers need the same database."
  - "The app servers are stateless. They keep no pastes, so reads fail too."
  - "Every read and write needs the database, so every request fails. More app servers do not help."
  - "Right. The single database is a single point of failure. Backups protect the data, and a standby copy on a second machine can take over quickly."
```
