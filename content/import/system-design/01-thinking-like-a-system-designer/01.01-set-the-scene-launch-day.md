Hana and Omar built Daftar, an app where university students share class notes (a fictional app). It runs on one rented server. A week before exams, a post about it reaches a student group with 10,000 members.

## One server, more students every minute

<InteractiveCanvas slug="sysdesign-m1-launch-day" />

Drag across the picture to change how many students are online. Start at 100: the server is 5% busy and a page takes about 10 ms. Now drag to 1,000, then 1,800. The crowd grows less than 2 times, but each page gets 5 times slower, and a line forms. Past 2,000, requests arrive faster than the server finishes them: the line grows and pages time out.

<GoDeeper title="Go deeper: where these numbers come from">

The picture uses made-up numbers for a fictional app, chosen so the arithmetic is easy. Each student with the app open sends one request every 20 seconds, or 0.05 requests a second. The server needs 10 ms of work for one request, so it can finish at most 100 requests a second. The share of time the server is working is called its <GlossaryTerm term="utilisation" definition="The share of time a server is busy: the rate requests arrive divided by the rate it can finish them. 50% means it is working half of the time." />. With these numbers, utilisation is the number of students times 0.05, divided by 100.

| Students online | Requests a second | Utilisation | Time per request |
|---|---|---|---|
| 100 | 5 | 5% | about 10.5 ms |
| 1,000 | 50 | 50% | 20 ms |
| 1,800 | 90 | 90% | 100 ms |
| 10,000 | 500 | 500% | grows without end |

The time per request comes from a simple queueing model called M/M/1. It says the average time a request spends in the system is the work time divided by one minus the utilisation: 10 ms / (1 - 0.5) = 20 ms at 50%, and 10 ms / (1 - 0.9) = 100 ms at 90%. The extra time is waiting in line behind other requests. The same model says how long that line is on average: utilisation / (1 - utilisation) requests, so 1 at 50% and 9 at 90%. The dots in front of the server in the picture show that number, and each dot in the lane stands for many requests. Real servers do not follow this model exactly, because real requests do not arrive or finish in such a regular random pattern. The model is still useful for one lesson: the curve is flat for a long time, then bends up sharply as utilisation nears 100%. You will measure that bend on your own laptop in module 2.

Marc Brooker of AWS puts the same idea in numbers: at 50% utilisation, a simple queue holds 1 request on average; at 99%, it holds 99. That is why slow pages are the first warning of overload. The server has not failed yet, but every request is waiting.

Past 100%, there is no steady state at all. At 10,000 students, 500 requests arrive each second and only 100 finish, so the line grows by 400 every second. After one minute, 24,000 requests are waiting. At 10 ms each, the last one would wait 4 minutes, and the student's browser gives up long before that. That is a <GlossaryTerm term="timeout" definition="A limit on how long a client waits for an answer. When it passes, the client stops waiting and reports an error, even if the server would have answered later." />. Some students press reload, which adds more requests to the same queue. Module 16 shows how retries like that can keep a system down after the first spike has passed.

</GoDeeper>

## Everything lives on one machine

<MermaidDiagram title="Daftar on launch day" chart={`flowchart LR
  S["Students' phones"] -->|every request| App
  subgraph Server["One rented server"]
    App["App code"] --> DB[("Database")]
    App --> Files["Uploaded PDFs"]

`} legend="One box holds the app, the database and the files. If that box is overloaded or stops, every part of Daftar stops with it." />

Daftar's code, its database and every uploaded PDF share that one server. When it is overloaded, everything is slow at once. If it crashes, nothing works. A part whose failure stops the whole system is a single point of failure.

<GoDeeper title="Go deeper: why one server is a fine place to start">

One server is not a mistake. For a new app with a few hundred users, it is cheap, simple to run and easy to debug. The problem is not the single box. The problem is not knowing where its limits are, and having no plan for the day you reach them.

There are two broad ways out, and you have probably heard of both. You can buy a bigger server, which is called scaling up. That is quick, but a bigger machine still has a ceiling, and it is still one box that can fail. Or you can run several servers and spread the work across them, which is called scaling out. That has no fixed ceiling, but it needs new parts: something to spread the requests, and a place for the data that every server can reach. Module 4 compares the two with numbers.

This module does not ask you to choose yet. It gives you the method first. Chapter 1.2 turns "lots of students" into requirements and numbers. Chapter 1.3 names the building blocks that big systems are made from. Chapter 1.4 walks through the steps a designer follows, on a small example. You will then set up the repository where you run real experiments for the rest of the course.

</GoDeeper>
