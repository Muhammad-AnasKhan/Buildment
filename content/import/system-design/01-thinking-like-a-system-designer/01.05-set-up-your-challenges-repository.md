## What you will have at the end

This course does not stop at pictures. In most modules you run a small system on your own laptop, measure it, break it on purpose and write down what happened. All of that work lives in one place: a public GitHub repository called `system-design-challenges` that you create today. By the end of the course it holds 19 challenges, each with code, tests, measured results and charts, which is real evidence of what you can do.

At the end of this chapter, your repository has a `toolkit/` folder for shared code and a `challenges/` folder with challenge 0. Challenge 0 has two parts, and each part has its own `README.md`. Part 1 checks that the right version of Node.js runs your code and your tests. Part 2 checks that Docker can start a container. Your tests pass on your laptop, and they also pass on GitHub's machines every time you push, shown by a green tick next to each commit.

**What you need.** A laptop running Windows 10 or 11, macOS or Linux, Git, and a GitHub account. You already know Git and the command line from the entry requirements. Plan for about an hour, plus download time. You will download two installers, Node.js and Docker. Their sizes change with each release, so check the size on each download page first if your data is limited or expensive. If your connection is weak today, do part 1 now and part 2 when the connection is better; nothing in part 1 needs Docker.

## How the pieces fit

The picture shows the path every change takes from now on. You write code and a test on your laptop and run the test there. When it passes, you push to GitHub. GitHub Actions, GitHub's built-in automation service, then starts a fresh machine, installs Node.js 24, and runs the same tests again. This is called continuous integration, or CI.

<MermaidDiagram title="From your laptop to a green tick" chart={`flowchart LR
  L["Your laptop: write code and tests"] -->|npm test| P{"Pass?"}
  P -->|no| L
  P -->|yes| G["git push to GitHub"]

Notice the clean machine in the middle. Your laptop has things installed that a stranger's laptop does not, and it is easy to write code that only works on yours. CI catches that, because the GitHub machine has nothing except what your repository tells it to install. Your mentor also sees the green tick or the red cross on every commit, without running anything.

## The layout

Every challenge in this course uses the same folder shape. Learning it once means you always know where things are, and so does your mentor.

```text
system-design-challenges/
  README.md                         what this repository is, and how to run it
  package.json                      Node.js settings and the test command
  .gitignore                        files Git must not track
  .github/
    workflows/
      tests.yml                     the CI job
  toolkit/
    env.js                          shared code: checks the Node.js version
  challenges/
    challenge-0-repository-setup/
      README.md                     a short glossary, then one line per part
      part-1-toolkit-check/
        README.md                   the 101: the idea from zero
        check.js                    the script you run
        check.test.js               the test
        results.md                  what you saw when you ran it
      part-2-docker-check/
        README.md                   the 101: the idea from zero
        results.md                  what Docker printed
```

The naming rule is `challenges/challenge-N-short-name/part-N-short-name/`, with lower-case words joined by hyphens. Each part folder holds a `README.md` that teaches the idea from zero (the 101), one script, its test and a `results.md` file with your real results. The challenge folder has its own `README.md` with a short glossary and one line per part. From challenge 1, parts that measure something also hold a `chart.svg`. Code that more than one challenge needs, such as the load generator in module 2, goes in `toolkit/`, so you write it once.

## Build it

<Steps title="Create the repository and pass the first test">
<Step title="Install Node.js 24" stepNumber="1">

This course uses Node.js 24, a long-term support (LTS) version. According to the Node.js release schedule (checked on 23 October 2026), Node 24 receives fixes until 30 April 2028, so it lasts for the whole course. Node 22 reaches end of life on 30 April 2027, during the course, so do not use it.

**Windows.** Open the Node.js download page at `https://nodejs.org/en/download`, choose version 24, Windows, and the Windows Installer (`.msi`). Run it and accept the defaults. Then close PowerShell and open a new window, so it finds the new `node` command.

**macOS and Linux.** Use nvm, the Node Version Manager, so you can switch versions later without `sudo`. In a terminal:

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash
# close the terminal and open a new one, then:
nvm install 24
nvm alias default 24
```

The nvm version in the link changes over time; the nvm README shows the newest one. On macOS you may instead use the macOS installer (`.pkg`) from the same Node.js download page.

On every system, check the result:

```text
> node --version
v24.x.y
> npm --version
(any version number)
```

The first line must start with `v24`. The other numbers will differ, and that is fine.

</Step>
<Step title="Create the repository on GitHub and clone it" stepNumber="2">

On GitHub, choose **New repository**. Name it exactly `system-design-challenges`, set it to **Public**, tick **Add a README file**, and create it. Then copy its HTTPS address and clone it. Replace `YOUR-USERNAME` with your GitHub user name:

```bash
git clone https://github.com/YOUR-USERNAME/system-design-challenges.git
cd system-design-challenges
```

The same two commands work in PowerShell, macOS Terminal and Linux. Every command from here on runs inside this folder.

</Step>
<Step title="Create the folders and the project files" stepNumber="3">

Create the folders. On macOS or Linux:

```bash
mkdir -p toolkit .github/workflows \
  challenges/challenge-0-repository-setup/part-1-toolkit-check \
  challenges/challenge-0-repository-setup/part-2-docker-check
```

In PowerShell on Windows:

```powershell
New-Item -ItemType Directory -Force -Path toolkit, .github/workflows, challenges/challenge-0-repository-setup/part-1-toolkit-check, challenges/challenge-0-repository-setup/part-2-docker-check
```

Now open the folder in your editor and create `package.json` in the top folder:

```json
{
  "name": "system-design-challenges",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "engines": { "node": ">=24" },
  "scripts": {
    "test": "node --test"
  }
}
```

`"type": "module"` lets you use `import` and `export` in `.js` files. `"test": "node --test"` uses the test runner built into Node.js, so you install nothing: when you run it with no file names, it finds every file whose name ends in `.test.js` and runs it.

Create `.gitignore` with one line, `node_modules/`. You have no packages yet, but later challenges will, and that folder must never be committed.

</Step>
<Step title="Write the test, then the toolkit function" stepNumber="4">

Write the test first. It says exactly what the toolkit must do. Create `challenges/challenge-0-repository-setup/part-1-toolkit-check/check.test.js` and copy this in:

```js
import { test } from "node:test";
import assert from "node:assert/strict";
import { checkNode, nodeMajor } from "../../../toolkit/env.js";

test("reads the major version from a version string", () => {
  assert.equal(nodeMajor("24.11.0"), 24);
  assert.equal(nodeMajor("v26.0.1"), 26);
});

test("throws on a string that is not a version", () => {
  assert.throws(() => nodeMajor("latest"));
});

test("rejects a version below the minimum", () => {
  assert.deepEqual(checkNode(24, "22.21.0"), { ok: false, major: 22, min: 24 });
});

test("this machine runs Node 24 or newer", () => {
  const result = checkNode();
  assert.ok(result.ok, `Node ${result.major} is too old: install Node ${result.min}`);
});
```

Now write `toolkit/env.js` yourself. It exports two functions:

```js
// toolkit/env.js
export function nodeMajor(version) {
  // "24.11.0" or "v24.11.0" -> 24
  // anything that does not start with a number -> throw an Error
}

export function checkNode(min = 24, version = process.versions.node) {
  // -> { ok: true or false, major: <number>, min: <number> }
}
```

`process.versions.node` is the running version without the `v`, for example `"24.11.0"`. Three hints, each one a decision rather than the code: remove one leading `v` before you split; the major version is the part before the first dot; and `Number("latest")` gives `NaN`, which `Number.isInteger` rejects, so that is your signal to throw. `checkNode` should call `nodeMajor`, not repeat its work.

Last, create `check.js` in the same part folder. This is the script a person runs to see the result in words:

```js
import { checkNode } from "../../../toolkit/env.js";

const result = checkNode();
console.log(`Node ${process.versions.node}: ${result.ok ? "OK" : "too old"} (need ${result.min} or newer)`);
process.exitCode = result.ok ? 0 : 1;
```

</Step>
<Step title="Run the tests and the script" stepNumber="5">

From the top folder of the repository, run the tests:

```text
> npm test
✔ reads the major version from a version string (0.69ms)
✔ throws on a string that is not a version (0.19ms)
✔ rejects a version below the minimum (0.58ms)
✔ this machine runs Node 24 or newer (0.12ms)
ℹ tests 4
ℹ suites 0
ℹ pass 4
ℹ fail 0
ℹ cancelled 0
ℹ skipped 0
ℹ todo 0
ℹ duration_ms 84.48
```

Your times will differ; `pass 4` and `fail 0` are what matter. If the output instead has lines starting with `ok 1 -`, that is the same result printed in another format, which Node uses when the output is not a terminal. Then run the script:

```text
> node challenges/challenge-0-repository-setup/part-1-toolkit-check/check.js
Node 24.11.0: OK (need 24 or newer)
```

</Step>
<Step title="Add the CI workflow and push" stepNumber="6">

Create `.github/workflows/tests.yml`:

```yaml
name: tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 24
      - run: node --version
      - run: npm test
```

Read it from the top: on every push and pull request, start a fresh Ubuntu machine, copy the repository onto it, install Node.js 24, print the version, and run your tests. There is no `npm install` step, because the project has no packages yet. Commit and push:

```bash
git add .
git commit -m "Set up challenge 0 with a Node version check and CI"
git push
```

Open your repository on GitHub and choose the **Actions** tab. Within a minute or two, the `tests` run should finish with a green tick. Open it and look at the `npm test` step: it shows the same four passing tests.

</Step>
<Step title="Install Docker and run hello-world" stepNumber="7">

From module 2 on, challenges run databases, caches and queues in containers, so Docker must work. A container is a program packaged with everything it needs, started from a file called an image.

**Windows and macOS.** Install Docker Desktop from `https://docs.docker.com/desktop/`, choosing the version for your system (on a Mac, Apple silicon or Intel). On Windows, the installer uses WSL 2, the Windows Subsystem for Linux, and offers to set it up if it is missing. Start Docker Desktop and wait until it says the engine is running.

**Linux.** Install Docker Engine by following the page for your distribution at `https://docs.docker.com/engine/install/`. Then let your user run Docker without `sudo`, and log out and back in so it takes effect:

```bash
sudo usermod -aG docker $USER
```

Then, on every system:

```text
> docker --version
Docker version (any recent version)
> docker run hello-world
...
Hello from Docker!
This message shows that your installation appears to be working correctly.
...
```

The first run downloads the small `hello-world` image, so it takes a moment. Docker Desktop uses a lot of memory while it runs. On a laptop with little memory, quit it when you are not working on a challenge.

</Step>
<Step title="Write the results and the READMEs, then push" stepNumber="8">

In `part-1-toolkit-check/results.md`, paste the output of `node --version`, the script's line, and the `pass` and `fail` lines from `npm test`. In `part-2-docker-check/results.md`, paste the output of `docker --version` and the two lines that start with "Hello from Docker!". Add one sentence to each saying where you ran it, for example "Windows 11 laptop, PowerShell".

Give each part folder a short `README.md` that teaches its idea from zero, in your own words: what the part checks, the command to run it, and a link to its `results.md`. Then write `challenges/challenge-0-repository-setup/README.md`. Start with a short 101 glossary in your own words: Node.js, npm, test runner, CI, container and image, one line each. Then give one line per part with the command to run it and a link to its folder. Replace the top `README.md` with two or three sentences on what this repository is, the command `npm test`, and a list of challenges that you will extend in each module. Commit and push, and check that the tick is still green.

</Step>
</Steps>

## Verify, including one failure on purpose

A passing test only means something if you have seen it fail. Break CI on purpose. In `.github/workflows/tests.yml`, change `node-version: 24` to `node-version: 22`, then commit and push. The run on the Actions tab now ends with a red cross. Open the `npm test` step and you will see the fourth test fail with a message like this:

```text
✖ this machine runs Node 24 or newer (0.96ms)
  AssertionError [ERR_ASSERTION]: Node 22 is too old: install Node 24
ℹ tests 4
ℹ pass 3
ℹ fail 1
```

That is your test doing its job: the machine had the wrong version, and the test said so in plain words. Change the line back to `24`, push again, and watch the tick turn green.

Then break your own code once. In `toolkit/env.js`, make `checkNode` always return `ok: true`. Run `npm test`: the test "rejects a version below the minimum" fails, because the toolkit now waves through Node 22. Undo the change and run the tests again. This is the habit for the whole course: every test you write, you should have seen fail at least once.

## When it does not work

**"node is not recognized" or "command not found: node".** The terminal was opened before Node.js was installed, so it does not know the new command yet. Close every terminal window and open a new one. With nvm, run `nvm use 24` and check that `nvm alias default 24` was run.

**In PowerShell, "npm.ps1 cannot be loaded because running scripts is disabled".** Windows blocks the small script that starts npm. Run `npm.cmd test` instead, which avoids the script, or run the command from the classic Command Prompt. Changing PowerShell's execution policy also works, but it is a security setting, so only do it if you understand what it allows.

**"Cannot use import statement outside a module".** `package.json` is missing `"type": "module"`, or the file is not in the top folder. Check the spelling and the place.

**`npm test` runs zero tests.** The test file name must end in `.test.js`. A file called `check-test.js` or `check.tests.js` is not found. Also check that you ran the command from the top folder.

**"Cannot find module .../toolkit/env.js".** Count the `../` steps: from the part folder, it is three levels up to the top folder. Also check that the file is called `env.js`, not `env.js.txt`; Windows sometimes hides the second ending.

**The Actions tab shows nothing.** The workflow file must be exactly at `.github/workflows/tests.yml`. A folder called `.github/workflow` or `github/workflows`, without the dot, is ignored.

**Docker: "Cannot connect to the Docker daemon" or "error during connect".** Docker Desktop is not running. Start it and wait until the engine is running. On Linux, start the service with `sudo systemctl start docker`. **"permission denied" on Linux** means you have not logged out and back in after the `usermod` command.
