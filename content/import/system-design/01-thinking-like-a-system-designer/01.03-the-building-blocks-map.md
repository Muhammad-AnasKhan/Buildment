A request from a student's phone to Daftar passes through several kinds of building blocks. Each block exists to solve one problem. Follow the requests through them in four groups, from the edge of the internet to the data.

## The edge: DNS and the CDN

<InteractiveCanvas slug="sysdesign-m1-edge-blocks" />

First the phone needs Daftar's address. DNS turns the name daftar.app into an IP address, and the phone keeps that answer for a while. Then it asks for the logo. A CDN, a network of servers spread around the world, already holds a copy near the student and answers without touching Daftar's own servers.

<GoDeeper title="Go deeper: DNS and CDNs, how they work and fail">

**DNS.** The Domain Name System is a worldwide directory of names. Your phone asks a nearby resolver, which either answers from memory or asks other name servers on your behalf. Every answer carries a <GlossaryTerm term="TTL" definition="Time to live: how many seconds a stored copy of an answer may be used before checking again. A TTL of 0 means do not store it at all." /> that says how long it may be kept. A long TTL means fewer lookups but slow changes: if Daftar moves to a new address, some phones keep using the old one until their copy expires. AWS load balancers use a TTL of 60 seconds for their names, so their addresses can change quickly. The address in the picture, 203.0.113.7, comes from a range kept for examples.

DNS is easy to forget because it usually just works, but it is a dependency like any other. On 19 and 20 October 2025, a race in the automation that manages DynamoDB's DNS records in AWS's us-east-1 Region left a regional name with no addresses at all. Services that depended on that name failed, and some took hours to recover after DNS was fixed.

**CDN.** A content delivery network keeps copies of responses on servers close to users. It decides how long a copy stays fresh from the `Cache-Control` header your server sends. `max-age=86400` means "fresh for one day". `no-cache` surprises many people: it allows storing, but the copy must be checked with your server before each use. `no-store` is the one that forbids storing. CDNs suit files that many people fetch and that rarely change: the logo, the app's scripts, and perhaps popular PDFs.

The main failure mode is a stale copy. If Hana changes the logo but the file keeps the same name, students see the old one until it expires. Two fixes exist: ask the CDN to delete its copies (an invalidation), or give each version a new file name, such as `logo.v2.png`, so the old copy is never asked for again.

**In AWS.** DNS is Amazon Route 53, which can also send users to the closest or the healthy copy of a service. The CDN is Amazon CloudFront, which offers both invalidation and versioned file names.

</GoDeeper>

## The front door: gateway and load balancer

<InteractiveCanvas slug="sysdesign-m1-front-door" />

Requests for Daftar's own data reach the front door. The gateway checks who is calling and how often. A script sending hundreds of requests a second gets 429, Too Many Requests. The balancer then spreads the accepted requests across the app servers, here by taking turns. Neither does Daftar's real work. They protect and share out the servers that do.

<GoDeeper title="Go deeper: what the front door decides">

**The gateway.** An API gateway is one place for the checks every request needs before it touches your code: is this caller allowed, and is it sending too much? Rate limits are often built as a token bucket: each caller has a bucket that refills at a steady rate, and each request takes one token, so short bursts pass but a flood is refused. Stripe, for example, runs its rate limiters as token buckets stored in Redis. The right answer to a caller over its limit is 429 Too Many Requests, defined in RFC 6585. Some tools answer 503 by default: nginx's rate limiter does, unless you set `limit_req_status 429`. Module 6 builds a rate limiter.

**The load balancer.** It picks one server for each request. Taking turns is called round robin. Better rules exist, such as "least requests": pick 2 servers at random and send the request to the one with fewer requests in progress. Load balancers work at one of two levels. A layer 7 balancer reads each HTTP request and can route by its path. A layer 4 balancer only sees network connections, and keeps every request on one connection on the same server. Module 4 compares the rules with real measurements.

A load balancer also runs health checks: small requests to each server every few seconds. A server that stops answering is taken out of the rotation. Chapter 1.4 shows this happening.

Two failure modes matter here. If the gateway or load balancer is one machine, it is a new single point of failure, so managed load balancers run on several machines behind one name. And a health check that is too strict can remove healthy servers: if every server reports "sick" because one shared dependency is slow, the balancer may take them all out together.

**In AWS.** The gateway is Amazon API Gateway, which throttles with a token bucket and returns 429. The load balancer is Elastic Load Balancing: an Application Load Balancer works at layer 7 and uses round robin by default, and a Network Load Balancer works at layer 4.

</GoDeeper>

## Compute: app servers and workers

<InteractiveCanvas slug="sysdesign-m1-compute-blocks" />

The app server does the work a student waits for: it saves the PDF and replies "saved" at once. The slow part, making a preview, goes to a worker, a program that takes jobs and runs them in the background. The student carries on. If previews pile up, you add more workers, and uploads stay fast.

<GoDeeper title="Go deeper: stateless servers and background jobs">

**Stateless app servers.** An app server should keep nothing on its own disk or in its own memory that another server would need: no uploaded files, no session data that only it knows. Everything that must last goes to the data blocks in the next picture. Then any server can answer any request, the load balancer can send each request anywhere, and you can add a server at the exam peak or replace a broken one without losing anything. That is what makes scaling out possible. The cost is that every request now reaches across the network for its data, which is slower than reading from local memory.

**Workers.** Typical worker jobs are previews and thumbnails, emails, reports and anything that calls a slow outside service. Three rules keep them safe. First, the job waits in a queue, not in the app server's memory, so it survives a crash. Second, a job may run twice: most queues deliver each job at least once, and a worker that crashes halfway leaves the job to be picked up again. So every job must be safe to repeat, which is called being <GlossaryTerm term="idempotent" definition="Safe to repeat: doing it twice has the same effect as doing it once. Making preview 42 twice is idempotent; sending the same email twice is not." />. Third, measure how many jobs are waiting. A growing queue means you need more workers, or that something downstream is broken.

**In AWS.** Both app servers and workers can run on Amazon EC2 instances, which are virtual machines. Workers often read their jobs from Amazon SQS, the Simple Queue Service. When a worker takes a job, SQS hides it from other workers for a time called the visibility timeout, 30 seconds by default. If the worker does not delete the job before then, SQS shows it again, and another worker runs it.

</GoDeeper>

## Data: cache, database, files, queue

<InteractiveCanvas slug="sysdesign-m1-data-blocks" />

One page view touches four homes for data. The cache keeps fast copies and may lose them at any time. The database holds the truth: every note's title, owner and course. Object storage holds big files like PDFs. The queue holds jobs until a worker takes them. Each one is good at one job and poor at the others.

<GoDeeper title="Go deeper: why four homes, not one">

**Cache.** The picture shows the most common pattern, called cache-aside or lazy loading: look in the cache, and on a miss read the database and keep a copy. A miss costs three trips instead of one, and a copy can go out of date when the note changes. Two habits help. Give every copy a TTL, so a stale copy cannot live forever. And when a note changes, delete its cached copy instead of updating it: Facebook's engineers chose delete because deletes are safe to repeat, while two updates racing each other can leave the older value in the cache. Never keep the only copy of anything in a cache. It may throw data away whenever it runs out of memory.

**Database.** The database is the source of truth. It checks rules on every write, such as "every note has an owner", and it can change several rows together or not at all. It is also the hardest block to scale, because every app server depends on it. Modules 7 to 9 are about this block: transactions, copies called replicas, and splitting data across machines.

**Object storage.** Object storage keeps files of any size under a name, and you fetch a whole file by that name. Each request is slower than a database query: rough 2026 measurements put a 128 KiB read from object storage at about 80 ms, against about 0.5 ms for a simple query to Redis or MySQL. So the database stores a note's title and the file's name, and object storage stores the PDF.

**Queue.** A queue holds messages between a producer and a consumer, so they do not have to run at the same speed or at the same time. Most queues deliver each message at least once, so the consumer must handle repeats, as the compute fold explained. Modules 14 and 15 go further.

**In AWS.** The cache is Amazon ElastiCache. The database is Amazon RDS or Aurora for SQL, or DynamoDB for a key-value store. Object storage is Amazon S3. The queue is Amazon SQS.

</GoDeeper>

## The whole map, one request at a time

<InteractiveCanvas slug="sysdesign-m1-block-map" />

Tap any block. The path a request takes to reach it lights up, and the panel says what the block does, how it fails and its AWS name. Then press Break it. Start with the cache: Daftar still works, but every read lands on the database. Then try DNS. Many large systems are these same blocks, arranged differently.

<GoDeeper title="Go deeper: every block on one page">

The phone talks to three things on the public internet: DNS, the CDN and the gateway. Everything behind the gateway sits on a private network that students cannot reach directly. The map in the picture leaves that boundary out; this one shows it.

| Block | Its job | A common way it fails | In AWS |
|---|---|---|---|
| DNS | Turns a name into an address | Old answers kept until the TTL ends; a missing record takes everything down | Route 53 |
| CDN | Serves copies near users | Serves a stale copy after a change | CloudFront |
| Gateway | Checks callers and limits their rate | Limits set too low block real users | API Gateway |
| Load balancer | Spreads requests over servers | Health checks remove healthy servers | Elastic Load Balancing (ALB, NLB) |
| App server | Runs the request's logic | Overloads at the peak; keeps state it should not | EC2 |
| Worker | Runs slow jobs in the background | Runs a job twice; falls behind | EC2, fed by SQS |
| Cache | Holds fast copies | Stale copies; many misses at once hit the database | ElastiCache |
| Database | Holds the truth | Becomes the bottleneck everyone waits for | RDS, Aurora, DynamoDB |
| Object storage | Holds big files | Slow per request if used for small hot data | S3 |
| Queue | Holds work for later | Grows without end when consumers fall behind | SQS |

Managed services are not the only choice. Every block has open-source software you can run yourself, and you will run several of them in your challenges with Docker: nginx or Envoy as a load balancer, Valkey (open source, BSD licence) as a cache, PostgreSQL as a database, and Kafka-compatible brokers as queues. Running them yourself costs your time; a managed service costs money and ties you to one provider. Module 18 discusses that trade-off.

</GoDeeper>
