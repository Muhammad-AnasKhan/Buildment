Daftar needs 500 requests a second in exam week. Hana can buy one big server or several small ones. On a price list they can cost the same. This chapter shows what else differs: the ceiling, the damage one failure does, and the price of a spare.

## A bigger server, until there is none

<InteractiveCanvas slug="sysdesign-m4-scale-up-ceiling" />

Traffic grows from 100 to 400 requests a second, and the team swaps in a bigger size. It works. Then traffic reaches 1,000, and the biggest size on the list does only 800. Scaling up is simple, but it stops at the largest machine anyone sells you.

<GoDeeper title="Go deeper: what scaling up gives and what it costs">

<GlossaryTerm term="Scaling up" definition="Also called vertical scaling: making one machine bigger (more CPU cores, more memory, a faster disk) so it can do more work. The opposite of scaling out." /> means moving to a bigger machine. <GlossaryTerm term="Scaling out" definition="Also called horizontal scaling: running more copies of the same service on more machines, with something in front that spreads the requests across them." /> means adding more machines of the same kind.

Scaling up is often the right first move. The code does not change. There is one process to watch, one set of logs, and no question of which server a user's request reached. Many apps never outgrow one well-sized machine, and running one is cheaper in people's time than running a fleet.

It has three costs. The first is the ceiling you just saw: a machine family has a largest size, and past it there is nothing to buy. The second is that every change of size is a restart, so growing is itself an outage. The third is less obvious: a bigger machine does not always do proportionally more work. A Node.js process runs your JavaScript on one thread, so an eight-core machine running one Node process uses mostly one core. To use the other seven you must run several processes on it, which is already a small step toward scaling out.

The sizes and prices in this chapter are a made-up price list, not any provider's. In it, price grows in step with size: small does 100 requests a second for $0.10 an hour, medium 200 for $0.20, large 400 for $0.40 and xlarge 800 for $0.80. Real price lists change, differ by region, and are not always this tidy. Use the made-up list to see the shape of the decision, not to price a real system.

## One failure: all, or one eighth

<InteractiveCanvas slug="sysdesign-m4-blast-radius" />

Both designs have 800 requests a second of capacity. One machine fails in each. The big server's students all get errors. The eight small servers lose one eighth, 12.5%, and the seven left still carry everyone. The share one failure takes out is called the blast radius, and more, smaller machines make it smaller.

<GoDeeper title="Go deeper: blast radius and independent failures">

The <GlossaryTerm term="blast radius" definition="How much of a system, or how many users, one failure takes out. One server out of eight has a blast radius of one eighth of the capacity." /> of a failure is how much it takes down with it. With N equal servers, one failure takes out 1/N of the capacity. With one server, N is 1, and the answer is everything.

This only works if the servers fail separately. Eight virtual machines that sit on the same physical host, share one power supply, or all received the same bad update at the same minute can fail together, and then they are one failure domain again. Chapter 2.6 called this the independence assumption behind parallel availability. Cloud providers let you spread machines over separate zones for exactly this reason (module 19).

There is a second, quieter benefit: you can now change the system without an outage. With eight servers, you can restart them one or two at a time for an update while the rest carry the load. That is a rolling update. Kubernetes, for example, by default lets at most 25% of a deployment's pods be unavailable during a rolling update and starts at most 25% extra. With one server, every update is a restart of everything.

The cost is that you now need something in front to spread the requests, and the app must work no matter which copy a request reaches. The last beat of this chapter and the rest of the module are about exactly that.

</GoDeeper>

## Plan for one server down

<InteractiveCanvas slug="sysdesign-m4-n-plus-one" />

Five servers carry 400 requests a second at 80% busy. One fails, and the four left must each take 100 a second: they are full, and the line grows. Count capacity with one server already gone. That rule is called N+1: if N servers carry the peak, run one more.

<GoDeeper title="Go deeper: sizing with N+1">

<GlossaryTerm term="N+1" definition="A sizing rule: if N servers are needed to carry the peak load, run N + 1, so the system still carries the peak after any one server fails." /> turns a vague wish ("survive a failure") into arithmetic. Work it in three steps.

First, decide how busy a server may get. Chapter 2.5 showed the wait grows sharply near 100%, so pick a ceiling such as 80%. Second, find N, the servers needed at peak under that ceiling: peak divided by (capacity per server times the ceiling), rounded up. Third, add one.

For Daftar's 400 requests a second on small servers of 100 each with an 80% ceiling: 400 / (100 x 0.8) = 5, so N is 5 and N+1 is 6. With 6 servers, normal load is 400 / 600, about 67% each. Lose one and 5 carry it at 80%, the ceiling you chose. The scene's fleet of 5 had no spare: losing one put 4 servers at 100%, past the knee, where requests wait without limit.

Why only one spare? Because two servers failing at the same moment is much rarer than one, if they fail independently. Teams that run across several zones often size for losing a whole zone instead: with three zones, each zone must be able to go while the other two carry the peak. That is the same idea with a bigger "one".

N+1 is also why scaling out is cheaper than it first looks. The spare is one server out of N+1. With 2 big servers, the spare is half the fleet. With 8 small ones, it is one eighth. You will see that in the next beat.

</GoDeeper>

## Pick sizes and counts yourself

<InteractiveCanvas slug="sysdesign-m4-instance-picker" />

Daftar needs 500 requests a second. Tap a size, then drag the number of servers. Watch three numbers: capacity, cost an hour, and how busy the rest would be if one server fails. Find the cheapest fleet that still carries 500 a second with one server gone. Notice which size wins, and why the spare costs less when servers are small.

<GoDeeper title="Go deeper: the cheapest fleet that survives a failure">

With the made-up price list and an 80% ceiling after a failure, the cheapest surviving fleets of small, medium and large servers look like this, with one xlarge for contrast. Each fleet also pays for a load balancer, which this picture prices at a made-up $0.05 an hour.

| Fleet | Capacity | Busy at 500/s | After one fails | Cost per hour |
|---|---|---|---|---|
| 8 small | 800 | 63% | 700, 71% busy | $0.85 |
| 5 medium | 1,000 | 50% | 800, 63% busy | $1.05 |
| 3 large | 1,200 | 42% | 800, 63% busy | $1.25 |
| 1 xlarge | 800 | 63% | 0, down | $0.80 |

The single xlarge is the cheapest line in the table and the only one that goes down with one failure. Among the fleets that survive, the small servers win because the spare is small: one small server is $0.10 of spare, one large server is $0.40. Prices grow in step with size here, so the whole difference comes from how much capacity you must hold back.

Smaller is not always better. Every server has a fixed overhead: the operating system, the app's own memory, connections to the database. A hundred tiny servers each holding a pool of 10 database connections open 1,000 connections, which may be more than the database can serve well (chapter 2.5 used Little's law on exactly that pool). More servers also mean more to watch and more places for a rare bug to show up. Teams usually settle on a size that keeps a fleet between a handful and a few dozen machines, and grow the count, not the size.

</GoDeeper>

## More servers need a front door

<MermaidDiagram title="What scaling out adds" chart={`flowchart LR
  U["Students"] --> LB["Load balancer (new): one address, spreads requests, skips dead servers"]
  LB --> A["App 1"]
  LB --> B["App 2"]
  LB --> C["App 3"]
  A & B & C --> SS["Session store (new): state that was in app memory"]
  A & B & C --> DB["Database (unchanged)"]
`} legend="Scaling out adds two parts that one server never needed: a load balancer in front and a shared place for state behind." />

One server needed neither box marked "new". Many servers need both. Students need one address, so a load balancer sits in front. And any server may get any request, so nothing a user needs can live in one server's memory. The next three chapters build these parts.

<GoDeeper title="Go deeper: the trade-off in one table">

| | Scale up (one bigger machine) | Scale out (more machines) |
|---|---|---|
| Ceiling | The largest size on the list | Far higher; the next limit is usually the database |
| One failure | Takes out everything | Takes out 1/N |
| Updates | A restart is an outage | Roll through servers a few at a time |
| Extra parts | None | Load balancer, shared state, a way to deploy to many |
| Spare for N+1 | A whole second machine | One small machine |
| Simplicity | One process, one log | Many processes; a request may land anywhere |

The decision is not either-or for long. Most systems do both: pick a sensible machine size, then scale out by count. The database usually scales up much longer than the app tier, because copying data safely is hard (modules 8 and 9).

**When to stay on one machine.** A low-traffic internal tool, a prototype, or a batch job that can be rerun after a crash may be better on one machine with a tested backup. The question to ask is not "can it scale?" but "what does one hour of downtime cost, and what does the extra machinery cost?"

**In AWS.** Machines are EC2 instances, sold in families with sizes from small to very large. The load balancer is Elastic Load Balancing, and a group of identical instances that grows and shrinks is an Auto Scaling group (chapter 4.6).
