A <GlossaryTerm term="load balancer" definition="A server that sits in front of several copies of a service, gives clients one address, and passes each connection or request to one of the copies." /> gives Daftar one address and spreads the work over its app servers. But "spreads" hides two different machines, and one setting that decides how long users see errors when a server dies.

## L4 picks once per connection

<InteractiveCanvas slug="sysdesign-m4-l4-connection" />

This balancer works at layer 4, the TCP connection. When the phone opens a connection, it hashes the addresses and ports and picks App 2. It never reads the requests inside, so all three go to App 2 while App 1 and App 3 sit idle. One choice per connection.

<GoDeeper title="Go deeper: what a layer 4 balancer sees">

"Layer 4" and "layer 7" come from the layers of network protocols. Layer 4 is the transport layer, TCP or UDP. A layer 4 balancer sees addresses, ports and packets. It does not read the HTTP request inside, so it does not know the path, the cookies or where one request ends and the next begins.

So it decides once, when a connection opens. AWS's Network Load Balancer, for example, picks a target for each TCP connection with a flow hash over the protocol, the source and destination addresses and ports, and the TCP sequence number, and then keeps that whole connection on that target. Every request the client sends on that connection goes to the same server.

That makes layer 4 fast and simple: it can pass packets along without understanding them, and it works for any protocol on top of TCP, such as a database protocol or a game protocol, not only HTTP. It also means balance depends on connections being short and many. Thousands of phones, each with its own connection, spread well. A few long, busy connections do not: a server that got a busy connection keeps it. HTTP/2 makes this sharper, because one connection carries many requests at once (chapter 3.4).

When does layer 4 make sense? When the traffic is not HTTP, when you need the lowest overhead, or when the app must see the client's own TCP connection, for example to end encryption itself.

</GoDeeper>

## L7 picks for every request

<InteractiveCanvas slug="sysdesign-m4-l7-request" />

This balancer works at layer 7, HTTP. It reads each request, so it can choose again every time: App 1, then App 2, in turn. It can also read the path, so POST /upload follows a rule to the upload servers. More choice and more control, at the cost of more work per request.

<GoDeeper title="Go deeper: what a layer 7 balancer sees, and what it costs">

A layer 7 balancer ends the client's connection itself, reads each HTTP request, and opens its own connections to the servers behind it. Because it sees every request, it can make a new choice for each one and use what is inside. AWS's Application Load Balancer, for example, evaluates its listener rules for each request and, by default, chooses among the matching targets with round robin.

That opens up useful rules: send `/upload` to servers with large disks, send `/api/v2` to the new version for a test, set a sticky-session cookie (chapter 4.3), add a header that tells the app the client's real address, or answer a health check for the whole site. It is also where encryption usually ends: to read the path, the balancer must decrypt the request, so it holds the TLS certificate.

The cost is work and delay. Reading and rewriting every request is more work than passing packets, and there are now two connections where there was one. One proxy hop costs about 50 microseconds, small next to a page but not zero, and the balancer itself must be scaled for the whole site's request rate.

**Spreading across zones.** A balancer usually runs in several zones and can send traffic only to its own zone's servers or to all of them. With 2 servers in zone A and 8 in zone B, sending across zones gives each server 10% of the traffic. Keeping traffic in its zone gives each zone half, so the 2 servers in A get 25% each and the 8 in B get 6.25% each. The servers in A do four times the work of those in B, so uneven zones need cross-zone balancing or equal counts per zone.

**The balancer's own address.** Clients find the balancer through DNS. Elastic Load Balancing's DNS records use a 60-second TTL so the balancer's own nodes can change address quickly (chapter 3.3 covers TTLs).

</GoDeeper>

## Health checks take a sick server out

<InteractiveCanvas slug="sysdesign-m4-health-check" />

The balancer asks each server "are you healthy?" every 10 seconds. App 2 crashes. Check one fails, then two, and requests sent to App 2 meanwhile fail. After the third failed check, App 2 is out, and App 1 and App 3 each go from a third to half of the work. The interval and count set how long users see errors.

<GoDeeper title="Go deeper: interval, threshold and what a check should test">

A <GlossaryTerm term="health check" definition="A small request the load balancer sends to each server on a schedule, such as GET /health. A server that fails enough checks in a row is taken out of rotation until it passes again." /> has two main settings. The interval is how often the balancer asks. The threshold is how many failures in a row remove a server, and usually a second threshold sets how many passes bring it back. The time to remove a dead server is up to interval times threshold: 10 seconds times 3 is 30 seconds in the picture. These are example settings, not any product's defaults.

Why not check every second and remove after one failure? Because a single failed check is often not a dead server. A server that is very busy may answer the check late. A network blip may drop one packet. Removing a server on one failure turns small hiccups into lost capacity, which pushes more work onto the others, which makes them answer late too. A short interval with a threshold of two or three failures is the middle ground this chapter uses.

What should `/health` test? The AWS Builders' Library names three kinds of check. A liveness check only proves the process answers. A local health check tests what this server needs on its own: it can write to its disk, its threads are not stuck. A dependency health check also tests the database or other services it calls. The last kind sounds safest and is the most dangerous, as the last beat of this chapter shows.

Kubernetes splits the same idea in two. A readiness probe decides whether a container should get traffic right now. A liveness probe decides whether to restart it. A server warming its cache is alive but not ready. A server that is stuck forever needs a restart, not just a break from traffic.

A health check also does not catch every failure. A server that answers `/health` with 200 but returns errors on real pages looks healthy. That is why teams also watch the error rate of real requests.

</GoDeeper>

## Fail a backend, watch the load shift

<InteractiveCanvas slug="sysdesign-m4-failover-play" />

Three servers share Daftar's traffic. Tap a server to fail it, and watch its share move to the others once the checks remove it. Count the failed requests before that happens, then switch to a shorter check interval and fail it again. Now fail a second server, and see what the last one must carry.

<GoDeeper title="Go deeper: errors before removal, load after it">

Two numbers describe a failover. The first is how many requests fail before the balancer removes the dead server. That is the dead server's share of traffic times the time to detect it. With 180 requests a second over three servers, the dead one was getting 60 a second. Removed after 30 seconds, that is about 1,800 failed requests. Checking every 2 seconds with the same threshold of 3 cuts it to 6 seconds, about 360 failures.

Many balancers and clients shrink this further by retrying a failed request on another server at once. A request that failed because its server was dead is usually safe to try again if it only reads data. A request that changes data, such as "pay", is only safe to retry if it is idempotent, which module 6 covers.

The second number is the load on the servers that are left. After one of three fails, two carry 180 a second, 90 each. If each can do 100 a second, they are 90% busy: past the knee from chapter 2.5, so waits grow a lot even though nothing has failed yet. After two fail, one server gets all 180 and falls over. This is chapter 4.2's N+1 rule from the balancer's side: the servers that are left must have room for the one that died.

In challenge 3 you will measure both numbers on your own load balancer: the errors per second while a dead backend is still in rotation, and the p99 once the others take its share.

</GoDeeper>

## Deep checks can fail every server

<InteractiveCanvas slug="sysdesign-m4-deep-check" />

Each server's health check also pings the database. The database slows down for a few seconds. Every check times out at the same moment, so every server looks sick, and the balancer has nobody left. A careful balancer then fails open: it sends traffic to all of them anyway, because some answer is better than none.

<GoDeeper title="Go deeper: fail open, and an outage made worse by health checks">

The danger of a dependency check is that the dependency is shared. The database is the same for every server, so when it is slow, every server fails its check together. The balancer would then remove the whole fleet because of a problem that removing app servers cannot fix. A soft dependency, one the app could partly work without, has become a hard one for the whole site.

The AWS Builders' Library gives two defences. First, prefer local health checks for removing servers from rotation, and watch dependencies some other way. Second, make the balancer <GlossaryTerm term="fail open" definition="When every server fails its health check at once, the load balancer stops trusting the checks and sends traffic to all servers, instead of to none." />: if every server fails its check at once, assume the check is wrong and keep sending traffic to all of them. The Builders' Library describes load balancers that work this way.

A real outage shows how health checks can make things worse. On 19 and 20 October 2025, a race in the automation that manages DNS records for DynamoDB in AWS's us-east-1 Region left its regional endpoint with no addresses. Services that depended on it failed. For hours afterwards, as backlogs cleared, EC2 launches and Network Load Balancer health checks also failed, and churn in health checks removed capacity. Among AWS's follow-ups was a limit on how fast health checks may remove capacity.

The lesson is the same at every scale: a check that removes servers is a powerful lever, so it needs a limit. Removing one server in ten because it is sick is good. Removing nine in ten at once is almost never the right answer, whatever the checks say.

</GoDeeper>
