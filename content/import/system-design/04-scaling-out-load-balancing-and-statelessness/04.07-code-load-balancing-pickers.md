Every load balancer, whatever its brand, has one small function at its heart: given the list of servers, which one gets this request? In chapter 4.5 you watched three answers to that question. In this chapter you write them. They are short, but each has a detail that is easy to get wrong, and a wrong picker fails quietly: requests still flow, just to the wrong place.

By the end, you will have three tested functions. `createRoundRobin()` returns a picker that takes turns and skips servers marked unhealthy. `leastConnections(servers)` returns the healthy server with the fewest requests in flight. `twoChoices(servers, random)` draws two different healthy servers and returns the less busy one. In challenge 3, next chapter, you paste all three into your own load balancer and measure them on real traffic.

## The shape of a server, and the shared rules

All three pickers receive the same thing: an array of server objects, in a fixed order. Each object has at least a `name`, an `active` count (the requests in flight on it right now) and a `healthy` flag. In challenge 3 your proxy keeps these objects up to date: it adds one to `active` when it forwards a request and takes one away when the answer comes back, and health checks set `healthy`.

```js
const servers = [
  { name: "A", active: 3, healthy: true },
  { name: "B", active: 0, healthy: false }, // failed its health checks
  { name: "C", active: 1, healthy: true },
];
```

Three rules hold for all three pickers, and the tests check each one.

**Skip unhealthy servers.** A server whose `healthy` is `false` must never be returned. Treat a missing `healthy` as healthy, so a simple test list like `[{ name: "A" }]` works.

**Return the server object itself, or `null`.** Return the object from the array, not its name and not a copy, because the proxy will change that object's `active` count. When no server is healthy, return `null`, and let the caller decide what to do (your proxy in challenge 3 answers `503 Service Unavailable`).

**Do not change the input.** A picker reads the list; it does not sort it, filter it in place or touch the counts. The proxy owns those numbers. A picker that sorts the array in place would quietly reorder the servers for every later request, and round robin's turns would stop making sense.

## Round robin keeps a turn

Round robin is the only picker with memory: it must remember whose turn is next. That is why it is a factory. `createRoundRobin()` returns a new function, and the turn lives in a variable inside it, in a closure. Two balancers made by two calls keep separate turns.

Walk through it with the three servers above, starting with `next` at 0. The first call looks at A, moves `next` to 1, and returns A because A is healthy. The second call looks at B, moves `next` to 2, finds B unhealthy and tries again: it looks at C, moves `next` to 0 (wrapping around), and returns C. The third call returns A again. So the order is A, C, A, C: B is skipped, and the others still take turns.

Two details matter. First, the turn is a position in the list, and it moves forward even past a skipped server. If you only moved it on success, you would look at B again on every call. Second, the loop must stop after trying every server once. Without that limit, a list where every server is unhealthy would spin forever, and your balancer would freeze on the first request after a total outage, the moment you most need it to answer.

Health can change between calls, because health checks run in the background. If B comes back, the next time its position comes up it is returned as usual. The turn does not need resetting.

## Least connections reads the counts

`leastConnections(servers)` needs no memory. It walks the list once, ignores unhealthy servers, and keeps the one with the smallest `active`. One loop, one comparison, no sorting.

The tie rule matters for the tests: when two healthy servers have the same count, return the one that comes first in the list. Use a strict "less than" when you compare, so a later server with an equal count does not replace the one you already have. With the example list, A has 3, B is skipped, and C has 1, so C wins.

Why not sort by `active` and take the first? Sorting is more work than one pass, and `sort` changes the array in place unless you copy it first, which breaks the "do not change the input" rule. One pass is both faster and safer.

## Two choices draws exactly twice

`twoChoices(servers, random = Math.random)` takes a second argument: a function that returns a number from 0 (inclusive) to 1 (exclusive), like `Math.random`. Passing it in is called dependency injection. In production you use the default, `Math.random`. In tests, the server passes a function that returns a fixed sequence of numbers, so the result is the same on every run and can be checked exactly.

For the tests to agree with your code, the draw must follow one exact rule. First keep only the healthy servers, in their original order; call that list `healthy` and its length `n`. Then:

1. If `n` is 0, return `null`. If `n` is 1, return that one server without calling `random` at all.
2. The first pick is `i = Math.floor(random() * n)`.
3. The second pick is `j = Math.floor(random() * (n - 1))`, and if `j >= i`, add one to `j`.
4. Return `healthy[j]` if its `active` is strictly smaller than `healthy[i]`'s; otherwise return `healthy[i]`.

Step 3 is the clever part. It draws from the `n - 1` servers that are not `i`, so `j` can never equal `i`, and every other server is equally likely. A naive version, drawing `j` the same way as `i` and trying again when they match, also works, but it calls `random` an unknown number of times, and fixed test sequences would run out. Step 4 says a tie goes to the first pick.

Work one example by hand. The healthy list is A (5 in flight), B (1), C (4), D (2), so `n` is 4. Suppose `random` returns 0.1, then 0.9. The first pick is `floor(0.1 x 4) = 0`, server A. The second is `floor(0.9 x 3) = 2`, and since 2 is at least 0, it becomes 3, server D. D has 2 in flight and A has 5, so D wins. That is the first roll in chapter 4.5's picture.

solution: |
  function createRoundRobin() {
    let next = 0;
    return function pick(servers) {
      for (let tried = 0; tried < servers.length; tried++) {
        const server = servers[next % servers.length];
        next = (next + 1) % servers.length;
        if (server.healthy !== false) return server;
      }
      return null;
    };
  }

  function leastConnections(servers) {
    let best = null;
    for (const server of servers) {
      if (server.healthy === false) continue;
      if (best === null || server.active < best.active) best = server;
    }
    return best;
  }

  function twoChoices(servers, random = Math.random) {
    const healthy = servers.filter((server) => server.healthy !== false);
    if (healthy.length === 0) return null;
    if (healthy.length === 1) return healthy[0];
    const i = Math.floor(random() * healthy.length);
    let j = Math.floor(random() * (healthy.length - 1));
    if (j >= i) j += 1;
    return healthy[j].active < healthy[i].active ? healthy[j] : healthy[i];
  }

## Check your understanding before you submit

Run the example list from the top of this chapter through each picker in your head. Round robin should give A, C, A, C. Least connections should give C. Two choices, with B unhealthy, has a healthy list of A (3) and C (1); whatever the two rolls, the pair is A and C, so it returns C.

If a test fails, read its message first. Each one names the servers, the random numbers where there are any, the answer it expected and the one it got. The two most common slips are moving the round robin turn only on success, which shows up as the same skipped server being looked at forever, and drawing the second pick from all `n` servers instead of `n - 1`, which shows up in the exact-draw test as the wrong server.

## Why these details matter in a real balancer

The tie rule and the exact draw are not only there to make tests possible. A tie rule that always favours the first server sends slightly more traffic to it when the fleet is idle, which is harmless; a tie rule that picks at random is fairer but harder to test. Real balancers make that choice deliberately, and so should you.

The `null` return matters most on a bad day. When every server fails its health checks at once, your balancer must still answer each client, quickly, with a clear error, not hang. Chapter 4.4 showed that this is also the moment to consider failing open. Your challenge 3 proxy turns `null` into a `503`, and you can see the effect in your own results.

Finally, notice what none of these pickers knows: how expensive a request is, how fast a server is, or what other balancers are doing. Least connections and two choices learn it indirectly, through `active`, which is exactly why they cope with a slow backend in challenge 3 and round robin does not.
