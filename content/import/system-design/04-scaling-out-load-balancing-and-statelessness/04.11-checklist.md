## Your gate answer: defend a three-tier design

The scenario is the one the lab in chapter 4.9 plays. A study platform must serve 10,000 requests a second at its evening peak, with a p99 under 200 ms and 99.9% availability, at a fixed budget per hour. It has three tiers: a web tier at the front (the load balancer and anything it needs), an app tier of servers that run the code, and a data tier that stores everything. The hardest moment is the third level of the lab: one app server fails at peak, and the targets must still hold.

If the sandbox lab is open for you, design it there and use your passing design for this answer. If it is not open yet, design it on paper with the made-up sizes and prices from chapter 4.2, where a small server does 100 requests a second for $0.10 an hour, a medium 200 for $0.20, a large 400 for $0.40 and an xlarge 800 for $0.80, and a load balancer costs $0.05 an hour. Either way, the mentor reads the reasoning, not the exact count.

Why this question? Because it joins every chapter of the module into one decision. The size of each server comes from 4.2, the session store from 4.3, the balancer and its checks from 4.4, the picker from 4.5 and the headroom from 4.6. In a design review, nobody asks about these parts one at a time. They ask whether the whole thing still works at peak with one part gone.

A strong answer covers five things in about 150 words. First, the app tier: which server size, how many, and the arithmetic that shows N+1 and a utilisation ceiling, so losing one server still keeps the others below the knee. Second, the balancer: layer 4 or layer 7, which picker, and its health check interval and threshold, with how long a dead server would keep getting requests. Third, state: where sessions and uploaded files live, so the app servers are stateless and the one that fails takes nothing with it. Fourth, the data tier: what you assume about it, since modules 8 and 9 teach how to copy and split it; say honestly that it is the part this module did not scale. Fifth, cost: your total per hour, and the one change you would make if the budget were cut by a fifth.

Show the numbers. "Enough servers" is not an answer; "50 medium servers carry 10,000 a second at 100% busy, so at an 80% ceiling I need 63, plus one spare" is. Check the units on each line the way you did in module 2. Name the setting you are least sure of, and say what you would measure to find out. In challenge 3 you measured how a dead backend shows up as errors and how the survivors' p99 rises; use one of those results as evidence, for example "with checks every 500 ms and a threshold of 2, my part 2 run removed the dead backend in about half a second".

Watch for three common gaps. The first is sizing for the peak and forgetting the failure, which is the whole point of level 3. The second is a health check that tests the database, which would take out every app server when the database is slow. The third is forgetting that the session store and the load balancer are themselves parts that can fail: say how each survives, even in one sentence.
