Daftar has three app servers and a load balancer. Most requests are quick page loads. A few are slow, like "export all my notes as a PDF". How the balancer chooses a server decides whether a slow request ruins the next user's page.

## Round robin ignores how busy servers are

<InteractiveCanvas slug="sysdesign-m4-round-robin-blind" />

Round robin takes turns: A, B, C, A, B, C. Here every third request is a 2-second export, so every export lands on A. A builds a line while B and C sit idle. Round robin counts requests, not work. When requests differ, the load does too.

<GoDeeper title="Go deeper: round robin, weights and random">

<GlossaryTerm term="Round robin" definition="A balancing rule that sends each new request to the next server in a fixed order, A, B, C, then A again, without looking at how busy any server is." /> is the simplest rule and often a good one. It needs no information about the servers, it is fair by count, and when every request costs about the same and every server is the same size, it spreads work evenly. AWS's Application Load Balancer uses it by default, and Envoy offers it too.

Its blind spot is in the picture. Round robin does not know that A is busy. If requests vary a lot in cost, or if one server is slower than the others (an older machine, a noisy neighbour on the same host, a long garbage-collection pause), round robin keeps sending it a full share. The slow server's queue grows while the others have room.

The export pattern in the picture is deliberately unlucky: a slow request every third request lines up exactly with three servers. Real traffic is not that regular, but the effect is real. Any request that lands behind a slow one waits, and that wait shows up in p99.

Two variants fix part of the problem. Weighted round robin gives a bigger server more turns: if C has twice the capacity, it gets two turns for every one of A's. That handles servers of different sizes, but not requests of different costs. Random choice picks a server at random for each request. Over many requests it spreads as evenly as round robin, and it needs no shared counter, which helps when many balancers run side by side. It shares the same blind spot.

</GoDeeper>

## Least connections asks who is free

<InteractiveCanvas slug="sysdesign-m4-least-busy" />

Now the balancer counts the requests still in flight on each server: A 3, B 0, C 1. Each new request goes to the smallest count, so B gets the next two, and C gets the one after. Busy A gets nothing new until it catches up. The choice follows the work, not the turn.

<GoDeeper title="Go deeper: least connections, and what it needs">

<GlossaryTerm term="Least connections" definition="A balancing rule that sends each new request to the server with the fewest requests (or connections) still in progress. Also called least requests or least outstanding requests." /> uses a number the balancer already has. Every request it forwards and has not yet seen answered is in flight on that server. A server that is slow, for any reason, holds its requests longer, so its count rises and it gets fewer new ones. Nobody has to measure the server's CPU or know which requests are expensive.

This adapts to both problems round robin had: uneven requests and uneven servers. In challenge 3 you will give one of three backends three times the work per request and watch round robin keep sending it a third of the traffic while least connections sends it much less.

It has costs. The balancer must keep an accurate count for every server, updated on every request start and finish. A tie needs a rule; in this chapter and in exercise 4.7, the first server in the list wins. And the count only covers what this balancer sent. When several balancers run side by side, each sees only its own requests, so its counts are partial.

There is also a known trap with a server that fails fast. A server that answers every request instantly with an error has the lowest count of all, so least connections sends it more and more traffic. Health checks (chapter 4.4) and watching error rates protect against that.

</GoDeeper>

## Two random choices, nearly as good

<InteractiveCanvas slug="sysdesign-m4-two-choices" />

Checking every server's count takes work when there are hundreds. So the balancer picks just two at random and sends the request to the less busy of the pair. A and D are compared: D wins. Then B and C: B wins. The busiest servers are almost never chosen, after looking at only two counts.

<GoDeeper title="Go deeper: why two choices are enough">

Pure random choice can be unlucky: sometimes it picks a server that already has a long line. The <GlossaryTerm term="power of two choices" definition="A balancing rule: pick two servers at random and send the request to the one with fewer requests in flight. Comparing just two avoids the busiest servers almost as well as checking all of them." /> fixes most of that bad luck at a very small cost. For the request to land on a busy server, both random picks must be busy, which is much rarer than one pick being busy.

Michael Mitzenmacher's analysis (2001) puts numbers on the shape. Going from one random choice to two gives an exponential improvement in the expected time a request spends in the system. Going from two to three is only a constant factor better. Most of the benefit comes from the second choice.

That is why real balancers use it. Envoy's least request balancer, by default, picks 2 random hosts and sends the request to the one with fewer active requests, and its documentation says this is nearly as good as a full scan of every host. A full scan of N servers costs N lookups per request; two choices cost two, whatever N is.

There is a second reason, about many balancers at once. If every balancer always picks the single least-busy server, and they all see the same counts, they can all send their next request to that same server at the same moment, and it is suddenly the busiest. Random pairs spread those choices out.

## Same traffic, four algorithms

<InteractiveCanvas slug="sysdesign-m4-algorithm-race" />

The same requests go through four balancers side by side: random, round robin, least connections and two choices. Drag the load from low to high and watch each server's line and each algorithm's p99. At low load all four look alike. Near the top, the two that look at queues pull away from the two that do not.

<GoDeeper title="Go deeper: reading the race">

At low load every algorithm is fine, because every server has idle time. A request that lands on a slightly busy server waits a little, and the p99 barely moves. This is why teams often never notice which algorithm their balancer uses until a busy day.

As load rises, the knee from chapter 2.5 appears, but not equally. Random and round robin let one server's line grow while another sits idle, so some requests wait behind a slow one even though there is spare capacity elsewhere. Their p99 bends up first. Least connections and two choices keep the lines more even, so the knee comes later.

Least connections may edge out two choices in a picture like this, because one balancer sees every request and its counts are exact. Two choices gets close with two lookups instead of four. With hundreds of servers and several balancers, that cost and the herding problem change the ranking in its favour.

The algorithm cannot create capacity. Past 100% busy, all four fall over, just in different orders. The algorithm decides how well you use the capacity you have; N+1 and autoscaling decide how much you have.

</GoDeeper>

## Pick the algorithm by your traffic

<MermaidDiagram title="Which balancing algorithm?" chart={`flowchart TD
  Q1{"Must the same key always reach the same server? (a cache shard, a game room)"}
  Q1 -->|"yes"| H["Hashing: consistent hashing, such as ring hash or Maglev"]
  Q1 -->|"no"| Q2{"Do requests or servers differ a lot in speed?"}
  Q2 -->|"no, all alike"| RR["Round robin, weighted if sizes differ"]
  Q2 -->|"yes"| Q3{"Many servers or many balancers?"}
  Q3 -->|"few"| LC["Least connections"]
  Q3 -->|"many"| P2["Two random choices"]
`} legend="Start with whether a key must stick to one server; then whether requests are uneven; then how many servers and balancers share the choice." />

Ask three questions. Must one key always reach one server, like a cache shard? Use hashing. Are requests or servers uneven? If not, round robin is enough. If they are, use least connections with a few servers, and two random choices with many servers or many balancers.

<GoDeeper title="Go deeper: hashing, and why plain modulo moves almost everything">

Some requests must reach a particular server: the server that caches that user's data, or the one hosting a game room. Then the balancer hashes a key, such as the user id, and maps the hash to a server.

The obvious mapping is `hash(key) % N`. It breaks badly when N changes. Go from 3 servers to 4, and a key stays on its server only if its hash gives the same remainder for 3 and for 4. Count the hashes 0 to 11: only 0, 1 and 2 stay put. That is 3 in 12, a quarter. Three quarters of all keys move, so almost every cache is cold at once, right when you added a server to cope with load.

Consistent hashing fixes this. Karger and colleagues introduced it in 1997 for distributed caching, to relieve hot spots. Servers and keys are placed on a ring, and each key belongs to the next server along the ring. Adding a fourth server takes over only part of one arc, so only about a quarter of the keys move, the new server's fair share. Envoy offers two forms, ring hash (also called Ketama) and Maglev. Module 9 builds a ring with virtual nodes and measures exactly how many keys move.

Hashing has the same blind spot as round robin: it ignores load. One very popular key, a celebrity's profile, sends all of its traffic to one server, and consistent hashing does nothing about it (module 9 calls this the hot key problem).

</GoDeeper>
