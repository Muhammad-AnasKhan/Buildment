Daftar now runs on two app servers behind a load balancer. Hana logs in, taps "My notes", and sees the log-in page again. Nothing crashed. This chapter shows where her login went, and where state should live once there is more than one server.

## Logged in on one server only

<InteractiveCanvas slug="sysdesign-m4-session-lost" />

Hana logs in on App 1, which keeps her session in its own memory. The balancer takes turns, so her next request goes to App 2. App 2 has never seen her. The code is the same on both servers; the memory is not. That difference is state.

<GoDeeper title="Go deeper: what a session is, and why memory is the trap">

When you log in to a website, the server checks your password once. After that, it needs to remember that this browser belongs to you, without asking for the password on every click. It does this with a <GlossaryTerm term="session" definition="What a server remembers about one logged-in user between requests: who they are, and sometimes small things like their language or cart. The browser holds only a session id, usually in a cookie." />. The server makes a random session id, stores "this id belongs to Hana" somewhere, and sends the id to the browser in a cookie. The browser sends the cookie back with every request, and the server looks the id up.

"Somewhere" is the question. The easiest place is a plain object in the app's own memory, and many web frameworks start that way by default, because it needs no setup. On one server it works perfectly. On two, it breaks exactly as in the picture: the session exists on the server that created it and nowhere else.

{/* source needed: common web frameworks (for example express-session) default to an in-memory session store that is not meant for production. Not in the dossier. */}

This is the general rule behind the whole module. A <GlossaryTerm term="stateless" definition="An app server is stateless when it keeps nothing a later request needs: every request carries or fetches what it needs, so any copy of the server can answer it, and any copy can be removed." /> app server keeps nothing that a later request needs. That is what makes it safe to add, remove, restart or replace one: no user loses anything when it goes. In-memory sessions are the most common way a server stops being stateless, but not the only one. Uploaded files saved to the server's own disk, a counter kept in a variable, and a job that is half done in memory all break the same rule.

Notice that the bug depends on luck. With round robin over two servers, every other request lands on the "wrong" server. With random choice, about half do. With ten servers, nine in ten do. Testing on one server, or on a laptop, never shows it.

</GoDeeper>

## Sticky sessions: same user, same server

<InteractiveCanvas slug="sysdesign-m4-sticky-pin" />

The balancer now reads a cookie, "app=1", and sends Hana to App 1 every time. Her session is always there, so she stays logged in. Then App 1 crashes. The balancer must send her somewhere else, and her session died with App 1. Sticky sessions do not remove the state. They hide it until a server goes.

<GoDeeper title="Go deeper: what sticky sessions cost">

<GlossaryTerm term="Sticky sessions" definition="Also called session affinity: the load balancer sends all requests from one user to the same server, usually by setting a cookie or by hashing the client's address." /> are popular because they fix the symptom with one setting and no code change. They have four costs.

**Failure logs people out.** Every user pinned to a server that dies loses their session. With four servers, one crash logs out about a quarter of everyone. You will count this in the next beat.

**Scaling in logs people out too.** When an autoscaler removes a server at night (chapter 4.6), its users are logged out just as if it had crashed, unless the server is first <GlossaryTerm term="drained" definition="Taken out of rotation for new users while it finishes the requests and sessions it already has, before it is stopped." /> for long enough that its sessions end.

**Load stops being even.** The balancer can no longer send a request to whoever is least busy. It must send it to that user's server. A few very active users pinned to one server make it hot while others sit idle, and a new server added during a spike gets only new users, so it takes a long time to help.

**Deploys get slower.** Restarting servers one at a time for an update now logs out each server's users in turn, so teams wait for sessions to drain before every restart.

Stickiness is not always wrong. A WebSocket connection (chapter 3.5) is sticky by nature, since it is one long connection to one server. A layer 4 balancer that keeps a connection on one server is sticky per connection (chapter 4.4). The point is not to depend on stickiness for anything you cannot afford to lose.

The word comes back in module 11: some consistency guarantees are "sticky available", meaning they hold only while a client keeps talking to the same server. The cost there is the same as here: lose the server and you lose the guarantee.

## Kill a server, count the logouts

<InteractiveCanvas slug="sysdesign-m4-kill-server" />

Four servers share 1,200 logged-in students. Pick where sessions live, then tap a server to kill it. With sticky sessions, its 300 students are logged out. With a shared store, nobody is. Now tap the store itself and see what the shared store costs: it has become the one part that everybody needs.

<GoDeeper title="Go deeper: the numbers behind the picture">

With in-memory sessions and no stickiness, users are logged out even when nothing fails. With round robin over four servers, a user's next request reaches the server that holds their session only one time in four. So three requests in four miss, and the app is unusable.

With sticky sessions, everyone stays on their own server, so nothing is lost until a server dies. Then the share logged out is that server's share of users: 1,200 / 4 = 300, a quarter. With 10 servers it would be a tenth. More servers make each failure smaller, but never zero.

With a shared store, killing any app server logs out nobody, because the session never lived there. The balancer's next request for that user goes to any server, and that server reads the session from the store.

The catch is the last tap. Every request now reads from the store, so if the store fails, every user is logged out at once, the same as a single server failing in chapter 4.1. The store needs its own copy: a replica that can take over (module 8), in a different failure domain from the first. You have not removed the single point of failure; you have moved it to a part that is small, simple and easier to copy than your whole app.

</GoDeeper>

## Move the session to a shared store

<InteractiveCanvas slug="sysdesign-m4-session-store" />

App 1 saves Hana's session in a shared store and sends her only the session id. Her next request lands on App 2, which asks the store and gets her session back. Now the app servers hold nothing unique. Any server can serve her, and any server can be restarted or removed.

<GoDeeper title="Go deeper: choosing a session store, and the token option">

A session store needs three things: fast reads by key, an expiry on each entry so old sessions disappear, and a copy that survives the loss of one machine. An in-memory key-value store fits well. Valkey is an open-source one under the BSD-3-Clause licence; its small container image is about 19 MB, and challenge 4 uses it. Redis 8 works the same way here, under the RSALv2, SSPLv1 or AGPLv3 licence, so check which one your use allows. A table in the database you already have also works, and is a good choice when traffic is modest, since it adds no new system to run.

The cost is one extra round trip per request. A query to Redis, Memcached or MySQL takes about 500 microseconds, and a round trip inside one region about 250 microseconds. That is small next to a 50 ms page, but it is on every request, and the store must handle the whole site's request rate.

There is a second way to stay stateless: put the session in the request itself. The server writes the user's id and an expiry into a token, signs it with a secret key, and gives it to the browser. Any server with the key can check the signature and trust the token without asking a store. The trade-off is revocation: you cannot easily log a user out early or ban them, because the token stays valid until it expires, unless you keep a list of revoked tokens, which is a store again. Many teams use short-lived signed tokens plus a store for the rare revoke.

{/* source needed: signed session tokens such as JSON Web Tokens (RFC 7519) and the revocation trade-off. Not in the dossier. */}

**Debugging tip.** If users report "random logouts" only after you added a second server, look for state in memory first. Log which server answered each request next to the session id; a logout that always follows a change of server is the signature of this bug.

</GoDeeper>

## Where each kind of state goes

<MermaidDiagram title="Keep the app server stateless" chart={`flowchart LR
  APP["App server: code and copies only"]
  APP -->|"who is logged in"| S["Session store (Valkey) or signed token"]
  APP -->|"notes, users, orders"| D["Database"]
  APP -->|"uploaded photos and files"| O["Object storage"]
  APP -->|"slow jobs: emails, exports"| Q["Queue and workers"]
  APP -.->|"may stay local: a cache, since it is only a copy"| C["Local cache"]
`} legend="Each kind of state leaves the app server for a store that every server can reach. Only copies, such as a cache, may stay local, because losing them loses nothing." />

Sessions go to a shared store. Records go to the database. Uploaded files go to object storage, not the server's disk. Slow work goes to a queue. A local cache may stay, because it is only a copy: losing it costs speed, not data. Check each server against this map.

<GoDeeper title="Go deeper: state that hides in plain sight">

The map is easy to agree with and easy to break by accident. These are the places state most often hides in an app server.

**Files on local disk.** A user uploads a photo of their notes, and the server saves it to its own disk. The next request for the photo lands on another server and gets a 404. Uploaded files belong in object storage that every server can reach (module 1 named it as a building block).

**Counters and limits in memory.** A rate limiter that counts requests in a variable counts only the requests that reached that server. With four servers, each user gets four times the limit. Module 6 moves the counter into a shared store, the same move as sessions.

**Scheduled jobs.** A timer in the app that sends a reminder email every hour runs on every copy. With four servers, each user gets four emails. Run scheduled work once, in a worker, or with a lock (module 12).

**Half-done work.** A server that starts an export and keeps it in memory loses it if it is stopped halfway. A queue keeps the job until a worker confirms it is done (module 15).

**Caches.** These are allowed to stay, as long as nothing depends on them. A local cache makes each server a little different for a few seconds, which can surprise users who bounce between servers. Module 5 covers when that matters.

A quick test for any server: imagine it is deleted right now and replaced by a fresh copy. If any user would lose anything, that thing is state in the wrong place.

</GoDeeper>
