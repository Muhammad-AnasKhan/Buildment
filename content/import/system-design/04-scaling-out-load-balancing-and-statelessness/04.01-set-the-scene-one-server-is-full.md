## One big server, one restart

<InteractiveCanvas slug="sysdesign-m4-one-big-server" />

The server is only half busy, and it answers fine. Then it restarts, and every request fails, because there is nothing else to answer. A bigger server bought Daftar more room, but not a second place to run. One machine is one restart, one crash or one full disk away from zero.

<GoDeeper title="Go deeper: two walls a single server hits">

Daftar's numbers come from module 1: each student with the app open sends about one request every 20 seconds, 0.05 a second. 8,000 students send 400 a second. The old small server needed about 10 ms per request, so it could finish about 100 a second. The team's answer was to buy a bigger machine. In this story it is eight times bigger, so it can do about 800 a second and runs half busy. These are made-up round numbers, chosen so the arithmetic is easy.

That move, a bigger machine, is called scaling up, or vertical scaling. It is often the right first step. Nothing in the code changes, there is still one database connection pool and one place to look at logs, and the bill is easy to read. Chapter 4.2 takes it seriously.

It hits two walls. The first is **failure**. A single machine is a single place where everything can stop at once. That includes planned stops: an operating system update, a new version of the app, a move to a larger size. Each one is a restart, and each restart is an outage. With one server, "deploy on Friday night" means "Daftar is down on Friday night".

The second wall is **size**. Every cloud price list and every hardware catalogue has a largest machine. Next term the university plans to open Daftar to all its faculties. If 20,000 students come online at once, that is 1,000 requests a second, more than the big server can do. When the biggest size is not enough, scaling up has nowhere to go.

Both walls have the same way out: run more than one copy of the app. That is scaling out, or horizontal scaling. It has its own costs, and this module is about paying them well.

</GoDeeper>

## Many small servers, one front door

<MermaidDiagram title="Daftar scaled out" chart={`flowchart LR

This is where the module ends up. A load balancer is the one front door. Behind it run several identical app servers, so a restart takes out one of them, not all. Sessions move to a shared store. An autoscaler adds servers when traffic grows. Each box is one chapter.

<GoDeeper title="Go deeper: the module, box by box">

Chapter 4.2 compares one big machine with many small ones on three things: how much they can carry, what they cost, and how much one failure takes out. It also gives you a rule for how many servers to run so that losing one does not overload the rest.

Chapter 4.3 is about the arrow to the session store. When a user logs in on App 1 and their next request lands on App 2, App 2 must still know who they are. You will see why "sticky sessions" only half solve this and why most teams move session state out of the app server.

Chapter 4.4 opens the load balancer. Some balancers pick a server once per connection, others for every request, and they see different things. You will also see how health checks take a dead server out of rotation, and how a badly designed check can take out every server at once.

Chapter 4.5 compares the ways a balancer chooses: taking turns, asking who is least busy, or comparing just two servers picked at random. Chapter 4.6 adds the autoscaler and the reason it is always a little late.

Then you build. In 4.7 you write three server pickers in JavaScript. In challenge 3 (chapter 4.8) you put them inside a small load balancer of your own, kill a backend in the middle of a test and record what your users would have seen.

A word on what this picture leaves out: the database is still one box. Copies of the database come in module 8, and splitting it in module 9. Scaling out the app tier first is common, because app servers that hold no unique data are the easiest part of a system to copy.

</GoDeeper>
