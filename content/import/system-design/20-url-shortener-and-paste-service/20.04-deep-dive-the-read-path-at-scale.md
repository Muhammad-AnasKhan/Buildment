At peak, Wasla answers about 100,000 redirects a second, and almost all of them are reads of a tiny row. This is the second deep dive of the design loop. It follows one redirect through the cache, decides what status code to send, moves counting off the path, and ends with the failure that every cache design must survive.

## A miss costs three trips, a hit one

<InteractiveCanvas slug="sysdesign-m20-read-path" />

The redirect service uses cache-aside: look in the cache first. On a miss, read the database and store the answer in the cache. That is three trips. The next click for the same code finds it in the cache, which is one trip. In the course's numbers a hit costs 0.55 ms at the service and a miss costs 3.05 ms.

<GoDeeper title="Go deeper: where 0.55 ms and 3.05 ms come from">

Cache-aside is also called lazy loading. The application checks the cache, and on a miss it reads the database and writes the value into the cache, so the cache fills only with data that was asked for. A miss costs three trips: one to the cache, one to the database, and one to the cache again [S26]. Facebook's memcache is the same kind of "look-aside" cache, and on a write it deletes the cached copy rather than updating it, because a delete can be repeated safely [S24].

The numbers are built from napkin-math [S3]. A proxy hop takes about 0.05 ms and a cache query about 0.5 ms. For a database read on a table this big, where the index no longer fits in memory, the course assumes 2 ms, a few times the 0.5 ms of an in-memory query. Napkin-math warns that its numbers can be 2 to 3 times off, so treat them as a way to compare, not as a benchmark.

| Case | Working | Time at the service |
|---|---|---|
| Hit | 0.05 proxy + 0.5 cache | 0.55 ms |
| Miss | 0.05 proxy + 0.5 cache + 2 database + 0.5 store in cache | 3.05 ms |

What goes in the cache. The key is the code. The value is the long address and the expiry date, a few hundred bytes. The cache entry must never outlive the link: set its time to live (TTL, how long a copy may be used) to the smaller of an hour and the time left before expiry. When an owner deletes a link, delete the cache entry as well (chapter 5.5).

Wasla also wants a cache in each app server's memory for the few hottest codes, as chapter 5.6 describes, with a TTL of a few seconds. That keeps one viral code from loading one cache node.

</GoDeeper>

## Drag the hit rate, watch the database

<InteractiveCanvas slug="sysdesign-m20-hit-rate-play" />

Drag the hit rate. The average time falls smoothly, but p99 stays at the miss time until the hit rate reaches 99%, then drops at once. The database load tracks the misses: at 90%, 10,000 reads a second need about 5 nodes. At 99%, one node is enough. From 95% to 99% the average gains 0.1 ms, but p99 drops from 3.05 to 0.55 ms.

<GoDeeper title="Go deeper: the formulas, and what moves the hit rate">

With hit rate h, hit time 0.55 ms and miss time 3.05 ms:

- Average time = h x 0.55 + (1 minus h) x 3.05 = 3.05 minus 2.5h, in ms.
- p99 = 0.55 ms if h is 99% or more, otherwise 3.05 ms. (A hit rate of 98% means 2% of requests are slow, and p99 needs at most 1% slow.)
- Database operations = misses + creates = 100,000 x (1 minus h) + 1,000 a second.
- Nodes needed = that number divided by 2,500 (the planned load of one node), rounded up.

| Hit rate | Average | p99 | Database operations a second | Nodes |
|---|---|---|---|---|
| 0% | 3.05 ms | 3.05 ms | 101,000 | 41 |
| 50% | 1.80 ms | 3.05 ms | 51,000 | 21 |
| 90% | 0.80 ms | 3.05 ms | 11,000 | 5 |
| 95% | 0.68 ms | 3.05 ms | 6,000 | 3 |
| 99% | 0.58 ms | 0.55 ms | 2,000 | 1 |

From 95% to 99% the average improves by only 0.1 ms, but p99 drops from 3.05 ms to 0.55 ms and two database nodes disappear.

What decides the hit rate is the size of the cache and how uneven the traffic is (chapter 5.4). If most clicks go to a small set of links, a small cache catches most of them. Link traffic is plausibly like that, since a few links go viral, but the skew is an assumption until Wasla measures its own hit rate. Measure it, and watch p99 and the database load, not only the average.

The picture ignores creates that fill the cache, expiry, and the cost of keeping the cache itself alive. It models one request at a time, with fixed service times, not a queue.

</GoDeeper>

## 301 means "keep this answer"

<InteractiveCanvas slug="sysdesign-m20-redirect-301" />

A redirect needs a status code. A 301 means "moved for good", and browsers and CDNs may keep the answer. The phone taps once and Wasla counts one click. On the second tap the phone goes straight to the news site and never asks Wasla. Wasla cannot count that click, and it cannot change or switch off the link for that phone.

<GoDeeper title="Go deeper: what a 301 saves and what it gives up">

A 301 is the fastest redirect: for a phone that keeps the answer, the second click costs Wasla nothing, and the cache and database see no load. It also helps search engines treat the short address as a permanent alias. That is why some services use it.

The cost is control. Wasla cannot count the clicks that never arrive, so the analytics are wrong. It cannot change the destination, and it cannot stop a link that turns out to point to a bad site, for every browser that already holds the 301, until the browser lets it go. Browsers decide how long to keep a 301, and the time can be very long. Wasla does not control it.

{/* source needed: RFC 9110 sections 15.4.2 (301 Moved Permanently) and 15.1 (301 is cacheable by default). */} Freshness and how a cache may reuse an answer are defined in RFC 9111 [S22].

</GoDeeper>

## 302 sends every click through Wasla

<InteractiveCanvas slug="sysdesign-m20-redirect-302" />

A 302 means "found, for now". It is not kept by default, so the second tap asks Wasla again. Wasla counts two clicks, and it can still change the destination or stop the link. The price is load: every click arrives, about 100,000 a second at peak. Wasla pays that price on purpose, which is why the cache is in the design.

<GoDeeper title="Go deeper: the middle path, and what Wasla chooses">

Wasla sells click counts and must be able to remove an abusive link, so it answers 302. The cost is the whole read path from beat 1.

There is a middle path. A 302 can carry `Cache-Control: max-age=60`, which allows a browser or CDN to reuse it for 60 seconds [S22]. A viral link then reaches Wasla at most once a minute from each browser or CDN node. And a bad link stays live for at most 60 seconds. The cost is clicks that are not counted during the minute, so Wasla would count them at the CDN, or accept an undercount. For a campaign link with a huge spike, that trade is often right. For an ordinary link, plain 302 is simpler and the analytics stay honest.

{/* source needed: RFC 9110 section 15.4.3 (302 Found) and section 15.4.8 (307 Temporary Redirect, which keeps the request method). */}

</GoDeeper>

## Count the click after the redirect

<InteractiveCanvas slug="sysdesign-m20-click-queue" />

If the redirect service wrote the count to a database before it replied, a slow counter would slow every redirect. Instead it answers at once and drops a click event into a queue. A counter worker adds it up later. The redirect takes 0.55 ms whatever the counter is doing. Counts may be a few seconds late.

<GoDeeper title="Go deeper: events, windows and unique visitors">

A click event holds the code, a time, and a few fields such as the country. At a peak of 100,000 a second and about 100 bytes each, that is about 10 MB a second into the queue, which a partitioned log carries easily (chapter 15.3).

The worker adds events into a count per code per hour, which is the tumbling window from chapter 15.6 and the aggregator you wrote in 15.8. Queues deliver at least once, so a retry can count a click twice [S83]. For Wasla's analytics that is acceptable, and the course says so in the requirements. If the numbers ever became billing, the worker would need event ids and a record of the ones it has seen (chapter 14.5).

A hot link has a hot key. If the queue is partitioned by code, one viral code puts all of its clicks on one partition (chapter 9.4). Partition by a random number, or by the code plus a small random suffix, and let the worker add the parts together.

Unique visitors are harder than clicks. A HyperLogLog counter estimates the number of different visitors in small memory: Redis uses up to 12 KB per counter, with a standard error of 0.81% [S115]. That is too much for all 30 billion links, so Wasla would keep one only for links that opted in to detail.

If the queue is down, the redirect must not fail. The service sends the event with a short time limit, then drops it or keeps it in a small local buffer. Losing some clicks is better than losing redirects. That is a choice about which failure to accept.

</GoDeeper>

## A cold cache drowns the database

<InteractiveCanvas slug="sysdesign-m20-cache-loss" />

With a 90% hit rate the database sees about 11,000 operations a second. Now the cache restarts empty. Every redirect misses, and the database is asked for about 101,000 a second, 9 times what it was sized for. It slows, redirects time out, users retry, and the load grows. A cache that the database cannot live without is no longer only an optimisation.

<GoDeeper title="Go deeper: how to survive the cold cache">

Several fixes work together.

- **Spread the cache over many nodes** with consistent hashing (chapter 9.3). If one of ten nodes restarts, only a tenth of the keys miss, and the database sees about 9,000 extra operations a second (a tenth of the 90,000 hits), not all 90,000.
- **Warm it before it takes traffic.** Fill the new cache from the hottest codes before the load balancer sends it requests.
- **Coalesce misses.** When many requests miss the same code at once, let one of them read the database and make the others wait for its answer. Facebook's leases do this and cut peak database queries from 17,000 to 1,300 a second in one test [S24]. Chapter 5.6 covers stampedes.
- **Shed load.** Better to refuse some requests with a fast error than to let every request time out (chapter 16.5).
- **Rate limit unknown codes.** Scanners that try random codes miss the cache every time, and a miss for a code that does not exist is never cached. Count unknown-code misses per address, limit them (chapter 6.5), and store "not found" for a short time.

The lesson for the interview is the question behind the failure: "what happens when the cache is empty?" If the honest answer is "the database falls over", the cache is load-bearing and needs the same care as the database.

**In AWS.** ElastiCache is the managed cache; Amazon documents the lazy-loading strategy used here [S26]. DynamoDB gives conditional writes for the "save only if free" step [S42] and spreads load by hashing the partition key [S40]. CloudFront can keep answers close to readers when a response has freshness information, and invalidation or versioned names remove them [S28]. SQS or Kinesis can carry the click events [S83, S132]. {/* source needed: Amazon documentation for caching HTTP redirects in CloudFront. */}

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "The redirect service uses cache-aside. A hit is one trip, a miss is three. I would size the database for the miss rate: at a 90% hit rate that is about 10,000 reads a second plus the creates. I would return 302, not 301, so every click reaches me for counting and so I can stop a bad link. Clicks go to a queue after the response, so a slow counter cannot slow a redirect. Then I ask what breaks. If the cache restarts empty the database takes everything, so I spread the cache over nodes, coalesce misses and limit unknown codes."

**Expect:** "Why not a 301, which is faster?" **Answer:** "It is faster for the second click, but I lose the count and the control. I could send a 302 with a short max-age to get most of the speed back."

</GoDeeper>
