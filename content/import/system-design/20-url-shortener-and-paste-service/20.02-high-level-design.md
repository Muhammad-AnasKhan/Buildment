You have Wasla's numbers: about 100,000 redirects and 1,000 new links a second at peak, and about 9 TB in five years. This is the sketch step of the design loop. Draw the two paths first, then add only the blocks the numbers ask for.

## Creating a link: the write path

<MermaidDiagram title="The write path" chart={`flowchart LR
  C["Client"] -->|"POST /links"| G["Gateway: rate limit"]
  G --> W["Create service"]
  W -->|"1. ask for a code"| K["Code generator"]
  W -->|"2. save only if the code is free"| S[("Links store")]
  S -->|"3. saved"| W
  W -->|"4. 201 + short link"| C
`} legend="A create request is limited, given a code, and saved only if that code is free. The reply carries the short link." />

A create request is limited per user, checked, and given a code. It is saved only if that code is still free. That "put if absent" write means two requests can never take the same code. The reply is `201 Created` with the short link. How the code is made is the next chapter.

<GoDeeper title="Go deeper: the contract and the checks">

The whole API is two requests.

```text
POST /links   body: { "url": "https://...", "alias": "summer-sale" (optional), "expiresAt": "..." (optional) }
              -> 201 Created   { "code": "aB3x9Kp", "short": "https://wasla.example/aB3x9Kp" }
              -> 400 Bad Request   if the url is not valid
              -> 409 Conflict      if the alias is already taken
              -> 429 Too Many Requests   if the user is over the limit
GET  /aB3x9Kp -> 302 Found with a Location header holding the long address
              -> 404 Not Found   if there is no such code
              -> 410 Gone        if the link has expired
```

The create service checks the address before it saves anything. It accepts only `http` and `https`, because a link that starts with `javascript:` could be used to attack readers. It refuses addresses longer than 2,048 characters (a course limit) and addresses that point back at Wasla itself, which would make a loop.

The gateway limits creates per user with a token bucket (chapter 6.5). Redirects are public and are not limited this way, but you will see in chapter 20.4 why unknown codes need their own limit.

A client that times out will retry a create. Without care, each retry makes a new code for the same address. An idempotency key (chapter 6.4) fixes that: the client sends a random key with the request, and Wasla returns the first answer for a key it has seen.

The "save only if free" step is the same idea as compare-and-set in chapter 7.5. In PostgreSQL it is a unique key on the code. In DynamoDB it is a conditional write that succeeds only if the item does not exist yet [S42]. If it fails because the code is taken, the create service asks for another code and tries again.

</GoDeeper>

## Opening a link: the read path

<MermaidDiagram title="The read path" chart={`flowchart LR
  B["Browser"] -->|"GET /aB3x9Kp"| L["Load balancer"]
  L --> R["Redirect service"]
  R -->|"1. look"| H[("Cache")]
  R -->|"2. on a miss, read"| S[("Links store")]
  R -->|"3. 302 + long address"| B
`} legend="The redirect service looks in the cache first and the links store second, then sends the browser on. The service itself keeps nothing." />

A click reaches a redirect service. It looks in the cache first and the store second. It answers `302` with the long address, `404` if the code is unknown, or `410` if the link has expired. The create and redirect services are separate on purpose: one takes about 1,000 requests a second at peak, the other about 100,000. They scale on their own.

<GoDeeper title="Go deeper: expiry, stateless servers and reused codes">

The redirect service is stateless (chapter 4.3): everything it needs is in the cache or the store, so the load balancer can send any request to any copy. To add capacity, add copies.

Expiry works the way it did for PasteBox in chapter 1.4. Every read checks `expires_at` and answers `410 Gone` after it. A cleanup job removes old rows later, but it only frees disk. The reads never trust the job.

Should a freed code be given to a new link? Not soon. An old poster may still print the code. If Wasla gave it to a stranger, people who scan the poster would land on the stranger's page. A safe habit is never to reuse a code. With 3.5 trillion codes and only 30 billion used in five years, not reusing costs almost nothing.

</GoDeeper>

## Step through the design at peak

<InteractiveCanvas slug="sysdesign-m20-design-stepper" />

Step through the build. At each step, watch the database card: it shows how many times its planned load it carries. Adding app servers does nothing for the database. The cache is the step that matters. After it, the database sees about 11,000 operations a second, and five partitions bring each one to 2,200.

<GoDeeper title="Go deeper: the numbers behind each step">

The picture uses these course numbers. An app server finishes at most 10,000 redirects a second and is planned at half of that, 5,000. A database node finishes at most 5,000 operations a second and is planned at half of that, 2,500. Planning at half keeps the wait short (chapter 2.5).

| Step | What changes | App servers | Database load |
|---|---|---|---|
| 1. One box | App and database together | 1 | 101,000 / 2,500 = 40 times its plan |
| 2. App servers | 100,000 / 5,000 = 20 stateless servers | 20 | Unchanged: still 40 times |
| 3. A cache | 90% of redirects answered by the cache | 20 | 10,000 misses + 1,000 creates = 11,000, about 4.4 times |
| 4. Partitions | Split by a hash of the code (chapter 9.2) into 5 | 20 | 2,200 on each, 88% of its plan |
| 5. A click queue | Count clicks off the redirect path (chapter 20.4) | 20 | Unchanged, and no counting on the hot path |

The 90% hit rate is an assumption. The next chapters show how to measure it and what happens when it drops. Each partition also keeps two more copies on other machines (chapter 8.2), so one failure loses no data, and the fleet holds 3 times 9 TB, about 27 TB.

Storage: 9 TB over 5 partitions is 1.8 TB each. That fits on one disk per node with room to grow. If Wasla later keeps links for ten years, add partitions and move whole partitions to new nodes (chapter 9.5).

</GoDeeper>

## One table, read by code only

<MermaidDiagram title="The data model" chart={`erDiagram
  LINK {
    string code PK
    string long_url
    datetime created_at
    datetime expires_at
    string owner_id
  }
  CLICK_COUNT {
    string code
    datetime hour
    int clicks
  }
  LINK ||--o{ CLICK_COUNT : "counted in"
`} legend="LINK holds one row per short link, found by its code. CLICK_COUNT holds one row per code per hour, written by a separate worker." />

Wasla asks one question: what is behind this code? So one table keyed by code is enough, with no joins. Click counts live in a second table, so counting never touches the hot row. Split by a hash of the code, and every request goes to exactly one partition.

<GoDeeper title="Go deeper: choosing the store">

A row is about 300 bytes in the estimate: the code (7 bytes), the long address (around 200 bytes on average, a course number), two timestamps and an owner id.

Two choices fit. A key-value or wide-column store such as DynamoDB hashes the partition key for you and spreads load [S40]. Its per-partition limits are 3,000 read units and 1,000 write units a second [S40], which is why a single viral code needs a cache in front. The alternative is PostgreSQL with sharding by hand. It gives you SQL and a familiar tool, but you must run the shards, the routing and the moves yourself. The team of four from chapter 20.1 is a reason to prefer a managed key-value store.

"Show me my links" needs a lookup by owner. That is a different question from "what is behind this code?", so it needs a secondary index (chapter 9.6). In DynamoDB a global secondary index is updated asynchronously and is eventually consistent [S41]. A new link may take a moment to show in the owner's list. That is acceptable, and it keeps the redirect path simple.

</GoDeeper>

## A paste is a link to text

<MermaidDiagram title="Pastes reuse the same machine" chart={`flowchart LR
  C["Client"] -->|"POST /pastes"| W["Create service"]
  W -->|"same code generator"| K["Code generator"]
  W -->|"row: code + blob key"| S[("Links store")]
  W -->|"body"| O[("Object storage")]
  B["Browser"] -->|"GET /aB3x9Kp"| R["Redirect service"]
  R --> H[("Cache")]
  R -->|"on a miss"| S
  R -->|"fetch body"| O
`} legend="A paste uses the same codes, store, cache and read path as a link. The only new block is object storage for the text." />

A paste service is the same machine with one change. The code points to text, not a web address. The text goes to object storage and the row keeps only its key. Codes, cache and partitions are unchanged. Pastes never change, so a CDN can keep them for a long time.

<GoDeeper title="Go deeper: what changes for text">

PasteBox in chapter 1.4 stored the text inside the table, because it was small and the traffic was tiny. Here the bodies average about 10 KB and go up to 1 MB (the same course numbers as PasteBox), and the table holds billions of rows. Keeping bodies in the table would make every row large and every partition heavy. Object storage is built for large values. A read of a body from blob storage took about 80 ms in napkin-math's measurement [S3], so small bodies belong in the cache too.

A paste is returned with `200 OK` and the text, not a redirect. Because a paste never changes after it is saved, its response can carry `Cache-Control: public, max-age=86400`, so a CDN or browser may reuse it for a day [S22]. That is the answer to a viral paste: the CDN serves it near each reader, and Wasla's servers never see most of those reads.

Pastes raise a new question: can they be private? An unlisted paste is protected only by its code. If codes follow a counter, anyone can guess the next one. Chapter 20.3 returns to this and picks a different code method for pastes than for links.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Two paths. A create call is rate limited, gets a code, and is saved with a put-if-absent write, then returns 201. A redirect goes to a stateless service that checks a cache, falls back to the store by code, and returns 302. One table keyed by code, split by a hash of the code. A cache answers about 9 in 10 redirects, so the database sees around 11,000 operations a second, which five partitions share. For pastes I would keep the same codes and read path and put the body in object storage."

**Expect:** "Why not one service for both?" **Answer:** "Creates are about 1% of the traffic. Splitting lets me scale the redirect fleet alone, and a bug in create cannot slow redirects."

</GoDeeper>
