In chapter 20.3 you chose how Wasla makes its codes: a counter, written in base62, with each app server claiming a block of numbers so it does not ask for every code. In 20.4 you saw what the redirect does with a code. The part in between is small. A function turns a number into at most 7 characters, a second function turns the characters back, and a third object hands out numbers from a block and claims a new block only when the old one runs out.

Each piece is short, and each is easy to get slightly wrong. A slightly wrong encoder passes every test that uses small numbers and fails the day a code needs a zero in front. A slightly wrong allocator passes with one server and hands out the same number twice when two servers run. In this chapter you write all three in plain JavaScript and test them against the cases that catch those mistakes.

## What the tests do to your code

The tests are built around the places where these functions fail. For the encoder they use the edges of base62: 0, the last single digit, the step from `Z` to `10`, a number that needs padding, a number that is already longer than the padding, and the last 7-character code. For both functions they send bad input. For the allocator they count how many times your code asks the shared store for a block, they run two allocators on one store at the same time, they crash one in the middle of a block, and they fill the keyspace on purpose.

Nothing is `async`, and nothing reads a clock or a random number. Each test gives the same answer every time, and the message of a failing test tells you which rule you broke.

## The contract

**`encodeBase62(n, minLength = 1)`** takes a non-negative integer `n` that JavaScript can hold exactly (a safe integer) and returns a string. The alphabet is the 10 digits, then the 26 lowercase letters, then the 26 uppercase letters, in that order: `0` is the first character, `a` stands for 10, `z` for 35, `A` for 36 and `Z` for 61. The string is padded on the left with `0` to at least `minLength` characters, and it is never cut, so a number that needs 8 characters stays 8 characters. Zero encodes as `0`, padded if needed. It throws a `RangeError` if `n` is not a non-negative safe integer, or if `minLength` is not a positive integer.

**`decodeBase62(text)`** reverses it. Leading zeros do not change the value. It throws a `RangeError` if `text` is not a non-empty string, if it contains a character outside the alphabet, or if the value would be larger than `Number.MAX_SAFE_INTEGER`. Past that limit the answer would be wrong without any warning, so refusing is the safe choice.

**`createRangeAllocator({ rangeSize, claimRange, limit = Infinity })`** returns an object with two methods. `claimRange(size)` is supplied by the caller. It is the shared store: it returns the first number of a fresh range of `size` numbers, and it guarantees that no two callers ever get overlapping ranges. In production it is one atomic update of a counter row. In the tests it is a plain function.

`next()` returns the next number. The first call claims a range, and so does any call that finds the current range used up. It never claims early: creating the allocator makes no claim at all. If a range would run past `limit`, it is cut at `limit`. If a claim starts at or past `limit`, there is no room, so `next()` throws a `RangeError`.

`remaining()` returns how many numbers are left in the current range. Before the first claim that is 0.

An allocator checks its settings. `rangeSize` must be a positive integer or it throws a `RangeError`. `claimRange` must be a function or it throws a `TypeError`. If `claimRange` returns something that is not a non-negative safe integer, `next()` throws a `TypeError`.

## A worked example by hand

Here is the code applied by hand to a case that is not in the tests. First the encoder, for the number 3,000,000. Divide by 62 again and again, and keep each remainder, starting from the right.

| Step | Number | Divided by 62 | Remainder | Character |
|---|---|---|---|---|
| 1 | 3,000,000 | 48,387 | 6 | `6` |
| 2 | 48,387 | 780 | 27 | `r` (27 is the 28th symbol, after `0` to `9` and `a` to `q`) |
| 3 | 780 | 12 | 36 | `A` |
| 4 | 12 | 0 | 12 | `c` |

Read the remainders from the last step to the first: `cAr6`. Padded to 7 characters it is `000cAr6`. To check it, decode it with the loop `n = n * 62 + digit`, left to right: ((12 x 62 + 36) x 62 + 27) x 62 + 6 = 3,000,000. The loop never needs a power of 62.

Now the allocator, with `rangeSize` 5 and two servers, A and B, on one store that starts at 0.

| Call | Who | Range claimed | Number returned | Store next value |
|---|---|---|---|---|
| 1 | A | 0 to 4 | 0 | 5 |
| 2 | B | 5 to 9 | 5 | 10 |
| 3 | A | none, uses its block | 1 | 10 |
| 4 | B | none, uses its block | 6 | 10 |
| 5 to 7 | A | none | 2, 3, 4 | 10 |
| 8 | A | 10 to 14 | 10 | 15 |

A's fifth number is 4, the last in its block, and its sixth call finds the block empty and claims a new one. A never saw 5, because B holds that block. Suppose instead that A crashes after returning 2. Numbers 3 and 4 are never used, and the next server to claim gets 10, because B moved the store to 10. Nothing is repeated, and two numbers are wasted. Wasting is the price of not asking the store for every number.

## Five ways this goes wrong

**Forgetting the zero.** A loop that runs while `n > 0` returns an empty string for 0. Encode 0 as `0`, and let the padding step do the rest.

**Cutting a long code to fit.** If a caller asks for `minLength` 7 and the number needs 8 characters, the answer must be 8 characters. Cutting it would give two numbers the same code, which is the one thing a code must never do.

**Claiming early or every time.** An allocator that claims a range when it is created wastes a block for every server that starts and never makes a link. One that claims on every call is a counter with extra steps. The tests count claims.

**Changing state before the claim is checked.** If `next()` sets its range from a bad claim, a later call may return garbage or loop. Validate the claim first, then change anything.

**Trusting a number that is too big.** In JavaScript, integers above `Number.MAX_SAFE_INTEGER` look fine but lose their last digits. Decoding 12 characters of `z` gives a number that has already lost its precision. The decoder must stop and throw as soon as the running value leaves the safe range.

When a test fails, read its message first. Each one names the input, what it expected and what your code returned.

solution: |
  const BASE62 = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

  function encodeBase62(n, minLength = 1) {
    if (!Number.isSafeInteger(n) || n < 0) {
      throw new RangeError("n must be a non-negative safe integer");
    }
    if (!Number.isInteger(minLength) || minLength < 1) {
      throw new RangeError("minLength must be a positive integer");
    }
    let text = "";
    let rest = n;
    while (rest > 0) {
      text = BASE62[rest % 62] + text;
      rest = Math.floor(rest / 62);
    }
    return text.padStart(minLength, "0");
  }

  function decodeBase62(text) {
    if (typeof text !== "string" || text.length === 0) {
      throw new RangeError("text must be a non-empty string");
    }
    let n = 0;
    for (const ch of text) {
      const digit = BASE62.indexOf(ch);
      if (digit === -1) throw new RangeError("not a base62 character: " + ch);
      n = n * 62 + digit;
      if (!Number.isSafeInteger(n)) throw new RangeError("too large to decode safely");
    }
    return n;
  }

  function createRangeAllocator({ rangeSize, claimRange, limit = Infinity } = {}) {
    if (!Number.isInteger(rangeSize) || rangeSize < 1) {
      throw new RangeError("rangeSize must be a positive integer");
    }
    if (typeof claimRange !== "function") {
      throw new TypeError("claimRange must be a function");
    }
    let current = 0;
    let end = 0; // the range is [current, end); empty until the first claim
    return {
      next() {
        if (current >= end) {
          const start = claimRange(rangeSize);
          if (!Number.isSafeInteger(start) || start < 0) {
            throw new TypeError("claimRange must return a non-negative integer");
          }
          if (start >= limit) throw new RangeError("keyspace exhausted");
          current = start;
          end = Math.min(start + rangeSize, limit);
        }
        return current++;
      },
      remaining() {
        return end - current;
      },
    };
  }

## Check your understanding before you submit

Run one more case in your head with your code. Make an allocator with `rangeSize` 3 and `limit` 7, on a store that starts at 0. Call `next()` seven times. The first claim is 0, the second is 3, and the third starts at 6 and is cut at 7, so the last range holds only the number 6. You get 0, 1, 2, 3, 4, 5, 6 and three claims. The eighth call claims a start of 9, which is past the limit, so it throws a `RangeError`. Then call `remaining()` after the seventh number: it is 0.

Now put the numbers through the encoder with `minLength` 7. Number 6 becomes `0000006`, and number 3,844 (62 squared) becomes `0000100`. The codes are tiny numbers padded with zeros, and they look nothing like Wasla's real links. That is the weakness from chapter 20.3: a counter is easy to read. A real service would add a scrambling step between the allocator and the encoder. You will not write it here, because the point of this exercise is that the two parts you did write are exact.

## How to say it in an interview

**Say:** "The code is a number written in base62, padded to seven characters. Each app server claims a block of a million numbers from a shared counter row in one atomic update, then hands numbers out from memory. Two servers cannot get the same block. A crash wastes the rest of that server's block, which is fine, because there are 3.5 trillion codes and about 30 billion links. The unique key on the code is the safety net."

**Expect:** "What if the counter store is down?" **Answer:** "Servers keep creating links until their block runs out. At 100 creates a second per server, a block of a million lasts nearly three hours."

## What this unlocks

The allocator pattern, claiming a block of ids so you do not ask for each one, is not only for short links. Any system that needs unique ids across many servers can use it, such as order numbers or batch ids. The wider idea, paying one shared trip for many local actions, comes back as batching, as caching and as the lease. Chapter 20.7 asks you to use these ideas on scenarios you have not seen.
