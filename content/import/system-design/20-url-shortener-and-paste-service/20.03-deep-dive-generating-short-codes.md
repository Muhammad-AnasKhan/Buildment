Every short link needs a code that no other link has. Wasla writes codes with <GlossaryTerm term="base62" definition="Writing a number with 62 symbols instead of 10: the digits 0 to 9, the letters a to z, and the letters A to Z. Seven base62 characters can write any number below 62 to the power 7, which is about 3.5 trillion." />. This chapter is the deep dive of the design loop: three ways to make the code, the numbers that separate them, and one choice.

## Hash the URL: same URL, same code

<InteractiveCanvas slug="sysdesign-m20-hash-same-url" />

One way is to hash the long address, which means to run it through a function that gives a fixed-size scrambled number, and keep the first 7 characters. The same address always gives the same code, so Ana and Cy share one row. That saves space. It also means they share one set of click counts and one expiry date.

<GoDeeper title="Go deeper: how the hash becomes a code, and what it costs">

Take a hash such as SHA-256, keep its first 41 bits, and write that number in base62. Forty-one bits can hold numbers up to 2 to the power 41, which is about 2.2 trillion. That is below 62 to the power 7, about 3.5 trillion, so the result always fits in 7 characters.

What the method gives. It needs no counter and no coordination between servers. A retry of the same create gets the same code, so creating is safe to repeat without an idempotency key (chapter 6.4).

What it costs. Two different addresses can hash to the same 7 characters. The next beat shows how often. When that happens, the unique key on the code refuses the second insert. The create service then hashes the address again with a small counter added, and tries the new code. So the unique key is still needed, and a clash costs one more round trip.

The shared row is a product problem. If two customers shorten the same address, one customer's expiry date or a "delete my link" request changes the other's. To avoid it, hash the user id together with the address. Then the same user gets the same code back, and different users get different ones.

Last, the code is not a secret. Anyone can hash an address and compute its code. That does not matter for public links. It matters for private ones.

</GoDeeper>

## Drag the length, watch the clashes

<InteractiveCanvas slug="sysdesign-m20-collision-play" />

Drag the code length from 4 to 9 characters, and the number of stored links from 1 million to 30 billion. The share of codes already taken is the chance that a new random code clashes. At 30 billion links, 6 characters is more than half full. Seven characters is under 1% full, and 8 is far below it. Wasla needs at least 7.

<GoDeeper title="Go deeper: the formulas, and why the first clash comes early">

With L characters there are 62 to the power L codes. If n links are stored, the share taken is n divided by that number. For a random code, that share is the chance it is already taken. If a fraction f is taken, the average number of tries per create is 1 divided by (1 minus f), so the average number of extra tries is f divided by (1 minus f).

| Code length | Possible codes | Share taken at 30 billion | Extra tries per create |
|---|---|---|---|
| 5 | 916 million | cannot hold 30 billion | not possible |
| 6 | 56.8 billion | 53% | about 1.1 |
| 7 | 3.52 trillion | 0.85% | about 0.009 |
| 8 | 218 trillion | 0.014% | about 0.00014 |

At 193 creates a second, 7 characters means about 1.7 extra tries a second. Nothing to worry about. Eight characters would cost one more character in every link, for almost nothing gained. Seven is the choice.

There is a trap in the word "rare". The first clash does not wait until the table is nearly full. With N possible codes, the first clash is expected after about 1.25 times the square root of N codes. This is the birthday problem: the number of pairs of codes grows with the square of the count. The square root of 3.5 trillion is about 1.9 million, so the first clash is expected near 2.4 million random codes. At 193 creates a second, that is after about 3.4 hours. A clash is rare for one create, and certain over a month.

That is why every method needs the unique key. It is the safety net under all three: a code is only saved if no row has it.

</GoDeeper>

## Count, then write the number in base62

<InteractiveCanvas slug="sysdesign-m20-counter-base62" />

Another way is to count. The counter gives 125, and base62 writes 125 as 21, padded with zeros to `0000021`. No two links ever share a number. But the codes follow each other, so anyone can try `0000023` and read other people's links. And every code costs a trip to one counter.

<GoDeeper title="Go deeper: base62, and how to hide the order">

To write a number in base62, divide by 62 again and again and keep the remainders. For 125: 125 = 2 x 62 + 1, so the digits are 2 and 1, which is `21`. Pad on the left with zeros to a fixed length. You build this encoder in chapter 20.5.

A counter has two honest weaknesses. First, it is one machine that every create depends on (chapter 10.7). Second, it leaks. The code shows roughly how many links Wasla has, and a competitor can watch it grow. Anyone can also walk through all the codes.

A counter's speed is not the problem. At 193 creates a second, one database sequence can keep up. An atomic counter in DynamoDB is not safe to retry, because a retry after a timeout may count twice [S42]. For codes that is harmless: a skipped number only wastes a code, and nothing hands out the same number twice.

To hide the order, you can pass the number through a scrambling step that is one-to-one, so no two numbers give the same code. A plain multiplication is not enough: the last character would still follow the count in a pattern. A small Feistel network is the usual tool. It is obfuscation, not encryption, and it does not make a code secret.

Why not use a Snowflake ID (chapter 10.7)? Its layout of 41, 10 and 12 bits makes 63 bits [S65]. Written in base62 that is 11 characters. Seven characters hold about 41.7 bits, so a Snowflake ID is too long for a short link.

</GoDeeper>

## Claim a block, then work alone

<InteractiveCanvas slug="sysdesign-m20-range-allocator" />

One counter can keep up, but every create would wait for it, and if it fails nobody can create. So each app server claims a block of 1 million numbers in one trip, then hands them out from memory. Two servers never get the same block. If a server crashes, the rest of its block is skipped. Skipping is cheap, because there are 3.5 trillion codes.

<GoDeeper title="Go deeper: why the block can be big, and how little it costs">

At peak, Wasla makes about 1,000 links a second. With 10 app servers, each makes about 100 a second. A block of 1 million numbers lasts one server about 10,000 seconds, nearly 3 hours. If the table that hands out blocks is down, the servers keep creating links for hours. For the whole service at the average of 193 creates a second, a block of 1 million is claimed about once every 86 minutes. The table is almost idle.

Wasted numbers are the price. A crash wastes at most one block. Suppose all 10 servers crashed every day for five years. That is 10 x 365 x 5 = 18,250 blocks, or 18 billion numbers, which is 0.5% of the 3.5 trillion. And crashes are far rarer than that. A big block is safe because the keyspace is huge.

The table that hands out blocks is one row with a counter. Claiming a block is one atomic step: read the counter, add the block size, store it, and return the old value. Two servers that claim at once get different blocks, because the database handles the two claims one after the other (chapter 7.5).

Codes from different servers interleave in time, so the order of codes does not exactly match the order of creation. Code order is still guessable, to a degree. In chapter 20.5 you will write this allocator.

</GoDeeper>

## Pre-make random codes in a pool

<InteractiveCanvas slug="sysdesign-m20-key-pool" />

A third way moves the work out of the user's request. A background job makes random codes ahead of time and keeps them in a pool. An app takes 1,000 at a time and the pool marks them used. The codes are random, so they are hard to guess, and creating a link never retries. The price is one more system to run and back up.

<GoDeeper title="Go deeper: how the pool works, and how it fails">

The key maker draws random 7-character codes and inserts them into a pool table with a unique key. If a code is already there, used or not, the insert fails and the maker draws again. So the collisions from the last beat still happen, but in the background, where no user waits.

How big must the pool be? One day of Wasla's average creates is 193 x 86,400, about 16.7 million codes. At 7 bytes each that is about 117 MB. The pool is tiny.

Handing out codes must be atomic: two apps must never take the same code. The pool marks a batch used, or moves it to a used table, in one step that locks the rows it takes.

Failures to plan for. An app that crashes holds up to 1,000 codes that are lost, as with a wasted block. If the pool runs empty, creates stop, so the key maker needs an alarm on the number of unused codes, and the app needs a fallback such as a random code with a unique key. If the pool itself is down, the apps can still use the codes they already hold, for a while.

</GoDeeper>

## Wasla counts; private pastes go random

<MermaidDiagram title="Choosing a code method" chart={`flowchart TD
  A["Need a code"] --> B{"Must codes be hard to guess?"}
  B -->|"no, links are public"| F{"Must the same URL always get the same code?"}
  F -->|"no"| H["Counter blocks plus base62: Wasla links"]
  F -->|"yes"| G["Hash of the URL, with a salt on a clash"]
  B -->|"yes, private pastes"| C{"Can we run one more system?"}
  C -->|"yes"| D["Key pool of random codes"]
  C -->|"no"| E["Random code, unique key, retry"]
`} legend="Two questions pick the method: must codes resist guessing, and must the same URL always get the same code? The unique key sits under every branch." />

Two questions pick the method. Must codes resist guessing? Must one URL always get one code? Wasla's links are public, and nobody needs the same code twice. So Wasla takes counter blocks plus base62. Private pastes need codes nobody can guess, so they take random codes. The unique key sits under every branch.

<GoDeeper title="The trade-off, written out">

A trade-off is easier to defend when you write it the same way every time (chapter 1.4).

- **The choice:** counter blocks of 1 million, written in base62, 7 characters, with a unique key on the code.
- **Why now:** Wasla's links are public by promise (chapter 20.1), creates are only 193 a second, and one table row can hand out blocks.
- **What it buys:** no clashes and no retries, no trip to a coordinator for 999,999 of every 1,000,000 codes, and a coordinator that can be down for hours.
- **What it costs:** codes that roughly follow creation order, so anyone can walk through them and see a competitor's growth. A wasted block for each crash. One more small table to run.
- **The alternative:** random codes with a unique key and retry. It is simpler, hard to guess, and costs about 1.7 extra tries a second at 30 billion links.
- **When to switch:** the day links may point at private pages, or the day an abuse report shows people walking the codes. Then move to random codes. A custom alias already goes through the unique key, so that path exists.

What fails? If the block table is down, creates continue until each server's block runs out, about 3 hours at peak. If an app crashes, its block is skipped. If a custom alias equals a counter code, the unique key refuses the insert and the app takes the next number.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "I need 7-character base62 codes. 62 to the power 7 is 3.5 trillion, and I expect 30 billion links, so under 1% of codes are used. I would give each app server a block of a million numbers from a shared counter row and encode with base62. There are no clashes, and the counter is touched once per million creates. I keep a unique key on the code as a safety net, and it also handles custom aliases. If links could be private, I would use random codes, because a counter is easy to guess."

**Expect:** "What about hashing the URL?" **Answer:** "It needs no coordination, and a retry gets the same code. But two URLs can still clash, because a short hash has few bits, so I still need the unique key and a rehash on clash. And two users share one row. Counters are simpler for Wasla."

</GoDeeper>
