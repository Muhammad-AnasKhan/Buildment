Chapter 24.2 gave Safar a way to search. Now the other half: the million phones that keep the map true. Every driver reports a place every 4 seconds, and every report must land in the right box.

## A ping every 4 seconds adds up

<InteractiveCanvas slug="sysdesign-m24-write-every-ping" />

Each driver's phone reports its place every 4 seconds. With a million drivers online that is 250,000 reports a second. If every report becomes a row written to a database, we need about 100 database nodes, each planned at 2,500 writes a second. And the data is old after 4 seconds.

<GoDeeper title="Go deeper: the arithmetic, and sending fewer pings">

Each report is about 50 bytes: a driver id, latitude and longitude, a time, and the heading and speed. 250,000 reports of 50 bytes is 12.5 MB a second, or 100 Mbit/s. That is small for the network. The load that matters is the number of separate writes, each one a disk operation with its own cost, at 2,500 a second for one database node (the course number from chapter 20.2).

The phone can send fewer pings. A driver who has not moved 20 m, or turned, does not need to report every 4 seconds. Suppose 40% of drivers online are waiting or stopped and report every 15 seconds, and the other 60% still report every 4. The rate becomes 1,000,000 x (0.6 / 4 + 0.4 / 15), about 177,000 a second, 29% lower. The saving is real, and the design still needs a plan for 177,000 a second.

How do the pings arrive? Each phone holds a connection to a gateway, which is a stateless service (chapter 4.3) that you can add more of. Chapter 3.5 compares the ways to keep such a connection open. The gateway decides which box a ping belongs to and passes it on. It never keeps the place itself.

</GoDeeper>

## Keep only the latest place

<InteractiveCanvas slug="sysdesign-m24-latest-only" />

A search needs only where each driver is now. A new report replaces the old place, so the map holds one entry per driver: about 100 MB for a million drivers. History goes to a log, which other services read later, at their own speed, without slowing a search.

<GoDeeper title="Go deeper: the map, the log and two rules">

The map is two small structures in memory. One maps a driver id to the driver's latest place, the box it is in, and when it was last heard. The other maps a box code to the set of driver ids in it. A report updates both. At about 100 bytes a driver, a million drivers is 100 MB, which fits in memory with room to spare. We split the map over several machines because of the rate, not the size.

It looks like a cache, but it has no database behind it. For "where is the driver now?" the map is the only copy, and that is the point. Chapter 5.3 describes caches that refill from a database. This one refills from the drivers themselves.

**Rule 1: numbered pings.** Phones send reports over a network that can delay or reorder them. An old report that arrives late must not replace a newer one. So each phone numbers its reports, and the map ignores a report whose number is lower than the one it holds. This is the same idea as the log positions in chapter 8.4.

**Rule 2: history is separate.** Each accepted report is also appended to a log, as in chapter 15.3. Receipts, safety checks and trip replays read the log. Keeping every report would be about 1.1 TB a day, so Safar keeps the log for a few days and keeps the trace of a finished trip. The log is durable and replayable. The map is neither, and does not need to be.

</GoDeeper>

## Shard the map by box

<MermaidDiagram title="Pings and searches both route by box" chart={`flowchart LR
  P["Driver pings"] --> G["Gateways"]
  G -->|"box code"| R["Route by box code"]
  Q["Nearby search"] -->|"9 or 25 box codes"| R
  R --> S1["Shard 1: boxes 0 to h"]
  R --> S2["Shard 2: boxes j to r"]
  R --> S3["Shard 3: boxes s to z"]
`} legend="One routing rule for both paths: the box code decides the shard. Boxes next to each other usually share a shard, so a search usually reads one or two shards." />

Each shard keeps the drivers of some boxes. The gateway reads a ping's box code and sends it to the shard that owns the box. A search sends its box codes the same way and merges the answers. Boxes that share a code prefix sit on the same shard, so a search usually touches one or two shards.

<GoDeeper title="Go deeper: range or hash, again">

This is the choice from chapter 9.2. Sharding by box prefix is range partitioning: neighbours stay together, so a search rarely crosses shards. The price is the risk of a hot partition (chapter 9.4): a popular area lands on one shard, and the next beat is exactly that.

Sharding by a hash of the box code spreads the load evenly, but it scatters neighbours. Then each 9-box search can touch up to 9 shards, and its answer is as slow as the slowest of them (scatter-gather, chapter 9.6). At 40,000 searches a second, that is up to 360,000 shard calls a second.

Sharding by driver id has the same problem in a stronger form: every search asks every shard. Safar uses the box prefix for the live map and accepts the hot box. It plans for it with the tools in the stadium beat. A different key serves a different job: the driver's trip state is keyed by driver id (chapter 24.4), because a driver's status must have one owner while the place moves from box to box.

</GoDeeper>

## Add to the new box, then drop old

<InteractiveCanvas slug="sysdesign-m24-cross-cell-edge" />

A driver who crosses an edge belongs to a new box. Safar adds the driver to the new box first, and only then drops it from the old one. A search in between sees the driver twice and removes the duplicate. It never sees the driver missing, which would hide a free car from a waiting rider.

<GoDeeper title="Go deeper: how often it happens, and what can go wrong">

At 30 km/h a car moves about 33 m in 4 seconds. A 6-letter box is 0.6 to 1.2 km on a side, so a moving car crosses an edge on about 3 to 5 of every 100 reports. Most reports stay inside the same box and change only the place.

The map stores each driver's current box. When a report's box differs, the map does three things in order: add the driver to the new box, update the driver's record, remove the driver from the old box. If the machine stops between the first and last step, the driver may sit in two boxes. A search handles that by keeping one entry per driver id. The next report for that driver cleans the old box up, and a driver that is not heard from expires anyway (see the last beat).

If the two boxes live on different shards, the two steps are two messages. The same order protects the driver: the new shard learns of the driver before the old one forgets.

</GoDeeper>

## The stadium empties

<InteractiveCanvas slug="sysdesign-m24-stadium-night" />

After a match, 20,000 fans open the app in one box. One shard owns that box, so it gets all 4,000 searches a second, and the pings of 3,000 drivers waiting nearby. It carries 75 times the work of a quiet box. Fix it in two ways: split the box, and cache the map view for 2 seconds.

<GoDeeper title="Go deeper: three fixes for a hot box">

**Split the box.** A quadtree (chapter 24.2) cuts the stadium box into 22 smaller ones. They can live on different shards, so the load is shared. This is the same cure as a celebrity key in chapter 9.4: a hot key that more shards cannot share must be split first.

**Cache the map view.** Thousands of fans see almost the same map. Safar computes the cars of that box once every 2 seconds and serves the copy to everyone. 4,000 searches a second become one recompute every 2 seconds. A car moves about 17 m in 2 seconds, which a map screen will not show. When a copy expires, thousands of requests must not all recompute it at once. Let one request refresh it and the rest wait or use the old copy (chapter 5.6 on stampedes and hot keys). The cache is for the map screen only. The match step must read live places, because offering a ride to a driver who has already left is worse than a slow map.

**Calm the crowd.** Slow the map refresh in a crowded box from 5 to 10 seconds, and show only the nearest 8 cars. Rider requests still go through at full speed.

Be honest about the numbers. Our measured scan of 3,000 drivers took about 0.1 ms, so 4,000 searches a second use about 40% of one core. This stadium is busy, not broken. A concert ten times larger would break it. The design must not depend on being lucky. Check the real load of the hottest box, not the average of all boxes.

</GoDeeper>

## Restart empty, refill in seconds

<InteractiveCanvas slug="sysdesign-m24-index-restart" />

A map node restarts and holds nothing. Every driver reports again within 4 seconds, so the map fills itself. Nothing was backed up, and nothing needed to be. Riders on that node see few cars for a few seconds, then all of them.

<GoDeeper title="Go deeper: expiry, standbys and what must stay safe">

The map must also forget. A driver who goes through a tunnel, or closes the app, stops reporting. Without a rule the map would show a ghost car for ever. So each entry expires if it is not renewed: Safar uses 12 seconds, three missed reports. This is a time to live (chapter 5.5). A search can skip an entry older than 12 seconds when it reads, and a sweep removes old entries in the background.

For a gap shorter than 4 seconds, run a standby for each memory node that receives the same pings. This doubles the incoming network traffic for that node but not the storage that matters, and a failover is instant. Many designs skip the standby and accept the few seconds.

What must not be only in this map? The trips. A ride that has been accepted is money and a promise to two people. It goes in a durable store (chapter 7.2). The live map is the one place where losing the data is cheap, and a good design uses that on purpose.

</GoDeeper>

<GoDeeper title="In an interview">

**Say:** "Location updates are the load, about 250,000 a second. I would not write each one to a database, because the data is out of date in 4 seconds. I keep the latest place of each driver in memory, in a map from cell to drivers, sharded by cell prefix so a search touches one or two shards. History goes to a log for other services. If a node restarts, drivers refill it within one ping interval. For a hot cell, like a stadium, I split it and cache the map view for 2 seconds."

**Expect:** "What if the cell prefix makes one shard hot?" **Answer:** "I measure the hottest cell, not the average. Then I split it, so its parts can move to other shards, and cache the read. Hashing the cell would spread the load, but every search would touch up to nine shards."

</GoDeeper>
