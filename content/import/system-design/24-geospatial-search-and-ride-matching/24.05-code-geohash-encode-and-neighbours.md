In chapter 24.2 you saw that Safar finds nearby drivers by cutting the map into boxes. A driver's box code decides which shard receives the ping (24.3), and a search reads the rider's box and the boxes around it. All of that rests on three small functions. One turns a point into a code. One turns a code back into a box. One finds the eight boxes around a box.

Each function is short, and each is easy to get slightly wrong. An encoder that starts with latitude instead of longitude passes a test on one point and puts every driver in the wrong box. A neighbour function that steps from the edge of a box instead of its middle works until a rounding error lands the answer one box off. A neighbour function that forgets the 180 degree line works in every city on the map except the ones near it. In this chapter you write all three in plain JavaScript and test them against the cases that catch those mistakes.

## What the tests do to your code

The tests are built around the places where these functions fail. For the encoder they use published examples, including `u4pruydqqvj` for latitude 57.64911 and longitude 10.40744, and `ezs42` for latitude 42.6 and longitude -5.6. They check that a longer code starts with a shorter one, and that a point exactly on a middle line goes to the upper box. For the bounds they check that the box holds the point it came from and has the right size. For the neighbours they check the eight boxes around `ezs42`, a pair of drivers 30 m apart across a box edge, symmetry (the east neighbour of the west neighbour is yourself), wrap-around at longitude 180, and the poles.

Nothing is `async`, and nothing reads a clock or a random number. Each test gives the same answer every time, and the message of a failing test names the input and what it expected.

## The contract

**`geohashEncode(lat, lon, precision = 6)`** returns a string of `precision` characters. The alphabet is `0123456789bcdefghjkmnpqrstuvwxyz`: the ten digits and the lowercase letters except a, i, l and o. Each character holds 5 bits. The first bit halves the longitude range (-180 to 180), the second halves the latitude range (-90 to 90), and they alternate from there. A bit is 1 when the value is at or above the middle of the current range and 0 when it is below. It throws a `RangeError` if `lat` is not a number from -90 to 90, if `lon` is not a number from -180 to 180, or if `precision` is not an integer from 1 to 12.

**`geohashBounds(hash)`** reverses the walk. For each character it reads 5 bits, from the highest to the lowest, and halves the same ranges. What is left is the box: it returns `{ minLat, maxLat, minLon, maxLon }`. It throws a `RangeError` for an empty string, a value that is not a string, or a character outside the alphabet.

**`geohashNeighbours(hash)`** returns an object with the eight boxes around the box, each with the same length as `hash`: `n`, `ne`, `e`, `se`, `s`, `sw`, `w` and `nw`. East of the last box in a row wraps round to the first box at longitude -180, and west wraps the other way. There is no box north of the north pole or south of the south pole, so those entries are `null`.

## A worked example by hand

First the encoder, for latitude 42.6 and longitude -5.6, two characters (10 bits). Each row halves one range and writes one bit.

| Bit | Range being halved | Middle | Value | Bit written | New range |
|---|---|---|---|---|---|
| 1 | longitude -180 to 180 | 0 | -5.6 | 0 (below) | -180 to 0 |
| 2 | latitude -90 to 90 | 0 | 42.6 | 1 (above) | 0 to 90 |
| 3 | longitude -180 to 0 | -90 | -5.6 | 1 | -90 to 0 |
| 4 | latitude 0 to 90 | 45 | 42.6 | 0 | 0 to 45 |
| 5 | longitude -90 to 0 | -45 | -5.6 | 1 | -45 to 0 |

The five bits are 01101, which is 13. The alphabet is 0 to 9, then b, c, d, e, so 13 is the letter `e`. The next five bits (1, 1, 1, 1, 1) give 31, the last letter `z`. The two-character code is `ez`, and it is the start of `ezs42`. The code never needs a power of two or a division by 32: it only halves a range and writes a bit.

Now the neighbours of `ezs42`. The bounds function gives latitude 42.5830 to 42.6270 and longitude -5.6250 to -5.5811. So a box is 0.0439 degrees tall and wide. Its middle is latitude 42.6050 and longitude -5.6030. The east neighbour is the point one width to the right, longitude -5.5591, encoded with 5 characters. That is `ezs43`. Here are all eight, as the tests expect.

| Direction | Neighbour of ezs42 |
|---|---|
| n, ne | ezs48, ezs49 |
| w, e | ezefr, ezs43 |
| s, se | ezs40, ezs41 |
| sw, nw | ezefp, ezefx |

Look at the western column. The boxes on the west side start with `ezef`, not `ezs`. They are next to `ezs42` on the map, and share only 2 letters with it. This is the same trap as chapter 24.2: neighbours can have very different codes. That is why the function works from the map and not from the letters.

## Five ways this goes wrong

**Starting with latitude.** The first bit halves longitude. If you start with latitude, `ezs42` becomes some other code and every test with a published example fails.

**Using "greater than" instead of "at least".** A point exactly on a middle line, such as latitude 0, belongs to the upper box. With a strict "greater than" the point at (0, 0) lands in the lower box and the code is not `s0000`.

**Stepping from the edge.** If you add one box height to the top edge of the box, you land exactly on a boundary, and a tiny rounding error may put you in the wrong box. Step from the middle of the box, where there are half a box of safe space on every side.

**Forgetting the wrap and the poles.** When a step goes past 180, for example to 180.02, subtract 360 to get -179.98. A latitude above 90 does not exist, so the neighbour is `null`. Without these two rules your function works everywhere except the places that matter to a ride service on a date line island or a polar route.

**Changing the length.** A neighbour must have the same number of characters as the box it came from. If you encode with the default precision, a 5-character box returns 6-character neighbours, and the symmetry test fails.

When a test fails, read its message first. Each one names the input and what it expected.

solution: |
  const BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz";

  function geohashEncode(lat, lon, precision = 6) {
    if (typeof lat !== "number" || !(lat >= -90 && lat <= 90)) throw new RangeError("lat must be a number from -90 to 90");
    if (typeof lon !== "number" || !(lon >= -180 && lon <= 180)) throw new RangeError("lon must be a number from -180 to 180");
    if (!Number.isInteger(precision) || precision < 1 || precision > 12) throw new RangeError("precision must be an integer from 1 to 12");
    let minLat = -90, maxLat = 90, minLon = -180, maxLon = 180;
    let hash = "";
    let bits = 0, index = 0, useLon = true; // the first bit is a longitude bit
    while (hash.length < precision) {
      if (useLon) {
        const mid = (minLon + maxLon) / 2;
        if (lon >= mid) { index = index * 2 + 1; minLon = mid; } else { index = index * 2; maxLon = mid; }
      } else {
        const mid = (minLat + maxLat) / 2;
        if (lat >= mid) { index = index * 2 + 1; minLat = mid; } else { index = index * 2; maxLat = mid; }
      }
      useLon = !useLon;
      bits += 1;
      if (bits === 5) { hash += BASE32[index]; bits = 0; index = 0; }
    }
    return hash;
  }

  function geohashBounds(hash) {
    if (typeof hash !== "string" || hash.length === 0) throw new RangeError("hash must be a non-empty string");
    let minLat = -90, maxLat = 90, minLon = -180, maxLon = 180;
    let useLon = true;
    for (const ch of hash) {
      const value = BASE32.indexOf(ch);
      if (value === -1) throw new RangeError("not a geohash character: " + ch);
      for (let i = 4; i >= 0; i--) {
        const bit = (value >> i) & 1;
        if (useLon) {
          const mid = (minLon + maxLon) / 2;
          if (bit) minLon = mid; else maxLon = mid;
        } else {
          const mid = (minLat + maxLat) / 2;
          if (bit) minLat = mid; else maxLat = mid;
        }
        useLon = !useLon;
      }
    }
    return { minLat, maxLat, minLon, maxLon };
  }

  function geohashNeighbours(hash) {
    const b = geohashBounds(hash);
    const height = b.maxLat - b.minLat;
    const width = b.maxLon - b.minLon;
    const centreLat = (b.minLat + b.maxLat) / 2;
    const centreLon = (b.minLon + b.maxLon) / 2;
    // Step from the centre of the box, never from an edge, so rounding cannot push us into the wrong box.
    const at = (stepLat, stepLon) => {
      const lat = centreLat + stepLat * height;
      if (lat > 90 || lat < -90) return null;
      let lon = centreLon + stepLon * width;
      if (lon > 180) lon -= 360;
      if (lon < -180) lon += 360;
      return geohashEncode(lat, lon, hash.length);
    };
    return { n: at(1, 0), ne: at(1, 1), e: at(0, 1), se: at(-1, 1), s: at(-1, 0), sw: at(-1, -1), w: at(0, -1), nw: at(1, -1) };
  }

## Check your understanding before you submit

Run one more case in your head. Safar's rider stands at latitude 30.05 and longitude 31.201016, and a driver stands at the same latitude and longitude 31.201328. They are 30 m apart. Encode both with 6 characters. The rider is in `stq4vy` and the driver is in `stq4yn`. They share 4 letters, which would suggest a 39 km by 20 km area, yet they are 30 m apart. The east neighbour of `stq4vy` is `stq4yn`. That one fact is why a ride service reads nine boxes instead of one.

Now try the other trap. Take latitude 0.0001 and longitude -0.0001, and the point just east of it at longitude 0.0001. They are 22 m apart. Their codes are `ebpbpb` and `s00000`, and they do not share the first letter. A search that trusted prefixes would put these two points on opposite sides of the world. The neighbours function does not, because it works from the box and not from the letters.

## How to say it in an interview

**Say:** "A geohash alternates longitude and latitude bits, five bits to a character, so a longer code names a smaller box inside the bigger one. To find the boxes around a box I compute its middle and its height and width, step one box in each direction, and encode again at the same length. I step from the middle so rounding cannot push me into the wrong box, wrap longitude at 180, and return nothing past a pole. Then I measure the true distance, because the boxes only narrow the list."

**Expect:** "Why not look up neighbours by changing the last letter?" **Answer:** "At the edge of a parent box the neighbour has a different parent, so several letters change. Stepping on the map and encoding again is simpler and always right."

## What this unlocks

Encoding is the first step of every ping and every search in Safar, and the neighbours function is the second step of every search. With them, chapter 24.3's map can be a plain `Map` from box code to drivers. The wider idea, turning a two-direction question into a few lookups of keys, comes back anywhere an index has more than one dimension: time and place, price and rating, or two coordinates in a game world. Chapter 24.7 asks you to use these ideas on scenarios you have not seen.
