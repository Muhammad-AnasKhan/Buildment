## Twenty-three comments

Waleed is a backend developer at a small startup. He opens a pull request (a request to add his code to the main project) and asks Dalal to review it. An hour later he sees 23 comments.

Most are about small things: a variable name, an extra empty line, a different way to write a loop. One comment, in the middle, says the new endpoint lets any logged-in user delete another user's account. Every comment has the same tone and the same format.

Waleed works through the list from the top. He fixes the names and the empty lines. It is late, the power is about to go, and he misses the security comment. The code is merged with the bug.

Dalal found the most important problem. Her review still failed, because it did not show which comment mattered.

## Must change or optional?

A good review puts every comment in one of two groups.

| Must change | Optional suggestion |
|---|---|
| A bug, or something that will break | Your personal style or taste |
| A security or privacy risk | Another way that works equally well |
| Wrong facts, numbers or names | Small wording changes |
| It breaks a rule the team agreed on | An idea for a later version |
| Users or readers will be confused or misled | A tiny detail that does not change the result |

The question to ask is: **"If this stays as it is, what goes wrong?"** If the answer is "something breaks, someone is harmed or misled, or a team rule is broken", it must change. If the answer is "it would just be different from how I would do it", it is a suggestion.

## Label every comment

Make the group visible. Start each comment with a short label, so the author can see at once what matters:

```text
Must change: This endpoint deletes any account by ID, but it
does not check that the ID belongs to the logged-in user. Any
user could delete someone else's account. Can we add an
ownership check here?

Suggestion: This loop could use map() to be a bit shorter.
Happy either way.

Question: Why is the timeout 60 seconds? I'm not sure what
the right value is, so I'd like to understand.
```

In code review, many teams also write **nit** (short for "nitpick", a very small detail) at the start of a tiny optional point. Use whatever labels your team uses, as long as everyone knows which ones must be fixed.

A short summary at the top also helps: "Two must-change points, four suggestions. Ready to merge once the two are fixed." Put the must-change points first.

## Write comments people can act on

The SBI ideas from chapter 2.2 work here too. A useful review comment:

- **Points to the exact place:** the line, the paragraph, the table.
- **Says what and why:** what the problem is and what goes wrong because of it.
- **Offers a way forward:** a fix, an example, or a question.
- **Talks about the work, not the person:** "This function does not check the ID", not "You forgot security again".

Written comments sound harsher than spoken ones, especially across languages. A short "Nice, this is much easier to read than before" costs you five seconds and tells the author what to keep.

## Reviewing a document

The same rules apply to a grant proposal, a README or a client report. Wrong numbers, missing required sections and claims the team cannot support are must-change. A sentence you would write differently is a suggestion. If you are not sure, write it as a question.

<Callout type="warning" title="Do not turn taste into rules">
If you mark your personal style as "must change", authors stop trusting your labels. Keep "must change" for real problems, and your must-change comments will be taken seriously.
</Callout>
