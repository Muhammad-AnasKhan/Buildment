# 8.2 — IDOR and marketplaces

> **[Read]** · Chapter 08 — Authorization & isolation · *Vendor B edits Vendor A's store — real breach pattern*

**Insecure Direct Object Reference (IDOR)** — also called **BOLA** (Broken Object Level Authorization) in OWASP API Top 10 — is the #1 marketplace breach pattern: change an id in the URL, access someone else's data.

<BigWordAlert term="IDOR" plainEnglish="Insecure Direct Object Reference — changing an ID in the URL to access someone else's data." whyItMatters="FreshMarket must verify product.storeId matches the requesting vendor — otherwise any vendor edits any catalogue." />

## Classic attack

IDOR is the most boring-looking attack in security — no malware, no exploit, just a changed number. That is exactly why it is so common: it needs nothing more than a logged-in user and a guessable id. Watch how it plays out:

Vendor A is authenticated. Legitimate request:

```
PATCH /api/stores/STORE_A_ID
Authorization: Bearer <vendor A token>
```

Attacker changes id:

```
PATCH /api/stores/STORE_B_ID
Authorization: Bearer <vendor A token>
```

**Vulnerable API:** Updates Store B — Vendor A renamed competitor's shop.

**Secure API:** **403 Forbidden** — ownership check failed.

The id in the URL is just a *reference*. The question every route must answer is: "whoever holds this id — do they own it?" If that check is missing, the reference becomes a key to anyone's data.

## Why marketplaces are high risk

Marketplaces are a special target because every resource is *someone else's* money. The impact column below is why the OWASP API Top 10 ranks this as the #1 API risk — not because it is clever, but because it is trivial to exploit and devastating when it lands.

| Resource | IDOR impact |
|---|---|
| Store | Rebrand competitor, change address |
| Product | Change price to £0.01, delete inventory |
| Order | View customer PII, mark shipped falsely |
| Cart | Merge or view another user's cart |

One missing check on PATCH becomes front-page incident.

## Auth without authorization fails

Authentication gets you *into the building*; it says nothing about which rooms you may enter. If your pipeline stops after auth, every authenticated user can reach every resource — which, in a marketplace, means every vendor can reach every other vendor's shop.

```
✅ requireAuth — proves token valid
❌ stops here — any vendor hits any storeId
✅ requireRole('vendor') — proves role
❌ stops here — Vendor A still hits Store B
✅ assertStoreOwner(storeId, req.user.id) — proves object ownership
```

All three layers for mutating vendor resources.

## Real-world pattern

In a real breach, the API returns 200 with a generic message and the attacker just walks id-by-id, harvesting everything reachable. Consistent, unambiguous status codes are part of the defense — 403 tells the client (and your logs) exactly what happened.

API returns 200 with generic message — attacker enumerates ids. Use **403** consistently; optional 404 to hide existence — course uses **403** for clarity in tests.

Document store ids in test notes — not secrets.

## Client is not trusted

A common beginner assumption is that the UI *is* the security: "I hid the edit button, so nobody can edit." Hidden form fields, React props, and disabled buttons are all trivially bypassed — the attacker does not use your UI at all, they use curl. **Every mutating route validates server-side.**

## Common beginner mistakes

1. **Relying on "secret" ids** — MongoDB ObjectIds look random, but they are guessable and often leak through other endpoints. Obscurity is a speed bump, not a lock.
2. **Checking ownership in the UI only** — hiding the button is UX, not security; the API must reject the request itself.
3. **Returning 401 for a wrong owner** — the user *is* authenticated; a 401 triggers the client's refresh loop and hides the real problem. Wrong owner is 403.
4. **Only testing the happy path** — the IDOR test (Vendor B on Store A) is the test that matters; if you only ever test with the owner, the missing check goes unnoticed.

## ✅ Do / ❌ Don't

**✅ Do:** Test IDOR with two seed vendors every chapter adding PATCH/DELETE.

**✅ Do:** Log ownership failures in dev — not in production response body.

**❌ Don't:** Rely on UI hiding edit buttons for security.

**❌ Don't:** Return 401 for wrong owner — user IS authenticated → **403**.
