# 8.5 — RBAC and ownership

> **[Learn]** · Chapter 08 — Authorization & isolation · *Role check + store chain lookup*

FreshMarket uses **two-layer authorization**: role-based access control (RBAC) at the route, then **ownership chain lookup** at the object.

<BigWordAlert term="Role-based access control" plainEnglish="Permissions tied to user role — vendors manage stores, customers browse and buy, admins oversee all." whyItMatters="FreshMarket's `requireRole('vendor')` middleware blocks customers from product create routes." />

## Roles (RBAC)

Roles are the coarse-grained layer: they decide *which kind of user* may even reach an endpoint. FreshMarket has exactly two, and no admin role in the MVP — keeping the set small keeps the matrix readable.

| Role | Description |
|---|---|
| vendor | Operates one store, products, vendor orders |
| customer | Browses, cart, checkout, own orders |

No admin role in MVP.

**requireRole('vendor')** — rejects customer token with 403 before handler runs.

## Ownership chain lookup

Roles tell you *who may enter the room*; ownership tells you *which room they may touch*. When a route mutates an object by id, the server must load that object and confirm it belongs to the caller — it can never trust the caller's claim. For stores the check is direct; for products it walks one extra hop (product → store → owner), because products are owned through their store.

For mutating Store identified by `:id`:

```
1. store = await Store.findById(storeId)
2. if !store → 404 Not Found
3. if store.userId.toString() !== req.user.id → 403 Forbidden
4. proceed
```

For Product (Ch 11 preview):

```
1. product = await Product.findById(productId)
2. store = await Store.findById(product.storeId)
3. if store.userId !== req.user.id → 403
```

**Never trust client-sent userId or storeId in body** for authorization — derive from token + DB.

## Helper function contract

Ownership logic repeats on every vendor route, so it lives in one helper rather than being copy-pasted. A single `assertStoreOwner` means one place to audit when a future chapter adds a new route — and one place to fix if the logic ever changes.

```
assertStoreOwner(storeId, userId) → void | throws ForbiddenError
```

Centralize in `shared/ownership.js` — used by store routes, product routes, order status updates.

Throws or returns `{ ok: false }` — consistent error type for route handlers.

## Combined stack example

This is the full pipeline for a mutating vendor route. Read it as a filter: each stage rejects a different kind of bad actor, and the ones that slip past are caught by the next stage.

**PATCH /api/stores/:id**

| Step | Middleware / logic |
|---|---|
| 1 | requireAuth |
| 2 | requireRole('vendor') |
| 3 | assertStoreOwner(req.params.id, req.user.id) |
| 4 | storesService.updateStore(...) |

Customer never reaches step 3 with vendor-only route — blocked at step 2.

Vendor B reaches step 3 — blocked with 403.

## Customer-scoped resources

Not every resource is owned through a store chain. Cart items and orders belong to a *customer* directly, so the ownership check is a single field match — no chain to walk. Recognizing when a resource is chain-owned versus directly-owned is the modelling half of authorization.

Cart and orders use **direct userId match**:

```
CartItem.find({ userId: req.user.id })
Order.find({ customerId: req.user.id })
```

No store chain — different ownership model.

## Matrix preview (full doc in 8.8)

The matrix is how you *prove* a route is safe without reading every handler. Each row names the role and the exact ownership check — if you can write a row, you can implement it.

| Action | Role | Ownership check |
|---|---|---|
| PATCH /stores/:id | vendor | store.userId |
| POST /products | vendor | caller's store exists |
| PATCH /products/:id | vendor | product → store → userId |
| GET /cart | customer | cart.userId |
| GET /vendor/orders | vendor | order.storeId → store.userId |

## Performance note

Every ownership check is one extra database read per mutating request. That cost is trivial at marketplace scale — correct authorization is worth far more than a millisecond. Only if a handler runs several ownership checks should you cache the loaded store on `req` for reuse.

Ownership check adds one DB read per mutating request — acceptable for MVP. Cache storeId on req in handler if multiple checks — optional.

## Common beginner mistakes

1. **Trusting `:id` from the URL without a DB lookup** — the id is just a claim; the DB is the only source of truth for who owns the record.
2. **Comparing ObjectIds with `==`** — ObjectId vs string comparisons silently fail. Use `.toString()` or `.equals()`.
3. **Only requiring the role** — `requireRole('vendor')` makes *every* vendor able to touch *every* store; the ownership check is the layer that actually isolates tenants.
4. **Putting ownership logic inline in each handler** — it drifts. One `assertStoreOwner` helper is auditable; five copies are not.

## ✅ Do / ❌ Don't

**✅ Do:** Compare ObjectIds with `.toString()` or `equals()`.

**✅ Do:** 404 when store id invalid — optional vs 403 hide existence.

**❌ Don't:** Skip store lookup — trusting :id from URL without DB verify.
