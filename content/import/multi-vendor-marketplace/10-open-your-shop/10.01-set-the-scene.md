# 10.1 — Set the scene

> **[Read]** · Chapter 10 — Open your shop · *Vendor lands after login — no store yet*

**Where the project is now:** Chapter 9 gave vendors a **store API** — create, fetch mine, update — proven with curl. A logged-in vendor can open a shop programmatically. The React app still treats every vendor like any other authenticated user: no shop setup screen, no settings page, no gate blocking dashboard routes.

**Where this chapter goes:** Vendors **open and manage their shop in the browser** — setup form, settings form, and an onboarding redirect that forces storeless vendors through `/vendor/open-shop` before they reach product pages.

This is a **build chapter**. Every sub-chapter from 10.5 onward adds client routes and pages. The gate is **runnable proof**: new vendor registers → forced to open shop → can edit settings → cannot reach product routes until store exists.

## Bridge from last chapter

Chapter 9 gave vendors a **store API** — `POST /stores`, `GET /stores/me`, `PATCH /stores/:id` — all proven with curl and protected by Chapter 8 middleware. A developer can open a shop; a **human vendor** still sees the same generic React app as everyone else. Chapter 7 taught the login UI pattern; Chapter 10 applies it to **vendor onboarding**: forms, settings, and a redirect gate that sends storeless vendors to "Open your shop" before they reach inventory routes.

## In plain English

| Term | Simple meaning |
|---|---|
| **Onboarding gate** | Router check that blocks dashboard pages until a store exists |
| **Vendor layout** | Shared shell — nav, header — for all `/vendor/*` pages |
| **Open your shop** | First-time setup form — name, description, address |
| **Store settings** | Edit page for an existing shop — calls `PATCH /stores/:id` |
| **`GET /stores/me` → 404** | Signal: no shop yet — trigger onboarding redirect |
| **Protected route** | Page that requires login — from Chapter 7, extended with store check |

## Think of it like a shop lease signing

Chapter 9 built the **registry office** where stall applications are filed. Chapter 10 is the **counter where the vendor actually signs** — a form in the browser, not a curl command. If they try to walk into the stockroom (`/vendor/products`) before signing, security sends them back to the lease desk. Same API underneath; humans get screens.

## Common beginner questions

**Q: Why another frontend chapter — didn't Chapter 7 cover React?**  
A: Chapter 7 was authentication UI for everyone — login, register, verify, protected routes. Chapter 10 is vendor-specific shop UI: a setup form, a settings page, and an onboarding gate, none of which Chapter 7 touched. Think of Chapter 7 as teaching the front door lock, and Chapter 10 as building a whole new room behind it. The patterns carry over — `useAuth`, protected routes, API helpers — but the features are new: a storeless vendor must be funneled to "Open your shop" before reaching any dashboard page. Same toolbox, different job.

**Q: Can I build product pages here since the vendor is already logged in?**  
A: No — stay on shop identity only. Products get their own chapters: the API in Chapter 11 and the dashboard UI in Chapter 12. There's a practical reason for the split: each chapter has a small, testable gate. If you smuggle product forms in now, you're debugging store onboarding *and* product CRUD at once, and when something breaks you won't know which feature caused it. Chapter 10's deliverable is narrow: a vendor can open a shop and edit its settings. Stocking shelves comes next.

**Q: What happens when `GET /stores/me` returns 404?**  
A: That 404 is the onboarding trigger, not an error. It's the API's way of saying "this vendor has no store yet", and the React app turns that into a redirect to `/vendor/open-shop` — the setup form. So the flow reads like a conversation: the app asks "do you have a store?", the server answers "no", and the app responds "then let's make one". The same check works in reverse: once a store exists, `GET /stores/me` returns 200 and the gate lets the vendor through to the dashboard.

**Q: Do customers see these pages?**  
A: No. Everything under `/vendor/*` — the open-shop form, store settings, the vendor layout — is for sellers only, and the routes are protected by the vendor role check from Chapter 8. A customer who tries to visit `/vendor/open-shop` gets redirected or blocked just like any other protected route. Customers get their own experience in Week 3: browsing the catalogue, carts, and orders. Your job this chapter is the vendor side only, so don't build customer screens here.

**Q: Do I need new server endpoints?**  
A: Usually not. Chapter 9's API — `POST /stores`, `GET /stores/me`, `PATCH /stores/:id` — powers every screen in this chapter: the setup form calls `POST /stores`, the gate calls `GET /stores/me`, and settings calls `PATCH /stores/:id`. That's the payoff of building the API first. The only exception is if you discover a real gap while testing — say, a field the store model doesn't have. That's fine, but add it deliberately and document it, not because the UI "felt" like it needed something.

**Q: What if a vendor bookmarks `/vendor/products` before opening a shop?**  
A: The onboarding gate catches them. It's a router-level check that runs whenever a vendor dashboard page loads, not just once at login — so a bookmark, a refresh, or a fresh session all get the same treatment. When the page tries to load, the app calls `GET /stores/me`; a 404 means "no shop yet", and the app redirects to `/vendor/open-shop` before the product page renders. That's the difference between a button someone can skip and a gate enforced on every path into the vendor area.

## The onboarding story (user narrative)

1. Maya registers as vendor, verifies OTP, logs in.  
2. App checks `GET /stores/me` → **404** — no shop yet.  
3. Router sends her to **Open your shop** — name, description, address.  
4. Submit → `POST /stores` → **201**.  
5. Redirect to vendor dashboard home (product list comes in Ch 12).  
6. Later she edits blurb in **Store settings** → `PATCH /stores/:id`.  

If she bookmarks `/vendor/products` before step 4, the **gate** sends her back to open-shop.
