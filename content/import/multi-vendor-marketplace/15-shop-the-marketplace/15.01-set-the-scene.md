## Bridge from last chapter

Chapter 14 gave you a **public catalogue API** — `GET /products` with filters, pagination, store names, and photos. You proved it with curl: paginated JSON from multiple vendors, query count not exploding (N+1 fixed).

What Chapter 14 did **not** give you: anything a normal person would call a **shop**. Humans do not browse groceries with terminal commands.

What you carry into Chapter 15:

| From Chapter 14 | What the UI needs it for |
|---|---|
| `GET /products?page=&limit=&category=&storeId=` | Shop grid + filters + pagination controls |
| `GET /products/:id` | Product detail page before add-to-cart |
| `store.name` on each item | "Sold by Green Valley" on every card |
| `imageUrl` | Product photos on cards and detail |
| Stable public DTO | React displays what API returns — no duplicate filter logic |

If Chapter 14 gate is incomplete — especially N+1 verification and two-store seed — **finish that first**. Chapter 15 will hammer `GET /products` on every filter change; a slow or wrong API becomes a slow or wrong shop.

## In plain English

| Term | Simple meaning |
|---|---|
| **Storefront / shop page** | The customer-facing product grid — `/shop` in the browser |
| **Product card** | One tile: photo, name, price, store name, link to detail |
| **Filter bar** | Controls that narrow the catalogue (category, store) and refetch from API |
| **Pagination UI** | Prev/Next or page numbers that change the `page` query param |
| **API client helper** | A small function in `client/src/api/` that calls `GET /products` — keeps fetch logic out of components |
| **Add-to-cart stub** | Button on detail page that exists visually but does not POST yet — wired in Chapter 17 |

## Think of it like turning the API into a shop window

Chapter 14 built the **inventory computer** in the back office — accurate, filtered, paginated. Chapter 14 is the spreadsheet; Chapter 15 is the **glass display** customers actually look at.

Same products. Same prices. Same store names. Now with photos, whitespace, and a URL your roommate can open without knowing what curl is.

## Common beginner questions

**Q: Why not build the shop UI in the same chapter as the API?**  
A: Because splitting keeps each gate testable on its own. Chapter 14 proved `GET /products` with curl — right JSON, right filters, no N+1. Had the UI lived in the same chapter, a bug could hide in either place and you'd debug both at once. With the split, when the grid looks wrong you know the API isn't the culprit: it already returned clean data. API proven with curl, UI proven in the browser — when things break, you know which half to blame.

**Q: Do I need to be logged in to browse?**  
A: Not for the Chapter 15 gate — the shop is a public storefront, so anyone can browse without an account. Login only matters once a customer wants to do something persistent, like add to cart. The add-to-cart button on the detail page is a visual stub this chapter; the real wiring comes in Chapter 17, and that's when the customer token becomes necessary. So don't bolt auth onto the shop grid yet — keep browsing public for now.

**Q: Should I filter products in React after one big fetch?**  
A: No. The API already supports filtering with query parameters and it paginates — it returns one page at a time, not the whole catalogue. If you fetched everything once and filtered in browser memory, you'd break pagination, download hundreds of products into the tab, and duplicate logic the server already has. Instead, send `category` and `storeId` (and `page`) as query parameters and refetch on every filter change. The server stays the single source of truth for what gets shown.

**Q: Why is the add-to-cart button not doing anything?**  
A: That's intentional — this chapter builds the shop window, not the cart. The spec says the button on the product detail page is a stub: it exists visually and maybe shows a toast or a console log, but it does not POST anything yet. The real wiring comes in Chapter 17, after the cart API exists in Chapter 16. So don't chase a bug; the "bug" is the planned roadmap. A visible-but-inert button marks exactly where the next chapter plugs in.

**Q: Where does each product card get its data?**  
A: Directly from the API response — one card field maps to one API field. `imageUrl` becomes the photo, `name` the title, `price` with `unit` the price line, and `store.name` the "Sold by Green Valley" label. Because Chapter 14 already handled publish/stock filtering and pagination on the server, your React component just renders what `GET /products` returns — it should not re-check whether a product is published or in stock. Duplicate that logic in React and you get two sources of truth that drift apart.

**Q: My images don't show — where do I look first?**  
A: Work backwards through the chain. First check the API response: does the product actually have an `imageUrl`? If the seed or Chapter 13 upload never ran, it's empty. Then check your card component — is `<img src={product.imageUrl}>` actually using the field? Finally, open the browser network tab and look at the failed request: a 404 means the URL points at a file that doesn't exist on Cloudinary. One of those three steps is where the answer hides.

## The gap between "API catalogue" and "marketplace window"

Your API can answer catalogue queries via curl. Humans need:

- Visual grid with photos and price per unit  
- Filters that feel instant  
- Product detail before add-to-cart  
- Navigation that says "shop" not "developer console"

Chapter 15 is the **frontend pair** to Chapter 14 — same pairing pattern as 07, 10, 12.

## Editorial design intent

FreshMarket uses a **clean editorial style** — name the product yourself, but the UI pattern is:

- Generous whitespace  
- Product card: photo, name, price/unit, store name  
- Filters as horizontal bar — not heavy e-commerce chrome  
- Pagination or load-more — not infinite scroll required for gate

Match vendor dashboard typography where sensible — one design system.
