# 15.12 — Quiz

> **[Check]** · Chapter 15 — Shop the marketplace · *Three questions: filter and page state, refetch versus client-side filtering, cart-ready detail data*

The shop can look finished while three decisions underneath it are still wrong. Each scenario below puts you at one of those decision points.

```quiz
type: mcq
id: q1
question: A shopper is on page 5 of the shop grid and then picks fruit in the category dropdown. The handler updates the category but leaves page state at 5. What does the shopper most likely see?
options:
  - A full page of fruit, since the API re-sorts on category
  - The same twenty products, because the API ignores the filter
  - An empty grid, because fruit has fewer than five pages
  - A 404 from the route, because page 5 no longer exists
correct: 2
explanation: "A filter change has to reset page to 1 before the refetch. Page 5 of the fruit results is normally past the end of a much shorter list, so the API returns an empty page and the shopper reads it as a broken filter. The tempting first option assumes the API quietly rewinds you to page 1 when the category changes — it filters inside the page window you asked for, and keeps returning page 5."
```

```quiz
type: mcq
id: q2
question: A teammate's filter handler keeps the twenty items already on screen and hides the non-matching ones in React whenever a shopper picks a store. Testers report that the filtered results are missing products. What is the cause?
options:
  - One page is filtered, so later pages never show
  - Store name casing differs from the seeded values
  - Grid CSS hides any card that sits below the fold
  - The API returns drafts because no token is sent
correct: 0
explanation: "The grid only ever holds the twenty items of the current page, so hiding non-matching cards filters a slice rather than the catalogue — every product on that store's later pages is simply absent. The casing and CSS options are real bugs worth checking, but both would hide a card that did load; here the missing products were never in the payload, which the Network tab shows as a request with no storeId param."
```

```quiz
type: mcq
id: q3
question: The detail page's add-to-cart stub logs productId and quantity. Chapter 16 groups cart lines by vendor, so each line posts a storeId too. What should the stub capture now?
options:
  - The store name, so the cart can group its lines
  - The full product, so nothing is lost later on
  - The category, so checkout can group by aisle
  - The store id already on the product it loaded
correct: 3
explanation: "The detail page already fetched the whole product, store.id included, so capturing it costs nothing and Chapter 17 becomes one handler swap. The store name is the tempting near-miss — it groups nothing reliably, because two vendors can share a name and a rename would break every cart line already written. Keeping the full product is closer but hides what the cart contract actually needs."
```
