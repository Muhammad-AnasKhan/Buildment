# 23.4 — VPS vs PaaS

> **[Learn]** · Chapter 23 — Deploy · *Options; pick one path for course*

Pick **one deploy path** for this course. Document in README — not every option.

This decision affects how you set env vars, run the worker, inspect logs, roll back a bad release, and renew TLS. There is no universally best choice. Pick the option whose failure modes you can operate and explain.

## Options comparison

| Approach | Operational help | You still own |
|---|---|---|---|
| PaaS API + worker | Builds, service restart, logs, TLS, env UI | Correct commands, health checks, scaling and rollback |
| Static client host | CDN, atomic asset deploys, TLS | Build-time API URL, SPA fallback, cache behavior |
| Single VPS | Full machine and network control | OS patches, firewall, proxy, TLS, process restart, backups |

## Course recommendation

**Beginners:** a PaaS web service for the API, a second service for the worker, and a static client host reduce Linux administration. Confirm the current provider supports every process before starting.

**Comfortable with Linux:** a single VPS with Caddy or Nginx and a process manager exposes more of the stack, but the result is only stronger if you also configure firewall rules, automatic restart, certificate renewal, and security updates.

**Mandate:** HTTPS on both client and API. HTTP-only gate fails.

## Worker deployment per path

| Path | How worker runs |
|---|---|
| Render / Railway | Second service, same repo, start command `npm run worker` |
| VPS + PM2 | `pm2 start src/worker.js --name worker` + `pm2 save` |
| Fly.io | Second process in `fly.toml` or separate app |

**Never** assume checkout notifications work without verifying worker service in host dashboard.

## CORS production

Update `app.js` CORS `origin` to production client URL — not `localhost:5173` only.

Typical env key: `CLIENT_ORIGIN=https://app.yourdomain.com`

Browser login fails with cryptic CORS errors if this still points at local dev.

## MongoDB Atlas

Allow deploy host IP or use `0.0.0.0/0` with strong password for PaaS (IPs change). Document security tradeoff in learning log.

Worker and API **both** need `MONGODB_URI` if processor loads User/Order documents.

## In plain English

| Term | Simple meaning |
|---|---|
| **PaaS** | Platform runs the server for you — you push code, they handle machine |
| **VPS** | You rent a virtual Linux computer — you install Node, nginx, PM2 yourself |
| **Static host** | Serves pre-built HTML/JS/CSS files — no Node server for React in production |

## Think of it like housing

**PaaS** = furnished apartment — utilities included, less control, faster move-in.

**VPS** = empty flat — you bring furniture (nginx, PM2, certs), but you own the layout.

Both are valid homes for FreshMarket. Pick one and document it — do not half-deploy on three platforms.

## Common beginner questions

**Q: Can I deploy client and API on the same Vercel project?**  
A: Not the Express API and worker. Vercel is built for static sites and serverless functions, which don't fit a long-running Express server or a worker process that must stay alive to watch Redis. The typical split is Vercel for the built React client, and Render or Railway for the API plus a second worker service. You're not picking one host — you're picking where each of the three pieces lives.

**Q: Do I need a custom domain?**  
A: No — the gate passes with platform HTTPS URLs like `*.onrender.com` and `*.vercel.app`. A custom domain is portfolio polish, not a requirement. What *is* required is HTTPS: an HTTP-only URL fails the gate, because secure cookies and professional demos both need the padlock. If you add a domain later, it's configuration on top of the same app, not a re-architecture.

**Q: What is a cold start?**  
A: Some hosting plans stop an idle service and boot it when the next request arrives. Measure the behavior on your chosen plan, note it in the README, and make health-check expectations match reality. Do not assume every slow or failed first request is a cold start; inspect service logs.

**Q: How do I decide between PaaS and VPS?**  
A: Match the choice to your comfort level, not to what sounds impressive. PaaS (Render, Railway) is a furnished apartment: HTTPS and env vars are handled, you push code and move in fast. A VPS is an empty flat: you install Node, nginx or Caddy, PM2, and TLS yourself — more setup, but you understand every layer, which makes a stronger viva story. The course requires only that you pick one path, document it, and not half-deploy on three platforms.

**Q: Why does CORS need the production client URL?**  
A: CORS is the browser's rule for which origins may call your API. If your API only allows `localhost:5173`, the deployed site at `https://app.yourdomain.com` gets blocked, and login fails with those confusing "blocked by CORS policy" errors. So you set the CORS `origin` in `app.js` — or `CLIENT_ORIGIN` in env — to the production client URL. It's one of the most common deploy bugs: the app works locally, then mysteriously breaks in production.

**Q: Why is the React app called "static" in production?**  
A: Because after `npm run build`, your React app is just a folder of HTML, CSS, and JavaScript files in `client/dist/` — no Node server needed to serve them. A static host like Vercel stores those files and serves them fast; the React code runs in the browser. That's also why `VITE_API_URL` must be correct at build time: the bundle is frozen, and the static host serves exactly what you built.

## ✅ Do / ❌ Don't

**✅ Do:** Match `VITE_API_URL` to deployed API including `https://`.

**✅ Do:** Deploy worker as explicit second service — not an afterthought.

**❌ Don't:** Deploy API without setting all env vars on host.

**❌ Don't:** Leave CORS on localhost only.
