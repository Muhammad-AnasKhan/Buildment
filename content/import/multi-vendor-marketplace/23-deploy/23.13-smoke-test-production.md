# 23.13 — Smoke test production

> **[Build]** · Chapter 23 — Deploy · *Health, login, Stripe test checkout, worker on live URL*

Deployed is not done. A health route proves one process can answer one request; it does not prove browser CORS, cookies, Stripe webhooks, Redis queues, or the worker. This smoke test follows a single traceable checkout across those boundaries.

**Where the project is now:** Client and API on HTTPS (23.10–23.12); env for API and worker (23.8); worker deployed — **must be running**.

**After this step:** Critical paths on **live HTTPS** verified; worker processes checkout job; results in README.

Prove the **deployed system** — API, client, MongoDB, Redis, Cloudinary, **and worker**. Health-only fails gate. Chapter 22.15 proved async locally — repeat on public URLs.

## Prepare a traceable test

Use Stripe test mode, dedicated production-smoke customer and vendor accounts, and products that are clearly marked as test data. Open API and worker logs before starting. Record the API revision, worker revision, client revision, time, and a request or checkout ID so you can connect evidence across services.

## Smoke test script — mandatory

| # | Test | Pass criteria |
|---|---|---|
| # | Boundary | Pass evidence |
|---:|---|---|
| 1 | API readiness | HTTPS `/health` succeeds and required dependencies are ready |
| 2 | Browser auth | Login and protected-page refresh work without CORS or cookie errors |
| 3 | Catalogue | Product image and data come from production services; search returns it |
| 4 | Cart | Add two vendors' products; refresh preserves the cart |
| 5 | Stripe test checkout | Test payment succeeds; webhook updates orders; cart clears at the intended point |
| 6 | Worker | Matching job is consumed; retries create one observable notification effect |
| 7 | Customer result | Order history shows both vendor orders with immutable price snapshots |
| 8 | Vendor result | Each vendor sees only its own order |

The checkout ID or PaymentIntent ID should connect rows 5–8. A generic startup log is not evidence that the worker consumed this checkout.

## Worker smoke test — contract

Verify worker **consuming** — not just Redis up or checkout 201.

| Method | Pass criteria |
|---|---|
| Logs | Tail worker **during** row 5 paid checkout |
| Pattern | `[NOTIFY]` from Ch 22.12 |
| Timing | Within your documented queue target |
| Multi-store | Two-store cart → multiple notify lines |
| Durability | Stop worker, enqueue one test-mode checkout job, restart, and confirm the queued job reaches a completed state |

If there is no matching job, compare API and worker `REDIS_URL` fingerprints, queue name, deploy revision, and processor logs. Do not paste the Redis URL itself into the README or learning log.

## Rollback rehearsal

A release is not operationally safe until you know how to leave it. Identify the last known-good API, worker, and client revisions. Rehearse the host's rollback mechanism with a low-risk release or redeploy the same known-good revision, then repeat readiness and browser-auth checks.

Record:

- which revision and configuration snapshot you would restore;
- whether API and worker must roll back together because the queue payload changed;
- whether a database change is backward compatible;
- how the client CDN and `index.html` cache are refreshed;
- who decides to roll forward instead of back when payment data has already been written.

Never use a destructive database reset as rollback. Application rollback cannot undo orders or payments; schema and data changes require forward-compatible migrations or a separate recovery plan.

## README contract

Record date, URLs, deployed revisions, worker service name, sanitized checkout correlation ID, rows 1–8, and rollback target. Do not include tokens, credentials, customer PII, or raw environment values.

## Failure modes

| Symptom | Likely cause |
|---|---|
| Health OK, else fails | Wrong `VITE_API_URL` in client |
| 201, no worker log | Worker down; wrong `REDIS_URL` |
| Checkout 500 | Inspect correlated API and Stripe test-mode logs; do not guess |
| Login browser-only fail | Cookie / CORS |
| Search empty | Redis index — Ch 21 |

## ✅ Do / ❌ Don't

**✅ Do:** Run the critical rows after every release; run the full matrix before the chapter gate.

**❌ Don't:** Health-only gate; skip row 6 because 201 passed.

**❌ Don't:** Test localhost post-deploy; assume deploy = worker running.
