# 23.10 — Deploy API and worker

> **[Build]** · Chapter 23 — Deploy · *Server on VPS/Render/Railway; PM2 or native*

**Why this step matters:** The API is the brain — auth, checkout, cache, and job enqueue all live here. Until `/health` returns 200 on HTTPS with `db: connected`, nothing else in production can work.

**Where the project is now:** Full marketplace runs on localhost (Ch 2–22); production env checklist and client build are prepped (23.8–23.9) — the API has no public URL.

**After this step:** Express is reachable at an HTTPS origin, the worker is connected to the same queue, and both services have identifiable logs and a previous release to roll back to.

## Deploy contract — you implement per host

| Step | Spec |
|---|---|
| Push code | Git deploy or image build |
| Install deps | Use the repository's lockfile and production install command |
| Set env | All keys from 23.8 |
| Start command | `node src/server.js` or `npm start` |
| Process manager | PM2, systemd, or PaaS native restart |

**Listen on `process.env.PORT`** — host sets dynamically on PaaS.

Use the package manager that owns the lockfile. If the project uses pnpm, an `npm ci` command is not reproducible. Build and start API and worker from one Git commit so they agree on queue names and payload shapes.

## Deploy the worker separately

Create a second long-running service from the same revision:

| Property | API | Worker |
|---|---|---|
| Start command | `npm start` or project equivalent | `npm run worker` |
| Port | Binds `process.env.PORT` | No HTTP port unless you built a health endpoint |
| Shared dependency | MongoDB and Redis as used by API | Same Redis queue; MongoDB if processors use it |
| Readiness evidence | `/health` response | Startup log plus a consumed test job |

Do not start the worker as a background shell command inside the web service. The host must supervise it independently so a web restart or scale event does not silently remove consumers.

</ApiRequestPanel>

`200` should mean the process is ready for traffic. If the route reports database state, it must return a non-success status when the required database is unavailable. Decide whether Redis failure blocks readiness or creates a documented degraded mode; do not always return `ok` while required dependencies are disconnected.

## MongoDB Atlas

Before the API can talk to the database, your Atlas cluster has to accept connections from your host. A production-ready setup needs three things:

- Production cluster or dedicated DB user
- Network access allows deploy IP
- Connection string in host env only

## Logs and rollback marker

Tail API and worker logs separately. Confirm every line identifies the service and deploy revision. Record the previous known-good commit or platform deploy before continuing; “redeploy something older” is not a rollback plan.

If startup fails, roll back code and configuration as a pair. A previous build with a new incompatible environment value can fail exactly like the new release.
