# 23.12 — Deploy client

> **[Build]** · Chapter 23 — Deploy · *Vercel/Netlify/same VPS*

**Why this step matters:** Mentors evaluate the **shop URL**, not your git repo. This step puts the React build where browsers can load it — with SPA fallback so `/shop` refresh does not 404.

**Where the project is now:** API and worker are live, and 23.11 established the final API HTTPS origin. Produce the final client artifact now, even if you made a provisional build in 23.9.

**After this step:** Production client URL loads React app and fetches production API.

## Deploy contract

| Host type | Action |
|---|---|
| Vercel / Netlify | Connect repo; root `client/`; build `npm run build`; output `dist` |
| Same VPS | Copy `dist/` to `/var/www/app`; Nginx static root |

Set `VITE_API_URL` in the host's **production build** environment, trigger a fresh build from the intended Git revision, and inspect its Network requests after deployment. Reusing a local `dist/` directory makes it harder to identify what source and environment produced the live bundle.

## SPA fallback

Configure redirects:

- Netlify: `_redirects` → `/* /index.html 200`
- Vercel: `vercel.json` rewrites

Without this, `/shop` refresh returns 404.

## Complete the browser boundary

Once the static host assigns the client HTTPS origin:

1. set the API's `CLIENT_ORIGIN` to that exact origin;
2. restart or redeploy the API;
3. send credentialed requests only from the approved origin;
4. verify refresh-token cookies in the browser rather than with `curl` alone.

For caching, hashed files under `assets/` may be cached for a long time. Serve `index.html` with revalidation so a rollback or new build can point browsers at the new asset hashes.

## Smoke in browser

1. Open production client URL.
2. Home or shop loads.
3. Network tab — API calls go to **production** API domain.
4. No mixed content errors.
5. Log in and refresh a protected route; the session still works.
6. Refresh `/shop` directly; the SPA fallback serves the application.

## ✅ Do / ❌ Don't

**✅ Do:** Test deep link `/shop` refresh.

**❌ Don't:** Deploy stale `dist/` from wrong API URL.

## Verify

- [ ] Client HTTPS loads
- [ ] Network requests target final production API, never localhost
- [ ] Login and protected-route refresh work with production cookie/CORS policy
- [ ] `/shop` deep-link refresh works
