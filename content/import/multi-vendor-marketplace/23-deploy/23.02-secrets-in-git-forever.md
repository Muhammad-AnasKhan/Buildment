# 23.2 — Secrets in Git forever

> **[Read]** · Chapter 23 — Deploy · *`git log -- .env` must be empty*

Before deploy, re-run Chapter 4 discipline at production scale. **`git log -- .env` must be empty.** Production credentials pasted into README or learning log disqualify the gate.

Deploy amplifies every secret leak — a key in Git history can be scraped by bots within minutes of a public push. This sub-chapter is the **audit** before you touch a host env panel.

## Why this matters for first-time deployers

| Mistake | Real consequence |
|---|---|
| Commit `server/.env` "just once" | Key lives in Git history forever unless rotated |
| Paste `MONGODB_URI` in README | Anyone with repo access owns your database |
| Put `JWT_SECRET` in client `VITE_*` | Bundled into JavaScript — visible in browser DevTools |
| Screenshot host panel with values | Portfolio post leaks production creds |

**Environment variables on the host** are the production version of `.env` — same keys, different values, never committed.

## Production secret inventory

| Variable | Host | Never in |
|---|---|---|
| `MONGODB_URI` | API server env | Git, client bundle |
| `JWT_SECRET` / refresh pepper | API server env | Git |
| `CLOUDINARY_API_SECRET` | API server and any image-processing worker | Git, client bundle |
| `CLOUDINARY_CLOUD_NAME` | API and client only if the code reads it | Treat as public configuration |
| `REDIS_URL` | API server env **and worker** | Git |
| `STRIPE_SECRET_KEY` / webhook secret | API server env | Git, client bundle, screenshots |
| `VITE_API_URL` | **client build** env | Public configuration; never place credentials beside it |

## Pre-deploy verification

```bash
git log --all --full-history -- ".env" "**/.env"
git check-ignore -v server/.env client/.env
```

An empty path-history check proves only that files named `.env` were not committed. Also review CI files, README examples, screenshots, and source constants for copied values. Use a repository secret scanner when your hosting or Git provider offers one.

If a secret ever entered Git, revoke or rotate it first. History rewriting may reduce accidental discovery, but it cannot recall clones, forks, caches, or logs. A new Atlas password, new signing secret, or revoked Stripe key is what makes the old value useless.

## `.env.example` completeness

Gate 23.8 requires **every** production variable documented with placeholder — teammates reproduce deploy without guessing.

`.env.example` is **committed**. `.env` is **not**. The example file is a map, not a vault.

## Host env panels

Render, Railway, Vercel, VPS `/etc/environment` or PM2 ecosystem — **same keys** as local, **different values**.

Do not use screenshots of the values as documentation. Record variable **names**, purpose, owner process, and rotation source; keep values in the host's secret store.

## In plain English

| Term | Simple meaning |
|---|---|
| **Secret** | Password, API key, connection string — anything that grants access if leaked |
| **`.env.example`** | Template showing **which** variables exist — placeholders only |
| **Rotate** | Change a leaked secret to a new value — old one stops working |

## Common beginner questions

**Q: I accidentally committed `.env` once. Am I fine if I delete it now?**  
A: No — deleting the file does nothing, because Git history keeps every version forever. Anyone who cloned the repo at any point still has those values, and scraping bots may too. The fix is rotation: change every secret that was in the file (new Atlas password, new `JWT_SECRET`) so the old values stop working. Rewriting history with `git filter-repo` is possible, but only try it if your mentor advises — rotation is usually enough.

**Q: Can I commit production `VITE_API_URL`?**  
A: The URL itself is usually fine to commit — it's already visible in your browser's Network tab whenever anyone uses the app. The danger is treating client env vars like a secret vault. Anything starting with `VITE_` gets bundled into your JavaScript, so a `VITE_MONGODB_URI` or an API password would be readable by anyone who opens DevTools. URLs are public; credentials are not.

**Q: Does the worker need the same secrets as the API?**  
A: It needs the same values only for dependencies it actually uses. BullMQ requires the same `REDIS_URL`; a processor that loads orders also needs `MONGODB_URI`. It should not receive Stripe or JWT secrets if no worker code reads them. Separate process inventories prevent both missing configuration and unnecessary privilege.

**Q: Why is `.env.example` committed but `.env` never is?**  
A: Because they serve opposite purposes. `.env.example` is a map: it lists which variables your app needs, with placeholders, so any teammate — or future you — can create a real `.env` from it. `.env` is the vault: it holds real credentials, so it must stay out of Git. The gate checks both: `git log -- "**/.env"` must be empty for secrets, and `.env.example` must be complete with no real values in it.

**Q: What does it mean to "rotate" a secret?**  
A: Rotation means replacing a possibly-leaked secret with a brand-new one so the old value no longer grants access. If a `MONGODB_URI` ever hit Git, you'd create a new Atlas database user and update the host env panel; if `JWT_SECRET` leaked, you'd generate a new one — which also invalidates old tokens. It's like changing the locks after losing a key: the leaked copy becomes useless, and the damage stops.

## ✅ Do / ❌ Don't

**✅ Do:** Use separate MongoDB user for production.

**✅ Do:** Restrict Atlas IP to deploy host or `0.0.0.0/0` with strong password — document tradeoff in learning log.

**❌ Don't:** Commit production `.env` "just once".

**❌ Don't:** Put `MONGODB_URI` in client `VITE_*`.
