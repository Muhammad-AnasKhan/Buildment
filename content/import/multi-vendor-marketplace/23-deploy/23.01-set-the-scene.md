# 23.1 — Set the scene

> **[Read]** · Chapter 23 — Deploy · *Bridge from localhost; hosting + env vars demystified for first deploy*

**Where the project is now:** Full marketplace on localhost — auth, vendor dashboard, customer shop, cart, checkout, orders, cache, search, **async worker** (Chapter 22). Mentors cannot click your demo URL because **there is no public URL**.

**Where this chapter goes:** **Production deploy** — API, **worker**, and client on HTTPS; secrets in host env only; smoke tests pass; processes survive restart.

Deployment is not a single command. It is the first time all your assumptions meet a different machine and the public internet. The API needs a stable address, the client must be built against that address, and the worker must keep consuming after your terminal closes.

Your API needs a stable URL. Your client needs to know that URL at build time. MongoDB, Redis, and webhooks must accept connections from the host, not only your laptop.

After deploy, run the full demo with Stripe **test mode**: a vendor adds a product, a customer checks out, the webhook updates the order, and the worker consumes the notification job. That end-to-end pass is the chapter gate. Modules 24 and 25 then harden the deployed checkout with inventory reservations and server-owned promotion pricing.

## Bridge from last chapter

Chapters 2–21 built a complete app on **your laptop**:

| Works on `localhost` | Does not work for mentors / employers |
|---|---|
| `http://localhost:5173` shop | They cannot open your browser |
| `server/.env` with secrets | Files on your disk are not "deployed" |
| `npm run dev` + `npm run worker` in terminals | Processes die when you close the laptop |
| MongoDB Atlas dev cluster | May block unknown IPs |

Chapter 23 is the **deployment milestone** — same app, different **home**. You copy the API to a host, run the worker as a second process, build the client with the final API URL, and prove smoke tests pass on **HTTPS**.

Nothing new to learn about grocery or JWT here. This is **operations** — the skill that turns "I built a course project" into "here is my live demo link."

## In plain English

| Term | Simple meaning |
|---|---|
| **Deploy** | Put your app on a computer that stays on 24/7 so anyone on the internet can use it |
| **Host / hosting** | The company or server that runs your app — Render, Railway, Vercel, a VPS, etc. |
| **Environment variables (env vars)** | Secret settings the host injects at runtime — database URL, JWT secret — **not** baked into Git |
| **Production** | The live version real users (or mentors) hit — as opposed to `localhost` development |
| **HTTPS** | Encrypted web — padlock in browser; required for secure cookies and professional demos |
| **Build** | Compile the React app into static files (`client/dist/`) with the production API URL frozen in |
| **PaaS (Platform as a Service)** | Host manages the server for you — Render, Railway, Vercel — faster for beginners |
| **VPS (Virtual Private Server)** | You rent a Linux machine and configure everything — more control, more setup |
| **Smoke test** | Quick check that critical paths work on production — health, login, checkout |
| **Process manager** | Keeps API and worker running after reboot — PM2, systemd, or PaaS auto-restart |

## Think of it like moving into a shopfront

Chapters 2–21 were **building in your garage** — tools everywhere, `.env` on the workbench, you are the only one who knows the address.

Deploy is **opening the shopfront on Main Street**:

- **Signage** — HTTPS URLs mentors can click  
- **Utilities** — production MongoDB, Redis, Cloudinary wired through the host's env panel, not a file in Git  
- **Staff schedule** — API and worker processes that restart when the power blips  
- **Grand opening test** — smoke script: walk in as customer, buy from two vendors, confirm vendor sees the order  

The product inside is the same. The **address and utilities** change.

## Localhost is not shipped

Everything you've run locally has to be re-created in production — this table is the gap you're closing:

| Local truth | Production requirement |
|---|---|
| `http://localhost:5000` | `https://api.yourdomain.com` |
| `VITE_API_URL` in client `.env` | Build-time production API URL |
| MongoDB local/Atlas dev cluster | Production database user + IP allowlist |
| Redis optional local | Production Redis URL (cache + BullMQ queue) or fallback documented |
| Worker `npm run worker` in second terminal | Second process on host (PM2, Render worker service, etc.) |
| `.env` on your laptop | Host environment panel — never Git |

## Common beginner questions

**Q: What is "deploy" in one sentence?**  
A: Deploy means copying your server and your built client to machines that stay online 24/7, wiring in the production secrets on the host, and getting HTTPS URLs that work for anyone — even when your laptop is closed. Everything you built on `localhost` moves into a new home with a public address. Your laptop is a demo; a deployed app is a product anyone can open.

**Q: Where do secrets go in production?**  
A: In the host's environment variable panel — Render's "Environment", Railway's "Variables", or a VPS's `/etc/environment` or PM2 ecosystem file. The variable *names* match `server/.env.example`; only the *values* change to production credentials. That's the production version of your local `.env`: the host injects them at runtime. Never commit a production `.env` to Git — and leave your local `.env` untouched so your dev setup keeps working too.

**Q: What is `VITE_API_URL` and why does it matter at build time?**  
A: `VITE_API_URL` is the base URL your React app calls — the API host. Vite bakes `import.meta.env.VITE_API_URL` straight into the JavaScript bundle when you run `npm run build`, so the URL is frozen into the static files in `client/dist/`. It is not read from a runtime file. Change the API later and you must rebuild and redeploy the client, or the old bundle keeps calling the old URL.

**Q: Do I deploy only the API?**  
A: No — the gate needs three pieces: an HTTPS API, an HTTPS client, and the worker process. Chapter 22's whole point was that the worker is a separate process, and production is no different. Deploy only the API and checkout still enqueues jobs, but nothing processes them, so no `[NOTIFY]` notifications ever appear. It's the classic "worked in dev, silently broken in production" trap.

**Q: Which host should I pick?**  
A: Pick a host that can run a long-lived Node API and a separate worker, or use a VPS with a process manager. Use a static host for the Vite client if that makes the setup clearer. Product features, pricing, and free-tier behavior change, so verify the current host documentation before committing to a path.

**Q: What if a smoke test passes locally but fails on production?**  
A: It almost always means the environment differs, not the code. Common culprits: the client build points at the wrong `VITE_API_URL`, CORS still only allows `localhost:5173`, the worker is missing an env var like `REDIS_URL`, or MongoDB Atlas isn't allowing the host's IP. Chapter 23.13 walks a fix matrix for exactly these. The skill is reading error messages and checking your config — not rewriting working code.
