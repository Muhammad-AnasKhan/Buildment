# 23.14 — Restart survival test

> **[Build]** · Chapter 23 — Deploy · *Reboot server — API + worker come back*

Process dashboards can show “running” before an application is ready. This test restarts API and worker independently, measures recovery at their real boundaries, and proves Redis keeps queued work while the worker is unavailable.

**Where the project is now:** Smoke tests passed (23.13) — API, client, worker on HTTPS; worker processed checkout.

**After this step:** The API becomes ready within a documented target, the worker reconnects without manual shell commands, and one job queued during worker downtime completes after recovery without duplicating its business effect.

Two server processes in production: API (HTTP, enqueue) and worker (BullMQ, Ch 22). API up + worker dead = 23.13 row 6 failure. Client static survives reboot — test API + worker.

**Gate:** Restart each process independently, verify readiness, then complete the queue durability test. Choose a recovery target appropriate to your host and record the measured time; 60 seconds is a useful course target, not a universal platform guarantee.

## Test matrix — you implement per host

| Action | API | Worker |
|---|---|---|
| PaaS redeploy API | Health 200 ≤60s | Unaffected if separate service |
| PaaS redeploy worker | Unaffected | Startup log; jobs resume |
| `pm2 restart <api>` | Health 200 ≤60s | Running unless restarted too |
| `pm2 restart <worker>` | Unaffected | Startup log; consumers reattach |
| VPS reboot | Auto-start if configured | Auto-start if configured |
| Kill worker PID | Health still 200 | Logs resume after restart |

API-only restart ≠ gate. Worker restart row mandatory.

## Verification sequence — spec

1. Baseline health check:

<ApiRequest
  label="GET /health after API restart"
  method="GET"
  url="https://api.yourdomain.com/health"
  responseStatus={200}
  responseBody='{"status":"ok","db":"connected"}'
/>

</ApiRequestPanel>

2. Restart API — poll readiness and record time to first reliable success
3. Quick auth in browser  
4. Stop the worker and confirm the API remains ready
5. Complete one Stripe test-mode checkout while the worker is stopped; capture the queued job ID
6. Start the supervised worker and confirm that exact job reaches a completed state
7. Restart the worker again and confirm idempotency prevents a duplicate notification effect

Do not flush Redis between steps; that would destroy the evidence you are trying to test. If API readiness fails, inspect startup and dependency logs. If the worker starts but the queued job remains, compare queue name, Redis connection, and deployed revision.

## Auto-start — VPS contract

| Component | Spec |
|---|---|
| API | `pm2 save` or systemd `enable` + `Restart=on-failure` |
| Worker | Second PM2 app or systemd unit — same env file |
| PaaS | Worker as declared service — not SSH one-off |

## Platform notes

| Platform | API restart | Worker restart |
|---|---|---|
| Render / Railway | Restart web service | Restart worker service |
| PM2 | `pm2 restart <api>` | `pm2 restart <worker>` — both in save |
| systemd | `restart` + `enable` | Second unit, both enabled |

Hosted cold starts may exceed the course target. Measure and document them, but distinguish an expected wake-up from a crash loop by inspecting logs and repeated readiness checks.

## Failure modes

| Symptom | Likely cause |
|---|---|
| Health never returns | Crash loop; check API logs |
| No worker after reboot | Not in `pm2 save` / not enabled |
| 201, no log post-restart | Wrong `REDIS_URL` after redeploy |
| Only API restarted | Incomplete gate |

## Learning log

Record the action used, API recovery time, worker restart time, queued job ID, and evidence that the job ran once. Explain which supervisor brings each process back without an SSH session.

## ✅ Do / ❌ Don't

**✅ Do:** Process manager for both; test worker restart; autostart on VPS.

**✅ Do:** New checkout after each restart.

**❌ Don't:** Claim deploy done without this test.

**❌ Don't:** One PaaS service for both API and worker.
