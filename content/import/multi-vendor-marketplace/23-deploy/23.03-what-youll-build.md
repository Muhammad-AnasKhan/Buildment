# 23.3 — What you'll build

> **[Read]** · Chapter 23 — Deploy · *HTTPS API + client + worker in production*

Deploy is not one button — it is a **checklist of deliverables** that prove your localhost app lives on the internet. Read this before choosing a host in 23.4.

## Deliverables

| Deliverable | Spec |
|---|---|
| Production API URL | HTTPS, `/health` returns 200 + `db: connected` |
| Production client URL | HTTPS, loads shop, points at production API |
| **Production worker** | Second process — `npm run worker` on host — notifications work |
| Env checklist | All vars in `.env.example` + host configured for API **and** worker |
| Smoke tests | Health, login, browse, checkout on live URL — worker log after checkout |
| Recovery proof | API + worker restart, queued jobs resume, rollback path recorded |
| README Deploy section | Steps another dev could follow |

## Three things leave your laptop

```
┌─────────────────────────────────────────────────────────┐
│  1. API server     Express + MongoDB + Redis + enqueue  │
│  2. Worker         BullMQ processors — NOT optional     │
│  3. Client static  React build from client/dist/        │
└─────────────────────────────────────────────────────────┘
```

Beginners often deploy 1 and 3 and wonder why checkout "works" but no `[NOTIFY]` logs appear. **The worker is deliverable #2.**

## Typical topology

```
Browser → HTTPS CDN/static host (client)
       → HTTPS API host (Express + PM2 or PaaS)
            → MongoDB Atlas
            → Redis (managed or same VPS)
            → Cloudinary
       → Worker host (same Redis + MongoDB as API)
```

**You pick** one path in 23.4 — document yours in README.

## Dependency order

Deployment has dependencies, so “follow the filenames” is not always the final execution order:

1. Audit secrets and create separate API, worker, and client environment inventories.
2. Deploy the API and worker, then obtain the API's real HTTPS origin.
3. Attach the API domain if you are using one.
4. Build the client with that final API origin and deploy it.
5. Set the API's exact `CLIENT_ORIGIN` to the final client origin and restart the API.
6. Run smoke, rollback, and restart checks.

Lesson 23.9 prepares and tests the client build contract before the API deploy. If your host assigns the API URL only after deployment, run the **final** build again after 23.11. Do not ship a guessed platform URL.

## Client build contract

```bash
cd client
VITE_API_URL=https://api.yourdomain.com npm run build
```

Output `client/dist/` deployed to static host or served by API — pick one.

The API URL is **frozen at build time** — not read from a runtime file on Vercel/Netlify.

## Common beginner questions

**Q: Is deploy a coding chapter?**  
A: Mostly not — it's a configuration and verification chapter. The code is done; operations begin. You'll copy the API to a host, build the client with a production `VITE_API_URL`, run the worker as a second process, and prove the pieces work over HTTPS with smoke tests. Expect the "coding" here to be small config fixes, not new features. That's normal — a big part of real engineering is shipping what already works.

**Q: Is a free tier enough?**
A: It may be, but host plans and sleep behavior change. Verify that the current plan supports a long-running web process, a separate long-running worker, outbound MongoDB and Redis connections, environment secrets, logs, and HTTPS. Record expected cold-start behavior rather than treating a slow first request as automatically correct.

**Q: One service or three?**  
A: Minimum is three pieces: the API service, the worker service, and the static client host. On a VPS you can compress that to two homes — PM2 runs both the API and worker on one machine, and nginx serves the built client. On PaaS, the worker is a second service from the same repo with the start command `npm run worker`. The worker is non-negotiable: deploy API and client alone and notifications silently stop.

**Q: What is a smoke test, and why run it on the live URL?**  
A: A smoke test is a quick sanity check that the critical paths work — health returns `db: connected`, a customer can log in, browse, and check out, and the worker logs notifications afterward. You run it on the production URLs, not localhost, because that's what a mentor will do. Passing locally proves nothing about DNS, CORS, env vars, or the worker on the host; the live URL is the only place all of those can fail.

**Q: Why is `VITE_API_URL` frozen at build time?**  
A: Because Vite is a build tool: when you run `npm run build`, it replaces `import.meta.env.VITE_API_URL` with whatever value you provided and bakes it into the static files in `client/dist/`. Those files don't load any runtime config — the API URL is literally in the bundle. So the value must be correct *at build time*, and changing it later means rebuilding and redeploying the client.
