# 3.3 — What you'll decide

> **[Read]** · Chapter 03 — Why MongoDB · *Three decisions that shape the entire project*

By the end of this chapter, you'll have made **three decisions** that Chapter 4–5 implement without reopening fundamentals:

<BigWordAlert term="Data modelling decision" plainEnglish="Choosing database technology and document shapes before writing models — design before code." whyItMatters="This chapter produces `docs/erd-draft.md` — the blueprint Chapter 5 implements in Mongoose." />

1. **Database family:** MongoDB (document store) for this marketplace
2. **ODM:** Mongoose for schemas, validation, and references in Node
3. **Modelling strategy:** References for ownership chain; embedded arrays for order line snapshots

This page states the decisions plainly. Sub-chapters 3.4–3.7 give you the evidence to understand *why*.

<Callout type="info" title="This is the foundation">
Beginners often treat database choice as "install whatever the tutorial uses." Here you **document why** — MongoDB for variable product attributes and embedded order lines, Mongoose for schema discipline. Chapter 4 won't re-debate this; it connects. Chapter 5 won't ask "SQL or Mongo?" — it implements.
</Callout>

## Decision 1 — MongoDB for FreshMarket (mandated)

**The course requires MongoDB.** Not because MERN is a meme — because:

- Product documents carry **variable grocery attributes** without migration churn
- Order documents naturally **embed line items** with snapshot fields at checkout
- The learning path matches **Mongoose populate** patterns taught in the catalogue chapters
- One document store aligns with **JSON APIs** end-to-end (React ↔ Express ↔ MongoDB)

You may personally prefer PostgreSQL for marketplaces — many production marketplaces use it well. **For this repo, use MongoDB** so chapter paths, query examples, and isolation patterns align.

## Decision 2 — Mongoose as the ODM

Raw MongoDB driver works. Mongoose adds:

- **Schemas** with types and enums (`unit: { type: String, enum: ['kg','g','litre','piece'] }`)
- **References** with `populate()` — taught explicitly when fixing N+1 (Chapter 14)
- **Middleware** hooks — useful for password hashing before save (Chapter 6)
- **Validation** at application boundary

Alternatives like Prisma (with MongoDB provider) or native driver are valid in industry. **This course uses Mongoose** — Chapter 5 filenames assume `*.model.js` Mongoose schemas.

## Decision 3 — Embed vs reference (preview)

This is the most important modelling choice. Here's the summary — full depth in 3.6:

| Data | Strategy | Reason |
|---|---|---|
| User ↔ Profile | **Reference** (two collections) | Identity vs profile split — Chapter 6 |
| Store → User | **Reference** | Store belongs to vendor |
| Product → Store | **Reference** | Product belongs to store; store name not copied onto every product |
| CartItem → Product, Store, User | **Reference** | Live cart tracks current product; still has storeId for split |
| Order → Customer, Store | **Reference** | Order belongs to customer and vendor store |
| Order line items | **Embed** in Order | Snapshot fields frozen at purchase — Chapter 18 |
| Refresh tokens (later) | **Reference or embed in User** | Chapter 6 specifies |

<Callout type="warning" title="Mismatch = rework">
Your ERD must show embed for order lines explicitly. Full depth in **3.6**. If your draft and code disagree later, fix the draft or the model — don't leave both telling different stories.
</Callout>

## When you would pick SQL instead

Write at least one paragraph in your learning log on **when relational wins**:

**Strong relational cases:**

- **ACID checkout** with serializable transactions as the primary correctness tool
- **Ad-hoc analytics** — revenue by category across vendors with complex JOINs
- **Strict foreign keys** enforced by the database — every ORM can leak; Postgres FK constraints are hard guardrails
- **Team expertise** — shipping beats theoretical fit

**This project's checkout** still needs atomic stock decrement and multi-order creation — you'll implement carefully in Chapter 18 with Mongoose. SQL would use `BEGIN TRANSACTION`. Both can be correct; know what you traded.

## Common questions

**Q: Can I use PostgreSQL if I know it better?**  
A: Not in this repo, and not without mentor agreement — and the reason is practical, not a technology loyalty test. Every chapter from here assumes Mongoose paths, document-style queries, and embedded or referenced relationships, so switching databases means mentally translating every example for twenty chapters. If you genuinely prefer SQL, that's a valid real-world choice, but it belongs in your *own* project, not this course. Here the skill being taught is deciding which model fits the data, using MongoDB as the vehicle.

**Q: What's the one deliverable that gates Chapter 4?**  
A: `docs/erd-draft.md` — your entity relationship diagram — plus a learning-log entry proving you can explain embed vs reference in your own words. The ERD is your design contract: it says what collections exist, what fields they hold, and how they connect, all before any code is written. The explanation matters because the gate tests understanding, not file creation. No ERD, no Chapter 4 — that's the rule, so treat the draft as the real output of this chapter.

**Q: Why decide embed/reference before writing code?**  
A: Because the decision is cheap on paper and expensive in code — and the checkout case makes it concrete. If an order only *references* its products, the order history shows the product's current price, so a price rise silently rewrites yesterday's receipts. If the order *embeds* the price at purchase, the receipt stays frozen and honest. That's not a UI bug or a query bug; it's a data-modelling bug, and it's only cheap to fix while it's still a decision in a document rather than a schema you've built a whole feature on.
