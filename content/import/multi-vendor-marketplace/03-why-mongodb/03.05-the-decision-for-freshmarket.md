# 3.5 — The decision for FreshMarket

> **[Learn]** · Chapter 03 — Why MongoDB · *MongoDB + Mongoose — mandated; why for this domain*

<BigWordAlert term="MongoDB" plainEnglish="The document database this course uses — collections, BSON documents, and Mongoose as the Node.js ODM." whyItMatters="FreshMarket commits to MongoDB here so every later chapter (models, queries, indexes) stays consistent." />

## What you'll learn

By the end of this chapter, you should be able to say out loud:

> "We use MongoDB with Mongoose for this marketplace because [your reasons], and we accept [trade-offs] as the cost."

This isn't about blindly following instructions. It's about understanding the trade-offs so you can explain your choices — in interviews, in code reviews, and in your learning log.

<Callout type="info" title="Interview prep">
When an interviewer asks "why did you pick MongoDB?" you should answer from **this project's specific needs** — not from a marketing brochure. Being able to name both pros and accepted cons shows you understand trade-offs.
</Callout>

## The decision (non-negotiable for this course)

Here's what this course mandates:

| Choice | Selection |
|---|---|
| Database | **MongoDB** (Atlas or local) |
| ODM | **Mongoose** |
| Modelling | **References** for ownership; **embedded arrays** for order line snapshots |
| IDs | MongoDB **ObjectId** |

Chapter 4 connects with `MONGODB_URI`. Chapter 5 creates `*.model.js` files. Deviating to Postgres **breaks every subsequent chapter's paths and examples**.

<Callout type="warning" title="Fork in the road">
If you strongly prefer Postgres, you can fork the course and adapt the examples yourself — but for the standard path, this decision is locked in now.
</Callout>

## Why MongoDB for *this* project — the pros

### 1. Document shape matches the API

Express sends JSON. React consumes JSON. MongoDB stores BSON documents that map cleanly — less "impedance mismatch" than ORM-mapping every row to a nested cart response.

### 2. Embedded order lines

An order is a natural aggregate: header (customer, store, status) + array of line items with snapshot fields. One read fetches the full order for customer history — no separate join table needed.

### 3. Grocery product evolution

Core fields stay fixed (`unit`, `stockQty`, etc.). But some products might have optional nested `attributes: { organic: true }` — without requiring `ALTER TABLE` migrations.

### 4. Mongoose ecosystem for teaching

`populate()`, schema enums, middleware for hash-on-save, indexes declared in schema — all appear in later chapters with measurable exercises. Mongoose gives us a structured path to follow.

### 5. MERN portfolio coherence

Employers scanning a MERN project expect MongoDB. Delivering the full stack consistently is a portfolio goal of this course.

## The trade-offs you accept

Every decision has a cost. Here's what you're accepting by choosing MongoDB:

### 1. Fewer database-enforced constraints

A bug can insert a product with an invalid `storeId` if the service layer skips validation. In Postgres, the database would reject it automatically.

**Mitigation:** Mongoose refs, service-layer checks, and tests (Chapter 8 isolation tests).

### 2. Reporting queries take more work

"Revenue by category last month across all vendors" is often more SQL-fluent than MongoDB aggregation for beginners.

**Mitigation:** Out of scope for the core course. Advanced content may cover it.

### 3. Transaction mental model

Multi-document checkout must be designed explicitly — MongoDB doesn't hide this from you.

**Mitigation:** Chapter 18 covers the checkout spec.

### 4. Schema drift without discipline

"Schemaless" doesn't mean "no schema" — documents without a Mongoose schema become chaos.

**Mitigation:** Every collection gets a `*.model.js` file in Chapter 5.

## Final scorecard

Here's the weighted comparison that led to this decision:

| Criterion | Weight | MongoDB | PostgreSQL |
|---|---|---|---|
| Matches chapter materials | High | ✓ | ✗ |
| Embedded order snapshots | High | ✓ natural | ✓ via `order_items` |
| Grocery field enums in schema | Medium | ✓ | ✓ |
| JSON API ergonomics | Medium | ✓ | ~ via ORM |
| Ad-hoc BI / SQL reports | Low in scope | ~ | ✓ |
| FK enforcement by default | Medium | ~ app layer | ✓ |

**Winner for this course:** MongoDB — weighted by teaching path and document aggregates, not by universal superiority.

<Callout type="tip">
**Notice the weights.** "Matches chapter materials" and "Embedded order snapshots" are both *High* weight — those drive the decision. "Ad-hoc BI" is *Low* because it's out of scope. This is how you weigh trade-offs in real projects.
</Callout>

## Common questions

**Q: Is MongoDB "mandated" just because MERN starts with M?**  
A: No — the "M" is a hint, not the reason. FreshMarket picks MongoDB because the data actually fits a document model: an order embeds its line items and price snapshot naturally in one document, the JSON your API sends maps almost one-to-one onto Mongo documents (less shape-shifting between database and response), and Mongoose's schema layer is forgiving for learners. The MERN coherence is a convenience — one language everywhere — but it's the document-shaped data that makes the choice honest.

**Q: What cons must I honestly accept?**  
A: Three real trade-offs. First, referential integrity is enforced by your application code, not the database — nothing stops you storing a `storeId` that points nowhere unless your code checks. Second, reporting and analytics across collections take more work than SQL. Third, multi-document operations like checkout need explicit design (transactions or careful ordering) because a single document can't span everything. Knowing the cons matters: a bar-raiser asks "what did MongoDB cost you?", and "I know these three" is the right answer.

**Q: Can I switch to Postgres at Chapter 10?**  
A: Practically, no — and that's by design, not an accident. Twenty chapters of examples, routes, and schemas assume Mongoose and document semantics; switching at Chapter 10 means rewriting every query, every model, and every decision you've made so far. The course commits to MongoDB so you can spend your energy learning the *patterns* — ownership, snapshots, caching, auth — instead of re-learning a database. If you want a different stack, that's a Chapter 0 decision for your own project, not a mid-course change.

## Mongoose's role — not optional

Starting in Chapter 5, you'll create files like:

```
server/src/modules/products/products.model.js
```

Mongoose gives us:
- Schema enums for `unit`
- `populate()` for references
- Middleware for password hashing
- Indexes declared in schema

Raw MongoDB driver inserts are fine for scripts, but **not** the course convention for models.
