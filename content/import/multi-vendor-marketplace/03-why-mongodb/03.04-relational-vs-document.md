# 3.4 — Relational vs document models

> **[Learn]** · Chapter 03 — Why MongoDB · *Side-by-side comparison; orders and ownership in both worlds*

<BigWordAlert term="Document database" plainEnglish="A database that stores records as JSON-like documents in collections instead of rows in joined tables." whyItMatters="MongoDB fits FreshMarket's nested cart items and varied product fields without complex JOIN queries." />

## What you'll learn

By the end of this chapter, you'll be able to:

- Describe how the same marketplace data looks in SQL tables vs MongoDB collections
- Explain why embedded order lines make sense in a document database
- Understand that transactions and N+1 query problems exist in both worlds

You don't need to pick a side forever. You just need to understand **why this course uses documents** for FreshMarket — and be able to explain that choice.

<Callout type="info">
**You're not choosing a religion.** You're choosing what fits this grocery marketplace and this course's teaching path. If you understand both models, you can explain your choice — and that's what matters in interviews.
</Callout>

## Think of it like…

**Two filing systems for the same shop.**

- **Relational (SQL):** Every fact goes on a separate index card, cross-referenced by ID numbers. Strict, organized, great for accountants.
- **Document (MongoDB):** An order folder contains the full receipt stapled inside — customer info, items, totals, all in one place. Great for "show me what this customer bought."

FreshMarket needs both styles in different places: references for live catalogue data, and embedded snapshots for historical orders.

## The same marketplace in relational form

Let's sketch the SQL tables for our core entities:

```
users       (id, email, password_hash, role, ...)
profiles    (id, user_id FK, display_name, avatar_url, ...)
stores      (id, vendor_user_id FK, name, address, ...)
products    (id, store_id FK, name, price_cents, unit, stock_qty, ...)
cart_items  (id, customer_user_id FK, product_id FK, quantity, ...)
orders      (id, customer_user_id FK, store_id FK, status, total, ...)
order_items (id, order_id FK, product_id FK, quantity,
             price_at_purchase, name_at_purchase, unit_at_purchase, ...)
```

**Foreign keys** enforce the rules: a product's `store_id` must exist; an `order_item`'s `order_id` must exist. The database rejects bad inserts automatically.

**A checkout query** joins `order_items` → `orders` → `stores` → `users`. **A catalogue query** joins `products` → `stores` to show shop names on product cards.

This model is proven, normal, and used by many marketplaces at scale. Nothing wrong with it.

## The same marketplace in document form

Now let's model the exact same data in MongoDB collections:

```
users     { _id, email, passwordHash, role, ... }
profiles  { _id, userId ref users, displayName, ... }
stores    { _id, userId ref users, name, ... }
products  { _id, storeId ref stores, name, price, unit, stockQty, ... }
cartitems { _id, userId ref users, productId ref products, storeId ref stores, quantity }
orders {
  _id,
  customerId ref users,
  storeId ref stores,
  status,
  orderItems: [
    { productId, nameAtPurchase, priceAtPurchase, unitAtPurchase, quantity }
  ]
}
```

**References** (`ObjectId` + `ref`) replace foreign keys — but enforcement happens in your application code, not in the database rejecting bad inserts.

**Order lines are embedded** — no separate `order_items` collection needed. Snapshot fields live inside the order document itself.

## Side-by-side comparison

The table below lines up the same concerns in both worlds, so you can see exactly what changes and what stays the same:

| Concern | Relational (SQL) | Document (MongoDB) |
|---|---|---|
| **Ownership chain** | FK: `product.store_id` → `stores.id` | Ref: `product.storeId` → `stores._id` |
| **Schema changes** | Migrations (`ALTER TABLE`) | Flexible documents; discipline required |
| **Order snapshot** | `order_items` columns duplicated at insert | Embedded subdocuments in order |
| **Cart** | `cart_items` table with FKs | `cartitems` collection with refs |
| **Catalogue + store name** | `JOIN products + stores` | `populate('storeId')` or `$lookup` |
| **Multi-vendor checkout** | Transaction: insert N orders + lines | Transaction or careful ordering; multiple order docs |
| **Constraints** | DB-enforced FK, CHECK, UNIQUE | App + Mongoose schema; unique indexes possible |
| **JSON API fit** | ORM maps rows → objects | Documents map naturally to JSON |

<Callout type="tip">
**Neither column "wins" universally.** In the real world, fit to your team and your access patterns decides. In this course, fit to the teaching path decides — and that path is MongoDB.
</Callout>

## The denormalization trap (and when to break the rule)

Here's a mistake you'll be tempted to make: copying `vendorName` onto every `products` row or document because a JOIN feels slow.

**Why it's a problem:** When the vendor renames their shop, you now have thousands of stale copies. Every product card shows the old name.

**The right approach:** Store the name on `stores`; let your catalogue query join or populate once per page.

**The exception — order snapshots:** Copying `nameAtPurchase`, `priceAtPurchase`, and `unitAtPurchase` onto order lines is **correct on purpose**. History must not update when a product changes.

<Callout type="warning">
**Mark snapshot fields clearly in your ERD.** Show `nameAtPurchase` and `priceAtPurchase` on the embedded order lines — not just `productId`. This tells future-you that these fields are intentional copies, not a denormalization mistake.
</Callout>

## Transactions — both worlds can checkout

Multi-vendor checkout must do several things atomically:

1. Create multiple `orders` (one per vendor)
2. Decrement stock on multiple `products`
3. Clear `cartitems` for the customer
4. Fail entirely if any item is out of stock

**PostgreSQL:** Uses `BEGIN … COMMIT` — a familiar pattern.

**MongoDB:** Supports multi-document transactions on replica sets (Atlas qualifies). Chapter 18 covers the checkout spec.

<Callout type="warning">
**Don't choose MongoDB thinking you'll avoid transaction thinking.** Checkout correctness matters in both worlds. The syntax differs; the responsibility doesn't.
</Callout>

## N+1 queries — a trap in both worlds

This is one of the most common performance bugs in real apps.

**Relational ORM trap:** Load 20 products, then loop 20 separate queries to fetch each store name.

**Mongoose trap:** Same thing — `await Store.findById()` called once per product in a loop.

**The fix:** Use a JOIN in SQL; use `populate()` or a single aggregation in MongoDB. Chapter 14 measures query count — the database family doesn't save you from lazy loading.

## Common questions

**Q: Are MongoDB documents schemaless chaos?**  
A: The *database* will happily store documents that don't match each other, but your *team* doesn't have to. MongoDB is flexible by default; the discipline comes from you. In Chapter 5 you enforce a shape with Mongoose schemas, so every Product has the same required fields and types, just like a SQL table would. The practical difference: you can add a field to one document (or evolve the schema gradually) without a heavy migration. Freedom of the engine, discipline of the schema — that's the whole trick.

**Q: Does MongoDB mean no joins?**  
A: Not exactly — it means joins look different. In SQL you write a `JOIN` to combine two tables. In MongoDB you either store a reference and call `populate()`, which fetches the related documents for you in a second query, or you use the aggregation pipeline, which can combine data in richer ways. So you still combine data; you just reach for different tools. What matters is the same in both worlds: think about what you're combining and how many queries it takes — the N+1 trap exists in both.

**Q: What's the denormalization trap in one sentence?**  
A: Copying store names onto every product feels fast — until the vendor renames their shop and you have thousands of stale copies. **Except** for order snapshots, where "stale" prices are *correct* on purpose: your receipt should show what you paid, not today's price. That's the whole rule of thumb — reference live, mutable data; copy only immutable history.
