## Why this chapter matters

Your app will store:

- **Users** with roles (vendor vs customer)
- **Stores** owned by vendors
- **Products** with grocery-specific fields (unit, stock, perishability)
- **Cart items** tied to customers and products
- **Orders** split per vendor with **snapshotted prices**

You *could* store that in PostgreSQL, MySQL, MongoDB, or something else. The choice affects:

- How you model **ownership** (vendor → store → product)
- How you model **order lines** (embedded snapshots vs join tables)
- How you enforce **multi-vendor checkout** (one cart → many orders)
- How you query the **public catalogue** (filters, pagination, search)

Picking a database because "MERN starts with M" is how tutorials teach. Picking a database because **this product's needs fit** is how engineers ship.

<Callout type="info" title="The order matters">
decide → connect → implement. Chapter 3 decides. Chapter 4 connects. Chapter 5 implements. Don't skip ahead.
</Callout>

## Key terms — plain English

| Term | What it means |
|---|---|
| **Database** | Where the app stores data permanently — survives server restarts |
| **Document** | One JSON-like record in MongoDB — e.g. one product, one order |
| **Collection** | A group of documents — like a table, but without fixed columns |
| **Schema / model** | The rules for what fields a document must have (Chapter 5) |
| **Reference** | Storing another document's ID and looking it up when needed |
| **Embed** | Copying sub-objects inside a parent document |
| **ERD** | Entity-relationship diagram — a map of your data |

## Think of it like…

**Planning shelf labels before the warehouse opens.** Chapter 2 built the building (skeleton). You're not moving stock in yet; you're drawing the layout so Chapter 4 can connect the warehouse and Chapter 5 can fill shelves without guessing.

<ArticleBreak title="Embedding vs referencing: the grocery catalog decision" subtitle="How FreshMarket thinks about product data before schemas exist" readMinutes={8}>

In a grocery marketplace, a product belongs to a store, and a store belongs to a vendor. You can embed store details inside each product document for fast reads, or store IDs and fetch related documents when needed.

Embedding makes catalogue pages fast — one query returns product plus store name. Referencing keeps updates clean — change a store name once, not on thousands of products.

FreshMarket uses a hybrid: embed small, stable snapshots (like store display name) where read performance matters, and reference IDs where ownership and updates matter. You will feel this trade-off again in checkout when order snapshots must not change if a vendor renames their shop later.

</ArticleBreak>

## Common questions

**Q: Why not install MongoDB in Chapter 2?**  
A: Because you'd be setting up a database before you know what data it has to hold, and that's the fastest way to build a schema you have to throw away. The products in a grocery marketplace don't just have names — they need `unit`, `price`, `stockQty`, and maybe a perishability flag — and orders need price snapshots so a receipt never changes after checkout. Chapters 3–5 make you design the shapes first (the `docs/erd-draft.md`) and only then connect the engine that fits them. Install early and you'll end up fighting a generic schema with copy-paste workarounds exactly when checkout needs it most.

**Q: Is this just reading — does my repo change?**  
A: Your repo changes, just not with code. In sub-chapters 3.8–3.9 you commit `docs/erd-draft.md` — a design document that sketches your collections, their fields, and the relationships between them. That's not busywork: professional teams review a data model on paper before anyone writes a single `mongoose.model()`. So yes, you'll have real git history and a concrete deliverable from this chapter; it's just design-shaped rather than code-shaped.

**Q: I don't know MongoDB deeply. Can I still do this?**  
A: Yes — this chapter is built for exactly that situation. Sub-chapters 3.4–3.6 introduce SQL and MongoDB side by side using the same FreshMarket entities (users, stores, products, carts, orders), so you compare how each would model the same thing without needing background in either. You don't need to master MongoDB to follow; you need curiosity and a willingness to sketch. The gate is the ERD draft plus being able to explain embed vs reference in your own words — both fully covered here.
