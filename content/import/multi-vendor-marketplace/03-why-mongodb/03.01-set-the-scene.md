# 3.1 — Set the scene

> **[Read]** · Chapter 03 — Why MongoDB · *Every marketplace needs a database — which shape fits?*

## Where we are now

Chapter 2 left you with a running skeleton — Express API, React client, `GET /health` working in curl and in the browser. You can start the server and see "ok" in the browser. But here's the problem: **restart the server and every vendor, product, cart, and order disappears.** Your app has no memory yet.

<Callout type="warning" title="What's missing?">
Your module folders under `server/src/modules/` exist but they're empty. Data doesn't persist. This chapter is where we decide what goes in those folders — before writing a single line of database code.
</Callout>

Before you install Mongoose or paste a connection string (Chapter 4), you'll decide **what kind of database** this marketplace needs and sketch **what collections** you'll create in Chapter 5.

This is a **design chapter**. There's no new API endpoint to demo yet. The deliverable is understanding + a design file: `docs/erd-draft.md`.

## Why this chapter matters

Your app will store:

- **Users** with roles (vendor vs customer)
- **Stores** owned by vendors
- **Products** with grocery-specific fields (unit, stock, perishability)
- **Cart items** tied to customers and products
- **Orders** split per vendor with **snapshotted prices**

You *could* store that in PostgreSQL, MySQL, MongoDB, or something else. The choice affects:

- How you model **ownership** (vendor → store → product)
- How you model **order lines** (embedded snapshots vs join tables)
- How you enforce **multi-vendor checkout** (one cart → many orders)
- How you query the **public catalogue** (filters, pagination, search)

Picking a database because "MERN starts with M" is how tutorials teach. Picking a database because **this product's needs fit** is how engineers ship.

<Callout type="info" title="The order matters">
decide → connect → implement. Chapter 3 decides. Chapter 4 connects. Chapter 5 implements. Don't skip ahead.
</Callout>

## Key terms — plain English

| Term | What it means |
|---|---|
| **Database** | Where the app stores data permanently — survives server restarts |
| **Document** | One JSON-like record in MongoDB — e.g. one product, one order |
| **Collection** | A group of documents — like a table, but without fixed columns |
| **Schema / model** | The rules for what fields a document must have (Chapter 5) |
| **Reference** | Storing another document's ID and looking it up when needed |
| **Embed** | Copying sub-objects inside a parent document |
| **ERD** | Entity-relationship diagram — a map of your data |

## Think of it like…

## Common questions

**Q: Why not install MongoDB in Chapter 2?**
A: Because you'd connect before knowing **what shape** your data needs. Grocery products need units and perishability; orders need price snapshots. Designing first prevents copy-paste schemas that break at checkout.

**Q: Is this just reading — does my repo change?**
A: You **commit** `docs/erd-draft.md` in sub-chapters 3.8–3.9. That's real progress — design artifacts live beside code in professional teams.

**Q: I don't know MongoDB deeply. Can I still do this?**
A: Yes. Sub-chapters 3.4–3.6 explain both SQL and MongoDB using **the same marketplace entities** side by side. Curiosity is enough.
