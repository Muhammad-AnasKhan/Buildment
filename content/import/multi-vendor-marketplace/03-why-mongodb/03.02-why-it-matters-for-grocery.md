# 3.2 — Why grocery data is different

> **[Read]** · Chapter 03 — Why MongoDB · *Flexible product attributes (unit, weight, perishable)*

## The core insight

A generic marketplace tutorial uses products like "T-shirt" or "Book" — one price, one item. Real grocery breaks that template:

- Rice sells by **kg**, not by "one item"
- Milk sells by **litre**
- Coriander sells as a **bunch**
- Stock can be **45.5 kg**, not just 45 items
- **Perishables** need special handling

These aren't cosmetic details. They change your database schema, your validation rules, your checkout copy, and how you explain this project in an interview.

<Callout type="info" title="This is what makes your project real">
If your Product document is only `{ name, price, imageUrl }`, you built a different app. Checkout in Chapter 18 won't make sense because grocery receipts need units. Domain fields prove this is **FreshMarket**, not a renamed generic shop.
</Callout>

## Think of it like…

**Price tags at a real greengrocer.** Bananas are per bunch; rice is per kilogram; milk is per litre. The tag always says **price per unit** — ₹120/kg means something different from ₹120/piece. Your Product document is that tag.

## Grocery fields you can't skip

| Field | Example | Why it exists |
|---|---|---|
| `unit` | `kg`, `g`, `litre`, `piece` | Price is "per unit" — ₹120/kg ≠ ₹120/piece |
| `stockQty` | `45.5` | Stock isn't always whole items |
| `isPerishable` | `true` / `false` | Drives UI badges and future features |
| `category` | `Dairy`, `Grains`, `Produce` | Browse filters in Chapter 14 |

<Callout type="warning" title="Don't add these later">
Put grocery fields on your Product shape **now** in the ERD. Retrofitting `unit` after Chapter 5 means rewriting schemas. Decide now, code once.
</Callout>

## How grocery affects database choice

Grocery inventory varies a lot:

- Rice: brand, origin, bag size
- Cheese: refrigerated, expiry-minded
- Herbs: perishable, sold in bunches

**Relational approach:** `products` table + `product_attributes` table or many nullable columns — works, but every new attribute needs a migration.

**Document approach:** core fields on every product (`unit`, `stockQty`, etc.) plus optional nested objects for category-specific extras — e.g. `{ organic: true }` for produce without `ALTER TABLE`.

Neither is magic. Documents reduce friction when **shape varies by category** and you accept **application-level validation** instead of database-enforced column types.

## Multi-vendor ownership still dominates

Grocery fields don't replace the harder rule: **every product belongs to one store belonging to one vendor**. Whether SQL or MongoDB, you model:

```
Vendor (User) → Store → Product
```

Customer cart items reference **product + store** so checkout can split by vendor (Chapter 18). Perishability doesn't relax isolation — Vendor A still never edits Vendor B's `stockQty`.

## Orders must capture units

When a customer buys **2 kg** of rice at **₹120/kg**, the order line snapshot must record:

- `nameAtPurchase` — "Basmati Rice"
- `priceAtPurchase` — 120 (per unit at purchase time)
- `unitAtPurchase` — `kg`
- `quantity` — 2

Without `unitAtPurchase`, history shows "₹120" with no idea if that was per kg or per bag. Grocery receipts are **unit-aware** by nature.

<Callout type="tip" title="This is why order lines embed snapshots">
You'll embed these on order lines in Chapter 18. The decision is about **correct receipts**, not NoSQL fashion.
</Callout>

## When grocery would push you toward SQL

Be honest — MongoDB isn't universal:

| Scenario | Why SQL appeals |
|---|---|
| Strict inventory ledger with double-entry | Transactions across ledger tables |
| Complex reporting across vendors for tax | SQL analytics, JOINs, window functions |
| Heavy constraints on unit enums at DB level | `CHECK` constraints on `unit` column |

This course still uses MongoDB — but your learning log must name **one case** where SQL would compete. Interviewers respect trade-offs, not fanboyism.

## Domain vocabulary for your ERD

Use these names consistently in `docs/erd-draft.md`:

| Concept | Collection (MongoDB) | Notes |
|---|---|---|
| Login identity | `users` | role: vendor or customer |
| Profile fields | `profiles` | linked to user |
| Shop | `stores` | one per vendor |
| Listing | `products` | belongs to store |
| Cart row | `cartitems` | customer + product + store + qty |
| Purchase | `orders` | one per vendor per checkout; embeds lines |

Exact naming (`cartitems` vs `cart_items`) is up to you — just stay consistent in Chapter 5.

## Common questions

**Q: Can I add grocery fields later in Chapter 5?**
A: You could — but deciding them **now** prevents a generic schema you must retrofit. Put units and categories on your draft Product shape today.

**Q: Does perishability change API logic in Week 1?**
A: Not yet — it enables UI badges and portfolio narrative later. Still model it; seed data should mix perishable and non-perishable items.

## ✅ Do / ❌ Don't

**✅ Do:** Put grocery fields on the Product shape in your ERD — not "we'll add unit later."

**✅ Do:** Note on Order embedded lines that snapshot includes **unit**, not just price.

**❌ Don't:** Model products as strings on the cart without `productId` — checkout needs references.

**❌ Don't:** Skip `storeId` on cart items — multi-vendor split depends on it (Chapter 16).
