# 19.13 — Idempotency and double-submit

> **[Build]** · Chapter 19 — Payment processing · *Intent idempotency; double submit*

**Why this step matters:** Payment succeeded **once** — your system must commit orders **once**. Without an idempotency guard, a double-click, a client retry, or a webhook replay quietly charges one payment but creates two order sets.

<BigWordAlert term="Idempotency key" plainEnglish="Unique key on payment requests so retrying network failure does not double-charge." whyItMatters="Shopper double-clicks Pay — FreshMarket must not create two charges for one cart." />

**Where the project is now:** Payment Intents, gated checkout, and the webhook run (19.9–19.12) — nothing stops a double-submit or webhook replay from creating a second order set.

**After this step:** Checkout uses database-enforced uniqueness inside the commerce transaction so one Payment Intent can create only one order per store. Replays return the existing complete order set.

Chapter 18 warned: double-click "Place order" could create duplicate order sets. Payment adds a **natural idempotency key** — the Payment Intent id. Same charge must never produce two sets of split orders.

This sub-chapter is **learn + build**: understand retry semantics, then enforce them in checkout and webhook.

## In plain English

| Term | Simple meaning |
|---|---|
| **Idempotent** | Doing the same operation twice has the **same effect** as once |
| **Idempotency key** | Unique id — here `paymentIntentId` — that identifies one logical purchase |
| **Double submit** | User double-clicks checkout or client retries POST on timeout |
| **Webhook retry** | Stripe sends same event again if your server returned 500 or timed out |
| **At-most-once orders** | One succeeded PI → one set of orders — never two |

## Think of it like a receipt number

The card terminal assigns transaction ref **`pi_abc123`**. If the cashier prints receipts twice for the same ref, accounting is broken. Your database must say: "I already fulfilled **`pi_abc123`**" — second attempt returns the **same orders**, not new ones.

## Failure modes without idempotency

| Scenario | Bad outcome |
|---|---|
| Double POST `/checkout` same PI | Two order sets, stock decremented twice |
| Webhook + checkout both run | Race creates duplicate orders |
| Client retry after 504 | Customer charged once, two fulfilment queues |
| Webhook retry after 500 | Duplicate vendor packing lists |

Payment succeeded **once** — your system must commit orders **once**.

## Build — idempotency contract

Implement in `verifyAndCheckout` (19.11):

**Before** stock decrement or order insert:

1. Query by `stripePaymentIntentId`; a completed replay can return those orders immediately.
2. If none exist, run stock decrement, all split-order inserts, and cart clear in one MongoDB transaction.
3. Enforce a compound unique index on `{ stripePaymentIntentId: 1, storeId: 1 }` because one checkout creates one order per store.
4. If a concurrent request receives a duplicate-key error, abort, reload the complete existing set, and return it.

Do not make `stripePaymentIntentId` alone unique on `Order`; split checkout deliberately repeats it. A plain lookup index improves speed but does not prevent a race.

## Cart + PI timing edge case

| Situation | Policy |
|---|---|
| PI succeeded, cart cleared, idempotent replay | Return existing orders — OK |
| PI succeeded, cart still full (checkout crashed mid-way) | Retry checkout with same PI should **complete or return existing** — never second charge |
| PI succeeded, cart changed before retry | Reject — amount mismatch vs PI; manual support path in README |

Document chosen policy in learning log.

## Webhook vs checkout race

Both may run within milliseconds when payment succeeds.

**Spec:** A read-before-write check is an optimization, not the concurrency guarantee. The transaction plus compound unique index is the guarantee. The webhook records a missing-order reconciliation case rather than calling checkout from a mutable cart.

## Partial-set safety

A replay must never return one vendor order while another from the same checkout is missing. Insert every split order in one transaction so the observable state is either the complete set or no set.

## Client guidance (Chapter 20 preview)

The server-side idempotency only protects the user if the client plays its part. Give the checkout form these habits:

- Disable "Place order" button after first click.
- On network error, retry checkout with **same** `paymentIntentId` — server idempotency makes retry safe.
- Do not create a **new** Payment Intent for the same cart unless user explicitly restarts checkout.

## Connection to Stripe idempotency keys

Stripe API accepts `Idempotency-Key` header on **create** calls — prevents duplicate Payment Intents if client retries `POST /payments/intent`. Optional stretch: store key header, replay same intent response.

Separate from **order** idempotency on `paymentIntentId` — implement order guard for gate.

## ✅ Do / ❌ Don't

**✅ Do:** Check existing orders by `stripePaymentIntentId` at start of checkout.

**✅ Do:** Make webhook handler safe to run 10 times for same event.

**✅ Do:** Log idempotent replays at info — "checkout replay pi_…".

**❌ Don't:** Rely on button disable alone — network retries bypass UI.

**❌ Don't:** Create new PI on checkout retry — same payment, same PI.
