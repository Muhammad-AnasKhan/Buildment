## Chapter 19 — Payment processing checklist (gate)

Do **not** open Chapter 20 until every box is ticked and learning log answers are written below.

### Stripe config

- [ ] `STRIPE_SECRET_KEY` in `server/.env.example` (placeholder only)
- [ ] `STRIPE_WEBHOOK_SECRET` in `server/.env.example`
- [ ] `VITE_STRIPE_PUBLISHABLE_KEY` in `client/.env.example`
- [ ] `shared/stripe.js` exports configured client from config
- [ ] Server fails clearly if secret key missing
- [ ] Test mode only — no live keys in repo

### Payment Intent

- [ ] `POST /payments/intent` requires customer auth
- [ ] Empty cart → 400
- [ ] Amount computed server-side from cart — not from body
- [ ] Returns `paymentIntentId`, `clientSecret`, `amount`, `currency`
- [ ] Dashboard shows intent with matching amount
- [ ] Does not create orders or decrement stock
- [ ] Retried create attempt reuses its Stripe idempotency key
- [ ] Metadata binds the intent to user and cart version without PII

### Payment-gated checkout

- [ ] `POST /checkout` requires `{ paymentIntentId }`
- [ ] Bare checkout without PI → 400
- [ ] Retrieves PI from Stripe API — not client-only status
- [ ] Rejects unless `status === 'succeeded'`
- [ ] Rejects amount mismatch vs server cart total
- [ ] Rejects wrong owner, currency, or changed-cart fingerprint
- [ ] Runs Ch 18 pipeline: split, snapshots, stock, clear cart
- [ ] Each order has `stripePaymentIntentId` (same across split)
- [ ] Each order has `paymentStatus: 'paid'`
- [ ] Vendor token on checkout → 403

### Webhooks

- [ ] `POST /webhooks/stripe` uses raw body parser on this route only
- [ ] Valid signature → 200
- [ ] Invalid signature → 400
- [ ] `payment_intent.succeeded` handled without duplicate orders
- [ ] Stripe event IDs are deduplicated separately from Payment Intent IDs
- [ ] Paid intent without orders is recorded for reconciliation, not rebuilt from a mutable cart
- [ ] Tested with Stripe CLI `listen` locally

### Idempotency

- [ ] Duplicate checkout POST with same succeeded PI → same orders, no double stock
- [ ] Webhook retry does not duplicate orders
- [ ] Two concurrent checkout requests produce one complete split-order set
- [ ] Compound PI/store uniqueness is enforced inside the transaction
- [ ] Strategy documented in README

- [ ] Two-store cart → two paid orders, one PI id
