# 19.2 — Fake checkout trap

> **[Read]** · Chapter 19 — Payment processing · *Free checkout / charge-without-order failure modes*

Chapter 18's `POST /checkout` creates orders, reduces stock, and clears the cart — **without checking whether anyone paid**. That was the right teaching order. It is **not** production.

This sub-chapter names the trap **before** you wire Stripe in 19.9–19.14.

## The bug in one sentence

**Anyone with a customer JWT can empty your vendors' stock for free.**

## How teams accidentally ship this

It never looks like a single decision — it looks like a sensible sequence. Each row below is a step you've already seen in this course, plus the trap hiding behind it.

| Step | What goes wrong |
|---|---|
| Build checkout API first (correct for learning) | Orders and stock work — demo feels "done" |
| Defer payment to "Phase 2" | Phase 2 never ships; app stays free |
| Trust client "paid" flag | `{ paid: true }` in JSON — trivial to forge |
| Skip server-side Stripe verify | Attacker skips Stripe.js entirely; POST `/checkout` directly |
| No webhook | Client closes tab after pay; order never created — angry customer **and** lost revenue |

MongoDB does not know about money. Stripe does not create your orders. **Your server** must connect the two.

## In plain English

| Term | Simple meaning |
|---|---|
| **Fake checkout** | Order pipeline runs without payment verification |
| **Trust boundary** | Anything from the browser is untrusted; server re-checks with Stripe |
| **Revenue leak** | Stock goes down, fulfilment work happens, platform collects ₹0 |
| **Double loss** | Free groceries **plus** oversell if retries duplicate orders |

## Think of it like a self-service checkout with no scanner

Customers bag items and walk out. The **receipt printer** (Chapter 18) works perfectly — split receipts, frozen prices, inventory down. Nobody watched the **till**.

A mentor runs one curl:

```bash
curl -X POST http://localhost:5000/api/checkout \\
  -H "Authorization: Bearer <customer-token>" \\
  -d '{}'
```

If that still creates orders after Chapter 19, your payment gate failed.

## What production requires

Five requirements separate a demo from a payment system. You'll hit all five in the build cluster — the table tells you which sub-chapter answers each.

| Requirement | Chapter 19 answer |
|---|---|
| Money collected before order commit | Verify Payment Intent `succeeded` before Ch 18 pipeline |
| Amount matches cart | Compare Stripe `amount` to server-computed cart total |
| Card data never on your server | Stripe.js + Payment Intents — PCI scope stays small |
| Backup if client disconnects | `POST /webhooks/stripe` with signature verification |
| Test without real charges | Test mode keys + `4242…` card only |

## Grocery marketplace makes it worse

If free checkout is bad for a normal shop, it's worse for one selling perishables across many vendors. The same one-POST attack now damages every stall at once.

| Scenario | Cost of fake checkout |
|---|---|
| Perishable stock decremented | Vendor throws away packed orders nobody paid for |
| Multi-vendor split | **Every** stall loses inventory on one free POST |
| Price snapshots on orders | Legal receipt says ₹400 owed — customer paid ₹0 |
| Demo to investor | One curl destroys credibility |

## The fix (preview — you build in 19.10–19.12)

```
Before (Chapter 18):
  POST /checkout → orders

After (Chapter 19):
  POST /payments/intent → clientSecret
  Stripe.js confirm
  POST /checkout { paymentIntentId }
    → retrieve PI from Stripe API
    → status === 'succeeded' && amount OK
    → then Chapter 18 pipeline
```

**Do not** delete the Chapter 18 pipeline. **Wrap** it.

## UI consequence (Chapter 20)

"Place order" must not call bare `POST /checkout`. Flow becomes:

1. Create Payment Intent (server).
2. Confirm payment (Stripe.js).
3. Checkout with `paymentIntentId` (server).

Chapter 20 builds the screens. Chapter 19 makes the API **honest**.

## Common beginner questions

**Q: Was Chapter 18 wasted?**  
A: No — it was exactly the right order. You built and tested the hardest commerce logic — split orders, snapshots, atomic stock, fail-all — with no payment noise to complicate debugging. Professional teams do the same thing: stub the checkout, prove the core pipeline, then attach the payment gateway at a clean seam. Chapter 19 doesn't rewrite Chapter 18; it wraps it with a verification step. If you'd built both at once, every failure would be ambiguous — is it the commerce bug or the Stripe bug? That's miserable to debug.

**Q: Why can't I just check payment in the browser?**  
A: Because anything the browser does, the browser can be told to lie. A normal user confirms payment with Stripe.js and everything looks fine — but an attacker skips that step and POSTs `/checkout` directly, so your frontend check simply never runs. That's why the trust boundary is hard: browser checks are UX polish, but the **server** must be the authority, calling Stripe's API itself to retrieve the Payment Intent and confirm it actually succeeded before creating any order. No server-side verification, no guarantee of payment — just a pretty button.

**Q: What about cash on delivery?**  
A: That's a completely different product decision. With COD there's no card charge at all, so you'd skip Stripe entirely — but you'd still need a `paymentStatus` enum on your orders (something like `pending`, `paid`, `cancelled`) so fulfilment knows the order hasn't been paid yet. FreshMarket's choice is **card checkout via Stripe test mode**, so this course follows that path: payment happens first, verified by the server, and only then do orders get created. The habit that matters is that payment status lives on the order, whichever method you pick.

**Q: Is the webhook optional?**  
A: For the learning gate, no — it's required. The webhook is your backup line: the customer confirms payment, then closes the tab before your frontend can call `/checkout`. Without a webhook, the money exists but no order was ever created — an angry customer and lost revenue. Stripe calls your server's `POST /webhooks/stripe` when the payment status changes, and you confirm the order from there. Building it teaches two things every Stripe integration needs: **signature verification** (proving the POST really came from Stripe) and **idempotency** (handling the same event twice without duplicating orders).

**Q: What actually stops someone from emptying the store for free?**  
A: Your server — and only your server. In Chapter 18, anyone holding a customer JWT could run one `curl` against `POST /checkout` and create orders, decrement stock, and clear carts without paying a rupee. Chapter 19 closes that hole by making the server refuse checkout unless it can independently confirm a Payment Intent succeeded for the right amount. Never accept a `{ paid: true }` flag from the client — that's just JSON anyone can type. The moment stock only leaves the shelf after a verified payment, the fake-checkout bug is dead.

## ✅ Do / ❌ Don't

**✅ Do:** Treat unpaid checkout as a **bug** after this chapter.

**✅ Do:** Keep Chapter 18 tests — extend them with payment setup.

**❌ Don't:** Add `{ paid: true }` to checkout body without Stripe verify.

**❌ Don't:** Store card numbers in MongoDB "for later".
