# 19.1 — Set the scene

> **[Read]** · Chapter 19 — Payment processing · *Bridge from Ch 18; payment after checkout logic; Stripe test mode*

**Where the project is now:** Chapter 18 gave you a **working checkout pipeline** — one `POST /checkout` turns a multi-vendor cart into split orders with price snapshots, atomic stock decrement, and cart cleared on success. Proof so far is curl and Compass. **No money moves.** Anyone with a customer token can create orders for free.

<BigWordAlert term="Payment processing" plainEnglish="Collecting money from shoppers via a payment provider — Stripe in this course." whyItMatters="FreshMarket without real payments is a demo — Stripe handles PCI and card networks." />

**Where this chapter goes:** **Real Stripe payment processing** — one Payment Intent for the full cart total, client confirmation with Stripe.js, server verification before checkout runs, webhooks as backup. Every split order from one checkout shares the same `stripePaymentIntentId` and `paymentStatus: 'paid'`.

This is a **backend build chapter**. It pairs with Chapter 20 the way Chapter 18 paired with Chapter 17's cart UI. The gate is **payment-gated checkout**: no order without a succeeded Payment Intent.

## Bridge from last chapter

Chapter 18 was deliberate: you built **order logic first** — split by store, snapshots, stock, fail-all semantics — without a payment gateway in the way. That ordering matters.

| Why orders before payment | What would break if reversed |
|---|---|
| Checkout pipeline is already tested | Payment succeeds but order creation fails → charged customer, no receipt |
| Snapshots and stock are the hard part | You debug Stripe *and* commerce bugs at once |
| `POST /checkout` is a clear seam | Payment verification plugs in **before** the existing pipeline runs |

Chapter 18's FAQ said payment was out of scope **for that chapter**. Chapter 19 is where FreshMarket stops being a demo shop that gives groceries away.

**Gate chain:** Clear the Chapter 18 gate before opening this lesson.

What you carry into Chapter 19:

| From Chapter 18 | Why payment depends on it |
|---|---|
| `POST /checkout` pipeline | Payment gate wraps **existing** split-order logic — do not rewrite snapshots |
| Cart total from server-side cart | Payment Intent amount must match **your** computed total, not client guess |
| Split orders (one per store) | One charge, many orders — same Payment Intent id on each |
| Customer auth | Payment routes scoped to logged-in customer |

If checkout without payment still creates orders, **fix Chapter 18 first**. Payment is a guardrail on top, not a replacement.

## In plain English

| Term | Simple meaning |
|---|---|
| **Payment Intent** | Stripe's object for "collect this amount from this customer" — tracks status from `requires_payment_method` to `succeeded` |
| **Stripe.js** | Stripe's browser library — collects card details safely; card numbers never touch your server |
| **Payment-gated checkout** | Server refuses to create orders until Stripe confirms the Payment Intent **succeeded** |
| **Platform collects** | FreshMarket (your platform) charges the customer once — vendors are paid out separately in real life; **not** Stripe Connect in this course |
| **Webhook** | Stripe calls your server when status changes — backup if the client disconnects after paying |
| **Test mode** | Fake money, test keys (`pk_test_…`, `sk_test_…`) — no real charges |

## Think of it like paying at the market hall desk

Chapter 18 built the **receipt printer** — sort items by stall, freeze prices, reduce stock, clear the basket. But the customer walked through without opening their wallet.

Chapter 19 adds the **card reader at the desk**:

1. Cashier totals the basket (`POST /payments/intent`).
2. Customer taps card on the reader (Stripe.js confirms the Payment Intent).
3. Cashier checks the reader says **Approved** (server verifies with Stripe API).
4. **Only then** the receipts print (existing checkout pipeline).

One swipe. Multiple stall receipts. Same transaction reference on every receipt.

## The payment flow (overview)

```
Customer cart (server total = ₹345)
        │
        POST /payments/intent
        │  → Stripe returns clientSecret + paymentIntentId
        │
        Client: Stripe.js confirmCardPayment(clientSecret)
        │
        POST /checkout { paymentIntentId }
        │  → Server: stripe.paymentIntents.retrieve(id)
        │  → status === 'succeeded' && amount matches cart
        │  → run Ch 18 pipeline (split, snapshot, stock, clear cart)
        │  → each Order gets stripePaymentIntentId, paymentStatus: 'paid'
        │
        POST /webhooks/stripe (async backup)
        │  → signature verify, idempotent handling
```

Chapter 20 wires Stripe.js in the browser. This chapter proves the **server** refuses unpaid checkout.

## Common beginner questions

**Q: Why not Stripe Connect for multi-vendor payouts?**  
A: Because Connect is built for marketplaces that split a single charge across many vendors' Stripe accounts — powerful, but a big system to set up and reason about. For a medium-length course, FreshMarket uses **platform collects**: the customer pays you once into your own Stripe account (in test mode), and vendor payout is treated as a separate business process outside this build. You still build the real parts — Payment Intents, server-side verification, webhooks — but you keep the money model simple enough to finish and explain honestly.

**Q: Why verify on checkout if the client already confirmed payment?**  
A: Never trust the browser. A customer — or someone with their token — can modify the frontend, skip Stripe.js entirely, and POST `/checkout` directly with any id they invent. So your server must call Stripe itself: `stripe.paymentIntents.retrieve(id)`, then check the status is `succeeded` and the amount matches the cart total you computed. Only then does the Chapter 18 pipeline run. The client confirmation is UX; the server's Stripe call is the authority that actually decides whether the order exists.

**Q: One Payment Intent for a two-store cart?**  
A: Yes. The customer fills one basket at the market-hall desk and taps their card **once** for the full cart total. That one Payment Intent then links every order that checkout creates — Green Valley's order and Harbor Market's order both store the same `stripePaymentIntentId` and `paymentStatus: 'paid'`. When accounting asks "which charge covers these orders?", one id answers for all of them. Split the **orders** for fulfilment, but keep the **payment** single — that's the whole model, expanded in sub-chapter 19.4.

**Q: Do I replace the Chapter 18 checkout?**  
A: No — you extend it. Chapter 18's pipeline — split orders, price snapshots, atomic stock decrement, cart cleared — is tested and correct, and payment shouldn't touch any of it. You add one verification step at the top of `POST /checkout`: retrieve the Payment Intent from Stripe, confirm it succeeded and the amount matches, and only then let the existing pipeline run. Wrapping beats rewriting: fewer changes mean fewer new bugs, and your Chapter 18 tests still pass with payment attached.

**Q: Will I be moving real money in this chapter?**  
A: No — test mode only, the whole way through. You'll use test keys (`pk_test_…`, `sk_test_…`) and Stripe's success test card `4242 4242 4242 4242`, so charges are fake and no bank is touched. The API shapes, Dashboard views, and error codes are identical to production, so you learn the real thing safely. Live keys (`sk_live_…`) stay out of the repo forever — mentors grade test-mode proof only, and activating live payments is out of scope for this course.

**Q: What if payment succeeds but checkout crashes?**  
A: That's the nasty edge case, and the honest answer is: it needs a backup plan. The customer paid, but your server crashed before creating orders — now you retry the checkout, and if you're not careful, you create duplicate orders. Sub-chapters 19.12–19.13 cover the two tools that handle this: the **webhook**, which lets Stripe tell your server "this payment succeeded" as a backup when the client disappears, and **idempotency**, which makes retries safe by recognizing a payment already handled. Document your edge cases in the learning log.
