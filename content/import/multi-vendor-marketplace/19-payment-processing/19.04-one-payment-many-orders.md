# 19.4 — One payment, many orders

> **[Learn]** · Chapter 19 — Payment processing · *One charge, split orders; shared `stripePaymentIntentId`*

FreshMarket is a **market hall**, not a single shop. The customer fills one basket from Green Valley and Harbor Market, pays **once**, and receives **two fulfilment orders**. This sub-chapter teaches the payment model beginners confuse most.

<BigWordAlert term="Single charge, split orders" plainEnglish="One Payment Intent covering total cart while creating multiple vendor order records." whyItMatters="Shopper pays once for mangoes and bread — FreshMarket splits fulfillment, not card charges." />

## In plain English

| Term | Simple meaning |
|---|---|
| **One payment** | Single Stripe charge for the **entire cart total** |
| **Many orders** | Still one Order document per vendor/store (Chapter 18) |
| **Platform collects** | Money lands in **your** Stripe account (test mode) — not split automatically to vendors |
| **Shared payment reference** | Every order from one checkout stores the same `stripePaymentIntentId` |
| **Fulfilment ≠ billing** | Vendors pack their order; payout to vendors is a separate business step |

## Think of it like one receipt roll, two stall tickets

At the hall checkout you swipe **once** for ₹345 total. The system prints:

- Ticket A — Green Valley's items — ₹305 — ref `pi_abc123`
- Ticket B — Harbor Market's items — ₹40 — ref **`pi_abc123`** (same)

Accounting asks: "Which card charge covers both stalls?" → one Payment Intent id links them.

## Why not one Payment Intent per vendor?

| Approach | Problem for this course |
|---|---|
| One PI per store | Customer confirms **multiple** card taps — terrible UX |
| Stripe Connect per vendor | Correct for marketplaces at scale — out of scope here |
| One PI for cart total | Matches "one checkout button" — **this course** |

You still **split orders** for fulfilment. You do **not** split card charges in Stripe for the medium-course build.

## Data model consequence

After successful checkout, Compass shows:

```
Order 1: { storeId: A, total: 305, stripePaymentIntentId: "pi_...", paymentStatus: "paid" }
Order 2: { storeId: B, total: 40,  stripePaymentIntentId: "pi_...", paymentStatus: "paid" }
```

**Invariant:** Sum of the split-order totals equals the Payment Intent amount for this course because there are no separate fees or tips.

## Amount must come from the server

| Wrong | Right |
|---|---|
| Client sends `{ amount: 100 }` to create intent | Server sums cart lines |
| Client sends discounted total | Server re-validates stock and prices at intent **and** checkout |
| Trust Stripe amount alone at checkout | Recompute cart total; compare to PI `amount` |

Both `POST /payments/intent` and `POST /checkout` must use the **same** total function — extract shared helper in `payments.service.js` or `cart.service.js`.

Convert money with integer arithmetic. Store and sum paise/cents directly, or round each decimal conversion exactly once at the boundary. Floating-point expressions such as `19.99 * 100` are not a reliable accounting model.

## Metadata for debugging

When creating the Payment Intent, set Stripe **metadata** (strings only):

| Key | Example | Why |
|---|---|---|
| `userId` | Mongo user id | Support: which account paid |
| `cartItemCount` | `3` | Quick sanity check in Dashboard |
| `storeCount` | `2` | Expect two orders after checkout |
| `cartFingerprint` | Stable hash/version | Detect that the cart changed after intent creation |

Do not put PII or card data in metadata. Metadata supports ownership and diagnostics; it is not a cart snapshot from which a webhook can safely recreate orders.

## Common beginner questions

**Q: Does each vendor get paid automatically?**  
A: Not in this build, no. With "platform collects," the money lands in **your** Stripe account as one charge, and splitting it to Green Valley and Harbor Market is a separate business step — real marketplaces handle that with Stripe Connect, invoices, or manual settlement, and this course leaves it out of scope on purpose. Your gate is simpler and fully testable: the customer has paid the platform, and every order from that checkout is marked `paymentStatus: 'paid'`. Explain "platform collect ≠ vendor payout" in your README so it's clear this is a deliberate scope cut, not an accident.

**Q: What if the cart total is 0?**  
A: Reject the checkout — don't try to create a zero-amount Payment Intent. A ₹0 charge makes no sense at a card reader and will only confuse Stripe, your test Dashboard, and you. An empty or free cart is an invalid state for checkout, so your server should treat it as an error before any Stripe call happens. Check for a valid, positive total in the same place you validate the rest of the cart — fail early, give the customer a clear message, and don't let the flow continue.

**Q: Can I refund just one stall's items?**  
A: That's a genuinely hard production problem, and it's out of scope here. A single Payment Intent covers orders from multiple vendors, and Stripe's built-in refund applies to the whole charge — splitting one refund across vendors while keeping every stall's accounting correct is complex. This course documents it as out of scope; the stretch note is a **full refund from the Stripe Dashboard** for demo purposes. If you want partial refunds later, research how real marketplaces split refunds across vendor balances — but don't let it block your course gate.

**Q: Why store paymentStatus on the order if Stripe already knows it's succeeded?**  
A: Because your order list shouldn't need to call Stripe just to render a page. Every time you show orders — customer order history, vendor dashboards — reading `paymentStatus: 'paid'` straight from the order document is instant, while asking Stripe about every intent would add network calls and latency to every screen. The order's status is a denormalized copy for fast reads; Stripe stays the source of truth for the actual charge. You set the order's status once, when the webhook or checkout confirms the payment, and keep it in sync.

**Q: Does a single-store cart still use the same pattern?**  
A: Yes — same flow, just less splitting. With only Green Valley in the cart, checkout creates **one** Order document and one Payment Intent, and that single order stores the same `stripePaymentIntentId` and `paymentStatus: 'paid'`. The "one payment, many orders" model simply collapses to one-and-one. Keeping the identical code path for both cases means you never write special logic for single-store carts — the shared helper computes the total, creates the intent, and verifies the amount the same way every time.

## ✅ Do / ❌ Don't

**✅ Do:** Store the same `stripePaymentIntentId` on every order from one checkout.

**✅ Do:** Explain in README that platform collect ≠ vendor payout.

**❌ Don't:** Create two Payment Intents for a two-store cart.

**❌ Don't:** Merge split orders into one because "customer paid once".
