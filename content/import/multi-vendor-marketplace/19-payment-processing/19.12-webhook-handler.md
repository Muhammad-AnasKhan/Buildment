# 19.12 — Webhook handler

> **[Build]** · Chapter 19 — Payment processing · *Stripe webhook; signature verify*

**Why this step matters:** Customers close tabs. Networks drop. Your server might crash after Stripe marks a Payment Intent **succeeded** but before `POST /checkout` finishes. Webhooks are Stripe's **retryable phone call** — "this payment really succeeded."

<BigWordAlert term="Webhook" plainEnglish="HTTP callback from Stripe to your server when payment succeeds — authoritative paid signal." whyItMatters="FreshMarket marks orders paid on `payment_intent.succeeded` webhook — not client redirect alone." />

**Where the project is now:** Checkout verifies PI on `POST /checkout`; no webhook route; Stripe cannot notify your app asynchronously.

**After this step:** `POST /webhooks/stripe` verifies Stripe's signature over raw bytes, deduplicates events, and records payment outcomes for reconciliation.

## Route mounting — critical Express detail

Webhook signature uses **raw body bytes**. Your app likely uses `express.json()` globally.

**Spec:**

1. Register webhook route **before** `express.json()` **or** use `express.raw({ type: 'application/json' })` on **only** `/webhooks/stripe`.
2. Pass raw `Buffer` body to `stripe.webhooks.constructEvent(body, signature, webhookSecret)`.

Wrong parser → signature always fails → 400 → Stripe retries forever.

Document mount order in README with one-line diagram.

## Scaffold webhooks module

```
server/src/modules/webhooks/
  webhooks.routes.js
  webhooks.service.js
```

Full path: `POST /api/webhooks/stripe` (match Stripe CLI forward URL).

**No JWT.** Auth is signature only.

## handleStripeWebhook(rawBody, signatureHeader) — contract

**Steps (spec — you implement):**

1. If missing signature header → 400.
2. `constructEvent` — on failure log and return 400 (invalid signature).
3. Deduplicate by Stripe `event.id`; delivery is at least once.
4. Switch on `event.type`:
   - **`payment_intent.succeeded`:** record the PI id, customer metadata, and whether a complete order set exists.
   - If no orders exist, mark the payment for reconciliation and client retry/support handling.
   - **Do not create orders from the customer's current cart.** It may have changed since intent creation; automatic recovery requires a durable checkout snapshot.
   - **`payment_intent.payment_failed`:** record a sanitized failure state.
   - **Other types:** acknowledge after intentionally ignoring them.
5. Return **200 JSON `{ received: true }`** only after handling or durably recording the event.

`event.id` prevents repeated handling of one delivery. `paymentIntent.id` links multiple event types to one logical payment. Keep those identities separate.

## Local development — Stripe CLI

```bash

```

Copy CLI `whsec_…` into `STRIPE_WEBHOOK_SECRET`. Restart server after env change.

Trigger test event:

```bash

```

## ✅ Do / ❌ Don't

**✅ Do:** Return 200 for events you intentionally ignore — stops endless retries.

**✅ Do:** Acknowledge only after the event effect or reconciliation record is durable.

**✅ Do:** Use constant-time compare via Stripe SDK — do not roll your own HMAC.

**❌ Don't:** Parse webhook with `express.json()` on same route.

**❌ Don't:** Recreate orders from a mutable cart merely because a succeeded event arrived.

**❌ Don't:** Expose webhook URL without signature verify "for testing".
