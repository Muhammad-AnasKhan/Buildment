If queues are new to you: you are **not** changing what checkout returns — you are adding a **second process** that picks up notification tasks after the API says 201.

## In plain English

| Piece | Simple role |
|---|---|
| `queue.js` | API writes a to-do item to Redis |
| `worker.js` | Separate program that reads to-dos and runs them |
| `order.created` job | To-do: "tell vendors and customer about new orders" |
| `order.statusUpdated` job | To-do: "tell customer their order status changed" |

## Common beginner questions

**Q: How many new terminals do I need?**  
A: Two for server-side work: one running the API (`npm run dev`) and one running the worker (`npm run worker`). Add the React dev server and that's three if you're testing in the browser at the same time. It's the same multi-process habit you built in Chapter 2 with client and server — now there's just one more process. The API enqueues jobs, the worker processes them, and Redis is the middleman between the two.

**Q: Will I change the React app?**  
A: No — this chapter is entirely server-side. The browser still calls the same `POST /checkout` and `PATCH /vendor/orders/:id` routes and gets the same responses, with no new fields. The enqueueing happens inside the API handler after the response is ready, so async is invisible to the client. Your proof it works is server timing plus worker logs: 201 arrives first, then `[NOTIFY]` logs appear a moment later.

**Q: What if I already added `sendEmail` in checkout?**  
A: Remove it before 22.11. If you leave it in and also enqueue a job, you're not fixing the sync trap — you're adding async work on top of a handler that still blocks on email. The point of the build steps is to move that side effect *out* of checkout, not to run it twice. Undo the old approach first so you can see the before/after clearly in the worker logs.

**Q: What is a job payload, and why should it stay small?**  
A: The payload is the data you hand the queue so the worker knows what to do — for `order.created`, a few order IDs, the customer ID, and their email. Keep it minimal: pass identifiers and let the worker fetch fresh details from MongoDB if it needs them. That keeps enqueueing fast and avoids acting on stale data sitting in Redis. If the payload carried a full snapshot and the order changed, your notification could be built on outdated facts.

**Q: How does the worker know a new job is waiting?**  
A: The worker keeps a connection open to the same Redis and watches the queue. When the API calls `add()`, the job appears in Redis and the worker picks it up and runs the matching processor — for example, logging the mock vendor and customer notifications. You never tell the worker "go now" directly; the queue is the communication channel. That's why both processes need the same `REDIS_URL`, and why nothing happens if the worker isn't running — jobs just wait in line.

## Job contracts

### `order.created`

**Enqueue when:** `POST /checkout` returns success — all orders inserted, cart cleared, stock decremented.

**Payload (illustrative — you define exact shape):**

```javascript
{
  orderIds: ['...', '...'],       // all orders from this checkout
  customerId: '...',
  customerEmail: '...',           // or fetch in worker from User
}
```

**Worker behaviour:**

- For each order: log mock vendor notification (`storeId`, `orderId`, line summary)
- Once: log mock customer confirmation (all `orderIds`, total count)
- **No** real SMTP required — structured `console.log` with clear prefix e.g. `[NOTIFY]`

**Enqueue from API:** non-blocking — `add()` without awaiting processor completion.

### `order.statusUpdated`

**Enqueue when:** `PATCH /vendor/orders/:orderId` succeeds — status persisted.

**Payload:**

```javascript
{
  orderId: '...',
  customerId: '...',
  previousStatus: 'pending',
  newStatus: 'packed',
  storeId: '...'
}
```

**Worker:** mock customer email — "Your order is now packed".

### `product.updated` (optional)

**Enqueue when:** Product create/update/delete succeeds (instead of or in addition to sync `invalidateCatalogueCache` from 20.11).

**Payload:** `{ productId, action: 'update' | 'create' | 'delete' }`

**Worker:** call same invalidation logic as Ch 21 — keeps PATCH response fast if invalidation was slow.

## HTTP behaviour contract (unchanged externally)

| Endpoint | Response | Change internally |
|---|---|---|
| POST `/checkout` | 201 `{ orders }` | + enqueue `order.created` after commit |
| PATCH `/vendor/orders/:id` | 200 order JSON | + enqueue `order.statusUpdated` after save |

**Clients see no new fields** — async is server-internal.

## npm scripts contract

| Script | Command | Purpose |
|---|---|---|
| `dev` / `start` | existing | API only — enqueues jobs |
| `worker` | `node src/worker.js` | Processes all registered queues |

Document in README: **both must run** for notifications in dev.
