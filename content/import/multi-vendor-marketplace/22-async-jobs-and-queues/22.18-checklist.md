## Chapter 22 — Async jobs and queues checklist (gate)

Do **not** open Chapter 23 until every box is ticked and learning log answers are written below.

### Queue infrastructure

- [ ] `bullmq` (+ `ioredis` if needed) in `server/package.json`
- [ ] `shared/queue.js` connects via `REDIS_URL`
- [ ] `jobs.constants.js` defines queue name + three job names
- [ ] API boots without worker running

### Worker process

- [ ] `server/src/worker.js` exists as separate entry
- [ ] `npm run worker` documented in README
- [ ] Worker registers processors for implemented jobs
- [ ] Worker logs startup message with queue name

### order.created

- [ ] Enqueued **after** checkout commits (orders + stock + cart clear)
- [ ] `POST /checkout` still returns 201 — unchanged response shape
- [ ] Processor logs `[NOTIFY][vendor]` per order / store
- [ ] Processor logs `[NOTIFY][customer]` once per checkout batch
- [ ] A controlled processor delay does not add the same delay to checkout latency (22.15)

### order.statusUpdated

- [ ] Enqueued after successful `PATCH /vendor/orders/:orderId`
- [ ] Invalid transitions do not enqueue
- [ ] Processor logs customer status notification

### Retries and idempotency

- [ ] `attempts` + `backoff` configured
- [ ] `jobId` dedup on `order.created` and `order.statusUpdated`
- [ ] Forced failure test shows retry — documented in learning log
- [ ] Exhausted failures remain visible with job ID and final error
- [ ] API and worker lifecycle logs can be correlated without exposing payloads or secrets

### Optional — product.updated

- [ ] Async cache invalidation wired OR explicitly skipped with reason in log
- [ ] If implemented: 20.11 stale-price test still passes after worker runs

### Prior gates

- [ ] Chapter 21 Redis cache works
- [ ] Chapter 18 checkout split orders
- [ ] Chapter 20 vendor status PATCH
- [ ] Explain sync trap and why checkout must not await email
- [ ] Explain difference between Redis cache keys and BullMQ keys
- [ ] Explain why worker is separate process
- [ ] Name two domain events that enqueue jobs

### Learning log — write now

Answer **in your own words** in the fields below:

1. **Architecture:** Draw or describe API vs worker vs Redis — who enqueues, who processes?

2. **Timing:** Compare checkout latency with and without a temporary processor delay. Why is terminal log order not reliable proof?

3. **Multi-vendor:** Two-store checkout — how many vendor notify logs? Paste redacted worker output.

4. **Status job:** Describe PATCH → enqueue → worker log sequence.

5. **Retries:** Which errors retry, which fail immediately, and what does `jobId` deduplication not guarantee?

6. **Redis shared:** Same `REDIS_URL` as Ch 21 — any conflicts? How do you avoid `FLUSHALL` accidents?

7. **Production preview:** How will you run and monitor the worker in production (PM2, second service, alerts, etc.)?
