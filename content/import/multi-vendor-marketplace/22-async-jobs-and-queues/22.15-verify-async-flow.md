# 22.15 — Verify async flow

> **[Build]** · Chapter 22 — Async jobs & queues · *Latency isolation, delivery, retry, and failure evidence*

Wiring jobs is not proof that the architecture behaves correctly. This lesson tests the boundary under a controlled delay, then checks multi-vendor fan-out, backlog recovery, retry behavior, and observability.

<BigWordAlert term="Async flow verification" plainEnglish="Place order, confirm HTTP fast, check worker logs/email inbox for side effects." whyItMatters="FreshMarket gate proves jobs run — not just enqueue without processing." />

**Where the project is now:** Queue module, worker, and job processors wired. Checkout and status PATCH enqueue jobs — not yet proven end-to-end.

**After this step:** Documented evidence that processor latency does not inflate checkout latency, multi-vendor notify count is correct, and failed or duplicate work is visible.

End-to-end proof that checkout and status PATCH are **fast** and notifications run **asynchronously** in the worker.

## Test 1 — Processor delay does not become checkout delay

**Steps:**

1. Record checkout time with the normal processor.
2. Add a temporary development-only two-second delay at the start of `order.created` processing.
3. Run checkout again with a fresh cart and record the HTTP time.
4. Confirm the worker finishes roughly two seconds later while HTTP latency remains close to baseline.
5. Remove the temporary delay.

**curl with timing:**

**Pass criteria:**

- [ ] HTTP 201
- [ ] Response time stays close to baseline despite the processor delay
- [ ] Worker shows 2× vendor + 1× customer notify logs

Do not rely on terminal line order. The worker can process an accepted job before Node flushes the HTTP response, even though the handler never waits for the processor.

## Test 2 — Worker was down, then started

**Steps:**

1. Stop worker.
2. Run checkout → 201 still succeeds.
3. Start worker → backlog job processes (if `removeOnComplete` allows).

**Pass criteria:**

- [ ] Commerce works without worker — notifications eventual
- [ ] Document behaviour if enqueue fails when Redis down (22.11)

## Test 3 — Status update notification

**Steps:**

1. Vendor PATCH `pending` → `packed` on one order.
2. API 200 immediately.
3. Worker logs `[NOTIFY][customer][status]`.

**Pass criteria:**

- [ ] Status in DB before notify log
- [ ] Customer refresh shows `packed` independent of notify timing

## Test 4 — Retry and exhausted-failure visibility

Throw a temporary retryable error for one known development job. Confirm the worker logs the same job ID with increasing `attemptsMade`, applies backoff, and eventually reaches the failed state after the configured limit. Remove the fault immediately afterward.

Then exercise one permanent validation error and confirm it fails without wastefully retrying as though it were a transient outage.

## Failure diagnosis

| Symptom | Likely cause |
|---|---|
| 201 but no logs | Worker not running or wrong queue name |
| Checkout slowed by processor delay | Handler is awaiting processor work or still sends inline |
| Jobs stuck | Processor throws every attempt — check MongoDB in worker |
| Duplicate logs | Missing `jobId` dedup |
| Job disappears after final retry | Failed-job retention or event logging is misconfigured |
