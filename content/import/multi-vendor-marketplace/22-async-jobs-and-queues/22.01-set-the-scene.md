# 22.1 — Set the scene

> **[Read]** · Chapter 22 — Async jobs & queues · *Bridge from Ch 21; why async after paid checkout; queues/workers FAQ*

**Where the project is now:** Week 4 polish underway — catalogue cached in Redis (Chapter 21), commerce flow complete in browser (Chapters 18–19). Checkout creates orders, decrements stock, clears cart. **No notifications** run after checkout or status changes.

**Where this chapter goes:** **Async job queue** with **BullMQ + Redis** — checkout and status PATCH return fast; **workers** send vendor and customer notifications in the background (mock email via `console.log` for gate).

Same Redis instance from Chapter 21 — different keys than cache. Separate **worker process** (`npm run worker`).

## Bridge from last chapter

Chapter 21 made browsing **fast**. Chapter 22 makes checkout **reliable under side effects** — the emails, SMS, and push notifications every real marketplace sends **after** an order exists.

Right now your checkout handler does the right **synchronous** work:

1. Validate cart  
2. Create orders + decrement stock  
3. Clear cart  
4. Return 201  

That is correct. The trap is step 5 that teams add later: *"Oh, let's also send confirmation emails before we return."* Chapter 22 teaches you to **stop at step 4** and hand step 5 to a **worker** that runs in a separate process.

| Chapter 21 solved | Chapter 22 solves |
|---|---|
| Repeated catalogue reads are slow | Checkout blocked by slow/unreliable notifications |
| Stale prices from cache | 500 errors when email provider times out **after** order already created |
| Search without index | Customer waits 2 seconds for SMTP while staring at a spinner |

**Why after checkout works, not during:** Order creation and stock must be **immediate and consistent** — the customer needs a 201 with order IDs **now**. Email can arrive three seconds later. If email fails, you **retry in the worker** without undoing a valid order.

## In plain English

| Term | Simple meaning |
|---|---|
| **Async (asynchronous)** | "Do this later" — the API responds first, background work follows |
| **Job queue** | A to-do list stored in Redis — jobs wait in line until a worker picks them up |
| **Enqueue** | Add a task to the to-do list — fast, milliseconds |
| **Worker** | A separate Node process that reads the to-do list and does the slow work |
| **BullMQ** | A library that manages the to-do list — retries, scheduling, job metadata |
| **Processor** | The function the worker runs for each job — e.g. "send mock vendor email" |
| **Side effect** | Something that happens because of an action but is not the main result — email after order is a side effect; the order itself is the main result |
| **Sync trap** | Putting slow side effects **inside** the checkout handler so the customer waits or the whole request fails |

## Think of it like a restaurant kitchen

**Synchronous (must happen before the waiter returns):** Take the order, charge the card, print the ticket, deduct ingredients from inventory. The customer cannot leave without knowing whether the order was accepted.

**Asynchronous (can happen after):** Send a text when the food is ready, email a receipt, notify the supplier. If the text fails, the meal still happened — you retry the text later.

Your checkout API is the **waiter**. The worker is the **back office** that sends texts. Chapter 22 wires the ticket to the back office **after** the waiter tells the customer "Order confirmed."

## The sync side-effect problem

```
POST /checkout
  → validate cart
  → create orders
  → decrement stock
  → clear cart
  → send email to customer        ← blocks response
  → send email to vendor A        ← blocks response
  → send email to vendor B        ← blocks response
  → return 201 (800ms later)
```

Customer waits for SMTP. One slow vendor notification fails the whole checkout. Chapter 22 moves notifications **off the request path**.

## Common beginner questions

**Q: What is a queue? I thought Redis was for cache.**  
A: A queue is just a to-do list: jobs line up in order and a worker works through them one at a time. Redis isn't only for caching — it's a fast in-memory store that can hold many kinds of data. Chapter 21 stored cached catalogue strings in it; Chapter 22 stores BullMQ job lists in it. Same Redis server, different key prefixes, so they never collide. Think of the cache as a photograph you look up, and the queue as an inbox where tasks wait their turn.

**Q: Why a separate worker process? Why not just `setTimeout` in the API?**  
A: Because `setTimeout` is a timer that lives and dies with your API process. Restart the server and the pending callback is gone; if it throws, nothing retries it; and it shares memory with HTTP traffic, so a burst of notifications could slow checkout for everyone. A worker is a separate process that survives independently, can retry failed jobs, and can scale on its own in production (Chapter 23). That's the whole point of the "sync trap": slow side effects don't belong inside the request handler.

**Q: What if the worker is not running when a checkout happens?**  
A: Nothing breaks. The API enqueues the job and returns 201; the job simply waits in Redis until you start the worker, then it gets processed. That's "eventual" delivery, which is fine for notifications. Compare that with stock decrement — if that waited, customers could over-order, so it stays synchronous. Notifications can wait; order creation and stock can't.

**Q: Do I need real SendGrid/Mailgun for this chapter?**  
A: No. For the gate, a structured `console.log` with a `[NOTIFY]` prefix is enough — you're proving the queue-and-worker pipeline works, not integrating a paid email provider. When you later swap in a real service, the job payload and the processor shape stay the same; only the "send" line inside the processor changes. That's the nice thing about queues: enqueue, retry, and process mechanics are provider-agnostic.

**Q: Should checkout wait until the worker finishes?**  
A: No — and the gate actually checks this. When you demo, the 201 response should arrive *before* the worker's notification logs appear in the other terminal. If you `await` the worker's processing inside the checkout handler, the customer is back to staring at a spinner while SMTP takes two seconds: you've rebuilt the very "sync trap" this chapter exists to kill. Enqueue the job, return 201, let the worker do the rest.

**Q: What jobs will I build?**  
A: Two required and one optional. `order.created`, enqueued after checkout succeeds, notifies each vendor and the customer. `order.statusUpdated`, enqueued after `PATCH /vendor/orders/:id`, tells the customer their order's status changed. Optional: `product.updated`, to bust the catalogue cache asynchronously — a tie-in to Chapter 21. Each job is a small payload describing what happened; the worker runs the matching processor for it.
