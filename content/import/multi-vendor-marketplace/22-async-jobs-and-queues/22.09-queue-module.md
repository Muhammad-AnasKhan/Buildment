# 22.9 — Queue module

> **[Build]** · Chapter 22 — Async jobs & queues · *`server/src/shared/queue.js` — BullMQ connection*

**Why this step matters:** The queue module is the API's outbound mailbox — every async job in this chapter enqueues through here. One shared module prevents queue-name typos that silently drop jobs.

<BigWordAlert term="Queue module" plainEnglish="Server code defining queues, job types, and enqueue helpers — separate from HTTP routes." whyItMatters="FreshMarket checkout calls `orderQueue.add()` — worker process picks up elsewhere." />

**Where the project is now:** Commerce, cache, and search are complete (Ch 18–21); no BullMQ dependency or queue module — notifications would have to run inline.

**After this step:** `server/src/shared/queue.js` exports a BullMQ `Queue` (or factory) connected via `REDIS_URL` from Chapter 21 config.

## Env contract

Reuse existing — no new variable required:

```
# server/.env.example (already from Ch 21)
REDIS_URL=redis://127.0.0.1:6379
```

`config.js` already exposes `redisUrl` — import in `queue.js`.

## queue.js exports — spec

| Export | Purpose |
|---|---|
| `getNotificationsQueue()` | Returns singleton Queue instance |
| `enqueueJob(jobName, data, opts?)` | Thin wrapper around `queue.add` — optional |
| `closeQueues()` | Graceful shutdown on API exit — optional |

**Queue name:** `notifications` (or constant from `jobs.constants.js`).

**Connection:** `new IORedis(redisUrl, { maxRetriesPerRequest: null })` — BullMQ requires `maxRetriesPerRequest: null` on shared connection (document in README comment).

## Implementation constraints

| Rule | Reason |
|---|---|
| Lazy init or init on first enqueue | Queue setup does not make worker availability an API boot dependency |
| Do not block `server.js` boot on queue connect | Same spirit as Redis cache fallback |
| Log queue connection errors at warn level | Ops visibility |

If `REDIS_URL` is missing, fail with an explicit configuration error rather than silently creating a localhost connection. If Redis is temporarily unavailable during enqueue, the caller may preserve the committed order and log the missed side effect, but that is a documented availability tradeoff—not reliable delivery.

## Queue defaults belong in one place

Put attempts, exponential backoff, and retention defaults on the Queue or the enqueue helper instead of copying them into every service call. A single policy makes later tuning reviewable and prevents `order.created` from retrying while `order.statusUpdated` silently fails once.

Keep payload validation at the enqueue boundary. Reject an empty `orderIds` array or missing status transition before a malformed job reaches the worker.

## jobs.constants.js — spec

Co-locate in `modules/jobs/` or `shared/jobs/`:

```javascript
export const QUEUE_NAMES = {
  NOTIFICATIONS: 'notifications',
};

export const JOB_NAMES = {
  ORDER_CREATED: 'order.created',
  ORDER_STATUS_UPDATED: 'order.statusUpdated',
  PRODUCT_UPDATED: 'product.updated',
};
```

Import in `queue.js` and processors — single source of truth.

## Boot wiring

**API (`server.js`):** No worker here. Optional: import `getNotificationsQueue()` once to verify connection — not required for gate.

**Do not** register Worker in `server.js` — that belongs in `worker.js` (22.10).

## Commit

```bash
git add server/src/shared/queue.js server/src/modules/jobs/jobs.constants.js server/package.json
git commit -m "feat(server): add bullmq queue module"
```

## ✅ Do / ❌ Don't

**✅ Do:** Share `REDIS_URL` with cache — one Redis instance.

**✅ Do:** Export typed job name constants — avoid string typos.

**❌ Don't:** Instantiate Worker in queue module — separation of concerns.

**❌ Don't:** Hardcode Redis host — use config.
