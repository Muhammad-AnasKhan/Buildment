# 22.17 — Recap and what's next

> **[Wrap]** · Chapter 22 — Async jobs & queues · *Recap — what you built and what comes next*

Chapter 22 moved **notifications and optional cache bust** off the HTTP hot path — BullMQ on the same Redis as Chapter 21, separate worker process, commerce responses stay fast.

<BigWordAlert term="Async-ready platform" plainEnglish="HTTP path lean; slow work queued — production pattern before deploy in Chapter 23." whyItMatters="Deployed FreshMarket runs API and worker processes — both need restart survival." />

## What you built

**queue.js** — BullMQ Queue connected via `REDIS_URL`.

**worker.js** — standalone consumer; `npm run worker`.

**order.created** — enqueue after checkout; processor mocks vendor + customer notify.

**order.statusUpdated** — enqueue after vendor PATCH; processor mocks customer status email.

**Retries + jobId** — transient failures retry with backoff; duplicate enqueue is reduced while job records are retained.

**Observability** — enqueue, active, completed, and failed logs share job and domain identifiers without dumping sensitive payloads.

**product.updated** (optional) — async catalogue invalidation tied to Ch 21.

## Architecture you can explain

```
API commits commerce state synchronously
        ↓
API enqueues side-effect jobs (milliseconds)
        ↓
API returns 201/200
        ↓
Worker processes jobs independently
```

Week 4 demo: a controlled processor delay does not increase checkout latency. That is stronger evidence than the incidental order of two terminal lines.

## What you did not build (by design)

- Real SendGrid/Mailgun integration
- Kafka or separate microservice
- Inventory reservation queues (built in **Chapter 24**)
- Bull Board UI (optional stretch)
- Transactional outbox for guaranteed database-to-queue handoff
- Exactly-once email delivery; BullMQ processing is at least once

Swap `console.log` for email provider in portfolio — same queue shape.
