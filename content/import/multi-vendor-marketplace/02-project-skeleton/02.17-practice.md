## Stretch goal

Add a second public endpoint on the API and surface it on Home (or a footnote section).

## Server contract to implement

| Method | Path | Auth | Success |
|---|---|---|---|
| GET | `/version` | None | `200` JSON |

Response body **minimum:**

```json
{
  "version": "0.1.0",
  "name": "GreenBasket API"
}
```

Use your product name and a semver string you choose. **You implement the route** — same pattern as `/health`.

Mount at root `/version` or under `/api/version` — if you prefix, update client helper path to match.

## Client task

1. Add `getVersion()` to `api/client.js` (or extend generic GET helper)
2. On Home, fetch version after health succeeds — or in parallel with `Promise.all`
3. Display version string under API status

**Handle errors** — version fetch failing shouldn't crash page if health succeeded (decouple state).

## What people get wrong on this stretch

The point is to repeat the loop cleanly, not to rush a second endpoint. Three classic misses:

1. **Copy-pasting the health handler and forgetting the contract** — the version endpoint returns `version` + `name`, not the health `status`. Read the response JSON, don't assume it matches `/health`.
2. **Coupling the version fetch to the health fetch** — if `Promise.all` fails, one error hides the other. Decouple the states so a version failure never blanks the health display (and vice versa).
3. **Mounting the route but not updating the client path** — if you prefix `/api/version`, update `getVersion()` to match. A 404 here is a path mismatch, not a logic bug.
