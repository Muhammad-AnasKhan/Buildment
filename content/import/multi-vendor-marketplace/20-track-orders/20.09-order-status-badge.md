# 20.9 — Order status badge

> **[Build]** · Chapter 20 — Track orders · *pending → packed → dispatched*

**Why this step matters:** One shared badge component keeps status labels consistent across confirmation, customer history, and vendor inbox — without it, the same order shows "Pending" in one place and "pending" in another.

<BigWordAlert term="Fulfilment status" plainEnglish="The vendor-owned progress of a paid order: pending, packed, then dispatched." whyItMatters="Customers and vendors need the same words for the same server state, with text as well as colour." />

**Where the project is now:** Confirmation (20.6), customer history (20.7), and vendor inbox (20.8) render status strings — each page formats them differently.

**After this step:** Orders display **status** consistently — `pending` → `packed` → `dispatched` (or your enum).

## Component contract

`OrderStatusBadge.jsx` — prop `status: string`.

| Status | Visual |
|---|---|
| `pending` | Neutral — awaiting fulfilment |
| `packed` | In progress |
| `dispatched` | Complete / shipped |

Use customer-facing labels such as “Order received,” “Packed,” and “Dispatched” while keeping the raw enum in code. Map an unknown value to “Status unavailable” and log it; showing an arbitrary server string can expose internal vocabulary and hide a schema mismatch.

This component displays **fulfilment** status only. If payment state appears on an internal vendor view, render it separately as `paymentStatus`; `paid` is not a step between `pending` and `packed`.

## Schema alignment

Use exact enum values from Order model (Ch 5). Document in README:

```
pending | packed | dispatched
```

Optional: `cancelled` — out of scope unless implemented.

## Where used

- Order confirmation
- My orders list
- Vendor orders list

Single component — one mapping table.

## Accessibility

Badge text must be readable without colour and meet contrast requirements in every state. A static badge usually needs no special ARIA role because its text is already exposed. Put `aria-live="polite"` on the surrounding update message when a status changes instead of making every badge announce itself on initial page load.

## ✅ Do / ❌ Don't

**✅ Do:** Centralize status → label/color map.

**✅ Do:** Default new orders to `pending` from API.

**❌ Don't:** Hardcode different labels per page.

## Verify

- [ ] Badge consistent on customer and vendor pages
- [ ] Unknown status has a safe fallback and development warning
- [ ] Text and contrast communicate status without relying on colour
