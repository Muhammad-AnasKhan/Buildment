**Why this step matters:** Customers review their order, pay with a test card, and only then trigger `POST /checkout` with a verified `paymentIntentId`.

**Where the project is now:** Cart page groups items by store (Ch 17); Ch 19 provides payment intent + gated checkout API. No `/checkout` screen with payment form yet.

**After this step:** Customer reviews cart at `/checkout`, pays via **Stripe Payment Element**, then `POST /checkout` with `paymentIntentId`, then navigates to confirmation.

## Payment flow — contract

```
/cart → /checkout
  1. Load cart (grouped, read-only)
  2. POST /payments/intent → clientSecret
  3. Render Payment Element with clientSecret
  4. Customer clicks "Pay and place order"
  5. stripe.confirmPayment() → succeeded
  6. POST /checkout { paymentIntentId }
  7. Navigate to /orders/confirmation with { orders }
```

**❌ Don't** call `POST /checkout` before step 5 succeeds.  
**❌ Don't** send prices in checkout body — server snapshots from cart.

Treat the displayed cart total as a review aid, not the charge authority. The payment-intent endpoint must recalculate from the authenticated server cart. If the cart changes after the intent is created, stop and create a fresh intent rather than trying to force the old amount through checkout.

## Step 1 — API helpers

| Helper | Contract |
|---|---|
| `createPaymentIntent()` | `POST /payments/intent` → `{ clientSecret, paymentIntentId }` |
| `checkout({ paymentIntentId })` | `POST /checkout` with body → `{ orders: [...] }` |

Bearer via Ch 7 interceptor on both.

## Step 2 — Page load

1. On mount: `getCart()` — reuse `StoreCartGroup` / `CartItemRow` **read-only**.
2. Parallel or sequential: `createPaymentIntent()` when cart non-empty.
3. Wrap payment section in `<Elements stripe={stripePromise} options={{ clientSecret }}>`.
4. Empty cart → redirect to `/cart` or `/shop`.
5. Render per-store sections + **grand total** (sum of store subtotals).

Create one Payment Intent for the current cart version, not on every render. React development mode may run effects more than once, so guard the request and ignore stale responses after unmount. A remounted Payment Element must use the client secret that belongs to the currently displayed cart.

| Data | Display |
|---|---|
| Group by `storeId` | One section per store |
| `storeName` | Section heading |
| Line name, unit, price, qty | Read-only rows |
| Per-store subtotal | Sum of line totals |
| Payment Element | Below totals — card entry |

## Step 3 — Pay and place order

1. **Pay and place order** button:
   - `isSubmitting` disables button
   - Call `stripe.confirmPayment({ elements, redirect: 'if_required' })`
2. On `succeeded`:
   - `checkout({ paymentIntentId })` from payment-intent response
3. Success `201` → navigate to `/orders/confirmation` with `{ orders }` in state
4. On payment error → show Stripe/message inline; stay on checkout
5. On checkout API error after payment succeeded → show urgent message (payment captured — document support flow in README); log for mentor
6. On full success, refresh cart badge so header count clears

Model this as explicit UI states such as `loading`, `ready`, `confirming-payment`, `creating-orders`, `recovery`, and `complete`. Disable navigation-sensitive controls while either payment confirmation or order creation is in flight.

If Stripe succeeds but `POST /checkout` times out or returns 5xx, **do not charge again**. Keep the original `paymentIntentId`, explain that payment may already be complete, and offer a retry that sends the same id. Chapter 19's idempotency contract must return/recover the existing order batch without duplicates. Also link to `/orders` so the customer can check whether the orders already exist.

## POST /checkout — API contract (Ch 19)

```
POST /api/checkout
Authorization: Bearer <customer-token>
Content-Type: application/json

{ "paymentIntentId": "pi_..." }
```

| Response | UI action |
|---|---|
| `201` + `{ orders: [...] }` | Navigate to confirmation |
| `400` empty cart / bad intent | Message; do not navigate |
| `409` intent reused | Message; link to order history |
| `401` | Redirect login |
| `5xx` | Message + retry guidance |

The `409` and recovery cases should check order history before suggesting another payment. A generic “try again” that creates a new Payment Intent risks duplicate charges and destroys customer trust.

## Accessibility contract

Use a real form with one clear submit button. Move focus to the error summary after a failed attempt, announce payment/order progress through a polite live region, and keep Stripe's embedded fields reachable in keyboard order. Do not communicate declined, processing, or successful states by colour alone.

## ✅ Do / ❌ Don't

**✅ Do:** Create intent only when cart has items; remount Elements when `clientSecret` changes.

**✅ Do:** Disable button during confirm + checkout POST; show two store sections for two-vendor carts.

**✅ Do:** Clear cart badge on success via cart refetch.

**✅ Do:** Reconcile with the checkout API response; never fabricate order ids or statuses in client state.

**❌ Don't:** POST /checkout before Stripe reports `succeeded`.

**❌ Don't:** Put secret key in client — publishable key only.

**❌ Don't:** Skip auth header — interceptor from Ch 7 must attach Bearer token.

## Troubleshooting

| Observation | Likely cause | Action |
|---|---|---|
| Payment Element blank | Missing `clientSecret` or publishable key | Check env; intent created? |
| 401 on checkout | Token missing/expired | Re-login |
| Payment ok, checkout 400 | Amount mismatch or intent not succeeded | Server logs; re-create intent |
| Payment succeeded, checkout timed out | Order result unknown | Retry same Payment Intent id; check order history |
| 201 but one order | Single-store cart | Add second vendor's products |
| CORS error | URL mismatch | Align `VITE_API_URL` |
