## Common beginner questions

**Q: Do I need to rebuild the cart page?**  
A: No. The Chapter 17 cart page stays exactly as it is — you only add a path from its existing CTA to the new `/checkout` route. This chapter is purely additive: new pages (`Checkout.jsx`, `OrderConfirmation.jsx`, `MyOrders.jsx`, `VendorOrders.jsx`) plus reusable components like `OrderCard`, `OrderStatusBadge`, and `OrderLineRow`. Because the cart already groups items by store, checkout just has to read what the cart hands over and turn it into a request to `POST /checkout`.

**Q: Do I need any new backend work for this chapter?**  
A: Almost none — and that's a sign you're building on solid APIs. There are no new MongoDB collections, no Redis, no background workers. The only possible server addition is `PATCH /vendor/orders/:orderId` to update order status, and only if Chapter 18 didn't already build it (with vendor ownership and store scope required). Everything else is React calling the routes from Chapters 18–19 through helpers like `checkout()`, `getMyOrders()`, `getVendorOrders()`, and `updateOrderStatus()`.

**Q: How do the customer and vendor see the same order differently?**  
A: They read the same data — the same `orderItems` shape, the same snapshots — but from different routes. The customer's `/orders` page lists the orders they paid for, while the vendor's `/vendor/orders` page shows only orders containing products from *their* store. That isolation is enforced server-side by ownership and store-scope checks, so the UI simply renders what it's given. Reusing one `OrderLineRow` component on both pages keeps the two views from drifting apart as you build.

**Q: What does "pass state or refetch" mean for the confirmation page?**  
A: After payment succeeds you need to show what was just ordered — the split orders and their totals. "Pass state" means sending the order data from checkout to `/orders/confirmation` via React Router's `state`, which is instant but lost if the page is refreshed. "Refetch" means calling the order API again when the page mounts, which costs one request but always stays accurate. Either is fine for the course; the key is that confirmation must never depend on data that vanished when the page reloaded.

**Q: Can the vendor and customer share one browser session for the demo?**  
A: No — that would hide the isolation this chapter proves. If both accounts share a session, you can't demonstrate that Vendor A never sees Vendor B's orders, or that the customer badge updates when the vendor marks an order `packed`. Use separate browser profiles or an incognito window: one for the customer, one for the vendor, and let the demo script show the two views side by side. Isolation proof is literally part of the Week 3 gate.
