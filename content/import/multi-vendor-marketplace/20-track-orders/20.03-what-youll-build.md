## User flows you are wiring

```
Customer:  /cart → /checkout → [Place order] → /orders/confirmation → /orders
Vendor:    /vendor/orders → [Mark packed] → customer refreshes /orders
```

## Shared state contract

Customer and vendor pages must render the same order id, snapshot lines, total, and fulfilment status returned by the server. Keep formatting in shared components, but keep permissions in the API: the customer route is scoped by `customerId`, the vendor route by the vendor-owned store.

Each page must distinguish four states:

- loading: the request has not resolved;
- empty: a successful request returned no orders;
- error: the request failed, with a retry action;
- ready: authoritative orders render.

Do not use an empty array as both “still loading” and “no orders.” That creates a misleading flash and makes failures look like valid empty accounts.

## Optional API addition

If status PATCH not built in Ch 18:

```
PATCH /vendor/orders/:orderId
{ "status": "packed" }
```

Vendor ownership + store scope required. Implement in 20.10 if missing.

## Definition of Done preview

- [ ] Full Week 3 demo in browser (script in 20.11)

- [ ] Vendor isolation in UI — A never sees B's orders
- [ ] Status badge updates after vendor PATCH + customer refresh

## Definition of done

- the checkout button cannot create overlapping submissions;
- payment success followed by an API error has a clear recovery path;
- confirmation never guesses which old orders belonged to the latest payment;
- customer and vendor pages render snapshots through shared components;
- vendor status controls expose only valid next transitions;
- the API response reconciles every status update;
- focus, error announcements, button labels, and status text work without relying on colour.
