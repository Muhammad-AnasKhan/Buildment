# 20.4 — Where the project is now

> **[Build]** · Chapter 20 — Track orders · *Paid checkout API tested*

**Why this step matters:** UI built on broken APIs wastes hours — wrong JSON shapes, missing routes, and snapshot fields you never tested in curl all become mysterious React bugs. Five minutes of API proof here saves an afternoon of debugging empty confirmation pages.

**Build cluster starts here.** Chapter 18 left checkout working via API — orders exist in MongoDB with embedded snapshots. Chapter 20 adds the **browser layer** so customers and vendors see those orders without curl.

**After this chapter:** Full Week 3 commerce demo in the browser — browse → cart → checkout → confirmation → order history on both sides.

Save one redacted JSON response per route in the learning log. Confirm both list routes return the same order ids, snapshots, totals, and fulfilment statuses for the same checkout; only actor-specific fields should differ.

## Expected order JSON shape (UI contract)

Customer and vendor pages read **embedded** line items — no product lookup for price:

```json
{
  "_id": "...",
  "storeId": "...",
  "status": "pending",
  "total": 305,
  "orderItems": [
    {
      "nameAtPurchase": "Organic milk 1L",
      "priceAtPurchase": 120,
      "unitAtPurchase": "each",
      "quantity": 2
    }
  ],
  "createdAt": "..."
}
```

Vendor list may add `customerId` or populated customer name — match your API from Ch 18.

## Status enum — align UI badges

Use the same `status` values your Order schema defines, e.g.:

`pending` → `packed` → `dispatched`

Keep `paymentStatus: paid` separate. `cancelled` is not part of this module unless your server already defines its authorization, stock, refund, and transition rules.

Vendor PATCH in **20.10** must send the same enum the API accepts.
