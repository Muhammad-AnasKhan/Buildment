# 20.6 — Order confirmation page

> **[Build]** · Chapter 20 — Track orders · *Receipt after checkout*

One payment can create **two orders** (one per vendor). The confirmation page proves checkout worked and shows the customer what they bought — using **snapshot prices**, not live catalogue prices.

<BigWordAlert term="Order confirmation" plainEnglish="Post-payment thank-you page showing order IDs and summary — reduces buyer anxiety." whyItMatters="FreshMarket shoppers need immediate proof payment worked — before email receipt arrives." />

![Order confirmation — UI preview](/showcase/multi-vendor-marketplace/order-confirmation-page.png)

*Production-style UI preview — thank-you message, separate order cards per vendor, snapshot line prices.*

---

## Step 1 — Create the route

**Path:** `/orders/confirmation`  
**Auth:** Customer only (protected route)

**Data source:**

| Pattern | When |
|---|---|
| Navigation state from checkout | Primary: exact `{ orders: [...] }` batch |
| Exact batch lookup | Use only if your API can query by saved order ids or Payment Intent id |
| Order-history link | Safe fallback when exact batch identity was lost on refresh |

Do not fetch all history and assume the newest two orders belong to this payment. Another tab, a retry, or a webhook can make that guess wrong. Without an exact batch lookup, explain that confirmation details are no longer in navigation state and send the customer to `/orders`, where every authoritative order is visible.

---

## Step 2 — Layout per order

For **each order** in the checkout response, show:

| Element | Source |
|---|---|
| Store name | From order or populated store |
| Order id | Short display OK |
| Line items | **Snapshots only** — nameAtPurchase, priceAtPurchase, unitAtPurchase, quantity, lineTotal |
| Order total | order.total |
| Status | `pending` badge |
| Link | "View all orders" → `/orders` |

**Heading:** "Thank you — your orders are placed" (use plural when 2+ orders)

Show the full order id through a copy action even if the visible label is shortened. Support needs the real identifier, and two truncated ids can look identical.

---

## Step 3 — Explain the split

One friendly sentence:

*"Each store will pack and deliver their items separately."*

This connects to the cart grouping from Chapter 17 — the customer already saw the split before paying.

---

## Step 4 — Empty / edge cases

| Case | UI |
|---|---|
| Landed without state and no exact lookup | Explain recovery; link to order history |
| Single-store checkout | One order block — still use same layout |
| Two-store checkout | Show count: "2 orders from 2 stores" |
| Exact lookup fails | Error message + retry and order-history link |

On navigation, focus the confirmation heading and announce the number of orders created. Use semantic headings for each store receipt so screen-reader users can move between split orders without reading every line.

---

## What NOT to do

- Do not populate live `product.price` for display — use snapshots
- Do not merge all lines into one receipt — hides the multi-vendor split

---

## Verify

1. Complete two-store checkout in browser
2. Confirmation shows **two order sections**
3. Totals match API response
4. Hard refresh — exact batch refetch works, or a clear recovery state links to history without guessing
