## Two states, two owners

Orders now carry two different kinds of truth. `paymentStatus` records whether the platform verified the Stripe payment; the fulfilment `status` records what the vendor has done with that paid order. Do not merge them into one badge or allow a fulfilment click to rewrite payment state.

| State | Authority | Example |
|---|---|---|
| Payment | Stripe, verified by the server | `paid` |
| Fulfilment | Store-scoped vendor action | `pending` → `packed` → `dispatched` |

The browser displays these server-owned values. It may update quickly after an action, but the API response—not an optimistic guess—is the final authority shared by customer and vendor views.

## In plain English

| Term | Simple meaning |
|---|---|
| **Checkout page** | Review cart + Stripe card form + Place order |
| **Payment Element** | Stripe's embeddable payment UI — safe card entry on your page |
| **Order confirmation** | "Thank you" after pay — may show **more than one order** if items came from different stores |
| **Order history** | Past orders the customer can return to |
| **Vendor order inbox** | Vendor's list of orders to pack — only **their** store's orders |
| **Order status** | Fulfilment progress — `pending` → `packed` → `dispatched` |
| **Snapshot fields** | Prices and names **frozen at purchase** on each line |

## Think of it like a real grocery run

You filled your basket at two stalls (multi-vendor cart). At checkout you review totals, tap your card on the machine (Payment Element), and the system prints **two receipts** — one per stall.

Chapter 20 builds those screens:

- Customer sees both receipts on confirmation and in order history.
- Each stall owner sees only **their** receipt.
- Status badges update when a stall marks "packed."

## What a trustworthy UI must communicate

Customers need to know that one charge can produce multiple store orders, that each store fulfils separately, and that old receipts never change when catalogue prices change. Vendors need a focused queue containing only their store's orders and one valid next action per status. Both actors need clear loading, empty, error, and retry states rather than a blank screen that looks like “no orders.”

Use separate browser sessions for the customer and each vendor. The Week 3 proof is not merely that both pages render; it is that one authoritative order changes on the vendor side and the customer later sees the same state without either client inventing it.
