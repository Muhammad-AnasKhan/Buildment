# 20.7 — Customer orders page

> **[Build]** · Chapter 20 — Track orders · *List from `GET /orders/my`*

**Why this step matters:** Confirmation is a one-time screen — order history is where customers return days later. This page proves snapshot prices stay correct when vendors change the catalogue.

<BigWordAlert term="Customer order list" plainEnglish="Page listing shopper's orders with status, date, and link to detail." whyItMatters="Returning FreshMarket customers check 'where is my order' here." />

**Where the project is now:** Confirmation page shows orders after checkout (20.6). No persistent **order history** route — refresh or return later has no dedicated home.

**After this step:** `/orders` lists customer history from `GET /orders/my` — split orders as separate cards with snapshot line prices.

History is where the **price snapshot trap** (Ch 18) shows in UI. Every line reads `orderItems` embedded fields — never live catalog prices.

## Step 1 — API contract

```
GET /api/orders/my
Authorization: Bearer <customer-token>
```

**Middleware:** `requireAuth`, `requireRole('customer')` — Ch 18.15.

| Field | Use in UI |
|---|---|
| `_id` | Card key |
| `status` | `OrderStatusBadge` |
| `total` | Formatted currency |
| `createdAt` | Date/time |
| `storeId` / populated store | Store name heading |
| `orderItems[]` | `nameAtPurchase`, `priceAtPurchase`, `unitAtPurchase`, `quantity` |

Response: array or `{ orders: [...] }` — match vendor list envelope. Sort `{ createdAt: -1 }` on server.

## Step 2 — Page load contract

1. On mount → `getMyOrders()`.
2. Loading → spinner (not empty state).
3. Zero orders → empty state + link to `/shop`.
4. With orders → one `OrderCard` per order, newest first.
5. `401` → redirect login; 5xx → message + retry.

Keep the last successful list visible during a manual refresh and mark it as updating, rather than flashing back to an empty page. Ignore responses from requests started for a previous user session. The API response remains authoritative: replace the list from the successful response instead of merging guessed statuses.

## Step 3 — OrderCard contract

| Data | Display |
|---|---|
| Store name | Card title |
| `createdAt` | Human-readable date |
| `status` | Badge |
| `total` | Prominent total |
| `orderItems` | `OrderLineRow` list or expandable section |

**Split orders:** Two orders from one checkout → **two cards** — do not merge. Match confirmation formatting (20.6).

Add **Orders** nav link; confirmation "View all orders" → `/orders`. Customer role only.

Use an `<h1>` for the page, an accessible list for order cards, semantic headings per store, and a labelled “Refresh orders” control. When a refresh changes a fulfilment status, announce the updated label in a polite live region; the badge text must still make sense without colour.

## ✅ Do / ❌ Don't

**✅ Do:** Separate cards per order; reuse `OrderLineRow` from confirmation.

**✅ Do:** Show `pending` badge on new orders.

**❌ Don't:** Fetch live product prices or populate product for display.

**❌ Don't:** Merge split orders into one receipt card.

## Troubleshooting

| Observation | Likely cause | Action |
|---|---|---|
| One card after two-store checkout | UI merging by date | One card per `order._id` |
| Wrong line prices | Used product populate | Read snapshot fields |
| Empty after checkout | Wrong logged-in user | Match checkout session |
| 403 | Vendor token on customer route | Separate sessions |
| Flash of empty state | No loading flag | Spinner until response |
