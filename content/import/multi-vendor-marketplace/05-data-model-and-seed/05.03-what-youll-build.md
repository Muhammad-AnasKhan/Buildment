# 5.3 — What you'll build

> **[Read]** · Chapter 05 — Data model & seed · *All Mongoose models + seed script + ERD*

By the end of Chapter 5, your repo contains **six Mongoose models**, a **runnable seed script**, and a **final ERD** committed to `docs/erd.md`. No API routes yet — only schemas and test data.

<BigWordAlert term="Domain model layer" plainEnglish="The set of Mongoose schemas representing FreshMarket entities — users, stores, products, carts, orders." whyItMatters="Every API chapter from auth to checkout reads and writes through these models." />

## Why this matters for absolute beginners

Chapter 5 is where FreshMarket becomes **real in the database** — not health checks, not empty folders, but vendors, stores, and products you can click in Compass. The deliverables table is your gate checklist. Weak models here mean every auth, cart, and checkout chapter fights the same schema mistakes. Strong models mean you mostly **wire routes** to shapes that already exist.

## Common beginner questions

**Q: Why six models before any routes?**  
A: Because every route you'll write later needs a real, predictable shape to read and write against. Think of a schema as the contract between your database and your handlers: register needs User and Profile fields, vendor CRUD needs Store and Product, cart and checkout need CartItem and Order. Define each shape once and every later chapter reuses it. If you wrote routes first, you'd guess field names like `price` vs `cost`, then refactor both the model and every handler that touched it. Strong schemas now mean later chapters mostly wire routes to shapes that already exist.

**Q: Why build CartItem and Order schemas now when their routes don't arrive until much later?**  
A: Because the schema is the contract that the cart and checkout chapters will code against, and it's far cheaper to define it now than to retrofit it. The Order model must embed `orderItems` with snapshot fields like `priceAtPurchase` — that decision shapes how checkout works in Chapter 18, so it belongs with the rest of the data model, not bolted on later. Your final ERD also needs the full picture, and the gate wants seed data visible in Compass. These models aren't dead weight; Chapter 16 and 18 import them directly.

**Q: Must seed create exactly `vendor-a@test.local`?**  
A: You don't need that exact string, but you do need deterministic, documented test identities — and this course uses those emails for a reason. Chapter 8's isolation tests assume two distinct vendors they can look up by email. If your seed uses random or undocumented emails, the tests can't find the vendors, and a teammate can't reproduce your data. Decide your test identities once, use them everywhere — seed, login tests, demo scripts — and document them in the README. Predictability is the whole point of seed data.

**Q: What's an idempotent seed?**  
A: An idempotent operation gives the same result no matter how many times you run it — so running `npm run seed` twice doesn't leave you with four stores and double products. Two common patterns: clear-then-insert, where the script wipes the collections first then inserts fresh; or upsert, where it inserts new documents and updates existing ones matched by a stable key like email. The goal for FreshMarket is that seed is safe to run repeatedly without polluting the database in ways that break later tests. Document whichever pattern you choose in the README.

**Q: Keep `erd-draft.md`?**  
A: Yes — keep it as the "before" picture, because the diff between draft and final tells the story of your design evolving. The draft from Chapter 3 is a sketch; the final `erd.md` must match your implemented Mongoose schemas field for field. In your learning log, note what changed and why — for example, you added `isPublished` on Product because vendors need a draft state before a product goes live. Keeping both shows an interviewer you don't just ship code; you can explain how a design changed and what drove that decision.

## Seed data specification

The seed script must create **deterministic, named test entities** for isolation tests in Chapter 8:

| Entity | Count | Notes |
|---|---|---|
| Vendor users | 2 | `vendor-a@test.local`, `vendor-b@test.local` — passwords hashed in Ch 6; plain for seed OK if documented |
| Customer users | 2 | `customer-a@test.local`, `customer-b@test.local` |
| Profiles | 4 | One per user |
| Stores | 2 | Store A → Vendor A; Store B → Vendor B |
| Products | 5–10 per store | Mix of perishable/non-perishable; varied units |
| CartItems | 0 | Created in later chapters |
| Orders | 0 | Created at checkout demo |

**Idempotent seed:** Running seed twice should not duplicate stores — use upsert or clear-then-insert pattern. Document your choice in README.

## Model design principles (course mandate)

1. **Module colocation** — each model lives in its feature module folder
2. **Refs over embed** — except order line snapshots
3. **Grocery fields** — not generic `{ title, price }` only
4. **Indexes noted** — unique email on User; compound indexes where queries demand (document in ERD)
5. **Timestamps** — `createdAt` / `updatedAt` on all collections
6. **No route handlers** — models and seed only
