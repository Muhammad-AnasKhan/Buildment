**Where this chapter goes:** You implement **every collection** your marketplace needs — User, Profile, Store, Product, CartItem, Order — with grocery-specific fields, a seed script that populates realistic test data, and a final **`docs/erd.md`** aligned with what you actually built.

<ArticleBreak title="The FreshMarket ownership chain" subtitle="User → vendor → store → product → cart → order" readMinutes={7}>

Every document in FreshMarket answers one question: who owns this, and who is allowed to change it?

A User becomes a vendor by opening a store. Products belong to exactly one store. Carts belong to shoppers. Orders split by vendor at checkout because each shop fulfils its own items.

Draw this chain before you write handlers. Authorization bugs — a vendor editing another vendor's tomatoes — almost always trace back to a missing link in this chain.

</ArticleBreak>

## Bridge from last chapter

Chapter 4 connected MongoDB — `shared/config.js`, `shared/db.js`, boot order correct, `GET /health` reporting `db: connected`. Your database is **reachable but empty** (or nearly so). Chapter 3's ERD describes vendors, stores, products, carts, and orders; Chapter 2's module folders wait for files.

What carries forward: connection helpers (seed will reuse `connectDB()`), your ERD draft, and empty `modules/*` placeholders. What you add now is **enforceable structure** — Mongoose schemas for every collection, grocery-specific product fields, embedded order line snapshots, and seed data with **two vendors** so isolation tests in Chapter 8 have something to attack.

The hat you wear now is **domain modeller**. You translate paper design into schemas that every future route depends on. Wrong refs break vendor isolation; missing snapshot fields break order history at checkout. Auth routes come in Chapter 6 — but they need User and Profile documents to exist first. That is why schemas precede login API work.

## In plain English

| Term | Meaning |
|---|---|
| **Mongoose schema** | Blueprint for one collection — field types, required flags, enums |
| **Model** | The compiled schema you call to create and query documents |
| **`ObjectId`** | MongoDB's default id type — used for references between documents |
| **`ref`** | Field pointing to another collection's document — enables `populate()` |
| **Seed script** | A one-off program that inserts test data — two vendors, sample products |
| **Ownership chain** | User → Store → Product — who may touch which document |
| **Snapshot fields** | Copied price/name/unit on order lines — frozen at purchase time |
| **Denormalisation** | Copying data for speed — correct on orders, wrong on live products |

## Common beginner questions

**Q: Why models before auth — shouldn't login come first?**  
A: Because login and register code need real User and Profile documents to exist before they can do anything. Register creates a User with fields like `email`, `passwordHash`, `role`, and `isVerified`; login reads `passwordHash`. If you build the auth routes first, you'll be guessing field names against imaginary users, and you'll refactor both the model and the route when the shape finally lands. Data shape first, HTTP layer second. Think of it as writing the tenant roster before the security desk stamps anyone in — Chapter 6's register flow depends on the documents Chapter 5 defines.

**Q: Why separate User and Profile?**  
A: Because login identity and display information change at different rates and serve different jobs. The User holds auth-critical, rarely-changing fields — email, password hash, role, verification status — while Profile holds display data like name and avatar that updates often. Splitting them keeps auth queries lean (you don't drag an avatar along when verifying a login) and matches how Chapter 6's register flow creates both records at once. It also keeps credentials clearly separated from public-facing profile data, which is a nice story for a viva.

**Q: Can I skip seed and add data manually in Compass?**  
A: You could, but it breaks the gate and, worse, it breaks Chapter 8. The seed script is required proof: two vendors, two stores, and products with grocery fields, all with deterministic identities like `vendor-a@test.local`. Manual clicking isn't reproducible — a fresh clone or a teammate can't redo it, and the isolation tests in Chapter 8 assume predictable test emails they can look up. The seed script is a repeatable source of truth for test data; your hands are not. Make the script the one way data gets in.

**Q: What's wrong with putting `vendorName` on every product?**  
A: Every copy goes stale the moment the vendor renames their shop. If Green Valley Grocer rebrands, you'd have to update every product document that carries the name, and one missed product leaves two spellings of the same store in the catalogue. Instead, store a `storeId` reference on the product and look the name up with populate when you display it — one source of truth in the stores collection. The exception is orders, where copied names are intentional receipts of what you paid at purchase time. That trap is the whole point of sub-chapter 5.2.

**Q: Do I build API routes this chapter?**  
A: No — this chapter is schemas and seed only; the routes arrive from Chapter 6 onward. Every route you'll write later depends on the shapes you define now: register needs User and Profile, vendor CRUD needs Store and Product, cart and checkout need CartItem and Order. If you add routes now you'd be building against models that don't exist yet, and you'd blur the course's step-by-step arc. The gate here is runnable proof: the seed runs and Compass shows documents — not a single HTTP endpoint.

## The gap between "connected" and "useful"

Right now MongoDB answers: *Can the server reach the database?*

It cannot answer:

- What does a vendor look like in a document?
- How does a product know which store it belongs to?
- What gets copied into an order at checkout time?

Those are **schema decisions** — the most consequential choices in a marketplace. Wrong refs break isolation in Chapter 8. Missing snapshot fields break order history in Chapter 18. Chapter 5 is where design from Chapter 3 becomes **enforceable structure**.

## Why this chapter sits after config

Chapter 4 established **one connection path** — `connectDB()` from `shared/db.js`. Chapter 5's seed script reuses that same path. If you skipped Chapter 4's gate, stop here — seed will fail or write to the wrong database.

Chapter 5 assumes:

- `docs/erd-draft.md` committed from Chapter 3
