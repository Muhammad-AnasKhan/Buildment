## Common beginner questions

**Q: Schema vs model — what's the one-line difference?**  
A: A schema is the blueprint; a model is the compiled constructor you actually query. You describe fields, types, and rules in the schema — `email: String`, `required: true` — then call `mongoose.model('User', userSchema)` once to get the model. From then on you use `User.create()`, `User.find()`, `User.findOne()` and never touch the schema again. So: schema defines the shape, model gives you the handle. Define the model once in `user.model.js` and import it elsewhere — if you recompile it in multiple files, Mongoose throws `OverwriteModelError`.

**Q: Why a unique index on email?**  
A: Because login does "find the user for this email", and if two users share an email the server can't know whose password to check. The unique index gives you both speed and correctness: email lookups are fast, and duplicate emails are impossible at the database level. You could check with `User.findOne` before registering, but two requests racing at once can both pass the check; a unique index is a hard guarantee the pre-check can't provide. It's the first index to add on User, because Chapter 6 auth depends on email being a reliable key.

**Q: Why does populate return null, and how do I fix it?**  
A: Populate returns null (or just the id) when Mongoose can't find the document your ref points to — usually a mismatched ref name or a missing document. Three things must all be true: the `ref` string matches the registered model name exactly (`'Store'`, not `'store'`), the referenced document actually exists in the database, and you called `.populate('storeId')` on the query. The most common bug is a casing or spelling mismatch, and it fails silently — no error, just a null. If you see null, check the ref string first, then confirm the document exists.

**Q: Pre-save password hash in Chapter 5 or Chapter 6?**  
A: Hashing lands in Chapter 6 — in Chapter 5 you only define the `passwordHash` field on the User schema. The model can declare it as a required String now, and the seed may write a placeholder until bcrypt exists, as long as you document it. In Chapter 6 you'll implement hashing in the auth service, used by both register and login, so the hash logic lives in exactly one place. If you put it in a Mongoose pre-save hook now, you'll rewrite it in Chapter 6 anyway — and Chapter 6.5 explains why the service layer is the better home.

**Q: Collection name `users` vs file `user.model.js`?**  
A: The file name is just a convention for humans; Mongoose derives the collection name from the model name by lowercasing and pluralizing. `mongoose.model('User', schema)` gives collection `users`, `'Store'` gives `stores`. Be aware Mongoose's pluralizer isn't perfect English — `CartItem` becomes `cartitems`, not `cart_items` or `cartItems`. Knowing the real collection names matters when you inspect seed data in Compass or run raw queries. The file name `user.model.js` is purely organisational; Mongoose never reads it.

## Concepts to extract from reading

### 1. Schema vs Model

- **Schema** — blueprint (fields, types, rules)
- **Model** — compiled constructor bound to collection name

Pattern for this course:

```
user.model.js  →  defines schema + exports mongoose.model('User', userSchema)
```

Other files `import User from './user.model.js'` — never recompile model.

### 2. ObjectId refs

```javascript
storeId: { type: Schema.Types.ObjectId, ref: 'Store', required: true }
```

Populate only works when:

- `ref` string matches registered model name exactly
- Referenced document exists
- You call `.populate('storeId')` on query

### 3. Subdocuments vs refs

| Pattern | Use when |
|---|---|
| **Ref** | Entity has own lifecycle (Product, Store) |
| **Embed subdocument array** | Snapshot lines on Order — no independent Product |

Order `orderItems[]` is embedded — not a separate collection.

### 4. Timestamps

```javascript
{ timestamps: true }
```

Adds `createdAt`, `updatedAt` — use on all top-level schemas this chapter.

### 5. Indexes

Declare in schema or ERD:

- `User.email` — unique
- `Store.userId` — unique (one store per vendor)
- `Product.storeId` — index for vendor queries
- `CartItem.userId` — index for cart fetch

Read: [Mongoose indexes](https://mongoosejs.com/docs/indexes.html)

## Common mistakes (learn now, avoid in 5.10–5.13)

| Mistake | Symptom |
|---|---|
| Model defined twice | OverwriteModelError |
| Wrong ref name | populate returns null id only |
| Forgot `required: true` | Seed saves incomplete docs silently |
| Mixed plural collection names | Mongoose defaults to lowercase plural — know your collection names in Compass |
| Schema typos in enum | ValidationError on seed |
