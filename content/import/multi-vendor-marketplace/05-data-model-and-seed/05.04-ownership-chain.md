# 5.4 — Ownership chain

> **[Learn]** · Chapter 05 — Data model & seed · *Who may change each document?*

A role tells the API what kind of user is signed in. It does not tell the API **which** shop that user owns. Two vendors have the same role, but Vendor B must not edit Vendor A's product. Your data model needs an ownership path the API can check on every private request.

<BigWordAlert term="Object ownership" plainEnglish="A link from a document back to the user who is allowed to change it." whyItMatters="A vendor token is not enough. The API must prove that this particular product belongs to the signed-in vendor." />

## Follow the ownership path

Start with the signed-in user's id, not an id supplied in the request body. A vendor owns a Store through `Store.userId`. The Store owns Products through `Product.storeId`. A customer owns CartItems through `CartItem.userId` and Orders through `Order.customerId`. A vendor can read an Order only when `Order.storeId` points to their Store.

<MermaidDiagram title="FreshMarket ownership paths" chart={`flowchart LR
  Vendor[Signed-in vendor] -->|Store.userId| Store[Store]
  Store -->|Product.storeId| Product[Product]
  Store -->|Order.storeId| Order[Vendor order view]
  Customer[Signed-in customer] -->|CartItem.userId| Cart[CartItem]
  Customer -->|Order.customerId| Order
  Cart -->|CartItem.productId| Product
  Cart -->|CartItem.storeId| Store
`} legend="Arrows name the field that connects the two documents. An Order has both a customerId and a storeId." />

Read the two paths separately. A vendor follows Vendor → Store → Product before changing a listing. A customer follows Customer → CartItem before changing a cart line. The Order has both a buyer and a fulfilling store, so each side gets a different, scoped view of the same purchase.

## Try one unsafe request

Suppose Vendor B sends `PATCH /products/PRODUCT_A_ID`, where that product belongs to Vendor A. Checking `req.user.role === 'vendor'` lets the request through: both users are vendors. The handler must also load the product and compare its `storeId` with the store owned by `req.user.id`.

```javascript
const myStore = await Store.findOne({ userId: req.user.id });
const product = await Product.findById(req.params.id);
if (!myStore || !product || !product.storeId.equals(myStore._id)) {
  return res.sendStatus(404);
}
// Only now may this vendor change the product.
```

Returning `404` for a product outside this vendor's store avoids revealing whether another vendor's id exists. The important rule is the query scope, not the exact error wording. Chapter 8 adds this check to routes and tests it with two seeded vendors.

The **one store per vendor** rule also needs a unique index on `Store.userId` and a guarded create route. Walking through Store makes ownership easy to check; the walk alone does not prevent a vendor from creating a second Store.

## Why the cart line carries three ids

A CartItem points to the customer (`userId`), the product (`productId`), and the product's store (`storeId`). The server verifies that the line's `storeId` matches the product when the item is added and again at checkout. It never trusts the store id merely because the browser sent it.

Keeping `storeId` on the cart line makes grouping at checkout simple: all lines for Store A become one Order for Store A, and lines for Store B become another. The order also stores `customerId` for the buyer's history. Each Order embeds the product name, unit, and price **as they were at purchase**, so an old receipt does not change when a vendor edits a listing.

## Name the references clearly

Use `userId` on Store, `storeId` on Product, and `customerId` on Order. These names say what each link means. In Mongoose, a `ref` string must match the registered model name exactly: `ref: 'Store'` points to `mongoose.model('Store', storeSchema)`. A different case can break population.

Index fields used to scope frequent queries, such as `Product.storeId` and `CartItem.userId`. A vendor product list starts from the vendor's Store, then queries `Product.find({ storeId: myStore._id })`. A customer cart starts from `CartItem.find({ userId: req.user.id })`. A global product or cart query followed by a UI filter is not an ownership check.

## Check your model before continuing

In `docs/erd-draft.md`, draw the two ownership paths and label each arrow with the actual field name. Then answer these questions without looking back:

1. Which two documents must the API compare before Vendor B can edit a product?
2. Why does a CartItem carry `storeId` when Product already has it?
3. Which fields let a customer and a vendor see only their own orders?

If you can answer those, the models in Chapter 5 will support the authorization checks in Chapter 8.
