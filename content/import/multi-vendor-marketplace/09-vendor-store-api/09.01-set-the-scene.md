# 9.1 — Set the scene

> **[Read]** · Chapter 09 — Vendor store API · *Verified vendor needs a shop*

**Where the project is now:** Chapters 6–8 gave you identity and isolation — vendors register, log in, and your API knows who they are. `requireAuth` returns 401 without a valid token. `requireRole('vendor')` returns 403 for customers. `assertStoreOwner` blocks cross-vendor store edits. But a verified vendor still has **no shop** in the database — only a user record with `role: vendor`.

**Where this chapter goes:** Vendors create and manage **their store** through the API — one store per vendor, owned by the authenticated user, protected by the isolation middleware from Chapter 8.

This is a **build chapter**. Every sub-chapter from 9.7 onward adds routes and service logic to your repo. The gate is **runnable proof**: a vendor can create a store, fetch it, update it, and a second vendor cannot PATCH the first vendor's store.

## Bridge from last chapter

Chapter 8 installed **server-side permission rules** — `requireRole('vendor')`, `assertStoreOwner`, and a stub `PATCH /stores/:id` that returns **403** when Vendor B attacks Vendor A's store. You proved isolation with curl; you committed `docs/AUTHORIZATION.md`. But a new vendor still has **no store document** — only a user row with `role: vendor`. Chapter 9 is the first **vendor feature** that uses those guards for real: create shop, fetch mine, update mine. Authorization before features — not the other way around.

## In plain English

| Term | Simple meaning |
|---|---|
| **Store** | A vendor's shop on the marketplace — name, address, description |
| **One store per vendor** | Each seller gets exactly one shop; duplicates rejected at create |
| **`POST /stores`** | API call that opens a new shop (once per vendor) |
| **`GET /stores/me`** | Fetch **my** shop without guessing MongoDB ids |
| **`vendorId`** | Field linking a store document to the User who owns it |
| **Service layer** | Business logic separate from HTTP routes — finds store by vendor |
| **404 on GET /stores/me** | No shop yet — Chapter 10 turns this into an onboarding redirect |

## Think of it like a market stall license

Chapter 8 made sure vendors cannot rearrange each other's stalls. Chapter 9 hands out the **license to open a stall** — one license per vendor, registered with the market office (your API). Until that license exists, the vendor is authenticated but not yet a seller. Customers will browse stalls in Week 3; vendors cannot stock shelves without a stall name on the map.

## Common beginner questions

**Q: Why API before the "Open your shop" UI in Chapter 10?**  
A: Same pattern as auth: Chapter 6 built the API and Chapter 7 built the screens on top of it. You build the contract first and prove it with curl, then the React forms call fixed shapes instead of guesses. curl takes the browser out of the picture — when a request fails, the bug is in your server code, not hidden behind a spinner or client state. If you built the UI first, you'd be debugging two layers at once while the response shape is still changing. Chapter 10 reuses the exact JSON shapes you prove here.

**Q: Can a vendor have two stores?**  
A: Not in this course. One vendor, one store — that's the marketplace's trust model, and it's enforced at `POST /stores`: if a store already exists for this vendor, the route rejects the second attempt (a 409 Conflict is a good choice). The rule can't live only in the UI, because anyone can skip your React forms and call the API directly — so the server enforces it. Allowing multiple shops per owner is a valid product decision for some marketplaces, but it complicates ownership logic everywhere, so the course deliberately keeps it simple.

**Q: Why `GET /stores/me` instead of `GET /stores/:id`?**  
A: Because "me" removes the need to know your own MongoDB `_id`. A vendor shouldn't have to open Compass, copy a 24-character id, and paste it into a URL — they should just ask for their own store. The route resolves the store from the authenticated user in the JWT (`req.user.id`), finds it by `vendorId`, and returns it. It's also safer by construction: with `:id`, a naive route risks IDOR (guess an id, read someone else's store), while "me" is scoped to the caller, so there's nothing to guess.

**Q: Why does `GET /stores/me` return 404 when a new vendor has no store?**  
A: Because 404 is the signal for "you don't have one yet" — and Chapter 10 turns that signal into the onboarding redirect. A brand-new vendor has no store document, so fetching "mine" finds nothing and returns 404 instead of inventing an empty store. That sounds like an error, but it's actually a feature: the client checks the status code, understands "this vendor still needs to open a shop", and sends them to the setup form. It's not a broken server — "no store yet" is real, meaningful information your UI can act on.

**Q: Do customers use these routes?**  
A: No. `POST /stores`, `GET /stores/me`, and `PATCH /stores/:id` are vendor-only, guarded by `requireRole('vendor')` — a customer who logged in fine still gets 403. Customers are shoppers, not sellers, so opening a shop makes no sense for them; their routes arrive in Week 3 (browsing, cart, orders). Forcing `requireRole('vendor')` on these endpoints is part of your authorization matrix: every role sees exactly the endpoints their job needs, and nothing more.

**Q: What if I skipped Chapter 8?**  
A: Stop and go back. Store routes without ownership checks are an IDOR vulnerability from day one — any vendor token could `PATCH /stores/:id` on any store someone guessed, including another vendor's. The `requireRole('vendor')` and `assertStoreOwner` guards from Chapter 8 are the whole reason these routes are safe to write. Chapter 9 assumes you already proved the 403 test: Vendor B gets 403 on Vendor A's store. If that test doesn't pass, every store route you add inherits the hole. Authorization before features — not the other way around.

## The gap between "logged in vendor" and "open shop"

Right now your marketplace can answer:

- Who is this user? (JWT + role)
- Can Vendor B edit Vendor A's stub store? (403 — Chapter 8)

It cannot answer:

- How does a new vendor **open their first shop**?
- What happens if they try to create a **second** store?
- How does the vendor fetch **their own** store without knowing the MongoDB `_id`?

Those are **store lifecycle** problems — the first real vendor-facing feature after auth.

## Why this chapter sits after authorization

Chapter 8 was deliberate: you built **role checks and ownership helpers** before writing store CRUD. Without that foundation, `PATCH /stores/:id` becomes an IDOR vulnerability on day one.

Chapter 9 assumes:

- **`docs/AUTHORIZATION.md`** committed from Chapter 8
- **`requireRole`** and **`assertStoreOwner`** exist in `shared/` or `auth/`
- **Store model** exists from Chapter 5 with `vendorId` (or equivalent owner ref)
- You tested **Vendor B → 403 on Vendor A's store** with a stub route

If Chapter 8 gate is incomplete, finish the IDOR test first — store routes inherit the same checks.

## What "vendor store API" means in product terms

A store is the vendor's **public face** on the marketplace:

| Concern | API responsibility |
|---|---|
| Shop exists | `POST /stores` — vendor creates once |
| Shop identity | Name, description, address, logo URL |
| One vendor, one shop | Enforce at create — reject duplicate |
| Vendor sees own shop | `GET /stores/me` — no ID guessing |
| Vendor updates own shop | `PATCH /stores/:id` — ownership check |

Customers will browse products **by store** in Week 3. Vendors cannot list products until a store exists — Chapter 10 enforces that in the UI; Chapter 9 builds the API.
