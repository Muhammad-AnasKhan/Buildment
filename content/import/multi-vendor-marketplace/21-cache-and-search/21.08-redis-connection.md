# 21.8 — Redis connection

> **[Build]** · Chapter 21 — Cache & search · *`server/src/shared/redis.js`*

**Why this step matters:** Catalogue caching in Chapter 21 and BullMQ in Chapter 22 share one Redis service. A clear connection boundary prevents ad-hoc clients while still allowing public browsing to fall back to MongoDB.

<BigWordAlert term="Redis" plainEnglish="In-memory data store used here for HTTP response cache — key-value with TTL support." whyItMatters="FreshMarket Redis runs alongside MongoDB — separate connection string in env." />

**Where the project is now:** Every `GET /products` hits MongoDB (Ch 14–15); no Redis dependency or connection module exists.

**After this step:** `server/src/shared/redis.js` connects to Redis from `REDIS_URL`; fails gracefully or logs warning per 21.14 strategy.

## Env contract

```
# server/.env.example
REDIS_URL=redis://127.0.0.1:6379
```

Add to `config.js` validation — **optional** for dev if fallback required, or **required** if you want fail-fast. Course gate requires **fallback when down** (21.14) — optional URL with `getRedisClient()` returning null is valid pattern.

Choose the contract deliberately. MongoDB is required because it owns product data; Redis is optional for this read path because it only accelerates it. Missing configuration, refused connections, and runtime disconnects should all lead cache helpers to the same safe state: unavailable.

## redis.js exports — spec

| Export | Purpose |
|---|---|
| `connectRedis()` | Call on boot after MongoDB or parallel |
| `getRedisClient()` | Returns client or null if unavailable |
| `disconnectRedis()` | Graceful shutdown optional |

Use `node-redis` v4+ or `ioredis` — document package in README.

## Connection lifecycle

Create one client, attach its error listener before connecting, and attempt the connection during boot. Do not create a new client for every request. Your module should distinguish **ready** from merely **created** so catalogue code never sends commands through a disconnected client.

Use a bounded connection/retry strategy. If Redis cannot connect promptly, log one useful warning and let the API become ready with caching disabled. When the client reconnects, later requests may use it again without restarting the API.

## Commit

```bash
git add server/src/shared/redis.js server/.env.example server/package.json
git commit -m "feat(server): add redis connection module"
```

## ✅ Do / ❌ Don't

**✅ Do:** Update `.env.example` — not real credentials.

**✅ Do:** Single client instance — connection pool.

**❌ Don't:** Put Redis password in client `.env`.

## Verify

- [ ] Redis up → one client becomes ready and `PING` returns `PONG`
- [ ] Wrong URL → API still boots after a bounded wait and logs a warning
- [ ] Redis returns → the existing lifecycle can recover or reconnect predictably
- [ ] No secret appears in client env files or logs
