# 21.10 — Measure before/after

> **[Build]** · Chapter 21 — Cache & search · *Log response times; note in README*

**Why this step matters:** Interviewers ask "did caching help?" — honest before/after numbers in README turn a tutorial exercise into evidence. Even modest gains on a small seed prove you measured, not guessed.

<BigWordAlert term="Cache benchmark" plainEnglish="Measuring response time with cache cold vs warm — proves optimization worth complexity." whyItMatters="FreshMarket gate includes before/after ms — data beats guessing cache helped." />

**Where the project is now:** Cache middleware serves catalogue HITs (21.9) — no measured numbers prove it helps.

**After this step:** README documents **response time** for catalogue GET — cold vs cache HIT.

## Measurement contract

Use the same URL, seed data, machine, and server process as the baseline in 21.7. Confirm the first request logs a miss and the next requests log hits; otherwise you are not comparing the paths you claim to compare.

Run at least five warm hits and report the median or all samples. Local datasets are small, so the latency difference may be modest. The more important proof is that hit requests avoid MongoDB work while returning identical data.

## ✅ Do / ❌ Don't

**✅ Do:** Record methodology — same machine, same dataset.

**✅ Do:** Compare response bodies or a stable checksum before comparing speed.

**❌ Don't:** Fake numbers.

**❌ Don't:** `FLUSHALL` in production docs as test step.
