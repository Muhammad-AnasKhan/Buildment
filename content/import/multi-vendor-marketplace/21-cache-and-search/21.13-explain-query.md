# 21.13 — Explain query

> **[Build]** · Chapter 21 — Cache & search · *`explain()` — index scan not collection scan*

**Why this step matters:** "We added search" is weak in a viva — `explain()` proof that MongoDB uses your index, not a full collection scan, shows you verified performance instead of assuming.

<BigWordAlert term="explain()" plainEnglish="MongoDB command showing whether query used index or collection scan — performance X-ray." whyItMatters="FreshMarket search slow? explain() reveals missing index before throwing hardware at it." />

**Where the project is now:** Text index is created and `?search=` uses `$text` (21.12) — no proof the index is actually used.

**After this step:** You have proof that search uses **text index** — not collection scan.

## Run explain

Run the database query directly in a script, mongosh, or a temporary local-only diagnostic. Do not call the cached HTTP URL: a cache hit bypasses MongoDB and therefore proves nothing about the query plan.

```javascript
const explain = await Product.find(
  { $text: { $search: 'rice' } },
  { score: { $meta: 'textScore' } }
).explain('executionStats')
```

Inspect `executionStats.executionStages` or `queryPlanner.winningPlan`.

## Pass criteria

| Result | Gate |
|---|---|
| `TEXT` stage or named text-index plan | ✓ Pass |
| `COLLSCAN` on large collection | ✗ Fix index |

MongoDB plan shapes vary by version, so do not search only for a literal top-level `IXSCAN`. Confirm the winning plan references the text index, then inspect `totalDocsExamined`, `totalKeysExamined`, `nReturned`, and execution time. A tiny seed may make every plan look fast; the plan and examined counts are the durable evidence.
