## Bridge from last chapter

You closed **Week 3** in Chapter 20 — full commerce in the browser: browse → cart → checkout → split confirmation → customer history → vendor inbox → status updates. The product **works**. Week 4 asks: *will it survive real traffic and feel fast?*

| Week 3 (feature-complete) | Week 4 (polish & ship) |
|---|---|
| Every shop page load queries MongoDB | Repeat visits served from **cache** |
| Search may scan every product | Search uses a **text index** |
| Checkout returns immediately | Notifications move to **background jobs** (Ch 22) |
| `localhost` only | **HTTPS** on the internet (Ch 23) |

Chapter 21 is the **performance layer** — not new features customers notice, but the difference between a demo that works for you and one that stays fast when fifty people browse dairy at once.

**Do not open this chapter until Chapter 20 gate is ticked.** Cache on a broken checkout flow hides nothing useful.

## The two promises you must keep

Performance work is only successful if it preserves the behaviour customers already rely on. By the gate, FreshMarket must keep two promises at the same time:

1. **Repeat catalogue reads do less work.** An identical public request can reuse a cached response instead of querying MongoDB again.
2. **The response remains truthful.** Product writes remove affected cached responses, search uses a real index, and a Redis outage makes browsing slower rather than unavailable.

That second promise is the harder one. A fast response with yesterday's price is not an optimization; it is a correctness bug.

## In plain English

| Term | Simple meaning |
|---|---|
| **Redis** | A very fast in-memory database that sits beside MongoDB — like a sticky note the server checks before opening the filing cabinet |
| **Cache** | A saved copy of a recent answer — so the server does not repeat the same expensive work |
| **Cache hit** | The answer was already on the sticky note — instant return |
| **Cache miss** | Sticky note empty — server fetches from MongoDB, then saves a copy for next time |
| **TTL (time to live)** | How long a cached answer stays valid before it expires automatically — e.g. 5 minutes |
| **Cache invalidation** | Deliberately throwing away stale sticky notes when data changes — e.g. vendor updates a price |
| **Text index** | MongoDB's built-in search index — finds products by words in name and category without scanning every row |
| **Fallback** | When Redis is down, the app still works — just slower — by reading MongoDB directly |

## Think of it like a shop window display

The **catalogue** (`GET /products`) is your shop window — the most looked-at part of the store. Every customer who opens `/shop` asks the same question: *"What products are on page 1?"*

Without cache, your server walks to the warehouse (MongoDB) for **every single glance** — even when nothing changed since the last customer.

With cache, the first customer triggers a warehouse trip; the next hundred read from a **photograph of the window display** (Redis) until a vendor rearranges the shelf (product write) or the photograph expires (TTL).

**Important:** You cache the **shop window**, not the **checkout desk**. Cart, orders, and auth stay fresh every time — they are personal and change constantly.

## The hot path

```
Customer opens /shop
  → GET /products?page=1&category=Dairy
  → MongoDB query + populate store
  → repeat for every user, every page load
```

Catalogue is read-heavy. Chapter 21 adds a cache layer — not for cart or orders.

## Keep the source of truth explicit

MongoDB remains authoritative. Redis may hold a serialized copy of a public response, but it never decides a price, owns stock, or replaces a product write. Chapter 22 will reuse the same Redis service for queues, so catalogue keys must be namespaced and cache cleanup must never erase the whole Redis database.

<Callout type="warning">
Do not cache carts, checkout, orders, authentication, or health responses in this module. They are personal, write-sensitive, or expected to report live state.
</Callout>
