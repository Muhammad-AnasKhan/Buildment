# 21.2 — Stale cache trap

> **[Read]** · Chapter 21 — Cache & search · *Update price → old cache serves wrong data*

Vendor changes milk price from ₹65 to ₹70. Customer still sees ₹65 for an hour because catalogue response was **cached without invalidation**. Trust erodes faster than slow pages.

<BigWordAlert term="Stale cache trap" plainEnglish="Serving outdated product price or stock from cache after vendor updated the real record." whyItMatters="FreshMarket shoppers seeing wrong price destroys trust — invalidation strategy matters." />

This sub-chapter names the trap **before** you wire Redis in 21.8–21.11. Speed without correctness is worse than no cache at all.

## The bug

The trap has three steps, and none of them looks wrong in isolation. The cache returns fast data, the write succeeds, and only then does the mismatch appear — on the *next* read. Tracing it later is hard because the stale copy lives outside your database.

| Step | Problem |
|---|---|
| Cache `GET /products` 60 min TTL | Fast reads |
| Vendor PATCHes price | MongoDB updated |
| Customer GET | **Stale JSON from Redis** |

TTL alone eventually fixes — **eventually** is not acceptable for price.

## Why beginners fall into this trap

Caching feels like a win the first time you see `CACHE HIT` in logs. It is easy to ship TTL and forget **writes**. The bug only appears when a vendor edits a product — often days later, blamed on "the cache being weird."

**Rule:** Every cache needs an **invalidation story** for every write path that affects cached data.

## Fix — two mechanisms (both in this chapter)

The fix is not one mechanism but two, playing different roles. TTL is your safety net — it guarantees a wrong answer eventually goes away even if you forget a write path. Event invalidation is your correctness — it makes the wrong answer disappear the moment the data changes. Production caches need both; beginners ship one and call it done.

| Mechanism | When |
|---|---|
| **TTL** | Safety net — e.g. 5–15 min — catches missed invalidation bugs |
| **Event invalidation** | On product POST/PATCH/DELETE — delete matching cache keys immediately |

Chapter 21 implements **both in sequence** (21.4).

```
On GET:  try cache → on miss, query DB → set with TTL
On POST/PATCH/DELETE product:  delete cache keys for catalogue
```

## What to invalidate

Invalidation is per *write path*, not per cache. List every way a product can change in your API and make sure each one busts the catalogue cache — the DELETE case is the easiest to forget, because the product vanishes from the DB but lingers in Redis.

Minimum: bust catalogue cache keys when **any** product write affects public list:

- Create product
- Update price, stock, publish status
- Delete product

One write can affect many cached responses. A price may appear on page 1, in a category filter, and in search results, so deleting only one key is insufficient. Use one catalogue namespace such as `catalogue:*` and invalidate every variant after a successful public product mutation.

## Order the write and invalidation correctly

Invalidate **after MongoDB confirms the write**. Deleting first creates a race: a customer can miss the cache, read the old MongoDB value while the write is pending, and put that old value straight back into Redis.

The safe baseline is:

```text
validate ownership and input
  → commit product write in MongoDB
  → invalidate catalogue keys
  → return success
```

If invalidation fails, the database write is still real. Log the failure with enough context to investigate, let TTL bound the stale window, and document whether your service fails the request or returns success with an operational warning. Do not silently hide the inconsistency.

## What not to cache

Not everything belongs in a shared cache. The rule of thumb: cache **shared, slow, read-only** data — never user-specific responses and never writes. Caching a cart would return one customer's cart to another if the key logic is off.

| Route | Why |
|---|---|
| POST /checkout | Write — never cache |
| GET /cart | User-specific |
| GET /orders/my | User-specific |
| GET /health | Cheap; db status must be live |

## In plain English

| Term | Simple meaning |
|---|---|
| **Stale cache** | Cached answer is **out of date** — still fast, but wrong |
| **Invalidation** | Throwing away cached copies when the real data changed |
| **TTL** | Automatic expiry — "this sticky note is valid for 5 minutes" |

## Think of it like a sale sign in the window

You put a "Milk ₹65" sign in the window (cache). Vendor changes the shelf price to ₹70 (MongoDB update). If you do not replace the sign (invalidation), customers see the wrong price until the sign falls off by itself (TTL expiry).

## Prove freshness, do not infer it

Warm a catalogue key, change a visible field through the real vendor endpoint, and request the exact same catalogue URL again. The first read after the write must be a miss containing the new value; the following read should be a hit containing that same value. This proves the write path, prefix cleanup, and refill path work together.

## ✅ Do / ❌ Don't

**✅ Do:** Invalidate on write paths in products module.

**✅ Do:** Log cache HIT/MISS in dev.

**❌ Don't:** Cache per-user catalogue without varying key by auth — public only.

**❌ Don't:** Forget invalidation because TTL exists.
