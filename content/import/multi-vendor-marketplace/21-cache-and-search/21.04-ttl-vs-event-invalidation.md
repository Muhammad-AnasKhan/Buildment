# 21.4 — TTL vs event invalidation

> **[Learn]** · Chapter 21 — Cache & search · *Both; implement both in sequence*

Production caches use **both**. TTL is a safety net; invalidation is correctness on writes.

<BigWordAlert term="TTL vs event invalidation" plainEnglish="TTL expires cache after fixed time; event invalidation clears cache when data changes." whyItMatters="FreshMarket uses both — TTL safety net plus bust on vendor product save." />

Beginners often pick one and wonder why production still breaks. This sub-chapter gives you the **decision frame** before you implement in 21.9 and 21.11.

## TTL only

An expiry time is easy to set, but a cached product can stay stale until the clock runs out. That is acceptable for rarely changing data. It is a poor rule by itself for a catalogue where vendors edit prices and availability.

**Example failure:** TTL = 15 minutes. Vendor fixes a typo price at 10:00. Customers see wrong price until 10:15.

## Event invalidation only

Deleting affected cache keys after a product write makes the next read fresh. But every write path must remember to do it. If a `DELETE` route forgets, the old entry can stay until something else removes it.

**Example failure:** You invalidate on `PATCH` but forget `DELETE` — deleted products appear in cache until manual flush.

## Both (course mandate)

```
On GET:  try cache → on miss, query DB → set with TTL
On POST/PATCH/DELETE product:  delete cache keys for catalogue
```

<MermaidDiagram title="Catalogue cache read and product update" chart={`flowchart LR

Event invalidation is the normal freshness path: delete keys when a vendor changes a product. TTL is the backup: even a missed key eventually expires. Neither rule replaces the other.

TTL catches bugs in invalidation — keys expire eventually. Invalidation catches user-visible errors — prices fix now.

## Key design

Document pattern in README:

```
catalogue:{hash(sortedQueryParams)}
```

Or single key `catalogue:all` if only unfiltered list cached — **prefer per-query** if filters exist from Ch 14.

Different `page`, `category`, and `search` params → different keys → invalidation must clear **all catalogue keys** (prefix delete), not one key.

Canonicalize parameters before building the key. `?page=1&category=Dairy` and `?category=Dairy&page=1` describe the same request and should not create two entries. Normalize defaults too: decide whether an omitted `page` and `page=1` share a key, then apply that rule consistently.

## Invalidation call sites

`products.service.js` — after successful:

- `createProduct`
- `updateProduct`
- `deleteProduct`

Call `invalidateCatalogueCache()` — not scattered in routes. One function, one place to audit.

## In plain English

| Term | Simple meaning |
|---|---|
| **TTL** | "Throw this cached answer away after N seconds" — automatic |
| **Event invalidation** | "Throw cached answers away **when something specific happens**" — e.g. vendor saves product |
| **Prefix delete** | Delete all keys starting with `catalogue:` — clears every cached page/filter variant |

## Think of it like milk expiry dates

The two invalidation strategies map onto a shelf-life decision you already make in real life:

**TTL** = printed expiry date on the carton — good enough if nobody changes the recipe.

**Event invalidation** = pulling all cartons from the shelf the moment the recipe changes.

**Both** = pull immediately on recipe change *and* expiry date as backup for any cartons you missed.

## Failure cases to reason about

This module deliberately invalidates the whole catalogue namespace. That trades some cache efficiency for a correctness story you can audit. Selective invalidation can come later, when you can reliably identify every page, filter, and search containing the changed product.

Watch for these failures:

- the MongoDB write succeeds but invalidation throws;
- invalidation runs before the write and a concurrent miss repopulates old data;
- a query parameter is omitted from the key and different responses collide;
- cleanup uses `FLUSHALL` and destroys Chapter 22 queue data;
- a prefix scan deletes only its first batch and leaves more keys behind.

Choose a TTL between 300 and 900 seconds and document why. TTL limits damage; event invalidation provides freshness.

## ✅ Do / ❌ Don't

**✅ Do:** Implement TTL in 21.9, invalidation in 21.11 — sequence matters for testing.

**✅ Do:** Use Redis `DEL` or `SCAN`+`DEL` for pattern — avoid `KEYS` in production docs note.

**❌ Don't:** Invalidate entire Redis DB — `FLUSHALL` nukes unrelated keys.

**❌ Don't:** Assume one cache key — filters and pagination multiply keys.
