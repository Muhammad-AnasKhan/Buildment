# 13.14 — Bridge to Week 3 (customer experience)

> **[Bridge]** · Chapter 13 — Product photos · *Role switch: vendor → customer; plain English; self-check before Week 3*

You finished **Week 2 — vendor experience**. Take a breath. This sub-chapter exists because the shift to Week 3 is the biggest **role change** in the course — not because Week 3 is harder, but because you stop thinking like a shop owner and start thinking like a shopper.

<BigWordAlert term="Customer experience pivot" plainEnglish="Transition from vendor-side build to shopper-side browse, cart, and checkout." whyItMatters="FreshMarket Week 3 assumes vendor catalogue exists — you now build what customers see." />

## What you just finished (Week 2 recap)

As a **vendor**, you built:

- Login and registration (Ch 6–7)  
- Proof that vendors cannot touch each other's data (Ch 8)  
- Opening a shop in the browser (Ch 9–10)  
- Adding products with grocery fields and photos (Ch 11–13)  

**Week 2 demo:** A vendor can log in, open a shop, add a product with a photo, and see it in their dashboard.

If that demo is not true in your browser yet, **do not start Chapter 14**. Week 3 builds on seeded products in MongoDB that vendors created — empty shops make Week 3 feel broken when the problem is Week 2.

## What changes in Week 3

| Week 2 mindset | Week 3 mindset |
|---|---|
| "I am the seller" | "I am the buyer" |
| Routes like `/vendor/products` | Routes like `/products` (public catalogue) |
| Forms that **create** data | Pages that **browse** and **buy** |
| One store at a time | **Many stores** in one cart |
| curl with vendor token | curl + browser as **customer** |

You are **not** throwing away vendor work. Customers will browse the **same products** vendors published — new API routes sit **beside** vendor routes, not instead of them.

## In plain English

| Term | Simple meaning |
|---|---|
| **Public catalogue** | The shop window — products any customer can see without being a vendor |
| **Vendor-scoped route** | API that only shows **your** inventory when **you** are logged in as vendor |
| **Customer** | User with role `customer` — buys from many vendors |
| **Multi-vendor cart** | One shopping cart with items from Shop A and Shop B — checkout splits into two orders later |

## Think of it like a real market hall

Week 2 you built **stalls** (stores) and **shelves** (products). Week 3 you build the **aisles** where shoppers walk, pick items from different stalls, and pay once at the end — the system splits money and orders per stall behind the scenes (Chapter 18).

## Common beginner questions

**Q: Do I delete the vendor pages?**  
A: No — delete nothing. The vendor dashboard stays exactly as it is: vendors still manage their stall at `/vendor/products`, create products, and upload photos. Week 3 is additive — you build customer-facing pages like `/shop` and `/cart` that sit beside the vendor UI in the same codebase. Both sides read the same MongoDB collection, just through different routes. Throwing away the vendor work would also break your seed data pipeline, and customers need those published products to browse in the first place.

**Q: Why another chapter before the shop UI?**  
A: Same rhythm the course has followed all along: API first, UI second — Chapters 6→7, 11→12, and now 14→15. Chapter 14 builds `GET /products` so the Chapter 15 React grid has real, paginated data from the server instead of hardcoded arrays you throw away. If you built the shop screen first, you'd invent a fake data shape and then rework the whole page once the real API arrived. A stable contract first turns the UI step into mostly wiring.

**Q: Do customers need to log in to browse?**  
A: Not necessarily. The course's public catalogue allows browsing without a JWT — anyone can look in the shop window. Login becomes necessary once a customer wants to *do* something persistent: adding to a cart (Chapters 16–17) and checking out (Chapter 18) require a logged-in customer account. So plan for two gates: reading publicly, and acting as a customer. Chapter 14's spec defines the public read; the cart chapters add the auth requirement.

**Q: Why will my one cart split into two orders?**  
A: Because a marketplace has one customer but many vendors. You drop tomatoes from Green Valley and bread from Harbor Market into a single basket and pay once — but behind the scenes each stall is a separate business that needs its own order and its own money. At checkout, the system groups your cart lines by `storeId` and creates one order per vendor (Chapter 18). Your cart page will even show those vendor sections, so the split never surprises the shopper.

**Q: Do customers create products too?**  
A: No — customers browse and buy; they never create products. Products are written by vendors through their dashboard, and customers see only the published, in-stock ones through the public catalogue. That's the marketplace pattern: one collection of product documents, two very different doors — a write door for vendors, a read door for customers. It's also a neat interview line: two routes, one MongoDB collection.

## Week 3 roadmap — where you are in the story

Week 3 is **customer commerce**: browse → cart → checkout → track orders. You already built the vendor side; now shoppers use the same product data.

| Chapter | You build | Customer can… |
|---|---|---|
| **14** (next) | Public catalogue API | — (curl only) |

| **16–17** | Cart API + UI | Add items from different stores to one basket |
| **18–19** | Checkout + payment | Pay once; orders split per vendor |
