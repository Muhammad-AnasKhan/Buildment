# 24.04 — Reserve vs decrement

> **[Learn]** · Chapter 24 — Inventory reservations · *Two different moments*

Inventory math fails when teams pick **one** moment to subtract stock. FreshMarket uses **two** moments on purpose.

## Two clocks

| Moment | Action | Updates `stockQty`? | Updates ATP? |
|---|---|---|---|
| Customer clicks **Pay** / checkout starts | Create `active` reservations | No | Yes (lower) |
| Stripe webhook **payment succeeded** | Confirm reservations | Yes (decrement) | Already reflected |
| TTL or cancel | Release reservations | No | Yes (restore) |

Decrementing `stockQty` at checkout **start** would strand inventory when payments fail. Decrementing only at **display** time would still oversell under concurrency.

## ATP formula (this course)

For a product `P`:

```
availableQty = max(0, P.stockQty - P.reservedQty)
```

After payment confirm for quantity `q`:

```
P.stockQty -= q
P.reservedQty -= q
```

Confirmed rows are terminal audit records. Their quantity has left both on-hand stock and the
active reservation counter.

## MongoDB pattern: conditional reserve

Reserve must use a **guarded write**, not “read ATP, then insert a reservation.” FreshMarket keeps
`reservedQty` on Product and claims units atomically:

```javascript
const claimed = await Product.findOneAndUpdate(
  {
    _id: productId,
    $expr: {
      $gte: [
        { $subtract: ['$stockQty', { $ifNull: ['$reservedQty', 0] }] },
        requestedQty,
      ],
    },
  },
  { $inc: { reservedQty: requestedQty } },
  { new: true, session }
);
```

If `claimed` is null, return 409 `INSUFFICIENT_STOCK`. In the same MongoDB transaction, insert the
`active` StockReservation. The Product write creates contention on one document, so two customers
cannot both claim the last unit. An aggregation followed by an insert does not provide that guarantee.

## Idempotent confirm

Webhooks retry. Confirm handler:

```
find reservation by checkoutId + productId
inside one transaction, update status = active → confirmed
if no active row, check whether it is already confirmed → return success
else decrement both stockQty and reservedQty with $gte guards
```

Reservation confirmation and both counter decrements belong in one transaction. If the guarded
Product update fails, abort the transaction, return a webhook error so Stripe retries, and alert
operations. Never persist `confirmed` while leaving the counters unchanged.

## Vendor dashboard copy

Show three numbers:

- **On shelf** — `stockQty`
- **Held at checkout** — `reservedQty`
- **Available online** — ATP

Vendors understand “held at checkout” better than “reserved documents in MongoDB.”
