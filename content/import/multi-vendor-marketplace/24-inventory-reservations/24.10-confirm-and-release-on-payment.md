# 24.10 — Confirm and release on payment

> **[Build]** · Chapter 24 — Inventory reservations · *Money and atoms align*

Payment success is the only place `stockQty` drops. Abandonment and explicit cancel **release** holds without touching on-hand count.

## Step 1 — confirmReservations

Add `server/modules/inventory/confirm.js`:

```javascript
export async function confirmReservationsForPaymentIntent(paymentIntentId) {
  const paymentIntent = await stripe.paymentIntents.retrieve(paymentIntentId);
  const checkoutId = paymentIntent.metadata.checkoutId;
  const reservations = await StockReservation.find({ checkoutId });

  for (const r of reservations) {
    await withTransaction(async (session) => {
      const transitioned = await StockReservation.findOneAndUpdate(
        { _id: r._id, status: 'active' },
        { $set: { status: 'confirmed', confirmedAt: new Date(), paymentIntentId } },
        { new: true, session }
      );
      if (!transitioned) return; // already confirmed/released — inspect and log released case

      const product = await Product.findOneAndUpdate(
        {
          _id: r.productId,
          stockQty: { $gte: r.quantity },
          reservedQty: { $gte: r.quantity },
        },
        { $inc: { stockQty: -r.quantity, reservedQty: -r.quantity } },
        { new: true, session }
      );
      if (!product) throw new Error('INVENTORY_CONFIRM_INVARIANT_FAILED');
    });
  }
}
```

`withTransaction` is pseudocode for your existing Mongoose session helper. The important guarantee is
that reservation status and both Product counters commit together. Do not mark the reservation
confirmed first and merely log a failed stock decrement; that records a state the business cannot
explain.

Call this from your existing `payment_intent.succeeded` handler before publishing downstream
“order paid” jobs. If confirmation throws, return a non-2xx webhook response so Stripe retries and
alert operations with the checkout id.

## Step 2 — Attach paymentIntentId to reservations

When Stripe returns the PaymentIntent id at checkout, update reservations:

```javascript
await StockReservation.updateMany(
  { checkoutId, status: 'active' },
  { $set: { paymentIntentId: pi.id } }
);
```

## Step 3 — releaseForCheckout

```javascript
export async function releaseForCheckout(checkoutId) {
  const active = await StockReservation.find({ checkoutId, status: 'active' });
  for (const reservation of active) {
    await releaseReservation(reservation._id);
  }
}
```

`releaseReservation` uses a transaction: conditionally change `active → released`, then decrement
Product `reservedQty` by the same quantity. If the status transition loses to confirmation, it does
nothing. Invoke it from checkout cancel or `payment_intent.canceled`; clearing an ordinary cart
should release only the checkout attempt tied to that cart, not unrelated holds.

## Step 4 — Webhook idempotency

If your webhook handler already stores processed event ids, keep that — confirm function must tolerate duplicate calls.

## Verify

- Pay once — reservation `confirmed`; both `stockQty` and `reservedQty` decrease by line quantity.
- Replay webhook payload (Stripe CLI) — no second counter change.
- Cancel before pay — reservation `released`, `reservedQty` decreases, `stockQty` stays unchanged.
- Race cancel against webhook confirm — exactly one terminal transition wins and no counter goes negative.
