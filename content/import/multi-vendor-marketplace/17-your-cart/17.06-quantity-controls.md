# 17.6 — Quantity controls

> **[Build]** · Chapter 17 — Your cart · *PATCH on change*

In 17.5 your cart page **shows** quantities. This lesson makes them **editable**. The pattern you learn here — change something on the server, then refresh what you display — is used again in checkout and order tracking.

<BigWordAlert term="Quantity stepper" plainEnglish="Plus/minus controls that update item count and re-fetch or optimistically update the cart." whyItMatters="Cart UX lives or dies on responsive quantity changes and clear remove actions." />

## The one rule to remember

**Never change the quantity in React alone.** Always:

1. User clicks + or −
2. Call `PATCH /cart/:itemId` with the new quantity
3. On success → refetch `GET /cart` and re-render

If you skip step 3, the screen can show "5 kg" while the database still has "2 kg" — that breaks trust in your demo.

## Where the project is now → after this step

| Now | After 17.6 |
|---|---|
| Quantities are static numbers | + and − buttons update the server |
| Subtotals only change on full page reload | Subtotals refresh after each PATCH |

---

## Step 1 — Add buttons to `CartItemRow`

Each row gets:

| Control | What it does |
|---|---|
| **+** button | Increase quantity by 1 |
| **−** button | Decrease quantity by 1 |

Disable both buttons while a PATCH request is in flight — prevents double-clicks sending two requests.

---

## Step 2 — Wire the PATCH call

```
PATCH /api/cart/:itemId
Authorization: Bearer <token>
Body: { "quantity": <positive integer> }
```

**Important:** `:itemId` is the cart line's `_id` from `GET /cart` — **not** the product id.

Add a helper if needed:

```
updateCartItem(itemId, quantity) → PATCH /cart/:itemId
```

---

## Step 3 — Handle the − button at quantity 1

When quantity is 1 and the user clicks −, you have two acceptable choices:

| Choice | Behaviour |
|---|---|
| **A (recommended)** | Call `DELETE` instead — covered fully in 17.7 |
| **B** | Disable − at quantity 1 — user must click Remove |

Pick one and write it in your README. Do not send `quantity: 0` if your Chapter 16 API rejects it.

---

## Step 4 — Refetch and recalculate

After a successful PATCH:

1. Call `GET /cart` again (or use the PATCH response if it returns the full cart — match your Ch 16 shape)
2. Re-run your grouping logic from 17.5
3. Store subtotals and grand total **must** update — no stale numbers

---

## Step 5 — Show errors from the API

| Status | Meaning | What the user should see |
|---|---|---|
| 400 | Invalid quantity or over stock | Short message near the row — use API text if provided |
| 404 | Line was already removed | Refetch cart — row may be gone |
| 401 | Session expired | Redirect to login |

If the user tries to add more than `stockQty`, the server should reject it — show that message, do not silently fail.

---

## Optional: optimistic UI

You **may** update the number instantly and roll back if PATCH fails. That feels snappier but is harder to debug. For the gate, **refetch after success** is enough and is easier to explain in your learning log.

---

## Common mistakes

| Mistake | Symptom | Fix |
|---|---|---|
| PATCH with `productId` | 404 every time | Use cart line `_id` |
| Update React state only | Reload shows old quantity | Always PATCH then refetch |
| Allow quantity 0 via PATCH | 400 error | DELETE instead (17.7) |
| Forget subtotals | Totals wrong after + click | Recalculate after refetch |
