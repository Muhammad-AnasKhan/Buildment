## In plain English

| Term | Meaning |
|---|---|
| **Environment variable** | A key-value setting outside your code — e.g. `MONGODB_URI` in `.env` |
| **`.env` file** | Local file holding secrets and config — never committed to Git |
| **`.env.example`** | A committed template listing variable **names** with fake placeholders |
| **Config module** | One file (`shared/config.js`) that reads and validates all env vars |
| **Boot order** | The sequence on startup: load config → connect DB → start listening |
| **Fail-fast** | Crash immediately with a clear error if required config is missing |
| **Mongoose** | Node library that connects to MongoDB — models come in Chapter 5 |
| **Connection string (URI)** | The address and credentials MongoDB expects — treat as a secret |

## Common beginner questions

**Q: Why config before schemas — isn't the data model the point?**  
A: There's a practical reason: Mongoose models need a live connection to do anything, so wiring the connection first means you debug one problem at a time. Think of it as running the power cable before installing the refrigerators — you prove the infrastructure before you stock it with models. There's also a habit reason: teams set up secret-handling discipline before real customer data exists. A leaked connection string in Git is painful; learning `.env` discipline on an empty database is cheap. When Chapter 5 adds schemas, they'll connect to a database that already works, so "why won't this save?" is never also "why won't this connect?"

**Q: Local MongoDB or Atlas — which should I pick?**  
A: Either one satisfies the course gate, so pick based on your machine and workflow. Local MongoDB suits you if you want offline work, no cloud signup, and fast iteration — Compass and your URI both point at `127.0.0.1`. Atlas suits you if local installs are painful on your machine, you develop on multiple computers, or you want setup that mirrors most deployment guides. Sub-chapter 4.5 has the full comparison. The one rule that matters: pick one and stick with it through Week 1, because switching mid-course means re-verifying your connection string and re-running every health check.

**Q: Will the React app talk to MongoDB directly?**  
A: Never. Your browser runs JavaScript that anyone can read, so it can't be trusted with database credentials. Instead, the client sends HTTP requests to Express, and Express — running on your server where secrets live — talks to MongoDB using `MONGODB_URI`. A customer's browser asks Express for products; Express asks the database and sends the JSON back. That one-way chain keeps the connection string out of browser code, which is exactly the rule from Chapter 2: anything that must not appear in browser JavaScript stays on the server.

**Q: What if the server starts but MongoDB is down?**  
A: Then your server should not pretend everything is fine — that's the whole point of the health check this chapter builds. If Express comes up while the database is unreachable, you design for honest behavior: either crash at boot (fail-fast) or keep serving but report `db: disconnected` on `/health` so you can see the problem. Picture a market hall with the lights on but the refrigerators dead — shoppers would assume the produce is cold. Your health endpoint is the sign that tells the truth about the database, not just "the Node process is alive."

**Q: Do I need to re-debate SQL vs MongoDB here?**  
A: No — Chapter 3 closed that decision, and reopening it now wastes a day. What matters here is that your ERD is committed and your collections are named, because this chapter connects the wire and Chapter 5 writes models against that blueprint. You *can* connect MongoDB without a design, but you'd be building schemas with no map, and rework at checkout time is exactly what the blueprint is meant to prevent. If your Chapter 3 gate isn't finished, finish the draft first — then the build steps in this chapter make sense.

## The gap between "runs" and "remembers"

Right now your marketplace can answer one question: *Is the Node process alive?*

It cannot answer:

- Is MongoDB reachable from this server?
- What connection string does this environment use?
- Should the API start if the database is down?

Those are **configuration and boot-order** problems — not schema problems. Chapter 5 writes Mongoose models; **Chapter 4 connects the wire**. Order matters: connect → then implement schemas → then seed.

## Why this chapter sits after "Why MongoDB"

Chapter 3 was deliberate: you decided **document model + collections** before installing drivers. Jumping straight to `mongoose.connect()` without that design produces copy-paste schemas that break at checkout.

Chapter 4 assumes:

- You committed **`docs/erd-draft.md`**
- You know **User, Store, Product, CartItem, Order** are coming in Chapter 5
- You are **not** re-debating SQL vs MongoDB here

If Chapter 3 gate is incomplete, finish the ERD draft first — you can still connect MongoDB, but you'll implement models without a blueprint.

## What "config & database" means in production terms

Professional Node APIs treat configuration as **inputs to the process**, not constants in source code:

| Concern | Where it lives | Why |
|---|---|---|
| MongoDB connection string | `server/.env` → read by `shared/config.js` | Different per machine (local, staging, production) |
| API port | `server/.env` or host default | Deploy platforms set `PORT` dynamically |
| Client API base URL | `client/.env` as `VITE_API_URL` | Already started in Chapter 2 |
| Secrets | Never in Git | `.gitignore` + `.env.example` without values |

**Fail-fast:** If `MONGODB_URI` is missing or invalid, the server should **not** silently run pretending everything is fine. Chapter 4 teaches that discipline before you have user data to lose.
