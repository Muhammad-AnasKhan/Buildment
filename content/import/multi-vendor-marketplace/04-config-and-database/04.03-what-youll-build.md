# 4.3 — What you'll build in this chapter

> **[Read]** · Chapter 04 — Config & database · *The blueprint for connecting your app to MongoDB*

## What you'll build

By the end of Chapter 4, your marketplace API will:

1. **Connect to MongoDB on startup** — no more fake health responses
2. **Read configuration from environment variables** with validation (fail fast if something's missing)
3. **Report database status** on the `/health` endpoint
4. **Show database status** on your React Home page

**Not in this chapter:** Mongoose models, seed script, auth, new routes beyond health changes.

## Boot order: connect before you serve

Professional APIs connect dependencies **before** accepting traffic:

```
1. Load config
   ↓ (validate env — fail if MONGODB_URI missing)
2. Connect to MongoDB
   ↓ (await mongoose connection)
3. Start HTTP server
   ↓ (app.listen)
4. On shutdown signal
   ↓ (disconnect MongoDB gracefully)
```

<Callout type="warning" title="Why this order matters">
If you `listen` first, health checks may report `status: ok` while DB is down — lying to load balancers. Config validation must run *before* the connect attempt so errors are clear.
</Callout>

## Environment variables you'll need

| Variable | Required | Example |
|---|---|---|
| `MONGODB_URI` | yes | `mongodb://127.0.0.1:27017/your-app-db` |
| `PORT` | no (default 5000) | `5000` |
| `NODE_ENV` | no | `development` |

## Health endpoint contract

**Before Chapter 4:**
```json
{ "status": "ok" }
```

**After Chapter 4:**
```json
{
  "status": "ok",
  "db": "connected"
}
```

When MongoDB is down, health must **never** claim `"db": "connected"`.

## Common questions

**Q: Do I create Mongoose models in this chapter?**
A: No — connection and config only. Models are Chapter 5.

**Q: Why connect before calling `listen()`?**
A: So the API doesn't accept traffic while pretending to be healthy.

**Q: Does the client need new env vars for MongoDB?**
A: No — the browser still only uses `VITE_API_URL`.
