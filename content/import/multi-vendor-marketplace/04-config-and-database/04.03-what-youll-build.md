## Boot order: connect before you serve

Professional APIs connect dependencies **before** accepting traffic:

```
1. Load config
   ↓ (validate env — fail if MONGODB_URI missing)
2. Connect to MongoDB
   ↓ (await mongoose connection)
3. Start HTTP server
   ↓ (app.listen)
4. On shutdown signal
   ↓ (disconnect MongoDB gracefully)
```

<Callout type="warning" title="Why this order matters">
If you `listen` first, health checks may report `status: ok` while DB is down — lying to load balancers. Config validation must run *before* the connect attempt so errors are clear.
</Callout>

## Health endpoint contract

**Before Chapter 4:**
```json
{ "status": "ok" }
```

**After Chapter 4:**
```json
{
  "status": "ok",
  "db": "connected"
}
```

When MongoDB is down, health must **never** claim `"db": "connected"`.

## Common questions

**Q: Do I create Mongoose models in this chapter?**  
A: No — this chapter is connection and configuration only. You set up the Mongo driver, wire `db.js` into your app on boot, and prove the connection with the health check. The models (User, Store, Product, Cart, Order) come in Chapter 5, after Chapter 3's design work has settled the shapes. Keep this chapter narrow on purpose: a connection that's proven first is far easier to debug than one tangled up with schemas. If you're tempted to add a model now, remember Chapter 5 will hand you the exact fields to use.

**Q: Why connect before calling `listen()`?**  
A: So your API never claims to be healthy while its database is down. If you start serving traffic first and connect to MongoDB afterwards, there's a window where requests arrive and fail because the database isn't ready — your health endpoint would report "up" while the app can't do anything real. Connecting first means `app.listen()` only runs once the database is reachable, so `/health` can report the true state of the world instead of a lie. Boot order is a small detail that saves you a whole class of confusing bugs.

**Q: Does the client need new env vars for MongoDB?**  
A: No — and this is an important separation to internalise. The React app never talks to MongoDB directly; it only talks to your Express API via `VITE_API_URL`. The `MONGODB_URI` lives in the server's `.env` and never leaves the server. If you ever see a database URI in browser code, that's a security problem — it means the client could bypass your API and hit the database with full access. The browser gets `VITE_API_URL`; the server keeps the keys.
