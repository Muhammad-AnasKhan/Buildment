# 4.4 — Environment variables vs hardcoded config

> **[Learn]** · Chapter 04 — Config & database · *12-factor config; `.env.example` vs `.env`*

## What you'll learn

By the end of this chapter, you'll understand:

- Why hardcoding config values will eventually break your app
- How the 12-factor config principle keeps your code portable
- The difference between `.env` (secret, never committed) and `.env.example` (template, always committed)
- Where each config value belongs

## Why this matters

Hardcoding feels faster on day one — paste the URI, move on. But day thirty, your mentor clones the repo and nothing runs. Or you deploy, and the app uses port 8080 while your code listens on 5000.

<Callout type="warning" title="Configuration is not code">
It's *input* to your code. One `config.js` reader keeps env vars discoverable; scattered `process.env` everywhere does not.
</Callout>

## Think of it like…

**A recipe vs the ingredients in your fridge.** The recipe (code) is the same everywhere. But ingredients (env vars) change per kitchen — your laptop, staging, production. You wouldn't bake the shop's address into the recipe.

## The hardcoded anti-pattern

Here's what *not* to do:

```javascript
// ❌ Never ship this
mongoose.connect('mongodb://127.0.0.1:27017/greenbasket')
app.listen(5000)
```

**Why this breaks:**

| Problem | When it hurts |
|---|---|
| Wrong DB on deploy | Production writes to a localhost string |
| Secret in Git | Connection string committed forever |
| Port conflict | Host uses `PORT=8080`; app listens on 5000 |
| Teammate clone | Their MongoDB runs elsewhere — they edit your source |

## 12-factor config — in plain language

The [12-factor app methodology](https://12factor.net/config) says: *store config in the environment.*

1. **Code** reads `process.env.VAR_NAME` via your `config.js` wrapper
2. **Environment** supplies values — `.env` file locally, host dashboard in production
3. **Same codebase** runs everywhere; only env differs

## `.env` vs `.env.example` — know the difference

This is a common source of confusion:

| File | Committed to Git? | Contents |
|---|---|---|
| `.env` | **Never** | Real secrets and local overrides |
| `.env.example` | **Always** | Key names + fake placeholders + comments |

When you add `MONGODB_URI`, `.env.example` should contain:

```env
# MongoDB connection string — copy to .env and set your real URI
MONGODB_URI=mongodb://127.0.0.1:27017/freshmarket-dev

# HTTP port (optional — defaults to 5000 in config)
PORT=5000
```

<Callout type="warning">
**No real Atlas password in the example file.** `.env.example` is committed to Git — treat it as public documentation.
</Callout>

## Loading `.env` in Node

The course accepts any of these **if documented in README**:

| Approach | Notes |
|---|---|
| **`dotenv` package** | `import 'dotenv/config'` at top of `server.js` |
| **Node `--env-file`** | `node --env-file=.env src/server.js` — Node 20+ |

Whatever you pick: env must load **before** `config.js` validation runs.

## Validation — fail fast

Reading `process.env.MONGODB_URI` without validation gives `undefined` — then Mongoose throws a confusing error. Better approach:

1. At startup, `config.js` checks required keys
2. Missing key → log error → exit non-zero
3. Developer fixes `.env` before retrying

## Defaults — when they're OK

| Setting | OK to default? | Example |
|---|---|---|
| `PORT` | yes | `process.env.PORT || 5000` |
| `NODE_ENV` | yes | default `development` |
| `MONGODB_URI` | **no** | must come from env |
| `JWT_SECRET` (Ch 6) | **no** | must come from env |

## Client-side env (Vite recap)

Vite only exposes variables prefixed with `VITE_`: `import.meta.env.VITE_API_URL`

**Never** put `MONGODB_URI` in a `VITE_` variable — it would ship to every user's browser.

<Callout type="danger" title="Security mistake">
`VITE_MONGODB_URI` exposes your database connection string to every user. Database URIs belong on the server only.
</Callout>

## ✅ Do / ❌ Don't

**✅ Do:** Document in README: "Copy `server/.env.example` to `server/.env` and set MONGODB_URI."

**✅ Do:** Re-run server after editing `.env` — the process doesn't hot-reload env changes.

**❌ Don't:** Commit `.env` "just this once" — send teammates `.env.example` instructions.

**❌ Don't:** Use `VITE_MONGODB_URI` — architectural mistake.
