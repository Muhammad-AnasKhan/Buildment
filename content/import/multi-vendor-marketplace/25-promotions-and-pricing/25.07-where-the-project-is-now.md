# 25.07 — Where the project is now

> **[Bridge]** · Chapter 25 — Promotions & pricing

Enter this build with working payments and inventory reservations from Chapter 24. The cart records intent—product references and quantities—while checkout reloads products and snapshots `priceAtPurchase` on vendor orders. That is the right foundation: promotions will extend the existing server-owned checkout path, not create a second path around it.

Before adding files, trace one successful checkout from the route to the Stripe call and success webhook. Write down the exact names your project uses for the cart, checkout ID, PaymentIntent ID, vendor grouping, and order items. The examples in this module describe responsibilities; adapt names instead of creating duplicate concepts.

## Baseline audit

Confirm the current state in code, not only in the UI:

| Area | What should already exist | Gap you will close |
|---|---|---|
| Cart | Product IDs and quantities for signed-in user | Optional normalized `appliedCouponCode` |
| Checkout | Reloads products and calculates current subtotals | Calls the shared pricing service |
| Orders | One vendor order with immutable item price snapshots | Discount and pricing snapshots |
| Payment | Server creates PaymentIntent | Amount comes from recomputed pricing |
| Webhook | Idempotently marks matching orders paid | Creates one checkout redemption |
| Inventory | Reservation correlated by `checkoutId` | Reuses the same checkout correlation ID |

If the browser currently sends `total`, `subtotal`, `unitPrice`, or `discount` in the checkout body, remove their authority now. It is acceptable for old clients to keep sending those fields temporarily, but the server must ignore them.

## Choose one correlation key

Chapter 24 introduced a stable `checkoutId` and placed it in PaymentIntent metadata. Reuse that value for pricing snapshots and coupon redemption. Creating a separate promotion attempt ID makes webhook recovery harder because several identifiers then describe the same purchase.

## Seed plan

Add two or three coupons in `seed.js` or a dedicated `seed-coupons.js` script:

- `FRESH10` platform percent with cap
- `BAKERY5`, tied to the seeded Sunrise Bakery store ID and requiring an eligible minimum subtotal
- `ONCE24`, with a one-redemption-per-user limit for the retry test

Do not put ordinary seeded coupon codes in `.env.example`; they are test data, not environment configuration or secrets. Document them beside the seed command or in the project README so another developer can recreate the same scenario.

## Baseline checkpoint

Before continuing, record these three values from an undiscounted test checkout:

1. the cart API subtotal;
2. the PaymentIntent amount in Stripe test mode;
3. the sum of the created vendor order totals.

They should match. If they do not, fix the existing pricing path before adding coupon logic; a promotion layer will amplify an unexplained mismatch.
