# 25.14 — Checklist and learning log

> **[Gate]** · Chapter 25 — Promotions & pricing

This gate asks for observable behavior, not only the presence of files. Run it with a cart containing products from at least two vendors so the allocation and redemption model are genuinely exercised.

## Chapter 25 checklist

- [ ] `Coupon` model with scope, type, caps, validity, unique `code`
- [ ] Invalid coupon shapes fail model validation; normalized code is unique
- [ ] `CouponRedemption` records one checkout and links all vendor order IDs
- [ ] Cart stores only coupon intent; apply and idempotent remove routes return server pricing
- [ ] `computeCartPricing` is called by both cart preview and checkout start
- [ ] Sum of line discounts equals cart discount, including a rounding-remainder case
- [ ] Store coupon leaves other vendors' lines unchanged
- [ ] PaymentIntent `amount` equals server `totalCents` and sum of vendor order totals
- [ ] Orders snapshot per-line and per-order discount fields plus coupon funding scope
- [ ] Replayed success webhook leaves one redemption and increments the counter once
- [ ] Failed or expired coupon stops checkout before PaymentIntent creation
- [ ] Apply endpoint returns `429` after the configured attempt limit
- [ ] Unknown, expired, exhausted, and wrong-store codes share one public error shape
- [ ] Structured rejection logs omit raw code, cart contents, and customer PII

## Learning log

1. **Trust boundary:** Trace what happens if the client sends a fake `totalCents`. Which server values replace it before Stripe?

2. **Multi-vendor:** Show how one fixed discount was allocated across lines, then rolled up into two vendor orders without losing a cent.

3. **History:** Why is there one redemption per checkout but a discount snapshot on every vendor order?

4. **Concurrency:** What can still happen if two customers race for the final global redemption, and what would an atomic claim add?

5. **Abuse:** Why do generic errors and rate limiting solve different parts of code enumeration?
