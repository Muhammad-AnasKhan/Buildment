# 25.09 — Validate coupon API

> **[Build]** · Chapter 25 — Promotions & pricing

The apply route should coordinate HTTP concerns; it should not become the rules engine. Put coupon policy in a service that checkout can call again without constructing a fake request or duplicating conditions.

Implement `server/modules/pricing/validateCoupon.js`. Its server-only result distinguishes success from failure:

```typescript
{ ok: true, coupon, eligibleLines, eligibleSubtotalCents }
{ ok: false, reason }
```

`reason` is for tests, metrics, and trusted logs. It never goes directly into the public response.

## Core checks (implement in order)

```javascript
export async function validateCoupon({ code, cart, userId, now = new Date() }) {
  const normalized = typeof code === 'string' ? code.trim().toUpperCase() : '';
  if (!normalized || normalized.length > 40) return fail('INVALID_FORMAT');

  const coupon = await Coupon.findOne({ code: normalized, isActive: true });
  if (!coupon) return fail('NOT_FOUND');

  if (now < coupon.startsAt || now >= coupon.endsAt) return fail('OUTSIDE_WINDOW');

  const eligibleLines = filterEligibleLines(cart, coupon);
  if (eligibleLines.length === 0) return fail('SCOPE');

  const eligibleSubtotalCents = sumLines(eligibleLines);
  if (eligibleSubtotalCents < coupon.minSubtotalCents) return fail('MIN_SUBTOTAL');

  if (coupon.maxRedemptions != null && coupon.redemptionCount >= coupon.maxRedemptions) {
    return fail('GLOBAL_CAP');
  }

  if (coupon.maxRedemptionsPerUser != null) {
    const userUses = await CouponRedemption.countDocuments({ couponId: coupon._id, userId });
    if (userUses >= coupon.maxRedemptionsPerUser) return fail('USER_CAP');
  }

  return { ok: true, coupon, eligibleLines, eligibleSubtotalCents };
}
```

`filterEligibleLines` must compare normalized MongoDB IDs safely—use `.equals()` or convert both sides to strings. A failed object-versus-string comparison is a common reason a valid store coupon appears to match no lines.

Pass `now` from tests rather than mocking the system clock. Add unit cases for one millisecond before `startsAt`, exactly at `startsAt`, and exactly at the exclusive `endsAt` boundary.

## Route: POST `/cart/coupon`

Authentication is required. The only body field is `{ code }`.

1. Validate the body shape and load the authenticated user's cart with current products.
2. Run validator.
3. On success, persist the normalized `appliedCouponCode`, call `computeCartPricing` from the next lesson, and return its preview.
4. On failure: 400 with `{ error: 'INVALID_COUPON', message: "This code isn't valid for your cart." }`.

## DELETE `/cart/coupon`

Clear `appliedCouponCode`; return repriced cart.

Do not return the Coupon document. The browser needs the safe display fields from the pricing preview, not internal caps, database IDs, redemption counts, or the validator's reason.

The `DELETE` route should be idempotent: removing a code when none is applied still returns the ordinary undiscounted pricing preview.

## Failure behavior

Use status `400` for an invalid or ineligible coupon, `401` for missing authentication, `429` for rate limiting, and the project's normal `500` path for an unexpected database failure. Do not convert an outage into “invalid coupon”; that hides an operational problem and makes debugging impossible.

## Verify before the UI

Use the API directly and save the response examples:

- lowercase `fresh10` is stored and returned as `FRESH10`;
- `BAKERY5` applies only when Sunrise Bakery's eligible subtotal reaches its minimum;
- another user's one-time redemption does not block the current user;
- a known wrong-store code and an unknown code return the same public error shape;
- deleting twice succeeds and returns the same undiscounted total.
