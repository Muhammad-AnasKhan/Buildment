# 25.12 — Rate limits and abuse

> **[Build]** · Chapter 25 — Promotions & pricing · *Hardening*

Coupon codes are credentials with financial value. An attacker can automate guesses such as `SAVE10`, `SAVE20`, and leaked campaign names far faster than a real customer can type them. Generic errors prevent direct disclosure, but without throttling the endpoint still acts as an oracle.

## Rate limit middleware

Reuse the shared Redis infrastructure from Chapter 21 when available. Apply two limits to `POST /cart/coupon`: one keyed by authenticated user and one keyed by normalized IP. A user-only key misses attackers rotating accounts; an IP-only key can punish many legitimate users behind one network.

- User key: `coupon-attempt:user:${userId}`
- IP key: `coupon-attempt:ip:${ip}`
- Starting policy: 20 attempts per 60 seconds per key
- Response: `429` with `{ error: 'TOO_MANY_ATTEMPTS', retryAfterSeconds }`
- Header: `Retry-After` with the same rounded-up delay

Check both counters before coupon lookup and increment for every apply attempt, including a valid code. Otherwise, response timing or remaining-limit behavior can reveal whether a guessed code exists.

An in-memory `Map` is acceptable only for a clearly labeled local exercise. It resets on restart, grows unless cleaned up, and gives each API instance a separate allowance. Production throttling needs Redis or another shared store with key expiry.

## Logging

Emit a structured event on rejection. Prefer the project's logger over `console.warn` so fields are queryable:

```javascript
logger.warn('coupon_rejected', {
  reason,
  userId,
  couponFingerprint: hashForLogs(normalized),
  requestId,
});
```

Do not log the raw coupon code, full cart, email address, access token, or address. A stable keyed fingerprint lets operators group repeated guesses without turning logs into a coupon-code inventory. Use the internal reason in logs while the client continues to receive the generic invalid message.

Useful counters include total attempts, rejected attempts by internal reason, rate-limited requests, and redemption failures. Alert on sudden changes rather than treating every invalid code as an incident.

## Admin kill switch

Set `isActive: false` on a coupon in your admin path or mongosh during the demo. The next apply attempt and next checkout recomputation must reject it without a deploy. An already paid order remains unchanged because it uses snapshots.

## Optional stretch

- Add a cooldown that increases after repeated failures for the same user.
- Add campaign-specific monitoring for unusually fast redemption growth.
- Introduce atomic coupon claims if a hard global cap has financial or contractual importance.

## Verify

Automate these checks instead of clicking Apply repeatedly:

1. Send 20 failed attempts as one user and confirm the next response is `429` with `Retry-After`.
2. Confirm an attempt from a second user on a different IP still works.
3. Advance beyond the window and confirm the first user can try again.
4. Inspect logs: they contain the internal reason and request ID, but not the raw code or cart.
5. Deactivate `FRESH10` after applying it; checkout must stop before creating a PaymentIntent.
