# 25.03 — What you'll build

> **[Learn]** · Chapter 25 — Promotions & pricing · *Blueprint*

The module has four responsibilities. Keep them separate so coupon policy does not leak into controllers or React components:

1. **Coupon policy** describes when and where a code may apply.
2. **Validation** decides whether a code is eligible for this user and cart now.
3. **Pricing** calculates integer-cent line totals and allocation.
4. **Checkout** snapshots that result and records a redemption after payment succeeds.

## Collections

The `Coupon` collection stores mutable campaign rules. An administrator may deactivate a coupon, but an existing paid order must never be reconstructed from the current coupon document.

**Coupon**

| Field | Notes |
|---|---|
| `code` | Uppercase normalized unique index |
| `scope` | `platform` \| `store` |
| `storeId` | Required when scope is store |
| `type` | `percent` \| `fixed_cents` |
| `value` | `10` = 10%, or `1000` = 1,000 smallest currency units |
| `maxDiscountCents` | Optional cap for percent discounts |
| `minSubtotalCents` | Minimum eligible subtotal |
| `startsAt` / `endsAt` | Validity window |
| `maxRedemptions` | Global cap |
| `maxRedemptionsPerUser` | Per customer |
| `isActive` | Kill switch |

`CouponRedemption` is an append-only audit event. Store one row per successful checkout, not one per vendor order:

```typescript
{
  couponId,
  userId,
  checkoutId,
  paymentIntentId,
  orderIds,
  discountCents,
  createdAt
}
```

A unique index on `{ couponId, checkoutId }` makes webhook retries harmless. `orderIds` links the single redemption to every vendor order produced by that checkout.

## Routes

| Method | Path | Role |
|---|---|---|
| POST | `/cart/coupon` | Validate, save code, return authoritative preview |
| DELETE | `/cart/coupon` | Remove saved code and return repriced cart |
| POST | `/coupons/validate` | Optional dry run using the same validator |

Vendor admin (stretch): `POST /vendor/coupons` — document in learning log if you skip UI and seed coupons.

## Pricing service

`computeCartPricing({ cart, userId, now })` reloads current product prices, validates the cart's saved code, and returns:

```typescript
{
  lines: Array<{ productId, storeId, quantity, unitPriceCents, subtotalCents, discountCents, payableCents }>,
  discountTotalCents: number,
  subtotalCents: number,
  totalCents: number,
  coupon: { code, scope } | null,
  errors: Array<{ code: string }>
}
```

Pass `now` explicitly in tests so campaign-window cases are deterministic. The service returns internal error codes to trusted server callers; the route maps coupon failures to one safe public message.

## Checkout integration

- Checkout start calls `computeCartPricing`; it rejects a saved coupon that became invalid.
- Each order stores `subtotalCents`, `discountCents`, `totalCents`, `couponCode`, coupon funding scope, and `pricingVersion: 1`.
- PaymentIntent metadata contains `checkoutId` for webhook correlation.
- The success webhook inserts one redemption and increments the global count idempotently.

The course uses payment success as the redemption point. A failed PaymentIntent therefore does not consume a customer's one-time code. This choice still has a concurrency edge: two simultaneous checkouts can both validate the last available use. You will document that limitation and the transaction/claim strategy required for a stricter production system.

## Abuse controls

- Rate-limit `POST /cart/coupon` by user and IP (for example, 20 attempts per minute).
- Normalize codes (`trim`, uppercase) to block case variants.
- Do not leak “code exists but not for you”; use the same public error for unknown, expired, exhausted, and wrong-scope codes.

## Definition of done

You are finished when changing the browser's displayed total cannot change the Stripe amount, vendor order totals add exactly to the PaymentIntent amount, and a replayed success webhook cannot create a second redemption.
