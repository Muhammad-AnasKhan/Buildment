# 25.11 — Snapshot discounts on order

> **[Build]** · Chapter 25 — Promotions & pricing · *Checkout integration*

Chapter 18 split one cart into one order per vendor. Chapter 24 gave the checkout attempt a stable `checkoutId`. This lesson carries the already allocated line discounts through both ideas without recalculating them during vendor grouping.

The order is a receipt, so it needs enough frozen pricing data to explain the charge after product prices or coupon policy changes. The redemption is different: it records that the customer consumed the coupon once for the entire checkout.

## Checkout start changes

1. Generate or reuse the stable `checkoutId` for this attempt.
2. Load the authenticated cart and call `computeCartPricing({ cart, userId })`.
3. If the cart has a saved code but validation now fails, return a refreshed preview and stop before Stripe.
4. Call `reserveForCheckout` from Chapter 24 with the same quantities and `checkoutId`.
5. Group the **priced lines** by `storeId`; sum their existing subtotals, discounts, and payable totals.
6. Assert that the sum of vendor order totals equals `pricing.totalCents`.
7. Persist pending orders with immutable pricing snapshots.
8. Create the PaymentIntent for `pricing.totalCents` and include `checkoutId` in metadata.
9. Attach the returned PaymentIntent ID to orders and reservations using your existing Chapter 24 flow.

Do not keep a MongoDB transaction open while waiting for Stripe. Stripe is outside MongoDB and cannot participate in that transaction. If PaymentIntent creation fails, follow Chapter 24's compensating path: release active reservations and mark or remove pending records according to the checkout design you already chose.

Each vendor order stores:

```javascript
{
  couponCode: pricing.coupon?.code ?? null,
  discountCents: orderDiscount,
  subtotalCents: orderSubtotal,
  totalCents: orderTotal,
  pricingVersion: 1,
}
```

Also snapshot `couponScope` so settlement can distinguish platform-funded from vendor-funded discounts. Embed each line's `discountCents` alongside `priceAtPurchase` and quantity. Never reload the mutable Coupon later to rebuild a receipt.

Before insert, enforce these equalities:

```text
orderSubtotal === sum(orderItems[].subtotalCents)
orderDiscount === sum(orderItems[].discountCents)
orderTotal === orderSubtotal - orderDiscount
pricing.totalCents === sum(all vendor order totals)
```

## Redemption on payment success

In the `payment_intent.succeeded` handler, after locating the checkout and marking its orders paid, write one redemption for the whole checkout. Put the read, insert, and counter update in the same MongoDB transaction when your deployment supports it:

```javascript
await session.withTransaction(async () => {
  const existing = await CouponRedemption.findOne({
    couponId,
    checkoutId,
  }).session(session);

  if (existing) return;

  await CouponRedemption.create([{
    couponId,
    userId,
    checkoutId,
    paymentIntentId,
    orderIds,
    discountCents: pricingDiscountSnapshot,
  }], { session });

  await Coupon.updateOne(
    { _id: couponId },
    { $inc: { redemptionCount: 1 } },
    { session }
  );
});
```

The unique indexes from 25.08 are the final defense if two webhook workers race. Handle a duplicate-key result as “already processed,” then confirm the existing redemption matches this checkout instead of incrementing again.

Use the discount saved on the orders or a checkout pricing snapshot in the webhook. Do not run `computeCartPricing` after payment: catalogue prices and coupon rules may have changed since Stripe accepted the amount.

## Stripe

`paymentIntents.create({ amount: pricing.totalCents, ... })` has no client override. Include `checkoutId` and the authenticated user ID in metadata for lookup, but keep the full cart and coupon policy out of Stripe metadata.

## Be honest about redemption races

Counting successful redemptions during validation enforces normal use but does not strictly protect the final global slot from two simultaneous checkouts. A production system with scarce coupons needs an atomic claim before payment, plus expiry/release behavior similar to Chapter 24's stock reservations. That is intentionally outside this module's one-code MVP; document it instead of claiming the count query is concurrency-safe.

## Verify

- Apply `FRESH10`, checkout, and pay; Stripe amount equals the sum of vendor order totals.
- Edit `FRESH10` afterward; the paid order still displays its original coupon and discount snapshots.
- Replay the success webhook; there is still one redemption and the coupon counter increases only once.
- Complete one `ONCE24` checkout; the next validation for the same user is rejected.
- Force Stripe creation to fail; active stock reservations are released and no redemption exists.

**Next:** Protect the validation surface from guessing and make rejected attempts observable without leaking customer data.
