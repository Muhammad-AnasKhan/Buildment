# 25.02 — Why never trust client totals

> **[Learn]** · Chapter 25 — Promotions & pricing · *Trust boundary*

The client may **display** `$42.50`. Only the server may decide to **charge** `$42.50`. Anything in React state, local storage, a hidden input, or a request body can be changed by the person making the request.

## Attack you are preventing

A user submits checkout with DevTools:

```json
{ "couponCode": "SAVE50", "clientTotalCents": 100 }
```

If the API forwards `clientTotalCents` to Stripe, the attacker pays $1 for a $200 cart. A signed-in user is not automatically trustworthy: authentication tells FreshMarket *who* sent the request, not whether the numbers in it are true.

The opposite failure is also harmful. If the cart UI applies `SAVE50` locally but checkout ignores it, the customer sees one price and gets charged another. The safe design is not “ignore the client”; it is “make one server pricing service authoritative everywhere.”

## Separate intent from authority

The request may contain the customer's **intent**: apply code `SAVE50`, buy these cart quantities, or remove a coupon. It must not contain authoritative prices, discounts, or totals.

| Value | Accepted from client? | Authoritative source |
|---|---:|---|
| Coupon code | Yes, as untrusted input | Coupon collection after normalization |
| Cart quantity | Already stored through cart API | Authenticated server-side cart |
| Unit price | No | Current Product document at pricing time |
| Discount amount | No | Pricing service |
| Payment amount | No | Pricing service at checkout start |

## Correct flow

```
Client → POST /cart/coupon { code }
Server → load authenticated cart + current prices
Server → validate rules → persist normalized appliedCouponCode
Server → compute line totals + deterministic discount allocation
Client → display server-returned pricingPreview
Client → POST /checkout/start (no total in body)
Server → reload and recompute → reserve stock → create PI for server amount
Webhook → confirm payment + write one idempotent redemption
```

Recompute **again** at checkout start because applying a coupon is a preview, not a promise. Prices can change, eligibility can disappear, a global redemption cap can be reached, or the coupon can expire between apply and pay. If the saved code is no longer valid, stop before Stripe and ask the customer to review the refreshed cart.

## Multi-vendor twist

One checkout may split into **one order per vendor** (Chapter 18). A platform coupon might fund $10 across all stores; a store coupon applies only to lines from its `storeId`. Your engine must allocate discount cents to eligible lines before it groups those lines into orders. Otherwise, two separately rounded order discounts may not add up to the PaymentIntent amount.

| Coupon scope | Applies to |
|---|---|
| `platform` | Eligible lines marketplace-wide |
| `store` | Lines where `line.storeId === coupon.storeId` |

A redemption belongs to the overall `checkoutId`, not to each vendor order. The vendor orders keep their own discount snapshots, while one checkout-level redemption consumes the coupon once.

## Stripe alignment

PaymentIntent `amount` must equal the sum of the server-computed vendor order totals. Assert this equality before calling Stripe; do not rely on a later webhook to discover a mismatch.

## What to verify later

The strongest test changes the inputs between preview and checkout. Apply a valid coupon, then expire or deactivate it in the database. Checkout must refuse the stale preview and must not create a PaymentIntent. That proves checkout recomputes instead of trusting yesterday's server response.
