# 25.04 — Coupon types and rules

> **[Learn]** · Chapter 25 — Promotions & pricing · *Rules engine*

Coupon behavior becomes unreliable when rules live in scattered `if` statements. Write the policy as an ordered pipeline first; later, the validator can follow the same order and return a precise internal reason.

## Validation pipeline

1. Normalize the code, reject an empty or overlong value, and look up an active coupon.
2. Check the time window: `startsAt <= now < endsAt`. Treat `endsAt` as exclusive so adjacent campaigns do not overlap at one instant.
3. Select eligible merchandise lines. A store coupon includes only lines owned by that store.
4. Calculate `minSubtotalCents` from those **eligible** lines only.
5. Check global successful redemptions against `maxRedemptions`.
6. Check this user's successful redemptions against `maxRedemptionsPerUser`.
7. Calculate the total discount, then allocate it to eligible lines.

Cheap, non-database checks should happen early, but correctness matters more than micro-optimizing this short pipeline. Keep the order stable so tests and logs describe the same failure when several rules are false.

## Percent vs fixed

All monetary arithmetic stays in integer smallest units. Never convert to floating-point dollars for a calculation and then convert back.

**Percent:** `discount = floor(eligibleSubtotalCents * value / 100)`, then apply `maxDiscountCents` when present. Choose `floor` deliberately: a promotion must not discount more than its exact percentage. Use the same rule in tests and receipt explanations.

**Fixed:** apply up to `value` units, never more than the eligible subtotal. A $50 fixed coupon on $30 of eligible goods produces a $30 discount, not a negative total or store credit.

## Allocation across lines (proportional)

For platform $10 off a cart with two vendors, split by line subtotals so vendor payouts stay explainable:

```
lineDiscount_i = floor(totalDiscountCents * lineSubtotalCents_i / eligibleSubtotalCents)
```

Floors may leave a remainder. Allocate one leftover cent at a time to eligible lines sorted by descending subtotal, then by stable product ID as a tie-breaker. A deterministic tie-breaker means the same cart always produces the same order snapshots.

After allocation, assert both invariants:

```text
sum(line.discountCents) === discountTotalCents
line.payableCents === line.subtotalCents - line.discountCents
```

Group priced lines into vendor orders only **after** those assertions pass.

## FreshMarket examples

| Code | Rule | Intent |
|---|---|---|
| `FRESH10` | Platform 10% max $15 | Launch campaign |
| `BAKERY5` | Store fixed $5, min $20 at Sunrise Bakery | Vendor-funded promo |
| `ONCE24` | `maxRedemptionsPerUser: 1` | New customer offer |

The funding source follows scope in this version: FreshMarket funds `platform` coupons, and the matching vendor funds `store` coupons. Snapshot that scope on each order so future settlement reports do not depend on a coupon that may later be edited.

## Errors (user-facing)

Use one message for security-sensitive failures: **“This code isn’t valid for your cart.”** The server may record an internal reason such as `COUPON_EXPIRED` or `SCOPE_MISMATCH`, but logs should not include the full cart or other customer data.

## Edge cases to write down before coding

- An empty cart has no eligible subtotal and cannot receive a coupon.
- A zero-payable cart is allowed only if your Stripe flow supports bypassing a zero-amount PaymentIntent; otherwise cap the promotion below zero and document the product decision.
- A removed or inactive product must fail normal cart validation before coupon math.
- A store coupon in a mixed cart leaves every other store's lines unchanged.
- A platform coupon with a cap applies the cap before proportional allocation.
