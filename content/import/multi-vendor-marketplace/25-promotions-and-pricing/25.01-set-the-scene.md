# 25.01 — Set the scene

> **[Open]** · Chapter 25 — Promotions & pricing · *After inventory, fix the money*

Chapter 24 made stock honest under concurrent checkout. Now FreshMarket has a different kind of race: a customer applies `FRESH10`, sees a discounted total, waits five minutes, and checks out after the campaign has expired. At the same time, the vendor may have changed a price and an attacker may have edited the total in DevTools.

The visible cart is only a preview. The amount sent to Stripe must come from current products, current coupon rules, and the authenticated user's cart on the server. That makes promotions a pricing problem, a security boundary, and an accounting problem—not a decorative input beside the cart total.

In this module, you will build the smallest promotion system that can explain every charged cent. It supports one coupon per checkout, platform- and store-funded discounts, percentage and fixed discounts, limits, and immutable order snapshots.

## The failure you are designing against

Suppose Aisha buys groceries from Sunrise Bakery and Green Valley Produce. A platform coupon removes 10% from both stores, but FreshMarket creates one order per vendor. If the system saves only the final PaymentIntent amount, it cannot later answer:

- How much discount belonged to each vendor order?
- Who funded the promotion: the vendor or the platform?
- Did Aisha consume her one allowed redemption once, or once per vendor order?
- Why does the receipt differ from today's catalogue prices?

Those questions shape the data model and checkout flow in the later lessons.

## Objectives

- Model **coupons** with scope (platform vs store), type (percent vs fixed), caps, and validity window.
- Validate codes in an API that returns a **pricing preview**, not hidden client math.
- Recalculate cart subtotals server-side when a coupon is applied or removed.
- Allocate discount cents deterministically across eligible lines and vendor orders.
- Snapshot the discount breakdown on each order at checkout, extending the Chapter 18 receipt pattern.
- Record one idempotent redemption per checkout and enforce global and per-user limits.
- Rate-limit validation attempts without exposing whether a guessed code exists.

## The pricing invariant

By the end of the module, the same pricing result must drive all three surfaces:

1. the cart preview returned by the API;
2. the PaymentIntent amount created at checkout;
3. the subtotal, discount, and total snapshots stored on each order.

The browser may display that result, but it never becomes the source of truth.

## Out of scope

- Stackable coupons (only one active code per checkout in this pass)
- Dynamic pricing / surge
- Stripe Coupons API as source of truth (FreshMarket owns rules in MongoDB; Stripe receives the computed amount)
- Vendor promotion-management UI (seed representative coupons for this pass)
- Taxes, delivery-fee discounts, and refunds (keep the exercise focused on merchandise lines)
