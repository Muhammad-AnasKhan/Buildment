# 7.3 — What you'll build

> **[Read]** · Chapter 07 — Login & registration · *Register, login, OTP verify pages*

Chapter 7 delivers **browser auth UX** wired to Chapter 6 API — register, verify, login, silent refresh, protected navigation.

## Why this matters for absolute beginners

This checklist is the **browser-side gate** — three pages, shared auth state, interceptor, protected routes. Each maps to build sub-chapters 7.9–7.16. Without the list, it is easy to build Login but forget boot-time refresh or OTP route — users appear logged out on every reload.

## Common beginner questions

**Q: Do I need Redux for auth?**  
A: No — auth state is small and read by many pages, which is exactly what React Context is for. Redux brings a store, actions, and reducers to manage a state that barely changes: a `user` object and a few flags. A `useAuth` hook backed by an `AuthProvider` gives every page `user`, `isAuthenticated`, `isLoading`, and `login`/`logout` with a fraction of the code. What actually matters is that all pages read from one shared source of truth so three forms don't drift apart — and Context satisfies that. Reach for Redux only if the state genuinely grows beyond Context's scope.

**Q: Can I change the API shapes from Chapter 6?**  
A: No — and that's a constraint, not a rule to bend. You proved those exact JSON shapes work with curl, and later chapters build on the same `user` object. If a response field doesn't match what your page expects, adapt the client to the contract: check your curl output, then fix the form code. If you change the server instead, you're debugging React and Express at once — the hardest combination — and you'll silently break the tests you're meant to reuse. The server is the contract; the client is the adapter.

**Q: Where do vendors land after login?**  
A: Somewhere useful — a vendor heads to their workspace, a customer goes shopping. Both are placeholder stubs this chapter: `/vendor` for vendors and `/` for customers, though the exact paths are your choice. Use `useNavigate` after login, reading the role from the `user` object, or keep it simple and send everyone through a small redirect. Document the paths in your router, because the real vendor dashboard lands in Chapter 10 and the shop in Chapter 15, and those chapters need to know where to plug in.

**Q: Why centralize auth in one `useAuth` hook instead of each page?**  
A: Because the alternative is three login flows that slowly drift apart. If `Login.jsx` stores the user one way and `Register.jsx` another, fixing a bug means hunting through every copy. Putting the state and methods in one `AuthProvider` gives you a single place for `user`, login, logout, and the boot-time refresh — the client-side mirror of the single `auth` module you built on the server. One source of truth means one place to fix bugs, and every page automatically stays consistent.

**Q: Why does boot-time refresh matter so much?**  
A: Because the access token lives in memory, and memory dies on page reload. Without a refresh attempt on mount, a user who logs in, reloads, and goes to shop is bounced straight back to the login screen — even though their server session is perfectly valid. The one line on mount — call `POST /api/auth/refresh` with the httpOnly cookie, receive a new access token — is what makes reloads feel seamless. It's the single most common "why am I logged out?" bug in this chapter, so build it in from day one.

## Pages

You need exactly three screens, and each one wraps a single Chapter 6 endpoint. The page is the "view"; the endpoint is the "action". Keeping this mapping one-to-one matters because it lets you debug from either side — if a form fails, you already know which API call to inspect and whether the bug lives in your form or in the server.

| Page | Route | API calls |
|---|---|---|
| Register | `/register` | POST /api/auth/register |
| Verify OTP | `/verify-otp` | POST /api/auth/verify-otp |
| Login | `/login` | POST /api/auth/login |

After a successful login the user should land somewhere useful. The destination depends on who they are — a vendor goes to their workspace, a customer goes shopping. Both are placeholder stubs for now; the real vendor dashboard arrives in Chapter 10 and the shop in Chapter 15.

- vendor → `/vendor` or dashboard stub  
- customer → `/` or shop stub  

Exact paths are your choice — document them in the router so Chapter 10 can change them later.

## useAuth / AuthContext

Every page in this chapter needs to know *who the current user is* and *how to log in or out*. Duplicating that logic inside each form is how you end up with three slightly different login flows that drift apart. So you centralize auth state in one shared hook the whole app calls — the client-side version of the single `auth` module you built on the server. One place for state, one place for bugs.

Provides:

- `user`, `isAuthenticated`, `isLoading`  
- `login(email, password)`  
- `register(...)`  
- `verifyOtp(email, otp)`  
- `logout()`  
- `accessToken` — internal to api client, not exposed to components unnecessarily  

**Boot: attempt refresh on mount to restore session.** That one line on mount is what keeps users logged in across page reloads. Without it, every refresh kicks you back to the login screen even though the server session is still valid — the single most common "why am I logged out?" bug in this chapter.

## API client extensions

Your `api/client.js` helper from Chapter 2 knows how to talk to the server, but it knows nothing about authentication yet. You extend it in *one* place so every request automatically carries the user's identity — and knows how to recover when a session expires. Centralizing it here means individual pages never repeat token logic and never accidentally skip the header.

- Attach `Authorization: Bearer` when access token set  
- On 401: call refresh once → retry original request → if fail, logout + redirect login  
- `credentials: 'include'` for refresh cookie  

## ProtectedRoute

Some pages should only be reachable by a logged-in user. Writing an "are they logged in?" check inside every page repeats the same code and invites mistakes. Instead you wrap the route once in a guard component — the client-side half of the authorization you will enforce on the server in Chapter 8.

Wrapper component:

- If loading → spinner or null  
- If !authenticated → `<Navigate to="/login" />`  
- Else → render children  

Apply it to the vendor routes preview now — full role gates arrive in Chapter 8.

## Server adjustment (optional)

Chapter 6 may return the refresh token in the JSON body. If so, Chapter 7 moves it into an httpOnly cookie so browser JavaScript cannot read it — the security pattern from 7.2. This is the one place this chapter touches the server, and it should be a *small* change.

```
Set-Cookie: refreshToken=...; HttpOnly; Path=/api/auth; SameSite=Lax
```

May require `cookie-parser` on the server. If login now returns a cookie plus an empty refresh field in the body, document that contract change in your README.

## Common beginner mistakes

The three bugs that waste the most mentee time on this chapter, in order of frequency:

1. **Forgot `credentials: 'include'`** — the refresh cookie is never sent, so silent refresh "always 401s" and the user is logged out on every reload. This looks like a server bug but is a one-line client omission.
2. **Stored the access token in localStorage** — it works, which is exactly the trap. Any script on the page can read it; the whole point of 7.2 was to avoid this.
3. **Redirected by role using response fields that never exist** — the `login` response shape must match Chapter 6 exactly. Check your curl output before writing code that reads a field the API does not send.
