## Why this matters for absolute beginners

Chapter 7 combines React Router, forms, cookies, and async boot logic — easy to glue wrong. Thirty minutes on Navigate, credentials, and your Chapter 6 curl notes prevents building pages that work in isolation but fail after reload or CORS.

## Common beginner questions

**Q: Why do I need to read fetch credentials docs for a React course?**  
A: Because your auth depends on a browser feature, not on React. The refresh token lives in a cookie, and cookies only cross origins when the request uses `credentials: 'include'`. Miss that one option and the cookie never leaves the browser, so your silent refresh "always 401s" — even though the same call works fine in curl. Understanding what the browser does with cookies is what turns a mysterious reload bug into an obvious one-line omission. The MDN page is short; skim it once and you'll save hours later.

**Q: Controlled inputs without a form library — really?**  
A: Really, and it's deliberate. A form library like Formik or React Hook Form brings validation, touched-state tracking, and a pile of concepts you don't need yet. Controlled inputs are just state: `value={email}` with an `onChange` that updates the state on every keystroke. Three small forms — login, register, verify-otp — don't justify a dependency that hides what's happening. The gate cares that your auth flow sends the right body to the right endpoint, not that you used a library to build the form. Fewer dependencies, clearer learning.

**Q: Why is `Access-Control-Allow-Origin: *` invalid with credentials?**  
A: The browser spec forbids a wildcard origin once cookies are involved — sending your cookie to "any origin" would defeat the point of cookies entirely. With `credentials: 'include'`, the server must echo your exact Vite origin — `http://localhost:5173` — plus `Access-Control-Allow-Credentials: true`. This is the classic "works in curl, fails in browser" trap, because curl never enforces CORS; the browser silently blocks the refresh call instead. If refresh mysteriously fails this chapter, check the CORS headers first.

**Q: Why decide the four patterns before writing any UI code?**  
A: Because these decisions come up *during* the build, and pausing mid-build to re-architect is how bugs sneak in. Choosing auth state (Context + `useAuth` hook), the form approach (controlled inputs), error display (single message vs field errors), and how the email reaches `VerifyOtp` (via `location.state` from Register) now makes the build sub-chapters mechanical — you write code instead of making judgment calls. Write the choices in your learning log too, since Chapter 8 and beyond will inherit them and need to know what you picked.

**Q: What's the difference between `Navigate` and `useNavigate`?**  
A: `Navigate` is a component you render to redirect — perfect inside a `ProtectedRoute`, where an unauthenticated user hitting a guarded page simply outputs `<Navigate to="/login" />`. `useNavigate` is a hook that returns a function you call from code, which suits actions — like calling `navigate('/vendor')` right after a successful login or registration. Same outcome, two triggers: declarative rendering for "this page says no," and imperative calls for "this flow finished." Both are in your mandatory reads, and knowing when to use each is exactly what Chapter 8's guards will need.

## CORS + credentials

This is the classic "works in curl, fails in browser" chapter. The moment you send cookies with `credentials: 'include'`, the browser demands an explicit origin — a wildcard `*` is rejected by spec. If your server still answers `Access-Control-Allow-Origin: *`, refresh calls fail silently with no obvious error.

Server must respond:

```
Access-Control-Allow-Origin: http://localhost:5173  (not * when credentials)
Access-Control-Allow-Credentials: true
```

Update server CORS config in build cluster if not already.
