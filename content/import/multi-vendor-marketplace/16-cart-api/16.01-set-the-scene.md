## In plain English

| Term | Simple meaning |
|---|---|
| **Cart** | The customer's saved list of "I want to buy these" before checkout |
| **Cart line / cart item** | One row: a product, how many, which store sells it |
| **Multi-vendor cart** | **One basket** with items from Shop A **and** Shop B — not two separate carts |
| **`storeId` on each line** | A copy of which vendor fulfills that item — checkout uses it to split orders later |
| **User scoping** | Every cart query filters by **logged-in user's id** — you never see someone else's basket |
| **Stock check on add** | Server reads current `stockQty` when adding — does not reserve stock until checkout (Ch 18) |
| **Persisted cart** | Saved in the database — survives refresh, different tab, tomorrow |

## Think of it like one shopping basket at a real market

At a farmers' market you carry **one basket**. You pick tomatoes from Stall A and bread from Stall B. You do **not** get a second basket per stall.

FreshMarket works the same:

```
Your one cart
├── Tomatoes   (Green Valley stall)
├── Milk       (Green Valley stall)
└── Salmon     (Harbor Market stall)
```

At checkout (Chapter 18), the system splits into **two orders** — one per stall — but the customer still clicked **one** "Place order" button. That split only works if each cart line already knows its **`storeId`**. Chapter 16 stores that key when the customer adds an item.

## Common beginner questions

**Q: Why not store the cart in React state or localStorage?**  
A: Because browser storage is flaky and unshareable. A cart in React state dies the moment the page refreshes; localStorage survives a reload but only on that one device and browser, so it won't follow you to another machine, and the server can't trust it anyway. A *persisted* cart lives in MongoDB, scoped to the logged-in customer's `userId`, so it survives refresh, another tab, tomorrow, and any device. That server-side cart is also the only thing checkout (Chapter 18) can securely trust and turn into an order. Guest carts are out of scope for MVP — log in first.

**Q: Do I need two carts for two vendors?**  
A: No — that's the classic beginner mistake, and it would wreck the marketplace experience. One customer, one cart, many vendors. Your single basket holds tomatoes from Green Valley *and* salmon from Harbor Market as separate cart lines, and each line records its own `storeId` so the server knows which stall supplies it. At checkout the system groups lines by `storeId` and creates one order per vendor — but you, the customer, only ever see and pay for one basket.

**Q: Why save `storeId` on each line if the product already has `storeId`?**  
A: Because the product could change, and checkout shouldn't have to guess. If checkout had to look up every product to rediscover its vendor, that's extra queries and fragile grouping — and a product could move to a different store later, silently rerouting an order. So the cart copies `storeId` onto the line at add time and validates it matches the product's real `storeId`. The line knows its vendor the moment it enters the basket, which is exactly what makes the Chapter 18 split possible.

**Q: When does stock actually decrease?**  
A: Not when you add to cart — that's the common misunderstanding. Adding only *checks* the current `stockQty` and rejects the add if there isn't enough. Real stock decrement happens at checkout in Chapter 18, when the order is actually created and the vendor commits to fulfilling it. Think of the cart as a wish list with a sanity check: adding doesn't reserve anything, so two customers can both have the last avocado in their carts — whoever checks out first gets it.

**Q: Can vendors use the cart?**  
A: Yes — vendors are also customers when they're shopping. The cart routes are scoped to any logged-in user, so a vendor browsing the marketplace with their account uses exactly the same `POST /cart` and `GET /cart` endpoints as a customer. The route doesn't care about your role, only that you're authenticated and only ever reading or writing *your own* cart. The `storeId` on each line still does its job, because the checkout split depends on which vendor *supplies* an item, not who is buying it.

**Q: Why API-only this chapter — no cart page yet?**  
A: Same pattern as every backend half of a pair (6→7, 11→12, 14→15): prove the contract before the screen. This chapter you test with curl — add items from two stores, check that User A cannot read User B's cart — and get the API rock-solid without React in the way. If a multi-vendor add or user-isolation test fails in curl, it's unambiguously a server bug. Chapter 17 is the UI pair: it renders what these routes return and wires the add-to-cart button.

## The gap between "browse" and "buy"

Browse answers *what exists*. Cart answers *what this customer intends to purchase* — across **multiple vendors** in one basket.

Without `storeId` on each line, checkout would re-query products to guess vendor grouping — fragile and slow. Chapter 16 embeds the split key at add time.
