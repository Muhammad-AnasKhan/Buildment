## Final ship checklist

### Runnable product

- [ ] Production client URL loads without errors
- [ ] Week 3 commerce demo works on **production** (browse → two vendors → cart → Stripe test pay → vendor sees order)
- [ ] Week 2 vendor flow works on production (login → products with photos)
- [ ] Week 4 search returns results on production
- [ ] Worker processed checkout on production (row 6 from 22.13)
- [ ] No console errors on primary user paths

### Repository hygiene

- [ ] README: local setup, deploy steps, demo accounts (no passwords — "see seed" or "contact mentor")
- [ ] `.env.example` files complete
- [ ] No secrets in Git history (`git log -- "**/.env"` empty)
- [ ] Sensible commit history — features findable

### Learning logs

- [ ] Chapter gates completed on the platform
- [ ] Each gate chapter has honest answers — not one-line stubs

## Demo video — 3 to 5 minutes

1. Customer browses and filters
2. Add from two stores
3. Checkout — enter Stripe test card — show split confirmation
4. Vendor login — order inbox — status update
5. Optional: search, mention cache/async in voiceover ("confirmation appeared before notification logs — that's the worker")

Upload unlisted YouTube/Loom; link in README and `docs/DEMO.md`.

## Common beginner questions

**Q: Is Chapter 99 more coding?**  
A: Mostly not — it's verification and packaging. You'll work through the ship checklist, write the README top section with live links, record a demo video, and fill the final learning log. The only "new" work is fixing whatever breaks on production before evaluation. The point is to prove the app is real and shippable, not to add features. If the app runs and the docs are honest, this chapter is mostly assembly.

**Q: My Atlas cluster paused. Am I done?**  
A: Not until the live URL works at evaluation time. If your database pauses, or the free tier spins the app down and you don't restart it, a mentor clicking your link sees an error — and that's the first thing they check. Redeploy, wake the cluster, and run a smoke test before submitting. A dead link is worse than no link, because it looks like you never verified your own work.

**Q: Do I need a custom domain?**  
A: No — platform HTTPS URLs like `*.vercel.app` or `*.onrender.com` pass the gate. Custom domains are portfolio polish for later. What matters is that the URL is HTTPS and actually loads at evaluation time. Evaluators care more that the app works and that you can explain the stack than about the vanity address.

**Q: What if I skipped optional sub-chapters?**  
A: That's fine as long as the required gates are honestly met. The risk isn't skipping; it's pretending you didn't. Document what you skipped and why in your learning log, so a mentor sees an honest engineer rather than a checkbox-filler. If a skipped bit turns out to be required, come back and do it — the bar-raiser will probe exactly what you claim to know.

**Q: Why does the live URL alone not prove I built the app?**  
A: Because anyone can fork a tutorial repo and deploy it. The URL proves a marketplace runs, but not that *you* understand it. That's why Chapter 99 also demands docs, a demo video, and honest learning logs — deliverables that make the work yours. "Necessary, but not sufficient" means the URL gets the mentor's attention, and everything else earns their trust.
