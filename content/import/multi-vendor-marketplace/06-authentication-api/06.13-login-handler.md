# 6.13 — Login handler

> **[Build]** · Chapter 06 — Authentication API · *`POST /auth/login` — compare hash; issue tokens*

**Why this step matters:** Login proves bcrypt compare works and gates unverified users — the daily path vendors and customers repeat. Tokens issued here feed every protected route and Chapter 7's browser session.

<BigWordAlert term="Credential verification" plainEnglish="Comparing submitted password to stored hash and rejecting login if either email or password is wrong." whyItMatters="FreshMarket returns the same error for bad email and bad password — prevents account enumeration." />

**Where the project is now:** Register works; login endpoint stub or incomplete.

**After this step:** `POST /api/auth/login` validates credentials with bcrypt, blocks unverified users, returns access and refresh tokens on success.

## Why login is the critical path

Every marketplace session starts here — vendors opening their dashboard, customers returning to cart. In production, login is among the **highest-traffic endpoints** and the first place attackers probe with credential stuffing.

| Production concern | What this handler must do |
|---|---|
| Password safety | Compare with bcrypt — never log or echo the plain password |
| Account state | Reject unverified users (403) — spam shops blocked at gate |
| Token issuance | Short access + revocable refresh — feeds Chapter 7 session |
| Enumeration | Same error message for wrong email vs wrong password (401) |
| Rate limiting | Optional stretch — document in README for portfolio |

Login is not "just another route." Chapter 8 ownership checks assume `req.user.id` came from a **verified** login. A broken login handler breaks every protected feature downstream.

## Request contract

**POST** `/api/auth/login`

**Body:**

| Field | Required |
|---|---|
| email | yes |
| password | yes |

## Success response — 200

```json
{
  "accessToken": "eyJhbG...",
  "refreshToken": "eyJhbG...",
  "user": {
    "id": "664a...",
    "email": "vendor-a@test.local",
    "role": "vendor",
    "displayName": "Vendor A"
  }
}
```

**user object:** No passwordHash. Include profile displayName from Profile lookup.

Token structure refined in 6.14–6.15 — login calls `issueTokens(user)` service helper.

## Error responses

| Status | Condition |
|---|---|
| 400 | missing email/password |
| 401 | wrong email or password |
| 403 | isVerified false |
| 500 | server error |

Use generic "Invalid credentials" for wrong email/password if preventing enumeration.

## Common mistakes

| Mistake | Symptom | Fix |
|---|---|---|
| Forgot `isVerified` check | Unverified users reach vendor dashboard | Return 403 before issuing tokens |
| Return `passwordHash` in user object | Security leak in Network tab | Select fields explicitly; use toJSON transform |
| Different error for "user not found" vs "wrong password" | Email enumeration attack | Same 401 message for both |
| Sync bcrypt in handler | Event loop blocks under load | Use `await bcrypt.compare` |
| Skip Profile lookup | Login works but UI shows blank name | Load displayName for Chapter 7 forms |
| Hardcode token expiry in handler | Drifts from config | Read `JWT_ACCESS_EXPIRY` from config.js |

## Service behaviour

1. Find User by email — include passwordHash (select +passwordHash if schema hides)  
2. If !user → 401  
3. `bcrypt.compare(password, user.passwordHash)` — if false → 401  
4. If !user.isVerified → 403 `{ message: "Email not verified" }`  
5. Load Profile for displayName  
6. Call token issuance (6.14 + 6.15)  
7. Return tokens + safe user object
