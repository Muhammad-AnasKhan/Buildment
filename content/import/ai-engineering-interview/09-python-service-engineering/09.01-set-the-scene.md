## The Monday the summaries stopped

Omar is a backend developer at Sahel Relief (a fictional NGO that runs food and water programmes). Field staff upload short reports from the places they work. Omar built a small service that sends each report to a model provider and returns a five-line summary for the programme managers.

For three months it worked. The provider answered in about 3 seconds. Managers opened the summaries page each morning, read the five lines and moved on. Nobody thought about the code between the page and the provider.

On a Monday morning the provider slowed down. Calls that took 3 seconds now took 40. Omar's code had no time limit on the call, so each request simply waited. The managers saw a spinner. Some refreshed the page, which sent a second request while the first one was still waiting.

Then something stranger happened. The page that lists reports, which never calls the model, stopped loading too. So did the health check. The hosting platform decided the service was dead and restarted it, which dropped every request in progress. The provider recovered after 20 minutes. Omar's service needed another 15 minutes and a manual restart before it worked again.

## Why one slow dependency stopped everything

Omar's service ran 8 workers, and each worker could handle one request at a time. Requests arrived about once every 2 seconds. When each one took 3 seconds, about 1 or 2 workers were busy on average. There was plenty of room.

The arithmetic is simple. If one request arrives every 2 seconds and each one takes 40 seconds, about 20 requests are in progress at the same time. Omar had 8 workers. Within 16 seconds every worker was stuck waiting on the provider, and every other request waited in a queue behind them. The fast page was not slow because of its own work. It was slow because there was nobody left to do it.

The refreshes made it worse. Each refresh added a new request but did not cancel the old one. And when the provider began to return "too many requests" errors, Omar's code retried at once, five times in a row, with no pause. Every failure turned into more load on a provider that was already struggling.

## What a prepared service does

None of this needed a smarter model. It needed ordinary service engineering, the kind the hands-on round tests:

- A **time limit** on every model call, so a slow provider costs 5 seconds, not 40.
- A **concurrency limit**, so at most a few model calls run at once and the rest of the service keeps its workers.
- **Retries** only for errors that may succeed next time, with a growing, random pause between them, and inside a total time budget.
- **Validation** at the door, so bad requests are rejected before they cost a model call.
- **Structured errors**, so the page can show "the summary service is busy, try again in a minute" instead of a spinner.
- **Async code**, so one process can wait on many network calls without a thread for each.

With these in place, the same Monday looks different. Summaries fail fast with a clear message for 20 minutes. The reports list and the health check keep working. When the provider recovers, the service recovers with it, with no restart.

## Why interviewers ask about this

Interviewers for AI engineering roles know that most of the code around a model is plain backend code. In the hands-on round you may be asked to write an endpoint that calls a model, then add a timeout, a retry and a limit. In the system design round a common probe is: "Your provider gets slow. Walk me through what your service does." A candidate who answers with numbers, like the 40 seconds and 8 workers above, stands out.
