```quiz
type: mcq
question: "Tamer's async FastAPI service calls a provider SDK that only has a sync complete() method, directly inside async def. One request alone takes 2 seconds. With 10 users at once, every request takes about 20 seconds. What is the best fix?"
options:
  - "Run the SDK call with asyncio.to_thread so the event loop stays free"
  - "Raise the semaphore limit so that more calls can run at the same time"
  - "Add a retry with backoff so slow calls get a second chance to finish"
  - "Wrap the SDK call in asyncio.timeout so slow calls are cancelled early"
correct: 0
explanations:
  - "Right. The sync call blocks the event loop, so requests run one after another. to_thread moves the wait to a worker thread, and the loop can serve other requests."
  - "The limit is not the problem. A blocking call stops the event loop, so no other call can run no matter how many slots exist."
  - "The calls are not failing, they are queued behind a blocked loop. Retries would add more blocked work."
  - "asyncio.timeout can only cancel code at an await. A sync call that blocks the loop cannot be interrupted this way."
```

```quiz
type: mcq
question: "Nour's request handler runs keyword search and vector search in parallel. The answer needs both results, so if one search fails, the other result is useless. Which tool fits best?"
options:
  - "asyncio.gather with return_exceptions=True, then check each result"
  - "A TaskGroup, so the other search is cancelled when one fails"
  - "A for loop that awaits the keyword search, then the vector search"
  - "asyncio.gather with default settings, so the error reaches the caller"
correct: 1
explanations:
  - "This works, but the other search always runs to the end, even when its result will be thrown away."
  - "Right. A TaskGroup cancels the remaining tasks when one fails, which is what you want when the parts are only useful together."
  - "This runs the searches one after another, so the request takes the sum of both times instead of the longer one."
  - "The error reaches the caller, but gather does not cancel the other search. It keeps running in the background."
```

```quiz
type: mcq
question: "Your service calls a model provider and gets back one of four errors. Which one should call_with_retries retry with backoff?"
options:
  - "400: the prompt has an invalid field"
  - "401: the API key was rejected"
  - "422: the request schema is invalid"
  - "503: service briefly unavailable"
correct: 3
explanations:
  - "A 400 means the request itself is wrong. It will fail the same way on every retry."
  - "A rejected key will be rejected again. This needs a person to fix the key, so alert instead of retrying."
  - "A schema error comes from the request, not from a passing problem. Retrying only repeats it."
  - "Right. A 503 usually means a passing server problem, so a few retries with backoff and jitter may succeed."
```

```quiz
type: mcq
question: "The provider answers a call with 429 and the header Retry-After: 30. The user's request has 5 seconds left in its time budget. What should the service do?"
options:
  - "Wait 30 seconds, then retry once, since the provider asked for it"
  - "Ignore Retry-After and retry with normal backoff inside the budget"
  - "Fail now with 503 and a Retry-After header for the caller"
  - "Retry at once, because a 429 means the call never reached the model"
correct: 2
explanations:
  - "Waiting 30 seconds breaks the 5 second budget. The user would be gone, or the request cut off, before the retry starts."
  - "The provider has said when it will accept calls again. Retrying earlier will most likely get another 429 and adds load."
  - "Right. The wait the provider asks for cannot fit in the budget, so fail fast and tell the caller when to come back."
  - "A 429 asks you to slow down. Retrying at once is exactly the behaviour that keeps a rate limit in place."
```
