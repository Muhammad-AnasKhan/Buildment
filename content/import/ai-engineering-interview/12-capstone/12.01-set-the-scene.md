## One system you can defend

In module 11 you practised answers with fictional projects. An interviewer will ask about yours. The strongest thing you can bring to a loop is a small system you built end to end, with an evaluation report that has real numbers, one failure you found and fixed, and a design you can explain under follow-up probes.

That is the capstone. You adapt the Bustan Books code from your build chapters to a new scenario, add what a reviewer expects from a portfolio project, measure it, and defend it in a recorded mock interview. It runs on your laptop, with no paid API key, because every test uses the fake model from chapter 3.5.

## Choose a scenario

All three scenarios are fictional. You write the documents yourself, 6 to 10 short files of 100 to 300 words each, in the style of real policies or runbooks. Do not copy real company documents, and do not include real names or personal data. Because you write them, you know which chunk answers which question.

**A. A policy assistant for Sanabel Microfinance (a fictional lender).** Loan officers ask about loan rules: who is eligible, grace periods, fees, late payments, which documents a borrower needs. The safe tool is `get_loan(loan_id)`, which reads a loan's status from a small in-memory table. The risky tool is `request_repayment_extension(loan_id, days)`, which a branch manager must approve.

**B. A support agent for Karmel Crafts (a fictional online shop for handmade goods).** Customers ask about shipping, returns, product care, payments and custom orders. The safe tool is `lookup_order(order_id)`. The risky tool is `request_refund(order_id, amount)`, which a staff member must approve. This scenario is closest to Bustan Books, so it is the fastest to adapt. If you choose it, spend the saved time on at least two should-haves.

**C. A knowledge bot for Nakhla Systems (a fictional remote software team of 15).** Engineers ask about deploy rules, the on-call rota, the incident process, access and past architecture decisions. The safe tool is `get_service_status(service)`. The risky tool is `restart_service(service)`, which the on-call engineer must approve.

Choose the scenario you can write documents for most easily. It does not change your grade.

## Must-haves

Your mentor checks each of these. A missing must-have means the capstone comes back for revision.

1. **Retrieval with citations.** Answers cite chunk ids, and the service says it does not know when no chunk passes the score threshold.
2. **One tool call that needs human approval.** The risky tool pauses the LangGraph graph with `interrupt()` and runs only after approval, as in chapter 7.6.
3. **A FastAPI endpoint** with Pydantic validation, retries with backoff, a timeout, structured errors and a concurrency limit, as in chapter 9.6.
4. **A golden set of at least 20 questions,** each labelled with the chunk ids that answer it.
5. **An evaluation report** with recall@k, precision@k, MRR and a faithfulness check, and one failure you found, fixed and re-measured.
6. **A regression eval that runs as a test** and fails when quality drops below a threshold.
7. **Structured logs or traces:** one JSON log line per request, with a request id, latency, retrieved ids and outcome, and no raw user text.
8. **A README** that tells a stranger how to install, run the tests, run the eval and start the service.
9. **A one-page design note:** the problem, the design, the main trade-off, the risks and what you would change.
10. **Tests that pass with no API key,** using the fake model.

## Should-haves

These lift a capstone from "meets" to "strong". Choose two or three that fit your scenario: hybrid search with BM25 and rank fusion; query rewriting for vocabulary your users really type; a small router that skips retrieval for greetings; three or more out-of-scope questions in the golden set; a judge-model faithfulness check on a sample, compared with your own labels; HTTP endpoints for the approval flow; a cost and latency budget table; a container build; or a CI workflow that runs `pytest` on every push.

## Out of scope

You do not need, and should not spend time on: a public deployed URL, user authentication, object storage, a web frontend, training or fine-tuning a model, or GPU work. A real or local model is optional and must sit behind an adapter, so the tests still use the fake model. Deployment and authentication are design topics here: describe them in the design note, as in gate 10.7.

## How your mentor reviews it

Your mentor has about 45 minutes for your capstone: 5 minutes to clone it and run the tests from your README, 10 minutes for the report and design note, 10 minutes reading the service and the agent, 10 minutes for your recording, and 10 minutes to write feedback with one to three follow-up probes. You answer those probes by resubmitting.

| Area | Meets | Strong |
|---|---|---|
| Design | All must-haves; the note explains the request path and the approval point | Choices are justified with numbers; alternatives are named and rejected for a reason |
| Evaluation | 20+ golden questions; four metrics reported; regression test fails on a drop | One failure is traced to a cause, fixed and re-measured, with any regression it caused |
| Engineering | Tests pass from a clean clone with no key; errors are structured | Clear interfaces; failure paths are tested; one should-have is fully done |
| Safety | The risky tool cannot run without approval; logs hold no raw user text | Injection is considered in a test or the note; tool arguments are validated |
| Communication | README works; the recording covers the five parts in about five minutes | Answers lead with a decision and a number; limits are stated plainly |
