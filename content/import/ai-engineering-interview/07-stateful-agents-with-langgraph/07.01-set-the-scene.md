## The loop that worked on Friday

Omar is a junior engineer at Bustan Books (a fictional online bookshop). In module 6 he built the support agent as a plain Python loop. The loop asks the model what to do, calls a tool, adds the result to a list of messages and goes round again. On Friday the demo went well. A customer asked "Where is order 1042?" and the agent looked it up and answered in two steps.

On Monday the shop's manager, Huda, added one rule. The agent must never pay a refund alone. A person must approve it first. Omar added a line to his loop: when the model asks for `issue_refund`, stop and wait for Huda.

That one line caused three problems in the first week.

**Waiting.** Huda approves refunds in batches, about twice a day. A request could wait four or five hours. Omar's loop kept the messages in memory, so the process had to stay alive the whole time. When the server restarted after a power cut, every waiting refund was lost. Customers had to ask again, and two of them asked in angry emails.

**Testing.** Omar wanted a test that says "the agent pauses before paying, and pays once after approval". His loop was one long function. To test the pause he had to mock the model, the clock and the input function at the same time. The test was 80 lines long and broke whenever he changed the prompt.

**Seeing what happened.** A customer said they were refunded twice. Omar had no record of which step ran, what the state was before the refund, or who approved it. He could only read the log lines he had remembered to print.

## What a graph changes

None of these problems is about the model. They are about state: where the agent's progress lives, who can change it, and whether it survives a restart. This module teaches you to build the agent as a graph with LangGraph.

Each step is a small function called a node. The data the steps share is a typed object called the state. After each step, the framework saves a copy of the state, so a run can stop, wait for days and then continue from the exact point where it stopped.

In this module you will learn four ideas and then build them.

- How a node's output is merged into the shared state, and why some keys need a rule for merging (a reducer).
- How saved state gives you memory inside one conversation, and how a separate store gives memory across conversations.
- How to pause before a risky tool call, show a person the facts, and resume with their decision without paying twice.
- When several cooperating agents are worth their cost, and when one agent with good tools is better.

## Why interviewers ask about this

Agent questions in interviews have moved past "what is ReAct". A hiring manager wants to know whether your agent can be trusted with real actions. Typical questions are: "What happens if the server restarts while the agent waits for approval?", "How do you stop a refund from being paid twice?" and "How would you test the approval step?". Answer with a state design, a checkpoint and a test. Then you sound like someone who has shipped an agent, not only demoed one.

The build chapter, 7.6, gives you that answer in code. You will write a small Bustan Books agent with two tools, `lookup_order` and `issue_refund`, where the graph pauses before any refund. Nine tests prove it pauses, pays once on approval, pays nothing on rejection, and never pays twice. It runs on your laptop with no model and no API key.
