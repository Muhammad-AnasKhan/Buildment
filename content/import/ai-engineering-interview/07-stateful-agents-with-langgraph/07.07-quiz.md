```quiz
type: mcq
question: "A fictional NGO's report agent runs three extractor nodes in parallel. Each returns a dictionary of figures under the key figures, for example budget from one node and staff count from another. The fields never overlap. What should figures be declared with?"
options:
  - "No reducer, because each node writes different fields of the dictionary"
  - "A merge reducer that combines dictionaries, such as {**current, **new}"
  - "operator.add, because it joins any two values coming from parallel nodes"
  - "add_messages, because it can replace an entry that has the same id"
correct: 1
explanations:
  - "LangGraph sees one key, not its fields. Three writers to a key without a reducer in one superstep raise InvalidUpdateError."
  - "Right. A merge reducer folds each node's dictionary into the current one, so all three sets of figures are kept."
  - "operator.add works for lists, but Python cannot add two dictionaries with +, so the merge would fail with a TypeError."
  - "add_messages is built for lists of chat messages with ids, not for a dictionary of figures."
```

```quiz
type: mcq
question: "A support agent uses the customer's email address as its thread_id for every conversation, forever. A customer has chatted 40 times over a year. What problem does this design cause?"
options:
  - "Each new message starts with an empty state, so nothing is ever remembered"
  - "The checkpointer cannot store more than one conversation for each customer"
  - "Thread ids must be random values, so an email address raises an error"
  - "All 40 chats pile into one thread, so history and token cost keep growing"
correct: 3
explanations:
  - "The opposite happens. The same thread id loads the same saved state every time, so everything is remembered."
  - "A checkpointer stores any number of threads. The problem is that this design puts everything in one of them."
  - "A thread id is any string you choose. An email works technically; it is a poor choice for design and privacy reasons."
  - "Right. One endless thread grows every year and lets old facts leak into new chats. Use one thread per conversation and a store for lasting facts."
```

```quiz
type: mcq
question: "A node runs log_request(), which inserts a row into a database, and then calls interrupt(payload). The graph has a checkpointer. A reviewer later resumes it with an approval. What happens to the database row?"
options:
  - "It is written twice, because the node runs again from the top on resume"
  - "It is written once, because LangGraph resumes at the line after interrupt()"
  - "It is written once, because the checkpointer records the database write"
  - "It is never written, because interrupt() undoes the work done in the node"
correct: 0
explanations:
  - "Right. On resume LangGraph calls the node again from its first line, so every side effect before interrupt() repeats."
  - "LangGraph does not freeze the function mid-way. It re-runs the node, and interrupt() then returns the resume value."
  - "The checkpointer saves graph state, not your database calls. It cannot stop your code from inserting a second row."
  - "interrupt() undoes nothing. The insert ran before the pause and is in the database."
```

```quiz
type: mcq
question: "A refund approval screen shows only 'Approve tool call issue_refund? yes / no'. Reviewers approve 99 percent of requests in under 2 seconds. What is the best change?"
options:
  - "Remove the approval step, since reviewers approve almost every request"
  - "Add a second reviewer for every refund, so two people must click yes"
  - "Show the amount, reason and order evidence, and record who decided"
  - "Approve automatically after 2 seconds, since that is what reviewers take"
correct: 2
explanations:
  - "A 99 percent approval rate with no facts on screen suggests rubber-stamping, not safe requests. Removing the check hides the problem."
  - "Two people who see no facts are no better than one. It doubles the cost without improving the decision."
  - "Right. A reviewer can only judge what they can see, and a recorded decision with a name makes the step accountable."
  - "This turns the approval into a delay. No person would actually review anything."
```

```quiz
type: mcq
question: "Bustan Books has one agent with 8 tools, including issue_refund. It also summarises book reviews that customers upload. The team worries a review could trick the agent into a refund. Which change gives a clear, named benefit?"
options:
  - "Add a supervisor that routes every request, so one agent controls the rest"
  - "Move issue_refund to a billing agent that never reads uploaded reviews"
  - "Split into one agent per tool, so each prompt is short and focused"
  - "Use handoffs between two identical agents, so one checks the other"
correct: 1
explanations:
  - "A supervisor adds routing calls, but the agent reading reviews could still hold the refund tool. It does not separate the risk."
  - "Right. The agent that reads untrusted text no longer holds the risky tool. The refund keeps its approval step as a second layer."
  - "Eight agents add many calls and hand-offs, and nothing says which one reads untrusted text or holds the refund tool."
  - "Two identical agents read the same text with the same tools, so a trick that fools one can fool both."
```
