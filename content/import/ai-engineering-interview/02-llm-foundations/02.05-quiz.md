```quiz
type: mcq
question: "A chatbot sends about 1,500 input tokens and gets about 300 output tokens per request, 5,000 requests a day. With example prices of $2 per million input tokens and $6 per million output tokens, what does it cost over a 30-day month?"
options:
  - "About $24 a month"
  - "About $450 a month"
  - "About $720 a month"
  - "About $7,200 a month"
correct: 2
explanations:
  - "$24 is the cost of one day, not a month. Multiply by 30."
  - "$450 counts only the input tokens. The 300 output tokens at $6 per million add $270 a month."
  - "Right. Each request costs 1,500 x $2 plus 300 x $6, divided by a million, which is $0.0048. Times 5,000 a day is $24, and times 30 days is $720."
  - "$7,200 is ten times too high. Check the division by one million in the price."
```

```quiz
type: mcq
question: "Users of a study assistant say they stare at a blank screen for about 6 seconds. The time to first token is 0.7 seconds, and answers are about 400 tokens written at 80 tokens a second. Which change most improves how fast it feels, without changing the answer?"
options:
  - "Stream the answer so text appears after about 0.7 seconds"
  - "Cut the system prompt by 100 tokens to speed up the first token"
  - "Lower the temperature so the model writes the answer faster"
  - "Retrieve two more chunks so the model needs less time to think"
correct: 0
explanations:
  - "Right. Most of the wait is the 5 seconds of writing. Streaming shows text from the first token, so the user starts reading after 0.7 seconds, although the total time is the same."
  - "100 fewer input tokens saves very little time before the first token, and the 5 seconds of writing are unchanged."
  - "Temperature changes which tokens are picked, not how fast they are written."
  - "More chunks add input tokens, which makes the wait before the first token longer, not shorter."
```

```quiz
type: mcq
question: "A policy assistant sends 12 retrieved chunks with every question. On a test set, many answers are wrong even when the right chunk was retrieved, and in those cases it was usually in positions 5 to 8 of the prompt. What is the best first experiment?"
options:
  - "Switch to a model with a larger context window and send 20 chunks"
  - "Raise the temperature so the model considers more of the chunks"
  - "Ask users to write longer, more detailed questions to the assistant"
  - "Send fewer, better-ranked chunks and re-run the same test set"
correct: 3
explanations:
  - "A bigger window does not help when the right chunk is already inside it. More chunks bury it deeper and raise cost and latency."
  - "A higher temperature adds randomness. It does not make the model read the middle of the prompt more carefully."
  - "The problem appears even when retrieval found the right chunk, so the questions are not the cause."
  - "Right. The pattern suggests the model uses chunks in the middle less reliably. Fewer, better-ranked chunks make the right one easier to use, and the same test set shows whether it worked."
```

```quiz
type: mcq
question: "An internal helpdesk bot uses only embedding search. Questions like 'What does error E-4031 mean?' often return general troubleshooting pages instead of the page about E-4031. What is the most likely fix?"
options:
  - "Increase the embedding size from 384 to 1,024 dimensions"
  - "Add keyword search and merge its results with vector results"
  - "Lower the similarity threshold so more pages are returned"
  - "Re-embed all pages with the same model to refresh the vectors"
correct: 1
explanations:
  - "Error codes carry little general meaning for any embedding model, so a bigger vector is unlikely to fix this, and it costs more storage."
  - "Right. Keyword search matches the exact string E-4031, which embeddings handle poorly. Merging both result lists keeps the meaning-based matches too."
  - "A lower threshold returns more pages, but the general pages still outrank the exact one."
  - "The same model gives the same vectors, so nothing changes."
```

```quiz
type: mcq
question: "A step reads customer emails and extracts the order number and refund amount as JSON, with temperature set to 1.0. Running the same email twice sometimes gives different amounts. What should the team change first?"
options:
  - "Keep 1.0 and run each email three times, using the most common answer"
  - "Remove the schema, so the model has more freedom in how it answers"
  - "Lower the temperature to near 0 and keep validating every reply"
  - "Switch to a bigger embedding model to read the email text better"
correct: 2
explanations:
  - "Voting can reduce variation, but it triples the cost of every email and keeps the cause. Fix the setting first."
  - "Without a schema, bad values reach the refund code unchecked. Extraction needs more checking, not less."
  - "Right. Extraction should give the same output for the same input, so a temperature near 0 is the first fix, and validation still guards the shape."
  - "Embeddings are used for search, not for writing the extraction, so this does not affect the amounts."
```
