```quiz
type: mcq
question: "Lina is about to test three prompt versions for the Wadi Labs runbook bot and log each test as an MLflow run. Which parameters make the three runs fair to compare next month?"
options:
  - "Prompt version, dated model version, golden set version and top_k"
  - "The prompt text only, since the prompt is the one thing that changes"
  - "Run start time, run duration and the name of the person who ran it"
  - "The final recall@5 and MRR values, written into the name of each run"
correct: 0
explanations:
  - "Right. These are the inputs that can change a score. With them logged, Lina can check that only the prompt differs between runs."
  - "Other settings can change too, such as the model behind an alias or the golden set. Without them, a later reader cannot tell what really differed."
  - "These help with cost and ownership, but they do not show whether the runs used the same model and questions."
  - "Results belong in metrics, and they say nothing about the settings that produced them."
```

```quiz
type: mcq
question: "A rare bug in a tool call fails about 1 request in 1,000. Traces are kept with 10% head sampling, so engineers almost never find a failed trace. Which change helps most?"
options:
  - "Raise head sampling to 20% so twice as many traces are kept"
  - "Keep every error trace with tail sampling, plus 5% of the rest"
  - "Log the full prompt in every span so each trace has more detail"
  - "Lower head sampling to 5% so storage costs drop for the team"
correct: 1
explanations:
  - "This doubles storage but still drops 80% of the failed traces, because the choice is made before anyone knows the request will fail."
  - "Right. Tail sampling decides after the request ends, so every failed request is kept, and normal traffic is still sampled cheaply."
  - "More detail does not help if the failed trace was never kept. It also adds personal data and storage cost."
  - "This keeps even fewer failed traces, which makes the problem worse."
```

```quiz
type: mcq
question: "Huda's internal tool at Najm Microfinance gets about 30 questions a day, only in office hours. Answers are short, under 5 seconds, and need no GPU. Users have said a 2 second cold start is fine. The team runs no cluster. Which target fits best?"
options:
  - "A managed Kubernetes cluster with autoscaling"
  - "A container service with three warm copies all day"
  - "A GPU machine pool, so that answers come back faster"
  - "Serverless functions that scale to zero when idle"
correct: 3
explanations:
  - "A cluster costs money when idle and needs an owner. Neither fits 30 short questions a day on a team with no cluster."
  - "Three warm copies cost money all day for a tool that is idle most of the time, and users already accept a short cold start."
  - "The tool calls a hosted model and needs no GPU. A GPU pool would add cost without making the answers faster."
  - "Right. Traffic is low and short, cold starts are acceptable, and scaling to zero makes the idle hours almost free."
```

```quiz
type: mcq
question: "Reem sets up a daily online evaluation on a 5% sample of Sahel Relief's assistant answers. Which check needs an LLM judge rather than a few lines of plain code?"
options:
  - "Whether the answer cites at least one chunk id"
  - "Whether the cited ids are among the retrieved ids"
  - "Whether the claims are backed by the retrieved text"
  - "Whether the reply is the standard 'I don't know' text"
correct: 2
explanations:
  - "A regular expression that looks for ids in brackets can check this. No judge is needed."
  - "Code can compare the cited ids with the ids retrieval returned. No judge is needed."
  - "Right. Deciding whether a sentence is supported by a passage needs language understanding, which is what an LLM judge provides."
  - "A string comparison with the fixed 'I don't know' message is enough here."
```

```quiz
type: mcq
question: "One hour after a prompt release, the cost per hour alert fires at 4 times the 7 day average for that hour. Error counts look normal. What should the on-call engineer look at first in the traces?"
options:
  - "Tokens and tool calls per request, before and after the release"
  - "The uptime of each copy of the service over the past seven days"
  - "The health check results, since restarts can raise the hourly bill"
  - "The cache keys, since a cache hit costs more than a full model call"
correct: 0
explanations:
  - "Right. Cost per request comes from tokens and the number of model and tool calls. Comparing them before and after the release shows what the new prompt changed."
  - "Uptime does not explain a cost jump, and the service is clearly up because it is answering."
  - "Health checks do not call the model in a well built service, so restarts do not explain a fourfold model bill."
  - "A cache hit skips the model, so it costs less, not more. The cache is not where to look first."
```
