## A correct answer that helps nobody

Reem works on the support assistant for Bustan Books (a fictional online bookshop). It is the RAG assistant you built in module 3: it answers from three policy documents about shipping, returns and accounts, and it cites its sources.

On Monday a customer writes: "Where is my order 1187? I ordered it ten days ago." The assistant replies: "Standard shipping takes 5 to 8 working days [shipping#0]." Every word is true, and the citation is right. The customer is still angry, because they asked about their order, not about the policy. Ten days is already past the policy's limit, and the assistant has no way to know what happened to this parcel.

The policy documents do not contain order 1187. No golden set, chunk size or reranker can fix that. The facts the customer needs live in another system: the order database. To answer, the assistant must ask that system, read the reply, and then write its answer.

## From reading to acting

Reem's team gives the model a tool: a function called `lookup_order` that takes an order id and returns its status. The model does not run the function itself. It writes a structured request, such as "call `lookup_order` with order id 1187". Your code checks that request, runs the function, and hands the result back to the model. The model then writes the answer: "Your order 1187 left our warehouse 6 days ago, and tracking has not changed for 4 days."

That loop is small, but it changes what the system is. Before, the model could only write text. Now it can make things happen in the world, one tool at a time. A few weeks later the support lead asks for a second tool, `issue_refund`, so the assistant can refund a damaged book without a person typing it in. Reading an order is harmless. Sending money back is not.

## What can go wrong

Once a model can call tools, new failures appear, and none of them looked like problems in a RAG system.

The model might call `lookup_order` with "one thousand one hundred eighty-seven" instead of "1187". It might call it again and again when the order system is slow, spending money and time on every call. It might decide on its own that a customer deserves a refund of the full order, when the policy only covers the damaged book. Each of these is a design question with a clear answer: validate the arguments, limit the loop, and ask a person before risky actions.

Then there is a bigger question. Does this task need an agent at all? "Where is my order?" always follows the same steps: find the order id, look it up, explain the status. A fixed piece of code can do that with one model call, faster and more predictably than an agent that decides each step for itself.

## Why interviewers ask about agents

Agentic AI roles exist because companies want models that do work, not only answer questions. So interviewers probe two things. First, the mechanics: how does a model call a tool, and what happens when the arguments are wrong? Second, judgment: how do you stop the loop, which actions need a person, and when is an agent the wrong design?

The second set matters more for senior roles. Many candidates can describe an agent. Fewer can explain why they did not build one, or what their agent does when a tool fails for the fifth time. By the end of this module you can answer both.
