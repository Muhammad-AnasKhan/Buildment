## Module 6 checklist

- [ ] I can describe a tool with a name, a description and a JSON Schema for its arguments
- [ ] I can explain why an invalid or failed tool call is returned to the model as an observation, not raised as a crash
- [ ] I can tell a read tool from a write tool, and explain how an idempotency key makes a write safe to retry
- [ ] I can trace a ReAct loop turn by turn and name the five ways it should end
- [ ] I can choose between a fixed workflow, a router, an orchestrator and an agent, and say when not to use an agent
- [ ] I answered the practice questions in chapters 6.2, 6.3 and 6.4 aloud, and finished the quiz in 6.5
- [ ] I submitted the agent design below

## Learning log

1. **Your tools:** Think of your capstone, or the Bustan Books assistant. Which of its tools only read, and which write? Which write tools need a person's approval, and why those?
2. **Your errors:** Write one error message a tool could return that helps the model fix its call, and one that does not. What makes the difference?
3. **Your limits:** What turn limit and budget would you set for your agent? What data would you collect in the first week to check them?
4. **Your design choice:** Is your capstone task better served by a workflow, a router or an agent? Name the one fact about the task that decides it.

## Your interview answer

In a system design round, the interviewer may say: "Design an agent for this task." A weak answer lists tools and stops. A strong answer also says how each tool is checked, how the loop ends, and where the agent must not act on its own. It may even say that part of the task should not be an agent at all.

A good shape has five parts. First, the task and why it needs tools: what facts or actions live outside the documents. Second, the tools, each marked read or write, with the key fields of its schema. Add one rule your code checks that the schema cannot, such as a refund never above the order total. Third, how errors come back: specific messages as observations, and a retry cap. Fourth, the stop rules with numbers: a turn limit, a repeated-call check, a budget in tokens or seconds, and what the user sees when a limit hits. Fifth, when the agent must stop and ask, and which parts of the task you would build as a fixed workflow instead.

Numbers make the design believable. You do not need real traffic. Say what you would assume, for example "most runs should end in 3 or 4 turns, so I cap at 6", and say what you would measure to check the assumption. The interviewer cares more about the reasoning than the exact value.

Watch for two common gaps. The first is approval only in the prompt: "the model is told to ask first" is not a control. Say that the code pauses before every write tool, whatever the model decides. The second is a stop with no reply: when a limit hits, the user must still get a message and a path to a person.

Before you submit, read your design once as the interviewer would. Could a teammate build each tool from your description? Could they test every stop rule with one failing case, such as a tool that always times out? If the answer is no, add the missing field, number or rule. Your mentor will look for exactly these gaps.

Use your capstone scenario if you have chosen one. If not, design the Bustan Books support agent with `lookup_order` and `issue_refund`. You may write your answer, record it, or both. The written answer is required; the recording is optional.
