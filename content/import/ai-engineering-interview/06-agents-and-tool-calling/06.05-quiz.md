```quiz
type: mcq
question: "A Bustan Books customer gives order number 9999. The model calls lookup_order with '9999', which passes validation, but the order system replies that no such order exists. What should your code do with that result?"
options:
  - "Raise an exception, so that the request ends with a clear 500 error"
  - "Retry the same call until the order system finds the missing order"
  - "Return the error to the model as the observation for that tool call"
  - "Remove lookup_order from the tool list so the model stops calling it"
correct: 2
explanations:
  - "A crash gives the customer 'Something went wrong' and gives the model no chance to explain or ask for the right number."
  - "The order does not exist, so the same call will fail every time. Retrying wastes turns and money."
  - "Right. The model reads 'no order 9999' and can tell the customer or ask them to check the number."
  - "The tool works; only this order id is wrong. Removing it would break every later order question in the conversation."
```

```quiz
type: mcq
question: "Omar's support agent has four tools. Which one should pause for a person's approval before it runs?"
options:
  - "issue_refund, because it moves money and is hard to undo once sent"
  - "lookup_order, because it reads order details such as the address"
  - "search_policy, because it can return a document that is out of date"
  - "get_tracking, because the courier's system is often slow to respond"
correct: 0
explanations:
  - "Right. A refund is a write action with a real cost. It belongs at a fixed approval point, enforced in code."
  - "Reading an order needs access control, so the agent sees only this customer's orders. It does not need a person to approve each read."
  - "Stale documents are a retrieval and content problem. Approving every search would not fix it, and it is a read tool."
  - "A slow read tool needs a timeout and a budget, not an approval step."
```

```quiz
type: mcq
question: "Reem's agent has a turn limit of 20. In the logs, 95 percent of runs finish within 3 turns, but some runs reach 20 turns by calling lookup_order with the same order id, getting the same timeout each time. What is the best change?"
options:
  - "Raise the turn limit to 40, so that slow runs have time to finish"
  - "Remove the turn limit and trust the model to stop when it should"
  - "Add a sentence to the system prompt asking the model to stop early"
  - "Add a repeated-call check, and lower the turn limit to about 6"
correct: 3
explanations:
  - "The repeated calls get the same timeout, so more turns only add cost. Nothing new is learned on turn 21."
  - "The logs show the model does not stop by itself in this case. Without a limit, one run could go on until someone kills it."
  - "A prompt instruction is a request, not a rule. The model already ignored the repeated failures."
  - "Right. Identical calls with identical results are caught at the third call, and a limit near 6 still leaves room above the usual 3 turns."
```

```quiz
type: mcq
question: "Tamer's router labels each message and sends it to a fixed path. Customers complain that refund requests get a polite policy answer and no refund. What should Tamer do first?"
options:
  - "Replace the router with one agent that has every support tool"
  - "Measure the router's accuracy per label on labelled messages"
  - "Add more policy documents so the policy answers are complete"
  - "Lower the temperature of the model that writes policy answers"
correct: 1
explanations:
  - "That gives up the cost and testing benefits of the router before the cause is known. The problem is likely one label."
  - "Right. The symptom points at misrouting. A golden set of labelled messages shows how often refunds are labelled as policy questions, and which wording causes it."
  - "The policy answers are not the problem. The refund requests should never reach the policy path."
  - "Temperature changes how the policy path writes, not which path a message takes."
```

```quiz
type: mcq
question: "A customer writes 'Please refund my order, the cover was torn.' The order system shows three orders from this customer in the last week. What should the agent do next?"
options:
  - "Refund the most expensive order, since it is the biggest risk"
  - "Refund all three orders, and let support correct it afterwards"
  - "Ask the customer which of the three orders had the torn cover"
  - "Refund the newest order, because it most likely arrived last"
correct: 2
explanations:
  - "The price says nothing about which book was damaged. A wrong refund costs money and confuses the customer."
  - "Two of the three refunds are probably wrong, and refunds are hard to undo. This is the kind of action stop rules exist to prevent."
  - "Right. A required fact is missing, so the agent should stop and ask instead of guessing before a write action."
  - "This is a guess. The damaged order could be any of the three, so the agent should not act on it."
```
