```quiz
type: mcq
question: "Huda changes Najm's chunking rule from fixed 300-word chunks to chunks split by section heading. She deploys the new code. What must happen before loan officers see better answers?"
options:
  - "Restart the API so the query path loads the new chunking code"
  - "Raise k so the query path returns more of the new chunks"
  - "Re-run the indexing path so every document is chunked again"
  - "Clear the model's cache so it forgets the old chunk text"
correct: 2
explanations:
  - "Chunking runs on the indexing path. Restarting the query side does not change the chunks already stored."
  - "The store still holds only the old chunks, so a larger k returns more old chunks."
  - "Right. Chunks are made and stored when documents are indexed. Until every document is chunked and embedded again, search still sees the old chunks."
  - "The model does not keep chunk text between questions. The old chunks live in the vector store, not in the model."
```

```quiz
type: mcq
question: "A clinic network wants a policy assistant. Staff often mix French and Arabic in one question, and questions may contain patient names that must not leave the clinic's network. Which embedding choice fits best?"
options:
  - "A multilingual model run locally, tested on real mixed questions"
  - "A hosted model with the largest dimension the budget can pay for"
  - "A hosted English model, with each question machine-translated"
  - "The model that ranks first on a public English benchmark list"
correct: 0
explanations:
  - "Right. It handles mixed languages, keeps patient names inside the network, and is checked on the questions staff really ask."
  - "A hosted model sends patient names outside the network, and a larger dimension says nothing about French and Arabic support."
  - "The question and its patient names still leave the network, and translation errors on mixed sentences add a new failure point."
  - "An English benchmark does not predict quality on mixed French and Arabic questions, and it says nothing about where data goes."
```

```quiz
type: mcq
question: "A contract assistant uses fixed 200-word chunks with no overlap. Answers often miss conditions such as 'unless the client pays within 10 days', which come right after the rule they change. What is the best first change?"
options:
  - "Increase k from 3 to 8 so more neighbouring chunks reach the model"
  - "Switch to a larger embedding model with more dimensions per vector"
  - "Cut the chunk size to 50 words so that each chunk matches precisely"
  - "Split by clause and add overlap so conditions stay with their rule"
correct: 3
explanations:
  - "A larger k may sometimes pull in the next chunk, but not reliably, and it adds unrelated text and tokens to every prompt."
  - "The embedding is not the problem. The rule and its condition are in different chunks, so no embedding can match them together."
  - "Smaller chunks cut rules apart even more often, so more conditions get separated from their rule."
  - "Right. Splitting at clause boundaries keeps a rule whole, and overlap keeps a condition that crosses a boundary in at least one chunk."
```

```quiz
type: mcq
question: "Najm's assistant takes the top 10 chunks for a question, then keeps only chunks tagged with the officer's branch. One small branch has 2% of all chunks, and its officers often get 'I don't know'. What is the most likely cause?"
options:
  - "The embedding model cannot read branch names inside chunk text"
  - "The filter drops most of the top 10, so almost nothing is left"
  - "The min_score threshold is set too low for short branch policies"
  - "The vector index was never trained on the branch metadata field"
correct: 1
explanations:
  - "Branch tags are metadata used by the filter. The embedding does not need to read them for the filter to work."
  - "Right. This is post-filtering. With 2% of chunks matching, the top 10 holds about 0.2 matching chunks on average, so the answer is starved. Filtering before the search fixes it."
  - "A threshold that is too low would let more chunks through, not fewer. The empty results come from the filter."
  - "Vector indexes are built from vectors, not metadata fields. The order of filter and search is the problem."
```

```quiz
type: mcq
question: "A team has 40,000 chunks and a retrieval budget of 200 ms. Exact search takes 12 ms on their server. A teammate wants to add an HNSW index now. What is the best response?"
options:
  - "Add HNSW now, because approximate search is always faster to run"
  - "Add HNSW now, and raise ef_search until its recall reaches 1.0"
  - "Keep exact search, which fits the budget and misses nothing"
  - "Move the vectors to a hosted vector database before they grow"
correct: 2
explanations:
  - "Speed is not the problem at 12 ms against a 200 ms budget, and the index adds recall loss, memory and tuning."
  - "Pushing an approximate index to perfect recall gives up its speed advantage and still adds memory and build time, to solve a problem the team does not have."
  - "Right. Exact search meets the budget with room to spare and always returns the true nearest vectors. Add an index when measurements show exact search is too slow."
  - "A hosted service adds monthly cost and moves data outside the team's network, for a collection that is small and fast today."
```
