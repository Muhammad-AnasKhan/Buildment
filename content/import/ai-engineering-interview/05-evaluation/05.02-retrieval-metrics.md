## The model cannot use what it never sees

Omar maintains the report search for Sahel Relief (a fictional NGO). A field officer asks: "How many families got food parcels in March?" The answer is spread over four chunks: weekly distribution logs in three field reports. The retriever returns ten chunks, ranked by similarity, and the top three go into the prompt.

The model adds up the families in the chunks it sees and gives a total that is far too low. Omar reads the prompt and finds the cause: only two of the four useful chunks were in the top three. The other two were at ranks 6 and 9, so the model never saw them.

No prompt change fixes this. If the right chunk is not retrieved, the model cannot use it. So before you judge answers, you measure retrieval. By the end of this chapter you can compute three retrieval metrics by hand, say how they change with k, and pick the one that matches a decision.

## Labels first, then numbers

Every retrieval metric needs the same input: for each test question, which chunks are relevant. A person decides this once, by reading the documents. A fixed collection of such questions with labels is called a <GlossaryTerm term="golden set" definition="A fixed list of test questions, each with the chunks or answers that a correct system should find. You run it again after every change." />.

Then you run each question through the retriever and compare its ranked list with the labels. The diagram shows the flow for one question and for the whole set.

```mermaid
flowchart LR
  Q[Golden question] --> R[Retriever]
  R --> L[Ranked list of ids]
  G[Relevant ids label] --> C[Compare top k]
  L --> C
  C --> M[Recall, precision, RR]
  M --> A[Mean over all questions]
```

Notice that the labels and the ranked list meet in one place: the comparison of the top k. Every metric in this chapter is a different way of counting that overlap. Change k, and every number can change.

<BigWordAlert term="Recall@k" plainEnglish="Of all the relevant chunks for a question, the share that appear in the top k results." whyItMatters="In RAG the model can only use what is retrieved, so low recall means missing facts in the answer, however good the model is." />

## Three metrics on one ranked list

Use Omar's list. The retriever returned 10 chunks. The relevant ones sit at ranks 2, 3, 6 and 9. There are 4 relevant chunks in total.

**Recall@k** is the number of relevant chunks in the top k, divided by all relevant chunks (here, 4). It answers: did we find everything?

**<GlossaryTerm term="precision@k" definition="Of the top k results, the share that are relevant. It shows how much of the context you send is useful." />** is the number of relevant chunks in the top k, divided by k. It answers: how much of what we send is useful?

**<GlossaryTerm term="reciprocal rank" definition="1 divided by the rank of the first relevant result, or 0 if there is no relevant result. A first hit at rank 2 gives 0.5." />** is 1 divided by the rank of the first relevant chunk. If nothing relevant appears, it is 0. It answers: how soon does the first useful chunk appear?

Now count, one k at a time.

| k | Recall@k | Precision@k |
|---|---|---|
| 1 | 0 / 4 = 0.00 | 0 / 1 = 0.00 |
| 3 | 2 / 4 = 0.50 | 2 / 3 = 0.67 |
| 5 | 2 / 4 = 0.50 | 2 / 5 = 0.40 |
| 10 | 4 / 4 = 1.00 | 4 / 10 = 0.40 |

At k = 1 the top chunk is not relevant, so both numbers are 0. At k = 3 the chunks at ranks 2 and 3 are inside, so recall is 0.50 and precision is 0.67. At k = 5 nothing new arrives (rank 6 is just outside), so recall stays at 0.50 while precision falls to 0.40. At k = 10 all four are inside, so recall reaches 1.00, but six of the ten slots are noise.

The reciprocal rank is 1 / 2 = 0.5, because the first relevant chunk is at rank 2. If you only look at the top k, it is 0 at k = 1 and 0.5 for every k of 2 or more. It never changes again, however many relevant chunks arrive later.

## From one question to a golden set

One question tells you little. You compute each metric per question, then take the mean over the golden set. For reciprocal rank the mean has its own name: <GlossaryTerm term="mean reciprocal rank (MRR)" definition="The average of the reciprocal ranks over all test questions. 1.0 means the first result was always relevant." />.

Say Omar has three questions. The first is the one above, with the first relevant chunk at rank 2, so 0.5. In the second, the first chunk is relevant: 1 / 1 = 1.0. In the third, the first relevant chunk is at rank 4: 1 / 4 = 0.25. MRR is (0.5 + 1.0 + 0.25) / 3 = 0.583. Recall@k and precision@k are averaged the same way.

<InteractiveCanvas slug="retrieval-metrics-at-k" />

**What this shows.** One ranked list of 10 chunks with 4 relevant ones, at ranks 2, 3, 6 and 9. Moving k changes how much of the list counts. Recall can only go up as k grows, precision usually goes down, and reciprocal rank depends only on the first relevant hit.

**Try this.** First, move k from 1 to 2. Recall goes from 0 to 0.25, precision from 0 to 0.50, and reciprocal rank jumps to 0.5, where it stays for every larger k. Second, move k from 3 to 5. Recall stays at 0.50, because ranks 4 and 5 hold no relevant chunk, while precision falls from 0.67 to 0.40. Then find the smallest k where recall reaches 1.00: it is 9, and precision there is 4 / 9 = 0.44.

**What changed.** Each step in k adds one chunk to the count. If that chunk is relevant, recall and precision both rise; if it is noise, recall stays flat and precision falls.

**Limits of the model.** The canvas shows one question with yes or no relevance. A real evaluation averages many questions, and some chunks are only partly useful. It also ignores cost: a bigger k means a longer prompt for every request.

## Which number to report

For RAG, recall@k is usually the first number to watch, with k equal to the number of chunks you really put in the prompt. A missing chunk becomes a missing fact. Precision@k matters second: noise costs tokens, adds latency, and can distract the model. MRR matters when only the top result counts, for example when the interface shows one source link.

The trade-off is k itself. In this example, a bigger k raises recall but each extra chunk costs tokens. If one chunk is about 300 tokens, going from k = 3 to k = 10 adds about 2,100 tokens to every request. A common senior answer is to retrieve more (say 20), rerank, and send fewer (say 5). Then recall@20 measures the retriever and recall@5 measures what the model really sees.

Sometimes relevance is not yes or no. One chunk answers the question fully; another only gives background. **<GlossaryTerm term="nDCG" definition="Normalised discounted cumulative gain: a ranking score that uses graded relevance and gives less credit to useful results that appear lower in the list." />** handles this. Each result gets a grade, for example 2 for fully relevant, 1 for partly relevant and 0 for not relevant. Each grade is divided by the base-2 log of its rank + 1, so lower positions count less. The discounted grades are summed, and the sum is divided by the best possible sum for that question. The result is between 0 and 1. Use nDCG when your labels have grades and the order of the top results matters; it costs more labelling time than yes or no labels.

## Failure modes and debugging

**Labels go stale.** If labels are chunk ids and you change chunk size, the ids point at different text. Re-label, or label by document and position, after any chunking change.

**The golden set is too small.** With 10 questions, one question moves mean recall by up to 0.10. Do not celebrate a change from 0.80 to 0.85 on 10 questions; read the questions that changed.

**Questions copy the documents.** If you write test questions while reading the chunks, you reuse their exact words, and retrieval looks better than it is with real users. Take questions from real logs when you can.

**The mean hides the worst cases.** A mean recall of 0.9 can hide one question type that always fails. Always print the questions with recall 0 next to the mean.

<Callout type="warning" title="Use the same k as production">
If the eval uses k = 10 and the service sends 3 chunks to the model, your recall number describes a system you do not run. Report recall at the k you really use.
</Callout>

## In the interview

Retrieval metrics come up in the project deep dive ("what was your recall?") and in system design ("how would you evaluate this before launch?"). The interviewer wants the formula, a real number, and a reason for your k. Answer each practice question aloud first, then open it and compare.

<FaqGroup title="Practice questions">
<FaqItem question="Your recall@5 is 0.90, but users still complain about wrong answers. What do you check next?">

Recall says the right chunks reach the model, so I look after retrieval. First I check faithfulness: are the answer's claims supported by the chunks it was given? Then I check precision@5: if only 1 of 5 chunks is useful, the model may be distracted by the 4 noisy ones. I also read the questions with the lowest recall, because a mean of 0.90 can hide a whole question type at 0. Finally I check whether the golden set looks like real traffic, since complaints come from real questions.

**Follow-up probes:**

- How would you measure faithfulness without reading every answer?
- What if the complaints come from a question type that is not in your golden set?

</FaqItem>
<FaqItem question="When would you report MRR instead of recall@k?">

I report MRR when the first useful result is what the user sees or what the system acts on. Examples are a search box that shows one top link, or an agent that only reads the first result. Recall@k is better for RAG with several chunks in the prompt, because the model can use a relevant chunk at rank 3 as well as one at rank 1. I usually report both: recall@k for coverage and MRR for ordering. If MRR drops while recall stays the same, the right chunks are still found but they moved down, which points at the ranking or the reranker.

**Follow-up probes:**

- What would nDCG add that MRR does not?
- How would a reranker change each metric?

</FaqItem>
<FaqItem question="How would you build and label a golden set for a new RAG system?">

I start with 50 to 100 questions from real user logs if they exist, or from the people who will use the system. A domain expert labels the relevant chunks for each one, and a second person checks a sample so the labels are consistent. I make sure the set covers every document type and the hard cases, such as questions that need two documents, plus a few with no answer in the documents. I keep the set in version control and re-check the labels whenever the chunking changes.

**Follow-up probes:**

- How do you keep the golden set from going stale as documents change?
- Why include questions that have no answer in the documents?

</FaqItem>
</FaqGroup>
