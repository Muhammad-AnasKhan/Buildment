## What you will have at the end

At the end of this chapter, your `rag-agent-service` repository can measure itself. You will have three metric functions with their own tests, and a golden set of 12 Bustan Books (a fictional online bookshop) questions with labelled source chunks. You will also have a command that prints recall@3, precision@3 and MRR, and a test that fails when recall or MRR drops below a floor you chose.

Interviewers care about this for two reasons. In the hands-on round, "write recall@k and test it" is a common small task, and the edge cases (k larger than the list, nothing relevant) are where candidates slip. In the project deep dive, one of the strongest things you can say about a RAG project is: "the eval runs as a test on every pull request, and it fails below 0.90 recall."

**What you need.** Your laptop, Python 3.11 or later, and the repository from chapter 3.5 with its tests passing. Nothing new to download: you only use pytest, which you installed in chapter 1.4. Plan about two hours, including time to read your own chunks and label them.

## Decide the edge cases first

A metric function is easy to write and easy to get subtly wrong. Write down what each edge case should do before you write code. The tests below check exactly these rules.

**k is 0 or negative.** Raise `ValueError`. A top 0 makes no sense, and silently returning 0 would hide a bug in the caller.

**k is larger than the list.** If the retriever returns only 2 chunks and k is 5, look at the 2 you have, and still divide precision by k. That is the definition of precision@k, and it correctly punishes a retriever that returns too little. Dividing by the length of the list instead is the most common mistake; one test catches it.

**The relevant set is empty.** Return 0.0 from all three functions. Nothing relevant can be found. In this golden set every question has at least one relevant chunk, and the regression test checks that, so an empty set means a labelling mistake.

**The same id appears twice in the list.** Count each relevant id once. Turning the top k into a set before you count handles it.

**The mean of an empty list.** Raise `ValueError`. An empty golden set is a bug, and a mean of 0 would hide it.

For `reciprocal_rank`, walk the list from rank 1 and return 1 divided by the rank of the first id that is in the relevant set, or 0.0 if none is. `evaluate` passes it only the top k, so the mean is MRR at k.

Here is the golden set. Each line is one JSON object with an `id`, the `question` a customer might ask, and the `relevant` chunk ids, which come from the documents in `data/docs`. Questions 3, 7 and 12 need two chunks, because their answer crosses a chunk boundary or two parts of a policy.

{"id": "q04", "question": "Where can I find the tracking number for my parcel?", "relevant": ["shipping#1"]}
{"id": "q05", "question": "Who pays customs fees and import taxes?", "relevant": ["shipping#2"]}
{"id": "q06", "question": "How many days do I have to return a book?", "relevant": ["returns#0"]}
{"id": "q07", "question": "My book arrived damaged. Can I send it back?", "relevant": ["returns#0", "returns#1"]}

Do not trust these labels blindly. Chunk ids depend on your documents and your chunk size and overlap, so you check every label against your own chunks in step 3. Labelling is the slow part of any eval, and it is the part interviewers ask about: who labelled it, how, and how you keep it current.

## The acceptance tests

These are the tests your code must pass. Copy them exactly. The first file uses the ranked list from chapter 5.2, with relevant chunks at ranks 2, 3, 6 and 9, so you can check every number against your hand calculation.

```python
import pytest

from app.metrics import mean, precision_at_k, recall_at_k, reciprocal_rank

# The ranked list from chapter 5.2: relevant chunks at ranks 2, 3, 6 and 9.
RANKED = [f"c{i}" for i in range(1, 11)]
RELEVANT = {"c2", "c3", "c6", "c9"}


@pytest.mark.parametrize("k, expected", [(1, 0.0), (3, 0.5), (5, 0.5), (10, 1.0)])
def test_recall_at_k(k, expected):
    assert recall_at_k(RANKED, RELEVANT, k) == pytest.approx(expected)


@pytest.mark.parametrize("k, expected", [(1, 0.0), (3, 2 / 3), (5, 0.4), (10, 0.4)])
def test_precision_at_k(k, expected):
    assert precision_at_k(RANKED, RELEVANT, k) == pytest.approx(expected)


def test_reciprocal_rank_uses_the_first_relevant_hit():
    assert reciprocal_rank(RANKED, RELEVANT) == pytest.approx(0.5)
    assert reciprocal_rank(["c2", "c1"], RELEVANT) == pytest.approx(1.0)
    assert reciprocal_rank(["c1", "c4"], RELEVANT) == 0.0


def test_mrr_over_three_queries():
    rrs = [reciprocal_rank(RANKED, RELEVANT), 1.0, 0.25]
    assert mean(rrs) == pytest.approx(0.583, abs=0.001)
```

The same file continues with the edge cases you decided above.

```python
def test_k_larger_than_the_list_still_divides_by_k():
    assert recall_at_k(["c2", "c3"], RELEVANT, 5) == pytest.approx(0.5)
    assert precision_at_k(["c2", "c3"], RELEVANT, 5) == pytest.approx(0.4)


def test_empty_relevant_set_scores_zero():
    assert recall_at_k(RANKED, set(), 3) == 0.0
    assert precision_at_k(RANKED, set(), 3) == 0.0
    assert reciprocal_rank(RANKED, set()) == 0.0


@pytest.mark.parametrize("k", [0, -1])
def test_k_must_be_positive(k):
    with pytest.raises(ValueError):
        recall_at_k(RANKED, RELEVANT, k)
    with pytest.raises(ValueError):
        precision_at_k(RANKED, RELEVANT, k)


def test_mean_of_nothing_is_an_error():
    with pytest.raises(ValueError):
        mean([])
```

The second file is the regression eval. Every test in it is marked `eval` by the `pytestmark` line, using the marker you registered in `pyproject.toml` in chapter 1.4.

```python
import pytest

from app.evaluate import build_store, evaluate, load_golden
from app.ingest import load_chunks

# Floors set a little below the scores on the day the golden set was made.
K = 3
RECALL_FLOOR = 0.90
MRR_FLOOR = 0.85

pytestmark = pytest.mark.eval


@pytest.fixture(scope="module")
def store():
    return build_store("data/docs")


@pytest.fixture(scope="module")
def golden():
    return load_golden("data/golden.jsonl")
```

It ends with one data check and two quality floors.

```python
def test_golden_set_is_well_formed(golden):
    assert len(golden) >= 10
    ids = [row["id"] for row in golden]
    assert len(ids) == len(set(ids)), "golden ids must be unique"
    known = {chunk.id for chunk in load_chunks("data/docs")}
    for row in golden:
        assert row["question"].strip(), row["id"]
        assert row["relevant"], f"{row['id']} has no relevant chunks"
        missing = set(row["relevant"]) - known
        assert not missing, f"{row['id']} points at unknown chunks {missing}"


def test_recall_does_not_drop(store, golden):
    scores = evaluate(store, golden, k=K)
    assert scores["recall_at_k"] >= RECALL_FLOOR, scores


def test_mrr_does_not_drop(store, golden):
    scores = evaluate(store, golden, k=K)
    assert scores["mrr"] >= MRR_FLOOR, scores
```

## Choosing the floors

The floors in the test are a decision, and you should be able to defend them. The scores on the day this golden set was made were 0.958 recall and 0.917 MRR. The floors sit a little below: 0.90 and 0.85.

Why not exactly at the current score? Because a floor at the current score fails on any small drop, including a harmless change that moves one first hit from rank 1 to rank 2. Why not far below, say 0.70? Because then a real drop passes. With 12 questions, one single-chunk question that loses its relevant chunk takes recall down by about 0.08, from 0.958 to 0.875, which is below 0.90. So this floor fails on the loss of even one question, which is what you want with a deterministic retriever.

With a real model in the loop (for example, a model judge for faithfulness), scores move a little between runs even when nothing changed. Then you need more margin, more questions, or the mean of several runs. When quality improves for real, raise the floors in the same pull request, so the gain cannot quietly slip away. Never lower a floor just to make a red run green without writing down why.

## Running the eval in CI

On your laptop you run the eval by hand. In a team, your CI service runs it on every pull request. The setup does not depend on which CI service you use: it is a job that checks out the code, installs the requirements, and runs commands. pytest exits with a non-zero code when any test fails, and a CI service treats a non-zero exit as a failed check. Make that check required, and a failing eval blocks the merge.

A common layout is two steps, so the fast unit tests report first:

```bash
pip install -r requirements.txt
pytest -m "not eval" -q
pytest -m eval -q
```

Here the eval is free and fast, so it runs on every pull request. In a real system with a model judge, the eval calls a paid model, takes minutes and needs an API key. Teams then run it on pull requests that touch prompts, chunking or retrieval code, and nightly on the main branch. The key lives in the CI service's secret store, never in the repository. Save the printed scores as a build artifact as well, so you can see the trend over weeks and not only pass or fail.

<Callout type="tip" title="Print the failing questions">
When a floor fails, the mean tells you that quality dropped but not where. A useful next step for your capstone is to print the ids of questions with recall 0 next to the scores.
</Callout>

## Verify

You have finished when `pytest -q tests/test_metrics.py` shows 15 passed, `python -m app.evaluate` prints three scores, and `pytest -m eval -q` shows 3 passed.

Now break it on purpose, to see the eval do its job. Imagine a teammate shrinks the embedding to save memory. In `build_store`, change `HashingEmbedder()` to `HashingEmbedder(dim=16)` and run the eval again. With only 16 buckets, many different words land in the same bucket, so unrelated chunks start to look similar.

```text
$ pytest -m eval -q
(output shortened)
E       AssertionError: {'recall_at_k': 0.8333333333333334, 'precision_at_k': 0.3333333333333333, 'mrr': 0.5277777777777778}
E       assert 0.8333333333333334 >= 0.9
FAILED tests/test_eval_regression.py::test_recall_does_not_drop - AssertionEr...
FAILED tests/test_eval_regression.py::test_mrr_does_not_drop - AssertionError...
2 failed, 1 passed, 18 deselected in 0.52s
```

No unit test failed, and the code still runs. Only the eval noticed that MRR fell from 0.917 to 0.528. That is the whole point of this chapter. Change `dim` back and confirm the eval passes again.

If something else fails, these are the two most likely causes.

**`points at unknown chunks`.** The data check failed, for example `q08 points at unknown chunks {'returns#4'}`. A label names a chunk id that your documents do not produce. This happens after you change a document, the chunk size or the overlap. Print your chunk ids again (step 3) and fix the label. Every chunking change means a re-labelling check.

**`test_k_larger_than_the_list_still_divides_by_k` fails.** Your precision divides by the length of the list, not by k. With a list of 2 and k = 5 you get 1.0 when the answer is 0.4. Divide by k.

If you see `ModuleNotFoundError: No module named 'app'` or a missing `data/golden.jsonl`, you are running from the wrong folder. Run every command from the `rag-agent-service` folder, because the paths in the tests are relative to it.
